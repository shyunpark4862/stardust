# O3: minimize(Nelder–Mead, BFGS, L-BFGS-B)의 속도 (scipy 1.18.1과 비교)

`bench/optimize/o3/speed.py`로 쟀다(2026-11-20, Apple M4 Pro, scipy 1.18.1·numpy 2.5.4, Accelerate). 시간은 ms, 여러 번(많아야 5번, 2초를 넘으면 그만) 가운데 가장 빠른 값이다. 원래 출력은 `speed.log`, 값 전체는 `speed.json`이다.

- 문제: scipy의 일반화된 Rosenbrock(`rosen`, `rosen_der`), n = 2, 10, 100, 1000(L-BFGS-B는 10⁴도), x0 = (−1.2, 1, −1.2, 1, …). 함수는 각 라이브러리의 배열로 썼다(sd는 sd, scipy는 numpy). BFGS·L-BFGS-B는 해석적 기울기와 차분(`jac=None`: scipy의 절대 간격 '2-point')이다. 큰 n은 반복 상한(`max_iter`, 두 라이브러리에 같게)을 두었다.
- "반복당 자기 비용"은 전체 시간에서 사용자 함수(`fun`, `jac`) 안의 시간을 빼고 반복 수로 나눈 것이다. 방법 자체의 비용(선 탐색, 갱신, 차분의 고리, 콜백을 부르는 고리)이다.
- 걸음이 scipy와 같으므로(O9) 모든 줄에서 반복 수, `nfev`, `njev`, `status`가 같다.
- 1스레드 / 10스레드를 함께 적었다. 사용자 함수가 Python이라 병렬은 Accelerate의 큰 행렬곱(BFGS n = 1000) 안뿐이다.

- 작은 n(2–100)에서 반복당 자기 비용은 scipy의 1/2–1/20이다(BFGS n = 2: 1.0 µs 대 22 µs, Nelder–Mead n = 10: 0.3 µs 대 6.7 µs). scipy는 반복마다 Python에서 numpy 연산, `ScalarFunction`의 기억, 선 탐색의 Python 코드를 거치고, 이 라이브러리는 반복 전체가 C++이고 콜백만 Python이다. L-BFGS-B는 scipy도 반복의 계산이 C라서 차이가 작다(2.3 µs 대 7.8 µs; scipy의 몫은 setulb를 부르는 Python 고리와 `ScalarFunction`이다).
- 차분의 기울기에서 차이가 더 크다(L-BFGS-B n = 1000: 반복당 0.35 ms 대 4.3 ms, BFGS n = 100: 0.046 ms 대 0.49 ms). scipy는 `approx_derivative`가 변수마다 numpy 배열을 복사하고 Python에서 나눈다. 이 라이브러리는 차분의 고리가 C++이다(사용자 함수를 n번 부르는 비용은 위의 자기 비용에 들지 않는다).
- Nelder–Mead n = 1000: 0.14 ms 대 0.76 ms. 반복마다의 일은 무게중심(N² 덧셈, numpy와 같은 순서)이다. 정렬은 행 번호만 옮기고(scipy는 `np.take`로 단체 전체를 복사한다), 멈춤 판정은 처음으로 허용오차를 넘는 값에서 그친다(scipy는 N²의 차이를 모두 만든다; 판정의 결과는 같다).
- BFGS n = 1000: 9.4 ms 대 11.5 ms(10스레드 5.1 대 7.2). 둘 다 H를 scipy의 식대로 n³의 행렬곱 두 번으로 갱신하므로(호출점이 비트까지 같으려면 그래야 한다) 시간의 대부분이 같은 Accelerate dgemm이다. 10스레드가 빨라지는 곳은 이것뿐이다(O0의 기준선과 같다). n²의 2계수 갱신으로 바꾸면 크게 줄겠지만 끝자리가 scipy와 갈린다(O61: O6에서 다시 본다).
- L-BFGS-B n = 10⁴: 0.353 ms 대 0.369 ms. 같은 C 알고리즘이고 BLAS 호출도 같아 시간이 거의 같다.
