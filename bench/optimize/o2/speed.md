# O2: 스칼라 근·최솟값과 배치 함수의 속도 (scipy 1.18.1과 비교)

`bench/optimize/o2/speed.py`로 쟀다(2026-11-20, Apple M4 Pro, scipy 1.18.1·numpy 2.5.4). 시간은 ms, 여러 번(많아야 5번, 2초를 넘으면 그만) 가운데 가장 빠른 값이다. 원래 출력은 `speed.log`, 값 전체는 `speed.json`이다. 다른 작업이 돌던 때라(부하 5–9) 작은 시간은 몇 %씩 흔들린다.

- 스칼라 문제: sin x − x/2(APS 1, 구간 (π/2, π), x0 = 2)와 x³ − 2x − 5(Chandrupatla 1, 구간 (2, 3), x0 = 2.5)의 근, eˣ − 5x의 최솟값(구간 (0, 1, 3), 경계 (0, 3)). 사용자 함수는 `math`로 쓴 같은 Python 함수다.
- "호출당 자기 비용"은 전체 시간에서 f 안의 시간을 빼고 f의 호출 수로 나눈 것이다(방법 자체의 비용: 걸음의 계산과 콜백을 부르는 고리). newton·halley의 `fprime`·`fprime2`는 따로 재지 않아 자기 비용에 든다(두 라이브러리 모두).
- 배치 문제: O0의 기준선과 같은 x³ − 2x − c = 0(구간 (0, 3), `bracket_root`는 0에서)과 (x − c)² + 0.01cx⁴의 최솟값(구간 (−1, 0.5, 11), `bracket_minimum`은 0에서)이고, c = linspace(1, 10, n)은 원소마다 `args`로 넘긴다(O39). 사용자 함수는 각 라이브러리의 배열로 썼다(sd는 sd, scipy는 numpy; 같은 식 `x**3 - 2 * x - c`).
- 배치의 "값 하나당 자기 비용"은 f 밖의 시간을 모든 원소의 함수값 수(`nfev`의 합)로 나눈 것이다.
- 1·10스레드는 프로세스마다 `sd.set_num_threads`로 바꿨다. 커널은 1스레드이고 10스레드에서 달라지는 것은 사용자 함수 안의 sd 연산(10⁵ 이상의 `x**3` 등)뿐이다.

- f의 호출 수와 원소마다의 `nfev`가 scipy와 같다(같은 걸음).
- 원소의 함수값 하나에 커널이 쓰는 시간은 6–12 ns다(`args`를 남은 원소로 모으는 것을 넣어; 크기에 거의 상관없다). scipy는 반복마다 numpy로 마스크를 만들고 배열(`args` 포함)을 줄이고 복사하므로 작은 배치에서 47–105 ns, 10⁵ 이상에서 7–32 ns다. 10⁶ 원소의 전체 시간은 1스레드에서 find_root 2.3배, find_minimum 2.6배, bracket_root 1.4배 빠르고 bracket_minimum은 비슷하다(64 ms 대 66 ms). 10스레드에서는 사용자 함수의 sd 연산이 나뉘어 3.1배, 4.9배, 2.0배, 1.7배다.
- 원소 하나의 상태(find_root는 double 10개)를 한곳에 두고 반복마다 원소를 두 번 지나간다(점과 `args` 쓰기, 갱신·판정·줄이기·다음 걸음). 상태를 필드마다 따로 둔 배열은 10⁶ 원소에서 지나갈 때마다 열 개 넘는 흐름을 메모리에서 읽어 같은 계산이 4–5배 느리다.
- 원소마다 `root_scalar`(brentq)를 부르는 고리는 원소 하나에 6.4 µs(scipy의 `brentq` 7.6 µs)다. 배치는 10⁴ 원소에서 그 1/46이다(1.39 ms 대 64.4 ms).
