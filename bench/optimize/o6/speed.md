# O6: sd.optimize 전체의 속도 (scipy 1.18.1과 비교, 고치기 전과 뒤)

`bench/optimize/o6/speed.py`로 쟀다(2026-11-20, Apple M4 Pro, scipy 1.18.1·numpy 2.5.4, Accelerate). O1–O5 벤치의 문제와 크기를 그 스크립트의 코드 그대로 돌리고(같은 문제, 같은 재는 규칙), 거기 없던 `check_grad`, `least_squares`의 3점 차분과 경계, L-BFGS-B와 Nelder–Mead의 경계를 더했다. 값 전체는 `speed_before.json`(O5 커밋 1f995c9의 커널), `speed_after.json`(O6의 변경 뒤)이다.

- 시간은 ms, 여러 번(많아야 5번, 2초를 넘으면 그만) 가운데 가장 빠른 값이다. 1스레드 / 10스레드를 함께 적었다(스레드 수마다 프로세스를 따로 띄운다: `VECLIB_MAXIMUM_THREADS`, `sd.set_num_threads`).
- "own"은 사용자 함수 밖의 시간(방법 자체의 비용)을 단위로 나눈 것이다: 반복 방법은 반복 하나(ms), 스칼라는 f 호출 하나(µs), 배치는 함수값 하나(ns). 1스레드 값이다.
- 사용자 함수는 O1–O5처럼 각 라이브러리의 배열로 썼다(sd는 sd, scipy는 numpy). 그래서 전체 시간의 비는 두 라이브러리의 배열 연산 속도도 반영한다. 방법끼리의 비교는 own이 맞다.
- `least_squares('lm')`과 `root('lm')`의 "고치기 전"은 축약 없는 lmder(nls의 빌드)다. 고친 뒤는 scipy의 빌드(O95)라 계산이 다르다. BFGS의 "뒤"는 O(n²) 갱신(O99)이라 걸음이 scipy와 반올림만큼 다르다(반복 수가 조금 다를 수 있다).

## O95(비트 동일)로 느려진 곳

- `least_squares('lm')`은 scipy처럼 m × n의 J에 MINPACK의 피벗 QR을 한다(전에는 LAPACK의 블록 QR 뒤 n × n). m ≫ n에서 반복당 비용이 커졌다: (10³, 10) 0.057 → 0.077 ms, (10⁵, 10) 3.96 → 6.47 ms, (10⁴, 100) 6.57 → 17.7 ms(10스레드 7.8 ms). 모두 아직 scipy보다 빠르다(0.088, 6.87, 36.8 ms). 남은 비용은 MINPACK 순서의 합 사슬(열 노름, 반사의 내적, Q^T f)과 m × n 행렬을 단계마다 두 번 지나가는 메모리 흐름이다.
- m = n에서는 거꾸로 빨라졌다(QR 두 번이 한 번이 됨): m = n = 40 own 0.063 → 0.035 ms(scipy 0.051), `root('lm')` n = 100 0.172 → 0.114 ms(scipy 0.169).

## 아직 scipy보다 느리거나 비슷한 곳

- `root` n = 10(hybr, lm 차분): 전체 시간이 scipy의 1.00–1.10배다. own은 거의 같다(0.98–0.99 µs 대 0.92–0.94 µs). 차이는 사용자 함수(이쪽은 sd 배열 연산, scipy는 numpy)와 호출 하나의 고정 비용(새 `sd.ndarray` 하나, 약 0.1 µs)이다.
- `nnls` (100, 10): 11.8 µs 대 8.2 µs. 커널은 7.8 µs로 같고, 차이는 Python 층(입력 확인, `OptimizeResult`)이다.
- 큰 `lsq_linear`·`nnls`, L-BFGS-B n = 10⁴: 같은 LAPACK·BLAS 호출이거나 같은 C 알고리즘이라 같거나 조금 빠르다. 비트를 지키며 줄일 곳이 없다.
- `least_squares` 'trf' m = n = 40: own 0.077 대 0.084 ms. 반복의 대부분이 40 × 40의 LAPACK QR(18 µs)과 80 × 40의 SVD(47 µs)이고 그 결과가 비트를 정한다.

## 비트를 바꾸는 후보 (O94: 재서 물었다)

| 후보 | 잰 것 | 이득 | 결과의 차이 | 결정 |
|---|---|---|---|---|
| BFGS: H를 O(n²)로 갱신 | rosen, own/반복 1스레드 (10스레드) | n = 100 0.022 → 0.0062 ms, n = 300 0.29 → 0.036, n = 1000 8.8 (4.8) → 0.29 (0.28), n = 2000 83 (40) → 1.7 (1.5) | 아래 | 넣었다(O99) |
| least_squares 'trf': 경계 없을 때(dh = 0) SVD를 [Rh; 0](2n × n) 대신 Rh(n × n)에 | own/반복 | m = n = 40 0.078 → 0.074 ms, (200, 100) 0.88 → 0.85 ms | nls의 'trf'도 같은 커널이라 nls의 비트도 바뀐다 | 넣지 않는다(O100) |

BFGS의 O(n²) 갱신(넣은 것; n ≥ 2에서 v = Hy, H − ρ(s vᵀ + v sᵀ) + (ρ² yᵀv + ρ) s sᵀ, (i, j)와 (j, i)를 같은 식으로 계산해 H가 비트까지 대칭; n = 1은 scipy의 곱의 꼴, O102)을 scipy(O3까지의 sd와 같다)와 견준 것(MGH 110경우와 Rosenbrock n = 2, 10, 50, 100, 114경우): x가 비트까지 같음 13, 반복 수와 nfev가 같음 80, status가 같음 113, x가 상대 10⁻⁶ 안 89. 기록된 113번(`tests/optimize/test_minimize.py`)에서 해석적은 status 112·x 10⁻⁶ 안 94·f 10⁻⁸ 안 102, 차분은 107·79·88이고, 수렴한 실행은 모두 ‖g‖∞ ≤ gtol이다. status가 다른 것은 scipy가 수렴하고 이쪽이 같은 최솟값 근처에서 status 2(선 탐색이 걸음을 못 찾음)로 멈춘 것이다. n = 1까지 펼친 식으로 하면 Chebyquad n = 1의 10x0·100x0이 H − 2H + H + s/y의 상쇄(s/y ≪ H)로 곡률을 잃어 반복 1–2번 만에 멈췄다(status 해석적 111, 차분 105): 그래서 n = 1은 곱의 꼴이다. 더 큰 n에서도 극단적인 척도(Brown almost-linear 100x0)에서는 scipy와 다를 수 있다. `hess_inv`는 갱신 한 번 뒤에 scipy의 것과 상대 1.7×10⁻¹⁵ 안이다(110경우). 끝의 `hess_inv`는 경로가 반올림만큼 갈려 상대 차이의 중앙값이 4×10⁻⁹, 큰 것은 O(1)이다.
