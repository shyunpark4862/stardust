# 난수 영역 설계 (sd.random)

> 상태: **T3 완료·승인** (2026-11-15). 결정은 §1(R1–R16; R12–R16은 추천안, 사용자 위임 2026-11-22).

`sd.random`은 난수의 바탕이다. 분포별 표본은 여기가 아니라 `sd.stats`의 각 분포(`X.sample(shape, rng=rng)`, [stats.md](stats.md) §4)에 있다.

- 공개 함수와 시그니처는 [docs/api/random.md](../api/random.md)에 있다.
- 쓰는 곳: `sd.stats`의 표본, `sd.htest`의 순열·부트스트랩, frame의 표본 뽑기·섞기, 테스트 데이터.

## 1. 결정 기록 (사용자, 2026-11-15)
| 번호 | 결정 |
|---|---|
| R1 위치 | 별도 모듈 `sd.random`. stats 안이 아니다 |
| R2 생성기 | **계수기형 자체 설계**: 원소 번호에서 바로 난수를 만든다. 모든 연산이 병렬이고 스레드 수와 무관하게 같은 값이다. numpy와 값은 다르다(numpy의 비트 호환 대신 고른 것) |
| R3 API | Generator 객체: `rng = sd.random.default_rng(seed)`. 전역 함수와 전역 상태가 없다 |
| R4 범위 | 생성기 + 기본 도구만: `random`([0, 1) 균등), `integers`, `choice`, `permutation`. 분포별 표본은 stats에 (R1과 함께 정함: 중복이 없고, 매개변수 규칙이 하나다). `shuffle`은 R9로 뺐다 |
| R5 생성기 (T3, 2026-11-15) | Philox4×64-10 (§2) |
| R6 시드 | int(0 이상, 크기 제한 없음)·그런 int의 시퀀스·None(OS 엔트로피). 키는 numpy SeedSequence와 같은 해시로 만든다(그래서 키는 numpy Philox의 키와 같다; 값은 계수기 쓰는 법이 달라 다르다) |
| R7 spawn·상태 | `spawn(n)`(독립 생성기), 상태 읽기·쓰기(`state`), 피클·복사 모두 |
| R8 공유 | 한 Generator를 여러 Python 스레드가 함께 쓰면 호출마다 자기 구간을 원자적으로 예약한다(키와 위치는 네이티브 상태 `_core.random.State`에 있고, 예약은 그 안의 스핀 잠금 아래 한 번의 네이티브 호출이다, R16). 깨지지 않고 같은 난수를 두 번 쓰지 않지만, 어느 스레드가 어느 구간을 받는지는 실행 순서에 따른다. 재현하려면 스레드마다 `spawn` |
| R9 섞기 | `shuffle` 없이 `permutation`만. stardust에는 인자를 제자리에서 바꾸는 함수가 없다(값을 바꾸는 것은 `out=`, `+=`, 인덱스 대입). 제자리가 필요하면 `x[...] = rng.permutation(x)`. 방법은 재서 정하고, 결과는 스레드 수와 무관하다 |
| R10 인자 | `integers`의 `low`·`high`는 int 또는 int64 배열이고 `shape`와 함께 브로드캐스트한다(numpy와 같은 규칙). `choice`의 `p`는 음수·NaN이 없고 합이 1에서 sqrt(eps) 안이어야 하며(numpy와 같다), 합으로 나눠 쓴다 |
| R11 기본값 (T3 승인, 2026-11-15) | `integers`의 `shape=None`은 `low`·`high`를 브로드캐스트한 모양이다(둘 다 스칼라면 Python `int`). `default_rng`에 Generator를 주면 같은 객체를 그대로 돌려준다: 시드든 Generator든 `rng = sd.random.default_rng(rng)` 한 줄로 받고, 넘긴 생성기의 상태가 그대로 이어진다(복사본을 주면 같은 난수가 반복된다) |
| R12 `random()`의 스칼라 (최적화 2026-11-22) | `shape=None`이면 원소 하나짜리 배열을 만들고 꺼내지 않고, `_k.uniform1_state`가 생성기의 상태에서 위치를 예약해(R16) 블록 하나(계수기 (pos / 4, 0, 0, 0))의 단어로 Python `float`를 바로 돌려준다(`_k.uniform1`은 키와 위치를 받는 같은 계산이다). 8바이트라 메모리 검사도 거르지 않는다. 같은 단어, 같은 변환이라 값이 같다. 호출 비용이 약 1/2–1/4이 되어 numpy의 스칼라와 비슷하다 (추천안, 사용자 위임 2026-11-22) |
| R13 `integers`의 기각 (최적화 2026-11-22) | 범위가 하나인 호출에서 r ≤ 2⁶⁰(기각이 단어 16개에 하나 아래)이면 기각을 그 자리에서 처리하는 고리(따로 컴파일한 함수)다. r > 2⁶⁰이면 원소마다 후보를 쓰고 기각된 원소의 번호를 갈래 없이 모아(64개까지) 첫 추가 블록(단어 0–3)을 넷씩 `philox4`로 만든다. 단어 4부터는 전처럼 블록 하나씩이다. 전에는 기각마다 블록 하나를 지연 시간에 묶여 따로 계산했다(r = 2⁶³ + 1에서 단어 절반). 같은 원소가 같은 단어를 같은 순서로 쓰므로 값이 같다. r = 2⁶³ + 1에서 약 2배 (추천안, 사용자 위임 2026-11-22) |
| R14 가중치 비복원 `choice` (최적화 2026-11-22) | 키 E/p를 모두 만들어 정렬하지 않고, 한 번 훑으며 지금까지의 작은 k개를 쥔다: 처음 k개를 넣고 `nth_element`로 그 가장 큰 키 T를 정한 뒤, 원소는 T보다 작을 때만 받고 받은 것이 k개 더 쌓이면 다시 고른다. 쥔 것이 k개면 키를 다 계산하지 않는다: 이 u(2⁻⁵³의 배수, (0, 1])에서 −log u ≥ 1 − u이므로 1 − u > T·p·(1 + 2⁻⁴⁰)이면 키가 T보다 크다(여유가 log·나눗셈·곱의 반올림을 덮는다). 경주의 앞쪽에서는 E가 작아 이 한계가 빡빡하므로 계산하는 키가 거의 들어오는 키다. 계산한 키는 `race_keys`와 같은 식이고 순서는 (키, 첨자)라 결과가 안정 `argsort(keys)[:k]`와 같다(잘린 키의 동률 포함; 무작위 100문제와 테스트). 10⁵개에서 10³개를 고르는 데 약 3.5–4배 (추천안, 사용자 위임 2026-11-22) |
| R15 Fisher–Yates의 미리 읽기 (최적화 2026-11-22) | `permutation`과 비복원 균등 `choice`의 배열 경로는 n ≥ 2¹⁹이면 걸음 i + 16의 뽑기를 16걸음 앞서 만들고 그 항목을 미리 읽는다(배열이 캐시를 넘으면 걸음마다 임의 접근이다; 10⁷에서 약 1.8배). 캐시 안(10⁵)에서는 미리 읽기가 오히려 느려 쓰지 않는다. 배열 경로의 작업 배열은 0으로 채우지 않고 0 .. n − 1로 바로 채운다. 걸음과 단어가 같아 값이 같고 `choice(n, shape=k, replace=False)`가 `permutation(n)`의 앞 k개라는 관계도 그대로다 (추천안, 사용자 위임 2026-11-22) |
| R16 생성기 상태와 예약 (최적화 2026-11-22) | Generator의 키와 위치는 C++의 `random::State`(`csrc/random/random.hpp`, Python에서 `_core.random.State`)에 있다. `reserve(n)`은 (키, 위치)를 읽고 위치를 n만큼(2⁶⁴ 법) 옮기는 것을 스핀 잠금(`std::atomic_flag`) 아래 한 번에 하고, `set`은 키와 위치를 함께 바꾼다. 그래서 다른 스레드가 `state`를 대입해도 예약은 둘 다 옛 값이거나 둘 다 새 값이다. `Generator._reserve`는 이 호출 하나이고(전에는 Python `threading.Lock` 아래의 세 대입과 튜플), 네이티브 스칼라 커널(`uniform1_state`, stats의 `<분포>_sample1s`)은 상태를 받아 직접 예약한다. Python 잠금(`_lock`)은 `_seq`(시드 수열)를 상태와 함께 읽고 바꾸는 `state`·`spawn`에만 남았다. `_key`는 상태를 읽는 속성이다. 같은 위치, 같은 단어라 같은 시드의 값이 같다(골든 random 141개 그대로). 스칼라 `random()`이 약 2.4배, 스칼라 분포 표본(stats T75)이 약 2배 빨라졌다 (추천안, 사용자 위임 2026-11-22) |

## 2. 생성기 (`csrc/random/philox.hpp`)
- **Philox4×64-10** (Salmon et al., "Parallel random numbers: as easy as 1, 2, 3", SC 2011; Random123). 키(128비트)와 계수기(256비트)에서 64비트 넷을 만드는 함수다. 상태가 없어서 어느 계수기 값이든 바로 계산된다.
- 정확성: Random123의 알려진 답(KAT) 세 벡터와 비트까지 같고, numpy의 Philox와도 같다: 같은 키의 numpy Philox 수열은 우리 수열을 원소 4개(한 블록) 민 것이다(numpy는 계수기 1에서 시작한다. tests/random/test_random.py).
- **블록 넷을 함께**: 한 블록은 곱셈 20번이 이어지는 의존 사슬이라 지연 시간에 묶인다(블록당 약 12 ns). 독립인 블록 넷의 라운드를 섞어 곱셈기를 채운다(`philox4`). 균등 난수 10⁶개 2.98 → 1.14 ms. 블록마다 비트는 같다.

## 3. 결정성: 원소의 부분 수열
- Generator는 키와 위치 `pos`(지금까지 쓴 원소 수)를 든다. 크기 n인 호출의 원소 i는 스트림의 원소 e = pos + i이고, 호출이 끝나면 `pos += n`이다.
- **원소 e의 단어**: 첫 단어는 계수기 (e / 4, 0, 0, 0) 블록의 e mod 4번째 단어다(이웃한 원소 넷이 블록 하나를 나눈다). 기각 표본에 더 필요한 단어는 계수기 (e, j, 0, 0), j ≥ 1 블록에서 차례로 받는다. 두 계수기는 둘째 단어(0과 1 이상)로 갈려서 만나지 않는다.
- 그래서 원소 하나의 값은 (키, e)만으로 정해진다. 작업을 어떻게 나누든, 스레드가 몇 개든 같은 값이다. 호출을 나누어 불러도 앞의 원소들은 같다. 2026-11-22부터 다른 영역은 스레드 수와 무관한 비트를 약속하지 않지만, 이 영역은 이 설계(R2)로 그대로 약속한다. 커널을 빠르게 할 때(R12–R15)도 원소마다 쓰는 단어와 그 순서를 바꾸지 않아, 같은 시드의 값이 판에 따라 바뀌지 않는다.
- 위치의 예약은 생성기 상태의 잠금 안에서 한 번의 네이티브 호출로 한다(R8, R16). 계산은 잠금 밖이다.

## 4. 기본 도구 (`csrc/random/random.cpp`, `src/stardust/random/__init__.py`)
| 함수 | 방법 |
|---|---|
| `random` | 첫 단어의 위 53비트 × 2⁻⁵³ (numpy와 같은 변환). `shape=None`은 배열 없이 `float`를 바로 돌려준다(R12) |
| `integers` | Lemire의 거의 나눗셈 없는 방법(r = high − low, w·r의 위 64비트; 아래 64비트가 2⁶⁴ mod r보다 작으면 기각하고 그 원소의 추가 단어로 다시). 범위가 하나인 흔한 호출은 2⁶⁴ mod r을 한 번만 구한다(범위 2⁶³에서는 원소 절반이 나눗셈을 했다). 그 호출의 기각은 r ≤ 2⁶⁰이면 그 자리에서, 더 크면 모아서 넷씩 블록을 만든다(R13). 64비트 부호 없는 산술이라 int64의 어떤 쌍이든 정확하다 |
| `permutation` | Fisher–Yates. 걸음 i는 원소 pos + i의 단어로 [i, n)을 고른다. 결과 배열 안에서 바로 섞는다(따로 받는 메모리가 없다). **재서 골랐다**: 무작위 64비트 키를 정렬하는 방법(병렬)은 10⁶에서 Fisher–Yates(순차)보다 1스레드 약 2.9배, 10스레드 약 1.3배 느렸다. n이 캐시를 넘으면 Fisher–Yates는 걸음마다 임의 접근이라 정렬 방식(10스레드)이 10⁷에서 1.8배, 3·10⁷에서 2.7배 빨랐다(2026-11-20). 그래도 그대로 둔다(사용자 결정 2026-11-20): 크기에 따라 방법이 바뀌면 `choice(n, shape=k, replace=False)`가 `permutation(n)`의 앞 k개라는 관계가 깨진다. 큰 n은 뽑기를 앞서 만들고 항목을 미리 읽어 그 차이를 줄인다(R15) |
| `choice` 복원 | 균등은 `integers`, 가중치는 누적합(마지막을 1로 나눔)과 `searchsorted(side='right')`(확률 0인 원소는 뽑히지 않는다) |
| `choice` 비복원 | 균등은 Fisher–Yates의 앞 k걸음. k ≤ n/16이면 건드린 항목만 해시 표에 둔다(O(k); 전체를 섞던 처음보다 10⁶개에서 1000개를 고르는 데 수백 배 빠르다). 표는 평평한 열린 주소 표다: 16바이트 칸(키, 값) bit_ceil(2k)개, 빈 칸은 키 −1, 피보나치 해시, 선형 탐사라 채움률이 1/2 이하다. 뽑기는 표와 상관없으므로 16걸음 앞서 만들고 그 두 칸(i와 j의 자리)을 미리 읽어 둔다(prefetch). 노드마다 할당하는 `std::unordered_map`보다 평평한 표가 약 3배, 미리 읽기가 그 위에 약 1.6배 빨랐다(10¹⁰개에서 10⁶개, 2026-11-22). 걸음과 단어가 같아 결과는 비트까지 같다. 그 밖에는 결과 옆에 n개짜리 배열을 두고 섞는다(n ≥ 2¹⁹이면 미리 읽기, R15). 같은 걸음, 같은 단어라서 `choice(n, shape=k, replace=False)`는 `permutation(n)`의 앞 k개다. 가중치는 Efraimidis–Spirakis: 원소마다 E/p(E는 표준 지수)의 작은 k개(확률 0은 inf)를 (키, 첨자) 순서로. 모든 키를 정렬하지 않고 한 번 훑으며 고른다(R14) |
- dtype: 실수는 float64, 정수는 int64.
- **메모리 검사** (API.md §2): 호출이 받는 메모리 전체를 스트림을 움직이기 전에 물리 메모리와 비교한다(`_check_alloc`, `_take`). 결과만 보면 안 된다. 섞기의 작업 메모리가 결과보다 클 수 있다.
  - 비복원 균등 `choice`: 결과 8k바이트에 해시 경로는 원소당 64바이트(상한; 표는 16·bit_ceil(2k)바이트라 32–64바이트), 배열 경로는 8n바이트를 더한다(`_shuffle_bytes`). `permutation(n)`은 8n바이트뿐이다.
  - 배열을 섞는 `permutation(x)`는 섞은 복사본(n × 한 행의 바이트)을, 배열 모집단의 `choice`는 고른 원소(k × 원소 크기, complex는 16바이트)를 더한다.
- **메시지**: `shape`의 `()`와 음수 축은 배열을 만들 때와 같은 문장이다(`0-dimensional arrays are not supported (stardust has no 0-d arrays)`, `negative dimensions are not allowed`). 배열 인자의 dtype이 틀리면 `…, not float64`, 배열이 아니면 `'p' must be an sd.ndarray, not list`다. `sd.stats`의 `sample()`도 같은 `shape` 해석(`_sample_shape`)과 같은 문장을 쓴다. 틀린 호출 모양(인자 개수, 없는 키워드, positional-only를 키워드로)은 `default_rng`만 `_calls.function`이 `default_rng(): …` 꼴로 바꾼다. Generator의 메서드는 Python의 문장 그대로다: 짧은 호출이라 감싸는 비용(약 60ns)을 쓰지 않는다 (사용자 결정 2026-11-20, API.md §2.1).

## 5. 시드 (R6)
- numpy `SeedSequence`(풀 크기 4)를 Python으로 옮겼다(numpy에 기대지 않으려고). 키는 `generate_state(2, uint64)`라 numpy Philox의 키와 같다. `spawn`도 numpy와 같은 키다(spawn_key에 번호를 붙인다). 테스트가 numpy와 비교한다.
- `None`은 `secrets.randbits(128)`이다. `state` 대입의 `entropy`에는 `None`을 받지 않는다(`TypeError`). 대입할 때마다 다른 상태가 되어 "그 상태로 돌아간다"는 약속이 깨지기 때문이다.
