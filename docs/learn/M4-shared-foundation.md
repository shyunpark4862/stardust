# M4. 공통 바닥 정리 (frame을 받을 준비)

> frame(옛 stardust-pandas)이 M5에서 들어올 자리를 만들었다. 스레드풀의 의미를 pandas판에 맞추고, 병렬화 기준값을 영역의 것으로 옮기고, `Buffer`와 `DType`에 frame이 쓸 것을 더하고, 아래 층이 위 층을 알던 곳을 없앴다. **배열과 linalg의 결과는 비트까지 같다**: 골든 7,746개, 1,844개.

## 1. 결과
| 항목 | 결과 |
|---|---|
| 테스트 | 2,430개 통과 |
| 골든 출력 | 배열 7,746개, linalg 1,844개 모두 같음 |
| 성능 | 옛 패키지와 같은 자리 비교: 배열 0.99–1.04, linalg 0.95 (기하평균). 표에 걸린 줄 넷은 프로세스를 여러 번 띄워 보니 회귀가 아니었다 (§7) |
| 컴파일 경고 | 없음 (`-Wall -Wextra -Wpedantic`) |

## 2. 스레드풀: pandas판의 의미로
세 벌의 풀은 핵심(상주 워커, spin 후 대기, atomic 카운터, 호출 스레드 참여, 중첩 금지)이 같았다. pandas판은 M12 이후의 리뷰에서 세 가지를 더 고쳐 두었다. 그것을 가져왔다.

| | 전 (numpy판) | 지금 (pandas판의 의미) |
|---|---|---|
| `available()` | 태스크 밖이고 2스레드 이상 | + **풀이 다른 Python 스레드의 일로 바쁘지 않을 때** |
| `parallel_for`의 GIL | 실제로 병렬로 돌 때만 놓음 | **부르면 언제나 놓음** (직렬로 돌게 되어도) |
| `busy()` | 없음 | 있음 |
| `FirstRow` | 없음 | 있음: 태스크들이 찾은 실패 위치 중 가장 앞의 것 |

- **왜 `available()`이 바쁜 풀을 보는가**: 다른 Python 스레드가 풀을 쓰는 중이면 이 호출의 `parallel_for`는 어차피 호출 스레드 혼자 돈다. 그런데 "나눌 수 있다"고 보고 나눈 알고리즘(조각 계획, 조각별 부분 결과)을 고르면, 나눈 비용만 내고 직렬로 돈다. 바쁘면 처음부터 직렬 알고리즘을 고르는 편이 빠르다. 결과는 같다(결정성 규칙).
- **왜 GIL을 언제나 놓는가**: `parallel_for`를 부른다는 것은 이미 일이 크다는 뜻이다(기준값 판단은 부르는 쪽이 한다). 그 일이 풀이 바빠 직렬로 돌게 되어도 다른 Python 스레드는 돌 수 있어야 한다.
- 배열과 linalg의 작은 호출 경로는 `parallel_for`를 부르지 않는다(기준값을 먼저 본다). 그래서 작은 호출에 GIL을 놓고 잡는 비용이 더해지지 않는다. 같은 자리 비교의 작은 호출 줄(`tiny a + b`, 3×3 linalg)이 그대로인 것으로 확인했다 (§7).
- pandas판의 나머지 셋(`for_chunks`, `Unlocked`, `kChunkRows`)은 가져오지 않았다. frame의 기준값(2¹⁷)과, 비트맵의 바이트를 두 태스크가 함께 쓰지 않게 64의 배수로 맞춘 청크 크기(16K행)에 묶인 **frame의 정책**이다. M5에서 `frame/`으로 간다.

## 3. 기준값은 영역의 것
- 풀 헤더에 있던 `kThreshold`(2¹⁵), `kTaskWork`(2¹²)는 배열이 자기 커널로 잰 값이었다. pandas는 같은 이름에 2¹⁷을 두었다. 한 풀에 한 값을 두면 둘 중 하나는 틀린다.
- 그래서 풀은 태스크를 돌리기만 하고, **언제 나눌지는 영역이 정한다**.
  - 배열: `sd::kParallelThreshold`, `sd::kParallelTask` (`array/parallel_limits.hpp`)
  - frame (M5): `sd::frame::kParallelThreshold` = 2¹⁷
  - linalg: 비용 모델 (`linalg/cost.hpp`). 긴 합만 배열과 같은 값(2¹⁵, 2¹²)을 쓴다.
- **영역마다 같은 이름**으로 둔다(일관성 원칙, DESIGN §1.4). 배열 코드는 이름공간 `sd`에, frame 코드는 `sd::frame`에 있으니 각자 자기 값을 찾는다.

## 4. `Buffer`와 `DType`
- `Buffer::size()`: 데이터의 바이트 수. frame의 Column이 슬라이스 범위를 확인할 때 쓴다(pandas판에 있던 것).
- `DType`에 `String`을 더했다: `{Bool, Int64, Float64, Complex128, String}`.
  - 배열의 dtype 수를 뜻하던 `kNumDTypes`(4)는 `kNumArrayDTypes`로 이름을 바꿨다. 표의 크기(캐스팅 4×4, 원소별 연산 표), dtype 객체 배열이 이것을 쓴다. 이름만 보고 "모든 dtype"으로 잘못 읽지 않게 하기 위해서다.
  - `is_array_dtype(d)`, `itemsize(String) = 0`(바이트는 offsets와 UTF-8 버퍼에 있다), `dtype_name(String) = "string"`.
  - `String`을 더하자 컴파일러가 `switch` 하나를 짚었다(`-Wswitch`): Python 스칼라 → C++ 값 변환. Python 스칼라의 dtype은 문자열일 수 없으므로 도달하지 않는 경우로 적었다.
- **계획과 다르게 한 것**: DESIGN §4.2는 `Datetime64`도 더하기로 했다. 더하지 않았다. 어느 영역에도 그 코드가 없다(pandas에서 Tier 2로 남아 있었다). 쓰는 코드 없이 enum 값만 두면 `switch`마다 "도달하지 않음"만 늘어난다. frame이 구현할 때 더한다.

## 5. 아래 층이 위 층을 알던 곳
- M1에서 `kernels/neon.hpp`를 `base/`로, `kernels/vforce.hpp`를 `accelerate/`로 옮겼다. 이름만 보고 "공용 부품"으로 판단했다. 그런데 두 파일 모두 배열의 연산 정의(`ops::Maximum`, `ops::Exp` …)에 대한 특수화였다. 그래서 `base/`가 `array/kernels/scalar_ops.hpp`를 include하는 역방향 의존이 생겼다.
- 처음 계획(ROADMAP)은 스칼라 변환 규칙을 `base/scalar_cast.hpp`로 내리는 것이었다. 그것으로는 풀리지 않는다: 의존하는 것은 변환 규칙이 아니라 연산자 타입이다.
- **고친 방법**: 배열 코드는 배열로 돌려보냈다.
  - `neon.hpp` → `array/kernels/neon.hpp` (`git mv`, 이력 유지)
  - `vforce.hpp`는 둘로 나눴다. 연산과 무관한 부분(함수 타입, `vvpow`/`vvatan2`의 인자 순서를 맞추는 래퍼, 버퍼에 모아 부르는 strided 실행기)은 `accelerate/vforce.hpp`에 남고, "어느 연산이 vForce로 가는가"의 표는 `array/kernels/vforce.hpp`로 갔다.
- 이제 `base/`, `parallel/`, `accelerate/`는 `array/`를 include하지 않는다 (grep으로 확인).

## 6. BLAS 래퍼
- `matmul`이 직접 부르던 cblas 여섯 개(`ddot`/`zdotu_sub`, `dgemv`/`zgemv`, `dgemm`/`zgemm`)를 `accelerate/blas.hpp`의 템플릿 셋(`blas::dot`, `blas::gemv`, `blas::gemm`)으로 감쌌다. linalg의 `accelerate/lapack.hpp`와 같은 방식이다(float64와 complex128을 템플릿 하나로).
- `matmul.cpp`에서 `if constexpr (cplx)` 분기 세 쌍이 사라졌다.

## 7. 성능
옛 패키지와 통합판을 같은 자리에서 번갈아 2라운드 (`bench/merge/m4/final/table.md`):

| 영역 | 스레드 | 줄 | 통합판/옛 패키지 기하평균 | 10% 넘게 느려짐 | 10% 넘게 빨라짐 |
|---|---|---:|---:|---:|---:|
| 배열 | 10 | 17 | 0.992 | 0 | 0 |
| 배열 | 1 | 17 | 1.040 | 3 | 0 |
| linalg | 10 | 258 | 0.952 | 1 | 40 |
| linalg | 1 | 258 | 0.948 | 0 | 44 |

numpy/scipy 대비 linalg(10스레드, 248줄): 빠름 191, 비슷 48, 느림 9.

**표에 걸린 네 줄은 회귀가 아니었다.** 프로세스를 네 번씩 새로 띄워 번갈아 쟀다 (단위 µs, 15번 중 최솟값/중앙값):

| 줄 | 옛 패키지 | 통합판 |
|---|---|---|
| `f + g` 1스레드 | 194/197, 148/152, 149/151, 148/152 | 148/151, 190/201, 147/192, 147/152 |
| `maximum(f, g)` 1스레드 | 201/202, 146/151, 146/152, 146/148 | 187/190, 196/204, 175/185, 151/172 |
| `eig` (100, 32, 32) 10스레드 | 2576/2600, 2709/2760, 2689/2744, 2785/2846 | 2950/3019, 2662/2700, 2779/2821, 2869/2971 |

- 원소 100만 개의 1스레드 원소별 연산은 **옛 패키지든 통합판이든 프로세스마다 약 148µs 아니면 약 195µs**로 갈린다. M3의 `solve_tridiagonal` 배치와 같은 현상이다. 표 한 번(프로세스 몇 개)은 이 갈림을 회귀로 잘못 읽게 한다.
- `eig` 배치는 두 범위가 겹친다(차이 약 4%, 잡음 안).
- 원인 짐작: 1스레드 연산은 호출 스레드에서 돈다. 그 스레드가 P코어와 E코어 중 어디에 놓이는지, 큰 배열의 페이지가 어떻게 잡히는지에 따라 프로세스 단위로 달라지는 것으로 보인다. 확인하지는 않았다.

## 8. 리뷰 포인트
1. **풀의 의미가 바뀌었다**: 바쁜 풀이면 직렬 경로, `parallel_for`는 언제나 GIL을 놓음. 결과는 같고(골든), 작은 호출 비용도 같다.
2. **기준값은 영역의 것이다**: 같은 이름(`kParallelThreshold`)을 영역마다 자기 이름공간에 둔다.
3. **M1의 판단 하나를 고쳤다**: `neon.hpp`와 `vforce.hpp`는 공용 부품이 아니라 배열 코드였다. 파일 이름이 아니라 무엇에 의존하는지로 층을 정해야 했다.
4. **계획과 다르게 한 것 둘**: `Datetime64`는 더하지 않았다(쓰는 코드가 생길 때). 스칼라 변환 규칙은 `base/`로 내리지 않았다(역방향 의존의 원인이 아니었다).
5. **측정 방법**: 짧거나 메모리에 묶인 호출은 프로세스마다 두 갈래로 갈린다. 표에 걸린 줄은 프로세스를 여러 번 띄워 분포로 확인한다. M5부터 이 확인을 기본 절차로 한다.
6. 다음은 M5(frame 옮기기)다. `for_chunks`, `Unlocked`, frame의 기준값이 `frame/`으로 가고, frame의 pairwise 합이 `base/pairwise.hpp`를 쓰게 된다.
