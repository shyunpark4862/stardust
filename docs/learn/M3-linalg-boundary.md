# M3. linalg 경계 없애기 (1단계 끝)

> 별도 패키지 시절에 생긴 linalg와 배열 사이의 경계를 없앴다. linalg는 이제 `NDArray`를 직접 받고 직접 만든다. 중복이던 `DType`, 변환 규칙, pairwise 합을 한 벌로 줄였다. **결과는 비트까지 같다**: 골든 linalg 1,844개, 배열 7,746개. 일부러 바꾼 것은 결과의 `.base` 하나다.

## 1. 결과
| 항목 | 결과 |
|---|---|
| 테스트 | 2,430개 통과 (M2의 2,424 + 큰 대각 오프셋 6개) |
| 성능 | 측정에서 회귀 둘을 찾아 고쳤다. 같은 자리에서 번갈아 재면 배열은 같고(기하평균 0.99–1.00), linalg는 6–7% 빠르다. 10% 넘게 느려진 줄은 없다 (§6) |
| 골든 출력 | 배열 7,746개, linalg 1,844개 모두 같음 (strides, 메시지 포함) |
| 호출 시간 | 결과 배열 하나에 약 120ns 줄어듦 (§4) |
| 바뀐 동작 | linalg 결과의 `.base`가 내부 블록 객체 → `None` (배열 규칙과 같아짐) |
| 고친 정의되지 않은 동작 | `trace`/`diagonal`의 큰 오프셋에서 부호 있는 오버플로 |

## 2. 경계에 있던 것과 지금
| 별도 패키지 시절 | 지금 |
|---|---|
| `Input`: `PyObject_TypeCheck` → `PyObject_GetBuffer` → format 문자열(`?`, `q`, `d`, `Zd`)로 dtype 판정 → 끝날 때 `PyBuffer_Release` | `is_ndarray`로 확인하고 `NDArray`를 빌린다. 인터페이스(`shape`, `stride`, `batch_shape` …)는 그대로라 호출부는 고치지 않았다 |
| 결과: 128B 정렬 블록(`_OutBlock`) → buffer protocol로 내보냄 → 캐시해 둔 `sd.asarray`로 감쌈 | linalg가 strides를 정하고 배열의 `new_array_strided`가 `NDArray`를 만든다 → `nb::cast` |
| `pyrefs`: `ndarray` 타입, `asarray`, `get_num_threads`, dtype 객체 넷, 결과 타입, `LinAlgError` | 결과 타입과 `LinAlgError`만 |
| 나눌 때마다 Python으로 `get_num_threads()`를 불러 풀 크기를 맞춤 | `parallel::available()` 하나 |
| `dtype=` 인자: 캐시해 둔 dtype 객체와 비교 | 배열의 `dtype_object(DType)`와 비교 (같은 객체) |

### 2.1 strides를 누가 정하나
- 처음 계획(ARCHITECTURE)은 배열에 `new_array_fortran(dtype, batch, m, n)`을 더하는 것이었다. 바꿨다: 배열에는 **strides를 받는** `new_array_strided(dtype, shape, strides, nbytes)`를 더하고, strides 계산은 linalg에 남겼다.
  - 행렬마다 열 우선, 배치 축은 바깥에 C 순서라는 것은 LAPACK이 쓰는 방식에서 나온 **linalg의 정책**이다. 배열이 알 일이 아니다. 배열은 메모리(Buffer)와 플래그만 맡는다.
- **길이 0인 축에서 두 공식이 다르다.** 배열의 `new_array`는 0인 축을 1로 쳐서 그 바깥 strides가 0이 되지 않게 한다(`max(shape, 1)`). linalg는 0을 그대로 곱한다. 골든 출력은 strides도 비교하므로, linalg의 공식을 써야 옛 결과와 같다. 실제로 첫 빌드에서 골든 1,844개가 모두 같았다.

### 2.2 `Py_ssize_t`와 `std::int64_t`
- buffer protocol이 주던 shape과 strides는 `Py_ssize_t*`였다. `NDArray`는 `std::int64_t`다. macOS arm64에서 둘은 크기가 같지만 **타입이 다르다**(`long` 대 `long long`).
- `reinterpret_cast`로 넘기면 동작은 하겠지만, 엄격한 별칭 규칙(strict aliasing) 위반이다. 컴파일러는 `long`과 `long long`을 다른 타입으로 보고 최적화할 수 있다.
- 그래서 linalg 안의 span과 vector 타입 자체를 `std::int64_t`로 바꿨다 (`batch.hpp`, `norms.cpp`, `basic.cpp`).

## 3. 한 벌로 줄인 것
- **`DType`**: linalg가 따로 정의하던 enum(값의 순서도 같았다)과 `itemsize`를 지웠다. `base/dtype.hpp`의 것을 쓴다.
- **float → int64 변환**: linalg의 `saturate_to_int`(분기 셋)와 배열의 `saturate_to_int64`(NEON FCVTZS 명령 하나)는 같은 규칙이다: 0 쪽으로 자르고, 범위 밖은 포화, NaN → 0. 배열의 것을 쓴다. 이 규칙을 `base/`로 내리는 것은 M4다(`base/neon.hpp`의 역방향 의존과 함께).
- **pairwise 합**: 두 구현은 같은 알고리즘이고 항을 가져오는 방식만 달랐다.
  - 배열: 접근자 `get(i)`로 항을 하나씩 읽는다.
  - linalg: 잎(128개)을 버퍼에 먼저 채운 뒤 더한다. 레이아웃과 무관하게 더하는 루프가 하나라 벡터화되는 것이 장점이다 (linalg에서 잰 최적화).
  - 그래서 **비트를 정하는 부분만** `base/pairwise.hpp`로 옮겼다: 트리 모양(`split`), 잎의 합(`leaf`, `leaf_complex`), 긴 합의 병렬 계획과 합치기(`plan`, `combine`). 항을 가져오는 방식은 영역마다 남겼다.
  - 골든에서 배열과 linalg의 모든 합이 비트까지 같다. M4에서 frame의 세 번째 사본도 같은 정의로 바꾼다.
- **`available_here()`**: M2에서 linalg를 위해 공용 풀에 더했지만, 이제 linalg가 `parallel::available()`만 쓰게 되어 다시 뺐다.

## 4. 얼마나 빨라졌나
`bench/merge/m3_boundary.py`, 같은 자리에서 고치기 전과 후 (단위 ns, 7라운드 중 최솟값):

| 호출 | 전 | 후 | 차이 |
|---|---:|---:|---:|
| `inv` 2×2 | 402 | 283 | −119 |
| `solve` 3×3 | 414 | 300 | −115 |
| `cholesky` 3×3 | 312 | 188 | −123 |
| `qr` 3×3 (결과 2개) | 1178 | 935 | −243 |
| `eigh` 3×3 (결과 2개) | 1377 | 1185 | −193 |
| `svd` 3×3 (결과 3개) | 3246 | 3008 | −238 |
| `det` 2×2 (스칼라) | 136 | 137 | +1 |
| `trace` 3×3 (스칼라) | 51 | 48 | −3 |
| `solve` (1000, 3, 3) | 16249 | 15881 | −368 |

- **결과 배열 하나에 약 120ns.** 예상은 약 200ns였다(`asarray` 113ns + 블록 할당·해제 82ns + 기타). 차이는 새로 드는 비용이다: `NDArray`와 그 Python 객체를 만드는 데 약 75ns가 든다. 줄어든 것은 `asarray` 호출, 블록 객체, buffer protocol 왕복이다.
- 스칼라를 돌려주는 함수는 결과 배열을 만들지 않으므로 그대로다. 입력 쪽 절약(`GetBuffer`/`Release` 약 5ns)은 측정 잡음 안이다.
- 3×3 `cholesky`는 40%, `solve`는 28% 줄었다. 작은 행렬에서는 호출 경로가 계산보다 크다는 것이 다시 확인된다.

## 5. 정리 항목 (`docs/design/linalg.md` §10.9, §10.10)
- **고친 것**
  - `trace`/`diagonal`의 오프셋 k가 행렬 밖이면(`k >= n` 또는 `k <= -m`) 빈 대각을 (0, 0)에서 시작한다. 전에는 k = −2⁶³에서 `-k`가, 아주 큰 |k|에서 `r0 * stride`가 부호 있는 오버플로(정의되지 않은 동작)였다. 결과는 우연히 맞았다. 극단값 6개를 테스트로 고정했다.
  - `ldl_unpack`이 LAPACK workspace 몫인 scratch 슬롯 4를 빌려 쓰던 것을 함수 몫의 슬롯 3으로 옮겼다.
  - `conj_if_complex`(네 벌), `parse_mode`(두 벌)를 `ops/common.hpp` 한 곳으로.
- **남겨 둔 것과 이유**
  - `ord` 파서 두 벌: 합치면 에러 종류가 바뀐다(`ord=True`가 한쪽은 TypeError, 다른 쪽은 ValueError). 에러 일관성을 정하는 M6에서 함께 고친다.
  - `check_rhs_rows`: 중복이 아니었다. 구조화된 인자의 행렬은 n×n 모양이 아니라서 다른 메시지가 필요하다.
  - `cond`의 두 번째 패킹: LU가 사본을 덮어쓰므로 필요하다. 없애려면 `lu_factor` 변형이 필요한데, 드문 경로 하나라서 두었다.

## 6. 1단계 보고서: 배열 + linalg

### 6.1 측정에서 찾아 고친 회귀 두 개
`base/pairwise.hpp`로 합친 직후, 옛 벤치마크 스크립트를 그대로 통합판에 돌렸더니(`bench/merge/rerun.sh`, import 대체 모듈 `bench/merge/shim/`) 느려진 줄이 나왔다.

1. **배열의 합이 1스레드에서 약 37% 느려졌다** (`sum(f)` 110 → 152µs, `var(f)` 309 → 390µs).
   - 원인: 배열의 `pairwise_sum`이 `pairwise::tree` → 람다 → `pairwise::leaf` → 접근자 람다의 여러 겹을 거치게 되었고, 잎의 합(원소마다 도는 루프)이 끝까지 인라인되지 않았다.
   - 확인: `reduce.hpp`만 옛것으로 되돌려 같은 자리에서 재면 110µs로 돌아온다.
   - 고침: `pairwise::leaf`, `leaf_complex`에 `[[gnu::always_inline]]`. 결과는 110µs, 비트는 그대로.
   - 교훈: "같은 알고리즘을 한 곳에" 옮기는 것만으로도 성능이 바뀔 수 있다. 골든 출력은 비트만 본다. 성능은 따로 재야 한다.
2. **linalg의 짧은 합이 느려졌다** (`matrix_norm(ord=1)` (1000, 3, 3) 13 → 17µs, `trace` 5.3 → 6.2µs, 1스레드).
   - 원인: 옛 linalg의 `pairwise_sum`에는 "잎 하나면 재귀 호출 없이 바로 더한다"는 빠른 길이 있었다. 합치면서 이것을 트리 호출로 바꿨다. 3항짜리 합이 행렬마다 세 번이라 재귀 함수 호출 비용이 드러났다.
   - 고침: 빠른 길을 되살렸다. 두 줄 모두 옛 값과 같아졌다.

### 6.2 기준선과 다르게 보였지만 회귀가 아니었던 것
- M0 기준선(다른 날 잰 값)과 비교하면 배열의 1스레드 원소별 연산 세 줄(`f + g`, `maximum`, `ft + 1.0`)이 1.3–1.4배 느려 보였다.
- 옛 패키지와 통합판을 **같은 자리에서 번갈아** 재면 차이가 없다 (`f + g` 190 대 185µs). 옛 프로젝트의 최종 보고서 값(197µs)과도 맞는다. M0 기준선의 그 세 줄(148µs 등)이 그날만의 이상값이었다.
- 그래서 1단계 보고서는 **같은 자리에서 번갈아 잰 값**으로 쓴다 (`bench/merge/sameseat_table.py`). 다른 날의 기준선은 큰 변화를 거르는 데만 쓴다.

### 6.3 회귀처럼 보였지만 아니었던 것: 프로세스마다 갈리는 값
- linalg `solve_tridiagonal`의 (1000, 3, 3) 배치(10스레드)가 처음 네 번의 비교(옛 패키지 먼저, 통합판 나중)에서는 통합판이 2–4µs 느렸다. M2 커밋으로 되돌린 빌드도 느려서, 공용 풀을 쓰게 된 M2부터의 회귀로 의심했다. 그런데 두 풀의 코드는 이름공간을 빼면 같다.
- Mac이 잠들지 않게 한 뒤 다시 번갈아 재자 양쪽 모두 **프로세스마다 약 7µs와 약 10.5µs 중 하나로** 갈렸다 (25번 잰 중앙값: 옛 패키지 7.4, 8.1, 10.4, 10.6 / 통합판 7.0, 10.4, 10.6, 12.0). 전체 표를 잰 회차에서는 반대로 옛 패키지가 17.5µs, 통합판이 9.4µs였다.
- 그래서 회귀가 아니라 **이 호출의 10스레드 시간이 프로세스 단위로 두 갈래**인 것이다. 태스크가 아주 작아서(약 5µs 배치를 나눔) 스레드가 어느 코어에 놓이는지에 따라 달라지는 것으로 보인다. 원인을 확인하지는 않았다. 1스레드에서는 언제나 같다(약 37µs).
- 교훈: 짧은 병렬 호출 하나는 "같은 자리에서 번갈아"도 프로세스 몇 개로는 판단할 수 없다. 프로세스를 여러 번 새로 띄워 분포를 봐야 한다.

### 6.4 표: 옛 패키지 대 통합판 (같은 자리에서 번갈아, 2라운드)
`bench/merge/m3/final/table.md` (`bench/merge/sameseat_table.py`)

| 영역 | 스레드 | 줄 | 통합판/옛 패키지 기하평균 | 10% 넘게 느려짐 | 10% 넘게 빨라짐 |
|---|---|---:|---:|---:|---:|
| 배열 | 10 | 17 | 0.997 | 0 | 0 |
| 배열 | 1 | 17 | 0.988 | 0 | 1 |
| linalg | 10 | 258 | 0.944 | 0 | 45 |
| linalg | 1 | 258 | 0.934 | 0 | 59 |

- **배열은 그대로다.** 1단계에서 배열은 옮기기만 했고(M1), 바뀐 것은 pairwise 합의 정의가 `base/`로 간 것뿐이다(§6.1에서 성능을 되찾음).
- **linalg는 작은 행렬에서 빨라졌다.** 빨라진 줄은 거의 모두 3×3, 32×32와 작은 배치다. 결과 배열 하나에 약 120ns를 줄인 것(§4)이 그대로 보인다: 3×3 `cholesky` 0.61배, `lu` 0.58–0.66배, `diagonal` 0.56배.
- **큰 행렬은 같다.** 계산이 Accelerate LAPACK이라 경계와 무관하다.
- **numpy/scipy와 비교**(10스레드, 248줄): 통합판이 10% 넘게 빠름 189, 비슷 50, 느림 9. 기하평균 3.21배. 옛 linalg 최종 보고서(195 / 43 / 10)와 거의 같고, 느린 줄이 하나 줄었다.

## 7. 리뷰 포인트
1. **바뀐 동작은 `.base` 하나다.** linalg 결과의 `.base`가 내부 블록 객체에서 `None`으로 바뀌었다. 배열 규칙과 같아졌다. 다른 결과는 골든 출력에서 비트까지 같다.
2. **성능은 골든 출력이 지켜 주지 않는다.** 이번에 "같은 알고리즘을 한 곳으로" 옮긴 것만으로 배열의 합이 37% 느려졌고, linalg의 짧은 합도 느려졌다. 둘 다 고쳤다. 앞으로 고치는 마일스톤(M4, M6)도 같은 자리 비교(`sameseat_table.py`)를 끝에 돌린다.
3. **기준선 측정이 흔들렸다.** M0 기준선의 1스레드 원소별 줄 몇 개와 10스레드 `solve_tridiagonal` 배치는 그날, 그 프로세스만의 값이었다. 판단은 같은 자리에서 번갈아 잰 값으로 한다.
4. **설계 하나를 바꿨다**: 배열에 `new_array_fortran` 대신 strides를 받는 `new_array_strided`를 더했다. 레이아웃은 linalg의 정책이라 linalg에 두었다.
5. **1단계가 끝났다.** 다음은 M4(공통 바닥 정리)다: pandas판 풀, `Buffer`에 `size()`, `base/dtype.hpp`에 `String`·`Datetime64`, 스칼라 변환 규칙과 `base/neon.hpp`의 역방향 의존 정리.
