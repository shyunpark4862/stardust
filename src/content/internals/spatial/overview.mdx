## 한눈에 보기

`sd.spatial`은 세 가지 일을 해요. 점 사이의 거리를 재고(`pdist`, `cdist`, 거리 함수 열네 개, `squareform`), 전체 거리 행렬을 만들지 않고 가까운 이웃을 찾고(`kneighbors`, `radius_neighbors`), 한 번 만든 KD 트리로 같은 데이터에 여러 번 묻게 해 줘요(`KDTree`와 그 메서드 여섯).

이 영역의 설계는 한 문장으로 모여요. **짝 하나의 거리는 한 커널이 정하고, 이웃의 순서는 (거리, 색인)의 전순서가 정해요.** 그래서 같은 짝 (x, y)는 `pdist`, `cdist`, 거리 함수, `kneighbors`, 트리의 잎 어디서 계산하든 같은 비트이고, 이웃 찾기의 답은 "모든 짝을 그 커널로 계산해 (거리, 색인)으로 정렬한 것"이라는 정의 하나로 정해져요. 빠른 길(GEMM 고르기, KD 트리, 단위 구 위의 트리)은 이 정의를 바꾸지 않고, 답이 될 수 없다고 증명된 짝을 건너뛸 뿐이에요.

층은 아래로만 기대요. `csrc/spatial/`은 배열, 스레드풀, Accelerate의 BLAS 래퍼, `base/`의 사인·코사인 위에 서고, 다른 영역의 C++ 코드는 `spatial/`을 몰라요. linalg의 합과 노름에도 기대지 않아요. 거리의 합은 이 영역이 정한 타일 순서라서([한 짝 커널](/internals/spatial/pair-kernel/)) 남의 합을 빌려 쓰면 그 순서가 깨지기 때문이에요.

C++ 하위 모듈 `stardust._core.spatial`은 소스 파일마다 하나씩 있는 `bind_*`(`bind_distance`, `bind_kdtree`, `bind_neighbors`, `bind_query`, `bind_dual`, `bind_sphere`)를 차례로 불러 만들어요. 그래서 네이티브 이름은 모두 밑줄로 시작하는 내부 이름이고, 사용자는 Python 함수와 `KDTree` 클래스만 봐요.

```python
>>> import math
>>> import stardust as sd
>>> sorted(n for n in dir(sd._core.spatial) if not n.startswith("__"))
['_KDTree', '_ball_point', '_ball_tree', '_cdist', '_count', '_kneighbors', '_paired', '_pairs', '_pdist', '_radius_neighbors', '_sphere_kneighbors', '_sphere_radius', '_squareform_tomatrix', '_squareform_tovector']
```

Python 층은 인자를 모두 검사하고 C++ 층은 넘겨받은 배치(dtype, 차원, 연속성)만 확인해요. 검사가 한곳(`_common.py`)에 모여 있어서 `kneighbors`와 `KDTree.query`가 `k`와 `distance_upper_bound`를 같은 함수, 같은 메시지로 검사해요. 공개 함수의 에러는 부른 함수의 이름으로 시작하고, C++ 쪽의 에러는 Python이 이미 막은 배치가 어긋났을 때만 나요.

## 길 고르기

같은 질문을 푸는 길이 넷이에요. 고르는 기준은 거리 이름과 입력의 모양뿐이고 값은 보지 않아요.

| 길 | 쓰는 곳 | 조건 | 자세히 |
|---|---|---|---|
| 직접 전수 | 모든 거리 | 다른 길이 맞지 않을 때 | [한 짝 커널](/internals/spatial/pair-kernel/), [병렬화와 결정성](/internals/spatial/parallel/) |
| GEMM 고르기 | 가중치 없는 `euclidean`·`sqeuclidean`(`minkowski` p = 2 포함) | 1 ≤ n ≤ 2¹⁶, mA ≥ 64, mB ≥ 2048(n ≥ 8이면 1024) | [유클리드 혼합 계산](/internals/spatial/euclid-gemm/) |
| XB로 만든 KD 트리 | 가중치 없는 `euclidean`·`cityblock`·`chebyshev`·`minkowski`(p ≥ 1) | n ≤ 4, k ≤ 32, mB ≥ 2048이고 mA ≥ 2048이거나 (mA ≥ 512, mB ≥ 32768). 다른 p의 `minkowski`는 n ≤ 8, mB ≥ 1024, mA·mB ≥ 2¹⁷ | [KD 트리](/internals/spatial/kdtree/), [질의](/internals/spatial/queries/) |
| 단위 구 KD 트리 | `haversine` | mB ≥ 128, mA ≥ 16, 8k ≤ mB, 그리고 모든 점이 \|위도\| ≤ fl(π/2), \|경도\| ≤ 8 | [단위 구 위의 KD 트리](/internals/spatial/haversine-tree/) |

`KDTree.query`도 반대 방향으로 고르기를 해요. p = 2이고 점의 차원 m이 점 수 n에 비해 높으면 트리 대신 입력 순서의 `data`에 `kneighbors`의 전수(모양이 맞으면 GEMM 고르기)를 써요. 트리의 질의당 일은 대략 $2^{5m/6}$로, 전수는 n으로 자라니 그 둘을 견주는 식이에요. `_kdtree.py`의 `_brute_pays(n, m, k)`가 $5m/6 + \tfrac14\log_2 k + 7 - \log_2 n \ge 0.5$이면 전수를 골라요(k가 크면 트리가 조금 더 불리해지는 몫이 $\tfrac14\log_2 k$예요).

```python
>>> from stardust.spatial._kdtree import _brute_pays
>>> _brute_pays(10**5, 3, 1), _brute_pays(10**5, 16, 10)
(False, True)
```

`sqeuclidean`은 KD 트리 길에 들지 않아요. 트리는 √를 씌운 거리 d̂로 순서를 정하는데, 서로 다른 두 제곱합이 √의 반올림 뒤 같은 d̂가 될 수 있어요. 그러면 제곱합 (ŝ, j)의 순서와 (d̂, j)의 순서가 동점에서 갈려 결과가 정의와 달라질 수 있어요.

### 길이 결과를 바꾸지 않는 까닭

답이 길과 무관하려면 세 가지가 서야 해요.

1. **거리가 같은 비트.** 어느 길이든 짝의 거리는 `cdist`의 커널이 구해요. 전수 길은 `cdist`의 구동기를 블록마다 그대로 부르고(`CdistBlocks`), GEMM 길은 남은 짝을 같은 한 짝 커널(`pair_scalar`)과 같은 마무리 함수로 다시 계산하고, 트리의 잎도 같은 커널이에요. 타일 커널의 레인과 한 짝 커널이 같은 비트라는 것은 [한 짝 커널](/internals/spatial/pair-kernel/)에서 보여요.
2. **순서가 전순서.** 힙과 정렬과 합치기가 모두 `before(a, b) = a.d < b.d || (a.d == b.d && a.j < b.j)` 하나로 견줘요. 전순서라 어떤 순서로 넣고 어떻게 나눠 합쳐도 가장 작은 k개는 하나로 정해져요. NaN인 거리는 `d < upper`도 `d <= r`도 거짓이라 힙에 들어오지 않아요.
3. **건너뛰기가 보수적.** 빠른 길이 짝을 건너뛰는 것은 그 짝의 거리 d̂가 지금의 문턱 T보다 **엄격히** 크다고 증명될 때뿐이에요. 엄격하니 같은 거리에 색인이 작은 점(동점)도 빠지지 않아요. GEMM 고르기는 [정리 3](/internals/spatial/euclid-gemm/), KD 트리는 상자까지의 거리 하한, 단위 구 트리는 현 거리의 여유가 그 증명이에요.

테스트용 숨은 인자 `path`(1 전수, 2 GEMM, 3 트리)로 세 길을 강제로 타 보면 거리와 색인이 바이트까지 같아요.

```python
>>> from stardust.spatial import _neighbors as N
>>> rng = sd.random.default_rng(7)
>>> XA, XB = rng.random((300, 3)), rng.random((5000, 3))
>>> outs = [N._knn("kneighbors", XA, XB, 4, "euclidean", None, None, None, None, math.inf, path=p) for p in (1, 2, 3)]
>>> [o.distances.tolist() == outs[0].distances.tolist() and o.indices.tolist() == outs[0].indices.tolist() for o in outs]
[True, True, True]
```

스레드 수도 같은 이유로 답을 바꾸지 않아요. 일은 크기로만 나누고, 질의 하나나 짝 하나는 한 태스크가 처음부터 끝까지 계산해요. GEMM은 고르기에만 쓰이니 Accelerate의 스레드 모드(`VECLIB_MAXIMUM_THREADS`)가 GEMM의 끝자리를 바꿔도 답은 그대로예요. 나누는 방식은 [병렬화와 결정성](/internals/spatial/parallel/)에 모았어요.

## 결과 객체

`query`와 `kneighbors`는 `QueryResult(distances, indices)`를 돌려줘요. 다른 영역의 결과 튜플과 함께 `stardust/_results.py`에 있는 namedtuple이고, 두 배열은 돌려주기 전에 쓰기 금지가 돼요.

```python
>>> r = sd.spatial.kneighbors(XA[:2], XB, k=3)
>>> type(r).__name__, type(r).__module__
('QueryResult', 'stardust._results')
>>> r.indices.tolist()
[[827, 2296, 3973], [451, 966, 3202]]
>>> r.indices._flags()["writeable"]
False
```

반경 질의 셋(`radius_neighbors`, `query_ball_point`, `query_ball_tree`)은 `_radius.py`의 `RadiusResult`를 써요. 생성자는 CSR 꼴의 세 배열과 모양을 받아 검사도 복사도 하지 않고 쓰기 금지로만 만들어요. 꼴(행마다 색인 오름차순, `indptr`의 누적 개수)은 그것을 만든 네이티브 찾기가 보장하니까요. `tocsr()`는 부를 때마다 희소 배열 `sd.sparse.csr_array((distances, indices, indptr), shape=shape)`를 만들어요. 거리는 복사하지 않아서 그 `data`는 결과의 `distances`와 같은 쓰기 금지 배열이에요.

```python
>>> rr = sd.spatial.radius_neighbors(XA[:4], XB, 0.05)
>>> rr
RadiusResult(shape=(4, 5000), nnz=10)
>>> rr.tocsr()
<csr_array of shape (4, 5000), float64, 10 stored elements>
```

거리가 0인 짝(자기 자신, 중복된 점)은 CSR에 **저장된 0**으로 남아요. 희소 행렬의 저장 자리가 곧 이웃 그래프의 변이라서, 0을 지우면 중복된 점이 이웃에서 사라지기 때문이에요. 필드와 쓰임은 [결과 객체](/api/spatial/results/) 페이지에 있어요.

## 다른 영역과 만나는 자리

- **sparse.** `RadiusResult.tocsr()`와 `KDTree.sparse_distance_matrix`가 `sd.sparse.csr_array`를 만들어요. 이 의존은 Python 층에만 있어요. C++의 `spatial/`은 `sparse/`를 모르고, CSR의 세 배열을 직접 채운 뒤 Python이 그것을 희소 배열로 감싸요. 정수 인자 판별 하나(`is_int`)도 sparse의 Python 도우미를 빌려 써요.
- **linalg와 배열.** `mahalanobis`의 기본 `VI`는 `sd.cov(X, rowvar=False, correction=1)`의 역행렬을 `sd.linalg.inv`로 구하고, `seuclidean`의 기본 `V`는 `sd.var(..., correction=1)`이에요. 공분산이 특이하면 `inv`의 `LinAlgError`를 받아 이 영역의 메시지로 바꿔 다시 던져요.
- **linalg의 노름과는 비트가 다를 수 있어요.** 거리의 합은 linalg의 합을 쓰지 않으니 `euclidean(x, y)`와 `sd.linalg.vector_norm(x - y)`는 n ≥ 16에서 끝자리가 갈릴 수 있어요. n < 16이면 두 순서가 같은 차례 합이라 언제나 같아요.

```python
>>> a = sd.asarray([0.1 * i for i in range(40)])
>>> b = sd.asarray([0.07 * i * i % 1.0 for i in range(40)])
>>> sd.spatial.euclidean(a[:15], b[:15]) == sd.linalg.vector_norm(a[:15] - b[:15])
True
>>> d1, d2 = sd.spatial.euclidean(a, b), sd.linalg.vector_norm(a - b)
>>> d1 == d2, abs(d1 - d2) <= 2 * math.ulp(d1)
(False, True)
```

어느 쪽도 틀린 것이 아니에요. 둘 다 정확도 계약 안이고, 합의 순서만 달라요. 이 영역이 linalg의 16레인 순서 대신 타일 순서를 고른 까닭은 [한 짝 커널](/internals/spatial/pair-kernel/)에서 다뤄요.
