## 약속과 이 영역의 동작

라이브러리의 약속은 같은 기계, 같은 스레드 수, 같은 입력이면 실행마다 같은 비트라는 것이에요. `sd.spatial`의 API는 그보다 강하게, 결과가 **스레드 수, 계산 길(전수, GEMM 고르기, KD 트리, 단위 구 트리), Accelerate의 스레드 모드와 상관없이** 같다고 정해 둬요. 이웃의 집합, 동점의 순서, 결과의 정렬, 거리의 비트가 모두 그래요. 이것을 네 가지로 지켜요.

1. **짝 하나의 거리는 한 커널이 정해요.** 어느 함수, 어느 길, 어느 태스크에서 계산하든 같은 짝은 같은 비트예요([한 짝 커널](/internals/spatial/pair-kernel/)).
2. **이웃의 집합과 순서는 ($\hat d$, 색인)의 전순서가 정해요.** 후보를 어떻게 나눠 찾든 전순서의 앞 $k$개나 경계 안의 집합은 하나예요.
3. **일은 크기로만 나눠요.** 조각과 태스크의 경계는 입력의 모양과 트리로만 정하고, 이 영역의 C++ 코드는 스레드 수를 읽지 않아요. 출력 원소 하나는 태스크 하나가 써요.
4. **합쳐야 하는 부동소수점 합은 정해진 순서로 더해요.** 가중 `count_neighbors`는 태스크 번호 순서, GEMM 고르기의 열 평균은 조각 순서예요.

```python
>>> import math
>>> S = sd.spatial
>>> rng = sd.random.default_rng(8)
>>> X, Q, w = rng.random((60000, 3)), rng.random((3000, 3)), rng.random(60000)
>>> A, B = rng.random((800, 20)), rng.random((3000, 20))
>>> G = sd.stack([sd.asin(2 * rng.random(4000) - 1), math.pi * (2 * rng.random(4000) - 1)], axis=1)
>>> def run():
...     t = S.KDTree(X)
...     d, i = t.query(Q, k=5)
...     r = t.query_ball_point(Q, 0.03)
...     c = t.count_neighbors(t, [0.01, 0.02], weights=w)
...     kn = S.kneighbors(A, B, k=4)
...     rn = S.radius_neighbors(A, B, 0.9)
...     hv = S.kneighbors(G[:200], G, k=3, metric="haversine")
...     pd = S.pdist(A, metric="cosine")
...     return [v.tolist() for v in (t.data, d, i, r.indptr, r.indices, r.distances, c,
...                                  kn.distances, kn.indices, rn.indices, rn.distances,
...                                  hv.distances, hv.indices, pd)]
>>> n0 = sd.get_num_threads()
>>> sd.set_num_threads(1)
>>> one = run()
>>> sd.set_num_threads(10)
>>> ten = run()
>>> sd.set_num_threads(n0)
>>> one == ten
True
```

이 예의 호출은 모두 기준 크기를 넘어요. 10스레드에서는 트리를 하위 트리로 나눠 만들고, 질의점을 64개씩 나누고, 짝 셈을 노드 쌍으로 나누고, `kneighbors`는 GEMM 고르기의 블록으로, `haversine`은 단위 구 트리로 풀어요. 1스레드에서는 같은 조각을 차례로 돌아요. 결과는 같아요.

## 기준 크기와 GIL

나누기 시작하는 크기는 배열 영역의 규칙을 따라요. 작업량이 float64 연산 $2^{15}$개 분량 이상이면 일을 태스크로 나누고, 그 크기부터는 스레드 수와 상관없이 GIL을 놓아요. 그래서 `set_num_threads(1)`이어도 큰 이웃 찾기가 도는 동안 다른 Python 스레드가 돌 수 있어요. 작업량은 함수마다 이렇게 어림해요.

| 함수 | 작업량 |
|---|---|
| `pdist`, `cdist`, 거리 함수의 배치 | 짝의 수 $\times$ 짝 하나의 항 수($n$, 커널에 따라 그 몇 배) |
| 행마다의 준비(정규화, 비트 묶음) | 행 수 $\times n \times 8$ |
| `kneighbors`, `radius_neighbors` | $m_A \times m_B \times$ 짝 하나의 비용(GEMM 길은 $n$) |
| `KDTree` 만들기 | $n \times \max(m, 1)$ |
| `query`, `query_ball_point` | 질의점 수 $\times \max(m, 1) \times 64$ |
| 이중 트리 질의 | ($A$의 점 수 + $B$의 점 수) $\times \max(m, 1) \times 64$ |
| `haversine` 트리 길 | $(m_A + m_B) \times 3 \times 64$ |

```cpp
// csrc/spatial/neighbors.cpp
template <class F>
void for_tasks(int64_t ntasks, int64_t work, F&& fn) {
    if (ntasks <= 0) return;
    const parallel::Unlocked unlocked(work >= kParallelWork);
    if (work < kParallelWork || ntasks == 1) {
        for (int64_t t = 0; t < ntasks; ++t) fn(t);
    } else {
        parallel::parallel_for(ntasks, fn);
    }
}
```

기준보다 작으면 같은 태스크를 호출한 스레드가 GIL을 쥔 채 차례로 돌아요. 태스크의 경계는 기준과 무관하게 같아요. 이중 트리 질의도 기준 아래에서 같은 조각 쌍을 직렬로 돌아요. 트리 만들기만은 기준 아래에서 뿌리부터 한 번에 직렬로 만드는데, 그래도 같은 트리예요.

스레드풀은 겹쳐 쓰지 않아요. 태스크 안에서 부른 `parallel_for`는 그 태스크의 스레드에서 직렬로 돌아요. 예를 들어 `kneighbors`의 전수 길은 태스크마다 `cdist`의 구동기를 블록 하나에 부르는데, 그 구동기의 나누기는 태스크 안에서 차례로 돌아요. 구동기의 나누기도 크기로만 정하고 원소 하나를 한 번만 쓰니, 직렬로 돌든 나란히 돌든 같은 비트예요.

## 무엇을 어떻게 나누나

| 일 | 나누는 단위 | 결과가 같은 까닭 |
|---|---|---|
| `cdist`(타일 커널) | `XA` 행 블록 $\times$ `XB` 패널 묶음, 태스크마다 짝·항 $2^{20}$개 남짓 | 출력 원소 하나를 한 태스크가 같은 커널로 써요 |
| `pdist` | 행 묶음을 짝의 수로 고르게(앞 행일수록 짝이 많아요) | 위와 같아요 |
| 행마다의 준비(`cosine`·`correlation`의 정규화, `hamming`·`jaccard`의 비트 묶음, `XB` 패널 꾸리기) | 행 구간 | 행 하나의 계산이에요 |
| GEMM 고르기의 준비(`XB`의 열 평균, 옮긴 행, 노름) | 4096행 조각 | 열 평균은 조각마다의 부분합을 조각 순서로 더해요. 이 값은 고르기에만 쓰여요 |
| `kneighbors`, `radius_neighbors`(전수, GEMM 고르기) | `XA` 조각 $\times$ `XB` 구간 | 구간마다 따로 찾고 $(\hat d, j)$로 합쳐요 |
| `KDTree` 만들기 | 위 단계는 수준마다, 아래는 점 $\max(2^{12}, n/64)$개 이하의 하위 트리 | 점 집합은 전순서로, 자리는 미리 센 번호로 정해요([KD 트리](/internals/spatial/kdtree/)) |
| `query`, `query_ball_point` | 질의점 64개 | 질의 하나는 한 태스크가 처음부터 끝까지 찾아요 |
| `query_ball_tree`, `query_pairs`, `count_neighbors` | 깊이 4의 노드 조각 쌍(트리마다 16개 이하), 반경이 많은 셈은 더 얕게 | 목록은 행으로 모아 정렬해요. 가중 합은 태스크 번호 순서로 더해요 |
| `haversine` 트리 길 | 행의 옮기기는 $2^{14}$행 조각, 질의는 64점에서 시작해 조각이 32개보다 적으면 4점까지 반으로 | 질의 하나는 한 태스크가 찾고, 답은 `haversine` 커널과 $(\hat d, j)$로 정해요 |

### XA 조각과 XB 구간

`kneighbors`와 `radius_neighbors`는 `XA`를 행 조각으로 나누고, 조각이 32개보다 적으면 `XB`도 4096행 이상의 구간으로 나눠 (조각, 구간)마다 태스크 하나를 줘요. 질의점이 적어도 스레드가 모두 일하게 하려는 것이에요. 나누는 값은 모두 $m_A$, $m_B$, $k$로 정해요.

```cpp
// csrc/spatial/neighbors.cpp
// By the sizes alone. k: kneighbors' k (0: radius_neighbors).
Layout layout(int64_t ma, int64_t mb, int64_t qa_max, int64_t k) {
    Layout L;
    L.qa = k > 0 ? std::clamp<int64_t>(kHeapEntries / k, 1, qa_max) : qa_max;
    L.nA = ma == 0 ? 0 : ceil_div(ma, L.qa);
    int64_t S = 1;
    if (L.nA > 0 && L.nA < kMinTasks) {
        S = std::min(ceil_div(kMinTasks, L.nA), std::max<int64_t>(1, mb / kSegmentMin));
        if (k > 0) S = std::min(S, std::max<int64_t>(1, kSegmentSlots / std::max<int64_t>(1, ma * k)));
    }
    L.seg = std::max<int64_t>(8, ceil_div(std::max<int64_t>(mb, 1), S) + 7) / 8 * 8;
    L.S = mb == 0 ? 1 : ceil_div(mb, L.seg);
    return L;
}
```

`kneighbors`는 구간마다 자기 힙으로 그 구간의 앞 $k$개를 찾아 정렬해 두고, 모든 태스크가 끝나면 행마다 구간들의 정렬된 목록을 $(\hat d, j)$로 병합해 앞 $k$개를 골라요. 합집합의 앞 $k$개는 각 구간의 앞 $k$개 안에 있으니 병합한 결과가 곧 답이에요. `radius_neighbors`는 구간마다의 목록이 이미 $j$ 순서이고 구간도 $j$ 순서로 이어져 있어, 구간 순서로 이어 붙이면 행이 색인 순서가 돼요.

### 노드 조각 쌍

이중 트리 질의는 트리를 깊이 4의 노드(그보다 얕은 잎은 그 잎)로 잘라요. 트리마다 조각이 16개 이하이고, 조각의 쌍 $(a, b)$가 태스크 $a\cdot(B\text{의 조각 수}) + b$예요. `query_pairs`는 $a \le b$만이에요. 자르기는 트리로만 정해져요.

```cpp
// csrc/spatial/dual.cpp
// The nodes at `depth` below `node` (or the leaves above it), in preorder.
void pieces(const KdTree& t, int64_t node, int depth, std::vector<int64_t>& out) {
    const KdNode& nd = t.nodes[static_cast<size_t>(node)];
    if (depth == 0 || nd.right < 0) {
        out.push_back(node);
        return;
    }
    pieces(t, node + 1, depth - 1, out);
    pieces(t, nd.right, depth - 1, out);
}
```

`count_neighbors`는 태스크마다 반경 $R$개 + 1칸의 셈을 따로 두므로, 반경이 많으면 칸이 $2^{22}$개를 넘지 않게 깊이를 줄여요.

```cpp
    // csrc/spatial/dual.cpp
    int depth = kDepth;
    while (depth > 0 && (int64_t{1} << (2 * depth)) * (R + 1) > kCountSlots) --depth;
```

깊이는 반경의 수로 정해지니 같은 입력에서는 늘 같아요. 정수 셈은 어느 순서로 더해도 같고, 가중 셈은 태스크마다의 셈을 태스크 번호 순서로 더해 비트가 정해져요([질의](/internals/spatial/queries/)).

### 단위 구 트리의 질의 조각

`haversine`의 트리 길은 질의점이 적은 호출이 많아서(트리 길은 $m_A \ge 16$부터예요) 조각을 질의점 수에 맞춰 줄여요. 64점에서 시작해 조각이 32개보다 적으면 4점까지 반으로 줄여요. 이것도 질의점 수만 봐요.

```cpp
// csrc/spatial/sphere.cpp
int64_t query_block(int64_t q) {
    int64_t b = kQueryBlock;
    while (b > kQueryBlockMin && q < kQueryTasks * b) b /= 2;
    return b;
}
```

## Accelerate의 스레드 모드

이 영역에서 BLAS를 부르는 곳은 GEMM 고르기 하나예요. GEMM `dgemm`은 행렬을 블록으로 나누고 마이크로커널로 곱을 더하는데, 그 블록 크기와 덧셈 순서는 Accelerate의 판과 스레드 모드(`VECLIB_MAXIMUM_THREADS`)에 따라 달라져 결과의 끝자리가 바뀔 수 있어요. 그래서 GEMM의 결과는 "이 짝은 답이 될 수 없다"는 판정에만 쓰고, 그 판정은 GEMM이 오차 한계 안의 어떤 값을 내도 맞도록 증명한 여유로 해요([유클리드 혼합 계산](/internals/spatial/euclid-gemm/)). 남은 짝의 거리는 언제나 한 짝 커널로 다시 구하고, 순서는 $(\hat d, j)$예요. 그래서 GEMM의 끝자리는 답에 닿지 않아요. 트리와 이중 트리 순회, `haversine` 트리 길은 BLAS를 부르지 않아요.

테스트는 `VECLIB_MAXIMUM_THREADS=1`과 기본 모드의 두 프로세스에서 GEMM 길을 지나는 호출들의 결과 바이트를 해시로 견줘 같은지 봐요.

## 작업 메모리의 상한

사용자가 모양으로 요청한 출력(`pdist`의 $m(m - 1)/2$, `cdist`의 $m_A \cdot m_B$, `kneighbors`의 $m_A \cdot k$) 말고는, 이웃 찾기의 작업 메모리가 입력과 무관한 상한 안이에요. 전체 $(m_A, m_B)$ 거리 행렬을 만들지 않아요.

| 길 | 태스크마다 쥐는 것 |
|---|---|
| 직접 전수 | 거리 블록 $2^{16}$개 double(512 KB), `cdist` 구동기가 꾸리는 `XB` 행 $2^{18}$개 double 이하 |
| GEMM 고르기 | 옮긴 `XA` 조각과 `XB` 블록 각각 $2^{19}$개 double 이하, $G$ ($256 \times 2048$ 이하, 4 MB), 하한의 줄 |
| `kneighbors`의 힙 | $2^{16}$자리(1 MB) 이하. $k$가 그보다 크면 조각이 한 행이라 $k$자리 |
| `kneighbors`의 구간 버퍼 | 모두 합쳐 $2^{22}$자리 이하 |
| `count_neighbors` | 태스크 $\times (R + 1)$칸, 모두 합쳐 $2^{22}$칸 이하 |

호출 전체로 쥐는 것도 있어요. GEMM 길은 `XB`의 행마다 double 둘(옮긴 행의 제곱 노름과 그 반지름)을 쥐고, 옮긴 `XB` 전체가 $2^{27}$개 double 이하면 그 사본도 쥐어요(넘으면 블록마다 다시 옮겨요). `KDTree`는 잎 순서의 사본 $n \cdot m \cdot 8$바이트, 색인 $n \cdot 8$바이트, 노드마다 상자 $16m$바이트와 24바이트를 쥐어요. 점이 `leafsize`보다 많은 트리에서는 잎마다 점이 $\texttt{leafsize}/2$개 이상이라 노드가 $4n/\texttt{leafsize}$개보다 적어요. `data`를 읽거나 `query`가 전수 길을 타면 입력 순서의 사본 $n \cdot m \cdot 8$바이트가 더해져요. `haversine` 트리 길은 호출마다 행의 $\cos\varphi$와 3차원 점($(m_A + m_B)\cdot 4$개 double), `XB`의 트리, 잎 순서의 (위도, 경도, $\cos$ 위도) $3 \cdot m_B$개 double을 쥐어요.

## 출력 크기 검사

모양으로 크기가 정해지는 출력은 할당 전에 이 기계의 물리 메모리와 견줘요. `pdist`($8 \cdot m(m - 1)/2$바이트), `cdist`($8 \cdot m_A \cdot m_B$), 거리 함수의 배치($8 \times$ 짝 수), `squareform`의 행렬, `kneighbors`와 `query`(거리와 색인 $16 \times$ 행 수 $\times k$)가 넘으면 아무것도 잡지 않고 `MemoryError`예요.

크기를 미리 알 수 없는 `KDTree`의 목록(`query_ball_point`, `query_ball_tree`, `sparse_distance_matrix`, `query_pairs`)은 찾는 동안 찾은 짝의 수를 원자적으로 세다가 물리 메모리를 넘을 수가 되면 모든 태스크가 찾기를 멈추고 `MemoryError`예요([질의](/internals/spatial/queries/)). 멈추는 시점은 스레드마다 다르지만 결과를 버리니 상관없어요. 개수만 묻는 `return_length`와 `count_neighbors`는 색인을 모으지 않아요.

## 시험

결정성은 모두 바이트로 봐요. 거리(`pdist`, `cdist`, 거리 함수의 배치), 이웃 찾기(전수, GEMM 고르기, 구간 나누기를 부르는 모양), `KDTree`(만들기의 노드·상자·색인, `query`, 반경, 짝, 셈), `haversine` 트리 길의 테스트가 각각 1, 3, 10스레드의 결과를 견줘요. 만들기는 12만 점이라 위 단계와 하위 트리, 큰 노드의 표본 띠를 모두 지나요. Accelerate의 스레드 모드는 위에서 본 두 프로세스의 해시로 봐요.
