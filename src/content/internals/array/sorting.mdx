## 한눈에 보기

`sort`와 `argsort`는 C++ 함수 `sort_impl`(`csrc/array/ops/sort.cpp`) 하나가 처리해요. 흐름은 이래요.

1. complex는 순서가 없으므로 TypeError를 내요. 그다음 `axis`, `descending`, `stable`을 해석해요(기본값 `axis=-1`, `descending=False`, `stable=True`).
2. 입력의 메모리 순서를 따르는 새 배열(`new_array_like`)을 결과로 할당해요. `argsort`면 int64 배열이에요.
3. 정렬할 축을 따라 놓인 원소의 묶음(레인)은 서로 독립이므로, 레인 단위로 나눠 여러 스레드에서 정렬해요(`run_lanes`, [연산 엔진](/internals/array/engine/)).
4. 레인 하나는 원소를 작업 버퍼로 읽어 오면서 NaN을 따로 모으고, 나머지를 dtype과 길이로 고른 알고리즘으로 정렬한 뒤 결과에 다시 써요.

알고리즘은 dtype과 레인 길이만 보고 골라요. 데이터 분포는 보지 않아요.

| 경우 | 알고리즘 | 결과 |
|---|---|:---:|
| 16개 이하의 레인 (모든 dtype, `sort`·`argsort`) | Batcher의 정렬 네트워크, 같은 값이면 원래 인덱스 순 (`stable=False`도) | 안정 |
| int64·float64 값(`sort`, `unique_values`, `unique_counts`), 1024개 이상 | LSD 기수 정렬 (`stable=False`도) | 안정 |
| int64·float64 (값, 인덱스) 쌍(`argsort`, `unique_inverse`, `unique_all`), 128개 이상 | LSD 기수 정렬 (`stable=False`도) | 안정 |
| int64 값, 32–1023개 | NEON 정렬 네트워크 + bitonic 병합 | 안정과 같음(구별 불가) |
| float64 값, 32–1023개 | NEON 정렬 (`stable=False`도). `-0.0`과 `+0.0`이 섞여 있으면 정렬 뒤에 0 구간의 부호를 입력 순서로 되써요 | 안정과 같음 |
| 그 밖(17개 이상의 짧은 레인, bool), `stable=True` | 하향식 merge sort (16개 이하의 구간은 insertion sort) | 안정 |
| 그 밖(17개 이상의 짧은 레인, bool), `stable=False` | introsort (quicksort + heapsort, 16개 이하의 구간은 insertion sort) | 불안정 |

설계의 뼈대는 네 가지예요.

- 비교 함수에서 NaN을 없애요. NaN을 미리 분리해 두면 나머지는 NaN 검사 없는 `a < b`로 정렬할 수 있어요.
- 안정 정렬이 아닌 빠른 알고리즘도, 결과가 안정 정렬과 구별되지 않으면 써요. int64에서 같은 값은 비트까지 같으니 순서가 바뀌어도 결과 배열은 똑같아요. NEON 정렬을 쓸 수 있는 근거예요.
- int64와 float64는 `stable=False`여도 대부분 안정 정렬의 결과를 내요. 값 정렬(`sort`)은 길이와 상관없이, `argsort`는 레인이 16개 이하이거나 128개 이상일 때예요. 안정 정렬의 결과는 불안정 정렬로서도 올바른 결과예요. 이 경우에는 안정 경로(기수 정렬, NEON 정렬과 0의 부호 되쓰기)가 불안정 경로보다 빠르거나 같고, 결과가 스레드 수에 따라 달라질 여지도 없어요. 17–127개인 `argsort(stable=False)`는 introsort라 동점 인덱스의 순서가 입력 순서와 다를 수 있어요.
- 결과는 지금 스레드 수와도 상관없어요. 긴 레인을 조각으로 나눠 병렬로 정렬할 때도, 조각 경계는 길이로만 정하고 병합은 "동점이면 왼쪽 먼저"라서 직렬 안정 정렬과 비트까지 같아요.

`unique_*`는 "평탄화 → 안정 정렬 → 이웃 비교"로 구현돼요. 해시 테이블을 쓰지 않아요.

이 페이지의 수치는 Apple M4 Pro, numpy 2.5.4에서 잰 값이에요. 따로 적지 않으면 원소 100만 개, 1스레드예요.

## 순서 규칙

### NaN은 가장 큰 값이에요

비교 순서는 한 가지뿐이고, NaN을 가장 큰 값으로 쳐요. 그래서 NaN은 오름차순이면 맨 끝, 내림차순이면 맨 앞에 와요. frame의 정렬과 같은 규칙이에요.

- `-0.0`과 `+0.0`은 같은 값으로 비교해요(IEEE 754의 `==`). 안정 정렬이면 둘은 입력 순서를 지켜요.
- `descending=True`에서도 동점 원소는 입력 순서를 지켜요. 오름차순 결과를 뒤집지 않고 비교 함수를 뒤집기(`b < a`) 때문이에요. 오름차순 결과를 뒤집으면 동점 원소의 순서도 뒤집혀 안정성이 깨져요. 예외는 동점을 구별할 수 없는 NEON 정렬 경로로, 거기서는 결과를 뒤집어도 아무 차이가 없어요.
- complex는 `sort`, `argsort`에서 TypeError예요. `unique_*`만 (실수부, 허수부) 사전순을 써요.

```python
>>> import stardust as sd
>>> f = sd.asarray([3.0, float("nan"), -0.0, 1.0, 0.0, float("nan")])
>>> sd.sort(f)
array([-0.0,  0.0,  1.0,  3.0,  nan,  nan], dtype=float64)
>>> sd.sort(f, descending=True)
array([ nan,  nan,  3.0,  1.0, -0.0,  0.0], dtype=float64)
>>> sd.argsort(sd.asarray([2, 1, 2, 1]), descending=True)
array([0, 2, 1, 3], dtype=int64)
```

내림차순에서도 `-0.0`이 `0.0`보다 앞이에요. 입력에서 먼저 나왔기 때문이에요. 마지막 예에서 두 개의 2(위치 0, 2)와 두 개의 1(위치 1, 3)도 각각 입력 순서를 지켜요.

### NaN 분리: `load_split_nans`

NaN을 가장 큰 값으로 치는 비교 함수를 그대로 쓰면 이래요.

$$
\text{less}(a, b) = (a < b) \;\lor\; (\text{isnan}(b) \land \lnot\,\text{isnan}(a))
$$

비교할 때마다 NaN 검사가 두 번 들고 분기가 생겨요. 정렬은 비교를 $O(n \log n)$번 하니 이 비용이 계속 쌓여요.

대신 레인을 작업 버퍼로 읽어 올 때 NaN과 나머지를 따로 채워요.

```cpp
        // csrc/array/ops/sort.cpp, load_split_nans (줄인 발췌)
        std::int64_t nans = 0;
        for (std::int64_t i = 0; i < n; ++i) nans += is_nan(load_as<T>(x + i * stride));
        std::int64_t rest = nans_first ? nans : 0, nan = nans_first ? 0 : n - nans;
        for (std::int64_t i = 0; i < n; ++i) {
            const T v = load_as<T>(x + i * stride);
            buf[is_nan(v) ? nan++ : rest++] = make(i, v);
        }
        return nans;
```

- 정렬할 구간에는 NaN이 없으니 평범한 `a < b`(또는 `b < a`)로 정렬해요. 비교마다 NaN을 검사하는 정렬보다 1.22배 빨라요. 기수 정렬에도 이 분리가 필요해요. NaN은 비트 패턴이 여러 가지라 키로 바꾸면 순서가 맞지 않아요.
- NaN끼리는 언제나 원래 순서예요. 그래서 오름차순의 맨 끝 NaN 묶음도, 내림차순의 맨 앞 NaN 묶음도 안정 정렬의 결과와 같아요. 내림차순으로 바꾸는 데 추가 비용이 없어요. 정렬할 구간의 시작이 NaN 개수만큼 밀릴 뿐이에요.
- `argsort`는 `make`가 `(값, 원래 인덱스)` 쌍을 만들어 같은 함수로 처리해요. `if constexpr`로 int64, bool이면 NaN 세기를 컴파일 시점에 통째로 빼요.

## 알고리즘 선택

### dtype과 길이만 보는 이유

데이터를 보고 알고리즘을 고르는 휴리스틱(예: "값의 범위가 좁으면 계수 정렬", "이미 정렬돼 있으면 건너뛰기")은 넣지 않아요. 이유는 두 가지예요.

- 같은 크기의 배열이 데이터에 따라 몇 배씩 다른 시간이 걸리면 성능을 예측하기 어려워요.
- 휴리스틱의 기준값이 특정 데이터에 맞춰지면 다른 데이터에서 오히려 느려질 수 있어요.

dtype과 길이로 고르는 것(16개 이하면 정렬 네트워크, 1024개 이상의 int64·float64 값, 128개 이상의 쌍이면 기수 정렬)은 휴리스틱이 아니에요. 같은 dtype, 같은 길이면 언제나 같은 알고리즘이에요.

예외로 데이터를 보는 곳이 하나 있어요. 32~1023개의 float64 값을 NEON 정렬로 정렬할 때 `-0.0`과 `+0.0`이 둘 다 있는지 한 번 훑어 봐요(`zero_signs`). `stable=False`도 안정 경로로 가므로 언제나 훑어요. 알고리즘을 고르려는 것이 아니라 결과를 정확하게 맞추려는 것이에요. NEON 정렬은 동점 순서를 지키지 않는데, float64에서 "같지만 비트가 다른" 값은 (NaN을 빼면) `-0.0`과 `+0.0`뿐이에요. 둘이 섞여 있으면 NEON 정렬이 그 순서를 바꿔 안정 정렬과 다른 결과가 나올 수 있어요. 그래도 알고리즘은 그대로 NEON 정렬이에요. 정렬하기 전에 0의 부호를 입력 순서대로 비트 하나씩 적어 두었다가, 정렬한 뒤 0이 모인 구간에 그 부호대로 되써요. 결과는 안정 정렬과 비트까지 같아요. 방법과 비용은 아래 "±0이 섞인 안정 정렬"에 있어요.

### argsort는 (값, 인덱스) 쌍을 정렬해요

`argsort`를 구현하는 흔한 방법은 인덱스 배열 `idx = [0, 1, ..., n-1]`을 만들고, `a[idx[i]] < a[idx[j]]`로 비교하며 인덱스만 옮기는 간접 정렬이에요. 비교할 때마다 `a`의 무작위 위치를 읽어야 해서, 배열이 캐시보다 크면 비교마다 캐시 미스가 나요.

stardust는 `Keyed<T>{value, index}` 쌍(16바이트)을 정렬해요. 비교에 필요한 값이 옮기는 원소 안에 같이 있으니, 메모리를 순서대로 지나가요. 원소가 두 배 크니 옮기는 바이트는 늘지만, 캐시 지역성이 그보다 더 중요해요.

argsort에는 NEON 정렬을 쓰지 않아요. 인덱스가 결과로 나오니, 동점 원소의 순서가 그대로 드러나요. "구별할 수 없으니 안정 정렬이 아니어도 된다"는 논리가 성립하지 않아요. 대신 16개 이하는 원래 인덱스로 동점을 가르는 정렬 네트워크로, int64와 float64의 쌍은 128개 이상이면 [기수 정렬](#기수-정렬-int64-float64)로 가요. 비교를 하지 않는 안정 정렬이라 동점 순서가 저절로 지켜져요.

### merge sort (짧은 쌍과 bool의 안정 정렬)

int64·float64 쌍이 17–127개이거나, 기수 정렬도 NEON 정렬도 없는 bool(17개 이상)을 안정 정렬할 때 써요. `csrc/array/kernels/sort.hpp`의 `merge_sort`는 하향식(top-down) merge sort예요.

```cpp
// csrc/array/kernels/sort.hpp, merge_sort (줄인 발췌)
template <typename T, typename Less>
void merge_sort(T* a, T* tmp, std::int64_t n, Less less) {
    if (n <= kSmall) {
        insertion_sort(a, n, less);
        return;
    }
    const std::int64_t m = n / 2;
    merge_sort(a, tmp, m, less);
    merge_sort(a + m, tmp, n - m, less);
    if (!less(a[m], a[m - 1])) return;  // the halves are already in order
    std::copy(a, a + m, tmp);
    // Merge tmp[0, m) and a[m, n) into a. Take from the right half only when
    // strictly smaller: equal keys keep their original order (stability).
    std::int64_t i = 0, j = m, k = 0;
    while (i < m && j < n) a[k++] = less(a[j], tmp[i]) ? a[j++] : tmp[i++];
    while (i < m) a[k++] = tmp[i++];
}
```

- 오른쪽 원소는 `less(a[j], tmp[i])`일 때, 곧 엄격히 작을 때만 가져와요. 같으면 왼쪽(원래 앞에 있던 것)이 먼저 나가니 안정 정렬이에요.
- 작업 공간은 $n/2$예요. 왼쪽 반만 `tmp`로 복사하고, 병합 결과를 `a`의 앞에서부터 써요. 쓰는 위치 $k$는 오른쪽 반의 읽는 위치 $j$를 앞지르지 않으므로($k = i + (j - m) \le j$), 오른쪽 반은 복사하지 않아도 돼요. 오른쪽 반이 남으면 이미 제자리에 있으니 마지막 루프도 필요 없어요.
- 왼쪽 반의 마지막이 오른쪽 반의 처음보다 크지 않으면 이미 순서대로라 병합을 건너뛰어요. 그래서 이미 정렬된 입력에서는 병합이 모두 생략되어 비교 $O(n)$번이면 끝나요. 데이터를 보고 경로를 고르는 것이 아니라, 알고리즘 안의 한 번의 비교예요.
- 16개 이하의 구간은 insertion sort로 정렬해요. 이 크기에서는 재귀와 병합의 고정 비용보다 insertion sort가 빨라요. insertion sort도 `less(v, a[j-1])`가 엄격해서 안정적이에요.

시간 $O(n \log n)$, 추가 공간 $n/2$개, 재귀 깊이 $O(\log n)$이에요.

### introsort (짧은 레인과 bool의 `stable=False`)

`unstable_sort`는 Musser의 introsort[1]예요. int64·float64는 쌍이 17–127개일 때만, bool은 17개 이상이면 `stable=False`일 때 이것을 써요.

- quicksort 부분은 처음, 가운데, 끝 세 원소의 중앙값을 피벗으로 고르고(정렬된 입력에서 최악이 되는 것을 막아요), Hoare 분할[2]을 해요. Hoare 분할은 양쪽 끝에서 안쪽으로 오며 피벗보다 큰 것과 작은 것을 맞바꾸는 방식으로, Lomuto 분할보다 교환이 적어요.
- 분할한 뒤에는 작은 쪽으로만 재귀하고 큰 쪽은 `while` 루프로 이어 가요. 재귀할 때마다 크기가 절반 이하로 줄어드니 스택 깊이는 $O(\log n)$이에요.
- 재귀 깊이가 $2 \lfloor \log_2 n \rfloor$을 넘으면 그 구간은 heapsort(`std::make_heap` + `std::sort_heap`)로 바꿔 정렬해요. 그래서 운 나쁜 피벗이 계속 나와도 최악이 $O(n \log n)$이에요. 깊이 한도는 C++20의 `std::countl_zero`(앞쪽 0비트 수)로 $\lfloor \log_2 n \rfloor = 63 - \text{countl\_zero}(n)$을 계산해 정해요.
- 16개 이하는 insertion sort예요.

## 16개 이하의 레인: 정렬 네트워크

`(125000, 8)` 배열의 `sort(axis=1)`처럼 짧은 행이 아주 많으면, 레인마다 작업 버퍼를 잡고 merge sort를 하는 고정 비용이 대부분이에요. 그래서 16개(`kNetworkMax`) 이하의 레인은 버퍼 없이 레지스터 안에서 **정렬 네트워크**로 정렬해요(`network_sort`, `network_sort_values`, `csrc/array/ops/sort.cpp`).

정렬 네트워크는 비교-교환(두 자리를 비교해 순서가 틀리면 바꾸기)의 고정된 목록이에요. 어떤 입력이 와도 같은 자리들을 같은 순서로 비교하므로 분기가 없어요. 16입력에는 Batcher의 홀짝 병합 네트워크(odd-even merge sort, 비교기 63개)를 써요[3][4].

```cpp
// csrc/array/ops/sort.cpp (network_pairs)
template <int M>
constexpr auto network_pairs() {
    constexpr int N = kNetworkMax;
    struct List {
        NetworkPair pairs[80] = {};  // Batcher's network on 16 has 63 comparators
        int size = 0;
    } l;
    for (int p = 1; p < N; p <<= 1)
        for (int k = p; k >= 1; k >>= 1)
            for (int j = k % p; j + k < N; j += 2 * k)
                for (int i = 0; i < k && i + j + k < N; ++i)
                    if ((i + j) / (2 * p) == (i + j + k) / (2 * p) && i + j + k < M)
                        l.pairs[l.size++] = {i + j, i + j + k};
    return l;
}
```

- **NaN을 먼저 떼어요.** 레인을 읽으며 NaN을 끝(내림차순이면 앞)에 입력 순서대로 모으고, 나머지 $m$개만 네트워크로 정렬해요(위 "NaN 분리"와 같은 규칙).
- **$m$마다 맞는 네트워크.** 16입력 네트워크에서 $m$ 이상의 자리를 건드리는 비교기를 빼면, 빠진 자리에 $+\infty$가 있다고 본 것과 같아요. $+\infty$는 비교-교환에서 움직이지 않으므로, 남은 비교기가 $m$개를 올바르게 정렬해요. 이 목록을 $m = 0 \dots 16$마다 컴파일할 때 만들고(`constexpr`), 비교-교환을 모두 펼쳐서 값이 레지스터에 머물러요.
- **분기 없는 비교-교환.** 비교 하나와 선택 둘이에요. 조건을 `||`, `&&`로 쓰면 컴파일러가 분기를 넣어서, 비트 연산 `|`, `&`로 써요.

```cpp
    // csrc/array/ops/sort.cpp (network_run의 비교-교환, argsort)
    auto cas = [&](int p, int q) {
        const T vp = v[p], vq = v[q];
        const std::int64_t ip = ix[p], iq = ix[q];
        // q goes first: strictly before in the order, or equal and earlier in the
        // input. Bitwise, not ||/&&: no branch (the values are never NaN here).
        const bool lt = Descending ? vp < vq : vq < vp;
        const bool swap = lt | ((vp == vq) & (iq < ip));
        v[p] = swap ? vq : vp;
        v[q] = swap ? vp : vq;
        ix[p] = swap ? iq : ip;
        ix[q] = swap ? ip : iq;
    };
```

- **`argsort`**: 값과 원래 인덱스를 함께 옮기고, 같은 값이면 인덱스가 작은 쪽이 앞이에요. 그래서 결과는 안정 정렬과 같아요. `stable=False`도 같은 경로이고, 그것도 올바른 불안정 결과예요.
- **`sort`**: 값만 옮겨요. 인덱스를 함께 비교하면 단계마다 사슬이 길어져 눈에 띄게 느렸어요. 같은 값 가운데 구별되는 것은 $-0.0$과 $+0.0$뿐이므로, 두 부호가 섞여 있으면 입력 순서의 부호를 비트로 적어 두었다가 정렬 뒤 0 구간에 되써요(아래 "±0이 섞인 안정 정렬"과 같은 방법). 결과는 안정 정렬과 비트까지 같아요.
- 버퍼를 잡고 merge sort를 하는 것보다 `sort`와 `argsort` 모두 훨씬 빨라요. 17~31개는 그대로 merge sort나 introsort예요.

## NEON 정렬

`csrc/array/kernels/simd_sort.hpp`는 float64와 int64 값을 NEON 레지스터 안에서 정렬해요. M4의 NEON 레지스터는 128비트라 float64나 int64를 두 개 담아요. 정렬은 두 단계예요.

### 1단계: 16개 블록을 정렬 네트워크로

**정렬 네트워크**는 "비교-교환"을 정해진 순서로 적용하는 정렬 방법이에요[3]. 비교-교환 $(i, j)$는 위치 $i$와 $j$의 값을 비교해 작은 것을 $i$에, 큰 것을 $j$에 두는 연산이에요. 순서가 데이터와 무관하게 고정돼 있어서 분기가 하나도 없어요.

NEON에서는 비교-교환 하나가 명령어 두 개예요. 두 레지스터의 `min`과 `max`를 구하면 끝이에요. 게다가 레지스터 하나에 값이 두 개 있으니, 네트워크를 레지스터 단위로 적용하면 두 레인이 동시에 정렬돼요. 이것을 네트워크를 "세로로" 적용한다고 해요.

```cpp
// csrc/array/kernels/simd_sort.hpp (줄인 발췌)
struct F64 {
    using T = double;
    using V = float64x2_t;
    // ...
    static V min(V a, V b) { return vminq_f64(a, b); }
    static V max(V a, V b) { return vmaxq_f64(a, b); }
    // ...
};

template <typename Tr>
inline void cmpx(typename Tr::V& a, typename Tr::V& b) {  // compare-exchange: a <- min, b <- max
    const typename Tr::V lo = Tr::min(a, b);
    b = Tr::max(a, b);
    a = lo;
}
```

블록 하나는 16개 값이에요. 레지스터 8개(`v[0]`부터 `v[7]`까지)에 2개씩 싣고, 8입력 네트워크를 레지스터 단위로 적용해요. 쓰는 네트워크는 비교기 19개짜리예요. 8입력 정렬 네트워크의 최소 비교기 수가 19개로 알려져 있어요[3].

| 층 | 비교-교환 |
|:---:|---|
| 1 | (0,2) (1,3) (4,6) (5,7) |
| 2 | (0,4) (1,5) (2,6) (3,7) |
| 3 | (0,1) (2,3) (4,5) (6,7) |
| 4 | (2,4) (3,5) |
| 5 | (1,4) (3,6) |
| 6 | (1,2) (3,4) (5,6) |

같은 층의 비교-교환은 서로 다른 레지스터를 건드리므로 CPU가 동시에 실행할 수 있어요. 깊이는 6층이에요.

네트워크가 끝나면 `v[0..7]`의 레인 0이 정렬된 열 하나, 레인 1이 또 하나예요. 이 두 열을 2×2 전치(`vzip1q`, `vzip2q`)로 꺼내 길이 8인 정렬된 런(run) 두 개로 메모리에 써요.

int64에는 문제가 하나 있어요. NEON에는 64비트 정수 min/max 명령이 없어서, 비교(`vcgtq_s64`)와 비트 선택(`vbslq_s64`)으로 대신해요.

```cpp
    // csrc/array/kernels/simd_sort.hpp, I64 (줄인 발췌)
    static V min(V a, V b) { return vbslq_s64(vcgtq_s64(a, b), b, a); }
    static V max(V a, V b) { return vbslq_s64(vcgtq_s64(a, b), a, b); }
```

`F64`, `I64`처럼 dtype마다 "두 레인 벡터 연산"을 묶은 traits 구조체를 템플릿 인자 `Tr`로 넘겨서, 네트워크와 병합 코드는 한 벌만 써요.

### 2단계: bitonic 병합

길이 8인 런들을 둘씩 병합해 16, 32, …로 키워요. 병합도 레지스터 안에서 해요. 그 바탕은 정렬된 4개와 정렬된 4개를 분기 없이 합치는 `merge4x4`예요. Batcher의 bitonic 병합[4]을 레지스터 두 개 크기로 쓴 것이에요.

**bitonic 수열**은 증가하다가 감소하는(또는 그 회전인) 수열이에요. 정렬된 $a$ 뒤에 정렬된 $b$를 뒤집어 붙이면 bitonic이에요. bitonic 수열 $x_0, \dots, x_7$에 "반 정리기(half-cleaner)"

$$
\ell_i = \min(x_i, x_{i+4}), \quad u_i = \max(x_i, x_{i+4}) \qquad (i = 0, 1, 2, 3)
$$

를 적용하면, $\ell$의 모든 값이 $u$의 모든 값 이하이고, $\ell$과 $u$가 각각 다시 bitonic이 돼요[4]. 길이 4인 bitonic 수열은 거리 2, 거리 1의 비교-교환 두 번(`bitonic_clean4`)으로 정렬돼요.

```cpp
    // csrc/array/kernels/simd_sort.hpp, merge4x4 (줄인 발췌). a = (a0, a1), b = (b0, b1)은 각각 정렬된 4개
    typename Tr::V r0 = Tr::swap(b1), r1 = Tr::swap(b0);
    const typename Tr::V l0 = Tr::min(a0, r0), l1 = Tr::min(a1, r1);
    b0 = Tr::max(a0, r0);
    b1 = Tr::max(a1, r1);
    a0 = l0;
    a1 = l1;
    bitonic_clean4<Tr>(a0, a1);
    bitonic_clean4<Tr>(b0, b1);
```

긴 런 두 개의 병합(`merge_runs`)은 이 블록을 반복해요.

1. 두 런에서 4개씩 레지스터에 올려요.
2. `merge4x4`로 합쳐 아래 4개를 내보내고, 위 4개는 레지스터에 남겨요.
3. 두 런 중 다음 원소(머리)가 작은 쪽에서 4개를 더 올려, 남겨 둔 위 4개와 다시 `merge4x4`해요.
4. 한쪽이 바닥나면 다른 쪽을 계속 올리고, 마지막에 남은 위 4개를 내보내요.

이렇게 병합해도 순서가 맞아요. 남겨 둔 4개는 모두 이미 읽은 부분에서 왔으니, 자기가 나온 런의 현재 머리보다 크지 않아요. 3단계에서 머리가 작은 쪽 런 X에서 읽으므로, 남겨 둔 4개는 다른 런 Y의 머리보다도 크지 않아요. 새로 올린 4개는 X의 나머지보다 크지 않아요. 그래서 합친 8개 중 아래 4개는 아직 읽지 않은 어떤 원소보다도 크지 않고, 다음으로 내보낼 4개가 정확히 그것이에요. 이 방식은 Inoue 등의 AA-sort[5]와 Chhugani 등의 SIMD 병합[6]에서 쓰인 레지스터 안 bitonic 병합과 같은 구조예요.

분기는 출력 4개당 하나예요(3단계의 "어느 런에서 올릴까"). 스칼라 병합은 출력 원소마다 분기 하나라서, 무작위 데이터에서는 그 절반이 예측에 실패해요.

### 전체 구조와 세부 사항

```cpp
    // csrc/array/kernels/simd_sort.hpp, sort (줄인 발췌)
    const std::int64_t padded = (n + 15) / 16 * 16;  // whole blocks; the padding (kMax) sorts to the end
    // ...
    T stack[2 * kStack];
    std::unique_ptr<T[]> heap;
    if (padded > kStack) heap = std::make_unique_for_overwrite<T[]>(static_cast<size_t>(2 * padded));
    T* src = heap ? heap.get() : stack;
    T* dst = src + padded;
    std::copy(data, data + n, src);
    std::fill(src + n, src + padded, Tr::kMax);
    for (std::int64_t i = 0; i < padded; i += 16) sort_block16<Tr>(src + i);
    for (std::int64_t width = 8; width < padded; width *= 2) {  // merge passes, ping-pong between buffers
        for (std::int64_t i = 0; i < padded; i += 2 * width) {
            const std::int64_t na = std::min(width, padded - i), nb = std::min(width, padded - i - na);
            merge_runs<Tr>(src + i, na, src + i + na, nb, dst + i);
        }
        std::swap(src, dst);
    }
    std::copy(src, src + n, data);
```

- 길이를 16의 배수로 맞추려고 남는 칸에 `+inf`(float64)나 `INT64_MAX`(int64)를 채워요. 이 값들은 정렬하면 맨 끝으로 가고, 마지막에 앞의 $n$개만 복사하니 사라져요. 입력에 원래 `+inf`가 있어도 같은 값끼리는 구별되지 않으니 상관없어요.
- 병합 패스는 $\lceil \log_2(n/8) \rceil$번이에요. 블록 정렬이 길이 8인 런을 만들고, 패스마다 두 배가 돼요. 두 버퍼(`src`, `dst`)를 번갈아 쓰는 ping-pong 방식이에요.
- 작은 입력은 스택 버퍼를 써요. 채운 길이가 256 이하면 스택의 `T stack[512]`(float64면 4KB)를 써요. 짧은 레인을 아주 많이 정렬할 때(예: shape (3e5, 10)인 배열의 `quantile`) 호출마다 힙 할당을 하면 numpy보다 2배 느려져요. 더 길면 힙에 `2 × padded`개를 할당해요. `std::make_unique_for_overwrite`(C++20)는 할당만 하고 0으로 채우지 않아요. 어차피 곧 덮어쓸 메모리예요.
- 입력에 NaN이 있으면 안 돼요. `vminq_f64`/`vmaxq_f64`(AArch64의 FMIN/FMAX)는 NaN을 전파해요. NaN 하나가 네트워크를 지나며 여러 칸으로 퍼질 수 있어요. 그래서 NaN은 반드시 먼저 분리해요(`load_split_nans`).
- 32개 미만에는 쓰지 않아요(`kSimdMin`). 그보다 짧으면 insertion sort나 merge sort와 차이가 없어요.
- `quantile`과 `median`도 정렬이 필요할 때 이 NEON 정렬을 써요. 그쪽은 $\pm 0$을 구별하는 전순서로 결과를 다듬는 과정이 더 있어요([통계 함수](/internals/array/statistics/)).

### NEON 정렬을 써도 되는 조건: 안정성

NEON 정렬은 안정 정렬이 아니에요. 네트워크는 같은 값끼리도 교환하고, `merge_runs`의 "머리가 작은 쪽" 판단은 `a[ia] <= b[ib]`라서 같은 값이면 어느 쪽이든 먼저 나갈 수 있어요. 그래서 결과가 안정 정렬과 구별되지 않을 때만 써요.

- int64는 같은 값이면 비트까지 같아서, 순서가 바뀌어도 결과 배열은 똑같아요.
- float64에서 같은 값이 다른 비트일 수 있는 경우는 NaN(이미 분리)과 $\pm 0$뿐이에요. $\pm 0$이 섞여 있지 않으면 구별되지 않아요. 섞여 있으면 0 구간만 입력 순서로 되써서 안정 정렬과 같은 결과로 만들어요(아래 "±0이 섞인 안정 정렬"). `stable=False`여도 똑같이 해요. 불안정 정렬을 따로 두면 긴 레인은 1스레드에서도 조각으로 나눠야 해요(아래 "풀을 쓸 수 있을 때만 조각으로"). 원소 100만 개를 NEON 정렬로 잴 때 그 경로는 약 25ms, 안정 경로는 약 14ms였어요.
- 내림차순은 오름차순으로 정렬한 뒤 `std::reverse`로 뒤집어요. 동점을 구별할 수 없으니 뒤집어도 안정 정렬의 결과와 같아요.
- argsort에는 쓰지 않아요(위 참고).

$\pm 0$이 섞인 안정 정렬도 merge sort로 돌리지 않고, NEON 정렬 뒤에 0 구간만 고쳐 써요. 1024개 이상의 float 값은 NEON 정렬보다 빠른 기수 정렬로 가요(아래).

## 기수 정렬 (int64, float64)

### LSD 기수 정렬

int64·float64 값이 1024개 이상이거나, int64·float64 (값, 인덱스) 쌍이 128개 이상이면 **LSD(least significant digit) 기수 정렬**[7]을 써요. 64비트 키를 8비트씩 8자리로 보고, 가장 낮은 자리부터 자리마다 **계수 정렬**을 해요.

자리 $d$의 계수 정렬은 세 단계예요.

1. 각 키의 자리 값(0–255)의 개수를 세요. $c_v$ = 자리 값이 $v$인 키의 수.
2. 누적합으로 각 자리 값의 시작 위치를 구해요. $\text{pos}_v = \sum_{v' < v} c_{v'}$.
3. 입력을 앞에서부터 읽으며 `dst[pos[v]++] = src[i]`로 흩뿌려요.

3단계가 입력 순서대로 진행하므로, 같은 자리 값끼리는 원래 순서를 지켜요(안정). 각 자리의 정렬이 안정이니, 낮은 자리부터 높은 자리까지 하면 전체가 안정 정렬이 돼요. 높은 자리가 같은 키는 낮은 자리로 정렬된 순서를 그대로 유지하니까요. 그래서 `sort`, `argsort`, `unique_*`가 같은 함수를 써요.

시간은 $O(d \cdot (n + 256))$($d$는 실제로 정렬하는 자리 수, $d \le 8$), 추가 공간은 원소 $n$개짜리 임시 버퍼와 카운터 $8 \times 256$개예요. 비교를 하지 않으니 비교 정렬의 $O(n \log n)$ 하한에 묶이지 않아요.

### int64의 키

기수 정렬은 키를 부호 없는 정수로 보고 정렬해요. 부호 있는 int64의 순서를 부호 없는 순서로 바꾸려면 부호 비트를 뒤집으면 돼요.

$$
\text{key}(v) = v \oplus 2^{63}
$$

음수는 부호 비트가 1이라 뒤집으면 0으로 시작하고, 양수는 1로 시작해요. 그러면 $-2^{63} \mapsto 0$, $-1 \mapsto 2^{63} - 1$, $0 \mapsto 2^{63}$, $2^{63} - 1 \mapsto 2^{64} - 1$로 순서가 보존돼요.

내림차순이면 키 전체를 비트 반전해요(`~u`). 큰 값이 작은 키가 되어 앞으로 와요. 결과를 뒤집지 않으니 같은 값은 여전히 원래 순서예요. float64 키도 같은 방법을 써요.

### float64의 키

IEEE 754의 float64는 부호 비트 1개, 지수 11비트, 가수 52비트를 이 순서로 담은 **부호-크기(sign-magnitude)** 표현이에요. 지수가 가수보다 위에 있고 지수는 바이어스를 더한 부호 없는 값이라, 양수끼리는 비트 패턴을 부호 없는 정수로 읽은 순서가 값의 순서와 같아요. 음수는 크기가 클수록 비트가 크니 순서가 거꾸로예요. 그래서 이렇게 바꿔요(`csrc/array/ops/sort.cpp`의 `radix_key`).

```cpp
// csrc/array/ops/sort.cpp, radix_key (float64)
inline std::uint64_t radix_key(double v, bool descending) {
    const std::uint64_t b = std::bit_cast<std::uint64_t>(v == 0.0 ? 0.0 : v);
    const std::uint64_t u = (b >> 63) ? ~b : b | (std::uint64_t{1} << 63);
    return descending ? ~u : u;
}
```

- 양수는 부호 비트만 세워요. 모든 양수가 $2^{63}$ 이상으로 올라가 음수의 키보다 커지고, 양수끼리의 순서는 그대로예요.
- 음수는 64비트 전체를 반전해요. 부호 비트가 0이 되어 양수 아래로 가고, 크기의 순서가 뒤집혀서 "크기가 클수록 작은 키"가 돼요.
- $-0.0$은 $+0.0$으로 바꾼 뒤 키를 만들어요. 둘은 `==`로 같은 값이니 키도 같아야 동점이 돼요. 기수 정렬은 안정이라 같은 키끼리는 입력 순서를 지키므로, 두 0은 비교 기반 안정 정렬처럼 입력 순서대로 남아요. 정렬하는 것은 (값, 인덱스) 쌍이고 키는 그때그때 계산하므로, 값 자체(부호)는 바뀌지 않아요.
- NaN은 키로 만들지 않아요. NaN은 지수가 모두 1이고 가수가 0이 아닌 비트 패턴이라, 부호와 가수에 따라 키가 여기저기 흩어져요. 레인을 읽을 때 이미 분리해 두었으므로(`load_split_nans`) 정렬할 구간에는 NaN이 없어요.

몇 가지 값의 비트와 키를 16진수로 보면 순서가 보존되는 것을 알 수 있어요.

| 값 | 비트 | 키 |
|:---:|:---:|:---:|
| $-\infty$ | `FFF0000000000000` | `000FFFFFFFFFFFFF` |
| $-2.0$ | `C000000000000000` | `3FFFFFFFFFFFFFFF` |
| $-0.5$ | `BFE0000000000000` | `401FFFFFFFFFFFFF` |
| $-0.0$ | `8000000000000000` | `8000000000000000` |
| $+0.0$ | `0000000000000000` | `8000000000000000` |
| $0.5$ | `3FE0000000000000` | `BFE0000000000000` |
| $2.0$ | `4000000000000000` | `C000000000000000` |
| $+\infty$ | `7FF0000000000000` | `FFF0000000000000` |

키는 위에서 아래로 커지고, $-0.0$과 $+0.0$의 키가 같아요. 무한대도 특별히 다룰 필요가 없어요. 이 변환은 원소마다 비교 하나와 비트 연산 몇 개라, 흩뿌리는 패스마다 다시 계산해도 메모리 이동보다 싸요.

### 최솟값 기준과 자리 건너뛰기

한 번 훑어 키의 최솟값 $\text{lo}$와 최댓값 $\text{hi}$를 구하고, $\text{key} - \text{lo}$를 정렬해요. 그러면 정렬할 자리 수는

$$
d = \min\{\, d' : (\text{hi} - \text{lo}) \gg 8d' = 0 \,\} = \left\lceil \log_{256}(\text{hi} - \text{lo} + 1) \right\rceil
$$

이에요. 모든 키가 같으면 $d = 0$이라 아무것도 안 해요(안정 정렬은 이미 그대로).

최솟값을 빼는 것이 왜 중요한지는 음수와 양수가 섞인 경우에 드러나요. 값이 $[-1000, 1000)$이면 부호를 뒤집은 키에서 $-1$은 `0x7FFF…FF`, $+1$은 `0x8000…01`이에요. 맨 위 바이트는 `0x7F`와 `0x80`을, 나머지 바이트는 `0xFF`와 `0x00`을 오가니, 8자리 모두 값이 달라 건너뛸 자리가 없어요. 최솟값을 빼면 범위가 1999라 두 자리로 끝나요. 100만 개를 정렬할 때 최솟값을 빼지 않으면 10.5ms, 빼면 2.4ms예요(1스레드).

float64 키에도 같은 코드가 그대로 적용되지만, 실수에서는 자리가 거의 줄지 않아요. 가수 52비트가 무작위라 아래 여섯 바이트는 모든 키에서 제각각이고, 위 두 바이트(부호와 지수)만 범위에 따라 줄 수 있어요. 예를 들어 $[0.5, 1.5)$의 값은 키의 범위가 `0x0018000000000000`이라 일곱 자리이고, 양수와 음수가 섞인 표준정규분포는 여덟 자리를 모두 흩뿌려요.

그리고 센 개수를 보아 모든 키가 그 자리에서 같은 바이트면(`c[digit(a[0])] == n`) 그 자리를 건너뛰어요. 옮길 것이 없기 때문이에요.

```cpp
    // csrc/array/ops/sort.cpp, radix_sort (줄인 발췌)
    std::array<std::array<std::int64_t, 256>, 8> count;
    for (int d = 0; d < digits; ++d) count[d].fill(0);
    for (std::int64_t i = 0; i < n; ++i) {
        const std::uint64_t k = key(a[i]) - lo;
        for (int d = 0; d < digits; ++d) ++count[d][(k >> (8 * d)) & 255];
    }
    // ...
    for (int d = 0; d < digits; ++d) {
        std::array<std::int64_t, 256>& c = count[d];
        auto digit = [&](const E& e) { return ((key(e) - lo) >> (8 * d)) & 255; };
        if (c[digit(a[0])] == n) continue;  // one byte value for all keys
        std::int64_t sum = 0;
        for (std::int64_t& v : c) sum += std::exchange(v, sum);  // counts -> first slots
        for (std::int64_t i = 0; i < n; ++i) dst[c[digit(src[i])]++] = src[i];
        std::swap(src, dst);
    }
    if (src != a) std::copy(src, src + n, a);
```

- 모든 자리의 개수를 한 패스에 세요. 자리별 개수는 키의 집합에만 달려 있고 순서와 무관하니, 흩뿌리기 전에 한꺼번에 셀 수 있어요. 자리마다 세기 패스를 따로 하면 읽기가 $2d$번이지만, 한 번에 세면 세기 1번 + 흩뿌리기 $d$번이에요(최소·최대를 구하는 패스는 따로).
- `std::exchange(v, sum)`는 `v`에 `sum`을 넣고 옛 값을 돌려줘요. 한 줄로 "배타적 누적합"을 만드는 관용구예요.
- `Key` 함수 객체를 템플릿 인자로 받아, int64 값 정렬(`int64_t`)과 쌍 정렬(`Keyed<int64_t>`, `Keyed<double>`)이 같은 코드를 써요. 람다가 인라인되니 추상화 비용이 없어요.

### 비교 정렬보다 빠른 이유

기수 정렬은 패스마다 레인을 한 번 순서대로 읽고, 256개 구간에 흩뿌려 써요. 원소마다 하는 일은 키 계산, 카운터 하나 읽기와 늘리기, 저장 하나이고, 데이터에 따라 갈리는 분기가 없어요. 반면 (값, 인덱스) 쌍의 merge sort는 $\log_2 n$단계에 걸쳐 원소마다 "어느 쪽을 가져올까"를 정하는데, 무작위 데이터에서는 이 선택의 절반이 예측에 실패해요. 100만 개면 merge sort는 약 16단계, 단계마다 16바이트 쌍을 약 $1.5n$번 옮기고, 기수 정렬은 세기 1번과 흩뿌리기 최대 8번이에요. 흩뿌리기는 256개 구간에 나눠 쓰지만, 구간마다 쓰는 위치는 순서대로 늘어나요.

### 기준값: 1024와 128

기수 정렬에는 레인마다 고정 비용이 있어요. 키의 최솟값·최댓값을 구하는 패스, 카운터(최대 8 × 256개)를 비우고 누적합을 구하는 일이에요. 짧은 레인에서는 이 비용 때문에 비교 정렬보다 느려요. 아래 표는 $2^{20}$개의 int64를 길이 $n$인 레인으로 나눠 1스레드로 잰 결과예요.

| $n$ | 값: NEON | 값: 기수 | 쌍: merge sort | 쌍: 기수 |
|---:|---:|---:|---:|---:|
| 64 | 3.2ms | 14.7ms | 13.2ms | 15.2ms |
| 128 | 3.9ms | 10.1ms | 16.0ms | 10.6ms |
| 512 | 5.9ms | 6.4ms | 21.6ms | 6.9ms |
| 1024 | 6.8ms | 6.0ms | 24.3ms | 6.4ms |

그래서 값은 1024개(`kRadixMinValues`), 쌍은 128개(`kRadixMinPairs`)부터 기수 정렬이에요. 쌍의 기준이 낮은 이유는 비교 대상이 다르기 때문이에요. 값은 빠른 NEON 정렬과 비교하지만, 쌍은 NEON 정렬을 쓸 수 없어 merge sort와 비교해요.

float64 쌍의 기준도 128개예요. 같은 조건($2^{20}$개를 길이 $n$인 레인으로, 1스레드)에서 merge sort와 비교한 값이에요.

| $n$ | 쌍: merge sort | 쌍: 기수 |
|---:|---:|---:|
| 64 | 17.8ms | 22.7ms |
| 128 | 21.6ms | 16.6ms |
| $2^{20}$ (레인 하나) | 77.3ms | 10.9ms |

무작위 실수는 여덟 자리가 모두 달라 int64보다 흩뿌리기 패스가 많은데도, 128개부터 기수 정렬이 빨라요. 레인이 길수록 차이가 커져서, 레인 하나에서는 7배예요.

float64 값도 기수 정렬로 정렬해요. 데이터가 두 배인 쌍의 기수 정렬이 값의 NEON 정렬보다 빨랐어요(100만 개 1스레드: float `argsort` 10.2ms, NEON 정렬의 `sort` 13.3ms). 값의 기준은 int64와 같은 1024개예요. $-0.0$과 $+0.0$은 같은 키라서, 안정한 기수 정렬은 0들을 입력 순서대로, 부호 그대로 남겨요. 그래서 NEON 경로처럼 0의 부호를 따로 적어 둘 필요가 없어요.

이 기준은 넓은 범위의 데이터로 정한 값이에요. 좁은 범위에서는 자리 수가 줄어 기수 정렬이 더 일찍 이기지만, 그것을 보고 기준을 바꾸면 같은 길이의 배열이 값의 범위에 따라 다른 알고리즘을 타게 돼요.

기수 정렬을 쓰는 연산의 측정값이에요(100만 개, 1스레드).

| 연산 | stardust | numpy | 배율 |
|---|---:|---:|:---:|
| `sort(i)`, 넓은 범위 | 5.8ms | 19.1ms | 3.3× |
| `sort(i)`, $[-1000, 1000)$ | 2.5ms | 9.8ms | 3.9× |
| `argsort(i)`, $[-1000, 1000)$ | 2.7ms | 36.6ms | 13.6× |
| `argsort(f)`, 표준정규분포 | 10.3ms | 68.6ms | 6.7× |

`argsort(i)`가 13배 빠른 것은 stardust가 (값, 인덱스) 쌍을 비교 없이 기수 정렬로 옮기기 때문이에요. 범위가 좁아 두 자리로 끝나요. `argsort(f)`는 여덟 자리를 모두 흩뿌려도 numpy보다 6.7배 빨라요. numpy의 기본 `argsort`는 간접 비교 정렬이에요.

## 긴 레인 하나의 병렬 정렬

### 레인이 여럿이면 레인 단위로

2차원 배열의 행마다 정렬하는 것처럼 레인이 여럿이면, 레인끼리 독립이니 레인 단위로 스레드에 나눠요. 이터레이터가 "레인 하나 = 원소 $n$개 분량의 일"로 보고 나눠요. 2000행 × 2000열의 행마다 정렬은 1스레드 12.7ms, 10스레드 1.45ms, numpy 26.6ms예요. 14스레드에서는 1스레드의 9.7배까지 빨라져요.

### 레인 하나를 조각으로

레인이 하나뿐이면(1차원 100만 개의 `sort`) 레인 단위 분할로는 스레드를 쓸 수 없어요. 그래서 $2^{17}$개 이상인 레인은 레인 자체를 나눠요.

- 조각 크기는 $2^{16}$개(`kSortPiece`)이고, 길이로만 정해요. 스레드 수를 보지 않아요. $2^{15}$, $2^{16}$, $2^{17}$ 가운데 모든 경우에 가장 빠른 값은 없어서 가운데 값을 써요.
- 비교 정렬을 쓰는 경우(bool)에는 조각마다 직렬 알고리즘(NEON 정렬, merge sort 등 위의 선택 그대로)으로 병렬 정렬해요. 그다음 이웃한 런을 둘씩 병합하는 단계를 런이 하나가 될 때까지 반복해요. 100만 개면 조각 16개, 병합 4단계예요.

병합 단계도 병렬이어야 해요. 마지막 단계는 병합이 하나뿐이니, 병합 하나를 여러 스레드가 나눠 해야 해요. 그래서 병합 하나를 출력 구간 $2^{15}$개(`kMergeChunk`) 단위로 잘라 태스크로 만들어요. 문제는 출력 구간 $[k_0, k_1)$을 채우려면 두 런 $A$, $B$의 어디부터 읽어야 하는지 알아야 한다는 점이에요. 그 위치는 **merge path**[8]의 이진 탐색으로 찾아요.

출력의 첫 $k$개에 $A$에서 온 원소가 $i$개, $B$에서 온 원소가 $j = k - i$개라고 하면, $i$는 다음을 만족하는 값이에요(동점이면 $A$가 먼저).

$$
A[i-1] \le B[j] \quad \text{그리고} \quad B[j-1] < A[i]
$$

$i$에 대해 단조로운 조건이라 이진 탐색으로 $O(\log k)$에 찾아요.

```cpp
    // csrc/array/ops/sort.cpp, co_rank (줄인 발췌)
    std::int64_t lo = std::max<std::int64_t>(0, k - nb), hi = std::min(k, na);
    while (lo < hi) {
        const std::int64_t i = lo + (hi - lo) / 2, j = k - i;
        if (j > 0 && i < na && !less(B[j - 1], A[i])) lo = i + 1;  // A[i] goes before B[j-1]: take more of A
        else hi = i;
    }
    return lo;
```

태스크마다 구간의 시작 $k_0$과 끝 $k_1$에서 `co_rank`를 구해, 그 사이를 평범하게 병합해요. 모든 태스크가 서로 다른 출력 구간을 쓰니 동기화가 필요 없어요. 병합 루프에는 분기가 없어요.

```cpp
            // csrc/array/ops/sort.cpp, sort_long의 병합 루프 (줄인 발췌)
            while (i < i1 && j < j1) {  // branch-free: random data mispredicts half the time
                const bool take_b = less(B[j], A[i]);
                *out++ = take_b ? B[j] : A[i];
                j += take_b;
                i += !take_b;
            }
```

동점이면 왼쪽 런이 먼저예요(`less(B[j], A[i])`가 엄격). 왼쪽 런은 원래 배열에서 앞에 있던 원소이니, 안정 정렬된 런을 이렇게 병합하면 직렬 안정 정렬과 비트까지 같은 결과가 나와요.

### 기수 정렬: 병합 없이 자리마다 병렬

int64·float64 값과 쌍은 기수 정렬로 정렬해요. 여기에 조각 + 병합을 쓰면 오히려 느려요. 기수 정렬이 이미 빨라서 병합 패스가 더 비싸요(2스레드 7.4ms 대 1스레드 6.0ms). 그래서 기수 정렬의 각 자리를 병렬로 처리해요(`radix_sort_parallel`).

1. 세기(병렬): 조각 $t$마다 자리 값 $v$의 개수 $c_{t,v}$를 세요.
2. 시작 위치(직렬): "자리 값 순 → 조각 순"으로 누적해요.

   $$
   \text{pos}(t, v) = \sum_{v' < v} \sum_{t'} c_{t', v'} \;+\; \sum_{t' < t} c_{t', v}
   $$

3. 흩뿌리기(병렬): 조각마다 자기 시작 위치부터 써요.

같은 자리 값끼리는 조각 순서(= 원래 순서)대로 놓이니, 직렬 계수 정렬과 똑같은 안정 순서예요. 직렬판과 다른 점은 자리마다 세기 패스를 따로 한다는 것이에요. 최솟값과 최댓값도 조각마다 구해 합쳐요.

### 풀을 쓸 수 있을 때만 조각으로

조각 + 병합은 직렬 정렬에 없는 추가 패스예요. 1스레드에서도 언제나 조각을 쓰면 `sort(i)`가 5.8ms에서 13.6ms로, NEON 정렬의 `sort(f)`가 13.1ms에서 23.6ms로 느려졌어요. 그래서 스레드풀을 실제로 쓸 수 있을 때(`parallel::available()`)만 조각을 써요.

스레드가 있을 때만 다른 경로를 타면, 보통은 스레드 수에 따라 결과의 비트가 달라질 수 있어요. 여기서는 그런 일이 없어요. 안정 정렬의 결과는 하나로 정해지므로, 조각을 쓰든 안 쓰든 같은 비트가 나와요.

불안정 정렬은 이 전환을 할 수 없어요. 안정이 아니면 결과가 유일하지 않아요. introsort의 동점 순서는 조각 경계에 따라 달라지므로, 1스레드일 때 조각 없이 정렬하고 10스레드일 때 조각으로 정렬하면 결과가 달라져요. 그래서 불안정 정렬이 긴 레인을 만나면 1스레드에서도 언제나 조각으로 정렬해요. 이 경우가 실제로 생기는 것은 bool의 `argsort(stable=False)`뿐이에요. int64와 float64는 `stable=False`여도 안정 알고리즘(기수 정렬, 짧은 float 값의 NEON 정렬과 0의 부호 되쓰기)으로 가고, bool 값의 정렬은 같은 값이 비트까지 같아 동점 순서가 드러나지 않아요.

| 연산 (100만 개) | 1스레드 | 10스레드 | numpy |
|---|---:|---:|---:|
| `sort(i)` int64 | 2.5ms | 1.0ms | 9.8ms |
| `argsort(f)` | 10.3ms | 4.3ms | 68.6ms |
| `argsort(i)` | 2.7ms | 1.3ms | 36.6ms |

10스레드에서 1스레드 대비 2–2.5배 빨라져요. 비교 정렬(bool)은 조각 정렬 뒤에 직렬 정렬에 없는 병합 단계(100만 개면 4단계)가 붙고, 단계마다 레인 전체를 읽고 써요. 기수 정렬은 자리마다 세기와 흩뿌리기 사이에 직렬 누적합이 끼고, 흩뿌리기는 메모리 대역폭에 묶여 스레드를 늘려도 덜 빨라져요. 레인이 여럿이면 레인 단위로 나뉘어 이런 추가 비용이 없어요(2000행 정렬은 10스레드에서 1스레드의 8.5배).

## argsort와 numpy의 기본값

`argsort`의 기본값은 양쪽이 달라요. stardust는 `stable=True`이고, numpy 2.5.4의 `np.argsort`는 `kind='quicksort'`(안정이 아닌 간접 정렬)예요. 측정은 양쪽 모두 기본 인자로 해요. 그래도 비교가 공정한 것은, stardust의 float64·int64 `argsort`가 `stable=False`여도 같은 기수 정렬을 쓰기 때문이에요.

원소 100만 개 `argsort(f)`는 numpy 68.6ms, 1스레드 10.3ms, 10스레드 4.3ms예요.

- `stable=False`라고 더 빠르지는 않아요. 16개 이하와 128개 이상의 쌍에는 불안정 정렬을 따로 두지 않으니 같은 경로이고 같은 결과예요. 동점 인덱스의 순서가 상관없는 사용자도 손해 보지 않아요.
- numpy의 불안정 정렬보다도 빨라요. 불안정 정렬은 비교 정렬이라 $O(n \log n)$번 비교하고, 무작위 데이터에서 분기의 절반이 예측에 실패해요. 기수 정렬은 비교 없이 패스 몇 번으로 끝나요.

## ±0이 섞인 안정 정렬

### 문제: 구별되는 동점은 0뿐이에요

`sort`는 float64 값을 언제나 안정 정렬의 결과로 정렬해요(`stable=False`도 같은 경로예요). 값만 정렬할 때 안정 정렬과 NEON 정렬의 결과가 갈릴 수 있는 곳은 한 군데예요. NaN을 떼어 낸 레인에서 두 float64 $a$, $b$가 `a == b`이면서 비트가 다른 경우는 $\{-0.0, +0.0\}$ 한 쌍뿐이에요. 그러니 0이 아닌 값들은 어떤 정렬 알고리즘을 쓰든 결과의 비트열이 하나로 정해져요. 달라질 수 있는 것은 0끼리의 부호 순서 하나예요.

정렬된 결과에서 0은 한 구간에 모여요. 레인에 음수가 $m$개, 0이 $k$개 있으면 오름차순 결과는

$$
\underbrace{r_0 \le \dots \le r_{m-1}}_{\text{음수 } m\text{개}} \;<\; \underbrace{r_m = \dots = r_{m+k-1} = 0}_{\text{0 구간 } k\text{개}} \;<\; \underbrace{r_{m+k} \le \dots}_{\text{양수}}
$$

예요. 안정 정렬은 같은 값의 입력 순서를 지키므로, 0 구간의 $j$번째 칸에는 입력에서 $j$번째로 나온 0이 그 부호 그대로 들어가요. NEON 정렬의 결과는 0 구간의 위치와 길이가 같고(같은 값들의 정렬이니까요), 그 안에서 `-0.0`과 `+0.0`이 놓인 순서만 다를 수 있어요.

### 방법: 0의 부호를 비트로 적어 두었다가 되쓰기

그래서 0 구간만 고쳐 쓰면 안정 정렬의 결과가 돼요. 0 구간에 들어갈 값은 모두 0이니, 적어 둘 정보는 0마다 부호 한 비트면 충분해요. $j$번째로 나온 0의 부호를 비트 배열의 $j$번째 비트에 적어요(`csrc/array/ops/sort.cpp`의 `zero_signs`와 `sort_values_serial`).

```cpp
// csrc/array/ops/sort.cpp (줄인 발췌)
struct ZeroSigns {
    std::vector<std::uint64_t> bits;
    std::int64_t count = 0, negative = 0;
};
inline ZeroSigns zero_signs(const double* a, std::int64_t n) {
    ZeroSigns z;
    z.bits.assign(static_cast<std::size_t>(n / 64 + 1), 0);
    std::uint64_t* w = z.bits.data();
    std::int64_t c = 0, neg = 0;
    for (std::int64_t i = 0; i < n; ++i) {
        const std::uint64_t is_zero = a[i] == 0.0;
        const std::uint64_t sign = std::signbit(a[i]) ? 1 : 0;
        w[c >> 6] |= (sign & is_zero) << (c & 63);
        c += static_cast<std::int64_t>(is_zero);
        neg += static_cast<std::int64_t>(sign & is_zero);
    }
    z.count = c, z.negative = neg;
    return z;
}
        // ...
        if (n >= kSimdMin) {
            ZeroSigns zeros;  // when a stable sort could tell the zeros apart
            bool rewrite = false;
            if constexpr (ops::is_float<T>) {
                if (stable) {
                    zeros = zero_signs(a, n);
                    rewrite = zeros.negative > 0 && zeros.negative < zeros.count;
                }
            }
            simd_sort::sort<std::conditional_t<ops::is_float<T>, simd_sort::F64, simd_sort::I64>>(a, n);
            if (descending) std::reverse(a, a + n);  // ties are indistinguishable here
            if constexpr (ops::is_float<T>) {
                if (rewrite) {
                    T* z0 = descending ? std::partition_point(a, a + n, [](T v) { return v > 0; })
                                       : std::partition_point(a, a + n, [](T v) { return v < 0; });
                    const std::uint64_t* w = zeros.bits.data();
                    for (std::int64_t k = 0; k < zeros.count; ++k) {
                        const std::uint64_t bit = (w[k >> 6] >> (k & 63)) & 1;
                        z0[k] = std::bit_cast<T>(bit << 63);  // +0.0 or -0.0
                    }
                }
            }
            return;
        }
```

코드의 `stable`은 float64면 언제나 참이에요. 값 정렬의 입구(`sort_values`)가 float64의 `stable=False`를 참으로 바꿔 넘기기 때문이에요.

1. 훑으며 적기. `zero_signs`가 레인을 한 번 읽으면서 세 가지를 한꺼번에 해요. 0의 개수를 세고, `-0.0`의 개수를 세고, 0을 만날 때마다 그 부호를 다음 비트에 적어요. "두 부호가 다 있는가"를 알아내는 읽기와 부호를 적는 읽기가 같은 패스예요.
2. 고칠지 정하기. `-0.0`이 하나도 없거나 0이 전부 `-0.0`이면 0끼리도 비트가 같아 고칠 것이 없어요. 대부분의 데이터가 이 경우이고, 적어 둔 비트는 쓰지 않고 버려요.
3. 정렬. NEON 정렬을 그대로 돌려요. 내림차순이면 뒤집어요.
4. 0 구간 찾기. 정렬된 배열에서 `std::partition_point`(이분 탐색, $O(\log n)$)로 첫 0의 위치를 찾아요. 오름차순이면 "음수가 끝나는 곳", 내림차순이면 "양수가 끝나는 곳"이에요.
5. 되쓰기. 그 자리부터 0의 개수만큼, $k$번째 칸에 $k$번째 비트로 만든 0을 써요. float64에서 `+0.0`은 64비트가 모두 0이고 `-0.0`은 맨 위 부호 비트만 1이라, 비트를 63칸 올린 정수를 `std::bit_cast`로 double로 읽으면 바로 그 값이에요.

훑는 루프에는 분기가 없어요. 원소가 0인지에 따라 갈리는 `if` 없이, 비교 결과(0 또는 1)를 그대로 산술에 써요. 0이 아닌 원소에서는 비트 배열에 0을 OR하고 카운터에 0을 더하니 아무것도 바뀌지 않아요. 분기가 없다는 점은 0이 많은 데이터에서 중요해요. 0이 절반쯤 무작위로 흩어져 있으면 "0인가"로 갈리는 분기는 두 번에 한 번꼴로 예측이 틀려요.

부호 대신 0 자체를 모아 둘 수도 있어요. 값이 0인 원소를 입력 순서대로 double 배열에 복사해 두었다가 그대로 덮어써도 결과는 같아요. 하지만 0 하나에 8바이트가 들고, 0이 몇 개인지 미리 모르니 배열이 자라면서 다시 할당돼요. 원소 100만 개의 절반이 0이면 4MB를 쓰고 읽는 일이에요. 비트로 적으면 0 하나에 1비트라 같은 입력에서 약 62.5KB이고, 크기를 처음에 $\lfloor n/64 \rfloor + 1$워드로 한 번에 잡아요(0이 $n$개여도 들어가요). 100만 개 레인이면 125KB로 L2 캐시에 머물러요.

내림차순에서도 0 구간은 입력 순서예요. 안정 내림차순은 "오름차순 안정 정렬을 뒤집은 것"이 아니라, 값은 큰 것부터 놓되 같은 값끼리는 입력 순서를 지키는 정렬이에요. 그래서 0 구간에는 오름차순과 똑같이 0이 입력 순서대로 들어가요. NEON 정렬 결과를 뒤집으면 0 구간 안의 순서도 뒤집히지만, 어차피 통째로 덮어쓰므로 상관없어요.

1024개 이상의 레인에는 이 과정이 없어요. float 값은 기수 정렬로 가고, 기수 정렬은 $-0.0$과 $+0.0$을 같은 키로 보고 안정하게 옮기므로 0 구간이 처음부터 입력 순서예요.

`quantile`과 `median`이 쓰는 전순서 정렬(`sort_float64_total`)도 NEON 정렬 뒤에 0 구간을 고쳐 써요. 그쪽은 입력 순서가 아니라 "`-0.0`이 먼저"로 써요([통계 함수](/internals/array/statistics/)).

### 비용

훑기는 32~1023개 float64 값을 NEON 정렬로 정렬하면 `stable`과 상관없이 언제나 하는 $O(n)$ 읽기 패스 한 번이고, 비트 배열 $\lfloor n/64 \rfloor + 1$워드($n/8$바이트)를 써요. 두 부호가 섞여 있을 때만 0의 개수 $k$만큼의 되쓰기 $O(k)$가 더 들어요. 정렬 자체가 $O(n \log n)$이라 훑기 한 번은 그에 비해 작은 몫이에요.

numpy의 기본 `np.sort`는 안정 정렬이 아니라서 0의 부호 순서를 지키지 않아요. stardust는 이 짧은 레인에서도 0의 부호를 입력 순서로 지켜요.

## unique_*

### 정렬 기반: 평탄화 → 안정 정렬 → 이웃 비교

`unique_inverse`와 `unique_all`은 `unique_parts` 하나로 계산해요. `unique_counts`는 위치가 필요 없어서 `unique_values`처럼 값만 정렬해요(아래).

1. 평탄화: C 순서로 연속이면 x 그대로, 아니면 C 순서 복사본을 만들어요.
2. NaN 분리: `load_split_nans`로 (값, 원래 위치) 쌍을 채우면서 NaN을 맨 뒤로 보내요(원래 순서대로).
3. 안정 정렬: NaN이 아닌 앞부분 $m$개를 `sort_keyed`로 안정 정렬해요. int64와 float64는 128개 이상에서 기수 정렬이에요.
4. 묶음 찾기: 정렬된 순서에서 이웃과 값이 다른 자리가 새 묶음의 시작이에요. NaN 구간 전체는 마지막 묶음 하나예요.
5. 결과 만들기: 묶음 $k$가 정렬 순서의 $[\text{begin}_k, \text{end}_k)$를 차지하면

   $$
   \text{values}[k] = \text{buf}[\text{begin}_k].\text{value}, \quad \text{indices}[k] = \text{order}[\text{begin}_k], \quad \text{counts}[k] = \text{end}_k - \text{begin}_k
   $$

   이고, 묶음 안의 모든 $i$에 대해 $\text{inverse}[\text{order}[i]] = k$예요. 묶음을 약 4096원소 분량씩 조각으로 나눠 병렬로 써요(`for_pieces`). 원소마다 묶음이 하나뿐이라 `inverse`의 각 칸은 한 번만 쓰여요.

원소가 32768개 이상이면 정렬과 묶음 찾기는 GIL을 놓고 해요.

### 처음 나온 것이 대표

이 방식은 3단계가 안정 정렬이라서 성립해요. 같은 값의 묶음 안에서 원소는 x에서의 순서대로 놓이니, 묶음의 첫 원소가 곧 x에서 처음 나온 원소예요.

- `indices`(첫 등장 위치)가 따로 계산 없이 나와요.
- `-0.0`과 `+0.0`은 같은 값이라 한 묶음인데, 대표값은 먼저 나온 쪽이에요.
- NaN 묶음의 대표값은 x에서 처음 나온 NaN을 비트 그대로 쓴 값이에요. NaN끼리는 비교하지 않으니(4단계는 NaN이 아닌 부분에서만 비교해요), 페이로드가 다른 NaN도 같은 묶음이에요. 추가 비용도 없어요.
- complex는 (실수부, 허수부) 사전순으로 정렬하고, 어느 한쪽이 NaN이면 NaN 묶음이에요.

```python
>>> import stardust as sd
>>> sd.unique_values(sd.asarray([0.0, -0.0, 1.0]))
array([0.0, 1.0], dtype=float64)
>>> sd.unique_values(sd.asarray([-0.0, 0.0, 1.0]))
array([-0.0,  1.0], dtype=float64)
>>> sd.unique_all(sd.asarray([2.0, float("nan"), 0.0, float("nan"), -0.0]))
UniqueAllResult(values=array([0.0, 2.0, nan], dtype=float64), indices=array([2, 0, 1], dtype=int64), inverse_indices=array([1, 2, 0, 2, 0], dtype=int64), counts=array([2, 1, 2], dtype=int64))
```

numpy 2.5.4의 `np.unique`는 정렬된 결과의 첫 원소를 보여 줘요. `np.unique([0.0, -0.0, 1.0])`과 `np.unique([-0.0, 0.0, 1.0])`이 둘 다 `[-0., 1.]`이에요. 정렬 알고리즘이 $\pm 0$을 어떻게 놓느냐에 달린 값이라 입력 순서로 예측할 수 없어요. stardust는 frame과 같이 "처음 나온 값"을 대표로 써요.

### unique_values와 unique_counts는 값만 정렬

`unique_values`는 위치도 개수도 필요 없어요. `unique_counts`도 위치는 필요 없고, 개수는 정렬된 값에서 같은 값 구간의 길이예요. 그래서 둘 다 쌍이 아니라 값만 안정 정렬하고, 제자리에서 압축해요(`sorted_groups`).

```cpp
            // csrc/array/ops/sort.cpp, sorted_groups (발췌)
            sort_values(buf.get(), m, /*stable=*/true, /*descending=*/false);
            // Compact in place: keep the first of every run of equal values.
            for (std::int64_t i = 0; i < m; ++i) {
                if (i == 0 || !same(buf[groups - 1], buf[i])) {
                    buf[groups++] = buf[i];
                    if constexpr (Counts) counts.push_back(1);
                } else if constexpr (Counts) {
                    ++counts.back();
                }
            }
            if (m < n) {  // the NaNs: one value, the first NaN of x
                buf[groups++] = buf[m];
                if constexpr (Counts) counts.push_back(n - m);
            }
```

옮길 데이터가 절반(8바이트 대 16바이트)이에요. 값만 정렬하니 위에서 본 빠른 경로도 쓸 수 있어요. int64와 float64는 1024개 이상에서 기수 정렬, 그보다 짧으면 NEON 정렬이에요($\pm 0$이 섞여 있으면 0 구간을 입력 순서로 되써요). 둘 다 결과가 안정 정렬과 같으니 "처음 나온 값" 규칙이 그대로 지켜져요. `unique_counts`도 쌍을 정렬해 쓰지 않는 `inverse`까지 만들면 `unique_values`의 약 5배가 걸려요(int64 $10^7$개, 1000종, 10스레드: 48.8ms 대 9.2ms).

$[0, 1000)$의 int64라면 범위가 1000이라 기수 정렬이 두 자리로 끝나요. 10스레드에서는 기수 정렬만 병렬이고 NaN 분리와 압축은 직렬이에요.

### 해시 기반 경로를 두지 않는 이유

값의 종류를 세는 데는 해시 테이블이 흔히 쓰이지만, stardust에는 해시 경로가 없어요.

- int64는 기수 정렬로 이미 numpy보다 빨라요. `unique_counts`가 값 1000종일 때 3.9ms 대 8.4ms, 모두 다른 값일 때 9.3ms 대 20ms예요.
- 해시는 값 종류가 적으면 더 빠를 수 있지만, 모두 다르면 테이블이 커져 캐시 미스로 느려질 수 있어요. 종류 수를 보고 경로를 고르면 같은 크기의 배열이 데이터에 따라 몇 배씩 다른 시간이 걸려 성능을 예측하기 어려워요.
- 정렬 기반은 결과가 정렬된 순서로 나오고, "처음 나온 값" 규칙도 안정성에서 공짜로 나와요. 해시로 같은 결과를 내려면 결과를 다시 정렬해야 해요.

복잡도는 int64와 float64면 $O(d \cdot n)$(기수 정렬), 그 밖은 $O(n \log n)$이고, `unique_inverse`·`unique_all`의 추가 공간은 쌍 버퍼 $n$개 + 위치 배열 $n$개 + inverse $n$개예요. 묶음 찾기는 직렬이고, 결과 쓰기는 묶음 조각으로 병렬이에요.

## 작업 버퍼

### 짧은 레인은 스레드별 scratch

`(100000, 32)` 배열을 `sort(axis=1)`하면 길이 32인 레인을 10만 번 정렬해요. 레인마다 작업 버퍼를 `malloc`하면 할당 비용이 정렬 비용보다 커져요. 그래서 17개 이상, 64KB(`kScratchBytes`) 이하의 레인은 **스레드별 scratch**를 써요. 16개 이하의 레인은 버퍼 없이 스택에서 정렬 네트워크로 정렬해요(위).

```cpp
// csrc/array/ops/sort.cpp, LaneBuffer
template <typename T>
class LaneBuffer {
public:
    LaneBuffer(std::int64_t n, int slot) {
        if (n * static_cast<std::int64_t>(sizeof(T)) <= kScratchBytes) {
            thread_local std::unique_ptr<std::byte[]> mem =
                std::make_unique_for_overwrite<std::byte[]>(static_cast<size_t>(2 * kScratchBytes));
            ptr_ = reinterpret_cast<T*>(mem.get() + slot * kScratchBytes);
        } else {
            heap_ = buffer<T>(n);
            ptr_ = heap_.get();
        }
    }
    T* get() const { return ptr_; }
    T& operator[](std::int64_t i) const { return ptr_[i]; }

private:
    std::unique_ptr<T[]> heap_;
    T* ptr_;
};
```

- 함수 안의 `thread_local` 정적 변수는 스레드마다 하나씩 있고, 그 스레드가 처음 지나갈 때 한 번만 초기화돼요. 그래서 한 스레드는 128KB를 한 번 할당한 뒤 계속 재사용해요. 클래스 템플릿 안에 있으니 원소 타입 `T`마다 따로예요. 한 스레드가 차지하는 scratch는 타입마다 최대 2 × 64KB예요.
- scratch는 슬롯 두 개로 나뉘어요. 슬롯 0은 레인 자체(`sort_lane`, `argsort_lane`), 슬롯 1은 merge sort의 왼쪽 반 복사본이나 기수 정렬의 임시 버퍼예요. 한 레인을 정렬하는 동안 두 버퍼가 동시에 필요하니 겹치지 않게 나눠요.
- 스레드풀 워커에서도 안전해요. 레인 하나는 한 스레드가 처음부터 끝까지 처리하므로, 다른 스레드와 scratch를 공유할 일이 없어요.
- `buffer<T>`는 `std::unique_ptr<T[]>`예요. `std::vector<bool>`은 비트로 압축된 특수화라 `data()` 포인터가 없어 `bool*`로 정렬할 수 없어요. 그래서 모든 dtype에 같은 형태의 버퍼를 써요.

NEON 정렬은 자기 버퍼를 따로 가져요(채운 길이 256 이하면 스택, 위 참고). 긴 레인의 병렬 정렬은 병합용으로 $n$개짜리 버퍼를 하나 할당해요.

## searchsorted, nonzero, take

`csrc/array/ops/searching.cpp`에 있는, 정렬 순서와 인덱싱을 쓰는 함수들이에요.

### searchsorted

정렬된 `x1`에서 `x2`의 각 값이 들어갈 자리를 찾아요.

- **x1은 있는 그대로 찾아요.** 이진 탐색이 읽는 키 하나하나를 그 자리에서 승격한 dtype으로 바꿔요(`assign`이 하는 변환과 같아요). x1을 승격한 dtype의 연속 복사본으로 만들면, int64 x1에 float 값을 찾거나 x1이 strided일 때 호출마다 $O(n)$이 들어요. 찾기 자체는 $O(\log n)$인데요. `sorter`가 있으면 먼저 `x1[sorter]`로 모아요(인덱싱의 gather).
- **찾을 값(x2)은** 승격한 dtype의 연속 배열이 아니면 한 번 복사해요. Python 스칼라 x2는 리스트와 `asarray`를 거치지 않고 바로 변환해요(같은 변환 함수라 OverflowError 규칙이 같아요).
- 비교 함수는 `sort`의 순서와 같아요(NaN이 가장 커요).

  $$
  \text{before}(a, b) = (a < b) \;\lor\; (\text{isnan}(b) \land \lnot\,\text{isnan}(a))
  $$

  `left`는 $\lnot\,\text{before}(x_1[i], v)$인 첫 $i$, `right`는 $\text{before}(v, x_1[i])$인 첫 $i$예요. 둘 다 "값 앞에 오는 키의 수"로 쓸 수 있어서, 답은 `below(k, v)`인 키의 개수예요. NaN은 정렬된 배열 끝의 NaN 묶음 앞(`left`) 또는 뒤(`right`)를 찾아요.

**분기 없는 이진 탐색을 8개씩 나란히** 해요.

```cpp
                    // csrc/array/ops/searching.cpp (searchsorted의 group)
                    auto group = [&]<int L>(std::int64_t j) {
                        std::int64_t base[L] = {};
                        for (std::int64_t len = n; len > 1;) {
                            const std::int64_t half = len / 2;
                            for (int l = 0; l < L; ++l)
                                base[l] = below(key(base[l] + half), v[j + l]) ? base[l] + half : base[l];
                            len -= half;
                        }
                        for (int l = 0; l < L; ++l) o[j + l] = base[l] + below(key(base[l]), v[j + l]);
                    };
```

- 길이를 반씩 줄이며 선택 하나로 시작점을 옮겨요. 비교 결과로 갈라지는 분기가 없어서 예측 실패가 없어요.
- 값 8개(`kLanes`)는 같은 길이 순서를 밟으므로 한 루프에서 함께 돌아요. 서로 독립인 키 읽기 8개가 동시에 진행되어, 키 배열이 캐시를 넘을 때 캐시 실패 8개가 겹쳐요. 값 하나씩 찾으면 서로 기대는 캐시 실패의 사슬이 값마다 생겨요. 키 배열이 캐시를 넘을수록 이득이 커요.
- 찾을 값이 많으면 병렬로 나눠요. 일의 양을 $m \cdot \lfloor \log_2(n + 1) \rfloor$로 어림해 $2^{15}$ 이상이고 풀이 비어 있으면, 4096개씩(`kParallelTask`) 태스크로 나눠요. 결과가 정수 위치라 나누는 방법과 상관없이 같아요.

복잡도는 x2의 변환 $O(m)$와 찾기 $O(m \log n)$예요.

### nonzero

0이 아닌 원소의 위치를 축마다 int64 배열로 돌려줘요. 마스크 인덱싱과 같은 두 단계 구조예요.

1. x가 C 순서로 연속이면 그대로, 아니면 자기 dtype으로 C 순서 복사본을 만들어요.
2. C 순서를 $2^{16}$개(`kNonzeroChunk`) 조각으로 나눠 조각마다 참의 수를 세요(병렬).
3. 누적합으로 조각마다 쓸 자리를 정하고, 조각마다 채워요(병렬).

채우기는 분기가 없어요.

```cpp
            // csrc/array/ops/searching.cpp, nonzero의 1차원 채우기 (줄인 발췌)
            std::int64_t k = start[t];
            const std::int64_t end_k = start[t + 1];
                // ...
                constexpr std::int64_t kRun = 16;
                for (; i + kRun <= e; i += kRun) {
                    std::int64_t c = 0;
                    if constexpr (std::is_same_v<T, bool>) {
                        const uint8x16_t v = vld1q_u8(reinterpret_cast<const std::uint8_t*>(p + i));
                        c = vmaxvq_u8(v) == 0 ? 0 : vminvq_u8(v) != 0 ? kRun : 1;  // 1: some, not all
                    } else {
                        for (std::int64_t j = 0; j < kRun; ++j) c += truthy(p[i + j]);
                    }
                    if (c == 0) continue;
                    if (c == kRun) {
                        for (std::int64_t j = 0; j < kRun; ++j) o[k + j] = i + j;
                        k += kRun;
                        continue;
                    }
                    for (std::int64_t j = 0; j < kRun; ++j) {
                        if (k < end_k) o[k] = i + j;
                        k += truthy(p[i + j]);
                    }
                }
```

- 1차원은 16개 블록마다 참의 수를 먼저 세요. bool이면 NEON 최대 하나와 최소 하나로 "하나도 없음", "모두 참", "섞임"을 가려요. 하나도 없으면 블록을 건너뛰고, 모두 참이면 위치 16개를 연달아 쓰고, 섞여 있을 때만 아래 루프를 돌아요. 희소한 마스크(1% 참)에서는 원소마다의 저장이 사라져요.
- 섞인 블록과 다차원은 모든 위치를 `o[k]`에 쓰고, 참일 때만 `k`를 늘려요. 마스크 압축과 같은 기법이에요. 무작위 마스크에서 "참이면 쓰기" 분기는 예측이 빗나가요. 분기 없이 쓰면 예측 실패가 없어요.
- 참의 수를 세는 첫 패스도 bool이면 바이트 카운터에 16개씩 더해요(`count_nonzero`와 같은 방법).
- `k < end_k` 검사는 조각의 마지막 참 다음에 다음 조각의 자리를 쓰지 않게 막아요. 이 조건은 마지막 참 이후에만 거짓이 되니 거의 언제나 같은 쪽으로 가서 예측이 잘 맞아요. 마스크 압축이 작은 버퍼를 쓰는 것과 같은 문제를 다른 방법으로 푼 것이에요.
- 다차원이면 원소마다 축 수만큼 위치를 쓰지 않아요. 마지막 축의 위치만 원소마다 쓰고, 앞 축의 위치는 한 행 안에서 같으니 행이 끝날 때 그 행의 출력 구간 전체를 `std::fill`로 한 번에 채워요. 원소마다 축 수만큼 쓰는 것보다 저장이 훨씬 적어요.
- 조각 수는 크기로만 정하고, 원소 수가 $2^{15}$ 이상이고 조각이 둘 이상일 때 병렬로 돌아요(`for_pieces`). 위치는 정수라 결과가 나누는 방법과 상관없어요.

### take와 take_along_axis

- `take(x, indices, axis=k)`는 키 `(:, …, :, indices)`(앞에 slice `k`개)를 만들어 인덱싱의 gather를 불러요([인덱싱](/internals/array/indexing/)). 1차원이면 `gather_one`, 아니면 `gather_take`로 가요. 인덱싱이 내는 IndexError를 C++ 예외로 바꿔 다시 던지는데(`gather_named`), 그래야 바인딩이 메시지 앞에 "take(): "를 붙여요.
- `take_along_axis`는 결과를 메모리 순서대로 원소별로 돌아요. x를 그 축의 stride를 0으로 둔 뷰로 보면, 결과의 각 위치는 자기 레인의 첫 원소 `x[..., 0, ...]`를 가리켜요. 거기에 `index * stride`를 더해 원소를 읽어요.

  ```cpp
          // csrc/array/ops/searching.cpp, along_loop (줄인 발췌). args: x(축 stride 0), indices, out
          std::int64_t k = *reinterpret_cast<const std::int64_t*>(args[1] + i * s[1]);
          if (k < 0) k += c.n_x;
          *reinterpret_cast<T*>(args[2] + i * s[2]) = *reinterpret_cast<const T*>(args[0] + i * s[0] + k * c.x_stride);
  ```

  어느 축을 따라 고르든 결과 메모리를 순서대로 지나고, 이터레이터가 병렬로 나눠요. 레인 단위로 돌면 C 순서 행렬의 `axis=0`에서 2.5배 느려요. 범위 검사는 먼저 한 번, 조각별로 분기 없이(`b |= q[i] < -n || q[i] >= n`) 병렬로 해요. 나쁜 것이 있을 때만 C 순서로 첫 번째를 찾아 메시지를 만들어요. 같은 일을 다차원 고급 인덱싱으로 하는 것보다 1스레드 3.5배, 10스레드 12배 빨라요.

## 성능

정렬과 `unique_*`의 1스레드 값과 그 원인을 모았어요(원소 100만 개, numpy 2.5.4, 기본 인자).

| 연산 | 1스레드 | numpy | 주된 원인 |
|---|---:|---:|---|
| `sort(i)`, 넓은 범위 | 5.8ms | 19.1ms | 기수 정렬, 비교 없음 |
| `sort(i)`, $[-1000, 1000)$ | 2.5ms | 9.8ms | 기수 정렬, 최솟값을 빼서 두 자리 |
| `argsort(f)` | 10.3ms | 68.6ms | (값, 인덱스) 쌍의 기수 정렬. numpy는 간접 비교 정렬. `stable=False`도 같은 경로 |
| `argsort(i)`, $[-1000, 1000)$ | 2.7ms | 36.6ms | 쌍의 기수 정렬, 두 자리 |
| 2000행 × 2000열의 행마다 `sort` | 12.7ms | 26.6ms | 레인 단위로 나눠 10스레드 1.45ms |
| `unique_counts`, 값 1000종 | 3.9ms | 8.4ms | 값만 기수 정렬 + 제자리 압축 |

알고리즘별 복잡도예요. $n$은 레인 길이, $d$는 기수 정렬의 자리 수($d \le 8$), $m$은 찾을 값의 수예요.

| 알고리즘 | 시간 | 추가 공간 | 안정 |
|---|---|---|:---:|
| NaN 분리 | $O(n)$, 두 번 읽기 | 레인 버퍼 $n$ | 예 |
| 정렬 네트워크 (16개 이하) | 비교기 최대 63개 | 없음 (스택) | `argsort`는 예, `sort`는 0의 부호를 되써서 안정과 같음 |
| NEON 정렬 | $O(n \log n)$, 병합 패스 $\lceil \log_2(n/8) \rceil$번 | $2n$ (256 이하는 스택) | 아니요 |
| 0 구간 되쓰기 (float64 값, 32–1023개) | 훑으며 부호 적기 $O(n)$. 두 부호가 섞여 있으면 되쓰기 $O(k)$ | 부호 비트 $n/8$바이트 | NEON 정렬의 결과를 안정 정렬과 같게 만들어요 |
| LSD 기수 정렬 (int64, float64) | $O(d \cdot (n + 256))$ | $n$ + 카운터 $8 \times 256$ | 예 |
| merge sort | $O(n \log n)$ | $n/2$ | 예 |
| introsort | 평균·최악 $O(n \log n)$ | 스택 $O(\log n)$ | 아니요 |
| 긴 레인 병렬 정렬 (비교 정렬) | 조각 정렬 + 병합 $\lceil \log_2(n / 2^{16}) \rceil$단계, 각 $O(n)$ | $n$ | 조각 알고리즘을 따름 |
| 긴 레인 병렬 기수 정렬 | 자리마다 세기·흩뿌리기를 조각별 병렬, 누적합은 직렬 $O(256 \cdot n/2^{16})$ | $n$ + 조각별 카운터 | 예 |
| `unique_*` | 정렬 + $O(n)$ | $3n$ 정도 | — |
| `searchsorted` | $O(m \log n)$ | x2의 복사본 $m$(필요할 때만) | — |
| `nonzero` | $O(N)$ 두 번 | 결과 | — |

## 정확도

정렬은 계산 없이 값을 옮기기만 하므로 값은 비트 그대로 보존돼요.

- 안정 정렬의 결과는 하나로 정해져요. 그래서 `sort`와 `argsort`의 기본(`stable=True`) 결과는 numpy의 `kind='stable'` 결과와 같아야 해요. NaN, `-0.0`/`+0.0`, 반복값이 섞인 float64 배열과 반복값이 많은 int64 배열(길이 10부터 30만까지)로 numpy 2.5.4의 `np.sort(kind='stable')`, `np.argsort(kind='stable')`와 비교하면 `sort`는 바이트까지, `argsort`는 인덱스까지 모두 같아요.
- int64와 float64는 `stable=False`여도 17–127개의 `argsort`를 빼면 안정 정렬과 같은 결과예요. 그래서 numpy의 기본(불안정) `np.sort`, `np.argsort`와는 동점 원소의 순서(float `sort`에서는 $\pm 0$의 순서)가 다를 수 있지만, `kind='stable'`과는 같아요. 불안정 정렬이 실제로 쓰이는 것은 17–127개의 쌍과 17개 이상인 bool의 `argsort(stable=False)`뿐이고, 이때도 긴 레인은 언제나 같은 조각으로 정렬하므로 같은 입력이면 스레드 수와 상관없이 같은 결과예요.
- 병렬 정렬의 결과는 직렬 정렬과 비트까지 같아요. 테스트가 1, 2, 3, 7, 10스레드에서 같은 바이트가 나오는지 확인해요([스레드풀과 결정성](/internals/core/threads/)).
- `unique_*`의 대표값은 첫 등장 값이라 numpy와 다를 수 있어요(`-0.0`/`+0.0`, complex NaN). 값의 집합과 개수는 같아요.
