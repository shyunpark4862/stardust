## 한눈에 보기

`x[key]`와 `x[key] = value`는 Python의 `__getitem__`, `__setitem__`이 C++ 함수 `getitem`, `setitem`(`csrc/array/ops/indexing.cpp`)을 바로 부르는 것으로 시작해요. Python 층에는 인덱싱 코드가 한 줄도 없어요. 키를 해석하는 일부터 원소를 옮기는 일까지 모두 C++에서 해요.

`getitem`은 세 단계로 일해요.

1. 빠른 경로 시도(`leading_ints_fast`): 키가 `x[1]`, `x[1, 2]`처럼 앞쪽 축에 놓인 Python int뿐이면 키 해석을 건너뛰고 오프셋을 바로 계산해요.
2. 키 해석(`make_plan`): 키의 항목을 하나씩 분류하고, 기본 항목(int, slice, `...`, `None`)을 적용해 **뷰**(`Plan::view`)를 만들어요. 고급 항목(정수 배열, bool 마스크)은 그 뷰의 연속한 축 범위로 남겨 둬요.
3. 실행: 고급 항목이 없으면 뷰(또는 Python 스칼라)를 그대로 돌려줘요. 있으면 경우에 따라 다른 루프로 새 배열을 채워요.

| 키의 모양 | 처리 | 결과 |
|---|---|---|
| 앞쪽 축의 Python int만 (`x[1, 2]`) | `leading_ints_fast`: 오프셋 직접 계산 | 원소(스칼라) 또는 뷰 |
| int, slice, `...`, `None` | `make_plan`: data 포인터·shape·strides만 다시 계산 | 뷰, 모든 축이 int면 스칼라 |
| 1차원 뷰 + 정수 배열 하나 (`f[idx]`) | `gather_one`: 합친 루프, 병렬 | 새 배열 |
| 정수 배열 하나 + 앞뒤 블록 (`m[:, rows]`) | `gather_take`: 결과 shape 위의 원소별 연산 하나 | 새 배열 |
| 정수 배열 여럿, dtype 변환 | 일반 경로: 오프셋을 1024개씩 만들어 바로 소비 | 새 배열 |
| bool 마스크 하나가 유일한 고급 항목 | 고정 청크 두 단계 + 분기 없는 압축 | 새 배열 |

설계의 뼈대는 네 가지예요.

- 기본 인덱싱은 계산이지 복사가 아니에요. 결과는 같은 메모리를 다르게 읽는 "설명"일 뿐이라, 1GB 배열을 잘라도 비용은 축 수에만 비례해요.
- 흔한 경우에는 합친 루프를 따로 둬요. 일반 경로는 어떤 키든 처리하지만 원소마다 하는 일이 많아요. `f[idx]`, `m[:, rows]`, `f[mask]`처럼 실제로 자주 쓰는 모양은 전용 루프로 보내요.
- 쓰기 전에 모두 검사해요. `x[idx] = v`는 범위 밖 인덱스가 하나라도 있으면 아무것도 쓰지 않아요. 검사가 루프 밖에 있으니 루프에는 에러 경로가 없어요.
- 병렬이어도 결과는 직렬과 비트까지 같아요. 마스크는 크기로만 정한 고정 청크로 나누고, 반복 인덱스가 있을 수 있는 scatter는 아예 나누지 않아요. 스레드 수에 따라 결과가 바뀌는 일이 없어요([스레드풀과 결정성](/internals/core/threads/)).

## 키 해석

### 항목 분류: `classify`

키가 튜플이면 각 원소를, 아니면 키 자체를 항목 하나로 보고 `classify`가 다섯 종류(`Kind`) 중 하나로 분류해요. 검사 순서가 곧 규칙이에요.

| 순서 | 검사 | 결과 |
|:---:|---|---|
| 1 | `None` | `NewAxis` |
| 2 | `Ellipsis` | `Ellipsis` |
| 3 | `PySlice_Check` | `Slice` |
| 4 | `PyBool_Check` | IndexError |
| 5 | stardust ndarray | `Array` (int64 또는 bool만) |
| 6 | 문자열·바이트가 아닌 시퀀스 (리스트, 튜플, numpy 배열 등) | `asarray`로 바꾼 뒤 `Array` |
| 7 | `__index__`가 있는 객체 (int, `numpy.int64` 등) | `Int` |
| 8 | 그 밖 | IndexError |

이 가운데 몇 가지 규칙에는 설명이 필요해요.

- Python bool은 int보다 먼저 걸러요. Python에서 `True`는 `int`의 하위 클래스라 `__index__`가 있어요. 4번 검사가 없으면 7번에서 `x[True]`가 `x[1]`이 돼요. numpy는 bool 스칼라를 0차원 마스크로 읽어요. stardust에는 0차원 배열이 없으니, 그렇게 읽으면 `x[1]`과 헷갈리기만 해요. 그래서 에러로 처리해요. bool 배열은 마스크로 받아요.
- 빈 리스트는 따로 처리해요. `asarray([])`는 float64 배열이 되는데, float 배열은 인덱스가 될 수 없어요. 인덱스 자리의 빈 리스트는 "고를 위치가 없음"이라는 뜻이 분명하므로 길이 0인 int64 배열로 바꿔요.
- `str`과 `bytes`는 시퀀스지만 인덱스로 쓰일 일이 없어요. 6번에서 시퀀스로 받으면 이상한 배열이 만들어지므로 미리 빼요.
- 너무 큰 int는 `PyLong_AsLongLongAndOverflow`가 넘침을 알려 주면 IndexError("index is out of bounds")로 처리해요. 범위를 벗어난 인덱스와 같은 종류의 실수로 봐요.
- 인덱스 배열의 dtype은 int64와 bool만 받아요. float 배열을 쓰면 "arrays used as indices must be of integer or boolean type, not float64" 에러가 나요.

### 고정 용량 저장소: `Items`

분류한 항목은 `Item` 구조체(종류, 원래 객체, int 값, 배열 객체, 마스크 여부)로 저장해요. 이것을 `std::vector<Item>`에 담으면 `x[1, 2]` 같은 짧은 키에서는 벡터가 커지며 하는 힙 할당이 비용의 대부분을 차지해요. 그래서 용량이 정해진 저장소 `Items`에 담아요.

키 하나에 들어갈 수 있는 항목 수에는 상한이 있어요. 축을 쓰는 항목(int, slice, 배열)은 최대 32개(차원 수 상한 `kMaxNdim`), `None`도 결과가 32차원을 넘지 않으니 최대 32개, `...`은 1개예요. 그래서 용량은 $2 \times 32 + 1 = 65$로 충분해요.

```cpp
// csrc/array/ops/indexing.cpp, Items (줄인 발췌)
class Items {
    static constexpr int kCapacity = 2 * kMaxNdim + 1;
    void push_back(Item&& it) { new (slot(n_++)) Item(std::move(it)); }
    Item& operator[](int i) { return *std::launder(reinterpret_cast<Item*>(slot(i))); }
    ~Items() { for (int i = 0; i < n_; ++i) (*this)[i].~Item(); }
    alignas(Item) std::byte storage_[kCapacity * sizeof(Item)];  // push 전까지 초기화하지 않음
    int n_ = 0;
};
```

여기에는 C++의 저수준 기능이 몇 가지 쓰여요.

- `std::array<Item, 65>`로 두면 생성할 때 65개의 `Item`을 모두 만들어요. `Item`에는 `nb::object`(Python 참조)가 있어 생성자와 소멸자가 공짜가 아니에요. 그래서 초기화하지 않은 바이트 배열을 두고, 실제로 넣는 항목만 placement new(`new (주소) Item(...)`)로 만든 뒤 소멸자에서 그만큼만 부숴요.
- `alignas(Item)`은 바이트 배열의 시작을 `Item`의 정렬 단위에 맞춰요. 그래야 그 자리에 `Item`을 만들 수 있어요.
- `std::launder`는 placement new로 만든 객체를 원래 바이트 배열 포인터에서 `reinterpret_cast`로 꺼낼 때, 컴파일러에게 "이 주소에는 새 객체가 있다"고 알려 주는 C++17 함수예요. 없으면 표준상 미정의 동작이 될 수 있어요.
- 복사 생성자와 대입은 `delete`해서 실수로 통째 복사되는 일을 막아요.

이 저장소는 함수의 스택에 놓이므로 키 해석에 힙 할당이 없어요(배열 항목을 `asarray`로 바꾸는 경우는 빼고요).

### 키 전체 검사

항목을 다 분류하면 키 전체를 한 번 훑어요.

- `...`이 둘 이상이면 IndexError예요.
- 축을 쓰는 항목의 수(마스크는 자기 차원 수만큼 써요)가 `x.ndim`보다 많으면 IndexError예요.
- 배열 옆의 int는 고급 인덱스예요. numpy와 같은 규칙이에요. 키에 배열이 하나라도 있으면 int도 "길이 1인 인덱스 배열"로 바뀌어요.
- 고급 항목은 붙어 있어야 해요. 첫 고급 항목과 마지막 고급 항목 사이에 slice, `None`, `...`이 끼어 있으면 IndexError예요. 이 규칙은 [아래](#고급-인덱스가-떨어져-있으면-에러예요)에서 자세히 다뤄요.

### `Plan` 만들기

검사를 통과하면 항목을 왼쪽부터 적용해 `Plan`을 만들어요.

```cpp
// csrc/array/ops/indexing.cpp
struct Plan {
    NDArray view;                  // 기본 항목을 적용한 뷰
    int first = 0;                 // 고급 항목이 가리키는 축의 시작 (view 기준)
    std::vector<NDArray> indices;  // 축마다 int64 인덱스 배열 하나
    bool mask_only = false;        // bool 마스크 하나가 유일한 고급 항목인가
    NDArray mask;
};
```

원본 배열 `a`의 축을 가리키는 커서 `src`를 옮겨 가며 항목마다 아래 표대로 처리해요. 여기서 $s_d$는 `a`의 축 $d$의 stride(바이트 단위), $n_d$는 그 축의 길이예요.

| 항목 | data 포인터 | view에 추가하는 축 | `src` |
|---|---|---|:---:|
| int $i$ | $i < 0$이면 $i + n_d$, 범위 검사 후 $+\,i \cdot s_d$ | 없음 (축이 사라짐) | +1 |
| slice | 길이가 0이 아니면 $+\,\text{start} \cdot s_d$ | 길이 $m$, stride $\text{step} \cdot s_d$ | +1 |
| `None` | 그대로 | 길이 1, stride 0 | 0 |
| `...` | 그대로 | 남은 축을 그대로 | +남은 축 수 |
| 고급 항목 | 그대로 | 가리키는 축을 통째로 남김 | +1 (마스크는 +ndim) |

마지막에 키가 건드리지 않은 뒤쪽 축은 그대로 남겨요. 그래서 `x[0]`은 `x[0, ...]`과 같아요.

고급 항목은 view에서 축을 지우지 않고 남겨 둬요. 그 축들은 view 안에서 연속한 범위 $[\text{first}, \text{first} + k)$를 이뤄요($k$는 인덱스 배열의 수). 인덱스 배열들은 서로 브로드캐스트되어 "인덱스 shape" $B$가 되고, 결과 shape는 이렇게 정해져요.

$$
\text{result.shape} = \text{view.shape}[:\text{first}] \;+\; B \;+\; \text{view.shape}[\text{first} + k:]
$$

인덱스 배열들이 서로 브로드캐스트되지 않으면 IndexError("shape mismatch: indexing arrays could not be broadcast together with shapes ...")예요. 브로드캐스트 자체는 ValueError를 내지만, 인덱스 모양이 틀린 것은 인덱스의 잘못이므로 IndexError로 바꿔요. 마스크의 shape가 맞지 않을 때와 같은 종류예요.

마스크는 브로드캐스트하지 않아요. 마스크의 각 축 길이가 가리키는 축의 길이와 정확히 같아야 해요.

### 빠른 경로: `leading_ints_fast`

`x[1, 2]`나 `x[1]` 같은 호출은 흔하고, 일반 경로로 처리하면 시간 대부분을 오프셋 계산이 아니라 준비 작업(Items 만들기, Plan 만들기, 뷰 복사)에 써요. 그래서 키가 "앞쪽 축의 정확한 Python int"뿐이면 키 해석 전체를 건너뛰어요.

```cpp
// csrc/array/ops/indexing.cpp, leading_ints_fast (줄인 발췌)
for (Py_ssize_t d = 0; d < n; ++d) {
    if (!PyLong_CheckExact(items[d])) return {};          // bool, numpy.int64 등은 일반 경로로
    long long i = PyLong_AsLongLongAndOverflow(items[d], &overflow);
    if (overflow) return {};
    if (i < 0) i += a.shape[d];
    if (i < 0 || i >= a.shape[d]) return {};               // 에러는 일반 경로가 낸다
    p += i * a.strides[d];
}
if (n == a.ndim) return load_python(a.dtype, p);           // 원소 하나: Python 스칼라
// 아니면 남은 축의 뷰
```

- `PyLong_CheckExact`는 하위 클래스를 받지 않아요. `bool`은 `int`의 하위 클래스라 여기서 저절로 빠지고, 일반 경로에서 정해진 에러를 내요.
- 실패하면 에러를 내지 않고 빈 객체를 돌려줘요. 범위 밖 인덱스나 너무 큰 int는 일반 경로가 다시 처리해 평소와 똑같은 메시지를 내요. 빠른 경로에 에러 메시지를 따로 두면 두 경로의 메시지가 어긋날 수 있어요.
- 일반 경로로 가면 `x[1, 2]`에 58ns가 들어요. 빠른 경로로는 25ns이고, numpy는 33ns예요. 남은 비용은 [작은 배열의 호출 비용](/internals/array/small-arrays/)에서 다뤄요.

`for v in x`처럼 배열을 반복할 때는 키를 아예 만들지 않아요. 반복자가 `item_along_axis0(x, i)`를 불러 축 0을 한 칸씩 걸어요. 하는 일은 `x[i]`의 빠른 경로와 같아요.

## 기본 인덱싱: 뷰 계산

### 원소의 주소

stardust 배열은 메모리 블록을 어떻게 읽을지 적은 설명이에요([데이터 모델](/internals/array/data-model/)). 원소 $(i_0, \dots, i_{k-1})$의 주소는 이렇게 계산해요.

$$
\text{addr}(i_0, \dots, i_{k-1}) = \text{data} + \sum_{d=0}^{k-1} i_d \cdot s_d
$$

기본 인덱싱은 이 식의 `data`, shape, $s_d$만 바꿔서, 원래 원소 중 일부를 가리키는 새 설명을 만들어요. 메모리는 건드리지 않아요.

슬라이스 `start:stop:step`을 축 $d$에 적용하면, 새 축의 $j$번째 원소는 원래 축의 $\text{start} + j \cdot \text{step}$번째 원소예요. 주소식에 넣으면 이렇게 돼요.

$$
\text{data} + (\text{start} + j \cdot \text{step}) \cdot s_d = \underbrace{(\text{data} + \text{start} \cdot s_d)}_{\text{새 data}} + j \cdot \underbrace{(\text{step} \cdot s_d)}_{\text{새 stride}}
$$

새 길이 $m$은 Python C API의 `PySlice_Unpack`과 `PySlice_AdjustIndices`가 계산해요[1]. 음수 start/stop, 생략된 값, 범위를 넘는 값의 처리가 Python 리스트의 슬라이스와 정확히 같아져요. 양의 step이면 $m = \max(0, \lceil (\text{stop} - \text{start}) / \text{step} \rceil)$예요.

몇 가지 경계 상황이 있어요.

- 음수 step인 `x[::-1]`은 start가 $n - 1$이 되어 data가 마지막 원소로 가고, stride가 $-s_d$가 돼요. 음수 stride도 주소식에는 아무 문제가 없어요.
- 빈 슬라이스는 start가 배열 밖일 수 있어요(`x[10:]`). 이때는 data를 옮기지 않아요. 원소를 읽을 일은 없지만, 버퍼 끝을 넘는 포인터를 만들지 않으려는 것이에요.
- `None`은 길이 1, stride 0인 축을 끼워 넣어요. 길이가 1이라 stride는 아무 값이어도 되지만 0으로 둬요.
- 모든 축이 int면 결과가 0차원이 되는데, stardust에는 0차원 배열이 없어요. 그래서 그 자리의 원소를 Python 스칼라로 읽어 돌려줘요(`load_python`). `Plan::view`는 내부에서 잠깐 ndim이 0일 수 있지만 밖으로 나가지 않아요.

끝으로 `update_flags()`가 연속성 플래그를 다시 계산하고, 결과 뷰의 `.base`는 메모리의 최종 소유자를 가리켜요. 뷰의 뷰를 만들어도 중간 뷰를 거치지 않아요.

기본 인덱싱의 비용은 키 길이와 차원 수에 비례하는 $O(\text{ndim})$이고 배열 크기와 무관해요. 뷰가 무엇이고 언제 복사가 일어나는지는 API 문서 [뷰](/api/array/views/)에 있어요.

## 고급 인덱스가 떨어져 있으면 에러예요

numpy에는 고급 인덱스가 slice로 떨어져 있으면 인덱스 축을 결과의 맨 앞으로 옮기는 규칙이 있어요[2]. 그런데 "배열 옆의 int도 고급 인덱스"라는 규칙과 겹치면 결과가 직관과 어긋나요. numpy 2.5.4에서 `x = np.arange(24).reshape(2, 3, 4)`로 보면 이래요.

| 키 | 고급 항목 | 붙어 있나 | numpy 결과 shape |
|---|---|:---:|:---:|
| `x[:, 0, [1, 2]]` | `0`, `[1, 2]` | 예 | (2, 2) |
| `x[0, :, [1, 2]]` | `0`, `[1, 2]` | 아니요 | **(2, 3)** |

두 번째는 "0번 판에서 1, 2번 열을 골라 (3, 2)"를 기대하기 쉽지만, 인덱스 축(길이 2)이 맨 앞으로 가서 (2, 3)이 돼요. stardust는 이 규칙을 두지 않고 파싱 단계에서 거부해요.

```text
IndexError: advanced indices (arrays, and ints next to them) separated by a slice,
newaxis or ellipsis are not supported; index in two steps, e.g. x[0][:, idx]
```

메시지가 두 단계로 나누는 방법을 바로 알려 줘요. `x[0]`은 뷰라서 비용이 거의 없어요.

```python
>>> import stardust as sd
>>> x = sd.reshape(sd.arange(24), (2, 3, 4))
>>> x[0][:, sd.asarray([1, 2])]
array([[ 1,  2],
       [ 5,  6],
       [ 9, 10]], dtype=int64)
```

이렇게 하면 결과 shape 규칙이 하나로 줄어요. 고급 항목은 언제나 붙어 있으므로, 인덱스 shape $B$는 언제나 "인덱싱한 축들이 있던 자리"에 들어가요. 구현에서도 "축을 맨 앞으로 옮긴 결과 레이아웃"이라는 경우가 사라져, gather와 scatter의 모든 경로가 위의 결과 shape 식 하나만 다루면 돼요.

## 정수 배열: gather

정수 배열로 읽는 것(`x[idx]`)을 gather라고 불러요. 흩어진 자리에서 원소를 모아 새 배열을 만드는 일이에요. 결과는 언제나 새 배열(복사본)이에요.

### 결과의 레이아웃: `advanced_result`

결과 배열의 메모리 순서는 view를 따라요. 원소별 연산의 결과가 입력의 메모리 순서를 따르는 것과 같은 규칙이에요(numpy의 `order='K'`에 해당).

- view의 축은 자기 stride 크기 순서를 유지해요.
- 인덱스 축 $B$는 인덱싱한 축들의 자리, 그중 가장 바깥(stride 절댓값이 가장 큰) 축의 위치에 들어가고, $B$의 축끼리는 C 순서예요.

구현은 "가짜 원본" `proto`를 만들어 `new_array_like`에 넘기는 방식이에요. `proto`의 strides는 view에서 가져오되, $B$ 축에는 인덱싱한 축들의 stride 중 최대값을 줘요. `new_array_like`가 stride 크기 순서로 축 순서를 정하니, 결과가 view와 같은 순서로 배치돼요.

그런데 gather 루프는 $B$를 한 덩어리로 다뤄요. 인덱스 점 $b$(C 순서 번호)의 블록이 결과에서 $b \times (\text{마지막 } B \text{ 축의 stride})$ 바이트에 있다고 가정해요. 길이 1인 축이나 stride 0인 축 때문에 `new_array_like`가 $B$ 축들 사이에 다른 축을 끼워 넣으면 이 가정이 깨지므로, 이를 검사해 가정이 깨지면 C 순서 결과로 돌아가요.

이 규칙이 왜 필요한지는 F 순서 배열에서 드러나요. `mT[:, rows]`(`m`은 C 순서 1000×1000, `mT`는 그 전치라 F 순서)를 C 순서 결과에 채우면, 읽는 쪽은 열을 따라 연속인데 쓰는 쪽은 1000원소씩 건너뛰어요. view를 따르는 F 순서 결과에 채우면 양쪽 다 연속이에요. C 순서 결과에 채우면 386µs, view를 따르는 결과에 채우면 114µs예요(numpy 149µs).

numpy는 C 순서 `m[:, rows]`에도 F 순서 결과를 만들어요(numpy 2.5.4: `C_CONTIGUOUS=False`, `F_CONTIGUOUS=True`). stardust는 C 순서 원본이면 C 순서 결과예요. 어떤 입력이든 "결과는 원본의 메모리 순서를 따른다"는 한 문장으로 설명돼요.

### 경로 1: 1차원 view와 인덱스 배열 하나 (`gather_one`)

`f[idx]`처럼 1차원 view에 인덱스 배열 하나, 원소 하나씩 옮기는 경우가 가장 흔해요. 이 경우만을 위한 합친 루프가 있어요.

```cpp
// csrc/array/ops/indexing.cpp, gather_one_loop (줄인 발췌)
template <typename T>
void gather_one_loop(std::byte* const* args, std::int64_t n, const std::int64_t* s, void* ctx) {
    const OneIndex& c = *static_cast<const OneIndex*>(ctx);
    bool bad = false;
    for (std::int64_t t = 0; t < n; ++t) {
        std::int64_t i = wrap_index(load_as<std::int64_t>(args[0] + t * s[0]), c.len);  // 음수 보정
        const bool oob = static_cast<std::uint64_t>(i) >= static_cast<std::uint64_t>(c.len);
        bad |= oob;                     // 분기 없이 표시만
        i = oob ? 0 : i;                // 나쁜 인덱스는 0번으로 읽는다
        *reinterpret_cast<T*>(args[1] + t * s[1]) = load_as<T>(c.base + i * c.stride);
    }
    if (bad) c.bad->store(true, std::memory_order_relaxed);
}
```

- 범위 검사 한 번으로 양쪽을 막아요. 음수를 보정한 $i$를 부호 없는 정수로 바꾸면, 음수는 아주 큰 수가 돼요. 그래서 $0 \le i < n$ 검사가 비교 한 번(`(uint64)i >= (uint64)n`)이 돼요.
- 검사 패스가 따로 없어요. 나쁜 인덱스를 만나도 루프를 멈추지 않고, `bad`에 표시만 한 뒤 0번 원소를 읽어요. 메모리 밖을 읽지 않게만 하는 것이에요. 루프가 끝나고 `bad`가 서 있으면 그때 `check_indices`로 처음부터 다시 훑어 C 순서로 첫 번째 나쁜 인덱스를 찾아 메시지에 넣어요. gather의 결과는 새 배열이라, 에러가 나도 지켜야 할 기존 데이터가 없으니 이렇게 해도 돼요.
- 루프 안에 에러 분기가 없어요. `i = oob ? 0 : i`는 점프 없이 조건부 선택으로 계산할 수 있는 형태이고, 에러를 내는 경로는 루프 밖에 있어요.
- 스레드 사이의 표시는 `std::atomic<bool>`에 relaxed로 써요. 여러 스레드가 동시에 "나쁜 것이 있었다"를 쓸 수 있고, 누가 먼저였는지는 상관없어요. 값은 루프가 끝난 뒤(풀의 작업이 끝나 동기화된 뒤) 읽으므로 순서 보장이 필요 없어요.
- 축 길이가 0이면 미리 검사해요. 0번 원소조차 없으니 "0번으로 읽기"가 불가능해요. 이때는 모든 인덱스가 나쁘므로 루프 전에 에러를 내요.
- 루프는 이터레이터 위에서 돌아요. `NdIter(ix.shape, {ix, out}).run(...)`이라서, 인덱스 배열이 다차원이거나 strided여도 되고, 큰 경우 이터레이터가 알아서 여러 스레드로 나눠요([연산 엔진](/internals/array/engine/)). 출력 원소마다 독립이라 나눠도 결과가 같아요.
- dtype 디스패치는 `visit_dtype(v.dtype, [&]<typename T>(std::type_identity<T>) { ... gather_one_loop<T> ... })` 같은 템플릿 람다로 해요. C++20의 템플릿 람다라서, 런타임 dtype 값 하나가 컴파일 시점 타입 `T`로 바뀌고 dtype마다 루프가 하나씩 인스턴스화돼요.

전용 루프를 두는 이유는 일반 경로가 이 경우에 하는 일이 너무 많기 때문이에요. 일반 경로는 원소마다 "인덱스 배열 $k$개" 루프를 돌며 stride와 shape를 다시 읽고, 오프셋을 별도 버퍼에 썼다가 다시 읽어요. 원소당 명령어가 약 26개로, 합친 루프의 3.5배예요.

### 경로 2: 인덱스 배열 하나와 블록 (`gather_take`)

`m[:, rows]`, `m[rows]`, `t3[:, :, idx]`처럼 인덱스 배열은 하나인데 그 앞뒤로 통째로 남는 축(블록)이 있는 경우예요. 수식으로 쓰면 이래요.

$$
\text{result}[\text{pre}, b, \text{post}] = \text{view}[\text{pre}, \text{idx}[b], \text{post}]
$$

이 경우를 일반 경로처럼 인덱스 점마다 블록 하나를 이터레이터로 복사하면, 블록이 길고 연속일 때(`m[rows]`)만 괜찮아요. 블록이 짧으면(`p3[idx]`: 3원소 블록 30만 개) 블록마다 이터레이터를 하나씩 만들어 numpy보다 3.4배 느리고, 블록이 멀리 떨어져 있으면(`m[:, rows]`: strided 열 1000개를 C 순서 결과에 씀) 1.4배 느려요.

그래서 `gather_take`는 이것을 결과 shape 위의 원소별 연산 하나로 봐요. 피연산자가 셋이고, 각 축에서의 stride를 이렇게 줘요.

| 피연산자 | pre 축 | $B$ 축 | post 축 |
|---|---|---|---|
| view (인덱스 축을 뺀 것) | view의 stride | 0 | view의 stride |
| 인덱스 배열 | 0 | 인덱스의 stride | 0 |
| 결과 | 결과의 stride | 결과의 stride | 결과의 stride |

stride가 0인 축은 "그 축을 따라 가도 같은 자리를 가리킨다"는 뜻이에요(브로드캐스팅과 같은 기법). 그러면 커널은 각 위치에서 `view_base + idx * (인덱스 축 stride)`만 계산해 원소를 옮기면 돼요. 메모리 순서, 축 합치기(coalescing), 병렬 분할은 원소별 연산처럼 이터레이터가 정해요.

```cpp
// csrc/array/ops/indexing.cpp, take_loop (줄인 발췌). args: view(블록 기준), index, out
template <typename T>
void take_loop(std::byte* const* args, std::int64_t n, const std::int64_t* s, void* ctx) {
    const Take& c = *static_cast<const Take*>(ctx);
    if (s[1] == 0) {  // 이 구간 전체가 같은 인덱스: 블록 복사 (m[rows])
        const std::byte* src = args[0] + wrap_index(load_as<std::int64_t>(args[1]), c.len) * c.stride;
        if (s[0] == sizeof(T) && s[2] == sizeof(T)) std::memcpy(args[2], src, n * sizeof(T));
        else for (std::int64_t t = 0; t < n; ++t) /* strided 복사 */;
        return;
    }
    for (std::int64_t t = 0; t < n; ++t) {
        const std::int64_t i = wrap_index(load_as<std::int64_t>(args[1] + t * s[1]), c.len);
        *reinterpret_cast<T*>(args[2] + t * s[2]) = load_as<T>(args[0] + t * s[0] + i * c.stride);
    }
}
```

- 인덱스 검사는 먼저, $|B|$개만 해요. 결과 원소 수가 아니라 인덱스 수만큼이에요. `m[rows]`(인덱스 1000개, 결과 100만 원소)라면 검사는 1000번이에요. 검사를 먼저 하니 루프에는 에러 경로가 없어요.
- 안쪽 구간에서 인덱스 stride가 0이면 구간 전체가 같은 인덱스예요. `m[rows]`의 안쪽 축은 한 행 전체이고 그 행은 인덱스 하나로 정해지니까요. 이때는 오프셋을 한 번만 계산하고 `memcpy`해요.

| 연산 (m은 1000×1000) | 1스레드 | 10스레드 | numpy |
|---|---:|---:|---:|
| `m[:, rows]` (인덱스 1000개) | 332µs | 51µs | 486µs |
| `t3[:, :, idx]` | 198µs | 29µs | 230µs |
| `m[rows]` | 122µs | 32µs | 158µs |
| `p3[idx]` (3원소 블록 30만 개) | 2145µs | 303µs | 2709µs |
| `take(m, rows, axis=0)` | 122µs | 32µs | 111µs |

Apple M4 Pro에서 잰 값이에요. numpy에서는 같은 일을 하는 `take`가 `m[rows]`보다 빨라요. 그래서 stardust의 `m[rows]`는 numpy의 1.29배이지만 `take`는 0.91배예요.

### 경로 3: 일반 경로

인덱스 배열이 여럿이거나(`x[i, j]`), 블록 복사에 dtype 변환이 필요한 경우가 여기로 와요(scatter에서 값의 dtype이 다를 때 등). 인덱스 shape $B$를 C 순서로 걸으며 점마다 view 안의 블록 오프셋을 계산해요.

$$
\text{off}(b) = \sum_{j=0}^{k-1} \text{wrap}\big(\text{idx}_j[b]\big) \cdot s_{\text{first}+j}
$$

`for_each_offset_chunk`의 구조는 이래요.

- 브로드캐스트를 stride 0으로 표현해요. 인덱스 배열 $j$를 $B$로 늘린 모습은 stride 표 `st[j][d]`(늘어난 축은 0)로만 나타내고, 실제로 늘린 배열은 만들지 않아요.
- 마지막 $B$ 축은 빽빽한 안쪽 루프로, 나머지 축은 주행거리계(odometer) 방식으로 걸어요. 다차원 인덱스를 매번 나눗셈으로 구하지 않고, 자동차 주행거리계처럼 마지막 자리부터 올려 가며 포인터를 stride만큼 더하고 빼요.
- 오프셋은 1024개씩 스택 버퍼에 만들어 바로 소비해요. 원소 100만 개를 고를 때 오프셋 배열을 통째로 만들면 8MB를 쓰고 다시 읽어야 해요. 1024개(8KB)짜리 버퍼 두 개(view 오프셋, 값 오프셋)는 L1 캐시에 머물러요. 버퍼가 차면 `emit(voff, woff, n, b0)`을 불러 그 1024개를 처리하고 다시 채워요.
- 범위 검사는 오프셋을 만들 때 해요. 이 경로의 gather는 직렬이라 에러를 바로 내도 돼요. `[[unlikely]]` 속성으로 에러 분기를 차가운 경로로 표시해요.

블록 하나를 옮기는 방법은 `with_block_copy`가 호출당 한 번 골라 람다로 넘겨요.

| 블록 | dtype | 고르는 복사 |
|---|---|---|
| 원소 하나 (블록 ndim 0) | 같음 | 타입이 정해진 대입문 `*(T*)d = *(T*)s` |
| 원소 하나 | 다름 | 캐스트 커널(`cast_kernel`)을 원소 1개로 호출 |
| 여러 원소 | 무엇이든 | 블록 하나마다 `NdIter`로 캐스트 커널 실행 |

복사 방법을 람다로 넘기면, 점마다 도는 바깥 루프가 그 람다 타입으로 인스턴스화돼요(`[&](auto copy) { ... }`의 제네릭 람다). 첫 번째 경우에는 대입문이 루프 안에 인라인되어, 원소마다 함수 포인터로 커널을 부르는 비용이 사라져요.

일반 경로의 gather는 직렬이에요. 이 경로는 흔하지 않고, 위의 두 특수 경로가 실제로 많이 쓰는 경우를 병렬로 처리해요.

## 정수 배열: scatter

정수 배열로 쓰는 것(`x[idx] = v`)을 scatter라고 불러요. `setitem`에서 키에 고급 항목이 있으면 `scatter`로 와요. scatter가 보장하는 성질은 이 처리 순서에서 나와요.

1. 값을 배열로: Python 스칼라는 대상 dtype의 원소 1개짜리 배열이 되고, 그 밖의 것은 `asarray`를 거쳐요. dtype은 위로만 변환돼요(`check_assignable`, [변환과 승격](/internals/array/conversion/)). float 배열에 `1j`를 넣으면 TypeError예요.
2. 겹침 처리: 값, 인덱스 배열, 마스크가 대상과 메모리를 공유할 수 있으면 먼저 복사해요([아래](#메모리-겹침)).
3. 값을 결과 shape으로 브로드캐스트: 엄격한 규칙이에요([아래](#엄격한-브로드캐스팅)). 실제 복사 없이 stride 0으로 늘린 `w`를 만들어요.
4. 모든 인덱스를 검사: 쓰기 전에 끝내요.
5. 쓰기.

### 쓰기 전에 모두 검사: 전부 아니면 전무

4단계 덕분에 `x[idx] = v`는 전부 아니면 전무예요. 범위 밖 인덱스가 하나라도 있으면 아무것도 쓰지 않고 IndexError를 내요. 검사는 `check_indices`가 해요.

```cpp
// csrc/array/ops/indexing.cpp, check_loop (줄인 발췌)
bool bad = false;
for (std::int64_t t = 0; t < n; ++t)  // 분기 없음: 벡터화된다
    bad |= static_cast<std::uint64_t>(wrap_index(load_as<std::int64_t>(args[0] + t * s[0]), c.len)) >=
           static_cast<std::uint64_t>(c.len);
if (bad) c.bad->store(true, std::memory_order_relaxed);
```

- 이 루프도 이터레이터 위에서 돌아서 큰 인덱스 배열이면 여러 스레드로 나뉘어요.
- 루프 안에서 멈추지 않으니 분기가 없고, `bad |= ...`는 벡터 비교와 OR로 바뀌어요.
- 나쁜 것이 있으면 그때만 C 순서로 다시 훑어 첫 번째 나쁜 인덱스로 메시지를 만들어요. 그래서 메시지는 스레드 수와 무관하게 언제나 같은 인덱스를 가리켜요.

```python
>>> import stardust as sd
>>> a = sd.zeros(5)
>>> a[sd.asarray([1, 1, 1])] = sd.asarray([1.0, 2.0, 3.0])
>>> a
array([0.0, 3.0, 0.0, 0.0, 0.0], dtype=float64)
```

이어서 `a[sd.asarray([0, 7])] = 9.0`을 하면 "index 7 is out of bounds for axis 0 with size 5"가 나고, `a[0]`은 0.0 그대로예요.

### 마지막 쓰기가 이긴다

위 예에서 1번 자리에 1.0, 2.0, 3.0이 차례로 쓰여 3.0이 남았어요. stardust는 인덱스가 반복되면 C 순서로 마지막에 쓴 값이 남는다고 보장해요. 이를 위해 쓰기는 언제나 인덱스의 C 순서로, 한 스레드에서 해요.

- 1차원 view + 인덱스 하나 + 같은 dtype(`scatter_one_loop`)은 `NdIter(..., IterMode::Naive).run(..., Split::None)`으로 돌아요. `IterMode::Naive`는 이터레이터가 축 순서를 메모리 순서로 바꾸지 않고 C 순서를 지키게 하고, `Split::None`은 나누지 않게 해요.
- 일반 경로는 `for_each_offset_chunk`로 $B$를 C 순서로 걸으며 써요.

### scatter가 거의 병렬화되지 않는 이유

원소 100만 개, 인덱스 100만 개에서 `g[idx] = 1.0`은 1스레드 1.03ms, 10스레드 795µs예요(numpy 960µs). gather(`f[idx]`)가 1스레드 692µs, 10스레드 82µs로 8.4배 빨라지는 것과 대조적이에요.

이유는 위의 보장이에요. 쓰기를 여러 스레드로 나누면, 같은 자리에 쓰는 두 인덱스가 다른 스레드에 갈 때 어느 쪽이 나중에 쓸지 정해지지 않아요. 결과가 스레드 수와 실행 타이밍에 따라 달라지고, 같은 코드를 다시 돌려도 다른 값이 남을 수 있어요. 그러면 결과를 재현할 수도, 틀린 결과를 추적할 수도 없어요. gather는 출력 원소마다 쓰는 자리가 하나뿐이라 이런 문제가 없어요.

10스레드에서 조금 빨라지는 부분은 4단계의 인덱스 검사 패스예요. 검사는 쓰기가 없으니 병렬로 돌아요. 쓰기 루프 자체(무작위 위치에 100만 번 쓰기)는 직렬이고, 무작위 쓰기는 어차피 캐시 미스가 지배해요. 1스레드 기준으로는 numpy(0.96ms)와 비슷해요.

## bool 마스크

### 마스크는 좌표로 바꾸지 않아요

`x[mask]`는 정의상 `x[nonzero(mask)]`, 곧 True인 자리의 좌표 배열로 gather하는 것과 같아요. 그대로 구현하면 좌표 배열을 만들고(마스크 한 번 읽기 + 좌표 쓰기), 다시 그것을 읽어 gather해야 해요.

stardust는 마스크가 유일한 고급 항목이면 `Plan::mask_only`로 표시하고 마스크 자체로 적용해요. 마스크를 한 번 훑으며 True인 자리만 복사하는 압축(compress)이에요. 마스크가 다른 정수 배열과 함께 쓰이면(`x[mask, idx]`) 그때만 `mask_positions`로 좌표 배열을 만들어 정수 배열 경로로 보내요.

### 고정 청크 두 단계

압축을 여러 스레드로 나누려면 문제가 하나 있어요. 각 스레드가 결과의 어디부터 써야 하는지는 앞부분의 True 수에 달려 있어요. 그래서 두 단계로 해요.

마스크를 C 순서로 $2^{14} = 16384$원소(`kMaskChunk`) 청크로 나누고,

1. 세기(병렬): 청크마다 True 수 $c_t$를 세요(`count_mask`).
2. 누적합(직렬): $\text{start}_t = \sum_{u < t} c_u$. 청크 $t$의 선택분이 결과에서 시작하는 위치예요. 마지막 값이 결과 길이 $\text{total}$이에요.
3. 결과 할당 후 채우기(병렬): 청크마다 자기 구간만 걸으며 결과의 $[\text{start}_t, \text{start}_{t+1})$을 채워요.

```cpp
// csrc/array/ops/indexing.cpp, count_mask (줄인 발췌)
parallel::parallel_for(mc.chunks, [&](std::int64_t c) {
    std::int64_t count = 0;
    mask_runs(m, vs, c * kMaskChunk, std::min(size, (c + 1) * kMaskChunk), [&](auto mp, auto ms, auto, auto, auto n) {
        if (ms == 1) {  // 연속: 바이트 합
            const std::uint8_t* q = reinterpret_cast<const std::uint8_t*>(mp);
            std::uint32_t part = 0;  // 구간은 kMaskChunk를 넘지 않으므로 32비트로 충분
            for (std::int64_t t = 0; t < n; ++t) part += q[t];
            count += part;
        } else { /* strided: 원소마다 */ }
    });
    mc.start[c + 1] = count;
});
for (std::int64_t c = 0; c < mc.chunks; ++c) mc.start[c + 1] += mc.start[c];  // 누적합
```

- 세기는 바이트 합이에요. stardust의 bool은 언제나 0 또는 1인 바이트라, True 수는 바이트를 더한 값이에요. 컴파일러가 이 루프를 NEON 벡터 덧셈으로 바꿔요(손으로 짠 intrinsic은 아니에요). 구간 하나는 청크(16384원소)를 넘지 않으므로 구간의 합은 `uint32_t` 누산기로 넘치지 않아요.
- 청크는 마스크 크기로만 정해요. 스레드 수를 보지 않아요. 모든 원소가 C 순서의 자기 자리에 들어가므로, 결과는 몇 스레드로 돌든 직렬로 돈 것과 정확히 같아요.
- 청크가 하나면 병렬로 돌지 않아요. `parallel_for`는 태스크가 하나면 그냥 호출한 스레드에서 돌려요. 마스크 원소가 16384개를 넘어 청크가 둘 이상이 되면 풀을 써요. 스레드풀의 기준값(`kParallelThreshold`)이 아니라 청크 수로 정해지는 경로예요.

`mask_runs`는 청크 하나를 "마지막 마스크 축의 구간"들로 쪼개 넘겨줘요. 청크의 시작 번호를 나눗셈과 나머지로 다차원 인덱스로 바꾼 뒤, 마지막 축을 따라 구간 단위로 진행하고, 행이 끝나면 주행거리계로 다음 행으로 넘어가요. 그래서 다차원 마스크(`m[mask2d]`)도, view가 strided인 경우도 같은 코드로 처리해요.

### 조각마다 세 갈래: `mask_pieces`

연속 구간은 다시 256원소 조각으로 잘라, 조각마다 True 수를 먼저 세요(또 바이트 합, 벡터화). 그 수에 따라 방법을 골라요.

| 조각의 True 수 | 방법 | 이유 |
|:---:|---|---|
| 0 | 건너뜀 | 할 일이 없음 |
| 1–31 | sparse: 8바이트씩 읽어 0이면 8개를 건너뜀 (`for_true`) | 대부분 False라 건너뛰기가 이득 |
| 32 이상 | dense: 분기 없는 압축 | 원소마다 분기하면 예측이 틀림 |

strided 구간(마스크가 연속이 아닌 경우)은 조각으로 나누지 않고 통째로 sparse 경로로 가요.

sparse 경로의 `for_true`는 마스크 8바이트를 `uint64_t` 하나로 읽어(`memcpy`로, 정렬 걱정 없이) 0이면 8원소를 한 번에 건너뛰어요. 1%만 True인 마스크에서는 대부분의 8바이트 묶음이 0이라 분기가 거의 언제나 같은 쪽으로 가고, 예측이 잘 맞아요. 원소마다 분기를 하나씩 두면 1% 마스크의 `x[m]`이 numpy보다 3.5배 느려요.

### 분기 없는 압축: `compress_chunk`

dense 조각은 이 루프로 처리해요.

```cpp
// csrc/array/ops/indexing.cpp, compress_chunk의 dense 경로 (줄인 발췌)
T buf[256];
std::int64_t cnt = 0;
for (std::int64_t t = 0; t < m; ++t) {
    buf[cnt] = load_as<T>(p + t * vstep);  // 모든 원소를 일단 buf[cnt]에 쓴다
    cnt += q[t];                            // True일 때만 cnt가 1 늘어난다
}
std::memcpy(out + b * step, buf, cnt * sizeof(T));  // 결과로 한 번에
b += cnt;
```

모든 원소를 `buf[cnt]`에 쓰지만, `cnt`는 마스크 바이트가 1일 때만 늘어나요. False 원소는 다음 원소에 덮어써지고, True 원소만 자리를 지켜요. 루프 안에 조건문이 없어요.

이렇게 쓰는 데는 이유가 있어요.

- 분기 예측 때문이에요. 무작위로 절반이 True인 마스크에서 "True면 복사" 분기는 원소마다 50% 확률로 예측이 틀려요. 현대 CPU에서 예측 실패 한 번은 십수 사이클이 들어요. 분기 하나짜리 루프는 100만 원소에 2.2ms가 걸려요. 분기 없는 루프는 데이터와 상관없이 원소마다 같은 일을 해요.
- 결과가 아니라 작은 버퍼에 쓰는 것은 데이터 경합을 피하려는 것이에요. 결과에 바로 `out[cnt] = x[t]`로 쓰면, 청크의 마지막 원소가 False일 때 `out[start_{t+1}]`, 곧 다음 청크의 첫 자리에 한 칸을 써요. 다음 청크는 다른 스레드가 채우고 있을 수 있으니 데이터 경합이에요. 256원소짜리 스택 버퍼(float64면 2KB)에 쓰면 쓰기가 언제나 이 스레드의 버퍼 안에 머물러요. 버퍼는 L1에 있으니 `memcpy` 한 번의 추가 비용은 작아요.
- 압축 루프 자체는 NEON이 아니라 스칼라 명령으로 돌아요. ARM NEON에는 x86 AVX-512의 `vcompress` 같은 압축 명령이 없어요. 벡터화되는 것은 True 수를 세는 바이트 합이고, 압축은 "분기 없음"으로 빨라져요.

numpy 2.5.4의 `f[mask]`는 `array_boolean_subscript`(`numpy/_core/src/multiarray/mapping.c`)가 처리해요. 이 함수는 마스크에서 False 구간과 True 구간의 경계를 차례로 찾아 True 구간 단위로 복사해요[3]. 무작위 절반 마스크에서는 구간의 평균 길이가 2원소라, 구간마다 드는 분기와 호출 비용이 원소 단위로 들어요. numpy 3.37ms 대 stardust 340µs(9.9배)의 차이는 이 구조 차이에서 나와요.

<Callout type="warn" title="bool 바이트는 0 또는 1이어야 해요">
분기 없는 압축과 바이트 합은 마스크 바이트를 정수로 더해요. 바이트가 2나 255면 `cnt`가 그만큼 뛰어 결과가 틀려지고, 버퍼 밖에 쓸 수도 있어요. stardust가 만드는 bool은 언제나 0/1이고, 버퍼 프로토콜이나 DLPack으로 바깥에서 들어오는 bool 버퍼는 가져올 때 검사해서 0/1이 아닌 바이트가 있으면 정규화한 복사본을 만들어요([Python과 C++의 경계](/internals/core/python-boundary/)).
</Callout>

### 블록이 있는 마스크

`m[rowmask]`처럼 마스크 뒤에 통째로 남는 축이 있으면 원소가 아니라 블록(행)을 옮겨야 해요. 이때는 `walk_chunk`가 청크의 True 자리마다 `on_true(b, view_offset)`을 부르고, `with_block_copy`가 고른 복사 함수로 그 블록을 결과의 $b$번째 자리에 옮겨요. 청크 구조와 병렬 분할은 같아요.

### 마스크 대입: `expand_chunk`

`x[mask] = v`도 같은 두 단계 구조예요. 청크마다 x의 서로 다른 원소만 건드리니 청크끼리 독립이에요. dense 조각의 처리가 압축과 반대 방향("확장")이에요.

값이 스칼라일 때는 원소의 원시 비트에 비트 마스크를 적용해요.

```cpp
// csrc/array/ops/indexing.cpp, expand_chunk의 스칼라 경로 (줄인 발췌)
using W = std::conditional_t<sizeof(T) % 8 == 0, std::uint64_t, std::uint8_t>;
constexpr int kWords = sizeof(T) / sizeof(W);   // float64: 1, complex128: 2, bool: 1
for (std::int64_t t = 0; t < m; ++t) {
    W* e = reinterpret_cast<W*>(p + t * vstep);
    const W keep = static_cast<W>(q[t]) - 1;     // False(0) → 모든 비트 1, True(1) → 0
    for (int j = 0; j < kWords; ++j) e[j] = (e[j] & keep) | (val[j] & ~keep);
}
```

- 선택을 비트 연산으로 직접 써요. `*e = q ? val : *e`로 쓰면 컴파일러가 이것을 "q가 참일 때만 저장"하는 분기로 바꿔요(100만 원소에 2.2ms). 마스크 바이트 $q \in \{0, 1\}$에서 $q - 1$은 0이면 모든 비트가 1, 1이면 0이에요. 그러면

  $$
  e' = (e \mathbin{\&} \text{keep}) \mathbin{|} (v \mathbin{\&} \lnot\text{keep})
  $$

  는 False면 $e$, True면 $v$예요.
- 원소를 원시 워드로 다뤄요. float을 float으로 다루지 않고 정수 워드로 다루니, False 원소의 비트(NaN 페이로드, `-0.0`의 부호)가 비트 그대로 남아요. `std::conditional_t`로 워드 타입을 컴파일 시점에 골라, 8의 배수 크기(int64, float64, complex128)는 64비트 워드로, bool은 바이트로 처리해요.

값이 배열일 때는 `*e = q[t] ? w[b] : *e; b += q[t];`로 써요. 여기서는 False 원소에서도 `w[b]`를 읽어요. 그런데 선택의 마지막 True 다음에는 $b = \text{total}$이 되어 `w[total]`, 값 배열의 끝을 하나 넘는 자리를 읽을 수 있어요. 그래서 루프 안에서 매번 막는 대신, 선택의 마지막 True가 든 조각 하나(`b + trues == total`)만 sparse 경로로 보내요. 나머지 조각에서는 $b$가 언제나 total보다 작아요.

| 연산 (원소 100만 개) | 1스레드 | 10스레드 | numpy |
|---|---:|---:|---:|
| `f[s]` (1% True) | 96µs | 20µs | 233µs |
| `f[b] = 0.0` (절반 True) | 410µs | 56µs | 2930µs |

Apple M4 Pro에서 잰 값이에요. 절반이 True인 `f[mask]`는 [성능](#성능) 절에 있어요.

## 인덱스 대입

### 기본 키의 대입

키에 고급 항목이 없으면 `setitem`은 `make_plan`이 만든 view에 값을 써요.

- 쓰기 금지 검사가 맨 먼저예요. `broadcast_to`의 결과나 읽기 전용으로 가져온 버퍼는 `writeable=False`이고, 키를 해석하기 전에 ValueError("assignment destination is read-only")를 내요.
- 모든 축이 int라 원소 하나에 쓸 때는 값으로 Python 스칼라만 받아요. shape (1,)인 배열도 안 돼요. 엄격한 브로드캐스팅에서 (1,)은 ()로 줄어들 수 없기 때문이에요. 스칼라를 대상 dtype으로 바꿔 `memcpy`로 저장하고 끝이에요. 엔진을 거치지 않아요.
- 그 밖의 키는 값을 배열로 만들고, dtype 검사(위로만), 모양 검사(엄격) 후 `assign_checked`가 엔진으로 써요.
- 스칼라 값은 한 번만 변환해요. `x[:] = 1.0`이나 `x[::2] = 1.0`의 값은 stride 0으로 브로드캐스트된 원소 하나예요. 엔진의 캐스트 커널은 입력 stride가 0이면 값을 대상 dtype으로 한 번 바꾼 뒤, 연속 출력이면 `std::fill`, 아니면 저장만 하는 루프로 써요. 원소마다 입력을 다시 읽으면 컴파일러가 출력과 입력의 겹침을 의심해 벡터화하지 않아요([원소별 커널](/internals/array/elementwise/)). 원소 100만 개 `x[:] = 1.0`이 62µs로 numpy(62µs)와 같고, `x[::2] = 1.0`도 123µs로 numpy(123µs)와 같아요.

### 엄격한 브로드캐스팅

대입의 값은 고른 shape으로 브로드캐스트되는데, 규칙이 numpy보다 엄격해요. 값이 고른 영역보다 축이 많으면 안 돼요. 길이 1인 축을 늘리는 것과 앞에 축을 붙이는 것은 되지만, 앞쪽의 길이 1인 축을 떼어내지는 않아요.

```cpp
// csrc/array/ops/indexing.cpp, check_value_shape (줄인 발췌)
const std::ptrdiff_t off = indexed.size() - value.size();
if (off < 0) throw value_shape_error(value, indexed);          // 값의 축이 더 많음
for (size_t d = 0; d < value.size(); ++d)
    if (value[d] != 1 && value[d] != indexed[d + off]) throw value_shape_error(value, indexed);
```

그래서 `a[sd.asarray([0, 1])] = sd.asarray([[1.0, 2.0]])`는 "cannot broadcast a value of shape (1, 2) to the indexed shape (2,)"예요. numpy는 앞쪽 길이 1인 축을 떼어내고 받아들여요. stardust가 받지 않는 것은 일반 브로드캐스팅과 같은 규칙을 쓰기 때문이에요. `x + y`에서 결과의 축 수가 줄어들지 않듯, 대입에서도 값의 축이 사라지지 않아요. 고급 키에서는 같은 규칙을 `scatter` 안에서 stride를 만들며 적용해요(늘어나는 축에 stride 0).

### 메모리 겹침

`x[i] = x[::-1]`처럼 값이 대상과 메모리를 공유하면, 앞에서 쓴 원소를 뒤에서 값으로 다시 읽어 결과가 틀려져요. stardust는 "모든 값을 다 읽은 다음 쓴 것"과 같은 결과를 보장해요.

- 판정은 보수적이에요. `may_share_memory`는 두 배열이 닿을 수 있는 바이트 범위 $[\text{lo}, \text{hi})$가 겹치는지 보고, 겹치면 stride의 최대공약수로 엇갈린 뷰(짝수 칸과 홀수 칸)를 가려내요([데이터 모델](/internals/array/data-model/)). 그래도 실제로는 서로 다른 원소만 건드리는데 겹친다고 보는 경우가 남지만, 그때는 복사가 한 번 더 들 뿐 결과는 맞아요.
- 같은 뷰를 제자리에 대입하면 아무것도 하지 않아요. `x[i] op= y`의 마지막 단계인 `x[i] = (이미 고쳐 쓴 뷰 x[i])`가 이 경우예요.
- 겹치면 임시 배열로 복사한 뒤 써요.
- 값만이 아니라 인덱스 배열과 마스크도 검사해요. `a[a] = 2`(정수 배열 `a`가 자기 자신의 인덱스)를 생각해 보면, 앞의 쓰기가 뒤에서 읽을 인덱스를 바꿔요. 의미가 틀리는 것보다 더 나쁜 일도 있어요. 인덱스는 4단계에서 이미 범위 검사를 통과했는데, 쓰기 중에 그 인덱스가 범위 밖 값으로 바뀌면 검사 없는 쓰기 루프가 배열 밖 메모리에 써요. 그래서 인덱스 배열과 마스크가 대상과 겹치면 쓰기 전에 복사해, 대입 전의 x 값으로 읽은 인덱스를 써요.

| 연산 | 시간 | 추가 공간 |
|---|---|---|
| 기본 인덱싱 | $O(\text{ndim} + \text{len(key)})$ | $O(1)$ (뷰) |
| gather (정수 배열) | $O(\lvert B \rvert \cdot L)$ | 결과 + $O(1)$ (일반 경로는 오프셋 버퍼 16KB) |
| scatter | $O(\lvert B \rvert)$ 검사 + $O(\lvert B \rvert \cdot L)$ 쓰기 | 겹칠 때만 복사본 |
| `x[mask]` | $O(N_{\text{mask}})$ 두 번 + $O(\text{선택 수} \cdot L)$ | 결과 + 청크 시작 위치 $N/2^{14}$개 |
| `x[mask] = v` | $O(N_{\text{mask}})$ 두 번 | 겹칠 때만 복사본 |

## 정확도

인덱싱은 계산을 하지 않고 값을 옮기기만 하므로, dtype이 같으면 결과는 원본 원소와 비트까지 같아요. numpy의 결과와도 같은 비트예요.

- gather, scatter, 마스크 압축은 원소를 그 타입 그대로 복사해요. NaN의 페이로드, `-0.0`의 부호도 보존돼요.
- 스칼라 마스크 대입은 원시 워드에 비트 선택을 하므로, False 원소는 비트 하나 바뀌지 않아요.
- 값의 dtype이 대상과 다르면(위로만 변환, 예: int64 값을 float64 배열에) 캐스트 커널이 변환해요. 변환 결과는 numpy의 캐스트와 같아요([변환과 승격](/internals/array/conversion/)).
- 어떤 경로든 결과는 스레드 수와 무관해요. 마스크는 고정 청크와 누적합으로, gather는 출력 원소의 독립성으로, scatter는 직렬 쓰기로 이를 지켜요. 에러 메시지도 언제나 C 순서로 첫 번째 나쁜 인덱스를 가리켜요.
