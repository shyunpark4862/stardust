  let i = 0;
  while (xs.length - 2 > i && x > xs[i + 1]) i++;

## 한눈에 보기

**리덕션**(reduction)은 배열의 원소 여러 개를 값 하나로 접는 연산이에요. `sum`, `prod`, `max`/`min`, `any`/`all`이 대표적이고, 같은 축을 따라가며 중간 결과를 모두 남기는 누적 스캔(`cumulative_sum`, `cumulative_prod`), 위치를 돌려주는 `argmax`/`argmin`, 합 위에 올라가는 `mean`/`var`/`std`도 이 장에서 다뤄요. 분위수, 공분산, 히스토그램은 [통계 함수](/internals/array/statistics/)에 있어요.

이 장의 설계는 네 가지 원칙으로 요약돼요.

1. **리덕션도 원소별 연산과 같은 이터레이터 위에서 돌아요.** 출력을 입력 모양으로 브로드캐스트해서(줄이는 축의 stride가 0) 커널이 `out = f(out, x)`만 하면 되게 만들어요. 커널은 이터레이터가 넘겨 준 구간의 모양을 보고 "구간 하나를 값 하나로 접기"와 "행을 행에 더하기" 중 하나를 골라요.
2. **float 합은 numpy와 같은 알고리즘, 같은 순서로 더해요.** numpy의 pairwise 합을 그대로 옮겼어요. 그래서 출력이 하나인 긴 합은 numpy와 비트까지 같고, 반올림 오차는 $n$이 아니라 $\log n$에 비례해 자라요. 병렬로 돌릴 때도 같은 트리를 따라 합쳐서 스레드 수와 상관없이 numpy와 비트가 같아요.
3. **순서와 상관없는 접기는 마음대로 나눠요.** 넘치면 한 바퀴 도는(wrap) 정수 덧셈·곱셈, max/min, and/or는 어떤 순서로 접어도 결과가 같으니 고정 조각으로 나눠 병렬로 접어요.
4. **순서가 결과를 바꾸는데 numpy의 순서로는 나눌 수 없으면, 모양만으로 정한 고정 구조로 바꿔요.** 블록 리덕션, float `prod`, 긴 float 스캔이 여기에 해당해요. 구조가 데이터 크기와 레이아웃으로만 정해지므로 결과는 언제나 결정적이지만, numpy와는 마지막 비트가 다를 수 있어요.

| 연산 | 접는 방법 | numpy와의 관계 | 병렬로 나누는 단위 |
|---|---|---|---|
| float/complex `sum` (출력 하나, 형변환 없음) | pairwise 트리 | 비트까지 같음 | 트리의 부분 트리(잎 4096개) |
| `sum(axis=-1)` 같은 안쪽 축 합 | 행마다 pairwise | 비트까지 같음 | 출력 축 |
| `sum(axis=0)` 같은 바깥 축 합 | 행을 행에 더함 | 같음, 블록으로 나누면 다를 수 있음 | 출력 축, 또는 줄이는 축의 고정 블록 |
| 정수 합·곱, max/min, any/all | 순서대로, NEON | 같음 | 고정 조각 |
| float/complex `prod` | 조각 안에 누산기 8개 | 다를 수 있음 | 4096원소 조각 |
| `argmax`/`argmin` | 레인마다 (값, 위치) 추적 | 같음 | 레인, 또는 긴 레인의 조각 |
| `cumulative_sum`/`cumulative_prod` | 레인마다 스캔, 길면 2단계 블록 스캔 | 8192원소 미만은 같음, 이상은 다를 수 있음 | 레인, 또는 블록 묶음 |
| `mean`, `var`, `std` | 합 → 나누기, 두 패스 | float64 연속 배열 전체는 같음 | 합과 같음 |

## 리덕션을 이터레이터 위에 올리기

### 문제

리덕션은 축 조합도, 레이아웃도 제각각이에요. C 순서 행렬의 `sum(axis=1)`은 메모리를 따라 연속인 구간을 줄이고, `sum(axis=0)`은 메모리상 바깥 축을 줄여요. 전치된 배열, 슬라이스, 3차원에서 두 축을 한꺼번에 줄이는 경우도 있어요. 이런 경우마다 루프를 따로 짜면 코드가 경우의 수만큼 불어나고, 경우마다 덧셈 순서가 달라져서 결과를 비트 단위로 맞출 수 없어요.

### 접근: 출력을 브로드캐스트해서 피연산자 둘로

원소별 연산의 엔진([연산 엔진](/internals/array/engine/))을 그대로 써요. 피연산자는 둘이에요.

- 입력 `x`
- 출력. 줄이는 축의 길이가 1인 배열(`keepdims` 모양)을 입력 모양으로 브로드캐스트한 것이에요. 브로드캐스트된 축의 stride는 0이에요.

이렇게 하면 줄이는 축을 따라 걸을 때 출력 포인터가 움직이지 않으니, 커널은 `out = f(out, x)`만 하면 돼요. 이터레이터는 리덕션인지 아닌지 모른 채 평소처럼 축을 정렬하고 합쳐서 가장 안쪽 구간마다 커널을 불러요.

### 구간의 모양이 전략을 정해요

이터레이터가 넘겨 주는 가장 안쪽 구간에서 출력의 stride `s[1]`을 보면 두 경우로 갈려요.

- **`s[1] == 0`: 안쪽 축 리덕션.** 구간 전체가 출력 한 칸으로 접혀요. 누산기 하나에 모아요. 여기서 pairwise 합, NEON max/min, 병렬 조각 같은 최적화가 들어가요. 예: C 순서 행렬의 `sum(axis=1)`, 1차원 배열의 `sum`.
- **`s[1] != 0`: 바깥 축 리덕션.** 구간이 출력 행 하나와 입력 행 하나예요. 출력 행에 입력 행을 원소별로 더해요(`op[i] = f(op[i], xp[i])`). 유지되는 축 방향으로 벡터화되고, 연속이면 원소별 연산의 NEON 커널(`neon_binary`)을 그대로 불러요. 예: C 순서 행렬의 `sum(axis=0)`.

어느 쪽이 되는지는 이터레이터의 축 재정렬이 정해요. 재정렬은 마지막 피연산자(출력)의 stride부터 보는데, stride 0은 정보가 없으니 건너뛰고 입력의 stride를 봐요. 결국 입력을 메모리 순서대로 걷는 축 순서가 나오고, 그 순서에서 가장 안쪽 축이 줄이는 축이면 안쪽 리덕션, 남는 축이면 바깥 리덕션이에요. 둘 다 입력을 메모리 순서로 한 번 훑으므로 캐시 효율은 같아요.

`keepdims_result`는 결과를 `new_array_like`로 할당해요. 입력의 strides 절댓값 순서로 축을 놓는 numpy의 `order='K'`와 같은 규칙이에요. F 순서 입력이면 출력도 F 순서가 되어, 이터레이터가 두 피연산자 모두를 메모리 순서로 걸을 수 있어요.

### 시작값

출력은 먼저 시작값으로 채워요(`fill`). 커널은 언제나 `out = f(out, x)`만 하므로, 시작값과 첫 원소를 연산한 결과가 그 원소 자신이어야 해요.

| 연산 | 시작값 | 이유 |
|:---:|:---:|---|
| `sum` | `+0` | `+0 + x == x`. 빈 합은 0이고, `sum([-0.0])`은 `+0.0 + -0.0 = +0.0`이에요. numpy도 `+0`에서 시작하므로 같아요 |
| `prod` | `1` | `1 · x == x` |
| `max` | dtype의 최솟값 (`-inf`, `INT64_MIN`) | 첫 원소가 반드시 이겨요. `-inf`나 `-0.0`만 있는 배열도 그 값이 정확히 남아요 |
| `min` | dtype의 최댓값 (`+inf`, `INT64_MAX`) | 같은 이유 |
| `any` / `all` | `false` / `true` | 논리합·논리곱의 항등원 |

`max`/`min`에는 진짜 항등원이 없어요. `-inf`를 돌려주는 "빈 max"는 수학적으로 틀린 답이에요. 그래서 접을 원소가 하나도 없는 출력이 있으면 `ValueError`를 내요(`require_nonempty`: 출력 하나에 접히는 원소 수가 0인데 출력은 비어 있지 않을 때).

### 결과의 모양과 dtype

- `finish`는 `keepdims=False`면 줄인 축을 뺀 뷰를 만들어요. 데이터는 그대로이고 shape와 strides만 줄여요. 모든 축을 줄였으면 0차원 배열 대신 Python 스칼라를 돌려줘요(stardust에는 0차원 배열이 없어요).
- `sum`/`prod`/누적 스캔은 bool을 int64로 쌓아요(`accumulate_dtype`). `dtype=`으로 다른 dtype을 지정할 수 있지만 `dtype=bool`은 `TypeError`예요. 덧셈과 곱셈에는 bool 루프가 없기 때문이에요.
- `mean`/`var`/`std`는 float64, complex 입력이면 complex128로 계산해요(`var`/`std`의 결과는 float64).

### dtype을 컴파일 시점 타입으로

런타임 dtype은 `visit_dtype`이 컴파일 시점 타입으로 바꿔요. C++20의 템플릿 람다(`[&]<typename T>(std::type_identity<T>)`)를 넘기면 dtype마다 한 번씩 인스턴스화돼요. 연산에 그 타입의 루프가 있는지는 연산 구조체의 변수 템플릿 `Op::ok<T>`가 알려 주고, `if constexpr`로 없는 조합은 아예 코드를 만들지 않아요.

```cpp
// array/ops/reduction.cpp의 fold (발췌)
template <typename Op>
nb::object fold(const NDArray& x, const Axes& ax, DType loop_dtype, bool keepdims, auto start) {
    NDArray out = keepdims_result(x, ax, loop_dtype);
    visit_dtype(loop_dtype, [&]<typename T>(std::type_identity<T>) {
        if constexpr (Op::template ok<T>) {
            fill<T>(out, start(std::type_identity<T>{}));
            run_reduce(x, out, &reduce_loop<Op, T>);   // 커널 = 함수 포인터 하나
        } else {
            unsupported(loop_dtype);                    // 예: complex의 max
        }
    });
    return finish(std::move(out), ax, keepdims);
}
```

`reduce_loop<Op, T>` 안에서는 `if constexpr` 사슬이 (연산, 타입) 조합마다 가장 좋은 경로를 골라요. float 덧셈이면 pairwise, float max면 NEON, 정수 max면 다른 NEON, 나머지는 단순 루프예요. 모든 분기가 컴파일 시점에 정해지므로 인스턴스마다 필요한 코드만 남아요.

### 형변환이 있는 리덕션

`mean(int64)`나 `sum(x, dtype=float64)`처럼 입력과 루프의 dtype이 다르면 `run_fold`가 커널을 `BufferedLoop`로 감싸요. 입력을 4096원소씩 L1에 들어가는 버퍼로 변환하고 그 버퍼에 커널을 돌려요. 입력 전체를 임시 배열로 바꾸는 것보다 메모리를 두 번 덜 지나요(자세한 것은 [연산 엔진](/internals/array/engine/)). 이 경우 커널이 받는 구간은 4096원소씩이고, 구간마다 `acc = acc + pairwise(구간)`으로 접혀요. 그래서 덧셈 순서가 numpy와 달라질 수 있어요([numpy와 비트가 달라지는 경우](#numpy와-비트가-달라지는-경우)).

## pairwise 합

### 문제: 순차 합은 느리고 부정확해요

가장 단순한 합 `s = s + x[i]`는 덧셈 하나가 끝나야 다음 덧셈을 시작할 수 있는 **의존 사슬 하나**예요. 부동소수점 덧셈은 지연(latency)이 여러 사이클이라, 원소마다 그 지연을 그대로 기다려요. 부동소수점 연산 장치(FP 유닛)는 사이클마다 덧셈 여러 개를 처리할 수 있는데, 대부분의 시간을 놀아요.

정확도도 나빠요. 첫 원소는 $n-1$번의 덧셈을 모두 거치고, 그때마다 반올림 오차가 쌓여요.

### 오차의 크기: 덧셈 사슬의 길이

부동소수점 덧셈 하나를 이렇게 모델링해요(Higham [1] 2장의 표준 모델).

$$
\operatorname{fl}(a+b) = (a+b)(1+\delta), \qquad |\delta| \le u = 2^{-53}
$$

어떤 순서로 더하든, 항 $x_i$가 최종 합에 이르기까지 거친 덧셈 수를 $h_i$라고 하면 계산된 합은

$$
\hat s = \sum_{i=1}^{n} x_i \prod_{k=1}^{h_i} (1+\delta_{ik}) = \sum_{i=1}^{n} x_i\,(1+\theta_{h_i}), \qquad |\theta_h| \le \gamma_h = \frac{h u}{1 - h u}
$$

이에요(Higham [1]의 Lemma 3.1). 따라서 $h = \max_i h_i$로 두면

$$
|\hat s - s| \le \gamma_h \sum_{i=1}^{n} |x_i| \approx h\,u \sum_{i=1}^{n} |x_i|
$$

예요. 오차 한계는 **가장 긴 덧셈 경로의 길이** $h$에 비례해요. 순차 합은 $h = n-1$이에요. 덧셈을 이진 트리 모양으로 하면 $h \approx \log_2 n$이 돼요(Higham [1] 4장의 pairwise summation).

### 알고리즘: numpy의 블록 pairwise 합

stardust는 numpy의 `DOUBLE_pairwise_sum`/`CDOUBLE_pairwise_sum`(numpy 소스 `numpy/_core/src/umath/loops_utils.h.src`의 `@TYPE@_pairwise_sum` [2])과 같은 알고리즘을 같은 순서로 써요. 순수한 이진 트리가 아니라 잎이 큰 트리예요.

- $n < 8$: `0.0`에서 시작해 순서대로 더해요.
- $8 \le n \le 128$ (`kBlock`, numpy의 `PW_BLOCKSIZE`): 누산기 8개가 원소를 8칸 간격으로 나눠 맡아요. 누산기 $j$는 $x_j, x_{j+8}, x_{j+16}, \dots$를 순서대로 더해요. 끝나면 `((r0+r1)+(r2+r3))+((r4+r5)+(r6+r7))`로 합치고, 8로 나누고 남은 원소는 그 뒤에 순서대로 더해요.
- $n > 128$: 반으로 나눠요. 이때 자르는 위치는 8의 배수로 내려요($n_2 = \lfloor n/2 \rfloor - (\lfloor n/2 \rfloor \bmod 8)$). 양쪽을 재귀로 더한 뒤 둘을 더해요.

```cpp
// base/pairwise.hpp (발췌)
inline constexpr std::int64_t kBlock = 128;          // numpy의 PW_BLOCKSIZE

inline std::int64_t split(std::int64_t n) {           // 반, 8의 배수로 내림
    const std::int64_t m = n / 2;
    return m - m % 8;
}

template <typename Get>
[[gnu::always_inline]] inline double leaf(std::int64_t n, const Get& get) {
    if (n < 8) {
        double res = 0.;
        for (std::int64_t i = 0; i < n; ++i) res += get(i);
        return res;
    }
    double r[8];
    for (int j = 0; j < 8; ++j) r[j] = get(j);
    std::int64_t i = 8;
    for (; i < n - (n % 8); i += 8)
        for (int j = 0; j < 8; ++j) r[j] += get(i + j);     // 독립 사슬 8개
    double res = ((r[0] + r[1]) + (r[2] + r[3])) + ((r[4] + r[5]) + (r[6] + r[7]));
    for (; i < n; ++i) res += get(i);                    // 나머지는 순서대로
    return res;
}

template <typename LeafSum>
double tree(std::int64_t begin, std::int64_t n, const LeafSum& leaf_sum) {
    if (n <= kBlock) return leaf_sum(begin, n);
    const std::int64_t n2 = split(n);
    return tree(begin, n2, leaf_sum) + tree(begin + n2, n - n2, leaf_sum);
}
```

원소 1000개의 트리는 이런 모양이에요. 왼쪽 자식은 언제나 8의 배수이고, 잎은 64~128개 사이예요.

### 이 알고리즘의 경로 길이

잎 하나($m \le 128$)에서 누산기 하나는 $\lfloor m/8 \rfloor$개의 항을 받아 $\lfloor m/8 \rfloor - 1$번 더하고, 합치는 데 3단계, 나머지 항이 있으면 최대 7번을 더 거쳐요. $m$이 8의 배수이면 최대 $15 + 3 = 18$, 나머지가 있으면 최대 $14 + 3 + 7 = 24$예요. 나머지가 있는 잎은 트리의 오른쪽 끝에만 생겨요(왼쪽 자식은 언제나 8의 배수). 트리의 깊이는 약 $\lceil \log_2(n/128) \rceil$이에요. 그래서

$$
h \lesssim 24 + \left\lceil \log_2 \frac{n}{128} \right\rceil
$$

이고, 원소 100만 개면 $h \lesssim 37$, 오차 한계는 약 $37u \approx 4 \times 10^{-15}$ 곱하기 $\sum |x_i|$예요. 순차 합의 한계 $(n-1)u \approx 1.1 \times 10^{-10}$보다 약 3만 배 작아요. 마지막의 `0 + 트리 합`은 0을 더하는 것이라 반올림이 없어요.

위 그래프는 오차 한계의 계수 $h$를 로그 눈금으로 그린 거예요. 순차 합은 $n$과 함께 곧게 올라가고, pairwise는 $n$이 백만 배 커져도 24~44 사이에 머물러요. 이 값은 최악의 경우의 한계이고, 반올림 오차가 서로 독립인 무작위 값처럼 행동한다고 보면 실제 오차는 이보다 훨씬 작아요(Higham [1] 4장의 통계적 관점). 정규분포 원소 1000만 개를 시드 4개로 더해 보면 상대오차가 순차 합은 4.0e-16~2.9e-13, pairwise는 0~4.2e-16이에요.

### 이 모양을 고른 이유

- **속도.** 잎 안에서 누산기 8개는 서로 의존하지 않는 사슬 8개예요. 덧셈 하나의 지연을 다른 7개가 덮어서 FP 유닛이 쉬지 않아요. 순차 합보다 5.6배 빨라요. 재귀는 128원소마다 한 번이라 함수 호출 비용은 무시할 만해요.
- **정확도.** 위에서 본 것처럼 경로 길이가 $\log n$으로 줄어요.
- **numpy와 같은 비트.** 알고리즘과 순서가 같으니 결과도 같아요. stardust는 시작값 `+0`에 구간 전체의 pairwise 합을 더하고, numpy도 이런 구간을 pairwise 한 번으로 더해요(numpy 2.5.4 기준).

이론상 더 정확한 다른 합(예: Kahan의 보정 합, Higham [1] 4장)은 쓰지 않아요. 다른 알고리즘은 numpy와 다른 비트를 내서, numpy로 얻은 결과와 stardust의 결과를 그대로 맞대 볼 수 없게 돼요.

numpy 2.5.4와 비교한 결과예요(정규분포 1,000,003개, 1스레드와 10스레드).

| 경우 | numpy와 비트가 같은가 |
|---|:---:|
| `sum(f)` | 같음 |
| `sum(f[::2])` (stride 16바이트) | 같음 |
| `sum(m, axis=1)`, (1000, 1000) | 같음 |
| complex `sum`, 30만 개 | 같음 |
| `mean(f)`, `var(f)`, `std(f)` | 같음 |

### 항을 접근자로 넘기기

트리와 잎은 원소를 직접 읽지 않고 **접근자** `get(i)`를 불러요. 배열의 커널은 이 접근자를 람다로 만들어 넘겨요.

```cpp
// array/kernels/reduce.hpp (발췌)
template <typename Get>
double pairwise_sum(std::int64_t begin, std::int64_t n, const Get& get) {
    return pairwise::tree(begin, n, [&](std::int64_t b, std::int64_t m) {
        return pairwise::leaf(m, [&](std::int64_t i) { return get(b + i); });
    });
}

// reduce_loop 안: strided 입력이면
auto at = [&](std::int64_t i) { return value(load_as<T>(x + i * s[0])); };
acc = acc + pairwise_sum_mt(n, at);
```

이 덕분에 여러 종류의 "항"이 임시 배열 없이 같은 트리로 흘러 들어가요.

- strided 입력: `x + i * stride`에서 읽어요.
- NaN을 건너뛰는 합(`nansum`): NaN이면 `0`을 돌려줘요.
- `var`의 두 번째 패스: $(x_i - m)^2$를 그 자리에서 계산해요.

모두 같은 트리를 지나므로 "그 값들로 만든 배열의 `sum`"과 비트가 같아요.

람다가 여러 겹(트리 → 잎 람다 → 잎 → 접근자 람다)이라 컴파일러가 모두 인라인해야 원소마다 함수 호출이 남지 않아요. 잎 함수 `pairwise::leaf`에 `[[gnu::always_inline]]`을 붙인 이유예요. 이 표시가 없으면 1스레드 `sum(f)`(원소 100만 개)가 110µs에서 152µs로 느려져요.

### 정의는 한 벌, 모든 영역이 함께 써요

트리 모양, 잎의 합, 병렬 계획과 합치기는 `base/pairwise.hpp` 한 파일에 있어요. 배열 영역은 위처럼 접근자로 부르고, linalg와 frame도 같은 정의를 불러요(linalg는 잎마다 버퍼를 채워 넘겨요). float 합의 비트를 정하는 코드가 이 파일 하나뿐이라서 `sd.sum`, `sd.linalg`의 합, frame의 float `sum`/`mean`이 같은 데이터에 같은 비트를 내요.

### 긴 합 하나를 여러 스레드로, 같은 비트로

트리 모양은 $n$만으로 정해져요. 그러니 원소가 `task`개 이하인 부분 트리는 서로 독립이고, 어떤 순서로 계산해도 돼요.

1. `pairwise::plan(n, task)`: 트리를 직렬과 똑같이 자르면서 원소 `task`개 이하인 부분 트리를 만나면 멈추고, 그 (시작, 길이)를 왼쪽부터 목록에 넣어요.
2. 목록의 부분 트리를 풀에서 병렬로 더해요. 부분 트리 안의 덧셈은 직렬 트리의 그 부분과 같아요.
3. `pairwise::combine(n, task, parts)`: 트리를 다시 같은 방식으로 자르며 내려가서, 잎 자리에 부분합을 끼워 넣고 같은 순서로 더해요.

```cpp
// base/pairwise.hpp (발췌)
inline Leaves plan(std::int64_t n, std::int64_t task, bool complex) {
    Leaves leaves;
    auto collect = [&](auto&& self, std::int64_t b, std::int64_t m) -> void {
        if (m <= task) { leaves.emplace_back(b, m); return; }
        const std::int64_t m2 = complex ? split_complex(m) : split(m);
        self(self, b, m2);
        self(self, b + m2, m - m2);
    };
    collect(collect, 0, n);
    return leaves;
}

template <typename T>
T combine(std::int64_t n, std::int64_t task, const std::vector<T>& parts) {
    std::size_t next = 0;
    auto rec = [&](auto&& self, std::int64_t m) -> T {
        if (m <= task) return parts[next++];
        const std::int64_t m2 = /* split(m) 또는 split_complex(m) */;
        const T left = self(self, m2);
        const T right = self(self, m - m2);
        return left + right;
    };
    return rec(rec, n);
}
```

재귀 람다는 자기 자신을 첫 인자(`auto&& self`)로 받아요. 람다 안에서는 자기 이름을 볼 수 없어서 쓰는 C++ 관용구예요. `std::function`을 거치지 않으므로 호출이 인라인될 수 있어요.

덧셈 하나하나가 직렬 트리와 같은 피연산자, 같은 순서이므로 스레드 수와 상관없이 직렬 트리와, 곧 numpy와 비트가 같아요. 부분 트리의 최대 크기(`kLeaf`)는 `kParallelTask` = 4096원소(complex는 2048개)예요. 이 경로는 $n \ge$ `kParallelThreshold` = 32768이고 풀을 쓸 수 있을 때만 타요. 원소 100만 개면 부분 트리가 수백 개예요. 테스트는 원소 300만 개에서 1스레드와 10스레드 모두 `sum(x) == np.sum(x)`를 확인해요.

## max/min, argmax/argmin

### float64 max/min: FMAX 하나가 정의 그 자체

`max`/`min`은 NaN을 전파하고 `-0 < +0`으로 봐요(IEEE 754-2019의 maximum/minimum [6]). 스칼라 코드로 쓰면 비교가 세 번(NaN, NaN, ±0) 필요한 함수예요. 그런데 AArch64의 `FMAX`/`FMIN` 명령은 바로 이 의미를 명령 하나로 계산해요. 그래서 연속 float64 구간은 NEON intrinsic으로 직접 접어요.

```cpp
// array/kernels/reduce.hpp의 neon_fold (발췌, Max 쪽만)
template <bool Max, bool SkipNan = false>
double neon_fold(const double* x, std::int64_t n, double acc) {
    std::int64_t i = 0;
    if (n >= 8) {
        float64x2_t v[4];                                   // 레지스터 4개 = 레인 8개
        for (int j = 0; j < 4; ++j) v[j] = vld1q_f64(x + 2 * j);
        for (i = 8; i + 8 <= n; i += 8)
            for (int j = 0; j < 4; ++j) v[j] = vmaxq_f64(v[j], vld1q_f64(x + i + 2 * j));   // FMAX
        const float64x2_t m = vmaxq_f64(vmaxq_f64(v[0], v[1]), vmaxq_f64(v[2], v[3]));
        acc = fmax_nan(acc, vmaxvq_f64(m));                 // 두 레인끼리 (FMAXV)
    }
    for (; i < n; ++i) acc = fmax_nan(acc, x[i]);           // 남은 원소
    return acc;
}
```

- 레지스터 4개를 독립 누산기로 써서 `FMAX`의 지연을 덮어요. 덧셈의 누산기 8개와 같은 생각이에요.
- max/min은 결합·교환 법칙이 정확히 성립하므로(NaN 전파와 ±0 처리를 포함해서) 순서를 바꿔도 결과가 같아요. 그래서 결과가 numpy와 같아요.
- 순차 비교보다 14배 빠르고 numpy와 같은 속도예요. 원소 100만 개 `max(f)`가 numpy 75µs, 1스레드 72µs, 10스레드 23µs예요.
- `nanmax`/`nanmin`은 같은 함수의 `SkipNan` 판이고, NaN을 건너뛰는 `FMAXNM`/`FMINNM`(`vmaxnmq_f64`)을 써요.
- 연속이 아닌 구간은 스칼라 루프예요. 바깥 축 리덕션(`max(axis=0)`)은 원소별 `maximum`의 NEON 커널이 행마다 돌아요.

### int64 max/min: 누산기 수는 지연 × 처리량으로 정해요

NEON에는 64비트 정수의 max/min 명령이 없어요. 비교(`vcgtq_s64`, CMGT)한 뒤 선택(`vbslq_s64`, BSL)하는 두 단계가 필요하고, 한 단계의 지연이 약 5사이클이에요.

- 단순 루프는 의존 사슬 하나라 numpy보다 1.6배 느려요.
- float처럼 레지스터 4개를 쓰면 단순 루프와 차이가 없어요. 지연 5사이클을 덮기에 4개는 부족해요.
- 레지스터 8개(레인 16개)를 써야 numpy와 같은 속도가 나와요. 원소 100만 개 `max(i)`가 numpy 76µs, 1스레드 72µs예요.

```cpp
// array/kernels/reduce.hpp의 neon_fold_int (발췌)
constexpr int kRegs = 8;
int64x2_t v[kRegs];
auto pick = [](int64x2_t a, int64x2_t b) {
    return Max ? vbslq_s64(vcgtq_s64(a, b), a, b) : vbslq_s64(vcgtq_s64(a, b), b, a);
};
for (i = 2 * kRegs; i + 2 * kRegs <= n; i += 2 * kRegs)
    for (int j = 0; j < kRegs; ++j) v[j] = pick(v[j], vld1q_s64(x + i + 2 * j));
for (int w = kRegs / 2; w >= 1; w /= 2)                    // 8 → 4 → 2 → 1 트리로 합침
    for (int j = 0; j < w; ++j) v[j] = pick(v[j], v[j + w]);
```

필요한 독립 사슬의 수는 대략 "명령 하나의 지연 × 사이클당 처리할 수 있는 명령 수"예요. 지연이 긴 연산일수록 사슬이 더 많이 필요하므로, float 덧셈에 맞춘 누산기 수를 다른 연산에 그대로 쓸 수 없어요.

### argmax/argmin: 레인 단위, 인덱스 순서

`argmax`는 동점이면 첫 위치, NaN이 있으면 첫 NaN의 위치를 돌려줘요. 그러려면 원소를 메모리 순서가 아니라 인덱스 순서로 봐야 해요. 그래서 원소별 이터레이터 대신 **레인 처리**(`run_lanes`, `array/ops/lanes.hpp`)를 써요. 이터레이터가 줄이는 축을 뺀 나머지 축을 돌고, 방문한 자리마다 레인 하나를 0부터 $n-1$까지 처리해요. 커널 호출 하나가 레인 하나를 통째로 처리하므로 레인 길이를 작업량 가중치로 넘겨서, 행이 많지 않아도 병렬 분할이 제대로 계산돼요.

연속 float64 레인은 NEON으로 처리해요. 레인 0이 짝수 인덱스, 레인 1이 홀수 인덱스를 맡아 각자 (최댓값, 위치)를 추적해요.

```cpp
// array/kernels/reduce.hpp의 neon_arg_extreme (발췌, max 쪽)
float64x2_t best = vld1q_f64(x);
int64x2_t at = {0, 1}, idx = {0, 1};
uint64x2_t ordered = vceqq_f64(best, best);           // NaN을 아직 못 봤으면 모든 비트 1
for (std::int64_t i = 2; i + 2 <= n; i += 2) {
    const float64x2_t v = vld1q_f64(x + i);
    idx = vaddq_s64(idx, vdupq_n_s64(2));
    const uint64x2_t better = vcgtq_f64(v, best);     // strict >: 레인 안에서 첫 위치 유지
    best = vbslq_f64(better, v, best);
    at = vbslq_s64(better, idx, at);
    ordered = vandq_u64(ordered, vceqq_f64(v, v));    // x == x 가 거짓이면 NaN
}
if (vminvq_u32(vreinterpretq_u32_u64(ordered)) == 0)  // 어느 레인이 NaN을 봤으면
    for (std::int64_t k = 0;; ++k) if (std::isnan(x[k])) return k;   // 처음부터 다시 훑기
// 두 레인을 합침: 값이 크면 그쪽, 같으면 작은 인덱스
```

- **동점 규칙.** 레인 안에서는 strict `>`라서 먼저 나온 위치가 남아요. 두 레인의 답이 같은 값이면 작은 인덱스를 골라요. 전체의 첫 위치는 두 레인 각자의 첫 위치 중 작은 쪽이므로 정확히 맞아요.
- **NaN.** 비교 `>`는 NaN에서 언제나 거짓이라 NaN은 `best`에 들어가지 않아요. 대신 "NaN을 본 적 있음"을 따로 모아요. NEON에는 64비트 비트 반전(NOT) 명령이 없어서, "NaN이 아님"(`x == x`)을 AND로 누적해요. NaN이 있으면 스칼라로 처음부터 다시 훑어 첫 NaN을 찾아요. NaN은 드물다고 보고 흔한 경우를 빠르게 했어요.
- `nanargmax`/`nanargmin`은 NaN을 `-inf`(max)/`+inf`(min)로 읽어요(`vbslq_f64(vceqq_f64(v, v), v, farv)`). numpy가 NaN을 바꾸는 값과 같아서 결과도 같아요.
- complex에는 순서가 없으므로 `TypeError`예요.

연속 int64 레인은 두 번 읽어요(`neon_arg_extreme_i64`, 8개 이상). NEON에는 64비트 정수 max/min이 없어서 비교(`vcgtq_s64`)와 선택(`vbslq_s64`) 두 명령이 필요해요. float처럼 한 번 읽으며 위치까지 따라가면, 벡터마다 "비교 → 값 선택 → 위치 선택"이 앞의 결과에 기대는 사슬이 되어 지연을 숨길 수 없어요. 그래서 일을 둘로 나눠요.

1. **극값만 구해요.** 레지스터 넷(원소 8개)에 서로 독립인 비교-선택 사슬을 하나씩 두고 접어요. 사슬끼리 기대지 않으므로 지연이 겹쳐요.
2. **그 값이 처음 나오는 위치를 찾아요.** 극값을 모든 레인에 퍼뜨리고, 원소 넷씩 `vceqq_s64`로 비교해 하나라도 같으면 멈춘 뒤 그 넷 안에서 스칼라로 첫 위치를 골라요.

```cpp
// array/kernels/reduce.hpp의 neon_arg_extreme_i64 (발췌, max 쪽)
auto pick = [](int64x2_t a, int64x2_t b) { return vbslq_s64(vcgtq_s64(a, b), a, b); };
for (; i + 8 <= n; i += 8) {                      // 1단계: 독립 사슬 넷
    m0 = pick(vld1q_s64(x + i), m0);     m1 = pick(vld1q_s64(x + i + 2), m1);
    m2 = pick(vld1q_s64(x + i + 4), m2); m3 = pick(vld1q_s64(x + i + 6), m3);
}
// ... 넷을 합치고 꼬리를 더해 best를 얻어요
const int64x2_t bv = vdupq_n_s64(best);
for (k = 0; k + 4 <= n; k += 4) {                  // 2단계: 처음 나오는 넷을 찾으면 멈춤
    const uint64x2_t e = vorrq_u64(vceqq_s64(vld1q_s64(x + k), bv), vceqq_s64(vld1q_s64(x + k + 2), bv));
    if (vmaxvq_u32(vreinterpretq_u32_u64(e))) break;
}
for (;; ++k) if (x[k] == best) return k;
```

- 동점이면 저절로 첫 위치가 나와요. 2단계가 앞에서부터 찾다가 처음 만난 곳에서 멈추기 때문이에요. 정수에는 NaN이 없어서 따로 볼 것이 없어요.
- 2단계는 대개 짧아요. 극값이 앞쪽에 있으면 금방 멈추고, 맨 뒤에 있어도 비교 하나짜리 루프로 한 번 더 읽는 것뿐이에요. 원소 100만 개 `argmax(i)`가 1스레드 122µs로 numpy(125µs)와 같아요. 스칼라 루프는 493µs, 한 번 읽으며 위치를 따라가는 NEON 루프는 222µs예요.

긴 레인 하나(`argmax(f)`처럼 `axis=None`)는 4096원소 조각으로 나눠 조각마다 답을 구한 뒤(`arg_whole`), 조각 순서대로 비교해요. NaN이 있는 첫 조각이 이기고, 아니면 값이 큰 쪽, 같으면 앞 조각이에요. 각 조각의 답이 그 조각의 첫 최댓값(또는 첫 NaN)이므로 이 규칙으로 직렬과 정확히 같은 답이 나와요. 원소 100만 개 `argmax(f)`는 numpy 558µs, 1스레드 471µs, 10스레드 57µs예요(numpy 대비 9.7배, 1스레드 대비 8.2배). 비교와 선택이 원소마다 몇 번씩 있는 계산 중심의 연산이라 스레드 수에 거의 비례해 늘어나요.

## 순서와 상관없는 접기, any/all

### 고정 조각으로 나눠 병렬로

어떤 접기는 순서를 어떻게 바꿔도 결과가 같아요. 이런 접기를 컴파일 시점에 표시하는 변수 템플릿이 있어요.

```cpp
// array/kernels/reduce.hpp
template <typename Op, typename T>
inline constexpr bool order_free = std::is_same_v<Op, ops::Maximum> || std::is_same_v<Op, ops::Minimum> ||
                                   std::is_same_v<Op, ops::NanMaximum> || std::is_same_v<Op, ops::NanMinimum> ||
                                   std::is_same_v<Op, ops::LogicalOr> || std::is_same_v<Op, ops::LogicalAnd> ||
                                   ((std::is_same_v<Op, ops::Add> || std::is_same_v<Op, ops::Multiply>) &&
                                    (ops::is_int<T> || ops::is_bool<T>));
```

int64 덧셈과 곱셈은 넘치면 wrap해요. $2^{64}$로 나눈 나머지의 덧셈·곱셈이라 결합·교환 법칙이 정확히 성립해요. max/min, and/or도 마찬가지예요.

출력이 하나인 긴 구간($n \ge 32768$)이면 4096원소씩 고정 조각으로 나눠 풀에서 접고, 조각 결과를 순서대로 합쳐요. 각 조각은 자기 첫 원소에서 출발해요. 시작값이 필요 없으니 항등원이 없는 max/min에도 그대로 쓸 수 있어요. 조각 결과를 담는 배열은 `std::vector<T>`가 아니라 `std::make_unique_for_overwrite<T[]>`(C++20)로 만들어요. `std::vector<bool>`은 원소를 비트로 압축하므로, `T`가 `bool`일 때 여러 태스크가 이웃한 원소에 쓰면 같은 바이트를 동시에 쓰는 데이터 경쟁이 생겨요. `_for_overwrite`는 어차피 덮어쓸 메모리를 0으로 채우지 않아요.

### any/all의 조기 종료

`any`는 True를 하나 찾으면, `all`은 False를 하나 찾으면 답이 정해져요. bool 입력이면 4096원소 블록마다 "답이 정해졌는가"를 보고, 정해졌으면 멈춰요. 같은 출력의 다음 구간도 시작하자마자 돌아와요.

```cpp
// reduce_loop의 any/all 부분 (발췌)
constexpr bool decided = std::is_same_v<Op, ops::LogicalOr>;   // any는 true, all은 false에서 결정
for (std::int64_t off = 0; off < n && acc != decided; off += 4096) {
    const std::int64_t m = std::min<std::int64_t>(4096, n - off);
    const std::uint8_t* p = reinterpret_cast<const std::uint8_t*>(x) + off;
    std::uint8_t bits = decided ? 0 : 1;
    for (std::int64_t i = 0; i < m; ++i) bits = decided ? (bits | p[i]) : (bits & p[i]);
    acc = Op::f(acc, bits != 0);
}
```

- 블록 안은 분기 없는 벡터 OR/AND예요. 원소마다 "찾았나?"를 검사하면 분기가 원소마다 생겨요. 검사를 4096원소마다 한 번으로 줄이면 블록 안은 NEON으로 16바이트씩 처리돼요.
- 블록을 `bool`이 아니라 `uint8_t`로 접어요. `bool`로 쓰면 컴파일러가 OR 루프를 "첫 True 찾기" 루프로 바꿔서 원소마다 분기가 생겨요. 그러면 원소당 0.9ns, 모두 False인 100만 개에 906µs가 걸려요.
- 앞쪽에 True가 있는 `any(b)`는 0.1µs예요(numpy 0.5µs).
- 조기 종료와 병렬 조각은 함께 쓰지 않아요. `reduce_loop`에서 bool any/all 분기가 병렬 조각 분기보다 앞에 있어서, bool 입력은 언제나 직렬로 접다가 멈추는 경로를 타요.
- `any`/`all`은 모든 dtype에서 `x != 0`을 봐요(NaN은 True). bool이 아닌 입력은 버퍼 캐스팅으로 bool로 바뀌어 4096원소씩 커널에 들어와요. 이때 커널은 답이 정해진 뒤 바로 돌아오지만, 버퍼 캐스팅은 남은 구간도 변환하므로 입력 전체를 읽어요. 조기 종료의 이득은 bool 입력에서만 온전히 나와요.

`count_nonzero`도 순서와 상관없는 접기예요. 전용 커널(`count_loop`)이 x를 직접 읽어 int64로 세요. bool 복사본을 만들지 않고, 긴 구간은 조각으로 나눠 병렬로 세요.

연속 bool은 바이트 카운터로 세요. 바이트마다 int64에 더하면 바이트를 64비트로 넓히는 명령이 원소마다 붙어요(원소 100만 개 47µs). 그래서 16바이트씩 읽어 바이트 카운터 16개에 더해요. `vtstq_u8(v, v)`는 0이 아닌 바이트에서 `0xFF`(−1)인 마스크라, 카운터에서 빼면 1씩 늘어요. 바이트 카운터는 255에서 넘치므로 255번(4080바이트)마다 `vaddlvq_u8`로 넓혀 합에 더하고 다시 0에서 시작해요. 원소 100만 개 `count_nonzero(b)`가 23µs로 numpy(23µs)와 같아요.

```cpp
// array/kernels/reduce.hpp의 count_loop, 연속 bool (발췌)
while (i + 16 <= e) {
    uint8x16_t c = vdupq_n_u8(0);
    const std::int64_t stop = std::min(e - 15, i + 255 * 16);   // 넘치기 전에 멈춤
    for (; i < stop; i += 16) {
        const uint8x16_t v = vld1q_u8(p + i);
        c = vsubq_u8(c, vtstq_u8(v, v));                        // 0이 아니면 +1
    }
    acc += vaddlvq_u8(c);                                       // 16개를 넓혀 합침
}
```

## 블록 리덕션

### 문제: 출력 축만으로는 나눌 수 없는 리덕션

C 순서 행렬의 `sum(axis=0)`은 남는 축(열)이 메모리상 안쪽이라 바깥 축 리덕션이에요. 병렬로 나누려면 제약 두 가지가 걸려요.

- 리덕션은 출력이 실제로 걸친 축만 나눌 수 있어요. 줄이는 축을 스레드끼리 나누면 출력 원소 하나에 여러 스레드가 접게 되고, 접는 순서가 스레드 수에 따라 달라져서 같은 입력이라도 결과의 비트가 달라져요([스레드풀과 결정성](/internals/core/threads/)).
- 안쪽 축은 1024원소(`kMinInnerPiece`)보다 짧게 자르지 않아요. 짧은 조각은 커널 호출마다 스트리밍이 끊겨 오히려 느려요.

(1000, 1000) 행렬은 안쪽 축(1000열)이 1024보다 짧아서 자를 수가 없어요. 이 두 제약만 따르면 태스크가 하나뿐이라, 스레드가 10개여도 1스레드와 같은 시간이 걸려요.

### 접근: 줄이는 축을 고정 개수의 블록으로

줄이는 축 하나를 블록으로 나눠요.

1. 블록마다 **출력의 복사본**을 만들어 시작값으로 채우고, 그 블록의 행을 복사본에 접어요. 블록끼리는 독립이라 풀에서 병렬로 돌아요.
2. 복사본을 블록 순서대로 출력에 접어요. 이 마지막 접기도 같은 리덕션 커널로 해요. 복사본을 축 하나(길이 = 블록 수)로 쌓은 배열을 줄이는 셈이에요.

이렇게 해도 답이 맞으려면 시작값이 "다시 접어도 그대로"여야 해요. 출력도 시작값을 담고 있고 복사본도 시작값에서 출발했으니, 마지막 접기에서 시작값이 한 번 더 들어가기 때문이에요. 모든 리덕션의 시작값은 이 조건을 만족해요(`0 + p = p`, `1 × p = p`, `max(최솟값, p) = p`, `false ∨ p = p`).

```cpp
// array/ops/reduction.cpp의 reduce_blocked (발췌)
template <typename Fold>
void reduce_blocked(const NDArray& x, NDArray& out, const Blocks& b, Loop combine, Fold fold) {
    const std::int64_t bytes = out.nbytes();
    auto store = std::make_unique_for_overwrite<std::byte[]>(b.count * bytes);
    std::vector<NDArray> xs(b.count, x), parts(b.count, out);   // 뷰는 여기서(호출 스레드) 만든다
    for (std::int64_t t = 0; t < b.count; ++t) {
        const std::int64_t begin = t * b.size;
        xs[t].shape[b.axis] = std::min(x.shape[b.axis] - begin, b.size);
        xs[t].data += begin * x.strides[b.axis];
        parts[t].data = store.get() + t * bytes;
    }
    parallel::parallel_for(b.count, [&](std::int64_t t) {
        std::memcpy(parts[t].data, out.data, bytes);             // 시작값 복사
        fold(xs[t], parts[t]);                                   // 이 블록을 복사본에 접기
    });
    NDArray all = out;                                           // 복사본들을 축 하나로 쌓은 뷰
    all.data = store.get();
    all.shape[b.axis] = b.count;
    all.strides[b.axis] = bytes;
    const IterOperand ops[] = {operand(all), operand(out)};
    NdIter(all.shape_span(), ops).run(combine, nullptr, Split::Reduction);   // 블록 순서대로
}
```

블록 뷰(`xs`, `parts`)는 태스크에 들어가기 전에 호출 스레드에서 미리 만들어요. `NDArray`를 복사하면 Python 쪽 `.base` 객체의 참조 횟수가 바뀌는데, 태스크는 GIL 없이 돌고, GIL 없이 참조 횟수를 건드리면 Python 객체가 망가질 수 있어요.

### 언제, 몇 개로 나누는가

`plan_blocks`가 정해요. `plan_blocks`가 보는 것은 모양, 레이아웃, dtype과 이터레이터의 분할 계획(`NdIter::plan`)뿐이에요. 분할 계획 자체도 스레드 수를 보지 않아요.

- 출력이 원소 하나이고 형변환이 없으면 나누지 않아요. 그 경우는 pairwise 트리나 순서와 상관없는 조각이 이미 긴 구간을 나눠요.
- 원래 계획의 태스크가 8개 이상이면 나누지 않아요. 출력 축만으로 충분히 나뉘어요.
- 일이 기준값보다 작으면 나누지 않아요. 일은 "원소 수 × 피연산자의 안쪽 stride 중 가장 큰 것(최대 8바이트)"로 세고, float64 원소 32768개(`kParallelThreshold`)에 해당하는 262144바이트와 비교해요.
- 나눌 축은 줄이는 축 중 가장 긴 것이에요. 블록 수는

$$
\text{want} = \min\!\Big(16,\ \Big\lfloor \frac{\text{extent}}{32} \Big\rfloor,\ \Big\lfloor \frac{W}{4096} \Big\rfloor\Big)
$$

이고($W$는 일을 float64 원소 수로 환산한 것), $\text{want} < 2$이거나 원래 계획의 태스크 수 이하이면 나누지 않아요. 블록 크기는 $\lceil \text{extent}/\text{want} \rceil$, 블록 수는 $\lceil \text{extent}/\text{크기} \rceil$예요.

| 상수 | 값 | 이유 |
|---|:---:|---|
| `kMaxBlocks` | 16 | 블록 하나마다 출력 크기의 복사본(채우기와 마지막 접기)이 들어요. 10스레드를 채우고 남을 만큼이면 충분해요 |
| `kMinBlock` | 32 | 블록이 짧으면 복사본 비용이 두드러져요. (64, 2000)을 8행짜리 블록 8개로 나누면 1스레드가 30% 느려져요. 블록당 32행 이상이면 복사본 비용이 약 10분의 1로 줄어요 |
| `W / 4096` | — | 블록 하나가 태스크 하나(`kParallelTask` = 4096원소) 이상의 일을 맡게 해요 |

예를 들면 이래요.

| shape (`sum(axis=0)`) | 원래 계획 | 블록 |
|---|:---:|:---:|
| (1000, 1000) | 태스크 1개 (1000열은 1024보다 짧음) | 63행 × 16개 (마지막 55행) |
| (300, 300) | 태스크 1개 | 34행 × 9개 (마지막 28행) |
| (64, 2000) | 태스크 2개 (2000열을 1024씩) | 나누지 않음: 64/32 = 2가 태스크 수 2 이하 |

형변환이 있는 전체 리덕션(`sum(bool)`, `mean(int64)`)도 블록으로 나눠요. 버퍼 캐스팅이 커널에 4096원소씩 넘기므로 커널이 구간을 나눌 수 없기 때문이에요. 블록으로 나누지 않으면 bool 1000만 개의 `sum`이 1스레드 1.47ms, 10스레드 1.33ms로 거의 병렬이 되지 않아요. 블록마다 자기 버퍼 캐스팅을 직렬로 돌리면 블록끼리 병렬이 돼요.

### 결정성과 numpy와의 관계

블록 구조는 모양, 레이아웃, dtype만으로 정해지고, 스레드가 하나여도 같은 구조로 계산해요. "스레드가 있을 때만 블록으로" 같은 경로는 없어요. 그래서 결과는 스레드 수와 상관없이 같은 비트예요.

대신 float 덧셈과 곱셈은 numpy와 비트가 다를 수 있어요. numpy는 열마다 1000행을 위에서부터 순서대로 더하고, stardust는 블록 안에서 순서대로 더한 뒤 블록 합 16개를 순서대로 더해요. 정규분포 (1000, 1000)의 `sum(axis=0)`에서 numpy와 비트가 같은 열은 5.1%예요. 같은 데이터로 1, 2, 3, 7, 10스레드의 결과를 바이트로 비교하면 모두 같아요(`sum(axis=0)`, `var(axis=0)`, 긴 `cumulative_sum`, `prod` 모두). 블록으로 나누지 않는 (64, 2000), (100, 100), (200, 50)은 numpy와 비트가 같고, (300, 300)은 9개 블록으로 나뉘어 달라요. max/min, any/all, 정수 합은 블록으로 나눠도 numpy와 같아요.

정확도는 오히려 좋아져요. 열 하나의 합에서 가장 긴 덧셈 경로는 numpy가 999번, 블록 리덕션은 블록 안 62번 + 블록 사이 15번 = 77번 정도예요. 오차 한계가 약 13분의 1이에요. 1000×1000 정규분포 `sum(axis=0)`의 numpy 대비 최대 상대 차이는 입력에 따라 $10^{-13}$ ~ $10^{-12}$ 정도예요(시드 4개로 잰 값). 합이 0에 가까운 열일수록 상대 차이가 커져요.

### 블록의 비용과 이득

블록으로 나눌 때와 나누지 않을 때를 같은 조건에서 비교한 값이에요(`sum(axis=0)`, 1스레드 / 10스레드).

| shape | 나누지 않을 때 | 블록으로 나눌 때 | numpy |
|---|---:|---:|---:|
| (1000, 1000) | 123 / 115µs | 130 / **32µs** | 123µs |
| (4000, 250) | 122 / 122µs | 126 / **42µs** | 129µs |
| (300, 300) | 10.7 / 10.7µs | 12.4 / 7.3µs | 11.4µs |
| (64, 2000) | 14.6 / 11.3µs | 나누지 않음 | 15.4µs |

블록으로 나누면 1스레드에서는 복사본 비용으로 3~16% 느려지고, 10스레드에서는 (1000, 1000) 기준 3.6배 빨라져요. 블록 리덕션은 `mean`, `var`의 두 번째 패스, NaN을 건너뛰는 합과 개수에도 같은 코드로 쓰여요.

## float/complex `prod`

### 문제: 곱셈 사슬 하나

왼쪽부터 차례로 곱하면 곱셈 하나(지연 4사이클)씩 기다리는 사슬 하나가 돼요. 원소 100만 개에 0.78ms가 걸리고, numpy의 float `prod`가 바로 이 방식이에요. 더 빠르게 하려면 곱하는 순서를 바꿀 수밖에 없고, 순서를 바꾸면 numpy와 비트가 같을 수 없어요. 그래서 `prod`는 numpy의 순서 대신, 빠르면서 병렬로 나눌 수 있는 순서로 곱해요.

### 접근: 4096원소 조각, 조각 안에 누산기 8개

```cpp
// array/kernels/reduce.hpp의 product_piece (발췌)
template <typename T, typename Get>
T product_piece(std::int64_t b, std::int64_t m, const Get& get) {
    if (m < 8) { /* 왼쪽부터 곱한다 (m == 0이면 1) */ }
    T a[8];
    for (int j = 0; j < 8; ++j) a[j] = get(b + j);
    std::int64_t i = 8;
    for (; i + 8 <= m; i += 8)
        for (int j = 0; j < 8; ++j) a[j] = a[j] * get(b + i + j);    // 누산기 j는 8칸 간격
    for (int j = 0; i < m; ++i, ++j) a[j] = a[j] * get(b + i);       // 나머지는 a[0]부터
    for (int w = 1; w < 8; w *= 2)                                    // ((a0·a1)·(a2·a3))·((a4·a5)·(a6·a7))
        for (int j = 0; j < 8; j += 2 * w) a[j] = a[j] * a[j + w];
    return a[0];
}
```

`product_mt`는 구간을 4096원소(`kLeaf`) 조각으로 나눠 조각마다 `product_piece`를 부르고, 조각 결과를 왼쪽부터 곱해요. $n \ge 32768$이고 풀을 쓸 수 있으면 조각을 병렬로 계산해요. 구조는 $n$에만 의존하므로 1스레드에서도 같은 구조로 계산하고, 결과는 스레드 수와 상관없이 같아요. complex도 같은 코드이고, 곱셈은 numpy와 같은 FMA 공식의 `ops::Multiply::f`예요.

1스레드는 numpy보다 약 7.3배, 10스레드는 약 21µs로 약 37배 빨라요. complex는 1스레드 14배, 10스레드 108배 빨라요. 스레드 수를 1, 2, 4, 10으로 바꾸면 105, 63, 33, 22µs로 고르게 줄어요. `product_mt`는 100만 개를 4096원소 조각 245개로 나눠 `parallel_for`로 돌리고, 조각 결과를 `part` 배열에 모아 왼쪽부터 곱해요. 조각 하나가 0.5µs 정도의 일이고, 조각 결과를 쓰는 것은 조각마다 한 번뿐이라 캐시 라인을 다투는 비용도 무시할 만해요.

데이터에 따라 속도가 달라지지도 않아요. 이 입력의 곱은 언더플로해서 0이 되므로 서브노멀 연산이 끼어들 수 있지만, 모두 1.0인 입력, 1에 가까운 입력, 넘쳐서 `inf`가 되는 입력도 1스레드 103~107µs, 10스레드 22~25µs로 같아요.

### 정확도: 한계는 같고, 비트는 달라요

곱셈은 덧셈과 달리 순서가 오차 **한계**를 바꾸지 않아요. 넘침이나 언더플로가 없으면 어떤 순서든 곱셈 $n-1$번이 각자 $(1+\delta)$를 하나씩 곱하므로

$$
\hat p = p \prod_{k=1}^{n-1} (1 + \delta_k), \qquad |\hat p - p| \le \gamma_{n-1}\,|p|
$$

이에요(Higham [1] 3장). 순서가 바뀌면 마지막 비트는 달라지지만, 최악의 상대오차 한계는 numpy의 왼쪽부터 곱하기와 같아요.

<Callout type="warn" title="넘침과 언더플로의 시점이 바뀌어요">
곱하는 순서가 바뀌면 중간값이 넘치거나 0이 되는 시점도 바뀌어요. 그래서 차이가 마지막 비트에 그치지 않는 입력이 있어요. numpy가 유한한 값을 낼 때 stardust가 `inf`나 `nan`을 낼 수 있고, 그 반대도 있어요.
</Callout>

예를 들어 `[1e200, 1e-200]`을 8번 반복한 원소 16개를 곱하면 이래요.

```python
>>> import stardust as sd
>>> sd.prod(sd.asarray([1e200, 1e-200] * 8))
nan
```

numpy는 왼쪽부터 곱해서 중간값이 1과 1e200 사이를 오가고 답은 `1.0`이에요. stardust에서는 누산기 0이 0번째와 8번째(둘 다 1e200)를 맡아 `1e200 · 1e200 = inf`, 누산기 1이 1번째와 9번째(둘 다 1e-200)를 맡아 `1e-200 · 1e-200 = 0`이 되고, 합칠 때 `inf · 0 = nan`이에요.

반대 방향의 예도 있어요. $[0.5, 1.5)$의 균등분포 난수 100만 개를 곱하면 참값은 대략 $e^{-45000}$이라 double로는 0이에요. stardust는 `0.0`, numpy는 `5e-324`(가장 작은 서브노멀 $2^{-1074}$)를 내요. numpy의 사슬이 $2^{-1074}$에 이르면 그다음부터는 0.5보다 큰 수를 곱할 때마다 반올림으로 다시 $2^{-1074}$가 되어 거기에 머물러요. stardust의 누산기 8개는 각자 0까지 내려가요. 둘 다 언더플로이지만 다른 값이에요.

넘쳤을 때 왼쪽부터 다시 계산하는 방법은 쓰지 않아요. 넘침을 보고 경로를 바꾸면 데이터의 값에 따라 알고리즘이 달라져요. 그러면 계산 순서가 모양·레이아웃·dtype만으로 정해지지 않고, 같은 모양의 입력이라도 값에 따라 다른 순서로 계산돼요. NaN 전파, `inf · 0 = nan` 규칙, 스레드 수와 상관없는 결과는 그대로예요. 블록 `prod(axis=0)`과 긴 `cumulative_prod`도 같은 이유로 넘치는 시점이 numpy와 다를 수 있어요.

## 누적 스캔

### 의미

`cumulative_sum`의 첫 출력은 "항등원 + 첫 입력"이 아니라 첫 입력 그 자체예요. 그래서 `-0.0`이 남아요(numpy와 같아요). `0.0 + -0.0`은 `+0.0`이 되기 때문에 이 차이가 보여요.

```python
>>> sd.cumulative_sum(sd.asarray([-0.0, -0.0]))
array([-0.0, -0.0], dtype=float64)
```

`include_initial=True`(Array API)면 출력 앞에 항등원(0 또는 1)을 먼저 쓰고, 그다음 칸부터 스캔해요. 스캔은 인덱스 순서가 중요한 연산이라 `argmax`처럼 레인 단위로 돌아요(`run_lanes`). 레인끼리는 독립이므로 여러 레인은 레인 단위로 병렬이고, 그 안에서 부른 병렬 호출은 직렬로 돌아요. 태스크마다 다시 일을 나누면 스레드 10개가 각자 일을 만들어 서로 다투게 되기 때문이에요([스레드풀과 결정성](/internals/core/threads/)).

### 문제: 순차 스캔은 사슬 하나

`acc = acc + x[i]; out[i] = acc`는 덧셈 지연(원소당 약 0.5ns)에 묶인 사슬 하나예요. 원소 100만 개에 495µs예요. 더 빠르게 하려면 사슬을 여러 개로 나눠야 해요.

### 접근: 2단계 블록 스캔

float/complex 레인이 8192원소(`2 * kScanBlock`) 이상이면 이렇게 해요. 블록 크기는 `kScanBlock` = 4096이에요.

1. **블록마다 따로 스캔해요.** 각 블록은 자기 첫 원소에서 출발해요. 블록 4개(`kScanGroup`)를 한 루프에서 나란히 돌려 사슬 4개를 동시에 진행하고, 블록 묶음은 풀에서 병렬로 돌아요.
2. **carry를 직렬로 구해요.** 블록 $b$의 carry는 블록 $b$ 앞의 모든 원소의 합이에요. 블록 끝값들만으로 계산돼요(블록 수만큼의 덧셈).
3. **블록 1부터 각 원소에 carry를 더해요**(곱셈 스캔이면 곱해요). 의존성이 없는 스트리밍 루프라 벡터화되고 병렬로 돌아요.

블록 $b$ 안의 $j$번째 원소를 $\ell^{(b)}_j$(그 블록 안에서의 누적합)라고 하면

$$
c_1 = \ell^{(0)}_{4095}, \qquad c_b = c_{b-1} + \ell^{(b-1)}_{4095}, \qquad y^{(b)}_j = c_b + \ell^{(b)}_j \quad (b \ge 1)
$$

3단계는 출력을 한 번 더 지나는 추가 패스예요. 그래도 1단계에서 사슬 4개가 동시에 진행되는 이득이 더 커서 1스레드에서도 순차 스캔보다 빨라요(순차 495µs, 블록 385µs).

블록은 $n$에만 의존하고, float 스캔은 스레드가 하나여도 이 경로를 타요. 그래서 스레드 수와 상관없이 같은 비트예요. 정수 스캔은 wrap하는 덧셈·곱셈이라 어느 경로로 해도 비트가 같아요. 그래서 정수 스캔은 병렬로 돌 수 있을 때($n \ge 32768$이고 풀을 쓸 수 있을 때)만 블록 경로를 타요. 그래야 3단계의 추가 패스를 감수할 값어치가 있어요.

### 1단계 루프의 구현

1단계의 "블록 4개 나란히" 루프에는 속도를 좌우하는 선택이 네 가지 들어 있어요.

```cpp
// array/kernels/reduce.hpp의 scan_group (발췌)
template <typename Op, typename T, bool Contig, bool SkipNan = false>
void scan_group(const std::byte* x, std::int64_t xs, std::byte* o, std::int64_t os,
                std::int64_t first, std::int64_t blocks, std::int64_t n) {
    if constexpr (Contig) xs = os = sizeof(T);              // stride가 컴파일 시점 상수
    // ... xp[j], op[j]: 블록 j의 시작, acc[j]: 블록 j의 누산기
    auto chunk = [&]<bool First>(std::int64_t i) {
        T v[kScanGroup][8];
        for (int j = 0; j < kScanGroup; ++j)
            for (int k = 0; k < 8; ++k) v[j][k] = ld(j, i + k);           // 블록마다 8개 load
        if constexpr (First)
            for (int j = 0; j < kScanGroup; ++j) acc[j] = v[j][0];        // 자기 첫 원소에서 출발
        for (int k = First ? 1 : 0; k < 8; ++k)
            for (int j = 0; j < kScanGroup; ++j) v[j][k] = acc[j] = Op::f(acc[j], v[j][k]);  // 사슬 4개
        for (int j = 0; j < kScanGroup; ++j)
            for (int k = 0; k < 8; ++k) st(j, i + k, v[j][k]);            // 블록마다 8개 store
    };
    chunk.template operator()<true>(0);
    for (std::int64_t i = 8; i < kScanBlock; i += 8) chunk.template operator()<false>(i);
}
```

- **블록마다 8개씩 모아서 load → scan → store.** 블록 4개에 원소 하나씩 번갈아 저장하는 것이 가장 단순하지만 느려요. 결과는 언제나 새로 할당한 배열에 쓰는데, 새 메모리의 첫 쓰기는 16KB 페이지마다 페이지 폴트를 일으켜요. 블록 4개는 32KB씩 떨어져 있어 서로 다른 페이지이고, 원소 하나씩 번갈아 쓰면 4개 페이지의 폴트가 겹쳐 5.7배 느려요(100만 개 1.7ms 대 0.3ms).
- **연속이면 stride를 컴파일 시점 상수로.** `Contig` 템플릿 인자가 참이면 stride를 `sizeof(T)`로 고정해요. stride를 런타임 값으로 두면 2.3배 느려요.
- **첫 덩어리는 `template <bool First>`로 분리.** 첫 덩어리에만 "누산기를 첫 원소로 초기화"하는 단계가 있어요. 시작 인덱스를 런타임 값으로 두면 루프 경계가 상수가 아니라서 컴파일러가 루프를 완전히 펼치지 못하고, `v[4][8]`이 레지스터가 아니라 스택에 남아 2배 느려요. C++20의 템플릿 람다(`[&]<bool First>`)를 `chunk.template operator()<true>(0)`로 부르면 같은 본문에서 두 판이 컴파일 시점에 갈라져요.
- **타입으로 직접 읽기.** `load_as`(내부가 `memcpy`)로 읽으면 컴파일러가 값을 스택에 두어 원소마다 메모리 연산이 세 번 생겨요. 연속이면 `reinterpret_cast<const T*>`로 직접 읽어요.

블록 4개가 다 차지 않는 마지막 묶음은 블록마다 순차 스캔(`scan_serial`)을 해요. carry 배열도 `make_unique_for_overwrite`로 0을 채우지 않고 할당해요.

### 정확도

8192원소 이상의 float 스캔은 numpy와 비트가 다를 수 있어요. 정규분포 1,000,003개로 비교하면 첫 블록(0~4095)과 두 번째 블록의 처음 몇 원소는 같고, 처음 달라지는 위치는 4099예요. 전체의 99.3%가 마지막 비트에서 다르고, numpy 대비 최대 상대 차이는 4.2e-13이에요. 8191원소 레인은 블록 경로를 타지 않아 numpy와 비트가 같아요.

정확도는 나빠지지 않아요. 순차 스캔에서 $i$번째 결과는 덧셈 $i$번의 경로를 거치지만, 블록 스캔에서는 블록 안 $(i \bmod 4096)$번 + carry $\lfloor i/4096 \rfloor$번 + 1번이에요. 원소 100만 개의 마지막 결과라면 경로가 약 100만에서 약 4300으로 줄어요.

## mean, var, std

### mean

결과 dtype(float64 또는 complex128)으로 합한 뒤 개수로 나눠요. 합은 `sum`과 같은 `run_reduce`이므로 pairwise, 블록, 병렬이 모두 그대로 적용돼요. 빈 입력은 `0/0 = nan`이에요. 정수 입력은 버퍼 캐스팅으로 float64가 되어 4096원소씩 합해져요. 그래서 `mean(int64)`는 형변환이 있는 리덕션이고 numpy와 비트가 다를 수 있어요. 예를 들어 $\pm 2^{62}$ 범위의 int64 100만 개 `j`로 `sum(j, dtype=float64)`를 구하면 난수 입력 20개 모두에서 numpy와 비트가 달라요. 값이 작아서 부분합이 모두 $2^{53}$ 아래의 정수로 정확히 표현되면 어떤 순서로 더해도 같으니 차이가 없어요.

frame의 int64 `mean`도 `sd.sum(x, dtype=sd.float64)`을 개수로 나누는 같은 계산이라, 두 영역의 결과가 비트까지 같아요.

### var: 두 패스

`var`는 입력을 두 번 읽어요. 먼저 평균을 구하고, 그다음 편차 제곱을 더해요.

$$
\bar x = \frac{1}{N}\sum_{i} x_i, \qquad \operatorname{var} = \frac{1}{N - c} \sum_{i} \lvert x_i - \bar x \rvert^2
$$

$c$는 `correction`(기본 0)이에요. $N - c \le 0$이면 NaN이에요(빈 입력 포함, Array API). numpy는 이때 경고를 내고 0으로 나눠요.

1. 첫 패스: 위의 `mean`을 keepdims 모양으로 구해요(`mean_keepdims`).
2. 둘째 패스: `sq_dev_loop`가 입력과 (브로드캐스트한) 평균을 읽어 $\lvert x - m \rvert^2$를 그 자리에서 계산하고 접어요. 임시 배열은 만들지 않아요. 안쪽 축이면 접근자 람다로 pairwise 트리에 넣고, 바깥 축이면 원소마다 더하고, 필요하면 블록 리덕션으로 나눠요.

```cpp
// array/kernels/reduce.hpp의 sq_dev_loop (발췌)
template <typename T, bool SkipNan = false>
void sq_dev_loop(std::byte* const* args, std::int64_t n, const std::int64_t* s, void*) {
    auto sq = [&](std::int64_t i) {
        const T d = load_as<T>(x + i * s[0]) - load_as<T>(m + i * s[1]);
        double sq;
        if constexpr (ops::is_cplx<T>) sq = d.real() * d.real() + d.imag() * d.imag();
        else sq = d * d;
        return sq;                                   // (SkipNan이면 NaN 자리에 +0.0)
    };
    if (s[2] == 0) { *out += pairwise_sum_mt(n, sq); return; }   // 안쪽 축: sum과 같은 pairwise
    for (std::int64_t i = 0; i < n; ++i) out[i * s[2]] += sq(i);  // 바깥 축
}
```

`std = sqrt(var)`예요. complex 입력의 편차 제곱은 $\mathrm{re}^2 + \mathrm{im}^2$이고 결과는 float64예요. `-ffp-contract=off`로 빌드하므로 `d * d`나 `re*re + im*im`이 FMA로 합쳐지지 않아요.

정수 입력의 두 번째 패스는 `as_dtype(x, float64)`로 입력 전체의 float64 복사본을 먼저 만들어요. 첫 패스(`mean`)는 버퍼 캐스팅이라 복사본이 없지만, 두 번째 패스는 복사본을 거쳐요.

### 두 패스를 쓰는 이유: 정확도

교과서의 한 패스 공식 $\sum x_i^2 - (\sum x_i)^2 / N$은 큰 두 수의 차라서 자릿수가 사라져요. 평균에 비해 분산이 작은 데이터에서 심해요. 예를 들어 `[4, 7, 13, 16] + 1e9`의 참분산은 22.5인데, 한 패스 공식으로 float64 계산을 하면 `-128.0`이 나와요. 두 패스인 `sd.var`는 `22.5`예요.

Chan, Golub, LeVeque [3]의 분석에서는 조건수 $\kappa = \lVert x \rVert_2 / \sqrt{S}$($S$는 편차 제곱합)로 상대오차를 대략 이렇게 어림해요.

| 알고리즘 | 상대오차의 크기 |
|---|:---:|
| 교과서 한 패스 공식 | $N u\,\kappa^2$ |
| 두 패스 (평균을 먼저 빼기) | $N u + N^2 u^2 \kappa^2$ |

평균이 분산보다 크면 $\kappa^2 \approx 1 + N\bar x^2 / S$가 커져요. 한 패스 공식의 오차는 $\kappa^2$에 비례해 커지지만, 두 패스에서는 $\kappa^2$ 항에 $u^2$가 곱해져 있어요. stardust는 두 합을 모두 pairwise로 하므로 위 식의 $N$이 합의 경로 길이 $h$(약 $\log_2 N$ 크기)로 줄어요.

Welford [4]의 한 패스 갱신 공식은 메모리를 한 번만 읽지만, numpy와 다른 연산을 하므로 비트가 같을 수 없어요. 그래서 numpy와 같은 두 패스를 써요.

### numpy와의 비트 관계, 그리고 속도

numpy 2.5.4의 `_var`(`numpy/_core/_methods.py` [5])는 평균을 `umr_sum` 후 `true_divide`로 구하고, `x = subtract(arr, arrmean)`으로 새 배열을 만든 뒤 `square(x, out=x)`로 제자리에서 제곱하고, `umr_sum(x)`로 더해요. 값으로는 stardust와 같은 연산을 같은 순서로 해요. 편차 제곱이 같은 값이고 같은 pairwise 트리로 더해지니, 연속 float64 배열 전체의 `var`/`std`는 numpy와 비트가 같아요(1스레드, 10스레드 모두). 블록으로 나뉘는 축 리덕션이나 형변환이 있는 경우는 합의 순서가 달라 다를 수 있어요.

complex 입력은 합이 numpy와 비트까지 같아도 `mean`과 `var`/`std`의 마지막 비트가 다를 수 있어요. 합을 개수 $N$으로 나누는 방법이 다르기 때문이에요. numpy의 complex 나눗셈은 분모의 역수를 먼저 구해 실수부와 허수부에 곱하고($a \cdot (1/N)$), stardust는 실수부와 허수부를 $N$으로 직접 나눠요($a / N$). 두 결과는 마지막 비트에서 갈릴 수 있고, 평균이 다르면 편차 제곱합도 달라져요. 길이가 제각각인 난수 입력 300개 가운데 `mean`은 120개, `var`는 77개가 numpy와 달라요.

속도는 메모리 왕복 수에서 갈려요. numpy는 평균 패스(읽기) + 빼기(읽기, 새 배열 쓰기와 그 페이지 폴트) + 제곱(읽기, 쓰기) + 합(읽기)이고, stardust는 평균 패스(읽기) + 편차 제곱합 패스(읽기)예요. 원소 100만 개 `var(f)`는 numpy 478µs, 1스레드 312µs(1.53배), 10스레드 58µs(8.3배)예요.

## numpy와 비트가 달라지는 경우

결정성(스레드 수와 상관없이 같은 비트)은 모든 경우에 지켜요. numpy와 비트를 맞추는 일은 아래 경우에만 포기하는데, 이유는 모두 같아요. numpy의 순서를 지키면 병렬로 나눌 수 없거나, 사슬 하나에 묶여 느려요.

| 경우 | stardust의 순서 | 얻는 것 |
|---|---|---|
| 줄이는 축이 바깥에 있어 남는 축만으로 나눌 수 없는 리덕션 (`sum`/`mean`/`var`/`prod(axis=0)` 등) | 줄이는 축을 고정 블록으로 | 1000×1000 `sum(axis=0)`이 10스레드에서 numpy의 4.0배 |
| float/complex `prod` | 4096원소 조각 안에 누산기 8개 | 1스레드에서 numpy의 7.3배 |
| 8192원소 이상의 float/complex `cumulative_sum`/`cumulative_prod` | 4096원소 블록 2단계 스캔 | 순차 스캔 대비 1스레드 1.3배, 10스레드 7배 |
| 형변환이 필요한 리덕션 (`mean(int64)`, `sum(x, dtype=float64)` 등) | 4096원소 버퍼 단위로 접고, 전체 리덕션은 고정 블록으로 | 메모리 왕복 감소, 병렬화 |

numpy의 기본 버퍼 크기는 `np.getbufsize()` = 8192원소이고(numpy 2.5.4), stardust의 버퍼는 L1에 맞춘 4096원소예요. 버퍼 경계가 다르니 덧셈 순서도 달라서, 위에서 본 것처럼 큰 정수의 float64 합은 numpy와 비트가 달라요.

정수 결과(`sum(bool)`, 정수 합·곱)는 순서와 상관없으므로 언제나 같아요. 형변환이 없고 출력이 하나인 긴 합(`sum(f)`)은 numpy와 비트가 같아요.

- **`sum`, `mean`, `max`:** 1스레드는 numpy와 같은 수준이에요. 둘 다 메모리를 한 번 읽는 연산이라 메모리에 묶여 있어요(8MB를 111µs에 읽으면 초당 약 72GB). 10스레드는 numpy 대비 `sum`과 `mean`이 4.7~4.8배, `max`가 3.3배에서 대역폭에 걸려요. `sum(m, axis=0)`의 0.99배는 같은 속도로 봐야 해요.
- **`sum(m, axis=0)`:** 블록 리덕션 덕분에 10스레드에서 4.0배예요. 블록으로 나누지 않으면 태스크 하나라 1스레드와 같아요.
- **`argmax(f)`:** 원소마다 비교와 선택이 있는 계산 중심이라 10스레드에서 9.7배예요. `argmax(i)`는 두 번 읽는 NEON 루프라 1스레드에서 numpy와 같아요.
- **`var`:** 메모리 왕복이 numpy보다 적어서 1스레드에서도 1.53배예요. int64 입력은 두 번째 패스 전에 float64 복사본을 만들지만 numpy보다 1.77배 빨라요.
- **`count_nonzero(b)`:** 바이트 카운터 루프로 numpy와 같아요.
- **`cumulative_sum`:** 직렬 스캔부터 numpy보다 빠르고, 블록 스캔과 병렬로 더 벌어져요.

곱과 NaN을 건너뛰는 리덕션의 측정이에요. `fn`은 표준정규분포 100만 개의 10%를 NaN으로 바꾼 배열이에요.

- **`prod`:** 1스레드 7.3배는 누산기 8개로 곱셈 사슬을 8개로 나눈 효과예요. 10스레드는 245개 조각으로 나눠 약 21µs예요.
- **`cumulative_prod`:** `cumulative_sum`과 같은 블록 스캔이라 배율도 비슷해요(5.5배, 31배).
- **`nansum`:** 1스레드 8.1배, 10스레드 50배예요. 차이는 패스 수에서 나요. numpy 2.5.4의 `nansum`(`numpy/lib/_nanfunctions_impl.py`)은 `_replace_nan`으로 `np.isnan(a)` 마스크를 만들고, `a`를 통째로 복사하고, `np.copyto(a, 0, where=mask)`로 NaN 자리를 0으로 바꾼 뒤 `np.sum`을 불러요[8]. 마스크와 복사본이라는 새 배열 둘을 쓰고 읽어요. stardust의 `nansum`은 [항을 접근자로 넘기기](#항을-접근자로-넘기기)의 접근자에서 NaN을 0으로 바꿔 pairwise 트리에 바로 흘려보내요(`nan_fold` → `nan_fold_keepdims`, `reduce_loop`의 NaN 건너뛰기 판). 입력을 한 번만 읽으므로 `sum(f)`(111µs)보다 조금 느린 157µs에 끝나요. 같은 트리를 지나므로 "NaN을 0으로 바꾼 배열의 `sum`"과 비트가 같아요. numpy도 결국 그 배열의 pairwise `sum`이라, 1스레드와 10스레드 모두 numpy와 비트까지 같아요.

### 복잡도

| 연산 | 시간 | 추가 메모리 |
|---|:---:|---|
| `sum`, `prod`, `max`, `min`, `any`, `all` | $O(N)$ | 출력, 병렬 조각 결과 $O(N/4096)$, 블록이면 복사본 $\le 16 \times$ 출력 |
| pairwise 트리 | $O(N)$, 재귀 깊이 $O(\log N)$ | 병렬이면 부분 트리 목록 $O(N/4096)$ |
| `argmax`, `argmin` | $O(N)$ (NaN이 있으면 최대 2번 훑음) | 비연속 `axis=None`이면 C 순서 복사본 |
| 누적 스캔 | $O(N)$, 블록이면 출력을 한 번 더 지남 | 출력, carry $O(N/4096)$ |
| `mean` | $O(N)$ | 출력 |
| `var`, `std` | $O(N)$, 입력을 두 번 읽음 | 출력과 평균 (정수 입력이면 float64 복사본) |

## 정확도

| 연산 | numpy 2.5.4와의 관계 | 오차 한계 |
|---|---|---|
| float/complex `sum` (출력 하나, 형변환 없음) | 비트까지 같음, 스레드 수와 무관 | $\gamma_h \sum \lvert x_i \rvert$, $h \lesssim 24 + \lceil \log_2(n/128) \rceil$ |
| 안쪽 축 합 (`axis=-1`, C 순서) | 비트까지 같음 | 같음 |
| 블록 리덕션 (`sum(axis=0)` 등) | 다를 수 있음 (1000×1000 정규분포에서 최대 상대 차이 $10^{-13}$ ~ $10^{-12}$) | 블록 길이 + 블록 수로 줄어 순차 합보다 작음 |
| 정수 합·곱, max/min, any/all, argmax/argmin | 같음 | 정확 (정수는 wrap) |
| float/complex `prod` | 다를 수 있음, 넘침·언더플로 시점도 다를 수 있음 | $\gamma_{n-1} \lvert p \rvert$ (numpy와 같은 한계) |
| 누적 스캔, 8192원소 미만 | 같음 | — |
| 누적 스캔, 8192원소 이상 (float/complex) | 다를 수 있음 (최대 상대 차이 4.2e-13) | 경로 길이 $(i \bmod 4096) + \lfloor i/4096 \rfloor + 1$ |
| `mean`, `var`, `std` (연속 float64 전체) | 비트까지 같음 | 두 패스 [3] |
| complex `mean`, `var`, `std` | 마지막 비트가 다를 수 있음 (개수로 나누는 방법 차이) | 두 패스 [3] |
| 형변환이 있는 리덕션 | 다를 수 있음 | 버퍼 4096원소 단위의 pairwise |

테스트도 이 구분을 따라요. 같다고 한 것은 비트로 비교하고, 다를 수 있다고 한 것은 상대오차로 비교하면서, 1·2·3·7·10스레드의 결과가 바이트까지 같은지 따로 확인해요. 자세한 것은 [정확도와 검증](/internals/array/accuracy/)에 있어요.
