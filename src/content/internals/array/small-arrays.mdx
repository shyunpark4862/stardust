## 한눈에 보기

원소 3개짜리 float64 배열 두 개를 더하는 `a + b`에서 실제 덧셈은 1ns도 걸리지 않아요. 나머지는 모두 **호출 경로의 고정 비용**이에요. Python이 연산자를 C++ 함수로 넘기고, 인자를 검사하고, 결과 배열을 할당하고, 이터레이터를 준비하고, 결과를 Python 객체로 감싸는 비용이에요. 배열이 작을수록 이 비용이 전부가 돼요.

stardust는 이 비용을 다루는 데 세 가지 원칙을 지켜요.

1. 일반 경로를 싸게 만들어요. 연산마다 "작은 배열 전용 경로"를 따로 두지 않고, 모든 호출이 지나는 공통 부분(배열 객체의 할당, 타입 찾기, `NDArray` 복사, Buffer, 이터레이터)이 필요한 만큼만 일하게 해요. 특수 경로를 남발하면 경로마다 의미가 미세하게 달라질 위험이 생기고, 테스트해야 할 조합이 늘어나요.
2. 원인은 프로파일러로 찾아요. macOS의 `sample` 프로파일러로 작은 연산을 반복하는 루프를 보면, 시간은 nanobind의 호출 처리(약 10ns)나 계산이 아니라 할당, 해시표 찾기, 메모리 복사에 가 있어요.
3. 차원 상한은 지켜요. 배열 객체가 512바이트를 넘어 Python의 소형 할당기를 쓰지 못하는 문제는 최대 차원을 32에서 24로 줄이면 사라지지만, 32차원을 지키고 그 대신 객체를 다시 쓰는 인스턴스 풀로 비용을 없애요(아래 "배열 객체의 할당: 인스턴스 풀").

빠른 경로는 넷이에요. int와 slice만인 인덱스 키(`x[1, 2]`, `x[::2]`, `x[:, 5]`), 연속이고 같은 shape인 배열끼리의 작은 원소별 호출(`a + b`), 피연산자가 모두 Python 스칼라인 원소별 호출(`sd.sin(0.5)`), 그리고 `x[key]`와 반복을 받는 타입 슬롯이에요. 모두 일반 경로와 결과가 비트까지 같고, 조금이라도 특이한 입력은 일반 경로로 넘겨요. 이와 별도로 배열의 단순 속성(`shape`, `ndim` …)과 `len()`도 nanobind를 거치지 않고 CPython의 타입 슬롯으로 등록해요.

| 연산 | numpy 2.5.4와 견주면 | 무엇이 시간을 줄이나 |
|---|---|---|
| `finfo(float64)` | 빨라요 | 결과 객체를 한 번만 만들어 공유해요 |
| `x[1, 2]` | 빨라요 | int 키 빠른 경로, Python `float` |
| `x[::2]`, `x[:, 5]`, `x[5]` (뷰) | 빠르거나 같아요 | int·slice 키 빠른 경로, 타입 슬롯, 인스턴스 풀 |
| `x.shape`, `len(x)` | 같아요 | 타입 슬롯 |
| `a + b`, `exp(a)` (원소 3개) | 빨라요 | 이터레이터 없이 커널 한 번, 인스턴스 풀, Buffer 블록 재사용 |
| `zeros(3)`, `empty(3)` | 빠르거나 같아요 | shape를 스택에, 인스턴스 풀, Buffer 블록 재사용 |
| `list(x)`, `x.tolist()` | 빨라요 | 반복자 슬롯, 최종 크기의 리스트 |
| `sd.asarray(numpy 배열)` | `np.asarray`보다 느려요 | `np.asarray`는 입력을 그대로 돌려줘요. stardust는 결과 객체를 하나 만들어야 해요 |

잰 값은 `bench/array/speed.md`의 "작은 배열" 표에 들어가요. `x[1, 2]`는 Python `float`을 돌려주고, 2차원의 `x[5]`는 행 하나의 뷰(새 배열 객체)를 돌려줘요.

## 왜 작은 배열이 중요한가

과학 계산 코드에는 좌표 하나(원소 3개), 작은 행렬 하나(3×3)를 다루는 연산이 Python 루프 안에서 수없이 반복되는 경우가 많아요. 이런 코드에서는 큰 배열에서 아무리 빨라도 호출 한 번이 1µs라면 numpy보다 몇 배 느린 라이브러리가 돼요.

stardust가 Python 층을 얇게 두고 shape 계산, 브로드캐스팅, 인덱스 해석, dtype 결정을 모두 C++에서 하는 이유가 이것이에요([Python과 C++의 경계](/internals/core/python-boundary/)). 이런 로직을 Python으로 짜고 C++에는 커널만 맡기면 코드는 읽기 쉽지만, 작은 배열의 연산 한 번이 수 µs로 늘어나요(numpy는 1µs 이하예요). 이 페이지는 그렇게 C++로 내려온 경로 안에 남은 비용을 다뤄요.

## `a + b` 한 번의 여정

원소 3개짜리 `a + b`가 지나는 길을 순서대로 보면 이래요.

| 단계 | 하는 일 | 할당 |
|---|---|:---:|
| 1. Python → C++ | 인터프리터가 `a`의 타입에서 `__add__`(nanobind 함수 객체)를 찾아 불러요. nanobind가 인자 두 개를 `nb::handle`(빌린 참조)로 넘겨요 | 없음 |
| 2. 피연산자 확인 | `is_operand(b)`: 배열이거나 스칼라(Python bool/int/float/complex, numpy 스칼라)인지 봐요. 배열인지는 저장한 타입 포인터와 비교해요. 아니면 `NotImplemented` | 없음 |
| 3. 루프 고르기 | 두 dtype을 승격하고(`promote`), 루프 표에서 그 dtype 이상인 첫 루프를 골라요(`select`) | 없음 |
| 4. 빠른 길 확인 | 6단계의 조건을 보고 맞으면 4–5단계를 건너뛰어요. 아니면 배열 피연산자의 `NDArray`를 복사해 오고(`prepare`), shape를 고정 배열에 브로드캐스트해요(`broadcast_into`) | 없음 |
| 5. 결과 할당 | 결과 배열을 만들어요(`new_array`나 `new_array_like`). 256바이트 이하면 데이터는 Buffer 안이고, Buffer 블록은 스레드별 목록에서 꺼내요 | 목록이 비었을 때만 1번 |
| 6. 커널 | 피연산자가 모두 같은 shape이고 이미 루프 dtype이며 모두 C 연속(또는 모두 F 연속)이고 일이 풀을 쓰는 기준 아래이면, 이터레이터를 만들지 않고 평평한 메모리 전체에 커널을 한 번 불러요(`launch_contiguous`, n = 3). 아니면 `NdIter`를 만들어요 | 없음 |
| 7. C++ → Python | 결과 `NDArray`를 nanobind 인스턴스로 감싸요(`wrap`). 인스턴스 풀에서 객체를 꺼내고, `NDArray`를 그 자리로 옮겨요 | 풀이 비었을 때만 (Python 객체) |
| (나중에) 해제 | 결과 객체가 사라질 때 `NDArray` 소멸자가 `shared_ptr<Buffer>`를 놓고, 객체는 풀로 돌아가요. Buffer 블록은 스레드별 목록으로 돌아가요 | 보통 없음 |

C++ 쪽에서 메모리를 할당할 수 있는 곳은 5단계 한 곳이고, 그것도 스레드별 목록이 비었을 때뿐이에요. Python 객체도 풀이 비었을 때만 새로 할당해요. 작은 배열 하나에 `Buffer`, 데이터, 참조 카운트 블록을 따로 할당하거나, `std::vector`와 `std::stable_sort`가 임시 메모리를 할당하면 그만큼 호출이 길어져요. 뒤의 절에서 이런 할당을 하나씩 없애요.

4~6단계의 실제 코드를 줄인 발췌예요(`array/ops/ufunc.cpp`의 `launch`).

```cpp
// array/ops/ufunc.cpp (launch, 줄인 발췌)
const size_t nin = objs.size();
if (out_obj.is_none() && std::ranges::none_of(objs, [](nb::handle o) { return is_ndarray(o); }))
    return launch_scalars(objs, in_types, result, loop, nout);  // 모두 스칼라 (아래)
if (out_obj.is_none() && nout == 1)
    if (nb::object r = launch_contiguous(objs, in_types, result, loop, weight); r.is_valid()) return r;
std::array<NDArray, kMaxInputs> ins;
std::array<std::span<const std::int64_t>, kMaxInputs> shapes;  // fixed arrays: no allocation per call
size_t narrays = 0;
for (size_t k = 0; k < nin; ++k) {
    ins[k] = prepare(objs[k], in_types[k]);  // 배열이면 NDArray 복사
    if (is_ndarray(objs[k])) shapes[narrays++] = as_ndarray(objs[k]).shape_span();
}
// ... 브로드캐스트, 결과 할당, NdIter를 만들고 실행, wrap
```

### 작은 호출은 커널 한 번: `launch_contiguous`

같은 shape이고 연속인 배열끼리의 작은 호출에는 이터레이터가 할 일이 없어요. 축을 합치면 1차원 하나가 되고, 풀로 나누지도 않아요. 그런데 `NdIter`를 만들고 입력 `NDArray`를 복사하는 일이 작은 `x + y`에서 눈에 띄는 몫이었어요. 그래서 조건이 맞으면 이터레이터 없이 결과 배열을 할당하고 평평한 메모리 전체에 커널을 한 번 불러요.

```cpp
// array/ops/ufunc.cpp (launch_contiguous, 줄인 발췌)
for (size_t k = 0; k < nin; ++k) {
    if (!is_ndarray(objs[k])) continue;
    const NDArray& a = as_ndarray(objs[k]);
    if (a.dtype != in_types[k]) return {};
    if (first == nullptr) first = &a;
    else if (!std::ranges::equal(a.shape_span(), first->shape_span())) return {};
    c = c && a.c_contiguous;
    f = f && a.f_contiguous;
    bytes = std::max(bytes, a.itemsize());
}
if (first == nullptr || (!c && !f)) return {};
const std::int64_t n = first->size();
// NdIter::run's rule: fewer than three arrays moved (scalars are not) count for less
const std::int64_t arrays = std::ranges::count_if(objs, [](nb::handle o) { return is_ndarray(o); }) + 1;
const std::int64_t work = weight * std::min<std::int64_t>(bytes, 8) * n;
if ((arrays < 3 ? work / 3 * arrays : work) >= 8 * kParallelThreshold) return {};
// ... Python 스칼라는 스택의 원소 하나를 stride 0으로
NDArray res = c ? new_array(result, first->shape_span()) : new_array_like(*first, result);
args[nin] = res.data;
strides[nin] = res.itemsize();
if (n > 0) loop(args.data(), n, strides.data(), nullptr);
return wrap(std::move(res));
```

- 빈 객체를 돌려주면 "일반 경로로 가라"는 뜻이에요. dtype을 바꿔야 하는 피연산자, shape가 다른 피연산자(브로드캐스트), 연속이 아닌 배열, 풀을 쓸 만큼 큰 일은 모두 일반 경로예요.
- 풀을 쓸지는 이터레이터와 같은 식으로 판단해요. 연산의 무게(`weight`)를 곱하고, 움직이는 배열이 셋보다 적으면 그만큼 줄여 세요. 그래서 이터레이터가 풀을 쓰지 않을 크기는 모두 이 길이 맡아요.
- 비트가 같아요. 이터레이터도 이 경우 축을 하나로 합쳐 같은 스레드에서 같은 커널을 같은 인자로 부르기 때문이에요.

<Callout title="한 번의 호출에 할당은 몇 번인가">
`a + b` 하나에 필요한 메모리는 결과 Buffer 블록 하나(데이터가 그 안에 있어요)와 결과 Python 객체 하나예요. 둘 다 해제할 때 버리지 않고 모아 두었다가 다시 써요. Buffer 블록은 스레드별 목록(아래 "할당은 한 번"), Python 객체는 nanobind의 인스턴스 풀(아래 "배열 객체의 할당")이에요. 그래서 연달아 부르는 작은 호출에서는 `malloc`과 `free`가 보통 하나도 없어요.
</Callout>

## 프로파일러가 보여 주는 비용

작은 연산을 반복하는 루프를 `sample`로 보면, 아무 대책이 없을 때 시간은 이런 곳에 가요.

- 결과 객체의 할당과 해제: `NDArray`(560바이트)를 담은 Python 객체는 512바이트를 넘어 Python의 소형 할당기(pymalloc)를 쓰지 못하고 시스템 `malloc`으로 가요. macOS의 `free`가 그 메모리를 0으로 채우고, nanobind가 인스턴스마다 C++ 포인터 → Python 객체 해시표에 넣고 빼요.
- nanobind의 타입 찾기: `nb::isinstance<NDArray>`와 `nb::cast`가 호출마다 `type_info` 해시표를 찾아요.
- 고정 크기 배열을 통째로 복사하고 0으로 채우는 `memmove`, `memset`: `NDArray` 하나가 560바이트, 이터레이터(`NdIter`)가 1,600바이트예요. 작은 연산 하나에도 이런 객체가 여러 번 만들어지고 복사돼요.
- 작은 배열 하나에 `malloc` 세 번: `Buffer` 객체, 데이터, 그리고 `shared_ptr`의 제어 블록(참조 카운트가 사는 곳)이에요. 한 번으로 줄여도 그 블록의 `malloc`·`free`가 작은 연산에서 눈에 띄는 몫이에요.
- 정렬 할당: 타입을 128바이트로 정렬하면 할당이 정렬 할당(`malloc_type_aligned_alloc`)으로 가요.
- 표준 라이브러리의 숨은 할당: `std::vector`(shape, 인덱스 키 항목)와, 축을 정렬하는 `std::stable_sort`가 호출마다 임시 버퍼를 할당해요.
- nanobind의 함수 호출 경로 자체는 약 10ns로 작아요.

numpy보다 느린 원인이 "C++과 Python 사이를 건너는 비용"일 것이라고 짐작하기 쉬운데, 실제로는 stardust 자신의 객체 크기, 할당, 해시표 찾기예요. 그래서 바인딩 층을 바꾸는 대신 데이터 구조와 할당을 다뤄요. 아래 절에서 하나씩 없애요.

## 고정 배열은 두고, 필요한 칸만 만지기

### 왜 고정 배열인가

`NDArray`는 shape와 strides를 객체 안의 **고정 배열**에 담아요([데이터 모델](/internals/array/data-model/)).

```cpp
inline constexpr int kMaxNdim = 32;
using Dims = std::array<std::int64_t, kMaxNdim>;   // 객체 안에 박힌 256바이트

struct NDArray {
    std::shared_ptr<Buffer> buffer;
    std::byte* data = nullptr;
    DType dtype = DType::Float64;
    int ndim = 0;
    Dims shape;      // [0, ndim)만 의미가 있어요
    Dims strides;
    bool c_contiguous = true, f_contiguous = true, writeable = true;
    nb::object base;
};
```

shape를 `std::vector`로 두면 배열(뷰 포함)을 만들 때마다 힙 할당이 하나씩 붙어요. 고정 배열이면 배열을 만들어도 shape 때문에 할당하지 않아요. 대신 객체가 커요. shape와 strides가 각각 32 × 8 = 256바이트라서 `NDArray` 하나가 560바이트예요. 차원 수가 32를 넘으면 ValueError예요.

그래서 고정 배열은 그대로 두고, 필요한 칸만 만져요. 고정 배열의 장점(할당 없음)은 지키면서, 단점(큰 객체를 통째로 복사)만 없애는 방법이에요.

### 복사와 이동은 앞의 ndim칸만

컴파일러가 만들어 주는 복사 생성자는 `Dims` 두 개 512바이트를 모두 복사해요. 3원소 1차원 배열이면 그중 16바이트만 의미가 있어요. 그래서 복사와 이동을 직접 정의해요(`array/ndarray.hpp`, 발췌).

```cpp
NDArray(const NDArray& o) { *this = o; }
NDArray(NDArray&& o) noexcept { *this = std::move(o); }
NDArray& operator=(const NDArray& o) {
    if (this == &o) return *this;
    buffer = o.buffer;            // shared_ptr: 참조 카운트 +1 (atomic)
    base = o.base;                // Python 참조 +1 (base가 있을 때)
    copy_meta(o);
    return *this;
}
void copy_meta(const NDArray& o) {
    data = o.data;  dtype = o.dtype;  ndim = o.ndim;
    std::copy(o.shape.begin(),   o.shape.begin()   + o.ndim, shape.begin());
    std::copy(o.strides.begin(), o.strides.begin() + o.ndim, strides.begin());
    c_contiguous = o.c_contiguous;  f_contiguous = o.f_contiguous;  writeable = o.writeable;
}
```

- 기본 생성자는 `Dims`를 0으로 채우지 않아요. `Dims shape;`처럼 초기값 없이 선언한 `std::array<int64_t, 32>`는 C++에서 기본 초기화(default-initialization)되어 값이 정해지지 않은 채로 남아요. 비용이 없어요. 그래서 `launch`의 `std::array<NDArray, 4> ins;`처럼 `NDArray`를 미리 여러 개 만들어 두어도 싸요. 대신 앞의 `ndim`칸만 쓰고 읽는다는 규칙을 코드 전체가 지켜야 해요.
- 이동 생성자에 `noexcept`를 붙여서 표준 컨테이너가 재배치할 때 복사 대신 이동을 써요.

### 이터레이터도 같은 규칙

`NdIter`는 shape 하나와 피연산자별 strides(최대 5개)를 고정 배열에 담아요. 피연산자 상한이 5라서(`sd.special`의 `hyp2f1`이 입력 4개 + 출력 1개) 객체가 1,600바이트예요. 만들 때마다 이 객체를 0으로 채우면 작은 배열에서는 눈에 띄는 비용이 돼요.

```cpp
class NdIter {
    ...
    // 초기화하지 않아요: 앞의 ndim_칸과 nop_개 피연산자만 쓰고 읽어요.
    Dims shape_;
    std::array<Dims, kMaxOperands> strides_;
    std::array<std::byte*, kMaxOperands> data_{};
};
```

축을 재배열할 때 쓰는 임시 복사본도 살아 있는 칸만 복사해요.

```cpp
Dims shape_p;                                // 초기화하지 않음
std::array<Dims, kMaxOperands> strides_p;
std::copy(shape_.begin(), shape_.begin() + ndim_, shape_p.begin());
for (int k = 0; k < nop_; ++k)
    std::copy(strides_[k].begin(), strides_[k].begin() + ndim_, strides_p[k].begin());
```

## 할당은 한 번: Buffer 안의 작은 데이터

`Buffer`는 배열 데이터가 사는 메모리 블록이고, 여러 배열(뷰)이 `shared_ptr<Buffer>`로 함께 가리켜요. 평범하게 만들면 작은 배열 하나에 할당이 셋이에요.

1. Buffer 객체: `new Buffer`
2. 데이터: `malloc(nbytes + 128)`(128바이트 정렬을 위해 조금 더 할당)
3. `shared_ptr` 제어 블록: `shared_ptr<Buffer>(new Buffer)`처럼 만들면 참조 카운트를 담을 블록을 따로 할당해요

두 가지 방법으로 셋을 하나로 줄이고, 남은 하나도 다시 써요(`base/buffer.hpp`, `buffer.cpp`).

- `std::allocate_shared`로 만들어요. 객체와 제어 블록을 한 번의 할당에 나란히 놓아요. 1과 3이 합쳐져요.
- 256바이트 이하의 데이터는 Buffer 객체 안에 둬요. Buffer에 내장 영역 `inline_`이 있고, 작은 배열은 데이터 포인터가 그 안의 첫 128바이트 경계를 가리켜요. 2가 없어져요.
- 합친 블록(크기가 하나뿐이에요)은 해제할 때 스레드마다 64개까지 목록에 남겨, 다음 할당이 꺼내 써요.

```cpp
// csrc/base/buffer.hpp (발췌)
class Buffer {
    static constexpr std::size_t kAlignment = 128;   // M4의 캐시 라인
    static constexpr std::size_t kInline = 256;
    ...
    void* raw_ = nullptr;          // malloc한 포인터 (내장 데이터면 null)
    std::byte* data_ = nullptr;    // 실제 데이터 시작 (내장 영역 또는 정렬한 malloc 영역)
    std::int64_t size_ = 0;
    bool external_ = false;        // 버퍼 프로토콜로 빌려 온 메모리인가
    Py_buffer view_{};
    alignas(16) std::byte inline_[kInline + kAlignment - 16];
};
```

```cpp
// csrc/base/buffer.cpp (발췌)
std::shared_ptr<Buffer> make_buffer() { return std::allocate_shared<Buffer>(CachedAlloc<Buffer>{}, Buffer::Key{}); }

std::shared_ptr<Buffer> Buffer::allocate(std::int64_t nbytes, bool zeroed) {
    auto buf = make_buffer();  // the Buffer and its reference count, together
    buf->size_ = nbytes;
    if (static_cast<std::size_t>(nbytes) <= kInline) {
        const auto addr = reinterpret_cast<std::uintptr_t>(buf->inline_);
        buf->data_ = buf->inline_ + (((addr + kAlignment - 1) & ~(std::uintptr_t{kAlignment} - 1)) - addr);
        if (zeroed) std::memset(buf->data_, 0, static_cast<std::size_t>(nbytes));
        return buf;
    }
    ...  // 큰 배열: malloc/calloc + 128B 정렬
}
```

`Key`는 `allocate_shared`가 생성자를 부를 수 있게 공개된 표시 타입이에요. Buffer는 메모리를 준비하는 팩토리 함수(`allocate`, `adopt`)로만 만들고, `Buffer(Key{})`만으로는 빈 버퍼예요.

- 256바이트인 이유: float64 원소 32개, complex128 16개까지예요. 좌표, 작은 행렬(4×4 = 16개), 짧은 벡터가 모두 들어가요.
- 정렬: 내장 데이터도 128바이트(캐시 라인)에 맞춰서, 큰 배열과 마찬가지로 SIMD 루프의 첫 load가 캐시 라인 두 개에 걸치지 않아요. 그런데 타입 자체를 `alignas(128)`로 정렬하면 `allocate_shared`가 정렬 할당(`malloc_type_aligned_alloc`)으로 가서 작은 `x + y`에서 그 할당이 눈에 띄었어요. 그래서 타입은 16바이트 정렬(`malloc`이 보장하는 것)로 두고, 내장 영역을 `kInline + 112`바이트로 잡아 그 안의 첫 128바이트 경계부터 써요.
- 대가: 모든 Buffer 객체가 수백 바이트 커져요. 큰 배열은 데이터를 따로 할당하므로 내장 영역이 그냥 남는데, 수 MB짜리 데이터 옆에서는 무시할 만해요.
- 데이터프레임(`sd.frame`)의 컬럼도 같은 `Buffer`를 써서, 256바이트 이하의 컬럼 버퍼도 Buffer 안에 놓여요.

### 제어 블록의 스레드별 목록: `CachedAlloc`

할당을 한 번으로 줄여도 그 블록의 `malloc`과 `free`가 작은 연산에서 눈에 띄는 몫이에요. 그래서 `allocate_shared`에 넘기는 할당자가 블록을 다시 써요.

```cpp
// csrc/base/buffer.cpp (CachedAlloc의 할당과 해제)
T* allocate(std::size_t n) {
    static_assert(alignof(T) <= 16);  // what malloc guarantees on macOS
    if (n == 1 && t_cache.count > 0) return static_cast<T*>(t_cache.blocks[--t_cache.count]);
    if (n == 1 && t_cache.count == 0) (void)&t_flusher;  // registers the flusher on first use
    void* p = std::malloc(n * sizeof(T));
    if (p == nullptr) throw std::bad_alloc();
    return static_cast<T*>(p);
}
void deallocate(T* p, std::size_t n) {
    if (n == 1 && t_cache.count >= 0 && t_cache.count < BlockCache::kCached) {
        if (t_cache.count == 0) (void)&t_flusher;
        t_cache.blocks[t_cache.count++] = p;
        return;
    }
    std::free(p);
}
```

- 목록(`t_cache`)은 `thread_local`이라 잠금이 없어요. 다른 스레드에서 해제된 블록은 그 스레드의 목록에 들어가요. 메모리는 어느 쪽이든 `malloc`의 것이라 섞여도 괜찮아요.
- 스레드마다 64개(`kCached`)까지만 쥐고, 차면 `free`로 돌려줘요.
- 스레드가 끝나면 `t_flusher`의 소멸자가 남은 블록을 비우고 `count`를 −1로 둬요. 그 뒤의 해제는 `free`로 가요. 목록 자체는 소멸자가 없는 타입이라 스레드의 마지막 순간까지 쓸 수 있어요.
- 큰 데이터 블록은 모아 두지 않아요. 128KB 이상의 블록을 해제 뒤 전역으로 모아 두는 캐시도 시험했지만, Python 프로세스에서는 macOS `malloc`이 큰 블록을 이미 다시 써서 첫 쓰기 페이지 폴트가 없었어요.

<Callout title="할당 캐시는 둘뿐이에요">
해제한 메모리를 모아 두었다가 다시 쓰는 캐시는 둘만 둬요. Buffer 제어 블록의 스레드별 목록과, 아래의 ndarray 인스턴스 풀이에요. 둘 다 크기가 하나뿐인 블록이고 상한이 있어요. numpy 소스에도 작은 데이터 할당 캐시가 있지만(`numpy/_core/src/multiarray/alloc.c`의 `npy_alloc_cache` 계열)[4], 크기가 여러 가지인 데이터 블록의 캐시는 여러 스레드에서의 해제와 메모리를 OS에 돌려주는 시점까지 다뤄야 해서 두지 않아요.
</Callout>

## 할당하는 표준 알고리즘 피하기

작은 호출에는 표준 라이브러리가 몰래 하는 할당도 무시할 수 없어요.

새 결과 배열은 입력의 메모리 축 순서를 따라야 해요(numpy의 `order='K'`). 그래서 strides의 절댓값이 큰 축부터 정렬하는데, 같은 값이면 원래 순서를 지켜야 하므로 안정 정렬이어야 해요. `std::stable_sort`는 안정성을 위해 호출마다 임시 버퍼를 할당해요. 축은 많아야 32개이므로 할당이 없는 insertion sort를 써요. 시간 복잡도는 $O(d^2)$($d$는 차원 수)이지만 $d \le 32$이고 보통 1~3이라 할당 하나보다 훨씬 싸요(`array/ndarray.cpp`의 `new_array_like`).

```cpp
// array/ndarray.cpp의 new_array_like (발췌)
std::array<int, kMaxNdim> order;
std::iota(order.begin(), order.begin() + proto.ndim, 0);
std::array<int, kMaxNdim> slots;  // the places of the axes with a stride
int live = 0;
for (int d = 0; d < proto.ndim; ++d)
    if (proto.strides[d] != 0) slots[live++] = d;
std::array<int, kMaxNdim> axes = slots;
// Insertion sort (stable): at most 32 axes, and std::stable_sort would
// allocate a scratch buffer on every call (docs/design/array.md §11).
for (int i = 1; i < live; ++i)
    for (int j = i; j > 0 && std::llabs(proto.strides[axes[j]]) > std::llabs(proto.strides[axes[j - 1]]); --j)
        std::swap(axes[j], axes[j - 1]);
for (int i = 0; i < live; ++i) order[slots[i]] = axes[i];
```

stride가 0인 축(브로드캐스트)은 정렬에서 빼고 C 자리에 그대로 둬요. 자세한 것은 [데이터 모델](/internals/array/data-model/)에 있어요.

여러 shape의 브로드캐스트 결과도 `std::vector`가 아니라 고정 배열 `Dims`에 쓰고 차원 수를 돌려줘요(`broadcast_into`). ufunc의 피연산자 목록과 shape 목록도 `std::array<…, kMaxInputs>`예요.

`x[1, ::2, None]` 같은 인덱스 키를 해석할 때도 항목을 `std::vector`에 차례로 넣지 않고, 객체 안의 고정 용량 저장소(`Items`: 축을 쓰는 항목 32 + `newaxis` 32 + `...` 1)에 넣어요. vector가 커지면서 다시 할당하는 비용은 `x[1, 2]` 같은 호출에서 시간의 대부분이 될 만큼 커요.

생성 함수의 shape도 스택에 담아요. `zeros`, `ones`, `empty`, `full`은 `shape` 인자를 `parse_shape_arg`로 읽어요. int 하나나 32개 이하의 int tuple이면 객체 안의 `std::array`에 담고, 그 밖의 입력(에러 포함)만 일반 해석기 `parse_shape`로 넘겨 `std::vector`를 만들어요. 그래서 에러 메시지는 한 곳에서만 만들어지고, 흔한 호출에는 vector 할당이 없어요.

```cpp
// csrc/bind/pyutil.hpp (발췌)
struct ShapeArg {
    std::array<std::int64_t, kMaxNdim> small;   // 흔한 경우: 힙 할당 없음
    std::vector<std::int64_t> big;              // 드문 경우: 일반 해석기의 결과
    std::size_t n = 0;
    std::span<const std::int64_t> span() const;
};
```

공통 부분만 다뤘는데 모든 작은 연산이 함께 싸져요. `a + 1.0`, `a += b`, `sum(a)`가 모두 같은 `NDArray` 복사, 같은 Buffer, 같은 이터레이터를 쓰기 때문이에요. 특수 경로 대신 일반 경로를 다듬는 이유가 이것이에요.

## int와 slice만인 인덱스

일반 키 해석은 slice, `...`, `newaxis`, 정수 배열, bool 마스크를 모두 다룰 수 있는 계획(`Items`, `Plan`)을 만들고 걸어요. `x[1, 2]`, `x[::2]`, `x[:, 5]`에는 그 기능 대부분이 필요 없는데, 계획을 거치면 그것이 시간의 대부분이에요. slice 키도 계획을 거쳐 뷰를 만들면 numpy보다 느려요.

그래서 모든 항목이 정확히 Python `int`(하위 클래스 제외)이거나 경계가 `None`·정확한 int인 slice인 키는 계획 없이 오프셋, shape, strides를 바로 계산해요(`array/ops/indexing.cpp`의 `basic_fast`).

```cpp
// array/ops/indexing.cpp (basic_fast)
nb::object basic_fast(nb::handle x, PyObject* key) {
    const NDArray& a = as_ndarray(x);
    PyObject* const* items = &key;
    Py_ssize_t n = 1;
    if (PyTuple_Check(key)) {
        items = &PyTuple_GET_ITEM(key, 0);
        n = PyTuple_GET_SIZE(key);
    }
    if (n == 0 || n > a.ndim) return {};
    std::byte* p = a.data;
    std::int64_t shape[kMaxNdim], strides[kMaxNdim];
    int nd = 0;
    for (Py_ssize_t d = 0; d < n; ++d) {
        PyObject* it = items[d];
        if (PyLong_CheckExact(it)) {
            int overflow = 0;
            long long i = PyLong_AsLongLongAndOverflow(it, &overflow);
            if (overflow) return {};
            if (i < 0) i += a.shape[d];
            if (i < 0 || i >= a.shape[d]) return {};
            p += i * a.strides[d];
        } else if (PySlice_Check(it)) {
            // Plain-int bounds only: an object with __index__ could run code, and
            // a bad bound must raise the general path's error.
            auto* sl = reinterpret_cast<PySliceObject*>(it);
            for (PyObject* b : {sl->start, sl->stop, sl->step})
                if (b != Py_None && !PyLong_CheckExact(b)) return {};
            Py_ssize_t start, stop, step;
            if (PySlice_Unpack(it, &start, &stop, &step) < 0) {
                PyErr_Clear();  // step 0: the general path raises it
                return {};
            }
            const Py_ssize_t len = PySlice_AdjustIndices(a.shape[d], &start, &stop, step);
            if (len > 0) p += start * a.strides[d];  // an empty slice leaves the pointer alone
            shape[nd] = len;
            strides[nd] = a.strides[d] * step;
            ++nd;
        } else {
            return {};
        }
    }
    if (nd == 0 && n == a.ndim) return load_python(a.dtype, p);
    NDArray v = view_of(x);
    v.data = p;
    std::copy(shape, shape + nd, v.shape.begin());
    std::copy(strides, strides + nd, v.strides.begin());
    std::copy(a.shape.begin() + n, a.shape.begin() + a.ndim, v.shape.begin() + nd);
    std::copy(a.strides.begin() + n, a.strides.begin() + a.ndim, v.strides.begin() + nd);
    v.ndim = nd + a.ndim - static_cast<int>(n);
    v.update_flags();
    return wrap(std::move(v));
}
```

빈 객체를 돌려주면 "일반 경로로 가라"는 뜻이에요. 원소 `(i, j)`의 주소는 $\text{data} + i \cdot \text{strides}[0] + j \cdot \text{strides}[1]$이므로, 정수만 있으면 곱셈과 덧셈 몇 번으로 끝나요. slice는 `PySlice_AdjustIndices`가 길이와 시작을 정하고, 그 축의 stride에 step을 곱해요. 3×4 float64 배열이면 strides가 `(32, 8)`이라 `x[1, 2]`는 시작에서 $1 \cdot 32 + 2 \cdot 8 = 48$바이트 떨어진 원소예요.

</Fig>

이 경로가 지키는 점은 이래요.

- 조금이라도 특이하면 일반 경로로 넘겨요. `PyLong_CheckExact`는 int의 하위 클래스를 받지 않으므로 `True`(bool은 int의 하위 클래스)는 일반 경로로 가서 평소대로 IndexError가 나요(stardust는 Python bool을 인덱스로 받지 않아요). `numpy.int64(1)` 같은 정수형 객체와 경계에 `__index__`를 가진 객체가 있는 slice도 일반 경로예요. `__index__`는 사용자 코드를 실행할 수 있기 때문이에요. 범위 밖 인덱스와 step 0은 빠른 경로가 에러를 내지 않고 일반 경로로 넘겨서, 에러 메시지가 한 곳에서만 만들어져요.
- 결과는 일반 경로와 같아요. 모든 축이 정수면 Python 스칼라(`float`, `int`, `bool`, `complex`), 아니면 뷰예요. `view_of`는 뷰의 `.base`를 메모리의 최종 소유자로 접는 일반 경로의 규칙을 그대로 써요.
- 반복(`for row in x`)은 키를 만들지 않고 `item_along_axis0`으로 축 0을 직접 걸어요.

### `x[key]`는 타입 슬롯이 받아요

키 해석을 건너뛰어도, `x[5]`가 바인딩한 `__getitem__`까지 가는 길(메서드 찾기와 nanobind의 디스패치)이 그 호출에서 눈에 띄는 몫이었어요. 그래서 바인딩이 끝난 뒤 타입의 `mp_subscript` 슬롯을 `array_subscript`로 바꿔요. `__getitem__`을 대입하면 Python이 일반 슬롯을 다시 달아 버리므로 바인딩의 맨 마지막에 해요.

```cpp
// bind/array_bind.cpp (array_subscript)
PyObject* array_subscript(PyObject* self, PyObject* key) {
    try {
        nb::object r = getitem_fast(nb::handle(self), key);
        if (r.is_valid()) return r.release().ptr();
    } catch (...) {
        PyErr_Clear();  // the general path below raises it properly
    }
    PyObject* args[] = {self, key};
    return PyObject_Vectorcall(g_getitem, args, 2, nullptr);
}
```

흔한 키(int와 slice만인 키)는 슬롯 안에서 끝나요. 그 밖의 키와 모든 에러는 바인딩한 `__getitem__`을 vectorcall로 불러, nanobind가 해 주는 C++ 예외 → Python 예외 변환과 공개 이름이 붙은 에러 메시지를 그대로 써요. 그래서 슬롯을 거쳐도 에러 메시지가 같아요.

같은 이유로 반복자(`_ArrayIterator`)도 `tp_iter`/`tp_iternext` 슬롯이에요. 끝에서 `StopIteration` 객체를 만들지 않고 NULL을 돌려줘요. `list(x)`가 원소마다 메서드를 디스패치하던 비용이 없어서 numpy보다 빨라요. `tolist`는 리스트를 `PyList_New(n)`으로 최종 크기에 만들고 `PyList_SET_ITEM`으로 채워요. `append`로 키우는 것보다 빨라요.

## 피연산자가 모두 Python 스칼라일 때

`sd.sin(0.5)`, `sd.add(1, 2)`, `sd.special.expit(0.5)`처럼 배열이 하나도 없는 원소별 호출은 결과도 Python 스칼라예요(stardust에는 0차원 배열이 없어요). 그런데 일반 경로로 가면 스칼라마다 원소 1개짜리 배열을 만들고, 결과 배열을 만들고, 이터레이터를 돌린 뒤 결과 배열에서 값을 꺼내요. 할당이 여러 번이에요.

`launch_scalars`는 이런 호출에서(`out=`이 없을 때) 같은 루프 함수를 스택 버퍼 위에서 n = 1로 한 번 불러요(발췌).

```cpp
nb::object launch_scalars(std::span<const nb::handle> objs, std::span<const DType> in_types,
                          DType result, Loop loop, int nout) {
    alignas(16) std::byte buf[kMaxOperands][16];         // 스칼라 하나에 16바이트 (complex128)
    std::array<std::byte*, kMaxOperands> args;
    std::array<int64_t, kMaxOperands> strides;
    for (size_t k = 0; k < objs.size(); ++k) {
        // 일반 경로가 1원소 배열에 넣을 때와 같은 변환
        visit_dtype(in_types[k], [&]<typename T>(std::type_identity<T>) {
            *reinterpret_cast<T*>(buf[k]) = scalar_from_python<T>(objs[k], *scalar_dtype(objs[k]));
        });
        args[k] = buf[k];
        strides[k] = itemsize(in_types[k]);
    }
    ...                                                   // 출력 자리도 스택 버퍼
    loop(args.data(), 1, strides.data(), nullptr);        // 배열 경로와 같은 루프
    return load_python(result, buf[objs.size()]);
}
```

- 결과가 비트까지 같아요. 같은 변환으로 만든 같은 값에 같은 루프를 부르기 때문이에요. 원소별 연산은 원소마다 따로 계산하므로 "배열의 i번째 원소에 대한 결과"와 "그 원소 하나에 대한 결과"가 같아요.
- 배열 경로를 거치는 것보다 짧아요. 같은 ufunc 디스패치를 쓰는 모든 영역(`sd.special.expit(0.5)` 등)이 함께 덕을 봐요.

## 속성과 `len()`은 타입 슬롯으로

`x.shape`, `x.ndim`, `len(x)`는 일이 거의 없는 호출이라 경로의 고정 비용이 전부예요. nanobind의 `def_prop_ro`로 등록하면 속성을 읽을 때마다 nanobind의 함수 호출 처리(인자 변환, 오버로드 확인, 결과 변환)를 지나서 `x.shape`가 34ns, `len(x)`가 17ns예요(numpy 18ns, 7ns).

그래서 `shape`, `strides`, `ndim`, `size`, `dtype`, `itemsize`, `nbytes`, `base`는 CPython의 `tp_getset` 슬롯에, `len()`은 `sq_length`/`mp_length` 슬롯에 C 함수로 직접 등록해요(`bind/array_bind.cpp`). 인터프리터가 이 함수를 바로 불러서 `x.shape` 19ns, `len(x)` 7ns로 numpy와 같아져요. 이 함수들은 메모리 부족 말고는 실패하지 않아서 nanobind의 예외 변환이 필요 없어요. 등록 방법은 [Python과 C++의 경계](/internals/core/python-boundary/)의 "속성"에 있어요.

`finfo`, `iinfo`는 결과를 한 번만 만들어요. 결과는 바뀌지 않는 namedtuple이라, 처음 부를 때 만들어 정적 변수에 두고 같은 객체를 돌려줘요. 부를 때마다 결과 모듈에서 클래스를 찾아 만들면 377ns가 드는데, 한 번만 만들면 20ns예요. numpy(111ns, numpy도 객체를 캐시해요)보다 빨라요.

## 배열 객체의 할당: 인스턴스 풀

새 배열 객체를 돌려주는 모든 호출에는 결과를 담는 Python 객체의 할당과 해제가 붙어요.

- pymalloc을 쓰지 못해요. CPython은 512바이트 이하의 작은 요청을 전용 할당기(pymalloc)로 처리해요 [5]. 크기별로 나뉜 풀에서 블록을 꺼내는 일이라 싸요. `NDArray`가 560바이트이고 nanobind 인스턴스가 객체 머리를 더하므로, 배열 객체 하나는 이 경계를 넘어 시스템 `malloc`으로 가요. macOS의 `free`는 메모리를 0으로 채워요(`sample`로 보면 `_xzm_free`와 `__bzero`).
- nanobind는 인스턴스마다 C++ 포인터 → Python 객체 해시표에 넣고 빼요.

그래서 ndarray 클래스를 nanobind의 인스턴스 풀과 함께 만들어요(`nb::class_<NDArray>(m, "ndarray", nb::type_slots(ndarray_slots), nb::pooled(256))`). 해제된 ndarray 객체 256개까지를 해시표에 등록된 채로 모아 두었다가 다음 결과가 다시 써요. `malloc`·`free`와 해시표 넣고 빼기가 둘 다 사라지고, 풀이 비었을 때만 시스템 `malloc`으로 가요.

결과 객체를 만드는 `wrap`과 타입 검사 `is_ndarray`도 nanobind의 해시표를 찾지 않아요. `bind_ndarray`가 클래스를 만든 직후 그 타입 포인터를 `g_ndarray_type`에 저장하고, 두 함수가 그것을 바로 써요.

```cpp
// bind/pyutil.hpp (wrap)
inline nb::object wrap(NDArray&& a) {
    nb::object o = nb::inst_alloc(nb::handle(reinterpret_cast<PyObject*>(g_ndarray_type)));
    new (nb::inst_ptr<NDArray>(o)) NDArray(std::move(a));
    nb::inst_mark_ready(o);
    return o;
}
```

`nb::inst_alloc`이 풀에서 인스턴스를 받고, 그 자리에 `NDArray`를 옮겨 만든 뒤 `inst_mark_ready`로 마쳐요. `nb::cast(std::move(a))`는 같은 일을 하면서 타입 정보를 해시표에서 찾아요.

<Callout title="최대 차원을 32로 두는 이유">
객체 할당 비용은 최대 차원을 24로 낮춰 `NDArray`를 512바이트 밑으로 줄여도 사라져요. 그러면 32차원까지 받는 numpy 1.x보다도 상한이 낮아져요(numpy 2.x는 64). 길이 1인 축을 많이 끼워 브로드캐스팅하는 코드처럼 차원이 많은 배열을 쓰는 코드가 stardust에서만 실패하게 돼요. 작은 차원만 객체 안에 두고 넘치면 힙에 두는 구조도 맞지 않아요. shape와 strides를 읽는 모든 곳이 두 저장소를 구별해야 하고, 복사와 이동이 힙 소유권까지 다뤄야 해요. 그래서 32차원을 지키고, 객체를 다시 쓰는 인스턴스 풀로 그 비용을 없애요.
</Callout>

### 소유한 배열의 뷰는 Buffer를 갖지 않아요

뷰를 만들고 버릴 때마다 `shared_ptr<Buffer>`를 복사하면 원자적 증감이 두 번 들어요. 그런데 메모리를 직접 소유한 배열 `x`의 뷰는 `base = x`로 `x`를 붙잡고, `x`가 자기 Buffer를 살려 둬요. 그래서 이런 뷰에는 Buffer를 주지 않아요(`view_of`, [데이터 모델](/internals/array/data-model/)). `x`가 이미 뷰이거나 외부 메모리이면 그 `base`와 Buffer를 그대로 물려받아요.

## 넣지 않은 것

호출 비용을 더 줄일 방법이 남아 있지만, 아래 넷은 얻는 것보다 잃는 것이 커서 넣지 않아요.

| 방법 | 넣지 않는 이유 |
|---|---|
| 최대 차원을 24로 줄여 배열 객체를 512바이트 밑으로 | 32차원 상한을 지켜요(위 Callout). 인스턴스 풀이 같은 비용을 없애요 |
| 큰 데이터 블록의 캐시 | macOS `malloc`이 큰 블록을 이미 다시 써요(위 "할당은 한 번") |
| Buffer 타입을 16바이트 정렬로만 두기 | 작은 배열 데이터의 128바이트 정렬이 깨져요. 그래서 내장 영역 안의 오프셋으로 맞춰요 |
| 임시 배열 재사용(temporary elision) | 안전하게 판정할 수 없어요(아래) |

`a + b + c`에서 `a + b`의 결과는 다음 덧셈 뒤 바로 버려지는 임시 배열이에요. numpy는 이런 임시 배열을 알아보고 그 버퍼에 다음 결과를 써서 할당을 아껴요. stardust는 이것을 넣지 않아요. 임시 객체인지를 안전하게 판정할 수 없기 때문이에요.

- CPython의 `PyUnstable_Object_IsUniqueReferencedTemporary`[1]는 Python 코드 안의 임시 객체는 정확히 판정해요.
- 그런데 다른 C 확장(예: Cython 코드)이 빌린 참조로 들고 있는 `x`로 `x + y`를 계산한 뒤 `x`를 다시 읽으면, 이 API는 `x`도 임시 객체로 판정해요. 버퍼를 재사용하면 다시 읽은 `x`는 이미 덮어써져 있어요.
- 이것을 막으려면 numpy처럼 실행 중인 C 콜스택을 들여다보거나 현재 프레임의 바이트코드를 봐야 하는데, 둘 다 인터프리터의 내부 구현에 기대는 방법이에요.

그래서 연산자는 항상 새 출력 배열을 할당해요. 작은 배열에서는 그 할당이 위의 5단계 한 번이고, 그것도 스레드별 목록에서 다시 써요. 판정 방법별로 무엇이 어긋나는지는 [전체 구조](/internals/core/overview/)의 "임시 배열 재사용"에 있어요.

## numpy와의 차이, 호출별로

### `a + b`: 이터레이터 없이 커널 한 번

원소 3개짜리 `a + b`는 numpy보다 빨라요. 경로에 남은 고정 작업은 이래요.

- 피연산자 확인과 루프 고르기(타입 포인터 비교, dtype 승격)
- `launch_contiguous`의 조건 확인: dtype, shape, 연속성, 일의 양
- 결과 배열: 스레드별 목록의 Buffer 블록, 인스턴스 풀의 Python 객체
- 커널 한 번(n = 3)
- `named()`처럼 에러 메시지에 함수 이름을 붙이는 래퍼는 연산자에는 쓰지 않고, 공개 함수에 쓰더라도 C++ 예외가 나지 않으면 비용이 없어요(`try`/`catch`는 예외가 날 때만 실행되는 표 기반 방식이에요).

`exp(a)`, `sqrt(a)`, `a < b`도 같은 구성이에요. 브로드캐스트가 있는 `m + v`나 dtype을 바꿔야 하는 `a + i`는 일반 경로(입력 `NDArray` 복사, `NdIter`)를 지나요.

### 뷰를 돌려주는 인덱싱: `x[5]`, `x[::2]`, `x[:, 5]`

1차원 배열의 `a[1]`은 원소 하나라서 Python `float`을 돌려줘요. 2차원 배열의 `x[5]`나 slice가 있는 키는 뷰(새 배열 객체)를 돌려줘요. 타입 슬롯이 키를 받고, `basic_fast`가 계획 없이 shape와 strides를 계산하고, 뷰는 Buffer를 갖지 않고, 객체는 인스턴스 풀에서 와요. 그래서 numpy보다 빠르거나 같아요. `m.T`도 같은 구성이에요.

### `zeros(3)`

shape는 `parse_shape_arg`로 할당 없이 읽어요. 남는 것은 `dtype=` 키워드 인자를 받는 nanobind의 인자 처리, 스레드별 목록의 결과 Buffer(데이터는 Buffer 안에 있어요)와 그 0 채우기, 인스턴스 풀의 객체예요. numpy보다 빠르거나 같아요.

### `x[1, 2]`가 빠른 이유

- stardust는 슬롯 안의 빠른 경로에서 tuple 확인, 정수 두 개 읽기, 곱셈·덧셈 두 번, `float` 객체 하나 만들기로 끝나요.
- 돌려주는 객체가 달라요. stardust는 Python 내장 `float`을 돌려주고(`PyFloat_FromDouble`), numpy는 `numpy.float64` 스칼라 객체를 돌려줘요(`type(x[1, 2])`로 볼 수 있어요). stardust에는 0차원 배열도 자체 스칼라 타입도 없어서, 원소 하나는 언제나 Python 스칼라예요. Python `float`은 pymalloc의 자유 목록에서 바로 나와요.

### `sd.asarray(numpy 배열)`

numpy의 `np.asarray(numpy 배열)`은 입력을 그대로 돌려줘요. stardust는 numpy의 공개 C 구조체에서 data, shape, strides를 바로 읽어 공유하지만, 결과 객체를 하나 만들어야 해요. 그 객체 하나만큼의 시간이 남아서 `np.asarray`보다 느려요([변환과 승격](/internals/array/conversion/)).

### `sum(a)`: 호출 경로의 Python 코드

작은 배열의 `sum`에서 두 라이브러리는 호출 경로에 Python 코드가 있느냐로 갈려요. numpy 2.5.4의 `np.sum`을 따라가 보면(`numpy/_core/fromnumeric.py`) 이래요[2].

1. `np.sum`은 `numpy._ArrayFunctionDispatcher` 객체예요. `__array_function__` 프로토콜(다른 배열 라이브러리가 numpy 함수를 가로챌 수 있게 하는 장치)을 위해 인자를 먼저 살펴요.
2. 그다음 Python으로 짠 함수 `sum`이 돌아요. 제너레이터 검사 뒤 `_wrapreduction(a, np.add, 'sum', axis, dtype, out, keepdims=…, initial=…, where=…)`을 불러요.
3. `_wrapreduction`은 Python 코드예요. 키워드 인자를 dict comprehension으로 걸러 새 dict를 만들고, `type(obj) is not mu.ndarray`를 확인한 뒤 `ufunc.reduce(obj, axis, dtype, out, **passkwargs)`를 불러요.
4. `np.add.reduce`가 C에서 리덕션을 하고 `numpy.float64` 스칼라를 돌려줘요.

stardust의 `sd.sum`은 nanobind 함수 객체 자체예요(`type(sd.sum)`은 `nanobind.nb_func`). Python 코드를 하나도 거치지 않고 C++의 `sum()`으로 바로 들어가서, 인자 확인 → 출력(원소 1개, Buffer 내장) 할당 → 이터레이터 → 리덕션 커널(원소 3개라 순서대로 덧셈) → Python `float`으로 끝나요. 결과가 Python 스칼라라서 배열 객체를 만들지 않아요. 작은 배열을 위한 특수 경로는 없어요. 일반 리덕션 경로 그대로예요.

### `a.sum()` 메서드

numpy의 `a.sum()`은 `np.sum`의 래퍼 층을 건너뛰지만, C로 바로 가지는 않아요.

- numpy의 `a.sum()`도 Python 함수 하나를 거쳐요. `sys.setprofile`로 보면 `a.sum()` 한 번에 `numpy/_core/_methods.py`의 `_sum`이 불려요. 이 함수는 `umr_sum(a, axis, dtype, out, keepdims, initial, where)`, 곧 `np.add.reduce`를 부르는 한 줄짜리예요. `np.sum(a)`가 거치는 `_sum_dispatcher`, `sum`, `_wrapreduction` 세 단계보다는 훨씬 얇아요.
- 그 뒤는 `np.add.reduce`의 ufunc 리덕션 준비와 `numpy.float64` 스칼라 만들기예요.
- stardust의 메서드 `A.sum()`은 모듈 함수 `sum`을 그대로 등록한 것이라(`.def("sum", named("sum", &sum), ...)`) `sd.sum(A)`와 같은 경로예요.

## 성능

### 복잡도

작은 배열 호출의 비용은 원소 수가 아니라 차원 수에 비례하는 부분과 상수 부분으로 이뤄져요.

- `NDArray` 복사, 브로드캐스트, 이터레이터 구성, 플래그 계산: $O(d)$ (축 재배열만 $O(d^2)$), $d \le 32$
- 할당: 결과 배열당 C++ 1번(256바이트 이하면 Buffer와 데이터가 한 덩어리, 스레드별 목록에서 재사용) + Python 객체 1번(인스턴스 풀에서 재사용)
- 계산: $O(n)$, 원소 3개면 몇 ns

원소가 많아지면 계산이 빠르게 고정 비용을 넘어서요. 원소 400만 개 `f + g`는 1스레드 0.72ms라서 호출의 고정 비용은 무시할 만해요. 일이 원소 2¹⁵개(256KB) 분량 이상이면 스레드풀이 끼어들어요([스레드풀과 결정성](/internals/core/threads/)).

### 정리

| 연산 | numpy와 견주면 | 무엇이 시간을 정하나 |
|---|---|---|
| `finfo(float64)` | 빨라요 | 결과 객체 공유 |
| `x[1, 2]` | 빨라요 | 슬롯과 int 키 빠른 경로, Python `float` |
| `x.shape`, `len(x)` | 같아요 | 타입 슬롯 |
| `a + b`, `exp(a)` (원소 3개) | 빨라요 | 커널 한 번, 인스턴스 풀, Buffer 블록 재사용 |
| `zeros(3)` | 빠르거나 같아요 | 키워드 인자 처리, Buffer와 0 채우기 |
| `x[5]`, `x[::2]` (뷰) | 빠르거나 같아요 | 슬롯, int·slice 키 빠른 경로, 인스턴스 풀 |
| 스칼라만의 원소별 호출 | 빨라요 | `launch_scalars` |
| `sd.asarray(numpy 배열)` | 느려요 | 결과 객체 하나 (`np.asarray`는 입력을 그대로 돌려줘요) |

잰 값은 `bench/array/speed.md`의 "작은 배열" 표에 들어가요. 작은 연산은 일이 기준값보다 작아 `parallel_for`를 부르지 않으므로, 스레드 수는 `available()` 확인 비용 말고는 이 비용에 영향을 주지 않아요.

정확도는 이 페이지의 어떤 기법에도 영향을 받지 않아요. 다룬 것은 모두 메모리 관리와 호출 경로이고, 계산하는 루프와 순서는 그대로예요. 빠른 경로도 모두 일반 경로와 결과가 비트까지 같아요.
