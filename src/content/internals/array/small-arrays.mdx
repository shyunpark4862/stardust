## 한눈에 보기

원소 3개짜리 float64 배열 두 개를 더하는 `a + b`에서 실제 덧셈은 1ns도 걸리지 않아요. 그런데 호출 하나는 약 180ns가 걸려요. 나머지는 모두 **호출 경로의 고정 비용**이에요. Python이 연산자를 C++ 함수로 넘기고, 인자를 검사하고, 결과 배열을 할당하고, 이터레이터를 준비하고, 결과를 Python 객체로 감싸는 비용이에요. 배열이 작을수록 이 비용이 전부가 돼요.

stardust는 이 비용을 줄이는 데 두 가지 원칙을 지켰어요.

1. **일반 경로를 싸게 만들어요.** 연산마다 "작은 배열 전용 경로"를 따로 두지 않아요. 대신 모든 호출이 지나는 공통 부분(배열 객체 복사, 할당, 이터레이터)이 **필요한 만큼만** 일하게 고쳤어요. 특수 경로를 남발하면 경로마다 의미가 미세하게 달라질 위험이 생기고, 테스트해야 할 조합이 늘어나요.
2. **원인은 프로파일러로 찾아요.** macOS의 `sample` 프로파일러로 작은 연산을 반복하는 루프를 보면, 시간은 nanobind의 호출 처리(약 10ns)나 계산이 아니라 **메모리 복사·0 채우기와 `malloc`**에 가 있었어요. 짐작했던 곳과 달랐어요.

특수 경로는 딱 두 개만 있어요. 가장 흔한 작은 호출인 `x[1, 2]` 같은 정수 인덱싱, 그리고 피연산자가 모두 Python 스칼라인 원소별 호출(`sd.sin(0.5)`)이에요. 둘 다 일반 경로와 결과가 비트까지 같고, 조금이라도 특이한 입력은 일반 경로로 넘겨요.

## 왜 작은 배열이 중요한가

과학 계산 코드에는 좌표 하나(원소 3개), 작은 행렬 하나(3×3)를 다루는 연산이 Python 루프 안에서 수없이 반복되는 경우가 많아요. 이런 코드에서는 큰 배열에서 아무리 빨라도 호출 한 번이 1µs라면 numpy보다 몇 배 느린 라이브러리가 돼요.

stardust가 Python 층을 얇게 두고 shape 계산, 브로드캐스팅, 인덱스 해석, dtype 결정을 모두 C++에서 하는 이유가 이것이에요([Python과 C++의 경계](/internals/core/python-boundary/)). 이런 로직을 Python으로 짜고 C++에는 커널만 맡기면 코드는 읽기 쉽지만, 작은 배열의 연산 한 번이 수 µs로 늘어나요. numpy는 약 1µs 이하예요. 이 페이지는 그렇게 C++로 내려온 경로 **안에서** 남은 비용을 다뤄요.

## `a + b` 한 번의 여정

원소 3개짜리 `a + b`가 지나는 길을 순서대로 보면 이래요.

| 단계 | 하는 일 | 할당 |
|---|---|:---:|
| 1. Python → C++ | 인터프리터가 `a`의 타입에서 `__add__`(nanobind 함수 객체)를 찾아 불러요. nanobind가 인자 두 개를 `nb::handle`(빌린 참조)로 넘겨요 | 없음 |
| 2. 피연산자 확인 | `is_operand(b)`: 배열이거나 Python bool/int/float/complex인지 봐요. 아니면 `NotImplemented` | 없음 |
| 3. 루프 고르기 | 두 dtype을 승격하고(`promote`), 루프 표에서 그 dtype 이상인 첫 루프를 골라요(`select`) | 없음 |
| 4. 입력 준비 | 배열 피연산자의 `NDArray`를 복사해 와요(`prepare`). shape를 고정 배열에 브로드캐스트해요(`broadcast_into`) | 없음 |
| 5. 결과 할당 | 첫 입력의 레이아웃을 따라 결과 배열을 만들어요(`new_result` → `new_array_like`) | **1번** |
| 6. 이터레이터 | `NdIter`를 만들고(브로드캐스트, 크기 1 축 제거, 축 재배열, 차원 합치기), 일이 작으니 나누지 않고 커널을 한 번 불러요(n = 3) | 없음 |
| 7. C++ → Python | 결과 `NDArray`를 nanobind 인스턴스로 감싸요(`nb::cast`): Python 객체 할당, 인스턴스 등록, `NDArray` 이동 | 1번 (Python 객체) |
| (나중에) 해제 | 결과 객체가 사라질 때 `NDArray` 소멸자가 `shared_ptr<Buffer>`를 놓고, 마지막 참조면 메모리를 돌려줘요 | 해제 1번 |

C++ 쪽에서 메모리를 할당하는 곳은 5단계 **한 곳, 한 번**뿐이에요. 처음부터 그랬던 것은 아니에요. 아래에서 보듯 고치기 전에는 작은 배열 하나에 `malloc`이 세 번, 그 밖에 `std::vector`와 `std::stable_sort`의 임시 할당이 더 있었어요.

4~6단계의 실제 코드를 줄인 발췌예요(`array/ops/ufunc.cpp`의 `launch`, `run_loop`).

```cpp
nb::object launch(std::span<const nb::handle> objs, std::span<const DType> in_types,
                  DType result, Loop loop, nb::handle out_obj) {
    if (out_obj.is_none() && std::ranges::none_of(objs, is_ndarray))
        return launch_scalars(objs, in_types, result, loop);      // 모두 스칼라 (아래)

    std::array<NDArray, kMaxInputs> ins;                          // 고정 배열: 할당 없음
    std::array<std::span<const int64_t>, kMaxInputs> shapes;
    size_t narrays = 0;
    for (size_t k = 0; k < objs.size(); ++k) {
        ins[k] = prepare(objs[k], in_types[k]);                   // 배열이면 NDArray 복사
        if (is_ndarray(objs[k])) shapes[narrays++] = as_ndarray(objs[k]).shape_span();
    }
    Dims dims;                                                    // 브로드캐스트 결과도 고정 배열
    const int ndim = broadcast_into(std::span(shapes.data(), narrays), dims);
    const std::span<const int64_t> shape(dims.data(), ndim);

    NDArray res = new_result(objs, shape, result);                // 유일한 C++ 할당
    run_loop(ins, in_types, std::span(&res, 1), shape, loop);     // NdIter를 만들고 실행
    return wrap(std::move(res));                                  // nanobind 인스턴스로
}
```

지금 `a + b` 하나는 C++ 할당 1번(결과 Buffer)과 Python 객체 할당 1번(nanobind 인스턴스)이에요. 결과는 새 객체여야 하므로, 이보다 줄이려면 해제한 메모리를 모아 두었다가 다시 쓰는 캐시가 필요해요. 그것은 넣지 않기로 한 최적화예요(아래 "고친 것 2"의 주의). 남은 차이는 아래 "남은 비용"에서 다뤄요.

## 프로파일러가 보여 준 것

고치기 전 측정은 `a + b`(원소 3개) 280ns, `x[1, 2]` 98ns였어요(같은 시점의 numpy는 146ns, 33ns). `a + b`를 반복하는 루프를 `sample`로 보니 시간이 이렇게 퍼져 있었어요.

- **고정 크기 배열을 통째로 복사하고 0으로 채우는 `memmove`, `memset`.** `NDArray` 하나가 약 560바이트, 이터레이터(`NdIter`)가 약 1.3KB였어요. 작은 연산 하나에도 이런 객체가 여러 번 만들어지고 복사됐어요.
- **작은 배열 하나에 `malloc` 세 번.** `Buffer` 객체, 데이터, 그리고 `shared_ptr`의 제어 블록(참조 카운트가 사는 곳)이에요.
- **표준 라이브러리의 숨은 할당.** `std::vector`(shape, 인덱스 키 항목)와, 축을 정렬하는 `std::stable_sort`가 호출마다 임시 버퍼를 할당했어요.
- nanobind의 함수 호출 경로 자체는 약 10ns로 작았어요(따로 잰 값).

numpy보다 느린 원인이 "C++과 Python 사이를 건너는 비용"일 것이라고 짐작하기 쉬운데, 실제로는 stardust 자신의 객체 크기와 할당이었어요. 그래서 바인딩 층을 바꾸는 대신 데이터 구조를 고쳤어요.

## 고친 것 1: 고정 배열은 두고, 필요한 칸만 만지기

### 왜 고정 배열인가

`NDArray`는 shape와 strides를 객체 안의 **고정 배열**로 가져요([데이터 모델](/internals/array/data-model/)).

```cpp
inline constexpr int kMaxNdim = 32;
using Dims = std::array<std::int64_t, kMaxNdim>;   // 객체 안에 박힌 256바이트

struct NDArray {
    std::shared_ptr<Buffer> buffer;
    std::byte* data = nullptr;
    DType dtype = DType::Float64;
    int ndim = 0;
    Dims shape;      // [0, ndim)만 의미가 있어요
    Dims strides;
    bool c_contiguous = true, f_contiguous = true, writeable = true;
    nb::object base;
};
```

shape를 `std::vector`로 두면 배열(뷰 포함)을 만들 때마다 힙 할당이 하나씩 붙어요. 고정 배열이면 배열을 만들어도 shape 때문에 할당하지 않아요. 대신 객체가 커요. shape와 strides가 각각 32 × 8 = 256바이트라서 `NDArray` 하나가 560바이트예요. 차원 수가 32를 넘으면 ValueError예요.

프로파일 결과를 보고 고정 배열을 없애는 대신 **고정 배열은 그대로 두고 "필요한 만큼만 만지기"**를 택했어요. 고정 배열의 장점(할당 없음)은 지키면서, 단점(큰 객체를 통째로 복사)만 없애는 방법이에요.

### 복사와 이동은 앞의 ndim칸만

컴파일러가 만들어 주는 복사 생성자는 `Dims` 두 개 512바이트를 모두 복사해요. 3원소 1차원 배열이면 그중 16바이트만 의미가 있어요. 그래서 복사와 이동을 직접 정의했어요(`array/ndarray.hpp`, 발췌).

```cpp
NDArray(const NDArray& o) { *this = o; }
NDArray(NDArray&& o) noexcept { *this = std::move(o); }
NDArray& operator=(const NDArray& o) {
    if (this == &o) return *this;
    buffer = o.buffer;            // shared_ptr: 참조 카운트 +1 (atomic)
    base = o.base;                // Python 참조 +1 (base가 있을 때)
    copy_meta(o);
    return *this;
}
void copy_meta(const NDArray& o) {
    data = o.data;  dtype = o.dtype;  ndim = o.ndim;
    std::copy(o.shape.begin(),   o.shape.begin()   + o.ndim, shape.begin());
    std::copy(o.strides.begin(), o.strides.begin() + o.ndim, strides.begin());
    c_contiguous = o.c_contiguous;  f_contiguous = o.f_contiguous;  writeable = o.writeable;
}
```

- **기본 생성자는 `Dims`를 0으로 채우지 않아요.** `Dims shape;`처럼 초기값 없이 선언한 `std::array<int64_t, 32>`는 C++에서 기본 초기화(default-initialization)되어 값이 정해지지 않은 채로 남아요. 비용이 없어요. 그래서 `launch`의 `std::array<NDArray, 4> ins;`처럼 `NDArray`를 미리 여러 개 만들어 두어도 싸요. 대신 앞의 `ndim`칸만 쓰고 읽는다는 규칙을 코드 전체가 지켜야 해요.
- 이동 생성자에 `noexcept`를 붙여서 표준 컨테이너가 재배치할 때 복사 대신 이동을 써요.

### 이터레이터도 같은 규칙

`NdIter`는 shape 하나와 피연산자별 strides(최대 5개)를 고정 배열로 가져요. 지금은 피연산자 상한이 5라서(`sd.special`의 `hyp2f1`이 입력 4개 + 출력 1개) 약 1.6KB예요. 처음에는 이것을 0으로 채웠는데, 작은 배열에서 눈에 띄는 비용이었어요.

```cpp
class NdIter {
    ...
    // 초기화하지 않아요: 앞의 ndim_칸과 nop_개 피연산자만 쓰고 읽어요.
    // 1.3KB를 매번 0으로 채우는 것이 작은 배열에서 보이는 비용이었어요.
    Dims shape_;
    std::array<Dims, kMaxOperands> strides_;
    std::array<std::byte*, kMaxOperands> data_{};
};
```

축을 재배열할 때 쓰는 임시 사본도 살아 있는 칸만 복사해요.

```cpp
Dims shape_p;                                // 초기화하지 않음
std::array<Dims, kMaxOperands> strides_p;
std::copy(shape_.begin(), shape_.begin() + ndim_, shape_p.begin());
for (int k = 0; k < nop_; ++k)
    std::copy(strides_[k].begin(), strides_[k].begin() + ndim_, strides_p[k].begin());
```

## 고친 것 2: 할당 세 번을 한 번으로

`Buffer`는 배열 데이터가 사는 메모리 블록이고, 여러 배열(뷰)이 `shared_ptr<Buffer>`로 함께 가리켜요. 고치기 전에는 작은 배열 하나를 만들 때 할당이 셋이었어요.

1. `new Buffer` — Buffer 객체
2. `malloc(nbytes + 128)` — 데이터(128바이트 정렬을 위해 조금 더 할당)
3. `shared_ptr` 제어 블록 — `shared_ptr<Buffer>(new Buffer)`처럼 만들면 참조 카운트를 담을 블록을 따로 할당해요

두 가지를 바꿔서 하나로 줄였어요(`base/buffer.hpp`, `buffer.cpp`).

- **`std::make_shared`로 만들어요.** `make_shared`는 객체와 제어 블록을 한 번의 할당에 나란히 놓아요. 1과 3이 합쳐져요.
- **256바이트 이하의 데이터는 Buffer 객체 안에 둬요.** Buffer에 `alignas(128) std::byte inline_[256]`이라는 내장 영역이 있고, 작은 배열은 데이터 포인터가 이곳을 가리켜요. 2가 없어져요.

```cpp
class Buffer {
    static constexpr std::size_t kAlignment = 128;   // M4의 캐시 줄
    static constexpr std::size_t kInline = 256;
    ...
    void* raw_ = nullptr;          // malloc한 포인터 (내장 데이터면 null)
    std::byte* data_ = nullptr;    // 실제 데이터 시작 (내장 영역 또는 정렬한 malloc 영역)
    std::int64_t size_ = 0;
    bool external_ = false;        // 버퍼 프로토콜로 빌려 온 메모리인가
    Py_buffer view_{};
    alignas(kAlignment) std::byte inline_[kInline];
};

std::shared_ptr<Buffer> Buffer::allocate(std::int64_t nbytes, bool zeroed) {
    auto buf = std::make_shared<Buffer>(Key{});      // Buffer와 참조 카운트를 한 번에
    buf->size_ = nbytes;
    if (static_cast<std::size_t>(nbytes) <= kInline) {
        buf->data_ = buf->inline_;                    // 작은 배열: 추가 할당 없음
        if (zeroed) std::memset(buf->inline_, 0, nbytes);

    }
```

- **256바이트인 이유:** float64 원소 32개, complex128 16개까지예요. 좌표, 작은 행렬(4×4 = 16개), 짧은 벡터가 모두 들어가요. 설계 문서에 256을 고른 측정 기록은 따로 없어요.
- **대가:** 모든 Buffer 객체가 256바이트 커져요. 128바이트 정렬 때문에 Buffer 객체 하나가 384바이트예요. 큰 배열은 데이터를 따로 할당하므로 내장 영역이 그냥 남는데, 수 MB짜리 데이터 옆에서 384바이트는 무시할 만해요.
- **정렬:** 내장 영역도 128바이트(캐시 줄)에 맞춰서, 큰 배열과 마찬가지로 SIMD 루프의 첫 load가 캐시 줄 두 개에 걸치지 않아요.
- 데이터프레임(`sd.frame`)의 컬럼도 같은 `Buffer`를 써서, 256바이트 이하의 컬럼 버퍼도 Buffer 안에 놓여요.

<Callout type="warn" title="작은 메모리 할당 캐시는 넣지 않았어요">
"작은 Buffer를 해제하지 말고 모아 두었다가 다시 쓰기" 같은 할당 캐시는 설계 문서의 "넣지 않은 최적화"에 "특수 케이스용 fast path 남발"과 함께 명시되어 있어요. numpy 소스에는 이런 캐시가 있어요(`numpy/_core/src/multiarray/alloc.c`의 `npy_alloc_cache` 계열). stardust는 할당 **횟수**를 줄이는 쪽을 택했고, 캐시가 가져오는 복잡도(여러 스레드에서의 해제, 메모리를 OS에 돌려주는 시점)는 들이지 않았어요.
</Callout>

## 고친 것 3: 할당하는 표준 알고리즘 피하기

작은 호출에는 표준 라이브러리가 몰래 하는 할당도 무시할 수 없어요.

**축 정렬은 insertion sort.** 새 결과 배열은 입력의 메모리 축 순서를 따라야 해요(numpy의 `order='K'`). 그래서 strides의 절댓값이 큰 축부터 정렬하는데, 같은 값이면 원래 순서를 지켜야 하므로 안정 정렬이어야 해요. `std::stable_sort`는 안정성을 위해 호출마다 임시 버퍼를 할당해요. 축은 많아야 32개이므로 insertion sort로 바꿨어요. 시간 복잡도는 $O(d^2)$($d$는 차원 수)이지만 $d \le 32$이고 보통 1~3이라 할당 하나보다 훨씬 싸요(`array/ndarray.cpp`의 `new_array_like`).

```cpp
std::array<int, kMaxNdim> order;
std::iota(order.begin(), order.begin() + proto.ndim, 0);
for (int i = 1; i < proto.ndim; ++i)              // 안정 insertion sort, 할당 없음
    for (int j = i; j > 0 && std::llabs(proto.strides[order[j]]) >
                             std::llabs(proto.strides[order[j - 1]]); --j)
        std::swap(order[j], order[j - 1]);
```

**브로드캐스트는 고정 배열에.** 여러 shape의 브로드캐스트 결과를 `std::vector`로 돌려주던 것을 `Dims`에 쓰고 차원 수를 돌려주게 바꿨어요(`broadcast_into`). ufunc의 피연산자 목록과 shape 목록도 `std::array<…, kMaxInputs>`예요.

**인덱스 키 항목은 고정 용량 저장소에.** `x[1, ::2, None]` 같은 키를 해석할 때 항목들을 `std::vector`에 차례로 넣던 것을, 객체 안의 고정 용량 저장소(`Items`: 축을 쓰는 항목 32 + `newaxis` 32 + `...` 1)로 바꿨어요. vector가 커지면서 다시 할당하는 비용이 `x[1, 2]` 비용의 대부분이었어요.

### 1~3의 효과

| 연산 | 고치기 전 | 고친 뒤 | 같은 시점의 numpy |
|---|---:|---:|---:|
| `a + b` (원소 3개) | 280ns | 174ns | 146ns |
| `x[1, 2]` | 98ns | 60ns | 33ns |

`a + 1.0`, `a += b`, `sum(a)`는 이때부터 numpy보다 빨라졌어요. 연산마다 따로 손대지 않고 공통 부분만 고쳤는데 모든 작은 연산이 함께 빨라진 것이, 특수 경로 대신 일반 경로를 고친 이유예요.

## 고친 것 4: 앞쪽 축이 정수인 인덱스

1~3 뒤에도 `x[1, 2]`는 60ns로 numpy(33ns)의 두 배 가까웠어요. 남은 시간은 거의 모두 **일반 인덱스 계획을 만들고 걷는 데** 들었어요. 키 해석은 slice, `...`, `newaxis`, 정수 배열, bool 마스크를 모두 다룰 수 있는 계획(`Plan`)을 만드는데, `x[1, 2]`에는 그 기능이 하나도 필요 없어요.

그래서 "**앞쪽 축들이 모두 정확한 Python int**"인 키만 계획 없이 바로 처리해요(`array/ops/indexing.cpp`의 `leading_ints_fast`, 발췌).

```cpp
nb::object leading_ints_fast(nb::handle x, PyObject* key) {
    const NDArray& a = as_ndarray(x);
    PyObject* const* items = &key;               // x[1]: 키가 int 하나
    Py_ssize_t n = 1;
    if (PyTuple_Check(key)) {                    // x[1, 2]: 키가 tuple
        items = &PyTuple_GET_ITEM(key, 0);
        n = PyTuple_GET_SIZE(key);
    }
    if (n == 0 || n > a.ndim) return {};         // 빈 객체 = "일반 경로로 가라"
    std::byte* p = a.data;
    for (Py_ssize_t d = 0; d < n; ++d) {
        if (!PyLong_CheckExact(items[d])) return {};          // bool, numpy 정수 등은 일반 경로
        int overflow = 0;
        long long i = PyLong_AsLongLongAndOverflow(items[d], &overflow);
        if (overflow) return {};                              // 너무 큰 int
        if (i < 0) i += a.shape[d];                           // 음수 인덱스
        if (i < 0 || i >= a.shape[d]) return {};              // 범위 밖: 일반 경로가 에러를 낸다
        p += i * a.strides[d];
    }
    if (n == a.ndim) return load_python(a.dtype, p);          // 원소 하나: Python 스칼라
    NDArray v = view_of(x);                                   // 남은 축의 뷰
    v.data = p;
    v.ndim = a.ndim - n;
    std::copy(a.shape.begin() + n, a.shape.begin() + a.ndim, v.shape.begin());
    std::copy(a.strides.begin() + n, a.strides.begin() + a.ndim, v.strides.begin());
    v.update_flags();
    return wrap(std::move(v));
}

nb::object getitem(nb::handle x, nb::handle key) {
    if (nb::object r = leading_ints_fast(x, key.ptr()); r.is_valid()) return r;
    Plan plan = make_plan(x, key);               // 그 밖의 모든 키
    ...
}
```

원소 `(i, j)`의 주소는 $\text{data} + i \cdot \text{strides}[0] + j \cdot \text{strides}[1]$이므로, 정수만 있으면 곱셈과 덧셈 몇 번으로 끝나요. 3×4 float64 배열이면 strides가 `(32, 8)`이라 `x[1, 2]`는 시작에서 $1 \cdot 32 + 2 \cdot 8 = 48$바이트 떨어진 원소예요.

여기서 주의한 점들이에요.

- **조금이라도 특이하면 일반 경로로 넘겨요.** `PyLong_CheckExact`는 int의 하위 클래스를 받지 않으므로 `True`(bool은 int의 하위 클래스)는 일반 경로로 가서 평소대로 IndexError가 나요(stardust는 Python bool을 인덱스로 받지 않아요). `numpy.int64(1)` 같은 정수형 객체도 일반 경로에서 `__index__`로 처리돼요. 범위 밖 인덱스는 빠른 경로가 에러를 내지 않고 일반 경로로 넘겨서, 에러 메시지가 한 곳에서만 만들어져요.
- **결과는 일반 경로와 같아요.** 모든 축이 정수면 Python 스칼라(`float`, `int`, `bool`, `complex`), 아니면 남은 축의 뷰예요. `view_of`는 뷰의 `.base`를 메모리의 최종 소유자로 접는 일반 경로의 규칙을 그대로 써요.
- 반복(`for row in x`)은 키를 만들지 않고 `item_along_axis0`으로 축 0을 직접 걸어요.

결과: `x[1, 2]` **58 → 22ns**(그때 numpy 31ns), `x[1]` 82 → 66ns(numpy 41ns). 이번 벤치마크에서는 `x[1, 2]`가 25ns, numpy 35ns예요.

## 고친 것 5: 피연산자가 모두 Python 스칼라일 때

`sd.sin(0.5)`, `sd.add(1, 2)`, `sd.special.expit(0.5)`처럼 배열이 하나도 없는 원소별 호출은 결과도 Python 스칼라예요(stardust에는 0차원 배열이 없어요). 그런데 일반 경로로 가면 스칼라마다 원소 1개짜리 배열을 만들고, 결과 배열을 만들고, 이터레이터를 돌린 뒤 결과 배열에서 값을 꺼내요. 할당이 여러 번이에요.

`launch_scalars`는 이런 호출(그리고 `out=`이 없을 때)에서 **같은 루프 함수**를 스택 버퍼 위에서 n = 1로 한 번 불러요(발췌).

```cpp
nb::object launch_scalars(std::span<const nb::handle> objs, std::span<const DType> in_types,
                          DType result, Loop loop, int nout) {
    alignas(16) std::byte buf[kMaxOperands][16];         // 스칼라 하나에 16바이트 (complex128)
    std::array<std::byte*, kMaxOperands> args;
    std::array<int64_t, kMaxOperands> strides;
    for (size_t k = 0; k < objs.size(); ++k) {
        // 일반 경로가 1원소 배열에 넣을 때와 같은 변환
        visit_dtype(in_types[k], [&]<typename T>(std::type_identity<T>) {
            *reinterpret_cast<T*>(buf[k]) = scalar_from_python<T>(objs[k], *scalar_dtype(objs[k]));
        });
        args[k] = buf[k];
        strides[k] = itemsize(in_types[k]);
    }
    ...                                                   // 출력 자리도 스택 버퍼
    loop(args.data(), 1, strides.data(), nullptr);        // 배열 경로와 같은 루프
    return load_python(result, buf[objs.size()]);
}
```

- **결과가 비트까지 같아요.** 같은 변환으로 만든 같은 값에 같은 루프를 부르기 때문이에요. 원소별 연산은 원소마다 따로 계산하므로 "배열의 i번째 원소에 대한 결과"와 "그 원소 하나에 대한 결과"가 같아요.
- 호출 하나에 약 90ns 줄었어요. 같은 ufunc 디스패치를 쓰는 모든 영역이 함께 덕을 봐요. `sd.special.expit(0.5)`는 140 → 48ns가 됐어요.

## 시도하고 넣지 않은 것

| 시도 | 결과 | 판단 |
|---|---|---|
| ndarray 타입을 캐시하고 nanobind의 저수준 API(`inst_alloc`, `inst_mark_ready`)로 인스턴스를 직접 만들기 | `x[1]` 83 → 80ns | 잡음 수준이라 넣지 않았어요 |
| `__getitem__`을 C 슬롯 `mp_subscript`로 직접 등록하기 | 예상 이득 약 7ns | 하지 않았어요. nanobind가 해 주는 C++ 예외 → Python 예외 변환을 직접 처리해야 해요 |
| 작은 메모리 할당 캐시 | — | 설계 원칙상 넣지 않아요(위 Callout) |
| 임시 배열 재사용(temporary elision) | — | 안전하게 만들 수 없어서 넣지 않았어요(아래) |

**임시 배열 재사용.** `a + b + c`에서 `a + b`의 결과는 다음 덧셈 뒤 바로 버려지는 임시 배열이에요. numpy는 이런 임시 배열을 알아보고 그 버퍼에 다음 결과를 써서 할당을 아껴요. stardust도 시도했어요.

- CPython의 `PyUnstable_Object_IsUniqueReferencedTemporary`는 Python 코드 안에서는 임시 객체를 정확히 판정해요(인자를 `nb::handle`로 받을 때. `nb::object`로 받으면 참조가 하나 늘어서 한 번도 임시로 판정되지 않아요).
- 그런데 다른 C 확장(예: Cython 코드)이 빌린 참조로 받은 `x`로 `x + y`를 계산한 뒤 `x`를 다시 읽으면, 이 API는 `x`를 임시 객체로 판정해요. 버퍼를 재사용하면 다시 읽은 `x`는 이미 덮어써져 있어요.
- 이것을 막으려면 numpy처럼 C 콜스택을 검사해야 해요. "C 콜스택을 뒤지는 수준의 해킹이 필요하면 넣지 않는다"는 규칙에 따라 뺐어요. 현재 프레임의 바이트코드가 `BINARY_OP`인지 보는 방법도 인터프리터 내부에 의존하고, 반사 연산(`__radd__`) 경로에 구멍이 남아서 택하지 않았어요.
- 그래서 연산자는 항상 새 출력 배열을 할당해요. 작은 배열에서는 그 할당이 위의 "5단계" 한 번이에요.

## 남은 비용과 numpy와의 차이

### `a + b`: 181ns 대 158ns

numpy가 약 23ns 빨라요. 할당 횟수는 이미 numpy와 비슷하므로(결과 데이터 + 배열 객체), 남은 차이는 경로 전체에 얇게 퍼져 있어요. 각 단계의 비용을 따로 재지는 않았어요. 코드에서 보이는 고정 작업은 이래요.

- 입력 `NDArray` 두 개의 복사: 각각 `shared_ptr` 참조 카운트의 atomic 증가·감소, shape/strides 몇 칸 복사
- `NdIter` 구성: 브로드캐스트, 축 정리, 차원 합치기(1차원이라 거의 바로 끝나요)
- `available()` 확인(스레드 지역 변수와 atomic 읽기 몇 번)과 분할 계획(일이 24바이트로 기준값보다 작아 나누지 않음)
- nanobind 인스턴스 할당과 등록(nanobind는 C++ 객체 주소 → Python 객체의 표를 관리해요), `NDArray` 이동
- `named()`처럼 에러 메시지에 함수 이름을 붙이는 래퍼는 연산자에는 쓰지 않고, 공개 함수에 쓰더라도 C++ 예외가 나지 않으면 비용이 없어요(`try`/`catch`는 예외가 날 때만 실행되는 표 기반 방식이에요).

### `x[1]`: 1차원은 24ns 대 28ns, 2차원은 65ns 대 39ns

1차원 배열의 `x[1]`은 원소 하나라서 `x[1, 2]`와 같은 빠른 경로(`leading_ints_fast`)를 타고 Python `float`을 돌려줘요. 같은 조건의 두 번째 측정에서 24ns, numpy 28ns로 stardust가 1.2배 빨라요. 이유는 아래 `x[1, 2]`와 같아요.

2차원 배열의 `x[1]`은 원소가 아니라 남은 축의 **뷰**(새 배열 객체)를 돌려줘요. 빠른 경로가 키 해석은 건너뛰지만, 뷰 객체를 만드는 비용은 남아요. 설계 문서의 분석으로는 nanobind 인스턴스의 등록과 할당, `NDArray` 복사(`view_of`에서 `NDArray`를 하나 복사하고 `.base` 참조를 올림), 메서드 호출 경로에 고르게 퍼져 있어서 한 군데를 고쳐 크게 줄일 곳이 없어요. 위 표의 `inst_alloc` 실험이 그 확인이에요.

### `zeros(3)`: 106ns 대 63ns

설계 문서의 측정은 99ns 대 61ns였고, 성능 종합의 표와 같은 조건으로 다시 잰 값은 106ns 대 63ns예요(1스레드와 10스레드 모두 같은 크기). `zeros`는 `shape` 인자를 `parse_shape`로 읽는데, 이 함수는 `std::vector<int64_t>`를 돌려줘요(정수 하나여도 원소 1개짜리 vector를 만들어요). 그래서 `zeros(3)`에는 결과 Buffer 말고도 vector의 할당과 해제가 한 번씩 있어요. 이것이 차이의 얼마를 차지하는지는 재지 않았어요. `dtype=` 키워드 인자를 받는 nanobind의 인자 처리도 경로에 있어요.

### `x[1, 2]`: 25ns 대 35ns — stardust가 빠른 이유

- stardust는 빠른 경로에서 tuple 확인, 정수 두 개 읽기, 곱셈·덧셈 두 번, `float` 객체 하나 만들기로 끝나요.
- **돌려주는 객체가 달라요.** stardust는 Python 내장 `float`을 돌려주고(`PyFloat_FromDouble`), numpy는 `numpy.float64` 스칼라 객체를 돌려줘요(둘 다 numpy 2.5.4와 현재 빌드에서 `type(x[1, 2])`로 확인). stardust는 0차원 배열이나 자체 스칼라 타입을 두지 않는다는 규칙이 있어서, 원소 하나는 언제나 Python 스칼라예요.

### `sum(a)`: 92ns 대 581ns — 6배 차이의 정체

이 차이는 C++과 C의 속도 차이가 아니라 **호출 경로에 Python 코드가 있느냐**의 차이예요. numpy 2.5.4의 `np.sum`을 따라가 보면(`numpy/_core/fromnumeric.py`에서 확인):

1. `np.sum`은 `numpy._ArrayFunctionDispatcher` 객체예요. `__array_function__` 프로토콜(다른 배열 라이브러리가 numpy 함수를 가로챌 수 있게 하는 장치)을 위해 인자를 먼저 살펴요.
2. 그다음 Python으로 짠 함수 `sum`이 돌아요. 제너레이터 검사 뒤 `_wrapreduction(a, np.add, 'sum', axis, dtype, out, keepdims=…, initial=…, where=…)`을 불러요.
3. `_wrapreduction`은 Python 코드예요. 키워드 인자를 dict comprehension으로 걸러 새 dict를 만들고, `type(obj) is not mu.ndarray`를 확인한 뒤 `ufunc.reduce(obj, axis, dtype, out, **passkwargs)`를 불러요.
4. `np.add.reduce`가 C에서 리덕션을 하고 `numpy.float64` 스칼라를 돌려줘요.

stardust의 `sd.sum`은 nanobind 함수 객체 자체예요(`type(sd.sum)`은 `nanobind.nb_func`). Python 코드를 하나도 거치지 않고 C++의 `sum()`으로 바로 들어가서, 인자 확인 → 출력(원소 1개, Buffer 내장) 할당 → 이터레이터 → 리덕션 커널(원소 3개라 순서대로 덧셈) → Python `float`으로 끝나요. 작은 배열을 위한 특수 경로는 없어요. 일반 리덕션 경로가 그 자체로 92ns예요.

### `a.sum()` 메서드: 91ns 대 213ns

함수 형태의 비교는 numpy에 불리해요. 그래서 메서드 형태 `a.sum()`도 성능 종합의 표와 같은 조건(numpy 2.5.4, 7라운드 중 가장 빠른 값)으로 쟀어요. stardust 91ns, numpy 213ns로 여전히 2.36배예요. 1스레드와 10스레드는 91ns와 92ns로 같아요.

numpy의 `a.sum()`은 `np.sum`의 래퍼 층을 건너뛰지만, C로 바로 가지는 않아요.

- **numpy의 `a.sum()`도 Python 함수 하나를 거쳐요.** `sys.setprofile`로 보면 `a.sum()` 한 번에 `numpy/_core/_methods.py`의 `_sum`이 불려요. 이 함수는 `umr_sum(a, axis, dtype, out, keepdims, initial, where)`, 곧 `np.add.reduce`를 부르는 한 줄짜리예요. `np.sum(a)`가 거치는 `_sum_dispatcher`, `sum`, `_wrapreduction` 세 단계보다는 훨씬 얇아요.
- **남은 비용 대부분은 numpy의 리덕션 기계 자체예요.** `np.add.reduce(a)`만 따로 재면 188ns예요(이 문서를 쓰며 잰 값). `a.sum()`의 213ns 중 약 25ns가 `_sum` 래퍼이고, 나머지가 ufunc 리덕션의 준비와 `numpy.float64` 스칼라 만들기예요. 그 안을 더 나눠 재지는 않았어요.
- stardust의 메서드 `A.sum()`은 모듈 함수 `sum`을 그대로 등록한 것이라(`.def("sum", named("sum", &sum), ...)`) `sd.sum(A)`(92ns)와 같은 경로예요.

그러니 함수 형태의 6.3배 중 약 2.7배(581ns → 213ns)는 numpy의 Python 래퍼 층이고, 남은 2.4배는 리덕션 경로 자체의 고정 비용 차이예요.

## 성능

### 복잡도

작은 배열 호출의 비용은 원소 수가 아니라 **차원 수**에 비례하는 부분과 상수 부분으로 이뤄져요.

- `NDArray` 복사, 브로드캐스트, 이터레이터 구성, 플래그 계산: $O(d)$ (축 재배열만 $O(d^2)$), $d \le 32$
- 할당: 결과 배열당 C++ 1번(256바이트 이하면 Buffer와 데이터가 한 덩어리) + Python 객체 1번
- 계산: $O(n)$, 원소 3개면 몇 ns

원소가 많아지면 계산이 빠르게 고정 비용을 넘어서요. 원소 100만 개 `f + g`는 1스레드 164µs로, 고정 비용(약 0.2µs)은 0.1% 남짓이에요. 원소 3개와 100만 개 사이 어디쯤부터 계산이 지배하는지는 연산마다 달라요. 그 위로 원소 2¹⁵개(256KB)를 넘으면 스레드풀이 끼어들어요([스레드풀과 결정성](/internals/core/threads/)).

### 정리

| 연산 | 처음 | 지금 | numpy | 바뀐 것 |
|---|---:|---:|---:|---|
| `a + b` (원소 3개) | 280ns | 181ns | 158ns | 필요한 칸만 복사, 할당 1번, 할당하는 표준 알고리즘 제거 |
| `x[1, 2]` | 98ns | 25ns | 35ns | 위 + 정수 인덱스 빠른 경로 |
| `x[1]` (2차원, 뷰) | 82ns | 65ns | 39ns | 정수 인덱스 빠른 경로 |
| `x[1]` (1차원, 원소) | — | 24ns | 28ns | 정수 인덱스 빠른 경로 |
| `sum(a)` (원소 3개) | — | 92ns | 581ns | 일반 경로만으로 (numpy는 Python 래퍼를 거침) |
| `a.sum()` (원소 3개) | — | 91ns | 213ns | `sd.sum`과 같은 경로 (numpy는 `_methods._sum`과 `add.reduce`) |
| `zeros(3)` | — | 106ns | 63ns | 남은 차이: `parse_shape`의 vector 할당 등 |
| 스칼라만의 원소별 호출 | — | 약 90ns 단축 | — | `launch_scalars` (`expit(0.5)` 140 → 48ns) |

(처음 값은 각 개선을 넣을 때 잰 값이고 측정 시점이 서로 달라요. "지금"의 `a + b`, `x[1, 2]`, `sum(a)`는 첫 벤치마크, 1차원 `x[1]`, `a.sum()`, `zeros(3)`은 같은 조건의 두 번째 측정, 2차원 `x[1]`은 설계 문서의 값이에요.)

이 페이지의 수치는 모두 1스레드와 10스레드에서 같아요. 작은 연산은 일이 기준값보다 작아 `parallel_for`를 부르지 않으므로, 스레드 수는 `available()` 확인 비용 말고는 영향이 없어요. 위 벤치마크의 181ns 대 190ns 차이는 측정 잡음이에요.

정확도는 이 페이지의 어떤 변경에도 영향을 받지 않아요. 바꾼 것은 모두 메모리 관리와 호출 경로이고, 계산하는 루프와 순서는 그대로예요. 빠른 경로 두 개도 일반 경로와 결과가 비트까지 같아요.
