## 한눈에 보기

값이 한 dtype에서 다른 dtype으로 옮겨 가는 길은 다섯 가지예요. 이 페이지는 각 길의 규칙과 그 규칙을 구현한 방법을 다뤄요.

| 길 | 예 | 규칙 | 구현 |
|---|---|---|---|
| **승격** (연산의 dtype 고르기) | `int_arr + 1.5` | 높은 쪽 dtype, 그 연산의 루프가 있는 첫 dtype | `promote`, `select` (`csrc/base/dtype.hpp`, `csrc/array/ops/ufunc.cpp`) |
| **Python 데이터에서 만들기** | `asarray([[1, 2], [3, 4.5]])` | shape 찾기, 원소 종류를 승격해 dtype 정하기, 값 쓰기 | `csrc/array/ops/asarray.cpp` |
| **다른 라이브러리에서 가져오기** | `asarray(np_arr)`, `from_dlpack(t)` | 저장 타입이 정확히 같으면 공유, 손실 없는 확장이면 복사 | `asarray.cpp`, `csrc/array/ops/dlpack.cpp` |
| **명시적 변환** | `astype`, `dtype=` | 손실이 있어도 변환. float → int는 0 방향 자르기 + 포화 + NaN → 0 | `cast_value` (`csrc/array/convert.hpp`), `saturate_to_int64` (`csrc/base/saturate.hpp`), `cast_loop` (`csrc/array/kernels/cast.hpp`) |
| **암묵적 변환** | `x[...] = v`, `out=`, `x += y` | 승격 순서의 위로만. 아래로 가면 TypeError | `check_assignable` (`csrc/array/ops/copy.cpp`) |

이 다섯 길을 꿰는 원칙은 셋이에요.

1. dtype은 dtype만 보고 정해요. 값을 보고 결과 dtype이나 에러 여부를 정하는 규칙이 없어요. `uint64` 버퍼는 값이 작아도 거부하고, 암묵적 하향 변환은 `2.0`처럼 손실이 없는 값이어도 거부해요. 예외는 하나뿐인데, int64 범위를 벗어난 Python int를 int64로 바꿔야 할 때 나는 `OverflowError`예요(값 하나를 저장할 수 없으니까요).
2. 원소 단계의 변환은 실패하지 않아요. 막아야 할 변환(complex → float 등)은 dtype 단계에서 원소를 하나도 건드리기 전에 막아요. 그래서 변환 커널 안에는 에러 경로가 없고, 컴파일러가 루프를 자유롭게 벡터화해요.
3. 모든 변환은 정의된 동작이에요. C++에서 정의되지 않은 동작(undefined behaviour, UB)인 캐스트를 그대로 쓰지 않아요. 대표적인 예가 float → int64인데, 그대로 캐스트하면 UB가 될 수 있는 이 변환을 ARM 명령 하나로 해요.

## 승격

### dtype 네 개가 일직선

배열 dtype은 `bool`, `int64`, `float64`, `complex128` 넷이고, 승격 순서는 일직선이에요.

$$
\texttt{bool} \;<\; \texttt{int64} \;<\; \texttt{float64} \;<\; \texttt{complex128}
$$

`DType` enum의 값이 이 순서대로 매겨져 있어서([데이터 모델](/internals/array/data-model/)), 두 dtype의 승격은 큰 쪽을 고르는 것뿐이에요.

```cpp
// csrc/base/dtype.hpp
constexpr DType promote(DType a, DType b) { return a > b ? a : b; }
```

- Python 스칼라도 같은 규칙이에요. `bool` → bool, `int` → int64, `float` → float64, `complex` → complex128로 보고 배열과 똑같이 승격해요. numpy 2의 "약한 스칼라"(Python 스칼라는 배열의 dtype에 맞춰 준다는 NEP 50의 규칙) [1] 같은 예외가 없어요. stardust에는 float32나 int8처럼 "좁은" 타입이 없어서, 약한 스칼라 규칙이 결과를 바꾸는 경우가 거의 남지 않아요. 규칙 하나로 충분해요.
- numpy 스칼라(`numpy.float64`, `numpy.int64` …)도 Python 스칼라처럼 받아요. `numpy.float64`와 `numpy.complex128`은 Python `float`, `complex`의 서브클래스라 그대로 통과하고, 나머지는 타입 이름이 `numpy.`으로 시작할 때만 numpy의 추상 타입(`numpy.bool`, `numpy.integer`, `numpy.floating`, `numpy.complexfloating`)과 `isinstance`로 대조해요(`scalar_dtype`, `csrc/array/convert.cpp`). stardust는 numpy를 import하지 않아요. 이미 import된 모듈만 `PyImport_GetModule`로 한 번 찾아 캐시해요. numpy 스칼라가 존재한다면 numpy는 이미 import돼 있으니까요. 타입 이름의 앞 6글자를 `strncmp`로 보는 검사가 먼저라, numpy 스칼라가 아닌 객체는 `isinstance` 호출 없이 바로 걸러져요.

### 루프 선택: 승격한 dtype부터 위로

연산마다 "어느 dtype의 루프가 있는가"를 적은 표가 있어요. 승격한 dtype부터 위로 올라가며 루프가 있는 첫 dtype을 써요. numpy의 루프 선택과 같은 규칙이에요.

```cpp
// csrc/array/ops/ufunc.cpp (발췌)
DType select(const LoopTable& table, DType d, std::span<const DType> inputs, const char* symbol) {
    for (int k = static_cast<int>(d); k < kNumArrayDTypes; ++k)
        if (table[k].loop) return static_cast<DType>(k);
    no_loop(inputs, symbol);
}
```

비용은 최대 네 칸을 보는 것이라 상수 시간이에요. 아래 규칙은 코드로 따로 적지 않았고, 모두 이 표에서 저절로 나와요.

| 연산 | bool | int64 | float64 | complex128 | 결과 |
|---|:---:|:---:|:---:|:---:|---|
| `add`, `subtract`, `multiply`, `pow` | – | ✓ | ✓ | ✓ | bool 산술은 int64예요. `True + True == 2` |
| `divide` | – | – | ✓ | ✓ | 정수끼리 나누면 float64예요 |
| `sqrt`, `exp`, `sin`, … | – | – | ✓ | ✓ | 정수 입력은 float64로 계산해요 |
| `floor_divide`, `remainder` | – | ✓ | ✓ | – | complex에는 없어요 |
| `atan2`, `hypot`, `copysign`, `nextafter` | – | – | ✓ | – | |
| `less`, `greater`, `maximum`, `minimum` | ✓ | ✓ | ✓ | – | complex에는 순서가 없어서 TypeError |
| `equal`, `not_equal` | ✓ | ✓ | ✓ | ✓ | 비교는 산술이 아니라 bool에도 루프가 있어요 |
| `floor`, `ceil`, `trunc` | ✓ | ✓ | ✓ | – | 정수·bool 루프는 항등 함수라 dtype을 유지해요 |
| `logical_and`, `logical_or`, `logical_not` | ✓ | – | – | – | int64에서는 위로 올라가도 루프가 없어 TypeError |
| `bitwise_and`, `bitwise_or`, `bitwise_invert` | ✓ | ✓ | – | – | |
| `bitwise_left_shift`, `bitwise_right_shift` | – | ✓ | – | – | bool 입력은 따로 막아요 |

몇 가지를 따라가 보면 이래요.

- `int_arr / int_arr`: 승격하면 int64예요. `divide`에는 int64 루프가 없으니 위로 올라가 float64 루프를 써요. 입력은 실행 중에 float64로 변환돼요.
- `bool_arr + bool_arr`: 승격하면 bool인데 `add`에는 bool 루프가 없어요. 위로 올라가 int64 루프를 써요. numpy 2.5.4는 bool끼리 더하면 bool(논리합)이지만, stardust는 int64예요. `sum`, `prod`, 누적 연산도 bool을 int64로 쌓아요.
- `logical_and(int_arr, int_arr)`: 승격하면 int64예요. `logical_and`는 bool 루프만 있고, 선택은 위로만 가므로 bool까지 내려가지 않아요. `TypeError: logical_and(): not supported for int64 and int64`예요(Array API 표준의 규칙과 같아요).
- 시프트는 루프 표만으로는 bool 입력을 막을 수 없어요. bool은 위로 올라가 int64 루프에 닿기 때문이에요. 그래서 연산 정의에 `no_bool_inputs` 표시를 두고, 디스패치가 bool 입력을 먼저 거부해요.

### 표를 컴파일 시점에 만드는 방법

각 연산은 `csrc/array/kernels/scalar_ops.hpp`에 구조체 하나로 정의돼요. "어느 저장 타입에 루프가 있는가"는 변수 템플릿 `ok<T>`로 적어요.

```cpp
// csrc/array/kernels/scalar_ops.hpp (발췌)
struct Divide {
    static constexpr const char* name = "divide";
    template <typename T> static constexpr bool ok = is_float<T> || is_cplx<T>;
    static double f(double a, double b) { return a / b; }
    static c128 f(c128 a, c128 b) { return cdiv(a, b); }
};
// ...
struct LeftShift {
    static constexpr const char* name = "bitwise_left_shift";
    static constexpr bool no_bool_inputs = true;
    template <typename T> static constexpr bool ok = is_int<T>;
    static i64 f(i64 a, i64 b) { return static_cast<u64>(b) >= 64 ? 0 : static_cast<i64>(static_cast<u64>(a) << b); }
};
```

`csrc/array/kernels/elementwise.hpp`가 이것을 표로 바꿔요.

```cpp
// csrc/array/kernels/elementwise.hpp (발췌)
struct LoopEntry {
    Loop loop = nullptr;
    DType out = DType::Bool;
};
using LoopTable = std::array<LoopEntry, kNumArrayDTypes>;
// ...
template <typename Op, typename T, int Arity>
constexpr LoopEntry entry() {
    if constexpr (!Op::template ok<T>) {
        return {};
    } else if constexpr (Arity == 1) {
        return {&unary_loop<Op, T>, dtype_of<unary_result_t<Op, T>>};
    } else {
        return {&binary_loop<Op, T>, dtype_of<binary_result_t<Op, T>>};
    }
}
// ...
template <typename Op> inline constexpr LoopTable binary_table = detail::make_table<Op, 2>();
```

- `if constexpr`로 루프가 없는 dtype은 인스턴스화 자체를 하지 않아요. `Divide::f`에 int64판이 없어도 컴파일 오류가 나지 않는 이유예요.
- 출력 dtype은 `Op::f`의 반환 타입에서 `dtype_of`로 구해요. 비교 연산의 `f`가 `bool`을 반환하므로 출력 dtype이 bool이 되는 식이에요. 손으로 적은 출력 dtype 표가 따로 없으니, 표와 함수가 어긋날 수 없어요.
- 표는 `inline constexpr` 변수라 컴파일 시점에 채워져 바이너리의 읽기 전용 데이터에 들어가요. 런타임 초기화 비용도, 초기화 순서 문제도 없어요.
- 시프트의 bool 거부 표시는 C++20 `requires` 식 `constexpr bool no_bool = requires { Op::no_bool_inputs; };`로 읽어요. 이 멤버가 있는 연산만 `true`가 돼요.

### dtype이 다른 입력

`int_arr + float_arr`은 float64 루프로 계산해요. int64 입력은 실행 중에 4096원소씩 작은 버퍼로 변환한 뒤 루프에 넘겨요(버퍼 단위 캐스팅). 입력 전체를 float64 임시 배열로 바꾸면 메모리를 두 번 더 지나기 때문이에요. 자세한 내용과 버퍼 크기가 4096인 이유는 [연산 엔진](/internals/array/engine/)에 있어요. 원소 100만 개의 `f * i + g`(float64와 int64가 섞임)는 1스레드 397µs, numpy 635µs예요.

Python 스칼라 피연산자는 루프 dtype으로 미리 변환한 원소 1개짜리 배열이 되고, 이터레이터가 stride 0으로 브로드캐스트해요. 원소마다 변환하지 않아요.

### int와 float의 비교

`int_arr == float_arr`은 승격 규칙대로 float64 루프에서 비교해요. int를 float64로 바꾼 뒤 비교하므로, $2^{53}$을 넘는 정수는 반올림된 다음 비교돼요. `asarray([2**53 + 1]) == asarray([2.0**53])`은 `True`예요. numpy와 같고, frame도 같은 규칙을 따라요.

## 중첩 시퀀스에서 만들기

### 입구의 순서

`asarray(obj, dtype=None, copy=None)`(`csrc/array/ops/asarray.cpp`)는 `obj`를 이 순서로 봐요.

1. ndarray: 그대로 돌려주거나, `dtype`이 다르거나 `copy=True`이면 변환·복사해요.
2. 정확한 `numpy.ndarray`: 조건이 맞으면 버퍼 프로토콜을 거치지 않고 바로 공유해요(아래 "numpy 배열은 바로 공유해요"). 맞지 않으면 6번 길로 가요.
3. Python 스칼라: 0차원 배열이 될 것이므로 `ValueError`예요.
4. list, tuple: 아래의 두 패스 알고리즘으로 만들어요.
5. range: 버퍼가 아니라서 `PySequence_List`로 int 리스트를 만든 뒤 4번 길로 보내요(frame도 range를 받아요).
6. 버퍼 프로토콜을 지원하는 객체: 다음 절에서 다뤄요.
7. 그 밖은 `TypeError`예요. generator는 받지 않아요.

**패스 1a: shape 찾기** (`discover_shape`). 각 깊이에서 첫 원소만 따라 내려가며 길이를 모아요. `[[1, 2.5], [3, True]]`는 바깥 길이 2, 첫 원소 `[1, 2.5]`의 길이 2, 그 첫 원소 `1`은 시퀀스가 아니므로 멈춰서 shape `(2, 2)`예요. 도중에 ndarray를 만나면 그 배열의 shape를 이어 붙여요(`asarray([sd.arange(2), [1.5, 2]])`도 돼요). 깊이가 32를 넘으면 여기서 `ValueError`예요. 비용은 깊이에 비례하는 $O(\text{ndim})$뿐이에요.

**패스 1b: 검사와 종류 승격** (`validate`). 이제 모든 원소를 재귀로 돌며 1a의 shape와 맞는지 확인해요.

- 안쪽 깊이에서는 시퀀스의 길이가 `shape[depth]`와 같아야 해요. ndarray면 남은 shape와 같아야 해요.
- 가장 안쪽(`depth == ndim`)에서는 원소가 Python 스칼라여야 해요. `scalar_dtype`으로 종류를 읽어 지금까지의 종류와 승격해요. 시퀀스가 나오면 깊이가 맞지 않는 것이라 ragged(들쭉날쭉한) 에러이고, 스칼라도 시퀀스도 아니면(문자열 등) `TypeError`예요.

```cpp
// csrc/array/ops/asarray.cpp (발췌)
void validate(PyObject* o, size_t depth, const std::vector<std::int64_t>& shape, std::optional<DType>& kind) {
    auto merge = [&](DType d) { kind = kind ? promote(*kind, d) : d; };
    if (depth == shape.size()) {
        if (auto d = scalar_dtype(o)) return merge(*d);
        if (is_seq(o) || is_ndarray(o)) ragged(shape);
        throw nb::type_error(("cannot store an object of type '" + py_type_name(nb::handle(o)) +
                              "' in an array (only bool, int, float and complex)")
                                 .c_str());
    }
    if (is_ndarray(o)) {
        const NDArray& a = as_ndarray(o);
        // ...
        return merge(a.dtype);
    }
    if (!is_seq(o) || seq_len(o) != shape[depth]) ragged(shape);
    for (Py_ssize_t i = 0; i < shape[depth]; ++i) validate(seq_item(o, i), depth + 1, shape, kind);
}
```

dtype은 `dtype=`이 있으면 그것, 없으면 승격한 종류, 원소가 하나도 없으면(`asarray([])`) float64예요. 종류와 dtype 사이에서 `check_castable`을 불러 complex → float/int를 여기서 막아요(`asarray([1+0j], dtype=sd.float64)`는 허수부가 0이어도 `TypeError`예요. 값이 아니라 dtype을 보니까요).

**패스 2: 값 쓰기** (`fill_nested`). C 순서의 새 배열을 할당하고(0으로 채우지 않아요), 같은 재귀로 돌며 포인터 하나(`T*& out`)를 앞으로 밀면서 값을 써요. 원소마다 `scalar_from_python<T>`가 Python 객체를 저장 타입으로 바꿔요. 안에 든 ndarray는 행 우선 순회(`for_each_element`)로 원소를 꺼내 `cast_value`로 변환해요.

### 왜 두 패스인가

- dtype을 알아야 쓸 수 있어요. `[1, 2, 3.5]`는 마지막 원소를 보기 전까지 int64인지 float64인지 몰라요. 한 패스로 하려면 int64로 쓰다가 다시 변환하거나, 원소를 일단 Python 객체 목록으로 모아야 해요.
- shape를 알아야 할당할 수 있어요. 결과 배열을 한 번에 정확한 크기로 할당하려면 shape가 먼저 필요해요.
- 검사가 할당보다 먼저예요. ragged나 지원하지 않는 원소는 메모리를 할당하기 전에 드러나요.

numpy도 shape와 dtype을 먼저 알아낸 뒤 값을 채우는 방식이에요(`PyArray_DiscoverDTypeAndShape`, `numpy/_core/src/multiarray/array_coercion.c`) [2].

### shape를 첫 원소에서 읽어도 되는 이유

1a는 첫 원소만 보지만, 1b가 모든 원소를 그 shape와 대조하므로 들쭉날쭉한 입력을 빠짐없이 잡아요. 어긋나면 "기대한 shape"을 에러 메시지에 그대로 적어 줄 수 있어요.

```python
>>> sd.asarray([[1, 2], [3]])
Traceback (most recent call last):
    ...
ValueError: asarray(): inhomogeneous nested sequence: expected every level to match shape (2, 2)
```

`[1, [2]]`이면 1a가 첫 원소 `1`에서 멈춰 shape `(2,)`가 되고, 1b에서 둘째 원소가 스칼라 자리에 놓인 시퀀스라 같은 에러가 나요(기대 shape `(2,)`).

### 복잡도와 비용

원소(잎)가 $N$개, 중간 시퀀스가 $M$개이면

- 시간: 1a가 $O(\text{ndim})$, 1b와 2가 각각 $O(N + M)$이에요. 잎 하나를 두 번 방문해요(종류 읽기 한 번, 값 변환 한 번).
- 추가 메모리: shape 벡터와 재귀 스택뿐이에요. 재귀 깊이는 ndim + 1 이하이고 ndim은 32 이하라 스택이 넘칠 걱정이 없어요. 중간 Python 객체를 만들지 않아요.
- `PyList_GET_ITEM`/`PyTuple_GET_ITEM` 매크로로 원소를 **빌린 참조**로 읽어요. 원소마다 참조 카운트를 올렸다 내리는 일이 없어요. list와 tuple만 받으니 일반 시퀀스 프로토콜(`PySequence_GetItem`)을 쓸 필요가 없어요.
- 원소의 종류 판정은 `PyBool_Check` → `PyLong_Check` → `PyFloat_Check` → `PyComplex_Check` 순서예요. `bool`은 `int`의 서브클래스라 반드시 먼저 봐야 해요.

### 범위 밖의 Python int

int64 범위를 벗어난 Python int는 int64로 바꿔야 할 때만 `OverflowError`가 나요.

```python
>>> sd.asarray([2**70, 0.5])
array([1.1805916207174113e+21,                    0.5], dtype=float64)
>>> sd.asarray([2**70])
Traceback (most recent call last):
    ...
OverflowError: asarray(): Python int too large to convert to int64
```

첫 줄은 종류가 float64로 승격되므로 `2**70`을 float로 읽어요. 둘째 줄은 int64로 저장해야 하므로 에러예요. 이 검사는 패스 2에서 원소를 쓸 때 일어나요. 이미 할당한 배열은 `NDArray`의 `shared_ptr`가 소멸하면서 해제되므로 새지 않아요. 검사 방법은 아래 "Python int의 int64 범위 검사" 절에 있어요.

## 버퍼 프로토콜로 가져오기

### 공유할 것인가, 복사할 것인가

numpy 배열, `memoryview`, `array.array`처럼 PEP 3118 버퍼 프로토콜 [3]을 지원하는 객체는 `PyObject_GetBuffer(obj, &view, PyBUF_RECORDS_RO)`로 메모리를 받아요. `PyBUF_RECORDS_RO`는 "strides와 format을 달라, 읽기 전용이어도 된다"는 요청이에요.

먼저 format 문자열을 해석해요(`parse_format`).

- 앞의 바이트 순서 표시: `>`, `!`는 big-endian, `<`, `=`, `@`는 이 기계의 순서(little-endian)예요.
- 정수 코드는 문자(`b h i l q n`)가 아니라 `itemsize`로 크기를 정해요. C의 `long`(`l`)처럼 플랫폼마다 크기가 다른 코드가 있어서예요. 부호 없는 쪽(`B H I L Q N`)도 같아요.
- `e f d`는 float16/32/64, `Zf`, `Zd`는 complex64/128, `?`는 bool이에요.
- 그 밖의 format(구조체, 문자열 등)은 `TypeError`예요.

그 결과로 원천 타입 14가지(`Src` enum) 중 하나가 정해지고, 각 원천은 손실 없이 넓힐 수 있는 dtype이 정해져 있어요.

| 원천 | 들어갈 dtype | 공유 가능 |
|---|:---:|:---:|
| `bool` (`?`) | bool | ✓ (바이트가 0/1일 때) |
| `int64` | int64 | ✓ |
| `int8`, `int16`, `int32`, `uint8`, `uint16`, `uint32` | int64 | 복사 |
| `uint64` | – | `TypeError` |
| `float64` | float64 | ✓ |
| `float16`, `float32` | float64 | 복사 |
| `complex128` | complex128 | ✓ |
| `complex64` | complex128 | 복사 |

복사 없이 공유하려면 다섯 조건이 모두 맞아야 해요.

1. 원천이 stardust의 저장 타입과 정확히 같아요(`is_storage_of`).
2. little-endian이에요(바이트를 뒤집을 필요가 없어요).
3. 원소가 **자연 정렬**돼 있어요. 데이터 주소와 모든 stride가 `alignof(T)`의 배수라는 뜻이에요. `alignof(std::complex<double>)`이 8이라 complex128도 8바이트 정렬이면 돼요.
4. bool이면 모든 바이트가 0 또는 1이에요.
5. `copy=True`가 아니에요.

공유하면 `Buffer::adopt`가 `Py_buffer`를 넘겨받고, 배열의 `base`는 내보낸 객체(`view.obj`), `writeable`은 `!view.readonly`가 돼요. 하나라도 어긋나면 복사하고, `copy=False`였다면 `ValueError`예요.

### numpy 배열은 바로 공유해요

numpy 배열을 버퍼 프로토콜로 받으면, numpy가 내보낼 때마다 format 문자열을 다시 만들어 캐시와 비교하는 일이 호출의 절반을 차지하고 `Py_buffer` 관리가 나머지예요. 그래서 정확히 `numpy.ndarray`(하위 클래스는 아니에요)인 입력은 numpy의 공개 C 구조체(`numpy/_core/include/numpy/ndarraytypes.h`의 `PyArrayObject_fields`와 `PyArray_Descr`의 앞부분, numpy 1.x와 2.x에서 같은 자리)에서 data, shape, strides, flags를 바로 읽어요(`share_numpy`).

- 조건은 위의 공유 조건과 같아요. 원소 타입이 넷 중 하나(`type_num`: bool 0, long 7·longlong 9, double 12, cdouble 15)이고, native 바이트 순서이고, 정렬되어 있고, `dtype=`이 다르지 않고 `copy=True`가 아니어야 해요. bool은 0/1 검사를 똑같이 해요.
- 원소가 없는 배열은 버퍼 경로로 보내요. numpy의 빈 배열은 stride가 0일 수 있는데, 버퍼 내보내기는 C 연속 stride를 주기 때문이에요.
- 결과의 `base`는 그 numpy 배열이고 Buffer는 없어요. numpy 배열에 대한 참조가 메모리를 살려 둬요. 쓰기 가능 여부는 numpy의 내보내기와 같아요(`WRITEABLE`이고 `WARN_ON_WRITE`가 아닐 때).
- numpy 타입은 이름(`tp_name`이 `"numpy.ndarray"`)으로 한 번 알아보고 포인터를 저장해요. numpy를 import하지 않아요.
- 조건에 맞지 않으면(big-endian, float32, 하위 클래스, 정렬 안 됨 등) 버퍼 경로로 가요. 그래서 결과는 어느 길이든 같은 뷰, 같은 `.base`, 같은 쓰기 가능 여부예요.

```python
>>> import numpy as np
>>> n = np.arange(6.0)
>>> sd.asarray(n).base is n
True
```

`PyObject_GetBuffer`로 받은 뷰는 반드시 `PyBuffer_Release`로 돌려줘야 해요. 그 사이의 어느 검사에서든 예외가 날 수 있으므로, 작은 RAII 가드(`ViewGuard`)가 소멸자에서 release해요. 공유가 결정되면 가드를 해제(`armed = false`)하고 소유권을 `Buffer`에 넘겨요.

### 정렬을 요구하는 이유

커널은 `reinterpret_cast<const double*>(p)`처럼 저장 타입의 포인터로 원소를 읽어요. C++에서 정렬되지 않은 주소를 `double*`로 읽는 것은 정의되지 않은 동작이고, 컴파일러는 정렬을 가정한 최적화를 할 수 있어요. 정렬되지 않은 외부 버퍼(예: 구조체 배열의 한 필드, 바이트 단위로 자른 버퍼)는 드물어요. 그래서 입구에서 복사하고, 모든 커널은 정렬을 가정해요. 복사 경로는 원소를 `std::memcpy`로 읽으므로(`load<T>`) 정렬과 무관하게 안전해요.

### bool 바이트 검사

bool 버퍼에는 0과 1이 아닌 바이트가 들어 있을 수 있어요(예: numpy에서 `uint8` 배열을 `.view(bool)`로 본 것). stardust의 bool 커널은 바이트를 더해 True를 세요(`sum`, 마스크의 개수 세기). 2라는 바이트가 있으면 True 하나가 2로 세어져요.

그래서 bool 버퍼를 공유하기 전에 모든 바이트의 OR을 구해 1 이하인지 봐요.

```cpp
    // csrc/array/ops/asarray.cpp (발췌): 분기 없는 OR 리덕션
    if (target == DType::Bool && shareable && aligned && copy != true) {
        std::uint8_t any = 0;
        foreign.update_flags();
        if (foreign.c_contiguous) {
            const auto* q = static_cast<const std::uint8_t*>(view.buf);
            for (std::int64_t i = 0, n = foreign.size(); i < n; ++i) any |= q[i];
        } else {
            // ...
        }
        valid = any <= 1;
    }
```

모든 바이트가 0 또는 1이면 OR도 0 또는 1이고, 2 이상의 바이트가 하나라도 있으면 OR에 1보다 높은 비트가 켜져요. 원소마다 비교하고 분기하는 대신 OR만 하므로 컴파일러가 16바이트씩 NEON으로 벡터화해요. 원소 100만 개에서 8.3µs로, 비교하고 분기하는 루프(235µs)보다 훨씬 빨라요. 0/1이 아닌 바이트가 있으면 0/1로 정규화해서 복사해요.

입구 한 곳에서 막으면 모든 bool 커널을 한 번에 지킬 수 있어요. 대신 공유한 뒤에 바깥(numpy 쪽)에서 바이트를 바꾸는 경우는 막지 못해요.

```python
>>> b = np.array([0, 2, 1], dtype=np.uint8).view(np.bool_)
>>> sd.asarray(b)
array([False,  True,  True], dtype=bool)
>>> sd.asarray(b, copy=False)
Traceback (most recent call last):
    ...
ValueError: asarray(): copy=False, but this bool buffer holds bytes other than 0 and 1
```

### 넓히는 복사

공유할 수 없으면 새 배열에 복사하면서 변환해요. 원천 타입 13가지(`uint64` 제외)와 대상 dtype 4가지의 조합을 템플릿 람다 두 겹으로 만들어요.

```cpp
    // csrc/array/ops/asarray.cpp (발췌)
    NDArray dst = new_array_like(foreign, target);  // keeps the source's memory order
    visit_src(src, [&]<typename S>(std::type_identity<S>) {
        visit_dtype(target, [&]<typename T>(std::type_identity<T>) {
            // ...
            if ((PyBuffer_IsContiguous(&view, 'C') && dst.c_contiguous) ||
                (PyBuffer_IsContiguous(&view, 'F') && dst.f_contiguous)) {
                const auto* sp = static_cast<const std::byte*>(view.buf);
                T* dp = reinterpret_cast<T*>(dst.data);
                const std::int64_t n = dst.size();
                constexpr std::int64_t w = static_cast<std::int64_t>(sizeof(S));
                for_pieces(n, kParallelTask, n, [&](std::int64_t, std::int64_t i0, std::int64_t i1) {
                    if (swapped) {  // byte-reversed (a big-endian buffer): the same flat loop
                        for (std::int64_t i = i0; i < i1; ++i)
                            dp[i] = cast_value<T>(widen(load_swapped<S>(sp + i * w)));
                    } else {
                        for (std::int64_t i = i0; i < i1; ++i) dp[i] = cast_value<T>(widen(load<S>(sp + i * w)));
                    }
                });
                return;
            }
            // ...
            auto run = [&](auto&& load_one) {
                // ...
            };
            if (swapped) run([](const std::byte* p) { return load_swapped<S>(p); });
            else run([](const std::byte* p) { return load<S>(p); });
        });
    });
```

- 넓히기는 모두 정확해요. 32비트 이하의 정수는 int64에, float16과 float32의 모든 값은 float64에, complex64는 complex128에 정확히 들어가요. 그래서 이 변환은 `dtype=` 없이도 자동으로 해요.
- `uint64`는 값이 아니라 dtype으로 거부해요. $2^{63}$ 이상의 값이 하나도 없어도 `TypeError`예요. 값을 보고 판단하면 같은 코드가 데이터에 따라 성공하기도 실패하기도 하고, 값에 따라 dtype을 바꾸면 이번에는 결과 dtype이 데이터에 따라 달라져요. `dtype=`을 주어도 거부하고, frame도 같은 규칙이에요.
- big-endian은 복사하면서 바이트를 뒤집어요(`load_swapped`, 아래 "바이트 뒤집기"). 공유는 하지 않아요.
- float16(`__fp16`)은 저장 전용 타입이라 먼저 `float`로 바꾼 다음(`widen`) 변환해요.
- `dtype=`을 주면 넓힌 값에 명시적 변환(`cast_value`, 아래 절)을 한 번 더 해요. `asarray(np_float32, dtype=sd.int64)`는 float32 → float64 → int64(포화)예요.
- 결과의 레이아웃은 원본의 메모리 축 순서를 따라요. F 순서 numpy 배열을 가져오면 F 순서 결과가 나와요(int32 `(2, 3)` F 순서 배열의 결과 strides가 `(8, 16)`).
- 0차원 버퍼와 32차원을 넘는 버퍼는 `ValueError`예요.

복사 루프는 두 갈래예요.

**평탄한 경로: 루프 하나.** 버퍼가 연속이면(C 순서든 F 순서든, 바이트 순서가 어느 쪽이든), 원본과 결과는 같은 순서로 놓인 원소 $n$개의 줄 두 개예요. 결과 배열은 원본의 메모리 축 순서를 따라 만들므로(`new_array_like`), C 연속 버퍼의 결과는 C 연속이고 F 연속 버퍼의 결과는 F 연속이에요. 그러면 shape가 몇 차원이든 메모리 순서로 $i$번째 원소를 읽어 $i$번째 자리에 쓰면 돼요.

$$
\texttt{dst}[i] = \operatorname{cast}_T\bigl(\texttt{src}[i]\bigr), \qquad i = 0, 1, \dots, n - 1
$$

- 컴파일러가 벡터화해요. 원본 주소가 `sp + i * sizeof(S)`라서 원소 간격이 컴파일 시점 상수예요. `load<S>`는 고정 크기 `std::memcpy`라 load 명령 하나로 접히고, 결과 쪽은 `T*` 인덱스 접근이에요. big-endian이면 load 뒤에 바이트 뒤집기 명령이 하나 붙을 뿐 루프의 모양은 같아요. 바이트 순서 분기는 조각마다 한 번, 루프 밖에서 해요. 간격이 런타임 값인 루프는 컴파일러가 연속 접근임을 알 수 없어 벡터화하지 못해요([원소별 커널](/internals/array/elementwise/)의 "바이트 stride 루프는 벡터화되지 않아요"와 같은 문제예요). `S`와 `T`의 조합마다 템플릿이 따로 인스턴스화되므로, 원천 타입마다 손으로 쓴 SIMD 경로 없이 조합마다 맞는 루프가 만들어져요.
- 정렬되지 않은 버퍼도 이 경로예요. 읽기가 `memcpy`라서 원본 주소가 원소 크기의 배수가 아니어도 정의된 동작이에요. 정렬이 맞지 않아 공유하지 못한 float64 버퍼가 이 경로로 복사돼요.
- 풀에 나눠요. `for_pieces`가 $[0, n)$을 4096원소(`kParallelTask`)짜리 조각으로 자르고, 원소가 $2^{15}$개 이상이면 스레드풀에서 돌려요([연산 엔진](/internals/array/engine/)의 "이터레이터 밖: `for_pieces`"). 조각마다 서로 다른 자리에 쓰고 값은 원소마다 독립이라, 결과는 스레드 수와 무관해요.
- 복사에 쓰는 임시 메모리는 없어요. 추가 메모리는 결과 배열뿐이에요.

**일반 경로: 결과의 메모리 순서로, 조각마다 odometer.** 연속이 아닌 버퍼(`np_arr[::2]`, `m[:, 1:]`, 전치한 뷰 등)는 원소 간격이 축마다 달라 평탄한 루프로 쓸 수 없어요. 이 경로는 먼저 축을 결과 배열의 stride 절댓값이 큰 순서로 정렬해요. 결과는 원본의 메모리 축 순서를 따라 만들어졌으므로(`new_array_like`), 이 순서는 원본의 메모리 순서이기도 해요. 그 순서로 원소에 $0, 1, \dots, n - 1$번까지 번호를 매기고, 번호 구간을 평탄한 경로와 똑같이 `for_pieces`로 잘라 풀에서 돌려요.

```cpp
                // csrc/array/ops/asarray.cpp, 일반 경로 (발췌)
                int perm[kMaxNdim];
                for (int d = 0; d < nd; ++d) perm[d] = d;
                std::stable_sort(perm, perm + nd, [&](int x, int y) {
                    return std::abs(dst.strides[x]) > std::abs(dst.strides[y]);
                });
                std::int64_t shp_[kMaxNdim], ss_[kMaxNdim], ds_[kMaxNdim];
                for (int d = 0; d < nd; ++d)
                    shp_[d] = dst.shape[perm[d]], ss_[d] = foreign.strides[perm[d]], ds_[d] = dst.strides[perm[d]];
                const std::int64_t* shp = shp_;
                const std::int64_t* ss = ss_;
                const std::int64_t* ds = ds_;
                const auto* sbase = static_cast<const std::byte*>(view.buf);
                std::byte* dbase = dst.data;
                for_pieces(n, kParallelTask, n, [&](std::int64_t, std::int64_t i0, std::int64_t i1) {
                    std::int64_t idx[kMaxNdim];
                    std::int64_t rem = i0, so = 0, dof = 0;
                    for (int d = nd - 1; d >= 0; --d) {
                        idx[d] = rem % shp[d];
                        rem /= shp[d];
                        so += idx[d] * ss[d];
                        dof += idx[d] * ds[d];
                    }
                    const std::int64_t inner = shp[nd - 1], si = ss[nd - 1], di = ds[nd - 1];
                    const bool dense =
                        si == static_cast<std::int64_t>(sizeof(S)) && di == static_cast<std::int64_t>(sizeof(T));
                    for (std::int64_t i = i0; i < i1;) {
                        const std::int64_t len = std::min(inner - idx[nd - 1], i1 - i);
                        const std::byte* ps = sbase + so;
                        std::byte* pd = dbase + dof;
                        if (dense) {
                            T* dp = reinterpret_cast<T*>(pd);
                            for (std::int64_t k = 0; k < len; ++k)
                                dp[k] = cast_value<T>(widen(load_one(ps + k * static_cast<std::int64_t>(sizeof(S)))));
                        } else {
                            for (std::int64_t k = 0; k < len; ++k, ps += si, pd += di)
                                store(pd, cast_value<T>(widen(load_one(ps))));
                        }
                        i += len, so += len * si, dof += len * di, idx[nd - 1] += len;
                        for (int d = nd - 1; d > 0 && idx[d] == shp[d]; --d) {  // carry
                            so += ss[d - 1] - shp[d] * ss[d];
                            dof += ds[d - 1] - shp[d] * ds[d];
                            idx[d] = 0;
                            ++idx[d - 1];
                        }
                    }
                });
```

- 결과의 메모리 순서로 걷는 이유: 논리적 C 순서(마지막 축이 가장 빨리 도는 순서)로 걸으면, 전치한 뷰에서는 논리적 마지막 축이 원본과 결과 양쪽에서 메모리상 가장 멀리 뛰는 축이에요. 안쪽 루프가 원소마다 수 KB씩 건너뛰며 읽고 써서 캐시 미스가 시간을 정해요(float32 `m.T` 1000×1000을 그렇게 걸으면 1스레드 870µs). 메모리 순서로 걸으면 안쪽 축이 원본에서 가장 촘촘한 축이 되어 122µs예요.
- 안쪽 축이 붙어 있으면 인덱스 루프예요. `m[:, 1:1001]`처럼 행 안은 연속이고 행 사이만 떨어진 버퍼는 안쪽 축의 간격이 양쪽 모두 원소 크기와 같아요. 이때는 평탄한 경로처럼 `ps + k * sizeof(S)`로 읽고 `dp[k]`에 쓰는 루프라 컴파일러가 벡터화해요. 간격이 런타임 값인 strided 루프로 돌면 같은 버퍼가 260µs, 인덱스 루프로는 127µs예요.
- 조각의 시작점은 나눗셈으로 구해요. 번호 $i_0$의 축별 인덱스는 shape를 진법의 밑으로 삼은 자릿수예요. 마지막 축부터 `%`와 `/`로 풀면서, 인덱스에 그 축의 stride를 곱해 더하면 원본과 결과에서의 바이트 오프셋이 나와요. 조각마다 한 번, $O(\text{ndim})$이에요. 그래서 조각은 앞 조각이 어디서 끝났는지 몰라도 혼자 시작할 수 있고, 어느 스레드가 어느 조각을 맡아도 같은 원소를 같은 자리에 써요.
- 안쪽 루프는 평탄해요. 안쪽 축을 따라 `len`개를 도는 동안 하는 일은 포인터 이동과 load, 변환, store뿐이에요. 축 인덱스를 올리고 끝을 검사하는 odometer의 일은 안쪽 축 한 줄에 한 번만 해요. 원소마다 odometer를 한 칸씩 돌리면(원소마다 자리올림 검사) int32 100만 개에 417µs가 들어요.
- 자리올림: 축 $d$가 끝에 닿으면 인덱스를 0으로 되돌리고 축 $d - 1$을 한 칸 올려요. 오프셋은 `ss[d - 1] - shp[d] * ss[d]`만큼 옮겨요. 축 $d$를 처음으로 되감고(`- shp[d] * ss[d]`) 바깥 축을 한 칸 나아가는(`+ ss[d - 1]`) 것을 한 번에 더한 값이에요.
- 1차원에서는 odometer가 사라져요. `nd == 1`이면 자리올림 루프가 돌지 않고, 조각 하나가 strided 루프 하나예요.
- 결과는 스레드 수와 상관없어요. 조각마다 서로 다른 원소를 쓰고, 값은 원소마다 독립이에요.

안쪽 축이 붙어 있지 않으면(`i32[::2]`, `m[:, ::2]`) 간격 `si`, `di`가 런타임 값이라 컴파일러가 벡터화하지 못해요. 그래서 이 경우는 벡터화되는 루프보다 느려요. 안쪽 축이 붙어 있는 2차원 버퍼와 전치한 뷰는 안쪽 루프가 벡터화돼요.

### 바이트 뒤집기

big-endian 버퍼(`>f8`, `>i4` 등)의 원소는 바이트 순서가 이 기계(little-endian)와 반대예요. `load_swapped<S>`가 원소 하나를 읽으면서 뒤집어요.

```cpp
// csrc/array/ops/asarray.cpp, load_swapped
template <typename S>
S load_swapped(const std::byte* p) {
    constexpr bool cplx = std::is_same_v<S, std::complex<float>> || std::is_same_v<S, std::complex<double>>;
    if constexpr (!cplx && (sizeof(S) == 2 || sizeof(S) == 4 || sizeof(S) == 8)) {  // one part: a byte swap instruction
        using U = std::conditional_t<
            sizeof(S) == 2, std::uint16_t, std::conditional_t<sizeof(S) == 4, std::uint32_t, std::uint64_t>>;
        U u;
        std::memcpy(&u, p, sizeof u);
        if constexpr (sizeof(S) == 2) u = __builtin_bswap16(u);
        else if constexpr (sizeof(S) == 4) u = __builtin_bswap32(u);
        else u = __builtin_bswap64(u);
        S v;
        std::memcpy(&v, &u, sizeof v);
        return v;
    } else if constexpr (cplx) {  // two parts, each swapped on its own
        using P = typename S::value_type;
        return S(load_swapped<P>(p), load_swapped<P>(p + sizeof(P)));
    }
    constexpr std::size_t part = cplx ? sizeof(S) / 2 : sizeof(S);
    std::byte tmp[sizeof(S)];
    for (std::size_t k = 0; k < sizeof(S); k += part)
        for (std::size_t b = 0; b < part; ++b) tmp[k + b] = p[k + part - 1 - b];
    return load<S>(tmp);
}
```

- 뒤집기는 명령 하나예요. `__builtin_bswap16/32/64`는 정수의 바이트 순서를 뒤집는 컴파일러 내장 함수이고, ARM64에서는 `REV` 명령 하나(벡터화되면 `REV16`/`REV32`/`REV64`의 벡터판)로 번역돼요. 바이트를 하나씩 임시 배열에 거꾸로 옮기는 루프보다 빠르고, 평탄한 루프 안에서 벡터화를 막지 않아요.
- float도 정수로 뒤집어요. 바이트를 같은 크기의 부호 없는 정수로 읽어(`memcpy`) 뒤집고, 그 비트를 다시 float로 읽어요(`memcpy`). `memcpy` 두 번은 컴파일하면 사라져요.
- complex는 실수부와 허수부를 따로 뒤집어요. complex128의 16바이트는 double 두 개가 (실수부, 허수부) 순서로 놓인 것이고, big-endian에서도 두 부분의 순서는 같아요. 16바이트를 통째로 뒤집으면 두 부분의 자리가 바뀌어요. 그래서 부분 타입 `P`로 자기 자신을 두 번 불러 8바이트(complex64는 4바이트)씩 뒤집어요.
- 연속인 big-endian 버퍼는 평탄한 경로예요. 뒤집기가 load에 붙은 명령 하나라, 평탄한 루프의 벡터화가 그대로 유지돼요. 연속이 아닌 big-endian 버퍼는 일반 경로에서 같은 `load_swapped`를 써요.

### 복사하는 경로의 속도

원소 100만 개, 1스레드, numpy 2.5.4에서 잰 값이에요. `m`은 float32 2차원 배열이에요.

| 연산 | stardust | numpy | 지나는 경로 |
|---|---:|---:|---|
| `sd.asarray(i32)` (int32 → int64) | 60µs | 99µs (`astype`) | 평탄한 루프 |
| `sd.asarray(>f8 2차원 [::2])` (행을 한 칸 건너) | 102µs | 117µs | 일반 경로, 안쪽 축은 인덱스 루프 + 뒤집기 |
| `sd.asarray(m[:, 1:1001])` (행 안이 연속) | 127µs | 142µs | 일반 경로, 안쪽 축은 인덱스 루프 |
| `sd.asarray(m.T)` (1000×1000 전치) | 122µs | 137µs | 일반 경로, 결과의 메모리 순서 |

- 연속인 버퍼는 평탄한 루프 하나라 컴파일러가 벡터화해요. 같은 int32 넓히기를 원소마다 odometer로 걸으면 417µs예요. 연속인 big-endian 버퍼도 뒤집기가 load에 붙은 명령 하나라 같은 평탄한 루프예요.
- 행 안이 연속인 2차원 버퍼와 전치한 뷰는 안쪽 축이 양쪽에서 붙어 있어 인덱스 루프가 벡터화돼요. 간격이 런타임 값인 strided 루프로 돌면 `m[:, 1:1001]`이 260µs, 논리적 C 순서로 걸으면 `m.T`가 870µs예요.
- 전치한 뷰의 결과는 원본처럼 F 순서이고, 이후 연산의 엔진이 이 레이아웃을 그대로 따라가요.
- 결과 배열을 새로 할당하는 비용은 두 라이브러리 모두 같은 조건이에요(numpy의 `astype`도 새 배열을 만들어요).

### 복사 없이 공유하는 비용

복사가 없는 경로도 고정 비용이 있어요. `np.asarray(ndarray)`는 이미 numpy 배열이면 같은 객체를 그대로 돌려주므로 하는 일이 인자 확인뿐이에요. stardust에서 이에 맞는 것은 같은 객체를 돌려주는 `sd.asarray(sd 배열)`이에요. `sd.asarray(numpy 배열)`은 다른 라이브러리의 객체를 받아 새 Python 객체를 만드는 일이라 하는 일이 달라요. strided 뷰나 전치한 뷰도 복사 없이 공유하므로 같은 경로예요.

그 비용이 어디에 쓰이는지 코드 순서대로 보면 이래요(`asarray` → `share_numpy`).

1. `is_ndarray`가 아니므로 `share_numpy`가 타입 포인터를 저장한 numpy 타입과 비교해요. 같으면 numpy의 C 구조체에서 dtype 번호, 바이트 순서, shape, strides, flags를 읽고 정렬을 확인해요. 스칼라 검사(`scalar_dtype`)는 이 뒤라서 numpy 배열은 그 비용을 치르지 않아요.
2. `NDArray`를 채우고 `base`에 numpy 배열의 참조를 둬요. Buffer는 만들지 않아요.
3. `wrap`이 인스턴스 풀에서 객체를 받아요.

`np.asarray`가 입력을 그대로 돌려주는 것과 견주면 결과 객체 하나만큼의 시간이 남아요. 그 밖의 버퍼(`memoryview`, `array.array`, 조건에 맞지 않는 numpy 배열)는 `PyObject_GetBuffer`, format 해석, `Buffer::adopt`를 거치고, 결과가 버려질 때 Buffer의 소멸자가 GIL을 확인(`PyGILState_Ensure`)한 뒤 `PyBuffer_Release`를 불러요.

반대 방향(stardust 배열을 numpy가 읽는 것)은 `bf_getbuffer` 슬롯으로 복사 없이 내보내요. format은 `?`, `q`, `d`, `Zd`예요. 자세한 내용은 [데이터 모델](/internals/array/data-model/)과 [Python과 C++의 경계](/internals/core/python-boundary/)에 있어요.

## DLPack으로 가져오기

DLPack은 라이브러리 사이에서 텐서를 복사 없이 주고받는 메모리 구조 규약이에요 [4]. Python Array API 표준이 `from_dlpack`과 `__dlpack__`, `__dlpack_device__`를 정해 두었어요 [5]. stardust는 CPU와 네 가지 배열 dtype만 받아요(`csrc/array/ops/dlpack.cpp`).

### 헤더 없이 ABI를 직접 적어요

DLPack 1.0의 C 구조체(`DLTensor`, `DLManagedTensor`, `DLManagedTensorVersioned` 등)는 소스에 직접 적어요. `dlpack.h` 헤더 파일을 저장소에 들이지(vendor) 않고, 같은 메모리 배치의 구조체를 선언해요. 버전 있는 capsule `"dltensor_versioned"`와 옛 capsule `"dltensor"`를 둘 다 읽고 써요.

### 가져오는 순서

1. `x.__dlpack__(max_version=(1, 0), copy=...)`을 불러요. 생산자가 키워드를 모르는 옛 구현이라 `TypeError`가 나면 인자 없이 다시 불러요. 속성 이름, 키워드 이름, 버전 tuple은 처음 한 번 만들어 두고, 속성은 한 번씩만 찾고, 호출은 vectorcall이에요([Python과 C++의 경계](/internals/core/python-boundary/)). 정확한 numpy 배열은 이 단계 전에 `asarray`와 같은 공유(`share_numpy_array`)를 먼저 해 봐요. `__dlpack__`이 설명할 뷰와 같은 뷰이고, `base`가 capsule 대신 numpy 배열이에요.
2. capsule 이름을 `"used_dltensor_versioned"`(또는 `"used_dltensor"`)로 바꿔요. 규약상 이것이 "소비자가 가져갔다"는 표시예요.
3. 곧바로 소유권을 가져와요. 텐서 포인터를 담은 새 capsule(`"sd_dlpack_owner"`)을 만들고, 그 capsule의 소멸자가 생산자의 `deleter`를 부르게 해요. capsule을 만들지 못하면 그 자리에서 `deleter`를 부르고 에러를 내요.
4. 그다음에 검사해요. 버전의 major가 1보다 크거나 장치가 CPU가 아니면 `BufferError`, dtype이 넷 중 하나가 아니면 `TypeError`, 0차원이거나 32차원을 넘으면 `ValueError`예요.

소유권을 검사보다 먼저 가져오는 이유는 누수를 막기 위해서예요. 이름을 바꾼 뒤에는 텐서를 놓아 줄 책임이 소비자에게 있어요. 검사를 먼저 하고 에러를 던지면 그 텐서는 아무도 놓지 않아요. 소유권을 먼저 owner capsule에 넘겨 두면, 어느 검사에서 예외가 나든 owner가 소멸하면서 `deleter`가 불려요.

### 배열로 바꾸기

- DLPack의 strides는 원소 단위이고, stardust는 바이트 단위라 itemsize를 곱해요. strides가 null이면 C 연속이라는 뜻이라 직접 계산해요.
- `data`에 `byte_offset`을 더한 곳이 첫 원소예요.
- 만든 배열의 `buffer`는 비어 있고, `base`가 owner capsule이에요. 메모리는 owner capsule이 살아 있는 동안 유지되고, 배열이 사라지면 capsule이 사라지며 생산자의 `deleter`가 불려요.
- 버전 있는 형식의 `READ_ONLY` 표시는 `writeable = false`가 돼요.
- 정렬과 bool 바이트 규칙은 버퍼 프로토콜과 같아요. 어긋나면 복사하는데, 이 경우의 복사본은 원본의 메모리 순서가 아니라 C 순서로 만들어요(바이트 단위 복사, bool은 0/1로 정규화).
- `copy=True`: 생산자가 "복사했음"(`IS_COPIED`) 표시를 달았으면 다시 복사하지 않아요. 표시가 없으면(옛 형식 등) stardust가 복사해요.

### 내보내기

`ndarray.__dlpack__`은 배열의 뷰(Buffer와 base를 붙잡아요)와 원소 단위 shape·strides 벡터를 담은 `Export` 구조체를 `manager_ctx`에 넣어요. `deleter`는 소비자가 어느 스레드에서든 부를 수 있어서, GIL을 잡은 뒤 `Export`를 지워요(뷰가 Python 참조를 붙잡고 있으니까요). 아무도 가져가지 않은 capsule은 capsule 소멸자가 `deleter`를 불러요.

쓰기 금지 배열은 버전 있는 형식의 `READ_ONLY` 표시로 내보내요. 옛 형식에는 그 표시를 담을 자리가 없어서 `BufferError`예요(numpy도 같은 이유로 거부해요). `copy=True`로 내보내면 복사본에 `IS_COPIED` 표시를 달아요.

## 명시적 변환

### 규칙 하나, 함수 하나

`astype`, 생성 함수의 `dtype=` 인자, 버퍼 가져오기가 모두 같은 규칙을 써요. `dtype=`을 주는 것은 명시적 변환이라, 손실이 있어도 `astype`처럼 변환해요(`asarray([1.5], dtype=sd.int64)`는 `[1]`).

| 원천 \ 대상 | bool | int64 | float64 | complex128 |
|---|---|---|---|---|
| **bool** | 그대로 | 0 / 1 | 0.0 / 1.0 | (0, 0) / (1, 0) |
| **int64** | `x != 0` | 그대로 | 가장 가까운 float64 | (가까운 float64, 0) |
| **float64** | `x != 0` (NaN은 True) | 0 방향 자르기, 포화, NaN → 0 | 그대로 | (x, 0) |
| **complex128** | 실수부나 허수부가 0이 아니면 True | `TypeError` | `TypeError` | 그대로 |

원소 하나의 변환은 템플릿 함수 하나예요.

```cpp
// csrc/array/convert.hpp (발췌)
template <typename To, typename From>
To cast_value(From v) {
    if constexpr (std::is_same_v<To, bool>) {
        if constexpr (is_complex_v<From>) return v.real() != 0 || v.imag() != 0;
        else return v != From(0);
    } else if constexpr (is_complex_v<To>) {
        if constexpr (is_complex_v<From>) return To(static_cast<double>(v.real()), static_cast<double>(v.imag()));
        else return To(static_cast<double>(v), 0.0);
    } else if constexpr (is_complex_v<From>) {
        // Instantiated by generic dtype x dtype loops but never reached:
        // check_castable rejects complex -> real before any element is touched.
        check_castable(DType::Complex128, dtype_of<To>);
        __builtin_unreachable();
    } else if constexpr (std::is_same_v<To, std::int64_t> && std::is_floating_point_v<From>) {
        return saturate_to_int64(static_cast<double>(v));
    } else {
        return static_cast<To>(v);
    }
}
```

- `From`은 배열의 저장 타입 넷뿐 아니라 버퍼 가져오기에서 만나는 `int16`, `float` 같은 좁은 타입도 될 수 있어요. 그래서 템플릿이에요.
- complex → 실수는 dtype 단계에서 막아요(`check_castable`, `TypeError: cannot convert complex128 to float64: the imaginary part would be lost`). 실수부가 필요하면 `real(x)`를 쓰면 돼요. 원소 단계의 함수는 실패하지 않으므로, 루프에 에러 검사가 들어가지 않아요.
- `__builtin_unreachable()`은 "이 가지는 실행되지 않는다"고 컴파일러에 알려 줘요. `cast_loop<complex128, double>` 같은 표의 칸은 표를 꽉 채우려고 인스턴스화되지만 실제로 선택되지 않아요.
- int64 → float64는 `static_cast<double>`이에요. $|x| \le 2^{53}$이면 정확하고, 그보다 크면 가장 가까운 float64로 반올림돼요(ARM의 `SCVTF` 명령이 기본 반올림 모드인 round-to-nearest-even으로 바꿔요). C++에서 이 변환은 정의된 동작이에요. numpy와 비트가 같아요.
- X → bool은 `x != 0`이에요. NaN은 0과 같지 않으므로 True예요. `-0.0`은 0과 같으므로 False예요.

### 캐스트 커널 표

배열 전체를 변환할 때는 `(원천, 대상)` 쌍마다 1차원 루프 하나가 있는 4×4 표를 써요(`csrc/array/kernels/cast.hpp`). 원소별 연산과 같은 커널 형태(`Loop`)라 같은 nd 이터레이터와 스레드풀 위에서 돌아요.

```cpp
// csrc/array/kernels/cast.hpp (발췌)
template <typename From, typename To>
void cast_loop(std::byte* const* args, std::int64_t n, const std::int64_t* strides, void*) {
    if (strides[0] == sizeof(From) && strides[1] == sizeof(To)) {  // contiguous
        if constexpr (std::is_same_v<From, To>) {
            // ...
            std::memcpy(args[1], args[0], static_cast<size_t>(n) * sizeof(To));
            return;
        }
        const From* src = reinterpret_cast<const From*>(args[0]);
        To* dst = reinterpret_cast<To*>(args[1]);
        std::int64_t i = 0;
        if constexpr (std::is_same_v<From, double> && std::is_same_v<To, std::int64_t>) {
            // ...
            for (; i + 4 <= n; i += 4) {
                vst1q_s64(dst + i, vcvtq_s64_f64(vld1q_f64(src + i)));
                vst1q_s64(dst + i + 2, vcvtq_s64_f64(vld1q_f64(src + i + 2)));
            }
        }
        for (; i < n; ++i) dst[i] = cast_value<To>(src[i]);
        return;
    }
    // ...
}
```

- 연속 구간은 인덱스로 접근하는 루프라 컴파일러가 벡터화할 수 있어요. 바이트 stride를 더해 가는 루프는 벡터화되지 않아요([원소별 커널](/internals/array/elementwise/)).
- 같은 타입의 연속 복사(표의 대각선, `x.copy()`)는 `memcpy`예요. OS가 칩에 맞춰 튜닝한 함수라 가장 넓은 load/store를 써요. 원소 100만 개의 `x.copy()`가 원소별 대입 루프로는 118µs, `memcpy`로는 94µs이고, numpy와 같아요.
- float → int64만 NEON intrinsic을 직접 써요. 다음 절에서 이유를 설명해요.
- 표는 `cast_row<From>`을 넷 쌓은 `inline constexpr` 배열이고, `cast_kernel(from, to)`가 인덱스 두 개로 꺼내요.

`astype`은 같은 dtype이고 `copy`가 `True`가 아니면 같은 객체를 그대로 돌려주고, 그 밖에는 `new_array_like`로 원본의 메모리 축 순서를 따르는 새 배열을 만들어 이 커널로 채워요. 기본값이 `copy=True`라서 따로 지정하지 않으면 항상 복사해요.

### float → int64: 정의된 동작이면서 빠르게

규칙은 0 방향으로 자르고, 범위를 벗어나면 포화시키고, NaN은 0으로 바꾸는 거예요.

$$
\operatorname{cvt}(x) =
\begin{cases}
0 & x \text{가 NaN} \\
2^{63} - 1 & x \ge 2^{63} \;(+\infty \text{ 포함}) \\
-2^{63} & x \le -2^{63} \;(-\infty \text{ 포함}) \\
\operatorname{trunc}(x) & \text{그 밖}
\end{cases}
$$

```python
>>> sd.asarray([1.5, -2.7, float('nan'), 1e300, -float('inf')]).astype(sd.int64)
array([                   1,                   -2,                    0,
        9223372036854775807, -9223372036854775808], dtype=int64)
```

평범한 C++ 캐스트는 쓸 수 없어요. `static_cast<std::int64_t>(x)`는 C++ 표준에서 "자른 값이 대상 타입으로 표현될 수 없으면 동작이 정의되지 않는다"고 정해져 있어요(`[conv.fpint]`) [6]. NaN, $\pm\infty$, $|x| \ge 2^{63}$이 모두 여기에 해당해요. 정의되지 않은 동작이면 컴파일러는 그런 입력이 없다고 가정해도 되고, 결과는 플랫폼과 최적화 수준에 따라 달라질 수 있어요. 실제로 x86의 `CVTTSD2SI` 명령은 이런 입력에 모두 $-2^{63}$("integer indefinite" 값)을 내요 [7]. numpy는 이 캐스트를 C로 하고, 잘못된 값이면 `RuntimeWarning: invalid value encountered in cast`를 내요. arm64 macOS의 numpy 2.5.4에서는 위 예와 같은 값이 나오지만 경고가 함께 떠요.

stardust는 이런 입력에도 값을 하나로 정해요. NaN → 0, 포화예요. 원소 단계의 변환이 실패하거나 경고를 내지 않아야 변환 커널에 에러 경로가 없어서 컴파일러가 루프를 벡터화할 수 있고, 같은 입력이 플랫폼과 최적화 수준에 상관없이 같은 값을 내요.

규칙을 그대로 코드로 옮기면 분기가 셋 생기고, 이 코드는 느려요.

```cpp
// 규칙을 그대로 적은 코드 (설명용으로 줄임): 정의된 동작이지만 벡터화되지 않는다
if (std::isnan(x)) return 0;
if (x >= 0x1p63) return INT64_MAX;
if (x < -0x1p63) return INT64_MIN;
return static_cast<std::int64_t>(x);   // 여기서는 범위 안이라 정의된 동작
```

정의된 동작이지만 clang은 이 루프를 벡터화하지 못해요. 이렇게 짜면 원소 100만 개 `astype` float → int64가 1스레드 464µs로, numpy(243µs)보다 느려요.

ARM에는 이 규칙을 그대로 수행하는 명령이 있어요. AArch64의 `FCVTZS`(Floating-point Convert to Signed integer, rounding toward Zero)는 0 방향으로 자르고, 범위를 벗어나면 가장 가까운 표현 가능한 값으로 포화시키고, NaN이면 0을 내요 [8]. 규칙이 정확히 같으니 명령을 직접 불러요.

```cpp
// csrc/base/saturate.hpp
#include <arm_neon.h>
// ...
inline std::int64_t saturate_to_int64(double x) { return vcvtd_s64_f64(x); }
```

- `vcvtd_s64_f64`는 스칼라 `FCVTZS` 하나로 컴파일되는 ACLE(Arm C Language Extensions) intrinsic이에요 [9]. intrinsic은 C++ 함수처럼 보이지만 명령 하나로 바뀌므로, C++의 캐스트 규칙이 아니라 명령의 정의를 따라요. 그래서 NaN과 범위 밖 값에서도 정의된 결과예요.
- 이 함수를 원소마다 부르는 루프는 컴파일러가 벡터 `FCVTZS`(128비트 레지스터에 두 개씩)로 바꿔요. 분기가 없으니 벡터화를 막는 것이 없어요.
- 연속 캐스트 루프는 벡터판 `vcvtq_s64_f64`를 직접 쓰고, 한 번에 레지스터 두 개(원소 4개)씩 처리해 load를 더 많이 겹쳐 띄워요.
- 이 함수는 배열, linalg, frame이 함께 써요. frame의 `astype`도 같은 규칙(포화, NaN → 0)을 따르므로 공통 기반(`csrc/base/`)에 있어요.

명령 하나로 하면 89µs로, 분기 셋으로 쓴 루프(464µs)보다 5배 넘게 빠르고 numpy(243µs)보다도 빨라요.

<Callout type="note" title="이식성">
  이 구현은 ARM의 `FCVTZS` 의미에 기대요. stardust의 대상은 Apple silicon Mac 하나이고 런타임 CPU 디스패치를 하지 않아요. 다른 아키텍처로 옮긴다면 같은 규칙을 그 아키텍처의 명령이나 분기 없는 선택(select)으로 다시 써야 해요. 규칙 자체는 `saturate_to_int64` 한 함수에 모여 있어요.
</Callout>

## 암묵적 변환 검사

### 위로만

대입(`x[...] = v`), `out=`, 제자리 연산자(`x += y`), `dtype=` 없는 `full_like`의 채움 값, `clip`의 `min`/`max`는 승격 순서의 위로만 변환해요. 아래로 가면 `TypeError`예요.

```cpp
// csrc/array/ops/copy.cpp
void check_assignable(DType from, DType to) {
    if (from > to) {
        std::string msg = std::string("cannot implicitly convert ") + dtype_name(from) + " to " + dtype_name(to) +
                          " (that would lose information); convert explicitly with astype";
        throw nb::type_error(msg.c_str());
    }
}
```

```python
>>> x = sd.arange(3)
>>> x += 1.5
Traceback (most recent call last):
    ...
TypeError: cannot implicitly convert float64 to int64 (that would lose information); convert explicitly with astype
```

- dtype만 보고 판정해요. `int_arr[0] = 2.0`도 `TypeError`예요. 값을 보고 판단하면(2.0은 되고 1.5는 안 되고) 같은 코드가 데이터에 따라 성공하기도 하고 실패하기도 해요. 비용은 enum 비교 한 번이에요. frame도 같은 규칙이에요.
- `out=`에서는 루프의 출력 dtype과 `out`의 dtype을 비교해요. `sd.add(int_arr, int_arr, out=float_arr)`는 int64 결과를 float64로 올리는 것이라 괜찮아요.
- `full_like(int_arr, 1.5)`는 `int_arr[...] = 1.5`와 같은 일이라 `TypeError`예요. `dtype=`을 주면 `full`처럼 명시적 변환이에요.
- `clip`은 x의 dtype을 유지해요(Array API). 그래서 `min`/`max`가 x의 dtype으로 암묵적으로 변환될 수 있어야 해요.
- 쓰기 금지 배열 검사(`ValueError`)도 같은 자리에서 해요(`assign_checked`).

### 넓은 `out=`

`out=`가 결과보다 넓은 dtype이면 결과 dtype의 새 배열에 먼저 계산한 뒤 `assign`으로 `out`에 변환해 넣어요. 메모리를 한 번 더 지나지만 경로가 단순하고, 새 배열은 입력과 겹칠 수 없으니 겹침 처리도 따로 필요 없어요([데이터 모델](/internals/array/data-model/)). 버퍼 단위 캐스팅은 입력에만 하고 출력에는 하지 않아요.

## Python int의 int64 범위 검사

### 언제 검사하나

Python int는 크기 제한이 없지만 int64는 $[-2^{63}, 2^{63}-1]$이에요. 규칙은 하나예요. int64로 바꿔야 할 때만 `OverflowError`가 나요.

| 식 | 결과 | 이유 |
|---|---|---|
| `int_arr + 2**70` | `OverflowError` | 승격한 피연산자 dtype이 int64 |
| `float_arr + 2**70` | float64로 계산 | 승격한 dtype이 float64라 int를 float로 읽어요 |
| `divide(int_arr, 2**64)` | `OverflowError` | 루프는 float64지만, 승격한 피연산자 dtype은 int64 |
| `sqrt(2**64)` | `OverflowError` | 같은 이유 |
| `asarray([2**70, 0.5])` | float64 | 종류가 float64로 승격 |
| `asarray([2**70])` | `OverflowError` | int64로 저장해야 해요 |
| `asarray([10**400, 0.5])` | `OverflowError` | float64로도 담을 수 없어요 |
| `float_arr * 10**400` | `OverflowError` | 같은 이유(연산자라 메시지에 함수 이름이 없어요) |

ufunc에서는 루프 dtype이 아니라 승격한 피연산자 dtype으로 판정해요(`check_int_scalars`). 루프 dtype으로 판정하면 `divide`의 루프가 float64라서 `divide(int_arr, 2**64)`만 정상이 되고, 다른 이항 함수(`add`, `multiply` …)와 어긋나요. 그래서 승격한 dtype이 bool이나 int64이면 어느 루프로 계산하든 int를 int64로 봐요. frame도 같은 규칙이에요.

```cpp
// csrc/array/ops/ufunc.cpp (발췌)
void check_int_scalars(std::span<const nb::handle> objs, DType promoted) {
    if (promoted > DType::Int64) return;
    for (nb::handle o : objs)
        if (!is_ndarray(o) && scalar_dtype(o) == DType::Int64) (void)scalar_from_python<std::int64_t>(o, DType::Int64);
}
```

### 어떻게 검사하나

```cpp
// csrc/array/convert.cpp (발췌)
std::int64_t py_to_int64(PyObject* p) {
    int overflow = 0;
    long long v = PyLong_AsLongLongAndOverflow(p, &overflow);
    if (overflow != 0) throw std::overflow_error("Python int too large to convert to int64");
    if (v == -1 && PyErr_Occurred()) throw nb::python_error();
    return v;
}
```

- CPython의 `PyLong_AsLongLongAndOverflow` [10]는 범위를 벗어나면 예외를 설정하지 않고 `overflow` 플래그만 ±1로 돌려줘요. 정상 경로에서 예외 객체를 만들었다 지우는 비용이 없고, 범위 밖일 때 stardust의 메시지로 된 `OverflowError`를 바로 던질 수 있어요. `std::overflow_error`는 nanobind가 Python의 `OverflowError`로 바꿔요.
- float로 읽을 때는 `PyFloat_AsDouble`(int에도 동작)을 써요. float64로도 표현할 수 없을 만큼 큰 int(약 $1.8 \times 10^{308}$ 이상)이면 CPython이 이름 없는 `OverflowError`를 설정하는데, `py_to_double`이 그것을 지우고 `std::overflow_error("Python int too large to convert to float64")`를 던져요. int64 쪽과 같은 꼴이라 바인딩이 함수 이름을 붙여요(`asarray(): Python int too large to convert to float64`).

```cpp
// csrc/array/convert.cpp (발췌)
double py_to_double(PyObject* p) {
    double v = PyFloat_AsDouble(p);  // works for int too
    if (v == -1.0 && PyErr_Occurred()) {
        if (!PyErr_ExceptionMatches(PyExc_OverflowError)) throw nb::python_error();
        PyErr_Clear();  // an int beyond the double range: ours, so that the function's name is added
        throw std::overflow_error("Python int too large to convert to float64");
    }
    return v;
}
```

이름 붙은 int 인자(`shape`, `axis`, `k`, `num`)도 범위 밖이면 `OverflowError`예요. 이쪽은 `operator.index` 규칙으로 읽는 `index_value`/`parse_int`가 맡아요([Python과 C++의 경계](/internals/core/python-boundary/)).

## 성능

| 작업 | 시간 복잡도 | 추가 메모리 | 비고 |
|---|---|---|---|
| 승격, 루프 선택 | $O(1)$ | 없음 | enum 비교와 표 네 칸 |
| 암묵적 변환 검사 | $O(1)$ | 없음 | dtype만 봐요 |
| 중첩 시퀀스 | $O(N + M)$ (두 번 방문) | $O(\text{ndim})$ | 재귀 깊이 33 이하 |
| 버퍼 공유 | $O(\text{ndim})$, bool이면 $O(n)$ 검사 | 없음 | bool 검사 100만 개 8.3µs |
| 버퍼 복사·넓히기 (연속, 어느 바이트 순서든) | $O(n)$, 병렬 | 결과 배열 | 평탄한 루프 (int32 → int64 100만 개 60µs, numpy `astype` 99µs) |
| 버퍼 복사·넓히기 (연속이 아님) | $O(n)$, 병렬. 축 정렬 $O(\text{ndim} \log \text{ndim})$, 조각마다 시작점 계산 $O(\text{ndim})$ | 결과 배열 | 결과의 메모리 순서로 odometer. 안쪽 축이 붙어 있으면 인덱스 루프가 벡터화돼요 |
| numpy 배열 공유 (`asarray`, `from_dlpack`) | $O(\text{ndim})$, bool이면 $O(n)$ 검사 | 없음 | 버퍼 프로토콜도 DLPack 생산자도 거치지 않아요 |
| DLPack 공유 | $O(\text{ndim})$, bool이면 $O(n \cdot \text{ndim})$ 검사 | 없음 | |
| `astype` | $O(n)$, 병렬 | 결과 배열 | 연속 f → i는 벡터 `FCVTZS` |

- `astype` f → int64가 numpy보다 빠른 이유는 분기 없는 `FCVTZS` 하나로 변환하기 때문이에요(위 "float → int64" 절).
- `f * i + g`가 빠른 이유는 int64 → float64 변환을 4096원소 버퍼로 하면서 바로 계산해, 변환 결과를 메모리에 다시 쓰지 않기 때문이에요(1스레드 397µs, numpy 635µs, [연산 엔진](/internals/array/engine/)).
- DLPack의 bool 검사는 원소마다 오프셋을 처음부터 다시 계산하는 단순한 순회라 $O(n \cdot \text{ndim})$이에요. 버퍼 프로토콜 쪽은 C 연속이면 평탄한 OR 루프를 써요.
- 버퍼 프로토콜의 복사 경로는 위 "복사하는 경로의 속도"에, 복사 없는 공유의 고정 비용은 "복사 없이 공유하는 비용"에 있어요. `from_dlpack`의 고정 비용은 [Python과 C++의 경계](/internals/core/python-boundary/)에서 다뤄요.

## 정확도

- 넓히기(int8–uint32 → int64, float16/32 → float64, complex64 → complex128, bool → 무엇이든)는 모두 정확해요.
- int64 → float64는 round-to-nearest-even 한 번이에요. $|x| \le 2^{53}$이면 정확해요. numpy와 비트가 같아요.
- float64 → int64는 위 식 그대로예요. 범위 안의 유한한 값은 numpy와 같은 값이에요(둘 다 0 방향 자르기). NaN, $\pm\infty$, 범위 밖 값은 stardust에서 NaN → 0, 포화이고, numpy는 C에서 정의되지 않은 동작이라 플랫폼에 따라 값이 다르고 경고를 내요.
- X → bool은 `x != 0`이라 반올림이 없어요. NaN은 True, `-0.0`은 False예요.
- Python 스칼라: int → float64는 CPython의 변환(`PyFloat_AsDouble`)을 그대로 써요. float → float64는 그대로 복사예요.
- 버퍼 단위 캐스팅으로 변환한 값은 같은 `cast_value`를 거치므로, 미리 전체를 변환한 경우와 비트가 같아요.
