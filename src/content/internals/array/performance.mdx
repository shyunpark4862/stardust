export const lin = (pts) => (x) => {
  for (let i = 1; i < pts.length; i++) {
    const [x0, y0] = pts[i - 1];
    const [x1, y1] = pts[i];
    if (x >= x0 && x <= x1) return y0 + ((y1 - y0) * (x - x0)) / (x1 - x0);
  }
  return NaN;
};

## 한눈에 보기

이 페이지는 배열 영역(`sd`) 전체의 성능을 numpy와 비교해요. 거의 모든 공개 함수를 세 크기(원소 3개, 1만 개, 100만 개, 일부는 1천·10만·1천만 개)와 여러 레이아웃(연속, strided(원소를 건너뛰며 읽는 뷰), 전치, 브로드캐스트), 여러 dtype으로 잰 380개 경우예요. 측정 스크립트는 `bench/array/full_scan.py`이고, 결과 표는 `bench/array/full_scan/full_scan.md`예요.

| 항목 | 값 |
|---|:---:|
| 경우 | 380 |
| 1스레드에서 numpy보다 느린 줄 | 73 |
| 10스레드(기본값)에서도 느린 줄 | 34 |
| 결과가 numpy와 다른 줄 | 0 |

느린 73줄은 네 갈래로 나뉘어요. 자세한 내용은 아래 "느린 줄" 절에 있어요.

1. 측정의 흔들림이에요. 메모리에 묶인 단순한 연산은 라운드마다 두 값 중 하나로 떨어지고, 가장 빠른 값을 고르는 방식 때문에 이것이 배율 차이로 보여요. 0.95~1.00배 줄 대부분과 complex 덧셈(0.83배)이 여기에 들어요.
2. 같은 일의 비교가 아니에요. `np.asarray(numpy 배열)`은 같은 객체를 그대로 돌려주는 12ns짜리 일이고, `sd.asarray(numpy 배열)`은 새 배열 객체를 만드는 일이에요.
3. 설계상의 대가예요. scatter는 쓰기 전에 모든 인덱스를 검사하고(전부 아니면 전무), `acosh`는 입력과 무관하게 vForce를 쓰고, `argsort`의 기본은 안정 정렬이에요.
4. 작은 배열 호출의 고정 비용이에요. 결과 배열 객체 하나를 만드는 데 numpy보다 15~20ns 더 들어요. 뷰, `zeros(3)`, 원소 3개 연산이 0.5~0.85배예요. 최대 32차원을 지키는 대가로 받아들이는 비용이고, 이유는 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

빠른 이유는 크게 다섯 가지로 묶여요.

1. 같은 일을 더 적은 메모리 왕복으로 해요. 버퍼 단위 캐스팅, `var`의 두 번째 패스를 커널 하나로, `nansum`의 NaN을 접근자에서 0으로([연산 엔진](/internals/array/engine/), [집계](/internals/array/reductions/)).
2. 의존 사슬을 끊어요. 누적 합의 블록 스캔, `prod`의 다중 누산기, 손으로 짠 NEON([집계](/internals/array/reductions/), [원소별 커널](/internals/array/elementwise/)).
3. 분기를 없애요. 마스크의 분기 없는 압축, `where`의 비트 마스크 선택, 정렬 네트워크([인덱싱](/internals/array/indexing/), [정렬과 집합](/internals/array/sorting/)).
4. 더 빠른 라이브러리나 알고리즘을 골라요. vForce 초월함수, int64와 float64 (값, 인덱스) 쌍의 기수 정렬([원소별 커널](/internals/array/elementwise/), [정렬과 집합](/internals/array/sorting/)).
5. 스레드를 써요. numpy는 BLAS를 빼면 한 스레드로 돌아요. stardust는 기본 10스레드이고, 결과는 스레드 수와 상관없이 비트까지 같아요([스레드풀과 결정성](/internals/core/threads/)).

## 측정 방법

### 기계와 버전

| 항목 | 값 |
|---|---|
| 기계 | Apple M4 Pro (arm64 macOS, P코어 10 + E코어 4) |
| 캐시 | 캐시 라인 128B, 페이지 16KB, P코어 L1d 128KB, L2 16MB(코어 5개가 공유, 클러스터 2개) |
| SIMD | NEON 128비트 (float64·int64는 2개, complex128은 1개) |
| Python | 3.15.0 |
| numpy | 2.5.4, BLAS·LAPACK은 Accelerate (`np.show_config()` 기준). 그대로 실행해요(BLAS를 빼면 1스레드) |
| stardust | 1스레드, 그리고 기본값 10스레드(P코어 수) |

### 방법

- 데이터: 따로 적지 않으면 원소 100만 개예요. `f`, `g`는 $[0.5, 1.5)$의 균등 난수, `fs`는 표준정규분포(양쪽 부호), `i`는 $[-1000, 1000)$의 int64, `b`는 절반이 True인 bool, `c`는 complex128, `f2`, `g2`는 1000×1000, `ft`는 `f2.T`(F 순서 뷰), `fst`는 200만 개 배열의 `[::2]`, `idx`는 인덱스 10만 개, `idxn`은 100만 개예요. 두 라이브러리에 같은 값을 넣어요(numpy 배열과 그 복사로 만든 stardust 배열).
- 결과 확인: 시간을 재기 전에 경우마다 양쪽을 한 번씩 실행해 결과를 비교해요(shape, dtype 종류, 값; NaN은 같다고 봐요). 그래서 빠른 줄이 다른 답을 숨길 수 없어요. 380개 모두 같아요. 대입문처럼 값을 돌려주지 않는 경우는 대입 뒤의 배열을 비교해요. 이 대조는 이 측정 스크립트의 것이에요. 모든 영역이 함께 쓰는 [속도 측정](/internals/core/benchmarks/) 체계는 결과를 비교하지 않고 시간만 재요. 결과가 맞는지는 테스트가 맡아요.
- 시간: 경우마다 적어도 20ms 걸리는 반복 루프를 7번 재서 가장 빠른 값을 골라요. 380개 전체를 이렇게 한 바퀴 도는 것이 **라운드**이고, 라운드를 10번 되풀이해 라운드 사이의 최솟값을 잡아요. 라운드는 시간에 걸쳐 흩어져 있어서, 배경 작업이 한때 몰려도 한 라운드만 손해를 보고 최솟값은 지켜져요. 10라운드에 46분이 걸려요.
- 배율: numpy 시간 ÷ stardust 시간이에요. 1보다 크면 stardust가 빨라요. 막대그래프의 시간은 [numpy, stardust 1스레드, stardust 10스레드] 순서예요.

### 해석할 때의 함정

- 캐시 크기: 원소 100만 개(8MB)는 L2(16MB)에 상당 부분 남아요. 그래서 메모리에 묶인 연산은 이 크기에서 실제 DRAM 대역폭보다 빠르게 보이고, 스레드 확장성도 다르게 나와요. 크기별 줄(1천~1천만 개)과 아래 "스레드 확장성"의 400만 개 측정을 같이 봐요.
- 새 메모리의 첫 쓰기: 결과는 언제나 새 배열에 쓰므로, 새로 받은 페이지에 처음 쓸 때 페이지 폴트가 나요(페이지 16KB). 이 측정은 매번 새 결과를 만드는 실제 상황 그대로예요.
- 두 갈래로 떨어지는 시간: 메모리에 묶인 단순한 연산은 같은 경우라도 라운드마다 두 값 중 하나가 나와요(아래 "측정의 흔들림"). 그래서 이런 연산의 0.9~1.2배 차이는 "같음"으로 읽어요.
- 코드 주소: 짧고 뜨거운 루프는 64바이트 명령 인출 블록 경계에 따라 1.7배까지 갈려요([행렬곱](/internals/array/matmul/)의 int64 루프).
- 워커가 깨어 있는 상태: 같은 연산을 연달아 부르므로 풀의 워커가 spin 중이에요. 실제 코드에서 병렬 호출 사이에 100µs 넘게 쉬면 워커가 잠들고, 다음 호출이 깨우는 비용(macOS에서 작업당 수십 µs)을 내요([스레드풀과 결정성](/internals/core/threads/)).

작은 배열은 두 갈래로 갈려요.

- Python 숫자나 이미 있는 객체를 돌려주는 호출은 빨라요. `sum`, `mean`, `max`는 6~10배예요. numpy의 이 함수들은 Python 코드를 거치고, stardust는 인자 해석부터 결과까지 C++ 함수 하나예요. `finfo`는 결과(불변 namedtuple)를 한 번 만들어 공유해요. `x.shape`와 `len(x)`는 nanobind의 함수 호출 경로를 거치지 않는 타입 슬롯으로 등록해서 numpy와 같아요(19ns 대 18ns, 7ns 대 7ns).
- 새 배열 객체를 돌려주는 호출은 느려요. 원소 3개 덧셈, `zeros(3)`, 뷰를 만드는 인덱싱이 0.5~0.85배예요. 아래 "작은 배열의 고정 비용"에서 설명해요.

자세한 메커니즘은 [작은 배열의 호출 비용](/internals/array/small-arrays/)과 [Python과 C++의 경계](/internals/core/python-boundary/)에 있어요.

## 느린 줄

1스레드에서 numpy보다 느린 73줄을 원인별로 나누면 이래요. 표의 배율은 1스레드, 괄호 안은 10스레드예요.

### 측정의 흔들림

메모리를 한 번 지나가는 단순한 연산은 같은 경우라도 라운드마다 두 값 중 하나로 떨어져요. 라운드별 기록에서 이렇게 보여요.

| 메모리 이동 | 낮은 값 | 높은 값 | 예 |
|---|:---:|:---:|---|
| 입력 하나, 출력 하나 (16MB) | 약 94µs | 약 132µs | `abs`, `floor`, `square`, int64 `abs` |
| 입력 둘, 출력 하나 (24MB) | 약 147µs | 약 202µs | `add`, `subtract`, `maximum`, int64 `add`·`bitwise_xor`·`bitwise_left_shift` |
| complex 입력 둘, 출력 하나 (48MB) | 약 320~330µs | 약 406µs | complex `add`, `multiply` |

어느 값이 나오는지는 라이브러리가 아니라 라운드에 따라 달라져요. 예를 들어 complex `add`는 numpy가 10라운드 중 2번 320µs대를 얻었고 나머지 8번은 406µs였는데, stardust 1스레드는 한 번 388µs, 나머지는 406µs였어요. 라운드 최솟값을 쓰므로 0.83배로 보여요. 같은 현상이 반대쪽으로도 나와요. float64 `add`는 numpy가 9번 202µs, stardust가 대부분 151µs여서 1.17배로 보여요. 두 값으로 갈리는 원인은 아직 밝히지 못했어요.

그래서 이런 줄의 0.83~1.17배는 같은 커널의 같은 속도로 읽어요. 이 갈래에 드는 느린 줄은 complex `add`(0.83×), complex `multiply`(0.99×), int64 `add`·`bitwise_xor`·`bitwise_left_shift`(0.95~0.99×), `maximum`·`subtract`(0.99~1.00×), int64 `abs`(0.98×), `astype(f, complex128)`(0.97×, 158µs와 195µs로 갈려요)예요.

두 값으로 갈리지 않으면서 numpy와 1~5% 차이인 줄도 있어요. `zeros(N)`, `zeros((1000, 1000))`, `full_like`, `arange`(0.96~1.00×)는 첫 라운드를 빼면 라운드마다 numpy와 같은 값이에요. `isnan`, `floor`, `expm1`, `log1p`, `searchsorted(srt, f)`, `fw[:] = g`, `fw[::2] = 1.0`, `matmul(f2, v)`, 크기별 `i + j`·`copy`·`sum`(1.00×이고 소수점 셋째 자리에서 1 아래)은 같은 명령이나 같은 libm, 같은 BLAS를 쓰는 줄이에요. 바깥 축 리덕션(`sum`, `mean`, `max`의 `axis=0`, 0.98~0.99×)과 strided `sum`(0.96×), `concat(axis=1)`·`roll(axis=1)`·`tile`(0.95~0.96×), 겹치는 `x[1:] += x[:-1]`(0.96×), `nanquantile`(0.96×), 연속 `asarray` 넓히기(0.98~0.99×)는 라운드마다 꾸준히 2~5% 느려요. 10스레드에서는 모두 numpy보다 2~5배 빨라요.

### 같은 일의 비교가 아닌 줄

| 연산 | 1스레드 | 무엇을 비교하나 |
|---|:---:|---|
| `sd.asarray(numpy 배열)` (연속, strided, 전치) | 0.08~0.09× | numpy 쪽은 `np.asarray(numpy 배열)`이라 이미 numpy 배열인 입력을 그대로 돌려줘요(12ns). stardust는 버퍼 프로토콜로 남의 메모리를 받아 새 배열 객체를 만들어요(134~147ns). 같은 일인 `sd.asarray(sd 배열)`은 20ns예요 |
| `np.asarray(sd 배열)` | 0.11× | numpy가 남의 객체를 버퍼 프로토콜로 받아 새 numpy 배열을 만드는 비용(110ns)을, numpy 배열을 그대로 돌려주는 12ns와 비교한 값이에요. numpy가 미리 만든 `memoryview`를 받을 때(90ns)와 비슷한 크기예요 |
| `from_dlpack(numpy 배열)` | 0.51× | 양쪽 모두 `__dlpack__`를 부르지만, numpy는 자기 배열의 capsule을 자기 배열로 감싸요. stardust는 속성 조회, `__dlpack_device__` 확인, 소유자 capsule, 새 배열 객체 만들기까지 해요(225ns 대 116ns). 남은 차이의 대부분은 배열 객체 할당이에요 |
| `asarray(s3)` (그대로 돌려주기) | 0.62× | 양쪽 모두 같은 객체를 돌려줘요. 20ns 대 12ns의 차이는 nanobind의 함수 호출 경로와 키워드 인자(`dtype`, `copy`) 해석이에요 |

### 설계상의 대가

앞의 다섯 줄은 다른 것을 얻으려고 치르는 비용이에요. 마지막 두 줄(int64 `sign`, complex `square`)은 원인을 아직 찾지 못한 줄이에요.

| 연산 | 1스레드 | 10스레드 | 원인과 그대로 두는 이유 |
|---|:---:|:---:|---|
| `gz[idx] = 1.0` (scatter) | 0.91×, 0.94× | 1.19×, 1.21× | 쓰기 전에 모든 인덱스를 한 번 검사해요. 범위 밖 인덱스가 하나라도 있으면 아무것도 쓰지 않기(전부 아니면 전무) 위해서예요. 그 덕분에 쓰기 루프에는 에러 경로가 없어요. 반복된 인덱스에서는 마지막 쓰기가 이겨야 하므로 쓰기는 C 순서로 한 스레드에서 해요. 10스레드 이득은 병렬로 나뉘는 검사 패스에서만 나와요 |
| `acosh` | 0.86× | 7.84× | vForce를 써요. vForce의 `acosh`는 입력과 상관없이 거의 일정하고 libm은 입력에 따라 크게 달라져요. 작은 입력에서는 vForce가 빠르고, 큰 입력에서는 libm이 빨라요(`acosh`, $1 + [0, 10^6)$에서 16%). 이 측정의 입력 $[1.5, 2.5)$에서도 libm이 앞서요. 데이터를 보고 경로를 고르지 않으므로 vForce 하나만 써요 |
| `argsort(a)` (1천 개) | 0.86× | 0.86× | numpy의 기본은 안정성을 보장하지 않는 quicksort[2]이고 stardust의 기본은 안정 정렬[3]이에요. 안정 정렬인 float64 쌍의 기수 정렬은 레인마다 자리 카운터(최대 8×256개)를 비우고 누적하는 고정 비용이 있어서, 1천 개에서는 그 비용이 남아요. 1만 개부터는 2배, 100만 개는 6.7배 빨라요 |
| `vecdot(f2, g2)` | 0.86× | 5.90× | 곱을 pairwise 트리로 더해요. 길이 1000인 행마다 트리를 도는 비용이 남아요. 곱은 잎 안에서 합에 융합해요(FMA) |
| `take(f2, rows, axis=0)` | 0.91× | 3.44× | `take`는 키를 만들어 고급 인덱싱의 gather를 불러요. 그래서 `f2[rows]`와 같은 122µs예요. numpy는 `take`에 전용 루프가 있어 111µs이고, numpy의 `f2[rows]`는 158µs예요 |
| int64 `sign` | 0.77× | 3.13× | 연속 int64에서 `a < 0` 마스크와 `a > 0` 마스크의 차를 구하는 NEON 루프(벡터당 명령 셋)예요([원소별 커널](/internals/array/elementwise/)). 125µs 대 97µs로 느리고, 원인은 아직 밝히지 못했어요 |
| complex `square` | 0.94× | 3.94× | 실수부와 허수부를 나눠 싣고 `Square::f`와 같은 FMA를 쓰는 NEON 루프예요. 라운드마다 283µs 대 267µs로 꾸준히 6% 느리고, 원인은 아직 밝히지 못했어요 |

### 작은 배열의 고정 비용

| 연산 | 1스레드 | 시간 (numpy) |
|---|:---:|---|
| 1차원 뷰 `f[1000:2000]`, `f[::2]` | 0.48× | 90ns (43ns) |
| `f2[5]`, `f2[:, 5]`, `sm[1]`, `sm.T`, `sm[1:, ::2]` | 0.46~0.59× | 68~103ns (38~51ns) |
| `zeros(3)`, `empty(3)` | 0.66~0.69× | 86~91ns (59~61ns) |
| `exp(s3)`, `sqrt(s3)`, `s3 + t3s`, `s3 < t3s` | 0.81~0.84× | 149~179ns (121~151ns) |
| `concat([s3, t3s])`, `asarray([1.0, 2.0, 3.0])` | 0.92~0.96× | 143~260ns (137~238ns) |
| `empty(N)` | 0.85× | 130ns (110ns) |
| `unstack(f2)` (뷰 1000개) | 0.75× | 62.4µs (46.7µs) |
| 1천 개 `a + b`, `i + j`, `copy`, 1만 개 `fm + gm` | 0.93~0.99× | 287ns~1.8µs |

모두 계산이 거의 없고, 새 배열 객체를 하나(또는 `unstack`처럼 1000개) 만드는 줄이에요. 시간의 큰 몫은 그 객체의 할당이에요. `NDArray`는 최대 32차원의 shape와 strides를 고정 배열로 안에 둬서 560바이트이고, 이것을 담은 Python 객체는 512바이트를 넘어요. Python의 소형 할당기(pymalloc)는 512바이트까지만 맡으므로 이 객체는 시스템 `malloc`으로 가고, macOS의 `malloc`은 해제할 때 메모리를 0으로 채워요. 이 비용이 호출당 15~20ns예요. `unstack`의 차이 15.7µs도 뷰 1000개에 15.7ns씩이에요. 10스레드에서도 같은 값이라 34개 "10스레드에서도 느린 줄"의 대부분이 여기 있어요.

최대 차원이 24이면 객체가 512바이트 밑으로 내려가 이 비용이 사라져요(`zeros(3)`이 92ns 대신 73ns, `x[::2]`가 88ns 대신 74ns). 그래도 최대 차원 32를 지키고 이 비용을 받아들여요. 이유와 다른 대안은 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

두 종류로 갈려요.

- 메모리에 묶인 연산은 대역폭에서 멈춰요. `f + g`는 400만 개에서 96MB(입력 둘과 출력 하나)를 옮기는데, 1스레드가 이미 초당 약 130GB를 옮겨요. 스레드를 늘려도 1.7배가 한계이고, 12스레드부터는 오히려 떨어져요. 새 결과 배열의 첫 쓰기 페이지 폴트도 이 크기에서는 무시할 수 없어요.
- 계산에 묶인 연산은 거의 코어 수만큼 빨라져요. `argmax`, 행 단위 정렬, int64 matmul은 10스레드에서 7.5~8.5배예요. 원소 100만 개 전체 측정에서도 `exp`는 1스레드의 8.8배(121µs), `sin`은 8.6배(94µs)예요.

그 사이에 있는 연산(`sum`, `var`, `sqrt`, 버퍼 캐스트)은 계산과 메모리가 섞여 10스레드에서 2.4~4.7배에 그쳐요. 버퍼 캐스트(`i + f`)가 2.4배로 가장 낮고, `sum`이 3.5배, `sqrt`가 4.2배, `var`가 4.7배예요.

### 기본 10스레드인 이유

기본 스레드 수는 P코어 수(10)예요(`hw.perflevel0.physicalcpu`). 스레드를 14개(E코어 포함)로 늘리면 계산에 묶인 연산은 5~27% 빨라지고(원소 400만 개에서 1스레드 대비 `sin`이 9.4배에서 10.9배로), 메모리에 묶인 연산은 3~12% 느려져요. 위 표의 `f + g`가 12~14스레드에서 떨어지는 것이 그 예예요. 그래서 기본은 10으로 두고, 계산이 많은 작업이면 `sd.set_num_threads(14)`를 쓰면 돼요. 풀은 태스크를 atomic 카운터에서 동적으로 가져가므로, 느린 E코어가 섞여도 전체가 E코어를 기다리지 않아요. E코어는 태스크를 적게 가져갈 뿐이에요([스레드풀과 결정성](/internals/core/threads/)).

## 작은 크기에서 시간을 정하는 것

배열이 작아지면 시간을 정하는 것이 계산에서 고정 비용으로 바뀌어요. 크기에 따라 세 구간이 있어요.

### 수십~수백 ns: 호출 경로

원소가 몇 개뿐이면 계산은 몇 ns이고, 나머지는 호출 경로의 고정 비용이에요. 주요 비용은 다음과 같아요.

- 결과 배열의 Python 객체 할당. 512바이트를 넘어 시스템 `malloc`으로 가요(위 "작은 배열의 고정 비용").
- 고정 크기 배열의 복사. `NDArray` 하나가 560바이트, 이터레이터(`NdIter`)가 1,600바이트예요. 복사와 이동은 실제 ndim칸만 옮겨요.
- nanobind의 함수 호출 경로 자체는 약 10ns로 작아요.

stardust는 32차원 고정 배열을 두되 필요한 만큼만 만져서 이 비용을 줄여요. 복사는 실제 ndim칸만 하고, 256바이트 이하의 데이터는 Buffer 객체 안에 둬서 할당 세 번을 한 번으로 줄이고, 축 정렬과 shape 해석에는 할당이 없어요. 호출 경로에 Python 코드가 끼지 않는 것은 작은 `sum`이 numpy보다 6배 빠른 이유이기도 해요([Python과 C++의 경계](/internals/core/python-boundary/)).

### 수 µs~수십 µs: 1스레드 구간

일이 `kParallelThreshold` = $2^{15}$(float64 원소 기준, 바이트로 256KB) 미만이면 풀을 쓰지 않고 호출한 스레드에서 GIL을 쥔 채 돌아요. 이 값은 10스레드가 1스레드를 이기기 시작하는 크기에 맞춘 거예요. 이 값 이상이면 스레드 수와 상관없이 GIL을 놓고 돌아요.

| 연산 | 10스레드가 이기기 시작하는 크기 |
|---|---:|
| `exp` | 약 8천 원소 |
| `f + g` | 약 1.6만 원소 |
| `sum` | 약 3.2만 원소 |

문턱은 상수 하나이고, 가장 늦게 이득이 나는 `sum`에 맞춰요. 그래서 `exp`는 8천~3.2만 원소 구간에서 병렬 이득을 조금 놓치지만(1만 개 `exp`는 1스레드와 10스레드 모두 10.9µs), 어떤 연산도 병렬화 때문에 느려지지는 않아요. 일은 원소 수가 아니라 바이트로 세요. bool처럼 1바이트 피연산자만 있는 연산은 8배 많은 원소가 있어야 병렬로 돌아요. 4096원소짜리 bool 태스크는 4KB뿐이라 atomic 카운터와 캐시 라인을 주고받는 비용이 실제 일보다 크고, 원소 수로 세어 나누면 `b & b`가 10스레드에서 1스레드보다 느려요([연산 엔진](/internals/array/engine/)).

### 그 위: 병렬 구간의 고정 비용

병렬 호출 한 번의 고정 비용은 워커가 spin 중일 때 약 1.5µs예요. mutex 없이 세대 번호를 release/acquire로 주고받아 시작하기 때문이에요. 잠든 워커를 깨워서 시작하면 약 25µs, spin을 해도 mutex 경합이 있으면 약 18µs가 들어요. 태스크 하나는 `kParallelTask` = $2^{12}$원소예요. 고정 비용이 작으므로 태스크를 잘게 잘라 부하를 고르게 나눠요. 원소 100만 개 `f + g`(10스레드 39µs)에서 고정 비용은 4% 정도예요.

<Callout title="결정성과 성능">
병렬화의 모든 결정(어느 축을 나눌지, 블록을 몇 개로 할지, 조각 크기)은 shape, 레이아웃, dtype만으로 정하고 스레드 수를 보지 않아요. 그래서 스레드 수를 바꿔도 결과 비트가 같아요. 스레드를 쓸 수 있을 때만 타는 경로는 결과가 같다고 보장되는 경우(안정 정렬의 조각 병합, pairwise 합의 직렬 트리)에만 써요. 규칙과 예외는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.
</Callout>
