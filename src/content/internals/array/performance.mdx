import Callout from '../../../components/Callout.astro';
import Plot from '../../../components/fig/Plot.astro';

export const lin = (pts) => (x) => {
  for (let i = 1; i < pts.length; i++) {
    const [x0, y0] = pts[i - 1];
    const [x1, y1] = pts[i];
    if (x >= x0 && x <= x1) return y0 + ((y1 - y0) * (x - x0)) / (x1 - x0);
  }
  return NaN;
};

## 한눈에 보기

이 페이지는 배열 영역(`sd`)의 공개 함수가 numpy와 견줘 어디서, 왜 빠르거나 느린지를 연산 갈래별로 모아요. 연산마다의 메커니즘은 각 구현 글에 있어요.

빠른 이유는 크게 다섯 가지로 묶여요.

1. 같은 일을 더 적은 메모리 왕복으로 해요. 버퍼 단위 캐스팅, `var`의 두 번째 패스를 커널 하나로, `nansum`의 NaN을 접근자에서 0으로([연산 엔진](/internals/array/engine/), [집계](/internals/array/reductions/)).
2. 의존 사슬을 끊어요. 누적 합의 블록 스캔, `prod`의 다중 누산기, 손으로 짠 NEON([집계](/internals/array/reductions/), [원소별 커널](/internals/array/elementwise/)).
3. 분기를 없애요. 마스크의 분기 없는 압축, `where`의 비트 마스크 선택, 정렬 네트워크([인덱싱](/internals/array/indexing/), [정렬과 집합](/internals/array/sorting/)).
4. 더 빠른 라이브러리나 알고리즘을 골라요. 자체 NEON 초월함수(`exp`, `expm1`, `log1p`, `cos`)와 vForce 초월함수, int64와 float64 (값, 인덱스) 쌍의 기수 정렬, 짧은 레인의 정렬 네트워크([원소별 커널](/internals/array/elementwise/), [정렬과 집합](/internals/array/sorting/)).
5. 스레드를 써요. numpy는 BLAS를 빼면 한 스레드로 돌아요. stardust는 기본 10스레드이고, 같은 스레드 수면 실행마다 비트까지 같아요. 지금은 스레드 수를 바꿔도 같아요([스레드풀과 결정성](/internals/core/threads/)).

같은 SIMD 명령, 같은 libm, 같은 BLAS를 쓰거나 메모리 대역폭에 묶인 연산은 1스레드에서 numpy와 같아요. numpy보다 느린 자리는 두 갈래예요. 자세한 내용은 아래 "numpy보다 느린 자리" 절에 있어요.

1. 같은 일의 비교가 아니에요. `np.asarray(numpy 배열)`은 같은 객체를 그대로 돌려주는 일이고, `sd.asarray(numpy 배열)`은 새 배열 객체를 만드는 일이에요.
2. 설계상의 대가예요. scatter는 쓰기 전에 모든 인덱스를 검사하고(전부 아니면 전무), `acosh`는 입력과 무관하게 vForce를 쓰고, `argsort`의 기본은 안정 정렬이에요.

## 기계와 해석

### 기계와 버전

| 항목 | 값 |
|---|---|
| 기계 | Apple M4 Pro (arm64 macOS, P코어 10 + E코어 4) |
| 캐시 | 캐시 라인 128B, 페이지 16KB, P코어 L1d 128KB, L2 16MB(코어 5개가 공유, 클러스터 2개) |
| SIMD | NEON 128비트 (float64·int64는 2개, complex128은 1개) |
| Python | 3.15.0 |
| numpy | 2.5.4, BLAS·LAPACK은 Accelerate (`np.show_config()` 기준). 그대로 실행해요(BLAS를 빼면 1스레드) |
| stardust | 1스레드, 그리고 기본값 10스레드(P코어 수) |

### 해석할 때의 함정

- 캐시 크기: 원소 100만 개(8MB)는 L2(16MB)에 상당 부분 남아요. 그래서 메모리에 묶인 연산은 이 크기에서 실제 DRAM 대역폭보다 빠르게 보이고, 스레드 확장성도 다르게 나와요. 아래 "스레드 확장성"을 400만 개에서 보는 이유예요.
- 새 메모리의 첫 쓰기: 결과는 언제나 새 배열에 쓰므로, 새로 받은 페이지에 처음 쓸 때 페이지 폴트가 나요(페이지 16KB). 매번 새 결과를 만드는 실제 상황에서는 이 비용이 늘 들어요.
- 코드 주소: 짧고 뜨거운 루프는 64바이트 명령 인출 블록 경계에 따라 1.7배까지 갈려요([행렬곱](/internals/array/matmul/)의 int64 루프).
- 워커가 깨어 있는 상태: 같은 연산을 연달아 부르면 풀의 워커가 spin 중이에요. 실제 코드에서 병렬 호출 사이에 100µs 넘게 쉬면 워커가 잠들고, 다음 호출이 깨우는 비용(macOS에서 작업당 수십 µs)을 내요([스레드풀과 결정성](/internals/core/threads/)).

## 만들기, 변환, 모양 바꾸기

| 연산 | 이유 |
|---|---|
| `zeros_like` | `zeros`와 같은 경로로, 0으로 채워진 새 메모리를 받아요. 원소를 하나씩 쓰지 않아요 |
| `asarray(numpy f32 .T)` | 연속이 아닌 버퍼의 일반 복사는 결과의 메모리 순서로 걸어요. 축을 결과의 stride 크기순으로 정렬해 원본도 자기 레이아웃을 따라 읽으므로 원소마다 건너뛰지 않아요. 안쪽 축에서 양쪽이 연속이면 벡터화되는 인덱스 루프를 써요([변환과 승격](/internals/array/conversion/)) |
| `asarray(리스트)` | 중첩 리스트를 C++에서 두 번 훑어요. 먼저 shape와 원소 종류를 정하고, 다음에 행 우선으로 값을 써요 |
| `astype(f, int64)` | float → int64 규칙(0 쪽으로 자르기, 포화, NaN은 0)이 ARM `FCVTZS` 명령 하나와 같아서 벡터 `FCVTZS`로 돌려요 |
| `repeat(f, 2)` | 반복 수가 하나이면 원소별 개수와 시작 위치 배열을 만들지 않고, 원소 하나짜리 블록을 고정 횟수 저장 루프로 써요 |
| 뷰를 돌려주는 함수 | `expand_dims`, `broadcast_to`, `moveaxis`는 numpy에서 Python 코드를 거쳐요. stardust는 인자 해석부터 뷰 생성까지 C++ 함수 하나예요 |

`zeros(N)`, `ones(N)`, `full`, `concat`, `stack`, `roll`, `diff`, 같은 dtype의 연속 `asarray` 복사는 numpy와 같아요. 모두 메모리 쓰기 한 번이나 `memcpy`에 묶여 있어서 더 줄일 일이 없어요.

## 원소별 연산

| 연산 | 이유 |
|---|---|
| `f + g` 같은 단순 산술 | 연속 구간의 빠른 경로(fast path)는 바이트 stride 대신 인덱스로 접근하는 루프라 컴파일러가 NEON으로 벡터화해요. numpy도 SIMD라 1스레드는 같아요. 메모리에 묶여 10스레드 이득이 대역폭에서 멈춰요 |
| `f * i` | int64 `i`를 4096원소씩 L1에 맞는 버퍼로 바꿔 가며 계산해요(버퍼 단위 캐스팅). 입력 전체를 임시 배열로 바꾸지 않아 메모리를 덜 지나요 |
| `f2 + v` | 브로드캐스트한 축은 stride 0인 피연산자로 커널에 넘어가고, 안쪽 축은 양쪽이 연속이라 행마다 연속 fast path를 타요 |
| `ft + f2` | 메모리 순서가 섞인 2차원 피연산자는 16행 × 128열 타일로 돌아요. 타일의 행이 전치된 쪽의 캐시 라인을 다시 쓰고, 128개 라인(16KB)은 L1에 남아요([연산 엔진](/internals/array/engine/)) |
| 비교 (`f < g`) | 결과가 bool 바이트인 연속 루프예요. 원인별 분석은 [원소별 커널](/internals/array/elementwise/)에 있어요 |
| `sqrt`, `floor`, `abs` | 컴파일러가 `fsqrt.2d`, `frintm.2d` 등으로 벡터화해요. numpy도 같은 명령이라 1스레드는 같아요 |
| `exp`, `expm1`, `log1p`, `cos` | 배열 영역의 자체 NEON 커널이에요. 원소 둘을 레인 하나로 계산하고 표와 짧은 다항식으로 끝나서, 1스레드에서도 libm을 부르는 numpy보다 빨라요. 계산에 묶여 스레드 수만큼 거의 그대로 빨라져요 |
| `sin`, `log`, `atan`, `asin` | Accelerate vForce의 배열 함수예요. 계산에 묶여 스레드 수만큼 거의 그대로 빨라져요 |
| `tan` | vForce의 `vvtan`이 `-0`의 부호를 잃어서 libm을 써요. numpy도 같은 libm이라 1스레드는 같아요 |
| `nextafter` | libm을 부르지 않고 비트 패턴을 정수로 한 칸 옮기는 커널이에요 |
| complex `/` | numpy와 같은 Smith 알고리즘을 같은 순서로 계산해요(같은 비트). 원소마다 독립이라 10스레드에서 거의 코어 수만큼 빨라져요 |
| `where` | 조건이 연속 bool이고 값이 연속이거나 스칼라이면 8바이트 값을 마스크(`0 - c`)로 골라요. 무작위 조건에서 분기는 예측이 빗나가요 |
| `clip` | float64는 `FMAX` 뒤 `FMIN`, int64는 스칼라 경계면 비교·선택 두 번을 NEON 레지스터 두 개씩 해요 |

자세한 메커니즘은 [원소별 커널](/internals/array/elementwise/), [연산 엔진](/internals/array/engine/), [변환과 승격](/internals/array/conversion/)에 있어요.

## 집계, NaN 리덕션, 누적

| 연산 | 이유 |
|---|---|
| `sum(f)` | numpy와 같은 pairwise 알고리즘이고 잎이 더 넓어요(누산기 16개, 512개). 1스레드는 메모리 대역폭에 묶여 numpy와 같은 수준이에요. 10스레드는 재귀 트리의 4096원소 이하 부분 트리를 잎으로 삼아 병렬로 계산하고 같은 트리를 따라 합쳐요. 그래서 10스레드에서도 1스레드와 비트가 같아요 |
| `prod` | 4096원소 조각 안에 누산기 8개를 둬 곱셈 사슬 하나를 8개로 나눠요 |
| `max` | NEON 레지스터 4개(레인 8개)로 `FMAX`를 접어요. numpy도 SIMD라 같아요 |
| `argmax(f)` | 두 NEON 레인이 각자 (최댓값, 위치)를 추적해요. 긴 레인 하나는 조각마다 답을 구한 뒤 "앞 조각 우선"으로 합쳐 직렬 답과 정확히 같아요 |
| `argmax(i)` | int64는 두 번 읽어요. 먼저 서로 독립인 비교-선택 사슬 넷으로 최댓값을 구하고, 다음에 그 값이 처음 나오는 위치를 넷씩 비교해 찾아요 |
| `var` | 두 번째 패스(편차 제곱합)를 임시 배열 없이 커널 하나로 접어요. numpy의 `_var`(`numpy/_core/_methods.py`)는 편차 배열을 만들고, 제곱하고, 더하는 패스를 따로 돌아요[1] |
| `sum(f2, axis=0)` | 1스레드는 결과 행에 입력 행을 차례로 더하는 바깥 축 리덕션이라 numpy와 같아요. 10스레드는 줄이는 축을 고정 개수의 블록으로 나눠요(블록 리덕션) |
| `cumulative_sum` | numpy의 누적 합은 덧셈 하나가 앞 덧셈을 기다리는 사슬 하나예요. stardust는 4096원소 블록 4개를 한 루프에서 나란히 스캔하고, 블록 끝값으로 carry를 더하는 2단계 블록 스캔을 해요 |
| `nansum`, `nanmean`, `nanvar` | numpy는 `isnan` 마스크와 복사본을 만든 뒤 리덕션을 해요. stardust는 접근자에서 NaN을 0으로 바꿔 트리에 바로 넣어 입력을 한 번만 읽어요 |
| bool `count_nonzero` | 16바이트씩 바이트 카운터에 더하고 넘치기 전인 255번마다 넓혀 합쳐요 |
| 작은 `sum`, `max`, `var` | numpy의 `np.sum`은 Python 함수(`numpy/_core/fromnumeric.py`의 `sum` → `_wrapreduction`)를 거쳐요[1]. stardust는 C++ 함수 하나예요 |

자세한 메커니즘은 [집계](/internals/array/reductions/)에 있어요.

`var`, `cumulative_sum`, 블록 리덕션의 빠른 경로는 numpy와 더하는 순서가 달라서 마지막 비트가 다를 수 있어요. 어디서 얼마나 다른지는 [정확도와 검증](/internals/array/accuracy/)에 있어요. 스레드 수와 상관없이 비트가 같다는 성질은 모든 경로에서 지켜요.

## 통계

| 연산 | 이유 |
|---|---|
| `median`, `quantile` | 필요한 위치만 고르는 선택이에요. 레인 하나가 13만 개 이상이고 풀을 쓸 수 있으면 조각으로 나눈 병렬 정렬로 바꿔요. 어느 경로든 `-0.0 < +0.0`인 같은 전순서를 써서 같은 비트가 나와요 |
| `median(axis=...)` | 레인이 많으면 레인 단위로 나눠요. 레인이 4096개 이하면 NEON 정렬로 레인 전체를 정렬하는 쪽이 `nth_element`보다 빨라요 |
| `cov` | 시간 대부분이 Accelerate의 `syrk`예요. Accelerate는 `sd.set_num_threads`를 따르지 않으므로 10스레드 이득은 풀이 맡는 평균과 중심화에서만 나와요 |
| `histogram` | numpy는 65536개 블록마다 마스크, 구간 번호, 보정 두 번을 각각 배열 연산으로 하고 `bincount`를 불러요. stardust는 같은 계산을 원소 하나에 한 번에 하고 바로 세요 |
| `bincount` | 16개 고정 구간으로 나눠 구간마다 세고 합쳐요 |

자세한 메커니즘은 [통계 함수](/internals/array/statistics/)에 있어요.

## 정렬, 집합, 찾기

| 연산 | 이유 |
|---|---|
| `sort(i)` | 1024개 이상의 int64는 LSD 기수 정렬(8비트 자리)이에요. 최솟값을 빼서 실제로 다른 자리만 정렬하므로 $[-1000, 1000)$은 두 자리면 돼요 |
| `argsort(fs)` | float64 (값, 인덱스) 쌍도 128개부터 기수 정렬이에요. 부동소수점 비트를 정수 순서로 바꾼 키로 여덟 자리를 흩뿌려요. 안정 정렬이에요 |
| `argsort(i)` | 같은 기수 정렬이 두 자리로 끝나요 |
| `sort(f2, axis=1)` | 행 하나가 1000개라 NEON 정렬을 타고, 행끼리 독립이라 레인 단위로 나눠요 |
| `unique_*` | 안정 argsort 한 번(int64는 기수 정렬)과 이웃 비교로 값, 첫 위치, 역인덱스, 개수를 모두 얻어요. 값만 필요한 `unique_values`는 값만 정렬해요 |
| `searchsorted(srt, keys)` | 찾을 값이 많으면 4096개씩 나눠 병렬로 찾아요(위치는 정수라 나누는 방법과 무관해요) |
| `nonzero` | 채우기에 분기가 없어요. 모든 위치에 쓰고 참일 때만 커서를 늘려요. 다차원은 앞 축의 위치를 행마다 한 번에 채워요 |

정렬된 100만 개에서 무작위 값 100만 개를 찾는 `searchsorted(srt, f)`는 이진 탐색이 단계마다 캐시 미스를 기다리므로, 1스레드에서는 두 라이브러리가 같은 메모리 지연에 묶여요. 이득은 스레드로 나누는 데서 나와요.

자세한 메커니즘은 [정렬과 집합](/internals/array/sorting/)에 있어요.

## 인덱싱과 대입

| 연산 | 이유 |
|---|---|
| gather | 1차원·인덱스 배열 하나·같은 dtype이라는 가장 흔한 경우를 위한 합친 루프(`gather_one`)예요. 범위 밖 인덱스는 분기 없이 표시만 해 두고, 루프가 끝난 뒤 에러를 내요. 원소마다 독립이라 병렬로 나뉘어요 |
| 마스크 읽기 | 256원소 조각마다 True 수를 먼저 세어 0이면 건너뛰고, 많으면 분기 없이 압축해요. 절반이 True인 무작위 마스크에서는 원소마다 분기하면 예측이 50% 빗나가는데, 그 분기가 없어요. 청크로 나눠 세고 누적합으로 쓸 자리를 정한 뒤 병렬로 채우므로 결과는 지금 스레드 수와도 상관없어요 |
| 마스크 쓰기 | 같은 청크 구조로 분기 없이 써요 |
| `take_along_axis` | 결과를 메모리 순서대로 원소별로 돌아요. x는 그 축의 stride를 0으로 둔 뷰로 보고 원소마다 `x_view + index * stride`를 읽어요 |
| 스칼라 채우기 | 스칼라 값을 한 번 변환한 뒤 `std::fill`로 채워요 |
| `f2[10, 20]`, `f[::2]`, `f2[:, 5]` | 정확한 Python int와 slice만인 키는 타입 슬롯이 받아 키 해석 없이 오프셋, shape, strides를 바로 계산해요. numpy보다 빨라요 |
| scatter | 쓰기 전에 모든 인덱스를 검사해요. 아래 "설계상의 대가" 참고 |

자세한 메커니즘은 [인덱싱](/internals/array/indexing/)에 있어요.

## 행렬곱

| 연산 | 이유 |
|---|---|
| 3×4 @ 4×3 같은 아주 작은 float64 행렬 | 곱셈-덧셈이 512개 이하인 2차원 곱은 BLAS를 부르지 않고 자체 FMA 커널로 계산해요. BLAS 호출과 일반 경로의 준비가 시간의 절반을 넘었기 때문이에요 |
| float64 1000³ | 둘 다 같은 Accelerate `cblas_dgemm`을 불러요. Accelerate는 `sd.set_num_threads`를 따르지 않으므로 1스레드와 10스레드도 같아요 |
| int64 300³ | BLAS에는 정수 행렬곱이 없어 둘 다 자체 루프예요. numpy는 출력 원소마다 b의 열을 걷는 내적 루프이고, stardust는 b와 c의 행을 연속으로 걷는 i-k-j 루프에 4배 언롤이에요. 출력 행 묶음으로 병렬화해요 |
| 1000 × 8×8 | Accelerate는 256³ 이하의 행렬을 한 스레드로 돌리므로, 작은 행렬의 배치는 stardust의 풀에 나눠요. 1스레드는 같은 BLAS 호출 1000번이라 numpy와 같아요 |

자세한 메커니즘은 [행렬곱](/internals/array/matmul/)에 있어요.

## 크기에 따른 변화

- 1천 개: 풀을 쓰지 않는 크기(아래 `kParallelThreshold`)라 1스레드와 10스레드가 같아요. 호출 고정 비용이 계산과 비슷한 크기예요.
- 1천만 개(80MB): 캐시를 벗어나 메모리에 묶인 연산은 10스레드도 대역폭에서 멈춰요. `f + g`(96MB 이동)는 1스레드가 이미 초당 약 130GB를 옮겨서 1.7배가 한계예요.

## 작은 배열

원소 3개, 3×4 배열처럼 계산이 거의 없으면 호출 경로의 고정 비용이 시간을 정해요. 스레드를 쓰지 않으므로 1스레드와 10스레드가 같아요. 잰 값은 `bench/array/speed.md`의 "작은 배열" 표에 들어가요.

- Python 숫자나 이미 있는 객체를 돌려주는 호출은 빨라요. numpy의 `sum`, `mean`, `max`는 Python 코드를 거치고, stardust는 인자 해석부터 결과까지 C++ 함수 하나예요. `finfo`는 결과(불변 namedtuple)를 한 번 만들어 공유해요. `x.shape`와 `len(x)`는 nanobind의 함수 호출 경로를 거치지 않는 타입 슬롯으로 등록해서 numpy와 같아요.
- 새 배열 객체를 돌려주는 호출도 numpy보다 빠르거나 비슷해요. 작은 원소별 연산(`exp(s3)`, `s3 + t3`)은 이터레이터 없이 커널을 한 번 부르고, 결과 객체는 인스턴스 풀에서 다시 쓰고, 그 Buffer의 블록은 스레드별 목록에서 다시 써요. 그래서 numpy보다 빨라요. 뷰를 만드는 인덱싱(`x[::2]`, `x[:, 5]`, `x[5]`)과 `zeros(3)`, `empty(3)`도 numpy보다 빠르거나 같아요.

자세한 메커니즘은 [작은 배열의 호출 비용](/internals/array/small-arrays/)과 [Python과 C++의 경계](/internals/core/python-boundary/)에 있어요.

## numpy보다 느린 자리

### 같은 일의 비교가 아닌 경우

| 연산 | 무엇을 비교하나 |
|---|---|
| `sd.asarray(numpy 배열)` (연속, strided, 전치) | numpy 쪽은 `np.asarray(numpy 배열)`이라 이미 numpy 배열인 입력을 그대로 돌려줘요. stardust는 numpy의 C 구조체에서 바로 읽어 남의 메모리를 공유하지만, 새 배열 객체를 하나 만들어야 해요. 그 객체만큼의 시간이 남아요. 같은 일인 `sd.asarray(sd 배열)`은 그대로 돌려줘요 |
| `np.asarray(sd 배열)` | numpy가 남의 객체를 버퍼 프로토콜로 받아 새 numpy 배열을 만드는 일을, numpy 배열을 그대로 돌려주는 일과 견준 것이에요 |
| `from_dlpack(numpy 배열)` | numpy는 `__dlpack__`를 불러 capsule을 만들고 다시 자기 배열로 감싸요. stardust는 numpy 배열이면 `__dlpack__`를 부르지 않고 `asarray`와 같은 공유를 해서 numpy보다 빨라요 |
| `asarray(s3)` (그대로 돌려주기) | 양쪽 모두 같은 객체를 돌려줘요. 차이는 nanobind의 함수 호출 경로와 키워드 인자(`dtype`, `copy`) 해석이에요 |

자세한 내역은 [Python과 C++의 경계](/internals/core/python-boundary/)와 [변환과 승격](/internals/array/conversion/)에 있어요.

### 설계상의 대가

다른 것을 얻으려고 치르는 비용이에요.

| 연산 | 원인과 그대로 두는 이유 |
|---|---|
| `gz[idx] = 1.0` (scatter) | 쓰기 전에 모든 인덱스를 한 번 검사해요. 범위 밖 인덱스가 하나라도 있으면 아무것도 쓰지 않기(전부 아니면 전무) 위해서예요. 그 덕분에 쓰기 루프에는 에러 경로가 없어요. 반복된 인덱스에서는 마지막 쓰기가 이겨야 하므로 쓰기는 C 순서로 한 스레드에서 해요. 10스레드 이득은 병렬로 나뉘는 검사 패스에서만 나와요 |
| `acosh` | vForce를 써요. vForce의 `acosh`는 입력과 상관없이 거의 일정하고 libm은 입력에 따라 크게 달라져요. 작은 입력에서는 vForce가 빠르고, 큰 입력에서는 libm이 빨라요(`acosh`, $1 + [0, 10^6)$에서 16%). 데이터를 보고 경로를 고르지 않으므로 vForce 하나만 써요 |
| 작은 배열의 `argsort` | numpy의 기본은 안정성을 보장하지 않는 quicksort[2]이고 stardust의 기본은 안정 정렬[3]이에요. 안정 정렬인 float64 쌍의 기수 정렬은 레인마다 자리 카운터(최대 8×256개)를 비우고 누적하는 고정 비용이 있어서, 작은 배열에서는 그 비용이 남아요 |

### 작은 배열의 고정 비용

뷰(`f[1000:2000]`, `f[::2]`, `f2[5]`, `sm.T`), `zeros(3)`, `empty(3)`, 원소 3개의 원소별 연산, 뷰 여럿을 만드는 `unstack`은 모두 계산이 거의 없고, 새 배열 객체를 하나(또는 여럿) 만드는 호출이에요. `NDArray`는 최대 32차원의 shape와 strides를 고정 배열로 안에 둬서 560바이트이고, 이것을 담은 Python 객체는 512바이트를 넘어 Python의 소형 할당기(pymalloc)를 쓰지 못해요. 시스템 `malloc`으로 할당하고 해제하면 이것이 작은 호출 시간의 큰 몫이 돼요. 그래서 nanobind의 인스턴스 풀이 해제된 객체를 해시표에 등록된 채로 모아 두었다가 다시 써요(풀이 비면 시스템 `malloc`으로 가요). 최대 차원은 32예요. 이유와 다른 장치는 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

## 스레드 확장성

### 400만 개에서의 배율

100만 개는 캐시에 많이 남아서 메모리에 묶인 연산의 확장성을 제대로 보여 주지 못해요. 아래는 원소 400만 개에서 스레드 수를 바꿔 가며 잰 값이에요(1스레드 대비 배율).

두 종류로 갈려요.

- 메모리에 묶인 연산은 대역폭에서 멈춰요. `f + g`는 400만 개에서 96MB(입력 둘과 출력 하나)를 옮기는데, 1스레드가 이미 초당 약 130GB를 옮겨요. 스레드를 늘려도 1.7배가 한계이고, 12스레드부터는 오히려 떨어져요. 새 결과 배열의 첫 쓰기 페이지 폴트도 이 크기에서는 무시할 수 없어요.
- 계산에 묶인 연산은 거의 코어 수만큼 빨라져요. 행 단위 정렬과 int64 matmul은 10스레드에서 7.5~8.5배예요. 원소 100만 개의 `exp`, `cos`, `log1p` 같은 초월함수도 10스레드에서 여러 배 빨라져요.

그 사이에 있는 연산(`sum`, `var`, `sqrt`, 버퍼 캐스트)은 계산과 메모리가 섞여 10스레드에서 2.4~4.7배에 그쳐요. 버퍼 캐스트(`i + f`)가 2.4배로 가장 낮고, `sum`이 3.5배, `sqrt`가 4.2배, `var`가 4.7배예요.

### 기본 10스레드인 이유

기본 스레드 수는 P코어 수(10)예요(`hw.perflevel0.physicalcpu`). 스레드를 14개(E코어 포함)로 늘리면 계산에 묶인 연산은 5~27% 빨라지고(원소 400만 개에서 1스레드 대비 `sin`이 9.4배에서 10.9배로), 메모리에 묶인 연산은 3~12% 느려져요. 위 표의 `f + g`가 12~14스레드에서 떨어지는 것이 그 예예요. 그래서 기본은 10으로 두고, 계산이 많은 작업이면 `sd.set_num_threads(14)`를 쓰면 돼요. 풀은 태스크를 atomic 카운터에서 동적으로 가져가므로, 느린 E코어가 섞여도 전체가 E코어를 기다리지 않아요. E코어는 태스크를 적게 가져갈 뿐이에요([스레드풀과 결정성](/internals/core/threads/)).

## 작은 크기에서 시간을 정하는 것

배열이 작아지면 시간을 정하는 것이 계산에서 고정 비용으로 바뀌어요. 크기에 따라 세 구간이 있어요.

### 수십~수백 ns: 호출 경로

원소가 몇 개뿐이면 계산은 몇 ns이고, 나머지는 호출 경로의 고정 비용이에요. 주요 비용과 줄이는 방법은 이래요.

- 결과 배열의 Python 객체 할당. 512바이트를 넘어 pymalloc을 쓰지 못하지만, 인스턴스 풀에서 다시 써요(위 "작은 배열의 고정 비용").
- nanobind의 타입 찾기. 해시표를 찾지 않고 저장한 타입 포인터와 비교해요.
- 이터레이터. 작은 연속 원소별 호출은 이터레이터를 만들지 않고 커널을 한 번 불러요.
- 고정 크기 배열의 복사. `NDArray` 하나가 560바이트, 이터레이터(`NdIter`)가 1,600바이트예요. 복사와 이동은 실제 ndim칸만 옮겨요.
- nanobind의 함수 호출 경로 자체는 약 10ns로 작아요.

stardust는 32차원 고정 배열을 두되 필요한 만큼만 만져서 이 비용을 줄여요. 복사는 실제 ndim칸만 하고, 256바이트 이하의 데이터는 Buffer 객체 안에 둬서 할당 세 번을 한 번으로 줄이고, 그 블록도 스레드별 목록에서 다시 써요. 축 정렬과 shape 해석에는 할당이 없어요. 호출 경로에 Python 코드가 끼지 않는 것은 작은 `sum`이 numpy보다 빠른 이유이기도 해요([Python과 C++의 경계](/internals/core/python-boundary/)).

### 수 µs~수십 µs: 1스레드 구간

일이 `kParallelThreshold` = $2^{15}$(float64 덧셈 기준) 미만이면 풀을 쓰지 않고 호출한 스레드에서 GIL을 쥔 채 돌아요. 이 값은 10스레드가 1스레드를 이기기 시작하는 일의 양에 맞춘 거예요. 이 값 이상이면 스레드 수가 몇이든 GIL을 놓고 돌아요.

- 일은 원소 수 × 연산의 무게예요. 원소 하나의 비용을 float64 덧셈 단위로 연산마다 적어 두었어요(`op_weights`: `exp` 6, `log` 8, `cos` 14 …). 그래서 무거운 연산일수록 적은 원소부터 나눠요. `exp`는 8192개부터예요.
- 움직이는 배열이 둘뿐인 원소별 연산(복사, `abs(x)`, `x + 1.5`)은 일을 2/3로 세어요. 기준값을 정한 `x + y`는 배열 셋을 움직이기 때문이에요.
- 전체 float 리덕션(`sum`, `mean`, `max`/`min`, `var`의 제곱합)은 원소당 일이 아주 가벼워서 $2^{16}$(`kReduceThreshold`)부터 나눠요.
- 일은 원소 수가 아니라 바이트로 세요. bool처럼 1바이트 피연산자만 있는 연산은 8배 많은 원소가 있어야 병렬로 돌아요. 4096원소짜리 bool 태스크는 4KB뿐이라 atomic 카운터와 캐시 라인을 주고받는 비용이 실제 일보다 크고, 원소 수로 세어 나누면 `b & b`가 10스레드에서 1스레드보다 느려요([연산 엔진](/internals/array/engine/)).

### 그 위: 병렬 구간의 고정 비용

워커가 spin 중이면 병렬 호출 한 번의 고정 비용이 작아요. mutex 없이 세대 번호를 release/acquire로 주고받아 시작하기 때문이에요. 워커가 잠들어 있으면 깨우기가 더 들어서, 일이 약 20µs(`kWakeWorkNs`)를 넘어 깨우기를 갚을 만할 때만 깨워요. 배열 영역의 작업은 태스크 하나의 시간 어림을 풀에 알려서, 짧은 작업은 깨우기를 내지 않아요. 태스크 하나는 `kParallelTask` = $2^{12}$원소예요. 고정 비용이 작으므로 태스크를 잘게 잘라 부하를 고르게 나눠요. 원소별 연산은 조각을 256개까지로 묶어서, 무거운 연산의 긴 실행이 조각을 너무 많이 만들지 않게 해요([스레드풀과 결정성](/internals/core/threads/)).

<Callout title="결정성과 성능">
병렬화의 모든 결정(어느 축을 나눌지, 블록을 몇 개로 할지, 조각 크기)은 shape, 레이아웃, dtype만으로 정하고 스레드 수를 보지 않아요. 그래서 같은 스레드 수에서 실행마다 같은 비트이고, 지금은 스레드 수를 바꿔도 결과 비트가 같아요(약속은 아니에요). 연산의 무게나 깨우기 규칙은 언제 나눌지와 누가 태스크를 맡을지만 바꾸고 결과는 바꾸지 않아요. 스레드를 쓸 수 있을 때만 타는 경로는 결과가 같다고 보장되는 경우(안정 정렬의 조각 병합, pairwise 합의 직렬 트리)에만 써요. 규칙과 예외는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.
</Callout>
