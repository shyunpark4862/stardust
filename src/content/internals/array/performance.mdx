export const lin = (pts) => (x) => {
  for (let i = 1; i < pts.length; i++) {
    const [x0, y0] = pts[i - 1];
    const [x1, y1] = pts[i];
    if (x >= x0 && x <= x1) return y0 + ((y1 - y0) * (x - x0)) / (x1 - x0);
  }
  return NaN;
};

## 한눈에 보기

이 페이지는 배열 영역(`sd`) 전체의 성능을 numpy와 비교해요. 수치는 모두 같은 기계, 같은 프로세스에서 numpy와 번갈아 잰 값이에요. 측정은 두 번이에요. 첫 측정은 주요 연산 31줄이고, 두 번째 측정은 같은 방법으로 첫 측정에 없던 연산과 다시 확인할 연산 27줄을 쟀어요(아래 "두 번째 측정"). 각 줄의 원인은 짧게 적고, 자세한 메커니즘은 해당 구현 문서로 이어 줘요.

첫 측정 31줄을 1스레드 기준으로 나누면 이래요.

| 1스레드에서 numpy 대비 | 줄 수 | 연산 |
|---|:---:|---|
| 빠름 (1.1배 이상) | 19 | 원소별 7, `argmax`, `var`, `cumulative_sum`, 마스크, 정렬 4, int64 matmul, `x[1, 2]`, 작은 `sum`, `asarray` |
| 같음 (0.95~1.1배) | 8 | `sqrt`, `sum` 셋, `max`, `mean`, gather, float64 matmul |
| 느림 | 4 | `median` 0.84×, `argsort` 0.89×, 작은 `a + b` 0.87×, scatter 0.94× |

두 번째 측정에서 처음 나온 줄을 같은 기준으로 나누면 이래요(다시 잰 `sin`, `exp`, `argsort`, 400만 개 `f + g`는 뺐어요).

| 1스레드에서 numpy 대비 | 줄 수 | 연산 |
|---|:---:|---|
| 빠름 (1.1배 이상) | 13 | `nextafter`, `prod`, `cumulative_prod`, `nansum`, `cov` 셋, `histogram` 둘, `bincount`, int64 matmul 500³, `x[1]`, `a.sum()` |
| 같음 | 0 | |
| 느림 | 10 | ±0 섞인 `sort` 0.24×, `quantile` 0.79×, `argsort(stable=False)` 0.93×, 겹치는 `+=` 0.36×, 넓히는 `asarray` 둘 0.24×·0.22×, `zeros(3)` 0.60×, `from_dlpack` 0.43×, 복사 없는 `asarray` 0.07×, `np.asarray(sd 배열)` 0.12× |

(`x[1]`은 1.18배로 "빠름"에 넣었어요. 복사 없는 `asarray`와 `np.asarray(sd 배열)`은 numpy 쪽이 같은 객체를 돌려주기만 하는 값이라 같은 일의 비교가 아니에요. 아래에서 따로 설명해요.)

10스레드(기본값)에서는 첫 측정의 경우 작은 배열 줄과 일부러 직렬로 두는 연산(scatter), Accelerate가 이미 스레드를 쓰는 연산(float64 matmul)을 빼면 모두 numpy보다 1.4배 이상 빨라요. `argsort`는 6.1배, `median`은 1.4배가 되어 느림에서 빠름으로 바뀌어요. 두 번째 측정에서도 ±0 섞인 `sort`(1.59배), `quantile`(3.3배), 겹치는 `+=`(1.43배)는 10스레드에서 numpy를 넘어요. 10스레드에서도 느린 것은 병렬화하지 않는 넓히는 `asarray`와 고정 비용 줄들이에요. `cov`는 시간 대부분이 Accelerate라 스레드 수에 거의 반응하지 않아요(1.2~2배).

빠른 이유는 크게 다섯 가지로 묶여요.

1. **같은 일을 더 적은 메모리 왕복으로 해요.** 버퍼 단위 캐스팅, `var`의 두 번째 패스를 커널 하나로, 블록 리덕션([연산 엔진](/internals/array/engine/), [집계](/internals/array/reductions/)).
2. **의존 사슬을 끊어요.** 누적 합의 블록 스캔, 다중 누산기, 손으로 짠 NEON([집계](/internals/array/reductions/), [원소별 커널](/internals/array/elementwise/)).
3. **분기를 없애요.** 마스크의 분기 없는 압축, 정렬 네트워크([인덱싱](/internals/array/indexing/), [정렬과 집합](/internals/array/sorting/)).
4. **더 빠른 라이브러리나 알고리즘을 골라요.** vForce 초월함수, int64 기수 정렬([원소별 커널](/internals/array/elementwise/), [정렬과 집합](/internals/array/sorting/)).
5. **스레드를 써요.** numpy는 BLAS를 빼면 한 스레드로 돌아요. stardust는 기본 10스레드이고, 결과는 스레드 수와 상관없이 비트까지 같아요([스레드풀과 결정성](/internals/core/threads/)).

첫 측정의 느린 네 줄은 모두 이유가 분명해요. 일부러 정한 의미론(scatter의 "마지막 쓰기가 이긴다", `argsort`의 기본 안정 정렬)이거나, 넣지 않기로 한 최적화(작은 할당 캐시) 때문이에요. 두 번째 측정의 느린 줄은 성격이 달라요. 대부분이 **아직 빠르게 만들지 않은 경로**예요. ±0이 섞이면 가는 merge sort 대피 경로, 버퍼 프로토콜의 원소 단위 복사 루프, 보수적인 겹침 검사와 같은 뷰의 자기 대입, 배열에도 먼저 하는 numpy 스칼라 검사가 원인이에요. 원인이 모두 코드에서 드러나고, 고칠 방법도 보여요. 아래 "느린 줄" 절에 모두 모았어요.

## 측정 방법

### 기계와 버전

| 항목 | 값 |
|---|---|
| 기계 | Apple M4 Pro (P코어 10 + E코어 4) |
| 캐시 | 캐시 라인 128B, 페이지 16KB, P코어 L1d 128KB, L2 16MB(코어 5개가 공유, 클러스터 2개) |
| SIMD | NEON 128비트 (float64·int64는 2개, complex128은 1개) |
| numpy | 2.5.4, BLAS·LAPACK은 Accelerate (`np.show_config()` 기준) |
| stardust | 1스레드, 그리고 기본값 10스레드(P코어 수) |

### 방법

- **데이터:** 따로 적지 않으면 원소 100만 개(8MB) float64예요. `f`, `g`는 $[0.5, 1.5)$의 균등 난수, `i`는 $[-1000, 1000)$의 정수, `j`는 $[-2^{62}, 2^{62})$의 정수, `m`은 1000×1000, `ft`는 1000×1000의 전치(F 순서 뷰), `idx`는 $[0, 10^6)$의 정수 100만 개, `mask`는 절반이 True, `s`는 2000×1000, `u`는 $[0, 1000)$의 정수예요. 두 라이브러리에 같은 값을 넣어요.
- **시간:** `timeit.repeat(stmt, number=N, repeat=7)`로 N번 반복을 7라운드 재고, **가장 빠른 라운드**의 시간을 N으로 나눠요. 가장 빠른 값은 다른 프로세스나 OS의 방해를 가장 적게 받은 값이라, 연산 자체의 비용에 가장 가까워요.
- **순서:** 첫 측정은 numpy 전체 → stardust 1스레드 전체 → stardust 10스레드 전체 순서로 한 프로세스에서 재요. 두 번째 측정은 연산마다 numpy → 1스레드 → 10스레드 순서로 재요. 시간 측정과 라운드 수는 같아요.
- **두 번째 측정의 데이터:** `f`, `u`는 위와 같아요. ±0 섞인 입력은 원소의 약 절반이 0이고 그중 약 9.5%가 `-0.0`, 나머지는 $[0, 1)$의 난수예요. `nansum`의 입력은 `f`의 1%를 NaN으로 바꾼 것, 가중치 `w`는 $[0, 1)$의 난수, 400만 개 덧셈은 $[0.5, 1.5)$의 난수 둘이에요. 넓히기는 $[-1000, 1000)$의 int32와 $[0, 1)$의 float32 100만 개예요. `cov`는 numpy를 `ddof=0`으로 불러 stardust의 기본값과 맞췄어요. 겹치는 `+=`는 `x[::2] += x[1::2]`를 같은 배열에 되풀이해요.
- 배율은 numpy 시간 ÷ stardust 시간이에요. 1보다 크면 stardust가 빨라요.

### 해석할 때의 함정

이 기계에서 측정할 때의 함정이에요. 수치를 읽을 때 같이 봐야 해요.

- **캐시 크기:** 원소 100만 개(8MB)는 L2(16MB)에 상당 부분 남아요. 그래서 메모리에 묶인 연산은 이 크기에서 실제 DRAM 대역폭보다 빠르게 보이고, 스레드 확장성도 다르게 나와요. 확장성은 400만 개에서 따로 재요(아래 "스레드 확장성").
- **새 메모리의 첫 쓰기:** 결과는 언제나 새 배열에 쓰므로, 새로 받은 페이지에 처음 쓸 때 페이지 폴트가 나요(페이지 16KB). 출력 버퍼를 재사용하는 측정은 실제보다 빠르게 나와요. 이 벤치는 매번 새 결과를 만드는 실제 상황 그대로예요.
- **흔들림:** 메모리에 묶인 연산의 1스레드 값은 측정마다 20~30% 흔들려요. 그래서 1.1배 안쪽의 차이는 "같음"으로 읽어요. 두 측정에 모두 들어간 줄에서도 보여요. 10스레드 `sin`은 138µs와 102µs, 1스레드 `argsort(f)`는 82.71ms와 75.69ms였어요. 전체가 100µs 안팎인 10스레드 값은 특히 크게 흔들려요.
- **코드 주소:** 짧고 뜨거운 루프는 64바이트 명령 인출 블록 경계에 따라 1.7배까지 갈려요([행렬곱](/internals/array/matmul/)의 int64 루프). 버전 사이를 비교할 때는 각 시점을 다시 빌드해서 재요.
- **워커가 깨어 있는 상태:** 벤치는 같은 연산을 연달아 부르므로 풀의 워커가 spin 중이에요. 실제 코드에서 병렬 호출 사이에 100µs 넘게 쉬면 워커가 잠들고, 다음 호출이 깨우는 비용(macOS에서 작업당 수십 µs)을 내요([스레드풀과 결정성](/internals/core/threads/)).

| `sd.asarray(numpy 배열)` | 0.07× | **같은 일의 비교가 아니에요.** numpy의 13ns는 이미 numpy 배열인 입력을 그대로 돌려주는 값이고, stardust의 같은 동작(`sd.asarray(sd 배열)`)은 20ns예요. 175ns는 남의 버퍼로 새 배열 객체를 만드는 비용이에요. 그중 약 37ns는 numpy 배열에도 numpy 스칼라 검사(`PyObject_IsInstance` 네 번)를 먼저 하는 순서에서 나와요 |
| `np.asarray(sd 배열)` | 0.12× | 역시 같은 일이 아니에요. numpy가 버퍼 프로토콜로 남의 객체를 받는 비용이고, numpy가 `memoryview`를 받을 때(90ns)와 비슷한 크기예요 |
| `from_dlpack` | 0.43× | 속성 조회 두 번(`hasattr`), `__dlpack_device__` 호출, 키워드 인자로 `__dlpack__` 호출, 소유자 capsule과 배열 객체 만들기예요 |
| `zeros(3)` | 0.60× | `parse_shape`가 정수 하나에도 `std::vector`를 만들고, nanobind 인스턴스 생성과 할당이 남아요 |
| `x[1]` (1차원) | 1.18× | `x[1, 2]`와 같은 정수 키 빠른 경로를 타고 Python `float`을 돌려줘요 |
| `a.sum()` | 2.36× | numpy의 메서드도 Python 함수(`_methods._sum`)를 한 번 거치고, `np.add.reduce` 자체가 188ns예요. stardust의 메서드는 `sd.sum`과 같은 C++ 함수예요 |

## 느린 줄

느린 줄을 숨기지 않고 모았어요. 첫 측정의 네 줄은 원인이 알려져 있고, 그대로 둔 이유가 있어요.

| 연산 | 1스레드 | 10스레드 | 원인 | 그대로 둔 이유 |
|---|:---:|:---:|---|---|
| `median(f)` | 0.84× | 1.44× | 원본을 C 순서 float64 행으로 복사하고, NaN이 있는지 한 번 훑고, `std::nth_element`로 고르는 세 패스예요 | 전순서 비교로 어느 경로를 타든 같은 비트를 내기 위해서예요 |
| `argsort(f)` | 0.89× | 6.14× | 기본값이 안정 정렬(`stable=True`)이라 (값, 인덱스) 쌍의 하향식 merge sort를 해요. 1스레드에서는 조각 병렬 경로를 쓰지 않아요 | Array API의 기본값이 안정 정렬이고, 1스레드에서 조각을 쓰면 병합 패스가 더해져 더 느려요. numpy도 안정 정렬로 맞추면 1.04배로 같아요 |
| `g[idx] = 1.0` | 0.94× | 1.09× | 모든 인덱스를 먼저 검사한 뒤 C 순서로 한 스레드에서 써요 | 반복된 인덱스에서 마지막 쓰기가 이겨야 하고, 범위 밖 인덱스가 있으면 아무것도 쓰지 않아야(전부 아니면 전무) 해요 |
| `a + b` (원소 3개) | 0.87× | 0.83× | 결과 배열 하나마다 nanobind 인스턴스 생성과 메모리 할당이 있어요 | 더 줄이려면 할당 캐시나 특수 경우용 fast path가 필요한데, 캐시는 스레드 간 해제와 메모리 반환 시점의 복잡도를, 특수 경로는 경로마다 의미가 어긋날 위험을 들여와요 |

두 번째 측정의 느린 줄이에요. 고정 비용 줄(`from_dlpack`, `zeros(3)`, 같은 일이 아닌 두 `asarray`)은 위 "경계와 작은 호출"에 있어요. 나머지 다섯은 원인이 코드에서 드러나고, 그중 셋은 의미론을 바꾸지 않고 고칠 수 있는 경로예요.

| 연산 | 1스레드 | 10스레드 | 원인 | 상태 |
|---|:---:|:---:|---|---|
| `sort`(±0 섞인 `f`) | 0.24× | 1.59× | 안정 정렬에서 `-0.0`과 `+0.0`이 함께 있으면 NEON 정렬 대신 merge sort로 가요 | 고칠 수 있어요: 0 구간의 부호를 입력 순서로 다시 쓰면 NEON 정렬과 같은 결과예요 |
| `quantile(f, q 5개)` | 0.79× | 3.30× | `median`과 같아요: 복사, 따로 하는 NaN 패스, `nth_element` 선택(위치 10개) | `median`과 같은 이유로 그대로예요 |
| `argsort(stable=False)` | 0.93× | 6.19× | 1스레드에서도 조각 16개 + 병합 4단계예요 | 스레드 수와 무관한 결과를 위한 대가예요 |
| `x[::2] += x[1::2]` | 0.36× | 1.43× | 보수적인 겹침 검사의 거짓 양성 복사, 그리고 같은 뷰를 제자리에 다시 쓰는 대입 | 고칠 수 있어요: 같은 뷰의 대입은 건너뛰고, 쉬운 겹침은 정확히 판정 |
| 넓히는 `asarray` | 0.24×, 0.22× | 같음 | 버퍼 프로토콜의 복사가 엔진을 쓰지 않는 원소 단위 루프이고 병렬화도 안 돼요 | 고칠 수 있어요: 연속 입력의 빠른 루프, 또는 풀로 나누기 |

### `median`

stardust의 `median`은 레인 하나를 이렇게 처리해요([통계 함수](/internals/array/statistics/)).

1. 입력을 "남는 축 앞, 줄이는 축 뒤"의 C 순서 float64 행렬로 복사해요(`assign`). 고르기는 데이터를 제자리에서 바꾸므로 복사본이 필요하고, numpy의 `median`도 기본으로 복사본을 만들어요.
2. NaN이 있으면 결과가 NaN이므로 `std::any_of`로 한 번 훑어요.
3. 원소가 4096개를 넘고 레인이 하나뿐인데 풀을 쓸 수 없으면(1스레드) `std::nth_element`로 가운데 위치를 고르고, 짝수 길이면 왼쪽 절반의 최댓값을 `std::max_element`로 찾아요.

모든 비교는 `-0.0 < +0.0`인 전순서(`TotalLess`)로 해요. `a < b || (a == b && signbit(a) && !signbit(b))`라서 평범한 `<`보다 비교가 무거워요. `nth_element`는 100만 개에서 원소당 6.9ns예요. 그것만으로 6.9ms이고, 복사와 NaN 검사를 더하면 7.45ms예요. numpy 2.5.4의 `_median`(`numpy/lib/_function_base_impl.py`)은 가운데 위치 `[n/2 - 1, n/2]`에 마지막 위치(`-1`)를 더해 `partition`을 한 번 불러요. 가장 큰 값이 마지막 자리에 오므로 NaN 검사가 고르기 안에 들어가고, 따로 훑는 패스가 없어요. 고르기 알고리즘도 달라요(libc++의 `nth_element`와 numpy의 introselect).

전순서를 쓰는 이유는 결정성이에요. 레인 길이와 스레드 수에 따라 고르는 방법이 셋(삽입 정렬, NEON 정렬, `nth_element`) 중 하나로 갈리는데, 셋이 같은 전순서를 써야 `-0.0`과 `+0.0`이 섞인 입력에서도 어느 경로든 같은 비트가 나와요. 10스레드에서는 레인 하나를 조각으로 나눈 병렬 정렬(2¹⁶개 조각, merge path 병합)로 바꿔 4.31ms, numpy의 1.44배가 돼요.

### `argsort`

numpy의 `argsort`는 기본이 `kind='quicksort'`(안정성을 보장하지 않음)이고[2], stardust는 Array API를 따라 기본이 `stable=True`예요[3]. 같은 이름이지만 다른 일을 비교하는 셈이에요. stardust의 안정 `argsort`는 (값, 인덱스) 쌍을 하향식 merge sort로 정렬해요. 인덱스로 순서가 드러나므로 안정이 아닌 NEON 정렬을 쓸 수 없어요.

긴 레인 하나를 조각으로 나눠 정렬하고 병합하는 경로는 **풀을 쓸 수 있을 때만** 타요. 병합은 직렬 정렬에 없는 추가 패스라, 1스레드에서 늘 조각을 쓰면 오히려 느려져요(`sort(f)`가 13.1ms에서 23.6ms로). 안정 정렬은 조각을 쓰든 안 쓰든 결과가 같으므로, 스레드가 있을 때만 경로를 바꿔도 결정성이 깨지지 않아요. 그래서 10스레드에서는 6.14배가 돼요. int64 `argsort`는 기수 정렬이 안정 정렬이라 1스레드부터 numpy보다 크게 빨라요(6.7ms 대 82.2ms).

### scatter

`x[idx] = v`에는 두 가지 약속이 있어요.

- **반복된 인덱스에서는 마지막 쓰기가 이겨요.** numpy와 같은 의미론이에요. 쓰기를 여러 스레드에 나누면 같은 자리에 쓰는 순서가 정해지지 않아 이 약속이 깨지므로, C 순서로 한 스레드에서 써요. 10스레드에서도 직렬이에요.
- **전부 아니면 전무예요.** 범위 밖 인덱스가 하나라도 있으면 아무것도 쓰지 않아요. 그래서 쓰기 전에 모든 인덱스를 한 번 검사해요. 이 검사 패스가 numpy보다 약간 느린 원인이에요. 대가로 쓰기 루프에는 에러 경로가 없어요.

### 작은 `a + b`

원소 3개짜리 덧셈은 계산이 아니라 호출 경로가 시간을 정해요. stardust는 이 비용을 크게 줄였어요(고정 크기 배열을 실제 ndim칸만 복사, 256B 이하 데이터를 Buffer 객체 안에 둬 할당 세 번을 한 번으로, 할당 없는 축 정렬과 키 저장소). 남은 비용은 nanobind의 인스턴스 등록과 할당, `NDArray` 복사, 이터레이터 준비에 고르게 퍼져 있어요. 더 줄이려면 작은 메모리 블록을 재사용하는 할당 캐시나 연산마다의 특수 경로가 필요해요. 캐시는 여러 스레드에서의 해제와 메모리를 OS에 돌려줄 시점 같은 복잡도를 들여오고, 특수 경로는 경로마다 의미가 미세하게 어긋날 위험과 테스트할 조합을 늘려서 넣지 않았어요. 같은 이유로 `zeros(3)`(두 번째 측정 106ns 대 63ns), 2차원 배열의 `x[1]`(뷰를 만들어요, 65ns 대 39ns)도 numpy보다 느려요. 원소 하나를 돌려주는 1차원 `x[1]`은 24ns 대 28ns로 빨라요([작은 배열의 호출 비용](/internals/array/small-arrays/)).

### ±0이 섞인 `sort`

`sort`의 기본은 안정 정렬이에요. 값만 정렬할 때 NEON 정렬(안정이 아님)의 결과가 안정 정렬과 구별될 수 있는 경우는 같은 값인데 비트가 다른 `-0.0`과 `+0.0`뿐이에요. 그래서 `sort_values_serial`이 레인을 한 번 훑어(`zeros_of_both_signs`) 둘이 함께 있으면 merge sort로 가요. 같은 입력을 `stable=False`로 정렬하면 17.6ms, 0을 모두 `+0.0`으로 바꾸면 13.8ms(numpy 13.69ms)였고, 무작위 `f`에 `-0.0`과 `+0.0`을 하나씩만 넣어도 14.5ms가 65.9ms가 돼요(같은 방법으로 잰 값). 4배 차이는 데이터가 아니라 경로 때문이에요. 정렬된 결과에서 0은 한 구간에 모이고, 안정 정렬이라면 그 구간의 부호 순서는 입력에서 0이 나온 순서이므로, NEON 정렬 뒤에 그 구간만 다시 쓰면 merge sort 없이 같은 결과를 낼 수 있어요([정렬과 집합](/internals/array/sorting/)).

### 겹치는 `+=`

`x[::2] += x[1::2]`는 Python에서 `tmp = x[::2]; tmp += x[1::2]; x[::2] = tmp`예요. 1스레드 396µs를 단계별로 나누면 덧셈 156µs, 거짓 양성 복사 약 120µs, 같은 뷰의 자기 대입 119µs예요. `x[::2]`와 `x[1::2]`는 공유하는 바이트가 없지만 바이트 범위 검사(`may_share_memory`)는 겹친다고 답해 `x[1::2]`를 먼저 복사해요. 그리고 `setitem`은 값이 대상과 같은 뷰여도 대입 패스를 그대로 돌아요. numpy는 같은 덧셈을 복사 없이 하고(`np.add(a, b, out=a)`가 겹치지 않는 입력과 같은 시간), 같은 뷰의 대입은 0.1µs에 끝내요([데이터 모델](/internals/array/data-model/)).

### 넓히는 `asarray`

int32나 float32 numpy 배열은 저장 타입이 아니라서 복사하며 넓혀요. 그런데 넓히지 않는 복사(`sd.asarray(f, copy=True)`)도 430µs로 같으니 변환 비용이 아니에요. 버퍼 프로토콜의 복사는 이터레이터와 캐스트 커널을 쓰지 않고 `from_buffer` 안의 `for_each_element<2>`로 원소마다 런타임 바이트 stride를 옮기며 `memcpy` load와 store를 해요(원소당 약 0.42ns). `parallel_for`도 부르지 않아요. 같은 100만 원소를 stardust 배열에서 복사하면 엔진을 거쳐 102µs(10스레드 36µs)로 numpy와 같아요([변환과 승격](/internals/array/conversion/)).

## 스레드 확장성

두 종류로 갈려요.

- **메모리에 묶인 연산은 대역폭에서 멈춰요.** `f + g`는 400만 개에서 96MB(입력 둘과 출력 하나)를 옮기는데, 1스레드가 이미 초당 약 130GB를 옮겨요. 스레드를 늘려도 1.7배가 한계이고, 12스레드부터는 오히려 떨어져요. 새 결과 배열의 첫 쓰기 페이지 폴트도 이 크기에서는 무시할 수 없어요.
- **계산에 묶인 연산은 거의 코어 수만큼 빨라져요.** `argmax`, 행 단위 정렬, int64 matmul은 10스레드에서 7.5~8.5배예요. 원소 100만 개, 10스레드에서는 이 페이지의 두 측정에서 `exp`가 137µs와 131µs, `sin`이 138µs와 102µs였어요. 100µs 안팎인 10스레드 값은 측정마다 크게 흔들려요.

그 사이에 있는 연산(`sum`, `var`, `sqrt`, 버퍼 캐스트)은 계산과 메모리가 섞여 3.5~4.7배에서 멈춰요.

### 기본 10스레드인 이유

기본 스레드 수는 P코어 수(10)예요(`hw.perflevel0.physicalcpu`). 스레드를 14개(E코어 포함)로 늘리면 계산에 묶인 연산은 5~27% 빨라지고(`sin`이 9.4배에서 10.9배로), 메모리에 묶인 연산은 3~12% 느려져요. 위 표의 `f + g`가 12~14스레드에서 떨어지는 것이 그 예예요. 그래서 기본은 10으로 두고, 계산이 많은 작업이면 `sd.set_num_threads(14)`를 쓰도록 했어요. 풀은 태스크를 atomic 카운터에서 동적으로 가져가므로, 느린 E코어가 섞여도 전체가 E코어를 기다리지 않아요. E코어는 태스크를 적게 가져갈 뿐이에요([스레드풀과 결정성](/internals/core/threads/)).

## 작은 크기에서 시간을 정하는 것

배열이 작아지면 시간을 정하는 것이 계산에서 고정 비용으로 바뀌어요. 크기에 따라 세 구간이 있어요.

### 수십~수백 ns: 호출 경로

원소가 몇 개뿐이면 계산은 몇 ns이고, 나머지는 호출 경로의 고정 비용이에요. `sample` 프로파일러로 본 주요 비용은 다음이었어요.

- 고정 크기 배열을 통째로 복사하고 0으로 채우는 `memmove`/`memset`. `NDArray` 하나가 약 560바이트, 이터레이터가 약 1.3KB예요.
- 작은 배열 하나에 `malloc` 세 번(Buffer, 데이터, `shared_ptr` 제어 블록), 그리고 `std::vector`·`std::stable_sort`의 임시 할당.
- nanobind의 함수 호출 경로 자체는 약 10ns로 작아요.

stardust는 32차원 고정 배열을 유지하면서 "필요한 만큼만 만지기"로 이 비용을 줄였어요. 그 결과가 위의 작은 배열 줄이에요. Python 로직을 끼우지 않은 것(얇은 Python, 두꺼운 C++)이 작은 `sum`이 numpy보다 6배 빠른 이유이기도 해요([Python과 C++의 경계](/internals/core/python-boundary/)).

### 수 µs~수십 µs: 1스레드 구간

일이 `kParallelThreshold` = $2^{15}$(float64 원소 기준, 바이트로 256KB) 미만이면 풀을 쓰지 않고 호출한 스레드에서 GIL을 쥔 채 돌아요. 이 값은 10스레드가 1스레드를 이기기 시작하는 크기에서 정했어요.

| 연산 | 10스레드가 이기기 시작하는 크기 |
|---|---:|
| `exp` | 약 8천 원소 |
| `f + g` | 약 1.6만 원소 |
| `sum` | 약 3.2만 원소 |

상수 하나로 두고 가장 늦게 이득이 나는 `sum`에 맞췄어요. 그래서 `exp`는 8천~3.2만 원소 구간에서 병렬 이득을 조금 놓치지만, 어떤 연산도 병렬화 때문에 느려지지는 않아요. 일은 원소 수가 아니라 바이트로 세요. bool처럼 1바이트 피연산자만 있는 연산은 8배 많은 원소가 있어야 병렬로 돌아요(4096원소 bool 태스크는 atomic 카운터와 캐시 줄 주고받기 비용이 실제 일보다 커서 `b & b`가 10스레드에서 더 느렸어요).

### 그 위: 병렬 구간의 고정 비용

병렬 호출 한 번의 고정 비용은 워커가 spin 중일 때 약 1.5µs예요. mutex 없이 세대 번호를 release/acquire로 주고받아 시작하기 때문이에요(깨우기만 하면 약 25µs, spin을 넣어도 mutex 경합이 있으면 18µs였어요). 태스크 하나는 `kParallelTask` = $2^{12}$원소예요. 고정 비용이 작으므로 태스크를 잘게 잘라 부하를 고르게 나눠요. 원소 100만 개 `f + g`(10스레드 50µs)에서 고정 비용은 3% 정도예요.

<Callout title="결정성과 성능">
병렬화의 모든 결정(어느 축을 나눌지, 블록을 몇 개로 할지, 조각 크기)은 shape, 레이아웃, dtype만으로 정하고 스레드 수를 보지 않아요. 그래서 스레드 수를 바꿔도 결과 비트가 같아요. 이 규칙의 대가가 위의 `argsort`처럼 "스레드가 있을 때만 다른 경로"를 결과가 같다고 보장되는 경우에만 쓸 수 있다는 점이에요. 규칙과 예외는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.
</Callout>
