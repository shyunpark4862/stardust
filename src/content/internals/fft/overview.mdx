## 한눈에 보기

`sd.fft`는 이산 푸리에 변환과 그 친척들을 계산해요. 복소 변환(`fft`, `ifft`와 다차원 판), 실수와 에르미트 변환(`rfft`, `irfft`, `hfft`, `ihfft`와 다차원 판), 코사인·사인 변환(`dct`, `dst` 계열), 로그 간격 표본의 한켈 변환(`fht`, `ifht`), 그리고 도우미 여섯이에요. 공개 이름은 서른다섯 개이고 모두 `sd.fft`에 바로 있어요.

안쪽은 세 조각으로 읽으면 돼요.

- **계획(plan).** 변환의 종류와 길이 $n$이 정해지면 그 길이에 쓸 기수의 순서와 회전 인자 표를 한 번 만들어 둬요. 계획은 만든 뒤에 바뀌지 않아서 여러 스레드가 동시에 읽어요.
- **줄 커널.** 길이 $n$의 줄 하나를 계획대로 변환해요. 복소 변환의 커널이 바닥이고, 실수 변환과 코사인·사인 변환과 한켈 변환은 모두 그 위에 앞뒤 처리를 얹은 것이에요.
- **축 구동기.** 배열에서 변환 축을 따라 놓인 줄을 하나씩 꺼내 커널에 넘기고 결과를 제자리에 써요. 줄을 묶고, 태스크로 나누고, GIL을 놓는 일도 여기서 해요.

이 영역의 설계는 한 문장으로 모여요. **한 줄의 결과는 그 줄의 값과 변환의 종류, 길이, `norm`으로만 정해져요.** 어느 길로 계산할지를 종류와 길이만 보고 고르기 때문이에요. 그 약속과 근거는 [결정성](/internals/fft/determinism/)에서 따로 다뤄요.

층은 아래로만 기대요. `csrc/fft/`는 배열, 스레드풀, `base/`의 사인·코사인 위에 서고, BLAS와 LAPACK도 Accelerate의 vDSP도 부르지 않아요. 다른 영역의 C++ 코드는 `fft/`를 모르고, Python 층 `stardust.fft`도 다른 영역을 쓰지 않아요. 한켈 변환의 계수에 필요한 $\log\Gamma$까지 이 영역 안에서 계산해요.

C++ 하위 모듈 `stardust._core.fft`는 소스 파일마다 하나씩 있는 `bind_*`(`bind_basic`, `bind_helper`, `bind_r2r`, `bind_fftlog`)를 차례로 불러 만들어요. 네이티브 이름은 모두 밑줄로 시작하는 내부 이름이에요.

```python
>>> import stardust as sd
>>> C = sd._core.fft
>>> sorted(n for n in dir(C) if not n.startswith("__"))
['_c2c', '_c2cn', '_c2r', '_c2rn', '_cache_clear', '_cache_state', '_fast_len', '_fht', '_fht_cache_clear', '_fht_cache_state', '_fht_plan', '_fhtoffset', '_freq', '_plan_info', '_r2c', '_r2cn', '_r2r', '_r2rn', '_twiddles']
```

변환 함수는 열여덟 개인데 네이티브 진입점은 여섯이에요. `c2c`는 복소에서 복소로(`fft`, `ifft`), `r2c`는 실수에서 반쪽 스펙트럼으로(`rfft`, `ihfft`), `c2r`은 반쪽 스펙트럼에서 실수로(`irfft`, `hfft`) 가고, 끝에 `n`이 붙은 셋이 다차원 판이에요. `_plan_info`, `_cache_state`, `_cache_clear`, `_twiddles`는 테스트가 계획을 들여다보는 창이고 이 글의 예제도 그것을 써요.

다른 영역과 달리 변환 함수의 Python 층은 검사를 하지 않아요. 호출 모양만 정하고 인자를 그대로 넘겨요.

```python
# src/stardust/fft/_basic.py
@function
def fft(x, /, *, n=None, axis=-1, norm="backward"):
    """The discrete Fourier transform of x along `axis`: y_k = sum_j x_j e^(-2 pi i jk/n), times 1
    ('backward'), 1/sqrt(n) ('ortho') or 1/n ('forward'). n cuts or zero-pads the axis. complex128.
    Real input (bool, int64, float64) takes the real path: y_(n-k) = conj(y_k) exactly."""
    return _c2c(x, n, axis, norm, False)
```

검사는 C++의 `args.hpp`가 시그니처의 순서대로(`x`, `n`이나 `s`, `axis`나 `axes`, `norm`) 해요. 변환 열여덟 개가 같은 검사 함수를 쓰니 같은 잘못에는 같은 메시지가 나오고, 메시지는 부른 함수의 이름으로 시작해요.

실수 dtype(bool, int64, float64)의 `fft`는 `r2c_axis`로 가요. 실수 변환으로 반쪽 스펙트럼을 구한 뒤 나머지 반쪽을 켤레로 채우는 길이에요. 어느 쪽으로 갈지는 dtype이 정하고, 허수부가 모두 0인 복소 배열을 실수 길로 돌리는 일은 없어요. 값을 보고 길을 고르면 같은 dtype, 같은 길이의 결과가 입력값에 따라 다른 알고리즘에서 나오게 되니까요.

## 길 고르기

길은 변환의 종류와 길이의 함수예요.

| 종류 | 길이 | 길 | 자세히 |
|---|---|---|---|
| 복소 | 소인수가 모두 31 이하, $n \lt 2^{15}$ | 혼합 기수 | [Stockham 혼합 기수](/internals/fft/stockham/) |
| 복소 | 소인수가 모두 31 이하, $n \ge 2^{15}$ | 4단계. $n = n_1 n_2$로 나눈 안쪽 변환은 위 줄의 길 | [4단계 분해](/internals/fft/four-step/) |
| 복소 | 31보다 큰 소인수가 있음 | Bluestein. 안쪽은 길이 $m \ge 2n - 1$의 혼합 기수나 4단계 | [Bluestein](/internals/fft/bluestein/) |
| 실수 | 짝수 $n$ | 길이 $n/2$의 복소 변환과 회전 인자 한 번의 앞뒤 처리 | [실수와 에르미트 변환](/internals/fft/real-hermitian/) |
| 실수 | 홀수 $n$ | 길이 $n$의 복소 변환과 에르미트 부분 | [실수와 에르미트 변환](/internals/fft/real-hermitian/) |
| DCT·DST | 모든 형 | 실수나 복소 변환 위의 형별 알고리즘 | [DCT와 DST](/internals/fft/dct-dst/) |
| FFTLog | 모든 $n$ | 길이 $n$의 실수 변환, 계수의 곱, 역실수 변환 | [FFTLog](/internals/fft/fftlog/) |

복소 계획을 만드는 코드가 표의 첫 세 줄 그대로예요.

```cpp
    // csrc/fft/plan.cpp
    if (is_mixed_length(n)) {
        mixed_ = std::make_unique<CfftPlan>(n);
        cost_ = n * levels(n);
    } else {
        blue_ = std::make_unique<BluesteinPlan>(n);
        const int64_t m = blue_->m();
        cost_ = 2 * m * levels(m) + 4 * m;
    }
```

`is_mixed_length(n)`은 $n$을 2와 `kOddRadices`의 소수로 나눠 1이 남는지 봐요. 4단계인지는 `CfftPlan`의 생성자가 $n \ge 2^{15}$로 정해요. `_plan_info`로 길을 볼 수 있어요.

```python
>>> for n in (1000, 1001, 1009):
...     p = C._plan_info(n)
...     print(n, p["path"], p["radices"], p.get("m"))
1000 mixed [4, 2, 5, 5, 5] None
1001 mixed [7, 11, 13] None
1009 bluestein [3, 3, 3, 3, 5, 5] 2025
>>> [(n, C._plan_info(n)["path"]) for n in (31, 37, 62, 961, 1147)]
[(31, 'mixed'), (37, 'bluestein'), (62, 'mixed'), (961, 'mixed'), (1147, 'bluestein')]
```

$1001 = 7 \cdot 11 \cdot 13$은 혼합 기수이고 소수 1009는 Bluestein이에요. Bluestein 계획의 `radices`는 안쪽 길이 $m = 2025 = 3^4 \cdot 5^2$의 것이에요. $1147 = 31 \cdot 37$처럼 큰 소인수가 하나만 섞여도 길이 전체가 Bluestein으로 가요.

경계가 31인 까닭은 오차 한계예요. 일반 홀수 기수 $p$의 나비는 일이 $p$에 비례해 늘고 반올림도 그만큼 쌓여서, 37부터는 한 단의 오차가 이 영역이 약속한 한계를 넘어요. 그 셈은 [Stockham 혼합 기수](/internals/fft/stockham/)의 표에 있어요. `next_fast_len`이 돌려주는 길이는 그보다 좁은 집합(소인수가 11 이하)이에요. 혼합 기수 가운데서도 가장 싼 기수만 쓰는 길이라서 그래요.

한 길 안에서 다른 길이의 변환을 부르는 일도 있어요. 4단계는 길이 $n_1$과 $n_2$의 변환을, 짝수 길이 실수 변환은 길이 $n/2$의 복소 변환을, Bluestein은 길이 $m$의 변환을 불러요. 안쪽 변환은 안쪽 길이의 표대로 가고, 그래도 바깥 길이의 결과는 바깥 길이로만 정해져요.

## 계획과 캐시

계획은 (종류, 길이)마다 하나예요. 종류는 넷이에요.

| 종류 | 쥐고 있는 것 |
|---|---|
| `Complex` | 혼합 기수면 기수의 순서와 단마다의 회전 인자 표(4단계면 $n_1$, $n_2$의 계획과 회전 인자 표 하나), Bluestein이면 chirp, 핵의 변환, 안쪽 계획 |
| `Real` (짝수 $n$) | 길이 $n/2$의 복소 계획과 사후 처리의 회전 인자 표 |
| `Dct2` | DCT·DST 형 2와 3이 함께 쓰는 안쪽 실수 계획과 회전 인자 표 |
| `Dct4` | 형 4의 안쪽 복소 계획과 회전 인자 표(홀수 $N$이면 순열과 부호의 표) |

홀수 길이의 실수 변환은 실수 계획이 없고 같은 길이의 복소 계획을 그대로 써요. DCT-I과 DST-I은 실수 종류 $2(N - 1)$과 $2(N + 1)$을 써요.

실수 계획과 DCT 계획은 안쪽 복소 계획을 캐시에서 빌리지 않고 스스로 만들어 쥐어요. 같은 길이의 복소 계획이 캐시에 따로 있으면 메모리가 두 번 들지만, 계획을 만드는 동안 캐시의 잠금을 다시 잡을 일이 없고 캐시의 한 칸이 정확히 한 (종류, 길이)가 돼요. 복소 계획은 길이로만 정해지니 어느 사본이든 같은 비트를 내요.

**계획은 실행 시간을 재서 정하지 않아요.** 여러 알고리즘을 돌려 보고 빠른 것을 고르는 방식은 그때의 기기 부하에 따라 다른 알고리즘이 뽑힐 수 있고, 그러면 같은 입력의 끝자리가 실행마다 달라져요. 이 영역의 계획은 길이의 함수이고, 문턱(31, $2^{15}$)과 묶음 크기는 코드에 박힌 상수예요.

캐시는 프로세스에 하나이고, `shared_ptr`로 쥔 계획 32개, 합 256MB까지예요.

```cpp
// csrc/fft/plan.cpp
std::shared_ptr<const Plan> get_plan(Kind kind, int64_t n) {
    {
        const std::lock_guard<std::mutex> lock(g_mutex);
        if (Entry* e = find(kind, n)) {
            e->used = ++g_clock;
            return e->plan;
        }
    }
    std::shared_ptr<const Plan> made;
    {
        const parallel::GilRelease release;
        made = std::make_shared<const Plan>(kind, n);
    }
    const int64_t b = made->bytes();
    if (b > kCacheBytes) return made;
    std::shared_ptr<const Plan> dropped;  // freed after the lock is released
    const std::lock_guard<std::mutex> lock(g_mutex);
    if (Entry* e = find(kind, n)) {  // another thread made it meanwhile: keep the first
        e->used = ++g_clock;
        dropped = std::move(made);
        return e->plan;
    }
    while (!g_entries.empty() && (static_cast<int>(g_entries.size()) >= kCachePlans || g_bytes + b > kCacheBytes)) {
        auto lru = std::min_element(g_entries.begin(), g_entries.end(), [](const Entry& u, const Entry& v) {
            return u.used < v.used;
        });
        g_bytes -= lru->bytes;
        g_entries.erase(lru);
    }
    g_entries.push_back({kind, n, made, b, ++g_clock});
    g_bytes += b;
    return made;
}
```

읽을 곳이 넷 있어요.

1. **찾기는 뮤텍스 하나 아래의 선형 탐색이에요.** 칸이 많아야 32개라 해시가 필요 없어요. 찾으면 사용 시각 `used`를 올려요.
2. **만드는 동안은 잠금도 GIL도 쥐지 않아요.** 긴 계획을 만드는 사이에 다른 Python 스레드가 돌고, 다른 길이의 호출이 캐시에서 기다리지 않아요.
3. **두 스레드가 같은 계획을 동시에 만들면 먼저 넣은 쪽이 남아요.** 늦은 쪽은 제가 만든 것을 버리고 캐시의 것을 받아요. 계획은 (종류, 길이)로만 정해지니 어느 것을 써도 같은 비트예요. 버리는 사본은 잠금을 푼 뒤에 해제돼요.
4. **자리가 없으면 가장 오래 쓰지 않은 것부터 쫓아내요.** 쫓겨난 계획은 그것을 쥔 호출이 끝날 때 풀려요. 256MB를 혼자 넘는 계획은 캐시에 넣지 않고 그 호출만 쓰고 버려요.

```python
>>> C._cache_clear()
>>> x = sd.random.default_rng(1).random(8)
>>> _ = sd.fft.fft(x), sd.fft.fft(x + 0j), sd.fft.fft(sd.zeros(1009) + 0j)
>>> s = C._cache_state()
>>> s["plans"], s["lengths"], s["max_plans"], s["max_bytes"]
(3, [8, 8, 1009], 32, 268435456)
```

길이 8이 두 번 보이는 것은 실수 종류와 복소 종류가 따로 들어가서예요. 계획 마흔 개를 차례로 만들면 앞의 여덟이 쫓겨나요.

```python
>>> C._cache_clear()
>>> z = sd.zeros(64) + 0j
>>> for n in range(64, 104):
...     _ = sd.fft.fft(z, n=n)
>>> s = C._cache_state()
>>> s["plans"], s["lengths"][:3], s["lengths"][-3:]
(32, [72, 73, 74], [101, 102, 103])
```

쫓겨난 계획을 다시 만들어도 결과는 같은 비트예요. 계획에 들어가는 것이 모두 길이의 함수이기 때문이에요. 혼합 기수 계획의 크기는 원소 하나에 약 16바이트(회전 인자의 실수부와 허수부)이고, Bluestein 계획은 chirp($16n$바이트), 핵의 변환($16m$바이트), 안쪽 계획을 합쳐 원소 하나에 약 81바이트예요.

```python
>>> C._plan_info(1000)["bytes"], C._plan_info(1009)["bytes"]
(16384, 81576)
```

한켈 변환의 계획(계수와 바이어스)은 매개변수가 실수라 키가 달라서 전용 캐시(16개, 128MB)에 따로 둬요.

## 축 구동기

구동기는 배열을 줄의 모음으로 봐요. 줄은 변환 축을 따라 놓인 원소들이고, 다른 축의 색인 하나마다 줄이 하나예요. 줄 하나를 계획에 넘기는 방식이 셋 있어요.

| 방식 | 조건 | 하는 일 |
|---|---|---|
| 바로 읽기 | complex128, 변환 축의 간격이 16바이트(입력과 결과 모두), 0 채우기와 켤레 없음, 제자리가 아님 | 계획이 입력의 줄을 그 자리에서 읽고 결과의 줄에 바로 써요 |
| 두 줄 커널 | 바로 읽기가 아닌 complex128, 혼합 기수(4단계 아님), 0 채우기와 켤레 없음, 줄의 원소들이 L1 캐시에 머무는 간격 | 간격 있는 메모리에서 두 줄을 한꺼번에 읽어 변환하고 바로 써요 |
| 묶음 | 그 밖의 모두 | 이웃한 줄 여럿을 버퍼에 모아(dtype 변환, 자르기, 0 채우기) 한 줄씩 변환하고 흩어요 |

```cpp
    // csrc/fft/driver.cpp
    const bool in_place = x.data == out.data;
    const bool direct = dt == DType::Complex128 && xstride == 16 && ostride == 16 && nin >= n && !in_place && !conj_in;
    const bool xcontig = dt == DType::Complex128 && xstride == 16;
    const bool ocontig = ostride == 16;
```

세 방식은 메모리를 오가는 순서만 달라요. 한 줄에 하는 산술은 같은 계획의 같은 연산이라 결과의 비트가 같아요. 두 줄 커널이 왜 같은 비트인지는 [Stockham 혼합 기수](/internals/fft/stockham/)의 끝에서 보여요.

마지막 축이 아닌 축을 변환할 때는 줄의 원소가 메모리에서 띄엄띄엄 놓여요. 간격이 2의 큰 거듭제곱의 배수면 한 줄의 원소들이 캐시의 같은 집합 몇 개에 몰려서 서로를 밀어내요. 그래서 두 줄 커널은 줄 길이가 $8 \cdot 16384 / \max(\gcd(\text{간격}, 16384), 128)$ 이하일 때만 쓰고, 넘으면 묶음으로 모아요. 묶음의 복사는 128바이트 타일(복소 8칸, 실수 16칸) 단위로 해서, 버퍼의 줄은 캐시 줄 하나씩 채워지고 그동안 배열 쪽의 행들은 L1에 머물러요.

### 묶음과 태스크의 크기

```cpp
// csrc/fft/driver.cpp
int64_t block_lines(bool direct, int64_t line_doubles, int64_t lines) {
    if (direct) return 1;
    const int64_t fit = kScratchKeep / line_stride(line_doubles);
    return std::clamp<int64_t>(std::min(fit, (lines + kBlockShare - 1) / kBlockShare), 1, kBlockLines);
}
```

묶음은 버퍼 하나($2^{16}$개의 double, 512KB)에 들어가는 줄 수, 전체 줄 수의 $1/64$, 128줄 가운데 가장 작은 값이에요. 가운데 조건은 줄이 적은 호출에서 묶음 하나가 일을 다 가져가 다른 스레드가 놀지 않게 하려는 것이에요. 버퍼 안에서 줄의 간격은 `line_stride`가 정해요. 16개의 double(128바이트)의 배수로 올린 뒤 16을 더해서 2의 거듭제곱에서 비켜 놓아요. 길이 $2^k$의 줄을 딱 붙여 놓으면 묶음의 모든 줄이 같은 캐시 집합으로 떨어지기 때문이에요.

```cpp
// csrc/fft/driver.cpp
int64_t lines_per_task(int64_t lines, int64_t cost, int64_t block) {
    int64_t per = std::max<int64_t>({(kTaskWork + cost - 1) / cost, (lines + kMaxTasks - 1) / kMaxTasks, 1});
    return (per + block - 1) / block * block;
}
```

태스크 하나는 일의 양이 $2^{12}$ 단위가 되는 줄 수와 전체 줄 수의 $1/1024$ 가운데 큰 쪽을 묶음의 배수로 올린 것이에요. 뒤쪽 조건은 태스크 수의 상한이에요. 몇 줄짜리 태스크가 수만 개면 스레드들이 태스크 번호를 받아 가는 공유 카운터에서 부딪혀요. 한 줄의 비용은 계획이 알려 줘요. 혼합 기수는 $n \lceil \log_2 n \rceil$, Bluestein은 $2m \lceil \log_2 m \rceil + 4m$이에요.

호출 전체의 일(줄 수 $\times$ 비용)이 $2^{15}$ 이상이면 태스크를 풀에서 돌리고, 그 크기부터는 스레드 수와 상관없이 GIL을 놓아요. 그보다 작으면 같은 태스크를 호출한 스레드가 차례로 돌아요. 이 수들은 모두 입력의 크기에서만 나와요. 스레드 수를 읽는 곳이 없어요.

묶음의 버퍼는 스레드마다 쥐고 있는 scratch예요. 슬롯 넷(작업, 입력, 결과, 임시)이 각각 512KB까지 호출 사이에 남아요. 태스크마다 새로 할당하면 첫 접근의 페이지 폴트를 스레드들이 줄 서서 처리하게 돼서, 스레드를 늘려도 빨라지지 않아요. 더 큰 버퍼가 필요한 줄(아주 긴 줄)만 태스크가 그때 할당하고 끝나면 돌려줘요.

### 긴 줄 하나

줄 하나가 $2^{15}$ 이상이면 사정이 달라요. 줄을 태스크로 나눌 수가 없으니 줄 안을 나눠야 해요. 4단계가 그 일을 해요. 줄 하나를 길이 $n_1$의 변환 $n_2$개와 길이 $n_2$의 변환 $n_1$개로 쪼개 그것들을 풀의 태스크로 돌려요([4단계 분해](/internals/fft/four-step/)). 계획의 `parallel_inside()`가 참이면(4단계이거나 4단계를 안쪽에 쓰는 실수·Bluestein·DCT 계획) 구동기는 줄들을 호출한 스레드에서 차례로 하나씩 돌리고, 병렬은 줄 안에서 일어나요. 긴 줄의 $O(n)$ 패스(정규화, 켤레와 거울 채우기, Bluestein의 chirp 곱, 실수 변환의 앞뒤 처리)도 $2^{14}$칸씩 풀에서 나눠요.

```cpp
// csrc/fft/cfft.hpp
inline constexpr int64_t kChunk = int64_t{1} << 14;
template <class Fn>
inline void run_chunks(int64_t count, Fn&& fn) {
    if (count <= kChunk) {
        if (count > 0) fn(int64_t{0}, count);
        return;
    }
    run_tasks(
        (count + kChunk - 1) / kChunk, [&](int64_t t) { fn(t * kChunk, std::min(count, (t + 1) * kChunk)); }, kChunk
    );
}
```

이 패스들은 칸마다 따로 계산하는 일이라 어디서 끊어도 결과가 같아요. 풀은 겹쳐 쓰지 않아서, 이미 태스크 안에 있는 스레드가 `run_tasks`를 부르면 그 스레드가 조각을 차례로 돌아요.

## 다차원 변환

다차원 판은 축마다 구동기를 한 번씩 돌려요. 순서는 `axes`의 뒤에서 앞으로이고, 입력의 메모리 레이아웃과 무관하게 고정이에요. 축의 순서는 수학적으로는 결과를 바꾸지 않지만 반올림을 바꾸기 때문에 정해 둬야 해요.

```cpp
    // csrc/fft/basic.cpp
    for (int i = last; i >= 0; --i) {
        const int ax = axes[static_cast<size_t>(i)];
        const int64_t n = len[static_cast<size_t>(i)];
        const double s = i == 0 ? scale : 1.0;
        const bool ci = conj_in && i == last, co = conj_out && i == 0;
        if (own && cur.shape[static_cast<size_t>(ax)] == n) {
            c2c_axis(cur, ax, n, inverse, s, cur, ci, co);
        } else {
            NDArray out = new_result(cur, ax, n, DType::Complex128);
            c2c_axis(cur, ax, n, inverse, s, out, ci, co);
            cur = std::move(out);
            own = true;
        }
    }
```

- **첫 패스는 입력을 읽어 새 배열에 써요.** 그 뒤의 패스는 축의 길이가 그대로면 앞 패스의 배열을 제자리에서 변환해요(`out`이 `cur` 자신). 제자리 패스는 바로 읽기를 끄고, 줄을 통째로 읽은 뒤에 써요. 그래서 중간 배열이 많아야 둘이에요.
- **정규화 인자는 마지막 패스가 한 번 곱해요.** $N$은 길이들의 곱이고 인자는 $\mathrm{fl}(1/N)$이나 $\mathrm{fl}(1/\mathrm{fl}(\sqrt N))$ 하나예요. 축마다 $1/n_i$를 곱하는 것과 값은 같지만 반올림이 한 번이에요.
- **실수 쪽 패스의 자리는 정의가 정해요.** `rfftn`은 `axes`의 마지막 축의 실수 변환이 첫 패스이고, `irfftn`은 나머지 축의 복소 역변환을 먼저 한 뒤 마지막 축의 실수 역변환이 끝이에요. `irfftn`에서는 이 순서가 에르미트 대칭이 아닌 입력의 어느 부분이 버려지는지를 정해요.

패스마다 줄을 태스크로 나누니 각 패스가 병렬이에요. 그리고 축이 하나뿐인 `fftn`은 `fft`와, 정규화 인자가 1인 `fftn`은 `fft`를 뒤에서 앞으로 이은 것과 비트까지 같아요.

```python
>>> rng = sd.random.default_rng(3)
>>> Z = rng.random((12, 20, 30)) + 1j * rng.random((12, 20, 30))
>>> F = sd.fft
>>> F.fftn(Z).tolist() == F.fft(F.fft(F.fft(Z, axis=2), axis=1), axis=0).tolist()
True
>>> F.fftn(Z).tolist() == F.fft(F.fft(F.fft(Z, axis=0), axis=1), axis=2).tolist()
False
```

앞에서 뒤로 이으면 값은 같아도(둘 다 정확도 계약 안이에요) 끝자리가 달라요.

## 메모리

- **결과.** 사용자가 `n`이나 `s`로 요청한 결과가 물리 메모리보다 크면 할당 전에 `MemoryError`예요.
- **계획의 작업 버퍼.** 혼합 기수는 줄마다 $2n$개의 double, Bluestein은 $6m$개, 두 줄 커널은 줄 짝마다 $8n$개예요. 4단계의 작업 버퍼도 $2n$개이고, 그 태스크는 열이나 행 16개의 묶음 버퍼 둘과 안쪽 작업 버퍼를 스레드의 몫으로 따로 둬요.
- **묶음 버퍼.** 스레드마다 슬롯 넷 $\times$ 512KB까지 호출 사이에 남아요.
- **계획 캐시.** 32개, 256MB 안이에요. 한켈 변환의 계획은 16개, 128MB의 전용 캐시예요.
- **다차원의 중간 배열.** 많아야 둘이에요. `rfftn`의 중간 결과는 결과 배열 자체이고, `irfftn`의 중간 결과는 마지막 축이 $\lfloor n/2 \rfloor + 1$칸인 complex128 하나예요.
