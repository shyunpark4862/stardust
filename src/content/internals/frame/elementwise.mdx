## 한눈에 보기

이 글은 행 하나를 행 하나로 바꾸는 **원소별 연산**(`s + 1`, `a < b`, `m1 & m2`, `s.astype("string")`)과 컬럼 하나를 값 하나로 접는 **리덕션**(`sum`, `mean`, `var`, `std`, `min`, `max`, `count`)이 C++ 안에서 어떻게 돌아가는지 설명해요. 코드는 `csrc/frame/ops/`의 네 파일에 있어요.

| 파일 | 하는 일 |
|---|---|
| `ops/elementwise.cpp` | 산술, 비교, Kleene 논리, int64 비트 연산, 문자열 이어 붙이기, 단항 연산 (`binary_op`, `unary_op`) |
| `ops/reduce.cpp`, `ops/pairwise.hpp` | 리덕션 (`reduce`). float 합은 공통 기반의 `base/pairwise.hpp`를 불러요 |
| `ops/cast.cpp`, `ops/parse.hpp` | `astype`과 문자열 → 숫자 문법 |
| `column.cpp`, `bitmap.hpp` | 결과의 validity 비트맵을 만들고 마무리하는 함수 (`and_validity`, `finish_fixed`) |

설계는 네 가지 생각으로 요약돼요.

1. **행 루프 안에서 아무것도 고르지 않아요.** dtype, 스칼라인지 컬럼인지, 연산 종류는 루프에 들어가기 전에 템플릿 인자로 정해요. 그러면 루프 몸통이 분기 없는 한 줄이 되어 컴파일러가 NEON으로 벡터화해요. 행마다 고르는 구현은 같은 일을 하는데 아래 표들처럼 커널에 따라 1.5배에서 10배 넘게 느려요.
2. **결측은 비트맵으로, NA 자리의 값은 언제나 0으로 둬요.** 두 입력의 비트맵은 바이트 단위 AND로 합치고, 커널은 NA인지 묻지 않고 모든 행을 계산한 뒤 마지막에 NA 자리를 0으로 지워요. NA 자리가 0이라는 약속 덕분에 float 합은 NA를 건너뛰는 분기 없이 그냥 더해요.
3. **numpy·pandas와 비트까지 맞출 곳은 같은 알고리즘을 같은 순서로 써요.** float 합·평균·분산은 numpy의 pairwise 합, float `//`와 `%`는 numpy의 `npy_divmod`, float min/max는 IEEE 754-2019의 minimum/maximum, float → 문자열은 Python `str(float)`이에요.
4. **문자열 → 숫자는 엄격한 ASCII 문법 하나예요.** `astype`과 `read_csv`가 같은 코드를 써서, 같은 글자는 어디서 읽어도 같은 값이 되거나 같은 에러가 나요.

## 행 루프에서 고르지 않기

### 문제: 행마다 고르는 루프

원소별 연산을 가장 짧게 쓰면 이런 루프가 돼요. dtype과 연산 종류를 행마다 묻는 거예요.

```cpp
// 행마다 고르는 루프 (설명용으로 줄임). 쓰지 않는 모양이에요.
for (int64_t i = 0; i < n; ++i) {
    double x = a.is_int ? double(a.i64[i]) : a.f64[i];
    double y = b.is_scalar ? b.f64[0] : b.f64[i];
    switch (op) {
        case Add: out[i] = x + y; break;
        case Sub: out[i] = x - y; break;
        // ...
    }
    if (!a.valid(i) || !b.valid(i)) clear_bit(out_bits, i);
}
```

이 루프가 느린 이유는 세 가지예요.

- **명령 수.** 실제 계산은 덧셈 하나인데, 행마다 조건 검사와 `switch`의 점프가 몇 개씩 붙어요. `switch`는 보통 점프 표를 통한 간접 분기로 컴파일돼요.
- **분기 예측.** 현대 CPU는 분기의 결과를 미리 짐작하고 그 방향의 명령을 먼저 실행해요. 짐작이 틀리면 이미 실행한 명령을 버리고 다시 시작해야 해요. dtype이나 연산 종류는 호출 하나 안에서 바뀌지 않으니 예측이 잘 맞지만, `valid(i)`처럼 **데이터에 따라 갈리는 분기**는 NA가 무작위로 흩어져 있으면 자주 틀려요.
- **벡터화.** 가장 큰 이유예요. NEON 레지스터는 128비트라서 double 2개, 바이트 16개를 명령 하나로 처리해요. 컴파일러의 루프 벡터화기는 루프 몸통이 "모든 행에 같은 명령을 하는" 직선 코드일 때만 여러 행을 한 레지스터에 묶어요. 몸통 안에 행마다 갈리는 분기나 간접 점프가 있으면 벡터화를 포기하고 한 행씩 돌아요.

두 모양을 같은 조건(1M 행, 1스레드, Apple M4 Pro)에서 비교하면 차이가 커요.

| 연산 | 행마다 고르기 | 루프 밖에서 고르기 |
|---|---:|---:|
| Kleene `&` (행마다 연산을 `switch`로 고르고 분기하는 식 vs 연산을 템플릿 인자로, 분기 없는 식) | 5.09 ms | 1.07 ms |
| float `min` (이긴 행의 위치를 들고, 행마다 dtype `switch`와 NA 비트 확인 vs 값을 들고 NEON으로 접기) | 848 µs | 73 µs |

### 접근: 템플릿 인자로 루프를 여러 벌 만들어요

stardust는 "무엇을 할지"를 모두 컴파일 시점의 타입으로 바꿔요. 루프는 조합마다 한 벌씩 따로 컴파일되고, 각 루프 안에는 결정할 것이 남지 않아요.

먼저 입력 하나를 감싸는 작은 타입이 있어요. 행 `i`를 읽을 때 스칼라면 언제나 0번을, 컬럼이면 `i`번을 읽는데, 그 선택이 `if constexpr`라서 컴파일 시점에 사라져요.

```cpp
// ops/elementwise.cpp (발췌)
template <class T, bool Scalar>
struct In {
    const T* p;
    T operator[](std::int64_t i) const {
        if constexpr (Scalar) return p[0];   // 스칼라: 언제나 0번 (컴파일 시점에 정해짐)
        else return p[i];
    }
};

template <class A, class B, class F>
void visit_inputs(const Column& a, const Column& b, int scalar_side, F&& f) {
    const A* pa = a.data<A>();
    const B* pb = b.data<B>();
    if (scalar_side == 1) f(In<A, true>{pa}, In<B, false>{pb});    // 1 - s
    else if (scalar_side == 2) f(In<A, false>{pa}, In<B, true>{pb}); // s + 1
    else f(In<A, false>{pa}, In<B, false>{pb});                    // s + t
}
```

`scalar_side`를 보는 `if`는 호출마다 한 번뿐이에요. 그 뒤에 불리는 `f`는 세 가지 서로 다른 타입의 인자로 인스턴스화되어, 컬럼⊕컬럼, 컬럼⊕스칼라, 스칼라⊕컬럼이 각자의 루프를 가져요. 스칼라 쪽 루프에서는 `p[0]`이 루프 불변이라 컴파일러가 레지스터에 한 번 올려 두고 모든 행에 씁니다(브로드캐스트).

연산은 **람다**로 넘겨요. 람다는 저마다 고유한 타입이라, 람다를 받는 템플릿 함수는 람다마다 새로 인스턴스화되고 연산이 루프 안에 인라인돼요.

```cpp
// ops/elementwise.cpp (발췌, 줄임)
template <class R, class A, class B, bool CanNA = false, class F>
Column map2(const Column& a, const Column& b, int scalar_side, DType result, F f) {
    const std::int64_t n = scalar_side == 1 ? b.length : a.length;
    Column out = make_fixed(result, n);
    out.validity = and_validity(a, b, scalar_side, n);   // 결과의 NA (아래 절)
    R* o = reinterpret_cast<R*>(out.values->data());
    visit_inputs<A, B>(a, b, scalar_side, [&](auto x, auto y) {
        for_chunks(n, [&, x, y](std::int64_t lo, std::int64_t hi) {
            const auto xx = x;  const auto yy = y;  R* oo = o;   // 지역 변수로 (앨리어싱 절)
            for (std::int64_t i = lo; i < hi; ++i) oo[i] = f(xx[i], yy[i]);
        });
    });
    finish_fixed(out);
    return out;
}

template <class A, class B>
Column float_arith(Op op, const Column& a, const Column& b, int side) {
    auto run = [&](auto f) { return map2<double, A, B>(a, b, side, DType::Float64, f); };
    auto d = [](auto v) { return static_cast<double>(v); };
    switch (op) {                                   // 연산 종류는 여기서 한 번 고르고
    case Op::Add: return run([&](auto x, auto y) { return d(x) + d(y); });   // 람다마다 루프 한 벌
    case Op::Sub: return run([&](auto x, auto y) { return d(x) - d(y); });
    // ... Mul, TrueDiv, FloorDiv, Mod
    case Op::Pow: return float_pow<A, B>(a, b, side);   // 배열의 pow와 같은 커널
    }
}
```

`binary_op`는 dtype 조합을 보고 `float_arith<int64_t, double>`, `float_arith<double, double>`처럼 입력 타입을 템플릿 인자로 정해 불러요. 그러면 int64 컬럼 + float64 컬럼은 루프 안에서 `int64 → double` 변환(`SCVTF`)을 하고 더하는 루프 하나가 되고, int를 미리 float64 컬럼으로 바꾸는 복사가 없어요. 결국 루프 하나는 (결과 타입, 왼쪽 타입, 오른쪽 타입, 스칼라 위치, 연산)의 조합 하나예요.

비교는 결과가 bool 바이트(0 또는 1)인 같은 `map2`이고, Kleene 논리는 연산과 스칼라 위치를 `std::integral_constant`와 `template <Op O, int Side>`로 받는 전용 루프예요(아래 [Kleene 논리](#kleene-논리)).

### 컴파일러가 실제로 만드는 것

빌드 플래그(`-O3 -mcpu=native -ffp-contract=off`, Apple clang 21)로 컴파일한 `ops/elementwise.cpp`에 대해 루프 벡터화기가 내는 보고(`-Rpass=loop-vectorize`)는 이래요.

- float 산술(`+`, `-`, `*`, `/`)과 모든 비교, int64의 `+`, `-`, 비트 연산의 행 루프가 벡터화돼요. double 루프는 2레인 벡터를 4개씩 겹쳐(interleave) 한 번에 8행, bool 결과를 쓰는 비교는 바이트 16개 단위로 돌아요.
- 벡터화되지 않는 것은 이유가 있는 것들이에요. int64 `*`는 NEON에 64비트 정수 곱셈 벡터 명령이 없어서, float `//`, `%`, `**`는 루프 안에서 `fmod`, `pow` 같은 라이브러리 함수를 불러서, int64 `//`, `%`는 정수 나눗셈(역시 벡터 명령이 없어요)이, int64 `**`는 지수의 비트 수만큼 도는 안쪽 루프가 있고 셋 다 행마다 NA를 만들 수 있는 분기가 있어서 한 행씩 돌아요.
- 대가는 코드 크기예요. 조합마다 루프가 생기니 `ops/elementwise.cpp` 한 파일이 기계어 약 250KB가 돼요(확장 모듈 전체는 약 4.8MB). 경우의 수가 dtype 셋과 스칼라 위치 셋, 연산 열여덟 개로 정해져 있어서 감당할 만해요.

### 고르는 근거는 데이터가 아니라 컬럼의 속성이에요

루프 밖에서 고르는 기준은 dtype, 길이, **결측이 있는지**예요. 결측이 없는 컬럼에는 비트맵이 아예 없어서(null 포인터), 커널은 비트맵이 없으면 NA를 생각하지 않는 루프를 골라요. 이것은 값을 훑어보고 경로를 고르는 휴리스틱(예: "정렬되어 있으면 이진 탐색")과 달라요. 결측이 있는지는 컬럼이 만들어질 때 정해지는 속성이고, 그것을 보고 고른 두 경로는 같은 값을 내요. 값을 보고 경로를 바꾸면 같은 코드의 성능이나 결과 타입이 데이터에 따라 몰래 달라지기 때문에, stardust는 그런 휴리스틱을 쓰지 않아요([라벨, 조회, 선택](/internals/frame/labels/)).

### 스칼라는 1행 컬럼이에요

C++ 쪽 진입점은 `binary_op` 하나이고, 스칼라 피연산자는 Python 층(`_ops.scalar_column`)이 **1행짜리 Column**으로 만들어 넘겨요. 그래서 "Series와 스칼라"를 위한 커널이 따로 없고, 위의 `In<T, true>`가 그 차이를 전부 흡수해요.

- 반대쪽 연산 `1 - s`는 두 Column의 순서를 바꾸고 `scalar_side`를 1로 해서 같은 커널을 불러요.
- **NA 스칼라는 반대쪽 dtype의 1행 NA Column이에요.** `s_int + NA`는 int64 + int64, `s_int / NA`는 int64 / int64라서 float64가 돼요. NA를 위한 dtype 규칙이 따로 없고, 결과 dtype은 언제나 입력 dtype만으로 정해져요.
- `Series.__array_ufunc__ = None`이라서 `np.float64(2) * s`에서 numpy가 Series를 배열로 바꿔 계산해 버리지 않고 Series의 반대쪽 연산자에 넘겨요.

## NA 비트맵 합치기

### validity 비트맵

모든 dtype의 결측은 **validity 비트맵**이 나타내요. 행마다 1비트, 1이면 값이 있고 0이면 NA예요. 행 `i`는 바이트 `i / 8`의 비트 `i % 8`이에요(LSB 우선, Arrow와 같아요). 비트맵, NA 자리의 값이 0이라는 약속, 슬라이스가 비트 오프셋을 갖는 방식은 [컬럼과 메모리](/internals/frame/columns/)에 자세히 있어요. 원소별 결과의 비트맵은 세 단계로 만들어요.

1. 두 입력의 비트맵을 비트 0에서 시작하도록 옮긴 뒤 AND해요 (`and_validity`).
2. 커널이 직접 NA를 만들어요. `int // 0`, `int % 0`, `int ** 음수`가 그래요.
3. 마무리해요 (`finish_fixed`). NA를 세고, 하나도 없으면 비트맵을 버리고, NA 자리의 값을 0으로 지워요.

### 1단계: 비트 0으로 맞추기

슬라이스(`s[3:13]`, `head`, `tail`)는 데이터를 복사하지 않고 Buffer를 공유하면서 시작 위치 `offset`만 옮겨요. 그래서 슬라이스의 행 0이 비트맵의 비트 3에 있을 수 있어요. 두 입력의 오프셋이 다르면 같은 행이 서로 다른 비트 자리에 있으니 바이트끼리 바로 AND할 수 없어요. 그래서 먼저 각 입력의 비트맵을 비트 0에서 시작하는 새 비트맵으로 옮겨요(`rebased_validity` → `bitmap::copy_bits`).

옮기기는 비트 하나씩이 아니라 바이트 단위예요. 오프셋의 바이트 안 자리를 $s$ = `offset & 7`이라고 하면 출력 바이트 $j$는 입력 바이트 둘을 시프트해서 붙인 것이에요.

$$
\text{out}[j] = (\text{src}[k] \gg s) \;\big|\; (\text{src}[k+1] \ll (8 - s)), \qquad k = \lfloor \text{offset}/8 \rfloor + j
$$

  <ArrayFig name="src[1]" data={[1, 0, 1, 1, 0, 0, 1, 1]} tones={['b', 'b', 'b', 'a', 'a', 'm', 'm', 'm']} note="비트 8..15" />

  <ArrayFig name="out[0]" data={[1, 1, 1, 0, 1, 1, 0, 1]} tones={['a', 'a', 'a', 'a', 'a', 'b', 'b', 'b']} note="행 0..7" />

```cpp
// bitmap.hpp의 copy_bits (발췌)
for (std::int64_t j = 0; j < nbytes; ++j) {
    const std::int64_t k = first + j;
    unsigned v = src[k] >> shift;
    if (shift != 0 && k + 1 <= last_src) v |= static_cast<unsigned>(src[k + 1]) << (8 - shift);
    dst[j] = static_cast<std::uint8_t>(v);
}
if (n & 7) dst[nbytes - 1] &= static_cast<std::uint8_t>((1u << (n & 7)) - 1);  // 쓰지 않는 높은 비트는 0
```

`k + 1 <= last_src` 검사 덕분에 슬라이스의 마지막 비트가 든 바이트 너머를 읽지 않아요. 마지막 출력 바이트의 쓰지 않는 높은 비트를 0으로 지우는 것은 나중에 `popcount`로 NA를 셀 때 쓰레기 비트가 섞이지 않게 하려는 거예요.

### AND와 NA 스칼라

옮긴 두 비트맵을 바이트끼리 AND하면 "두 입력 모두 값이 있는 행"이 1인 비트맵이 돼요. 루프는 바이트 배열 두 개의 AND라서 컴파일러가 바이트 16개씩 벡터화해요.

```cpp
// column.cpp의 and_validity (발췌)
for (int side = 1; side <= 2; ++side) {
    const Column& c = *rows[side - 1];
    if (!c.validity) continue;                       // 결측 없는 쪽은 볼 것이 없어요
    if (side == scalar_side)                         // NA 스칼라: 모든 행이 NA
        return Buffer::allocate(bitmap::num_bytes(n), /*zeroed=*/true);
    if (!out) out = rebased_validity(c);
    else { auto other = rebased_validity(c); /* out[j] &= other[j] */ }
}
return out;                                          // 둘 다 결측이 없으면 null
```

스칼라 쪽은 1행이라 비트가 하나뿐이에요. 그 비트가 0(NA 스칼라)이면 결과의 모든 행이 NA이므로 0으로 채운 비트맵을 바로 돌려줘요. 값이 있는 스칼라는 비트맵이 없어서 아무것도 하지 않아요.

### 2단계: 커널이 만드는 NA

정수의 `// 0`, `% 0`, `** 음수`는 결과로 쓸 정수가 없어서 그 행이 NA가 돼요. 이런 연산만 `map2<..., CanNA = true>`로 불러요. 연산 람다가 `bool& na`를 하나 더 받아 켜면 루프가 그 행의 비트를 지워요.

```cpp
// map2의 CanNA 판 (발췌)
for (std::int64_t i = lo; i < hi; ++i) {
    bool na = false;
    oo[i] = f(xx[i], yy[i], na);
    if (na) bitmap::clear(bb, i);
}
```

이 경로는 행마다 분기가 있어서 벡터화되지 않지만, 정수 나눗셈 자체가 벡터 명령이 없는 연산이라 잃는 것이 적어요. 결과가 NA가 될 수 없는 연산(나머지 전부)은 `CanNA = false` 판을 써서 이 분기가 코드에 아예 없어요. 청크가 64의 배수(16,384행)라서 두 태스크가 비트맵의 같은 바이트를 동시에 고치는 일이 없어요([병렬화와 결정성](/internals/frame/parallel/)).

### 3단계: `finish_fixed`

결과를 만드는 고정폭 커널은 모두 끝에 `finish_fixed`를 불러요.

1. **NA를 세요.** 비트맵의 1인 비트를 `popcount`로 세고, 길이에서 빼요. 바이트마다 `popcount`를 더하는 루프라 벡터화돼요.
2. **NA가 없으면 비트맵을 버려요.** 예를 들어 `s[s.notna()] + 1`처럼 NA가 있던 컬럼에서 NA를 걸러 낸 뒤의 결과에는 비트맵이 남지 않아요. 그래서 "결측이 없으면 비트맵이 없다"가 모든 결과에서 성립하고, 다음 연산이 NA 검사 없는 루프를 고를 수 있어요.
3. **NA 자리의 값을 0으로 지워요.** 커널은 NA 행도 그냥 계산했으니(예: `NA + 5`의 값 자리에 5) 쓰레기 값이 남아 있어요. 이것을 분기 없이 지워요.

세 번째 단계가 비트맵을 **바이트로 펼치는** 표를 써요. `bitmap::kExpand`는 256칸짜리 `uint64_t` 표이고, 칸 `b`에는 "바이트 `k`에 `b`의 비트 `k`(0 또는 1)"가 든 8바이트가 들어 있어요. 비트맵 1바이트로 표를 한 번 읽으면 8행 분량의 0/1 바이트가 한꺼번에 나와요.

```cpp
// column.cpp의 finish_fixed (발췌): 청크마다 펼쳐서 AND
for_chunks(col.length, [bits, v](std::int64_t lo, std::int64_t hi) {
    std::uint8_t m[kChunkRows];                       // 16 KB 스택 버퍼
    const std::int64_t len = hi - lo;
    bitmap::expand(bits + lo / 8, len, m);            // 8행씩 표 한 번
    T* w = v + lo;
    for (std::int64_t i = 0; i < len; ++i) w[i] &= static_cast<T>(0 - static_cast<T>(m[i]));
});
```

`0 - m[i]`는 값이 있으면(`m[i] = 1`) 모든 비트가 1인 수, NA면 0이에요. 그것과 AND하면 값은 그대로이거나 0이 돼요. 분기가 없어서 벡터화돼요. int64와 float64는 같은 루프예요. float64의 `0.0`은 모든 비트가 0인 수라서 정수 AND로 지워도 `+0.0`이 돼요.

### 행마다 비트를 읽는 방법과 비교

비트맵은 메모리를 행당 1비트만 써요. 대신 행 `i`의 비트를 꺼내려면 시프트와 마스크가 필요하고, 그 비트로 분기하면 위에서 본 문제가 다시 생겨요. pandas 3.1.1의 nullable 배열(`Int64`, `Float64`, `boolean`)은 행마다 1바이트짜리 numpy bool 마스크를 써서 이 문제가 없어요. `isna`가 마스크 복사 한 번이라 1M 행에 19µs예요. stardust는 메모리를 아끼는 비트맵을 저장 형식으로 두고, 계산할 때만 바이트로 펼쳐요. 두 방법을 같은 조건(1M 행, NA 10%, 1스레드)에서 비교한 값이에요.

| 연산 | 행마다 비트를 꺼내 분기 | 바이트로 펼쳐 분기 없이 |
|---|---:|---:|
| `isna` | 377 µs | 47 µs |
| `int + int` | 487 µs | 305 µs |
| `bool & bool` (Kleene) | 1.43 ms | 542 µs |
| float `std` | 1.03 ms | 475 µs |
| float `min` | 933 µs | 613 µs |

Polars 2.1.0은 Arrow 메모리 모델이라 validity가 같은 LSB 우선 비트맵이고, bool 값도 비트로 저장해요. stardust는 bool 값을 바이트로 저장해서(NEON 비교의 결과 바이트를 그대로 쓰려고) 비트맵과 값의 표현이 달라요. 그 선택은 [컬럼과 메모리](/internals/frame/columns/)에서 다뤄요.

## Kleene 논리

### 세 값의 논리

bool 컬럼끼리의 `&`, `|`는 NA를 **"참인지 거짓인지 모르는 값"**으로 보고 계산해요. 모르는 값이 무엇이든 답이 같으면 답이 정해지고, 그렇지 않으면 답도 모르는 값이에요.

- `False & NA`: NA가 True이든 False이든 `False`예요. 그래서 **False**.
- `True & NA`: NA가 True면 True, False면 False라서 정해지지 않아요. 그래서 **NA**.
- `True | NA`: 언제나 `True`. `False | NA`: **NA**.

이것이 Kleene의 (강한) 3값 논리예요 [7]. SQL의 `NULL`, pandas의 `pd.NA`, Polars의 null도 같은 규칙이에요. `^`(배타적 논리합)는 한쪽만 알아서는 답이 정해지지 않으니 어느 한쪽이라도 NA면 NA예요.

### 비트 연산으로 쓰기

행마다 값 `a`, `b`(0 또는 1)와 "값이 있음" 비트 `va`, `vb`가 있어요. 결과의 값과 "값이 있음"을 분기 없는 식으로 쓸 수 있어요.

**`&`**의 결과가 정해지는 조건은 둘 다 값이 있거나, 한쪽이 확실한 False인 경우예요.

$$
v = (v_a \land v_b) \lor (v_a \land \lnot a) \lor (v_b \land \lnot b), \qquad \text{값} = a \land b
$$

**`|`**의 결과가 정해지는 조건은 둘 다 값이 있거나, 한쪽이 확실한 True인 경우예요.

$$
v = (v_a \land v_b) \lor (v_a \land a) \lor (v_b \land b), \qquad \text{값} = a \lor b
$$

**`^`**는 $v = v_a \land v_b$, 값 $= a \oplus b$예요.

값의 식이 NA 쪽의 저장된 값과 상관없이 맞는 이유는 이래요. 한쪽이 NA인데 결과가 정해지는 경우는 `&`에서 다른 쪽이 False일 때(`0 & x = 0`)와 `|`에서 다른 쪽이 True일 때(`1 | x = 1`)뿐이에요. 어느 경우든 NA 쪽의 값은 답에 영향을 주지 않아요. 마지막에 `값 & v`로 쓰면 NA 행의 값 자리는 0이 되어 "NA 자리의 값은 0"이라는 약속도 지켜져요.

### 구현

`logic`은 두 입력의 비트맵을 `valid_bytes`로 바이트로 펼치고(비트맵이 없으면 모두 1), 연산과 스칼라 위치를 템플릿 인자로 받은 `logic_rows`가 위 식을 그대로 계산해요. 결과 비트는 8행씩 바이트 하나에 모아 써요.

```cpp
// ops/elementwise.cpp의 logic_rows (발췌, & 쪽만)
template <Op O, int Side>
void logic_rows(const uint8_t* x, const uint8_t* vx, const uint8_t* y, const uint8_t* vy,
                int64_t lo, int64_t n, uint8_t* o, uint8_t* bits) {
    for (int64_t j = lo / 8; j < bitmap::num_bytes(n); ++j) {          // 출력 비트맵의 바이트 하나
        unsigned byte = 0;
        for (int64_t i = j * 8; i < std::min(n, j * 8 + 8); ++i) {      // 8행
            const int64_t ia = Side == 1 ? 0 : i, ib = Side == 2 ? 0 : i;
            const unsigned a = x[ia], va = vx[ia], b = y[ib], vb = vy[ib];
            const unsigned value = a & b;
            const unsigned valid = (va & vb) | (va & (a ^ 1)) | (vb & (b ^ 1));
            o[i] = static_cast<uint8_t>(value & valid);                   // NA 자리는 0
            byte |= valid << (i & 7);
        }
        bits[j] = static_cast<uint8_t>(byte);
    }
}
```

- `Side`가 템플릿 인자라서 `Side == 1 ? 0 : i`도 컴파일 시점에 정해져요.
- 청크의 시작 `lo`가 64의 배수라서 출력 비트맵의 바이트 경계와 언제나 맞아요.
- NA 스칼라도 같은 식으로 처리돼요. `s | NA`의 `NA`는 값 0, `vb = 0`인 1행 bool 컬럼이라, `a`가 True인 행은 `va & a = 1`로 정해지고 나머지는 NA가 돼요. 다른 연산처럼 `and_validity`의 "NA 스칼라면 모든 행이 NA" 규칙을 타지 않는 것은 그 규칙이 Kleene에서는 틀리기 때문이에요.

```python
>>> import stardust as sd
>>> s = sd.frame.Series([True, False, None])
>>> s & sd.frame.NA
0     <NA>
1    False
2     <NA>
dtype: bool
>>> s | sd.frame.NA
0    True
1    <NA>
2    <NA>
dtype: bool
```

### pandas와의 비교

pandas 3.1.1의 `boolean` 배열은 같은 규칙을 `pandas/core/ops/mask_ops.py`의 `kleene_and`, `kleene_or`로 계산해요 [10]. 값과 마스크가 각각 numpy bool 배열이고, `~(left | left_mask)`, `~(right | right_mask)`, `(left_mask & ~right_false) | (right_mask & ~left_false)`처럼 배열 전체에 대한 numpy 연산을 여러 번 해요. 연산 하나마다 새 배열을 쓰고 읽으니 메모리를 여러 번 왕복해요. stardust는 펼친 바이트를 읽으며 한 번에 값과 비트를 내요. 같은 조건(1M 행, 1스레드)에서 이 커널의 `&`는 위 표의 542µs(NA 10%)예요.

## 정수 규칙

int64 산술의 원칙은 **값 때문에 실패하지 않는다**예요. 오버플로는 wrap하고, 정의되지 않는 결과는 NA예요.

### wrap: 부호 없는 수로 계산하기

C++에서 부호 있는 정수의 오버플로는 정의되지 않은 동작이라, 컴파일러는 "오버플로는 없다"고 가정하고 코드를 바꿀 수 있어요. 그래서 `uint64_t`로 계산하고 되돌려요. 부호 없는 산술은 $2^{64}$로 나눈 나머지로 정의되어 있고, 하드웨어 명령은 부호 있는 덧셈과 같아요. 이 기법은 배열 영역과 같은 코드 모양이에요([원소별 커널](/internals/array/elementwise/)).

```cpp
std::int64_t wrap_add(std::int64_t x, std::int64_t y) {
    return static_cast<std::int64_t>(static_cast<std::uint64_t>(x) + static_cast<std::uint64_t>(y));
}
```

### 바닥 나눗셈과 나머지

Python과 numpy의 `//`는 바닥(floor) 나눗셈이고 `%`의 결과는 나누는 수의 부호를 따라요. C++의 `/`는 0 쪽으로 자르고 `%`는 나누어지는 수의 부호를 따라서, 나머지가 있고 부호가 다를 때 한 칸 보정해요.

```cpp
// ops/elementwise.cpp (발췌)
std::int64_t int_floordiv(std::int64_t x, std::int64_t y, bool& na) {
    if (y == 0) { na = true; return 0; }          // NA
    if (y == -1) return wrap_neg(x);              // INT64_MIN // -1 == INT64_MIN (wrap)
    std::int64_t q = x / y;                       // 0 쪽으로 자름
    if (x % y != 0 && ((x < 0) != (y < 0))) --q;  // 부호가 다르면 한 칸 내림
    return q;
}

std::int64_t int_mod(std::int64_t x, std::int64_t y, bool& na) {
    if (y == 0) { na = true; return 0; }
    if (y == -1) return 0;
    std::int64_t r = x % y;
    if (r != 0 && ((r < 0) != (y < 0))) r += y;   // 나누는 수의 부호로
    return r;
}
```

나누는 수가 -1인 경우를 따로 두는 이유는 `INT64_MIN / -1`이에요. 몫 $2^{63}$이 int64를 넘어서 C++ 표준은 정의하지 않고, x86의 `idiv`는 이 입력에서 예외를 내 프로세스를 죽이고, ARM의 `sdiv`는 wrap한 값을 내요. 플랫폼마다 다른 동작에 기대지 않으려고 -1이면 나눗셈 없이 `wrap_neg(x)`(= `0 - x`를 wrap)로 계산해요. `INT64_MIN % -1`도 같은 이유로 0을 바로 돌려줘요.

**0으로 나누기는 NA예요.** 정수 몫이 없으니 값이 아니라 "모름"으로 남겨요. 다른 라이브러리는 저마다 달라요(pandas 3.1.1, Polars 2.1.0, stardust 배열 영역).

| 식 | sd.frame | sd 배열 | pandas `int64` | pandas `Int64` | Polars `i64` |
|---|:---:|:---:|:---:|:---:|:---:|
| `1 // 0` | NA | 0 | `inf` (float64로 바뀜) | 0 | null |
| `1 % 0` | NA | 1 | `NaN` (float64로 바뀜) | 0 | null |
| `2 ** -1` | NA | 0 | ValueError | ValueError | 에러 |

배열은 결측이 없어서 `a // 0 == 0`, `a % 0 == a`로 정의하고, 그래서 $a = (a \mathbin{//} b) \cdot b + a \bmod b$가 언제나 성립해요. frame에는 NA가 있으니 정의할 수 없는 값을 지어내지 않고 NA로 둬요.

```python
>>> x = sd.frame.Series([7, -7, 7, 1])
>>> y = sd.frame.Series([2, 2, -2, 0])
>>> x // y
0       3
1      -4
2      -4
3    <NA>
dtype: int64
>>> x % y
0       1
1       1
2      -1
3    <NA>
dtype: int64
```

<Callout type="warn" title="pandas의 nullable 정수는 0으로 나누면 0이에요">
pandas 3.1.1의 `Int64` 배열에서 `1 // 0`과 `1 % 0`은 NA가 아니라 값 0이에요. 그 0은 결측으로 표시되지 않아서 이후의 합이나 평균에 그대로 들어가요. stardust에서는 같은 식이 NA라서 `sum`에서 빠지고 `count`에서도 세지 않아요.
</Callout>

### 거듭제곱과 시프트

- `int ** int`는 제곱을 반복하는 방식(지수의 비트를 아래부터 보며 `base *= base`)으로 $O(\log e)$번 곱하고, 곱마다 wrap해요(numpy와 같아요). 음수 지수는 정수 결과가 없어서 NA예요.
- `<<`, `>>`는 시프트 수를 부호 없는 수로 읽어요. 64 이상(음수도 부호 없는 수로는 아주 큰 수라서 포함)이면 모든 비트가 밀려 나가서 `<<`는 0, `>>`는 부호(0 또는 -1)예요. C++에서 비트 폭 이상으로 시프트하는 것도 정의되지 않은 동작이라 검사해요. `>>`는 산술 시프트예요.

```cpp
case Op::LShift: return run([](I x, I y) { return static_cast<U>(y) >= 64 ? I{0} : static_cast<I>(static_cast<U>(x) << y); });
case Op::RShift: return run([](I x, I y) { return static_cast<U>(y) >= 64 ? (x < 0 ? I{-1} : I{0}) : x >> y; });
```

이 람다의 삼항 연산자는 분기가 아니라 비교와 선택(`CSEL`, 벡터로는 비교 + `BSL`)으로 컴파일돼서 루프가 벡터화돼요.

### bool은 int64로 바꿔 계산해요

bool의 산술(`True + True`), 단항 `-`와 `abs`, 숫자와의 비교, int64와의 비트 연산은 bool 컬럼을 `astype(int64)`로 한 번 복사한 뒤 int 커널로 보내요. 배열 영역과 같은 규칙이에요. 그래서 `bool // False`가 0으로 나누기라 NA가 되는 것처럼, int의 규칙이 따로 코드를 쓰지 않아도 그대로 적용돼요. 대가는 bool 컬럼의 복사 한 번이에요. bool끼리의 `&`, `|`, `^`만 위의 Kleene 커널이에요.

## 비교와 문자열

### int와 float의 비교

int64와 float64를 비교하면 int를 float64로 바꾼 뒤 비교해요(`compare_plain<int64_t, double>`). C++의 산술 변환이 int64를 가장 가까운 double로(짝수 쪽으로) 바꾸므로, 같은 dtype끼리 비교하는 루프와 모양이 같아요. 배열 영역, numpy, pandas와 같은 규칙이에요. $2^{53}$을 넘는 int는 반올림된 뒤 비교되므로 `Series([2**53 + 1]) == 2.0**53`은 True예요. NaN과의 비교는 IEEE 754대로 False이고 `!=`만 True예요. bool이 숫자와 만나면 bool을 int64로 올려 비교해요.

조회 `x in s`는 다른 규칙(손실 없이 같은 값이 있을 때만 True)을 쓰는데, 그것은 [라벨, 조회, 선택](/internals/frame/labels/)에서 다뤄요.

### 문자열 비교: UTF-8 바이트 순서 = 코드포인트 순서

문자열 컬럼은 UTF-8 바이트를 이어 붙인 버퍼와 offsets로 저장되어 있어요([컬럼과 메모리](/internals/frame/columns/)). 비교는 디코딩 없이 `std::string_view::compare`로 바이트를 비교해요. 이것이 Python `str`의 비교(코드포인트 순서)와 같은 답을 내는 데는 두 사실이 필요해요.

1. **UTF-8은 바이트 사전식 순서가 코드포인트 순서와 같도록 설계되었어요** [8]. 코드포인트가 클수록 첫 바이트가 크거나(길이가 다른 경우: `0xxxxxxx < 110xxxxx < 1110xxxx < 11110xxx`), 같은 길이에서는 앞 바이트부터 큰 자리를 담기 때문이에요.
2. **`char_traits<char>::compare`는 바이트를 `unsigned char`로 비교해요** [9]. `char`가 부호 있는 타입인 플랫폼에서도 `0xC3`이 `0x7A`보다 큰 것으로 비교돼요. 부호 있는 비교라면 `0x80` 이상의 바이트가 음수가 되어 한글이 ASCII보다 앞에 오는 틀린 순서가 나와요.

### 문자열 이어 붙이기: 두 번 훑기

`string + string`은 결과의 바이트 수를 미리 알 수 없어서 두 번 훑어요.

1. 청크마다 결과 바이트 수를 더해요. 청크 순서로 누적합을 내면 각 청크가 쓰기 시작할 위치가 나와요.
2. 결과 버퍼를 한 번에 할당하고, 청크마다 자기 시작 위치부터 `memcpy`로 써요. offsets는 처음부터 절대 위치로 써요.

할당이 한 번이고 청크 사이에 경쟁이 없어서 병렬로 돌아도 결과가 같아요. 1M 행 이어 붙이기는 4.46ms, pandas 3.1.1은 37.4ms예요(1스레드, Apple M4 Pro).

### float `//`와 `%`: numpy의 `npy_divmod`

float의 바닥 나눗셈을 `floor(a / b)`로 계산하면 `a / b`가 먼저 반올림되면서 정수 경계를 넘을 수 있어요. 예를 들어 `0.1`은 실제로 $0.1000000000000000055\ldots$이라 $1.0 / 0.1$의 참값은 10보다 조금 작지만, 나눗셈이 반올림되어 정확히 `10.0`이 되고 `floor`도 10이에요. numpy와 Python은 9를 내요. stardust는 numpy의 `npy_divmod`를 단계 그대로 따라요 [11]. `fmod`로 정확한 나머지를 먼저 구하고, $(a - \text{mod}) / b$를 가장 가까운 정수로 맞추고, 부호와 0의 부호를 numpy와 같게 정해요. 단계별 설명은 [원소별 커널](/internals/array/elementwise/)에 있어요. 두 영역의 코드는 같은 알고리즘이에요.

```python
>>> sd.frame.Series([1.0, -7.5]) // sd.frame.Series([0.1, 2.0])
0    9.0
1   -4.0
dtype: float64
```

## 리덕션

### 결과의 모양

`reduce(op, column, skipna, correction)`의 결과는 **1행 Column**이에요. Series는 그것을 Python 스칼라나 `NA`로 꺼내고, DataFrame은 컬럼마다 하나씩 모아 1행 DataFrame을 만들어요(행 라벨은 연산 이름). 결과 dtype은 입력 dtype으로만 정해요(`reduction_dtype`). 예를 들어 float의 `min`은 NA여도 float64 NA예요.

| 입력 | `sum` | `mean`, `var`, `std` | `min`, `max` |
|---|---|---|---|
| float64 | pairwise 합 | pairwise 합 → 나누기 / 두 번 훑기 | IEEE minimum/maximum, NEON |
| int64 | wrap하는 정수 합 | 배열 영역의 float64 합 → 나누기 | 비교와 선택, NEON |
| bool | True의 개수 (int64) | 개수 → 나누기 / 0과 1로 float 경로 | 비교와 선택 |
| string | TypeError | TypeError | 이긴 행의 슬라이스 |

- `skipna=False`이고 NA가 하나라도 있으면 계산하지 않고 NA예요.
- 값이 모자라면(모두 NA인 `mean`, `개수 - correction ≤ 0`인 `var`) NA예요. NaN은 실제 계산에서 나올 때만 결과가 돼요. NaN은 결측이 아니라 평범한 float 값이라서 `skipna`와 상관없이 전파돼요.

### float 합: pairwise 합

float의 `sum`, `mean`, `var`, `std`는 모두 numpy와 같은 **pairwise 합**으로 더해요 [1, 11]. 128개 이하의 구간은 누산기 8개가 8칸 간격으로 나눠 더하고(서로 의존하지 않는 사슬 8개), 더 긴 구간은 반(8의 배수로 내림)씩 잘라 재귀해요. 반올림 오차의 한계가 $n$이 아니라 $\log_2 n$에 비례하고, 사슬 8개가 덧셈 장치를 쉬지 않게 해요. 알고리즘, 트리 모양, 오차 한계의 유도, 여러 스레드로 같은 비트를 내는 방법(부분 트리를 태스크로 돌리고 같은 트리 모양으로 합치기)은 [집계](/internals/array/reductions/)에 자세히 있어요. 정의는 모든 영역이 함께 쓰는 `base/pairwise.hpp` 한 벌이고, frame은 항을 **접근자 람다**로 넘겨요.

```cpp
// ops/pairwise.hpp (발췌)
inline constexpr std::int64_t kPairwiseLeaf = 1 << 14;    // 병렬 태스크 하나의 최대 항 수

template <class Get>
double pairwise_sum_parallel(std::int64_t n, const Get& get, std::int64_t cost = 1) {
    if (n <= kPairwiseLeaf || n * cost < kParallelThreshold) return pairwise_sum(0, n, get);
    const pairwise::Leaves leaves = pairwise::plan(n, kPairwiseLeaf, /*complex=*/false);
    std::vector<double> part(leaves.size());
    run_unlocked(part.size(), [&](std::int64_t t) {          // GIL을 놓고 parallel_for
        part[t] = pairwise_sum(leaves[t].first, leaves[t].second, get);
    });
    return pairwise::combine(n, kPairwiseLeaf, part);
}

template <class Get>
double float_sum(std::int64_t n, const Get& get, std::int64_t cost = 1) {
    return 0.0 + pairwise_sum_parallel(n, get, cost);       // numpy reduce는 항등원 0.0에서 시작
}
```

- frame의 태스크 크기는 $2^{14}$항, 배열은 4,096항이에요. 둘 다 **같은 트리**를 서로 다른 높이에서 자른 것이라, 잎의 덧셈 하나하나가 직렬 트리와 같은 피연산자, 같은 순서예요. 그래서 비트가 같아요. frame은 병렬로 나누는 기준값이 $2^{17}$행이라 태스크도 크게 잡았어요([병렬화와 결정성](/internals/frame/parallel/)).
- **`0.0 +` 시작**: numpy의 `add.reduce`는 항등원 `+0.0`에서 시작해요. `np.sum([-0.0] * 9)`가 `-0.0`이 아니라 `+0.0`인 이유이고, stardust도 같은 시작으로 같은 값을 내요.
- 테스트(`tests/frame/test_reduce.py`)는 길이 0~5,000의 무작위 입력(NA 포함, `-0.0`, 아주 작은 값 포함)에서 `sum`, `mean`, `var`, `std`를 numpy로 한 단계씩 재현한 값과 **비트 단위로** 비교하고, NA가 없으면 pandas와도 비교해요.

### NA 자리의 0이 하는 일

float 합의 접근자는 그냥 `v[i]`예요. NA 행을 건너뛰지 않고 그 자리의 `0.0`을 더해요.

```cpp
// reduce.cpp: float sum
const double* v = c.data<double>();
return scalar(DType::Float64, float_sum(c.length, [v](std::int64_t i) { return v[i]; }));
```

`0.0`을 더해도 합은 변하지 않으니(유일한 예외인 `-0.0 + 0.0 = +0.0`은 어차피 `0.0 +` 시작이 같은 결과를 내요) 결과는 "NA를 뺀 값들의 합"이에요. 이 단순함이 세 가지를 줘요.

1. **분기가 없어요.** NA 여부를 묻지 않으니 NA가 있든 없든 같은 루프이고, 같은 속도예요. NA 10%인 1M 행 float `sum`은 86µs예요(1스레드, Apple M4 Pro). pandas의 nullable `Float64`는 마스크로 값을 골라내요.
2. **트리가 길이로만 정해져요.** NA를 빼고 남은 값만 모아 더하면 뒤쪽 값들의 트리 위치가 NA의 개수와 위치에 따라 바뀌어요. 0을 남겨 두면 트리는 $n$만으로 정해지고, 병렬 계획(`pairwise::plan`)도 $n$만 보면 돼요. 그래서 스레드 수와 상관없는 결정성이 NA가 있어도 그대로 성립해요.
3. **정답이 하나로 정해져요.** 결과는 "NA 자리에 0.0을 넣은 배열의 `np.sum`"과 비트까지 같아요.

pandas 3.1.1과의 관계는 dtype에 따라 달라요.

- **numpy 기반 `float64`(결측이 NaN):** `nanops.nansum`이 결측 자리를 0으로 채운 배열(`_get_values(..., fill_value=0)`)의 `sum`을 불러요 [10]. 같은 생각이라 stardust의 NA 있는 합과 **비트까지 같아요**. `mean`과 `var(ddof=0)`도 같은 연산을 같은 순서로 해서 비트까지 같아요.
- **nullable `Float64`(결측이 마스크):** `masked_reductions`가 `np.sum(values, where=~mask)`를 불러요. numpy 2.5.4의 `where=` 리덕션은 마스크가 True인 **연속 구간마다** pairwise 합을 구해 그것을 차례로 더한 것과 비트까지 같은 값을 내요. 구간 사이는 순차 합이라서 덧셈 경로가 구간 수만큼 길어져요. NA 비율이 $p$이면 연속 구간은 약 $n\,p\,(1-p)$개, 1M 행에 NA 10%면 약 9만 개예요. 그래서 결과의 비트가 stardust와 다르고, 오차도 커요.

[1, 2)의 균등분포 1M 개에 NA 10%를 섞어 `math.fsum`(올바르게 반올림된 정확한 합)과 비교하면, stardust의 합은 `fsum`과 같거나 상대 오차 $2 \times 10^{-16}$ 이하(마지막 비트 하나)이고, pandas `Float64`의 합은 입력에 따라 상대 오차가 $10^{-16}$에서 $2 \times 10^{-14}$까지 퍼져요(시드 0~5).

### `mean`

- **float64**: `float_sum` / NA가 아닌 개수.
- **bool**: True의 개수(정수 합) / 개수.
- **int64**: 배열 영역의 `sd.sum(x, dtype=sd.float64)` / 개수예요(`mean_of` → `interop.cpp`의 `array_sum_float64`). 컬럼 위에 읽기 전용 배열 뷰를 씌워 배열의 리덕션을 그대로 불러요. NA 행은 0이라 그대로 더해요. 그래서 `Series.mean()`과 `sd.mean(s.to_array())`가 비트까지 같아요. 배열의 형변환이 있는 합은 4,096원소 버퍼 단위로 접혀서, 긴 컬럼에서는 numpy와 마지막 비트가 다를 수 있어요([집계](/internals/array/reductions/)). int64 평균만 frame의 pairwise가 아니라 배열의 합을 쓰는 것은, 같은 데이터의 평균이 두 영역에서 같은 비트로 나오게 하려는 거예요.

### `var`와 `std`: 두 번 훑기

분산은 평균을 먼저 구하고(첫 번째 훑기), 편차 제곱 $(x_i - \bar x)^2$을 pairwise로 더해(두 번째 훑기) `개수 - correction`으로 나눠요. `std`는 그 제곱근이에요.

$$
\bar x = \frac{1}{N} \sum_{i \in \text{값}} x_i, \qquad \operatorname{var} = \frac{1}{N - c} \sum_{i \in \text{값}} (x_i - \bar x)^2
$$

교과서의 한 번 훑는 식 $\sum x_i^2 - (\sum x_i)^2/N$은 큰 두 수의 차라서 평균이 표준편차보다 크면 자릿수가 사라져요. 두 번 훑는 방법의 오차 분석(Chan, Golub, LeVeque [6])과 예는 [집계](/internals/array/reductions/)에 있어요. 한 번 훑는 Welford 갱신식도 쓰지 않아요. numpy, pandas와 다른 연산을 하니 비트가 같을 수 없어요.

두 번째 훑기는 이래요. NA 행의 값은 0이지만 $(0 - \bar x)^2$은 0이 아니니, 여기서는 NA 행을 골라 0으로 바꿔야 해요.

```cpp
// reduce.cpp (발췌)
const std::vector<std::uint8_t> m = valid_bytes(c);          // 행마다 1바이트 (NA 없으면 모두 1)
const double ssd = float_sum(c.length, [&](std::int64_t i) {
    const double d = as_double(c, i) - mean;
    return m[i] ? d * d : 0.0;                               // 선택이지 분기가 아니에요
}, 4);
const double var = ssd / (static_cast<double>(count) - correction);
```

- `m[i] ? d * d : 0.0`은 `d * d`를 언제나 계산하고 고르는 식이라 분기 없는 `FCSEL`로 컴파일돼요. 비트맵을 바이트로 펼쳐 둔 덕분이에요.
- 항은 접근자에서 바로 계산되어 트리로 흘러가므로 편차 제곱 배열을 만들지 않아요. pandas의 `nanops.nanvar`는 값 배열을 복사하고(결측 자리를 0으로), `(avg - values) ** 2`로 새 배열을 만들고, 결측 자리를 다시 0으로 바꾼 뒤 더해요. 값으로는 같은 연산을 같은 순서로 하므로 결과가 비트까지 같고, 메모리 왕복은 stardust가 적어요.
- `cost = 4`는 이 항이 덧셈 한 번보다 4배 정도 일이 많다는 뜻이에요. 병렬로 나누는 기준을 $2^{17} / 4$행으로 낮춰요. 트리는 바꾸지 않아요.
- `correction`은 배열처럼 int나 float를 받아 double로 계산해요. 기본값은 0(모분산)이고, pandas의 기본값 `ddof=1`과 달라요. NA가 없고 같은 자유도를 주면 pandas와 비트까지 같아요.

### float `min`/`max`: IEEE 754-2019의 minimum/maximum

"두 수 중 작은 것"은 NaN과 부호 있는 0 때문에 정의가 여럿이에요.

| 정의 | `min(1, NaN)` | `min(+0, -0)` | 결합법칙 | AArch64 명령 |
|---|:---:|:---:|:---:|:---:|
| C의 `x < y ? x : y` | 순서에 따라 1 또는 NaN | 순서에 따라 다름 | 아니요 | — |
| IEEE 754-2008 minNum, C의 `fmin` | 1 (NaN을 무시) | 어느 쪽이든 | signaling NaN이 끼면 아니요 | `FMINNM` |
| **IEEE 754-2019 minimum** | **NaN** (전파) | **-0** | 예 | **`FMIN`** |

stardust의 float `min`/`max`는 NaN을 전파하고 `-0.0 < +0.0`으로 보는 IEEE 754-2019의 minimum/maximum이에요 [2]. numpy의 `np.min`/`np.max`와 같은 의미예요. 이 정의는 결합법칙과 교환법칙이 정확히 성립해서, 청크별 결과를 어떤 순서로 묶어도 같은 비트가 나와요. 그리고 AArch64의 `FMIN`/`FMAX` 명령이 바로 이 정의라서 [3], 비교 셋(NaN, NaN, ±0)을 명령 하나로 해요.

```cpp
// ops/pairwise.hpp (발췌): 스칼라도 벡터 명령의 한 레인으로
template <bool Max>
double ieee_minmax(double a, double b) {
    const float64x2_t x = vdupq_n_f64(a), y = vdupq_n_f64(b);
    return vgetq_lane_f64(Max ? vmaxq_f64(x, y) : vminq_f64(x, y), 0);
}
```

스칼라 경우도 C++ 식으로 따로 쓰지 않고 같은 명령의 레인 하나로 계산해요. 그래서 벡터 경로와 스칼라 경로(루프의 나머지, 청크 결과 접기)의 의미가 어긋날 수 없어요.

- **NA가 없으면** NEON 레지스터 4개(레인 8개)를 독립 누산기로 써서 8개씩 접어요. 누산기가 하나면 `FMIN`의 지연을 매번 기다려야 하는데, 넷이면 서로의 지연을 덮어요.
- **NA가 있으면** 1,024행 블록마다 NA 행을 항등원(`min`은 `+inf`, `max`는 `-inf`)으로 바꾼 복사본을 스택 버퍼에 만들고, 그 버퍼를 같은 명령으로 접어요. 항등원은 결과를 바꾸지 않으니 "NA를 뺀 값의 min"이에요. 코드는 분기 없는 선택(`buf[k] = m[k] ? v[k] : identity`)으로 쓰여 있지만, 지금 빌드(Apple clang 21)에서는 이 선택이 행마다 조건 분기로 컴파일돼요. 그래서 NA가 흩어져 있으면 이 복사 루프에서 분기 예측 실패가 생길 수 있어요.
- 모든 행이 NA거나 비어 있으면 NA예요.

같은 조건(1M 행, 1스레드, Apple M4 Pro)에서 float `min`은 73µs, pandas 3.1.1은 325µs예요.

```python
>>> sd.frame.Series([0.0, -0.0]).min()
-0.0
>>> sd.frame.Series([1.0, float("nan"), None]).max()
nan
```

### int64·bool `min`/`max`와 정수 합

- **int64 `min`/`max`** (`plain_minmax<Max, T>`): 값의 타입을 템플릿 인자로 받아 행 루프에 dtype `switch`가 없어요. NEON에는 64비트 정수의 min/max 명령이 없어서, NA가 없는 루프는 컴파일러가 비교(`CMGT`)와 비트 선택(`BIT`/`BIF`)으로 벡터화해요. 1M 행에 119µs, numpy 2.5.4는 79µs예요(1스레드, Apple M4 Pro). 배열 영역은 손으로 짠 NEON 루프에 누산기 8개를 써서 numpy와 같은 속도를 내요([집계](/internals/array/reductions/)). frame의 이 경로는 컴파일러의 벡터화에 맡겨 두었어요. NA가 있는 경로는 행마다 비트맵의 비트를 읽고 분기해요.
- **int64 `sum`**은 `uint64_t`로 더해 wrap해요. wrap하는 덧셈은 결합법칙이 성립하므로 청크 결과를 청크 순서로 접어요. 벡터화돼요. **bool `sum`**은 0/1 바이트를 더한 True의 개수예요. bool을 바이트로 저장한 대가로 1M 행에 바이트 1M 개를 읽어요(44µs). bool을 비트로 저장하는 Polars 2.1.0은 0.09µs예요(1M 행, 1스레드).
- **string `min`/`max`**는 바이트 순서로 이긴 행(같으면 앞의 행)의 위치를 찾고, 그 행의 1행 슬라이스를 돌려줘요. 문자열을 복사하지 않아요.

청크로 나눈 리덕션은 `over_chunks`가 청크별 결과를 **청크 순서로** 접어요. 청크는 행 수만으로 정해지므로 결과가 스레드 수와 무관해요. groupby는 같은 함수(`float_sum`, `ieee_minmax`)를 그룹마다 불러서 "그 그룹의 행만 고른 `Series`의 리덕션"과 같은 비트를 내요([groupby와 정렬](/internals/frame/groupby-sort/)).

## astype

### 변환 표

`astype`은 명시적 변환이라 손실이 있어도 바꿔요. 숫자끼리의 규칙은 배열 영역의 `astype`과 같아요. NA는 그대로 NA예요.

| 원래 → 대상 | 규칙 | 실패할 수 있나 |
|---|---|:---:|
| int64 → float64 | 가장 가까운 double (짝수 쪽으로) | 아니요 |
| float64 → int64 | 0 쪽으로 자르기, 범위 밖과 ±inf는 포화, NaN → 0 | 아니요 |
| bool → int64, float64 | 0과 1 | 아니요 |
| int64, float64 → bool | 0이 아니면 True (NaN도 True) | 아니요 |
| int64 → string | `std::to_string` (Python `str(int)`과 같음) | 아니요 |
| float64 → string | Python `str(float)` | 아니요 |
| bool → string | `"True"`, `"False"` | 아니요 |
| string → int64, float64 | 엄격한 문법 (`parse.hpp`) | 예 |
| string → bool | `"True"`와 `"False"`만 | 예 |

고정폭끼리의 변환은 `convert_fixed`, 문자열에서는 `from_string`, 문자열로는 `to_string`이 맡아요. 모두 `for_chunks`로 청크마다 돌아요.

### 실패하는 행 찾기: 검사와 변환을 나누기

`convert_fixed`는 변환 람다 `f`와 "이 값이 변환되는가"를 묻는 람다 `ok`를 받아요. 청크마다 먼저 모든 행의 `ok`를 `&=`로 모으고(중간에 멈추지 않으니 분기가 없어요), 실패가 있을 때만 앞에서부터 다시 찾아 첫 실패 행을 보고해요.

```cpp
// cast.cpp의 convert_fixed (발췌)
bool all_ok = true;
for (int64_t i = lo; i < hi; ++i) all_ok &= !(m == nullptr || m[i]) || ok(in[i]);
if (!all_ok) { /* 첫 실패 행을 찾아 bad.offer(i) */ return; }
if (m == nullptr) for (int64_t i = lo; i < hi; ++i) o[i] = f(in[i]);
else              for (int64_t i = lo; i < hi; ++i) o[i] = m[i] ? f(in[i]) : To{};
```

지금 숫자끼리의 변환은 모두 실패하지 않아서 `ok`가 언제나 `true`를 돌려주는 람다이고, 검사 루프는 컴파일러가 통째로 지워요. 실패할 수 있는 변환(문자열 → 숫자)은 `from_string`이 맡는데, 여러 청크가 동시에 실패해도 **행 순서로 가장 앞의 실패**가 보고되도록 `parallel::FirstRow`를 써요. 청크마다 자기의 첫 실패 행만 내고 가장 작은 행이 이기며, 앞에서 이미 실패했으면 뒤 청크는 일찍 멈춰요(`failed_before`). 에러 메시지에는 값의 `repr`이 들어가므로 병렬 구간이 끝나고 GIL을 다시 잡은 뒤에 만들어요([병렬화와 결정성](/internals/frame/parallel/)).

### float → int64: 포화 변환

`static_cast<int64_t>(x)`는 자른 값이 int64로 표현되지 않으면(NaN, ±inf, $|x| \ge 2^{63}$) 정의되지 않은 동작이에요. stardust는 이런 값에도 하나의 결과를 정해요.

$$
\operatorname{cvt}(x) =
\begin{cases}
0 & x \text{가 NaN} \\
2^{63} - 1 & x \ge 2^{63} \\
-2^{63} & x \le -2^{63} \\
\operatorname{trunc}(x) & \text{그 밖}
\end{cases}
$$

AArch64의 `FCVTZS`(0 쪽으로 자르는 부호 있는 정수 변환) 명령이 정확히 이 규칙이라서 [3], `base/saturate.hpp`의 `saturate_to_int64`가 그 intrinsic(`vcvtd_s64_f64`) 하나예요. 명령의 정의를 따르므로 C++의 캐스트 규칙과 상관없이 모든 입력에서 정의된 결과이고, 분기도 실패하는 행도 없어요. 배열, linalg와 같은 함수예요. 이 명령을 고른 이유와 규칙을 분기 셋으로 쓴 코드와의 비교는 [변환과 승격](/internals/array/conversion/)에 있어요.

frame의 `convert_fixed`는 이 함수를 원소마다 부르는 일반 루프라서, 지금 빌드에서는 원소마다 스칼라 `FCVTZS` 하나로 컴파일되고 벡터 명령(2원소씩)으로 묶이지 않아요. intrinsic 호출은 컴파일러의 루프 벡터화기가 벡터판으로 바꾸지 못하기 때문이에요. 배열 영역의 연속 캐스트 루프는 벡터판 `vcvtq_s64_f64`를 직접 불러요.

```python
>>> sd.frame.Series([1.5, -2.7, float("nan"), 1e300]).astype("int64")
0                      1
1                     -2
2                      0
3    9223372036854775807
dtype: int64
```

pandas 3.1.1은 NaN이나 inf가 있으면 이 변환에서 에러를 내요.

### float → string: Python `str(float)`과 같은 글자

float를 문자열로 바꾸는 규칙은 Python의 `str(float)`(= `repr(float)`)이에요. 두 부분으로 나뉘어요.

1. **어떤 숫자를 쓸까:** 다시 읽으면 같은 double이 되는 가장 짧은 십진 숫자열이에요.
2. **어떻게 쓸까:** 십진 지수에 따라 고정소수점이나 지수 표기로 써요.

#### 가장 짧은 round-trip 숫자열

double 하나는 실수 하나를 정확히 나타내요. `0.1`이라고 쓴 double의 실제 값은 $0.10000000000000000\allowbreak 55511151231257827\ldots$이에요. 하지만 그 double로 반올림되는 실수는 한 점이 아니라 **구간**이에요. 이웃한 두 double의 가운데까지가 모두 그 double로 읽혀요.

$$
\Big[\, v - \tfrac{1}{2}(v - v^{-}),\;\; v + \tfrac{1}{2}(v^{+} - v) \,\Big]
$$

`0.1`의 구간은 $[0.09999999999999999861\ldots,$ $0.10000000000000001249\ldots]$예요. 이 안에 `0.1`이라는 한 자리 숫자가 있으니 `"0.1"`이라고 쓰면 다시 읽어도 같은 double이에요. 반면 `0.1 + 0.2`의 결과(실제 값 $0.30000000000000004440\ldots$)의 구간은 $[0.30000000000000001665\ldots,$ $0.30000000000000007216\ldots]$이라 16자리 이하의 숫자(`0.3`, `0.3000000000000001` 등)는 들어가지 않고, 17자리 숫자 `0.30000000000000002`부터 `0.30000000000000007`까지 여섯 개가 들어가요. 이렇게 가장 짧은 후보가 여럿이면 실제 값에 가장 가까운 `0.30000000000000004`를 골라요.

C++17의 `std::to_chars(first, last, value)`(정밀도 인자가 없는 판)는 바로 이것을 요구해요. 표준의 문구는 "다시 읽으면 값이 정확히 복원되는 **가장 적은 글자 수**의 표현, 그런 표현이 여럿이면 값과의 차이가 가장 작은 것, 그래도 같으면 `round_to_nearest`로" [4]예요. 출력 글자가 하나로 정해지므로, 표준을 따르는 구현이라면 내부 알고리즘이 무엇이든 같은 문자열을 내요. Python의 `repr(float)`도 David Gay의 `dtoa`(mode 0, "다시 읽어 같은 값이 되는 가장 짧은 문자열")로 같은 문제를 풀어요 [5]. 그래서 유한한 모든 double에서 두 결과의 숫자열이 같아요(NaN과 무한대는 `nan`, `inf`로 따로 써요).

#### libc++ 안의 알고리즘: Ryu

stardust는 `std::to_chars(buf, end, d, std::chars_format::scientific)`을 불러요(`cast.cpp`의 `python_float_str`). macOS에서는 시스템의 libc++(`/usr/lib/libc++.1.dylib`)가 이 함수를 제공해요. LLVM libc++의 소스를 따라가면 이래요.

- `src/charconv.cpp`의 `to_chars(double, chars_format)`은 `_Floating_to_chars<_Format_only>`로 넘겨요.
- `src/include/to_chars_floating_point.h`(Microsoft STL의 구현을 옮겨 온 파일)의 `_Floating_to_chars`는 16진수가 아니면 `_Floating_to_chars_ryu`를 불러요.
- `src/include/ryu/ryu.h`의 `_Floating_to_chars_ryu`는 double이면 `__d2s_buffered_n`을 불러요. 이 코드는 Ulf Adams의 Ryu(GitHub `ulfjack/ryu`)에서 왔어요 [12].
- `src/ryu/d2s.cpp`의 `__d2s_buffered_n`이 0과 작은 정수를 따로 처리하고, 나머지는 `__d2d`로 가장 짧은 십진수를 구한 뒤 `d.ddde±XX` 꼴로 써요.

Apple이 배포하는 시스템 libc++는 LLVM 소스와 빌드가 다를 수 있지만, 표준이 출력을 하나로 정해 두었으므로 결과는 같아요.

Ryu는 Adams가 PLDI 2018에서 발표한 알고리즘이에요 [12]. Gay의 `dtoa`는 부동소수점으로 계산하는 빠른 길이 실패하면 임의 정밀도 정수(`Bigint`) 산술로 넘어가요. Ryu는 고정 폭 정수 연산(64비트 곱과 그것으로 만든 128비트 곱)과 미리 계산한 표만으로 **모든 double에서** 올바른 결과를 낸다는 것이 증명되어 있어서, 느린 대체 경로가 없어요. `__d2d`의 단계는 이래요.

1. **구간의 세 점을 정수로.** double을 $v = m_2 \cdot 2^{e_2}$(가수 $m_2$는 숨은 비트를 포함한 53비트)로 풀고, 반 간격을 정수로 다루려고 지수를 2 줄여 네 배 한 정수 셋을 만들어요. 가운데 $m_v = 4m_2$, 위쪽 경계 $m_p = 4m_2 + 2$, 아래쪽 경계 $m_m = 4m_2 - 1 - s$예요. 보통은 $s = 1$이라 구간이 대칭($\pm 2$)이지만, 가수가 $2^{52}$인 수(2의 거듭제곱)는 아래쪽 이웃이 절반만큼 가까워서 $s = 0$이에요(`mmShift`). $m_2$가 짝수면 경계값 자체도 짝수 쪽 반올림으로 $v$에 오므로 닫힌 구간으로 봐요(`acceptBounds`).
2. **십진수로 바꾸기.** 세 정수에 $2^{e_2}$를 곱한 값을 $10^{q}$로 나눈 몫을 구해요. 결과가 64비트 정수에 들어가는 십진 정수가 되도록 $q$를 고르는데, $e_2 \ge 0$이면 $q \approx \lfloor e_2 \log_{10} 2 \rfloor$이고 $2^{e_2}/10^{q} = 2^{e_2 - q}/5^{q}$라서 $5^{-q}$의 근사값을, $e_2 < 0$이면 $5^{-e_2-q}$의 근사값을 곱하고 시프트해요. 근사값은 122비트(역수)와 121비트로 자른 표(`__DOUBLE_POW5_INV_SPLIT`, `__DOUBLE_POW5_SPLIT`)에서 읽고, 곱은 64×128비트 곱셈 후 시프트(`__mulShiftAll`)예요. 이 정밀도면 몫의 내림이 언제나 정확하다는 것이 논문의 핵심 정리예요. 결과는 십진 정수 $v_m < v_r < v_p$와 공통 지수 $e_{10}$이에요.
3. **자릿수 지우기.** $v_p$와 $v_m$을 10으로 나눈 몫이 다르면, 구간 안에 끝자리가 0인 수가 있다는 뜻이니 한 자리를 지울 수 있어요. 세 수를 모두 10으로 나누고 지운 자리 수만큼 지수를 올려요. 몫이 같아지면 멈춰요. 이때 $v_r$이 그 길이에서 값에 가장 가까운 후보예요. 마지막으로 지운 숫자가 5 이상이면 $v_r$을 하나 올려요. 흔한 경우(약 99.3%)는 두 자리씩 지우는 빠른 루프로 가요.
4. **경계가 정확할 때.** $v_m$이나 $v_r$이 정확히 나누어떨어지는 드문 경우는 지운 숫자가 모두 0이었는지를 따로 추적해서, 닫힌 구간의 경계를 받아들일지와 정확히 가운데인 경우의 짝수 쪽 반올림을 정해요.
5. **작은 정수의 빠른 길.** 값이 $2^{53}$ 아래의 정수면(`__d2d_small_int`) 위 과정 없이 가수를 시프트한 정수에서 끝의 0만 지수로 옮겨요.

#### Python의 형식으로 다시 쓰기

`to_chars`의 지수 표기 결과(예: `1.2345678901234568e+17`)에서 숫자열과 십진 지수를 떼어 낸 뒤, CPython `format_float_short`의 `repr` 규칙대로 다시 써요 [5]. `decpt`를 "값 $= 0.d_1 d_2 \ldots \times 10^{\text{decpt}}$"의 지수라고 하면,

- `decpt` $\le -4$이거나 $> 16$이면 지수 표기 `d.ddde±XX`(지수는 최소 두 자리)
- 그 밖에는 고정소수점. 정수 값이면 `.0`을 붙여요.
- NaN은 `nan`, 무한대는 `inf`, `-inf`. 부호 있는 0은 `-0.0`이에요.

| double | 문자열 |
|---|---|
| `0.1 + 0.2` | `0.30000000000000004` |
| `1e16` | `1e+16` (decpt = 17) |
| `1e15` | `1000000000000000.0` (decpt = 16) |
| `1e-05` | `1e-05` (decpt = -4) |
| `0.0001` | `0.0001` (decpt = -3) |
| `5e-324` (가장 작은 비정규수) | `5e-324` |

```python
>>> sd.frame.Series([0.1 + 0.2, 1e16, 1e-5, 123.0]).astype("string")
0    0.30000000000000004
1                  1e+16
2                  1e-05
3                  123.0
dtype: string
```

#### 문자열 결과를 청크로 만들기

결과 문자열의 바이트 수를 미리 알 수 없으니 청크마다 자기 `std::string`에 쓰고 offsets는 청크 기준으로 적어요. 그다음 청크별 바이트 수의 누적합으로 각 청크의 시작 위치를 정하고, 결과 버퍼를 한 번에 할당해 청크마다 자기 자리에 복사하면서 offsets에 시작 위치를 더해요. 숫자 하나의 서식화가 덧셈보다 훨씬 비싸서 `cost = 16`으로 일찍 병렬로 나눠요.

## 엄격한 문자열 문법

### 문법

문자열 → 숫자 변환은 Python의 `int()`, `float()`보다 좁은 ASCII 문법만 받아요.

```text
int64   :=  [+-]? digit+                                    (int64 범위 안)
float64 :=  [+-]? ( digit+ ( "." digit* )? | "." digit+ ) ( [eE] [+-]? digit+ )?
         |  [+-]? ( "nan" | "inf" | "infinity" )            (대소문자 무관)
digit   :=  "0" … "9"                                       (ASCII만)
```

| 글자 | int64 | float64 | Python `int()` | Python `float()` |
|---|:---:|:---:|:---:|:---:|
| `"12"`, `"+5"`, `"-0"` | 받음 | 받음 | 받음 | 받음 |
| `"1e5"`, `"1."`, `".5"`, `"+.5e-3"` | 에러 | 받음 | 에러 | 받음 |
| `"NaN"`, `"INF"`, `"-Infinity"` | 에러 | 받음 | 에러 | 받음 |
| `"1e400"` | 에러 | `inf` | 에러 | `inf` |
| `" 1"` (앞뒤 공백) | 에러 | 에러 | 받음 | 받음 |
| `"1_000"` (밑줄) | 에러 | 에러 | 받음 | 받음 |
| `"١٢"` (아랍-인도 숫자) | 에러 | 에러 | 받음 (12) | 받음 |
| `"9223372036854775808"` | 에러 (범위 밖) | 받음 | 받음 | 받음 |
| `"."`, `"e5"`, `"1.5e"`, `"0x10"` | 에러 | 에러 | 에러 | 에러 |

받는 글자의 값은 Python과 같아요. float는 올바르게 반올림되어 Python `float(text)`와 비트까지 같고, 범위를 넘으면 `±inf`, 아주 작으면 `±0.0`이나 비정규수예요.

### 좁게 받는 이유

- **`astype`과 `read_csv`가 같은 문법이에요.** 두 함수가 `parse.hpp` 한 파일을 써요. `read_csv(..., dtype="string")`으로 읽은 뒤 `astype("float64")`를 해도, 처음부터 추론하게 둔 것과 같은 값이 나오거나 같은 글자에서 에러가 나요. CSV의 타입 추론("이 열의 모든 필드가 int 문법이면 int64")도 같은 문법이 정해요.
- **데이터의 이상을 숨기지 않아요.** 앞뒤 공백, 밑줄, 다른 문자 체계의 숫자가 숫자 열에 섞여 있다면 대개 데이터를 만든 쪽의 문제예요. 그것을 조용히 숫자로 읽으면 추론된 dtype과 값이 입력의 사소한 차이에 따라 달라져요. 받지 않으면 에러 메시지가 그 행을 가리켜요.
- **바이트만 보고 판단할 수 있어요.** ASCII 문법이라 유니코드 표 없이 바이트 비교로 파싱하고, 아래처럼 8바이트씩 한 번에 읽을 수 있어요.

### 한 번에 검사하고 읽기

문법 검사와 값 계산을 따로 하면 글자를 두 번 읽어요. `parse.hpp`는 한 번 훑으며 둘을 함께 해요.

- **`parse_int64(text, v)`**는 1(int64), 0(문법에 맞지 않음), -1(문법은 맞지만 int64 범위 밖)을 돌려줘요. 숫자를 읽으며 `uint64_t`에 쌓고, 앞의 0을 뺀 유효 자릿수가 19를 넘으면 범위 밖이 확실하니 -1, 아니면 $2^{63} - 1$(음수면 $2^{63}$)과 비교해요. CSV 추론은 -1과 0을 구분해서 쓰고(범위 밖 정수는 float64 후보로 남아요), `astype`은 1만 성공으로 봐요.
- **`parse_decimal(text, d)`**는 `Ok`, `Bad`, `Slow` 중 하나예요. 부호, 정수부, 소수부, 지수를 읽으며 십진 가수 $w$(최대 19자리)와 지수 $q$로 모아요. `Bad`는 문법에 맞지 않는 글자, `Slow`는 문법에는 맞을 수 있지만 이 빠른 길이 맡지 않는 경우(`nan`/`inf`, 유효 숫자가 19자리를 넘는 수, 아래 Eisel–Lemire가 판정하지 못한 수)예요.
- `Slow`면 `float_grammar`로 문법을 따로 확인하고 `slow_double`로 읽어요. `slow_double`은 `std::from_chars`를 부르고, 범위를 넘어 `result_out_of_range`가 나오면 `strtod`로 다시 읽어 `±inf`나 `±0.0`, 비정규수를 받아요. LLVM libc++의 소스에서 `from_chars`(double)는 글자를 가수와 지수로 읽은 뒤 LLVM libc의 `decimal_exp_to_float`에 변환을 맡겨요.

$w \cdot 10^{q}$를 올바르게 반올림된 double로 바꾸는 부분은 Clinger의 빠른 길(두 수가 모두 double로 정확하면 IEEE 곱셈이나 나눗셈 한 번)과 Eisel–Lemire 알고리즘(5의 거듭제곱을 128비트로 자른 표와 128비트 곱 한 번)이에요. 그리고 숫자 여덟 개를 8바이트 정수 하나로 읽어 곱셈 세 번으로 8자리 십진수로 바꾸는 SWAR 기법으로 숫자를 읽어요 [13]. 이 셋은 CSV 파싱의 중심이라 [read_csv](/internals/frame/csv/)에서 자세히 다뤄요.

문자열 → bool은 `"True"`와 `"False"`만 받아요. `"true"`, `"1"`, `"yes"`는 에러예요.

```python
>>> sd.frame.Series(["1e5", ".5", "NaN", "-Infinity"]).astype("float64")
0    100000.0
1         0.5
2         NaN
3        -inf
dtype: float64
>>> sd.frame.Series(["7", " 8"]).astype("int64")
Traceback (most recent call last):
    ...
ValueError: astype(): cannot convert string ' 8' to int64
```

## 벡터화를 막는 앨리어싱

위의 루프 발췌에는 `const auto xx = x;`, `R* oo = o;`처럼 이미 있는 값을 지역 변수로 다시 담는 줄이 자주 보여요. 군더더기처럼 보이지만, 빼면 루프가 벡터화되지 않고 몇 배 느려져요. 원인은 C++의 앨리어싱 규칙이에요.

### 규칙: `uint8_t`로 쓰면 무엇이든 바뀔 수 있어요

C++은 서로 다른 타입의 포인터가 같은 메모리를 가리키지 않는다고 가정해도 되게 해요(타입 기반 앨리어싱, `[basic.lval]`) [9]. 컴파일러는 `double*`로 쓴 값이 `int64_t` 변수를 바꾸지 않는다고 보고 최적화해요. 예외가 있어요. **`char`, `unsigned char`, `std::byte`로는 어떤 객체든 읽고 쓸 수 있어요.** 그래서 이 타입의 포인터로 쓰면 컴파일러는 "이 쓰기가 아무 객체나 바꿨을 수 있다"고 가정해야 해요. `uint8_t`는 `unsigned char`의 다른 이름이에요. frame은 bool 값, 펼친 비트맵, 비트맵 바이트를 모두 `uint8_t`로 다뤄요.

### 경우 1: 참조로 읽는 루프 경계

```cpp
struct C { int64_t length; };

void bad(const C& c, const uint8_t* in, uint8_t* out) {
    for (long i = 0; i < c.length; ++i) out[i] = in[i] ^ 1;     // 벡터화 안 됨
}
void good(const C& c, const uint8_t* in, uint8_t* out) {
    const long n = c.length;                                     // 지역 변수로 한 번
    for (long i = 0; i < n; ++i) out[i] = in[i] ^ 1;             // 바이트 16개 × 4씩
}
```

`bad`에서 `out[i]`에 쓰는 순간 `c.length`가 바뀌었을 수도 있어요(`out`이 `c`를 가리킬 수 있으니까요). 컴파일러는 매 반복 `c.length`를 메모리에서 다시 읽어야 하고, 반복 횟수를 루프에 들어가기 전에 알 수 없어요. 루프 벡터화기는 반복 횟수를 미리 계산할 수 있어야 여러 행을 묶을 수 있어서 포기해요. 같은 컴파일러(Apple clang 21, `-O3 -mcpu=native`)의 보고는 `bad`에 "Cannot vectorize uncountable loop", `good`에 "vectorized loop (vectorization width: 16, interleaved count: 4)"예요. `isna`에서 이 차이는 288µs와 48µs예요(1M 행, NA 10%, 1스레드). 그래서 `finish_fixed`, `isna`, `convert_fixed` 같은 `uint8_t` 루프는 경계와 포인터를 지역 변수로 꺼내 둬요.

표준 C++에는 C의 `restrict`(이 포인터만 이 메모리에 닿는다는 약속)가 없어요. 컴파일러 확장 `__restrict` 대신 지역 변수로 꺼내는 방법을 써요. 지역 변수는 주소가 밖으로 새지 않는 한 어떤 포인터로도 닿을 수 없다는 것을 컴파일러가 스스로 알아요.

### 경우 2: 람다의 캡처는 클로저 객체의 멤버예요

값으로 캡처한 변수는 지역 변수처럼 보이지만, 실제로는 **클로저 객체의 멤버**예요. 람다 몸통은 그 객체의 `operator()`이고, 캡처한 `o`를 읽는 것은 `this->o`를 메모리에서 읽는 것이에요. 게다가 `for_chunks`가 병렬로 돌 때 태스크는 `std::function`을 거쳐 불리므로 클로저 객체가 메모리에 있어요. 루프 안에서 `uint8_t*`로 쓰면 그 쓰기가 클로저 객체의 `o`를 바꿨을 수 있으니 매 반복 다시 읽어요.

```cpp
// selection.cpp의 isna (발췌)
for_chunks(col.length, [b, o, flip](std::int64_t lo, std::int64_t hi) {
    std::uint8_t* out = o + lo;              // 캡처를 태스크 안의 지역 변수로
    const std::int64_t len = hi - lo;
    bitmap::expand(b + lo / 8, len, out);
    if (flip)
        for (std::int64_t i = 0; i < len; ++i) out[i] ^= 1;
});
```

캡처 `[o, flip]`을 루프에서 바로 쓰면 1스레드 `isna`가 276µs, 태스크 안에서 지역 변수로 옮기면 44µs예요. `map2`의 `const auto xx = x; const auto yy = y; R* oo = o;`도 같은 이유예요.

### 경우 3: 연산은 함수 포인터가 아니라 람다로

`int_arith`가 `wrap_add` 같은 함수를 이름으로 넘기지 않고 `[](I x, I y) { return wrap_add(x, y); }`로 감싸는 이유예요. 함수 포인터를 넘기면 루프를 가진 템플릿은 "어떤 `int64(int64, int64)` 함수"로 한 번만 인스턴스화돼요. 직렬 루프라면 컴파일러가 그 포인터가 상수임을 따라가 인라인할 수 있지만, 태스크 몸통은 `std::function` 뒤에서 따로 컴파일되어 포인터가 런타임 값이 되고, 행마다 **간접 호출**이 남아요. 간접 호출이 있는 루프는 벡터화되지 않아요. 같은 조건에서 `int + int`가 함수 포인터로는 854µs, 람다로는 293µs예요. 람다는 타입마다 고유해서 루프가 연산마다 따로 인스턴스화되고, 연산이 루프 안에 인라인돼요.

### 경우 4: 참조로 잡은 Column

`Column`을 참조로 캡처한 람다가 루프 안에서 `c.data<T>()`나 `c.length`를 읽는 것도 경우 1, 2와 같은 문제예요. int64 저장 하나가 그 Column의 포인터 멤버를 바꿀 수 있다고 보고 매번 다시 읽어요. 조회 루프(`find_rows`)에서 이 문제를 피하는 방법은 [해시 테이블과 factorize](/internals/frame/hashing/)에 있어요.

<Callout type="tip" title="벡터화 여부를 확인하는 방법">
clang에 `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize`를 주면 루프마다 벡터화했는지, 못 했다면 왜인지를 줄 번호와 함께 알려 줘요. 위의 "uncountable loop", "call instruction cannot be vectorized", "the cost-model indicates that vectorization is not beneficial" 같은 문구가 이 보고예요.
</Callout>

1M 행 `float + float`는 pandas의 ⟦FBENCH "float + float" 1M pandas/sd@1⟧배(1스레드), `float sum`은 ⟦FBENCH "float sum" 1M pandas/sd@1⟧배예요. 원인은 이래요.

- **큰 데이터는 메모리 대역폭이 정해요.** `float + float` 1M 행은 16MB를 읽고 8MB를 써요. 커널은 벡터화된 루프 하나라 계산은 메모리를 기다리는 시간 아래에 숨어요. 10스레드는 코어마다 대역폭을 나눠 쓰다 대역폭 한계에 가까워지면 더 늘지 않아요. 합은 8MB를 한 번 읽고, pairwise의 사슬 8개 덕분에 덧셈의 지연이 드러나지 않아요.
- **작은 데이터는 호출 비용이 정해요.** 10행과 1천 행에서는 Python 층(인자 검사, 1행 Column 만들기, 결과 Series 만들기)과 nanobind 경계의 고정비가 시간의 대부분이에요. 이 비용과 그것을 줄인 방법은 [성능과 검증](/internals/frame/performance/)에 있어요.
- **10만 행은 1스레드예요.** 병렬로 나누는 기준값이 $2^{17}$ = 131,072행이라 10만 행은 호출 스레드에서 돌아요([병렬화와 결정성](/internals/frame/parallel/)).

## 정확도

| 연산 | 비트까지 같은 상대 | 조건 |
|---|---|---|
| float `+ - * /`, 비교 | numpy, pandas | `-ffp-contract=off`로 FMA 합치기를 막아요 |
| float `//`, `%` | numpy, pandas | `npy_divmod`의 단계 그대로 |
| int64 산술 | numpy, Python (wrap, 바닥 나눗셈) | 0으로 나누기와 음수 지수만 NA |
| float `sum`, `mean`, `var`, `std` | numpy를 한 단계씩 재현한 값 | 언제나. NA 자리는 0.0으로 |
| 〃 | pandas `float64` | 언제나(같은 자유도). nullable `Float64`와는 NA가 없을 때만 |
| int64 `mean` | 배열 영역의 `sd.mean` | 언제나. numpy와는 짧은 컬럼에서 |
| float `min`, `max` | numpy | NaN 전파, `-0.0 < 0.0` |
| float → string | Python `str(float)` | 모든 double |
| string → float | Python `float(text)` | 받는 문법 안의 모든 글자 |
| 모든 결과 | 1스레드의 결과 | 스레드 수와 무관 (청크와 트리가 길이로만 정해짐) |

float 합의 오차 한계는 $\gamma_h \sum |x_i|$, $h \lesssim 24 + \lceil \log_2(n/128) \rceil$이에요(1M 행이면 $h \lesssim 37$, 유도는 [집계](/internals/array/reductions/)). NA 자리의 0은 덧셈 경로를 늘리지 않아요. 트리의 모양이 NA와 상관없이 길이로만 정해지기 때문이에요.
