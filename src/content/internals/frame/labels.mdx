## 한눈에 보기

Series와 DataFrame의 행에는 **라벨**이 붙어 있어요. 라벨은 두 가지 일을 해요. 하나는 `s.loc["b"]`처럼 라벨로 행을 고르는 것(조회)이고, 다른 하나는 `a + b`처럼 두 Series를 더할 때 같은 라벨끼리 짝짓는 것(정렬, alignment)이에요. 이 글은 그 두 일과, 그 결과로 행을 실제로 옮기는 커널을 다뤄요.

| 하는 일 | 어디서 | 핵심 |
|---|---|---|
| 라벨 보관 | `_index.py`의 `RangeIndex`, `Index` | RangeIndex는 정수 셋, Index는 불변 Column 하나 |
| 라벨 → 위치 | `ops/hash.hpp`의 `LabelTable` | 라벨을 factorize한 결과(코드, 첫 위치, CSR)를 Index에 캐시 |
| 두 라벨 집합 맞추기 | `_select.py`의 `align` | 같은 Index면 위치대로, 아니면 해시 조회 두 번으로 합집합과 위치 배열 |
| 키 → 선택 | `_select.py`의 `by_label`, `by_position` | 키를 "하나 / 슬라이스 / take / 마스크" 넷 중 하나로 |
| 행 옮기기 | `ops/selection.cpp`의 `take`, `filter`, `set_rows` | 위치 -1은 NA, 분기 없는 압축, Copy-on-Write 대입 |

설계의 뼈대는 네 가지예요.

- **라벨 조회는 factorize 위에 있어요.** "두 라벨이 같은가"를 정하는 코드는 unique, groupby, merge가 쓰는 factorize 하나뿐이에요. 조회 엔진은 라벨 컬럼을 factorize한 결과를 저장해 둘 뿐이에요. 해시 테이블 자체는 [해시 테이블과 factorize](/internals/frame/hashing/)가 자세히 다뤄요.
- **결과의 모양은 키의 모양으로 정해요.** 슬라이스로 고르면 버퍼를 공유하고 RangeIndex가 RangeIndex로 남아요. 리스트나 마스크로 고르면 복사이고 결과 라벨은 Index예요. 마스크가 우연히 연속된 행을 골라도, 남은 라벨이 우연히 등차수열이어도 마찬가지예요.
- **조회는 데이터를 보고 경로를 고르지 않아요.** 정렬된 Index에서 이진 탐색을 하거나, 고유한 Index에서 빠른 길로 가는 일이 없어요. 같은 코드는 데이터와 상관없이 같은 타입의 결과를 같은 방식으로 내요. 데이터를 보는 길은 결과가 어느 길이든 같을 때만 둬요(`df[mask]`가 남는 행의 비율로 압축과 모으기 중 하나를 고르는 것처럼).
- **행을 옮기는 커널은 셋뿐이에요.** 위치로 모으는 `take`, 마스크로 압축하는 `filter`, 위치에 쓰는 `set_rows`예요. reindex, 정렬, merge, sort, groupby의 `first`/`last`가 모두 `take` 위에 있어서, 그 연산들은 dtype마다 따로 코드를 갖지 않아요.

이 글의 수치는 따로 적지 않으면 Apple M4 Pro 한 대에서 1스레드로 잰 호출당 최솟값이에요. pandas·Polars와 비교하는 수치는 버전을 적어요(pandas 3.1.1, Polars 2.1.0).

## RangeIndex와 Index

### RangeIndex: 정수 셋

라벨을 따로 주지 않으면 행 라벨은 `0, 1, 2, …`예요. 이런 라벨을 실제로 배열에 담아 두면 1M 행이면 8MB예요. 그래서 `RangeIndex`는 `(start, stop, step)` 세 정수만 저장해요. Python의 `range` 객체 하나예요.

- 스칼라 조회와 `in`은 산술이에요. `5 in idx`는 `range`의 `in`(나눗셈 한 번)이고, `idx._position_of(5)`는 `range.index(5)`예요. 라벨 배열도 해시 테이블도 만들지 않아요. `5 in RangeIndex(30_000_000)`을 해시 테이블로 답하면 라벨 3천만 개와 테이블을 만드는 데 158ms가 들어요.
- `_position_of`는 라벨을 `operator.index`로 Python `int`로 바꾼 뒤 `range`에 물어요. `range`는 정확히 `int`일 때만 산술로 답하고, numpy 정수(`np.int64(5)`)를 받으면 처음부터 훑어요. 3천만 행이면 1.5초예요.
- 라벨을 한꺼번에 봐야 할 때만 라벨 배열을 만들어요. 정렬(alignment), 여러 라벨 조회, 두 Index 비교(`equals`)가 그래요. 이때 `_column()`이 `arange(start, step, n)` 커널로 int64 Column을 만들고, 조회 엔진이 필요하면 그 위에 만들어 캐시해요.
- 위치로 고른 결과의 라벨은 산술로 만들어요. `_take(positions)`는 `positions × step + start`를 원소별 커널 두 번으로 계산해요. 기본 RangeIndex(`start = 0`, `step = 1`)라면 위치 배열 자체가 라벨이에요. 곱하고 더할 필요도 없이, 위치 Column을 그대로 결과 Index의 라벨로 써요. Column은 불변으로 다루므로 공유해도 안전해요.

```python
>>> s = sd.frame.Series([10, 20, 30, 40])
>>> s.iloc[1:3].index
RangeIndex(start=1, stop=3, step=1)
>>> s.iloc[[1, 2, 3]].index
Index([1, 2, 3], dtype=int64)
>>> s[s > 15].index
Index([1, 2, 3], dtype=int64)
```

슬라이스로 고른 결과는 RangeIndex로 남지만, 리스트나 마스크로 고른 결과는 남은 라벨이 `1, 2, 3`으로 등차수열이어도 Index예요. 결과 타입을 남은 라벨이 등차수열인지 보고 정하면, 같은 코드가 어떤 날은 RangeIndex를 돌려주고 어떤 날은 Index를 돌려줘요. 그 차이는 다음 연산(슬라이스가 복사인지, 조회가 산술인지)으로 번지고 성능까지 바꿔요. 그래서 결과 타입은 키의 모양으로만 정해요.

슬라이스의 결과 라벨은 위치에서 산술로 만들어요. 위치 슬라이스는 `slice.indices(n)`이 `(start, stop, step)` 위치로 바꿔 주는데(아래 "위치 키"), 0번 위치까지 내려가는 역순 슬라이스 `::-1`이면 `stop`이 `-1`이에요. 여기서 `-1`은 "0번 앞"이라는 뜻이에요. 이것을 `range`의 슬라이스에 그대로 넣으면 Python은 `-1`을 "마지막 원소"로 읽어서, 길이 4에서 `range(0, 4)[3:-1:-1]`이 빈 `range(3, 3, -1)`이 돼요. 그래서 `_slice`는 `range`를 다시 자르지 않고 개수와 첫 라벨로 새 `range`를 만들어요.

```python
# src/stardust/frame/_index.py, RangeIndex._slice (발췌)
def _slice(self, start, stop, step=1):    # 위치 range(start, stop, step)의 라벨
    r, count = self._range, len(range(start, stop, step))   # 위치의 개수: -1은 "0번 앞"
    first = r.start + start * r.step                        # 첫 위치의 라벨
    return RangeIndex._from_range(range(first, first + count * step * r.step, step * r.step), self._name)
```

라벨의 간격은 위치의 간격 `step`에 원래 간격 `r.step`을 곱한 것이고, 끝은 첫 라벨에서 그 간격으로 `count`번 간 자리예요. 라벨 `100, 110, 120, 130`에서 `::-2`면 위치 3, 1이고 라벨은 `130, 110`, 결과는 `range(130, 90, -20)`이에요.

```python
>>> s.iloc[::-1].index
RangeIndex(start=3, stop=-1, step=-1)
>>> s.iloc[::-1].index.tolist()
[3, 2, 1, 0]
```

### Index: 불변 Column 하나

`Index`는 int64나 string Column 하나와 이름으로 이뤄져요. Column은 [컬럼과 메모리](/internals/frame/columns/)에서 설명한 그 Column이고, Index에서는 NA가 없어요.

- float와 bool은 Index가 될 수 없어요. 라벨로 고를 때 라벨의 타입이 Index의 dtype과 맞아야 해요(`int` Index에 `10.0`이나 `True`는 TypeError). 같은 키의 규칙이 dtype마다 다르기 때문이에요. int64 키는 비트가 같으면 같고, float 키는 NaN끼리, `-0.0`과 `0.0`이 같아요. 라벨 dtype을 int64와 string으로 묶어 두면 조회가 언제나 "같은 dtype의 키를 같은 dtype의 테이블에서 찾기"가 되어 변환 규칙이 끼어들 틈이 없어요.
- Index는 불변이에요. 라벨을 바꾸는 메서드가 없고, 안의 Column을 고치는 경로도 없어요. 그래서 조회 엔진을 한 번 만들어 Index에 매달아 두면 무효화할 일이 없어요.
- Index는 값이 아니에요. `==`, `!=`는 TypeError이고 라벨 비교는 `equals()`로 해요. `equals`는 RangeIndex끼리면 `range` 비교(세 정수), 그 밖에는 두 Column을 원소별로 비교하는 `equals` 커널이에요(청크 병렬, 다른 원소를 찾으면 일찍 멈춤).
- `in`은 Series의 `in`과 같은 규칙이에요. 값을 그 dtype으로 손실 없이 바꿀 수 있을 때만 찾아요. 그래서 `1.0 in Index([1, 2])`는 True예요. 반면 `.loc[1.0]`은 TypeError예요. `in`은 "이 값과 같은 라벨이 있는가"라는 질문이라 타입이 달라도 True나 False로 답할 수 있지만, `.loc`은 행을 고르는 일이라 타입이 맞지 않는 라벨은 대부분 실수이기 때문이에요.

```python
>>> 1.0 in sd.frame.Index([1, 2])
True
>>> sd.frame.Series([1, 2], index=[1, 2]).loc[1.0]
Traceback (most recent call last):
    ...
TypeError: a label of an int64 index must be an int, not float
```

### 중복 라벨

Index는 중복 라벨을 허용해요. 대신 중복이 의미를 흐리는 곳에서는 에러를 내요.

- `.loc["a"]`(라벨 하나)는 언제나 스칼라를 돌려줘요. `"a"`가 두 행에 있으면 KeyError이고, 모두 원하면 `.loc[["a"]]`처럼 리스트로 고르라고 메시지가 알려 줘요.
- 정렬(alignment)은 두 Index가 같지 않으면 양쪽 라벨이 고유해야 해요(아래 "정렬").

```python
>>> t = sd.frame.Series([1, 2, 3], index=["a", "b", "a"])
>>> t.loc[["a"]]
a    1
a    3
dtype: int64
>>> t.loc["a"]
Traceback (most recent call last):
    ...
KeyError: "label 'a' is not unique; select with a list (['a']) to get every row"
```

pandas 3.1.1의 `s.loc["a"]`는 라벨이 하나면 스칼라, 여럿이면 Series를 돌려줘요. 결과 타입이 데이터(라벨이 몇 번 나오는가)에 따라 바뀌어요. stardust는 이것을 피하려고 "하나는 스칼라, 리스트는 Series"로 키의 모양에 묶어 둬요.

## 조회 엔진: LabelTable

### 라벨을 factorize해 두기

라벨로 위치를 찾는 가장 단순한 방법은 Index를 처음부터 훑는 거예요. 라벨 $n$개에서 한 번 찾는 데 $O(n)$이에요. 라벨 $k$개를 찾으면 $O(nk)$라서 정렬(alignment)처럼 라벨 수만큼 찾는 연산은 $O(n^2)$가 돼요.

그래서 처음 조회할 때 **라벨 → 위치** 해시 테이블을 만들어 두고 그 뒤로는 $O(1)$에 찾아요. stardust는 이 테이블을 따로 만들지 않고, 라벨 컬럼을 factorize한 결과를 그대로 써요. factorize는 값마다 "처음 나타난 순서의 정수 코드"를 주는 연산이에요.

`LabelTable`(`ops/hash.hpp`, `ops/hash.cpp`)의 멤버예요.

```cpp
// csrc/frame/ops/hash.hpp, LabelTable (멤버만 줄인 발췌)
class LabelTable {
    Column labels_;                         // 문자열 키가 이 바이트를 가리키므로 살려 둔다
    std::vector<std::int64_t> codes_;       // 위치마다 코드
    std::vector<std::int64_t> first_;       // 코드마다 처음 위치
    std::int64_t ngroups_ = 0;              // 서로 다른 라벨 수
    std::unique_ptr<Partitioned<std::uint64_t, Fmix64>> ints_;          // int64 라벨의 테이블
    std::unique_ptr<Partitioned<std::string_view, HashBytes>> strings_; // string 라벨의 테이블
    mutable std::vector<std::int64_t> group_start_, group_rows_;        // CSR, 처음 쓸 때 만든다
public:
    bool is_unique() const { return ngroups_ == labels_.length; }
    Column lookup(const Column& targets) const;          // 대상마다 코드, 없으면 -1
    Column first_positions(const Column& targets) const; // 대상마다 첫 위치, 없으면 -1
    Column all_positions(const Column& targets) const;   // 대상마다 모든 위치를 이어 붙여서
};
```

- 테이블은 factorize가 만든 그 테이블이에요. 생성자는 라벨 dtype에 따라 `Partitioned<uint64_t, Fmix64>`(int64) 또는 `Partitioned<string_view, HashBytes>`(string)의 `build`를 불러 `codes_`와 `first_`를 얻어요. `Partitioned`는 Swiss table 위의 factorize로, 라벨이 2¹⁷개 이상이고 풀을 쓸 수 있으면 해시의 위쪽 8비트로 256개 파티션에 나눠 병렬로 만들어요. 결과 코드는 직렬로 만든 것과 정확히 같아요. 이 부분은 [해시 테이블과 factorize](/internals/frame/hashing/)에 있어요.
- `is_unique`는 공짜예요. 서로 다른 라벨 수(`ngroups_`)가 라벨 수와 같으면 고유해요. 엔진을 만들면서 얻으므로 따로 훑지 않아요.
- 라벨과 같은 키 규칙을 공유해요. 조회의 "같은 라벨"은 unique, groupby, merge의 "같은 키"와 같은 코드에서 나와요. 그래서 두 규칙이 어긋날 수 없어요.

### 언제 만들고 어디에 두나

엔진은 처음 조회할 때 만들어서 Index 객체의 `_labels` 칸에 둬요(`_index.py`의 `_table()`).

```python
# src/stardust/frame/_index.py, Index._table
def _table(self):
    if self._labels is None:             # 처음 쓸 때 만든다
        self._labels = LabelTable(self._col)
    return self._labels
```

- 만들기만 하고 조회하지 않는 Index(대부분의 연산 결과)는 비용을 내지 않아요.
- Index는 불변이니 한 번 만든 엔진은 계속 맞아요. `Index._copy()`(이름만 바꾼 복사본)는 같은 라벨이므로 엔진도 같이 넘겨요.
- pickle에는 엔진을 넣지 않아요(`__reduce__`가 Column과 이름만 담아요). 읽은 쪽에서 처음 조회할 때 다시 만들어요.
- 비용은 같은 라벨의 factorize와 같아요. 처음 만들 때 한 번 테이블 비용을 내고, 그 뒤 스칼라 조회는 해시 찾기 한 번이에요.

캐시 칸을 채우는 코드는 GIL을 쥔 Python 코드예요. 다만 라벨이 2¹⁷개 이상이면 `Partitioned::build`가 만드는 도중에 GIL을 놓아요(병렬 구간, 또는 직렬 구간의 `Unlocked`). 그래서 두 Python 스레드가 같은 큰 Index를 동시에 처음 조회하면 둘 다 엔진을 만들 수 있어요. 두 엔진은 같은 라벨에서 만든 같은 결과이고, 늦게 끝난 쪽이 칸을 덮어쓸 뿐이라 결과는 달라지지 않아요. 만든 뒤의 조회는 엔진을 읽기만 해요.

### 세 가지 조회

| 메서드 | 돌려주는 것 | 쓰는 곳 |
|---|---|---|
| `lookup(targets)` | 대상 라벨마다 코드, 없으면 -1 | 아래 둘의 바탕 |
| `first_positions(targets)` | 대상 라벨마다 첫 위치, 없으면 -1 | `in`, `get_indexer`(정렬, reindex, 마스크 맞추기) |
| `all_positions(targets)` | 대상 라벨마다 그 라벨의 모든 위치를 위치 순서로, 대상 순서대로 이어 붙여서 | `.loc` 라벨 하나, 라벨 리스트, 라벨 슬라이스의 양 끝 |

**`lookup`**은 [해시 테이블과 factorize](/internals/frame/hashing/)의 `find_rows`를 불러요. 대상 dtype이 라벨 dtype과 다르면 TypeError예요. `find_rows`는 dtype과 "대상에 NA가 있는가"를 호출마다 한 번 골라서, 행 루프에는 "찾고 쓰기"만 남겨요. 대상 행 $k$개를 16,384행 청크로 나눠 병렬로 찾는데, 비용 가중치를 8로 줘서(조회 하나가 덧셈 하나보다 훨씬 비싸요) 대상이 2¹⁷ / 8 = 16,384개 이상이면 나눠요.

**`first_positions`**는 `lookup`의 결과에 `first_`를 한 번 더 거쳐요(`o[i] = first_[o[i]]`, -1은 그대로).

**`all_positions`**는 CSR을 써요. CSR(compressed sparse row)은 "코드 $g$의 위치들"을 한 배열 `rows`에 코드 순서로 모아 두고, `start[g]`부터 `start[g+1]` 직전까지가 코드 $g$의 몫이라고 적는 방식이에요. 처음 부를 때 counting sort로 만들어요.

```cpp
// csrc/frame/ops/hash.cpp, LabelTable::all_positions (CSR 만들기 부분, 줄인 발췌)
if (group_start_.empty()) {
    group_start_.assign(ngroups_ + 1, 0);
    for (std::int64_t c : codes_) ++group_start_[c + 1];               // 1. 코드마다 개수
    for (std::int64_t g = 0; g < ngroups_; ++g)                        // 2. 누적합 = 구간 시작
        group_start_[g + 1] += group_start_[g];
    group_rows_.resize(codes_.size());
    std::vector<std::int64_t> fill(group_start_.begin(), group_start_.end() - 1);
    for (std::int64_t i = 0; i < n; ++i) group_rows_[fill[codes_[i]]++] = i;  // 3. 위치 순서로 채우기
}
```

위치를 앞에서부터 차례로 채우므로 한 코드의 위치들은 저절로 위치 순서예요(안정 정렬). 이 CSR은 직렬로 GIL을 쥔 채 만들어요. 두 Python 스레드가 같은 캐시를 동시에 채우지 않게 하기 위해서예요. 만든 뒤의 조회 부분은 대상 수가 기준값 이상이면 `Unlocked`로 GIL을 놓아요. counting sort 자체와 그 병렬 버전은 [groupby와 정렬](/internals/frame/groupby-sort/)에 있어요.

라벨 하나를 고르는 `.loc["a"]`도 `all_positions`를 써요. 그 라벨이 몇 행에 있는지 알아야 "없음(KeyError) / 하나(그 위치) / 여럿(KeyError, 리스트로 고르라는 안내)"을 가를 수 있기 때문이에요. 그래서 Index에서 라벨 하나를 처음 고를 때 CSR도 함께 만들어져요.

### pandas는 데이터를 보고 길을 골라요

pandas 3.1.1의 조회 엔진(`pandas/_libs/index.pyx`의 `IndexEngine`)[5]도 처음 조회할 때 해시 테이블을 만들어 캐시해요. 라벨 dtype에 따라 `Int64HashTable`, `Float64HashTable`, `PyObjectHashTable`(pandas 3의 기본 `str` Index가 쓰는 `StringObjectEngine`) 등을 써요. 같은 점은 거기까지예요. `get_loc`에는 데이터를 보는 갈림길이 있어요.

- 라벨이 `_SIZE_CUTOFF` = 1,000,000개 이상이고 단조 증가(정렬되어 있음)면 해시 테이블을 만들지 않고 이진 탐색(`searchsorted`)으로 찾아요. 그보다 작거나 정렬되어 있지 않으면 해시 테이블을 만들어요.
- 중복 라벨이면 단조 증가일 때는 `slice`를, 아닐 때는 bool 마스크를 돌려줘요. `Index(["a", "b", "b", "c"]).get_loc("b")`는 `slice(1, 3)`, `Index(["b", "a", "b", "c"]).get_loc("b")`는 `[True, False, True, False]`예요.
- `get_indexer`(여러 라벨 조회)도 테이블이 아직 없고, 크고, 단조 증가이고, 고유하고, 찾을 라벨이 적으면 이진 탐색으로 가요.

이런 갈림길은 정렬된 큰 Index에서 메모리와 시간을 아껴 줘요. 대가로 같은 호출의 비용과 결과 타입이 데이터의 성질(정렬되어 있는가, 중복이 있는가)에 따라 바뀌어요. 정렬된 라벨 1M개의 Index는 테이블 없이 $O(\log n)$으로 찾지만, 라벨 하나만 순서가 다른 Index는 첫 조회에서 1M개짜리 테이블을 만들어요. stardust는 이것을 피하려고 언제나 같은 길(해시 테이블, 같은 타입의 결과)을 가요. 정렬된 Index에서 이진 탐색을 하지 않는 대가는 처음 조회의 테이블 비용이에요.

Polars 2.1.0에는 행 라벨이 없어요. 사용자 안내서는 "Polars는 index를 쓰지 않고 각 행은 표 안의 정수 위치로 가리킨다"고 적어요[3]. 라벨로 행을 찾으려면 그 값이 든 컬럼으로 필터하거나 join해요.

## 선택: 키를 네 모양으로

### 키 → 모양 → 결과

`.loc`, `.iloc`, `[]`에 들어오는 키는 Python 층(`_select.py`)에서 네 모양의 튜플 중 하나로 바뀌어요. 그 뒤의 모든 코드는 이 튜플만 봐요.

| 모양 | 만드는 키 | Series 결과 | 값 | 결과 라벨 |
|---|---|---|---|---|
| `("one", 위치)` | 라벨 하나, 정수 하나 | 스칼라 | — | — |
| `("slice", start, stop, step)` | 라벨 슬라이스, 위치 슬라이스 | Series | step 1이면 Buffer 공유, 아니면 `take` | RangeIndex는 RangeIndex, Index는 슬라이스 |
| `("take", 위치 Column)` | 라벨 리스트, 정수 리스트, 배열 | Series | `take`로 복사 | Index |
| `("mask", bool Column)` | bool Series | Series | 컬럼마다 `filter`로 바로 압축 | Index |

- DataFrame에서 행 하나를 고르면 `("one", p)`를 `("slice", p, p + 1, 1)`로 바꿔 1행 DataFrame을 만들어요. object dtype이 없으니 dtype이 섞인 행을 Series 하나로 담을 방법이 없고, 1행 DataFrame은 컬럼마다 dtype을 지켜요. 행 하나와 열 하나를 함께 고르면(`df.loc["r", "a"]`) 스칼라예요.
- step이 1인 슬라이스는 복사하지 않아요. `Column.slice`가 `offset`과 `length`만 바꾸고 Buffer를 공유해요. NA 개수는 그 범위의 비트를 popcount로 다시 세고, 0이면 비트맵을 떼어 내요. `head`, `tail`, repr의 행 생략도 이 길이에요. 1M 행 DataFrame의 `head()`가 656ns예요. 슬라이스와 null 개수는 [컬럼과 메모리](/internals/frame/columns/)에 있어요.
- step이 1이 아니면 `arange`로 위치를 만들어 `take`해요. 띄엄띄엄 놓인 행을 공유로 표현하려면 Column에 stride가 있어야 하는데, Column은 1차원 연속 배열로만 두었어요(stride가 있으면 모든 커널이 그 경우를 다뤄야 해요).
- 스칼라 하나는 `col.slice(p, 1).to_list(NA)[0]`이에요. 1행 슬라이스(복사 없음)에서 Python 객체 하나를 꺼내요. `.iloc[i]`가 435ns, `.iloc[a:b]`가 837ns예요.

### 위치 키 (`by_position`)

- 정수는 음수면 `n`을 더하고 `[0, n)`을 벗어나면 IndexError예요.
- 슬라이스는 Python의 `slice.indices(n)`이 그대로 `(start, stop, step)`을 줘요.
- 슬라이스의 양 끝과 step은 int나 `None`이어야 해요. 아니면 `cannot select rows by position with a slice of str; the ends and the step must be ints or None`처럼 IndexError예요.
- 원소가 모두 int인 위치 리스트(Python `int`만 든 list, uint64가 아닌 정수 numpy 배열, int64 `sd.ndarray`)는 한 번에 int64 Column으로 바꾸고, 범위 검사와 음수 보정을 커널 하나(`wrap_positions`)가 해요. list는 원소의 값이 아니라 타입의 집합(`set(map(type, key))`, C 안에서 한 번 훑기)만 봐요. 범위 밖 위치가 있으면 `parallel::FirstRow`로 가장 앞의 것을 찾아 메시지에 써요. 1M 위치를 원소마다 Python으로 검사하면 100~170ms이고, 커널로는 몇 ms예요.
- 그 밖의 키(bool, float이 섞인 list 등)만 원소마다 검사해 메시지를 만들어요. 위치 키의 형태가 틀리면(bool, float, str) 배열의 인덱싱처럼 IndexError예요. bool 배열은 마스크가 아니에요. 마스크는 bool Series만이에요.

### 라벨 키 (`by_label`)

- **라벨 하나**: `index._position_of(label)`. Index면 위의 `all_positions` 흐름이고, RangeIndex면 산술이에요.
- **라벨 리스트**: `_positions_of(labels)`가 라벨을 Index dtype의 Column으로 바꾼 뒤 두 번 조회해요. 먼저 `first_positions`로 -1(없는 라벨)이 있는지 보고, 하나라도 있으면 그 라벨들을 메시지에 담아 KeyError를 내요. 모두 있으면 `all_positions`로 라벨마다 모든 위치를 얻어요. 결과는 "라벨 순서대로, 한 라벨 안에서는 위치 순서대로"예요.
- **라벨 슬라이스** `a:b`: 양 끝 라벨의 위치를 `_position_of`로 찾아 위치 슬라이스로 바꿔요. 끝 라벨도 포함해요(`stop = 끝 위치 + 1`). 그래서 양 끝 라벨은 있어야 하고 고유해야 해요.

```python
>>> s = sd.frame.Series([1, 2, 3], index=["a", "c", "e"])
>>> s.loc["a":"e"]
a    1
c    2
e    3
dtype: int64
>>> s.loc["b":"d"]
Traceback (most recent call last):
    ...
KeyError: 'b'
```

pandas 3.1.1은 `get_slice_bound`[5]에서 끝 라벨을 찾지 못하면 Index가 단조일 때 `searchsorted`로 "들어갈 자리"를 찾아요. 그래서 정렬된 Index에서는 `s.loc["b":"d"]`가 `c` 하나를 돌려주고, 정렬되지 않은 Index에서는 같은 호출이 KeyError예요. 같은 코드가 데이터의 순서에 따라 성공하거나 실패하는 셈이에요. stardust는 정렬 여부를 보지 않으므로 없는 끝 라벨은 언제나 KeyError예요. 범위로 고르고 싶으면 라벨 대신 그 값이 든 컬럼을 비교해 마스크로 골라요.

### 마스크 키와 라벨 맞추기

bool Series로 행을 고를 때(`s[mask]`, `df[mask]`, `.loc[mask]`) 마스크에도 라벨이 있어요. 마스크의 라벨이 대상과 다르면 `aligned_mask`가 라벨로 맞춰요.

1. 두 Index가 같으면(같은 객체이거나 `equals`) 마스크 값을 그대로 써요.
2. 아니면 길이가 같고 대상 라벨이 고유해야 해요.
3. `mask.index._get_indexer(index)`로 대상 라벨마다 마스크에서의 위치를 찾아요(마스크 라벨도 고유해야 해요). 하나라도 -1이면 ValueError예요.
4. 그 위치로 마스크 값을 `take`해 대상 순서로 바꿔요.

길이가 같고, 대상 라벨이 고유하고, 대상의 모든 라벨이 마스크에 있으면(마스크 라벨도 고유) 두 라벨 집합은 같아요. 원소 수가 같은 두 집합에서 한쪽이 다른 쪽에 다 들어 있기 때문이에요. 대상에 중복이 있으면 이 논리가 깨지므로(길이가 같아도 마스크에만 있는 라벨이 있을 수 있어요) 대상의 고유성을 먼저 요구해요.

pandas 3.1.1(`pandas/core/indexing.py`의 `check_bool_indexer`)[5]도 라벨이 다르면 `get_indexer_for`로 맞추는데, 대상 라벨이 마스크에 없으면 에러를 내고 마스크에만 있는 라벨은 조용히 버려요. 위의 마지막 예가 pandas에서는 `a`, `e` 두 행을 돌려줘요(DataFrame이면 경고 하나와 함께). stardust가 두 라벨 집합이 같기를 요구하는 이유는, 마스크에만 있는 라벨은 대개 마스크를 다른 데이터에서 만들었다는 신호이기 때문이에요. 조용히 버리면 그 실수가 결과에 묻혀요.

## 정렬(alignment)

### 무엇을 하나

`a + b`에서 `a`와 `b`의 라벨이 다르면, 같은 라벨끼리 더하고 한쪽에만 있는 라벨은 NA로 둬요. 결과의 라벨은 두 라벨 집합의 합집합이에요. 순서는 왼쪽 라벨 순서, 그다음 오른쪽에만 있는 라벨을 오른쪽 순서대로예요. merge의 outer 조인이 행을 늘어놓는 규칙과 같아요([merge와 concat](/internals/frame/merge-concat/)).

```python

>>> b = sd.frame.Series([10, 20], index=["a", "c"])
```

결과는 int64로 남아요. 결측을 비트맵으로 표시하므로 NA가 생겨도 int가 float로 바뀌지 않아요.

### 알고리즘 (`_select.align`)

```python
# src/stardust/frame/_select.py, align (줄인 발췌)
def align(a, b, func=None):
    if a is b or a.equals(b):                          # 1. 같은 Index: 위치대로
        return a, None, None
    if a._dtype != b._dtype: raise TypeError(...)     # 2. int 라벨과 string 라벨은 맞출 수 없다
    if not a.is_unique or not b.is_unique: raise ValueError(...)
    only_b = (a._get_indexer(b) == -1).nonzero()      # 3. b의 라벨을 a에서 찾아 없는 것만
    union = Index(concat([a_labels, b_labels.take(only_b)]))
    a_pos = None if len(only_b) == 0 else concat([arange(0, 1, len(a)), [-1] * len(only_b)])
    b_pos = b._get_indexer(union)                      # 4. 합집합의 라벨을 b에서 찾기
    return union, a_pos, b_pos
```

1. **같은 Index면 위치대로 계산해요.** `is`로 먼저 보고, 아니면 `equals`로 원소를 비교해요. 같은 DataFrame에서 꺼낸 두 컬럼(`df["x"] + df["y"]`)은 같은 Index 객체를 공유해서 `is`에서 끝나요. 이것은 "같은 라벨 순서면 위치가 곧 짝"이라는 의미 규칙이에요. 데이터를 보고 빠른 길로 가는 휴리스틱이 아니라, 두 Index가 같은지라는 입력의 정의 자체를 묻는 것이라서 중복 라벨이 있어도 성립해요.
2. **dtype과 고유성을 검사해요.** int 라벨과 string 라벨은 맞출 수 없어요(RangeIndex는 int64로 쳐요). 같은 Index가 아니면서 중복이 있으면 ValueError예요.
3. **`a._get_indexer(b)`**는 `b`의 라벨마다 `a`에서의 첫 위치(`first_positions`)를 구하고, -1인 자리(`a`에 없는 라벨)만 `nonzero`로 골라요. 합집합은 `a`의 라벨 뒤에 그 라벨들을 이어 붙인 것이에요(`concat` 커널). `a`의 위치 배열은 `[0, 1, …, len(a)-1]` 뒤에 -1을 그만큼 붙인 것이에요. 붙일 것이 없으면 `None`을 돌려줘서 `a`의 컬럼을 `take` 없이 그대로 써요.
4. **`b._get_indexer(union)`**은 합집합의 라벨마다 `b`에서의 위치를 구해요. `b`에 없는 라벨은 -1이에요.

그 뒤 각 컬럼은 `take(positions)`로 다시 배열되고, 위치 -1은 NA 행이 돼요.

비용은 양쪽 엔진을 만드는 데 각각 $O(n)$, 조회 두 번에 $O(n_a + n_b)$, `take`가 컬럼마다 $O(n)$이에요. 모두 해시 조회와 순차 복사라서 비교 정렬이 없어요. string 라벨 1M개를 섞은 순서로 더하는 데 99ms가 들어요(1스레드, 엔진 만들기 포함).

### 정렬이 쓰이는 곳

같은 함수 하나가 정렬의 모든 경우를 맡아요.

- `Series ⊕ Series`(산술, 비교, 논리)
- `DataFrame ⊕ DataFrame`: 행은 `align`으로, 열은 이름의 합집합(왼쪽 컬럼 순서, 그다음 오른쪽에만 있는 컬럼)으로 맞춰요. 한쪽에만 있는 컬럼은 반대쪽 dtype의 NA 컬럼(`full_na`)과 계산해요. 그래서 결과 dtype을 정하는 규칙이 따로 없어요.
- Series들의 dict로 DataFrame 만들기: Index들을 왼쪽부터 차례로 `align`해 합집합을 만들고, 각 Series를 그 합집합으로 `reindexed`해요.
- `df["c"] = Series`, 행 대입의 값이 Series일 때, `Series(series, index=...)`, `reindex`: `reindexed(col, index, target)`이 같은 Index면 그대로, 아니면 `take(index._get_indexer(target))`이에요. 원래 라벨은 고유해야 해요.
- 마스크: 위의 `aligned_mask`

어느 경우든 int64 라벨과 string 라벨이 만나면 TypeError이고, 메시지는 한 함수(`_index.py`의 `mixed_labels`)가 만들어요(`cannot align int64 labels with string labels`). 앞은 라벨을 찾아보는 쪽 Index(`reindex`의 원래 Index, 마스크나 대입할 Series의 Index, 연산자의 왼쪽), 뒤는 그 안에서 찾을 라벨의 dtype이에요. 연산자, `reindex`, 마스크, 대입, 생성자가 모두 같은 꼴이에요.

`reindex([])`처럼 라벨이 하나도 없으면 맞지 않을 라벨도 없어요. 그런데 빈 list는 그대로 Index로 만들면 값이 없어서 int64로 추론돼요([리스트에서 dtype 추론](/api/frame/series/)). 그래서 `ensure_index(labels, func, like)`가 빈 list나 tuple을 받으면 원래 Index(`like`)의 dtype으로 빈 Index를 만들고, `label_column`도 dtype이 다른 빈 Index는 원래 dtype의 빈 Column으로 읽어요. string 라벨 Series의 `reindex([])`는 `.loc[[]]`처럼 string 라벨의 빈 결과예요.

### 합집합을 정렬하지 않는 이유

pandas 3.1.1은 두 Index가 다르면 합집합을 정렬해요. `Series._align_for_op` → `NDFrame._align_series` → `Index.join(how="outer")`로 가는데, `Index.join`이 `sort = sort or how == "outer"`로 outer 조인에서 정렬을 강제해요[5]. 그래서 `pd.Series([1, 2], index=["b", "a"]) + pd.Series([10, 20], index=["a", "c"])`의 라벨은 `["a", "b", "c"]`예요. 두 Index의 라벨이 같고 순서만 달라도 결과는 정렬된 순서예요. 두 Index가 같으면(`equals`) pandas도 정렬하지 않고 위치대로 계산해요.

stardust가 정렬하지 않는 이유는 두 가지예요.

- **비용**: 정렬은 $O(n \log n)$번의 비교이고, string 라벨이면 비교마다 바이트 비교예요. 왼쪽 순서를 지키는 합집합은 해시 조회 두 번이면 돼요.
- **예측**: 결과의 행 순서가 왼쪽 피연산자의 순서를 따르면, `a + b`의 결과를 `a`의 다른 결과와 나란히 놓아도 행이 어긋나지 않아요. 정렬된 순서는 두 Index가 같으면 적용되지 않고 다르면 적용되어, 같은 식의 행 순서가 데이터에 따라 바뀌어요.

### 중복 라벨이 있으면 왜 에러인가

라벨이 중복되면 "같은 라벨끼리 짝짓기"는 일대일이 아니에요. 왼쪽에 `a`가 2개, 오른쪽에 `a`가 3개 있으면 짝이 6개 생겨요. pandas 3.1.1은 이 경우 join처럼 곱집합을 만들어요. `index=["a", "b", "a"]`인 Series와 `index=["a", "a", "b"]`인 Series를 더하면 `a` 행이 4개(2 × 2), 모두 5행이 나와요. 산술 연산의 결과 길이가 데이터에 따라 입력보다 커지는 것은 대개 실수의 결과라서, stardust는 같은 Index가 아니면서 중복이 있으면 에러를 내요. 의도한 곱집합이라면 `merge`가 그 일을 명시적으로 해요.

```python
>>> t = sd.frame.Series([1, 2, 3], index=["a", "b", "a"])
>>> t + t
a    2
b    4
a    6
dtype: int64
>>> t + sd.frame.Series([1, 2, 3], index=["a", "b", "c"])
Traceback (most recent call last):
    ...
ValueError: cannot align indexes with duplicate labels
```

`t + t`는 같은 Index라서 위치대로 계산돼요. 중복이 있어도 짝이 분명하기 때문이에요.

Polars 2.1.0에는 정렬이 없어요. 두 Series의 연산은 위치대로이고 길이가 같아야 해요(`[1, 2] + [10, 20, 30]`은 `InvalidOperationError`, 길이 1인 Series만 퍼져요). 라벨로 짝지어야 하면 키 컬럼으로 `join`해요.

## take: 위치로 모으기

### 정의

`take(col, positions)`는 결과의 행 $i$에 `col`의 행 `positions[i]`를 두는 gather 연산이에요. 위치 -1은 NA 행이에요. 이 규칙 하나로 정렬(alignment)의 "없는 라벨", merge의 "짝 없는 행", groupby의 "값이 없는 그룹"이 모두 같은 커널로 처리돼요.

`take`는 reindex, 정렬, 라벨 리스트와 위치 리스트 선택, step이 1이 아닌 슬라이스, merge의 모든 결과 컬럼, `sort_values`/`sort_index`, groupby의 `min`/`max`/`first`/`last`, `dropna`, `drop_duplicates`, `unique_values`, 문자열 마스크 필터에 쓰여요.

### 고정폭 dtype

고정폭 dtype(bool, int64, float64)은 한 번 지나며 끝내요(`take_fixed`). 행마다 범위 검사를 누적하고, 값을 읽고, 결과 비트맵을 64행씩 워드로 모아 쓰고, NA 행에는 0을 써요. 분기가 없어요.

```cpp
            // csrc/frame/ops/selection.cpp
            for (std::int64_t i = b; i < e; ++i) {
                const std::int64_t p = pos[i];
                bad |= static_cast<std::uint64_t>(p + 1) > length;  // -1 .. length - 1
                const bool has = p >= 0;
                const std::int64_t q = has ? p : 0;
                const bool valid = has && (!src || bitmap::get(src, off + q));
                const T v = in[q];
                o[i] = valid ? v : T{};
                m |= static_cast<std::uint64_t>(valid) << (i - b);
            }
            w[b >> 6] = m;
            na += (e - b) - __builtin_popcountll(m);
```

- **범위 검사를 분기 없이.** 올바른 위치는 $-1 \le p < \text{length}$예요. $p + 1$을 부호 없는 정수로 보면 이 조건이 `p + 1 <= length` 하나가 되고(음수는 아주 큰 수가 돼요), 그 결과를 `bad`에 OR로 모아요. 루프가 끝난 뒤 하나라도 범위 밖이면 출력을 버리고 `IndexError`를 내요. 에러는 드무니 검사는 값을 모으는 루프에 얹어요.
- **-1도 분기 없이.** 위치가 -1이면 행 0을 읽고(`q = 0`, 길이가 0인 컬럼은 따로 처리해요) 그 값을 버려요. "위치가 있고 원래 행에 값이 있다"(`valid`)로 값과 0 중 하나를 골라요. 원래 컬럼에 결측이 없으면(`src`가 null) 비트맵을 읽지 않아요. 컬럼의 속성으로 고르는 거예요.
- **비트맵은 64행씩.** 결과의 validity 비트를 `m`에 모아 64행마다 워드 하나로 써요. NA 개수도 popcount로 그 자리에서 세요. 끝에 NA가 하나도 없으면 비트맵을 버려요.
- 범위 검사, 모으기, 결측 정리(`finish_fixed`)를 따로 하던 세 패스에 비해 한 번만 지나서 약 2배 빨라요. `take`의 시간은 주로 `in[q]`의 무작위 읽기, 곧 메모리 지연이 정해요. 위치가 섞여 있으면 행마다 캐시 미스가 날 수 있어요.
- 청크는 16,384행이고 64의 배수예요. 두 태스크가 같은 비트맵 워드를 쓰지 않아요. 위치 배열의 길이로만 청크를 나누므로 결과의 배치는 스레드 수와 상관없어요([병렬화와 결정성](/internals/frame/parallel/)).

### 문자열

문자열은 길이가 제각각이라 결과의 바이트 위치를 미리 알 수 없어요.

문자열의 `take`는 먼저 위치를 검사하는 패스(범위 밖, -1이 있는가)를 따로 돌고 나서 두 번 훑어요.

1. 청크마다 고른 문자열의 바이트 수를 더해요. 청크 순서로 누적합을 내면 청크마다 바이트를 쓰기 시작할 자리가 나와요(`chunk_starts`).
2. 청크마다 자기 자리부터 바이트를 `memcpy`하고, 행마다 끝 위치를 offsets에 적어요.

### 앨리어싱 때문에 지역 변수로 꺼내기

`gather`의 람다 안에서 `in`, `o`, `w` 같은 포인터를 지역 변수로 꺼내는 것은 우연이 아니에요. 람다가 캡처한 값은 클로저 객체의 멤버라서, 루프 안에서 다른 타입의 포인터(비트맵 워드, `char` 계열)로 쓰면 컴파일러는 그 쓰기가 클로저의 멤버를 바꿨을 수도 있다고 보고 매 반복 멤버를 다시 읽어요. C++에서 `char` 계열 포인터는 어떤 객체든 가리킬 수 있기 때문이에요. 그러면 루프가 벡터화되지 않아요. frame의 커널은 루프가 읽는 경계와 포인터를 태스크 안의 지역 변수로 둬요. 자세한 예와 측정은 [원소별 연산과 리덕션](/internals/frame/elementwise/)에 있어요.

## 마스크 필터: 분기 없는 압축과 모으기

### 분기 있는 압축의 문제

마스크로 행을 고르는 가장 직접적인 코드는 이래요.

```cpp
for (i = 0; i < n; ++i)
    if (keep[i]) out[k++] = in[i];
```

마스크가 무작위(예: `f > 0`, 정규분포 값이면 절반이 True)면 `if`가 어느 쪽으로 갈지 CPU가 예측할 수 없어요. 현대 CPU는 분기의 결과를 기다리지 않고 예측한 쪽으로 미리 명령을 실행하다가, 틀리면 그 일을 버리고 다시 시작해요. 무작위 마스크에서는 절반 가까이 틀리고, 틀릴 때마다 파이프라인에 미리 들어간 일을 버려요. 이 비용이 8바이트 복사 하나보다 훨씬 커요. Ross는 데이터베이스의 선택 연산에서 분기 예측 실패가 시간을 크게 좌우한다는 것과, 같은 결과를 내면서 분기 동작만 다른 계획을 고를 수 있다는 것을 정리했어요[1].

### 항상 쓰고, 남길 때만 전진

stardust의 고정폭(bool, int64, float64) 필터는 분기를 없애요.

```cpp
// csrc/frame/ops/selection.cpp, compact_rows (줄인 발췌)
template <class Get>
void compact_rows(const std::uint8_t* keep, std::int64_t lo, std::int64_t hi, Get get, auto* out) {
    std::int64_t last = hi - 1;
    while (last >= lo && !keep[last]) --last;      // 이 청크에서 마지막으로 남길 행
    std::int64_t k = 0;
    for (std::int64_t i = lo; i <= last; ++i) {
        out[k] = get(i);                           // 언제나 쓴다
        k += keep[i];                              // 남길 때만 다음 칸으로
    }
}
```

- 모든 행을 `out[k]`에 쓰고, 남길 행이면 `k`를 1 늘려요. 버릴 행은 다음 행이 같은 칸에 덮어써요. 루프에 데이터에 따라 갈리는 분기가 없어서 마스크가 아무리 무작위여도 예측 실패가 없어요.
- `keep[i]`를 그대로 더할 수 있는 것은 bool 컬럼이 행마다 1바이트(0 또는 1)이기 때문이에요. 마스크가 NA인 행은 값 자리가 0이라서 저절로 False예요. NA 검사가 필요 없어요.

### 병렬로 압축하기

결과의 어디부터 써야 할지는 앞쪽 청크가 몇 행을 남기는지에 달렸어요. 그래서 두 단계로 해요.

1. **청크마다 남길 행 수를 세요**(`kept_starts`: `keep` 바이트의 합). 청크 순서로 누적합을 내면 청크마다 출력을 시작할 자리가 나와요.
2. **청크마다 자기 자리부터 압축해요.**

"항상 쓰기"에는 함정이 하나 있어요. 마지막으로 남길 행 다음 행도 `out[k]`에 쓰는데, 그 칸은 이미 다음 청크가 쓰는 첫 칸이에요. 두 태스크가 같은 칸을 쓰면 경쟁이 생겨 결과가 스레드 일정에 달려요. 그래서 `compact_rows`는 자기 청크에서 마지막으로 남길 행까지만 돌아요(`last`를 먼저 찾는 이유). 그러면 모든 쓰기가 자기 청크의 출력 범위 안에 떨어져요. 그 뒤의 버릴 행들은 어차피 결과에 들어가지 않아요. 같은 이유로 출력 Buffer를 한 칸 크게 잡을 필요도 없어요.

청크는 행 수로만 정하고 누적합도 청크 순서로 내므로 결과의 배치는 스레드 수와 무관해요.

결측이 있는 컬럼은 값과 함께 validity도 압축해야 해요. 비트를 하나씩 꺼내 옮기는 대신, 비트맵을 행마다 0/1 바이트로 펼치고(`valid_bytes`, 256칸 표로 8행씩), 그 바이트 배열을 같은 `compact`로 압축한 뒤, 8개씩 모아 비트로 다시 접어요(`pack_bits`). 마지막에 `finish_fixed`가 NA 개수를 세요.

`nonzero(mask)`(True인 위치)도 같은 `compact_rows`에 `get(i) = i`를 넘긴 것이에요.

### 문자열은 take(nonzero(mask))

문자열은 압축하지 않고 `take(col, nonzero(mask))`로 가요. 같은 "항상 쓰기"를 문자열에 적용한 방법 둘을 1M 행에서 재면 둘 다 `take`보다 느렸어요. 문자열은 길이가 제각각이라 버릴 행까지 바이트를 쓰는 비용이 크고, `take`는 남길 행의 바이트만 옮기기 때문이에요.

### DataFrame: 컬럼을 한꺼번에 거르기

`df[mask]`는 마스크를 한 번 맞춘 뒤(`aligned_mask`) 남는 위치(`nonzero`)를 한 번 구하고, 모든 컬럼을 C++ 호출 하나로 걸러요(`filter_columns`). 그 위치를 결과 라벨(`Index._take`)과 문자열 컬럼이 함께 써요.

```python
        # src/stardust/frame/_frame.py
        if isinstance(key, Series):  # rows by a bool mask: each column compacted directly (docs/design/frame.md §7.3)
            mask = _select.aligned_mask(key, self._index)
            positions = mask.nonzero()  # the index's labels, and the string columns' rows
            cols = _core.filter_columns(list(self._cols.values()), mask, positions)
            return DataFrame._new(dict(zip(self._cols, cols)), self._index._take(positions))
```

`filter_columns`는 컬럼을 둘로 나눠요.

- **NA 없는 고정폭 컬럼**은 (컬럼, 청크) 쌍이 태스크 하나예요. 컬럼 하나는 기준값 아래여도 컬럼을 합친 일이 기준값을 넘으면 나뉘어서, 10만 행 × 100열 같은 넓은 프레임도 여러 스레드로 돌아요.
- **문자열과 NA가 있는 컬럼**은 하나씩 `take`나 `filter`를 불러요. 각 커널이 스스로 청크로 나눠요(한 태스크로 묶으면 그 컬럼이 한 스레드에서 돌아요).

NA 없는 고정폭 컬럼은 남는 행의 비율로 방법을 골라요. 남는 행이 마스크의 2/3 이하이면 위치로 모으고(gather), 그보다 많으면 위의 압축을 해요.

```cpp
    // csrc/frame/ops/selection.cpp
    const std::int64_t count = positions.length;
    const bool gather = count * 3 <= n * 2;
```

압축은 모든 행을 지나고, 모으기는 남는 행만 읽고 써요. 절반이 남는 100열 프레임에서 모으기가 1스레드 약 2배 빨랐어요. 모으기는 출력 위치를 청크로 나눠요. 두 방법 모두 같은 행을 같은 순서로 내므로 결과는 같아요. 이 선택은 데이터(남는 행의 수)를 보지만 결과를 바꾸지 않아요. 남는 행 수는 어차피 결과의 길이로 알아야 하는 값이라, 고르는 비용도 따로 들지 않아요.

`Series[mask]`와 `dropna`는 컬럼 하나의 `filter`예요. 언제나 압축이에요.

### pandas와 Polars의 필터

- **pandas 3.1.1**: Series의 bool 인덱싱은 `SingleBlockManager.get_rows_with_mask`에서 numpy의 bool 인덱싱(`values[mask]`)을 그대로 써요. DataFrame은 `DataFrame._getitem_bool_array`가 마스크를 위치로 바꾼 뒤(`key.nonzero()[0]`) `take`해요. 마스크가 모두 True면 얕은 복사로 끝내는 빠른 길도 있어요.
- **Polars 2.1.0**: bool이 비트로 저장되어 있어서, 필터 커널(`crates/polars-compute/src/filter/scalar.rs`의 `scalar_filter`)이 마스크를 64행씩 `u64` 하나로 읽어요. 64비트가 모두 0이면 건너뛰고, 모두 1이면 64개를 한 번에 복사하고, 1이 16개 이하면 `trailing_zeros`로 남길 행만 골라 복사하고, 그 밖에는 stardust와 같은 "항상 쓰고 비트만큼 전진" 루프(`scalar_dense_filter64`)를 돌아요. x86의 AVX-512가 있으면 전용 커널을 쓰는데, Apple Silicon에는 해당하지 않아요[4].

Polars는 64행 단위로 마스크의 모양을 보고 고르는데, 이것은 결과를 바꾸지 않는 커널 안의 작은 갈림길이에요. stardust는 bool을 바이트로 저장하므로 64행을 한 워드로 읽을 수 없고, 바이트 하나하나를 더하는 루프를 써요. bool을 바이트로 둔 이유(NEON 비교의 결과를 그대로 저장, 압축 커널이 단순)는 [컬럼과 메모리](/internals/frame/columns/)에 있어요.

## 대입: set_rows와 Copy-on-Write

### Python 쪽: 값 맞추기와 자기 Column 갖기

`s.loc[...] = v`, `s.iloc[...] = v`, `df.loc[rows, "c"] = v`는 모두 `Series._assign`으로 와요.

```python
# src/stardust/frame/_series.py, Series._assign
def _assign(self, sel, value):
    labels = None if sel[0] == "one" else _select.select_index(self._index, sel)
    values = assignment_values(value, self._dtype, labels)   # 1. 값을 컬럼 dtype의 Column으로
    self._col = self._col.share()                            # 2. 내 Column 객체를 따로 갖는다
    self._col.set_rows(_select.positions_column(sel), values) # 3. 쓰기 (Copy-on-Write)
```

1. **값 맞추기**: 스칼라는 `implicit_scalar`로, list는 추론한 뒤 `implicit`로 컬럼 dtype에 맞춰요. list와 tuple은 추론하기 전에 bool과 수(int, float, numpy 정수·실수)가 섞였는지 봐요(`_check_no_bool_mix`). 원소마다 값을 보지 않고 타입의 집합(`set(map(type, values))`, C 안에서 한 번 훑기)만 봐요. 섞였으면 TypeError예요. object dtype의 numpy 배열도 Python 객체를 담고 있으니 list로 바꿔 같은 검사를 해요. 생성자의 추론처럼 `[True, 2]`를 int64 `[1, 2]`로 승격하면 int 컬럼에 넣을 때 `True`가 아무 말 없이 `1`이 되기 때문이에요. 컬럼을 통째로 새로 만드는 `df["c"] = [True, 2]`는 이 길이 아니라서 생성과 같이 int64예요. 규칙은 dtype만 보고 위로만(`bool → int64 → float64`)이에요. int 컬럼에 `2.0`은 값과 상관없이 TypeError예요. 값이 Series면 고른 행의 라벨로 `reindexed`(정렬)한 뒤 같은 규칙을 적용해요. 마스크로 골랐으면 `select_index`가 남은 행의 라벨을 만들어 그 라벨로 맞춰요.
2. **자기 Column 객체 갖기**: Python 객체 둘이 같은 C++ Column 객체를 가리킬 수 있어요(`df["a"]`로 꺼낸 Series와 DataFrame). 그 객체를 고치면 둘 다 바뀌므로, 쓰는 쪽이 먼저 `share()`(Buffer를 공유하는 새 Column 객체, `shared_ptr` 셋의 복사)로 자기 객체를 만들어요. 이전 객체를 쥔 다른 주인이 없으면 이 대입으로 해제되고, Buffer의 참조 수가 함께 줄어요.
3. **`set_rows`**가 Buffer의 참조 수를 보고 필요할 때만 복사해요.

DataFrame의 `df.loc[rows, "c"] = v`는 그 컬럼으로 임시 Series를 만들어 `_assign`한 뒤 `df._cols["c"] = target._col`로 되돌려 놓아요. 없는 라벨에 대입하면 KeyError예요. pandas처럼 행을 늘리지 않아요(행을 늘리면 모든 컬럼의 Buffer를 다시 만들어야 해서, 대입 한 번의 비용이 데이터에 따라 크게 달라져요).

### C++ 쪽: detach

```cpp
// csrc/frame/ops/selection.cpp, detach (줄인 발췌)
void detach(Column& col, bool need_validity) {
    const bool shared = col.values.use_count() > 1 || (col.validity && col.validity.use_count() > 1);
    const bool add_bits = need_validity && !col.validity;
    if (!shared && !(add_bits && col.offset != 0)) {      // 나만 들고 있다: 그 자리에서
        if (add_bits) add_validity(col);
        return;
    }
    // 다른 주인이 있다: 내 행 범위 [offset, offset + length)만 새 Buffer로 복사
    auto values = Buffer::allocate(col.length * size);
    std::memcpy(values->data(), col.values->data() + col.offset * size, col.length * size);
    col.values = values;  col.validity = rebased_validity(col);  col.offset = 0;
    if (add_bits) add_validity(col);
}
```

- `use_count()`가 1이면 그 자리에서 써요. values와 validity Buffer를 가리키는 `shared_ptr`이 이 Column 하나뿐이라는 뜻이에요.
- 다른 주인이 있으면 복사해요. 주인은 다른 Series나 DataFrame의 Column, 같은 Buffer를 공유하는 슬라이스, `to_numpy`·`to_array`가 내준 읽기 전용 뷰(그 뷰의 capsule이 `shared_ptr` 복사본을 쥐고 있어요), 그리고 진행 중인 다른 연산이 인자로 잡은 옛 Column이에요. 복사는 자기 행 범위만 해요. 1M 행 컬럼의 10행짜리 슬라이스에 쓰면 10행만 복사하고 `offset`을 0으로 맞춰요.
- 대입할 값에 NA가 있는데 컬럼에 비트맵이 없으면 비트맵을 새로 달아요. `add_validity`는 `offset == 0`일 때만 쓸 수 있으므로(비트 0이 행 0), 공유되지 않았어도 `offset`이 0이 아니면 복사 경로로 가서 0부터 다시 맞춰요.

### 쓰기와 NA 개수

detach 뒤의 쓰기는 위치마다 차례로 해요. 값이 있으면 `memcpy`하고 비트를 세우고, NA면 값 자리를 0으로 지우고 비트를 내려요. 같은 위치가 여러 번 나오면 마지막 쓰기가 이겨요. 끝에서 NA 개수를 popcount로 다시 세고, 0이면 비트맵을 떼어 내요.

### 문자열은 언제나 새 Buffer

문자열 행의 값을 바꾸면 길이가 바뀔 수 있어서, 제자리에서 쓸 수 없어요. `set_rows`는 문자열 컬럼이면 참조 수와 상관없이 새 offsets와 바이트를 만들어요.

1. 행마다 "어느 값으로 바꾸나"를 적은 배열 `src`를 만들어요(바꾸지 않으면 -1, 같은 행에 여러 번 쓰면 마지막 것).
2. 행마다 바이트 수로 offsets를 채우고(첫 번째 훑기), 바이트를 복사해요(두 번째 훑기).

1M 행 문자열 컬럼에 한 행을 써도 컬럼 전체를 다시 만들어요. 문자열 값을 자주 바꾸는 작업에는 비싼 길이에요.

### GIL을 쥔 채 쓰는 이유

frame의 커널은 일이 크면 GIL을 놓고 돌아요. 그러면 다른 Python 스레드가 그 사이에 대입할 수 있어요. 연산은 호출 시점의 값을 봐야 해요(스냅샷 규칙). 이것이 지켜지는 이유는 둘이에요.

- 진행 중인 연산은 인자로 옛 Column 객체를 잡고 있고, 대입은 `share()`로 새 Column 객체를 만든 뒤 쓰므로, 그 사이 Buffer의 참조 수가 2 이상이라 대입이 복사해요.
- 남은 틈은 "`set_rows`가 Buffer를 제자리에서 고치는 도중에 다른 스레드의 연산이 시작되는 경우" 하나예요. 그래서 `set_rows`는 크기와 상관없이 GIL을 쥔 채 돌아요. GIL을 쥐고 있는 한 다른 스레드의 연산은 쓰기 전이나 쓴 뒤의 컬럼만 봐요.

스냅샷 규칙과 그 테스트는 [컬럼과 메모리](/internals/frame/columns/)에 있어요.

### pandas와 Polars의 Copy-on-Write

- **pandas 3.1.1**은 Copy-on-Write를 끌 수 없어요. 공유 여부를 Block 단위로 추적해요. `BlockValuesRefs`(`pandas/_libs/internals.pyx`)가 같은 메모리를 보는 Block의 약한 참조(weakref) 목록을 관리하고, `has_reference()`가 죽은 참조를 걷어낸 뒤 둘 이상 남았는지 봐요[5]. 대입(`BlockManager.setitem`, `SingleBlockManager.setitem_inplace`)은 참조가 있으면 Block을 깊은 복사한 뒤 써요. Block은 같은 dtype 컬럼 여럿을 합친 2차원 배열이라서(BlockManager의 consolidation), 공유와 복사의 단위가 컬럼 하나보다 클 수 있어요.
- **Polars 2.1.0**의 `Series.scatter`는 같은 Python 객체를 고쳐요. Rust 쪽(`crates/polars-python/src/series/scatter.rs`)은 참조 수를 1로 만들려고 Series를 잠시 꺼내 두고, `PrimitiveArray::with_values_mut`가 버퍼의 참조 수가 1이면 제자리에서, 아니면 복사본에 써요[4]. stardust의 `use_count()` 검사와 같은 생각이에요.

stardust는 Buffer를 가리키는 `shared_ptr`의 참조 수 하나로 판단해요. 약한 참조 목록이 없고, 단위는 언제나 컬럼 하나예요(2차원 블록이 없어요).

| 연산 | 시간 | 추가 메모리 |
|---|---|---|
| `LabelTable` 만들기 | $O(n)$ (factorize 한 번) | 코드 $8n$ B, 첫 위치, 해시 테이블 |
| CSR 만들기 | $O(n + g)$ ($g$: 서로 다른 라벨 수) | $8(n + g)$ B |
| 라벨 $k$개 조회 | $O(k)$ 기대 시간 | 결과 $8k$ B |
| 정렬(alignment) | $O(n_a + n_b)$ + 컬럼마다 `take` | 합집합 라벨, 위치 배열 둘 |
| step 1 슬라이스 | $O(1)$ + 비트맵 popcount $O(\ell / 8)$ | 없음 (Buffer 공유) |
| `take` ($k$개 위치) | $O(k)$, 무작위 읽기 | 결과 |
| 마스크 필터 | $O(n)$ 두 번 (세기, 압축) | 결과 (+ 결측이 있으면 바이트 $2n$) |
| `set_rows` (고정폭, $k$개 위치) | $O(k)$, 공유되어 있으면 + 복사 $O(\ell)$ | 공유되어 있으면 $\ell$행 |
| `set_rows` (문자열) | $O(\ell)$ | 컬럼 전체 |

### 작은 데이터의 호출 비용

10행에서는 커널보다 호출 비용(Python 층, 바인딩, 결과 객체 만들기)이 시간을 정해요.

- `df["a"]`는 dict에서 Column을 꺼내 Series 객체 하나를 만드는 일이에요. Column은 값 타입이라 Python 객체 안으로 `shared_ptr` 셋을 옮기기만 해요.
- `df[df["a"] > 0]`은 비교 한 번, 마스크 맞추기(같은 Index 객체라서 `is`에서 끝나요), 컬럼마다 `filter`, 결과 라벨의 `nonzero`예요.
