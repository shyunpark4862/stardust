## 한눈에 보기

데이터프레임의 데이터는 세 층으로 이루어져 있어요.

| 층 | 이름 | 파일 | 하는 일 |
|---|---|---|---|
| 메모리 블록 | `Buffer` | `csrc/base/buffer.hpp` | 참조 수로 수명을 관리하는 바이트 덩어리. 모든 영역이 함께 써요 |
| 컬럼 | `Column` | `csrc/frame/column.hpp` | dtype 하나의 1차원 배열. Buffer 최대 셋(값, 비트맵, 문자열 위치)과 정수 넷 |
| 표 | `Series`, `DataFrame` | `src/stardust/frame/_series.py`, `_frame.py` | Column에 행 라벨(Index)과 이름을 붙인 Python 객체 |

`Column`은 이렇게 생겼어요.

이 글의 요점은 다섯 가지예요.

1. **Column은 데이터를 갖지 않고 가리켜요.** 값은 `shared_ptr<Buffer>`로 공유해요. Column을 복사하면 포인터 셋이 복사될 뿐이고, 슬라이스(`head`, `.iloc[a:b]`)는 시작 위치와 길이만 바꾼 새 Column이에요.
2. **결측은 비트맵의 0 비트예요. 결측이 없으면 비트맵이 없어요.** 커널은 "비트맵이 있는가"를 한 번 보고 결측 검사가 없는 루프로 가요. 비트맵이 있으면 1바이트를 8바이트로 펼치는 표로 행마다 분기 없이 읽어요.
3. **결측 자리의 값은 언제나 0이에요.** 해시와 비교에 쓰레기 값이 섞이지 않고, 합 같은 커널이 결측 행을 분기 없이 그냥 계산에 넣을 수 있어요.
4. **쓰기는 Copy-on-Write예요.** 쓰기 직전에 Buffer의 참조 수를 보고, 다른 주인이 있으면 먼저 복사해요. 복사는 꼭 필요할 때만 일어나요.
5. **경계에서는 나갈 때 공유, 들어올 때 복사해요.** numpy·`sd.ndarray`로 내보낼 때는 같은 메모리를 가리키는 읽기 전용 배열을 주고, 받아들일 때는 언제나 복사해요.

## Buffer: 컬럼이 서 있는 메모리

`Buffer`는 배열, 선형대수, 데이터프레임이 함께 쓰는 메모리 블록이에요. 자세한 구현은 [데이터 모델](/internals/array/data-model/)에 있고, 여기서는 컬럼에 중요한 성질만 정리해요.

- **128바이트 정렬.** 데이터의 시작 주소가 Apple M4 Pro의 캐시 라인(128바이트) 경계에 놓여요. Arrow 명세는 8바이트나 64바이트 정렬을 권하는데 [1], stardust는 대상 기계의 캐시 라인에 맞췄어요.
- **작은 데이터는 Buffer 객체 안에.** 256바이트(`kInline`) 이하의 데이터는 Buffer 객체 안의 배열에 두고, Buffer와 참조 수 블록을 `make_shared`로 한 번에 할당해요. 컬럼으로 따지면 int64·float64 값은 32행까지, 비트맵은 2,048행까지, 문자열 offsets는 31행까지가 할당 한 번이에요. 10행짜리 컬럼은 값 버퍼 하나에 할당 한 번이고, 결측이 없으면 그게 전부예요.
- **`calloc`의 0 페이지.** 0으로 채운 Buffer를 큰 크기로 요청하면 운영체제가 처음 접근할 때 0으로 채우는 페이지를 받아요. 해시 테이블이 이것을 이용해요([해시 테이블과 factorize](/internals/frame/hashing/)).
- **참조 수.** `shared_ptr<Buffer>`의 복사본 개수가 곧 그 Buffer의 주인 수예요. Copy-on-Write가 이 수를 봐요.
- **물리 메모리 검사.** 물리 메모리보다 큰 요청은 할당 전에 거절해요. `Buffer::allocate`는 요청한 바이트 수를 이 기계의 물리 메모리(`sysctlbyname("hw.memsize")`, 한 번만 읽어요)와 비교해서, 넘으면 `std::bad_alloc`의 하위 클래스를 던져요. Python에서는 `MemoryError`이고, 메시지에 `cannot allocate N bytes: more than this machine's physical memory`가 들어가요. macOS는 큰 요청에도 주소 공간부터 내주고 실제 페이지는 쓸 때 채우므로, 검사하지 않으면 할당은 성공하고 쓰는 도중에 프로세스가 강제 종료될 수 있어요. 물리 메모리보다 작지만 남은 메모리보다 큰 요청은 운영체제에 맡겨요.

Buffer에는 외부 메모리를 빌려 쓰는 `Buffer::adopt`(버퍼 프로토콜)도 있지만, 데이터프레임은 쓰지 않아요. 이유는 아래 "numpy에서 들어올 때"에서 설명해요.

## DType: 네 가지

dtype은 모든 영역이 함께 쓰는 열거형이에요.

```cpp
// csrc/base/dtype.hpp
enum class DType : std::uint8_t { Bool, Int64, Float64, Complex128, String };
```

데이터프레임은 이 중 `Bool`, `Int64`, `Float64`, `String`을 써요. `Complex128`은 배열 영역에만 있어요. 원소 하나의 크기 `itemsize`는 bool 1, int64·float64 8이고, `String`은 0이에요. 문자열의 바이트는 고정 크기 칸이 아니라 따로 이어 붙인 버퍼에 있기 때문이에요(아래 "문자열" 절).

배열 영역에는 dtype을 C++ 타입으로 바꿔 함수를 부르는 `visit_dtype`이 있지만, 데이터프레임 커널은 그것을 쓰지 않고 dtype마다 자기 루프를 직접 골라요. 커널마다 받는 dtype 조합이 다르고(예: 비교는 bool과 int64가 만나면 bool을 int64로 바꾼 뒤 다시 골라요), 문자열은 별도의 루프가 필요하기 때문이에요.

Python 층과 바인딩은 dtype을 이름 문자열(`"int64"`)로 주고받고, C++에서는 `parse_dtype`이 이름을 열거형으로 바꿔요.

## Column 구조체

```cpp
// csrc/frame/column.hpp (발췌)
struct Column {
    DType dtype = DType::Float64;
    std::int64_t length = 0;
    std::int64_t offset = 0;      // Buffer 안의 첫 행. values의 원소, validity의 비트, offsets의 칸을 똑같이 센다
    std::int64_t null_count = 0;
    std::shared_ptr<Buffer> values;    // bool/int64/float64는 값, string은 모든 UTF-8 바이트
    std::shared_ptr<Buffer> validity;  // null_count == 0일 때 정확히 null
    std::shared_ptr<Buffer> offsets;   // string만: length + 1개의 int64 위치. 절대 위치라 슬라이스가 공유한다

    template <class T>
    const T* data() const { return reinterpret_cast<const T*>(values->data()) + offset; }

    bool is_valid(std::int64_t i) const { return !validity || bitmap::get(validity_bits(), offset + i); }

    std::string_view string_at(std::int64_t i) const {
        const std::int64_t* o = string_offsets();          // offsets->data() + offset
        return {reinterpret_cast<const char*>(values->data()) + o[i],
                static_cast<std::size_t>(o[i + 1] - o[i])};
    }

    Column slice(std::int64_t start, std::int64_t len) const;
    Column convert(DType target) const;   // 손실 없는 int64 ↔ float64 (조회 x in s용)
};
```

arm64 macOS(libc++)에서 각 부분의 크기예요.

| 부분 | 바이트 | 비고 |
|---|:---:|---|
| `dtype` | 1 | 다음 `int64_t`를 8바이트 경계에 두려고 7바이트를 채워요 |
| `length`, `offset`, `null_count` | 24 | |
| `values`, `validity`, `offsets` | 48 | libc++의 `shared_ptr`는 포인터 둘(객체, 제어 블록)이라 16바이트씩 |
| **합계** | **80** | |

80바이트는 데이터 크기와 무관해요. 1M 행 컬럼도 Column 자체는 80바이트이고, 1M 행의 값은 Buffer에 있어요.

### 지키는 약속

Column을 만들고 고치는 모든 코드가 다음 네 약속을 지켜요. 커널은 이 약속을 믿고 검사를 생략해요.

1. **`validity`가 null인 것과 `null_count == 0`은 같은 뜻이에요.** 결측이 하나라도 있으면 비트맵이 반드시 있고, 하나도 없으면 반드시 없어요. 슬라이스에서도 지켜요.
2. **결측 행의 값 자리는 0이에요.** 문자열이면 길이 0이에요.
3. **`offset`은 세 Buffer에 같은 단위로 적용돼요.** 행 i의 값은 `values`의 원소 `offset + i`, 결측 여부는 `validity`의 비트 `offset + i`, 문자열 위치는 `offsets`의 칸 `offset + i`에 있어요.
4. **문자열 offsets는 절대 위치예요.** 바이트 버퍼의 처음부터 센 위치라서, 슬라이스가 offsets를 다시 계산하지 않아요.

`data<T>()`와 `string_offsets()`가 `offset`을 미리 더해 주므로, 커널은 행 번호 0부터 `length - 1`까지만 생각하면 돼요.

### Python 쪽: 값 타입으로 넘어가요

`Column`은 nanobind로 `stardust._core.frame.Column`이라는 Python 클래스가 돼요. **값 타입**으로 바인딩해서, Python 객체 안에 80바이트 구조체가 그대로 들어 있어요. 커널이 돌려준 Column은 새 Python 객체 안으로 move되고, 이때 `shared_ptr` 셋의 소유권이 옮겨 갈 뿐 참조 수는 변하지 않아요. `shared_ptr<Column>`을 holder로 쓰는 방법보다 작은 연산이 두 배쯤 빨라요(원소 10개 `add`가 89 ns 대 190 ns. 이유는 [데이터프레임 영역의 구조](/internals/frame/overview/)에 있어요).

`Series`는 Column 객체 하나, Index 하나, 이름 하나를 담은 Python 객체예요.

```python
# src/stardust/frame/_series.py (발췌)
@own_reductions
class Series(Reductions):
    __slots__ = ("_col", "_index", "_name")
```

`__slots__`를 쓰면 인스턴스마다 `__dict__`가 없어서 객체가 작고 속성 접근이 빨라요. 연산 결과는 `Series._new(col, index, name)`으로 만드는데, `__init__`을 거치지 않고 세 칸을 바로 채워서 인자 검사를 다시 하지 않아요.

`Reductions`는 `sum`, `mean`, `min`, `max`, `std`, `var`, `count`의 인자 검사를 Series, DataFrame, GroupBy가 함께 쓰는 믹스인 클래스예요(`_reduce.py`). 그런데 함수는 자기가 정의된 클래스의 이름을 `__qualname__`과 코드 객체의 `co_qualname`에 담고 있고, 인자가 틀린 호출에 Python이 내는 메시지는 그 이름을 써요. 그대로 두면 `s.sum(axis=0)`의 메시지가 사용자가 모르는 `Reductions.sum()`으로 시작해요. 클래스 데코레이터 `own_reductions`는 일곱 메서드를 클래스마다 새 함수 객체로 복사하면서(`types.FunctionType`, `code.replace(co_qualname=...)`) 이름을 그 클래스의 것으로 바꿔요. 그래서 메시지가 `Series.sum() got an unexpected keyword argument 'axis'`처럼 다른 메서드와 같은 꼴이 돼요. 함수 본문(코드)은 공유하고 이름표만 다르므로 실행 비용은 같아요.

## validity 비트맵

### 직관: 결측을 어디에 적을까

컬럼의 어떤 행에 값이 없다는 사실을 적는 방법은 세 가지가 있어요.

- **값 자리에 특별한 값(sentinel)을 넣기.** float의 NaN, 객체 배열의 `None`이 그래요. 메모리가 더 들지 않지만, int64와 bool에는 비어 있는 비트 패턴이 없어요. 모든 비트 패턴이 이미 정상 값이거든요. 그래서 pandas의 기본 dtype은 int 컬럼에 결측이 생기면 float64로 바꿔요. 그리고 NaN을 결측으로 쓰면, 계산에서 나온 진짜 NaN과 "값 없음"을 구별할 수 없어요.
- **행마다 1바이트 마스크.** pandas의 nullable dtype(`Int64`, `Float64`, `boolean`)이 그래요. 값 배열 `_data` 옆에 행마다 1바이트 bool 배열 `_mask`(True = 결측)를 둬요 [2]. 읽기가 쉽지만 메모리가 행마다 1바이트 더 들어요.
- **행마다 1비트 비트맵.** Arrow 형식과 그것을 따르는 Polars가 그래요 [1]. 메모리가 1/8이지만 행 하나를 읽으려면 바이트를 찾고 비트를 꺼내야 해요.

stardust는 비트맵을 써요. 모든 dtype에 같은 방법이 통하고, 진짜 NaN과 결측이 구별되고, 메모리가 가장 적어요. 비트를 꺼내는 비용은 아래 "바이트로 펼치기"로 해결해요.

### 정의

- 행마다 1비트. 1이면 값이 있고, 0이면 결측이에요.
- **LSB 우선**: 행 i는 바이트 `i / 8`의 비트 `i % 8`(가장 낮은 비트가 비트 0)이에요. Arrow와 같은 비트 순서라서 [1], 비트맵 바이트가 Arrow의 것과 그대로 맞아요.
- 비트맵의 바이트 수는 `(행 수 + 7) / 8`이에요. 마지막 바이트에서 쓰지 않는 높은 비트의 값은 정해져 있지 않고, 어떤 커널도 읽지 않아요.

10행짜리 컬럼에서 행 1과 행 7이 결측이면 이래요.

행 i의 비트를 읽는 식은 이래요.

$$
\text{valid}(i) = \bigl(\text{bits}[\,i \gg 3\,] \gg (i \mathbin{\&} 7)\bigr) \mathbin{\&} 1
$$

`i >> 3`은 `i / 8`, `i & 7`은 `i % 8`이에요. 8이 2의 거듭제곱이라 나눗셈 없이 시프트와 AND로 돼요.

```cpp
// csrc/frame/bitmap.hpp (발췌)
inline std::int64_t num_bytes(std::int64_t nbits) { return (nbits + 7) / 8; }
inline bool get(const std::uint8_t* bits, std::int64_t i) { return (bits[i >> 3] >> (i & 7)) & 1; }
inline void set(std::uint8_t* bits, std::int64_t i)   { bits[i >> 3] |= std::uint8_t(1u << (i & 7)); }
inline void clear(std::uint8_t* bits, std::int64_t i) { bits[i >> 3] &= std::uint8_t(~(1u << (i & 7))); }
```

### 결측이 없으면 비트맵이 없어요

결측이 없는 컬럼의 `validity`는 null 포인터예요. 모든 비트가 1인 비트맵을 두지 않아요. 그래서 커널은 컬럼마다 한 번 `col.validity`를 보고 두 루프 중 하나를 골라요.

```cpp
// csrc/frame/ops/selection.cpp의 isna (발췌)
Column isna(const Column& col, bool want_na) {
    Column out = make_fixed(DType::Bool, col.length);
    auto bits = rebased_validity(col);      // 비트맵이 없으면 null
    if (!bits) {                            // 결측 없음: 전부 False (notna면 전부 True)
        std::memset(out_bytes, want_na ? 0 : 1, col.length);
        return out;
    }
    // 결측 있음: 비트를 바이트로 펼친다 (아래)
    ...
}
```

이 선택은 데이터를 훑어보고 고르는 휴리스틱이 아니에요. "결측이 있는가"는 Column이 이미 알고 있는 속성(`null_count`)이고, 값을 보지 않고 정해져요. 실제 데이터의 대부분은 결측이 없는 컬럼이라서, 그 경우의 커널은 결측 지원이 없는 커널과 같은 속도로 돌아요.

### popcount로 결측 세기

슬라이스나 대입 뒤에는 어떤 범위의 결측 수를 다시 세야 해요. 비트를 하나씩 세지 않고 바이트마다 `popcount`(1인 비트의 개수를 세는 명령, AArch64에서는 `cnt`)를 써요. 범위가 바이트 중간에서 시작하거나 끝나면, 양 끝의 덜 찬 바이트만 범위 밖 비트를 마스크로 지운 뒤 세요.

```cpp
// csrc/frame/bitmap.hpp의 count_set (줄임): 비트 [start, start + length) 중 1의 개수
std::int64_t first = start >> 3, last = (end - 1) >> 3;
auto byte_mask = [](int lo, int hi) { return std::uint8_t(((1u << hi) - 1) & ~((1u << lo) - 1)); };
if (first == last) return popcount(bits[first] & byte_mask(start & 7, ((end - 1) & 7) + 1));
std::int64_t count = popcount(bits[first] & byte_mask(start & 7, 8));        // 앞쪽 덜 찬 바이트
for (std::int64_t b = first + 1; b < last; ++b) count += popcount(bits[b]);  // 가운데 꽉 찬 바이트
count += popcount(bits[last] & byte_mask(0, ((end - 1) & 7) + 1));            // 뒤쪽 덜 찬 바이트
```

위 10행 예에서 행 3–7(비트 3–7)의 1을 세면, 바이트 0x7D에 비트 3–7만 남기는 마스크 0xF8을 씌워 0x78이 되고, popcount는 4예요. 범위 5행 중 4행에 값이 있으니 결측은 1개(행 7)예요. 1M 행이면 바이트 125,000개에 popcount를 한 번씩 하는 셈이라 수 µs예요.

### 비트를 0부터 다시 맞추기: `copy_bits`

두 컬럼의 비트맵을 합칠 때(예: `a + b`의 결과는 두 입력 모두 값이 있는 행만 값이 있어요) 바이트 단위로 AND하면 빨라요. 그런데 슬라이스는 비트맵의 중간 비트에서 시작할 수 있어요. `a`가 비트 3에서, `b`가 비트 0에서 시작하면 같은 행이 서로 다른 바이트 위치에 있어서 바이트끼리 AND할 수 없어요.

그래서 먼저 각 비트맵을 비트 0에서 시작하는 새 비트맵으로 옮겨요(`copy_bits`, `rebased_validity`). 출력 바이트 j는 입력 바이트 둘을 시프트해서 붙인 것이에요.

$$
\text{dst}[j] = \bigl(\text{src}[k] \gg s\bigr) \;\big|\; \bigl(\text{src}[k+1] \ll (8 - s)\bigr), \qquad k = \lfloor \text{offset}/8 \rfloor + j,\quad s = \text{offset} \bmod 8
$$

위 10행 비트맵에서 행 6–9(비트 오프셋 6, 4비트)를 옮기는 예예요.

`copy_bits`는 비트 `offset + n - 1`이 든 바이트 너머를 읽지 않아요(`k + 1`이 마지막 바이트를 넘으면 OR하지 않아요). 그래서 Buffer 끝을 넘어 읽지 않아요.

이렇게 맞춘 뒤 결과 비트맵은 바이트 단위 AND 한 줄이에요.

```cpp
// csrc/frame/column.cpp의 and_validity (줄임)
std::shared_ptr<Buffer> and_validity(const Column& a, const Column& b, int scalar_side, std::int64_t n) {
    std::shared_ptr<Buffer> out;
    for (int side = 1; side <= 2; ++side) {
        const Column& c = side == 1 ? a : b;
        if (!c.validity) continue;                         // 결측 없는 쪽은 건너뛴다
        if (side == scalar_side)                           // NA 스칼라: 모든 행이 결측
            return Buffer::allocate(bitmap::num_bytes(n), /*zeroed=*/true);
        if (!out) out = rebased_validity(c);
        else {
            auto other = rebased_validity(c);
            for (std::int64_t j = 0; j < bitmap::num_bytes(n); ++j) out_bytes[j] &= other_bytes[j];
        }
    }
    return out;                                            // 둘 다 결측이 없으면 null
}
```

스칼라는 1행 Column이에요. 스칼라가 결측(`s + NA`)이면 그 1행의 비트가 0이고, 결과는 모든 행이 결측이에요. 이때는 0으로 채운 비트맵을 새로 할당해 돌려줘요.

### 바이트로 펼치기: 분기 없이 읽는 방법

비트맵은 메모리가 적지만, 커널이 행마다 `get(bits, i)`로 비트를 꺼내고 그 결과로 분기하면 느려요. 비트 하나를 꺼내는 데 시프트와 AND가 들고, 결측이 무작위로 흩어져 있으면 "이 행은 결측인가" 분기를 CPU가 예측하지 못해요. 예측이 틀릴 때마다 파이프라인을 비우고 다시 시작하는 비용이 그 행에 붙어요. 무엇보다 행마다 분기가 있는 루프는 컴파일러가 SIMD로 벡터화하지 못해요.

그래서 비트맵을 행마다 0 또는 1인 바이트로 펼친 뒤 그 바이트로 분기 없이 골라요. 펼치는 방법은 256칸짜리 표예요.

```cpp
// csrc/frame/bitmap.hpp (발췌)
// 바이트 값 b마다, b의 비트 k를 바이트 k에 담은 8바이트 (0 또는 1)
inline constexpr std::array<std::uint64_t, 256> kExpand = [] {
    std::array<std::uint64_t, 256> t{};
    for (unsigned b = 0; b < 256; ++b)
        for (unsigned k = 0; k < 8; ++k) t[b] |= std::uint64_t((b >> k) & 1) << (8 * k);
    return t;
}();

inline void expand(const std::uint8_t* bits, std::int64_t n, std::uint8_t* out) {
    const std::int64_t full = n / 8;
    for (std::int64_t j = 0; j < full; ++j) std::memcpy(out + 8 * j, &kExpand[bits[j]], 8);  // 8행을 한 번에
    for (std::int64_t i = full * 8; i < n; ++i) out[i] = get(bits, i);                     // 남은 7행 이하
}
```

- 표는 `constexpr` 람다로 컴파일할 때 계산돼요. 실행 중에 만드는 비용이 없고, 2KB(256 × 8바이트)라서 L1 캐시(128KB)에 들어가요.
- `t[b]`의 바이트 k에 b의 비트 k를 넣었어요. Apple Silicon은 리틀 엔디언이라 64비트 정수의 바이트 k가 메모리에서 k번째 바이트예요. 그래서 `memcpy` 한 번이 행 8개의 0/1 바이트를 순서대로 써요.
- 비트맵 1바이트 → 표 조회 1번 → 8바이트 쓰기. 행 8개마다 분기 없는 load 하나, store 하나예요.

펼친 바이트로 커널을 쓰면 `valid ? x : 0` 같은 선택이 분기가 아니라 비트 연산이 돼요. 결측 자리를 0으로 지우는 `finish_fixed`가 그 예예요(아래). 이런 루프는 컴파일러가 NEON의 16바이트 AND로 벡터화해요.

두 설계를 같은 조건에서 비교한 값이에요(1M 행, 결측 10%, 1스레드, Apple M4 Pro).

| 커널 | 행마다 비트를 꺼내 분기 | 바이트로 펼쳐 분기 없이 |
|---|---:|---:|
| `isna` | 377 µs | 47 µs |
| `int + int` | 487 µs | 305 µs |
| `bool & bool` (Kleene) | 1.43 ms | 542 µs |
| float `std` | 1.03 ms | 475 µs |
| float `min` | 933 µs | 613 µs |

`isna`의 47 µs에는 펼치기 말고 손질이 하나 더 들어 있어요. 루프의 경계와 포인터를 지역 변수로 꺼내 둔 거예요. `uint8_t*`로 쓰는 루프에서는 C++ 규칙상 그 쓰기가 어떤 객체든(루프 경계 `col.length`도) 바꿀 수 있다고 봐서, 컴파일러가 매 반복 경계를 다시 읽고 벡터화를 포기해요. 같은 조건에서 펼치기만 하고 경계를 꺼내 두지 않은 루프는 288 µs예요(이 둘만 따로 비교하면 꺼낸 루프가 48 µs예요. 위 표의 47 µs와는 다른 회차의 측정이에요). 이 앨리어싱 문제는 [원소별 연산과 리덕션](/internals/frame/elementwise/)에 자세히 있어요.

펼치기의 대가는 청크마다 바이트 배열 하나예요. `finish_fixed`처럼 청크 안에서 펼치는 커널은 16,384바이트짜리 스택 버퍼 하나를 써서 힙 할당이 없어요. pandas의 nullable 배열은 처음부터 행마다 1바이트라서 펼치는 단계가 없는 대신, 메모리를 8배 쓰고 컬럼을 읽을 때마다 그 8배를 지나가요.

### 병렬로 쓸 때: 청크는 64행의 배수

여러 스레드가 한 비트맵의 서로 다른 행을 쓸 때, 두 스레드가 같은 바이트의 다른 비트를 쓰면 경쟁 조건이 생겨요. 바이트 쓰기는 "읽고, 비트를 바꾸고, 쓰기"라서 한쪽의 변경이 사라질 수 있거든요. 데이터프레임의 청크는 16,384행이고 64의 배수라서, 청크 경계가 언제나 바이트(그리고 64비트 워드) 경계에 떨어져요. 각 청크가 자기 비트맵 바이트를 경쟁 없이 써요. 청크와 스레드 정책은 [병렬화와 결정성](/internals/frame/parallel/)에 있어요.

## 결측 자리의 값은 0

### 왜 0으로 두나

결측 행의 값 자리에는 무엇이 있어도 의미상 상관없어요. 비트맵이 "값 없음"이라고 하니까요. Arrow 명세도 결측 칸의 값을 정하지 않아요 [1]. pandas 3.1.1에서 `pd.array([1, None, 3], dtype="Int64")`의 값 배열 `_data`는 `[1, 1, 3]`이에요. 결측 자리에 옆 값이 남아 있어요.

stardust는 결측 자리를 언제나 0으로 둬요(문자열은 길이 0). 이유는 넷이에요.

1. 해시와 비교에 쓰레기 값이 섞이지 않아요. 예를 들어 `NA + 5`의 값 자리에 5가 남아 있으면, 나중에 그 컬럼이 groupby 키가 될 때 결측 행을 다루는 코드가 한 번이라도 값 자리를 읽으면 5가 새어 나와요. 0이면 어떤 코드가 값 자리를 읽어도 결과가 같아요.
2. 결과가 비트까지 결정적이에요. 결측 자리에 "그때 메모리에 있던 값"이 남으면, 같은 연산의 결과 Buffer가 실행마다 바이트 단위로 달라질 수 있어요. pickle이나 바이트 비교 테스트가 흔들려요.
3. 분기 없는 커널을 짤 수 있어요. float 합은 결측 행의 0.0을 그대로 더해요. 0.0을 더해도 합은 변하지 않아요. 유일한 예외는 `-0.0 + 0.0 = +0.0`인데, 합은 어차피 `0.0 +`에서 시작해서(numpy와 같아요) 결과가 `-0.0`이 될 일이 없어요. int 합도 0을 더할 뿐이에요. 그래서 결측이 있는 컬럼의 합이 "결측 행을 골라내는" 루프 없이 결측 없는 컬럼과 같은 루프로 돌아요.
4. 마스크 필터가 결측을 False로 읽어요. bool 마스크의 결측 행은 값이 0이라서, 필터 커널이 비트맵을 보지 않고 값 바이트만 봐도 그 행을 버려요.

### `finish_fixed`: 결과를 마무리하는 한 함수

결과 컬럼을 만드는 고정폭 커널은 마지막에 모두 `finish_fixed`를 불러요. 커널 본체는 결측 행의 값 자리에 무엇을 써도 되고(예: `x[i] + y[i]`를 계산하면 결측 행에도 어떤 값이 써져요), 정리는 이 함수가 한 번에 해요.

```cpp
// csrc/frame/column.cpp (발췌)
void finish_fixed(Column& col) {
    col.null_count = 0;
    if (!col.validity) return;
    const auto* bits = col.validity_bits();
    col.null_count = col.length - bitmap::count_set(bits, 0, col.length);
    if (col.null_count == 0) {          // 결측이 없으면 비트맵을 버린다 (약속 1)
        col.validity.reset();
        return;
    }
    auto zero = [&](auto* v) {          // 결측 행의 값을 분기 없이 지운다 (약속 2)
        using T = std::remove_reference_t<decltype(*v)>;
        for_chunks(col.length, [bits, v](std::int64_t lo, std::int64_t hi) {
            std::uint8_t m[kChunkRows];                  // 16 KB 스택 버퍼
            const std::int64_t len = hi - lo;
            bitmap::expand(bits + lo / 8, len, m);       // 청크의 비트를 바이트로
            T* w = v + lo;
            for (std::int64_t i = 0; i < len; ++i) w[i] &= static_cast<T>(0 - static_cast<T>(m[i]));
        });
    };
    if (itemsize(col.dtype) == 1) zero(reinterpret_cast<std::uint8_t*>(col.values->data()));
    else zero(reinterpret_cast<std::int64_t*>(col.values->data()));   // int64와 float64가 같은 루프
}
```

값을 지우는 일은 `w[i] &= 0 - m[i]` 한 줄이 해요. `m[i]`가 1이면 `0 - 1`은 2의 보수로 모든 비트가 1이라서(`0xFFFF…FF`) AND해도 값이 그대로예요. 0이면 `0 - 0 = 0`이라서 AND하면 0이 돼요. 분기 없이 "값이 있으면 그대로, 없으면 0"이 되는 거예요.

  <ArrayFig name="값" data={[5, 7, 9, 2]} tones={['', 'g', '', '']} />
  <Op>{'&'}</Op>
  <ArrayFig name="0 - m" data={['FF…FF', '00…00', 'FF…FF', 'FF…FF']} tones={['', 'b', '', '']} note="m = [1, 0, 1, 1]" />
  <Op>→</Op>
  <ArrayFig name="결과" data={[5, 0, 9, 2]} tones={['', 'b', '', '']} />

float64를 int64 포인터로 다루는 이유는 IEEE 754의 `+0.0`이 모든 비트가 0인 값이기 때문이에요. 값을 정수로 보고 비트를 지우면 float로 읽었을 때 `+0.0`이에요. 그래서 8바이트 dtype 둘이 한 루프를 써요. 이 루프는 NEON의 128비트 AND로 벡터화돼서, 한 명령이 8바이트 값 둘을 처리해요.

## dtype별 값 저장

| dtype | 값 Buffer | 행마다 |
|---|---|:---:|
| `bool` | 바이트 하나에 값 하나 (0 또는 1) | 1바이트 |
| `int64` | 64비트 2의 보수 정수 | 8바이트 |
| `float64` | IEEE 754 binary64 | 8바이트 |
| `string` | offsets(int64, 행 수 + 1개) + 이어 붙인 UTF-8 바이트 | 8바이트 + 문자열 길이 |

비트맵은 결측이 있을 때만 행마다 1비트가 더해져요.

### bool은 바이트 하나

Arrow 형식은 boolean 값을 비트로 묶어 저장해요 [1]. stardust는 값 하나에 바이트 하나를 써요.

- 비교 결과를 그대로 쓸 수 있어요. NEON 비교 명령은 레인마다 "모두 0" 또는 "모두 1"인 바이트 마스크를 내요. 결과를 바이트로 저장하면 그 마스크에 1을 AND해서 바로 쓰면 되고, 비트로 묶는 단계가 필요 없어요.
- 마스크 필터가 단순해요. 분기 없는 압축 커널은 `k += keep[i]`처럼 마스크 바이트를 그대로 더해요([라벨, 조회, 선택](/internals/frame/labels/)). 비트였다면 행마다 비트를 꺼내야 해요.
- 커널의 dtype 처리가 단순해요. bool은 원소 크기 1인 고정폭 dtype이라서 `take`, `concat`, `finish_fixed`가 크기만 바꿔 같은 코드를 써요. 비트로 묶은 dtype은 이 모든 곳에 비트 단위 경로가 따로 필요해요.

대가는 메모리 8배와, bool 컬럼을 통째로 읽는 연산의 비용이에요. `bool.sum()`은 1M 바이트를 더해요(1M 행, 1스레드에서 44 µs). 비트로 저장하면 바이트 125,000개에 popcount를 하면 되므로 훨씬 짧아요.

### int64와 float64

8바이트 값이 그대로 이어져 있어요. numpy의 `int64`, `float64` 배열과 바이트 단위로 같은 배치라서, 결측이 없으면 numpy 배열이나 `sd.ndarray`가 이 Buffer를 그대로 가리킬 수 있어요(아래 "경계" 절).

### 문자열: offsets와 바이트

문자열은 길이가 제각각이라 고정 크기 칸에 넣을 수 없어요. 그래서 모든 문자열의 UTF-8 바이트를 한 버퍼에 이어 붙이고, 행 i의 문자열이 그 버퍼의 어디서 시작해서 어디서 끝나는지를 **offsets** 배열에 적어요. 행 i는 바이트 `[offsets[i], offsets[i+1])`이에요. 행이 n개면 offsets는 n + 1개예요. Arrow의 가변 길이 binary 레이아웃과 같은 방식이에요 [1].

offsets는 int64예요. int32 offsets는 한 컬럼의 문자열 바이트가 모두 합쳐 2GB(2³¹바이트)를 넘으면 쓸 수 없어요. 1M 행에 평균 2KB 문자열이면 넘는 크기예요. Arrow도 64비트 offsets를 쓰는 형식(`large_string`)을 따로 두는데 [1], stardust는 이 형식만 써요. 대신 행마다 4바이트를 더 써요.

문자열 컬럼을 만들 때는 두 번 훑어요. Python list에서 만들 때 첫 번째 훑기에서 각 문자열의 UTF-8 길이만 더하고, 바이트 버퍼를 그 크기로 한 번에 할당한 뒤, 두 번째 훑기에서 바이트를 복사하며 offsets를 써요. 버퍼가 자라면서 다시 할당되는 일이 없어요. `PyUnicode_AsUTF8AndSize`는 str 객체 안에 UTF-8 표현을 캐시하므로, 두 번째 훑기에서 같은 함수를 다시 불러도 인코딩을 다시 하지 않아요. 문자열 결과를 내는 커널(이어 붙이기, `fillna`)도 같은 모양이에요. 청크마다 결과 바이트 수를 세고, 그 누적합으로 청크마다 쓸 시작 위치를 정한 뒤, 청크마다 자기 자리에 써요.

**이 레이아웃으로 얻는 것.**

- 커널이 Python 객체를 거치지 않아요. 해시, 비교, 필터, 정렬이 바이트를 바로 읽어요. 행 i의 문자열은 `string_view` 하나(포인터와 길이)로 꺼내져요.
- 바이트 비교가 곧 Python의 문자열 순서예요. `std::string_view::compare`는 `char_traits<char>::compare`로 바이트를 부호 없는 값으로 비교해요. UTF-8은 바이트를 부호 없이 사전식으로 비교한 순서가 코드포인트 순서와 같은 인코딩이라서 [6], 디코딩하지 않고도 Python `str`과 같은 순서가 나와요.
- 문자열의 앞 8바이트를 정수 하나로 읽을 수 있어요. 정렬은 각 문자열의 앞 8바이트를 big-endian `uint64`로 읽어 기수 정렬해요. 바이트가 연속으로 놓여 있어서 `memcpy` 한 번이에요([groupby와 정렬](/internals/frame/groupby-sort/)).
- 이어 붙이기가 메모리를 차례로 지나가요. 결과 바이트 수를 먼저 세고 한 번에 할당한 뒤, 입력 바이트를 앞에서부터 복사해요.

**대가.**

- `tolist()`가 비싸요. 행마다 UTF-8을 디코딩해 str 객체를 새로 만들어요(`PyUnicode_DecodeUTF8`). 1M 행에 15.7 ms(1스레드)예요. 문자열을 Python 객체로 저장하는 구현(pyarrow가 없는 pandas 3의 `str` dtype)은 이미 있는 객체의 참조만 늘리면 돼요.
- `filter`와 `take`가 문자열 길이에 비례해요. 고른 행의 바이트를 새 버퍼로 복사해야 하거든요. 고정폭 dtype의 분기 없는 압축(항상 쓰고 남길 때만 위치를 늘리기)은 문자열에 맞지 않아요. 길이가 제각각이라 "항상 쓰기"가 비싸서, 문자열 마스크 필터는 `take(nonzero(mask))`로 해요.

Polars는 이 대가를 피하려고 Arrow의 문자열 view 레이아웃을 써요 [1, 3]. 행마다 16바이트짜리 view를 두고, 12바이트 이하의 문자열은 view 안에 통째로, 긴 문자열은 길이·앞 4바이트·버퍼 번호·위치를 적어요. `filter`와 `take`가 16바이트 view만 옮기면 되므로 문자열 길이와 무관해요. 대신 행마다 16바이트를 쓰고(offsets는 8바이트), 걸러진 뒤에도 긴 문자열 버퍼가 통째로 남아 있어서 언제 정리할지 정해야 해요 [3]. stardust는 짧은 문자열을 인라인으로 두는 레이아웃을 쓰지 않아요.

## 슬라이스: 복사하지 않기

### 방법

`head`, `tail`, step이 1인 `.iloc[a:b]`, 그리고 `repr`이 가운데 행을 생략할 때 보여 주는 앞뒤 부분은 모두 **슬라이스**예요. 슬라이스는 Buffer를 복사하지 않고 `offset`과 `length`만 바꾼 새 Column이에요.

```cpp
// csrc/frame/column.cpp
Column Column::slice(std::int64_t start, std::int64_t len) const {
    if (start < 0 || len < 0 || start + len > length) throw nb::index_error("column slice out of range");
    Column out = *this;                 // shared_ptr 셋의 복사: 참조 수만 하나씩 는다
    out.offset = offset + start;
    out.length = len;
    if (validity) {                     // 자기 범위의 결측만 다시 센다
        out.null_count = len - bitmap::count_set(validity_bits(), out.offset, len);
        if (out.null_count == 0) out.validity.reset();   // 약속 1: 결측 없으면 비트맵 없음
    }
    return out;
}
```

`offset`이 values의 원소, validity의 비트, offsets의 칸에 똑같이 적용되므로(약속 3), 세 Buffer 모두 그대로 공유해요. 문자열 offsets가 절대 위치라서(약속 4) offsets를 다시 계산할 필요도 없어요.

문자열도 같아요. 위 `["ab", "", "cde", NA]`에서 `slice(2, 2)`는 offsets의 칸 2–4(`[2, 5, 5]`)를 보고, 행 0은 바이트 `[2, 5)` = `"cde"`, 행 1은 길이 0인 결측이에요.

### 비용

슬라이스 하나의 비용은 Column 구조체 복사, 참조 수 증가 셋, 그리고 비트맵이 있으면 자기 범위의 popcount예요. popcount는 64행에 8번 정도라서 1M 행을 슬라이스해도 수 µs예요. 1M 행 DataFrame의 `head()`는 656 ns였어요(1스레드, Apple M4 Pro). 컬럼마다 슬라이스 하나와 `RangeIndex` 슬라이스 하나예요.

슬라이스가 결측을 다시 세는 이유는 약속 1 때문이에요. 1M 행 중 결측이 한 행뿐인 컬럼에서 `head()`를 했는데 앞 5행에 결측이 없으면, 그 5행짜리 컬럼은 비트맵이 없어야 해요. 그래야 그 결과를 받는 커널이 결측 없는 루프로 가요.

### 슬라이스가 아닌 것

step이 1이 아닌 슬라이스(`.iloc[::2]`), 위치 리스트, 마스크는 모두 `take`나 `filter`로 복사해요. 결과가 공유인지 복사인지는 키의 모양으로 정해요. 마스크가 우연히 연속된 행을 골라도 복사예요. 결과 타입이 데이터에 따라 몰래 바뀌지 않게 하려는 거예요([데이터프레임 영역의 구조](/internals/frame/overview/)).

## Copy-on-Write

### 문제

Buffer는 여러 Column이 공유해요. 슬라이스, `df["a"]`, `Series(other_series)`, numpy 뷰가 모두 같은 Buffer를 가리켜요. 그런데 사용자는 각 객체를 독립된 값처럼 다뤄요.

```python
s = df["a"]
s.iloc[0] = 99      # s만 바뀌고 df는 그대로여야 해요 (pandas 3과 같아요)
```

모든 파생 객체를 처음부터 복사하면 이 문제는 없지만, `head()` 하나에 1M 행을 복사하게 돼요. 그래서 **쓰기 전까지는 공유하고, 쓰는 순간 다른 주인이 있으면 그때 복사**해요. 이것이 Copy-on-Write예요. 그러려면 "지금 이 Buffer를 다른 누가 가리키고 있나"를 알아야 하고, 그 답이 참조 수예요.

### 참조 수

`std::shared_ptr`는 가리키는 객체와 함께 **제어 블록**(control block)을 하나 둬요. 제어 블록에는 지금 그 객체를 가리키는 `shared_ptr`의 개수(strong count)가 있어요. `shared_ptr`를 복사하면 1 늘고, 없애면 1 줄고, 0이 되면 객체를 해제해요. 증감은 원자적 연산이라 GIL 없이 여러 스레드에서 해도 안전해요. 이 개수를 읽는 함수가 `use_count()`예요.

Buffer의 `use_count()`가 1이면 그 Buffer를 가리키는 `shared_ptr`가 하나뿐이에요. 곧 지금 쓰려는 이 Column만 이 Buffer를 가리킨다는 뜻이라서, 그 자리에서 고쳐도 아무도 그 변화를 보지 못해요.

### 쓰기는 두 단계

```python
# src/stardust/frame/_series.py
def _assign(self, sel, value):
    labels = None if sel[0] == "one" else _select.select_index(self._index, sel)
    values = assignment_values(value, self._dtype, labels)   # 값을 컬럼 dtype으로 (암묵적 변환)
    self._col = self._col.share()                             # 1단계: 내 Column 객체를 따로 갖는다
    self._col.set_rows(_select.positions_column(sel), values) # 2단계: 참조 수를 보고 쓴다
```

**1단계: 쓰는 쪽이 먼저 자기만의 Column 객체를 만들어요.** `share()`는 같은 Buffer를 가리키는 새 Column 객체를 돌려줘요(바인딩에서 `[](const Column& c) { return c; }`, 곧 `shared_ptr` 셋의 복사예요).

이 단계가 필요한 이유는 `df["a"]`가 DataFrame의 사전에 든 Column 객체를 그대로 Series에 넣기 때문이에요. 두 Python 객체(`df`와 `s`)가 Column 객체 하나를 함께 쥐고 있으면, Buffer를 가리키는 `shared_ptr`는 그 Column 객체 안의 하나뿐이라서 `use_count()`가 1이에요. 2단계만 있다면 다른 주인이 없다고 판단해 그 자리에서 쓰고, `df`까지 바뀌어 버려요. 1단계로 Column 객체를 둘로 나누면 `shared_ptr`도 둘이 되어 참조 수가 2가 돼요.

반대로 옛 Column 객체를 다른 누구도 쥐고 있지 않으면(`s`가 직접 만든 Series라서 `s._col`만 그 객체를 가리키고 있었다면), `self._col = ...` 대입으로 옛 객체가 바로 해제되고 Buffer의 참조 수도 1로 돌아와요. 그래서 1단계는 불필요한 복사를 만들지 않아요.

**2단계: `set_rows`가 values와 validity Buffer의 참조 수를 봐요.**

```cpp
// csrc/frame/ops/selection.cpp의 detach (줄임)
// col에 아무도 공유하지 않는 values와 validity를 준다. 필요하면 자기 행만 복사한다.
void detach(Column& col, bool need_validity) {
    const bool shared = col.values.use_count() > 1 || (col.validity && col.validity.use_count() > 1);
    const bool add_bits = need_validity && !col.validity;        // 결측을 쓰는데 비트맵이 없다
    if (!shared && !(add_bits && col.offset != 0)) {
        if (add_bits) add_validity(col);                         // 그 자리에서: 모든 비트 1인 비트맵만 추가
        return;
    }
    const std::int64_t size = itemsize(col.dtype);
    auto values = Buffer::allocate(col.length * size, /*zeroed=*/false);
    std::memcpy(values->data(), col.values->data() + col.offset * size, col.length * size);  // 자기 행 범위만
    auto validity = rebased_validity(col);                       // 비트도 0부터 다시
    col.values = values;
    col.validity = validity;
    col.offset = 0;
    if (add_bits) add_validity(col);
}
```

- 참조 수가 1이면 복사 없이 그 자리에서 써요.
- 다른 주인(다른 Series, DataFrame, 슬라이스, numpy 뷰의 capsule, `sd.ndarray` 뷰)이 있으면 자기 행 범위만 새 Buffer로 복사하고 `offset`을 0으로 돌려요. 1M 행 컬럼의 5행짜리 슬라이스에 쓰면 5행만 복사돼요.
- 결측 값을 쓰는데 비트맵이 없으면 모든 비트가 1인 비트맵을 붙여요. `add_validity`는 `offset == 0`을 가정하므로, 공유되지 않았더라도 `offset`이 0이 아니면(슬라이스라면) 복사 경로로 가서 0부터 다시 맞춰요.

그다음 값을 쓰고 비트를 고친 뒤, 결측 수를 다시 세고 0이면 비트맵을 버려요(약속 1). 결측을 쓴 행의 값 자리는 `memset`으로 0으로 지워요(약속 2).

`s = df["a"]; s.iloc[0] = 99`가 지나는 단계예요.

| 시점 | `df._cols["a"]` | `s._col` | values Buffer의 `use_count()` | 결과 |
|---|---|---|:---:|---|
| `s = df["a"]` 뒤 | Column 객체 A | 같은 객체 A | 1 | 공유 |
| 1단계 `share()` 뒤 | A | 새 객체 B (같은 Buffer) | 2 | 아직 공유 |
| 2단계 `detach` | A → 옛 Buffer | B → **새 Buffer** (복사) | 1, 1 | 복사 후 B에만 씀 |

```python
>>> t.iloc[0] = 9.0
>>> np.shares_memory(s.to_numpy(), t.to_numpy())
False
>>> s.tolist(), t.tolist()
([1.0, 2.0, 3.0], [9.0, 2.0, 3.0])
```

Buffer의 다른 주인이 없을 때 정말로 그 자리에서 쓰는지도 확인할 수 있어요. `to_numpy()`가 Buffer를 가리키는 뷰라서 데이터 주소를 비교하면 돼요(임시 배열은 그 줄이 끝나면 사라져서 참조 수를 남기지 않아요).

```python
>>> p = s.to_numpy().__array_interface__["data"][0]
>>> s.iloc[0] = 5.0
>>> s.to_numpy().__array_interface__["data"][0] == p
True
```

10행 Series의 `s.iloc[3] = 1`은 0.94 µs였어요(1스레드, Apple M4 Pro).

### 문자열 컬럼은 언제나 새 Buffer

문자열 행에 쓰면 그 행의 길이가 바뀔 수 있어요. `"ab"`를 `"abcdef"`로 바꾸면 뒤 행의 바이트가 모두 밀려야 해요. 그래서 문자열의 `set_rows`는 참조 수와 상관없이 언제나 새 offsets, 바이트, 비트맵을 만들어요. 행마다 "새 값의 번호, 없으면 -1"을 적은 배열을 만들고(같은 행에 여러 번 쓰면 마지막 것이 이겨요), 그것으로 길이를 세어 offsets를 채운 뒤 바이트를 복사해요.

### 대입 값의 dtype

기존 컬럼의 행에 쓸 때는 값을 먼저 컬럼의 dtype으로 맞춰요(`_series.assignment_values`). 규칙은 암묵적 변환이에요. dtype만 보고 위로만(`bool → int64 → float64`) 바꾸고, 아래로는 값과 상관없이 TypeError예요. int 컬럼에 `2.0`을 넣는 것도 에러예요. 그래서 `set_rows`는 언제나 컬럼과 같은 dtype의 값만 받아요. 행 대입으로 컬럼 dtype이 바뀌는 일은 없어요.

`df.loc[rows, "c"] = value`도 같은 길이에요. 그 컬럼의 임시 Series를 만들어 `_assign`을 부르고, 결과 Column을 사전에 다시 넣어요. 컬럼을 통째로 바꾸는 `df["c"] = ...`은 사전 항목을 새 Column으로 바꾸는 것이라 Copy-on-Write가 필요 없어요.

### 참조 수를 믿어도 되는 이유

cppreference의 설명대로, 여러 스레드가 있을 때 `use_count()`의 값은 "대략적"으로 봐야 해요 [4]. 읽은 직후 다른 스레드가 새 주인을 만들 수 있고, `use_count() == 1`이어도 옛 주인의 접근이 아직 끝나지 않았을 수 있다는 거예요. 그래도 stardust에서는 1이라는 판단이 안전해요. 이유는 둘이에요.

- 새 주인은 기존 주인을 복사해야만 생겨요. 참조 수가 1이면 주인은 지금 쓰려는 Column 객체 하나뿐이에요. 그 객체를 쥔 Python 객체(`s`)에 다른 Python 스레드가 닿으려면 GIL이 필요한데, `set_rows`는 처음부터 끝까지 GIL을 쥐고 돌아요. 그동안 아무도 그 Column을 복사할 수 없어요.
- 옛 주인은 이미 사라졌어요. GIL 없이 도는 커널은 Python 인자로 받은 Column 객체를 통해 Buffer를 읽어요. 그 커널이 도는 동안에는 그 Column 객체가 살아 있으므로 참조 수가 2 이상이에요. 참조 수가 1로 떨어졌다는 것은 그 객체가 이미 해제되었다는 뜻이고, Python 객체의 해제는 커널이 돌아온 뒤 GIL을 쥔 채 일어나요.

### 스냅샷 규칙

커널은 일이 크면 GIL을 놓고 돌아요([병렬화와 결정성](/internals/frame/parallel/)). 그래서 한 Python 스레드가 `s + 1`을 계산하는 동안 다른 스레드가 `s.iloc[k] = ...`을 할 수 있어요. 이때도 연산은 호출 시점의 값을 봐요. 결과에 대입 전 값과 대입 후 값이 섞이지 않아요.

남은 틈은 하나예요. `set_rows`가 Buffer를 그 자리에서 고치는 동안(참조 수가 1이었던 경우) 다른 스레드의 연산이 시작되어 그 Buffer를 읽는 경우예요. 그래서 `set_rows`는 크기와 상관없이 GIL을 쥔 채 돌아요. 연산을 시작하려면 GIL이 있어야 하므로, 모든 연산은 그 컬럼을 대입 전이나 대입 후로만 봐요.

`groupby`에도 같은 문제가 있어요. 키 코드는 처음 집계할 때 계산해서 캐시하는데, 그 사이 `df["k"] = ...`로 키 컬럼이 바뀌면 옛 키 코드와 새 값 컬럼이 섞여요. 그래서 `df.groupby(...)`는 부른 순간의 컬럼 사전을 복사해 둬요(`dict(df._cols)`). Column 객체의 참조만 복사하므로 데이터는 복사되지 않고, 행 대입은 Copy-on-Write로 복사되므로 groupby 쪽에 보이지 않아요.

테스트는 한 스레드가 `s.iloc[k] = 1`을 k = 0, 1, 2, …로 쓰는 동안 다른 스레드가 `s + 0`을 반복해요. 모든 결과가 "앞의 k개만 1인" 꼴이어야 해요. 중간에 섞인 결과가 하나라도 나오면 실패예요.

### pandas 3과 비교

pandas 3도 Copy-on-Write가 유일한 모드예요 [5]. 구현은 달라요. pandas는 블록마다 `BlockValuesRefs` 객체를 두고, 같은 numpy 배열을 공유하는 블록을 약한 참조(weakref) 목록으로 추적해요. 쓰기 직전에 `has_reference()`로 그 목록에 살아 있는 다른 블록이 있는지 보고, 있으면 복사해요 [2]. stardust는 별도의 추적 객체 없이 `shared_ptr`가 이미 가진 참조 수를 읽어요. numpy 뷰처럼 바깥에서 Buffer를 쥔 것도 `shared_ptr` 복사본을 쥐고 있으므로 같은 수에 그대로 잡혀요.

## numpy와 주고받기

### 나갈 때: 읽기 전용으로 공유

결측이 없는 bool·int64·float64 컬럼의 `to_numpy()`는 Column의 values Buffer를 그대로 가리키는 읽기 전용 numpy 배열이에요(`convert.cpp`의 `to_numpy_view`). 복사가 없어서 1M 행이어도 448 ns예요(1스레드, Apple M4 Pro).

```cpp
// csrc/frame/convert.cpp (발췌)
// numpy 배열이 Buffer를 쓰는 동안 살려 두는 capsule
nb::capsule buffer_owner(const std::shared_ptr<Buffer>& buf) {
    auto* holder = new std::shared_ptr<Buffer>(buf);      // 참조 수 +1
    return nb::capsule(holder, [](void* p) noexcept { delete static_cast<std::shared_ptr<Buffer>*>(p); });
}

nb::object to_numpy_view(const Column& col) {
    const std::byte* ptr = col.values->data() + col.offset * itemsize(col.dtype);   // 슬라이스면 그만큼 민 자리
    return nb::ndarray<nb::numpy, nb::ro>(ptr, {std::size_t(col.length)}, buffer_owner(col.values), {}, dtype)
        .cast();
}
```

- 배열의 owner는 `shared_ptr<Buffer>` 복사본을 담은 capsule이에요. capsule은 C 포인터와 소멸 함수를 감싼 Python 객체예요. numpy 배열이 살아 있는 동안 capsule이 살아 있고, 그동안 Buffer의 참조 수가 하나 늘어 있어요. Series가 먼저 사라져도 배열은 유효해요.
- 그래서 frame 쪽 쓰기는 먼저 복사해요. 뷰가 살아 있으면 참조 수가 2 이상이라 `detach`가 복사하거든요. Copy-on-Write에 뷰를 위한 코드가 따로 없어요. 뷰의 값은 바뀌지 않아요.
- 읽기 전용이어야 하는 이유는 반대 방향의 쓰기 때문이에요. 배열에 쓸 수 있으면 사용자가 배열을 통해 Series를 고칠 수 있어요. 그 쓰기는 frame의 Copy-on-Write를 거치지 않으므로, 같은 Buffer를 공유하는 다른 Series까지 몰래 바뀌어요. pandas 3도 같은 이유로 읽기 전용 배열을 줘요 [5]. Polars 2.1.0의 `to_numpy()`도 읽기 전용이에요.

```python
>>> s = sd.frame.Series([1.0, 2.0, 3.0])
>>> a = s.to_numpy()
>>> a[0] = 9.0
Traceback (most recent call last):
    ...
ValueError: assignment destination is read-only
>>> s.iloc[1] = 7.0
>>> a
array([1., 2., 3.])
>>> s.tolist()
[1.0, 7.0, 3.0]
```

결측 자리는 0으로 채워져 있으므로, 결측이 있는 컬럼도 기술적으로는 같은 뷰를 줄 수 있어요. 하지만 그러면 결측이 0이라는 값으로 둔갑해요. 그래서 결측이 있으면 `na_value=`를 꼭 받고, 뷰를 복사한 뒤 결측 자리에 그 값을 써요(`arr[~validity_mask] = na_value`).

```python
>>> sd.frame.Series([1, None, 3]).to_numpy()
Traceback (most recent call last):
    ...
ValueError: to_numpy(): cannot convert an int64 column with NA to numpy; pass na_value= to fill the NA rows
>>> sd.frame.Series([1, None, 3]).to_numpy(na_value=-1)
array([ 1, -1,  3], dtype=int64)
```

`copy=`는 배열 영역의 `asarray`와 같은 세 값이에요. `None`은 꼭 필요할 때만 복사(dtype 변환이나 결측 채우기), `True`는 언제나 복사, `False`는 복사가 필요하면 ValueError예요. `dtype=`으로 바꾸면 `astype`이 이미 새 Column을 만들었으므로 한 번 더 복사하지 않아요. 그 Column의 Buffer는 이 호출 말고는 주인이 없어서, 그 위에 쓸 수 있는 배열을 만들어 내줘요(`_column.to_numpy`의 `fresh` 표시, 아래 `to_array`와 같은 규칙). 결측을 채운 배열도 복사본이라 쓸 수 있어요. 읽기 전용은 컬럼의 Buffer를 그대로 보여 주는 뷰뿐이에요.

문자열 컬럼은 numpy에 맞는 고정 크기 표현이 없어서 object 배열을 만들고 원소마다 str을 넣어요. numpy가 str을 다른 dtype으로 해석하지 않도록 `np.empty(n, dtype=object)`에 채워 넣어요. `DataFrame.to_numpy()`는 컬럼마다 배열을 만들어 `np.stack(..., axis=1)`으로 쌓은 새 C 순서 2차원 배열이에요. 컬럼이 따로 떨어진 Buffer라서 공유할 2차원 메모리가 없거든요.

### numpy에서 들어올 때: 언제나 복사

`Series(np_array)`는 numpy 배열을 언제나 복사해요(`convert.cpp`의 `from_numpy`).

- numpy 배열은 밖에서 언제든 바뀔 수 있어요. 메모리를 공유하면, 사용자가 원래 numpy 배열(또는 그것의 다른 쓰기 가능한 뷰)에 쓸 때 Series가 몰래 바뀌어요. 그 쓰기는 frame을 거치지 않으므로 Copy-on-Write가 "아무도 쓰지 않는다"고 판단할 근거가 없어요. `Buffer::adopt`로 numpy 메모리를 감싸면 Buffer의 참조 수는 frame 안의 주인만 세요. 바깥의 numpy 쪽 주인은 보이지 않아요.
- 복사하는 김에 넓혀요. int8·int16·int32와 uint8·uint16·uint32는 int64로, float16·float32는 float64로 바꾸며 복사해요. stride가 있는 배열(`a[::2]`)도 stride대로 읽어요. 같은 템플릿 함수 `widen<To, From>`이 원소 타입 조합마다 따로 컴파일돼요.
- uint64는 값을 보지 않고 TypeError예요. 2⁶³ 이상의 값이 있을 수 있는 dtype이라서, 실제 값이 작아도 받지 않아요. 배열 영역의 `sd.asarray`와 같은 규칙이에요. big-endian 배열은 Python 층이 native 순서로 바꾼 뒤 넘겨요. 문자열과 object 배열은 Python 층이 `tolist()`로 바꿔 list 경로로 보내요.

```python
>>> n = np.arange(3)
>>> t = sd.frame.Series(n)
>>> n[0] = 100
>>> t.tolist()
[0, 1, 2]
```

비용은 1M int64에 109 µs였고(1스레드, Apple M4 Pro), 대부분 새 메모리의 페이지 폴트예요. 16KB 페이지마다 처음 쓸 때 운영체제가 페이지를 채워 넣어요. Polars 2.1.0은 numpy 배열의 메모리를 공유해요(`np.shares_memory`가 True). 공유하면 이 비용이 없지만, stardust의 Copy-on-Write는 위 이유로 공유를 받아들일 수 없어요.

### Python list에서

`Series([...])`는 C++에서 list를 두 번 훑어요(`from_list`).

1. **분류.** 원소마다 종류(NA, bool, int, float, str)를 정하고, 숫자는 이때 바로 읽어 임시 배열에 둬요. 문자열은 UTF-8 길이만 더해요.
2. **채우기.** 본 종류의 조합으로 dtype을 정하고(`inferred_dtype`, 승격은 `promote_columns`), 버퍼를 한 번에 할당해 채워요.

세부 규칙이 몇 가지 있어요.

- bool을 int보다 먼저 확인해요. Python의 `True`는 `int`의 하위 타입이라, int 검사를 먼저 하면 bool이 int로 분류돼요.
- numpy 스칼라는 따로 읽어요. `numpy.float64`는 Python `float`의 하위 타입이라 float로 잡히지만, `numpy.int32`나 `numpy.bool`은 `int`나 `bool`의 하위 타입이 아니에요. 타입 이름이 `numpy.`로 시작하면 `numpy.bool`은 bool로, `__index__`가 있으면 정수로, `__float__`가 있으면 실수로 분류해요.
- int64 범위 밖의 int는 표시만 해 둬요. 1단계에서 double로 읽어 두고, 2단계에서 float64 컬럼이 되면 그 double을 쓰고 int64 컬럼이 되면 OverflowError를 내요. 배열 영역과 같은 규칙이에요. double로도 읽을 수 없을 만큼 크면(`10**400`) `PyLong_AsDouble`이 Python의 OverflowError를 걸어 두는데, `int_value`가 그것을 지우고 C++ 예외(`std::overflow_error`)로 다시 던져요. 바인딩이 C++ 예외에만 함수 이름을 붙이므로, 이렇게 해야 메시지가 다른 에러처럼 `Series(): Python int too large to convert to float64`로 시작해요.
- `dtype=`은 명시적 변환이에요. 추론한 컬럼에 `astype`을 한 번 더 해요. 예외는 int만 있는 list를 float64로 요청할 때인데, 처음부터 float64로 채워요. 그래야 범위 밖의 int도 float로 받을 수 있어요.
- 결측 자리는 2단계에서 0으로 써요. 비트맵을 만든 뒤 그 행의 비트만 지워요.

dtype을 정하는 `inferred_dtype`은 `[[gnu::noinline]]`, 문자열과 숫자가 섞였을 때의 에러 함수는 `[[gnu::cold, gnu::noinline]]`이에요. 드물게 쓰는 코드를 행 루프 밖으로 빼서, 루프가 레지스터를 넉넉히 쓰게 하려는 거예요. 1M 개짜리 `list[int]`에서 Series를 만드는 데 4.77 ms였어요(1스레드, Apple M4 Pro).

### 꺼내기: `tolist`와 pickle

`tolist()`는 행마다 Python 객체를 만들어요(`PyBool_FromLong`, `PyLong_FromLongLong`, `PyFloat_FromDouble`, `PyUnicode_DecodeUTF8`). 결측은 `NA` 싱글턴의 참조예요.

pickle은 Column의 `__getstate__`가 자기 행만 바이트로 내요. `(dtype, length, null_count, values, validity, offsets)` 튜플이고, 비트맵은 `rebased_validity`로 0부터 다시 맞추고, 문자열 offsets는 첫 값을 빼서 0부터 시작하게 바꿔요. 그래서 1M 행 컬럼의 5행 슬라이스를 pickle하면 5행만 저장되고, 되살린 값이 비트까지 같아요.

## 배열 영역과의 경계

데이터프레임이 배열 영역(`sd.ndarray`)을 만나는 곳은 `frame/interop.{hpp,cpp}` 하나예요. `array/`의 헤더(`ndarray.hpp`, `ops/reduction.hpp`)를 include하는 frame 파일은 이것뿐이에요. 다른 frame 코드는 배열 영역을 모르므로, 배열 쪽 구조가 바뀌어도 고칠 곳이 이 파일 하나예요. 하는 일은 넷이에요.

| 함수 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `to_array_view(col, writeable)` | 결측 없는 bool·int64·float64 컬럼의 값 위에 1차원 `NDArray`를 만들어요. 복사 없음 | `Series.to_array` |
| `from_array(arr)` | 1차원 배열을 새 Column으로 복사해요. complex128은 TypeError | `Series(arr)`, `DataFrame(arr2d)`(열마다) |
| `columns_to_array(cols, n)` | 같은 dtype, 결측 없는 k개 컬럼으로 (n, k) F 순서 배열을 만들어요 | `DataFrame.to_array` |
| `array_sum_float64(col)` | int64·bool 컬럼 위의 읽기 전용 뷰로 배열의 `sd.sum(x, dtype=sd.float64)`을 불러요 | int64 `mean` |

### 나갈 때: 같은 Buffer를 가리키는 뷰

```cpp
// csrc/frame/interop.cpp (발췌)
NDArray view_of(const Column& col, bool writeable) {
    NDArray a;
    a.buffer = col.values;                                          // 같은 shared_ptr<Buffer>: 참조 수 +1
    a.data = col.values->data() + col.offset * itemsize(col.dtype); // 슬라이스면 그만큼 민 자리
    a.dtype = col.dtype;
    a.ndim = 1;
    a.shape[0] = col.length;
    a.strides[0] = itemsize(col.dtype);
    a.update_flags();
    a.writeable = writeable;
    return a;
}
```

배열과 데이터프레임이 같은 `Buffer` 타입을 쓰므로, 뷰는 Column의 `shared_ptr<Buffer>`를 그대로 복사해 써요. numpy 뷰처럼 capsule이 필요 없어요. 뷰가 살아 있는 동안 참조 수가 늘어 있으므로, frame 쪽 대입은 앞의 규칙 그대로 먼저 복사해요. 경계를 넘는 Copy-on-Write가 따로 코드 없이 성립해요.

```python
>>> s = sd.frame.Series([1, 2, 3])
>>> x = s.to_array()
>>> s.iloc[0] = 100
>>> x
array([1, 2, 3], dtype=int64)
>>> x[0] = 5
Traceback (most recent call last):
    ...
ValueError: assignment destination is read-only
```

뷰는 기본적으로 읽기 전용이에요. 이유는 numpy 뷰와 같아요. 예외는 이 호출이 방금 만든 Column이에요. `to_array(dtype=sd.float64)`처럼 dtype을 바꾸거나 `na_value=`로 결측을 채우면 새 Column이 생기는데, 그 Buffer는 다른 주인이 없으므로 쓸 수 있는 배열로 내줘요(`_column.array_column`이 돌려주는 `fresh` 표시). `copy=True`면 배열 쪽 `asarray(copy=True)`로 복사해요.

```python
>>> y = s.to_array(dtype=sd.float64)
>>> y[0] = -1.0
>>> s.tolist()
[100, 2, 3]
```

문자열 컬럼은 배열이 될 수 없어요. 배열 영역에 string dtype이 없기 때문이에요.

### 들어올 때: 언제나 복사

`Series(sd_array)`도 언제나 복사해요. 이유는 numpy와 같아요. 배열은 다른 쓰기 가능한 뷰를 통해 바뀔 수 있고, frame의 Copy-on-Write는 그 쓰기를 볼 수 없어요. 연속인 배열은 `memcpy` 한 번, stride가 있으면 원소마다 복사해요.

```python
>>> a = sd.arange(4)
>>> t = sd.frame.Series(a)
>>> a[0] = 9
>>> t.tolist()
[0, 1, 2, 3]
```

### DataFrame을 2차원 배열로: F 순서

`DataFrame.to_array()`는 (행 수, 컬럼 수) 모양의 **F 순서**(열 우선) 배열을 만들어요. F 순서에서는 컬럼 하나가 메모리에서 연속된 한 덩어리라서, 컬럼마다 `memcpy` 한 번으로 채워져요. strides는 `(itemsize, n·itemsize)`예요.

```python
>>> df = sd.frame.DataFrame({"k": [1, 2], "v": [0.5, 1.5]})
>>> df.to_array().strides
(8, 16)
```

C 순서였다면 컬럼의 원소를 `k`바이트 간격으로 흩어 써야 해요. F 순서는 `sd.linalg`가 가장 빨리 읽는 배치이기도 해요. 선형대수 함수는 LAPACK이 요구하는 열 우선 배치로 입력을 옮기는데(패킹), F 순서 입력은 열마다 복사와 유한성 검사를 한 번에 하는 경로로 가요([패킹과 결과 레이아웃](/internals/linalg/packing/)). 그래서 `sd.linalg.lstsq(df.to_array(), y)` 같은 코드가 복사 한 번으로 이어져요.

### int64 평균이 배열의 합을 부르는 이유

int64 컬럼의 `mean()`은 frame 안에서 계산하지 않고, 컬럼 위의 읽기 전용 뷰로 배열 영역의 `sd.sum(view, dtype=sd.float64)`을 부른 뒤 결측이 아닌 행 수로 나눠요. 결측 행은 0이라 그대로 더해도 돼요.

`Series.mean()`과 `sd.mean(s.to_array())`가 마지막 비트까지 같아야 하기 때문이에요. 배열의 int → float64 합은 4,096원소 버퍼 단위로 형변환하며 접는 고유한 순서로 더해요([리덕션](/internals/array/reductions/)). 같은 계산을 frame에 다시 쓰면 그 순서를 똑같이 흉내 내야 하고, 배열 쪽이 바뀔 때마다 따라 바꿔야 해요. 배열의 함수를 그대로 부르면 순서가 저절로 같아요.

대가는 둘이에요.

- 이 호출에는 GIL이 필요해요. Python 객체(읽기 전용 뷰)를 하나 만들고 배열의 공개 함수를 거치기 때문이에요. 합 자체는 배열 영역의 규칙대로 원소가 배열의 기준값(float64 덧셈 32,768개 분량) 이상이면 스레드 수와 상관없이 GIL을 놓고 돌아요. 뷰를 만들고 결과를 받는 앞뒤만 GIL을 쥐어요.
- frame의 float 합과 순서가 달라요. frame의 float 합은 pairwise 트리이고, int64 평균은 배열의 버퍼 단위 순서예요. 그래서 int64 그룹 평균(그룹의 행을 float64로 바꿔 frame의 pairwise 합으로 더해요)이 Series의 `mean()`과 비트까지 같은 것은 그룹이 4,096행 이하일 때예요.
