## 한눈에 보기

이 페이지는 데이터프레임 영역(`sd.frame`)의 성능을 pandas 3.1.1, Polars 2.1.0과 나란히 놓고, 결과가 맞는지 어떻게 확인하는지 설명해요. 비교 측정은 15개 케이스를 1천, 10만, 100만(1M) 행에서, 그리고 호출 비용을 보는 10행 케이스 4개를 재요(`bench/frame/final_compare.py`).

{/* 아래 표의 ⟦FBENCH …⟧는 측정 뒤에 실제 값으로 바뀌는 자리예요. 기하평균은 그 크기의 모든 케이스의 시간 비율로 구해요. */}

| 행 수 | pandas ÷ sd 1스레드 | Polars 1스레드 ÷ sd 1스레드 | pandas ÷ sd 10스레드 | Polars 14스레드 ÷ sd 10스레드 |
|---:|---:|---:|---:|---:|

| 1,000 | ⟦FBENCH 기하평균 1k pandas/sd@1⟧ | ⟦FBENCH 기하평균 1k polars@1/sd@1⟧ | ⟦FBENCH 기하평균 1k pandas/sd@10⟧ | ⟦FBENCH 기하평균 1k polars@14/sd@10⟧ |
| 100,000 | ⟦FBENCH 기하평균 100k pandas/sd@1⟧ | ⟦FBENCH 기하평균 100k polars@1/sd@1⟧ | ⟦FBENCH 기하평균 100k pandas/sd@10⟧ | ⟦FBENCH 기하평균 100k polars@14/sd@10⟧ |
| 1,000,000 | ⟦FBENCH 기하평균 1M pandas/sd@1⟧ | ⟦FBENCH 기하평균 1M polars@1/sd@1⟧ | ⟦FBENCH 기하평균 1M pandas/sd@10⟧ | ⟦FBENCH 기하평균 1M polars@14/sd@10⟧ |

시간 비율의 기하평균이에요. 1보다 크면 stardust가 빨라요. 크기마다 성능을 정하는 것이 달라요.

1. **10행과 1천 행은 호출 비용이 정해요.** 데이터를 만지는 시간보다 Python에서 C++로 들어가고 결과 객체를 만드는 고정 비용이 커요. pandas는 연산 하나에 수 µs를 쓰고, stardust는 수백 ns를 써요(아래 "작은 데이터").
2. **10만 행은 병렬화 기준값의 그늘이에요.** stardust는 2¹⁷(131,072)행보다 작은 일을 나누지 않으므로, 10만 행의 원소별 연산·필터·합·해시가 1스레드로 돌아요([병렬화와 결정성](/internals/frame/parallel/)).
3. **1M 행은 커널과 스레드가 정해요.** 해시 테이블, 기수 정렬, CSV 토크나이저의 설계와 10개 P코어가 시간을 정해요.

이 페이지의 나머지는 이 순서예요: 측정 방법 → 같은 입력 반복의 함정 → 작은 데이터 → 비교 표 → 느린 줄과 원인 → 결과 비트를 지키느라 하지 않는 최적화 → 테스트의 정답.

## 측정 방법

### 기계와 버전

| 항목 | 값 |
|---|---|
| 기계 | Apple M4 Pro (arm64 macOS, P코어 10 + E코어 4) |
| 캐시 | 캐시 라인 128B, P코어 L1d 128KB, L2 16MB(코어 5개가 공유, 클러스터 2개) |
| Python | 3.15.0 |
| numpy | 2.5.4 |
| pandas | 3.1.1. numexpr, bottleneck, pyarrow가 없는 환경이라 모든 연산이 한 스레드예요 |
| Polars | 2.1.0. 1스레드(`POLARS_MAX_THREADS=1`)와 기본값 14스레드 |
| stardust | 1스레드(`sd.set_num_threads(1)`)와 기본값 10스레드(P코어 수) |

열 이름은 `sd@1`, `sd@10`, `pandas`, `polars@1`, `polars@14`예요. 기본 스레드 수가 서로 달라요. Polars는 E코어까지 14개를 쓰고, stardust는 E코어를 섞으면 메모리에 묶인 연산이 느려져서 P코어 10개만 써요. 각자의 기본값을 그대로 비교하고, 1스레드 열로 코어 수를 뺀 비교도 함께 봐요.

### 입력

입력은 `data(n, seed)`가 numpy 난수로 만들어요(`np.random.default_rng(seed)`). 세 라이브러리에 같은 numpy 배열을 넣어요.

| 이름 | 값 | 쓰는 케이스 |
|---|---|---|
| `f`, `g` | 표준정규분포 float64, n개 | 원소별, 합, 필터, groupby의 값 |
| `low` | `[0, 1000)`의 int64, n개 | 키 1,000종 |
| `high` | `[0, n)`의 int64, n개 | 키가 많은 경우. 1M 행이면 약 63만 종이에요 |
| `strs` | `"key{v}"`, v는 `[0, n/10)`의 정수 | 문자열 키. 1M 행이면 약 10만 종이에요 |
| `L` | 열 `k`(`[0, m + m//9)`의 정수, n개)와 `a`(= `f`), m = n/10 | merge의 왼쪽 |
| `R` | 열 `k`(`0..m-1`의 무작위 순열, m개)와 `b`(표준정규분포) | merge의 오른쪽. 키가 모두 달라요 |
| `f{n}.csv` | 열 `x` 하나(= `f`), pandas `to_csv`로 씀 | `read_csv floats` |
| `m{n}.csv` | 열 `id`(0..n-1), `x`(= `f`), `name`(= `strs`), `flag`(`f > 0`) | `read_csv mixed` |

merge의 왼쪽 키는 오른쪽 키 범위보다 약 11% 넓게 뽑으므로, 왼쪽 행의 약 90%가 오른쪽 행 정확히 하나와 맞고 나머지는 맞는 행이 없어요(inner merge에서 빠져요).

### 케이스

각 라이브러리에서 같은 일을 하는 식이에요. 결과의 모양을 맞추려고 세 군데를 조정해요. pandas 정렬은 `kind="stable"`(stardust의 정렬은 언제나 안정 정렬이에요), Polars groupby는 결과를 키로 정렬(stardust와 pandas는 그룹을 키 순서로 돌려줘요), Polars join은 `maintain_order="left"`(stardust와 pandas는 왼쪽 행 순서를 지켜요)예요.

| 케이스 | stardust (`sd.frame`) | pandas | Polars |
|---|---|---|---|
| `float + float` | `f + g` | `f + g` | `f + g` |
| `float sum` | `f.sum()` | `f.sum()` | `f.sum()` |
| `mask filter` | `f[f > 0]` | `f[f > 0]` | `f.filter(f > 0)` |
| `nunique int, 1k keys` | `low.nunique()` | `low.nunique()` | `low.n_unique()` |
| `nunique int, n keys` | `high.nunique()` | `high.nunique()` | `high.n_unique()` |
| `nunique string` | `str.nunique()` | `str.nunique()` | `str.n_unique()` |
| `groupby int 1k sum` | `df.groupby("k")["f"].sum()` | 같음 | `df.group_by("k").agg(pl.col("f").sum()).sort("k")` |
| `groupby int, n keys, sum` | `df.groupby("kh")["f"].sum()` | 같음 | `df.group_by("kh").agg(pl.col("f").sum()).sort("kh")` |
| `groupby string sum` | `df.groupby("ks")["f"].sum()` | 같음 | `df.group_by("ks").agg(pl.col("f").sum()).sort("ks")` |
| `groupby int + string sum` | `df.groupby(["k", "ks"])["f"].sum()` | 같음 | `df.group_by(["k", "ks"]).agg(pl.col("f").sum()).sort(["k", "ks"])` |
| `merge n x n/10 inner` | `sd.frame.merge(L, R, on="k")` | `L.merge(R, on="k")` | `L.join(R, on="k", maintain_order="left")` |
| `sort int64` | `high.sort_values()` | `high.sort_values(kind="stable")` | `high.sort()` |
| `sort string` | `str.sort_values()` | `str.sort_values(kind="stable")` | `str.sort()` |
| `read_csv floats` | `sd.frame.read_csv(f{n}.csv)` | `pd.read_csv(…)` | `pl.read_csv(…)` |
| `read_csv mixed` | `sd.frame.read_csv(m{n}.csv)` | `pd.read_csv(…)` | `pl.read_csv(…)` |

여기서 `f`, `g`, `low`, `high`, `str`은 각 라이브러리의 Series이고, `df`는 열 `k`(= `low`), `kh`(= `high`), `ks`(= `strs`), `f`를 가진 데이터프레임이에요.

호출 비용을 보는 10행 케이스는 표준정규분포 10개 `a`로 만든 `s = Series(a)`, `df = DataFrame({"a": a, "b": a})`에서 `s + s`, `s.sum()`, `df["a"]`, `df[df["a"] > 0]`(Polars는 `df.filter(df["a"] > 0)`)이에요.

- **최솟값을 써요.** 평균과 중앙값은 다른 프로세스의 일, 운영체제의 인터럽트, 온도에 따라 흔들려요. 최솟값은 가장 덜 방해받은 실행이라 기계의 상태 변화에 가장 덜 흔들려요.
- **묶어서 재요.** 10행 연산은 수백 ns라 타이머 해상도와 루프 비용이 무시할 수 없어요. 묶음 하나가 수십 ms가 되게 해서 그것을 지워요.
- **번갈아 재요.** 세 라이브러리를 각각 한꺼번에 재면, 그사이 기계 상태가 바뀐 몫이 한 열에만 들어가요. 같은 스크립트로 열을 번갈아 두 바퀴 돌리면 그 변화가 모든 열에 고르게 들어가요. 다른 벤치마크가 함께 돌면 모든 값이 1.5~2배로 나오므로, 시작 전에 기계가 조용한지 확인해요.
- **Polars는 열마다 프로세스를 따로 띄워요.** Polars의 스레드 수는 `POLARS_MAX_THREADS`로 프로세스가 시작할 때 한 번 정해지고 바꿀 수 없어요. stardust도 같은 방식으로 열마다 프로세스를 띄워요(`--threads 1`).
- **결과를 버리지 않아요.** 각 호출은 결과 객체를 실제로 만들고 돌려줘요. 1M 행 원소별 연산은 매번 새 8MB 버퍼를 받아 처음 쓰면서 페이지 폴트를 내는데, 실제 사용에서도 그렇기 때문에 그대로 둬요.

### 새 입력 모드

`--fresh`를 주면 크기마다 시드가 다른 입력을 여러 벌 만들고(`fresh(n) = min(64, max(4, 4,000,000 // n))`: 1천 행 64벌, 10만 행 40벌, 1M 행 4벌), 호출할 때마다 다음 벌을 써요(`per_call_ns_cycle`). 비교 표의 1천·10만·1M 행은 이 모드예요. 10행 케이스는 같은 입력을 되풀이해요. 10행은 분기가 몇 개뿐이라 외울 것이 거의 없고, 보려는 것이 호출의 고정 비용이기 때문이에요. 왜 이 모드가 필요한지가 다음 절이에요.

## 같은 입력 반복의 함정

### 분기 예측기는 입력을 외울 수 있어요

CPU는 조건 분기(`if`)의 결과가 나오기 전에 어느 쪽으로 갈지 **예측**하고 그쪽 명령을 미리 실행해요. 예측이 맞으면 분기는 거의 공짜이고, 틀리면 미리 실행한 일을 버리고 다시 시작해요. 현대 고성능 코어에서 한 번 틀리는 비용은 십수 사이클이에요. 해시 테이블처럼 "이 칸이 비었나", "키가 같나"를 행마다 묻는 코드는 데이터가 무작위면 예측이 자주 틀려요.

현대의 예측기는 분기 하나의 과거만 보지 않고, **최근 분기 결과들의 이력**을 함께 보고 예측해요. 대표적인 설계인 TAGE는 길이가 기하급수로 늘어나는 여러 이력(수 개 ~ 수백 개 분기)마다 표를 두고, 가장 긴 이력에서 맞는 항목을 찾아 예측해요 [1]. 애플은 M4의 예측기 구조를 공개하지 않지만, 아래 측정이 보여 주는 것은 이런 긴 이력 예측기의 성질이에요.

같은 1천 행 입력으로 함수를 수천 번 부르면, 매 호출의 분기 결과 순서가 **완전히 같아요.** 긴 이력을 보는 예측기는 이 순서를 통째로 외우고, 두 번째 호출부터는 "무작위"였던 분기를 거의 다 맞혀요. 측정은 실제보다 빠른 시간을 보고하고, 분기가 많은 코드일수록 더 많이 이득을 봐요. 실제 사용에서는 같은 데이터를 수천 번 연달아 `nunique`하지 않으므로, 이 시간은 누구도 겪지 않는 시간이에요.

### 측정: linear probing과 Swiss table

키 1,000종짜리 해시 테이블에 행을 넣는 루프만 따로 잰 값이에요(행당 ns, 1스레드, Apple M4 Pro). 두 테이블 설계를 같은 입력 반복과 새 입력으로 쟀어요.

| 행 수 | linear probing, 같은 입력 | linear probing, 새 입력 | Swiss table, 같은 입력 | Swiss table, 새 입력 |
|---:|---:|---:|---:|---:|
| 1,000 | 3.65 | **11.8** | 6.49 | 8.50 |
| 10,000 | 1.25 | 5.73 | 2.45 | 3.67 |
| 1,000,000 | 4.11 | 4.35 | 1.84 | 1.86 |

- **같은 입력이면 linear probing이 이겨요.** 1천 행에서 3.65 대 6.49ns예요. linear probing은 빈 칸이나 같은 키를 만날 때까지 칸을 하나씩 보며 분기하는데, 그 분기를 예측기가 외웠어요.
- **새 입력이면 1천 행부터 Swiss table이 이겨요.** linear probing은 11.8ns로 같은 입력의 3.2배가 되고, Swiss table은 8.50ns예요. Swiss table은 칸마다 1바이트 제어 바이트(해시의 일부)를 두고 16칸의 제어 바이트를 SIMD 비교 한 번으로 검사해서, 행마다 예측해야 할 분기가 적어요 [3] ([해시 테이블과 factorize](/internals/frame/hashing/)). 같은 입력 반복은 바로 그 분기 예측 실패를 측정에서 지워서, Swiss table을 고른 이유를 보이지 않게 해요.
- **1M 행은 외울 수 없어요.** 분기 수백만 개의 순서는 어떤 예측기에도 너무 길어요. 두 모드의 차이가 없고, 테이블이 커서 캐시 미스가 시간을 정해요. 여기서는 Swiss table이 두 배 넘게 빨라요.

그래서 비교 측정은 새 입력 모드로 해요. 두 모드를 함께 보면 어느 코드가 분기 예측에 기대는지도 보여요. 같은 입력에서 크게 빨라지는 코드는 데이터에 따라 분기하는 코드예요.

<Callout type="warn">
새 입력 모드에도 대가가 있어요. 1M 행 입력 4벌은 합쳐서 캐시에 다 들어가지 않으므로, 메모리에 묶인 원소별 연산은 같은 입력을 되풀이할 때보다 느리게 나와요. 같은 입력이면 직전 호출이 남긴 입력의 일부가 L2 캐시(16MB)에 남아 있어요. 실제 사용에서 큰 컬럼은 대개 캐시 밖에서 오므로 새 입력의 시간이 실제에 더 가까워요.

Python 층을 얇게 두고 Column과 커널을 C++에 두는 구조의 비용은, 같은 C++ Column과 커널 위에 Series 클래스를 C++로 만든 모양과 Python으로 만든 모양을 나란히 놓으면 보여요(원소 10개, 같은 입력 반복, 1스레드, Apple M4 Pro).

| 연산 | Series를 C++로 | Series를 Python으로 |
|---|---:|---:|
| `s + s` | 92 ns | 256 ns |
| `s.sum()` | 30 ns | 66 ns |
| `df["a"]` | 64 ns | 91 ns |
| `df[df["a"] > 0]` (3열) | 400 ns | 1.10 µs |

- Python 층이 더하는 비용은 연산 하나에 30~200ns, 3열 필터는 약 0.7µs예요. pandas의 연산 하나가 수 µs라서 이 차이로 순위가 바뀌지 않고, 원소 100만 개에서는 두 모양의 차이가 측정 오차 안이에요.
- 반대로 `merge`처럼 옵션이 많은 API를 C++에서 파싱하면 코드가 길고 읽기 어려워요. 그래서 Python 층을 둬요.
- 지금의 공개 연산은 이 모양보다 일이 조금 더 있어요. NA 전파, 결과 이름 규칙(`s + t`의 이름은 두 이름이 같을 때만 남아요), dtype 검사가 더해져요.

**Column은 값 타입으로 넘겨요.** `_core.frame.Column`을 `std::shared_ptr<Column>`으로 돌려주면 원소 10개 `add`가 190ns, 값 타입이면 89ns였어요. nanobind는 `shared_ptr`을 돌려받을 때마다 Python 객체마다 `shared_ptr<void>` 복사본을 힙에 새로 만들고 전역 keep-alive 표에 등록해요(`nanobind/stl/shared_ptr.h`) [4]. 객체가 사라질 때 둘 다 되돌려요. 값 타입은 Python 객체 안에 미리 잡힌 저장 공간으로 Column을 move할 뿐이에요. Column 자체가 `shared_ptr<Buffer>` 셋을 든 작은 값이라 move가 싸요.

### 1천 행도 호출 비용이 커요

1천 행 float 덧셈은 8KB를 읽고 쓰는 일이라 커널이 1µs도 걸리지 않아요. 이 크기에서도 시간의 상당 부분이 위의 고정 비용이에요. Polars는 이 크기에서 스레드를 켜면 오히려 느려지는 줄이 있어요(1천 행 표의 Polars 1스레드와 14스레드 열). 일을 나누는 비용이 계산보다 크기 때문이에요. stardust는 기준값(2¹⁷행) 아래에서 풀을 쓰지 않으므로, 1천 행에서는 1스레드 열과 10스레드 열이 같은 일을 해요.

### 작은 데이터에서 효과가 큰 설계

새 입력으로 재면 작은 데이터의 시간이 같은 입력보다 커지는 곳이 드러나요. 그중 해시의 일부는 같은 입력 반복이 지운 분기 예측 실패이고(위 절), 나머지는 실제 비용이에요. 아래 세 설계가 그 비용을 줄여요. 모두 결과의 비트는 바꾸지 않아요.

- **(가)** 해시 테이블을 처음부터 행 수만큼 잡기. 대안은 32칸에서 시작해 두 배씩 키우기예요.
- **(나)** 나누지 않는 기수 정렬은 키를 한 번 읽어 8자리 히스토그램을 모두 세기. 대안은 자리마다 다시 세기예요.
- **(다)** 조회 루프의 dtype과 NA 유무를 호출마다 한 번 고르기. 대안은 행마다 묻기예요.

세 설계를 모두 쓴 구현과 모두 쓰지 않은 구현을 같은 조건(새 입력, Apple M4 Pro)에서 비교한 값이에요. 한 줄에 둘 이상의 설계가 함께 작용하기도 해서, 줄마다 관련된 설계를 적었어요.

| 경우 (새 입력) | 관련 설계 | 세 설계 모두 | 세 대안 모두 |
|---|:---:|---:|---:|
| int `nunique` 1천 행 | 가 | 4.5 µs | 11.2 µs |
| int `nunique`(키가 많음) 10만 행 | 가 | 0.73 ms | 1.58 ms |
| int `nunique`(키가 많음) 1M 행, 1스레드 | 가 | 7.9 ms | 15.1 ms |
| groupby int(키가 많음) 1M 행, 1스레드 | 가 | 32.8 ms | 46.5 ms |
| sort int64 1천 행 | 나 | 14.2 µs | 18.2 µs |
| groupby int 1k `sum` 1천 행 | 가, 나 | 31.4 µs | 47.5 µs |
| merge 1천 행 | 가, 다 | 11.6 µs | 14.3 µs |
| merge 1M 행, 10스레드 | 다 | 2.37 ms | 3.30 ms |

- **테이블을 미리 잡는 이유.** 32칸에서 두 배씩 키우면 키 수에 따라 $\log_2(\text{키 수})$번 다시 해시하고, 새 테이블마다 새로 받은 메모리에 처음 쓰면서 페이지 폴트를 내요. 키워 가는 테이블에서는 1만 행 groupby 시간의 4분의 1이 그 몫이에요. 빈 칸이 모두 0인 표현이라 큰 테이블은 `calloc`이 주는 0 페이지를 그대로 쓰고, 키가 떨어지는 페이지만 실제로 메모리를 받아요. 8바이트 키는 행 수만큼, 문자열 키는 최대 2¹⁶행 분량까지만 잡아요. 문자열 키는 같은 키인지 확인할 때마다 원래 문자열 바이트를 읽으므로, 테이블이 너무 크면 그 읽기가 캐시 밖으로 흩어져서 오히려 느려요(행 수만큼 잡으면 1M 행, 키 10만 종에서 키워 가기보다 26% 느려요) ([해시 테이블과 factorize](/internals/frame/hashing/)).
- **히스토그램을 한 번에 세는 이유.** 기수 정렬은 8자리(바이트) 각각의 히스토그램이 필요해요. 나누지 않을 때는 키를 한 번 읽으며 8개 히스토그램을 모두 셀 수 있어요. 키를 8번 읽지 않아도 돼요. 1천~1만 행에서 25~29% 빨라지고, 10만 행부터는 차이가 없어요(키를 읽는 시간보다 흩뿌리기가 커요) ([groupby와 정렬](/internals/frame/groupby-sort/)).
- **조회 루프를 고르는 이유.** 행마다 "NA인가, 문자열인가, 어느 dtype인가"를 물으면 1스레드 1M 행 merge 시간의 약 절반(48%)이 조회예요. 루프 밖에서 한 번 고르면 행 루프에는 찾기와 저장만 남아요([merge와 concat](/internals/frame/merge-concat/)).

### 빠른 이유

줄마다의 메커니즘은 각 글에 있어요. 크게 묶으면 이래요.

- **원소별 연산과 리덕션**: dtype, NA 유무, 스칼라 여부를 템플릿 인자로 루프 밖에서 고르므로 행 루프에 분기가 없고 컴파일러가 NEON으로 벡터화해요. float 합은 numpy와 같은 pairwise 트리를 잎 단위로 나눠 여러 스레드로 더해요([원소별 연산과 리덕션](/internals/frame/elementwise/)).
- **해시**: Swiss table(16칸 제어 바이트의 SIMD 비교), 미리 잡은 테이블, 해시로 나눈 병렬 factorize([해시 테이블과 factorize](/internals/frame/hashing/)).
- **groupby와 정렬**: groupby는 factorize → counting sort로 그룹별 행 모으기 → 그룹마다 집계예요. 정렬은 비교 정렬 대신 8바이트 키의 LSD 기수 정렬이고, 문자열은 8바이트 접두사로 기수 정렬한 뒤 접두사가 같은 구간만 비교해요([groupby와 정렬](/internals/frame/groupby-sort/)). 이 측정 환경의 pandas는 pyarrow가 없어 문자열을 Python 문자열 객체로 들고, 정렬도 그 객체들의 비교 정렬이라 차이가 커요.
- **CSV**: 64바이트 블록마다 따옴표·구분자·줄바꿈의 비트 마스크를 만들어 필드 경계를 꺼내는 structural index 토크나이저, Eisel–Lemire 숫자 파싱, 512KB 청크의 병렬 읽기([read_csv](/internals/frame/csv/)).
- **스레드**: pandas는 한 스레드예요. stardust는 기준값 이상에서 10스레드로 나눠요.

## 느린 줄과 그 원인

### 10만 행: 기준값의 그늘

10만 행은 기준값 2¹⁷(131,072)보다 작아요. 그래서 `cost`가 1인 커널(`float + float`, `float sum`, `mask filter`)과 해시 분할 factorize(`nunique`, groupby의 키 정리, merge의 테이블)가 1스레드로 돌아요. 이 크기에서 10스레드 열은 1스레드 열과 거의 같아요. Polars 14스레드는 이 크기에서도 나누는 연산이 있어서, 원소별 연산을 뺀 여러 줄에서 앞설 수 있어요.

이 크기에서도 나누는 것은 기수 정렬(흩뿌리기의 `cost`가 2라 65,536행부터)과 CSV(512KB 청크로 자르고, 10만 행 파일은 1MB를 넘어요)예요. 그래서 `sort int64`, `sort string`, `read_csv` 줄은 10만 행에서도 10스레드 열이 실제로 나눠서 돌아요.

기준값을 연산마다 다르게 두면 이 그늘을 줄일 수 있어요. 예를 들어 키가 많은 해시는 분기와 캐시 미스가 많아서 더 작은 크기부터 나눠도 이득일 수 있어요. 지금은 상수 하나와 커널별 무게(`cost`)만 둬요. 연산마다 기준값을 따로 두면 그 값마다 측정 근거를 지켜야 하기 때문이에요([병렬화와 결정성](/internals/frame/parallel/)).

### 키가 많은 해시: Polars보다 느린 무리

`nunique int, n keys`, `groupby int, n keys, sum`, `groupby string sum`, `merge` 줄은 Polars와 비교해 불리할 수 있는 무리예요. 구조에서 오는 이유가 셋 있어요.

1. **처음 나타난 순서로 번호를 다시 매겨요.** 병렬 factorize는 파티션마다 지역 코드를 매긴 뒤, 결과를 스레드 수와 무관하게 하려고 전역 코드를 "처음 나타난 순서"로 다시 매겨요(행 청크마다 첫 등장 행의 순위 매기기, 행마다 코드 쓰기). 행 전체를 두 번 더 지나는 일이에요. Polars는 그룹 순서를 기본으로 보장하지 않으므로(`maintain_order=False`) [5] 이런 단계가 필요 없어요. 이 단계가 차이의 얼마를 차지하는지는 아직 재지 않았어요.
2. **키가 많으면 테이블이 캐시를 넘어요.** 1M 행에 키 63만 종이면, 파티션으로 나누지 않은 테이블은 칸 2M개 × 16바이트 = 32MB예요. 256 파티션으로 나누면 파티션마다 약 3,900행, 칸 8,192개 × 16바이트 = 128KB라 L1~L2에 들어가요. 그래서 1스레드(나누지 않는 경로)에서 키가 많은 해시는 찾을 때마다 캐시 미스를 내요.
3. **문자열 키는 바이트를 다시 읽어요.** 8바이트 키는 (키, 행) 쌍 자체를 파티션으로 흩뿌려서 파티션 안에서 앞에서부터 차례로 읽어요. 문자열 키는 해시만 흩뿌리고, 해시가 같은 후보를 만나면 행 번호로 원래 문자열 바이트를 읽어 비교해요. 그 읽기는 문자열 버퍼의 아무 곳으로나 튀어요.

`merge`는 여기에 build 쪽 counting sort(코드별 행 모으기)와 출력 두 열의 take가 더해져요.

### `read_csv`의 1스레드

1스레드 `read_csv`는 필드 하나에 약 12ns를 써요. pandas의 C 토크나이저도 한 스레드인데, 1스레드 열끼리 비교하면 stardust가 불리할 수 있는 줄이에요(`read_csv floats`, `read_csv mixed`의 pandas ÷ sd@1 열). 10스레드에서는 512KB 청크를 나눠 읽어 앞서요. 토크나이저와 숫자 파싱의 구조는 [read_csv](/internals/frame/csv/)에 있어요.

### 10행 `s.sum()`

10행 `s.sum()`은 Polars가 앞설 수 있는 몇 안 되는 작은 줄이에요. 커널은 원소 10개를 더하는 몇 ns이고 나머지는 호출 비용이에요. 어느 단계(Python 메서드, 인자 변환, 결과 스칼라 만들기, NA 규칙 검사)가 차이를 만드는지는 아직 재지 않았어요.

### 단순한 구현보다 느린 세 줄

같은 기능을 단일 코어 최적화와 병렬화 없이 짠 단순한 직렬 구현과 비교하면, 새 입력 모드에서 이 설계가 10% 넘게 느린 줄이 셋 있어요.

| 경우 | 단순한 구현 | 이 설계 |
|---|---:|---:|
| sort int64 1천 행 | 10.7 µs | 14.2 µs |
| merge 1천 행 | 10.0 µs | 11.6 µs |
| 10행 마스크 필터 | 1.51 µs | 1.75 µs |

원인은 아직 밝히지 못했어요.

## 결과의 비트를 지키느라 하지 않는 최적화

더 빠를 수 있지만 결과를 바꾸거나 결과가 데이터에 따라 몰래 달라지게 하는 기법은 쓰지 않아요. 각각의 대가가 위 표의 어딘가에 있어요.

| 하지 않는 것 | 지키는 것 | 대가 |
|---|---|---|
| float 합의 재결합(청크마다 부분 합, `-ffast-math`, FMA로 합치기) | numpy·pandas와 같은 비트, 스레드 수와 무관한 비트 | 합은 pairwise 트리의 순서를 따라야 해요. 그래도 잎을 나누므로 병렬은 돼요. 모듈 전체를 `-ffp-contract=off`로 빌드해요 |
| groupby 합에 Kahan 보정 | 그룹 합 = 그 그룹만 고른 `Series.sum()` | pandas의 groupby 합(보정 합)과 비트가 다를 수 있어요. 값 `[1.0] + [1e-16] * 10` 한 그룹의 합이 pandas 3.1.1은 `1.000000000000001`, stardust와 `np.sum`은 `1.0000000000000007`이에요 |
| factorize 코드를 아무 순서로 | 처음 나타난 순서, 스레드 수와 무관 | 병렬 factorize에 번호를 다시 매기는 단계 |
| 불안정 정렬 | 같은 값은 원래 순서 | 정렬은 언제나 안정 정렬(기수 정렬)이에요 |
| 데이터를 보고 경로 고르기(정렬돼 있으면 이진 탐색, 고유하면 빠른 길, 기수 정렬에서 모든 키가 같은 바이트 자리 건너뛰기) | 성능과 결과 타입이 데이터에 따라 몰래 바뀌지 않음 | 정렬된 Index의 라벨 슬라이스도 해시 조회를 해요. 같은 바이트 자리도 8패스를 모두 돌아요 |
| 연산마다 다른 병렬 기준값 | 상수 하나와 측정 근거 | 10만 행의 그늘 |

## 테스트: 무엇을 정답으로 삼나

테스트는 `tests/frame/`(약 3,700줄)과 배열과의 경계 `tests/interop/`이에요. pytest와 hypothesis(무작위 입력을 만들어 성질을 확인하고, 실패하면 가장 작은 반례로 줄여 주는 속성 기반 테스트 라이브러리) [2]를 써요. 무작위 예제는 테스트마다 기본 200~300개이고, 환경 변수로 수천 개까지 늘려 긴 실행을 해요.

같은 코드로 정답과 결과를 만들면 틀려도 알 수 없어요. 그래서 정답은 stardust 밖의 것이거나, 규칙을 가장 단순하게 옮긴 별도 구현이에요.

### 정답의 종류

| 정답 | 무엇을 | 어떻게 |
|---|---|---|
| pandas 3.1.1 | 대부분의 연산 | 같은 입력을 pandas로 계산해 비교해요. pandas와 일부러 다르게 정한 곳(NA가 있어도 int는 int로 남기, NaN은 결측이 아님 등)은 pandas 결과를 그 규칙으로 바꾼 뒤 비교해요 |
| Python 참조 구현 | factorize, merge, `read_csv` | factorize는 Python dict의 `setdefault`로 처음 나타난 순서의 코드를 매겨요(NaN끼리 같고, NA는 별도 키). merge는 행 순서 규칙을 그대로 쓴 이중 반복문이에요. `read_csv`는 옵션과 추론 규칙(int → float → bool → string)을 정규식으로 옮긴 구현이에요 |
| Python 자체 | 정렬, 숫자 ↔ 문자열 | 정렬은 `sorted()`(`reverse=True`에서도 안정), float → 문자열은 `str(float)`, 문자열 → float은 `float(text)`와 비트까지 같아야 해요 |
| numpy 2.5.4 | float 합, mean, var, std | numpy로 한 단계씩 재현해 **비트**로 비교해요. NA 자리를 0.0으로 채운 배열의 `np.sum`, `np.sum / count`, `np.where(valid, (x - mean)**2, 0.0)`의 합(pandas의 nanvar와 같은 순서)이에요. `-0.0`과 `0.0`도 구분해요 |
| 배열 영역 | int 평균, int–float 비교, float → int 변환 | `sd.sum(x, dtype=sd.float64) / 개수`, `sd.equal`, `sd.astype`의 결과와 같아야 해요(`tests/interop/`) |
| 같은 영역의 다른 연산 | groupby | 그룹 집계는 그 그룹의 행만 고른 Series의 리덕션과 같아야 해요 |

float 리덕션 테스트는 길이를 0, 1, 7, 8, 9, 127, 128, 129, 300, 1000, 5000과 0~64의 무작위로 뽑아요. pairwise 합의 경계(8개 누산기, 128개 잎)를 일부러 지나게 하는 길이들이에요. 값은 ±10¹²의 유한한 float에 `0.0`, `-0.0`, `1e-300`을 섞고 NA를 무작위로 넣어요. NA가 없으면 pandas 자체도 정답으로 함께 써요.

### repr은 글자 단위로

`repr(Series)`와 `repr(DataFrame)`은 pandas의 출력과 **글자 하나까지** 같아야 해요. 행 0~100개, 열 0~23개, 극단적인 float(`1e-7`, `1e15`, `inf`, `-0.0` 등), 탭·줄바꿈과 여러 언어의 문자가 든 문자열을 무작위로 만들어 비교해요. 컬럼마다 pandas가 같은 모양으로 출력하는 객체(NA가 없으면 numpy dtype, 있으면 pandas의 nullable `Int64`·`boolean`·`string`, float의 NA는 `na_rep="<NA>"`)로 바꿔 넣어요. pandas의 nullable `Int64`는 음수를 한 칸 넓게 찍어서 이 차이는 따로 시험하고, 열이 20개를 넘어 가운데가 잘릴 때 pandas가 헤더 공백을 잘리기 전 위치의 dtype으로 고르는 경우는 비교에서 뺐어요.

### 스레드, 스냅샷, Copy-on-Write

- **스레드**: `tests/frame/test_threads.py`가 원소별·리덕션·해시·정렬·CSV를 1, 3, 기본 스레드 수에서 비교해요. 값의 비트, 행 순서, 에러 메시지까지예요([병렬화와 결정성](/internals/frame/parallel/)).
- **GIL**: `sd.set_num_threads(1)`에서 큰 호출(1,600만 행의 원소별 연산, 리덕션, 필터, groupby `sum`, 300만 행 정렬)을 부르는 동안 옆의 Python 스레드가 계속 도는지 봐요. 기준값 이상이면 스레드 수와 상관없이 GIL을 놓는다는 규칙의 시험이에요(`tests/frame/test_threads.py`, 영역 공통의 `tests/test_gil_release.py`).
- **스냅샷**: 한 스레드가 `s.iloc[k] = 1`을 k = 0, 1, 2, …로 쓰는 동안 다른 스레드가 `s + 0`을 되풀이하고, 모든 결과가 "앞의 k개만 1"인 꼴인지 봐요. 연산이 호출한 순간의 값만 본다는 규칙의 시험이에요.
- **Copy-on-Write가 실제로 그 자리에서 쓰는지**: 아무도 Buffer를 공유하지 않을 때 대입 전후의 `to_numpy()` 데이터 주소(`__array_interface__["data"]`)가 같은지 봐요. 복사가 필요 없을 때 복사하지 않는다는 것을 확인해요. 뷰를 들고 있으면 반대로 복사해야 해요.
- **배열과의 경계**(`tests/interop/test_frame_array.py`): `to_array`가 읽기 전용 뷰인지, frame 쪽 쓰기가 먼저 복사하고 뷰는 옛 값을 지키는지, 배열에서 만들 때 복사하는지, 승격 규칙과 dtype 객체가 배열 영역과 같은지 봐요.
- **공개 이름**: `test_api_surface.py`가 공개 이름과 시그니처를 API 명세 문서와 맞춰요.
