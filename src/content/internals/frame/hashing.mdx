## 한눈에 보기

데이터프레임의 많은 기능은 결국 "어느 행들이 같은 키인가"라는 질문 하나로 돌아가요. 중복 찾기, 고유값 세기, 그룹으로 묶기, 두 표를 키로 잇기, 라벨로 행 찾기가 모두 그래요. stardust는 이 질문을 **factorize** 하나로 풀어요. factorize는 컬럼의 값마다 정수 코드를 주는 일이에요. 같은 키는 같은 코드, 다른 키는 다른 코드를 받고, 코드는 0부터 빈틈없이 처음 나타난 순서로 매겨요. 그다음의 일은 값이 아니라 이 정수를 다루므로 dtype과 상관없이 단순한 배열 연산이 돼요.

모든 코드는 `csrc/frame/ops/hash.hpp`와 `hash.cpp`에 있어요.

| 부분 | 이름 | 하는 일 |
|---|---|---|
| 키 정규화 | `float_key` | NaN을 하나로, `-0.0`을 `0.0`으로 바꿔 "같은 키 = 같은 비트"로 만들어요 |
| 해시 함수 | `Fmix64`, `HashBytes` | 8바이트 키는 murmur3의 fmix64, 문자열은 wyhash식 곱셈 섞기 + fmix64 |
| 해시 테이블 | `SwissTable` | 칸 16개를 한 그룹으로 NEON 비교 한 번에 훑는 open addressing 테이블 |
| factorize 엔진 | `Partitioned` | 행이 적거나 스레드가 하나면 직렬 한 번, 아니면 해시로 256개 파티션에 나눠 병렬로. 어느 쪽이든 코드는 같아요 |
| 공개 커널 | `factorize`, `factorize_rows` | 컬럼 하나, 여러 컬럼(다중 키)의 코드 |
| 조회 | `ValueCodes`, `LabelTable`, `find_rows` | merge의 build/probe, Index의 라벨 조회 |

설계의 뼈대는 다섯 가지예요.

- **"같은 키"의 규칙은 한 곳에만 있어요.** NaN끼리 같고 `-0.0`과 `0.0`이 같다는 규칙을 factorize가 해시 전에 비트로 바꿔 두므로, unique·groupby·merge·Index가 규칙을 따로 구현하지 않아요.
- **Swiss table을 써요.** linear probing은 "이 칸에서 찾았나, 다음 칸으로 가나"를 매 행 분기로 묻는데, 이 분기를 CPU가 예측하지 못해요. Swiss table은 그 질문을 16칸짜리 비트 마스크 연산으로 바꿔 분기를 없애요.
- **테이블을 처음부터 크게 잡아요.** 행 수는 키 수의 상한이라 8바이트 키 테이블은 한 번도 자라지 않아요. 빈 칸을 0으로 정해 두어 `calloc`한 메모리가 곧 빈 테이블이고, 실제로 키가 들어간 페이지만 메모리를 차지해요.
- **병렬로 나눠도 코드는 직렬과 같아요.** 해시의 위쪽 8비트로 행을 나누고, 마지막에 "첫 등장 행의 순서"로 번호를 다시 매겨요. 결과가 나누는 방식과 무관하니 1스레드는 나누지 않는 직렬 경로를 그대로 써요.
- **데이터를 보고 경로를 고르지 않아요.** 테이블 크기와 직렬·병렬 여부는 행 수, dtype, 쓸 수 있는 스레드로만 정해요.

## factorize: 값을 정수 코드로

### 정의

factorize는 길이 $n$인 컬럼을 받아 세 가지를 돌려줘요.

- `codes`: 행마다 int64 코드 하나. 같은 키의 행은 같은 코드예요.
- `first`: 코드마다 그 코드가 처음 나온 행 번호.
- `ngroups`: 코드의 개수, 곧 서로 다른 키의 수(NA를 하나로 쳐서).

코드는 처음 나타난 순서예요. 행 0의 키가 코드 0, 그다음 처음 보는 키가 코드 1, …이에요. 그래서 `first`는 언제나 증가하는 배열이에요.

factorize는 공개 함수가 아니에요. 사용자는 그 위에 올라간 기능으로 결과를 봐요. 위 그림과 같은 값으로 보면 이래요.

```python
>>> import stardust as sd
>>> s = sd.frame.Series([3.0, float("nan"), 1.0, 3.0, -0.0, 0.0, None, float("nan")])
>>> s.drop_duplicates()
0    3.0
1    NaN
2    1.0
4   -0.0
6   <NA>
dtype: float64
>>> s.value_counts(sort=False)
   values  counts
0     3.0       2
1     NaN       2
2     1.0       1
3    -0.0       2
>>> s.nunique()
4
```

`drop_duplicates`가 남긴 행 번호 `0, 1, 2, 4, 6`이 바로 `first`예요. `value_counts(sort=False)`의 순서가 코드 순서이고, 기본값 `dropna=True`라서 NA 줄이 빠졌어요. `nunique()`는 `ngroups`(5)에서 NA 하나를 뺀 값이에요.

### 왜 모든 기능의 바닥인가

키를 정수 코드로 바꾸면 남은 일은 $0..\text{ngroups}-1$ 범위의 정수 배열을 다루는 일이에요. 배열 인덱스로 바로 쓸 수 있으니 개수 세기는 `counts[code] += 1` 한 줄이고, 그룹별로 행을 모으는 일은 counting sort가 돼요. 값이 문자열이든 float든 이 단계부터는 같은 코드가 돌아요.

| 기능 | factorize 위에서의 계산 | 자세한 곳 |
|---|---|---|
| `nunique()` | `ngroups` (`dropna=True`이고 NA가 있으면 1을 빼요) | |
| `duplicated(keep="first")` | `위치 != first.take(codes)` | [duplicated](/api/frame/duplicated/) |
| `duplicated(keep="last")` | 위와 같고 `first` 대신 코드마다 마지막 행(`group_counts`) | |
| `duplicated(keep="none")` | `counts.take(codes) > 1` | |
| `drop_duplicates()` | `duplicated`의 반대인 행만 `take` | |
| `value_counts()` | 개수로 안정 정렬한 코드 순서로 `take(first)`와 개수 | [value_counts](/api/frame/value_counts/) |
| `unique_values()` | `col.take(first)`를 groupby의 그룹 순서로 정렬 | [unique_values](/api/frame/unique_values/) |
| groupby | 코드가 곧 그룹 번호 | [groupby와 정렬](/internals/frame/groupby-sort/) |
| 문자열 정렬 | 고유 문자열의 순위가 문자열을 대신해요 | [groupby와 정렬](/internals/frame/groupby-sort/) |
| merge | 오른쪽 키로 테이블을 만들고 왼쪽 키를 조회 | [merge와 concat](/internals/frame/merge-concat/) |
| Index 조회 | 라벨의 코드와 코드마다 첫 위치 | [라벨, 조회, 선택](/internals/frame/labels/) |

`unique_values`, `duplicated`, `value_counts`는 Python 층(`src/stardust/frame/_unique.py`)에서 이 표 그대로 컬럼 연산으로 조립돼요. 두 보조 커널이 `hash.cpp`에 있어요.

- `group_counts(codes, ngroups)`: 코드마다 개수와 마지막 행을 한 번 훑어 세요. 직렬 루프 하나이고, 일이 기준값 이상이면 GIL을 놓아요.
- `stable_order(counts, ascending)`: 개수로 코드를 안정 정렬해요. 행이 아니라 코드(고유 키)마다 하나인 배열을 정렬하므로 `std::stable_sort`로 충분해요. 같은 개수끼리는 코드 순서, 곧 처음 나타난 순서를 지켜요.

그래서 "NaN은 NaN과 같은가", "`-0.0`과 `0.0`은 같은가", "NA끼리는 같은가" 같은 규칙이 C++ factorize 한 곳에만 있고, `unique_values`와 `groupby`와 `merge`가 서로 다른 답을 낼 수 없어요. 정렬의 키 변환([groupby와 정렬](/internals/frame/groupby-sort/))도 같은 정규화 함수에서 시작하므로 "factorize에서 같은 키는 정렬에서도 같은 값"이에요.

### 결과에 나오는 것은 원래 값이에요

factorize는 정규화한 키로 같음을 판단하지만, 결과에 보이는 값은 원래 값이에요. `first`가 원래 행 번호라서 `col.take(first)`가 그 키로 처음 나온 원래 값을 돌려주기 때문이에요. 위 예에서 `-0.0`이 먼저 나왔으니 `drop_duplicates`와 `value_counts`에 `-0.0`이 보이고, NaN도 처음 나온 NaN의 비트 그대로예요.

### pandas와 Polars에서는

pandas 3.1.1의 `pd.factorize`도 같은 일을 해요. `sort=False`(기본)면 처음 나타난 순서이고, 같은 float 값에서 `-0.0`과 `0.0`을 같은 키로, NaN끼리를 같은 키로 봐요. 다만 기본값(`use_na_sentinel=True`)에서 NaN은 결측으로 보고 코드 -1을 받아요. stardust에서 NaN은 결측이 아니라 평범한 float 값이고, 결측은 NA 하나예요.

```python
# pandas 3.1.1
pd.factorize(np.array([3.0, np.nan, 1.0, 3.0, -0.0, 0.0, np.nan]))
# (array([ 0, -1,  1,  0,  2,  2, -1]), array([ 3.,  1., -0.]))
```

pandas의 groupby도 키를 `algorithms.factorize`로 코드로 바꾸고(`pandas/core/groupby/grouper.py`), merge는 dtype별 `Factorizer`(`pandas/core/reshape/merge.py`)를 써요. 다만 pandas 3.1.1의 groupby에는 키가 이미 정렬돼 있는지 먼저 훑어 보고, 정렬돼 있으면 해시 테이블 없이 이웃 비교로 코드를 만드는 지름길(`_factorize_monotonic`)이 있어요. stardust는 이런 "데이터를 보고 경로를 고르는" 지름길을 두지 않아요. 같은 크기와 dtype이면 언제나 같은 경로라서 시간을 예측할 수 있어요.

Polars 2.1.0은 그룹의 순서를 기본으로 보장하지 않아요. `group_by`의 `maintain_order` 문서가 "그룹 순서를 입력과 맞추려면 이것을 켜야 하고, 기본 group by보다 느리다"고 적어요. stardust의 코드는 언제나 처음 나타난 순서이고 스레드 수와 무관해요. 그 대가가 병렬 경로의 "번호 다시 매기기" 단계예요(아래 [해시로 나눈 병렬 factorize](#해시로-나눈-병렬-factorize)).

## 키 정규화

### 해시 테이블은 "비트가 같으면 같은 키"일 때 가장 단순해요

해시 테이블의 두 연산, 해시와 같음 비교는 서로 맞아야 해요. "같은 키면 해시도 같다"가 깨지면 같은 키가 다른 칸으로 가서 영영 만나지 못해요. 그런데 float64의 같은 키 규칙은 비트 비교와 어긋나요.

- NaN끼리 같아요. 그런데 NaN의 비트는 여러 가지예요. 지수 비트가 모두 1이고 가수가 0이 아니면 모두 NaN이라, 부호와 가수(페이로드)가 다른 NaN이 $2^{53} - 2$가지 있어요. IEEE 754의 `==`로는 NaN이 자기 자신과도 같지 않아요.
- `-0.0`과 `0.0`이 같아요. `==`로는 같지만 비트는 부호 비트 하나가 달라요(`0x8000000000000000`과 `0`).

이 어긋남을 테이블 안에서 처리하면, 해시 함수와 비교 함수가 모두 "NaN인가, 0인가"를 키마다 물어야 해요. pandas가 그렇게 해요. pandas 3.1.1의 `kh_float64_hash_func`는 값이 `0.0`이면 0, NaN이면 0을 해시로 돌려주고, 비교 함수 `kh_floats_hash_equal`은 `a == b || (b != b && a != a)`예요(`khash_python.h`). 비교할 때마다 분기가 더 붙어요.

stardust는 해시하기 전에 키를 비트로 정규화해요.

```cpp
// csrc/frame/ops/hash.hpp
inline std::uint64_t float_key(double d) {
    if (d != d) return 0x7ff8000000000000ULL;   // 모든 NaN을 NaN 하나로
    if (d == 0.0) return 0;                      // -0.0을 +0.0의 비트로
    std::uint64_t bits;
    std::memcpy(&bits, &d, sizeof bits);
    return bits;
}
```

정규화한 뒤 float64 키는 int64 키와 똑같이 다뤄요. 테이블은 `uint64_t` 키 하나만 알면 되고, 같음 비교는 정수 `==` 하나예요. 정규화는 행마다 비교 두 번이지만 키를 읽을 때 한 번뿐이고, 비교마다 붙는 분기보다 싸요.

`memcpy`는 float의 비트를 정수로 읽는 C++의 정의된 방법이에요(포인터 캐스팅은 strict aliasing 규칙을 어겨요). 컴파일러는 이것을 레지스터 이동 하나(`fmov`)로 바꿔요.

### dtype별 키

| dtype | 테이블의 키 | 칸에 저장하는 `word` |
|---|---|---|
| bool | 0 또는 1 (`uint64_t`) | 키 자체 |
| int64 | 값의 비트 (`uint64_t`) | 키 자체 |
| float64 | `float_key(값)` | 키 자체 |
| string | `std::string_view` (컬럼의 바이트를 가리킴) | 키의 해시 |

8바이트에 들어가는 키(bool, int64, float64)는 `Fmix64`로 해시하는 `SwissTable<uint64_t, Fmix64>` 하나를 같이 써요. 문자열은 `SwissTable<std::string_view, HashBytes>`예요. 이 둘이 템플릿의 두 인스턴스이고, 어느 쪽인지는 `kInline = std::is_same_v<Key, std::uint64_t>`로 컴파일 시점에 정해져요. 그래서 "8바이트 키인가 문자열인가"를 묻는 분기가 행 루프에 없어요.

문자열 키의 `string_view`는 컬럼의 UTF-8 바이트를 가리킬 뿐 복사하지 않아요. 그래서 테이블을 오래 유지하는 `ValueCodes`와 `LabelTable`은 컬럼(`build_`, `labels_`)을 함께 붙잡아 바이트가 먼저 사라지지 않게 해요. 문자열 컬럼의 메모리 배치(offsets + 연속 바이트)는 [컬럼과 메모리](/internals/frame/columns/)에 있어요.

### NA는 테이블에 넣지 않아요

NA 행은 값 자리가 0이에요([컬럼과 메모리](/internals/frame/columns/)). 그래서 NA를 그대로 넣으면 int64의 0, float의 `0.0`, bool의 False, 빈 문자열과 같은 키가 돼요. 이것을 막으려고 NA 행은 테이블을 거치지 않아요.

```cpp
// csrc/frame/ops/hash.hpp, Partitioned::build의 직렬 경로 (줄인 발췌)
for (std::int64_t i = 0; i < n; ++i) {
    if (!valid(i)) {                                  // NA 행
        if (na_code_ < 0) {                           // 처음 나온 NA: 다음 번호를 준다
            na_code_ = static_cast<std::int64_t>(first.size());
            first.push_back(i);
        }
        codes[i] = na_code_;                          // 이후의 NA는 모두 같은 코드
        continue;
    }
    auto [code, added] = table.insert(key_of(i), static_cast<std::int64_t>(first.size()));
    if (added) first.push_back(i);
    codes[i] = code;
}
```

- 처음 나온 NA 행이 그 순서의 번호를 받고, 이후 NA 행은 모두 그 코드를 써요. NA도 "처음 나타난 순서" 규칙을 따르는 하나의 키예요. groupby(`dropna=False`)와 `drop_duplicates`에서 NA끼리 같다는 규칙이 여기서 나와요.
- merge는 NA 키가 아무것과도 맞지 않아야 해요. 그래서 merge의 build 쪽(`ValueCodes`)은 NA 코드를 -1로 바꾸고 그 뒤 코드를 하나씩 당겨요(아래 [조회](#조회-find_rows)).
- `valid(i)`는 컬럼에 비트맵이 있을 때만 비트를 읽는 람다이고, 비트맵이 없으면(NA가 하나도 없으면) 언제나 `true`를 돌려주는 람다예요. 어느 람다인지는 `factorize_with`가 호출마다 한 번 고르고, 둘이 각각 다른 템플릿 인스턴스가 되므로 NA 없는 컬럼의 루프에는 NA 검사가 아예 없어요.

## 해시 테이블의 기초: open addressing

### 해시 테이블 두 가지

해시 테이블은 키를 해시 함수로 정수 $h$로 바꾸고, $h$로 정한 자리에 키를 두어 평균 $O(1)$에 찾는 자료 구조예요. 서로 다른 키가 같은 자리를 원하는 충돌을 처리하는 방법이 두 갈래예요.

- **chaining:** 자리마다 연결 리스트를 두고 충돌한 키를 그 리스트에 달아요. C++의 `std::unordered_map`이 이 방식이에요. 노드마다 할당이 따로 있고, 찾을 때 포인터를 따라가며 캐시 미스가 나요.
- **open addressing:** 키를 배열 하나의 칸에 직접 넣어요. 원하는 칸이 차 있으면 정해진 순서(probe 순서)로 다른 칸을 차례로 봐요. 할당이 배열 하나이고 메모리를 순서대로 지나가요.

stardust, pandas(khash), Polars(hashbrown), Abseil의 `flat_hash_map`은 모두 open addressing이에요.

open addressing에서 중요한 양이 **적재율** $\alpha = (\text{키 수}) / (\text{칸 수})$예요. 칸이 찰수록 빈 칸을 만나기까지 더 많이 봐야 해요. 그래서 적재율이 정해 둔 상한을 넘으면 칸 수를 두 배로 늘리고 모든 키를 다시 넣어요(재해시).

### linear probing

가장 단순한 probe 순서가 linear probing이에요. 칸 $h \bmod m$에서 시작해 $h+1, h+2, \dots$를 봐요. 찾는 키를 만나면 성공, 빈 칸을 만나면 "없음"이에요. 연속한 칸을 보니 캐시에 유리해요.

Knuth의 분석[9]에 따르면, 적재율 $\alpha$에서 linear probing이 보는 칸 수의 기댓값은 성공한 검색이 약

$$
\tfrac{1}{2}\left(1 + \frac{1}{1-\alpha}\right),
$$

실패한 검색이 약 $\tfrac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)$이에요. $\alpha = 0.5$면 각각 1.5칸, 2.5칸이에요. $\alpha$가 1에 가까워지면 실패한 검색이 급격히 길어져요. 찬 칸들이 이어진 덩어리(클러스터)가 자라고, 덩어리에 떨어진 키는 덩어리 끝까지 가야 하기 때문이에요.

stardust에는 비교용 linear probing 테이블 `LinearTable`도 있어요. 실제로는 쓰지 않아요(`KeyTable = SwissTable`).

```cpp
// csrc/frame/ops/hash.hpp, LinearTable::insert (줄인 발췌). 칸 = {word, code}, code < 0이면 빈 칸
std::uint64_t s = h & mask_;
while (true) {
    Slot& e = slots_[s];
    if (e.code < 0) { /* 빈 칸: 여기에 넣는다 */ ...; return {new_code, true}; }
    if (matches(e, k, h)) return {e.code, false};   // 찾았다
    s = (s + 1) & mask_;                            // 다음 칸
}
```

칸은 `{word, code}` 16바이트, 칸 수는 2의 거듭제곱이라 `h & mask_`가 나머지 연산을 대신해요. 키가 절반을 넘으면 두 배로 늘려요.

### linear probing이 느린 이유: 분기 예측 실패

1M 행, 키 1,000종의 int64 `nunique`를 linear probing으로 하면 4.29ms예요(Apple M4 Pro, 1스레드). 테이블은 2,048칸 × 16B = 32KB로 L1 캐시에 다 들어가는데도 행마다 약 19사이클이 들어요.

후보를 하나씩 지워 보면 이래요.

- **probe 횟수가 아니에요.** 평균 1.48칸을 봤어요. 적재율 $1000/2048 \approx 0.49$에서 위 공식이 주는 값($\tfrac12(1 + 1/0.51) \approx 1.48$) 그대로예요.
- **메모리도 아니에요.** 테이블이 L1에 있어요.
- **분기예요.** 프로파일 샘플의 3분의 2가 "첫 칸의 키가 다르다 → 다음 칸으로" 분기 바로 뒤에 몰렸어요.

키가 첫 칸에 있을 확률이 약 3분의 2이고, 어느 행이 그 3분의 2에 들지는 해시에 달렸어요. 좋은 해시일수록 이 패턴은 무작위라서 분기 예측기가 맞힐 수 없어요. CPU는 예측한 쪽을 미리 실행하다가 예측이 틀리면 그 일을 버리고 다시 시작해요. 그런데 여기서 다시 시작해야 하는 일이 하필 긴 의존 사슬이에요.

$$
\text{키 읽기} \;\to\; \text{fmix64 (곱셈 2번)} \;\to\; \text{칸 읽기} \;\to\; \text{비교} \;\to\; \text{분기}
$$

각 단계가 앞 단계의 결과를 기다리므로 비순차 실행으로 겹칠 수 없어요. 예측이 맞으면 CPU는 다음 행의 사슬을 미리 시작해 두 행을 겹쳐 실행하지만, 틀리면 그 겹침이 사라지고 사슬 전체의 지연을 그대로 치러요.

### 측정의 함정: 같은 입력을 반복해서 재면

분기 예측기는 생각보다 많이 기억해요. 같은 입력으로 수천 번 불러 최솟값을 잡으면, M4 Pro의 예측기는 1천 행 입력의 분기 1천 개를 통째로 외워요. 그러면 분기가 많은 코드일수록 실제보다 빨라 보여요. 키 1,000종 테이블만 따로 잰 값이에요(행당 ns, Apple M4 Pro).

| 행 수 | linear probing, 같은 입력 | linear probing, 새 입력 | Swiss table, 같은 입력 | Swiss table, 새 입력 |
|---:|---:|---:|---:|---:|
| 1,000 | 3.65 | **11.8** | 6.49 | 8.50 |
| 10,000 | 1.25 | 5.73 | 2.45 | 3.67 |
| 1,000,000 | 4.11 | 4.35 | 1.84 | 1.86 |

같은 입력을 반복하면 작은 크기에서 linear probing이 이기는 것처럼 보이지만, 매번 새 입력을 주면 1천 행부터 Swiss table이 이겨요. 1M 행은 예측기가 외울 수 없어서 두 방식 모두 같은 입력과 새 입력의 차이가 거의 없어요. Swiss table은 바로 이 예측 실패를 없애려고 고른 구조인데, 같은 입력 반복은 측정에서 그 실패를 지워 버려요. 그래서 stardust의 측정은 새 입력 모드를 함께 써요([성능과 검증](/internals/frame/performance/)).

## Swiss table

### Abseil의 원래 설계

Swiss table은 Google이 Abseil 라이브러리의 `absl::flat_hash_map`으로 공개한 open addressing 테이블이에요[1][2][3]. Rust의 hashbrown도 그 포팅이고, Rust 표준 라이브러리의 `HashMap`이 1.36부터 이 구현을 써요[4]. 설계의 중심은 칸마다 1바이트의 메타데이터(제어 바이트)를 칸 배열과 따로 빽빽하게 두고, 그것을 SIMD로 한꺼번에 훑는 데 있어요.

설계 노트[1]와 `raw_hash_set.h`[2]가 설명하는 구조는 이래요.

- 해시를 둘로 나눠요. 64비트 해시를 H1(57비트)과 H2(나머지 7비트)로 나눠요. H1은 테이블 안의 위치(probe 시작점)를 고르고, H2는 칸의 제어 바이트에 저장해요.
- 제어 바이트는 1바이트예요. 최상위 1비트가 "제어 비트"이고 나머지 7비트가 H2예요. 찬 칸은 제어 비트가 0이고 H2를 담아요(0x00–0x7F). 특수 값으로 빈 칸(`kEmpty` = 0x80), 지운 칸(`kDeleted` = 0xFE, 툼스톤), 배열 끝 표시(`kSentinel` = 0xFF)가 있어요(`hashtable_control_bytes.h`[2]).
- 그룹 단위로 찾아요. 찾기는 H1으로 시작 위치를 정하고, 거기서 16바이트(그룹)의 제어 바이트를 SSE2 레지스터에 올려 H2와 한 번에 비교해요. 결과를 `_mm_movemask_epi8`로 16비트 마스크로 바꾸면, 1인 비트가 "H2가 같은 칸", 곧 후보예요. 후보만 실제 키와 비교해요. 그룹에 빈 칸이 있으면 거기서 "없음"이에요. 지운 칸은 probe를 멈추지 않아요.
- probe 순서는 그룹 단위의 삼각수 수열이에요. $p(i) = \text{Width} \cdot \tfrac{i^2 + i}{2} + \text{hash} \pmod{\text{capacity}+1}$이에요. 그룹 수가 2의 거듭제곱이면 모든 그룹을 정확히 한 번씩 지나요(`raw_hash_set.h`의 `probe_seq`[2]).
- 그룹은 아무 칸에서나 시작할 수 있어요. 그래서 끝 근처에서 16바이트를 읽어도 넘치지 않도록 제어 바이트 배열의 앞 15바이트를 끝에 복제해 둬요(`clones[kWidth - 1]`[2]).
- 최대 적재율은 7/8이에요(그룹 하나보다 큰 테이블)[2]. 16칸 그룹이면 평균 두 칸이 비어 있어요.

`raw_hash_set.h`의 주석은 거짓 후보가 드물다는 점도 계산해요[2]. H2가 무작위 7비트라면 다른 키의 H2가 우연히 같을 확률은 $1/128$이에요. probe 순서에서 확인해야 하는 "틀린" 칸이 $k$개면 키 비교가 헛도는 횟수의 기댓값은 $k/128$이고, 측정과 분석으로 보면 높은 적재율에서도 $k$가 32보다 작아 찾기 한 번에 헛비교가 1/8번 미만이에요.

이 설계는 linear probing의 문제를 이렇게 풀어요. "이 칸인가, 다음 칸인가"를 칸마다 분기로 묻는 대신, 16칸의 질문을 비교 명령 하나로 동시에 묻고 결과를 비트 마스크로 받아요. 남는 분기는 "후보가 있나"와 "빈 칸이 있나" 둘뿐인데, 둘 다 거의 언제나 같은 쪽으로 가요. 키가 이미 테이블에 있으면 첫 그룹에 후보가 있고(거의 언제나 진짜), 없으면 첫 그룹에 빈 칸이 있어요.

<Callout title="지금의 Abseil 소스">
설계 노트는 H2를 "나머지 7비트"라고 적지만, 지금의 `raw_hash_set.h`는 H2를 해시의 위쪽 7비트(`hash >> 57`)로, H1을 해시 전체(용량으로 마스크)로 써요. hashbrown도 위쪽 7비트(`Tag::full`)예요. stardust는 아래쪽 7비트를 써요. 이유는 아래 [비트의 쓰임](#해시-비트의-쓰임)에 있어요.

### stardust의 테이블: 칸과 제어 바이트

stardust의 `SwissTable`은 메모리 두 덩어리예요.

- **제어 바이트** `ctrl_`: 칸마다 1바이트. `calloc`으로 할당해요.
- **칸** `slots_`: 칸마다 `{word, code}` 16바이트. `malloc`으로 할당하고 초기화하지 않아요.

칸 수는 32 이상의 2의 거듭제곱이고, 16칸씩 그룹이에요. 그룹 $g$의 칸은 $16g, \dots, 16g+15$예요. 해시 $h$에서 두 값을 뽑아요.

- **태그** `tag = 0x80 | (h & 0x7f)`: 아래 7비트에 최상위 비트 1을 붙인 값. 찬 칸의 제어 바이트예요.
- **시작 그룹** `g = (h >> 7) & (그룹 수 - 1)`: 태그 바로 위의 비트들.

빈 칸의 제어 바이트는 0이에요. 찬 칸은 언제나 최상위 비트가 1이라(0x80–0xFF) 0과 겹치지 않아요. 지운 칸과 끝 표시는 없어요. stardust의 테이블은 지우는 연산이 없고(factorize는 넣기만 해요), 반복자도 없기 때문이에요.

칸의 `word`는 8바이트 키면 키 자체, 문자열이면 키의 해시예요. `code`는 키의 코드예요.

- 8바이트 키는 칸만 읽고 비교가 끝나요. 키를 찾으러 다른 메모리에 가지 않아요.
- 문자열은 먼저 칸의 해시를 비교하고, 64비트 해시까지 같을 때만 `keys_[code]`(코드로 찾는 `string_view` 배열)로 실제 문자열을 꺼내 비교해요. 해시가 다른 문자열은 바이트를 한 번도 읽지 않아요. 테이블이 자랄 때도 칸의 해시를 그대로 쓰므로 문자열을 다시 해시하지 않아요.

아래는 32칸(그룹 2개) 테이블에 int64 키 `42, 7, 3, 42, 10, 1, 7, 20, 30, 2`를 차례로 넣은 결과예요. 해시는 실제 `Fmix64` 값이에요. 예를 들어 `fmix64(42) = 0x810879608E4259CC`의 아래 7비트는 `0x4C`라서 태그는 `0xCC`이고, 그 위 비트(비트 7)가 1이라 그룹 1로 가요.

### 빈 칸이 0인 이유: calloc

Abseil에서 빈 칸은 0x80이라, 새 제어 바이트 배열은 그 값으로 채워야 해요(예: 키울 때 `memset(..., kEmpty, ...)`). stardust는 빈 칸을 0으로 정해서 `calloc`이 돌려준 0으로 된 메모리가 곧 빈 테이블이에요.

이 선택의 효과는 큰 할당에서 드러나요. 운영체제는 새로 매핑한 페이지를 처음 건드릴 때 0으로 채워 줘요. 그래서 큰 `calloc`은 메모리를 따로 지우지 않아도 되고, 실제로 읽거나 쓴 페이지만 물리 메모리를 차지해요. 칸 배열은 `malloc`이라 초기화하지 않고, 제어 바이트가 "찼다"고 할 때만 읽어요. 결과적으로 테이블을 크게 잡아도, 실제 비용은 키가 들어간 페이지의 수에 비례해요. 아래 [미리 잡기](#테이블을-미리-잡기)는 이 성질에 기대요.

테이블은 만들 때 메모리를 잡지 않아요. 기본 생성자는 빈 포인터로 시작하고, 처음 `reserve`나 `insert`에서야 할당해요. 병렬 경로는 파티션 256개의 테이블을 먼저 만들고 각각 `reserve`하는데, 만들 때 32칸을 잡으면 곧바로 버리고 다시 잡게 되어 파티션마다 할당이 두 번씩 생겨요.

### NEON으로 16칸을 한 번에 비교하기

x86의 SSE2에는 16바이트 비교 결과(바이트마다 0x00 또는 0xFF)를 16비트 정수로 모으는 `movemask`(`_mm_movemask_epi8`)가 있어요. Arm의 NEON에는 그런 명령이 없어요. stardust는 `vshrn_n_u16`(shift right and narrow)으로 같은 역할을 해요. 이 기법은 Kutenin의 글[5]이 정리한 것이고, 그 글에 따르면 Zstandard의 NEON 경로가 이 방법을 써요.

```cpp
// csrc/frame/ops/hash.hpp, SwissTable (줄인 발췌)
// 16바이트 비교 결과 → 64비트 마스크, 바이트마다 4비트(니블)
static std::uint64_t nibbles(uint8x16_t cmp) {
    return vget_lane_u64(vreinterpret_u64_u8(vshrn_n_u16(vreinterpretq_u16_u8(cmp), 4)), 0);
}
// 가장 낮은 니블 하나(4비트)를 지운다
static std::uint64_t clear_nibble(std::uint64_t m) {
    return m & ~(std::uint64_t{0xF} << (__builtin_ctzll(m) & ~3u));
}
```

`nibbles`가 하는 일을 단계로 나누면 이래요.

1. `vceqq_u8(ctrl, vdupq_n_u8(tag))`: 16바이트를 태그와 비교해요. 같은 바이트는 0xFF, 다른 바이트는 0x00이에요.
2. `vreinterpretq_u16_u8`: 같은 128비트를 16비트 레인 8개로 봐요. 레인 $j$는 바이트 $2j$(아래 8비트)와 $2j+1$(위 8비트)이에요(리틀 엔디언).
3. `vshrn_n_u16(…, 4)`: 레인마다 오른쪽으로 4비트 밀고 아래 8비트만 남겨요. 남는 8비트는 바이트 $2j$의 위 니블과 바이트 $2j+1$의 아래 니블이에요. 비교 결과 바이트는 0x00 아니면 0xFF라서, 위 니블이든 아래 니블이든 그 바이트의 결과(0 또는 F)를 그대로 담아요.
4. 결과 8바이트를 `uint64_t` 하나로 읽어요. 바이트 $i$의 결과가 비트 $4i..4i+3$에 놓여요.

그다음은 정수 연산이에요. `__builtin_ctzll(m)`(낮은 쪽 0비트의 수)을 4로 나누면(`>> 2`) 첫 후보 칸의 번호예요. 기본 AArch64 명령어에는 ctz가 없어서 컴파일러가 `rbit`(비트 뒤집기) + `clz`(높은 쪽 0비트 세기) 두 명령으로 만들어요[5]. 다음 후보로 넘어갈 때는 그 니블 4비트를 통째로 지워요(`clear_nibble`). `m & (m - 1)`로 가장 낮은 비트 하나만 지우면 같은 칸의 나머지 3비트가 남아 같은 후보를 네 번 보게 돼요.

빈 칸 검사는 `vceqzq_u8(ctrl)`이에요. "0과 같은가"는 AArch64에 즉시값 0과 비교하는 명령(`cmeq #0`)이 있어서, 비교할 상수를 레지스터에 올릴 필요가 없어요. 빈 칸을 0으로 정한 덕을 여기서도 봐요.

### 찾기와 넣기

```cpp
// csrc/frame/ops/hash.hpp, SwissTable::insert (줄인 발췌)
std::pair<std::int64_t, bool> insert(Key k, std::uint64_t h, std::int64_t new_code) {
    if (!ctrl_) [[unlikely]] allocate(32);
    const std::uint8_t tag = 0x80 | (h & 0x7f);
    for (std::uint64_t g = (h >> 7) & gmask_;; g = (g + 1) & gmask_) {     // 그룹을 차례로
        const uint8x16_t ctrl = vld1q_u8(ctrl_.get() + g * 16);             // 제어 바이트 16개
        for (std::uint64_t m = nibbles(vceqq_u8(ctrl, vdupq_n_u8(tag))); m; m = clear_nibble(m)) {
            const Slot& e = slots_[g * 16 + (__builtin_ctzll(m) >> 2)];     // 태그가 같은 칸
            if (matches(e, k, h)) return {e.code, false};                   // 있던 키
        }
        const std::uint64_t empty = nibbles(vceqzq_u8(ctrl));
        if (empty) {                                                        // 없는 키: 첫 빈 칸에 넣는다
            const std::uint64_t at = g * 16 + (__builtin_ctzll(empty) >> 2);
            ctrl_[at] = tag;
            slots_[at] = Slot{word_of(k, h), new_code};
            if (++size_ * 8 > capacity() * 7) grow();                       // 7/8을 넘으면 두 배로
            return {new_code, true};
        }
    }
}
```

`find`는 같은 루프에서 넣는 부분 대신 `return -1`이에요. 루프 하나에 분기는 셋이에요.

- 후보 루프(`m != 0`): 키 1,000종에 1M 행처럼 대부분의 행이 이미 있는 키면, 첫 그룹에 진짜 후보가 하나 있고 첫 비교에서 끝나요. 헛후보는 칸마다 $1/128$의 확률이에요.
- `matches`: 거의 언제나 참이에요.
- 빈 칸(`empty != 0`): 없는 키를 넣거나 찾을 때 거의 언제나 첫 그룹에서 참이에요.

세 분기 모두 한쪽으로 치우쳐 있어서 예측이 거의 틀리지 않아요. 남은 의존 사슬(키 → 해시 → 제어 바이트 16개 → 비교 → 칸 → 비교)은 같지만, 예측이 맞으니 CPU가 다음 행의 사슬을 미리 시작해 여러 행을 겹쳐 실행해요.

넣기 전에는 반드시 같은 그룹의 후보부터 봐요. 지우는 연산이 없으니 "어떤 키가 테이블에 있다면, 그 키는 probe 순서에서 처음으로 빈 칸이 있는 그룹 또는 그 앞의 그룹에 있다"가 언제나 성립해요. 키는 넣을 때 그 자리에 들어가고, 찬 칸은 다시 비지 않기 때문이에요. 그래서 빈 칸이 있는 그룹에서 멈춰도 놓치는 키가 없어요. 지우기가 있는 Abseil은 지운 칸을 빈 칸으로 되돌리면 이 성질이 깨지므로 툼스톤(`kDeleted`)을 두고, "그룹에 빈 칸이 있으면 그 그룹은 한 번도 꽉 찬 적이 없다"는 관찰로 일부 칸만 빈 칸으로 돌려요[2]. stardust는 이 장치가 모두 필요 없어요.

### 적재율 7/8과 키우기

키가 칸의 7/8을 넘으면 칸 수를 두 배로 늘리고(`grow`) 모든 키를 새 테이블에 다시 넣어요. 다시 넣을 때는 같은 키가 없다는 것을 아니까 후보 비교 없이 첫 빈 칸에 바로 넣어요. 8바이트 키는 칸의 `word`(키)를 다시 해시하고(곱셈 두 번), 문자열은 칸의 `word`가 이미 해시라 그대로 써요.

7/8이면 꽉 찬 셈인데도 괜찮은 이유는 태그가 키 비교를 걸러 주기 때문이에요. linear probing은 적재율이 오르면 칸마다 키 비교와 분기가 늘지만, Swiss table은 그룹 하나를 보는 비용이 칸 수와 무관하고 헛비교는 칸마다 $1/128$이에요. 7/8에서도 그룹 16칸에 평균 두 칸이 비어 있어서 없는 키는 대개 첫 그룹에서 끝나요.

7/8 상한은 테이블에 언제나 빈 칸이 있다는 뜻이기도 해요. 그래서 `for (g = …;; g = (g + 1) & gmask_)` 루프는 반드시 끝나요.

### Abseil, hashbrown과 다른 점

| | Abseil `raw_hash_set` | hashbrown | stardust `SwissTable` |
|---|---|---|---|
| 빈 칸 | 0x80 | 0xFF | **0x00** |
| 찬 칸 | 0x00–0x7F (H2) | 0x00–0x7F | 0x80–0xFF (`0x80 \| 태그`) |
| 지운 칸 / 끝 표시 | 0xFE / 0xFF | 0x80 / — | 없음 (지우기·반복자 없음) |
| 태그로 쓰는 비트 | 해시의 위 7비트 | 위 7비트 | **아래 7비트** |
| AArch64의 그룹 | 8칸 (64비트 NEON 비교) | 8칸 | **16칸** (128비트 비교 + `vshrn`) |
| 그룹의 시작 | 아무 칸 (끝에 제어 바이트 복제) | 아무 칸 (끝에 복제) | 16의 배수 |
| 그룹 사이 probe | 삼각수 수열 | 삼각수 수열 | 다음 그룹 (선형) |
| 칸 수 | $2^k - 1$ | $2^k$ | $2^k$, 32 이상 |
| 최대 적재율 | 7/8 | 7/8 | 7/8 |

- **AArch64의 그룹 크기.** Abseil은 x86에서는 16칸 그룹(`GroupSse2Impl`), AArch64 NEON에서는 8칸 그룹(`GroupAArch64Impl`)을 써요. 8바이트를 `vceq_u8`로 비교하면 결과가 그대로 64비트 정수(바이트마다 0x00/0xFF)가 되어 `vshrn`이 필요 없어요. hashbrown의 NEON 판도 8칸이에요(`src/control/group/neon.rs`의 `uint8x8_t`). Kutenin의 글[5]도 Abseil의 AArch64 판에 64비트 NEON 비교(8바이트 마스크)를 썼다고 적어요. stardust는 16칸 그룹을 `vshrn`으로 써요. 아래 측정은 Swiss table과 linear probing의 비교이고, 16칸 그룹과 8칸 그룹을 견준 측정은 아직 없어요.
- **그룹을 16의 배수에 맞춘 것.** 그룹이 항상 정렬된 자리에서 시작하므로 끝에 제어 바이트를 복제할 필요가 없고, 넣을 때 복제본을 함께 갱신하는 일도 없어요.
- **선형 그룹 probe.** 다음 그룹으로 차례로 가요. 테이블을 행 수만큼 미리 잡으면(아래) 적재율이 낮아 두 번째 그룹까지 가는 일이 드물어요.

### 측정: linear probing과 Swiss table

같은 조건(1M 행, 1스레드, Apple M4 Pro)에서 두 테이블을 비교한 값이에요.

| 1M 행 | linear probing | Swiss table |
|---|---:|---:|
| int `nunique`, 키 1,000종 | 4.29 ms | 2.03 ms |
| int `nunique`, 키 63만 종 | 21.5 ms | 15.2 ms |
| groupby int 1,000종 `sum` | 5.82 ms | 3.49 ms |

키가 적어 테이블이 L1에 있을 때 차이가 가장 커요(2.1배). 이때는 시간의 대부분이 분기 예측 실패였기 때문이에요. 키가 많으면 테이블이 캐시를 넘쳐 시간의 상당 부분이 캐시 미스라서 차이가 줄어요(1.4배). 키가 많은 경우를 더 빠르게 하는 방법은 아래 [병렬 factorize](#해시로-나눈-병렬-factorize)의 파티션이에요. 테이블을 캐시에 들어갈 만큼 작게 쪼개요.

## 해시 함수

### 무엇이 좋은 해시인가: avalanche

Swiss table은 해시의 아래 7비트를 태그로, 그 위 비트를 그룹으로 써요. 이 비트들이 키마다 고르게 퍼져야 해요. 태그가 몰리면 헛후보가 늘고, 그룹이 몰리면 한 그룹이 꽉 차서 probe가 길어져요.

해시 함수의 품질을 재는 기준이 **avalanche**(눈사태) 성질이에요. 입력의 비트 하나를 뒤집으면 출력의 각 비트가 1/2의 확률로 뒤집혀야 해요. 그러면 비슷한 키도 전혀 다른 해시를 받아요.

데이터프레임의 키는 무작위가 아니라서 이 성질이 특히 중요해요. 예를 들어 정수값을 가진 float64 키(`1.0, 2.0, 3.0, …`)는 비트로 보면 아래쪽 수십 비트가 모두 0이에요(`3.0` = `0x4008000000000000`). 해시 없이 비트를 그대로 쓰면 이런 키는 모두 태그가 같고 시작 그룹도 같아서, 한 그룹부터 차례로 채우며 키마다 긴 probe를 해요. 1000의 배수인 정수 ID, 초 단위를 밀리초로 바꾼 타임스탬프도 아래 비트가 몇 가지 값에 몰려요.

### 8바이트 키: fmix64

8바이트 키는 MurmurHash3의 마무리 함수 **fmix64**로 섞어요[6].

```cpp
// csrc/frame/ops/hash.hpp
struct Fmix64 {
    std::uint64_t operator()(std::uint64_t k) const {
        k ^= k >> 33;
        k *= 0xff51afd7ed558ccdULL;
        k ^= k >> 33;
        k *= 0xc4ceb9fe1a85ec53ULL;
        k ^= k >> 33;
        return k;
    }
};
```

smhasher 저장소의 `MurmurHash3.cpp`에 있는 `fmix64`와 상수까지 같아요. 두 연산이 번갈아 와요.

- **`k ^= k >> 33`**: 위쪽 31비트를 아래쪽으로 내려 섞어요. 곱셈은 아래 비트를 위로만 퍼뜨리므로(곱의 비트 $i$는 입력의 비트 $0..i$에만 달려요), 위 비트의 정보를 아래로 보내는 것은 이 시프트의 몫이에요.
- **`k *= 홀수 상수`**: 아래 비트를 위쪽 전체로 퍼뜨려요. 곱셈은 "상수의 1비트마다 $k$를 그만큼 밀어 더한 것"이라, $k$의 비트 하나가 그 위의 많은 비트에 영향을 줘요.

이 둘을 두 번 거치면 모든 입력 비트가 모든 출력 비트에 영향을 줘요. smhasher 위키는 두 곱셈 상수를 단순한 simulated annealing 탐색으로 찾았고, 그 결과 출력의 모든 비트가 0.25% 이내의 치우침으로 avalanche한다고 적어요[6]. 무작위 64비트 입력 1만 개에서 입력 한 비트를 뒤집으면 출력이 평균 31.9비트(이론값 32) 바뀌어요.

**fmix64는 전단사(bijection)예요.** `k ^= k >> 33`은 위 33비트를 바꾸지 않으므로 그것으로 아래 31비트를 복원할 수 있어 되돌릴 수 있고, 홀수 상수의 곱셈은 $2^{64}$을 법으로 역원이 있어요. 두 상수 모두 홀수예요(끝자리 `d`, `3`). 그래서 서로 다른 8바이트 키는 언제나 서로 다른 64비트 해시를 받아요. 한 가지 특이점은 `fmix64(0) = 0`이라는 것이에요. 키 0(과 `0.0`, False)은 태그 0x80, 그룹 0으로 가요. 키 하나의 자리일 뿐이라 문제가 되지 않아요.

비용은 곱셈 2번, 시프트 3번, XOR 3번이에요. 행마다 해시 하나가 테이블 조회의 의존 사슬 맨 앞에 놓이므로, 몇 사이클씩 걸리는 64비트 곱셈의 지연이 사슬에 그대로 더해져요.

### 문자열: HashBytes

```cpp
// csrc/frame/ops/hash.hpp, HashBytes
static std::uint64_t mum(std::uint64_t a, std::uint64_t b) {
    const unsigned __int128 r = static_cast<unsigned __int128>(a) * b;
    return static_cast<std::uint64_t>(r) ^ static_cast<std::uint64_t>(r >> 64);   // 128비트 곱의 두 반쪽을 XOR
}
std::uint64_t operator()(std::string_view s) const {
    constexpr std::uint64_t k0 = 0xa0761d6478bd642fULL, k1 = 0xe7037ed1a0b428dbULL;
    const char* p = s.data();
    std::size_t n = s.size();
    std::uint64_t h = k0 ^ (static_cast<std::uint64_t>(n) * k1);     // 길이를 섞어 시작
    for (; n >= 8; p += 8, n -= 8) {                                 // 8바이트씩
        std::uint64_t w;
        std::memcpy(&w, p, 8);
        h = mum(w ^ k1, h ^ k0);
    }
    if (n > 0) {                                                     // 남은 1–7바이트
        std::uint64_t w = 0;
        std::memcpy(&w, p, n);
        h = mum(w ^ k1, h ^ k0);
    }
    return Fmix64{}(h);                                              // 마무리
}
```

**mum: 128비트 곱의 두 반쪽을 XOR해요.** $64 \times 64 \to 128$비트 곱셈을 하고 위 64비트와 아래 64비트를 XOR해 64비트로 접어요. wyhash의 `_wymix`가 이것이에요(`_wymum`이 곱의 아래·위 반쪽을 돌려주고 `_wymix`가 둘을 XOR해요)[7]. foldhash는 같은 연산을 "folded multiply"라고 부르고 왜 섞이는지를 이렇게 설명해요[8]. 곱셈은 한 인자를 여러 칸 밀어 더한 것이라, 곱의 가운데 비트는 입력의 많은 비트에 달려 있지만 맨 아래와 맨 위 비트는 적은 비트에만 달려 있어요. 위 반쪽을 아래 반쪽에 접어 XOR하면 이 치우침이 서로 보완되어 출력의 모든 비트가 입력의 많은 비트에 달리게 돼요. 곱셈 한 번(AArch64에서는 아래 반쪽 `mul`과 위 반쪽 `umulh` 두 명령)에 8바이트를 섞어요.

나머지 부분은 이렇게 맞물려요.

- 비밀 상수와 XOR한 뒤 곱해요(`w ^ k1`, `h ^ k0`). 접은 곱은 한 인자가 0이면 결과가 0이라, 0인 단어(예: 0으로 채운 꼬리)가 상태를 지워 버려요. 상수와 XOR해 두면 입력 단어가 우연히 0이어도 곱하는 값은 0이 아니에요. foldhash도 모든 접은 곱을 `folded_multiply(input1 ^ secret1, input2 ^ secret2)` 꼴로 쓰는 이유를 같은 결함으로 설명해요[8].
- 상수 `k0 = 0xa0761d6478bd642f`, `k1 = 0xe7037ed1a0b428db`는 wyhash의 이전 판(`old_versions/`의 `wyhash_final1.h`, `wyhash_final2.h`, `wyhash_final4.h`)이 기본 비밀 값 `_wyp[0]`, `_wyp[1]`로 쓰던 상수예요[7]. 둘 다 홀수이고 1비트가 정확히 32개예요. wyhash의 현재 판은 다른 기본 상수를 쓰고, 비밀 값을 만드는 `make_secret`(바이트마다 1비트가 4개이고, 홀수이자 소수이며, 서로 32비트씩 다른 수)을 제공해요.
- 꼬리는 안전하게 읽어요. 남은 1–7바이트는 0으로 채운 `w`에 `memcpy`해요. 문자열 끝을 넘어 8바이트를 읽지 않아요. 컬럼의 마지막 문자열이 버퍼 끝에 붙어 있을 수 있어서예요.
- 길이를 섞어요. 꼬리를 0으로 채우므로 `"a"`와 `"a\0"`는 같은 단어 `0x61`을 만들어요. 시작 상태에 길이를 곱해 섞어(`k0 ^ n * k1`) 둘이 다른 해시를 받게 해요.
- 끝에 fmix64를 한 번 더 해요. Swiss table이 쓰는 아래 7비트(태그)와 그 위의 그룹 비트를 확실히 섞기 위해서예요.

wyhash 자체는 16바이트(또는 48바이트)씩 두 단어를 한 번에 접는 등 긴 문자열을 더 빠르게 처리하는 구조가 있어요. `HashBytes`는 그중 "mum으로 한 단어씩 상태에 접는" 중심 부분만 쓴 단순한 판이에요. 데이터프레임의 문자열 키는 대개 짧아서 이 정도로 충분해요.

바이트마다 곱셈 하나를 하는 FNV-1a(+ fmix64)와 비교하면, 1M 행, 키 10만 종의 string `nunique`(1스레드, Apple M4 Pro)가 FNV-1a로 16.6ms, mum으로 15.0ms예요. 10% 차이뿐인 이유는 문자열 factorize 시간의 대부분이 해시가 아니라 일치를 확인하는 키 비교(`memcmp`)와 메모리 접근에 있기 때문이에요.

<Callout title="해시에 씨앗이 없어요">
`Fmix64`와 `HashBytes`는 고정된 상수만 써요. 프로세스마다 무작위 씨앗(seed)을 섞지 않아요. 그래서 같은 입력은 언제나 같은 칸을 지나고, 시간도 실행마다 같아요. 대신 해시 충돌을 노리고 만든 입력(HashDoS)은 막지 못해요. 그런 입력에서도 결과(코드)는 언제나 같고 느려질 뿐이에요. 코드는 처음 나타난 순서로 매기므로 해시 값과 무관해요.
</Callout>

## 테이블을 미리 잡기

### 키워 가기의 비용

빈 테이블(32칸)에서 시작해 7/8마다 두 배로 키우면, 키 1,000개를 넣는 동안 6번 자라요. 자랄 때마다 모든 키를 다시 넣고, 새 메모리를 받아 처음 쓸 때마다 페이지 폴트가 나요. 프로파일로 보면 1만 행 groupby 시간의 25%, merge의 14%가 `grow()`예요.

### 행 수만큼 잡아요

행 수는 키 수의 상한이에요. 키가 행보다 많을 수는 없으니, 테이블을 행 수에 맞게 잡으면 한 번도 자라지 않아요. `reserve(n)`은 키 $n$개를 7/8 아래로 담는 가장 작은 칸 수를 잡아요.

```cpp
// csrc/frame/ops/hash.hpp, SwissTable::reserve
void reserve(std::int64_t n) {
    std::size_t slots = 32;
    while (static_cast<std::int64_t>(slots) * 7 < n * 8) slots *= 2;   // slots ≥ 8n/7
    if (slots > capacity()) allocate(slots);
}
```

`grow`는 `size * 8 > capacity * 7`일 때만 일어나는데, `reserve(n)` 뒤에는 $\text{capacity} \ge 8n/7$이라 키가 $n$개 이하인 동안 이 조건이 참이 될 수 없어요.

큰 테이블이 비싸지 않은 이유가 앞의 [calloc](#빈-칸이-0인-이유-calloc)이에요. 1M 행이면 $2^{21}$칸, 제어 바이트 2MB와 칸 32MB를 잡지만, 키가 1,000개뿐이면 키가 떨어진 페이지 수천 개 정도만 실제로 물리 메모리가 돼요.

직렬 경로(1스레드, 또는 행이 $2^{17}$ 미만)에서 잡는 크기를 바꿔 가며 잰 값이에요. 32칸에서 키워 가는 방식 대비 시간 비율이고, 1보다 작으면 빨라요(int64 키, Apple M4 Pro).

| 행 / 키 | $2^{16}$행까지만 잡기 | $2^{18}$행까지만 잡기 | 행 수만큼 잡기 |
|---|---:|---:|---:|
| 1천 / 1천 | 0.41 | 0.42 | 0.42 |
| 10만 / 10만 | 0.48 | 0.48 | 0.48 |
| 1M / 1천 | 0.85 | 0.92 | 0.97 |
| 1M / 10만 | 0.84 | 0.69 | 0.82 |
| 1M / 1M | 0.95 | 0.78 | **0.54** |

int 키는 행 수만큼 잡아도 키워 가기보다 느린 경우가 없고, 키가 많을수록(재해시가 많을수록) 이득이 커요. 큰 테이블의 페이지 비용은 1M / 1천 줄에 보여요. 키가 1,000개라 세 방식 모두 자라지 않는데, 행 수만큼 잡기(0.97)가 $2^{16}$행까지만 잡기(0.85)보다 느려요. 이 차이가 큰 테이블이 건드리는 페이지의 비용이에요. 그래서 8바이트 키는 행 수만큼 잡아요.

### 문자열은 2¹⁶행까지만

문자열은 사정이 달라요. 같은 측정이에요(ms).

| 행 / 키 | 키워 가기 | $2^{16}$행까지만 잡기 | 행 수만큼 잡기 |
|---|---:|---:|---:|
| 1M / 10만 | 12.1 | **11.5** | 15.3 |
| 1M / 1M | 34.8 | 34.9 | 33.2 |

행 수만큼 잡으면 1M 행, 키 10만 종에서 키워 가기보다 26% 느려요. 테이블이 32MB 칸 배열이 되고 키 10만 개가 그 위에 흩어져, 칸을 읽을 때마다 캐시 미스가 나요. 게다가 문자열은 태그와 해시가 맞은 뒤 `keys_[code]`로 키를 한 번 더 읽어야 해요. $2^{16}$행까지만 잡으면 어디서도 키워 가기보다 느리지 않아요. 그래서 문자열 키는 `min(n, 2^16)`행만큼 잡고, 그보다 키가 많으면 거기서부터 키워요.

이 기준들은 행 수와 dtype으로만 정해요. 키 수를 미리 세어 보거나 표본을 보는 일은 하지 않아요.

```cpp
// csrc/frame/ops/hash.hpp, Partitioned::build의 직렬 경로
table.reserve(kInline ? n : std::min<std::int64_t>(n, std::int64_t{1} << 16));
```

병렬 경로의 파티션은 dtype과 상관없이 파티션의 행 수만큼 잡아요. 1M 행이면 파티션 하나가 약 3,900행이라 테이블이 8,192칸(128KB)으로 작고, 문자열에서도 캐시를 넘치지 않아요.

## 다중 키

여러 컬럼을 함께 키로 쓸 때(행의 키가 값의 튜플일 때)는 `factorize_rows`가 컬럼 단위 factorize를 조합해요.

1. 컬럼마다 factorize해요. 컬럼 $j$의 코드는 $0..n_j-1$이에요.
2. 코드를 **혼합 기수**(mixed radix)로 합쳐요(`acc = acc × n_j + code_j`). 시계의 "시 × 60 + 분"과 같은 방식이에요. 서로 다른 튜플은 서로 다른 정수가 되고, 키 튜플 하나가 int64 하나가 돼요.
3. 곱이 $2^{62}$을 넘을 것 같으면, 그때까지 합친 `acc`를 먼저 factorize해서 실제로 나온 조합의 수로 좁혀요. 가능한 조합은 $\prod n_j$이지만 실제로 나오는 조합은 행 수 이하예요.
4. 마지막에 `acc`를 한 번 더 factorize해요. 코드가 빈틈없고 처음 나타난 순서를 따르게 돼요.

```cpp
// csrc/frame/ops/hash.cpp, factorize_rows (줄인 발췌)
Factorized acc = factorize(cols[0]);
std::int64_t acc_n = acc.ngroups;
for (std::size_t j = 1; j < cols.size(); ++j) {
    Factorized next = factorize(cols[j]);
    if (next.ngroups != 0 && acc_n > (std::int64_t{1} << 62) / next.ngroups) {
        acc = factorize(acc.codes);          // 넘칠 것 같다: 지금까지의 튜플을 빈틈없는 코드로
        acc_n = acc.ngroups;
    }
    // a[i] = a[i] * m + b[i]  (청크 병렬)
    acc_n *= next.ngroups;
}
return factorize(acc.codes);                 // 빈틈없고, 처음 나타난 순서
```

- 넘침 검사는 곱하기 전에 나눗셈으로 해요(`acc_n > 2^62 / n_j`). 곱한 뒤에 검사하면 이미 넘친 값을 보게 돼요.
- 마지막 factorize가 처음 나타난 순서를 만들어요. 혼합 기수 값의 크기 순서는 튜플의 사전식 순서이지 처음 나타난 순서가 아니에요. 그 값을 다시 factorize하면 행 순서로 처음 본 튜플부터 번호를 받아요.
- NA는 컬럼마다 하나의 코드라서, 튜플의 한 자리가 NA여도 같은 규칙으로 합쳐져요. `drop_duplicates`에서 NA끼리 같은 튜플이 되는 이유예요.
- 좁히는 단계도 테스트로 돌아가요. 각각 2,999종(소수)인 컬럼 7개를 만들면 $2999^7 > 2^{62}$이라 중간에 좁히기가 일어나요(`tests/frame/test_unique.py`).

혼합 기수 대신 튜플 자체를 해시하는 방법도 있어요(행마다 여러 컬럼의 값을 함께 해시해 테이블 하나에 넣기). 그러면 테이블의 키가 가변 길이 튜플이 되어 칸 구조와 비교가 복잡해지고, 컬럼 dtype 조합마다 다른 코드가 필요해요. 컬럼별 factorize + 정수 합치기는 모든 단계가 이미 있는 8바이트 키 경로를 그대로 써요.

merge의 다중 키도 같은 혼합 기수를 쓰지만, 오른쪽에 만든 테이블로 왼쪽을 조회하는 형태라서 좁히는 방법이 조금 달라요([merge와 concat](/internals/frame/merge-concat/)).

## 해시로 나눈 병렬 factorize

### 왜 해시로 나누나

factorize를 여러 스레드로 나누는 쉬운 방법은 행을 청크로 나눠 청크마다 테이블을 만들고 끝에 합치는 것이에요. 그런데 합치기는 키마다 "다른 청크에서 이미 본 키인가"를 다시 테이블에 물어야 해서, 키가 많으면 합치기가 결국 키 수만큼의 직렬 작업이 돼요.

stardust는 키를 해시로 나눠요. 해시의 위쪽 8비트로 키를 $P = 256$개 파티션 중 하나에 보내요. 같은 키는 같은 해시라서 언제나 같은 파티션에 가요. 그러면 파티션끼리는 키를 하나도 공유하지 않으니 합칠 것이 없어요. 파티션마다 독립적인 Swiss table을 만들면 끝이에요.

파티션은 테이블을 작게 만드는 효과도 있어요. 1M 행이면 파티션 하나가 약 3,900행이고 테이블이 8,192칸 × 16B = 128KB예요. 키 63만 종을 한 테이블에 넣으면 $2^{21}$칸 × 16B = 32MB라 probe마다 캐시 미스가 나요.

$P = 256$인 것은 다른 커널과 맞춘 값이에요. 기수 정렬의 한 자리(1바이트 = 256칸), 병렬 counting sort의 버킷 수와 같아요([groupby와 정렬](/internals/frame/groupby-sort/)). 1M 행이면 청크(16,384행)가 62개라 (청크 × 파티션) 카운터가 62 × 256개예요.

### 단계별로

**1단계: 해시와 개수.** 청크마다 `count[청크 × P + 파티션]`을 세요. 태스크는 자기 청크의 256칸만 쓰므로 원자 연산이 필요 없어요. 문자열은 여기서 구한 해시를 `hashes[i]`에 저장해 두고 다시 계산하지 않아요(문자열을 다시 해시하면 바이트를 다시 읽어요). 8바이트 키는 해시를 저장하지 않고 3, 4단계에서 다시 계산해요. fmix64 한 번은 몇 사이클이라 8바이트 × n 배열을 쓰고 읽는 것보다 싸요. NA 행은 세지 않고, 청크마다 첫 NA 행만 `FirstRow`에 내요. `FirstRow`는 여러 태스크가 낸 행 중 가장 작은 행을 남겨요([병렬화와 결정성](/internals/frame/parallel/)).

**2단계: 시작 위치.** (파티션 $p$, 청크 $c$)의 행이 놓일 자리를 정해요. 파티션 0의 청크 0, 청크 1, …, 그다음 파티션 1의 청크 0, …의 순서로 누적합이에요. 이 순서 덕분에 한 파티션 안에서 행이 원래 행 순서로 놓여요. 청크는 행 순서이고, 한 청크 안에서는 행을 차례로 흩뿌리니까요.

**3단계: 흩뿌리기.** 행마다 `Entry{word, row}` 16바이트를 자기 파티션 자리에 써요. `word`는 8바이트 키면 키, 문자열이면 해시예요. 그리고 `codes[i]`에 임시로 "행 i의 항목이 간 자리 j"를 적어 둬요(6단계에서 씀).

파티션이 행 번호로 키를 읽지 않고 (키, 행) 쌍 자체를 흩뿌리는 이유가 있어요. 파티션 하나의 행은 전체에 흩어져 있어서, 행 번호로 키와 해시를 읽으면 4단계의 읽기가 모두 무작위 접근이 돼요. 그렇게 읽으면 1스레드에서 직렬 factorize보다 2~4배 느려요(1M 행, 키 63만 종). 흩뿌려 두면 4단계는 파티션의 항목을 앞에서부터 차례로 읽어요. 흩뿌리기 자체도 쓰기 스트림이 파티션 256개로 나뉠 뿐 청크마다 순서대로 읽어요.

**4단계: 파티션마다 factorize.** 태스크 하나가 파티션 하나를 맡아요. 테이블을 파티션 행 수만큼 미리 잡아서 루프 안에 재해시도 할당도 없어요. 항목을 차례로 넣으며 지역 코드(파티션 안에서 처음 나타난 순서)를 항목의 `word` 자리에 덮어쓰고, 새 키면 그 행을 `firsts[p]`에 더해요. 파티션의 행이 원래 순서라서 `firsts[p]`는 정렬된 배열이에요. 문자열은 일치를 확인할 때 쓸 키를 `key_of(e.row)`로 가져와요. 항목의 행 번호는 파티션 안에서 증가하므로 이 읽기도 앞으로만 가요.

**5단계: 번호 다시 매기기.** 전역 코드의 정의는 "그 키의 첫 등장 행보다 앞선 첫 등장 행의 수"예요. 직렬 factorize의 코드가 정확히 이것이에요. 첫 등장 행은 모든 파티션의 `firsts[p]`에 나뉘어 있으니, 이들을 행 순서로 세면 돼요.

- 행 청크마다 태스크 하나예요. 태스크는 각 파티션의 `firsts[p]`에서 자기 청크 범위에 드는 조각을 가져와요. 조각 경계(`bound`)는 파티션마다 정렬된 `firsts[p]`를 한 번 훑으며 청크 경계 $C + 1$개를 계산해 둬요. 청크와 파티션마다 이진 탐색으로 경계를 찾는 방법(256 파티션 × 62 청크 × 3번)은 분기 예측 실패가 많아 1M 행, 키 63만 종에서 7ms가 들어요.
- 청크마다 첫 등장 행 수를 세어 누적합 `fstart`를 만들어요. 청크 $c$의 첫 코드가 `fstart[c]`예요.
- 청크 안에서는 길이 16,384의 `rank` 배열에 첫 등장 행을 1로 표시하고, 분기 없는 누적합으로 번호를 매겨요.

```cpp
// csrc/frame/ops/hash.hpp, Partitioned::build 5단계 (줄인 발췌)
std::int64_t g = fstart[chunk(lo)];
for (std::int64_t i = 0, len = hi - lo; i < len; ++i) {
    const std::int64_t is = rk[i];      // 첫 등장 행이면 1, 아니면 0
    g += is;
    rk[i] = g & -is;                    // 첫 등장 행: 코드 + 1, 아니면 0
}
```

`-is`는 `is`가 1이면 모든 비트가 1, 0이면 0이에요. 그래서 `g & -is`는 분기 없이 "첫 행이면 g, 아니면 0"이에요. 첫 등장 행은 키가 많으면 촘촘하고 무작위로 놓여서, `if (is)`로 쓰면 예측할 수 없는 분기가 돼요.

- 그다음 각 파티션 조각의 첫 행마다 `rank`에서 코드를 읽어 `global_[p][지역 코드]`와 `first[코드]`에 써요. 행마다 첫 등장 행 이진 탐색으로 순위를 찾는 방법(63만 × 20단계)보다 이 표시 배열이 훨씬 싸요.

태스크는 자기 청크의 자리에만 써요. `global_[p]`의 조각, `first`의 범위 `fstart[c]..fstart[c+1]`, `rank`가 모두 청크의 몫이라 두 스레드가 같은 캐시 라인에 쓰지 않아요. 모든 파티션이 공유 배열의 아무 곳에나 쓰면 거짓 공유(false sharing)로 캐시 라인이 코어 사이를 오가서, 10스레드가 1스레드의 3배밖에 빠르지 않아요(1M 행, 키 63만 종).

**6단계: 코드 쓰기.** 먼저 파티션마다 자기 항목의 지역 코드를 `global_[p]`로 전역 코드로 바꿔요(파티션 병렬, 순서대로 읽기). 그다음 행 청크마다 `codes[i] = entries[codes[i]].word`로 3단계에서 적어 둔 자리의 전역 코드를 읽어요. NA 행(3단계에서 -1)은 NA 코드를 받아요.

### 코드가 직렬과 같은 이유

1. 같은 키는 같은 해시라서 같은 파티션에 가요. 그래서 파티션 하나의 지역 코드가 그 키의 전부예요.
2. 파티션 안에서 행이 원래 순서라서, 파티션 안의 첫 등장 행이 그 키의 전체 첫 등장 행이에요.
3. 직렬 factorize의 코드는 정의상 "첫 등장 행의 행 순서 순위"예요. 5단계가 정확히 그 순위를 매겨요. NA도 첫 NA 행을 같은 순위 계산에 넣어요.

어느 단계도 스레드 일정에 따라 결과가 달라지지 않아요. 그래서 코드는 $P$와 스레드 수에 상관없이 직렬 factorize와 정확히 같아요. `tests/frame/test_threads.py`가 unique, nunique, value_counts, duplicated, groupby, merge, 라벨 조회를 1, 3, 기본 스레드 수에서 돌려 결과가 비트까지 같은지 확인하고, `drop_duplicates`가 Python의 `dict.fromkeys`(처음 나타난 순서)와 같은지도 확인해요.

### P = 256 또는 1

$P$는 행이 기준값($2^{17}$) 이상이고 풀을 쓸 수 있을 때(`parallel::available()`: 2스레드 이상, 태스크 밖, 풀이 다른 Python 스레드의 일로 바쁘지 않음) 256이고, 아니면 1이에요. $P = 1$이면 위의 여섯 단계 대신 처음의 직렬 루프 하나예요.

1스레드에서 나누지 않는 이유는 비용이에요. 여섯 단계는 직렬 한 번보다 메모리를 여러 번 지나요(해시, 흩뿌리기, 파티션 읽기, 번호 매기기, 코드 쓰기). 1M 행, 키 1,000종에서 1스레드로 여섯 단계를 돌면 4.5ms, 직렬 한 번은 2.0ms예요. 분할의 본질적 비용이라 1스레드는 직렬 경로를 써요. 코드가 같으니 경로를 스레드 수로 골라도 결과는 바뀌지 않아요. 결과가 나누는 방식에 따라 비트가 바뀌는 연산(float 합 등)은 이렇게 하지 못하고 길이로만 나눠요([병렬화와 결정성](/internals/frame/parallel/)).

키가 1,000종처럼 적으면 직렬 테이블도 L1에 들어가서 병렬의 이득이 작아요. 이득이 큰 것은 키가 많아 한 테이블이 캐시를 넘칠 때예요.

직렬 경로도 일이 기준값 이상이면 `Unlocked`로 GIL을 놓아서, 1스레드에서도 다른 Python 스레드가 돌아요.

### Polars는 어떻게 나누나

Polars 2.1.0의 polars-core에서 숫자 컬럼 하나의 행을 그룹으로 나누는 함수(`group_tuples`)도 해시로 파티션을 나눠요(`crates/polars-core/src/frame/group_by/hashing.rs`의 `group_by_threaded_slice`)[11]. 방식은 달라요.

- 파티션 수가 스레드 수예요(`_set_partition_size()` = rayon 스레드 수).
- 행을 흩뿌리지 않아요. 각 스레드가 모든 키를 훑으며 해시가 자기 파티션인 키만 자기 테이블(`PlHashMap`, hashbrown)에 넣어요. 소스 주석이 이 방식을 그대로 적어요.
- 파티션 번호는 `hash_to_partition(h, n) = (h × n) >> 64`(128비트 곱의 위쪽)이에요. 해시의 위쪽 비트로 고른다는 점은 stardust와 같아요.
- 결과의 그룹 순서는 파티션 순서로 이어 붙인 것이라 처음 나타난 순서가 아니에요. `sorted`를 요청하면 그룹을 첫 행으로 정렬해(`sort_unstable_by_key`) 처음 나타난 순서로 만들어요. 정렬이 한 번 더 들어요.

stardust는 키를 한 번만 읽어 흩뿌리고, 파티션을 스레드 수와 무관한 256개로 고정하고, 코드를 언제나 처음 나타난 순서로 다시 매겨요. Polars는 그 순서를 요청할 때만 정렬로 만들고, stardust는 정렬 없이 첫 등장 행의 순위로 만들어요.

## 조회: find_rows

factorize는 넣으면서 코드를 매기는 일이에요. 넣지 않고 찾기만 하는 곳이 두 군데 있어요.

- **merge의 probe:** 오른쪽 키로 테이블을 만들고(`ValueCodes`, build), 왼쪽 키는 찾기만 해요. 왼쪽 행의 코드는 오른쪽에서 같은 키의 코드, 없으면 -1이에요([merge와 concat](/internals/frame/merge-concat/)).
- **Index의 라벨 조회:** Index의 라벨로 만든 테이블(`LabelTable`)에서 찾을 라벨들의 코드를 얻어요([라벨, 조회, 선택](/internals/frame/labels/)).

두 테이블 모두 `Partitioned::build`로 만들어요. 그래서 크면 병렬로 만들어지고, 조회는 `Partitioned::find`예요. 해시의 위쪽 8비트로 파티션을 고르고, 그 파티션의 테이블에서 지역 코드를 찾고, `global_[p]`로 전역 코드로 바꿔요. 파티션이 하나면 테이블의 코드가 곧 전역 코드예요.

조회 루프가 `find_rows`예요.

```cpp
// csrc/frame/ops/hash.cpp, find_rows (줄인 발췌)
template <class Key, class Hash, class KeyOf>
void find_rows(const Partitioned<Key, Hash>& table, const Column& probe, KeyOf key_of,
               std::int64_t skip, std::int64_t* out) {
    const bool nulls = probe.null_count > 0;
    for_chunks(probe.length, [&](std::int64_t lo, std::int64_t hi) {
        const Partitioned<Key, Hash>& t = table;   // 태스크의 지역 변수로
        const KeyOf key = key_of;
        const std::int64_t s = skip;
        std::int64_t* o = out;
        if (!nulls) {
            for (std::int64_t i = lo; i < hi; ++i) {
                const std::int64_t c = t.find(key(i));
                o[i] = c - (c > s);                // NA 코드 보정, 분기 없이
            }
        } else {
            // 비트맵을 읽어 NA 행은 -1, 나머지는 위와 같다
        }
    }, 8);
}
```

- dtype과 NA 유무를 호출마다 한 번 고르고, 행 루프는 찾기와 저장뿐이에요. dtype은 호출하는 쪽(`ValueCodes::lookup`, `LabelTable::lookup`)이 `switch`로 한 번 골라 키 함수(람다)를 넘기고, 그 람다가 템플릿 인자라서 루프마다 따로 컴파일돼요. 행마다 "NA인가, 문자열인가, 어느 dtype인가"를 물으면, 1스레드 1M 행 merge 시간의 48%가 조회예요. 같은 조건에서 행마다 묻는 루프의 merge는 14.4ms, 호출마다 한 번 고르는 루프는 12.6ms예요.
- 읽는 포인터는 태스크의 지역 변수예요. 값 포인터, 비트맵, 문자열 offsets를 람다가 값으로 캡처해요(`string_keys`). 루프가 `o[i]`에 int64를 쓰는데, 키를 `Column`을 거쳐 읽으면 컴파일러는 그 쓰기가 `Column` 안의 포인터를 바꿨을 수도 있다고 보고 매번 다시 읽어요. 지역 변수에 둔 포인터는 그런 걱정이 없어요([원소별 연산과 리덕션](/internals/frame/elementwise/)의 앨리어싱).
- NA 코드 보정은 `c - (c > skip)`이에요. merge의 build 쪽은 NA 행에 -1을 주고, NA 코드보다 큰 코드를 하나씩 당겨 코드를 빈틈없이 유지해요. probe 쪽 결과에도 같은 보정이 필요한데, 찾지 못한 -1은 `skip`보다 작으니 그대로이고, `skip`보다 큰 코드만 1 줄어요. NA가 없으면 `skip`이 int64 최댓값이라 아무것도 바뀌지 않아요. 비교 결과(0 또는 1)를 빼므로 분기가 없어요.
- `for_chunks`의 `cost = 8`은 조회 한 번이 덧셈 한 번보다 몇 배 무겁다는 뜻이에요. 기준값을 그만큼 낮춰 더 작은 크기에서도 나눠요. 청크는 바꾸지 않아요.

merge를 "양쪽 키를 이어 붙여 함께 factorize"하는 방법과 build/probe의 비교, 행 순서 규칙은 [merge와 concat](/internals/frame/merge-concat/)에 있어요. Swiss table에서는 넣기와 찾기의 비용이 거의 같아서 두 방법의 시간이 측정 오차 안이었고, build/probe가 메모리를 덜 쓰고 코드가 단순해서 그쪽을 써요.

### 테이블 없이 찾는 곳: contains_key

`value in series`(Series의 값에 있는가)는 값 하나를 찾는 일이라 테이블을 만들지 않아요. `contains_key`가 같은 키 규칙(정수는 `==`, float은 `float_key`끼리 `==`, 문자열은 바이트 비교, NA는 NA와 같음)으로 컬럼을 청크마다 훑고, 하나라도 찾으면 원자 플래그를 세워 다른 청크도 일찍 멈춰요. 테이블을 만드는 비용($n$번 넣기)이 한 번 훑기($n$번 비교)보다 비싸기 때문이에요.

`nunique`는 factorize 한 번이 시간의 거의 전부라서 이 영역의 해시 성능을 가장 직접 보여 줘요. 1M 행에서 pandas 대비 배율은 키 1,000종 ⟦FBENCH "nunique int, 1k keys" 1M pandas/sd@1⟧배(1스레드), ⟦FBENCH "nunique int, 1k keys" 1M pandas/sd@10⟧배(10스레드), 키가 많을 때 ⟦FBENCH "nunique int, n keys" 1M pandas/sd@10⟧배, string ⟦FBENCH "nunique string" 1M pandas/sd@10⟧배예요. Polars(14스레드)와는 키가 많을 때 ⟦FBENCH "nunique int, n keys" 1M polars@14/sd@10⟧배, string ⟦FBENCH "nunique string" 1M polars@14/sd@10⟧배예요.

원인으로 알려진 것은 이래요.

- **pandas와의 차이.** pandas 3.1.1의 int64 테이블(khash)은 해시가 32비트(`key >> 33 ^ key ^ key << 11`)이고, 충돌하면 두 번째 해시(`murmur2_32to32(h) | 1`)만큼 건너뛰는 double hashing이에요. 칸이 찼는지는 칸마다 1비트의 플래그 배열에 따로 두고, 적재율 0.77에서 두 배로 늘려요(`khash.h`)[10]. 칸마다 "비었나, 키가 같나"를 분기로 묻는 구조라 위 linear probing과 같은 종류의 분기가 있어요. pandas가 문자열 객체 배열에 쓰는 `StringHashTable`은 Python 문자열 객체마다 UTF-8 포인터와 길이를 얻은 뒤(`PyUnicode_AsUTF8AndSize`) X31 해시(`h = h × 31 + 바이트`)로 테이블에 넣어요(`kh_strview`, `khash_python.h`). pyarrow가 없으면 pandas 3.1.1의 `str` dtype이 Python 객체로 저장되고(이 측정 환경이 그래요) 이 경로를 타요. stardust는 문자열이 이미 연속 바이트라 Python 객체를 거치지 않아요.
- **Polars와의 차이.** 구조에서 눈에 띄는 차이는 순서예요. stardust는 결과를 처음 나타난 순서로 다시 번호 매기는 단계(5, 6단계)를 늘 거치고, Polars는 그 순서를 기본으로 만들지 않아요. 키가 많은 줄에서 Polars가 빠르다면 이 단계가 그 차이에 들어가지만, 얼마를 차지하는지는 아직 재지 않았어요.

groupby와 merge의 시간은 factorize 뒤의 단계(행 모으기, 집계, 쌍 만들기)가 함께 들어가서 각 글에서 다뤄요([groupby와 정렬](/internals/frame/groupby-sort/), [merge와 concat](/internals/frame/merge-concat/)).

### 복잡도와 메모리

| 단계 | 시간 | 추가 메모리 |
|---|---|---|
| 직렬 factorize | $O(n)$ 기대값, 행마다 해시 1번 + 그룹 1개 비교 | 테이블: 칸마다 17B(제어 1B + 칸 16B), 8바이트 키는 $2^{\lceil \log_2 (8n/7) \rceil}$칸(최소 32). 쓴 페이지만 차지. 문자열은 `keys_` 16B × 키 수 |
| 병렬 factorize | $O(n)$, 메모리를 약 5번 지남 | `Entry` 16B × n, 문자열 해시 8B × n, 카운터 8B × 청크 × 256, 파티션 테이블 |
| 다중 키 ($k$ 컬럼) | 컬럼마다 factorize + 합치기 + 마지막 factorize | 코드 배열 8B × n |
| 조회 (`find_rows`) | 행마다 해시 1번 + 그룹 1개 비교 | 결과 8B × n |

결과(`codes`)는 언제나 행마다 int64 하나, 8B × n이에요. `nunique`처럼 개수만 필요한 기능도 이 배열을 만들어요. factorize 하나로 모든 기능을 받치는 구조의 대가예요.

## 정확성과 검증

factorize의 정답은 정의가 단순해서 Python으로 그대로 쓸 수 있어요. `tests/frame/test_unique.py`의 참조 구현은 Python `dict`예요. Python의 `dict`는 이미 `0.0`과 `-0.0`을 같은 키로 보니, NaN과 NA만 대신할 표지 객체로 바꿔 넣고 `seen.setdefault(key, len(seen))`로 처음 나타난 순서의 코드를 만들어요. hypothesis로 만든 무작위 컬럼(NaN, `-0.0`, NA, 중복이 섞인 int·float·string·bool, 여러 컬럼)에서 `duplicated`, `drop_duplicates`, `value_counts`, `nunique`가 이 참조와 같은지 확인해요. 같은 뜻이 있는 경우(nullable dtype의 int와 문자열)는 pandas와도 비교해요.

경계 경우도 따로 있어요.

- 다중 키의 좁히기: 2,999종 컬럼 7개($2999^7 > 2^{62}$).
- 테이블이 자라는 경우: 20만 행, 키 10만 3종(`test_large_column_grows_the_table`).
- 스레드 수 불변성: 같은 연산을 1, 3, 기본 스레드 수로 돌려 값의 비트, 행 순서, 에러 메시지가 같은지(`tests/frame/test_threads.py`). 병렬 경로를 타도록 기준값보다 큰 입력을 써요.
