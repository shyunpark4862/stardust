## 한눈에 보기

이 글은 행의 **순서**와 **묶음**을 다루는 두 기능의 안쪽을 설명해요.

- [`groupby`](/api/frame/groupby/)와 그 집계(`sum`, `mean`, `min`, `first`, `size`, `agg` …)
- [`sort_values`](/api/frame/sort_values/), [`sort_index`](/api/frame/sort_index/), 그리고 groupby 결과의 그룹 순서(`sort=True`)와 [`unique_values`](/api/frame/unique_values/)의 순서

둘은 같은 부품 몇 개를 나눠 써요.

| 부품 | 하는 일 | 파일 |

| factorize | 값마다 "처음 나타난 순서"의 정수 코드를 줘요. 같은 키의 규칙(NaN끼리 같음, `-0.0 == 0.0`)이 여기 한 곳에 있어요 | `csrc/frame/ops/hash.cpp` ([해시 테이블과 factorize](/internals/frame/hashing/)) |
| `counting_sort` | 위치 0..n-1을 0..K-1 범위의 정수 키로 안정 정렬해, 키마다 위치 목록(CSR)을 만들어요 | `csrc/frame/ops/radix.hpp` |
| `radix_key` | 값을 "값의 순서 = 부호 없는 정수의 순서"인 64비트 키로 바꿔요 | `csrc/frame/ops/radix.hpp` |
| `radix_sort` | 64비트 키로 LSD 기수 정렬을 해요. 키를 한 번 훑어 필요한 패스만, 낮은 자리부터 | `csrc/frame/ops/radix.hpp` |
| `order_rows` | 한 컬럼의 값들을 오름차순으로 늘어놓아요. 문자열은 8바이트 접두사로 기수 정렬한 뒤, 접두사가 같은 구간을 다음 8바이트로 다시 기수 정렬하거나 짧으면 비교 정렬해요 | `csrc/frame/ops/radix.hpp` |
| `Groups` | 행을 그룹별로 모으고 그룹마다 집계해요 | `csrc/frame/ops/groupby.cpp` |
| `sort_groups` | 그룹을 키 값의 순서로 늘어놓아요 | `csrc/frame/ops/groupby.cpp` |
| `argsort` | 여러 키, 키마다 방향과 NA 위치로 행의 순서를 구해요 | `csrc/frame/ops/sort.cpp` |

이 글의 핵심 아이디어는 다섯 가지예요.

- **groupby는 "모아서 집계"예요.** 키를 factorize해 행마다 그룹 번호를 얻고, counting sort로 같은 그룹의 행을 원래 순서대로 한곳에 모은 뒤(키로 이미 묶인 컬럼이면 그룹이 행의 구간이라 옮기지 않아요), 그룹마다 컬럼 리덕션과 같은 함수로 집계해요. 그래서 그룹의 합은 그 그룹의 행만 골라낸 Series의 `sum()`과 비트까지 같아요.
- **값의 순서는 64비트 정수 하나로 바꿔서 정해요.** int64는 부호 비트를, float64는 비트 전체나 부호 비트를 뒤집으면 부호 없는 정수의 크기 순서가 값의 순서가 돼요. 내림차순은 키의 모든 비트를 뒤집는 것으로 끝나고, 같은 값의 순서(안정성)는 그대로 지켜져요.
- **정렬은 비교하지 않는 LSD 기수 정렬이에요.** 낮은 자리부터 안정적으로 나눠 담아요. 먼저 키를 한 번 훑어, 이미 정렬된 키는 옮기지 않고, 역순이면 같은 값의 묶음째 뒤집고, 그 밖에는 키가 서로 다른 비트만 정렬해요. 어느 길이든 결과는 같은 안정 정렬이에요.
- **문자열은 고유값의 순위로 바꿔요.** 고유값만 8바이트씩 기수 정렬해 내려가며(접두사가 같은 구간은 다음 8바이트로, 짧은 구간은 비교로) 순위를 매긴 뒤, 행은 그 순위로 정렬해요.
- **나눠서 병렬로 해도 결과는 직렬과 같아요.** 병렬 기수 정렬과 병렬 counting sort는 원소가 놓이는 자리가 직렬 정렬과 정확히 같아요. 그래서 스레드를 쓸 수 없을 때는 더 단순한 직렬 정렬로 바꿔도 결과가 같아요.

## groupby: 모아서 집계하기

### 세 단계

예를 들어 키 컬럼 `k`가 `["b", "a", "b", NA]`, 값 컬럼 `v`가 `[1.0, 2.0, 3.0, 4.0]`이라고 해 볼게요.

1. **factorize:** 키 컬럼을 factorize해서 행마다 그룹 코드를 얻어요. 코드는 처음 나타난 순서라 `b`가 0, `a`가 1, NA가 2예요. 키가 여러 개면 키마다 factorize한 코드를 혼합 기수로 합쳐 다시 factorize해요. 해시 테이블과 그 규칙은 [해시 테이블과 factorize](/internals/frame/hashing/)에 있어요.
2. **행 모으기:** `Groups`가 행 위치 0..n-1을 코드로 안정 counting sort해요. 결과는 CSR(compressed sparse row) 모양의 두 배열이에요. 그룹 $g$의 행은 `rows[start[g] : start[g+1]]`이고, 그룹 안에서는 원래 행 순서예요. 코드가 0에서 시작해 내려가지 않고 1씩만 오르면(0, 0, 1, 1, 1, 2, …: 키로 이미 묶이거나 정렬된 컬럼) 그룹마다 행이 한 구간이라, 구간의 경계 `start`만 찾고 `rows`는 만들지 않아요(행 $j$는 $j$예요).
3. **그룹마다 집계:** 그룹의 행을 그 순서대로 읽어 컬럼 리덕션과 같은 함수로 집계해요. 결과는 그룹 하나에 한 칸인 Column이고, 코드 순서예요.

마지막으로 Python 층(`_groupby.py`)이 그룹 순서를 정해요. `sort=False`면 코드 순서 그대로, `sort=True`(기본값)면 [그룹 순서](#그룹-순서)에서 설명할 `sort_groups`의 순서예요. `dropna=True`(기본값)면 키에 NA가 있는 그룹을 순서에서 빼요. 결과 컬럼마다 이 순서로 `take`하고, 키 컬럼(그룹마다 처음 나온 행의 값)을 앞에 붙여 RangeIndex의 DataFrame을 만들어요.

```python
>>> df = sd.frame.DataFrame({"k": ["b", "a", "b", None], "v": [1.0, 2.0, 3.0, 4.0]})
>>> df.groupby("k").sum()
   k    v
0  a  2.0
1  b  4.0
>>> df.groupby("k", sort=False, dropna=False).sum()
      k    v
0     b  4.0
1     a  2.0
2  <NA>  4.0
```

이 세 단계(코드, 행 배치, 그룹 순서)는 `_Grouping` 객체에 한 번만 계산해 두고, 같은 groupby에서 나온 집계(`g.sum()`, `g["v"].mean()`, `g.agg(...)`)가 함께 써요. 처음 집계할 때 계산하므로 `df.groupby("k")`만 부르면 인자 검사 말고는 계산하지 않아요. 대신 groupby를 만들 때 컬럼 사전을 얕게 복사해 둬요. 그 뒤에 `df["k"] = ...`로 컬럼을 바꿔도 groupby는 만들 때의 컬럼을 봐요. Column은 버퍼를 공유하는 값이라 이 복사는 데이터를 복사하지 않고, 행에 대입하면 Copy-on-Write로 버퍼가 먼저 복사되니 그 대입도 보이지 않아요([컬럼과 메모리](/internals/frame/columns/)).

`GroupBy`는 그룹을 하나씩 꺼내는 반복을 지원하지 않아요. 그런데 `g["v"]`처럼 `__getitem__`이 있는 클래스는 `__iter__`가 없어도 Python이 `g[0]`, `g[1]`, …을 차례로 부르는 옛 반복 규약으로 `for`를 돌려요. 그러면 `list(g)`가 `g[0]`의 에러(`column names must be str, not int`)로 끝나서, 반복이 안 된다는 것을 알려 주지 못해요. 그래서 클래스에 `__iter__ = None`을 둬요. 이렇게 하면 Python이 반복할 수 없는 객체로 보고 `TypeError: 'GroupBy' object is not iterable`을 내요.

### counting sort로 행 모으기

**직관.** 학생 답안지를 반별로 나누는 일을 생각해 보세요. 먼저 반마다 몇 장인지 세면, 1반이 0번 칸부터, 2반이 (1반 장수)번 칸부터 … 하는 식으로 각 반이 놓일 자리를 미리 알 수 있어요. 그다음 답안지를 처음부터 한 장씩 집어 자기 반의 다음 빈칸에 꽂으면 끝이에요. 같은 반 안에서는 집은 순서대로 꽂히니 원래 순서가 그대로 남아요. 이것이 **counting sort**(계수 정렬, Knuth의 "distribution counting")예요[1][2].

**정의.** 키 $c_i \in [0, K)$인 위치 $i = 0, \dots, n-1$을 정렬해요.

1. **세기:** $\text{cnt}_k = |\{ i : c_i = k \}|$
2. **누적합:** $\text{start}_k = \sum_{k' < k} \text{cnt}_{k'}$, $\text{start}_K = n$
3. **놓기:** $i = 0, 1, \dots$ 차례로 `rows[fill[c_i]++] = i` (`fill`은 `start`의 복사본)

시간은 $O(n + K)$이고 비교가 없어요. 3단계가 $i$를 증가하는 순서로 놓으므로 같은 키끼리는 원래 순서를 지켜요. 이 성질을 **안정성**이라고 해요.

직렬 코드는 이 정의를 그대로 옮긴 루프 셋이에요.

```cpp
// csrc/frame/ops/radix.hpp
for (std::int64_t i = 0; i < n; ++i) ++start[static_cast<std::size_t>(key[i]) + 1];
for (std::int64_t k = 0; k < nkeys; ++k)
    start[static_cast<std::size_t>(k) + 1] += start[static_cast<std::size_t>(k)];
std::vector<std::int64_t> fill(start.begin(), start.end() - 1);
for (std::int64_t i = 0; i < n; ++i)
    perm[static_cast<std::size_t>(fill[static_cast<std::size_t>(key[i])]++)] = i;
```

세기를 `start[key + 1]`에 하는 것은 누적합을 제자리에서 하기 위한 요령이에요. 누적합이 끝나면 `start[k]`가 바로 그룹 $k$보다 앞선 행의 수, 즉 그룹 $k$의 첫 칸이 돼요.

그룹 코드는 factorize가 0부터 빈틈없이 매기므로 $K$가 그룹 수예요. 그래서 counting sort가 딱 맞아요. 값의 범위가 아무리 넓어도(예: int64 키 63만 종) 코드는 0..63만-1이에요.

### 왜 행을 모으나

그룹 집계를 하는 가장 흔한 방법은 모으지 않고 흩뿌리는 것이에요. 그룹마다 누산기를 하나씩 두고, 행을 원래 순서로 한 번 훑으며 `acc[code[i]] += v[i]`를 해요. pandas 3.1.1이 이렇게 해요. `pandas/_libs/groupby.pyx`의 `group_sum`은 행 $i$를 0부터 $N-1$까지 돌며 `labels[i]`가 가리키는 그룹의 누산기에 값을 더하고, float이면 그룹마다 보정항을 함께 두는 Kahan 보정 합[3]을 써요[4].

stardust가 행을 먼저 모으는 이유는 세 가지예요.

- 그룹 합이 Series의 합과 같아져요. float 합은 더하는 순서와 묶는 모양에 따라 마지막 비트가 달라져요. stardust의 컬럼 합은 numpy와 같은 pairwise 합이에요([리덕션](/internals/frame/elementwise/), [배열의 리덕션](/internals/array/reductions/)). pairwise 합은 값을 한 줄로 늘어놓고 반씩 나눈 트리 모양으로 더해요. 흩뿌리기 방식에서는 그룹의 값이 한 줄로 모이지 않으니 이 트리를 만들 수 없고, 그룹마다 처음부터 차례로 더하는 합(또는 Kahan 합)이 돼요. 모으면 그룹의 값이 한 줄이 되니 컬럼 합과 똑같은 함수를 부를 수 있어요.
- 그룹마다 독립인 일이 돼요. 그룹 단위로 태스크를 나누면 태스크끼리 공유하는 누산기가 없어요. 흩뿌리기 방식을 병렬로 하려면 스레드마다 누산기를 따로 두고 끝에 합쳐야 하는데, 그러면 합치는 순서가 더하는 순서를 바꿔요.
- min, max, first, last, var도 같은 틀이에요. 그룹의 행이 한 줄로 있으니 "그 행들로 컬럼 리덕션을 하는 것"이 모든 집계의 정의가 돼요.

대가는 행 위치 배열 하나(`rows`, 8바이트 × n, 1M 행이면 8MB)를 더 쓰고, 집계할 때 값을 `v[rows[j]]`처럼 간접으로 읽는 것이에요. 행 위치가 그룹 안에서 증가하는 순서라 그룹이 크면 거의 순서대로 읽지만, 그룹이 많고 작으면 무작위 읽기에 가까워요.

### 그룹 합이 Series의 합과 비트까지 같은 이유

그룹 $g$의 합은 이렇게 계산해요.

```cpp
            // csrc/frame/ops/groupby.cpp
            if (is_sum) {
                if (vf) {  // NA rows hold 0: the sum of the group's rows, as the column sum
                    od[g] = float_sum(n, [vf, b, row](std::int64_t k) { return vf[row(b + k)]; });
```

`b`는 그룹의 첫 칸(`start[g]`), `n`은 그룹의 행 수예요. `row(j)`는 행 배치의 $j$번째 행이에요. counting sort로 모았으면 `rows[j]`, 그룹이 구간이면 $j$ 자신이에요. 어느 쪽인지는 그룹 루프 밖에서 템플릿 인자(`Indirect`, `Identity`)로 골라서, 집계 루프 안에 그 분기가 없어요.

`float_sum`(`csrc/frame/ops/pairwise.hpp`)은 컬럼의 `sum()`이 부르는 바로 그 함수예요. 받는 것은 개수 `n`과 "k번째 값을 주는 함수" `get`뿐이에요. 합의 비트를 정하는 것은 두 가지예요.

1. **어떤 값이 어떤 순서로 들어오는가.** 그룹 합의 $k$번째 값은 그룹의 $k$번째 행의 값이고, counting sort가 안정이라 그 행들은 원래 순서예요. `df[df["k"] == 키]["v"]`로 골라낸 Series도 같은 행을 같은 순서로 담아요. NA 행은 두 쪽 모두 값 자리에 0.0을 담고 있어 함께 더해져요([컬럼과 메모리](/internals/frame/columns/): NA 자리의 값은 0). 0.0을 더해도 합은 바뀌지 않으니 분기 없이 함께 더해요.
2. **트리 모양.** pairwise 트리는 개수 $n$만으로 정해져요. $n < 16$이면 0.0부터 차례로, $n \le 512$이면 누산기 16개, 그보다 크면 16의 배수로 맞춘 절반씩 재귀예요. 앞에 `0.0 +`가 붙는 것까지 같아요.

두 입력의 수열이 같고 트리 모양이 같으니 모든 중간 덧셈이 같고, 결과 비트가 같아요. 그룹마다 처음부터 차례로 더하면 조금 빨라질 수는 있지만 이 일치가 깨지고, 재 보니 뚜렷이 빠르지도 않아서 pairwise로 두었어요. `mean`(합 / NA가 아닌 개수), `var`·`std`(평균을 구한 뒤 편차 제곱을 다시 pairwise로 더하는 두 번 훑기, 제곱은 fma 하나로 더해요)도 같은 함수(`float_sum`, `squares_sum`)를 같은 순서로 부르므로 같아요. 테스트는 그룹 결과의 정답을 "그 그룹의 행만 고른 Series의 리덕션"으로 두고 비트를 비교해요.

예를 들어 30만 행, 키 4종, 값의 10%가 NA인 무작위 입력에서 `sum`, `mean`, `var`, `std`, `min`, `max` 여섯 집계 모두 그룹 결과와 `df[df["k"] == i]["v"]`의 리덕션이 바이트까지 같아요.

pandas와는 다를 수 있어요. 20만 행, 키 3종, 크기가 $10^{-5}$에서 $10^5$까지 섞인 무작위 float 입력(numpy `default_rng(7)`로 만든 표준정규분포 값에 $10^{U(-5, 5)}$를 곱한 것)에서 세 그룹의 합을 16진수로 적으면 이래요(pandas 3.1.1).

| 그룹 | stardust 그룹 합 = 고른 Series의 `sum()` = `sd.sum` | pandas `groupby().sum()` | pandas 고른 Series의 `sum()` = numpy `sum` |
|:---:|:---:|:---:|:---:|
| 0 | `-0x1.f0c64912e3d0ep+21` | `-0x1.f0c64912e3d0cp+21` | `-0x1.f0c64912e3d10p+21` |
| 1 | `0x1.e2c089ec7a32ep+21` | `0x1.e2c089ec7a32dp+21` | `0x1.e2c089ec7a32fp+21` |
| 2 | `0x1.5501e7e667ceap+21` | `0x1.5501e7e667cebp+21` | `0x1.5501e7e667ceap+21` |

stardust의 pairwise 합은 numpy와 같은 알고리즘에 잎이 넓어서(누산기 16개, 블록 512개. numpy는 8개, 128개) numpy와도 마지막 자리가 다를 수 있어요. pandas의 그룹 합은 Kahan 합이라 pandas 자신의 Series 합(numpy의 pairwise 합)과도 마지막 몇 비트가 달라요. 정확도만 보면 Kahan 합의 오차 한계가 더 작아요. 합의 반올림 오차는 pairwise 합이 대략 $\varepsilon \log_2 n \sum |x_i|$, Kahan 합이 대략 $2\varepsilon \sum |x_i|$에 비례해요[5]. stardust는 한계를 조금 더 좁히는 것보다 "그룹 합은 그 행들의 합"이라는 정의가 비트까지 성립하는 쪽을 골랐어요. 같은 값을 groupby로 구하든 필터 후 `sum()`으로 구하든 배열의 `sd.sum`으로 구하든 같은 수가 나와요.

int64 컬럼의 그룹 `mean`(과 `var`, `std` 안의 평균)은 float로 더하지 않아요. 그룹의 행을 `IntSum`(`csrc/base/int_sum.hpp`)으로 정수인 채 정확히 더하고, 그 합을 한 번 반올림해 개수로 나눠요. Series의 int64 `mean()`도 같은 `IntSum`을 쓰므로([원소별 연산과 리덕션](/internals/frame/elementwise/)) 그룹 크기와 상관없이 비트가 같아요. 정수 덧셈에는 순서가 없으니 트리 모양을 맞출 필요도 없어요.

### 다른 집계

- **int64와 bool의 `sum`:** 부호 없는 64비트 정수로 더해 2의 보수로 감싸요(wrap). numpy와 같은 규칙이에요. 정수 덧셈은 결합법칙이 성립하니 순서가 결과를 바꾸지 않아요. bool은 True의 개수예요.
- **bool의 `mean`:** True의 개수를 NA가 아닌 개수로 나눠요.
- **`count`:** 그룹에서 NA가 아닌 행의 수예요. NA가 없는 컬럼은 세지 않고 그룹 크기를 그대로 써요. **`size`**는 NA와 상관없이 `start[g+1] - start[g]`예요.
- **`min`, `max`, `first`, `last`:** 값을 계산하지 않고 이긴 행을 골라요. `min`, `max`는 dtype마다 따로 컴파일한 루프(`winner`)가 그룹의 행을 읽어 고르고, `first`, `last`는 처음이나 마지막 값의 행을 골라요. 그룹마다 행 번호 하나(없으면 -1)를 적은 int64 컬럼을 만든 뒤 `take`로 값을 가져와요. `take`는 -1을 NA로 만들고 어떤 dtype이든 처리하니(문자열 포함), 집계 코드는 dtype마다 결과를 만드는 코드를 따로 두지 않아요.
  - 비교 규칙은 컬럼의 `min`, `max`와 같아요. float은 IEEE 754-2019의 minimum/maximum이라 NaN이 이기고 `-0.0 < 0.0`이에요. 그룹에서 처음 나온 NaN이 이기고, 같은 값이면 앞의 행이 남아요(엄격히 이길 때만 바꿔요). 문자열은 UTF-8 바이트 순서예요.
  - `first`는 그룹의 행을 앞에서부터, `last`는 뒤에서부터 보며 NA가 아닌 첫 행을 골라요. `skipna=False`면 NA든 아니든 첫 행이에요.
- **`skipna=False`:** 그룹에 NA가 하나라도 있으면 결과가 NA예요. 값이 모자라도 NA예요(모두 NA인 그룹의 `mean`, `count - correction <= 0`인 `var`). 컬럼 리덕션과 같은 규칙이에요.

결과의 NA는 그룹마다 바이트 하나(`valid[g]`)에 적었다가 마지막에 비트맵으로 접어요. 태스크가 그룹을 나눠 맡으면 두 태스크의 그룹이 비트맵의 같은 바이트에 들어갈 수 있어서, 비트를 바로 쓰면 같은 바이트에 두 스레드가 쓰는 경쟁이 생기기 때문이에요.

### 병렬: 그룹을 통째로 묶어 태스크로

행이 $2^{17}$개 이상이면 그룹들을 여러 태스크로 나눠요. 태스크의 경계는 그룹 사이에만 놓고, 태스크마다 행이 약 16K(`kChunkRows` = $2^{14}$)개가 되게 해요.

```cpp
    // csrc/frame/ops/groupby.cpp
    std::vector<std::int64_t> cuts{0};
    for (std::int64_t r = kChunkRows; r < n; r += kChunkRows) {
        const auto g =
            static_cast<std::int64_t>(std::lower_bound(start_.begin(), start_.end() - 1, r) - start_.begin());
        if (g > cuts.back()) cuts.push_back(g);
    }
    if (ngroups_ > cuts.back()) cuts.push_back(ngroups_);
```

`lower_bound`는 행 $r$을 담은 그룹(또는 $r$에서 시작하는 그룹)의 번호를 `start_`에서 이진 탐색으로 찾아요. 그 뒤 `run_unlocked`가 GIL을 놓고 묶음마다 태스크 하나로 돌려요([병렬화와 결정성](/internals/frame/parallel/)).

- `start_`는 증가하는 배열이라, "행 $r$ 근처에서 그룹을 끊는다"는 것은 이진 탐색 하나예요. 경계 계산은 태스크 수 × $\log G$번의 비교라 무시할 만해요.
- 한 그룹의 행이 16K보다 많으면 그 그룹 혼자 태스크가 되고, 아주 큰 그룹 하나가 태스크 하나를 차지해요. 그룹이 수십만 개면 태스크 하나가 그룹 수천 개를 맡아요.
- 경계가 어디든 결과는 같아요. 그룹마다 계산이 독립이고, 한 그룹은 언제나 한 태스크가 처음부터 끝까지 계산해요. 그래서 경계를 `start_`(데이터에서 나온 그룹 크기)로 정해도 결과가 스레드 수나 경계에 따라 달라지지 않아요.
- 태스크 안에서는 다시 나누지 않아요(풀은 중첩된 `parallel_for`를 호출 스레드에서 차례로 돌려요). 태스크가 하나뿐일 때(그룹이 하나)는 그 그룹의 `float_sum`이 컬럼 합처럼 pairwise 트리의 잎을 병렬로 더해요. 어느 쪽이든 트리 모양은 같아서 비트는 같아요([병렬화와 결정성](/internals/frame/parallel/)).
- `run_unlocked`는 GIL을 먼저 놓고 `parallel_for`를 불러요. `parallel_for`는 태스크가 하나면 GIL을 건드리지 않아서, 그룹이 하나뿐인 큰 groupby도 1스레드에서 GIL을 놓게 하려는 거예요. 이 경로는 행이 기준값(2¹⁷) 이상일 때만 와요.
- 값 컬럼이 여럿이면(`df.groupby("k").sum()`) Python 층이 모든 값 컬럼을 한 번에 넘겨요(`Groups.reduce_columns`). 행이 기준값 아래여도 행 × 컬럼이 기준값 이상이면 컬럼 하나를 태스크 하나로 나눠요. 넓은 프레임(10만 행 × 100열)이 이 크기에서도 여러 스레드로 돌아요. 결과는 컬럼마다 따로 부른 것과 같고, 에러는 태스크 전에 컬럼 순서로 검사해요.

## 그룹 순서

### 그룹이 아니라 키 값을 정렬해요

`sort=True`면 결과의 그룹을 키의 오름차순으로 늘어놓아요. 키가 여러 개면 첫 키가 우선이고, 같으면 다음 키로 가려요. NA 키 그룹은 맨 뒤예요(`dropna=False`일 때). 이 순서는 `sort_values`의 오름차순과 같아요. NaN은 +inf보다 크고, `-0.0`과 `0.0`은 같은 값, 문자열은 코드포인트 순서, `False < True`예요.

가장 단순한 구현은 그룹 번호 $0, \dots, G-1$을 `std::stable_sort`로 정렬하면서, 비교할 때마다 두 그룹의 키 컬럼을 차례로 비교하는 것이에요. 하지만 이 방법은 느려요. int 1,000종 × string 1만 종 키로 무작위 1M 행을 묶으면 그룹이 약 95만 개라, 비교가 약 $G \log_2 G \approx 1{,}890$만 번이고 비교마다 문자열 비교가 끼어요.

**키가 숫자나 bool 하나면** 그룹마다 한 행인 대표값을 안정 기수 정렬(`argsort`, 아래)한 순서가 곧 그룹 순서예요. NA는 맨 뒤이고, 같은 값(`-0.0`과 `0.0`, NaN끼리)인 그룹은 코드 순서대로 남아요. factorize, 순위, counting sort를 거치지 않아요.

**그 밖(문자열 키, 여러 키)에는** 키 값의 고유값을 정렬하고, 그룹에는 그 순위만 줘요. 마지막 키부터 한 키씩 이렇게 해요.

1. 그 키 컬럼(그룹마다 한 행, 즉 그룹의 대표값)을 factorize해서 같은 값의 그룹끼리 같은 코드를 줘요. 입력이 그룹 수 $G$만큼의 행이라 원래 행 수 $n$과 상관없어요.
2. 고유값 $u$개를 `order_rows`로 오름차순 정렬해요(아래의 기수 정렬). NA 코드는 맨 뒤에 붙여요.
3. 고유값마다 순위 $0, \dots, u-1$을 주고, 그룹마다 자기 키 값의 순위를 붙여요.
4. 지금까지의 그룹 순서를 순위로 안정 counting sort해요.

순위는 $0..u-1$로 빈틈없는 작은 정수라 counting sort 한 번($O(G + u)$)이면 정렬돼요.

마지막 키부터 하는 이유는 LSD 기수 정렬과 같아요. 안정 정렬을 뒤쪽 키부터 차례로 하면, 마지막 정렬(첫 키)에서 순위가 같은 그룹끼리는 그 전 정렬의 순서, 곧 뒤쪽 키의 순서를 지켜요. 그래서 결과는 첫 키가 우선이고 같으면 다음 키인 사전식 순서예요. 이 원리는 [아래](#lsd-기수-정렬)에서 바이트 자리로 다시 설명해요.

```python
>>> df = sd.frame.DataFrame({"a": [2, 1, 2, 1, 2, 1], "b": ["y", "x", "x", "y", "y", "x"],
...                          "v": [1, 2, 3, 4, 5, 6]})
>>> df.groupby(["a", "b"]).sum()
   a  b  v
0  1  x  8
1  1  y  4
2  2  x  3
3  2  y  6
>>> df.groupby(["a", "b"], sort=False).sum()
   a  b  v
0  2  y  6
1  1  x  8
2  2  x  3
3  1  y  4
```

두 설계를 같은 조건(1M 행, int 1,000종 × string 1만 종의 2키 `sum`, 1스레드)에서 재면, 키 값의 순위와 counting sort를 쓰는 설계가 groupby 전체(factorize, 행 모으기, 합, 그룹 순서)로 약 4배 빨랐어요.

### 같은 키와 같은 순서

float 키에서 "같은 그룹"은 factorize가, "그룹의 순서"는 정렬 키가 정해요. 둘은 같은 정규화 함수 `float_key`에서 시작해요. 모든 NaN을 비트 하나(`0x7ff8000000000000`)로, `-0.0`을 `+0.0`의 비트로 바꾸는 함수예요. 그래서 factorize에서 같은 키인 두 값은 정렬에서도 언제나 같은 값이에요. NaN 두 개가 한 그룹인데 정렬에서는 다른 자리에 가는 일이 생기지 않아요.

```python
>>> nan = float("nan")
>>> df = sd.frame.DataFrame({"k": [2.0, nan, -0.0, None, 0.0, float("inf"), -nan, 2.0],
...                          "v": [1, 2, 3, 4, 5, 6, 7, 8]})
>>> df.groupby("k", dropna=False).sum()
     k  v
0 -0.0  8
1  2.0  9
2  inf  6
3  NaN  9
4 <NA>  4
```

`-0.0`(행 2)과 `0.0`(행 4)이 한 그룹이고, 키로는 먼저 나온 `-0.0`이 보여요. 부호가 다른 두 NaN(행 1, 6)도 한 그룹이고 +inf 뒤에 와요. NA 그룹은 맨 뒤예요.

`unique_values()`도 같은 순서를 써요. 컬럼을 factorize해 코드마다 처음 나온 값을 꺼낸 뒤 `sort_groups`로 정렬해요. 값이 작은 범위에 있는 int64와 bool은 해시도 정렬도 없이, 범위만큼의 비트맵에 나온 값을 표시하고 차례로 읽어요([해시 테이블과 factorize](/internals/frame/hashing/)). 어느 길이든 `s.unique_values()`의 순서와 `groupby` 결과의 키 순서가 언제나 같아요.

### pandas, Polars와 비교

- **pandas 3.1.1**은 키 하나의 그룹 코드를 `algorithms.factorize(..., sort=True)`로 만들어, factorize할 때 고유값을 정렬하고 코드를 그 순서로 다시 매겨요. 고유값을 정렬한다는 생각은 같아요. 다만 그 앞에 데이터를 보는 빠른 길이 있어요. `_factorize_monotonic`이 숫자·날짜·bool dtype의 키가 이미 오름차순이나 내림차순으로 정렬되어 있는지(numpy 배열이면 고르게 뽑은 표본 8개를 먼저 보고, 그다음 전체를) 검사해서, 정렬되어 있으면 해시 테이블 없이 이웃한 값끼리 비교해 코드를 만들어요[6]. stardust도 데이터를 보는 길이 있어요. 키로 이미 묶인 코드는 행을 옮기지 않고, 숫자 키 하나의 그룹 순서는 이미 정렬되어 있으면 정렬하지 않아요. 조건은 결과(값, 순서, 결과 타입)가 어느 길이든 같아야 한다는 것이에요. 그래서 어느 경로가 탔는지는 시간에만 보이고 결과에는 보이지 않아요.
- **Polars 2.1.0**의 `group_by`는 기본으로 그룹 순서를 보장하지 않아요. `maintain_order=True`를 주면 입력에서 나타난 순서이고, 문서에 따르면 그쪽이 더 느려요[7]. 키 순서를 원하면 결과를 따로 정렬해요. stardust의 기본값(`sort=True`)은 pandas와 같고, `sort=False`의 "처음 나타난 순서"는 factorize의 코드 순서라 공짜예요.

## 값을 부호 없는 64비트 키로

### 왜 정수 하나로 바꾸나

정렬 알고리즘이 "a가 b보다 작은가"를 묻는 비교 함수를 쓰면, 값의 순서 규칙(NaN은 +inf보다 큼, `-0.0 == 0.0`, NA는 따로)이 비교마다 분기로 들어가요. 비교는 $O(n \log n)$번 일어나니 그 분기가 계속 쌓여요.

stardust는 정렬하기 전에 값마다 한 번, "값의 순서 = 부호 없는 정수의 순서"인 64비트 키를 만들어요(`radix_key`). 그다음부터는 키만 보면 돼요. 규칙은 키를 만드는 이 함수 한 곳에만 있고, 정렬 알고리즘은 dtype을 몰라요. 또 키가 정수면 비교하지 않는 [기수 정렬](#lsd-기수-정렬)을 쓸 수 있어요.

| dtype | 키 | 이유 |
|---|---|---|
| int64 | `x ^ (1 << 63)` | 부호 비트만 뒤집으면 음수가 양수보다 작은 부호 없는 수가 돼요 |
| bool | 0 / 1 | `False < True` |
| float64 | `b = float_key(x)`, 양수면 `b \| (1 << 63)`, 음수면 `~b` | 아래 설명 |
| string | 고유값의 순위 (정렬은 8바이트 접두사로) | [문자열의 순서](#문자열의-순서) |

```cpp
// csrc/frame/ops/radix.hpp
inline std::uint64_t radix_key(const Column& c, std::int64_t i) {
    switch (c.dtype) {
        case DType::Int64: return static_cast<std::uint64_t>(c.data<std::int64_t>()[i]) ^ (std::uint64_t{1} << 63);
        case DType::Bool: return c.data<std::uint8_t>()[i];
        case DType::Float64: {
            const std::uint64_t bits = float_key(c.data<double>()[i]);  // NaN and -0.0 normalized (hash.hpp)
            return (bits >> 63) ? ~bits : bits | (std::uint64_t{1} << 63);
        }
        case DType::String: break;
        case DType::Complex128: break;  // not a frame dtype
    }
    return 0;
}
```

string은 이 키를 쓰지 않고 순위로 따로 정렬해요.

`switch`가 행마다 있지만, 키를 만드는 루프는 행마다 한 번이고 정렬 패스들보다 가벼워요. 그리고 한 호출 안에서 dtype이 바뀌지 않으니 분기는 언제나 같은 쪽으로 가서 예측이 틀리지 않아요.

### int64: 부호 비트 뒤집기

int64는 2의 보수예요. 부호 없는 정수로 읽으면 $0, 1, \dots, 2^{63}-1$(양수)이 먼저 오고 그 뒤에 $-2^{63}, \dots, -1$(음수)이 와요. 맨 위 비트(부호 비트)만 뒤집으면 음수가 $0 \dots 2^{63}-1$로, 양수가 $2^{63} \dots 2^{64}-1$로 옮겨가고 각 구간 안의 순서는 그대로예요.

| 값 | 키 (16진수) |
|:---:|:---:|
| $-2^{63}$ | `0000000000000000` |
| $-1$ | `7FFFFFFFFFFFFFFF` |
| $0$ | `8000000000000000` |
| $1$ | `8000000000000001` |
| $2^{63}-1$ | `FFFFFFFFFFFFFFFF` |

### float64: 양수는 부호 비트, 음수는 전부

IEEE 754의 float64는 위에서부터 부호 1비트, 지수 11비트(바이어스를 더한 부호 없는 수), 가수 52비트예요. 이 배치 덕분에 양수끼리는 비트를 부호 없는 정수로 읽은 순서가 값의 순서예요. 지수가 크면 값이 크고, 지수가 같으면 가수가 큰 쪽이 커요. 음수는 부호 비트만 다르고 나머지가 "크기"라서, 비트가 클수록 값은 작아요.

그래서 이렇게 바꿔요.

- **양수(부호 비트 0):** 부호 비트를 세워요. 모든 양수가 $2^{63}$ 이상으로 올라가고 서로의 순서는 그대로예요.
- **음수(부호 비트 1):** 64비트를 모두 뒤집어요. 부호 비트가 0이 되어 양수 아래로 가고, "크기가 클수록 비트가 크다"가 "크기가 클수록 키가 작다"로 뒤집혀요.

이 변환을 정규화 없이 쓰면 IEEE 754-2019의 전순서 술어 totalOrder처럼 `-0.0 < +0.0`이 되고, 부호 비트가 선 NaN은 $-\infty$ 아래로, 그렇지 않은 NaN은 $+\infty$ 위로 가요[8]. stardust의 순서는 이것과 두 곳이 달라요. `-0.0`과 `0.0`은 같은 값이고, NaN은 부호와 상관없이 가장 큰 값이에요. 그래서 변환 전에 `float_key`로 정규화해요.

```cpp
// csrc/frame/ops/hash.hpp
inline std::uint64_t float_key(double d) {
    if (d != d) return 0x7ff8000000000000ULL;
    if (d == 0.0) return 0;
    std::uint64_t bits;
    std::memcpy(&bits, &d, sizeof bits);
    return bits;
}
```

| 값 | 비트 | `float_key` 뒤 | 키 | 내림차순 키 (`~키`) |
|:---:|:---:|:---:|:---:|:---:|
| $-\infty$ | `FFF0000000000000` | 그대로 | `000FFFFFFFFFFFFF` | `FFF0000000000000` |
| $-2.0$ | `C000000000000000` | 그대로 | `3FFFFFFFFFFFFFFF` | `C000000000000000` |
| $-0.5$ | `BFE0000000000000` | 그대로 | `401FFFFFFFFFFFFF` | `BFE0000000000000` |
| $-0.0$ | `8000000000000000` | `0000000000000000` | `8000000000000000` | `7FFFFFFFFFFFFFFF` |
| $+0.0$ | `0000000000000000` | 그대로 | `8000000000000000` | `7FFFFFFFFFFFFFFF` |
| $0.5$ | `3FE0000000000000` | 그대로 | `BFE0000000000000` | `401FFFFFFFFFFFFF` |
| $2.0$ | `4000000000000000` | 그대로 | `C000000000000000` | `3FFFFFFFFFFFFFFF` |
| $+\infty$ | `7FF0000000000000` | 그대로 | `FFF0000000000000` | `000FFFFFFFFFFFFF` |
| NaN | `7FF8000000000000` | 그대로 | `FFF8000000000000` | `0007FFFFFFFFFFFF` |
| 부호 있는 NaN | `FFF8000000000000` | `7FF8000000000000` | `FFF8000000000000` | `0007FFFFFFFFFFFF` |

- NaN이 +inf보다 커요. 정규화한 NaN의 비트 `7FF8…`가 +inf의 `7FF0…`보다 크고, 둘 다 양수 쪽 변환을 거치니 키에서도 NaN이 가장 커요. NaN을 특별히 다루는 코드가 없어요.
- 부호 있는 NaN도 같은 자리예요. 정규화하지 않으면 부호 비트가 선 NaN `FFF8…`은 음수로 취급되어 `~` 뒤에 `0007FFFFFFFFFFFF`, 곧 $-\infty$(`000FFFFFFFFFFFFF`)보다도 작은 키가 돼요. `float_key`가 이것을 막아요.
- `-0.0`과 `+0.0`은 같은 키예요. 기수 정렬은 안정이니 둘은 입력 순서대로 남아요. 정렬하는 것은 행 번호이고 키는 순서를 정하는 데만 쓰니, 결과에는 원래 값(`-0.0`이면 `-0.0`)이 그대로 나와요.

배열 영역의 정렬은 NaN을 정렬 전에 따로 떼어 내요([정렬과 집합](/internals/array/sorting/)). frame은 NaN을 결측이 아닌 평범한 float 값으로 다루고, 같은 키 규칙에서 이미 NaN을 하나로 모아 두었으니 키 하나로 충분해요.

### 내림차순: 키의 모든 비트를 뒤집기

내림차순은 키를 `~키`로 바꿔 오름차순으로 정렬해요. $k \mapsto 2^{64} - 1 - k$는 순서를 정확히 뒤집고, 같은 키는 뒤집어도 같은 키예요. 그래서 같은 값끼리는 여전히 입력 순서를 지켜요.

오름차순으로 정렬한 뒤 결과를 뒤집으면 이렇게 되지 않아요. 같은 값의 순서까지 뒤집히니 안정 정렬이 아니에요. 예를 들어 `[1, 2a, 2b]`(2a와 2b는 같은 값)를 오름차순으로 정렬해 뒤집으면 `[2b, 2a, 1]`이지만, 안정 내림차순은 `[2a, 2b, 1]`이에요.

NaN은 오름차순에서 맨 끝이니 내림차순에서는 맨 앞이에요. 오름차순의 정확한 거울이에요.

### NA는 키에 넣지 않아요

NA는 값의 순서 밖에 있어요. 어느 위치에 둘지는 방향과 따로 `na_position`이 정해요. 그래서 키를 만들기 전에 행을 "값이 있는 행"과 "NA 행"으로 나누고(`split_na`), 값이 있는 행만 정렬한 뒤 NA 행을 원래 순서대로 앞이나 뒤에 붙여요.

```cpp
    // csrc/frame/ops/sort.cpp
    std::vector<std::int64_t> valid_rows, na_rows;
    const bool has_na = key.validity && key.null_count > 0;
    if (has_na) split_na(key, order, valid_rows, na_rows);
    std::vector<std::int64_t>& rows = has_na ? valid_rows : order;
```

NA가 있으면 행을 둘로 나누고(각자 지금까지의 순서로), 값이 있는 행만 기수 정렬한 뒤 NA 행은 정렬하지 않고 앞이나 뒤에 붙여요. NA가 없으면 행 목록(`order`)을 그 자리에서 정렬해서, 떼고 붙이는 복사가 없어요.

NA를 키의 최댓값이나 최솟값으로 넣는 방법도 있지만, 그러면 NA가 NaN이나 +inf와 같은 키 공간을 나눠 쓰게 되고, 내림차순에서 `~`가 NA의 위치까지 뒤집어 버려요. 떼어 두면 "NA는 방향과 상관없이 `na_position`대로"가 코드 한 줄이에요. 컬럼에 NA가 없으면 `split_na`를 부르지 않아요.

```python
>>> s = sd.frame.Series([3.0, nan, -0.0, None, 1.0, 0.0, float("inf"), -nan])
>>> s.sort_values()
2   -0.0
5    0.0
4    1.0
0    3.0
6    inf
1    NaN
7    NaN
3   <NA>
dtype: float64
>>> s.sort_values(descending=True)
1    NaN
7    NaN
6    inf
0    3.0
4    1.0
2   -0.0
5    0.0
3   <NA>
dtype: float64
```

내림차순에서도 `-0.0`(행 2)이 `0.0`(행 5)보다 앞이고, 두 NaN(행 1, 7)도 입력 순서예요. NA는 두 경우 모두 기본값 `na_position="last"`대로 맨 뒤예요.

### 다중 키: 마지막 키부터

`sort_values(["a", "b"])`는 마지막 키 `b`로 먼저 안정 정렬하고, 그 결과 순서를 `a`로 다시 안정 정렬해요. [그룹 순서](#그룹이-아니라-키-값을-정렬해요)와 같은 원리예요. 키마다 따로 정렬하니 키마다 자기 방향과 NA 위치만 적용하면 되고, 키끼리 dtype이 달라도 돼요.

```cpp
    // csrc/frame/ops/sort.cpp
    if (keys.size() == 1 && already_sorted(keys[0], ascending[0])) return std::nullopt;
    std::vector<std::int64_t> order(static_cast<std::size_t>(n));
    std::iota(order.begin(), order.end(), std::int64_t{0});
    // Several keys: sort by the last key first, then each earlier key with a
    // stable sort, so the first key decides and later keys break its ties.
    for (std::size_t j = keys.size(); j-- > 0;) sort_by(keys[j], ascending[j], na_last[j], order);
```

`sort_by`는 `order`(지금까지의 순서)를 받아 그 순서를 입력으로 삼아요. `split_na`도 기수 정렬도 안정이라, 이 키에서 같은 행들은 앞선 키(뒤쪽 키)의 순서를 지켜요.

### 이미 정렬된 키는 정렬하지 않아요

키가 하나이고 NA가 없으면, `argsort`는 먼저 컬럼을 한 번 읽어 그 방향으로 이미 정렬되어 있는지 봐요(`already_sorted`). 같은 값이 이어져도 돼요. 안정 정렬이 그 순서를 그대로 지키기 때문이에요. 그렇으면 위치 배열 대신 None을 돌려주고, Python 층은 `take` 없이 컬럼과 Index를 Copy-on-Write로 공유해 결과를 만들어요. 여러 키나 NA가 있어서 정렬한 뒤에도 순서가 0..n-1 그대로이면 역시 None이에요.

결과 타입은 데이터에 따라 바뀌지 않아요. take를 건너뛰어도 원래 Index가 `RangeIndex`면 take가 돌려줄 `Index`(라벨 0..n-1)로 바꿔 돌려줘요. 공유한 컬럼은 쓰기 전에 복사되므로 복사본과 구별되지 않아요.

```python
>>> t = sd.frame.Series([1, 2, 2, 5])
>>> type(t.sort_values().index).__name__
'Index'
>>> type(t.iloc[[0, 1, 2, 3]].index).__name__
'Index'
```

`stable=False`도 받지만 같은 안정 정렬을 해요. 안정 정렬의 결과는 불안정 정렬로서도 올바른 결과이고, 기수 정렬은 안정이 공짜라 불안정 경로를 따로 둘 이유가 없어요.

## LSD 기수 정렬

### 원리

**직관.** 날짜 카드 더미를 연-월-일 순서로 정렬한다고 해 볼게요. 먼저 일로 카드를 31개 상자에 나눠 담았다가 상자 순서대로 모아요. 그다음 그 더미를 월로 12개 상자에, 마지막으로 연으로 나눠 담아요. 상자에 담을 때 카드의 상대 순서를 바꾸지 않는다면, 마지막에 연이 같은 카드들은 앞 단계에서 정해진 월·일 순서를 지키고 있으니 전체가 정렬돼요. 가장 덜 중요한 자리(least significant digit)부터 하므로 **LSD 기수 정렬**이에요[1][2].

**정의.** 64비트 키를 8비트씩 8자리 $d = 0, \dots, 7$(0이 가장 낮은 바이트)로 봐요. 자리 $d$의 값은 `(key >> 8d) & 0xff`예요. $d = 0$부터 7까지 차례로, 자리 값(0–255)을 키로 하는 안정 counting sort를 해요. 각 패스가 위의 counting sort(세기 → 누적합 → 놓기)와 똑같고, 키 대신 자리 값 256종이에요.

**왜 맞나.** 패스 $d$가 끝난 뒤에는 "아래 $d+1$바이트로 본 키"의 순서로 정렬되어 있어요(귀납법). 패스 $d+1$은 바이트 $d+1$로 나누는데, 그 바이트가 같은 원소들은 안정성 덕분에 패스 $d$까지의 순서, 곧 아래 바이트들의 순서를 지켜요. 그러니 아래 $d+2$바이트로 정렬돼요. 8패스 뒤에는 64비트 전체로 정렬돼요. 안정성이 없으면 이 논증이 깨져요. 위 자리로 나눌 때 아래 자리의 순서를 섞어 버리기 때문이에요.

정렬 전체도 안정이에요. 키가 완전히 같은 두 원소는 모든 패스에서 같은 상자에 들어가고, 매번 상대 순서를 지키니 끝까지 입력 순서예요.

**비용.** 패스마다 원소를 한 번 읽고 한 번 써요. 비교가 없으니 비교 정렬의 $O(n \log n)$ 하한에 묶이지 않고, 8자리를 모두 지나면 시간은 $O(8(n + 256))$이에요. 실제로는 [아래](#필요한-패스만-돌아요)처럼 키가 서로 다른 자리만 지나서 패스가 더 적어요. 데이터에 따라 갈리는 분기도 없어요. 원소마다 하는 일은 자리 값 계산, 카운터 하나 읽고 늘리기, 저장 둘이에요.

### 메모리 배치와 한 패스

frame의 기수 정렬은 키 배열과 행 배열 두 개를 함께 옮겨요. 패스마다 두 배열을 읽고 두 임시 배열에 쓴 뒤 `swap`해요.

```cpp
// csrc/frame/ops/radix.hpp
inline void radix_passes_serial(std::vector<std::uint64_t>& keys, std::vector<std::int64_t>& rows, const RadixPlan& p) {
    const std::size_t n = keys.size();
    const std::uint64_t off = p.offset;
    std::vector<std::int64_t> count(static_cast<std::size_t>(p.npass) << 11, 0);  // 2^11 per pass
    for (std::uint64_t k : keys) {
        const std::uint64_t x = k - off;
        for (int d = 0; d < p.npass; ++d)
            ++count[(static_cast<std::size_t>(d) << 11) + ((x >> p.shifts[d]) & ((1u << p.widths[d]) - 1))];
    }
    std::vector<std::uint64_t> keys2(n);
    std::vector<std::int64_t> rows2(n);
    std::vector<std::int64_t> next_(std::size_t{1} << 11);
    for (int d = 0; d < p.npass; ++d) {
        const int shift = p.shifts[d];
        const std::uint64_t mask = (std::uint64_t{1} << p.widths[d]) - 1;
        const std::int64_t* c = count.data() + (static_cast<std::size_t>(d) << 11);
        std::int64_t* next = next_.data();  // a local pointer: the row stores below cannot alias it
        std::int64_t at = 0;
        for (std::uint64_t b = 0; b <= mask; ++b) {
            next[b] = at;
            at += c[b];
        }
        const std::uint64_t* k = keys.data();
        const std::int64_t* r = rows.data();
        std::uint64_t* k2 = keys2.data();
        std::int64_t* r2 = rows2.data();
        for (std::size_t j = 0; j < n; ++j) {
            const std::int64_t to = next[((k[j] - off) >> shift) & mask]++;
            k2[to] = k[j];
            r2[to] = r[j];
        }
        keys.swap(keys2);
        rows.swap(rows2);
    }
}
```

- 패스마다 자리의 위치(`shifts`)와 폭(`widths`, 11비트 이하)은 계획(`RadixPlan`)이 정해요(아래). 키에서 `offset`(최솟값일 수 있어요)을 뺀 값의 자리를 읽어요.
- 히스토그램은 한 번에 모든 자리를 세요. 자리 $d$의 상자별 개수는 키의 집합만으로 정해지고 순서와 무관해요. 그래서 흩뿌리기 전에 한 번 읽으며 모든 자리를 셀 수 있어요. 자리마다 세면 읽기가 세기 $P$번 + 흩뿌리기 $P$번이고, 한 번에 세면 세기 1번 + 흩뿌리기 $P$번이에요.
- `next`는 지역 포인터예요. `r2[to] = r[j]`는 int64 저장이고 `next`도 int64 배열이에요. 컴파일러가 이 저장이 `next`의 어느 칸을 바꿨을 수도 있다고 보면, 다음 반복에서 `next[…]`를 메모리에서 다시 읽어야 해요. 그러면 카운터를 늘리는 일이 앞선 저장들을 기다려요. 이런 앨리어싱 문제는 [원소별 연산과 리덕션](/internals/frame/elementwise/)에서 자세히 다뤄요.
- 패스마다 `keys`와 `keys2`, `rows`와 `rows2`의 버퍼를 `swap`으로 바꾸므로 마지막 패스의 결과는 언제나 `keys`, `rows`에 있어요. 패스 수가 홀수여도 복사해 돌려놓을 일이 없어요.

옮기는 양을 세면, 1M 행에서 패스마다 16MB를 읽고 16MB를 써요. 메모리는 원래 두 배열과 임시 두 배열로 $32n$바이트(1M 행이면 32MB)예요.

배열 영역과는 배치가 달라요. 배열의 `argsort`는 (값, 인덱스) 16바이트 쌍을 정렬하고, 기수 키는 패스마다 값에서 다시 계산해요([정렬과 집합](/internals/array/sorting/)). frame은 키를 한 번 계산해 행과 함께 옮겨요. frame의 키는 행 번호로 컬럼을 찾아가서(`radix_key(c, rows[j])`) 만들고, 문자열은 순위 표를 거쳐야 하고, 여러 키의 정렬에서는 앞선 패스가 행 순서를 이미 바꿔 놓았기 때문이에요. 이런 간접 읽기를 패스마다 다시 하는 것보다 키를 함께 옮기는 편이 싸요.

### 필요한 패스만 돌아요

정렬하기 전에 키를 한 번 훑어요(`scan_keys`). 청크마다 최솟값, 최댓값, 모든 키의 OR와 AND, "내려가지 않는가", "올라가지 않는가"를 구하고 청크 순서로 합쳐요(청크 경계의 두 키도 비교해요). 이 한 번 읽기로 길이 셋 중 하나로 갈려요.

1. **이미 오름차순**(같은 값 허용)이면 아무것도 옮기지 않아요.
2. **내림차순**(같은 값 허용)이면 같은 키의 묶음을 통째로 뒤에서부터 늘어놓아요(`reverse_runs`). 묶음 안의 순서는 그대로라 안정 정렬의 결과와 같아요. 오름차순으로 정렬한 뒤 통째로 뒤집으면 같은 값의 순서까지 뒤집혀서 틀려요.
3. **그 밖에는 키가 서로 다른 비트만 정렬해요**(`plan_passes`). 두 계획 중 패스가 적은 쪽을 골라요.
   - (a) `키 − 최솟값`의 비트: 최댓값 − 최솟값이 $b$비트면 그 비트만 정렬하면 돼요.
   - (b) 모든 키에서 같지는 않은 바이트 자리: OR와 AND가 다른 비트가 하나라도 있는 바이트만이에요.

```cpp
// csrc/frame/ops/radix.hpp
inline RadixPlan plan_passes(const KeyScan& s, int digits, bool wide = false) {
    RadixPlan by_mask, by_range;
    const std::uint64_t differ = s.ones ^ s.zeros;  // bits that are not the same in every key
    for (int d = 0; d < digits; ++d)
        if ((differ >> (8 * d)) & 0xff) {
            by_mask.shifts[by_mask.npass] = 8 * d;
            by_mask.widths[by_mask.npass++] = 8;
        }
    const std::uint64_t span = s.hi - s.lo;
    by_range.offset = s.lo;
    const int bits = span == 0 ? 0 : 64 - __builtin_clzll(span);
    const int max_width = wide ? 11 : 8;
    const int npass = (bits + max_width - 1) / max_width;
    for (int d = 0, at = 0; d < npass; ++d) {
        // Bytes; wide digits: the bits left, spread evenly over the passes left.
        const int w = wide ? (bits - at + (npass - d) - 1) / (npass - d) : 8;
        by_range.shifts[d] = at;
        by_range.widths[d] = w;
        at += w;
    }
    by_range.npass = npass;
    return by_range.npass <= by_mask.npass ? by_range : by_mask;
}
```

빼는 자리가 결과를 바꾸지 않는 이유는 간단해요. 모든 키에서 같은 자리(또는 `키 − 최솟값`에서 언제나 0인 위쪽 자리)로 나누면 모든 원소가 한 상자에 들어가고, 안정 패스라 원소가 한 칸도 움직이지 않아요. 그런 패스는 빼도 순서가 같아요. 예를 들어 $[0, 10^6)$의 int64 키는 부호 비트를 뒤집은 키의 위 다섯 바이트가 모두 같아서(`80 00 00 00 00 …`), 8패스가 아니라 20비트의 2~3패스로 끝나요.

**자리의 폭.** 나누지 않는 정렬은 (a)의 비트를 11비트 이하의 고른 자리로 나눠요(`wide`). 패스 하나의 비용이 8~11비트에서 거의 같아서, 17~22비트 키가 3패스가 아니라 2패스로 끝나요. 다만 키가 $2^{15}$개(`kWideRadixKeys`)보다 적으면 2,048칸 히스토그램을 비우고 더하는 비용이 줄인 패스보다 커서 바이트 자리를 써요. 나누는 정렬은 언제나 바이트 자리예요(아래 "자리 크기").

호출하는 쪽이 정하는 자리의 상한(`digits`)도 그대로 있어요. bool 키는 1바이트, 문자열의 순위 키는 고유값 개수 $u$보다 작으니 $u - 1$을 담는 바이트 수(`digits_for`)예요. 위의 훑기가 같은 일을 하므로 이 값은 상한일 뿐이에요.

어느 길이든 결과는 하나의 안정 정렬이에요. 데이터에 따라 달라지는 것은 시간뿐이고, 같은 값의 순서도 길에 따라 바뀌지 않아요. frame은 데이터를 보고 길을 고르되 결과가 모든 길에서 같을 때만 그렇게 해요. 정렬된 Index에서 라벨 슬라이스에 이진 탐색을 쓰지 않는 것([라벨, 조회, 선택](/internals/frame/labels/))은 결과가 달라지는 길이라서예요.

### 나눠서 병렬로

**문제.** 패스 하나는 "모든 원소를 자리 값 순서로, 같은 자리 값 안에서는 입력 순서로" 놓는 일이에요. 스레드들이 입력을 나눠 맡아 각자 흩뿌리려면, 각 스레드가 자기 원소를 어디서부터 써야 하는지 알아야 해요.

**방법.** 키가 기준값(2¹⁷개) 이상이고 풀을 쓸 수 있으면 입력을 16K행(`kChunkRows`) 청크로 나누고, 계획의 패스마다 세 단계를 해요.

1. **청크별 히스토그램(병렬):** 청크 $c$마다 자리 값 $v$의 개수 $h_{c,v}$를 세요.
2. **시작 위치(직렬):** "자리 값 순서, 같은 자리 값 안에서는 청크 순서"로 누적해요.

   $$
   \text{pos}(c, v) = \sum_{v' < v} \sum_{c'} h_{c', v'} \;+\; \sum_{c' < c} h_{c', v}
   $$

3. **흩뿌리기(병렬):** 청크마다 자기 `pos(c, ·)`에서 시작해 직렬 패스와 똑같이 놓아요.

자리 값 $v$인 원소들의 칸은 앞 청크의 것부터 차례로 배정되고, 청크 안에서는 원소 순서대로 놓여요. 그러니 같은 자리 값끼리는 입력 순서이고, 원소가 놓이는 칸이 직렬 패스와 정확히 같아요. 스레드가 몇 개든, 어느 청크가 먼저 끝나든 결과가 같아요.

```cpp
                const std::uint64_t* k = keys.data();
                const std::int64_t* r = rows.data();
                std::uint64_t* k2 = keys2.data();
                std::int64_t* r2 = rows2.data();
                for (std::int64_t j = lo; j < hi; ++j) {
                    const std::int64_t to = next[((k[j] - off) >> shift) & 0xff]++;
                    k2[to] = k[j];
                    r2[to] = r[j];
                }
            },
            2
        );
```

- 위의 누적이 2단계(자리 값이 바깥, 청크가 안쪽)이고, `for_chunks`가 3단계예요. `at[c * 256 + b]`는 청크 $c$의 자리 값 $b$예요.
- 자리마다 히스토그램을 다시 세요. 직렬 경로는 모든 자리를 한 번에 세지만, 병렬 경로에서는 그럴 수 없어요. 자리 $d$의 패스에서 청크 $c$에 들어 있는 원소는 앞 패스가 옮겨 놓은 원소들이라, 패스마다 청크의 내용이 달라져요.
- 흩뿌리기도 `next`를 지역 배열로 복사해 써요. 직렬 경로와 같은 앨리어싱 이유예요.
- 청크 수가 데이터 길이로만 정해져요. `C = ⌈n / 16384⌉`이에요. 1M 행이면 62개이고, 카운터 배열 `at`은 $62 \times 256$칸(약 127KB)이에요.
- 키 훑기도 청크마다 하고 청크 순서로 합쳐요. 합친 결과(최솟값, 최댓값, 정렬 여부)는 직렬로 한 번 훑은 것과 같아요.

#### 히스토그램을 네 개로 나눠 세기

자리마다 다시 세는 것은 직렬 경로에 없는 패스예요. 히스토그램 하나로 세면 1스레드에서 이 구조가 약 1.3배 느렸어요.

```cpp
            // csrc/frame/ops/radix.hpp
            std::uint32_t h[4][256] = {};
            const std::uint64_t* k = keys.data();
            std::int64_t j = lo;
            for (; j + 4 <= hi; j += 4)
                for (int u = 0; u < 4; ++u) ++h[u][((k[j + u] - off) >> shift) & 0xff];
            for (; j < hi; ++j) ++h[0][((k[j] - off) >> shift) & 0xff];
            std::int64_t* out = at.data() + lo / kChunkRows * 256;
            for (int b = 0; b < 256; ++b) out[b] = std::int64_t{h[0][b]} + h[1][b] + h[2][b] + h[3][b];
```

`++h[x]`는 메모리에서 읽고, 1을 더하고, 다시 쓰는 일이에요. 다음 원소의 자리 값이 같으면 그 읽기는 방금의 쓰기가 끝나야 값을 받을 수 있어요(store-to-load forwarding). 같은 자리 값이 연달아 나오면 증가들이 한 줄로 이어진 **의존 사슬**이 되어, 원소마다 그 지연을 꼬박 기다려요. 위쪽 자리처럼 값이 몇 개 안 되는 자리에서 이 일이 심해요.

이웃한 원소 넷을 서로 다른 표에 세면 사슬이 넷으로 끊어져요. 원소 $j$와 $j+1$이 같은 자리 값이어도 다른 칸이라 서로 기다리지 않아요. 표 넷을 합치는 일은 자리 값마다 덧셈 셋, 256칸뿐이에요. 카운터는 `uint32_t`라 청크 하나(16K행)를 세기에 충분하고, 표 네 개가 4KB로 L1 캐시에 들어가요.

#### 자리 크기: 8비트

나누는 정렬의 자리를 11비트로 하면 패스가 줄지만, 10스레드에서 오히려 약 1.8배 느렸어요. 흩뿌리기는 상자마다 출력 위치가 하나씩 있는 **출력 스트림** $2^b$개에 나눠 쓰는 일이에요. 스트림마다 지금 쓰고 있는 캐시 줄(M4 Pro에서 128바이트)이 캐시에 머물러야 쓰기가 빨라요. 8비트면 256 스트림 × 배열 2개 × 128바이트 = 64KB로 P코어의 L1(128KB)에 들어가지만, 11비트면 2,048 스트림이라 512KB로 L1을 넘쳐요. 나누지 않는 정렬은 출력 흐름이 하나뿐인 스레드에서 도니 넓은 자리가 이득이에요.

### 나누지 않을 때

다음 둘 중 하나면 위의 병렬 구조 대신 직렬 패스(`radix_passes_serial`)를 써요.

- 풀을 쓸 수 없을 때(`parallel::available()`이 거짓): 1스레드이거나, 이미 다른 태스크 안이거나, 풀이 다른 Python 스레드의 일로 바쁠 때
- 키가 기준값 $2^{17}$개보다 적을 때. 그 아래에서는 직렬 정렬의 넓은 자리(패스가 적어요)가 바이트 자리로 나누는 정렬보다 빨랐어요.

```cpp
    // csrc/frame/ops/radix.hpp
    const bool split = parallel::available() && n >= kParallelThreshold;
    const Unlocked unlocked(split ? 0 : n * 2);  // the GIL rule of the passes (docs/design/frame.md §9.5)
    const KeyScan s = split ? scan_keys(keys) : scan_range(keys.data(), 0, n);
    if (s.nondecreasing) return;
    if (s.nonincreasing) {
        const Unlocked u(n);
        reverse_runs(keys, rows);
        return;
    }
    const RadixPlan p = plan_passes(s, digits, !split && n >= kWideRadixKeys);
    if (!split) {
        radix_passes_serial(keys, rows, p);
        return;
    }
```

두 경로는 결과가 같아서 바꿔 써도 돼요. 안정 정렬의 결과는 유일해요. 같은 키는 입력 순서, 다른 키는 키 순서라 놓일 자리가 하나로 정해져 있어요. 병렬 경로도 직렬 경로도 안정 정렬이니 같은 결과예요. 그래서 스레드 수를 보고 경로를 골라도 결과의 비트가 바뀌지 않아요. 결과가 나누는 방식에 따라 달라지는 float 합 같은 연산은 이렇게 하지 않고 길이로만 나눠요([병렬화와 결정성](/internals/frame/parallel/)).

직렬 경로는 히스토그램을 한 번에 세고 청크별 표가 없어서, 작은 입력에서 자리마다 세는 구조보다 빨라요(1천~1만 키에서 약 1.3배). `Unlocked(n * 2)`는 일이 기준값 이상이면 GIL을 놓아요. 직렬로 돌더라도 다른 Python 스레드가 그동안 돌 수 있게 하는 거예요.

## 문자열의 순서

### 8바이트 접두사로 기수 정렬

문자열은 길이가 제각각이라 64비트 키 하나에 다 담을 수 없어요. 그래서 `order_rows`는 8바이트씩 내려가요.

1. 문자열마다 앞 8바이트를 big-endian uint64로 읽어요(`string_prefix`). 8바이트보다 짧으면 0으로 채워요. 이 접두사로 기수 정렬해요.
2. 접두사가 같은 구간은 다음 8바이트(`string_key_at(s, 8)`)로 같은 일을 되풀이해요. 구간이 짧거나(128행 미만, `kStringRadixRun`) 구간의 어느 문자열에도 남은 바이트가 없으면 그 구간은 비교 정렬(`std::stable_sort`)로 끝내요.

가장 중요한 자리부터 나눠 내려가므로 MSD(most significant digit) 기수 정렬이에요. 한 깊이 안의 정렬은 위의 LSD 기수 정렬이고요.

```cpp
// csrc/frame/ops/radix.hpp
// The first 8 bytes of a string as a big-endian number (shorter strings
// padded with zero bytes): comparing prefixes compares the strings' first 8
// bytes in code point order (UTF-8 byte order).
inline std::uint64_t string_prefix(std::string_view s) {
    std::uint8_t b[8] = {};
    std::memcpy(b, s.data(), std::min<std::size_t>(8, s.size()));
    std::uint64_t k = 0;
    for (int j = 0; j < 8; ++j) k = (k << 8) | b[j];
    return k;
}
```

**big-endian으로 읽는 이유.** 사전식 순서는 첫 바이트가 가장 중요하고, 같으면 둘째 바이트, …예요. 첫 바이트를 정수의 맨 위 바이트에 두면 정수의 크기 비교가 정확히 이 순서가 돼요. Apple Silicon은 little-endian이라 8바이트를 그대로 `memcpy`해 정수로 읽으면 첫 바이트가 맨 아래 바이트가 되어 순서가 틀려요.

**UTF-8.** stardust의 문자열 순서는 코드포인트 순서예요. UTF-8은 바이트를 사전식으로 비교한 순서가 코드포인트 순서와 같도록 설계된 인코딩이라[9], 디코딩하지 않고 바이트만 비교해도 돼요.

| 문자열 | 접두사 (바이트) |
|:---:|:---:|
| `""` | `00 00 00 00 00 00 00 00` |
| `"Z"` | `5A 00 00 00 00 00 00 00` |
| `"a"` | `61 00 00 00 00 00 00 00` |
| `"a\0"` | `61 00 00 00 00 00 00 00` |
| `"apple"` | `61 70 70 6C 65 00 00 00` |
| `"applesauce"` | `61 70 70 6C 65 73 61 75` |
| `"b"` | `62 00 00 00 00 00 00 00` |
| `"가"` | `EA B0 80 00 00 00 00 00` |

**0으로 채워도 되는 이유.** 짧은 문자열을 0으로 채우면 `"a"`와 `"a\0"`(NUL 바이트 하나가 붙은 문자열)의 접두사가 같아져요. 0으로 채운 키는 어느 깊이에서도 같으니 둘은 끝까지 같은 구간에 남고, 남은 바이트가 없어지면 비교 정렬이 `std::string_view`의 비교로 `"a" < "a\0"`(짧은 쪽이 앞)을 정확히 가려요. 일반적으로 어느 깊이에서 키가 다르면 그 순서가 문자열의 순서와 같고, 끝까지 같으면 비교 정렬이 결정하니 결과는 언제나 바이트 사전식 순서예요.

```cpp
// csrc/frame/ops/radix.hpp
inline void order_string_run(const Column& c, std::int64_t* rows, std::int64_t len, std::size_t depth) {
    if (len < 2) return;
    bool more = false;  // a string longer than `depth`: a deeper level can tell rows apart
    if (len >= kStringRadixRun)
        for (std::int64_t j = 0; j < len && !more; ++j) more = c.string_at(rows[j]).size() > depth;
    if (!more) {
        std::stable_sort(rows, rows + len, [&](std::int64_t x, std::int64_t y) {
            return c.string_at(x) < c.string_at(y);
        });
        return;
    }
    std::vector<std::uint64_t> keys(static_cast<std::size_t>(len));
    std::vector<std::int64_t> sub(rows, rows + len);
    for (std::int64_t j = 0; j < len; ++j) keys[j] = string_key_at(c.string_at(sub[j]), depth);
    radix_sort_serial(keys, sub);
    std::copy(sub.begin(), sub.end(), rows);
    for (std::int64_t a = 0; a < len;) {
        std::int64_t b = a + 1;
        while (b < len && keys[b] == keys[a]) ++b;
        order_string_run(c, rows + a, b - a, depth + 8);
        a = b;
    }
}
```

- 첫 깊이 뒤의 구간은 시작하는 청크가 맡아요(`order_string_runs`). 청크는 자기 범위 앞에 걸친 구간(앞 청크에서 시작한 것)을 건너뛰고, 자기 범위에서 시작한 구간은 청크 끝을 넘어가도 끝까지 정렬해요. 구간끼리 겹치지 않으니 태스크끼리 독립이고, 어떤 구간도 두 번 정렬되거나 빠지지 않아요.
- 기준값($2^{17}$행) 이상인 긴 구간은 청크가 맡지 않고 따로 모아 두었다가, 호출 스레드가 하나씩 다음 8바이트로 병렬 기수 정렬하고 같은 방법으로 내려가요. 한 구간이 태스크 하나에 묶여 직렬로 도는 일을 막아요.
- 어느 경로로 가든 결과는 하나의 안정 정렬이라 같아요. 128행 기준과 기준값은 비용만 정해요.
- 무작위 키에서는 이 단계가 거의 일하지 않아요. 앞 8바이트가 거의 다 달라서 길이 2 이상인 구간이 드물어요.

```python
>>> t = sd.frame.Series(["b", "a", "apple", "가", "Z", None, "apples"])
>>> t.sort_values()
4         Z
1         a
2     apple
6    apples
0         b
3         가
5      <NA>
dtype: string
```

**왜 접두사로 먼저 나누나.** 고유 문자열 10만 개를 비교 정렬하면 비교가 약 $10^5 \log_2 10^5 \approx 170$만 번이고, 비교마다 두 문자열을 찾아가 `memcmp`해요. 접두사 기수 정렬은 문자열마다 한 번 8바이트를 읽고 나면 정수만 옮겨요. 같은 조건(1M 행, string 키 10만 종의 groupby, 1스레드)에서 접두사 기수 정렬이 고유값을 비교 정렬하는 설계보다 groupby 전체로 눈에 띄게 빨랐어요.

**왜 더 내려가나.** 흔한 키(`customer_…`, `https://…`)는 컬럼 전체가 앞 8바이트 하나를 나눠 가져요. 첫 접두사로만 나누고 구간을 비교 정렬하면 컬럼 전체가 구간 하나라서, 결국 직렬 비교 정렬 하나가 돼요. `customer_` 접두사가 붙은 고유 문자열 1M 개의 `sort_values`는 다음 8바이트로 내려가면 비교 정렬로 끝낼 때보다 1스레드 약 2배, 10스레드 약 8배 빨라요.

### 행은 고유값의 순위로

`order_rows`는 groupby의 그룹 순서에서도, `sort_values`에서도 써요. 다만 `sort_values`는 행 전체를 `order_rows`에 넣지 않고 고유값의 순위로 바꿔요.

```cpp
        // csrc/frame/ops/sort.cpp
        Factorized f = factorize(key);
        const auto* code = f.codes.data<std::int64_t>();
        std::vector<std::int64_t> distinct;
        for (std::int64_t g = 0; g < f.ngroups; ++g)
            if (key.is_valid(f.first.data<std::int64_t>()[g])) distinct.push_back(f.first.data<std::int64_t>()[g]);
        order_rows(key, distinct);
        std::vector<std::uint64_t> rank(static_cast<std::size_t>(f.ngroups));
        for (std::size_t r = 0; r < distinct.size(); ++r) rank[code[distinct[r]]] = r;
        std::vector<std::uint64_t> keys(rows.size());
        for_chunks(nv, [&](std::int64_t lo, std::int64_t hi) {
            for (std::int64_t j = lo; j < hi; ++j) {
                const std::uint64_t k = rank[code[rows[j]]];
                keys[j] = ascending ? k : ~k;
            }
        });
        // A rank is below the number of distinct strings: that count's bytes
        // are all the digits there are (radix.hpp).
        radix_sort(keys, rows, digits_for(distinct.empty() ? 0 : distinct.size() - 1));
```

1. 컬럼을 factorize해서 행마다 고유값 코드를 얻어요.
2. 고유값 $u$개만 `order_rows`로 정렬하고, 고유값마다 순위 $0..u-1$을 매겨요.
3. 행의 키는 자기 값의 순위예요. 이 키로 숫자와 똑같이 `radix_sort`해요.

- 방향이 정수 뒤집기로 끝나요. 내림차순은 `~순위`예요. 숫자 키와 같은 코드 경로를 타고, 같은 문자열끼리는 입력 순서를 지켜요. 문자열의 비교 함수를 뒤집은 정렬을 따로 두지 않아도 돼요.
- 문자열을 읽는 일이 고유값 사이에서만 일어나요. 같은 문자열이 몇 번 나오든 그 문자열은 순위 하나가 되고, `order_rows`에 한 번만 들어가요.
- 순위는 $u$보다 작으니 행의 기수 정렬은 많아야 $u - 1$을 담는 바이트 수만큼 패스해요(`digits_for`). 키 훑기가 실제로 다른 비트만 남기니 그보다 적을 수도 있어요.
- 다중 키에서 문자열과 숫자가 섞여도 돼요. 키마다 64비트 정수 키로 바뀌니 `argsort`의 "마지막 키부터 안정 정렬"이 dtype을 따지지 않아요.

대가는 행 전체를 한 번 factorize하는 해시 비용이에요. 행이 1M이고 고유값이 10만이면 해시 테이블에 1M 번 묻고, 기수 정렬은 1M 행에 많아야 3바이트 패스($10^5 - 1 < 2^{24}$, 넓은 자리면 2패스), `order_rows`는 10만 개에 대해 해요.

groupby의 그룹 순서(`sort_groups`)에서는 정렬할 대상이 이미 그룹마다 한 행이라, 고유값의 순위를 counting sort의 키로 바로 써요([그룹 순서](#그룹이-아니라-키-값을-정렬해요)).

## 병렬 counting sort: 2단계로

### 교과서 방법을 쓸 수 없는 이유

`counting_sort`는 groupby의 행 모으기(`Groups`), 그룹 순서(`sort_groups`), merge의 오른쪽 행 모으기([merge와 concat](/internals/frame/merge-concat/))가 써요. 행이 $2^{17}$개 미만이거나 풀을 쓸 수 없으면 위의 직렬 counting sort예요.

기수 정렬의 패스를 나눈 방법을 그대로 쓰면 (청크 × 키) 카운터가 필요해요. 기수 정렬은 키(자리 값)가 256종이라 문제없지만, counting sort의 키는 그룹 코드예요. 1M 행에 그룹 63만 개면 청크 62개 × 63만 = 약 3,900만 개 카운터(int64로 312MB)라, 데이터보다 훨씬 큰 표를 만들고 비워야 해요.

### 위쪽 비트로 버킷 256개, 그다음 버킷마다

그래서 두 단계로 해요.

1. **버킷으로 나누기:** 키 범위 $[0, K)$를 연속한 키 `width`개씩 버킷 $B \le 256$개로 나눠요. 키 $k$의 버킷은 `k >> wbits`예요. 이 버킷 번호로 기수 정렬의 한 패스와 똑같이 (청크 × 버킷) 카운터를 써서 안정적으로 흩뿌려요. 카운터는 $62 \times 256$개뿐이에요.
2. **버킷마다 counting sort:** 각 버킷은 자기 키 `width`개만 담당하는 작은 직렬 counting sort를 해요. 버킷끼리 독립이라 버킷이 태스크예요.

```cpp
// csrc/frame/ops/radix.hpp
// `width` is a power of two, so a key's bucket is a shift (a division
// per position cost more than the whole serial counting sort).
const std::int64_t buckets = 256;
int wbits = 0;
while ((std::int64_t{1} << wbits) * buckets < nkeys) ++wbits;
const std::int64_t width = std::int64_t{1} << wbits;
const std::int64_t B = std::max<std::int64_t>(1, (nkeys + width - 1) / width);
// ...
parallel::parallel_for(B, [&](std::int64_t b) {
    const std::int64_t k0 = std::min(nkeys, b * width), k1 = std::min(nkeys, (b + 1) * width);
    const std::int64_t r0 = bstart[static_cast<std::size_t>(b)], r1 = bstart[static_cast<std::size_t>(b) + 1];
    // Local counts: start[k0] belongs to the bucket before (it ends
    // there), so a bucket writes start only at (k0, k1].
    std::vector<std::int64_t> fill(static_cast<std::size_t>(k1 - k0), 0);
    for (std::int64_t j = r0; j < r1; ++j)
        ++fill[static_cast<std::size_t>(key[by_bucket[static_cast<std::size_t>(j)]] - k0)];
    std::int64_t at_pos = r0;
    for (std::int64_t k = k0; k < k1; ++k) {
        const std::int64_t c = fill[static_cast<std::size_t>(k - k0)];
        fill[static_cast<std::size_t>(k - k0)] = at_pos;
        at_pos += c;
        start[static_cast<std::size_t>(k) + 1] = at_pos;
    }
    for (std::int64_t j = r0; j < r1; ++j) {
        const std::int64_t i = by_bucket[static_cast<std::size_t>(j)];
        perm[static_cast<std::size_t>(fill[static_cast<std::size_t>(key[i] - k0)]++)] =
            i;  // stable: order within a key
    }
});
```

| 그룹 수 $K$ | `width` | 버킷 수 $B$ |
|---:|---:|---:|
| 1,000 | 4 | 250 |
| 100,000 | 512 | 196 |
| 630,000 | 4,096 | 154 |

- 결과는 직렬 counting sort와 같아요. 1단계는 버킷 번호에 대한 안정 정렬이라, 같은 버킷의 위치들이 원래 순서로 놓여요. 2단계는 그 순서를 입력으로 하는 안정 counting sort예요. 버킷 번호는 키의 위쪽 비트이고 2단계는 버킷 안의 키 전체로 정렬하니, 두 단계를 합치면 키에 대한 안정 정렬이에요. 기수 정렬의 2자리 버전(위쪽 비트가 높은 자리, 버킷 안의 키가 낮은 자리)을 MSD 순서로 한 것으로 볼 수 있어요. 그래서 이 연산도 [나누지 않을 때](#나누지-않을-때)처럼 스레드 수를 따라 직렬과 병렬을 골라도 같은 결과예요.
- `width`는 2의 거듭제곱이에요. 버킷 번호가 시프트 하나(`k >> wbits`)예요. `k / width`로 나누면 행마다 정수 나눗셈 하나가 드는데, 그 나눗셈만으로 직렬 counting sort 전체보다 비쌌어요.
- **버킷 경계의 `start` 칸.** `start[k]`는 "키 $k$보다 앞선 위치의 수"이고, 버킷 $b$의 첫 키 $k_0$의 `start[k0]`은 앞 버킷의 마지막 키가 끝나는 곳과 같은 칸이에요. 두 버킷이 이 칸을 함께 쓰면 쓰기 경쟁이 생기니, 버킷은 `start[k+1]`만 써서 $(k_0, k_1]$ 칸을 맡아요. `start[0]`은 처음부터 0이에요.
- 2단계의 지역 카운터 `fill`은 버킷마다 `width`칸이라, 63만 그룹에서도 4,096칸(32KB)으로 L1에 들어가요.

Index의 조회 엔진도 라벨의 모든 위치를 묻는 조회(`.loc` 라벨 하나, 라벨 리스트, 라벨 슬라이스의 양 끝)를 처음 할 때 라벨 코드로 CSR을 만드는데, 그쪽은 `LabelTable` 안에 같은 방식의 직렬 counting sort를 따로 두고 있어요([라벨, 조회, 선택](/internals/frame/labels/)).

## 배열 영역의 정렬과 비교

배열 영역의 `sort`, `argsort`([정렬과 집합](/internals/array/sorting/))와 순서 규칙은 같고, 구현은 여러 곳이 달라요.

| | 배열 (`csrc/array/ops/sort.cpp`) | frame (`csrc/frame/ops/radix.hpp`, `sort.cpp`) |
|---|---|---|
| 순서 규칙 | NaN이 가장 큼, `-0.0 == 0.0`, 내림차순은 정확한 거울, 안정 | 같아요. 여기에 NA는 `na_position`으로 따로 |
| NaN 처리 | 정렬 전에 NaN을 떼어 놓아요 | `float_key`가 NaN을 하나로 모아 +inf 위의 키가 돼요 |
| 알고리즘 선택 | dtype과 길이로 NEON 정렬, 기수 정렬, merge sort, introsort 중 하나 | 숫자와 bool은 언제나 LSD 기수 정렬(이미 정렬된 키와 역순 키는 따로), 문자열은 순위 + 기수 정렬 |
| 기수 정렬이 옮기는 것 | (값, 인덱스) 16바이트 쌍, 키는 패스마다 다시 계산 | 키 배열과 행 배열, 키는 한 번 계산 |
| 자리 수 | 최솟값을 빼고, 모든 키가 같은 자리를 건너뛰어요 | 같아요. `키 − 최솟값`의 비트와 서로 다른 바이트 중 패스가 적은 쪽, 직렬은 11비트 이하의 넓은 자리도 |
| 히스토그램 | 직렬은 한 번에, 병렬은 조각마다 자리별로 | 직렬은 한 번에 모든 자리, 병렬은 청크마다 네 개로 나눠 자리별로 |
| 병렬 | 긴 레인은 조각 + merge path 병합, 기수 정렬은 자리마다 병렬 | 기수 정렬은 자리마다 병렬(청크 16K행), 병합 단계 없음 |
| 직렬로 바꾸는 조건 | 풀을 쓸 수 있을 때만 조각으로 | 풀을 쓸 수 없거나 $n < 2^{17}$이면 직렬 |
| 문자열 | 없음 | 8바이트씩 내려가는 MSD 기수 정렬 + 짧은 구간 비교, 고유값 순위 |

frame이 모든 숫자 정렬에 기수 정렬을 쓰는 것은 frame의 정렬이 언제나 행 번호를 돌려주는 argsort이기 때문이에요. `sort_values`도 순서를 구한 뒤 모든 컬럼을 `take`해요. 배열 영역에서도 (값, 인덱스) 쌍의 정렬은 128개부터 기수 정렬이 merge sort보다 빨라요. 값만 정렬하는 NEON 정렬 같은 빠른 길은 결과가 행 번호인 frame에는 맞지 않아요(같은 값의 순서가 드러나요).

## pandas, Polars와 비교

| | stardust | pandas 3.1.1 | Polars 2.1.0 |
|---|---|---|---|
| 그룹 float 합 | 그룹의 행을 모아 pairwise 합. 고른 Series의 `sum()`과 비트가 같음 | 행 순서로 흩뿌리며 그룹마다 Kahan 합. Series의 `sum()`과 마지막 비트가 다를 수 있음 | — |
| 그룹 순서의 기본값 | 키 오름차순(`sort=True`), NA 그룹은 `dropna=True`면 빠짐 | 키 오름차순(`sort=True`) | 보장하지 않음(`maintain_order=False`) |
| 그룹 순서 구하기 | 숫자 키 하나는 대표값의 기수 정렬, 그 밖에는 키마다 고유값 순위 + counting sort | `factorize(sort=True)`, 키가 이미 정렬되어 있으면 빠른 길 | 따로 정렬 |
| 정렬의 안정성 | 언제나 안정 | `kind`로 고름(기본 `"quicksort"`) | `DataFrame.sort`의 `maintain_order=False`가 기본 |
| NaN | 값. +inf보다 큼. 내림차순에서 맨 앞 | 결측으로 취급해 `na_position` 쪽 | 가장 큰 값 |
| 결측 | NA, 기본 맨 뒤 | NaN/None, 기본 맨 뒤 | null, `Series.sort`는 기본 맨 앞(`nulls_last=False`) |

예를 들어 `[3.0, NaN, -0.0, None, 1.0, 0.0]`을 pandas의 `sort_values(kind="stable")`로 정렬하면 `[-0.0, 0.0, 1.0, 3.0, nan, nan]`이고(None도 NaN), 내림차순에서도 NaN이 맨 뒤예요. Polars의 `Series.sort()`는 `[None, -0.0, 0.0, 1.0, 3.0, nan]`처럼 null을 맨 앞, NaN을 맨 뒤에 둬요.

## 성능

### 복잡도

| 연산 | 시간 | 추가 메모리 |
|---|---|---|
| groupby 행 모으기 | $O(n + G)$ | `rows` $8n$(그룹이 구간이면 없음) + `start` $8(G+1)$ 바이트 |
| 그룹마다 집계 | $O(n)$ (var·std는 두 번 훑기) | 결과 $G$칸 |
| 그룹 순서, 키 $m$개 | 키마다 $O(G)$ factorize + $O(u)$ 기수 정렬 + $O(G + u)$ counting sort (숫자 키 하나는 $O(G)$ 기수 정렬 하나) | $O(G)$ |
| 숫자 키 정렬, 키 $m$개 | $O(P m n)$, $P$는 키가 다른 자리의 패스 수(많아야 8), 이미 정렬된 키는 읽기 한 번. 비교 없음 | $32n$ 바이트 (키, 행, 임시 둘) |
| 문자열 키 정렬 | $O(n)$ factorize + 고유값 $u$개의 8바이트씩 기수 정렬과 짧은 구간 비교 + $O(n \lceil \log_{256} u \rceil)$ | $32n$ 바이트 + 순위 $8u$ |

$G$는 그룹 수, $u$는 고유값 수예요. groupby 전체에서는 factorize(해시)가 가장 무거운 단계인 경우가 많아요([해시 테이블과 factorize](/internals/frame/hashing/)).

### pandas, Polars와 견주는 입력

입력은 무작위예요. `groupby int 1k`는 키 $[0, 1000)$, `groupby int, n keys`는 키 $[0, n)$(1M 행이면 고유값 약 63만), `groupby string`은 `"key0"`…`"key99999"` 꼴의 문자열 키(1M 행이면 10만 종), `groupby int + string`은 두 키를 함께 쓰고, 값은 표준정규분포 float이에요. `sort int64`는 $[0, n)$의 int64, `sort string`은 같은 문자열 컬럼이에요. pandas 정렬은 `kind="stable"`, Polars groupby는 결과를 키로 정렬해 같은 일을 하게 했어요.

이 입력의 성질에서 알 수 있는 점이에요.

- `sort int64`는 건너뛸 수 있는 자리가 많은 입력이에요. 키가 $[0, n)$이라 1M 행에서도 20비트뿐이라, 직렬이면 넓은 자리 2패스, 나누면 바이트 3패스예요([필요한 패스만 돌아요](#필요한-패스만-돌아요)).
- `sort string`의 문자열은 모두 8바이트 이하예요(`"key99999"`가 가장 길어요). 접두사가 문자열 전체라 구간 비교가 없고, 시간은 factorize와 두 번의 기수 정렬(고유값의 접두사, 행의 순위)이에요.
- 키가 많은 groupby는 factorize가 무거워요. 고유값 63만 종이면 해시 테이블이 캐시에 들어가지 않아요. 그 단계의 비용과 Polars와의 차이는 [해시 테이블과 factorize](/internals/frame/hashing/)에 있어요.
- 10만 행은 대부분 1스레드예요. groupby의 집계, 8바이트 키의 factorize, 기수 정렬은 기준값 $2^{17}$보다 작은 일을 나누지 않아요. 문자열 factorize와 값 컬럼이 많은 groupby는 이 크기에서도 나눠요.

### 스레드 확장

1M 행 정렬의 1스레드 대비 10스레드 배율은 벤치마크의 생성 표에 있어요. 기수 정렬은 패스마다 세기, 직렬 누적합, 흩뿌리기가 이어지고, 흩뿌리기는 16바이트 × n을 읽고 쓰는 메모리 대역폭 일이라 스레드 수만큼 빨라지지는 않아요.

## 정확도와 결정성

- 그룹 합, 평균, 분산은 그 그룹의 행만 고른 Series의 리덕션과 비트까지 같아요. 같은 값을 같은 순서로 같은 pairwise 트리에 넣기 때문이에요. int64의 평균은 두 쪽 모두 정확한 정수 합이라 그룹 크기와 상관없이 같아요.
- 정렬 결과는 유일해요. 언제나 안정 정렬이라 같은 입력의 결과 순서는 하나로 정해져 있고, `stable=False`도 같은 순서예요. 테스트는 Python의 `sorted()`(`reverse=True`에서도 안정)를 정답으로 써요.
- 같은 입력이면 실행마다 같은 결과예요. 지금은 스레드 수와도 상관없이 같아요(약속은 아니에요). groupby 집계는 그룹마다 독립이고, 기수 정렬과 counting sort는 병렬 경로에서도 원소가 직렬과 같은 칸에 놓여요. 그래서 1스레드에서 다른 알고리즘(직렬 정렬)을 써도, 데이터에 따라 다른 길(이미 정렬됨, 역순 묶음, 넓은 자리)로 가도 결과가 같아요. 테스트는 1, 3, 기본 스레드 수에서 같은 결과(값의 비트와 행 순서)가 나오는지 비교해요.
- 같은 키와 같은 순서가 맞물려요. factorize와 정렬 키가 같은 `float_key`에서 시작하니, groupby에서 한 그룹인 값들은 정렬에서도 같은 값이에요.
