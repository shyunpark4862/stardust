## 한눈에 보기

데이터프레임 영역(`sd.frame`)은 스레드풀을 따로 갖지 않아요. 배열, 선형대수, 특수함수와 함께 쓰는 풀 하나(`csrc/parallel/pool.*`) 위에서 돌고, 언제 나누고 얼마나 잘게 나눌지만 이 영역이 정해요. 그 정책이 `csrc/frame/parallel.hpp` 한 파일, 약 70줄이에요.

| 층 | 하는 일 | 어디에 |
|---|---|---|
| 풀 | 태스크 번호 `0 … ntasks-1`을 여러 스레드에 나눠 돌려요. 언제 나눌지는 모르고, 나누라는 대로 나눠요 | `parallel/pool.hpp`, `pool.cpp` |
| frame의 정책 | 기준값 2¹⁷(131,072), 청크 2¹⁴(16,384)행, `for_chunks`, `run_unlocked`, `Unlocked` | `frame/parallel.hpp` |
| 각 커널 | 청크마다 무엇을 계산하고, 청크의 부분 결과를 어떤 순서로 합칠지 | `frame/ops/*.cpp`, `frame/io/csv.cpp` |

뼈대는 다섯 가지예요.

1. **일이 작으면 나누지 않아요.** 행 수(에 커널의 무게를 곱한 값)가 2¹⁷보다 작으면 호출한 스레드에서 차례로 돌아요. 풀을 깨우는 고정 비용이 계산 시간보다 클 수 있는 크기예요.
2. **자르는 위치는 행 수로만 정해요.** 청크는 언제나 16,384행씩이고 마지막 청크만 짧아요. 스레드가 몇 개든 청크의 경계는 같아요.
3. **부분 결과는 고정된 순서로 합쳐요.** 청크 순서, 또는 numpy의 pairwise 합과 같은 트리 순서예요. 그래서 float 합, 행 순서, factorize 코드, 에러 메시지가 스레드 수와 상관없이 비트까지 같아요.
4. **결과가 나누는 방식과 무관하게 정확히 정해지는 연산은 예외예요.** factorize, 기수 정렬, counting sort, CSV 읽기는 1스레드일 때 나누지 않는 직렬 알고리즘을 써요. 어떻게 나눠도 답이 하나뿐이라서 결과가 같고, 1스레드가 쓸데없는 패스를 내지 않아요.
5. **일이 기준값 이상이면 계산하는 동안 GIL을 놓아요.** 스레드 수와 상관없어요. 풀로 나눠 돌든, 1스레드라서 호출 스레드가 청크를 차례로 돌든, 나누지 않는 직렬 구간이든 놓아요. 그동안 다른 Python 스레드가 돌아요. 기준값 아래의 작은 호출은 GIL을 쥔 채 돌아서 놓고 다시 잡는 비용을 내지 않아요.

## 공용 스레드풀

풀 자체는 [스레드풀과 결정성](/internals/core/threads/)이 자세히 다뤄요. 여기서는 frame이 기대는 성질만 짧게 모아요.

- **상주 워커와 카운터 하나.** 워커 스레드는 처음 한 번 만들어 두고 살려 둬요. 일이 오면 워커들과 호출한 스레드 자신이 공유 atomic 카운터에서 다음 태스크 번호를 집어 가요. 누가 어느 태스크를 맡을지 미리 정하지 않으므로 빠른 스레드가 더 많이 집어 가요. 그래서 청크의 일이 고르지 않아도(예: 어떤 청크에 NA가 몰려 있어도) 한 스레드가 늦게 끝나 모두를 기다리게 하는 일이 줄어요.
- 기본 스레드 수는 P코어 수예요. Apple M4 Pro에서는 10이에요. E코어까지 14개를 쓰면 메모리에 묶인 연산이 오히려 느려져서 P코어만 써요.
- **spin 후 잠들기.** 일이 끝난 워커는 최대 100µs 동안 다음 일을 기다리며 돌아요. 그 안에 새 일이 오면 병렬 호출의 고정 비용이 약 1.5µs이고, 잠든 워커를 깨워야 하면 약 25µs예요. 이 고정 비용이 아래 기준값을 정해요.
- **`available()`.** 스레드가 2개 이상이고, 지금 태스크 안이 아니고(중첩 금지), 풀이 다른 Python 스레드의 일로 바쁘지 않을 때 참이에요. frame의 몇몇 알고리즘(factorize, 기수 정렬, counting sort, CSV)은 이 값을 보고 나누는 경로와 직렬 경로 중 하나를 골라요.
- 바쁘면 기다리지 않아요. 다른 Python 스레드가 큰 일로 풀을 쓰는 중이면, 두 번째 호출은 줄을 서지도, 풀을 나눠 쓰지도 않고 자기 스레드에서 혼자 돌아요. 결과는 같아요(아래 "결정성").
- 스레드 수 API는 하나예요. `sd.set_num_threads(n)`, `sd.get_num_threads()`예요. `sd.frame`에는 따로 없어요. 풀이 하나라서 한 번 바꾸면 모든 영역에 적용돼요.

### pandas와 Polars는 어떻게 하나

- **pandas 3.1.1**은 연산 하나를 한 스레드로 돌려요. 산술은 numpy의 루프, groupby와 해시는 Cython 루프, `read_csv`의 기본 엔진은 C 토크나이저인데 모두 한 스레드예요. 선택 의존성인 numexpr(큰 산술을 여러 스레드로)이나 pyarrow 엔진을 깔면 일부가 여러 스레드를 쓰지만, 이 사이트의 비교 측정 환경에는 numexpr, bottleneck, pyarrow가 모두 없어요.
- **Polars 2.1.0**은 Rust의 rayon 크레이트가 만든 전역 스레드풀 하나를 써요(`crates/polars-core/src/runtime.rs`의 `THREAD_POOL`) [3]. rayon은 작업 훔치기(work stealing) 방식이에요. 스레드마다 할 일의 덱을 두고, 자기 덱이 비면 남의 덱에서 가져와요 [4]. 스레드 수는 `POLARS_MAX_THREADS` 환경 변수로 프로세스가 시작할 때 한 번 정하고 그 뒤로는 바꿀 수 없어요(`pl.thread_pool_size()` 문서). 기본값은 이 기계에서 14(E코어를 포함한 모든 코어)예요.
- stardust는 프로세스 안에서 `sd.set_num_threads`로 언제든 바꿀 수 있어요. 바꾸는 동안 다른 스레드가 풀을 쓰고 있으면 그 일이 끝나기를 기다렸다가 워커를 다시 만들어요.

## frame의 정책: `frame/parallel.hpp`

정책 전체가 다음 몇 줄이에요(발췌, 주석은 줄였어요).

```cpp
// csrc/frame/parallel.hpp
namespace sd::frame {

inline constexpr std::int64_t kParallelThreshold = 1 << 17;   // 131,072
inline constexpr std::int64_t kChunkRows         = 1 << 14;   // 16,384, 64의 배수

inline std::int64_t num_chunks(std::int64_t n) { return (n + kChunkRows - 1) / kChunkRows; }

// 기준값 이상의 일: 태스크 수, 스레드 수와 상관없이 GIL을 놓고 parallel_for를 부른다.
template <class F>
void run_unlocked(std::int64_t ntasks, F&& fn) {
    const parallel::Unlocked unlocked(true);
    parallel::parallel_for(ntasks, fn);
}

// f(lo, hi)를 청크 [lo, hi)마다. 청크는 n으로만 정해진다.
template <class F>
void for_chunks(std::int64_t n, F&& f, std::int64_t cost = 1) {
    if (n <= 0) return;
    const std::int64_t ntasks = num_chunks(n);
    auto task = [&](std::int64_t t) { f(t * kChunkRows, std::min(n, (t + 1) * kChunkRows)); };
    if (n * cost < kParallelThreshold) {              // 작은 일: 호출 스레드에서, GIL을 쥔 채
        for (std::int64_t t = 0; t < ntasks; ++t) task(t);
        return;
    }
    run_unlocked(ntasks, task);                       // 큰 일: GIL을 놓고 풀로
}

// 직렬 구간에서 GIL을 놓는다. work가 기준값 아래면 아무것도 하지 않는다.
class Unlocked : public parallel::Unlocked {
public:
    explicit Unlocked(std::int64_t work) : parallel::Unlocked(work >= kParallelThreshold) {}
};

}  // namespace sd::frame
```

| 이름 | 값 | 뜻 |
|---|---|---|
| `kParallelThreshold` | 2¹⁷ = 131,072 | 이보다 작은 일은 호출 스레드에서 돌아요 |
| `kChunkRows` | 2¹⁴ = 16,384행 | `for_chunks`의 청크 하나 |
| `num_chunks(n)` | ⌈n / 16384⌉ | 청크별 부분 결과를 담을 배열의 길이 |
| `for_chunks(n, f, cost)` | | `f(lo, hi)`를 청크마다. `n × cost`가 기준값 아래면 차례로, 아니면 `run_unlocked` |
| `run_unlocked(ntasks, fn)` | | GIL을 놓은 채로 `parallel_for(ntasks, fn)`을 불러요. 기준값 이상인지는 부르는 쪽이 이미 따진 뒤예요 |
| `Unlocked(work)` | | `work`가 기준값 이상이면 그 객체가 사는 동안 GIL을 놓아요. 공용 `parallel::Unlocked`에 frame의 기준값을 붙인 것이에요 |

- 작은 일에서도 청크로 돌아요. 기준값 아래에서도 `f`는 청크 0, 1, 2, …로 나뉘어 불려요. 1스레드와 10스레드가 같은 청크를 같은 크기로 계산한다는 뜻이고, 결정성의 바탕이에요. 청크 하나가 16K행이라 직렬로 돌 때 생기는 비용은 함수 호출 몇 번뿐이에요.
- `f`는 청크 경계를 받아요. 원소 하나마다 함수를 부르지 않아요. 청크 안의 루프는 커널이 직접 쓰고, 컴파일러가 그 루프를 벡터화할 수 있게 포인터와 경계를 지역 변수로 복사해 둬요([원소별 연산과 리덕션](/internals/frame/elementwise/)).
- `std::function`은 한 번만 거쳐요. `parallel_for`는 `std::function`으로 태스크를 받아요. 간접 호출은 태스크(16K행)마다 한 번이라 비용이 보이지 않아요.

### 무거운 커널은 기준값을 옮겨요: `cost`

행마다 하는 일이 덧셈 한 번보다 몇 배 무거운 커널은 `cost`를 넘겨요. `n × cost`를 기준값과 비교하므로, 무게가 `c`인 커널은 2¹⁷/c행부터 나눠요. 청크의 크기는 바꾸지 않아요. 청크까지 바꾸면 그 커널의 부분 결과 배치가 다른 커널과 달라져 규칙이 늘어나요.

| `cost` | 나누기 시작하는 행 수 | 쓰는 곳 |
|:---:|---:|---|
| 1 | 131,072 | 원소별 연산, 필터, take, 정수 합, min/max, float 합 |
| 2 | 65,536 | 기수 정렬의 흩뿌리기(`radix.hpp`) |
| 4 | 32,768 | 문자열 비교, 문자열의 8바이트 접두사 만들기, 해시 분할 factorize의 해시 계산과 번호 매기기, `var`/`std`의 제곱 편차 합 |
| 8 | 16,384 | 문자열 → 숫자 파싱(`astype`), 접두사가 같은 문자열 구간의 비교 정렬, 해시 조회(`find_rows`) |
| 16 | 8,192 | 숫자 → 문자열 서식(`astype("string")`, Python `str(float)`과 같은 글자) |

`cost`는 측정에 맞춘 정밀한 값이 아니라 "덧셈 한 번의 몇 배쯤인가"를 나타내는 2의 거듭제곱이에요. float 하나를 Python `repr`과 같은 글자로 쓰는 일은 덧셈보다 수십 배 무겁고, 8천 행만 돼도 나누는 쪽이 이득이에요.

## 기준값 2¹⁷

### 무엇과 무엇을 비교하나

나누면 두 가지 비용이 생겨요.

1. **풀을 움직이는 고정 비용.** 워커가 spin 중이면 호출 한 번에 약 1.5µs, 잠들어 있으면 깨우는 데 약 25µs예요. 일을 끝낸 뒤 모든 워커의 완료 보고를 기다리는 시간도 여기에 들어가요.
2. **청크별 부분 결과를 합치는 비용.** 필터라면 청크마다 남는 행 수를 세는 패스가 하나 더 생기고, 합이라면 청크의 부분 합을 다시 접어요.

기준값은 "10스레드가 1스레드를 이기기 시작하는 크기"예요. 청크가 16K행이므로 2¹⁶(65,536)행이면 태스크가 4개뿐이에요. 10스레드 중 4개만 일하고, 고정 비용은 그대로 내요. 그래서 이 크기에서도 10스레드가 `f + g`, `sum`, `isna`에서 졌어요. 2¹⁷(131,072)행, 태스크 8개부터 이겨요. 기준값을 낮춘 빌드에서 131,072행을 잰 값이에요(Apple M4 Pro).

| 연산 (131,072행) | 1스레드 | 10스레드 |
|---|---:|---:|
| `f + g` (float64) | 14 µs | 8 µs |
| `sum` (float64) | 13 µs | 5 µs |
| 마스크 필터 | 43 µs | 19 µs |

### 배열 영역과 값이 달라요

배열 영역의 기준값은 2¹⁵(float64 원소 32,768개)이고, 태스크 하나는 원소 4,096개예요([스레드풀과 결정성](/internals/core/threads/)). frame은 2¹⁷이에요. 이름(`kParallelThreshold`)은 같고, 배열은 `sd` 이름공간에, frame은 `sd::frame`에 있어서 각 영역의 코드가 자기 값을 찾아요. 값이 다른 이유는 각 영역이 자기 커널로 쟀기 때문이에요.

- frame의 청크는 배열의 태스크보다 4배 커요(아래 "청크 16K행"). 같은 기준값이면 frame 쪽 태스크 수가 4분의 1이라 고정 비용을 이기기 어려워요.
- frame의 커널은 결과 Column의 validity 비트맵, NA 개수(`null_count`)를 함께 만들고, 결과마다 부분 결과 배열(청크별 개수, 청크별 시작 위치)을 둬요. 같은 크기에서 배열 커널보다 앞뒤로 하는 일이 조금 더 있어요.

### 상수 하나예요

연산마다 다른 기준값을 두지 않아요. 연산마다 따로 두면 그 값마다 측정과 근거를 따로 지켜야 하고, 무거운 연산은 이미 `cost`로 나누는 시점을 앞당겨요. 대가도 있어요. 10만 행은 2¹⁷보다 작아서 `cost`가 1인 커널(원소별 연산, 필터, 합)과 해시 분할 factorize(아래)가 1스레드로 돌아요. 반면 Polars는 더 작은 크기부터 나누는 연산이 있어서, 이 크기에서 Polars 14스레드가 앞서는 줄이 생겨요. 수치와 원인은 [성능과 검증](/internals/frame/performance/)에 있어요.

10만 행에서도 나누는 것은 `cost`가 큰 커널(기수 정렬의 흩뿌리기는 65,536행부터), 그리고 바이트 크기로 나누는 CSV예요(아래 "CSV").

## 청크 16K행

### 64의 배수: 비트맵의 바이트를 나눠 갖지 않아요

frame의 Column은 결측을 validity 비트맵으로 표시해요. 행 하나가 비트 하나이고, 8행이 바이트 하나예요([컬럼과 메모리](/internals/frame/columns/)). 두 태스크가 같은 바이트의 다른 비트를 동시에 쓰면 읽기-수정-쓰기가 겹쳐서 한쪽의 쓰기가 사라져요. 비트 쓰기를 atomic으로 하면 해결되지만 행마다 atomic 연산을 내야 해요.

청크가 64행의 배수이면 청크 경계가 언제나 64비트 워드 경계에 떨어져요. 태스크마다 자기 비트맵 바이트를 맡고, 평범한 쓰기로 경쟁 없이 써요.

경계가 캐시 라인과도 맞아요. 16,384행의 비트맵은 2,048바이트(캐시 라인 16개), int64·float64 값은 128KB예요. `Buffer`는 언제나 128바이트 경계에서 시작하므로(`base/buffer.hpp`의 `kAlignment`), 새로 만든 결과 버퍼에서 두 태스크가 같은 캐시 라인에 쓰는 일이 없어요. 같은 캐시 라인을 두 코어가 번갈아 쓰면 그 줄이 코어 사이를 오가요(거짓 공유, false sharing). 값의 바이트가 겹치지 않아도 생기는 비용이라 경계를 맞춰 둬요.

### 청크는 n으로만 정해져요

청크 `t`는 언제나 `[t × 16384, min(n, (t+1) × 16384))`예요. 스레드 수, 풀의 상태, 입력 값과 무관해요. 그래서 "청크마다 부분 결과를 만들고 청크 순서로 합친다"는 커널은 스레드 수와 상관없이 같은 계산을 해요. 이 성질을 쓰는 커널은 다음과 같아요.

- 원소별 연산, `astype`, `isna`: 행마다 따로 계산하고 결과 자리가 정해져 있어요.
- 필터와 압축: 청크마다 남는 행 수 → 시작 위치 → 각 청크가 자기 자리에 써요.
- 문자열 결과(문자열 이어 붙이기, 숫자 → 문자열): 청크마다 바이트 수 → 시작 위치.
- 정수 합, min/max: 청크마다 부분 결과 → 청크 순서로 접기.
- `valid_bytes`: 비트맵을 행마다 1바이트로 펼치기(`bitmap::expand`).

### 16K라는 크기

- **태스크 수.** 기준값 2¹⁷에서 태스크가 8개, 1M 행에서 62개예요. 10스레드가 1M 행을 나누면 스레드마다 6~7개를 집어 가므로, 마지막에 한두 스레드만 일하는 꼬리가 짧아요.
- **스택 버퍼 하나에 들어가요.** 결과를 마무리하는 `finish_fixed`는 NA인 행의 값을 0으로 만들어요(NA 자리의 값은 언제나 0이에요). 분기 없이 하려고 청크의 비트를 행마다 1바이트(0 또는 1)로 펼친 뒤, 값마다 `0 - m`(모든 비트가 1 또는 0)과 AND를 해요. 펼친 바이트는 `std::uint8_t m[kChunkRows]`, 16KB짜리 스택 배열 하나에 들어가고, P코어의 L1 데이터 캐시(128KB) 안에 남아요.
- **청크별 표가 작아요.** 기수 정렬과 해시 분할은 (청크 × 256)개의 카운터를 둬요. 1M 행이면 62 × 256 = 15,872개예요. 청크가 4분의 1이면 표가 4배가 되고, 그 표를 누적합으로 바꾸는 직렬 단계도 4배가 돼요.

```cpp
// csrc/frame/column.cpp, finish_fixed의 핵심 (발췌)
for_chunks(col.length, [bits, v](std::int64_t lo, std::int64_t hi) {
    std::uint8_t m[kChunkRows];                    // 16KB, 청크 하나 분량
    const std::int64_t len = hi - lo;
    bitmap::expand(bits + lo / 8, len, m);         // lo는 8의 배수(실제로는 64의 배수)
    T* w = v + lo;
    for (std::int64_t i = 0; i < len; ++i)
        w[i] &= static_cast<T>(0 - static_cast<T>(m[i]));   // NA면 0, 아니면 그대로
});
```

### 세고, 누적합을 내고, 쓰기

결과의 길이를 미리 모르는 커널(필터, 문자열 결과, merge의 출력)은 같은 꼴을 따라요. 병렬 prefix sum(scan)의 가장 단순한 형태예요 [5].

1. 청크마다 결과 개수(행 수나 바이트 수)를 세요. 청크 병렬.
2. 그 개수들의 누적합으로 청크마다 시작 위치를 정해요. 청크가 62개뿐이라 직렬로 해요.
3. 청크마다 자기 시작 위치부터 써요. 청크 병렬.

```cpp
// csrc/frame/ops/selection.cpp (발췌)
template <class Count>
std::vector<std::int64_t> chunk_starts(std::int64_t n, Count count, std::int64_t cost = 1) {
    std::vector<std::int64_t> start(num_chunks(n) + 1, 0);
    for_chunks(n, [&](std::int64_t lo, std::int64_t hi) { start[lo / kChunkRows + 1] = count(lo, hi); }, cost);
    for (std::size_t c = 1; c < start.size(); ++c) start[c] += start[c - 1];   // 청크 순서로
    return start;
}
```

세는 패스가 하나 더 들지만, 이 패스는 마스크(1바이트씩)만 읽으므로 값을 옮기는 패스보다 가벼워요. 1스레드에서도 같은 두 패스를 해요. 그래서 1스레드와 10스레드가 같은 일을 하고, 1스레드는 "나누지 않는 다른 알고리즘"으로 바뀌지 않아요.

### groupby는 그룹을 묶어요

groupby의 집계는 행이 아니라 그룹을 나눠요. 그룹은 counting sort로 모은 행 목록(`start`, `rows`)을 가지므로, 그룹 경계에서만 자를 수 있어요. `Groups::for_groups`는 약 16K행마다 그 행이 속한 그룹 경계로 자르고, 연속한 그룹 묶음 하나를 태스크 하나로 해요.

```cpp
// csrc/frame/ops/groupby.cpp (발췌)
template <class F>
void Groups::for_groups(F f) const {
    const std::int64_t n = rows_.size();
    if (n < kParallelThreshold) { f(0, ngroups_); return; }
    std::vector<std::int64_t> cuts{0};
    for (std::int64_t r = kChunkRows; r < n; r += kChunkRows) {
        // r번째 행이 시작하는 그룹 이후에서 자른다
        const auto g = std::lower_bound(start_.begin(), start_.end() - 1, r) - start_.begin();
        if (g > cuts.back()) cuts.push_back(g);
    }
    if (ngroups_ > cuts.back()) cuts.push_back(ngroups_);
    run_unlocked(cuts.size() - 1, [&](std::int64_t t) { f(cuts[t], cuts[t + 1]); });
}
```

- 그룹마다 집계는 독립이에요. 그룹 하나의 합은 언제나 그 그룹의 행을 원래 순서로 pairwise 합한 값이라, 자르는 위치가 어디든 결과가 같아요.
- 아주 큰 그룹이 하나뿐이면 묶음도 하나(태스크 하나)예요. `parallel_for`는 태스크가 하나면 풀을 쓰지 않고 그 자리에서 돌며 "태스크 안" 표시도 하지 않아요. 그래서 그 그룹의 float 합은 다음 절의 pairwise 잎 병렬을 그대로 써요. 큰 그룹이 둘 이상이면 각 그룹은 태스크 안에서 직렬 트리로 합해요. 트리가 같으므로 비트도 같아요.
- 태스크가 하나여도 GIL은 놓아요. `parallel_for`는 태스크가 하나면 GIL을 건드리지 않으므로(아래 "GIL"), `for_groups`는 `run_unlocked`로 감싸서 불러요. 이 경로는 행이 기준값 이상일 때만 오므로 기준값 규칙과 맞아요.

## GIL

CPython의 GIL(Global Interpreter Lock)은 한 순간에 한 스레드만 Python 객체를 만지게 하는 잠금이에요. C++ 커널이 GIL을 쥔 채 오래 돌면 그동안 다른 Python 스레드가 모두 멈춰요. 반대로 GIL을 놓은 코드는 Python 객체(참조 수, `repr`, 예외 객체)를 만지면 안 돼요.

### 규칙: 기준값 이상이면 스레드 수와 상관없이 놓아요

규칙은 하나예요. 일이 기준값(2¹⁷) 이상이면 GIL을 놓고 계산하고, 아래면 쥔 채 계산해요. 스레드 수는 보지 않아요. 그래서 `sd.set_num_threads(1)`이어도 큰 계산이 도는 동안 다른 Python 스레드(예: 웹 서버의 다른 요청)가 돌아요. 기준값 아래의 작은 호출은 GIL을 놓았다 다시 잡는 비용을 내지 않아요. 이 규칙은 배열, 선형대수, 특수함수 등 모든 영역이 같이 쓰고, 기준값만 영역마다 달라요([스레드풀과 결정성](/internals/core/threads/)).

GIL을 놓고 다시 잡는 일은 공용 풀의 `parallel::GilRelease`(생성자에서 `PyEval_SaveThread`, 소멸자에서 `PyEval_RestoreThread`)가 해요 [6]. frame은 이것을 두 길로 써요. 나누는 일은 `run_unlocked`로, 나누지 않는 직렬 구간은 `Unlocked(work)`로 감싸요.

| 경우 | GIL |
|---|---|
| `for_chunks`의 일이 기준값 아래 | 쥔 채 돌아요 |
| `for_chunks`의 일이 기준값 이상 | 놓아요(`run_unlocked`). 풀로 나누든, 1스레드라서 청크를 차례로 돌든 같아요 |
| float 합의 잎 병렬(`pairwise_sum_parallel`), groupby의 그룹 묶음(`for_groups`) | 기준값 이상에서만 나누고, 나눌 때는 `run_unlocked`라서 놓아요 |
| 풀이 다른 Python 스레드의 일로 바빠서 혼자 직렬로 돎 | 놓아요. 바쁜 쪽이 일을 끝내고 결과를 Python 객체로 돌려주려면 GIL이 필요해요 |
| `Unlocked(work)`로 감싼 직렬 구간, `work`가 기준값 이상 | 놓아요 |

공용 풀의 `parallel_for` 자체는 GIL을 이렇게 다뤄요.

```cpp
// csrc/parallel/pool.cpp (발췌)
void parallel_for(std::int64_t ntasks, const std::function<void(std::int64_t)>& fn) {
    if (ntasks <= 0) return;
    if (ntasks == 1 || t_in_task) {                  // 태스크 하나, 또는 태스크 안: GIL은 있는 그대로
        for (std::int64_t t = 0; t < ntasks; ++t) fn(t);
        return;
    }
    GilRelease release;                              // 태스크가 둘 이상: 스레드 수와 상관없이 놓는다
    if (pool().threads() <= 1) {                     // 1스레드: 호출 스레드가 차례로, GIL 없이
        for (std::int64_t t = 0; t < ntasks; ++t) fn(t);
        return;
    }
    pool().run(ntasks, fn);                          // 풀로 (풀이 바쁘면 이 스레드 혼자)
}

GilRelease::GilRelease() {
    // 태스크는 GIL을 쥐고 있지 않다: 워커는 가진 적이 없고, 호출 스레드는 이미 놓았다.
    if (!t_in_task && PyGILState_Check()) state_ = PyEval_SaveThread();
}
```

- 태스크가 둘 이상이면 `parallel_for`가 직접 놓아요. 스레드가 1개여도 놓고, 태스크를 호출 스레드에서 차례로 돌려요.
- 태스크가 하나면 GIL을 건드리지 않아요. 태스크를 하나로 정한 것은 부르는 쪽이 일의 크기를 보고 정한 것이라서, 풀은 그 자리에서 함수 한 번을 부를 뿐이에요. 그래서 일의 크기는 기준값 이상인데 태스크가 하나일 수 있는 곳은 부르는 쪽이 GIL을 놓아야 해요. frame에서는 그룹이 하나뿐인 groupby(`for_groups`)가 그래요. `run_unlocked`가 이 일을 맡아요. 먼저 `Unlocked`로 GIL을 놓고 `parallel_for`를 불러요. `for_chunks`는 기준값 이상이면 청크가 언제나 8개 이상이지만, 같은 함수를 써서 GIL 규칙이 태스크 수에 기대지 않게 해요.
- 겹쳐도 안전해요. `GilRelease`는 이 스레드가 지금 GIL을 쥐고 있을 때만 놓아요. 태스크 안이거나 이미 다른 `GilRelease`(`Unlocked`, `run_unlocked`) 아래이면 아무 일도 하지 않아요. 그래서 `for_groups`의 태스크 하나가 다시 `pairwise_sum_parallel`을 불러도, `read_csv`가 `Unlocked` 아래에서 청크를 나눠 돌려도 GIL을 두 번 놓지 않아요. 이미 놓은 곳 안의 `parallel_for`(병렬 factorize와 counting sort의 파티션 단계, CSV의 청크)는 그대로 불러요.

나누지 않는 직렬 구간은 `Unlocked(work)`로 감싸요. 다음이 그런 구간이에요.

- 직렬 factorize(`Partitioned::build`의 P = 1 경로)와 그룹별 개수(`group_counts`), `value_counts`의 정렬(`stable_order`)
- 직렬 기수 정렬(`radix_sort_serial`, `Unlocked(n * 2)`)과 직렬 counting sort
- 라벨 여러 개로 모든 위치를 찾는 조회(`LabelTable::all_positions`)의 조회 부분
- merge에서 오른쪽 조인을 위해 처음 나타난 순서로 번호를 다시 매기는 구간
- `concat`의 버퍼 이어 붙이기
- `read_csv` 전체(토큰화, 추론, 값 만들기)

그래서 1스레드에서도 큰 호출은 모두 GIL을 놓아요. `sd.set_num_threads(1)`에서 1,600만 행 float64 Series의 `s + s`(약 11ms), `s.sum()`(약 8ms), `s[s > 0]`(약 50ms)을 부르는 동안, 옆의 Python 스레드가 `while` 루프로 카운터를 각각 약 43만 번, 28만 번, 190만 번 올렸어요(Apple M4 Pro). GIL을 쥔 채였다면 0번이에요.

1스레드에서 더 드는 비용은 기준값 이상인 호출마다 GIL을 한 번 놓고 다시 잡는 것이에요. 호출 하나에 0.1µs 안팎이고, 기준값 크기의 호출도 계산에 수 µs가 걸려서 보이지 않아요. 131,072행부터 1M 행까지 여덟 연산(`f + f`, `sum`, `min`, 필터, groupby `sum` 등)을 GIL을 쥐는 빌드와 번갈아 쟀을 때 기하평균 차이가 +0.6%였고, 경우별 차이(대부분 ±3% 안)는 실행마다 부호가 바뀌는 잡음이었어요. 다른 Python 스레드가 Python 코드를 돌리고 있으면, 계산을 마친 호출이 GIL을 돌려받을 때까지 기다리는 시간은 따로 있어요(최대 `sys.getswitchinterval()`, 기본 5ms). 이것은 GIL을 놓는 모든 확장 모듈이 같아요.

int64 `mean`(과 그 평균을 쓰는 `var`, `std`)은 배열 영역의 `sd::sum`을 불러 합을 구해요(배열의 합과 비트를 맞추기 위해서예요). 그 합은 배열 영역의 기준값(float64 덧셈 32,768개 분량)부터 GIL을 놓아요. 배열을 만들어 넘기는 앞뒤 부분은 Python 객체를 다루므로 GIL을 쥐어요([컬럼과 메모리](/internals/frame/columns/)).

### 태스크는 Python 객체를 만지지 않아요

- 에러 메시지는 나중에 만들어요. 메시지에는 값의 `repr`이 들어가고 그것은 Python 호출이에요. 태스크는 실패한 행 번호만 남기고(아래 `FirstRow`), 메시지는 병렬 구간이 끝나 GIL을 다시 잡은 뒤 만들어요.
- Column 객체는 C++ 값이에요. 태스크가 읽는 Column은 C++의 `shared_ptr<Buffer>` 셋을 담은 값이고, Python 객체를 가리키지 않아요. 태스크가 Column을 복사해도 Python 참조 수가 바뀌지 않아요.
- 태스크 안에서 던진 C++ 예외는 풀이 잡아 `parallel_for`가 돌아온 뒤 호출 스레드에서 다시 던져요. 예외가 `Unlocked`나 `run_unlocked`의 범위를 빠져나가면서 소멸자가 GIL을 다시 잡으므로, 바인딩이 Python 예외로 바꿀 때는 GIL이 있어요.
- `Unlocked` 구간도 같은 규칙을 따라요. 1스레드에서 태스크를 차례로 돌 때도 GIL이 없으니, 스레드 수와 상관없이 같은 코드가 Python 객체 없이 돌아요.

### GIL을 일부러 쥐는 곳

- **행 대입 `set_rows`.** `s.iloc[k] = v`는 크기와 상관없이 GIL을 쥔 채 돌아요. 대입은 Buffer를 아무도 공유하지 않으면 그 자리에서 고치는데(Copy-on-Write), 그동안 다른 Python 스레드의 커널이 같은 Buffer를 읽기 시작하면 반쯤 쓴 값을 보게 돼요. GIL을 쥐고 있으면 다른 스레드의 호출은 대입 전이나 후에만 시작할 수 있어요. 이미 돌고 있는 연산은 인자로 받은 Column 객체를 쥐고 있어서 Buffer의 참조 수가 2 이상이고, 대입은 복사본에 써요. 그래서 연산은 언제나 호출한 순간의 값을 봐요([컬럼과 메모리](/internals/frame/columns/)).
- **Index 조회 엔진의 CSR.** 라벨의 모든 위치를 묻는 조회(`.loc["a"]`, 라벨 리스트, 라벨 슬라이스의 양 끝)는 코드별 행 목록(CSR)을 처음 쓸 때 만들어 캐시해요. 이 CSR은 GIL을 쥔 채 직렬로 만들어서, 두 Python 스레드가 같은 캐시 칸을 동시에 채우지 않아요. 그 앞의 해시 테이블(`LabelTable`)은 라벨이 기준값 이상이면 만드는 factorize가 GIL을 놓으므로, 두 Python 스레드가 동시에 처음 조회하면 테이블을 두 번 만들 수 있어요. 각자 자기 객체를 만들고 내용이 같으므로 어느 쪽이 캐시에 남아도 결과는 같아요. Index는 불변이라 만든 뒤에는 읽기만 해요([라벨, 조회, 선택](/internals/frame/labels/)).

## 결정성

결과는 스레드 수와 무관하게 비트까지 같아요. float 합의 비트, 결과의 행 순서, factorize가 매기는 코드, 에러 메시지까지예요. 사용자는 노트북에서 1스레드로 디버깅한 결과를 서버의 10스레드 결과와 그대로 비교할 수 있고, 테스트는 정답을 하나만 두면 돼요.

기본 규칙은 둘이에요.

1. **나누는 방식은 데이터의 길이(와 dtype)로만 정해요.** 스레드 수, 값, 풀의 상태를 보지 않아요.
2. **부분 결과는 고정된 순서로 합쳐요.** 1스레드도 같은 구조로 계산해요.

| 연산 | 나누는 방법 | 결과가 같은 이유 |
|---|---|---|
| 원소별, `astype`, 필터, take | 16K행 청크 | 행마다 따로 계산해요. 출력 위치는 청크 순서의 누적합이에요 |
| 정수 합, min/max | 청크, 청크 순서로 접기 | 결합법칙이 정확히 성립해요. 정수는 wrap하고, IEEE min/max도 결합적이에요 |
| float 합, mean, var, std | pairwise 트리의 잎(2¹⁴개 이하) | 직렬 트리와 같은 노드를 같은 순서로 더해요 |
| groupby 집계 | 그룹 묶음 | 그룹마다 독립이에요 |
| factorize | 해시 파티션 (P = 256 또는 1) | 코드를 처음 나타난 순서로 다시 매겨요 |
| 기수 정렬, counting sort | 청크와 버킷 | 원소가 놓이는 자리가 직렬과 정확히 같아요 |
| merge | probe 쪽 행의 청크 | 청크마다 자기 출력 구간에 써요 |
| `read_csv` | 512KB 바이트 청크 | 따옴표 안팎을 홀짝으로 정확히 알아요. 열의 종류는 열 전체 규칙으로 합쳐요 |
| 에러 | 청크마다 첫 실패 | 가장 앞의 행이 이겨요 |

### 정수 합과 min/max: 결합법칙

정수 덧셈(wrap)은 결합적이고 교환적이에요. 어떤 순서로 더해도 같은 비트가 나와요. 그래도 청크 순서로 접어요. `fold`가 결합적이기만 하고 교환적이지 않은 경우(예: "처음 나온 값")에도 같은 함수를 쓰기 위해서예요.

```cpp
// csrc/frame/ops/reduce.cpp (발췌)
template <class T, class Part, class Fold>
T over_chunks(std::int64_t n, T first, Part part, Fold fold) {
    std::vector<T> parts(num_chunks(n), first);
    for_chunks(n, [&](std::int64_t lo, std::int64_t hi) { parts[lo / kChunkRows] = part(lo, hi); });
    T acc = first;
    for (const T& p : parts) acc = fold(acc, p);     // fold(fold(fold(first, p0), p1), ...)
    return acc;
}
```

float `min`/`max`는 IEEE 754-2019의 minimum/maximum이에요. NaN이 하나라도 있으면 NaN이고, `-0.0`이 `0.0`보다 작아요. 이 연산은 결합적이에요. AArch64의 `FMIN`/`FMAX` 명령이 바로 이 연산이라서, 청크마다 벡터로 구한 부분 결과를 접어도 직렬과 같아요([원소별 연산과 리덕션](/internals/frame/elementwise/)).

### float 합: pairwise 트리의 잎을 나눠요

float 덧셈은 결합적이지 않아요. $(a + b) + c$와 $a + (b + c)$가 반올림 때문에 다를 수 있어요. 그래서 "청크마다 부분 합을 내고 청크 순서로 더하기"는 결과가 청크 크기에 따라 달라지고, numpy와도 달라요.

stardust의 float 합은 numpy의 pairwise 합과 같은 트리예요 [1][2]. 길이 $n$의 구간을 반으로(8의 배수로 내림해서) 계속 나누고, 128개 이하가 되면 8개의 누산기로 더해요. 이 트리는 $n$만으로 정해지므로, 트리의 부분 트리를 태스크로 나누면 돼요.

- `pairwise::plan(n, 2¹⁴)`이 트리를 따라 내려가며 원소 16,384개 이하의 부분 트리(잎)를 왼쪽부터 나열해요.
- 태스크마다 잎 하나를 직렬 트리로 더해요.
- `pairwise::combine`이 같은 트리를 다시 따라 내려가며, 잎의 부분 합을 직렬 재귀와 같은 자리에서 더해요.

```cpp
// csrc/frame/ops/pairwise.hpp (발췌)
inline constexpr std::int64_t kPairwiseLeaf = 1 << 14;

template <class Get>
double pairwise_sum_parallel(std::int64_t n, const Get& get, std::int64_t cost = 1) {
    if (n <= kPairwiseLeaf || n * cost < kParallelThreshold) return pairwise_sum(0, n, get);  // 직렬 트리
    const pairwise::Leaves leaves = pairwise::plan(n, kPairwiseLeaf, /*complex=*/false);
    std::vector<double> part(leaves.size());
    run_unlocked(part.size(), [&](std::int64_t t) {
        part[t] = pairwise_sum(leaves[t].first, leaves[t].second, get);
    });
    return pairwise::combine(n, kPairwiseLeaf, part);   // 같은 트리 모양으로 합치기
}

// numpy의 add.reduce처럼 0.0에서 시작한다: -0.0만의 합이 +0.0인 이유.
template <class Get>
double float_sum(std::int64_t n, const Get& get, std::int64_t cost = 1) {
    return 0.0 + pairwise_sum_parallel(n, get, cost);
}
```

잎의 크기 2¹⁴는 트리의 모양을 바꾸지 않아요. 트리는 직렬 재귀와 같고, 잎 크기는 "어느 깊이에서 태스크로 끊을지"만 정해요. 그래서 이 값을 바꿔도 결과의 비트는 같아요. 트리와 numpy 비트 일치의 자세한 설명은 [스레드풀과 결정성](/internals/core/threads/)과 [집계](/internals/array/reductions/)에 있어요.

NA가 있는 float 컬럼의 합은 NA 행을 0.0으로 보는 접근자로 같은 트리를 돌아요. `var`/`std`는 평균을 먼저 구하고, 제곱 편차를 같은 트리로 한 번 더 더해요(두 번 훑기).

### 결과가 하나뿐인 연산은 나누는 방식이 스레드 수를 따라요

기본 규칙(1스레드도 같은 구조)에는 예외가 있어요. 결과가 나누는 방식과 무관하게 정확히 정해지는 연산이에요.

| 연산 | 1스레드 (또는 `available()`이 거짓) | 나눌 때 | 결과가 하나뿐인 이유 |
|---|---|---|---|
| factorize | 해시 테이블 하나로 한 번 훑기 | 해시 위쪽 8비트로 256 파티션 | 코드는 "처음 나타난 순서"로 정의돼요 |
| 기수 정렬 | 한 번 읽어 8자리 히스토그램을 모두 세고 8패스 | 자리마다 청크별 히스토그램 → 흩뿌리기 | 안정 정렬의 결과는 유일해요 |
| counting sort | 개수 → 누적합 → 제자리에 | 256 버킷에 안정적으로 흩뿌린 뒤 버킷마다 | 안정 정렬이에요 |
| `read_csv` | 청크 하나 | 512KB 바이트 청크 | 파일의 레코드 순서 그대로예요 |

이 연산들을 나누면 직렬 한 번보다 메모리를 여러 번 지나는 단계가 생겨요. 1스레드에서도 나누면 그 비용만 내고 이득이 없어요. 1M 행, 키 1,000종의 factorize를 1스레드로 잴 때, 직렬 패스가 2.0ms이고 256 파티션으로 나눈 경로가 4.5ms였어요(Apple M4 Pro). 이런 연산 전반에서 나눈 경로는 1스레드에서 1.5~2.5배 느려요. 결정성 규칙이 지키려는 것은 같은 결과이고, 이 연산들은 어느 경로로 가도 결과가 같으므로 1스레드는 직렬 경로를 써요.

float 합은 이 예외에 들 수 없어요. 나누는 방식이 곧 덧셈의 순서이고, 순서가 비트를 바꾸기 때문이에요. 그래서 float 합은 1스레드에서도 같은 트리를 써요(그 트리 자체가 numpy의 직렬 알고리즘이라 1스레드에 손해가 없어요).

### factorize: 파티션으로 나눠도 처음 나타난 순서

factorize는 값마다 정수 코드를 매기는 일이에요. stardust의 코드는 처음 나타난 순서예요. 처음 나온 키가 0, 그다음 새 키가 1, …. `unique_values`, `drop_duplicates`, groupby(`sort=False`)의 결과 순서가 이 코드에서 나와요.

여러 스레드로 나눌 때는 해시의 위쪽 8비트로 행을 256개 파티션에 보내요. 같은 키는 같은 해시를 가지므로 언제나 같은 파티션에 가요. 파티션 안에서 행은 원래 행 순서로 놓여서, 파티션마다 매긴 **지역 코드**도 그 파티션 안에서는 처음 나타난 순서예요. 마지막에 전역 코드를 "그 키가 처음 나타난 행보다 앞에서 처음 나타난 키의 수"로 다시 매겨요. 아래는 파티션 둘, 행 여덟인 작은 예예요.

1. 행마다 해시를 구하고 (청크, 파티션)마다 개수를 세요. 청크 병렬.
2. (파티션, 청크) 순서의 누적합으로 시작 위치를 정해요. 파티션 순서, 그 안에서 청크 순서라서 파티션마다 행이 행 순서로 놓여요.
3. (키 또는 해시, 행) 쌍을 파티션으로 흩뿌려요. 청크 병렬.
4. 파티션마다 Swiss table로 지역 코드와 첫 등장 행을 정해요. 파티션 병렬.
5. 행 청크마다, 그 청크에 떨어지는 첫 등장 행을 모아 순위(전역 코드)를 매겨요. 청크 병렬. 태스크는 자기 청크 범위의 배열만 써요.
6. 행마다 자기 코드를 써요. 청크 병렬.

5단계가 결정성을 만드는 곳이에요. 파티션을 어느 스레드가 언제 처리했는지와 상관없이, 전역 코드는 첫 등장 행의 위치만으로 정해져요. 그래서 P = 256으로 나눈 결과와 P = 1(직렬)의 결과가 같고, P가 스레드 수를 따라도 돼요. 이 단계는 결정성을 위해 더하는 일이고, 그만큼 시간이 들어요. Polars는 그룹 순서를 기본으로 보장하지 않으므로(아래) 이런 단계가 필요 없어요.

5단계에서 순위를 매기는 루프는 분기가 없어요. 첫 등장 행은 키가 많으면 촘촘하고 무작위라서, `if`로 쓰면 분기 예측이 자주 빗나가요.

```cpp
// csrc/frame/ops/hash.hpp, 5단계의 순위 매기기 (발췌)
// rk[i]: 이 청크의 i번째 행이 첫 등장이면 1, 아니면 0
std::int64_t g = fstart[chunk];            // 앞 청크들의 첫 등장 수(누적합)
for (std::int64_t i = 0; i < len; ++i) {
    const std::int64_t is = rk[i];
    g += is;
    rk[i] = g & -is;                       // 첫 등장이면 1 + 코드, 아니면 0
}
```

### 기수 정렬과 counting sort: 자리가 같아요

LSD 기수 정렬(아래 자리부터 한 바이트씩 안정 counting sort를 8번)은 자리마다 세 단계로 나눠요([groupby와 정렬](/internals/frame/groupby-sort/)).

1. 청크마다 그 자리 바이트의 히스토그램(256칸)을 세요.
2. (바이트 값, 청크) 순서로 누적합을 내요. 바이트 값 0인 원소가 모두 앞에 오고, 그 안에서 청크 0의 원소, 청크 1의 원소, … 순서예요.
3. 청크마다 자기 위치부터 흩뿌려요.

2단계의 순서 덕분에 각 원소가 놓이는 자리는 직렬 counting sort가 놓는 자리와 정확히 같아요. 직렬 counting sort도 같은 바이트 값의 원소를 입력 순서로 놓고, 입력 순서는 청크 순서 그 자체이기 때문이에요.

groupby와 merge가 쓰는 counting sort(키 0..K−1, 키가 63만 종일 수도 있어요)는 (청크 × 키) 카운터를 둘 수 없어서 두 단계로 해요. 키의 위쪽 비트로 256개 버킷에 안정적으로 흩뿌린 뒤, 버킷마다 자기 키 범위만 따로 counting sort해요. 버킷 경계의 `start[k0]` 칸은 앞 버킷의 끝이라, 버킷은 `(k0, k1]` 칸만 써서 두 버킷이 같은 칸을 쓰지 않아요.

### merge: 청크마다 자기 출력 구간

merge는 한쪽(build)의 행을 코드별로 모아 두고(counting sort), 다른 쪽(probe)의 행을 차례로 보며 짝을 찾아요. 결과의 행 순서는 probe 쪽 행 순서, 같은 행의 짝은 build 쪽 행 순서예요([merge와 concat](/internals/frame/merge-concat/)).

- probe 행의 청크마다 출력 행 수를 세고(짝의 수, 짝이 없으면 left·outer에서 1), 누적합으로 시작 위치를 정한 뒤, 청크마다 자기 구간에 (probe 행, build 행) 쌍을 써요. 앞의 "세고, 누적합을 내고, 쓰기" 그대로예요.
- outer merge는 "probe 쪽 어느 행과도 맞지 않은 build 행"을 뒤에 붙여요. 이를 위해 세는 패스에서 코드마다 `probed` 플래그를 1로 써요. 여러 청크가 같은 코드의 플래그를 동시에 쓸 수 있어서 `std::atomic_ref`의 relaxed 저장을 써요. 모두가 같은 값(1)을 쓰므로 순서가 결과에 영향을 주지 않고, 읽기는 `parallel_for`가 끝난 뒤라 완료 보고의 동기화가 값을 보여 줘요.

### CSV: 따옴표의 홀짝

CSV는 아무 바이트에서나 자를 수 없어요. 따옴표 안의 줄바꿈은 레코드 경계가 아니기 때문이에요. 그런데 어떤 바이트가 따옴표 안인지는 그 앞에 나온 따옴표 개수의 홀짝으로 정해져요(`""`는 따옴표 둘이라 홀짝을 바꾸지 않아요) [7].

1. 본문을 512KB(2¹⁹바이트) 청크로 자르고, 청크마다 따옴표 개수의 홀짝을 세요. 병렬.
2. 그 홀짝의 누적 XOR이 각 청크의 시작이 따옴표 안인지 알려 줘요. 추측이 아니라 정확한 값이에요.
3. 청크마다 자기 안에서 시작하는 레코드를 토큰화해요. 첫 레코드는 따옴표 밖 줄바꿈 다음이고, 마지막 레코드는 경계를 넘어 끝까지 읽어요. 병렬.
4. 열마다, 청크마다 타입을 추론하고 값을 최종 버퍼에 써요. 청크의 종류(`int < float < text`)를 열 전체 규칙으로 합쳐요.

`nrows`가 있으면(앞에서부터 `nrows`개 레코드) 청크 하나, 곧 직렬로 읽어요. 앞 청크의 레코드 수를 알아야 어디서 멈출지 알기 때문이에요. 풀을 쓸 수 없을 때(1스레드 등)도 청크 하나예요. 결과가 자르는 방식과 무관하므로 청크 수가 스레드 수를 따라도 돼요. 512KB보다 작은 파일은 언제나 청크 하나예요. 자세한 토크나이저 설명은 [read_csv](/internals/frame/csv/)에 있어요.

### 에러: 첫 번째 행 (`FirstRow`)

1M 행 string 컬럼을 `astype("int64")`로 바꾸는데 세 곳에 숫자가 아닌 값이 있다고 해요. 여러 태스크가 동시에 검사하면 어느 태스크가 먼저 실패할지는 스레드 일정에 달려 있어요. 먼저 실패한 쪽을 알리면 메시지가 실행마다 바뀌어요.

`parallel::FirstRow`는 가장 작은 실패 행을 골라요.

```cpp
// csrc/parallel/pool.hpp (발췌)
class FirstRow {
public:
    void offer(std::int64_t row) {               // 이 태스크의 첫 실패 행
        std::int64_t cur = row_.load(std::memory_order_relaxed);
        while (row < cur && !row_.compare_exchange_weak(cur, row, std::memory_order_relaxed)) {}
    }
    bool failed_before(std::int64_t row) const { return row_.load(std::memory_order_relaxed) < row; }
    bool any() const { return row_.load() != kNone; }
    std::int64_t row() const { return row_.load(); }
private:
    static constexpr std::int64_t kNone = INT64_MAX;
    std::atomic<std::int64_t> row_{kNone};
};
```

- `offer`는 compare-and-swap 루프로 "지금 값보다 작을 때만 바꾸기"를 해요. 여러 태스크가 동시에 내도 가장 작은 값이 남아요. 다른 메모리와의 순서는 필요 없어서 relaxed로 충분하고, 값은 `parallel_for`가 돌아온 뒤에 읽어요.
- 청크는 자기 청크 안의 첫 실패만 내고 멈춰요. 그 뒤의 행은 볼 필요가 없어요.
- `failed_before(lo)`가 참이면 이 청크보다 앞에서 이미 실패한 것이므로, 청크는 시작하지 않고 끝나요. 먼저 실패한 청크 뒤쪽의 일을 아껴요.
- 메시지는 병렬 구간이 끝나고 GIL을 다시 잡은 뒤, `row()`의 값으로 만들어요.

`read_csv`는 여기에 순서를 하나 더 정해요. 토큰화 에러(필드 개수, 따옴표 규칙)가 값 에러보다 먼저이고, 토큰화 에러는 파일에서 가장 앞 청크의 것이에요. 값 에러는 열 순서로, 열 안에서는 가장 앞 행이에요. 직렬로 읽을 때 처음 만나는 에러와 같은 순서예요.

### pandas와 Polars는 어떤가

- **pandas 3.1.1**은 한 스레드로 돌므로 실행마다 같은 결과를 내요. 단 groupby의 그룹 합은 Kahan 보정 합이라, 같은 값을 `Series.sum()`(numpy pairwise)으로 더한 것과 비트가 다를 수 있어요. stardust의 그룹 합은 그 그룹의 행만 고른 `Series.sum()`과 같아요.
- **Polars 2.1.0**은 기본 설정에서 결과가 실행마다 달라질 수 있어요. 400만 행, 키 10종의 표에서 `df.group_by("k").agg(pl.col("f").sum()).sort("k")`를 실행하면, 기본 14스레드로 여섯 번 실행한 그룹 합 열이 여섯 번 모두 다른 비트였어요. `POLARS_MAX_THREADS=1`로는 세 번 모두 같았어요. 그룹의 순서도 기본으로는 정해지지 않아요. 같은 프로세스에서 100만 행, 키 1,000종의 `group_by("k")`를 다섯 번 부르면 결과의 첫 다섯 키가 다섯 번 모두 달랐어요. 입력 순서를 원하면 `maintain_order=True`를 줘야 하고, 문서는 이것이 기본 group by보다 느리다고 적어요.
- Polars의 `Series.sum()`은 1스레드와 14스레드의 결과가 같았지만 numpy의 합과는 비트가 달랐어요(같은 400만 개에서 마지막 자리가 달라요).

```python
# Polars 2.1.0 (결과가 실행마다 달라질 수 있어요)
rng = np.random.default_rng(0)
n = 4_000_000
f = rng.standard_normal(n) * 1e6
df = pl.DataFrame({"k": rng.integers(0, 10, n), "f": f})
g = df.group_by("k").agg(pl.col("f").sum()).sort("k")   # 14스레드: 실행마다 다른 비트
```

stardust는 같은 계산을 스레드 수 1, 3, 기본값으로 하면 모두 같고, 전체 합은 numpy의 `np.add.reduce`와, 그룹 합은 그 그룹만 골라 numpy로 더한 값과 비트까지 같아요.

```python
>>> import numpy as np
>>> rng = np.random.default_rng(0)
>>> n = 1_000_000
>>> f = rng.standard_normal(n) * 1e6
>>> k = rng.integers(0, 10, n)
>>> df = sd.frame.DataFrame({"k": k, "f": f})
>>> default = sd.get_num_threads()
>>> results = []
>>> for t in (1, 3, default):
...     sd.set_num_threads(t)
...     results.append((df["f"].sum(), df.groupby("k")["f"].sum()["f"].tolist()))
>>> sd.set_num_threads(default)
>>> all(r == results[0] for r in results)
True
>>> results[0][0] == float(np.add.reduce(f))
True
>>> results[0][1][3] == float(np.add.reduce(f[k == 3]))
True
```

### 테스트

`tests/frame/test_threads.py`가 결정성을 시험해요.

- 입력은 200,003행이에요. 청크 크기(16,384)의 배수가 아니고 기준값을 넘어서, 마지막의 짧은 청크와 여러 청크 경계를 모두 지나요. int, float(NaN 1%, `-0.0` 1%), string, bool 컬럼에 NA가 10% 섞여 있어요.
- 연산마다 1, 3, 기본 스레드 수로 실행해 결과를 비교해요. float은 `struct.pack("<d", v)`로 바이트를 비교하고, Series와 DataFrame은 dtype, 값, 라벨까지 비교해요. 원소별 연산 19종, 리덕션(`sum`, `mean`, `min`, `max`, `std`, `var`, `count` × 네 dtype), 해시(unique, `nunique`, `value_counts`, `duplicated`, `drop_duplicates`, groupby 셋, merge 넷, 라벨 조회), 정렬 여섯 가지가 대상이에요.
- 스레드 수와 무관하다는 것만으로는 부족해요. 1스레드도 같은 청크를 지나므로, 청크 경계에서 행을 잃거나 두 번 쓰는 버그는 모든 스레드 수에서 똑같이 틀려요. 그래서 numpy·Python과 따로 비교해요. float 합은 길이 16,384, 16,385, 200,003, 1,048,583에서 `np.add.reduce`와 비트가 같은지, factorize 순서는 `dict.fromkeys`(처음 나타난 순서)와 같은지, string 정렬은 Python `sorted()`와 같은지 봐요.
- **에러 위치**: string 컬럼의 행 90,000과 180,000에 숫자가 아닌 값을 넣고 `astype("int64")`의 메시지가 모든 스레드 수에서 행 90,000의 값(`'x2'`)을 말하는지 봐요.
- **CSV**: 512KB 청크 여럿에 걸친 파일(따옴표 안 줄바꿈, `""`, CRLF, 한글, 빈 문자열)을 직렬 정답(`test_csv.py`의 참조 구현)과 비교해요. 따옴표 필드 하나가 1.5MB로 세 청크에 걸치는 파일, 앞뒤에 에러가 둘 있는 파일(파일 순서로 앞의 것을 알려야 해요)도 있어요.
- **스냅샷**: 한 스레드가 `s.iloc[k] = 1`을 k = 0, 1, 2, …로 쓰는 동안 다른 스레드가 `s + 0`을 되풀이해요. 모든 결과가 "앞의 k개만 1"인 꼴이어야 해요.
- **GIL**: `set_num_threads(1)`에서 큰 호출을 부르는 동안 다른 Python 스레드가 카운터를 1,000번 넘게 올리는지 봐요. 300만 행 `sort_values`(직렬 기수 정렬의 `Unlocked`)와, 1,600만 행의 `s + s`, `sum`, `min`, `var`, 필터, groupby `sum`(청크와 잎, 그룹 묶음의 `run_unlocked`)이 대상이에요. 영역 공통의 `tests/test_gil_release.py`는 옆 스레드가 가장 오래 멈춘 시간을 재서, GIL을 쥔 호출이면 그 시간이 호출 시간만큼 길어지는 것으로 가려요.

## 확장성

### 같은 입력을 반복해 잰 값

1M 행, 1스레드와 10스레드, Apple M4 Pro. 같은 입력으로 거듭 불러 최솟값을 잰 값이에요([성능과 검증](/internals/frame/performance/)의 "같은 입력 반복의 함정" 참고. 이 표의 연산은 분기가 적어 그 영향이 작아요).

| 연산 | 1스레드 | 10스레드 | 배율 |
|---|---:|---:|---:|
| float + float | 178 µs | 41 µs | 4.3× |
| int + int, NA 10% | 289 µs | 73 µs | 4.0× |
| float > 0 | 380 µs | 53 µs | 7.2× |
| `isna`, NA 10% | 42 µs | 14 µs | 3.0× |
| `df[mask]` 4열 | 3.63 ms | 563 µs | 6.4× |
| float `sum` | 89 µs | 15 µs | 5.9× |
| float `std`, NA 10% | 485 µs | 79 µs | 6.1× |
| sort float64 | 13.0 ms | 2.67 ms | 4.9× |
| `read_csv` mixed, 1M × 4열 | 68.1 ms | 12.9 ms | 5.3× |

표의 연산은 두 무리로 갈려요.

- 메모리에 묶인 연산은 3~4배에서 멈춰요. `float + float` 1M은 16MB를 읽고 8MB를 써요. 계산은 원소마다 덧셈 하나라서, 스레드를 늘려도 메모리가 데이터를 대 주는 속도가 한계예요. `isna`는 비트맵(125KB)을 읽고 행마다 1바이트를 쓰는 일이라 1스레드에서도 42µs로 작아요. 나눠서 줄일 몫이 적어 3배예요.
- 옮기는 메모리에 비해 일이 많은 연산은 5~7배예요. 비교(`float > 0`)는 행마다 8바이트를 읽고 1바이트를 써서 덧셈(24바이트)보다 메모리를 훨씬 덜 옮겨요. 필터는 세기와 쓰기 두 패스, `std`는 두 번 훑기, 정렬은 8자리 × 두 패스예요. CPU가 일하는 몫이 커서 코어 수의 이득이 더 많이 남아요.
- 키가 1,000종인 해시(`nunique`, groupby)는 10스레드에서도 약 2배예요. 직렬 패스의 테이블(키 1,000개)이 L1 캐시에 들어가서 1스레드가 이미 빠르고, 나누는 경로는 흩뿌리기와 번호 매기기 패스를 더 내기 때문이에요.
