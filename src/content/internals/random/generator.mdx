## 한눈에 보기

`sd.random`의 생성기(`Generator`)가 기억하는 값은 두 가지뿐이에요.

- **키** $k = (k_0, k_1)$: 64비트 둘, 합쳐서 128비트예요. 시드에서 만들어져요([시드, spawn, 상태](/internals/random/seeding/)). 어떤 수열인지를 정해요.
- **위치** `pos`: 지금까지 꺼낸 원소의 수예요. 64비트 부호 없는 정수예요.

크기 n인 호출의 원소 i는 수열의 원소 $e = \text{pos} + i$이고, 호출이 끝나면 `pos`가 n만큼 늘어나요. 원소 e의 난수는 키와 e만으로 정해져서, 앞 원소를 먼저 계산할 필요가 없어요. 이 글에서 설명하는 성질은 모두 여기서 나와요.

핵심 아이디어는 네 가지예요.

1. **계수기형 생성기.** "직전 상태에서 다음 상태를 만드는" 대신, 계수기(정수) n을 키가 정하는 전단사 함수에 넣어 n번째 난수를 바로 만들어요. 함수는 Philox4×64-10이에요. 256비트 계수기를 256비트 출력(64비트 단어 넷)으로 바꿔요[1].
2. **원소마다 정해진 계수기.** 원소 e의 첫 단어는 계수기 $(\lfloor e/4 \rfloor, 0, 0, 0)$ 블록의 $e \bmod 4$번째 단어예요. 기각 표본에 더 필요한 단어는 계수기 $(e, j, 0, 0)$, $j \ge 1$ 블록에서 받아요. 그래서 어떤 원소가 기각을 몇 번 하든 다른 원소의 값은 바뀌지 않아요.
3. **예약은 잠금 안, 계산은 잠금 밖.** 호출은 위치 구간 `[pos, pos + n)`을 잠금 안에서 예약하고, 계산은 잠금을 풀고 스레드풀에서 해요. 원소의 값이 (키, e)로만 정해지니 일을 어떻게 나누든 결과가 같아요.
4. **블록 넷을 함께.** 블록 하나의 계산은 곱셈이 이어지는 의존 사슬이라 곱셈기의 지연 시간에 묶여요. 그래서 서로 독립인 블록 넷의 라운드를 섞어 계산해요. 균등 난수 10⁶개를 만드는 데 블록을 하나씩 계산하면 2.98ms, 넷을 함께 계산하면 1.14ms가 걸리고, 블록마다 비트는 똑같아요.

호출 하나는 이렇게 흘러가요.

## 의사난수와 두 종류의 생성기

### 의사난수란

컴퓨터는 정해진 계산만 해요. 그래서 프로그램이 만드는 "난수"는 정해진 규칙으로 만든 수열이에요. 같은 시작점에서 출발하면 언제나 같은 수열이 나와요. 이런 수를 의사난수(pseudorandom number)라고 해요. 같은 시드로 같은 결과를 다시 얻을 수 있다는 점(재현성)은 오히려 장점이에요.

좋은 의사난수 수열이 갖춰야 할 것은 이래요.

- **균등성:** 64비트 단어라면 $0$부터 $2^{64}-1$까지의 값이 고르게 나와요. 특정 비트가 1이 될 확률이 정확히 절반이어야 해요.
- **독립성:** 앞의 값을 보고 다음 값을 짐작할 수 없어요. 이웃한 값끼리, 몇 칸 떨어진 값끼리, 비트끼리 상관이 없어야 해요.
- **긴 주기:** 수열이 언젠가 처음으로 되돌아와 반복된다면, 그 길이(주기)가 어떤 프로그램도 다 쓰지 못할 만큼 길어야 해요.

"진짜 난수와 구별되지 않는다"는 것을 증명할 방법은 없어요. 그래서 실제로는 **통계 검사**를 많이 돌려서 구별해 내지 못하는지를 봐요. 표준으로 쓰이는 검사 묶음이 TestU01이에요[2]. 이 안의 SmallCrush(검사 10개), Crush(96개), BigCrush(106개)는 수열에서 값을 뽑아 분포, 간격, 행렬의 계수, 비트 패턴 같은 통계량을 계산하고, 그 값이 진짜 난수에서 나올 법한지를 p값으로 판정해요[1].

### 상태형 생성기

전통적인 생성기는 **상태**를 하나 두고, 한 걸음마다 상태를 바꾸면서 상태에서 출력을 만들어요.

$$
x_{n+1} = f(x_n), \qquad u_n = g(x_n)
$$

가장 간단한 예는 선형 합동 생성기(LCG)예요. $x_{n+1} = (a x_n + c) \bmod m$이에요. 장난감 크기로 $a = 5$, $c = 3$, $m = 16$, $x_0 = 0$이면 이래요.

$c$가 홀수이고 $a - 1$이 4의 배수이면 이 LCG는 $0 \dots 15$를 모두 한 번씩 거쳐 주기가 최대가 돼요[3]. numpy의 기본 생성기 PCG64도 이 계열이에요. 128비트 상태를 LCG로 진행하고, 출력 함수로 비트를 뒤섞어 64비트를 내요(주기 $2^{128}$)[4].

상태형 생성기는 본질적으로 순차적이에요. n번째 값은 n−1번째 상태에서 나와요. LCG처럼 수학 구조가 단순하면 "n걸음 건너뛰기"를 $O(\log n)$에 계산할 수 있어서(PCG64의 `advance`), 일을 나눠 주는 것 자체는 가능해요. 하지만 난수를 쓰는 쪽에서 문제가 생겨요.

- **원소마다 쓰는 난수 개수가 다르면 건너뛸 곳을 몰라요.** 범위 정수를 치우침 없이 만들려면 가끔 값을 버리고 다시 뽑아야 해요(기각 표본, [뽑기 알고리즘](/internals/random/sampling/)). 상태형 생성기에서는 버린 값만큼 뒤의 모든 원소가 밀려요. 원소 i가 수열의 몇째 값을 쓰는지가 앞 원소의 기각 횟수에 달려 있으니, 원소 i의 자리로 바로 건너뛸 수 없어요.
- **스레드마다 상태를 하나씩 두면 결과가 스레드 수에 따라 달라져요.** 스레드 p개가 각자 다른 수열을 쓰면, 원소 i가 받는 값은 "원소 i를 어느 스레드가 맡았는가"에 달려요.

### 계수기형 생성기

계수기형(counter-based) 생성기는 상태를 진행하지 않아요. n번째 값을 n 자체에서 만들어요[1].

$$
u_n = g\big(b_k(n)\big)
$$

여기서 n은 그냥 정수(계수기)이고, $b_k$는 키 k가 정하는 함수예요. 0, 1, 2, …처럼 너무나 규칙적인 입력을 넣어도 출력이 난수처럼 보이려면 $b_k$가 비트를 철저히 뒤섞어야 해요.

$b_k$를 **전단사**(bijection), 곧 p비트 정수 전체를 자기 자신으로 일대일로 보내는 함수로 고르면 좋은 성질이 하나 따라와요. 계수기가 $0$부터 $2^p - 1$까지 가는 동안 출력은 모든 p비트 값을 정확히 한 번씩 거쳐요. 출력이 겹치지 않으니 주기는 $2^p$이에요.

전단사이기만 하면 되는 것은 아니에요. $b_k(n) = n$도 전단사지만 난수와는 거리가 멀어요. "규칙적인 입력을 받아 키에 따라 무작위처럼 보이는 일대일 출력을 내는 함수"를 암호학에서는 **블록 암호**라고 불러요. 블록 암호를 계수기에 적용하는 것은 암호의 CTR 모드와 같은 구조이고, 차이는 출력을 평문과 XOR하는 대신 난수로 쓴다는 것뿐이에요[1]. 암호용 블록 암호는 공격자가 키를 알아내지 못하게 하려고 라운드가 많고 키 일정이 복잡해요. 난수에는 그런 보안이 필요 없으니, 라운드를 줄이고 키 일정을 단순하게 하면서 통계 검사는 그대로 통과하는 함수를 쓰면 돼요. Philox가 그렇게 설계된 함수예요.

| | 상태형 (예: PCG64) | 계수기형 (Philox) |
|---|---|---|
| n번째 값 | 앞의 상태를 거쳐야 해요(LCG 계열은 건너뛰기 $O(\log n)$) | $b_k(n)$ 한 번, $O(1)$ |
| 기억하는 것 | 상태(PCG64는 128비트 둘) | 키와 위치뿐 |
| 기각한 원소 | 뒤의 모든 원소를 밀어요 | 그 원소의 추가 계수기만 써요(아래) |
| 병렬 | 스레드마다 상태를 나눠야 해요 | 원소마다 독립. 아무 순서로 계산해도 돼요 |
| 독립된 수열 여러 개 | 건너뛰기나 별도 증분 | 키만 바꾸면 돼요 |

stardust가 계수기형을 고른 이유는 스레드 수와 무관한 결정성이에요. 배열 연산이 스레드 수와 상관없이 비트까지 같은 결과를 내듯([스레드풀과 결정성](/internals/core/threads/)), 난수도 같은 시드면 1스레드든 10스레드든 같은 값이어야 해요. 계수기형이면 원소 하나의 값이 (키, 원소 번호)의 순수 함수라서 이 성질이 거저 따라와요. 그 대가로 numpy와 같은 시드에서 같은 값을 내는 비트 호환은 포기했어요. numpy의 수열 순서를 따르면 기각이 뒤 원소를 미는 구조까지 따라와야 해서, 원소 하나를 독립으로 계산할 수 없기 때문이에요. 차이의 자세한 내용은 [시드, spawn, 상태](/internals/random/seeding/)에 있어요.

## Philox4×64-10

이름의 4×64는 64비트 단어 넷(256비트)을 받아 넷을 낸다는 뜻이고, 10은 라운드 수예요. 키는 64비트 둘(128비트)이에요. Salmon, Moraes, Dror, Shaw가 2011년에 Random123 라이브러리와 함께 발표했어요[1].

### 한 라운드

입력 단어를 $(c_0, c_1, c_2, c_3)$, 이 라운드의 키를 $(k_0, k_1)$이라 해요. 상수 곱수 둘이 있어요.

$$
M_0 = \texttt{0xD2E7470EE14C6C93}, \qquad M_1 = \texttt{0xCA5A826395121157}
$$

라운드 하나는 64비트 곱 두 개를 128비트로 계산해 위 64비트(hi)와 아래 64비트(lo)로 나누고, 단어 자리를 바꿔 끼워요.

$$
\begin{aligned}
(\mathrm{hi}_0, \mathrm{lo}_0) &= M_0 \cdot c_0, \qquad (\mathrm{hi}_1, \mathrm{lo}_1) = M_1 \cdot c_2 \\[2pt]
(c_0', c_1', c_2', c_3') &= (\mathrm{hi}_1 \oplus c_1 \oplus k_0,\;\; \mathrm{lo}_1,\;\; \mathrm{hi}_0 \oplus c_3 \oplus k_1,\;\; \mathrm{lo}_0)
\end{aligned}
$$

$\oplus$는 비트 XOR이에요. 곱 $M \cdot c$는 최대 128비트이고, $\mathrm{lo} = (M c) \bmod 2^{64}$, $\mathrm{hi} = \lfloor M c / 2^{64} \rfloor$예요.

| 새 단어 | 무엇으로 만드나 | 의미 |
|---|---|---|
| $c_0'$ | $c_2$를 곱한 위 절반 ⊕ $c_1$ ⊕ $k_0$ | 곱의 위 절반이 다른 단어와 키를 흔들어요 |
| $c_1'$ | $c_2$를 곱한 아래 절반 | 곱의 아래 절반이 그대로 자리를 옮겨요 |
| $c_2'$ | $c_0$를 곱한 위 절반 ⊕ $c_3$ ⊕ $k_1$ | 위와 같아요(다른 짝) |
| $c_3'$ | $c_0$를 곱한 아래 절반 | 위와 같아요(다른 짝) |

다음 라운드에서 곱해지는 단어는 $c_0'$과 $c_2'$이에요. 그런데 $c_0'$에는 $c_2$ 쪽 곱의 위 절반이, $c_2'$에는 $c_0$ 쪽 곱의 위 절반이 들어 있어요. 곧 두 곱셈 짝이 라운드마다 서로의 결과를 넘겨받아요. 한쪽 입력 비트의 영향이 한 라운드 만에 다른 쪽 곱셈으로 건너가요.

코드는 이 정의를 그대로 옮겨요.

```cpp
// csrc/random/philox.hpp (줄인 발췌)
inline void mulhilo(uint64_t a, uint64_t b, uint64_t& hi, uint64_t& lo) {
    const unsigned __int128 p = static_cast<unsigned __int128>(a) * b;   // 128비트 곱
    hi = static_cast<uint64_t>(p >> 64);
    lo = static_cast<uint64_t>(p);
}

inline Block philox(Block c, Key key) {          // Block = std::array<uint64_t, 4>
    constexpr uint64_t kM0 = 0xD2E7470EE14C6C93ULL, kM1 = 0xCA5A826395121157ULL;
    constexpr uint64_t kW0 = 0x9E3779B97F4A7C15ULL, kW1 = 0xBB67AE8584CAA73BULL;
    uint64_t k0 = key.k0, k1 = key.k1;
    for (int r = 0; r < 10; ++r) {
        if (r > 0) k0 += kW0, k1 += kW1;          // 키 일정: 라운드마다 상수를 더해요
        uint64_t hi0, lo0, hi1, lo1;
        mulhilo(kM0, c[0], hi0, lo0);
        mulhilo(kM1, c[2], hi1, lo1);
        c = {hi1 ^ c[1] ^ k0, lo1, hi0 ^ c[3] ^ k1, lo0};
    }
    return c;
}
```

`unsigned __int128`은 GCC·Clang이 제공하는 128비트 정수 타입이에요. 64×64비트 곱을 이 타입으로 쓰면 컴파일러가 64비트 ARM(AArch64)에서 곱의 아래 절반을 내는 `MUL`과 위 절반을 내는 `UMULH` 두 명령으로 바꿔요. 128비트 나눗셈 같은 느린 경로는 생기지 않아요.

### 전단사인 이유

라운드 하나는 거꾸로 풀 수 있어요. 출력 $(c_0', c_1', c_2', c_3')$와 키를 알면 입력을 이렇게 되찾아요.

1. $c_3' = \mathrm{lo}_0 = (M_0 c_0) \bmod 2^{64}$예요. $M_0$는 홀수라서 $2^{64}$를 법으로 하는 곱셈 역원 $M_0^{-1}$이 있어요. $c_0 = M_0^{-1} c_3' \bmod 2^{64}$로 $c_0$를 되찾아요.
2. $c_0$를 알았으니 $\mathrm{hi}_0$를 다시 계산하고, $c_3 = c_2' \oplus \mathrm{hi}_0 \oplus k_1$이에요.
3. 같은 방법으로 $c_1'$에서 $c_2$를, $c_0'$에서 $c_1$을 되찾아요.

입력을 출력에서 유일하게 되찾을 수 있으니 라운드는 전단사이고, 전단사를 열 번 합성한 것도 전단사예요. 이 구조는 일반화된 Feistel 함수예요. 아래 절반 $\mathrm{lo}(R) = (MR) \bmod 2^{64}$는 그 자체로 전단사인 부분이고, 위 절반에 키를 XOR한 $\mathrm{hi}(R) \oplus k$는 전단사일 필요가 없는 섞는 함수로, 다른 단어에 XOR로만 더해져요. XOR은 같은 값을 한 번 더 XOR하면 지워지니 되돌릴 수 있어요[1].

그래서 키 하나에 대해 256비트 계수기 $2^{256}$개가 모두 다른 256비트 블록으로 가요. 한 키의 수열 안에서 같은 블록이 두 번 나오는 일은 없어요. (64비트 단어 하나하나는 우연히 같을 수 있어요. 진짜 난수도 그래요.)

### 곱셈이 비트를 잘 섞는 이유

정수 곱셈은 한 명령으로 많은 비트를 섞는 가장 값싼 방법이에요. 상수 M과 곱할 때 입력의 한 비트를 뒤집으면 이런 일이 생겨요[1].

- **아래 절반:** 입력의 j번째 비트를 뒤집는 것은 $\pm 2^j$를 더하는 것이고, 곱은 $\pm 2^j M$만큼 바뀌어요. M이 홀수라서 $2^j M$의 가장 낮은 1비트가 j번째예요. 그래서 아래 절반은 j번째와 그 위쪽 비트만 바뀌고(j번째 비트는 늘 바뀌어요), 받아올림 때문에 여러 비트가 한꺼번에 바뀌어요.
- **위 절반:** 바뀐 값이 $2^{64}$ 자리를 넘어가는 부분이에요. 받아올림이 위로 번지면서 위 절반의 아래쪽 비트가 주로 바뀌어요.

한쪽은 위로, 다른 쪽은 아래로 퍼져요. Philox는 두 절반을 모두 쓰고(아래 절반은 다음 단어로, 위 절반은 다른 단어와 XOR), 단어 자리를 바꿔서 다음 라운드의 곱셈에 넣어요. 몇 라운드가 지나면 입력의 어느 비트든 출력의 모든 비트에 영향을 줘요.

이것을 수치로 볼 수 있어요. 무작위 계수기와 키에서 계수기의 한 비트를 뒤집고, 출력 256비트 가운데 몇 비트가 바뀌는지를 라운드 수별로 세면 이래요(무작위 입력 2000쌍).

### 곱수와 라운드 수

곱수 $M_0$, $M_1$은 저자들이 찾은 값이에요. 무작위 후보 수천 개에서 시작해 한두 비트를 바꾸고, 좋은 후보끼리 조각을 섞고, 4라운드 뒤의 avalanche 통계량이 가장 좋아지는 쪽으로 다듬었어요. 그다음 이 곱수로 몇 라운드부터 통계 검사를 모두 통과하는지를 봤어요[1].

**Crush-resistant**는 저자들이 정한 기준이에요. TestU01의 SmallCrush, Crush, BigCrush를 한 수열만이 아니라 계수기와 키를 나누는 여러 방식(연속 구간, 일정 간격, 키마다 몇 개씩 번갈아, 한 비트씩만 바뀌는 Gray 부호 계수기, 1인 비트 수가 일정한 계수기 등) 89가지 이상으로 돌려 실패가 하나도 없는 것이에요[1]. Philox4×64는 7라운드에서 이 기준을 통과했고, 저자들은 3라운드를 안전 여유로 더한 10라운드를 권해요. 여유분의 비용이 작기 때문이에요[1]. stardust는 이 권장을 따라 10라운드를 써요. numpy의 `Philox`도 같은 Philox4×64-10이에요.

### 키 일정

라운드마다 키에 상수를 더해요(첫 라운드는 키 그대로).

$$
k_0^{(r)} = k_0 + r\,W_0, \quad k_1^{(r)} = k_1 + r\,W_1 \pmod{2^{64}}, \qquad
W_0 = \texttt{0x9E3779B97F4A7C15},\; W_1 = \texttt{0xBB67AE8584CAA73B}
$$

$W_0$는 황금비의 소수 부분에 $2^{64}$를 곱한 값, $W_1$은 $\sqrt{3} - 1$에 $2^{64}$를 곱한 값이에요. $r W \bmod 2^{64}$처럼 무리수의 배수를 1로 나눈 나머지를 늘어놓은 것을 Weyl 수열이라고 하고, 같은 논문의 ARS 생성기가 쓰는 키 일정이에요[1]. 덧셈 두 번이라 비용이 거의 없고, 라운드마다 다른 키를 섞어서 열 라운드가 모두 같은 함수가 되지 않게 해요.

### Philox4×64-10을 고른 이유

- **계수기형이어야 해요.** 위에서 본 결정성 때문이에요.
- **64비트 단어.** 원소 하나가 64비트 단어 하나를 받으면 [0, 1)의 실수(53비트)와 범위 정수(64비트)를 단어 하나로 만들어요. 32비트 단어를 내는 변종(Philox4×32)이면 원소마다 단어 둘을 이어 붙여야 해요. AArch64에는 64비트 곱의 위 절반을 내는 `UMULH`가 있어서 64비트 변종이 불리하지 않아요.
- **공개된 설계와 알려진 답.** 라운드 수는 저자들의 권장값이고, Random123에 알려진 답(KAT) 벡터가 있어서 구현이 맞는지 비트까지 확인할 수 있어요(아래 "정확성"). numpy에도 같은 함수가 있어서 블록 단위로도 맞춰 볼 수 있어요.
- **같은 논문의 다른 후보.** AES 기반(ARS, AES)은 AES 전용 명령에 기대요. Threefry4×64는 덧셈·회전·XOR만 쓰지만 권장 라운드가 20이에요[1]. Philox는 라운드가 적은 대신 라운드 하나에 곱셈을 써요.

## 원소와 계수기

Philox 블록 하나는 64비트 단어 넷을 줘요. 이 단어를 수열의 원소에 어떻게 나눠 주느냐가 결정성을 정해요.

### 원소 e의 첫 단어

원소 e는 계수기 $(\lfloor e/4 \rfloor, 0, 0, 0)$ 블록의 $e \bmod 4$번째 단어를 받아요. 이웃한 원소 넷이 블록 하나를 나눠 쓰는 셈이에요.

원소마다 블록을 하나씩 쓰면(원소 e에 계수기 $(e, 0, 0, 0)$의 단어 0만) 블록 하나에서 단어 넷 가운데 하나만 쓰니 계산이 네 배예요. 원소 e의 블록에서 단어 넷을 모두 그 원소에 주는 방법(첫 단어 하나, 나머지 셋은 기각용 예비)도 같은 이유로 쓰지 않아요. 기각은 드물어서, 대부분의 원소에서 예비 단어 셋이 버려져요.

### 기각용 추가 단어

`integers`처럼 기각 표본을 쓰는 원소는 가끔 단어가 더 필요해요. 원소 e의 k번째 추가 단어($k = 0, 1, 2, \dots$)는 계수기 $(e, 1 + \lfloor k/4 \rfloor, 0, 0)$ 블록의 $k \bmod 4$번째 단어예요. 곧 계수기 $(e, j, 0, 0)$, $j \ge 1$의 블록을 차례로 써요.

```cpp
// csrc/random/philox.hpp, Stream::extra
// 원소 e의 추가 단어 k (0, 1, 2, ...): 블록 j = 1 + k/4의 단어 k mod 4
std::uint64_t extra(std::uint64_t e, std::uint64_t k) const {
    return philox({e, 1 + (k >> 2), 0, 0}, key_)[k & 3];
}
```

두 종류의 계수기는 계수기의 둘째 단어로 갈려요. 첫 단어용은 둘째 단어가 0, 추가 단어용은 1 이상이에요. 그래서 둘은 절대 만나지 않고, 어떤 단어도 두 원소가 함께 쓰지 않아요. 같은 원소의 추가 단어끼리도 k가 다르면 다른 단어예요.

| 쓰임 | 계수기 $(c_0, c_1, c_2, c_3)$ | 단어 | 쓰는 범위 |
|---|---|:---:|---|
| 원소 e의 첫 단어 | $(\lfloor e/4 \rfloor, 0, 0, 0)$ | $e \bmod 4$ | $c_0 \lt 2^{62}$ |
| 원소 e의 추가 단어 k | $(e, 1 + \lfloor k/4 \rfloor, 0, 0)$ | $k \bmod 4$ | $c_0 \lt 2^{64}$, $c_1 \ge 1$ |

위치 `pos`는 64비트이고 $2^{64}$에서 0으로 돌아가요(`_reserve`가 `& 0xFFFF…`로 잘라요). 그래서 키 하나의 수열은 원소 $2^{64}$개예요. 초당 10⁹개를 꺼내도 500년 넘게 걸리는 길이예요.

### 그래서 생기는 성질

원소 e의 값은 (키, e)만으로 정해져요. 여기서 세 가지 성질이 바로 나와요.

**1. 스레드 수와 무관해요.** 원소 범위를 어떻게 조각내고 어느 스레드가 어느 조각을 맡든, 각 원소는 자기 계수기에서 자기 단어를 받아요.

```python
>>> import stardust as sd
>>> before = sd.get_num_threads()
>>> outs = []
>>> for th in (1, 10):
...     sd.set_num_threads(th)
...     outs.append(sd.random.default_rng(7).integers(0, 3 * 2**61, shape=1_000_000))
>>> sd.set_num_threads(before)
>>> bool(sd.all(outs[0] == outs[1]))
True
```

범위 $3 \cdot 2^{61}$은 원소의 약 4분의 1이 기각되는 범위예요($2^{64} \bmod r = 2^{62}$이므로 기각 확률 $2^{62}/2^{64}$). 기각이 많아도 결과는 같아요.

**2. 호출을 나눠 불러도 같아요.** 8개를 한 번에 뽑든 3개와 5개로 나눠 뽑든, 원소 0–7은 같은 원소 번호예요.

```python
>>> whole = sd.random.default_rng(7).integers(0, 3 * 2**61, shape=8)
>>> s = sd.random.default_rng(7)
>>> parts = sd.concat([s.integers(0, 3 * 2**61, shape=3), s.integers(0, 3 * 2**61, shape=5)])
>>> bool(sd.all(whole == parts))
True
>>> s.state['position']
8
```

**3. 위치는 기각과 상관없이 정확히 n만큼 움직여요.** 기각한 원소는 자기 추가 단어를 쓰고, 그 단어는 수열의 위치를 차지하지 않아요. 상태형 생성기라면 위의 호출에서 위치가 기각 횟수만큼 더 움직이고, 뒤의 모든 원소가 그만큼 밀려요.

### 호출 하나가 쓰는 원소 수

메서드마다 예약하는 원소 수는 이래요. 다음 호출이 어디서 시작하는지는 이 수로만 정해져요.

| 호출 | 예약하는 원소 수 | 원소 하나가 쓰는 단어 |
|---|:---:|---|
| `random(shape)` | n (스칼라면 1) | 첫 단어 하나 |
| `integers(..., shape)` | n (스칼라면 1) | 첫 단어, 기각되면 추가 단어 |
| `choice(a, shape=k)` 복원, 균등 | k | `integers`와 같아요 |
| `choice(a, shape=k, p=p)` 복원, 가중치 | k | `random`과 같아요 |
| `choice(a, shape=k, replace=False)` 균등 | k | Fisher–Yates 걸음 하나 |
| `choice(a, shape=k, replace=False, p=p)` | n (모집단 크기) | 모집단 원소마다 경주 키 하나 |
| `permutation(x)` | n (첫 축 길이) | Fisher–Yates 걸음 하나 |

인자 검사는 예약보다 먼저 해요. 그래서 에러로 끝난 호출은 위치를 움직이지 않아요. 각 방법의 자세한 내용은 [뽑기 알고리즘](/internals/random/sampling/)에 있어요.

## 블록 넷을 함께: `philox4`

### 의존 사슬

블록 하나를 계산하는 열 라운드는 앞 라운드의 결과가 있어야 다음 라운드를 시작할 수 있어요. 라운드 안의 두 곱($M_0 c_0$, $M_1 c_2$)은 서로 독립이지만, 다음 라운드의 곱은 이번 라운드의 XOR 결과를 기다려요. 그래서 블록 하나는 "곱 → XOR → 곱 → XOR → …"이 열 번 이어진 **의존 사슬**이에요.

현대 CPU의 곱셈기는 파이프라인이라 매 사이클 새 곱셈을 받을 수 있지만, 곱셈 하나의 결과가 나오기까지는 몇 사이클이 걸려요(지연 시간). 사슬 하나만 계산하면 곱셈기가 대부분의 사이클을 결과를 기다리며 놀아요. 블록을 하나씩 계산하면 블록당 약 12ns가 걸리는데, 이 시간은 연산량이 아니라 사슬의 길이가 정해요.

### 네 사슬을 섞어요

서로 다른 계수기의 블록은 완전히 독립이에요. 블록 넷의 라운드 r을 한꺼번에 계산하면, 한 블록의 곱셈이 결과를 기다리는 동안 다른 블록의 곱셈이 곱셈기에 들어가요.

```cpp
// csrc/random/philox.hpp, philox4 (줄인 발췌)
// 계수기 (c0[q], 0, 0, 0), q = 0..3의 블록 넷을 함께
uint64_t a[4], b[4], c[4], d[4];                 // 블록마다 단어 넷 (b, c, d는 0에서 시작)
for (int q = 0; q < 4; ++q) a[q] = c0[q], b[q] = 0, c[q] = 0, d[q] = 0;
uint64_t k0 = key.k0, k1 = key.k1;
for (int r = 0; r < 10; ++r) {
    if (r > 0) k0 += kW0, k1 += kW1;              // 키 일정은 네 블록이 같아요
    for (int q = 0; q < 4; ++q) {                 // 서로 독립인 네 블록의 같은 라운드
        uint64_t hi0, lo0, hi1, lo1;
        mulhilo(kM0, a[q], hi0, lo0);
        mulhilo(kM1, c[q], hi1, lo1);
        const uint64_t na = hi1 ^ b[q] ^ k0, nc = hi0 ^ d[q] ^ k1;
        a[q] = na, b[q] = lo1, c[q] = nc, d[q] = lo0;
    }
}
// out[4q .. 4q+3] = (a[q], b[q], c[q], d[q])
```

- 단어를 블록별 구조체가 아니라 `a[4]`, `b[4]`, `c[4]`, `d[4]`처럼 같은 자리의 단어끼리 모아 둬요. 안쪽 루프가 짧고 고정 길이(4)라 컴파일러가 펼쳐서 레지스터에 두고, 독립인 네 곱셈 묶음을 나란히 내보내요.
- 첫 단어용 계수기는 둘째·셋째·넷째 단어가 언제나 0이라 `b`, `c`, `d`를 0으로 시작해요. 계수기 배열을 받을 필요가 없어요.
- 키 일정은 계수기와 무관하니 라운드마다 한 번만 계산해 네 블록이 같이 써요.
- 블록 하나하나의 계산은 `philox()`와 완전히 같아요. 계산 순서만 섞었을 뿐 각 블록의 연산은 그대로라서 비트도 같아요.

같은 조건(균등 난수 10⁶개, 1스레드)에서 블록을 하나씩 계산하면 2.98ms, 넷을 함께 계산하면 1.14ms예요. 원소 넷이 블록 하나이니 블록당 약 11.9ns에서 약 4.6ns가 된 셈이에요(1.14ms에는 실수 변환과 결과 쓰기도 들어 있어요). 블록당 12ns라는 사슬의 지연 시간이 처리량의 한계였다는 뜻이에요.

### 16원소 묶음: `Stream`

커널은 원소 번호로 단어를 달라고 해요. `Stream`이 그 사이에서 블록 넷(단어 16개)을 한 묶음으로 계산해 두고 꺼내 줘요.

```cpp
// csrc/random/philox.hpp, Stream::first (줄인 발췌)
std::uint64_t first(std::uint64_t e) {
    const std::uint64_t g = e >> 4;                     // e가 든 묶음 번호
    if (!have_ || g != group_) {                         // 새 묶음이면 블록 4g .. 4g+3을 함께 계산
        const std::uint64_t blocks[4] = {4 * g, 4 * g + 1, 4 * g + 2, 4 * g + 3};
        philox4(blocks, key_, words_);                   // words_: std::array<uint64_t, 16>
        group_ = g, have_ = true;
    }
    return words_[e & 15];                               // 원소 e = 묶음 안의 e mod 16번째 단어
}
```

묶음의 경계는 원소 번호로 정해져요(16의 배수). 호출의 시작 위치 `pos`나 조각의 경계와는 상관없어요. 그래서 조각 경계가 묶음 중간에 떨어지면 그 묶음을 양쪽 조각이 한 번씩 계산하지만(4096원소 조각마다 많아야 묶음 하나, 1/256 정도의 중복), 원소가 받는 단어는 어느 쪽에서 계산하든 같아요.

추가 단어(`extra`)는 기각할 때만 필요하고 드물어서 `philox()`로 블록 하나씩 계산해요.

## 호출 하나의 흐름: 예약과 병렬 계산

### 위치 예약

```python
# src/stardust/random/__init__.py, Generator._reserve
def _reserve(self, n):
    with self._lock:                     # threading.Lock
        key, p = self._key, self._pos    # 키와 위치를 함께 읽어요
        self._pos = (p + n) & _MASK64    # 2^64에서 0으로
    return key, p
```

메서드는 인자를 검사한 뒤 `_take(n, 이름)`을 거쳐 `_reserve(n)`으로 키와 구간 `[p, p + n)`을 받아 커널에 넘겨요(`_k.uniform(key[0], key[1], pos, …)`). `_take`는 예약하기 전에 호출이 받을 메모리(결과, 그리고 섞는 호출은 작업 메모리까지)를 이 컴퓨터의 물리 메모리와 비교해서, 넘으면 메서드 이름을 붙인 `MemoryError`(`random(): cannot allocate 8796093022208 bytes: more than this machine's physical memory`)를 내요. 그래서 거절된 호출은 위치를 움직이지 않아요. 잠금 안에서 하는 일은 읽기 셋과 쓰기 하나뿐이에요. 원소 계산은 잠금을 풀고 나서 해요.

키도 잠금 안에서 함께 읽는 것은 다른 스레드의 `state` 대입 때문이에요. `state` 대입은 키와 위치를 한 잠금 안에서 함께 바꿔요([시드, spawn, 상태](/internals/random/seeding/)). 메서드가 위치만 잠금 안에서 읽고 키는 `self._key`로 따로 읽으면, 그 사이에 대입이 끼어들어 옛 키와 새 위치(또는 그 반대)로 계산할 수 있어요. 둘을 한 번에 읽으면 대입 전 상태든 대입 후 상태든 온전한 한쪽만 봐요.

잠금이 필요한 이유는 "읽고 더해서 쓰기"가 한 동작이 아니기 때문이에요. GIL이 있어도 CPython은 바이트코드 사이에서 스레드를 바꿀 수 있어요. 두 스레드가 같은 `p`를 읽고 각자 `p + n`을 쓰면 두 호출이 같은 구간을 받아 같은 난수를 두 번 써요. 잠금 안에서 읽고 쓰면 구간이 겹치지 않고 빈틈 없이 이어져요.

- **깨지지 않아요.** 위치는 잠금 안에서만 바뀌고, 키는 계산 중에 바뀌지 않아요.
- **같은 난수를 두 번 쓰지 않아요.** 구간이 겹치지 않으니 어떤 원소 번호도 두 호출에 가지 않아요.
- **어느 스레드가 어느 구간을 받는지는 실행 순서에 달려요.** 각 호출의 결과는 받은 구간으로 정해지니, 스레드별 결과는 실행할 때마다 다를 수 있어요. 모든 호출이 받은 값을 모으면 언제나 같은 집합이에요.

스레드마다 재현되는 값이 필요하면 스레드마다 [`spawn`](/internals/random/seeding/)한 생성기를 주면 돼요. 생성기마다 키가 다르니 실행 순서와 상관없이 같은 값이에요.

테스트는 네 스레드가 생성기 하나에서 `integers(0, 2**62, shape=1000)`을 50번씩 부르게 하고, 끝난 뒤 위치가 정확히 200000이고 모은 20만 개의 값이 모두 다른지 확인해요(범위가 $2^{62}$이라 진짜로 같은 값이 나올 확률은 무시할 만해요). 구간이 한 번이라도 두 번 나갔다면 같은 값 1000개가 겹쳐 나와요.

### 병렬 분할

커널은 원소 범위 `[0, n)`을 배열 영역의 다른 수동 병렬 경로와 같은 `for_pieces`로 나눠요.

```cpp
// csrc/random/random.cpp, uniform (줄인 발췌)
inline constexpr std::int64_t kWordWork = 8;    // 원소 하나의 일: 블록 하나(~10ns)가 원소 넷을 맡아요

for_pieces(n, kParallelTask, n * kWordWork, [&](int64_t, int64_t i0, int64_t i1) {
    Stream s({k0, k1});                          // 조각마다 자기 Stream (묶음 캐시)
    for (int64_t i = i0; i < i1; ++i) o[i] = random::to_unit(s.first(pos + i));
});
```

- **조각:** `kParallelTask` = 2¹² = 4096원소씩이에요. 조각의 경계는 n과 4096만으로 정해지고, 스레드 수와 무관해요.
- **나눌지:** 일의 양을 "단순 원소별 연산 원소 몇 개 분량"으로 세어 배열 영역의 기준값 `kParallelThreshold` = 2¹⁵와 비교해요. 난수 원소 하나는 Philox 블록의 4분의 1이라 단순 연산보다 훨씬 무거워서 8로 쳐요. 그래서 원소가 4096개를 넘으면(조각이 둘 이상이면) 풀에서 돌아요.
- **조각마다 `Stream`:** 묶음 캐시가 조각 안에만 있으니 스레드끼리 공유하는 상태가 없어요. 조각이 순서 없이 아무 스레드에서 돌아도 돼요.
- **GIL:** 일(`n * kWordWork`)이 기준값 이상이면, 곧 원소가 4096개 이상이면 `for_pieces`가 스레드 수와 상관없이 GIL을 놓아요. 풀에서 돌든, 1스레드라 호출 스레드에서 차례로 돌든 같아요. 그동안 다른 Python 스레드가 같은 생성기에서 다음 구간을 예약하고 자기 계산을 할 수 있어요. 풀이 이미 다른 호출로 바쁘면 그 호출은 자기 스레드에서 혼자 계산하고, 결과는 같아요([스레드풀과 결정성](/internals/core/threads/#gil)).

`integers`, `race_keys`, `bits`도 같은 모양이에요. `fisher_yates`(섞기와 비복원 추출)만 순차 알고리즘이라 풀을 쓰지 않고, 크기와 상관없이 루프 동안 GIL만 놓아요. 그래도 걸음 i가 원소 `pos + i`의 단어를 쓰니 결과는 (키, `pos`, n, k)로만 정해져요.

같은 조건(원소 10⁶개, Apple M4 Pro, numpy 2.5.4)에서 `random(10**6)`은 stardust 1스레드 1.14ms, 10스레드 0.15ms이고, numpy의 `Generator`는 PCG64로 2.72ms, Philox로 2.37ms예요. 1스레드에서도 numpy보다 빠른 이유와 다른 메서드의 수치는 [성능과 검증](/internals/random/performance/)에서 다뤄요.

## 정확성: 알려진 답

생성기가 틀리면 결과가 "조금 덜 무작위"가 될 뿐 눈에 띄는 에러가 나지 않아요. 그래서 블록 함수를 비트 단위로 확인해요.

**알려진 답(KAT, known-answer test).** Random123은 함수마다 입력과 정답 출력 쌍을 공개해요(`kat_vectors`). Philox4×64-10의 세 벡터를 그대로 써요. 시험용으로 노출한 `_core.random.philox_block`이 블록 하나를 계산하고, 테스트가 네 단어를 비교해요.

| 계수기 | 키 | 출력 (64비트 단어 넷) |
|---|---|---|
| 0, 0, 0, 0 | 0, 0 | `16554D9ECA36314C` `DB20FE9D672D0FDC` `D7E772CEE186176B` `7E68B68AEC7BA23B` |
| 모든 비트 1 | 모든 비트 1 | `87B092C3013FE90B` `438C3C67BE8D0224` `9CC7D7C69CD777B6` `A09CAEBF594F0BA0` |
| π의 16진 자릿수 (`243F6A88…`) | π의 다음 자릿수 (`452821E6…`) | `A528F45403E61D95` `38C72DBD566E9788` `A5A1610E72FD18B5` `57BD43B5E52B7FE6` |

세 번째 벡터는 모든 단어에 0과 1이 섞여 있어 곱의 위·아래 절반, 키 일정의 받아올림을 모두 지나가요. 첫 번째는 0 입력, 두 번째는 모든 덧셈이 넘치는 극단이에요.

**계수기 배치.** 블록 함수가 맞아도 원소에 단어를 잘못 나눠 주면 결정성이 깨지거나 같은 단어를 두 번 쓸 수 있어요. 테스트는 Python으로 쓴 참조 Philox로 "원소 e = 블록 $(\lfloor e/4 \rfloor, 0, 0, 0)$의 단어 $e \bmod 4$"를 직접 계산하고, 커널 `bits`가 낸 원시 단어와 비교해요. 시작 위치는 0, 5, 13(묶음 중간)과 $2^{40} + 7$(큰 위치), 길이는 3–64로 묶음 경계를 여러 번 넘게 골랐어요. `philox4`와 `Stream`의 묶음 계산이 이 비교를 통과하니, 블록 넷을 섞어 계산해도 비트가 같다는 것도 함께 확인돼요.

**결정성.** 같은 시드로 스레드 1·3·10개에서 `random`(300001개), `integers`(200003개), `permutation`(50000), `choice`(100000개)를 이어 부르고 바이트까지 같은지, 그리고 한 호출 10000개와 1 + 3333 + 6666개로 나눈 호출이 같은지 확인해요. 길이를 4096의 배수가 아니게 골라 마지막 조각이 짧은 경우도 지나가요.

통계 검사(KS, 카이제곱)와 다른 테스트는 [성능과 검증](/internals/random/performance/)에 있어요.
