핵심은 다섯 가지예요.

1. **numpy의 `SeedSequence`와 같은 해시예요.** 그래서 같은 시드면 키가 numpy `Philox`의 키와 비트까지 같아요. numpy에 기대지 않으려고 Python으로 옮겼어요.
2. **해시는 비트를 철저히 섞어요.** 시드 0과 1의 키는 128비트 가운데 절반쯤이 달라요. 게다가 128비트 이하의 서로 다른 int 시드는 반드시 서로 다른 키가 돼요.
3. **`spawn`은 키를 새로 만들어요.** 자식은 부모의 엔트로피에 자기 번호(`spawn_key`)를 덧붙여 같은 해시를 거친 키를 받아요. 위치를 쪼개 나누지 않아요.
4. **상태는 키가 아니라 시드 수열과 위치예요.** `state`는 엔트로피, `spawn_key`, 낳은 자식 수, 위치를 담은 dict이고, 되살릴 때 키를 다시 계산해요. 복사와 피클도 이 dict 하나로 해요.
5. **numpy와 값은 달라요.** 키와 블록 함수는 같지만 계수기를 쓰는 순서와 단어를 원소에 나누는 방법이 달라서예요.

## 시드에서 32비트 단어로

해시는 32비트 단어의 나열을 입력으로 받아요. 시드는 먼저 이 나열로 바뀌어요.

- **int:** 아래쪽부터 32비트씩 잘라 늘어놓아요(little-endian). 0은 `[0]` 한 단어예요. 크기 제한이 없어서 $2^{200}$ 같은 시드도 단어 일곱 개가 될 뿐이에요.
- **int의 시퀀스:** 원소마다 위처럼 펼쳐서 차례로 이어 붙여요.
- **`None`:** `secrets.randbits(128)`로 운영체제의 엔트로피에서 128비트 int를 받아 그 int를 시드로 써요(아래 "엔트로피").

```python
# src/stardust/random/__init__.py
def _words(n):
    """A non-negative int as little-endian 32-bit words (0 -> [0])."""
    out = [n & _MASK32]
    n >>= 32
    while n:
        out.append(n & _MASK32)
        n >>= 32
    return out
```

음수, `bool`, 실수, 문자열은 받지 않아요. `bool`을 따로 막는 것은 `True`가 Python에서 int 1이라 실수로 넘긴 플래그가 조용히 시드 1이 되기 때문이에요. 실수 시드 `1.5`를 버림해서 받아 주면 `1.5`와 `1.7`이 같은 수열이 되는 것도 마찬가지로 알아채기 어려운 함정이라 `TypeError`예요.

### 같은 단어 나열이면 같은 키

이 변환은 단어의 나열만 남기고 시드의 "모양"은 버려요. 그리고 해시는 단어가 넷보다 적으면 빈자리를 0으로 채워요(아래). 그래서 다음은 모두 같은 키예요. numpy의 `SeedSequence`도 똑같아요.

```python
>>> import stardust as sd
>>> a = sd.random.default_rng(42).random(3)
>>> sd.random.default_rng((42,)).random(3).tolist() == a.tolist()
True
>>> sd.random.default_rng((42, 0)).random(3).tolist() == a.tolist()
True
>>> sd.random.default_rng(2**32).random(3).tolist() == sd.random.default_rng((0, 1)).random(3).tolist()
True
```

## 해시: 풀에 섞고 다시 뽑기

해시는 두 단계예요. 단어 나열을 32비트 단어 넷짜리 **풀**(128비트)에 섞어 넣고, 풀에서 키를 뽑아내요. numpy의 `SeedSequence`(`numpy/random/bit_generator.pyx`)를 그대로 옮긴 것이고[1], numpy는 이 설계가 M. E. O'Neill의 `seed_seq` 대안에서 왔다고 밝혀요[2].

### 부품 둘: `hashmix`와 `mix`

```python
# src/stardust/random/__init__.py (상수는 numpy와 같아요)
_INIT_A, _MULT_A = 0x43B0D7E5, 0x931E8875
_INIT_B, _MULT_B = 0x8B51F9DD, 0x58F38DED
_MIX_MULT_L, _MIX_MULT_R = 0xCA01F9DD, 0x4973F715
_XSHIFT = 16

def _hashmix(value, h):              # h.v: 부를 때마다 바뀌는 해시 상수
    value ^= h.v
    h.v = (h.v * _MULT_A) & _MASK32
    value = (value * h.v) & _MASK32
    return value ^ (value >> _XSHIFT)

def _mix(x, y):
    r = (_MIX_MULT_L * x - _MIX_MULT_R * y) & _MASK32
    return r ^ (r >> _XSHIFT)
```

모든 연산은 32비트($\bmod 2^{32}$)예요. Python int는 크기 제한이 없어서 곱할 때마다 `& _MASK32`로 잘라 C의 `uint32_t` 산술을 흉내 내요.

**`hashmix`는 32비트 값 하나를 다른 32비트 값으로 보내는 전단사예요.** 세 걸음이 모두 되돌릴 수 있어요.

1. **상수와 XOR:** $v \oplus h$. 같은 $h$를 다시 XOR하면 돌아와요. 0이 0으로 가지 않게 해요.
2. **홀수와 곱셈:** $v \cdot h' \bmod 2^{32}$. $h'$이 홀수면 $2^{32}$를 법으로 하는 역원이 있어서 되돌릴 수 있어요. $h$는 홀수 `0x43B0D7E5`에서 시작해 홀수 `0x931E8875`를 계속 곱하니 언제나 홀수예요. 곱셈은 아래 비트의 변화를 위쪽 비트로 퍼뜨려요.
3. **xorshift:** $v \oplus (v \gg 16)$. 위 16비트를 아래 16비트에 섞어서, 곱셈이 퍼뜨리지 못하는 방향(위에서 아래로)을 채워요. 한 번 더 하면 원래대로 돌아와요. $y = v \oplus (v \gg 16)$이면 $y \oplus (y \gg 16) = v \oplus (v \gg 16) \oplus (v \gg 16) \oplus (v \gg 32) = v$예요(32비트에서 $v \gg 32 = 0$).

해시 상수 $h$는 `hashmix`를 부를 때마다 `MULT_A`를 곱한 값으로 바뀌어요. 그래서 같은 값이라도 몇 번째로 해시되느냐에 따라 다른 곱수를 만나요. 단어의 순서가 결과에 들어가는 이유예요. 상수가 바뀌는 순서는 입력 값과 무관하고 부른 횟수로만 정해져요.

**`mix(x, y)`는 y를 고정하면 x에 대한 전단사예요.** $L$ = `MIX_MULT_L`이 홀수라 $Lx - Ry$에서 x를 되찾을 수 있고, 마지막 xorshift도 되돌릴 수 있어요. 같은 이유로 x를 고정하면 y에 대해서도 전단사예요($R$ = `MIX_MULT_R`도 홀수).

### 1단계: 풀에 섞기

```python
# src/stardust/random/__init__.py, _SeedSequence.__init__ (줄인 발췌)
run = _entropy_words(entropy)
spawn = _entropy_words(self.spawn_key)
if spawn and len(run) < _POOL:              # spawn_key가 있으면 엔트로피를 단어 넷까지 0으로 채워요
    run = run + [0] * (_POOL - len(run))
data = run + spawn

h = _HashConst(_INIT_A)
pool = [_hashmix(data[i] if i < len(data) else 0, h) for i in range(_POOL)]   # (a)
for src in range(_POOL):                                                       # (b)
    for dst in range(_POOL):
        if src != dst:
            pool[dst] = _mix(pool[dst], _hashmix(pool[src], h))
for src in range(_POOL, len(data)):                                            # (c)
    for dst in range(_POOL):
        pool[dst] = _mix(pool[dst], _hashmix(data[src], h))
```

- **(a) 채우기:** 처음 네 단어를 하나씩 해시해서 풀의 네 칸에 넣어요. 단어가 넷보다 적으면 0을 해시해 채워요. 그래서 `42`와 `(42, 0)`이 같아요.
- **(b) 서로 섞기:** 풀의 칸마다 그 칸을 해시한 값을 다른 세 칸 모두에 `mix`로 섞어요(12번). 이것이 끝나면 처음 네 단어의 모든 비트가 풀의 모든 칸에 영향을 줘요. 순서상 늦게 섞이는 단어도 앞 칸에 영향을 줘요.
- **(c) 나머지 단어:** 다섯째 단어부터는 하나씩 해시해서 풀의 네 칸 모두에 섞어요. 단어가 m개면 이 부분이 $4(m - 4)$번이에요.

### 2단계: 키 뽑기

```python
# src/stardust/random/__init__.py, _SeedSequence.key
def key(self):
    """generate_state(2, uint64): the 128-bit Philox key as two 64-bit ints."""
    h = _INIT_B
    words = []
    for i in range(4):
        v = self._pool[i % _POOL] ^ h
        h = (h * _MULT_B) & _MASK32
        v = (v * h) & _MASK32
        words.append(v ^ (v >> _XSHIFT))
    return (words[0] | (words[1] << 32), words[2] | (words[3] << 32))
```

풀의 칸마다 다른 상수(`INIT_B`, `MULT_B`)로 한 번 더 해시해서 32비트 단어 넷을 내고, 둘씩 붙여 64비트 키 $(k_0, k_1)$을 만들어요. numpy의 `generate_state(2, numpy.uint64)`와 같은 결과예요. 출력용 해시를 따로 두는 것은 풀보다 많은 단어를 뽑을 때(numpy는 다른 생성기를 위해 수백 단어를 뽑기도 해요) 출력끼리 뻔한 상관이 생기지 않게 하려는 설계예요[2]. stardust는 단어 넷만 뽑지만 numpy와 같은 키를 내려고 이 단계도 그대로 따라요.

비용은 생성기를 만들 때 한 번이에요. 시드가 단어 넷 이하면 `hashmix` 16번, `mix` 12번, 그리고 키 뽑기의 해시 4번이에요. Python으로 해도 짧은 일이고, 난수를 꺼낼 때는 다시 하지 않아요.

### numpy에 기대지 않고 옮긴 이유

stardust는 실행할 때 numpy가 필요 없어요(numpy는 테스트에만 써요). 시드 해시 하나 때문에 numpy를 필수 의존성으로 만들 수 없어서 Python으로 옮겼어요. 같은 키를 내는지는 테스트가 확인해요. 시드 0, 1, 12345, $2^{32}$, $2^{64}+3$, $2^{200}+7$, `(1, 2, 3)`, `(0,)`, `(2**70, 5)`에서 `numpy.random.SeedSequence(seed).generate_state(2, numpy.uint64)`와 키를 비교해요. 단어 하나, 여러 단어, 다섯 단어 이상(단계 (c)를 지나는 경우)을 모두 덮어요.

C++로 옮기지 않은 이유는 단순해요. 한 번만 하는 짧은 계산이고, Python int로 쓰면 크기 제한 없는 시드를 그대로 단어로 펼칠 수 있어요.

## 비슷한 시드가 무관한 수열이 되는 이유

사람이 고르는 시드는 0, 1, 2, … 또는 42, 43처럼 몇 비트만 다른 경우가 많아요. 시드를 그대로 키로 쓰면 키도 몇 비트만 달라요. 이런 키 사이에 구조가 남지 않게 하는 장치가 두 겹 있어요.

**첫째 겹: 해시.** 연속한 시드의 키는 이래요.

| 시드 | $k_0$ | $k_1$ |
|:---:|---|---|
| 0 | `db2cd7e7b0f478be` | `abf4641a2c71ba49` |
| 1 | `672d8ee56d6791ff` | `8ae19ca14eb1072c` |
| 2 | `8c8ea222a8ed588b` | `55aa58f36ee114ca` |
| 3 | `ad068d6f5dfd711b` | `b2a36eea2433f5f9` |

시드 0부터 2000까지 이웃한 쌍 2000개에서 두 키의 다른 비트 수를 세면 평균 63.9, 표준편차 5.6이에요. 128비트가 서로 무관하다면 다른 비트 수는 이항 분포 $B(128, \tfrac12)$를 따르고 평균 64, 표준편차 $\sqrt{32} \approx 5.66$이에요. 시드 12345의 32비트를 하나씩 뒤집어도 평균 64.0비트가 달라요. 시드에서 한 비트가 바뀌면 키의 비트가 각각 절반의 확률로 바뀌는, avalanche 기준에 맞는 모습이에요.

**둘째 겹: Philox의 키 섞기.** 키는 Philox의 열 라운드 모두에 XOR로 들어가고, 곱셈을 거치며 퍼져요. Philox의 저자들은 계수기를 고정하고 키만 바꾸는 수열, 키를 일정 간격으로 바꾸는 수열도 통계 검사에 넣었고 실패가 없었어요[3]. 그래서 해시가 없더라도 이웃한 키의 수열 사이에서 검출되는 상관은 없어요. 해시는 그 위에 한 겹을 더하고, numpy와 같은 키를 내게 해요.

```python
>>> sd.random.default_rng(0).random(3)
array([ 0.6861121579458175,  0.5625922809380222, 0.43239533440406797], dtype=float64)
>>> sd.random.default_rng(1).random(3)
array([0.09551019029449048, 0.28028699622055075, 0.37536262264203024], dtype=float64)
```

### 128비트 이하의 시드는 키가 겹치지 않아요

위의 부품이 모두 전단사라서 더 강한 성질이 있어요. `spawn_key`가 없고 시드가 단어 넷 이하($0 \le \text{seed} \lt 2^{128}$)이면 네 단계가 모두 일대일이에요.

1. 단어 나열은 0을 채워 정확히 넷이 돼요. 서로 다른 int는 서로 다른 네 단어예요.
2. (a)의 `hashmix`는 칸마다 전단사예요. 해시 상수의 순서는 값과 무관하니, 칸 i의 변환은 시드와 상관없이 정해진 하나의 전단사예요.
3. (b)의 각 걸음 `pool[dst] = mix(pool[dst], hashmix(pool[src]))`는 다른 칸(`src`)을 그대로 두고 `dst` 칸만 바꾸며, `src` 칸을 알면 되돌릴 수 있어요. 되돌릴 수 있는 걸음 12개를 이은 것이니 풀 128비트 전체에 대한 전단사예요.
4. 키 뽑기는 칸마다 전단사예요.

그래서 시드 → 키가 일대일이에요. $2^{128}$보다 작은 서로 다른 int 시드는 반드시 서로 다른 키가 되고, 따라서 서로 다른 수열이에요. 시드가 단어 넷보다 길면 입력이 출력보다 많으니 겹칠 수는 있지만(비둘기집), 설계가 출력을 고르게 퍼뜨리려 하므로 겹칠 확률은 무작위 128비트 두 개가 같을 확률 수준이에요[2].

## 엔트로피: `seed=None`

시드를 주지 않으면 `secrets.randbits(128)`로 128비트 int를 받아요. `secrets`는 `os.urandom`을 거쳐 운영체제의 암호용 난수원을 쓰는 Python 표준 모듈이에요. numpy도 같은 크기(`pool_size × 32` = 128비트)를 같은 방법으로 받아요[1].

```python
# src/stardust/random/__init__.py, _seed_entropy
if seed is None:
    return secrets.randbits(128)
```

- **받은 값은 시드로 남아요.** 그 int가 엔트로피로 저장되니 `state['entropy']`에서 꺼내 같은 생성기를 다시 만들 수 있어요. "실행마다 다르게, 하지만 나중에 재현할 수 있게"가 돼요.
- **128비트인 이유:** 키가 128비트이니 그 이상은 의미가 없고, 그보다 적으면 키 공간을 다 쓰지 못해요. 프로그램 여러 개가 각자 시드 없이 생성기를 만들 때 두 키가 겹칠 확률은 생성기가 n개일 때 대략 $n^2 / 2^{129}$로, $n = 2^{20}$(백만 개)이어도 $2^{-89}$ 정도예요.

```python
>>> rng = sd.random.default_rng()
>>> e = rng.state['entropy']
>>> e.bit_length() <= 128
True
>>> sd.random.default_rng(e).random(3).tolist() == rng.random(3).tolist()
True
```

## `spawn`: 독립된 생성기 나누기

### 키 만들기

`spawn(n)`은 자식 생성기 n개를 만들어요. 자식 i의 시드 수열은 부모와 같은 엔트로피에 `spawn_key = 부모의 spawn_key + (i,)`를 붙인 것이고, 번호 i는 부모가 지금까지 낳은 자식 수(`n_children_spawned`)부터 매겨요.

```python
# src/stardust/random/__init__.py
class _SeedSequence:
    def spawn(self, n):
        first = self.n_children_spawned
        self.n_children_spawned += n
        return [_SeedSequence(self.entropy, self.spawn_key + (i,)) for i in range(first, first + n)]

class Generator:
    def spawn(self, n, /):
        n = _count(n, "spawn", "n")
        with self._lock:                       # 번호 매기기를 원자적으로
            seqs = self._seq.spawn(n)
        return [Generator(s) for s in seqs]    # 자식마다 해시를 다시 거쳐 키를 만들어요
```

해시의 입력은 엔트로피 단어 뒤에 `spawn_key` 단어를 이어 붙인 것이에요. 이때 엔트로피가 단어 넷보다 짧으면 넷까지 0으로 채운 뒤에 붙여요. 그래서 엔트로피 42의 자식 0은 단어 `[42, 0, 0, 0, 0]`을, 자식 1은 `[42, 0, 0, 0, 1]`을 해시해요.

```python
>>> parent = sd.random.default_rng(42)
>>> kids = parent.spawn(2)
>>> [k.state['spawn_key'] for k in kids]
[(0,), (1,)]
>>> parent.state
{'bit_generator': 'Philox4x64-10', 'entropy': 42, 'spawn_key': (), 'n_children_spawned': 2, 'position': 0}
>>> parent.spawn(1)[0].state['spawn_key']
(2,)
>>> kids[0].spawn(1)[0].state['spawn_key']
(0, 0)
```

- **다시 부르면 번호가 이어져요.** 두 번째 `spawn(1)`은 자식 2를 줘요. 같은 자식을 두 번 내주지 않아요. 번호 매기기는 잠금 안에서 해서, 여러 스레드가 동시에 `spawn`해도 번호가 겹치지 않아요.
- **부모의 위치와 무관해요.** 자식의 키는 엔트로피와 `spawn_key`만으로 정해지고, 부모가 난수를 얼마나 꺼냈는지는 들어가지 않아요. `spawn`은 부모의 위치를 움직이지도 않아요. 자식은 모두 위치 0에서 시작해요.
- **numpy와 같은 키예요.** `numpy.random.SeedSequence(42).spawn(3)`의 각 자식의 `generate_state(2, numpy.uint64)`와 stardust 자식의 키가 같고, `spawn(3)` 뒤의 `spawn(1)`이 numpy의 `spawn_key=(3,)`과 같은지까지 테스트가 확인해요.

### 독립인 이유

**형제끼리는 키가 반드시 달라요.** 형제는 마지막 단어(번호 i)만 다르고 앞의 단어는 같아요. 해시의 (a)·(b) 단계까지는 똑같이 진행되고, (c) 단계에서 마지막 단어가 `pool[dst] = mix(pool[dst], hashmix(i))`로 섞여요. 앞 단계의 풀이 같으니 이 걸음은 i에 대한 전단사예요(`hashmix`도 전단사, `mix`도 둘째 인자에 대해 전단사). 그래서 $i \lt 2^{32}$인 서로 다른 번호는 서로 다른 풀 칸을 만들고, 키 뽑기도 칸마다 전단사라 키가 달라요. numpy 문서도 최상위 생성기에서 한 단계만 spawn하면 모든 상태가 다르다는 것이 보장된다고 적어요[4].

**그 밖의 쌍(부모와 자식, 사촌끼리)은 확률적으로 달라요.** 단어 나열의 길이나 앞부분이 다르면 해시가 섞는 과정이 달라져서, 두 키는 무작위 128비트 두 개처럼 행동해요. numpy 문서는 생성기 n개 가운데 어느 둘이 겹칠 확률을 비관적으로 $n^2 \cdot 2^{-128}$ 정도로 잡고, 백만 개($2^{20}$)면 $2^{-88}$이라고 적어요[4].

**키가 다르면 수열은 독립으로 볼 수 있어요.** Philox는 키가 다른 수열을 번갈아 섞은 입력에도 통계 검사를 통과하도록 검증됐어요[3]. 테스트는 자식 둘의 균등 난수 10000개씩의 상관계수가 0.05보다 작은지도 봐요.

### 위치를 쪼개는 대신 키를 만드는 이유

같은 키의 수열을 구간으로 나눠 줄 수도 있어요. 자식 i에게 위치 $i \cdot 2^{40}$부터를 주는 식이에요. 이 방법은 쓰지 않아요.

- **자식이 몇 개를 꺼낼지 미리 알아야 해요.** 구간이 작으면 자식끼리 겹치고, 크면 자식 수가 제한돼요. 키 공간은 128비트라 이런 계산이 필요 없어요.
- **나무가 깊어지면 구간 계산이 복잡해져요.** 손주, 증손주로 갈수록 구간을 다시 쪼개야 해요. `spawn_key`는 tuple에 번호를 하나 붙이면 끝이에요.
- **numpy와 같은 방법이에요.** 같은 시드로 같은 자식 키를 얻어, numpy의 `Philox`로 블록을 맞춰 볼 수 있어요.

## `state`: 생성기의 전부

`state`는 생성기를 되살리는 데 필요한 것을 모두 담은 dict예요.

```python
>>> r = sd.random.default_rng(5)
>>> x = r.random(17)
>>> r.state
{'bit_generator': 'Philox4x64-10', 'entropy': 5, 'spawn_key': (), 'n_children_spawned': 0, 'position': 17}
```

| 항목 | 뜻 |
|---|---|
| `bit_generator` | 생성기 이름. 언제나 `'Philox4x64-10'`이에요. 다른 생성기의 상태를 실수로 넣는 것을 막아요 |
| `entropy` | 시드에서 나온 엔트로피(int 또는 int의 tuple). `None`으로 만든 생성기는 그때 받은 128비트 int예요 |
| `spawn_key` | 생성기 나무에서의 자리. 최상위는 `()`예요 |
| `n_children_spawned` | 지금까지 낳은 자식 수. 다음 `spawn`의 첫 번호예요 |
| `position` | 지금까지 꺼낸 원소 수. $0 \le \text{position} \lt 2^{64}$ |

**키는 담지 않아요.** 키는 앞의 세 항목에서 언제든 다시 계산할 수 있어요. 대신 시드 수열을 담아 두어야 되살린 생성기에서 `spawn`이 같은 자식을 같은 번호로 이어서 낼 수 있어요. 키만 저장하면 `spawn`을 이어 갈 수 없어요.

### 되돌리기

`state`에 dict를 대입하면 그 상태로 돌아가요.

```python
# src/stardust/random/__init__.py, Generator.state의 setter (줄인 발췌)
try:
    entropy = _seed_entropy(value["entropy"], ".state", "entropy")   # default_rng와 같은 검사
    spawn_key = tuple(_count(v, ".state", "spawn_key") for v in value["spawn_key"])
    n_spawned = _count(value["n_children_spawned"], ".state", "n_children_spawned")
except (TypeError, ValueError, OverflowError) as e:   # 공용 검사는 "이름(): "을 붙여요
    raise type(e)(str(e).replace(".state(): ", ".state: ", 1)) from None
pos = ...                                                     # int, 0 <= pos < 2**64
seq = _SeedSequence(entropy, spawn_key, n_spawned)            # 해시를 다시 해서 엔트로피 풀을 만들고
with self._lock:
    self._seq, self._key, self._pos = seq, seq.key(), pos     # 세 가지를 한꺼번에 바꿔요
```

- 필드가 빠졌거나 `bit_generator`가 다르거나 값의 타입·범위가 틀리면 `TypeError`·`ValueError`이고, 생성기는 바뀌지 않아요. 모든 검사와 해시를 잠금 밖에서 끝낸 뒤에 대입하기 때문이에요. 잠금 안의 `seq.key()`는 이미 만든 풀에서 단어 넷을 섞어 꺼내는 짧은 계산이에요.
- 에러 메시지는 모두 `.state: `로 시작하고 잘못된 키의 이름을 담아요(`.state: 'entropy' must be non-negative`, `.state: missing key 'position'`). `default_rng`와 함께 쓰는 검사 함수는 `함수이름(): ` 꼴로 메시지를 만들므로, 받은 메시지의 `.state(): `를 `.state: `로 바꿔 다시 던져요. 속성은 함수가 아니라서 괄호를 붙이지 않아요.
- 시드 수열, 키, 위치를 한 잠금 안에서 바꿔요. 다른 스레드가 `state`를 읽는 도중이어도 옛 키와 새 위치가 섞인 상태를 보지 않아요.

```python
>>> saved = r.state
>>> y = r.random(3)
>>> r.state = saved
>>> r.random(3).tolist() == y.tolist()
True
```

위치를 원소 단위로 담으니, 되살린 생성기는 다음 원소부터 정확히 이어 가요. 상태형 생성기처럼 "버퍼에 남은 32비트 반쪽"이나 "기각 때문에 앞서 나간 상태" 같은 것이 없어요. 원소 e의 값이 (키, e)로만 정해지기 때문이에요([계수기형 생성기](/internals/random/generator/)).

## 복사와 피클

```python
# src/stardust/random/__init__.py
def __reduce__(self):
    return (_restore, (self.state,))

def __copy__(self):
    return _restore(self.state)

def __deepcopy__(self, memo):
    return _restore(self.state)

def _restore(state):
    g = Generator(_SeedSequence(0))
    g.state = state
    return g
```

- **피클은 `state` dict 하나예요.** 피클에 들어가는 것은 모듈 함수 `_restore`의 이름과 int·tuple로 된 dict뿐이라, C++ 객체나 버전에 따라 바뀌는 내부 구조가 없어요. 시드 42의 생성기를 기본 프로토콜로 피클하면 144바이트예요.
- **`__reduce__`가 따로 있어야 하는 이유:** `Generator`는 `threading.Lock`을 속성으로 두는데, 잠금 객체는 피클할 수 없어요. 기본 피클은 속성을 그대로 저장하려다 실패해요. 상태 dict만 저장하고 되살릴 때 새 잠금을 만들어요. 복사도 같은 이유로 잠금을 공유하지 않는 새 객체를 만들어요.
- **복사본은 같은 수열을 이어 가요.** 원본과 같은 키, 같은 위치이니 같은 난수를 다시 내요. 저장해 두었다가 같은 값을 다시 얻는 데는 맞지만, 서로 다른 난수가 필요한 곳에 쓰면 같은 값이 두 번 쓰여요. `n_children_spawned`도 복사되므로, 원본과 복사본이 각자 `spawn`하면 같은 자식이 나와요. 독립된 생성기가 필요하면 `spawn`을 쓰세요.

```python
>>> import copy
>>> c = copy.copy(r)
>>> c.random(2).tolist() == r.random(2).tolist()
True
>>> c.spawn(1)[0].state == r.spawn(1)[0].state
True
```

## `default_rng(rng)`는 같은 객체를 돌려줘요

`default_rng`에 `Generator`를 주면 그 객체를 그대로 돌려줘요. 복사본을 만들지 않아요.

```python
# src/stardust/random/__init__.py
def default_rng(seed=None, /):
    if isinstance(seed, Generator):
        return seed
    return Generator(_SeedSequence(_seed_entropy(seed, "default_rng")))
```

이렇게 하면 시드든 생성기든 받는 함수를 한 줄로 쓸 수 있어요.

```python
>>> def noisy(x, seed=None):
...     rng = sd.random.default_rng(seed)
...     return x + rng.random(2)
>>> rng = sd.random.default_rng(42)
>>> noisy(0.0, rng)
array([0.4513007976393718, 0.5280337747949365], dtype=float64)
>>> noisy(0.0, rng)
array([ 0.794826025358168, 0.7675771890620597], dtype=float64)
>>> rng.state['position']
4
```

- 생성기를 넘기면 함수 안의 `rng`가 바깥의 `rng`와 같은 객체라서, 함수가 꺼낸 만큼 바깥의 위치도 나아가요. 두 번 부르면 다음 값이 나와요.
- `default_rng`가 복사본을 돌려준다면, 함수가 꺼낸 난수가 바깥 생성기의 위치에 반영되지 않아요. 같은 생성기로 함수를 두 번 부르면 같은 난수가 반복되고, 함수 뒤에 바깥에서 꺼낸 난수도 함수가 쓴 것과 겹쳐요. 에러 없이 결과만 틀리는 버그예요.
- 정수 시드를 넘기면 부를 때마다 새 생성기라서 같은 시드면 같은 결과예요. 재현이 필요한 쪽과 이어 쓰기가 필요한 쪽을 같은 코드가 처리해요.

numpy의 `numpy.random.default_rng`도 `Generator`를 받으면 같은 객체를 돌려줘요(numpy 2.5.4).

## numpy와 키는 같지만 값이 다른 이유

같은 시드에서 stardust와 numpy의 `Philox`는 키가 같고(위 해시) 블록 함수도 같아요(같은 Philox4×64-10, 알려진 답이 같아요). 그런데 `random`, `integers`의 값은 달라요. 계수기를 쓰는 방법이 달라서예요.

### 1. 첫 블록의 계수기

numpy의 `Philox`는 계수기 0에서 시작하지만, 단어를 꺼낼 때 계수기를 먼저 1 올리고 블록을 계산해요. 그래서 numpy의 첫 블록은 계수기 $(1, 0, 0, 0)$이에요. stardust는 원소 0–3이 계수기 $(0, 0, 0, 0)$, 원소 4–7이 $(1, 0, 0, 0)$이에요. 둘 다 블록의 네 단어를 순서대로 쓰니, numpy의 j번째 64비트 단어는 stardust의 원소 $j + 4$의 단어예요.

`random`은 두 라이브러리 모두 "위 53비트 × 2⁻⁵³"이라, 같은 시드의 `random` 수열은 원소 넷만큼 밀려서 같아요.

```python
>>> import numpy as np
>>> mine = sd.random.default_rng(42).random(8)
>>> theirs = np.random.Generator(np.random.Philox(42)).random(4)
>>> mine[4:].tolist() == theirs.tolist()
True
```

이 일치는 키 해시와 블록 함수가 numpy와 비트까지 같다는 것을 한 번에 보여 줘요.

### 2. 단어를 원소에 나누는 방법

`integers`부터는 밀린 것만으로 설명되지 않아요.

```python
>>> sd.random.default_rng(42).integers(0, 1000, shape=8)
array([451, 528, 794, 767,  86, 141, 270, 874], dtype=int64)
>>> np.random.Generator(np.random.Philox(42)).integers(0, 1000, size=8)
array([925,  86, 140, 141, 407, 270, 235, 874])
```

- **numpy는 범위가 $2^{32}$ 이하면 64비트 단어를 32비트 반쪽 둘로 나눠** 원소 둘에 써요(아래 반쪽 먼저). 위의 numpy 결과에서 홀수째 자리의 86, 141, 270, 874는 단어마다 위 반쪽에서 나온 값이고, 같은 단어를 64비트로 쓴 stardust의 원소 4–7과 같아요. stardust는 범위와 상관없이 원소 하나가 64비트 단어 하나를 써요.
- **기각한 원소:** numpy는 수열의 다음 단어(또는 반쪽)를 가져가서 뒤의 원소가 모두 밀려요. stardust는 그 원소의 추가 계수기 $(e, j, 0, 0)$를 써서 다른 원소는 그대로예요.
- **`choice`, `permutation`:** 알고리즘이 달라요(가중치 비복원 추출의 Efraimidis–Spirakis 경주 등, [뽑기 알고리즘](/internals/random/sampling/)).

numpy의 방식에서는 원소 i가 수열의 몇째 단어(반쪽)를 쓰는지가 범위와 앞 원소의 기각 횟수에 달려 있어요. stardust는 원소 i의 단어를 (키, `pos + i`)만으로 정해서, 원소마다 독립으로, 아무 스레드에서나 계산할 수 있어요. numpy와 값까지 같게 만들려면 이 성질을 버려야 해서, stardust는 키 호환까지만 해요. 그래서 numpy에서 쓰던 시드를 그대로 쓰면 분포는 같고 값은 다른 결과를 얻어요.
