## 한눈에 보기

생성기(Philox4×64-10)가 내놓는 것은 64비트 부호 없는 정수, 곧 **단어**뿐이에요. 사용자가 원하는 것은 [0, 1)의 실수, 정해진 범위의 정수, 섞인 순서, 주머니에서 꺼낸 표본이에요. 이 페이지는 단어를 그런 값으로 바꾸는 네 도구, [random](/api/random/random/), [integers](/api/random/integers/), [permutation](/api/random/permutation/), [choice](/api/random/choice/)의 알고리즘을 다뤄요. 단어 자체가 어떻게 만들어지는지는 [계수기형 생성기](/internals/random/generator/)에, 시드가 키가 되는 과정은 [시드, spawn, 상태](/internals/random/seeding/)에 있어요.

| 호출 | 방법 | 예약하는 위치 수 | 계산하는 곳 |
|---|---|:---:|---|
| `random(shape)` | 단어의 위 53비트 × $2^{-53}$ | 원소 수 | C++ `uniform` |
| `integers(low, high)` | Lemire의 곱셈과 기각 | 원소 수 | C++ `integers` |
| `permutation(n)` | Fisher–Yates | $n$ | C++ `fisher_yates` |
| `choice(n, shape=k)` | `integers(0, n)`과 같아요 | $k$ | C++ `integers` |
| `choice(n, shape=k, p=p)` | 누적합 + `searchsorted` | $k$ | Python + `random` + `searchsorted` |
| `choice(n, shape=k, replace=False)` | Fisher–Yates의 앞 $k$걸음 | $k$ | C++ `fisher_yates` |
| `choice(n, shape=k, replace=False, p=p)` | Efraimidis–Spirakis의 지수 경주 | $n$ | C++ `race_keys` + `argsort` |

C++ 커널은 `csrc/random/random.cpp`에, 생성기는 `csrc/random/philox.hpp`에, Generator 객체와 인자 검사와 `choice`의 조립은 `src/stardust/random/__init__.py`에 있어요.

네 도구는 모두 같은 틀 위에 있어요.

1. **원소 하나의 값은 (키, 원소 번호)만으로 정해져요.** 크기 $n$인 호출의 원소 $i$는 생성기 수열의 원소 $e = \text{pos} + i$이고, 그 원소가 쓰는 단어는 $e$로 정해진 계수기에서 나와요. 그래서 일을 어떻게 나누든 스레드가 몇 개든 같은 값이에요.
2. **기각에 필요한 추가 단어는 다른 계수기에서 받아요.** 한 원소가 단어를 몇 개 쓰든 다음 원소의 단어는 바뀌지 않아요.
3. **호출이 쓰는 위치 수는 계산하기 전에 정해져요.** 위 표의 "예약하는 위치 수"는 기각이 몇 번 일어나든 같아요. 그래서 위치를 먼저 예약하고, 계산은 잠금 밖에서 해요.
4. **방법마다 결과가 정확히 균등해요.** 근사가 아니에요. 아래에서 방법마다 그 이유를 증명의 뼈대로 보여 줘요.

## 공통 틀: 원소 하나, 위치 하나

### 원소의 단어

Generator는 키 두 단어와 위치 `pos`(지금까지 쓴 원소 수)를 들고 있어요. 원소 $e$의 단어는 이렇게 정해요.

- **첫 단어:** 계수기 $(\lfloor e/4 \rfloor, 0, 0, 0)$의 블록이 내는 64비트 넷 가운데 $e \bmod 4$번째예요. 이웃한 원소 넷이 블록 하나를 나눠 써요.
- **추가 단어 $k$** ($k = 0, 1, 2, \dots$): 계수기 $(e, 1 + \lfloor k/4 \rfloor, 0, 0)$ 블록의 $k \bmod 4$번째예요. 기각 표본만 이것을 써요.

두 종류의 계수기는 둘째 단어가 0인지 1 이상인지로 갈려서 같은 블록을 두 번 쓰는 일이 없어요. 자세한 내용과 이 배치를 고른 이유는 [계수기형 생성기](/internals/random/generator/)에 있어요.

### 기각이 수열을 밀지 않아요

기각 표본(rejection sampling)은 "단어를 하나 받아서 조건에 맞지 않으면 버리고 다시 받는" 방법이에요. `integers`와 `permutation`이 이것을 써요. 버리는 일은 드물지만 언제 일어날지는 단어에 달려 있어요.

상태형 생성기(numpy의 PCG64처럼 내부 상태를 한 걸음씩 진행하는 생성기)에서는 단어가 하나의 줄로 나와요. 원소 하나가 단어를 하나 버리고 다음 것을 받으면, 그 뒤 원소들이 모두 한 칸씩 밀려요.

이 차이 때문에 생기는 성질이 셋이에요.

- **병렬로 계산할 수 있어요.** 원소 $e$의 값을 앞 원소를 계산하지 않고 바로 구할 수 있어요.
- **나눠 불러도 같아요.** `random(10)` 한 번과 `random(3)`, `random(7)` 두 번은 같은 열 개의 값을 내요. 원소 번호가 같기 때문이에요.
- **예약할 위치 수를 미리 알아요.** 여러 Python 스레드가 한 Generator를 함께 부르면, 호출마다 자기 구간 `[pos, pos + n)`을 잠금 안에서 예약하고 잠금 밖에서 계산해요. 기각이 수열을 밀면 계산이 끝나기 전에는 몇 칸을 쓸지 모르므로 이렇게 할 수 없어요.

예약은 Python 쪽 `Generator._reserve`가 해요(발췌).

```python
# src/stardust/random/__init__.py, Generator._reserve
def _reserve(self, n):
    with self._lock:                       # threading.Lock
        key, p = self._key, self._pos      # 키와 위치를 함께 읽어요(state 대입과 섞이지 않게)
        self._pos = (p + n) & _MASK64      # 위치는 2^64를 법으로 돌아요
    return key, p
```

C++ 커널은 키 두 단어와 예약한 시작 위치 `pos`를 인자로 받아요. 원소별 커널(`uniform`, `integers`, `race_keys`)은 결과를 4096개(`kParallelTask`)씩 조각으로 나눠 스레드풀에서 돌리고(`for_pieces`), 조각마다 `Stream` 객체 하나를 만들어 원소 16개(블록 넷)씩 단어를 계산해요. 조각 경계가 어디든 원소의 값은 (키, $e$)로만 정해지므로 결과 비트는 스레드 수와 무관해요. 스레드풀 자체는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.

## random: 53비트로 만드는 [0, 1)

### 변환

```cpp
// csrc/random/philox.hpp
inline double to_unit(std::uint64_t w) { return static_cast<double>(w >> 11) * 0x1p-53; }
```

단어 $w$의 위 53비트 $m = \lfloor w / 2^{11} \rfloor$를 꺼내 $2^{-53}$을 곱해요. 결과는

$$
u = m \cdot 2^{-53}, \qquad m \in \{0, 1, \dots, 2^{53} - 1\}
$$

이에요. 이 변환이 정확히 균등한 이유는 float64의 구조에 있어요.

- float64는 가수(유효숫자)가 53비트예요(저장하는 52비트와 숨은 1비트). 그래서 $2^{53}$ 미만의 정수는 **모두 정확히** 표현돼요. `static_cast<double>(m)`에는 반올림이 없어요.
- $2^{-53}$을 곱하는 것은 지수만 53 줄이는 일이라 이것도 정확해요.
- 그래서 결과는 0부터 $1 - 2^{-53}$까지 간격 $2^{-53}$인 격자 위의 $2^{53}$개 값이고, 각각의 확률이 정확히 $2^{-53}$이에요. 0은 나올 수 있고(확률 $2^{-53}$), 가장 큰 값은 $1 - 2^{-53}$이라 **1은 나오지 않아요.**

```python
>>> rng = sd.random.default_rng(7)
>>> rng.random(3) * 2**53
array([5443768500896341.0, 3137933354651780.0, 8796843943550596.0], dtype=float64)
```

$2^{53}$을 곱하면 모두 정수가 돼요. 값이 격자 위에 있다는 뜻이에요.

### 다른 변환을 쓰지 않는 이유

**64비트를 통째로 나누면 1이 나와요.** `static_cast<double>(w) * 0x1p-64`처럼 64비트 정수를 그대로 실수로 바꾸면, 53비트에 들어가지 않는 아래 11비트가 반올림돼요. $w \ge 2^{64} - 2^{10}$인 1024개의 $w$는 $2^{64}$로 올림되어 결과가 정확히 1.0이 돼요. 반올림 때문에 격자의 값마다 대응하는 $w$의 수도 달라져서 균등하지 않아요.

**0 근처의 더 촘촘한 실수는 쓰지 않아요.** float64는 0에 가까울수록 촘촘해서, [0, 1) 안에 표현 가능한 수가 $2^{53}$개보다 훨씬 많아요(약 $2^{62}$개). 그 모든 수를 "구간의 길이에 비례하는 확률"로 내려면 지수를 따로 뽑는 등 단어가 더 필요해요. stardust는 numpy와 같이 등간격 $2^{53}$개 격자를 써요. 변환 함수가 numpy와 같으므로, 같은 단어를 넣으면 numpy와 같은 실수가 나와요. 다만 stardust와 numpy는 단어 자체가 달라서([시드, spawn, 상태](/internals/random/seeding/)) 값은 달라요.

### 커널

```cpp
// csrc/random/random.cpp, uniform (줄인 발췌)
for_pieces(n, kParallelTask, n * kWordWork, [&](int64_t, int64_t i0, int64_t i1) {
    Stream s({k0, k1});                                  // 조각마다 하나
    for (int64_t i = i0; i < i1; ++i)
        o[i] = random::to_unit(s.first(pos + uint64_t(i)));  // 원소 e = pos + i
});
```

`kWordWork = 8`은 풀이 "나눌 만한 일인지" 판단할 때 쓰는 원소당 일의 양이에요. 일의 양 $8n$이 원소별 연산의 기준값 $2^{15}$ 이상이고 조각이 둘 이상이어야 나누므로, 원소가 4096개를 넘어야 풀을 써요. 그 이하는 호출한 스레드에서 돌아요. `s.first(e)`는 원소 16개(블록 넷)를 한꺼번에 계산해 두고, 같은 무리의 원소가 오면 저장해 둔 단어를 돌려줘요.

`random()`처럼 `shape`가 없으면 원소 하나짜리 배열을 계산하고 Python `float`로 꺼내요.

## integers: Lemire의 치우침 없는 정수

`integers(low, high)`는 $[\text{low}, \text{high})$의 정수를 고르게 뽑아요. 길이를 $r = \text{high} - \text{low}$라 하면 문제는 "64비트 단어 $w$에서 $[0, r)$의 정수를 정확히 균등하게 만들기"예요. 그다음 low를 더해요.

### 나머지는 치우쳐요

가장 쉬운 방법은 $w \bmod r$이에요. 하지만 $2^{64}$이 $r$의 배수가 아니면 균등하지 않아요. $2^{64}$개의 $w$를 $r$개의 결과에 나눠 주는데 똑같이 나눠지지 않기 때문이에요.

작은 예로 보면 바로 보여요. 단어가 3비트(값 0~7, 8가지)이고 $r = 3$이라고 해요.

  <ArrayFig name="w mod 3" data={[0, 1, 2, 0, 1, 2, 0, 1]} tones={['a', 'b', '', 'a', 'b', '', 'a', 'b']} note="0: 3번 · 1: 3번 · 2: 2번" />

64비트에서도 같은 일이 일어나요. 결과마다 $w$가 $\lfloor 2^{64}/r \rfloor$개 또는 그보다 하나 많이 대응해요. $r$이 작으면 차이가 $2^{64}$분의 1 수준이라 눈에 띄지 않지만, $r$이 $2^{64}$에 가까워지면 커요. 예를 들어 $r = 3 \cdot 2^{61}$이면 앞쪽 3분의 2의 값은 확률이 $3/2^{64}$이고 나머지는 $2/2^{64}$예요. 앞쪽 값이 1.5배 자주 나와요. 게다가 나머지 연산은 64비트 나눗셈이라 원소마다 하기에는 느려요.

### 곱셈으로 줄이기

Lemire의 방법 [2]은 나머지 대신 곱셈을 써요. $w$를 [0, 1)의 실수 $w / 2^{64}$로 보면, $r$을 곱해 내림한 값이 $[0, r)$의 정수예요.

$$
v = \left\lfloor \frac{w}{2^{64}} \cdot r \right\rfloor = \left\lfloor \frac{w \cdot r}{2^{64}} \right\rfloor
$$

$w \cdot r$은 128비트 곱이고, $2^{64}$으로 나눈 몫은 그 곱의 **위 64비트**예요. 나눗셈 없이 곱셈 한 번으로 끝나요. C++에서는 `unsigned __int128`(clang과 gcc의 128비트 정수 확장)로 곱하고 위아래를 잘라요. arm64에서는 `mul`(아래 64비트)과 `umulh`(위 64비트) 두 명령이에요.

같은 시드로 `random`과 `integers(0, 1000)`을 뽑아 보면 이 관계가 보여요. 실수에 1000을 곱해 내림한 값이 정수 쪽과 같아요.

```python
>>> sd.random.default_rng(7).random(5)
array([  0.604379713042429,  0.3483805860073663,  0.9766458690164233,
        0.5331813827756962, 0.46881748695593284], dtype=float64)
>>> sd.random.default_rng(7).integers(0, 1000, shape=5)
array([604, 348, 976, 533, 468], dtype=int64)
```

곱셈만으로는 아직 치우쳐요. 3비트 예에서 $w \cdot 3$의 "위 비트"(8로 나눈 몫)를 보면 결과 0과 1이 세 번, 2가 두 번이에요. 치우침의 양은 나머지와 같고 어느 값이 손해를 보는지만 달라요.

### 기각: 아래 64비트로 판정해요

치우침을 없애려면 결과마다 대응하는 $w$의 수를 똑같이 맞춰야 해요. 전체 $2^{64}$개 가운데

$$
t = 2^{64} \bmod r
$$

개를 버리면 남는 $2^{64} - t$개가 $r$의 배수가 되어 결과마다 $q = \lfloor 2^{64}/r \rfloor$개씩 돌아가요. 문제는 **어느** $t$개를 버리느냐예요. Lemire의 답은 "곱의 아래 64비트 $\ell = (w \cdot r) \bmod 2^{64}$이 $t$보다 작으면 버린다"예요.

3비트 예($2^3 = 8$, $r = 3$, $t = 8 \bmod 3 = 2$)로 확인해요.

| $w$ | $w \cdot 3$ | 위 비트 $v = \lfloor w \cdot 3 / 8 \rfloor$ | 아래 비트 $\ell = w \cdot 3 \bmod 8$ | $\ell \ge t = 2$? |
|:---:|:---:|:---:|:---:|:---:|
| 0 | 0 | 0 | 0 | 버림 |
| 1 | 3 | 0 | 3 | ✓ |
| 2 | 6 | 0 | 6 | ✓ |
| 3 | 9 | 1 | 1 | 버림 |
| 4 | 12 | 1 | 4 | ✓ |
| 5 | 15 | 1 | 7 | ✓ |
| 6 | 18 | 2 | 2 | ✓ |
| 7 | 21 | 2 | 5 | ✓ |

남은 $w$는 결과 0에 둘(1, 2), 1에 둘(4, 5), 2에 둘(6, 7)이에요. 정확히 균등해요.

**왜 언제나 맞을까요.** 결과 $v$에 대응하는 $w$들을 생각해요.

1. 그 $w$들은 연속한 정수이고, 곱 $w \cdot r$은 구간 $[v \cdot 2^{64}, (v+1) \cdot 2^{64})$ 안에 있는 **공차 $r$의 등차수열**이에요.
2. 아래 비트 $\ell = w \cdot r - v \cdot 2^{64}$도 그만큼 옮긴 등차수열이고, 모두 $[0, 2^{64})$ 안에 있어요. 이 구간 안에서 공차 $r$인 수열의 항은 빠짐없이 다 들어 있어요(앞뒤 항은 구간 밖이에요).
3. 남기는 구간 $[t, 2^{64})$의 길이는 $2^{64} - t = q \cdot r$로 $r$의 배수예요. 공차 $r$인 등차수열은 길이가 $q \cdot r$인 반열린 구간에 **정확히 $q$번** 들어가요. 수열이 어디서 시작하든 그래요.
4. 그래서 모든 $v$가 정확히 $q$개의 $w$를 남겨요.

버린 원소는 그 원소의 추가 단어로 다시 시도해요. 다시 뽑은 단어도 같은 규칙으로 판정하므로, 받아들여진 값은 모든 시도를 통틀어 균등해요.

**버릴 확률은 $t / 2^{64}$예요.** $t < r$이므로 $r$이 작으면 거의 0이에요.

| $r$ | $t = 2^{64} \bmod r$ | 버릴 확률 |
|---|---:|---:|
| 7 | 2 | $1.1 \times 10^{-19}$ |
| 1000 | 616 | $3.3 \times 10^{-17}$ |
| $10^9$ | 709551616 | $3.8 \times 10^{-11}$ |
| $2^{62}$, $2^{63}$ | 0 | 0 |
| $3 \cdot 2^{61}$ | $2^{62}$ | 1/4 |
| $2^{63} + 1$ | $2^{63} - 1$ | 약 1/2 |

가장 나쁜 경우는 $r$이 $2^{63}$보다 조금 클 때로 버릴 확률이 1/2에 가까워요. 그래도 원소 하나가 쓰는 단어는 평균 2개 이하예요. $r$이 2의 거듭제곱이면 $t = 0$이라 버리는 일이 없어요.

### 나눗셈을 거의 하지 않아요

$t = 2^{64} \bmod r$을 구하려면 64비트 나눗셈이 한 번 필요해요. 부호 없는 산술에서 `(0 - r) % r`로 계산해요. `0 - r`은 $2^{64} - r$로 돌아 들어가고, 거기서 $r$의 나머지는 $2^{64}$의 나머지와 같아요.

일반 경로(`random::bounded`)는 나눗셈을 피하려고 판정을 두 단계로 해요.

```cpp
// csrc/random/philox.hpp, bounded (줄인 발췌)
unsigned __int128 m = (unsigned __int128)w * r;
uint64_t lo = (uint64_t)m;
if (lo < r) {                          // 필요조건: t < r 이므로 lo ≥ r 이면 받아들여요
    const uint64_t t = (0 - r) % r;    // 여기서만 나눗셈
    for (uint64_t k = 0; lo < t; ++k) {
        m = (unsigned __int128)extra(k) * r;   // 원소의 추가 단어 k
        lo = (uint64_t)m;
    }
}
return (uint64_t)(m >> 64);
```

$t < r$이므로 `lo >= r`이면 볼 것도 없이 받아들여요. `lo < r`일 확률은 $r / 2^{64}$라서, $r$이 작으면 나눗셈을 사실상 하지 않아요.

그런데 $r$이 크면 이 필요조건이 자주 참이 돼요. $r = 2^{63}$이면 원소 절반이 `lo < r`이라서 절반이 나눗셈을 해요(그러고 나서 $t = 0$이라 하나도 버리지 않아요). 그래서 **범위가 모든 원소에 하나인 흔한 호출**(`low`, `high`가 스칼라)은 따로 처리해요. $t$를 호출마다 한 번만 구하고, 원소마다 `lo < t`만 비교해요.

```cpp
// csrc/random/random.cpp, integers의 스칼라 범위 경로 (줄인 발췌)
const uint64_t r = uint64_t(h) - uint64_t(l) + (endpoint ? 1 : 0);
const uint64_t t = r == 0 ? 0 : (0 - r) % r;           // 호출마다 한 번
for_pieces(n, kParallelTask, n * kWordWork, [&](int64_t, int64_t i0, int64_t i1) {
    Stream s(key);
    for (int64_t i = i0; i < i1; ++i) {
        const uint64_t e = pos + uint64_t(i);
        uint64_t v;
        if (r == 0) v = s.first(e);                     // 2^64개 전체: 그대로
        else {
            unsigned __int128 m = (unsigned __int128)s.first(e) * r;
            for (uint64_t k = 0; uint64_t(m) < t; ++k)  // 드물어요
                m = (unsigned __int128)s.extra(e, k) * r;
            v = uint64_t(m >> 64);
        }
        o[i] = int64_t(uint64_t(l) + v);
    }
});
```

같은 조건(원소 $10^6$, 범위 $2^{63}$, 1스레드)에서 원소마다 필요할 때 나눗셈을 하면 5.7ms, 호출마다 한 번 하면 1.5ms예요. 두 경로는 받아들이는 조건이 같고(`lo < t`) 같은 추가 단어를 쓰므로 결과 비트도 같아요.

`low`나 `high`가 배열이면 원소마다 범위가 다르므로 일반 경로로 가요. 이때 `low`, `high`는 결과 모양으로 브로드캐스트한 뷰(브로드캐스트한 축의 stride가 0)이고, 커널이 원소의 C 순서 번호에서 두 뷰의 바이트 위치를 계산해 읽어요. 모든 축의 stride가 0이면, 곧 실제로는 범위가 하나이면 스칼라 경로로 가요.

### int64 전체를 부호 없는 산술로

`low`, `high`는 int64 범위 안의 어떤 쌍이든 돼요. `integers(-2**63, 2**63 - 1, endpoint=True)`처럼 int64 전체도 돼요. 이것을 64비트 부호 없는 산술 하나로 처리해요.

- **길이:** $r = \text{high} - \text{low}$를 `uint64_t(h) - uint64_t(l)`로 구해요. 수학적으로 $\text{low} \le \text{high}$인 int64 쌍의 차는 $0$ 이상 $2^{64} - 1$ 이하라서 uint64에 정확히 들어가요. 두 수를 uint64로 바꾸면 각각 $2^{64}$를 법으로 같은 값이 되고, 부호 없는 뺄셈도 $2^{64}$를 법으로 계산되므로 결과가 정확해요.
- **전체 범위:** `endpoint=True`로 int64 전체를 고르면 $r = 2^{64}$인데, uint64에서는 0으로 돌아요. 그래서 $r = 0$을 "$2^{64}$"으로 읽고, 단어를 그대로 써요. $2^{64}$개 값이 하나씩 대응하니 치우침이 없어요.
- **더하기:** 결과는 `uint64_t(l) + v`를 int64로 바꾼 값이에요. 예를 들어 $\text{low} = -5$, $v = 7$이면 `uint64_t(-5)`는 $2^{64} - 5$이고, 7을 더하면 $2^{64}$를 법으로 2예요. int64로 바꾸면 2, 곧 $-5 + 7$이에요. 수학적인 답이 $[\text{low}, \text{high}]$ 안에 있으므로 int64로 표현되고, 법 $2^{64}$로 같은 값이 그 답이에요. C++20부터 부호 있는 정수가 2의 보수로 정해져서 uint64에서 int64로의 변환이 "법 $2^{64}$로 같은 값"으로 정의돼요. 이 코드가 기대는 것이 이 성질이에요.

부호 있는 산술로 `high - low`를 계산하면 `-2**63`과 `2**63 - 1` 같은 쌍에서 넘침이 나고, C++에서 부호 있는 정수의 넘침은 정의되지 않은 동작이에요.

### Python 쪽의 검사

커널을 부르기 전에 Python이 인자를 정리해요(`Generator.integers`).

- `low`, `high`는 int(또는 numpy 정수)이면 int64 범위인지, 배열이면 dtype이 int64인지 봐요. 범위 밖이면 `OverflowError`, 그 밖은 `TypeError`예요.
- `low < high`(`endpoint=True`면 `low <= high`)인지는 **받은 그대로의** `low`, `high`로 검사해요. `integers(n)`처럼 인자가 하나뿐이면 사용자가 준 것은 `high`뿐이므로, 메시지도 그 인자를 `high`로 불러요(`integers(): 'high' must be positive`, `endpoint=True`면 `non-negative`). 결과 모양으로 브로드캐스트한 것으로 검사하면 원소 $10^6$개짜리 비교를 한 번 더 하게 돼요.
- `shape`가 없으면 `low`, `high`를 브로드캐스트한 모양이 결과 모양이에요. 둘 다 스칼라면 원소 하나를 계산해 Python `int`로 돌려줘요.

## permutation: Fisher–Yates

### 무작위 순열이 균등하다는 뜻

$n$개를 늘어놓는 방법은 $n!$가지예요. 무작위 순열이 **균등하다**는 것은 $n!$가지가 모두 정확히 $1/n!$의 확률로 나온다는 뜻이에요. 원소 하나하나가 어느 자리에 고르게 가는 것만으로는 부족해요. 순서 전체의 확률이 같아야 해요.

흔히 하는 실수가 "자리마다 아무 자리와 바꾸기"예요. 걸음마다 $[0, n)$에서 고르면 뽑기의 경우가 $n^n$가지예요. $n = 3$이면 27가지인데 순열은 6가지라서, 27을 6으로 똑같이 나눌 수 없어요. 어떤 순열은 다른 순열보다 자주 나와요.

### 알고리즘

Fisher–Yates 섞기는 Durstenfeld가 컴퓨터용으로 정리한 형태로 널리 알려졌고 [3, 4], 이렇게 해요.

1. 배열을 `[0, 1, …, n-1]`로 채워요.
2. $i = 0, 1, \dots, n-1$마다 $[i, n)$에서 $j$를 고르게 골라 `a[i]`와 `a[j]`를 바꿔요.

$i$걸음이 끝나면 `a[i]`는 다시 건드리지 않아요. 걸음마다 "아직 자리를 받지 못한 원소들 가운데 하나를 골라 다음 자리에 놓는" 셈이에요.

**균등하다는 증명의 뼈대.** 두 가지로 볼 수 있어요.

- **세기:** 걸음 $i$는 $n - i$가지 가운데 고르므로 뽑기의 경우는 $n \cdot (n-1) \cdots 1 = n!$가지이고, 각각의 확률은 $1/n!$이에요. 서로 다른 뽑기는 서로 다른 순열을 내요. 결과 순열을 보면 첫 자리의 값에서 $j_0$를, 그것을 되돌린 배열의 둘째 자리에서 $j_1$을… 차례로 되찾을 수 있기 때문이에요. 뽑기와 순열이 일대일로 대응하니 모든 순열이 $1/n!$이에요.
- **앞부분:** $i$걸음이 끝났을 때 `a[0..i]`는 "$n$개에서 순서 있게 $i+1$개를 고른 것" 가운데 하나이고, 각각의 확률이 $\frac{1}{n} \cdot \frac{1}{n-1} \cdots \frac{1}{n-i}$로 모두 같아요. 걸음 $i$가 남은 $n - i$개에서 고르게 고르기 때문이에요. $i = n - 1$이면 순열 전체이고 확률이 $1/n!$이에요.

두 번째 성질은 비복원 추출에도 그대로 쓰여요(아래 "비복원, 균등").

Durstenfeld와 Knuth의 서술은 배열 끝에서 앞으로 가며 뒤쪽을 정해 나가고, numpy도 끝에서부터 섞어요. stardust는 앞에서 뒤로 가요. 두 방향은 거울상일 뿐 똑같이 균등하고, 앞에서 가면 앞 $k$자리가 먼저 정해지므로 표본을 그 자리에서 잘라 쓸 수 있어요.

### 걸음 i는 원소 pos + i의 단어를 써요

걸음 $i$의 $j$는 위의 `integers`와 같은 Lemire의 방법으로 $[0, n - i)$를 뽑아 $i$를 더한 값이에요. 그 단어는 수열의 원소 $\text{pos} + i$의 첫 단어이고, 기각되면 그 원소의 추가 단어를 써요.

```cpp
// csrc/random/random.cpp, fisher_yates (줄인 발췌)
Stream s({k0, k1});
auto draw = [&](int64_t i) {                     // 걸음 i의 j ∈ [i, n)
    const uint64_t e = pos + uint64_t(i);
    return i + int64_t(random::bounded(s.first(e), uint64_t(n - i),
                                       [&](uint64_t t) { return s.extra(e, t); }));
};
nb::gil_scoped_release release;                  // 루프 동안 GIL을 놓아요
std::vector<int64_t> a(n);
std::iota(a.begin(), a.end(), 0);
for (int64_t i = 0; i < k; ++i) std::swap(a[i], a[draw(i)]);
std::copy(a.begin(), a.begin() + k, o);          // permutation은 k = n
```

이렇게 정하면 생기는 성질이에요.

- **결과는 (키, pos, n)만으로 정해져요.** 걸음마다 기각이 몇 번 일어나든 다음 걸음의 단어는 바뀌지 않아요. 그래서 `permutation(n)`은 언제나 위치를 정확히 $n$개 예약해요.
- **스레드 수와 무관해요.** 이 루프는 순차라서 스레드를 쓰지 않아요. 앞 걸음의 교환이 뒤 걸음이 읽을 칸을 바꾸므로 걸음을 나눠 병렬로 할 수 없어요. 단어는 미리 정해져 있지만 교환의 순서가 결과를 정해요.
- **GIL을 놓아요.** 원소 $10^6$개면 수 ms 걸리므로, 그동안 다른 Python 스레드가 돌 수 있게 해요. 크기와 상관없이 놓아요. 결과 배열 객체를 만드는 `wrap()`은 GIL이 필요해서 루프 밖에서 해요.
- **결과 배열을 먼저 할당해요.** 할당은 루프 전에, GIL을 쥔 채 해요. `permutation(2**40)`(8TB)처럼 이 컴퓨터의 물리 메모리보다 큰 요청은 여기서 `MemoryError`가 되고, 위치도 이미 예약된 채로 끝나요. 그보다 앞서 Python 쪽이 $n \ge 2^{63}$을 `OverflowError`(`permutation(): 'x' is out of range`)로 걸러요. `choice`의 `a`도 같아요.

다음 걸음의 $j$는 배열 내용과 상관없이 단어만으로 정해져요. 그래서 CPU는 앞 걸음의 교환이 끝나기를 기다리지 않고 다음 걸음의 단어 계산과 메모리 읽기를 미리 시작할 수 있어요. 배열의 무작위 위치를 읽고 쓰는 것이 이 루프에서 가장 비싼 일이라, 여러 걸음의 메모리 접근이 겹치는 것이 중요해요.

### 정렬로 섞지 않는 이유

다른 방법으로 "원소마다 무작위 64비트 키를 붙여 키로 정렬하기"가 있어요. 키가 모두 다르면 정렬 순서는 균등한 순열이고, 키 만들기와 정렬 모두 병렬로 할 수 있어 결과도 스레드 수와 무관하게 만들 수 있어요.

같은 조건(원소 $10^6$개)에서 비교하면 이래요.

| 방법 | 1스레드 | 10스레드 |
|---|:---:|:---:|
| 무작위 키 정렬 (병렬) | 8.6ms | 3.8ms |
| Fisher–Yates (순차) | 3.0ms | 3.0ms |

Fisher–Yates가 10스레드 정렬보다도 빨라요. Fisher–Yates는 원소마다 교환 한 번으로 한 바퀴에 끝나지만, 정렬은 (키, 인덱스) 쌍(16바이트)을 만들고 여러 번 훑어야 해요([정렬과 집합](/internals/array/sorting/)의 기수 정렬은 자리마다 한 번씩 흩뿌려요). 정렬은 키가 겹칠 때 동점 처리 규칙이 순열을 아주 조금 치우치게 한다는 문제도 있어요. 64비트 키 $10^6$개가 겹칠 확률은 약 $n^2 / 2^{65} \approx 2.7 \times 10^{-8}$로 작지만 0은 아니에요. 그래서 섞기는 순차 Fisher–Yates예요.

### shuffle이 없는 이유와 배열의 permutation

stardust에는 인자를 제자리에서 바꾸는 함수가 없어요. 값을 바꾸는 길은 `out=`, `+=` 같은 제자리 연산자, 인덱스 대입뿐이에요. 그래서 numpy의 `shuffle` 대신 `permutation`만 있고, 제자리에서 섞으려면 `x[...] = rng.permutation(x)`처럼 대입해요([permutation](/api/random/permutation/)).

배열을 주면 `permutation`은 먼저 길이 $n$(첫 축의 길이)의 인덱스 순열을 위의 커널로 만들고, `take(x, perm, axis=0)`으로 새 배열에 모아요. 원소를 직접 섞지 않고 인덱스를 섞는 이유는 dtype과 행의 크기에 상관없이 한 커널로 처리하기 위해서예요. 인덱스를 섞는 단계가 같으므로 같은 시드에서 `permutation(n)`과 `permutation(x)`(첫 축 길이 $n$)는 같은 순서로 섞어요. 모으기(`take`)는 병렬로 돌아요.

### 복원, 균등: integers와 같아요

`choice(n, shape=k)`는 `integers(0, n, shape=(k,))`를 그대로 불러요. 같은 시드면 두 호출의 값이 같아요. 앞의 예에서 `integers(0, 1000, shape=5)`가 `[604, 348, 976, 533, 468]`이었고, `default_rng(7).choice(1000, shape=5)`도 같은 다섯 값이에요.

### 복원, 가중치: 누적합과 이진 탐색

원소 $i$를 확률 $p_i$로 뽑는 가장 직접적인 방법은 **역누적분포** 방법이에요. 누적합

$$
c_i = p_0 + p_1 + \cdots + p_i
$$

은 [0, 1)을 길이 $p_0, p_1, \dots$인 구간 $[c_{i-1}, c_i)$로 나눠요($c_{-1} = 0$). [0, 1)의 균등 난수 $u$가 구간 $i$에 떨어질 확률은 그 길이 $p_i$예요. 그러니 $u$가 들어간 구간의 번호를 찾으면 돼요. 누적합은 정렬되어 있으므로 이진 탐색이에요.

```python
# src/stardust/random/__init__.py, choice의 가중치 복원 경로
cdf = sd.cumulative_sum(p)
cdf = cdf / cdf[n - 1]                                # 마지막 값을 정확히 1로
u = self.random((k,))                                 # 위치 k개
idx = sd.minimum(sd.searchsorted(cdf, u, side="right"), n - 1)
```

`searchsorted(cdf, u, side="right")`는 $c_{i-1} \le u < c_i$인 $i$, 곧 $c_i > u$인 첫 $i$를 찾아요.

```python
>>> rng = sd.random.default_rng(7)
>>> rng.choice(4, shape=6, p=sd.asarray([0.1, 0.0, 0.6, 0.3]))
array([2, 2, 3, 2, 2, 2], dtype=int64)
```

`u`는 같은 시드의 `random(6)`과 같은 값이에요(앞의 예에서 0.604…, 0.348…, 0.977…). 세부 사항 셋이 정확성을 지켜요.

- **마지막 값으로 나누기.** 부동소수점 누적합의 마지막 값은 1이 아닐 수 있어요(예: 0.9999999999999999). 그러면 $u$가 그보다 크거나 같을 때 갈 구간이 없어요. 마지막 값으로 나누면 $c_{n-1} = 1$이 정확히 되고, $u < 1$이므로 언제나 어느 구간에 들어가요.
- **`side="right"`와 확률 0.** $p_i = 0$이면 $c_i = c_{i-1}$이라 구간 $[c_{i-1}, c_i)$가 비어요. `right`는 "$c_i > u$인 첫 $i$"를 찾으므로, $c_i > u$이면 $c_{i-1} > u$이기도 해서 탐색은 $i$보다 앞에서 멈춰요. 맨 앞 원소도 그래요. $p_0 = 0$이면 $c_0 = 0$이고, $u \ge 0$이라 $c_0 > u$가 될 수 없어요. `side="left"`였다면 $u = 0$일 때 $c_0 \ge 0$인 첫 자리 0을 돌려줘서, 확률 0인 원소 0이 뽑힐 수 있어요.
- **`minimum(…, n - 1)`.** 위의 두 성질로 결과는 언제나 $n - 1$ 이하지만, 인덱스가 범위를 벗어나지 않음을 값으로도 보장해 둬요.

numpy 2.5.4의 `choice`도 같은 방법(누적합, 마지막 값으로 나누기, `searchsorted(side='right')`)을 써요 [6]. 방법은 같지만 $u$가 달라서 값은 달라요.

비용은 누적합 $O(n)$과 탐색 $O(k \log n)$이에요. `random`과 `searchsorted`는 일이 크면 병렬로 나눠요(`searchsorted`는 찾을 값 4096개씩, [정렬과 집합](/internals/array/sorting/)). 뽑을 값 하나가 위치 하나를 써요.

### 비복원, 균등: Fisher–Yates의 앞 k걸음

`replace=False`이면 같은 원소를 두 번 고르지 않아요. Fisher–Yates의 "앞부분" 성질에서, 섞기를 $k$걸음에서 멈추면 앞 $k$자리는 $n$개에서 순서 있게 $k$개를 고르게 고른 것이에요. 그래서 비복원 균등 추출은 `fisher_yates(…, n, k)`, 곧 섞기의 앞 $k$걸음이에요. `permutation`과 같은 커널이고, 같은 위치에서 시작하면 같은 걸음을 밟아요.

```python
>>> sd.random.default_rng(7).permutation(10)
array([6, 4, 9, 0, 3, 7, 5, 1, 8, 2], dtype=int64)
>>> sd.random.default_rng(7).choice(10, shape=4, replace=False)
array([6, 4, 9, 0], dtype=int64)
```

결과는 고른 차례대로예요. 따로 증명할 알고리즘이 없고, 섞기의 성질이 그대로 표본의 성질이에요.

**큰 모집단의 작은 표본은 해시 맵으로 해요.** $n = 10^9$에서 1000개를 뽑으려고 8GB짜리 배열을 채울 수는 없어요. 그런데 $k$걸음 동안 건드리는 칸은 많아야 $2k$개예요. 나머지 칸은 처음 값 그대로, 곧 `a[i] = i`예요. 그래서 $k \le n/16$이면 배열 대신 **"자기 인덱스가 아닌 칸"만** `std::unordered_map`에 둬요.

```cpp
// csrc/random/random.cpp, fisher_yates의 해시 맵 경로 (줄인 발췌)
std::unordered_map<int64_t, int64_t> moved;     // 칸 번호 → 값 (값 ≠ 칸 번호인 것만)
moved.reserve(2 * k);
auto at = [&](int64_t i) { auto it = moved.find(i); return it == moved.end() ? i : it->second; };
for (int64_t i = 0; i < k; ++i) {
    const int64_t j = draw(i);                  // 배열 경로와 같은 j
    const int64_t vi = at(i), vj = at(j);
    moved[j] = vi;                              // a[j] ← a[i]
    o[i] = vj;                                  // a[i] ← a[j], 결과에 바로 써요
}
```

교환의 절반만 맵에 적는 데 주목하세요. `a[i]`의 새 값은 결과 `o[i]`에 쓰고 맵에는 적지 않아요. 걸음 $i$ 다음의 걸음들은 $i$보다 큰 칸만 읽으므로($i' > i$, $j' \ge i'$) 칸 $i$는 다시 읽히지 않기 때문이에요. 맵에는 걸음마다 많아야 한 항목이 늘어서 크기가 $k$ 이하예요.

$n = 8$, $k = 3$의 예로 두 경로를 나란히 보면 이래요.

| 걸음 | $j$ | 배열 경로의 `a` | 맵 경로의 `moved` | 결과 |
|:---:|:---:|---|---|---|
| 처음 | | `[0, 1, 2, 3, 4, 5, 6, 7]` | 비어 있음 | |
| 0 | 5 | `[5, 1, 2, 3, 4, 0, 6, 7]` | 5→0 | `[5]` |
| 1 | 5 | `[5, 0, 2, 3, 4, 1, 6, 7]` | 5→1 | `[5, 0]` |
| 2 | 6 | `[5, 0, 6, 3, 4, 1, 2, 7]` | 5→1, 6→2 | `[5, 0, 6]` |

두 경로는 같은 $j$로 같은 교환을 하므로 결과가 같아요. 어느 경로를 타든 `choice(n, shape=k, replace=False)`는 `permutation(n)`의 앞 $k$개와 같아요.

- 해시 맵 경로는 시간과 메모리가 $O(k)$라서 모집단 크기와 무관해요. 원소 $10^6$개에서 1000개를 뽑는 데 0.03ms예요([성능과 검증](/internals/random/performance/)).
- 배열 경로는 $O(n)$의 초기화와 $8n$바이트가 들지만 걸음마다 연속한 배열을 읽고 써요. 해시 맵의 찾기·넣기는 배열 접근보다 훨씬 비싸서, 표본이 모집단의 상당 부분이면 배열이 나아요. 둘을 가르는 기준이 $k \le n/16$이에요.

### 비복원, 가중치: Efraimidis–Spirakis의 지수 경주

**확률 모델.** 가중치가 있는 비복원 추출은 "매번 남은 원소 가운데 가중치에 비례해 하나를 고르고, 고른 것을 뺀 뒤 반복"하는 것으로 정의해요. 첫 원소는 확률 $p_i / \sum p$로, 둘째는 첫째를 뺀 나머지에서 다시 비례해 골라요. 결과는 고른 차례대로예요.

이 정의를 그대로 따르면 $k$번 각각 남은 가중치의 누적합을 다시 만들어야 해서 $O(nk)$예요. numpy 2.5.4는 이 정의에 가까운 반복을 해요. 남은 개수만큼 한꺼번에 뽑고, 겹친 것을 버리고, 고른 원소의 확률을 0으로 만들고 누적합을 다시 만드는 일을 다 찰 때까지 되풀이해요 [6].

**경주로 보기.** Efraimidis와 Spirakis는 원소마다 키 $u_i^{1/p_i}$($u_i$는 (0, 1]의 균등 난수)를 만들어 **큰** 키 $k$개를 고르면 같은 분포가 된다는 것을 보였어요 [5]. stardust는 같은 것을 로그로 바꿔 써요. $-\log$는 감소함수이므로

$$
u_i^{1/p_i} \text{가 큰 순서} \iff \frac{-\log u_i}{p_i} = \frac{E_i}{p_i} \text{가 작은 순서}
$$

예요. $E_i = -\log u_i$는 표준 지수분포(평균 1)를 따르고, $T_i = E_i / p_i$는 비율 $p_i$인 지수분포를 따라요. 원소마다 "도착 시각" $T_i$를 하나씩 정하고, **먼저 도착한 $k$개**를 도착 순서대로 고르는 거예요.

**왜 맞을까요.** 지수분포의 두 성질이면 돼요.

1. **가장 먼저 도착할 확률이 가중치에 비례해요.** 독립인 $T_j \sim \text{Exp}(p_j)$들 가운데 $T_i$가 가장 작을 확률은, $P = \sum_j p_j$라 하면

   $$
   \Pr\Big[T_i < \min_{j \ne i} T_j\Big] = \int_0^\infty p_i e^{-p_i t} \cdot e^{-(P - p_i) t} \, dt = \frac{p_i}{P}
   $$

   예요. 첫 도착자는 정확히 "가중치에 비례해 하나 고르기"예요.
2. **기억이 없어요.** 시각 $t$에 첫 도착자가 나왔을 때, 아직 도착하지 않은 원소의 남은 시간 $T_j - t$는 다시 비율 $p_j$인 지수분포이고 서로 독립이에요. 경주가 남은 원소들만으로 새로 시작하는 것과 같아요. 그래서 두 번째 도착자는 남은 원소 가운데 가중치에 비례해 골라져요.

이것을 $k$번 되풀이하면 도착 순서가 곧 위의 확률 모델이에요. 모든 $p_i$에 같은 수를 곱해도 도착 순서는 그대로이므로, 이 경로는 $p$를 합으로 나누지 않고 받은 그대로 써요.

**구현.** `race_keys` 커널이 원소마다 키를 만들어요.

```cpp
// csrc/random/random.cpp, race_keys (줄인 발췌)
for (int64_t i = i0; i < i1; ++i) {
    const double u = (double((s.first(pos + uint64_t(i)) >> 11)) + 1.0) * 0x1p-53;  // (0, 1]
    o[i] = pp[i] > 0.0 ? std::min(-std::log(u) / pp[i], std::numeric_limits<double>::max())  // E / p
                       : HUGE_VAL;
}
```

- **$u$는 (0, 1]이에요.** `random`의 격자에 $2^{-53}$을 더한 것이라 0이 나오지 않고, $-\log u$는 언제나 유한해요(0 이상 약 36.7 이하).
- **확률 0의 키는 inf예요.** 영원히 도착하지 않는 원소예요. Python이 미리 "$k$가 0이 아닌 확률의 수 이하"인지 검사하므로, 유한한 키가 언제나 $k$개 이상 있어요.
- **양수 확률의 키는 double의 최댓값에서 잘라요.** $-\log u$는 많아야 $53 \ln 2 \approx 36.74$라서, $p$가 $36.74 / (1.80 \times 10^{308}) \approx 2.04 \times 10^{-307}$보다 작으면 $E/p$가 넘쳐 inf가 될 수 있어요. 그러면 확률 0인 원소와 키가 같아지고, 안정 정렬이 인덱스가 작은 쪽을 먼저 두므로 앞에 놓인 확률 0인 원소가 뽑혀요. 그래서 넘친 키를 `std::numeric_limits<double>::max()`($\approx 1.80 \times 10^{308}$)로 자르고, 확률 0인 원소만 inf로 남겨요. 양수 확률은 아무리 작아도 확률 0인 원소보다 먼저 도착해요. 잘린 원소끼리는 키가 모두 같아서 인덱스 순서로 놓여요. 정확한 모델이라면 그들 사이에서도 확률에 비례해 골라야 하므로, 이 차이는 그런 원소를 둘 이상 뽑아야 할 때(곧 $k$가 확률이 그보다 큰 원소의 수보다 클 때) 드러나요.

```python
>>> sd.random.default_rng(42).choice(3, shape=2, replace=False, p=sd.asarray([0.0, 1e-310, 1.0]))
array([2, 1], dtype=int64)
>>> sd.random.default_rng(42).choice(3, shape=3, replace=False, p=sd.asarray([1.0, 1e-320, 1e-310]))
array([0, 1, 2], dtype=int64)
```

첫 줄에서 1번(확률 `1e-310`)은 확률 0인 0번보다 먼저 뽑혀요. 둘째 줄의 정확한 모델이라면 2번(`1e-310`)이 1번(`1e-320`)보다 거의 언제나 먼저지만, 둘 다 잘린 키라 인덱스 순서예요.

- **위치는 $n$개예요.** 원소마다 키 하나가 필요하므로 표본 크기 $k$가 아니라 모집단 크기 $n$만큼 예약해요.
- **고르기는 `argsort(keys)[:k]`예요.** 키 배열 전체를 안정 정렬(float64 (값, 인덱스) 쌍의 기수 정렬, [정렬과 집합](/internals/array/sorting/))하고 앞 $k$개의 인덱스를 써요. 키가 같으면 인덱스가 작은 쪽이 먼저예요. 비용은 키 만들기 $O(n)$(병렬)과 정렬이에요.

### p의 검사와 정규화

`p`가 있으면 인덱스를 뽑기 전에 Python이 검사해요.

1. `p`는 배열이어야 하고(아니면 `TypeError`), 1차원이고 길이가 원소 수 $n$이어야 해요.
2. float64로 바꿔요. 정수나 bool 배열도 받아요. complex128 배열은 확률이 될 수 없어서 바꾸기 전에 `TypeError`예요(`choice(): 'p' must be a real array, not an array of complex128`).
3. NaN이나 음수가 하나라도 있으면 `ValueError`예요.
4. 합이 1에서 $\sqrt{\varepsilon} \approx 1.49 \times 10^{-8}$($\varepsilon$은 float64의 기계 엡실론 $2^{-52}$) 넘게 벗어나면 `ValueError`예요. numpy와 같은 허용치예요. `1/3`을 세 번 더한 것처럼 반올림으로 생긴 작은 차이는 받아 주고, 손으로 반올림한 `[0.333, 0.333, 0.333]`처럼 큰 차이는 받지 않아요. 합은 `sd.sum`(pairwise 합)으로 구하고 numpy는 Kahan 합을 쓰므로, 허용치 경계에 아주 가까운 `p`에서는 두 라이브러리의 판정이 갈릴 수 있어요.
5. 비복원이면 $k$가 0이 아닌 확률의 수(`count_nonzero(p)`) 이하인지 봐요.

합이 정확히 1이 아니어도 되는 만큼 쓰는 쪽에서 맞춰요. 복원 경로는 누적합을 마지막 값으로 나누고, 경주 경로는 비율만 쓰므로 나눌 필요가 없어요.

## 복잡도

$n$은 모집단 크기(또는 원소 수), $k$는 뽑는 개수예요.

| 호출 | 시간 | 추가 메모리 | 쓰는 위치 | 병렬 |
|---|---|---|:---:|:---:|
| `random(n)` | $O(n)$ | 결과 | $n$ | 예 |
| `integers(…, shape=n)` | $O(n)$, 원소당 단어 평균 2개 이하 | 결과 | $n$ | 예 |
| `permutation(n)` | $O(n)$ | $8n$ 바이트 작업 배열 + 결과 | $n$ | 아니요 |
| `permutation(x)` | $O(n)$ + 모으기 | 인덱스 + 결과 | $n$ | 모으기만 |
| `choice` 복원, 균등 | $O(k)$ | 결과 | $k$ | 예 |
| `choice` 복원, 가중치 | $O(n + k \log n)$ | 누적합 + $u$ | $k$ | `random`과 탐색 |
| `choice` 비복원, 균등, $k \le n/16$ | $O(k)$ 기댓값 | 해시 맵 $O(k)$ | $k$ | 아니요 |
| `choice` 비복원, 균등, $k > n/16$ | $O(n)$ | $8n$ 바이트 | $k$ | 아니요 |
| `choice` 비복원, 가중치 | $O(n)$ 키 + 정렬 | 키 + 정렬 버퍼 | $n$ | 키와 정렬 |
