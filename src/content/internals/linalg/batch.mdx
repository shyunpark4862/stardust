## 한눈에 보기

`sd.linalg`의 모든 행렬 함수는 `(..., M, N)` 모양의 **행렬 묶음**을 받아요. 마지막 두 축이 행렬 하나이고, 그 앞의 축들이 배치예요. `solve`에 `(1000, 3, 3)`을 넣으면 3×3 연립방정식 1000개를 풀어요. 이 글은 그 1000개를 어떻게 걷고, 어떤 기준으로 스레드에 나누고, 왜 어떻게 나눠도 결과가 비트까지 같은지를 설명해요.

모든 행렬 함수는 같은 틀을 지나요. 그 틀이 `csrc/linalg/batch.hpp`의 배치 드라이버예요.

핵심 아이디어는 다섯 가지예요.

1. **배치 원소 하나는 LAPACK 호출 한 번(또는 정해진 몇 번)이에요.** 원소끼리는 서로 독립이라 어떤 순서로, 어느 스레드에서 돌려도 같은 계산이에요. 병렬화는 원소를 태스크로 묶는 일뿐이에요.
2. **나눌지는 시간으로 정해요.** 함수 계열마다 원소 하나의 직렬 비용을 `a + c·w` ns로 추정하고, 배치 전체가 10µs를 넘으면 나눠요. 태스크 하나는 약 5µs 분량이에요.
3. **원소 하나는 어디서 돌든 같은 비트를 내요.** 이를 위해 세 가지를 지켜요. 태스크마다 자기 작업 메모리를 쓰고, LAPACK에 주는 workspace 크기를 행렬마다 물었을 때와 같게 하고, LAPACK에 넘기는 배열을 모두 16바이트 정렬해요. 마지막 것은 Accelerate가 정렬에 따라 반올림을 다르게 하기 때문에 필요해요.
4. **실패는 가장 작은 인덱스를 보고해요.** 병렬로 돌아도 메시지가 스레드 수와 상관없이 같아요.
5. **합은 numpy의 pairwise 합이고, 긴 합은 트리의 잎 단위로 나눠요.** 같은 트리 순서로 합치므로 직렬, 그리고 numpy와 비트까지 같아요.

스레드풀 자체(상주 워커, atomic 카운터, spin 대기, GIL 해제)는 모든 영역이 함께 쓰는 것이라 [스레드풀과 결정성](/internals/core/threads/)에서 다뤄요. 이 글은 그 풀 위에서 linalg가 정하는 정책을 다뤄요.

## 배치 브로드캐스팅: `Batch`

### 규칙

인자가 여럿이면 배치 축끼리 브로드캐스트해요. 원소별 연산과 같은 규칙이에요. 오른쪽부터 맞추고, 길이 1인 축은 상대 길이로 늘어나고, 둘 다 1이 아닌데 다르면 `ValueError`예요.

`solve(a, b)`에서 `a`가 `(2, 1, 3, 3)`, `b`가 `(4, 3, 1)`이면 행렬 부분 `(3, 3)`과 `(3, 1)`을 떼고 남은 배치 모양 `(2, 1)`과 `(4,)`를 브로드캐스트해서 `(2, 4)`가 돼요. 결과는 `(2, 4, 3, 1)`이고, 연립방정식 8개를 풀어요.

### 자료 구조

`Batch`는 결과의 배치 모양과, 피연산자마다 배치 축의 **바이트 strides**를 가져요. 브로드캐스트로 늘어난 축(길이 1이었던 축, 없던 축)의 stride는 0이에요. 피연산자는 최대 4개(`kMaxOperands`)예요. 가장 많은 함수가 `solve_sylvester(a, b, c)`의 셋이고, 하나의 여유를 둬요.

```cpp
// linalg/batch.hpp (발췌)
class Batch {
public:
    Batch(std::initializer_list<BatchOperand> ops, const char* func);   // 브로드캐스트, 실패면 ValueError
    std::int64_t size() const;                                          // 배치 원소 수
    void offsets(std::int64_t idx, std::int64_t* out) const;            // 원소 idx의 피연산자별 바이트 오프셋
    std::string index_str(std::int64_t idx) const;                      // "(1, 2)": 에러 메시지용
private:
    std::vector<std::int64_t> shape_;
    std::int64_t size_ = 1;
    std::size_t nops_ = 0;
    std::vector<std::int64_t> strides_;   // nops_ × ndim, 늘어난 축은 0
};
```

### 원소 번호에서 오프셋으로

배치 원소에는 C 순서로 번호를 매겨요(마지막 축이 가장 빨리 변해요). `offsets(idx, out)`은 이 번호를 각 축의 인덱스로 풀고(혼합 기수 분해), 피연산자마다 인덱스 × stride를 더해 바이트 오프셋을 만들어요.

```cpp
// linalg/batch.cpp
void Batch::offsets(std::int64_t idx, std::int64_t* out) const {
    const std::size_t nd = shape_.size();
    for (std::size_t k = 0; k < nops_; ++k) out[k] = 0;
    for (std::size_t d = nd; d-- > 0;) {          // 마지막 축부터
        const std::int64_t i = idx % shape_[d];
        idx /= shape_[d];
        for (std::size_t k = 0; k < nops_; ++k) out[k] += i * strides_[k * nd + d];
    }
}
```

원소마다 오프셋을 처음부터 다시 계산하므로, 아무 원소에서나 시작할 수 있어요. 태스크가 배치의 중간부터 맡아도 앞 원소들을 걸어올 필요가 없어요. 비용은 원소 하나에 (배치 축 수) × (피연산자 수)번의 곱셈과 나눗셈이고, 그 원소에서 하는 패킹과 LAPACK 호출에 비하면 작아요.

같은 번호 체계를 에러 메시지에도 써요. `index_str(idx)`가 번호를 `(1, 2)` 같은 다차원 인덱스로 바꿔요. 배치 축이 없으면(행렬 하나면) 인덱스를 붙이지 않아요.

## 배치 드라이버: `run_batch`

### 몸체의 약속

`run_batch(batch, element_ns, body, max_tasks)`는 배치 원소마다 `body(i, off, scratch)`를 불러요.

- `i`: 원소 번호. 결과 배열에서 이 원소의 자리를 찾는 데 써요(`res + i * m * n`).
- `off`: 피연산자별 바이트 오프셋(`Batch::offsets`의 결과).
- `scratch`: 작업 메모리. 직렬이면 배치 전체가 하나를, 나누면 태스크마다 하나를 써요.
- 돌려주는 값: 성공이면 0, 실패면 양수 코드(`kSingular`, `kNonFinite` 등, `ops/common.hpp`). 몸체는 첫 실패에서 바로 돌아와요.

몸체는 Python 객체를 만지지 않아요. 배치의 추정 시간(원소 하나의 추정 시간 × 원소 수)이 `kParallelMinNs`(10µs) 이상이면 몸체는 GIL 없이 돌기 때문이에요. 나눈 배치는 워커 스레드에서 `parallel_for`가 GIL을 놓은 채로, 나누지 않은 배치(행렬 하나, 1스레드, 바쁜 풀)는 호출 스레드에서 `parallel::Unlocked`로 GIL을 놓은 채로 돌아요. 원소 하나의 추정 시간이 0인 함수(나누지 않기로 한 것)는 GIL을 쥔 채 돌아요. 결과 배열과 namedtuple은 `run_batch` 앞뒤에서 만들어요.

`solve`의 몸체는 이렇게 생겼어요.

```cpp
// linalg/ops/lu.cpp의 solve (발췌)
const Failure f = run_batch(b, cost(kLU, double(n) * n),
    [&](std::int64_t i, const std::int64_t* off, Scratch& s) {
        T* lu; lint* ipiv;
        if (const int code = lu_factor<T>(a, off[0], n, s, lu, ipiv)) return code;   // 패킹 + getrf
        // ... b를 결과 자리에 패킹하고 getrs ...
        return 0;
    },
    lu_task_cap(n, k, true));
if (f) raise(b, f, "solve", "a");
```

### 직렬과 분할

```cpp
// linalg/batch.hpp의 run_batch (발췌, 실패 처리는 아래 절에서)
template <class F>
Failure run_batch(const Batch& b, double element_ns, F&& body, int max_tasks = 0) {
    const std::int64_t n = b.size();
    if (n >= 2 && element_ns > 0 && element_ns * n >= kParallelMinNs && detail::begin_parallel()) {
        std::int64_t per = std::max<std::int64_t>(1, static_cast<std::int64_t>(kTaskNs / element_ns));
        if (max_tasks > 0 && (n + per - 1) / per > max_tasks) per = (n + max_tasks - 1) / max_tasks;
        const std::int64_t ntasks = (n + per - 1) / per;
        detail::run_tasks(ntasks, [&](std::int64_t t) {
            Scratch scratch;                       // 태스크마다 자기 작업 메모리
            std::int64_t offs[kMaxOperands];
            for (std::int64_t i = t * per; i < std::min(n, (t + 1) * per); ++i) {
                b.offsets(i, offs);
                body(i, offs, scratch);            // (실패 기록은 생략)
            }
        });
        /* ... 가장 작은 실패 고르기 ... */
    }
    Scratch scratch;                               // 직렬: 하나로 차례로
    std::int64_t offs[kMaxOperands];
    for (std::int64_t i = 0; i < n; ++i) {
        b.offsets(i, offs);
        if (const int code = body(i, offs, scratch)) return {i, code};
    }
    return {};
}
```

나누는 조건은 넷이 모두 맞을 때예요.

| 조건 | 이유 |
|---|---|
| 배치 원소가 2개 이상 | 원소 하나는 쪼갤 수 없어요 |
| `element_ns > 0` | 0은 "나누지 않음"의 표시예요(작은 띠 행렬의 `gbsv`, 아래) |
| `element_ns × n ≥ kParallelMinNs` (10µs) | 배치 전체의 추정 직렬 시간이 이보다 작으면 나누는 비용이 이득보다 커요 |
| `begin_parallel()` | 스레드가 둘 이상이고, 이미 태스크 안이 아니고(중첩 금지), 다른 Python 스레드가 풀을 쓰고 있지 않을 때 참이에요(`parallel::available()`) |

태스크 하나는 `max(1, ⌊kTaskNs / element_ns⌋)`개의 원소를 맡아요. 연속한 원소 묶음이라 태스크 `t`는 원소 `[t·per, (t+1)·per)`를 맡아요. 태스크를 어느 스레드가 집어 가는지는 실행마다 다르지만, 태스크가 맡는 원소 범위는 배치 크기와 비용 추정만으로 정해져요.

## 비용 모델: `a + c·w`

### 왜 시간으로 재나

배열 영역은 "원소 2¹⁵개 이상이면 나눈다"처럼 일의 양을 **원소 수(바이트)**로 재요. 원소 하나의 비용이 대략 일정한 원소별 연산에는 맞는 방법이에요. linalg에서는 맞지 않아요. 3×3 `svd` 하나는 원소 9개를 다루지만 같은 원소 9개의 `diagonal`보다 수백 배 오래 걸려요. 그래서 linalg는 일의 양을 **추정 시간**으로 재고, 함수 계열마다 원소 하나의 비용을 추정해요(`csrc/linalg/cost.hpp`).

$$
\text{element\_ns} = a + c \cdot w
$$

- $w$는 행렬의 원소 수 $m \cdot n$(정사각이면 $n^2$)이에요. 스트리밍 함수(`vecdot`, `trace`, 노름)는 출력 하나에 더하는 원소 수, 복사 함수(`diagonal`, `outer`, `kron`, `cross`)는 복사하는 원소 수예요.
- $a$는 호출 하나의 고정비(인자 해석, 작은 버퍼, LAPACK 진입), $c$는 원소 하나당 비용이에요.

```cpp
// linalg/cost.hpp (발췌)
struct Family { double a, c; };
inline constexpr Family kLU{70, 3.0};          // solve, inv, det, slogdet, lu, cholesky, ldl, matrix_power
inline constexpr Family kTriangular{30, 0.5};  // solve_triangular, cholesky_solve, lu_solve
inline constexpr Family kQR{180, 10};          // qr, qr_pivoted, hessenberg
inline constexpr Family kEigh{250, 45};        // eigh, eigvalsh (일반화 포함)
inline constexpr Family kSVD{1000, 80};        // svd, svdvals, matrix_rank, pinv, cond, lstsq, matrix_norm 2/-2/nuc
inline constexpr Family kEig{700, 200};        // eig, eigvals, schur
inline constexpr Family kSylvester{500, 370};  // solve_sylvester, w = (m² + n²) / 2
inline constexpr Family kBanded{20, 3};        // solve_tridiagonal, solve_banded, w = n·(대역폭 + 1)
inline constexpr Family kStream{12, 0.3};      // vecdot, 노름, trace: w = 출력 하나에 더하는 원소 수
inline constexpr Family kCopy{2, 0.5};         // diagonal, outer, kron, cross: w = 복사하는 원소 수
inline constexpr Family kExpm{600, 15};        // expm

inline double cost(Family f, double w) { return f.a + f.c * w; }
```

### 상수를 맞춘 방법과 오차

상수는 $n = 2$–256의 정사각 행렬에서 함수마다 잰 직렬 시간에 맞췄어요. 분해의 연산량은 $n^3$에 비례하는데도 $n^2$로 맞춘 이유는 이 범위에서 그쪽이 더 잘 맞기 때문이에요. 작은 행렬에서는 고정비와 $O(n^2)$ 작업(패킹, 유한성 검사, 결과 쓰기, LAPACK 안의 $O(n^2)$ 단계)이 시간의 대부분이에요. 맞춘 결과는 대부분 실제 시간의 1.2–2배 안이고, 가장 크게 벗어나도 3배예요. `kExpm`은 $n = 2$–256에서 실제 시간의 0.65–1.5배예요.

나눌지 말지, 몇 개씩 묶을지를 정하는 데는 이 정도면 충분해요. 2배 틀려도 태스크가 2.5µs나 10µs가 될 뿐이고, 그 범위에서는 성능 차이가 작아요(아래 `kTaskNs`).

큰 $n$에서는 모델이 과소 추정해요. 실제 일은 $n^3$로 자라기 때문이에요. 하지만 $n = 300$짜리 `solve` 하나의 추정만 해도 $70 + 3 \cdot 90000 \approx 270$µs라서 배치 원소가 2개만 돼도 이미 10µs를 넘어 나눠요. 과소 추정이 결정을 바꾸지 않아요.

### 기각한 대안: 첫 원소의 시간을 재기

상수 없이, 첫 원소를 돌려 걸린 시간을 보고 나머지를 나눌 수도 있어요. 하지만 그러면 같은 호출이 실행마다(기계가 바쁜 정도에 따라) 나뉘기도 하고 안 나뉘기도 해요. 결과의 비트는 어차피 같지만(아래 결정성 절), 성능이 재현되지 않고 원인을 추적하기 어려워져요. 고정 상수는 같은 입력에 언제나 같은 분할을 줘요.

### 두 상수: 언제, 얼마나 잘게

| 상수 | 값 | 뜻과 근거 |
|---|:---:|---|
| `kParallelMinNs` | 10µs | 배치 전체의 추정 직렬 시간(`element_ns × n`)이 이보다 작으면 직렬로 돌아요. 직렬로 약 8–10µs를 넘는 배치부터 나누는 쪽이 이겨요. 직렬 17µs인 3×3 `svd` 8개는 나누면 시간이 0.51배, 직렬 8µs인 3×3 `solve` 64개는 0.70배예요. 그보다 작은 배치를 나누면 3–10% 손해예요 |
| `kTaskNs` | 5µs | 태스크 하나의 추정 직렬 시간이에요. 2.5µs는 작은 배치에 조금 낫고 큰 배치에 조금 나빴고, 10µs는 그 반대였어요. 80µs는 태스크 수가 모자라 스레드가 놀았어요 |

`kParallelMinNs`가 10µs 근처인 이유는 풀의 고정비에서 짐작할 수 있어요. spin 중인 워커에 일을 넘기는 데 약 1.5µs가 들고([스레드풀과 결정성](/internals/core/threads/)), 태스크마다 `Scratch`를 새로 만들고 workspace 크기를 다시 물어요. 일이 몇 µs밖에 안 되면 이 비용이 이득을 삼켜요.

두 값은 상수처럼 쓰지만 변수(`inline double`)로 선언돼 있어요. 측정 실험에서만 비공개 함수 `_core.linalg._set_tuning(min_ns, task_ns)`로 바꾸고, 다른 코드는 바꾸지 않아요.

### 크기 기준은 없어요

"큰 행렬은 행렬 하나가 충분히 크니 배치를 나누지 말고 LAPACK 내부 스레드에 맡긴다"는 규칙은 두지 않아요. Accelerate는 거의 모든 LAPACK 루틴을 호출한 스레드 하나로 돌리기 때문이에요. 내부 스레드를 쓰는 것은 `getrf`의 $n \ge 768$뿐이고, `gesv`, `potrf`, `geqrf`, `syevd`, `gesdd`, `geev`는 $n = 1024$까지 사실상 1스레드예요(CPU 시간/경과 시간 ≤ 1.11). 그래서 배치 8에서 $n = 128$–1024 모든 크기에서 나누는 쪽이 빨랐어요. 내부 스레드를 쓰는 `getrf`의 `solve`, `inv`($n \ge 768$)도 나누면 1.7–2배 빨랐어요.

배열 영역의 `matmul`은 반대예요. Accelerate의 `gemm`은 큰 행렬에 여러 스레드를 쓰므로, 큰 행렬의 배치는 차례로 돌려요([행렬 곱](/internals/array/matmul/)). 같은 라이브러리라도 루틴마다 스레드를 쓰는 방식이 달라서 규칙이 갈려요.

### 예외: 작은 띠의 `gbsv`

`solve_banded`가 부르는 `gbsv`(띠 행렬 LU)에는 호출마다 약 1µs의 고정비가 있고, 이 부분은 스레드를 늘려도 빨라지지 않았어요. 작은 띠에서 나누면 오히려 1.1–2.7배 느려졌어요. 교차점은 kl = ku = 2에서 $n = 64$–96, kl = ku = 5에서 $n = 32$–48이에요. 그래서 $n \cdot (k_l + k_u + 1) \ge 400$(`kBandSplitMin`)일 때만 비용 모델대로 하고, 그 아래에서는 `element_ns = 0`(나누지 않음)을 넘겨요. 그 이상에서는 나누면 2–4배 빨라져요.

대역폭 (1, 1)은 `gbsv`가 아니라 삼중대각 전용 `gtsv`로 풀어서 이 고정비가 없고, 항상 비용 모델대로 해요([띠 행렬과 Sylvester 방정식](/internals/linalg/special/)).

## 태스크 수 상한: AMX에서 직렬로 도는 경로

### 무엇이 일어나나

Apple M 시리즈 칩에는 CPU 코어 묶음(클러스터)이 함께 쓰는 행렬 연산 장치가 있고, 흔히 AMX라고 불러요. Apple이 공개한 명령 집합이 아니라서 Accelerate 같은 시스템 라이브러리 안에서만 쓰여요. 여러 코어가 동시에 이 장치로 일을 보내면 그 일들은 장치 하나에서 차례로 처리돼요.

Accelerate가 작은 LAPACK 호출 일부를 이 장치로 보내는 것으로 보이는 경로가 둘 있어요. 이 경로는 스레드를 늘려도 빨라지지 않고, 몇 개를 넘으면 오히려 느려져요.

- `getrf`(LU 분해)의 $n = 32$–40. $n \le 31$과 $n \ge 48$은 스레드 수만큼 잘 빨라져요.
- 우변이 **8개 이상**인 삼각 풀기(`getrs`, `trtrs`, `potrs` 안의 `trsm`)의 $n = 24$–40. 우변 7개 이하와 $n \le 23$은 잘 빨라져요. 경계는 정확히 우변 7개와 8개 사이예요. 8개부터 `trsm`이 블록 경로로 바뀌는데, 이 경로는 호출마다 약 1.3–1.5µs의 고정비가 있고, 10스레드에서도 원소당 시간이 1스레드와 같아요.

Accelerate의 내부 구현은 공개돼 있지 않으므로, "AMX에서 직렬로 돈다"는 것은 측정의 모양(어느 크기에서 확장이 멈추는지, 몇 스레드에서 가장 빠른지)으로 판단한 것이에요.

### 규칙: `lu_task_cap`

태스크 수가 곧 동시에 일하는 스레드 수의 상한이에요. 그래서 이 경로에 걸리는 배치는 태스크 수를 줄여요. 각 크기에서 가장 빨랐던 스레드 수에 맞춘 값이에요.

| 경로 | 크기 | 태스크 수 상한 |
|---|:---:|:---:|
| `getrf`로 분해 | $n = 32$–35 | 5 |
| 우변 $k \ge 8$의 삼각 풀기 | $n = 24$–34 | 3 |
| 우변 $k \ge 8$의 삼각 풀기 | $n = 35$–40 | 5 |

```cpp
// linalg/cost.hpp
inline int lu_task_cap(std::int64_t n, std::int64_t k, bool factors) {
    if (!kLuTaskCapOn) return 0;                       // 실험용 스위치
    int cap = 0;
    auto tighten = [&](int c) { cap = cap == 0 ? c : (c < cap ? c : cap); };
    if (factors && n >= 32 && n <= 35) tighten(5);
    if (k >= 8 && n >= 24 && n <= 34) tighten(3);
    if (k >= 8 && n >= 35 && n <= 40) tighten(5);
    return cap;                                        // 0 = 상한 없음
}
```

함수마다 `n`(행렬 크기), `k`(우변 열 수), `factors`(`getrf`를 부르는지)를 넘겨요. `inv`는 우변이 단위행렬이라 `k = n`이고, `matrix_power`는 지수가 음수일 때만(역행렬을 `getrf + getrs`로 구할 때만) 넘겨요. 적용 대상은 `solve`, `inv`, `det`, `slogdet`, `lu`, `lu_solve`, `solve_triangular`, `cholesky_solve`, `matrix_power`(음수 지수), `cond`(±2 외의 `ord`)예요.

`getrf` 규칙이 측정된 범위(32–40)보다 좁게 35까지인 이유는 `lu` 때문이에요. `lu`는 분해 뒤에 L과 U를 따로 풀어 쓰는 일이 있는데, 이 부분은 스레드 수만큼 잘 빨라져요. $n = 36$–40에서 상한을 두면 `lu`가 5–12% 느려졌어요.

`run_batch`는 상한이 있으면 태스크당 원소 수를 늘려서 태스크 수를 맞춰요: 태스크가 `max_tasks`개를 넘으면 `per = ⌈n / max_tasks⌉`. 상한을 끈 것과 켠 것을 같은 자리에서 번갈아 재면, 해당 크기에서 1.1–1.5배 빨라지고(`inv` (100, 32, 32)는 1.39배) 그 밖의 크기에서는 같아요.

### 이 경로를 피하지 않는 이유

경로 자체를 피하는 방법도 있어요. 우변을 4열씩 나눠 풀면 블록 경로를 타지 않고, $n \approx 32$의 `getrf`를 블록이 아닌 `getf2`로 하면 AMX를 거치지 않아요. 둘 다 빨라지지만(`getrf` 부분은 6배) 결과의 비트가 바뀌어요. 계산 순서가 달라지기 때문이에요. 게다가 "어느 크기에서 다른 루틴을 부른다"는 규칙은 같은 함수의 결과가 행렬 크기에 따라 다른 계산에서 나오게 만들어요. 태스크 수 상한은 **어느 원소가 어느 스레드에서 도는지만** 바꾸므로 결과에 영향이 없어요. 그래서 이쪽을 택했어요.

### 관찰: 일부 크기에서 확장성이 낮아요

배치 512, 10스레드의 속도 향상은 대부분 5–9배인데, `det` $n = 32$(2.1배), `cholesky` $n = 48$(3.2배), `matrix_power` $n \ge 48$(3.6–4.3배)이 낮아요. Accelerate의 블록 알고리즘이 행렬 곱 부분을 AMX에서 돌린다고 보면, 블록 경로가 시작되는 크기에서 확장성이 떨어지는 것과 맞아요. 이것은 측정 모양에서 추론한 가설이고, stardust 코드로 바꿀 수 있는 부분이 아니라서 상한을 두지 않았어요. 위의 두 경로는 스레드 수별 시간을 직접 재서 "몇 스레드에서 가장 빠른지"가 분명했기 때문에 상한을 둔 경우예요. 배열 영역의 작은 행렬 배치 `matmul`도 32×32부터 약 2배에서 멈춰요([행렬 곱](/internals/array/matmul/)).

## 작업 메모리: `Scratch`

### 슬롯

몸체는 패킹한 행렬, 피벗 배열, LAPACK workspace 같은 임시 메모리가 필요해요. 행렬마다 `malloc`하면 작은 행렬에서는 할당이 계산보다 비싸요. 그래서 배치 원소들이 메모리를 재사용하도록 `Scratch`를 둬요. 직렬이면 배치 전체에 하나, 나누면 태스크마다 하나예요.

`Scratch`는 독립된 바이트 버퍼 9개(**슬롯**)와 정수 버퍼 2개예요. 각 버퍼는 요청받은 크기까지 커지기만 하고 줄지 않아요.

| 슬롯 | 쓰는 쪽 | 예 |
|:---:|---|---|
| 0–3, 정수 0 | 함수 몸체 | 패킹한 `a`, 피벗 `ipiv`, `matrix_power`의 곱 버퍼 두 개 |
| 4–5, 정수 1 | LAPACK 래퍼 | `work`, `rwork`, `iwork` |
| 6–8 | `LapackSlot` | 정렬되지 않은 출력 자리의 대역 (아래 16바이트 정렬 절) |

슬롯을 쓰는 쪽별로 나눈 이유는 서로 덮어쓰지 않게 하려는 것이에요. 몸체가 슬롯 0에 패킹한 행렬을 LAPACK 래퍼가 workspace로 덮어쓰면 안 되니까요. 쓰는 쪽이 정해진 슬롯만 쓰면 이런 충돌을 코드 한 곳만 보고 확인할 수 있어요.

### 0으로 채우지 않아요

`std::vector<std::byte>`의 `resize`는 새로 늘어난 부분을 0으로 채워요. 1000×1000 행렬에서는 이 0 채우기가 패킹 자체만큼 시간이 들었어요. 모든 사용처가 읽기 전에 쓰므로 0이 필요 없어요. 그래서 `Scratch`의 버퍼는 `new std::byte[]`로 받은 초기화되지 않은 메모리예요. 같은 이유로 linalg의 pairwise 합에서 complex 잎 버퍼도 `cplx buf[...]`(생성자가 0으로 채움) 대신 `alignas(16) double raw[...]`를 `cplx*`로 봐요.

### 작은 버퍼는 캐시 라인을 따로 가져요

나눈 배치에서는 태스크마다 `Scratch`가 있어요. 여러 스레드가 아주 작은 블록을 거의 동시에 요청하면 `malloc`이 서로 다른 스레드의 블록을 **같은 캐시 라인** 안에서 내줄 때가 있어요. 예를 들어 `lu_solve`는 원소마다 3바이트짜리 `seen` 배열(순열 검사)과 24바이트짜리 `perm`을 써요. 한 캐시 라인을 두 코어가 번갈아 쓰면, 쓸 때마다 그 라인의 소유권이 코어 사이를 오가요(false sharing [4]). 원소마다 쓰는 버퍼라 그 왕복이 원소마다 일어나요.

까다로운 점은 이 현상이 **프로세스마다** 다르다는 거예요. `malloc`의 상태가 프로세스마다 달라서, 같은 빌드에서도 어떤 프로세스는 라인이 겹치고 어떤 프로세스는 겹치지 않아요. `lu_solve` (1000, 3, 3), 10스레드에서 라인이 겹친 프로세스는 겹치지 않은 프로세스보다 약 1.3배 느려요. 빌드가 바뀌면 겹치는 프로세스의 비율도 바뀌어서, 코드는 그대로인데 빌드 사이에 성능이 달라진 것처럼 보여요.

그래서 4KB(`kSmall`)보다 작은 버퍼는 128바이트(Apple M 시리즈의 캐시 라인) 경계에서 시작하고, 크기도 128의 배수로 올려요. 그러면 버퍼 하나가 라인을 통째로 가지므로 다른 스레드의 버퍼와 라인을 나누지 않아요.

```cpp
// linalg/batch.hpp의 Scratch::Buf (발췌)
static constexpr std::size_t kLine = 128;    // Apple M 시리즈의 캐시 라인
static constexpr std::size_t kSmall = 4096;

std::byte* get(std::size_t want) {
    if (want > n) {
        if (want < kSmall) {                 // 작으면: 라인 경계에서, 라인 단위 크기로
            const std::size_t size = (want + kLine - 1) / kLine * kLine;
            p = {static_cast<std::byte*>(::operator new[](size, std::align_val_t{kLine})), Free{true}};
            n = size;
        } else {                             // 크면: 평범한 new[]
            p = {new std::byte[want], Free{false}};
            n = want;
        }
    }
    return p.get();
}
```

`std::unique_ptr`의 삭제자 `Free`는 그 블록이 정렬 할당인지 기억했다가 맞는 `operator delete`를 불러요. 정렬된 `operator new`로 받은 메모리는 정렬된 `operator delete`로 돌려줘야 하기 때문이에요.

### 큰 버퍼는 정렬 할당을 쓰지 않아요

모든 버퍼를 128바이트 정렬로 받으면 될 것 같지만, 큰 버퍼에서는 해가 돼요. 정렬된 `operator new`는 `malloc`이 놓아 둔 블록을 다시 쓰지 않는 경로로 가서, 큰 버퍼가 호출마다 새 페이지로 왔어요. 새 페이지는 처음 쓸 때 페이지 폴트를 일으켜요. 큰 버퍼까지 정렬 할당으로 받으면 `solve_triangular` (300, 300)과 (1000, 1000)이 1스레드에서 약 1.3배 느려져요. 큰 버퍼는 어차피 많은 라인에 걸치므로 라인을 나눠 쓰는 문제가 거의 없어요. 그래서 4KB부터는 평범한 `new[]`예요.

### workspace 크기는 한 번만 물어요

LAPACK의 많은 루틴은 작업 공간 `work`와 그 길이 `lwork`를 받아요. 필요한 길이는 블록 크기 같은 내부 사정에 따라 정해지므로, 호출하는 쪽은 먼저 `lwork = -1`로 불러 "얼마나 필요한지"를 물어요(workspace query [1]). 루틴은 계산하지 않고 `work[0]`에 최적의 길이를 써서 돌려줘요. 그다음 그만큼 할당하고 다시 불러요.

이 질의도 LAPACK 호출 한 번이라 고정비가 있어요. 작은 행렬의 배치에서 행렬마다 물으면 질의가 계산만큼 비싸요. `qr`은 `geqrf`와 `orgqr` 두 루틴을 부르므로 행렬마다 두 번 물어야 해요. 그래서 `Scratch`가 질의 결과를 기억해요.

```cpp
// linalg/batch.hpp (발췌)
using WorkKey = std::array<lint, 6>;   // 루틴 id, 크기 인자들, 원소 크기
template <class Query>
WorkSizes sizes(const WorkKey& key, Query&& query) {
    for (const auto& [k, v] : work_sizes_)
        if (k == key) return v;        // 같은 루틴, 같은 크기면 기억한 값
    work_sizes_.emplace_back(key, query());
    return work_sizes_.back().second;
}

// linalg/lapack.hpp의 syevd 래퍼에서
const WorkSizes z = s.sizes({kSyevd, n, lda, jobz, 0, esize<T>()}, [&] {
    /* dsyevd_/zheevd_를 lwork = liwork = -1로 불러 크기를 받아요 */
});
```

배치 안의 행렬은 모두 크기가 같으므로 질의는 직렬이면 배치당 한 번, 나누면 태스크당 한 번이에요. 키에 원소 크기를 넣은 것은 같은 루틴이라도 `double`과 `complex`의 요구량이 다르기 때문이에요. 목록은 선형 탐색이에요. 한 `Scratch`가 기억하는 키는 함수 하나가 부르는 루틴 수(많아야 서너 개)라서 해시가 필요 없어요.

중요한 성질은 **기억한 크기가 행렬마다 물었을 때와 같은 값**이라는 거예요. `gesdd`(SVD)는 `lwork`의 크기를 보고 내부 경로를 골라요. `lwork`가 다르면 다른 경로로 계산해서 결과 비트가 달라질 수 있어요([특이값 분해](/internals/linalg/svd/)). 질의 결과를 그대로 쓰므로, 배치의 어느 원소든, 직렬이든 병렬이든 같은 `lwork`로 계산해요.

## 16바이트 정렬: `LapackSlot`

### Accelerate는 정렬에 따라 반올림이 달라요

float64 3×3 행렬의 배치를 생각해 봐요. 결과 배열은 행렬을 72바이트 간격으로 이어 붙여요. 결과 배열의 시작은 128바이트 경계이지만, 원소 1의 자리는 72바이트, 원소 3의 자리는 216바이트로, **홀수 번째 원소의 자리는 16의 배수가 아니에요**(8바이트 어긋나요).

LAPACK에 결과 자리를 바로 넘기면(고유벡터를 결과 배열에 바로 쓰게 하는 식으로, [패킹과 결과 레이아웃](/internals/linalg/packing/)) 같은 행렬이 배치의 어느 위치에 있느냐에 따라 **다른 비트**를 받았어요. $n = 3, 5, 7, 9$의 무작위 행렬 120개 중 실수 `schur`는 18–30개, `svd`는 3–17개, `eigh`는 27–45개가 달랐어요. `eigh(a, b)`도 같았어요. complex는 원소 하나가 16바이트라 늘 정렬돼 있고, 다른 것이 0개였어요.

원인은 Accelerate 안쪽이라 볼 수 없지만, 정렬된 배열과 그렇지 않은 배열에 서로 다른 커널(예: 한 번에 두 개씩 읽는 SIMD 경로와 나머지를 따로 처리하는 경로)을 쓰고, 그 커널들의 덧셈 순서가 다르다고 보면 설명이 돼요. 덧셈 순서가 다르면 반올림이 달라지고, 고유값·특이값 반복 알고리즘은 그 차이를 마지막 비트까지 끌고 와요.

16바이트면 충분한지도 확인했어요. 행렬 자리가 16의 배수이지만 64의 배수는 아닌 크기($n = 2, 6, 10, 14, 18, 30$)에서는 위치와 상관없이 모두 같은 비트였어요.

### 규칙과 구현

**LAPACK과 BLAS에 넘기는 배열은 모두 16바이트 정렬해요.** 입력은 원래 `Scratch`에 패킹하므로 정렬돼 있어요(작은 버퍼는 128바이트 경계, 큰 버퍼는 `new[]`의 16바이트 경계). 문제는 결과 자리에 바로 쓰는 출력이에요. 이것을 `LapackSlot`이 맡아요.

```cpp
// linalg/ops/common.hpp
inline bool aligned16(const void* p) { return reinterpret_cast<std::uintptr_t>(p) % 16 == 0; }

template <class T>
class LapackSlot {
public:
    LapackSlot(T* slot, std::int64_t count, Scratch& s, int scratch_slot)
        : slot_(slot), n_(count),
          p_(aligned16(slot) ? slot : s.get<T>(static_cast<std::size_t>(count), scratch_slot)) {}
    ~LapackSlot() {
        if (p_ != slot_) std::copy(p_, p_ + n_, slot_);   // 대역에서 계산했으면 자리로 복사
    }
    LapackSlot(const LapackSlot&) = delete;
    LapackSlot& operator=(const LapackSlot&) = delete;
    T* get() const { return p_; }
private:
    T* slot_;
    std::int64_t n_;
    T* p_;
};
```

- 자리가 정렬돼 있으면 그 자리를 그대로 쓰고, 아니면 `Scratch`의 슬롯 6–8에서 대역을 받아요. 소멸자가 대역의 내용을 자리로 복사해요. 범위를 벗어날 때 정리하는 RAII 방식이라, 몸체가 중간에 실패 코드를 돌려주며 빠져나가도 복사를 잊지 않아요.
- 복사·대입을 지워서(`= delete`) 실수로 두 번 복사되는 일이 없게 해요.
- 그 자리에 쓰는 것은 패킹이든 LAPACK이든 후처리든 모두 `get()`을 거쳐요.
- 슬롯이 셋인 이유는 출력이 셋인 함수가 있기 때문이에요. `svd`는 U, V, 특이값을 한꺼번에 받아요.

`eigh`의 몸체에서 쓰는 모습은 이래요.

```cpp
// linalg/ops/spectral.cpp의 eigh_impl (발췌)
LapackSlot<T> vs(vo.as<T>() + i * n * n, n * n, s, Scratch::kAlign0);  // 고유벡터 자리
pack_triangle(..., vs.get(), n, ...);           // a를 그 자리에 바로 패킹
LapackSlot<double> ws(W + i * n, n, s, Scratch::kAlign1);              // 고유값 자리
return lapack::syevd(jobz, n, vs.get(), n, ws.get(), s) > 0 ? kNoConvergenceEig : 0;
```

정렬이 필요한 곳은 이 밖에도 있어요.

- `Scratch` 안에서 하나의 버퍼를 여러 하위 배열로 나눌 때(`gees`의 `wr`/`wi`, `solve_sylvester`의 R/S/U/W, 삼중대각의 세 대각), 각 하위 배열의 길이를 `pad2(n)`(짝수로 올림)로 잡아 다음 배열도 16바이트 경계에서 시작하게 해요.
- 삼각 행렬을 패킹 없이 그 자리에서 읽을 때(`triangle_operand`), 시작 주소와 열 간격이 모두 16의 배수일 때만 그 자리에서 읽어요.
- 결과 배열 자체는 128바이트 경계에서 시작해요(`outblock.cpp`).

이렇게 해서 **모든 함수에서 배치 결과가 행렬 하나씩 부른 결과와 비트까지 같아요.** `tests/linalg/test_optimizations.py`의 `test_batch_equals_one_by_one`이 홀수 크기 $n = 3, 5, 7, 40$의 배치 5개를 통째로 부른 결과와 하나씩 부른 결과를 22개 호출, float64·complex128에서 바이트로 비교해요.

<Callout type="warn" title="대역 복사의 비용">

## 실패 보고: 가장 작은 인덱스

### 규칙

배치 중 하나라도 실패하면(특이 행렬, NaN 입력, 수렴 실패) 호출 전체가 실패하고, 메시지에 **가장 작은 실패 인덱스**를 넣어요.

```python
>>> x = sd.asarray([[[2.0, 0.0], [0.0, 2.0]], [[1.0, 2.0], [2.0, 4.0]]])
>>> sd.linalg.inv(x)
Traceback (most recent call last):
    ...
stardust.linalg.LinAlgError: inv(): singular matrix (at batch index (1,))
```

### 직렬

앞에서부터 돌다가 첫 실패에서 멈춰요. 앞에서부터 보므로 그것이 가장 작은 인덱스예요.

### 나눌 때

태스크들은 아무 순서로나 돌아요. "처음 발견한 실패에서 모두 멈춘다"고 하면 빨리 끝나지만, 어느 인덱스가 보고될지가 스레드 타이밍에 달려요. 같은 입력에 실행마다 다른 메시지가 나오면 디버깅이 어려워져요. 그래서 이렇게 해요.

1. 태스크마다 자기 범위를 앞에서부터 돌다가 첫 실패를 자기 칸(`fails[t]`)에 기록하고 멈춰요.
2. 지금까지 알려진 가장 작은 실패 인덱스를 atomic 변수 `first`에 둬요. 실패한 태스크는 compare-and-swap으로 자기 인덱스가 더 작으면 바꿔요.
3. 태스크는 원소를 시작하기 전에 `first`를 보고, 자기 원소가 그보다 뒤면 멈춰요. 그 원소에서 실패가 나도 보고될 일이 없기 때문이에요.
4. 모두 끝나면 `fails`에서 가장 작은 인덱스를 골라요.

```cpp
// linalg/batch.hpp의 run_batch, 나눌 때 (발췌)
std::vector<Failure> fails(ntasks);
std::atomic<std::int64_t> first{std::numeric_limits<std::int64_t>::max()};
detail::run_tasks(ntasks, [&](std::int64_t t) {
    Scratch scratch;
    std::int64_t offs[kMaxOperands];
    for (std::int64_t i = t * per; i < std::min(n, (t + 1) * per); ++i) {
        if (i > first.load(std::memory_order_relaxed)) return;    // 더 작은 실패가 이미 있어요
        b.offsets(i, offs);
        if (const int code = body(i, offs, scratch)) {
            fails[t] = {i, code};
            std::int64_t cur = first.load(std::memory_order_relaxed);
            while (i < cur && !first.compare_exchange_weak(cur, i, std::memory_order_relaxed)) {}
            return;
        }
    }
});
Failure best;
for (const Failure& f : fails)
    if (f && (!best || f.index < best.index)) best = f;
```

왜 이것이 직렬과 같은 답을 내는지 보면 이래요. 직렬이 보고하는 인덱스를 $i^*$라고 해요. $i^*$를 맡은 태스크는 $i^*$에 도달하기 전에 멈추지 않아요. 멈추려면 $i^*$보다 작은 실패가 `first`에 있어야 하는데, $i^*$보다 작은 실패는 없기 때문이에요. 그 태스크는 $i^*$ 앞의 자기 원소들이 모두 성공하므로 $i^*$에서 실패를 기록해요. 다른 태스크가 기록하는 실패는 모두 $i^*$보다 뒤예요. 그래서 마지막에 고른 가장 작은 값은 언제나 $i^*$예요.

- `first`는 건너뛰기를 위한 힌트일 뿐이라 `memory_order_relaxed`로 충분해요. 최종 답은 `fails`에서 골라요. `fails`의 칸은 태스크마다 하나라 경쟁이 없고, `run_tasks`가 모든 태스크를 기다린 뒤에 읽으므로 그 쓰기가 보여요.
- `compare_exchange_weak`는 다른 스레드가 값을 바꿨거나 가짜 실패가 나면 `cur`에 현재 값을 넣고 false를 돌려줘요. 루프가 "내 인덱스가 더 작은 동안" 다시 시도해요.

`tests/linalg/test_parallel.py`의 `test_errors_name_the_smallest_index`가 원소 2000개 중 777번을 특이, 1234번에 inf, 1500번에 NaN을 넣고 스레드 1, 3, 10에서 같은 메시지(`at batch index (777,)`)가 나오는지 확인해요.

배열 영역의 같은 문제는 `parallel::FirstRow`가 같은 방법으로 풀어요([스레드풀과 결정성](/internals/core/threads/)).

## 합: pairwise와 긴 합

### numpy의 pairwise 합 그대로

linalg의 부동소수점 합은 모두 numpy의 pairwise 합이에요. 대상은 `vecdot`, `trace`, `vector_norm`(1, 2, p), `matrix_norm`(fro, ±1, ±inf, nuc), `cond`(fro, ±1, ±inf, nuc)의 합이에요.

알고리즘은 배열의 합과 같은 한 벌의 정의(`base/pairwise.hpp`)예요. 128개 이하는 누산기 8개로 더하고, 더 길면 8의 배수에서 반으로 나눠 재귀해요. complex는 잎이 64개이고 실수부, 허수부에 누산기가 4개씩이에요. 합은 `0.0 + 트리`예요. 덧셈 경로의 길이가 $\log n$ 정도라 오차 한계가 $n$이 아니라 $\log n$에 비례해요 [2]. numpy의 `DOUBLE_pairwise_sum`/`CDOUBLE_pairwise_sum`과 같은 알고리즘, 같은 순서예요 [3]. 자세한 알고리즘과 오차 분석은 [집계](/internals/array/reductions/)에 있어요.

항의 순서는 **논리적 C 순서**예요(마지막 축이 가장 빨리 변해요). 메모리 레이아웃과 상관없는 순서라서 결과도 레이아웃과 상관없어요. 그래서 같은 항이면 numpy와, 그리고 배열의 `sd.sum`과 비트까지 같아요. 예를 들어 `vecdot(x, y)`는 `sum(conj(x) * y, axis=-1)`과, `trace(x)`는 `sum(diagonal(x))`와 같아요.

### linalg만의 것: 잎 버퍼

배열 영역은 트리에 접근자 `get(i)`를 넘겨 원소를 그 자리에서 읽어요. linalg는 항을 먼저 잎 하나 분량(최대 128개)의 버퍼에 채우고, 그 버퍼를 더해요.

```cpp
// linalg/pairwise.hpp (발췌)
template <class Fill>
double pairwise(std::int64_t begin, std::int64_t n, Fill& fill) {
    return pairwise::tree(begin, n, [&fill](std::int64_t b, std::int64_t m) {
        double buf[kPairwiseBlock];            // 잎 하나 = 최대 128개
        fill(b, m, buf);                       // 항 b … b+m-1을 버퍼에
        return pairwise_leaf(buf, m);          // 같은 잎 합
    });
}
```

`fill(begin, len, out)`은 항 `begin`부터 `len`개를 차례로 `out`에 써요. 항이 무엇인지는 함수가 정해요. `vecdot`은 `conj(x[i]) * y[i]`(bool/int64를 float64로 바꾸면서), 노름은 `|x|`나 `|x|²`(임의의 strides와 축 수를 걸으면서)예요. linalg의 항은 종류가 많고 출처의 레이아웃도 제각각이에요. 버퍼를 거치면 **더하는 루프가 하나**가 되고, 그 루프는 연속 배열 위의 단순한 루프라서 벡터화돼요.

대가로 메모리를 두 번 지나요(채우기, 더하기). 1스레드의 긴 합은 그만큼 numpy보다 느려요(아래 성능 절).

### 짧은 합은 트리를 부르지 않아요

`pairwise_sum`은 $n \le 128$(complex는 64)이면 트리 함수를 부르지 않고 채운 뒤 바로 잎 합을 해요. 3×3 행렬의 열 합처럼 짧은 합이 배치마다 반복되면 재귀 함수 호출 자체가 드러나기 때문이에요. 이 길이 없으면 (1000, 3, 3)의 `matrix_norm(ord=1)`이 1스레드에서 약 1.3배 느려요. 트리를 부르든 안 부르든 잎 하나짜리 합은 같은 덧셈이라 비트는 같아요.

연속 float64 `vecdot`은 한 걸음 더 가서 버퍼도 쓰지 않아요. 잎 합의 접근자가 곱 `a[i] * c[i]`를 그 자리에서 계산해요. 같은 항을 같은 순서로 더하고, 빌드에서 FMA 축약을 꺼 두었으므로(`-ffp-contract=off`) 곱과 덧셈이 하나의 FMA로 합쳐지지 않아 비트가 같아요. 버퍼를 거치면 (1000, 1000)의 행마다 내적이 약 1.3배 느려요.

### 출력 하나의 긴 합은 잎 단위로 나눠요

배치를 나누는 것과 별개로, **출력 하나**의 합이 길면 그 합 자체를 나눠요. 기준은 배열 영역과 같아요. 항이 2¹⁵개(`kSumParallelMin`) 이상이면, 트리를 2¹²항(`kSumLeaf`) 이하의 부분 트리까지 내려가 그것들을 병렬로 더하고 같은 트리 순서로 합쳐요(`pairwise_plan`, `pairwise_run`, `pairwise_combine`).

덧셈 하나하나가 직렬 트리와 같은 피연산자, 같은 순서이므로 결과는 직렬과, 그리고 numpy와 비트까지 같아요. 잎을 앞에서부터 4096개씩 자르면 트리의 경계와 어긋나서 덧셈 순서가 바뀌므로, 잎도 트리를 따라 내려가며 만들어요. 이 방법은 [스레드풀과 결정성](/internals/core/threads/)에 자세히 있어요.

```cpp
// linalg/pairwise.hpp의 pairwise_sum_mt (발췌)
template <class T, class Fill>
T pairwise_sum_mt(std::int64_t n, Fill&& fill) {
    if (n < kSumParallelMin) return pairwise_sum<T>(n, fill);   // 짧으면: 계획도, 할당도 없음
    const auto plan = pairwise_plan(n, complex);                // 잎들의 (시작, 길이)
    if (plan.size() == 1) return pairwise_sum<T>(n, fill);      // 풀을 못 쓰면
    std::vector<T> parts(plan.size());
    pairwise_run(plan, [&](std::int64_t t) {
        auto f = fill;                                          // 태스크마다 복사본
        parts[t] = detail::pairwise(plan[t].first, plan[t].second, f);
    });
    return 0. + pairwise_combine(n, complex, parts);
}
```

- **짧은 합에는 아무것도 할당하지 않아요.** 2¹⁵항 미만이면 계획(`std::vector`)을 만들지 않고 바로 직렬 함수로 가요. 출력이 많은 짧은 노름(예: (1000, 3, 3)의 행렬마다 노름)에서 출력마다 벡터를 두세 개 만들면, 할당이 계산보다 비싸지고 나눈 배치의 태스크 안에서는 할당끼리 경쟁까지 해요.
- `fill`은 여러 스레드에서 동시에 불리므로 공유 상태에 쓰면 안 돼요. 태스크마다 복사본을 써요.

노름은 합과 함께 최댓값, NaN 여부, 0이 아닌 원소 수도 구해요. 이것들은 순서와 상관없는 값이라 잎마다 따로 구해 합쳐요. 단, 잎마다 **자기 칸**(`Side`)에 써요. 공유 변수 하나에 여러 스레드가 쓰면 경쟁이 생기기 때문이에요. 자세한 것은 [LAPACK 없이 계산하는 함수](/internals/linalg/basic/)에 있어요.

`matrix_norm`의 1, inf는 큰 행렬 하나의 열(행) 합들을 태스크로 나눠요. 줄 하나의 합은 직렬과 같고, 그 합들의 max/min은 순서와 상관없으므로 결과가 같아요.

## 중첩하지 않기

풀은 중첩하지 않아요. 태스크 안에서는 `begin_parallel()`이 false예요. 그래서 배치를 나눈 태스크 안의 긴 합, 큰 C 순서 행렬의 병렬 패킹([패킹과 결과 레이아웃](/internals/linalg/packing/)), `solve_sylvester`의 Schur 분해 두 개의 동시 실행([띠 행렬과 Sylvester 방정식](/internals/linalg/special/))은 그 스레드에서 직렬로 돌아요.

중첩을 허용하면 태스크가 다시 태스크를 만들고, 풀의 모든 스레드가 이미 바쁜 상태에서 안쪽 태스크를 기다리는 구조가 돼요. 바깥 분할만으로 코어가 이미 다 차므로 얻을 것이 없어요. 배치가 크면 배치를, 행렬 하나가 크면 그 안을 나눠요.

다른 Python 스레드가 풀을 쓰는 중이면 `begin_parallel()`이 false라서 이 호출은 나누지 않고 호출 스레드 혼자 돌아요. 바쁜 풀에 일을 넣고 기다리는 것보다 직렬 경로가 빠르고, 결과는 같아요.

## 결정성

**결과는 스레드 수와 상관없이 비트까지 같아요.** 병렬 경로마다 그 이유를 정리하면 이래요.

| 병렬 경로 | 나누는 단위 | 결과가 같은 이유 |
|---|---|---|
| 배치 | 연속한 원소 묶음 | 원소 하나는 어디서 돌든 같은 계산이에요: 자기 `Scratch`, 같은 `lwork`, 16바이트 정렬, 그리고 Accelerate는 여러 스레드에서 동시에 불러도 결과가 같아요 |
| 태스크 수 상한 | — | 어느 원소가 어느 스레드에서 도는지만 바뀌어요 |
| 실패 보고 | 태스크마다 첫 실패 | 가장 작은 인덱스를 골라요 |
| 출력 하나의 긴 합 | pairwise 트리의 잎 | 같은 트리 순서로 합쳐요 |
| `matrix_norm` 1/inf의 줄 | 줄 묶음 | 줄 하나의 합은 직렬과 같고, max/min은 순서와 상관없어요 |
| 큰 C 순서 패킹 | 열 32개 블록 | 복사뿐이에요 |
| Schur 쌍 | 두 분해 | 같은 배열과 같은 workspace 크기예요 |

배치 행의 마지막 전제(Accelerate가 동시 호출에 같은 결과를 낸다)는 측정으로 확인한 사실이에요. `getrf`, `gesv`, `potrf`, `geqrf`, `syevd`, `gesdd`, `geev`를 $n = 8, 64, 256$에서 10스레드로 동시에 불러도 모두 호출 스레드에서 부른 결과와 비트가 같았어요. Accelerate의 내부 스레드 수(`BLASSetThreading`으로 1에 고정)도 $n = 64, 512, 1024$에서 결과를 바꾸지 않았어요. 자세한 것은 [선형대수 영역의 구조](/internals/linalg/overview/)에 있어요.

테스트가 이것을 고정해요(`tests/linalg/`).

- `test_parallel.py`: 36개 호출 × float64·complex128 × 배치 세 가지(`(400,)`의 3×3, `(4, 30)`의 5×5, `(48,)`의 16×16, 모두 나눌 만큼 큼)를 스레드 1, 3, 10에서 바이트로 비교해요. 실패 메시지, 긴 합(4만 개, 100만 3개), Python 스레드 4개의 동시 호출도 봐요.
- `test_optimizations.py`: 배치 결과와 하나씩 부른 결과의 바이트 비교(위의 정렬 테스트)와, 비공개 함수(`_set_tuning`, `_set_lu_task_cap` 등)로 분할·상한을 끈 경로와 켠 경로의 비트 비교를 해요.

## 성능

배치의 이득은 두 가지에서 와요.

1. **호출 비용.** numpy는 배치의 행렬마다 같은 LAPACK을 부르지만 그 사이에 numpy 쪽 고정비가 있어요. stardust는 배치 전체를 C++ 루프 하나로 돌고, workspace 질의를 한 번만 하고, 0 채우기를 하지 않아요. 그래서 1스레드에서도 배치가 numpy보다 빨라요.
2. **코어 수.** numpy와 scipy는 배치를 코어 하나로 돌아요. scipy의 일부 함수(`schur`, `hessenberg`, `ldl` 등)는 Python 수준에서 행렬을 하나씩 돌아요. stardust는 배치를 나눠 여러 코어로 돌아요.

| 호출 | numpy 대비, 10스레드 | numpy 대비, 1스레드 |
|---|:---:|:---:|

| `vector_norm` (1000000,) | ⟦BENCH vector_norm (1000000,) t10⟧ | ⟦BENCH vector_norm (1000000,) t1⟧ |

1스레드의 긴 합은 numpy보다 느릴 수 있어요. 잎 버퍼를 채우고 다시 읽는 두 단계 때문이에요. numpy 2.5.4의 `np.vecdot`은 BLAS 내적(`np.dot`과 같은 값)을 쓰고, `np.linalg.vector_norm`은 `x*x`를 만든 뒤 numpy의 합을 불러요. 곱과 잎 합을 NEON 레지스터 안에서 한 번에 하면 같은 트리 그대로(비트를 바꾸지 않고) 이 차이를 줄일 수 있는데, 아직 하지 않았어요.

비용을 정리하면 이래요.

| 부분 | 비용 |
|---|---|
| `Batch` 생성 | $O(k \cdot d)$ ($k$: 피연산자 수, $d$: 배치 축 수) |
| 원소 하나의 오프셋 | $O(k \cdot d)$ 곱셈·나눗셈 |
| 분할 판단 | $O(1)$ |
| 태스크 하나의 시작 | `Scratch` 생성, 첫 원소의 workspace 질의 |
| 실패 보고 | 원소마다 relaxed atomic 읽기 하나, 실패하면 CAS 몇 번 |
| 정렬 대역 | 정렬되지 않은 자리마다 $O(mn)$ 복사 |
| 긴 합 하나 | 잎 $\lceil n/4096 \rceil$개 정도의 계획(벡터 하나), 합치기 $O(n/4096)$ |

## 정확도

배치와 병렬화는 값을 바꾸지 않아요. 원소 하나의 결과는 그 행렬을 혼자 불렀을 때와 비트까지 같고, 스레드 수, 배치 안의 위치, 분할 방식과 상관없어요. 정확도는 각 함수가 부르는 LAPACK 루틴이 정해요(각 알고리즘 글).

합은 pairwise 트리라서 $n$개 항의 합의 오차가 $\gamma_h \sum |x_i|$ 이하이고, $h$는 덧셈 경로의 최대 길이로 대략 $24 + \lceil \log_2(n/128) \rceil$이에요 [2]. 원소 100만 개면 $h \le 37$ 정도라, 순차 합의 $h = n - 1$보다 수만 배 작아요. 병렬로 나눠도 같은 트리라서 이 한계도, 결과 비트도 그대로예요.
