## 한눈에 보기

`sd.linalg`는 행렬을 다루는 함수 37개예요. 선형 시스템 풀기(`solve`), 분해(`lu`, `cholesky`, `qr`, `eigh`, `svd` 등), 노름과 행렬식 같은 지표, 띠 행렬과 Sylvester 방정식, 행렬 지수(`expm`)가 들어 있어요. 코드는 C++ 코어 `csrc/linalg/`에 있고, Python 쪽 `src/stardust/linalg/`에는 이름을 다시 내보내는 파일과 예외 클래스 하나뿐이에요.

이 영역의 뼈대는 다섯 가지예요.

1. **분해 알고리즘을 직접 짜지 않아요.** LAPACK(Linear Algebra PACKage, 밀집 행렬 분해의 표준 라이브러리 [1])을 불러요. macOS의 Accelerate 프레임워크에 들어 있는 구현이에요 [2]. 직접 짜는 것은 LAPACK에 없는 `expm`과, LAPACK이 필요 없는 원소 루프(`vecdot`, `outer`, `trace`, 노름 등)뿐이에요.
2. **stardust가 맡는 일은 LAPACK의 앞과 뒤예요.** 인자를 검사하고, 어떤 메모리 배치의 입력이든 LAPACK이 읽는 형태로 옮기고(패킹), 행렬 여러 개를 스레드에 나누고(배치), LAPACK이 돌려준 상태 값 `info`를 에러로 바꾸고, 결과 배열을 만들어요. numpy·scipy도 같은 Accelerate를 부르므로, 속도 차이는 거의 다 이 부분에서 나와요.
3. **함수마다 계산 경로가 하나예요.** 입력 값이나 크기를 보고 LAPACK 루틴을 바꾸지 않아요. 같은 함수의 결과는 언제나 같은 계산에서 나와요.
4. **결과는 입력의 메모리 배치, 배치 안의 위치, 스레드 수와 무관하게 비트까지 같아요.** 패킹, 16바이트 정렬, 배치 분할이 모두 이 성질을 지키도록 짜여 있어요.
5. **Python 코드를 거치지 않아요.** `sd.linalg.solve`는 C++ 함수 그 자체예요. 작은 행렬에서는 계산보다 호출 경로가 더 오래 걸리기 때문이에요.

모든 행렬 함수는 같은 순서를 밟아요. `solve(a, b)`를 예로 들면 이래요.

## 무엇이 들어 있나

| 묶음 | 함수 |
|---|---|
| 기본 연산 | `vecdot`, `outer`, `trace`, `diagonal`, `matrix_power`, `kron`, `cross` |
| 노름과 지표 | `vector_norm`, `matrix_norm`, `det`, `slogdet`, `matrix_rank`, `cond` |
| 선형 시스템 | `solve`, `solve_triangular`, `cholesky_solve`, `lu_solve`, `lstsq`, `inv`, `pinv` |
| 분해 | `lu`, `cholesky`, `qr`, `qr_pivoted`, `ldl`, `eigh`, `eigvalsh`, `eig`, `eigvals`, `schur`, `hessenberg`, `svd`, `svdvals` |
| 특수 구조 | `solve_tridiagonal`, `solve_banded`, `solve_sylvester` |
| 행렬 함수 | `expm` |

행렬곱 `matmul`과 전치 `matrix_transpose`는 배열 영역에 있어요([행렬곱](/internals/array/matmul/)). 선형대수 영역에서 다시 만들지 않아요.

모든 함수가 지키는 규칙은 이래요. 사용자가 보는 쪽의 설명은 [선형대수의 기본](/api/linalg/basics/)에 있어요.

- **행렬 묶음을 받아요.** 인자의 모양은 `(..., M, N)`이에요. 마지막 두 축이 행렬 하나이고 앞의 축들은 "배치"예요. `(1000, 3, 3)`은 3×3 행렬 1000개예요. 벡터 인자는 마지막 축 하나가 벡터예요.
- **float64와 complex128로 계산해요.** bool과 int64 입력은 float64로 바꿔 계산해요. 인자가 여럿이면 하나라도 complex128일 때 전부 complex128로 계산해요. 원소를 꺼내기만 하는 `diagonal`은 입력 dtype을 그대로 둬요.
- **배열 인자는 `sd.ndarray`만 받아요.** 리스트나 numpy 배열은 `sd.asarray`로 먼저 바꿔요.
- **경고를 내지 않아요.** 결과가 넘치면 inf이고, 정의되지 않는 계산은 에러예요.

### C++가 하는 일, Python이 하는 일

C++가 호출 하나의 전부를 맡아요. 인자 검사(배열인지, dtype, 모양), 배치 브로드캐스팅, 패킹, LAPACK 호출, `info` 해석, 결과 배열 만들기, 결과 namedtuple 채우기까지예요.

Python 쪽에 남는 것은 세 가지예요.

- `src/stardust/linalg/__init__.py`: 확장 모듈의 하위 모듈 `stardust._core.linalg`에 있는 함수를 `sd.linalg`의 이름으로 그대로 다시 내보내요. 그리고 import할 때 한 번 `_core.linalg._setup(LinAlgError, _results.LINALG)`를 불러 Python에서 정의한 타입을 C++에 넘겨요.
- `src/stardust/linalg/_errors.py`: `class LinAlgError(ValueError)` 하나예요. 정의한 뒤 `LinAlgError.__module__ = "stardust.linalg"`로 바꿔요. 클래스가 실제로 사는 모듈(`stardust.linalg._errors`)이 아니라 사용자가 쓰는 공개 경로가 traceback과 `repr`에 보이게 하려는 거예요.
- `src/stardust/_results.py`: 결과 namedtuple 타입들이에요. 배열 영역(`unique_all`, `histogram` 등)과 특수함수 영역(`airy`)의 결과 타입과 한 파일에 있어요. 라이브러리 전체의 결과 타입이 한 모듈에 모여 있어서 이름 규칙(`함수이름Result`)과 필드 이름 규칙이 한 곳에서 보여요.

```python
# src/stardust/linalg/__init__.py에서 발췌
_core = _sd_core.linalg
_core._setup(LinAlgError, _results.LINALG)   # 타입을 C++에 한 번 넘겨요
globals().update({_name: getattr(_core, _name) for _name in __all__ if _name != "LinAlgError"})
```

마지막 줄 때문에 `sd.linalg.solve`는 Python 함수가 아니라 nanobind가 만든 C++ 함수 객체예요. 호출하면 인터프리터가 Python 바이트코드를 한 줄도 실행하지 않고 C++로 들어가요.

### 왜 Python 래퍼를 두지 않나

함수마다 Python 래퍼를 두고 C++에는 "패킹 + LAPACK"만 맡기면 코드는 읽기 쉬워요. 인자 검사와 결과 조립을 Python으로 쓸 수 있으니까요. 하지만 Python 함수 하나를 거치면서 인자를 검사하고 결과를 조립하면 호출마다 약 1–2µs가 더 들어요. 작은 행렬에서는 LAPACK 계산이 그보다 훨씬 짧아요. 예를 들어 3×3 행렬의 LU 분해 결과로 단위행렬 우변을 푸는 `getrs` 단계는 약 0.1µs예요(Apple M4 Pro). 래퍼가 계산보다 몇 배 비싸지는 셈이에요. 작은 행렬을 많이 푸는 코드(시뮬레이션의 시간 단계, 점마다 3×3 변환)에서는 이 고정비가 전체 시간을 정해요.

그래서 인자 검사와 결과 조립까지 C++에 둬요. 대가는 에러 메시지와 namedtuple을 C++에서 만들어야 한다는 것인데, 이 부분은 영역 전체가 함께 쓰는 틀(`Input`, `raise`, `make_result`)이 한 번만 구현해요.

### C++가 쓰는 Python 객체

C++ 코어가 호출 중에 쓰는 Python 객체는 **결과 namedtuple 타입 11개와 `LinAlgError`**뿐이에요. `_setup`이 import 때 한 번 받아 `csrc/linalg/pyrefs.cpp`의 정적 구조체에 넣어 둬요.

```cpp
// pyrefs.hpp
enum class Result { Slogdet, LU, QR, QRPivoted, Lstsq, Eigh, SVD, Eig, Schur, Hessenberg, LDL, Count };

struct PyRefs {
    PyObject* linalg_error = nullptr;
    PyObject* results[static_cast<int>(Result::Count)] = {};
};
```

- `Result` 열거형의 순서와 Python의 `_results.LINALG` 튜플의 순서가 같아야 해요. 개수가 다르면 `_setup`이 `ValueError`를 내서 import가 실패해요. 개수가 어긋난 채로 조용히 돌아가는 일이 없어요.
- 받은 참조는 놓지 않아요. 프로세스가 끝날 때까지 필요한 객체이고, 인터프리터가 종료되는 도중에 참조를 놓는 것은 안전하지 않기 때문이에요.
- `LinAlgError`를 받기 전에 수치적 실패가 나면(import 도중에만 가능해요) `ValueError`로 대신해요.

## 인자 받기

### `Input`: 배열을 빌려 읽기

배열과 선형대수는 같은 확장 모듈 `stardust._core` 안에 있어요([전체 구조](/internals/core/overview/)). 그래서 선형대수 함수는 Python 객체에서 C++ 구조체 `NDArray`를 바로 꺼내요. 버퍼 프로토콜 같은 중간 형식을 거치지 않아요.

```cpp
// input.hpp, 줄임
class Input {
public:
    Input(nb::handle obj, const char* func, const char* arg);   // sd.ndarray가 아니면 TypeError
    DType dtype() const;
    int ndim() const;
    std::int64_t shape(int d) const;     // d < 0이면 뒤에서부터
    std::int64_t stride(int d) const;    // 바이트 단위
    const std::byte* data() const;
    std::span<const std::int64_t> batch_shape(int core) const;    // 마지막 core개 축을 뺀 앞부분
    std::span<const std::int64_t> batch_strides(int core) const;
private:
    const NDArray* x_;                   // 빌린 포인터
    const char *func_, *arg_;            // 에러 메시지에 쓸 이름
};
```

`Input`은 `NDArray`를 복사하지 않고 포인터만 빌려요. 호출이 끝날 때까지 Python 인자가 배열을 살려 두므로 안전해요. 함께 들고 있는 함수 이름과 인자 이름은 에러 메시지에만 쓰여요. 복사 생성자를 지워 두어서 실수로 복사되는 일도 없어요.

```python
>>> sd.linalg.inv([[1.0, 2.0], [3.0, 4.0]])
Traceback (most recent call last):
    ...
TypeError: inv(): 'x' must be an sd.ndarray, not list
>>> sd.linalg.inv(sd.ones((2, 3)))
Traceback (most recent call last):
    ...
ValueError: inv(): 'x' must be square in its last two dimensions, got 2x3
```

읽는 것은 `data` 포인터, 모양, 바이트 단위 strides, dtype 네 가지예요. **strides에는 조건이 없어요.** C 순서, F 순서, 한 칸씩 건너뛴 뷰, 음수 stride(뒤집은 뷰), stride 0(브로드캐스트한 뷰)을 모두 받아요. 어떤 배치든 패킹이 같은 형태의 작업 버퍼로 옮기기 때문이에요([패킹과 결과 레이아웃](/internals/linalg/packing/)).

모양 검사는 두 함수가 맡아요. `require_matrix`는 2차원 이상인지, `require_square`는 거기에 더해 마지막 두 축의 길이가 같은지 봐요.

### 배열이 아닌 인자

`upper=`, `mode=`, `rtol=`, `n`(`matrix_power`), `axis=`, `dtype=`, `ord=` 같은 인자는 `csrc/linalg/args.cpp`와 각 함수의 파서가 읽어요.

- 정수 자리에 bool을 받지 않아요(`parse_int`). `True`가 조용히 1로 쓰이는 일을 막아요. 정수 판정은 배열 영역과 같은 도우미(`bind/pyutil.hpp`의 `index_value`)를 써서, 받는 값과 에러 메시지가 두 영역에서 같아요.
- `rtol=`은 0 이상의 유한한 실수 하나만 받아요(`parse_rtol`). `None`이면 $\max(m, n)\cdot\varepsilon$이에요($\varepsilon$은 float64의 기계 엡실론 $2^{-52}$).
- `mode=`는 `'reduced'`나 `'complete'`만 받아요(`ops/common.hpp`의 `parse_mode`). `qr`, `qr_pivoted`, `svd`가 같은 함수를 써요.

배열이 아닌 인자와 모양에서 나는 에러(`TypeError`, `ValueError`)는 배치를 돌기 **전에** 나요. 계산을 시작한 뒤에 나는 에러는 값에 달린 것(NaN, 특이 행렬)뿐이에요.

### 우변 `b`의 규칙

`solve`류 함수의 우변은 한 가지 규칙으로 읽어요(`ops/common.hpp`의 `rhs_of`).

- `b`가 **1차원**이면 벡터 하나 `(M,)`이에요. 결과도 `(M,)`이에요.
- 그 밖에는 행렬 묶음 `(..., M, K)`예요. 열 K개가 우변 K개예요.

`b`의 차원 수만 보고 정해요. "`a`가 배치이면 `b`의 마지막 축을 벡터로 본다" 같은 규칙은 `a`와 `b`의 모양을 함께 봐야 하고, 같은 `b`가 `a`에 따라 다르게 읽혀요. 행렬 `a`가 n×n인데 `b`의 행 수가 n이 아니면 `ValueError`예요.

## 배치와 계산 타입

### 배치 브로드캐스팅

인자가 여럿이면 배치 축끼리 브로드캐스트해요(`batch.cpp`의 `Batch`). 원소별 연산과 같은 규칙이에요. 오른쪽부터 맞추고, 길이 1인 축은 상대 길이로 늘어나요.

```python
>>> a = sd.ones((4, 1, 3, 3)) + sd.eye(3)     # 배치 (4, 1)
>>> b = sd.ones((5, 3, 2))                    # 배치 (5,)
>>> sd.linalg.solve(a, b).shape               # 배치 (4, 5), 우변 2개
(4, 5, 3, 2)
```

`Batch`는 인자마다 배치 축의 바이트 strides를 적어 두고, 브로드캐스트되는 축은 0으로 둬요. 그래서 위 예의 `a`는 20번 복사되지 않고, 배치 원소 `(i, j)`가 `a`의 `i`번째 행렬을 가리킬 뿐이에요. 결과 배열의 배치 원소 번호 하나(C 순서로 0, 1, 2, …)를 주면 `Batch::offsets`가 인자마다의 바이트 오프셋으로 바꿔 줘요. 인자는 최대 4개(`lu_solve`의 `l`, `u`, `perm`, `b`)예요.

배치 원소 하나는 언제나 LAPACK 호출 한 번(또는 정해진 몇 번)이고, 원소끼리는 서로 독립이에요. 그래서 원소들을 어떤 순서로, 어느 스레드에서 돌려도 결과가 같아요. 나누는 기준과 작업 메모리는 [배치와 병렬화](/internals/linalg/batch/)에 있어요.

### 계산 타입은 템플릿 인자예요

계산 타입은 `double`과 `std::complex<double>`(코드에서는 `cplx`) 둘뿐이에요. 함수 몸체는 타입 `T`의 템플릿(제네릭 람다)으로 한 번만 쓰고, 실행 중에 dtype을 보고 둘 중 하나를 골라요.

```cpp
// ops/common.hpp
template <class F>
nb::object with_type(bool complex, F&& f) {
    if (complex) return f(std::type_identity<cplx>{});
    return f(std::type_identity<double>{});
}

// 쓰는 쪽 (ops/lu.cpp의 solve에서)
const bool complex = computes_complex(a.dtype()) || computes_complex(y.dtype());
return with_type(complex, [&]<class T>(std::type_identity<T>) -> nb::object {
    ...   // T로 쓴 몸체. 컴파일러가 double판과 cplx판 두 벌을 만들어요.
});
```

`std::type_identity<T>`는 값이 없는 빈 객체예요. 타입 하나를 람다의 인자로 넘기려고 쓰는 C++20의 표준 도구이고, `[&]<class T>(...)`처럼 템플릿 인자 목록을 가진 람다도 C++20에서 들어온 문법이에요. 분기는 호출당 한 번이고, 그 안의 루프와 LAPACK 호출은 모두 타입이 정해진 코드예요.

bool과 int64 입력을 float64로 바꾸는 변환은 따로 패스를 돌지 않고 패킹 안에서 해요. 실수 입력을 complex 계산에 쓸 때도 마찬가지예요.

## 호출 하나의 몸체: `solve`

실제 함수가 위의 틀을 어떻게 쓰는지 `solve`로 보면 이래요.

```cpp
// ops/lu.cpp의 solve, 줄임
nb::object solve(nb::handle ao, nb::handle bo) {
    Input a(ao, "solve", "a");
    Input y(bo, "solve", "b");
    require_square(a);
    const lint n = a.shape(-1);
    const Rhs r = rhs_of(y, n, "solve", "a");                  // b가 벡터인지 행렬 묶음인지
    const lint k = r.k;
    Batch b({{a.batch_shape(2), a.batch_strides(2)},
             {y.batch_shape(r.core), y.batch_strides(r.core)}}, "solve");
    const bool complex = computes_complex(a.dtype()) || computes_complex(y.dtype());
    return with_type(complex, [&]<class T>(std::type_identity<T>) -> nb::object {
        Out out = r.vec ? alloc_vectors(b.shape(), n, dtype_of<T>())
                        : alloc_matrices(b.shape(), n, k, dtype_of<T>());
        T* res = out.as<T>();
        const Failure f = run_batch(b, cost(kLU, double(n) * n),
            [&](std::int64_t i, const std::int64_t* off, Scratch& s) {
                T* lu; lint* ipiv;
                if (const int code = lu_factor<T>(a, off[0], n, s, lu, ipiv)) return code;  // pack + getrf
                LapackSlot<T> xs(res + i * n * k, n * k, s, Scratch::kAlign0);
                T* x = xs.get();
                if (!pack(y.dtype(), y.data() + off[1], n, k, r.rs, r.cs, x, n, true))
                    return kNonFiniteB;                                                    // b에 NaN·inf
                if (n > 0 && k > 0) lapack::getrs('N', n, k, lu, n, ipiv, x, n);
                return 0;
            }, lu_task_cap(n, k, true));
        if (f) raise(b, f, "solve", "a");
        return to_array(out);
    });
}
```

줄마다 하는 일이에요.

- `run_batch(batch, 원소 하나의 추정 비용, 몸체, 태스크 수 상한)`: 배치 원소마다 몸체를 불러요. 몸체는 원소 번호 `i`, 인자별 바이트 오프셋 `off`, 작업 메모리 `Scratch`를 받고, 성공이면 0, 실패면 양수 코드를 돌려줘요.
- `lu_factor`: `a`의 행렬 하나를 작업 메모리에 패킹하고 `getrf`로 분해해요. NaN·inf가 있으면 `kNonFinite`, 정확한 0 피벗이 나오면 `kSingular`를 돌려줘요.
- `LapackSlot`: 결과 배열에서 이 원소의 자리를 LAPACK에 넘길 수 있는 포인터로 바꿔요. 자리가 16바이트 경계에 있지 않으면 정렬된 작업 메모리를 대신 내주고, 끝날 때 자리로 복사해요.
- `pack(b → x)`: 우변을 **결과 자리에 바로** 복사해요. `getrs`가 우변을 해로 덮어쓰므로, 따로 옮길 것이 없어요.
- `raise`: 실패 코드와 배치 인덱스로 예외를 만들어요.

몸체 안에서는 Python 객체를 만지지 않아요. 배치의 추정 시간이 10µs 이상이면 몸체는 스레드 수와 상관없이 GIL 없이 돌기 때문이에요. 나눌 때는 스레드풀의 워커에서, 나누지 않을 때는 호출 스레드에서 돌아요([스레드풀과 결정성](/internals/core/threads/#gil)). 결과 배열과 namedtuple은 모두 `run_batch` 밖에서 만들어요.

## LAPACK을 감싸는 방법

### LAPACK과 BLAS가 행렬을 받는 방식

LAPACK은 Fortran으로 정의된 라이브러리이고, 그 아래에서 행렬곱·삼각 풀기 같은 기본 연산을 맡는 BLAS(Basic Linear Algebra Subprograms)를 불러요. 두 라이브러리의 인터페이스에는 감싸는 쪽이 따라야 하는 관례가 있어요 [1].

- **행렬은 열 우선(column-major)이에요.** $m \times n$ 행렬의 원소 $(i, j)$는 포인터 `a`에서 `a[i + j·lda]`에 있어요. `lda`(leading dimension)는 한 열의 시작과 다음 열의 시작 사이의 원소 수이고 $m$ 이상이에요.
- **입력을 덮어써요.** 분해 루틴은 결과를 입력 자리에 써요. `getrf`는 A를 L과 U로, `getrs`는 우변 B를 해 X로 바꿔 놓아요.
- **루틴 이름의 첫 글자가 타입이에요.** `d`는 실수 double, `z`는 복소수 double이에요. `dgetrf`와 `zgetrf`는 같은 알고리즘의 두 판이에요. 대칭 행렬 루틴은 실수판이 `sy`(symmetric), 복소수판이 `he`(Hermitian)로 이름도 달라요(`dsyevd`, `zheevd`). 직교 행렬을 만드는 루틴도 실수판 `or`(orthogonal), 복소수판 `un`(unitary)으로 갈려요(`dorgqr`, `zungqr`).
- **상태는 `info`로 돌려줘요.** 0이면 성공, 음수 $-k$이면 $k$번째 인자가 잘못됐다는 뜻, 양수는 루틴마다 뜻이 다른 수치적 실패예요(0 피벗의 위치, 수렴하지 않은 고유값의 수 등).
- **작업 메모리를 받는 루틴이 있어요.** `work` 배열과 그 길이 `lwork`를 넘겨요. `lwork = -1`로 부르면 계산하지 않고 가장 알맞은 크기만 알려 줘요(workspace query).

### 루틴 하나에 템플릿 하나

`csrc/linalg/lapack.hpp`는 쓰는 루틴마다 얇은 템플릿 함수를 하나씩 둬요. 타입 인자 `T`가 `double`이면 `d*`를, `cplx`이면 `z*`를 불러요.

```cpp
// lapack.hpp
inline lint checked(lint info, const char* routine) {
    if (info < 0) throw std::logic_error(std::string(routine) + ": illegal argument " + std::to_string(-info));
    return info;
}

// 부분 피벗 LU: A = P L U, 제자리. info > 0이면 U(info, info)가 정확히 0.
template <class T>
lint getrf(lint m, lint n, T* a, lint lda, lint* ipiv) {
    lint info = 0;
    if constexpr (std::is_same_v<T, double>) dgetrf_(&m, &n, a, &lda, ipiv, &info);
    else zgetrf_(&m, &n, a, &lda, ipiv, &info);
    return checked(info, "getrf");
}
```

- `if constexpr`는 컴파일할 때 한쪽 가지만 남겨요. 실행 중에는 분기가 없어요.
- Fortran 루틴은 모든 인자를 주소로 받아요. 래퍼가 값으로 받아 주소를 넘기므로, 부르는 쪽은 보통의 C++ 함수처럼 써요.
- 대칭 루틴처럼 실수판과 복소수판의 이름이나 인자 수가 다른 것도 같은 래퍼 안에서 갈라요. `syevd<T>`는 `dsyevd_` 또는 `zheevd_`를 부르고, 복소수판에만 있는 실수 작업 배열 `rwork`를 알아서 마련해요. 함수 몸체는 그 차이를 몰라도 돼요.
- **음수 `info`는 `std::logic_error`예요.** 인자가 잘못됐다는 뜻이므로 사용자 입력의 문제가 아니라 stardust 코드의 버그예요. 양수 `info`는 그대로 돌려주고, 뜻은 부른 함수가 해석해요.

작업 메모리가 필요한 루틴의 래퍼는 `Scratch`를 받아 크기 질의와 할당까지 맡아요.

```cpp
// lapack.hpp의 geqrf, 줄임 (복소수판은 같은 자리에서 zgeqrf_를 불러요)
template <class T>
lint geqrf(lint m, lint n, T* a, lint lda, T* tau, Scratch& s) {
    lint info = 0;
    lint lwork = s.sizes({kGeqrf, m, n, lda, 0, esize<T>()}, [&] {   // 이 Scratch에서 처음일 때만 실행
        lint query = -1;
        T best{};
        if constexpr (std::is_same_v<T, double>) dgeqrf_(&m, &n, a, &lda, tau, &best, &query, &info);
        else zgeqrf_(&m, &n, a, &lda, tau, &best, &query, &info);            // lwork = -1: 크기만 물어요
        return WorkSizes{work_size(best)};
    }).work;
    T* w = s.get<T>(lwork, Scratch::kWork);
    if constexpr (std::is_same_v<T, double>) dgeqrf_(&m, &n, a, &lda, tau, w, &lwork, &info);
    else zgeqrf_(&m, &n, a, &lda, tau, w, &lwork, &info);
    return checked(info, "geqrf");
}
```

배치 안의 행렬은 모두 크기가 같으므로 크기 질의는 `Scratch`마다 첫 행렬에서 한 번만 해요. 열쇠는 (루틴, 크기 인자, 원소 크기)이고, 기억해 둔 크기는 매번 물었을 때와 같은 값이에요. 이 점이 결과 비트에도 중요한데(`gesdd`는 `lwork`에 따라 내부 경로를 골라요), 자세한 이야기는 [배치와 병렬화](/internals/linalg/batch/)에 있어요.

감싼 루틴은 이래요. 무엇을 계산하는지는 아래 "함수와 루틴" 절의 표에 있어요.

| 종류 | 루틴 |
|---|---|
| LU, 삼각 | `getrf`, `getrs`, `trtrs` |
| 대칭 | `potrf`, `potrs`, `sytrf`/`hetrf` |
| QR, 최소제곱 | `geqrf`, `geqp3`, `orgqr`/`ungqr`, `gelsd` |
| 고유값 | `syevd`/`heevd`, `sygvd`/`hegvd`, `sygv`/`hegv`, `geev`, `gees`, `gehrd`, `orghr`/`unghr` |
| 특이값 | `gesdd`, `gesvd` |
| 띠, Sylvester | `gtsv`, `gbsv`, `trsyl3` |
| 노름 추정 | `lacn2` |
| BLAS | `gemm`, `gemv` |

행렬곱이 필요한 함수(`matrix_power`, `expm`, `solve_sylvester`, `pinv`)는 `sd.matmul`을 거치지 않고 `cblas_dgemm`/`cblas_zgemm`을 바로 불러요. 곱할 행렬이 이미 C++ 안의 작업 버퍼에 열 우선으로 놓여 있어서, 배열 객체로 감쌌다 푸는 단계가 필요 없어요.

### 64비트 정수 인터페이스

Accelerate는 옛 LAPACK 인터페이스와 새 인터페이스를 함께 제공하고, 새 인터페이스는 정수 인자가 32비트인 판과 64비트인 판으로 나뉘어요. stardust는 새 인터페이스의 64비트판(ILP64)을 써요. 컴파일 정의 `ACCELERATE_NEW_LAPACK`, `ACCELERATE_LAPACK_ILP64`가 그것을 고르고(`CMakeLists.txt`) [2], 정수 인자(차원, `lda`, 피벗 인덱스, `info`)는 모두 64비트가 돼요.

```cpp
// types.hpp
using lint = __LAPACK_int;   // Accelerate 헤더가 정의하는 LAPACK 정수 타입
static_assert(sizeof(lint) == 8, "ACCELERATE_LAPACK_ILP64 must be defined");
```

이유는 두 가지예요.

- stardust의 모양과 strides는 모두 `int64`예요. LAPACK 정수도 64비트면 경계에서 좁히는 변환과 그 넘침 검사가 필요 없어요. 32비트 인터페이스에서는 행렬의 원소 수나 작업 메모리 크기($O(n^2)$)가 $n \approx 46341$부터 32비트 정수를 넘어요($46341^2 > 2^{31} - 1$).
- 배열 영역의 `matmul`이 같은 Accelerate의 BLAS를 같은 설정으로 써요. 한 확장 모듈 안에서 두 인터페이스를 섞지 않아요.

`static_assert`는 컴파일 정의가 빠진 채 빌드되는 일을 막아요. 정의가 빠지면 `__LAPACK_int`가 32비트가 되고, 64비트인 모양 값이 LAPACK에 넘어가는 자리에서 조용히 잘려요. 그런 빌드는 아예 만들어지지 않아요.

## 설계 규칙 세 가지

### 함수마다 루틴은 하나

LAPACK에는 같은 문제를 푸는 루틴(드라이버)이 여럿 있는 경우가 많아요. 대칭 고유값만 해도 `syev`(QR 반복), `syevd`(분할 정복), `syevr`(MRRR), `syevx`(이분법)가 있어요. scipy는 이것을 `driver=` 옵션으로 사용자에게 열어 둬요.

stardust에는 `driver=` 옵션이 없고, 입력 값을 보고 루틴을 고르지도 않아요. 함수마다 하나를 정해 두었어요. 고르는 기준은 속도와 정확도를 잰 결과예요. 예를 들어 Apple M4 Pro에서 1000×1000 float64 행렬 하나로 드라이버끼리 비교하면 이래요.

| 문제 | 고른 루틴 | 시간 | 다른 루틴 |
|---|---|---:|---|
| `eigh` (고유값과 고유벡터) | `syevd` | 49ms | `syevr` 91ms, `syev` 474ms |
| `eigh(a, b)` | `sygvd` | 57ms | `sygv` 474ms |
| `svd` | `gesdd` | 64ms | `gesvd` 681ms |

하나로 정하는 이유는 일관성이에요. 루틴이 다르면 계산 순서가 달라서 결과의 마지막 비트가 달라져요. 옵션이나 입력 값에 따라 루틴이 바뀌면 같은 함수가 비슷한 입력에 비트가 다른 답을 내고, 테스트로 고정할 대상도 몇 배로 늘어요. 사용자가 고를 일이 생기면 그 선택이 맞는지 판단할 근거(행렬의 조건, 크기에 따른 성능)까지 사용자가 알아야 해요.

"값만 구하는 함수"와 "벡터까지 구하는 함수"는 서로 다른 함수예요(`eigvalsh`와 `eigh`, `svdvals`와 `svd`). 그래서 둘이 다른 루틴을 써도 이 규칙에 맞아요. 실제로 `svd`는 `gesdd`를, `svdvals`는 `gesvd`의 값 전용 모드를 써요. 값만 구할 때는 `gesvd`가 `gesdd`의 값 전용 모드보다 작은 행렬에서 25%, 큰 행렬에서 5% 빨라요. 일반화 문제도 같아요. `eigh(a, b)`는 `sygvd`, `eigvalsh(a, b)`는 `sygv`의 값 전용 모드(1000×1000에서 36ms, `sygvd`의 값 전용 모드는 74ms)예요.

겉보기 예외가 둘 있는데, 둘 다 입력 **값**으로 고르는 것이 아니에요.

- `solve_banded`는 대역폭이 (1, 1)이면 `gbsv` 대신 `gtsv`로 풀어요. 대역폭은 행렬의 값이 아니라 사용자가 준 옵션이에요. 그 결과 `solve_banded(..., lower_bandwidth=1, upper_bandwidth=1)`은 `solve_tridiagonal`과 비트까지 같아요([띠 행렬과 Sylvester 방정식](/internals/linalg/special/)).
- `expm`은 입력이 대각이거나 삼각이면 그 구조를 써요. 이것은 루틴 선택이 아니라 알고리즘의 한 단계이고, 결과의 뜻($e^{A}$)은 그대로예요([행렬 지수](/internals/linalg/expm/)).

### 구조는 함수 이름으로 골라요

행렬이 대칭 양정치이면 LU보다 Cholesky가 빠르고, 삼각이면 분해가 필요 없어요. scipy의 `solve(a, b, assume_a=None)`은 행렬을 훑어보고 구조를 자동으로 판별해요.

stardust의 `solve`는 **언제나 LU**예요. 구조를 쓰고 싶으면 그 구조의 함수를 불러요.

| 행렬의 구조 | 함수 |
|---|---|
| 일반 | `solve` |
| 삼각 | `solve_triangular` |
| 대칭 양정치 | `cholesky` 다음 `cholesky_solve` |
| 삼중대각, 띠 | `solve_tridiagonal`, `solve_banded` |
| 같은 행렬로 여러 번 | `lu` 다음 `lu_solve` |

자동 판별을 하지 않는 이유는 세 가지예요.

- 판별은 값에 달려 있어요. 반올림 오차 하나로 대칭이 깨진 행렬은 다른 경로로 가서 비트가 다른 답을 받아요. 배치에서는 원소마다 경로가 갈릴 수 있어요.
- 판별 자체가 $O(n^2)$의 추가 패스예요. 구조가 없는 흔한 경우에 모두가 그 비용을 내요.
- 함수 이름에 구조가 적혀 있으면 코드를 읽는 사람이 어떤 가정이 깔려 있는지 알아요.

### 크기에 따라 경로를 바꾸지 않아요

"작은 n에서는 A가 빠르고 큰 n에서는 B가 빠르다"는 측정이 나와도, 결과 비트가 달라지는 전환은 하지 않아요. 전환점을 두면 같은 함수의 결과가 크기에 따라 서로 다른 계산에서 나오게 돼요.

대표적인 예가 `inv`예요. `inv`는 `getrf`로 분해한 뒤 단위행렬을 우변으로 `getrs`를 불러요. LAPACK에는 역행렬 전용 루틴 `getri`가 있고, $n \ge 256$에서는 `getri`가 더 빨라요($n = 2048$에서 1.56배). 그래도 모든 크기에서 `getrs`를 써요. 덕분에 `inv(a)`가 `solve(a, I)`와 모든 크기에서 비트까지 같아요([LU 분해와 선형 시스템](/internals/linalg/lu/)).

**결과를 바꾸지 않는** 선택은 크기로 정해요. 배치를 스레드에 나눌지, 큰 행렬의 패킹을 풀에서 할지, 입력을 복사하지 않고 그 자리에서 읽을지가 그래요. 이것들은 같은 산술을 다른 순서나 다른 스레드에서 할 뿐이고, 켜든 끄든 결과 바이트가 같다는 것을 테스트가 확인해요.

## 함수와 루틴

함수마다 부르는 LAPACK 루틴과, 그 루틴이 수학적으로 하는 일을 한 줄로 적었어요. 알고리즘의 단계, 비용, 안정성, 대안 루틴과의 비교는 마지막 열의 글에 있어요. 설명은 LAPACK 참조 구현(netlib, `Reference-LAPACK`)의 소스와 문서가 정의하는 동작을 기준으로 해요 [1][5]. Accelerate는 같은 인터페이스를 구현하지만 내부(블록 크기, 커널)는 공개돼 있지 않아서, 같은 단계를 다른 블록 크기나 커널로 할 수 있어요. 분해 알고리즘의 일반적인 설명은 [3]이 좋아요.

기호: $P$는 순열(행이나 열의 자리바꿈), $L$은 아래 삼각, $U$와 $R$은 위 삼각, $Q$·$Z$·$V$는 직교(복소수면 유니터리) 행렬, $A^{H}$는 켤레 전치(실수면 그냥 전치)예요.

### 선형 시스템과 LU

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `solve` | `getrf` + `getrs` | 열마다 절댓값이 가장 큰 원소를 피벗으로 행을 바꿔 가며 $A = PLU$로 분해하고, 삼각 시스템 두 개를 차례로 풀어 $AX = B$ | [LU](/internals/linalg/lu/) |
| `inv` | `getrf` + `getrs` | 우변을 단위행렬로 둔 `solve`: $AX = I$의 해가 $A^{-1}$ | [LU](/internals/linalg/lu/) |
| `det`, `slogdet` | `getrf` | $\det A = \pm \prod_i u_{ii}$. 부호는 행 교환 횟수로 정하고, 곱은 stardust가 계산 | [LU](/internals/linalg/lu/) |
| `lu` | `getrf` | $A = PLU$를 $L$, $U$, `perm`으로 풀어 돌려줌(직사각 행렬도 됨) | [LU](/internals/linalg/lu/) |
| `lu_solve` | `trtrs` 두 번 | `b`의 행을 `perm`으로 모은 뒤 $LY = B$(대각 1), $UX = Y$를 대입으로 풂 | [LU](/internals/linalg/lu/) |
| `solve_triangular` | `trtrs` | 삼각 시스템 $TX = B$를 위에서부터(아래 삼각) 또는 아래에서부터(위 삼각) 대입으로 풂 | [LU](/internals/linalg/lu/) |
| `cond` (2, −2 외의 `ord`) | `getrf` + `getrs` | $\lVert A\rVert \cdot \lVert A^{-1}\rVert$. 역행렬은 `inv`와 같은 경로 | [LU](/internals/linalg/lu/) |
| `matrix_power` (음수 지수) | `getrf` + `getrs`, `gemm` | `inv`와 같은 경로로 $A^{-1}$을 구한 뒤 이진 거듭제곱 | [기본 연산](/internals/linalg/basic/) |

### 대칭 행렬

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `cholesky` | `potrf` | 대칭(에르미트) 양정치 행렬을 피벗 없이 $A = LL^{H}$로 분해. 대각에 양수가 아닌 값이 나오면 양정치가 아님 | [대칭 분해](/internals/linalg/symmetric/) |
| `cholesky_solve` | `potrs` | $LY = B$, $L^{H}X = Y$를 차례로 풂 | [대칭 분해](/internals/linalg/symmetric/) |
| `ldl` | `sytrf`/`hetrf` | 양정치가 아닐 수 있는 대칭(에르미트) 행렬을 행과 열을 같이 바꾸는 Bunch–Kaufman 피벗으로 $PAP^{H} = LDL^{H}$로 분해. $D$는 1×1과 2×2 블록 | [대칭 분해](/internals/linalg/symmetric/) |

### QR과 최소제곱

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `qr` | `geqrf` + `orgqr`/`ungqr` | Householder 반사로 열마다 대각 아래를 0으로 만들어 $A = QR$로 분해하고(`geqrf`), 반사들을 곱해 $Q$를 행렬로 만듦(`orgqr`) | [QR](/internals/linalg/qr/) |
| `qr_pivoted` | `geqp3` + `orgqr`/`ungqr` | 남은 열 중 노름이 가장 큰 열을 앞으로 옮겨 가며 $AP = QR$. $\lvert r_{ii}\rvert$가 줄어드는 순서라 랭크가 드러남 | [QR](/internals/linalg/qr/) |
| `lstsq` | `gelsd` | 이중대각으로 줄이고 분할 정복 SVD로 $\lVert Ax - b\rVert_2$를 최소로 하는 해 중 노름이 가장 작은 해를 구함. 랭크가 부족해도 됨 | [QR](/internals/linalg/qr/) |

### 고유값

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `eigh` | `syevd`/`heevd` | Householder로 삼중대각 $T$로 줄이고(`sytrd`), 분할 정복(`stedc`)으로 $T$를 분해한 뒤 되돌려 $A = V\Lambda V^{H}$ | [고유값](/internals/linalg/eigen/) |
| `eigvalsh` | `syevd`/`heevd` (값만) | 삼중대각으로 줄인 뒤 제곱근 없는 QR 반복(`sterf`)으로 고유값만 구함 | [고유값](/internals/linalg/eigen/) |
| `eigh(a, b)` | `sygvd`/`hegvd` | $Av = \lambda Bv$. $B = LL^{H}$로 $L^{-1}AL^{-H}$의 보통 문제로 바꿔(`sygst`) `syevd`처럼 풀고 $L^{-H}$로 되돌림 | [고유값](/internals/linalg/eigen/) |
| `eigvalsh(a, b)` | `sygv`/`hegv` (값만) | 같은 변환 뒤 `syev`로 고유값만 구함 | [고유값](/internals/linalg/eigen/) |
| `eig`, `eigvals` | `geev` | 균형 조정(`gebal`) → Hessenberg로 축소(`gehrd`) → shift QR 반복으로 Schur 형식(`hseqr`) → 삼각 행렬에서 고유벡터(`trevc3`) → 되돌림 | [고유값](/internals/linalg/eigen/) |
| `schur` | `gees` | 같은 축소와 QR 반복으로 $A = ZTZ^{H}$. $T$는 위 삼각(실수 입력이면 2×2 블록이 섞인 준삼각) | [고유값](/internals/linalg/eigen/) |
| `hessenberg` | `gehrd` + `orghr`/`unghr` | Householder 반사로 $A = QHQ^{H}$. $H$는 대각 바로 아래 한 줄까지만 0이 아닌 행렬 | [고유값](/internals/linalg/eigen/) |

### 특이값

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `svd` | `gesdd` | Householder로 이중대각 $B$로 줄이고(`gebrd`), 분할 정복(`bdsdc`)으로 $B$를 분해한 뒤 되돌려 $A = U\Sigma V^{H}$ | [SVD](/internals/linalg/svd/) |
| `pinv` | `gesdd`, `gemm` | 허용오차보다 큰 특이값만 뒤집어 $A^{+} = V\Sigma^{+}U^{H}$ | [SVD](/internals/linalg/svd/) |
| `svdvals` | `gesvd` (값만) | 이중대각으로 줄인 뒤 dqds 알고리즘(`bdsqr`가 부르는 `lasq1`)으로 특이값만 구함 | [SVD](/internals/linalg/svd/) |
| `matrix_rank` | `gesvd` (값만) | 가장 큰 특이값의 `rtol`배보다 큰 특이값의 개수 | [SVD](/internals/linalg/svd/) |
| `cond` (2, −2) | `gesvd` (값만) | $\sigma_{\max}/\sigma_{\min}$과 그 역수 | [SVD](/internals/linalg/svd/) |
| `matrix_norm` (2, −2, nuc) | `gesvd` (값만) | $\sigma_{\max}$, $\sigma_{\min}$, $\sum_i \sigma_i$ | [SVD](/internals/linalg/svd/) |

### 특수 구조와 행렬 함수

| 함수 | 루틴 | 루틴이 하는 일 | 글 |
|---|---|---|---|
| `solve_tridiagonal` | `gtsv` | 삼중대각 시스템을 부분 피벗 가우스 소거로 $O(n)$에 풂 | [띠와 Sylvester](/internals/linalg/special/) |
| `solve_banded` | `gbsv` (대역폭 (1, 1)이면 `gtsv`) | 띠 저장 형식 안에서 부분 피벗 LU로 분해하고 풂. 피벗 때문에 위쪽 띠가 kl만큼 넓어짐 | [띠와 Sylvester](/internals/linalg/special/) |
| `solve_sylvester` | `gees` 두 번 + `trsyl3` + `gemm` 네 번 | $AX + XB = C$. $A$, $B$를 Schur 형식으로 바꾸면 계수가 삼각인 방정식이 되고, `trsyl3`가 블록 단위 대입으로 풂 | [띠와 Sylvester](/internals/linalg/special/) |
| `expm` | `gemm`, `gemv`, `getrf` + `getrs`, `lacn2` | 스케일링과 제곱, Padé 유리 근사. `lacn2`는 행렬-벡터 곱만으로 1-노름을 추정 | [행렬 지수](/internals/linalg/expm/) |

### LAPACK을 부르지 않는 함수

`vecdot`, `outer`, `trace`, `diagonal`, `kron`, `cross`, `vector_norm`, `matrix_norm`(fro, ±1, ±inf), `matrix_power`(0 이상의 지수, BLAS `gemm`만 써요)는 직접 짠 루프예요. [LAPACK 없이 계산하는 함수](/internals/linalg/basic/)에서 다뤄요.

## Accelerate에 대해 알아 둔 사실

Accelerate의 내부는 공개돼 있지 않아요. 그래서 설계가 기대는 성질은 Apple M4 Pro(성능 코어 10개, 효율 코어 4개)에서 잰 결과예요. 다섯 가지예요.

**내부 스레드를 쓰는 것은 `getrf`의 큰 행렬뿐이에요.** 루틴이 쓴 CPU 시간을 경과 시간으로 나눈 값(1이면 코어 하나, 2면 평균 두 개)을 재면 이래요.

| 루틴 | n | CPU 시간 / 경과 시간 |
|---|:---:|:---:|
| `getrf` | 768 | 2.19 |
| `getrf` | 1024 | 2.98 |
| `gesv`, `potrf`, `geqrf`, `syevd`, `gesdd`, `geev` | 1024 이하 | 1.11 이하 |

배치가 아닌 큰 행렬 하나의 분해는 대부분 코어 하나에서 돌아요. numpy와 scipy도 같은 Accelerate를 부르므로 똑같아요. 이 사실에서 두 가지가 나와요. 큰 행렬의 배치도 stardust의 풀에 나눠요(Accelerate가 알아서 코어를 쓰리라고 기대할 수 없어요). 그리고 큰 행렬 하나의 분해는 numpy와 속도가 거의 같아요.

**여러 스레드에서 동시에 불러도 결과가 같아요.** `getrf`, `gesv`, `potrf`, `geqrf`, `syevd`, `gesdd`, `geev`를 n = 8, 64, 256에서 10스레드로 동시에 불렀을 때, 모든 스레드의 결과가 호출 스레드 혼자 계산한 결과와 비트까지 같았어요. 배치를 풀에 나눠도 결과가 바뀌지 않는다는 보장의 바탕이에요.

**Accelerate의 스레드 수는 결과를 바꾸지 않아요.** n = 64, 512, 1024에서 Accelerate를 1스레드로 고정한 결과와 기본 설정의 결과가 비트까지 같았어요. 내부 스레드를 쓰는 `getrf` n = 1024도 그래요. 다만 stardust는 Accelerate의 스레드 설정(`BLASSetThreading`)을 건드리지 않아요. 프로세스 전체에 걸리는 설정이라 배열 영역의 `matmul`과, 같은 프로세스의 numpy까지 바뀌기 때문이에요.

**배열이 16바이트 경계에 놓였는지에 따라 반올림이 달라져요.** 같은 행렬이라도 시작 주소가 16의 배수인지 아닌지에 따라 `schur`, `svd`, `eigh`의 결과가 마지막 비트에서 달라질 수 있어요. 그래서 LAPACK과 BLAS에 넘기는 모든 배열을 16바이트에 맞춰요([패킹과 결과 레이아웃](/internals/linalg/packing/)).

**작은 호출 일부는 코어들이 함께 쓰는 행렬 연산 장치(AMX)에서 차례로 돌아요.** n = 32–40 근처의 `getrf`와, 우변이 8개 이상인 n = 24–40의 삼각 풀기는 스레드를 늘려도 빨라지지 않고, 몇 개를 넘으면 느려져요. 이 경로에는 태스크 수 상한을 둬요([배치와 병렬화](/internals/linalg/batch/)).

## 실패를 알리는 방법

사용자가 보는 규칙은 [실패와 에러](/api/linalg/errors/)에 있어요. 여기서는 그 규칙이 왜 그렇고 어떻게 구현되는지를 봐요.

### 세 종류의 에러

| 원인 | 예외 | 언제 |
|---|---|---|
| 인자의 타입, 모양, 옵션 값 | `TypeError`, `ValueError` | 계산 전 |
| 입력에 NaN이나 inf | `ValueError` | 배치 원소를 패킹할 때 |
| 수치적 실패 (특이, 양정치 아님, 수렴 실패) | `LinAlgError` | LAPACK이 양수 `info`를 돌려줄 때, 또는 stardust의 대각 검사 |

`LinAlgError`는 `ValueError`의 하위 클래스예요. "값이 이 계산에 맞지 않는다"는 점에서 `ValueError`이고, `except ValueError`로도 잡혀요. traceback의 마지막 줄은 클래스의 `__module__`과 이름으로 만들어지므로, `_errors.py`가 `__module__`을 공개 경로로 바꿔 둔 덕분에 `stardust.linalg.LinAlgError`로 보여요.

```python
>>> x = sd.asarray([[1.0, 2.0], [2.0, 4.0]])
>>> sd.linalg.inv(x)
Traceback (most recent call last):
    ...
stardust.linalg.LinAlgError: inv(): singular matrix
>>> issubclass(sd.linalg.LinAlgError, ValueError)
True
>>> sd.linalg.LinAlgError.__module__
'stardust.linalg'
```

메시지는 다섯 가지예요: `singular matrix`, `matrix is not positive definite`, `eigenvalue algorithm did not converge`, `SVD did not converge`, 그리고 `solve_sylvester`의 `a and -b have a common or close eigenvalue`예요.

### 특이는 "정확한 0"만

`solve`와 `inv`가 특이 행렬이라고 판정하는 것은 **LAPACK이 정확히 0인 피벗을 보고할 때**(`getrf`의 `info > 0`)뿐이에요. 조건수를 추정해서 "거의 특이하다"고 판정하지 않아요.

"거의"의 기준은 문제마다 달라요. 조건수가 $10^{12}$인 행렬의 해는 유효숫자 네 자리쯤이 남는데, 그것으로 충분한 계산도 있고 아닌 계산도 있어요. 라이브러리가 문턱을 정하면 그 문턱 근처에서 입력의 작은 변화가 "답"과 "에러"를 가르게 돼요. 정확한 0은 그런 모호함이 없고, 0으로 나누는 것은 어떤 기준으로도 계산할 수 없어요. 해가 얼마나 믿을 만한지는 `cond`로 사용자가 판단해요.

삼각 인수를 받아 푸는 함수(`solve_triangular`, `cholesky_solve`, `lu_solve`)는 LAPACK을 부르기 **전에** 대각을 직접 훑어 정확한 0을 찾아요(`pack.hpp`의 `zero_on_diagonal`, $O(n)$). 이유는 루틴마다 달라요. `potrs`는 대각을 검사하지 않고 그대로 나누므로, 대각에 0이 있으면 에러 없이 inf나 NaN이 나와요. `trtrs`는 대각의 0을 `info`로 알려 주지만, 그때는 이미 우변을 패킹한 뒤라서 `b`의 NaN을 먼저 보고하게 돼요. 미리 훑으면 세 함수가 모두 "행렬의 특이 → `b`의 NaN" 순서를 지켜요(뒤의 "에러를 고르는 순서").

특이 행렬에서도 답이 정의되는 함수는 에러를 내지 않아요.

```python
>>> sd.linalg.det(x)
0.0
>>> sd.linalg.slogdet(x)
SlogdetResult(sign=0.0, logabsdet=-inf)
>>> sd.linalg.cond(x, ord=1)
inf
>>> sd.linalg.cond(x)
2.7556760105735884e+16
```

`lu`와 `ldl`은 특이 행렬도 분해해요(분해는 존재하고, 특이성은 $U$의 대각이나 $D$의 블록에 드러나요). `cond`는 그 경로가 정확한 특이를 만나면 inf(`ord=-2`는 그 역수인 0)예요. 위 예에서 `ord=1`은 `getrf`가 정확한 0 피벗을 만나 inf이고, 기본값 `ord=2`는 SVD의 가장 작은 특이값이 반올림 때문에 정확히 0이 아니어서 큰 유한값이에요. "특이"를 각 경로의 정확한 0으로만 정하는 같은 규칙의 결과예요.

### 유한성 검사

**LAPACK을 부르는 호출은 언제나 입력의 NaN과 inf를 검사해요.** 있으면 `ValueError`예요.

```python
>>> sd.linalg.det(sd.asarray([[1.0, float("nan")], [2.0, 4.0]]))
Traceback (most recent call last):
    ...
ValueError: det(): 'x' contains NaN or infinity
```

LAPACK은 유한하지 않은 입력에서 결과를 보장하지 않아요. 직접 계산(LU 등)은 NaN이 번져 나오는 정도지만, 반복 알고리즘(`eig`, `svd`)은 의미 없는 값을 내거나 수렴 실패를 보고할 수 있어요. 검사하지 않으면 같은 NaN 입력에 어떤 함수는 NaN을, 어떤 함수는 `LinAlgError`를, 어떤 함수는 그럴듯한 숫자를 내요. 검사를 켜고 끄는 옵션(scipy의 `check_finite=`)은 두지 않아요. 검사의 비용은 $O(n^2)$로 $O(n^3)$ 계산에 비해 작고, 패킹과 같은 패스에서 하므로 메모리를 한 번 더 읽지도 않아요.

세부 규칙이 세 가지 있어요.

- **LAPACK을 쓰지 않는 함수는 NaN을 그대로 전파해요.** `vecdot`, `outer`, `trace`, `diagonal`, `kron`, `cross`, `vector_norm`, `matrix_norm`(fro, ±1, ±inf)은 원소별 연산처럼 NaN이 들어가면 NaN이 나와요.
- **규칙은 함수가 아니라 호출 단위예요.** `matrix_power(x, n)`은 $n \ge 0$이면 BLAS 곱만 하므로 전파하고, $n$이 음수이면 역행렬을 `getrf`로 구하므로 검사해요. `matrix_norm`은 `ord`가 2, −2, `'nuc'`일 때만 SVD를 부르므로 그때만 검사해요.
- **읽는 원소만 검사해요.** 대칭 입력을 받는 함수(`cholesky`, `eigh`, `eigvalsh`, `ldl`)는 아래 삼각만 읽으므로 위 삼각에 무엇이 있든 상관없어요. `solve_triangular`는 지정한 삼각만, `solve_banded`는 띠 저장 형식에서 행렬 안에 해당하는 원소만 봐요.

```python
>>> sd.linalg.cholesky(sd.asarray([[4.0, float("nan")], [2.0, 3.0]]))   # 위 삼각은 읽지 않아요
array([[               2.0,                0.0],
       [               1.0, 1.4142135623730951]], dtype=float64)
```

### 에러를 고르는 순서

한 호출에서 여러 가지가 동시에 잘못될 수 있어요. 어떤 에러가 나올지는 정해져 있어요.

- **배치 원소 하나 안에서는 인자 순서대로 봐요.** 각 행렬의 특이 판정은 그 행렬의 유한성 검사 바로 뒤에 와요. `solve`는 `a`의 NaN → `a`가 특이 → `b`의 NaN 순서예요. `lu_solve`는 `l`의 NaN → `u`의 NaN → `u`가 특이 → `perm`이 순열이 아님 → `b`의 NaN이에요.
- **배치 전체에서는 가장 작은 인덱스의 에러 하나만 보고해요.** 그 에러가 `ValueError`인지 `LinAlgError`인지는 따지지 않아요.
- **배치 중 하나라도 실패하면 호출 전체가 실패해요.** 일부만 계산된 결과는 돌려주지 않아요.

```python
>>> good = [[1.0, 0.0], [0.0, 1.0]]
>>> bad = [[1.0, 2.0], [2.0, 4.0]]
>>> sd.linalg.inv(sd.asarray([good, bad, bad]))
Traceback (most recent call last):
    ...
stardust.linalg.LinAlgError: inv(): singular matrix (at batch index (1,))
```

순서를 고정하는 이유는 결정성이에요. 배치가 스레드에 나뉘어 돌면 어느 원소의 실패가 먼저 발견될지는 그때그때 달라요. "먼저 발견된 것"을 보고하면 같은 입력에 실행마다 다른 메시지가 나와요. "가장 작은 인덱스"는 스레드 수와 무관하게 하나로 정해져요.

### 구현: 실패 코드와 `raise`

배치 몸체는 예외를 던지지 않고 정수 코드를 돌려줘요. 몸체는 풀의 워커에서 돌 수 있고, 여러 워커가 동시에 실패할 수 있어서, 예외 대신 "인덱스와 코드"를 모은 뒤 호출 스레드에서 하나를 골라 던지는 쪽이 단순해요. 워커 스레드에서 C++ 예외를 던지면 그것을 호출 스레드로 옮겨 다시 던지는 장치가 따로 필요하고, 여러 예외 중 무엇을 고를지도 정해야 해요.

```cpp
// ops/common.hpp
constexpr int kNonFinite = 1;          // 첫 행렬 인자에 NaN 또는 inf
constexpr int kSingular = 2;           // 정확한 0 피벗, 삼각 인수의 대각에 0
constexpr int kNonFiniteB = 3;         // 우변에 NaN 또는 inf
constexpr int kNotPD = 4;              // 양정치가 아님
constexpr int kNoConvergence = 7;      // SVD가 수렴하지 않음
constexpr int kNoConvergenceEig = 8;   // 고유값 알고리즘이 수렴하지 않음
// ... (모두 11개)

[[noreturn]] void raise(const Batch& b, const Failure& f, const char* func, const char* arg,
                        const char* arg2 = nullptr, const char* arg3 = nullptr);
```

`run_batch`는 `Failure` 값(가장 작은 실패 인덱스와 그 코드)을 돌려주고, `raise`가 코드를 예외 종류와 메시지로 바꿔요. `arg`, `arg2`, `arg3`는 NaN이 든 인자의 이름을 메시지에 넣으려고 받아요. 메시지는 `함수이름(): 내용` 형식이고, 배치 축이 있으면 끝에 ` (at batch index (1, 2))`를 붙여요. 배치 축이 없는 호출에는 붙이지 않아요.

수치적 실패는 C++ 예외 `sd::linalg::LinAlgError`(`std::runtime_error`의 하위)로 던지고, nanobind에 등록한 변환기(`errors.cpp`의 `register_error_translator`)가 Python의 `LinAlgError`로 바꿔요. Python 예외 타입은 `_setup`이 넘겨준 그 클래스예요.

### 빈 행렬과 크기 0인 배치

- 배치 크기가 0이면 빈 결과예요. 에러가 아니에요. `inv(sd.ones((0, 3, 3)))`의 모양은 `(0, 3, 3)`이에요.
- 0×0 행렬은 수학의 관례를 따라요. `det`은 1(빈 곱), `slogdet`은 (1, 0), 노름은 0(빈 합)이에요.
- 값이 정의되지 않는 `cond`만 빈 행렬에서 `ValueError`예요.

함수 몸체는 $n = 0$이거나 우변이 0개이면 LAPACK을 부르지 않고 지나가요(위 `solve` 코드의 `if (n > 0 && k > 0)`). 빈 문제에는 할 계산이 없고, LAPACK 루틴 가운데는 크기 0을 받지 않는 것이 있어요. 예를 들어 `gelsd` 안의 `lalsd`는 우변 0개를 받으면 잘못된 인자로 보고 표준 에러 출력에 경고를 써요. 그래서 `lstsq`는 우변이 0개일 때 0으로 채운 열 하나를 넣고 결과는 버려요.

## 결과 만들기

### 배열, 스칼라, namedtuple

결과의 형태는 세 가지예요.

- **행렬 묶음** `(..., M, N)`: 행렬마다 열 우선으로 놓인 새 배열이에요(`outblock.cpp`의 `alloc_matrices`). LAPACK이 결과를 쓴 그 메모리를 그대로 돌려줘요. C 순서로 되돌리는 복사가 없어요. 이유와 영향은 [패킹과 결과 레이아웃](/internals/linalg/packing/)에 있어요.
- **벡터 묶음과 그 밖의 값**: 고유값, 특이값, `perm`, 배치마다의 `det`이나 노름은 보통의 C 순서 배열이에요(`alloc_vectors`, `alloc_c`).
- **0차원이면 Python 스칼라**: 배치가 없는 `det`, `trace`, `vector_norm`, `lstsq`의 `rank` 같은 값이에요. stardust에는 0차원 배열이 없어요. 이때는 배열을 만들지 않고 `float`, `complex`, `int`를 바로 만들어요.

결과 배열의 메모리는 배열 영역의 `Buffer`예요. 128바이트로 정렬돼 있고, 쓸 수 있으며, 자기 메모리를 가진 배열이에요(`base`가 `None`).

값을 여러 개 돌려주는 함수는 namedtuple을 돌려줘요.

| 함수 | 타입 | 필드 |
|---|---|---|
| `slogdet` | `SlogdetResult` | `sign`, `logabsdet` |
| `lu` | `LUResult` | `L`, `U`, `perm` |
| `qr` | `QRResult` | `Q`, `R` |
| `qr_pivoted` | `QRPivotedResult` | `Q`, `R`, `perm` |
| `lstsq` | `LstsqResult` | `solution`, `rank`, `singular_values` |
| `eigh` | `EighResult` | `eigenvalues`, `eigenvectors` |
| `svd` | `SVDResult` | `U`, `S`, `Vh` |
| `eig` | `EigResult` | `eigenvalues`, `eigenvectors` |
| `schur` | `SchurResult` | `T`, `Z` |
| `hessenberg` | `HessenbergResult` | `H`, `Q` |
| `ldl` | `LDLResult` | `L`, `D`, `perm` |

필드 이름은 Array API 표준 [4]에 그 함수가 있으면 표준의 이름을 따르고, 없으면 행렬을 대문자 한 글자로 써요. 순열은 언제나 int64 인덱스 벡터 `perm`이고 튜플의 마지막에 와요.

namedtuple은 C++가 채워요. 필드 배열을 모두 만든 뒤, 캐시해 둔 타입 객체를 vectorcall(인자를 C 배열로 넘기는 CPython의 빠른 호출 규약)로 불러요.

```cpp
// pyrefs.cpp
nb::object make_result(Result r, std::initializer_list<nb::handle> fields) {
    std::vector<PyObject*> args;
    for (nb::handle f : fields) args.push_back(f.ptr());
    PyObject* o = PyObject_Vectorcall(refs().results[static_cast<int>(r)], args.data(), args.size(), nullptr);
    if (!o) throw nb::python_error();
    return nb::steal(o);
}
```

필드 2개짜리 namedtuple 하나를 만드는 데 77ns가 걸려요.

### 결과 형태는 옵션으로 바뀌지 않아요

scipy에는 옵션에 따라 돌려주는 값의 개수가 바뀌는 함수가 있어요(`eigh(eigvals_only=)`, `svd(compute_uv=)`, `hessenberg(calc_q=)`, `qr(mode='r')`). stardust는 그런 경우 함수를 나눠요. `eigh`와 `eigvalsh`, `svd`와 `svdvals`, `qr`와 `qr_pivoted`가 따로 있고, `schur`는 언제나 $Z$를, `hessenberg`는 언제나 $Q$를 함께 계산해요.

함수의 반환 타입이 인자 값에 달려 있지 않으면, 호출하는 코드를 읽는 것만으로 결과가 무엇인지 알 수 있어요. 대가는 $Q$가 필요 없는 `hessenberg` 호출도 $Q$를 만드는 비용을 낸다는 것이에요.

## 호출 비용

작은 행렬에서는 LAPACK의 계산보다 그 앞뒤의 고정비가 시간을 정해요. 3×3 행렬의 LAPACK 계산은 0.1µs 안팎이지만, 인자를 읽고 결과 배열을 만드는 데도 비슷하거나 더 긴 시간이 들어요. 결과를 바꾸지 않으면서 고정비를 줄이는 장치들이에요.

| 장치 | 줄이는 것 | 자세히 |
|---|---|---|
| Python 래퍼 없음 | 호출마다 1–2µs | 이 글의 "Python과 C++의 분담" |
| `NDArray`를 직접 받고 직접 만듦 | 버퍼 프로토콜 왕복, 결과를 배열로 감싸는 호출 | [Python과 C++의 경계](/internals/core/python-boundary/) |
| 출력 자리에 바로 패킹 | 작업 버퍼 하나와 복사 한 번 | [패킹과 결과 레이아웃](/internals/linalg/packing/) |
| workspace 크기를 `Scratch`마다 한 번만 질의 | 행렬마다의 `lwork = -1` 호출 | [배치와 병렬화](/internals/linalg/batch/) |
| 작업 메모리를 0으로 채우지 않음 | 큰 행렬에서 패킹만큼 드는 초기화 | [배치와 병렬화](/internals/linalg/batch/) |
| 짧은 합에는 아무것도 할당하지 않음 | 출력마다의 힙 할당 | [LAPACK 없이 계산하는 함수](/internals/linalg/basic/) |
| 큰 행렬 전용 코드는 함수 밖으로 | 작은 호출의 분기와 코드 크기 | [패킹과 결과 레이아웃](/internals/linalg/packing/) |

남는 고정비의 대부분은 결과 객체예요. `NDArray`와 그 Python 객체를 만드는 데 약 75ns가 들어요. 그래서 스칼라를 돌려주는 함수가 가장 가벼워요. 아래 표의 값은 numpy 시간을 stardust 시간으로 나눈 배율이에요(1보다 크면 stardust가 빨라요).

| 호출 (행렬 하나, 3×3) | numpy 대비 (10스레드) |
|---|:---:|
| `trace` | ⟦BENCH trace (3,3) t10⟧ |
| `det` | ⟦BENCH det (3,3) t10⟧ |
| `diagonal` | ⟦BENCH diagonal (3,3) t10⟧ |
| `solve` | ⟦BENCH solve (3,3) t10⟧ |
| `inv` | ⟦BENCH inv (3,3) t10⟧ |

## 성능

numpy 2.5.4와 scipy 1.18.1도 Accelerate의 LAPACK을 불러요. 같은 루틴이 같은 기계에서 도니, 차이는 LAPACK 바깥에서 나와요. 크기와 모양에 따라 세 가지 양상으로 갈려요.

- **작은 행렬 하나**: 계산이 0.1µs 안팎이라 호출 경로의 고정비가 시간을 정해요. 위 "호출 비용"의 장치들이 그대로 차이가 돼요.
- **행렬 묶음(배치)**: numpy와 scipy는 배치를 코어 하나에서 차례로 돌아요. stardust는 배치 원소를 스레드풀에 나눠요. scipy의 일부 함수(`schur`, `hessenberg`, `ldl`, `expm` 등)는 배치를 Python 수준에서 하나씩 돌기 때문에 차이가 더 커요. 1스레드에서도 호출 비용이 원소마다 줄어든 만큼 빨라요.
- **큰 행렬 하나**: 시간의 거의 전부가 LAPACK 안이고, 그 LAPACK이 같아요. 그래서 차이가 작아요. 예외는 stardust가 numpy·scipy와 다른 루틴을 고른 함수예요. `solve`는 `getrf` + `getrs`인데, Accelerate의 `gesv`는 스레드를 쓰는 `getrf` 경로를 타지 않아서 $n = 1024$에서 `gesv` 9.0ms, `getrf` 4.8ms예요. `solve_sylvester`는 블록 루틴 `trsyl3`를 써서 `trsyl`보다 $n = 1000$에서 4.8배 빨라요.

| 호출 | numpy 대비 (10스레드) | numpy 대비 (1스레드) |
|---|:---:|:---:|
| `solve` (3, 3) | ⟦BENCH solve (3,3) t10⟧ | ⟦BENCH solve (3,3) t1⟧ |
| `solve` (1000, 3, 3) | ⟦BENCH solve (1000,3,3) t10⟧ | ⟦BENCH solve (1000,3,3) t1⟧ |
| `solve` (100, 32, 32) | ⟦BENCH solve (100,32,32) t10⟧ | ⟦BENCH solve (100,32,32) t1⟧ |
| `solve` (1000, 1000) | ⟦BENCH solve (1000,1000) t10⟧ | ⟦BENCH solve (1000,1000) t1⟧ |
| `eigh` (3, 3) | ⟦BENCH eigh (3,3) t10⟧ | ⟦BENCH eigh (3,3) t1⟧ |
| `eigh` (1000, 3, 3) | ⟦BENCH eigh (1000,3,3) t10⟧ | ⟦BENCH eigh (1000,3,3) t1⟧ |
| `eigh` (1000, 1000) | ⟦BENCH eigh (1000,1000) t10⟧ | ⟦BENCH eigh (1000,1000) t1⟧ |

함수와 모양 전체의 수치, 느린 경우와 그 이유는 [성능과 정확도](/internals/linalg/performance/)에 있어요.

복잡도는 루틴이 정해요. 밀집 행렬의 분해는 모두 $O(n^3)$ 시간이고(LU는 약 $\tfrac{2}{3}n^3$ flop, Cholesky는 약 $\tfrac{1}{3}n^3$ flop [3]), stardust가 더하는 패킹과 유한성 검사는 $O(n^2)$이에요. 공간은 입력의 작업용 복사본 하나($n^2$)와 결과, 그리고 루틴이 요구하는 workspace예요. 루틴마다의 flop 수는 각 알고리즘 글에 있어요.

## 정확도

수치적 정확도(역오차, 잔차)는 LAPACK 루틴의 성질이고, 각 알고리즘 글이 다뤄요. 이 영역이 구조로 보장하는 것은 **재현성**이에요.

**같은 입력은 언제나 같은 비트를 내요.** 세 가지에 대해 불변이에요.

| 무엇이 바뀌어도 | 결과가 같은 이유 |
|---|---|
| 입력의 메모리 배치 (C 순서, F 순서, 건너뛴 뷰, 뒤집은 뷰, 브로드캐스트) | 패킹이 모든 배치를 같은 열 우선 버퍼로 만들어요 |
| 배치 안의 위치 | LAPACK에 넘기는 배열을 모두 16바이트에 맞춰요 |
| 스레드 수 | 배치 원소 하나는 어느 스레드에서 돌든 같은 계산이고, Accelerate의 결과가 호출 스레드와 무관해요 |

numpy·scipy와의 관계는 함수마다 달라요. 같은 루틴을 같은 방식으로 부르는 함수는 비트까지 같고, 다른 루틴을 고른 함수는 반올림 수준에서 달라요. numpy가 부르는 루틴은 numpy 소스의 `umath_linalg.cpp`에서 볼 수 있어요 [6].

| 함수 | numpy·scipy와의 관계 |
|---|---|
| `eigh`, `qr`, `lstsq` | numpy 2.5.4와 비트까지 같아요 (같은 루틴, 같은 호출) |
| `outer`, `kron`, `cross`, 모든 부동소수점 합(`vecdot`, `trace`, 노름) | numpy와 비트까지 같아요 (같은 곱셈 식, 같은 pairwise 합 순서) |
| `ldl`, `solve_tridiagonal`, `solve_banded` | scipy 1.18.1과 비트까지 같아요 |
| `solve` | numpy와 반올림 수준에서 달라요 (numpy는 `gesv`, stardust는 `getrf` + `getrs`) |
| `svd` | 특이값은 같고 $U$, $V^{H}$가 다를 수 있어요 (`gesdd`가 workspace 크기에 따라 내부 경로를 고르는데, 크기를 정하는 방법이 서로 달라요) |
| `eigvalsh`, `svdvals` | 같은 함수의 `eigh`, `svd`가 주는 값과 $10^{-15}$ 수준에서 달라요 (값 전용 모드는 다른 알고리즘이에요. numpy도 같아요) |
| `expm` | scipy와 달라요 (같은 알고리즘을 직접 짰고, BLAS 호출 순서와 노름 계산이 달라요) |

stardust의 함수끼리 비트까지 같은 관계도 있어요. 함수마다 경로를 하나로 정해 두고, 같은 계산은 같은 코드(`lu_factor`, `lu_inverse`, `gtsv`)를 거치게 해서 생기는 관계예요.

- `inv(a)`와 `solve(a, I)`
- `matrix_power(x, -1)`과 `inv(x)`
- `lu_solve(*lu(a), b)`와 `solve(a, b)` (계산 타입이 같을 때)
- `cholesky(x, upper=True)`와 `cholesky(x)`의 켤레 전치
- `solve_banded(ab, b, lower_bandwidth=1, upper_bandwidth=1)`과 `solve_tridiagonal`

이 관계와 불변성은 모두 `tests/linalg/`의 테스트가 바이트 비교로 확인해요. 검증 방법은 [성능과 정확도](/internals/linalg/performance/)에 있어요.
