## 한눈에 보기

stardust는 numpy, 선형대수(scipy.linalg 계열), 데이터프레임(pandas 계열), 특수함수(scipy.special), 확률분포와 기술통계(scipy.stats 계열), 난수(numpy.random 계열), 회귀분석(statsmodels 계열), 최적화(scipy.optimize 계열)를 C++20으로 다시 만든 Python 라이브러리예요. 사용자는 `import stardust as sd` 하나로 여덟 영역을 써요.

| 영역 | Python 이름공간 | C++ 디렉터리 | 하는 일 |
|:---:|:---:|:---:|---|
| 배열 | `sd` | `csrc/array/` | N차원 배열, 원소별 연산, 집계, 인덱싱, 정렬, 행렬곱 |
| 선형대수 | `sd.linalg` | `csrc/linalg/` | LAPACK 기반 분해와 풀이, 노름, 배치 처리 |
| 데이터프레임 | `sd.frame` | `csrc/frame/` | Column, 결측(NA), groupby, merge, CSV |
| 특수함수 | `sd.special` | `csrc/special/` | 감마, 오차함수, Bessel 등 scipy.special의 함수 |
| 통계 | `sd.stats` | `csrc/stats/` | 단변량 확률분포 31개(연속 21개, 이산 10개. 정규, t, 감마, 베타, 극값, 비중심 분포, 이항, 포아송 …)의 밀도, 누적분포, 분위수, 모멘트, 표본. 다변량 분포 4개와 행렬 분포 3개. 기술통계(`describe`, `skew`, `rankdata` …) |
| 난수 | `sd.random` | `csrc/random/` | 계수기형 생성기(Philox), 균등 실수, 범위 정수, `choice`, `permutation` |
| 회귀 | `sd.regression` | `csrc/regression/` | 선형(OLS, WLS, GLS), 일반화 선형(GLM), 정규화(ridge, lasso, elastic net), 강건(RLM, Theil–Sen, Siegel), 분위, 비선형(NLS) 회귀와 그 추론 |
| 최적화 | `sd.optimize` | `csrc/optimize/` | 스칼라 근과 최솟값(원소마다 푸는 배치 포함), 다변수 최소화(Nelder–Mead, BFGS, L-BFGS-B, Newton-CG, 신뢰 영역), 비선형·선형 최소제곱, 방정식계의 근, 수치 미분 |

여덟 영역이 엮이는 방식은 네 가지로 요약돼요.

1. **확장 모듈은 `stardust._core` 하나예요.** 영역은 그 안의 하위 모듈(`_core.linalg`, `_core.frame`, `_core.special`, `_core.stats`, `_core.random`, `_core.regression`, `_core.optimize`)이에요. 그래서 스레드풀, dtype 객체, 배열 타입이 프로세스 안에 하나씩만 있고, 어느 영역의 C++ 코드든 배열을 C++ 객체 그대로 주고받아요.
2. **Python은 얇고 C++은 두꺼워요.** 배열 타입 자체, 연산자, 인자 해석, 브로드캐스팅, dtype 결정까지 C++이 해요. Python에는 재노출, 출력 형식(`repr`), 결과 namedtuple처럼 자주 불리지 않는 부분만 남아요. 예외는 객체가 상태를 지녀야 하는 곳이에요. 데이터프레임의 `Series`와 `DataFrame`, 통계의 분포 클래스, 난수의 `Generator`, 회귀의 결과 객체(`OLSResult` …), 최적화의 결과 객체(`OptimizeResult`)는 Python 클래스예요.
3. **의존은 아래로만 흘러요.** 위 층은 아래 층을 쓰고, 아래 층은 위 층을 몰라요. 새 영역은 디렉터리 하나와 Python 하위 모듈 하나로 붙고, 기존 영역을 고치지 않아요.
4. **대상 기계는 Apple M4 Pro 한 대예요.** `-mcpu=native`로 빌드하고, 런타임 CPU 디스패치가 없고, 병렬화 기준값과 버퍼 크기 같은 상수는 모두 이 기계에서 잰 값이에요.

## 층 구조

### Python 패키지 (`src/stardust/`)

Python 코드는 전부 합쳐 약 15,400줄이에요. 그중 회귀가 약 5,700줄, 데이터프레임이 약 3,200줄, 최적화가 약 2,700줄, 통계가 약 2,400줄, 난수가 약 550줄이에요. 배열·선형대수·특수함수 쪽 Python은 거의 재노출뿐이에요.

| 파일 | 하는 일 |
|---|---|
| `__init__.py` | `_core`의 배열 함수와 dtype 객체 약 160개를 재노출하고, 상수 `e`, `pi`, `inf`, `nan`, `newaxis`를 정의해요. 끝에서 `linalg`, `frame`, `special`, `random`, `stats`, `regression`, `optimize` 하위 패키지를 import해요 |
| `_format.py` | 배열의 `repr`/`str` (75줄). C++이 넘긴 요약 값을 문자열로 배치해요 |
| `_results.py` | 결과 namedtuple 전부 (`UniqueAllResult`, `SVDResult`, `AiryResult`, `TheilslopesResult`, `DescribeResult`, `CdfResult` …) |
| `_summary.py` | 회귀·최적화 결과의 `summary()`가 함께 쓰는 상자 그리기. 머리, 표, 수의 형식, 배치의 표([summary의 상자](/internals/regression/overview/#summary의-상자)) |
| `linalg/__init__.py` | `_core.linalg`의 함수를 `globals().update(...)`로 옮겨 오고, `LinAlgError`와 결과 namedtuple을 C++에 한 번 넘겨요(`_core._setup`) |
| `linalg/_errors.py` | `class LinAlgError(ValueError)` 정의. `__module__`을 `"stardust.linalg"`로 바꿔 traceback에 공개 경로가 보이게 해요 |
| `special/__init__.py` | `_core.special`의 함수를 재노출만 해요 |
| `stats/*.py` | 분포 클래스와 기술통계 함수. 단변량 분포는 매개변수를 들고 있다가(배열 매개변수는 생성할 때 한 번 복사해 쓰기 금지로 둬요), 메서드가 불리면 `_core.stats`의 원소별 함수(`normal_cdf` 같은 `<분포>_<메서드>`)에 넘겨요. 다변량·행렬 분포는 배치를 펼쳐 `mv_*`, `wishart_*` 같은 커널에, 기술통계는 줄여 갈 축을 맨 뒤로 옮겨 `desc_*` 커널에 넘겨요 |
| `random/__init__.py` | `Generator` 클래스와 `default_rng`. 시드에서 키 만들기, 수열 위치 관리, 인자 검증, `choice`와 `permutation`의 조합 절차 |
| `frame/*.py` | `Series`, `DataFrame`, `Index`, `GroupBy` 클래스, 인자 검증, 정렬(alignment) 절차, `repr`. 공개 이름은 `frame/__init__.py`에만 있고 다른 모듈은 모두 밑줄로 시작해요 |
| `regression/*.py` | 모형 함수(`ols`, `glm`, `lasso` …)와 결과 클래스(`OLSResult` …). 인자 검사, frame 컬럼과 NaN 정책 처리, 커널(`_core.regression`) 한 번 호출, 결과 객체 만들기. 표준오차나 p값 같은 추론 필드는 처음 읽을 때 `sd.stats`의 분포로 계산해요 |
| `optimize/*.py` | 공개 함수(`root_scalar`, `minimize`, `least_squares` …)와 결과 클래스 `OptimizeResult`. 인자와 `options` 검사, 사용자 함수가 돌려준 값의 모양과 형 확인, 커널(`_core.optimize`) 호출, 결과 객체 만들기. 정확한 5점 차분(`_diff.py`)은 Python에 있고 `regression`의 `nls`도 써요 |

`vecdot`은 Array API 표준이 최상위와 `linalg` 양쪽에 두라고 정한 함수예요. 둘은 다른 함수예요. 최상위 `sd.vecdot`은 배열의 함수라서 `matmul`처럼 bool과 int64를 int64로 두고 `sum(conj(x1) * x2)`를 계산해요. `sd.linalg.vecdot`은 선형대수의 규칙대로 int 입력도 float64로 계산해요. float64와 complex128 입력에서는 같은 계산이고 결과의 비트도 같아요.

### 바인딩 층 (`csrc/bind/`)

[nanobind](https://nanobind.readthedocs.io/)는 C++ 함수와 클래스를 Python에 노출하는 라이브러리예요. `bind/`에는 이런 파일이 있어요.

| 파일 | 하는 일 |
|---|---|
| `module.cpp` | `NB_MODULE(_core, m)`. 모듈 하나를 정의하고 영역별 등록 함수를 차례로 불러요 |
| `array_bind.cpp` | `ndarray` 타입: 속성, 연산자, 버퍼 프로토콜 내보내기, 스칼라 변환 금지 |
| `pyutil.{hpp,cpp}` | dtype 객체 다섯, 인자 해석(`parse_int`, `parse_axes`, `parse_bool` …), `is_ndarray`/`as_ndarray`, `view_of` |
| `errors.{hpp,cpp}` | 공개 함수 이름을 에러 메시지 앞에 붙이는 `named`, `call_named`, 메시지에 넣을 타입 이름 `py_type_name`(짧은 이름, numpy의 타입은 `numpy.bool`처럼 공개 모듈을 붙여요) |
| `linalg_bind.cpp`, `frame_bind.cpp`, `special_bind.cpp`, `stats_bind.cpp`, `regression_bind.cpp`, `optimize_bind.cpp` | 하위 모듈 `_core.linalg`, `_core.frame`, `_core.special`, `_core.stats`, `_core.regression`, `_core.optimize` |
| `stats_sample.cpp`, `stats_desc.cpp`, `stats_mv.cpp`, `stats_mvcdf.cpp`, `stats_matrix.cpp` | `_core.stats`의 나머지 커널: 분포의 표본, 기술통계, 다변량 분포와 그 누적분포, 행렬 분포 |
| `nary_bind.hpp` | 원소별 연산 정의 하나를 배열의 n항 디스패처에 얹어 Python 함수로 등록해요. special과 stats가 함께 써요 |

`module.cpp`의 등록 순서에는 이유가 있어요.

```cpp
// csrc/bind/module.cpp (줄인 발췌)
NB_MODULE(_core, m) {
    nb::set_leak_warnings(false);
    sd::register_dtypes(m);  // 맨 먼저: 다른 바인딩이 dtype 객체를 쓴다
    sd::bind_ndarray(m);
    sd::bind_creation(m);
    // ... 배열의 나머지 함수들
    m.def("set_num_threads", ...);
    m.def("get_num_threads", &sd::parallel::num_threads);
    sd::bind_linalg(m);   // 배열 다음: 위에서 등록한 배열 객체를 찾아 쓴다
    sd::bind_frame(m);
    sd::bind_special(m);  // 배열 다음, linalg와 같은 이유
    sd::bind_stats(m);    // 배열 다음, special과 같은 이유
    sd::bind_random(m);   // 배열 다음: ndarray를 돌려준다
    sd::bind_regression(m);  // linalg 다음: 배치 드라이버와 결과 블록을 쓴다
    sd::bind_optimize(m);    // 배열 다음: ndarray를 돌려준다
}
```

- dtype 객체(`sd.float64` 등)가 먼저 있어야 `ndarray.dtype` 같은 속성이 그 객체를 돌려줄 수 있어요.
- linalg, special, stats, random, optimize는 배열 타입이 nanobind에 등록된 뒤에야 `NDArray`를 인자로 받고 돌려줄 수 있어요. optimize는 사용자 함수에 넘기는 x도 `sd.ndarray`로 만들어요.
- regression(`sd::bind_regression`)은 linalg 다음이에요. linalg의 배치 드라이버(`run_batch`)와 결과 블록(`outblock`)을 그대로 쓰기 때문이에요. optimize(`sd::bind_optimize`)는 그 뒤, 맨 끝이에요.

배열의 공개 함수 대부분은 `bind/`가 아니라 `array/ops/*.cpp` 안의 `bind_xxx(m)` 함수가 등록해요. 예를 들어 `asarray`, `zeros`는 `array/ops/creation.cpp`의 `bind_creation`이, 원소별 함수는 `array/ops/ufunc.cpp`의 `bind_ufuncs`가 등록해요. 그래서 `array/ops/`는 "C++ 연산"과 "그 연산의 Python 입구"를 함께 담은 층이에요. 반면 `array/kernels/`, `array/iter.*`, `array/ndarray.*`, `array/convert.*`는 `bind/`를 include하지 않아요. 계산 코드는 Python을 모르고, Python 객체를 다루는 곳은 연산의 입구로 한정돼요. 난수도 같은 방식이라, 하위 모듈 `_core.random`은 `random/random.cpp`의 `bind_random`이 등록해요. 회귀는 `bind/regression_bind.cpp`가 하위 모듈을 만들고, 커널은 `regression/*.cpp`마다 있는 `bind_*` 함수가 그 안에 등록해요. 최적화도 같은 방식이에요(`bind/optimize_bind.cpp`와 `optimize/*.cpp`의 `bind_*`).

## 확장 모듈은 `stardust._core` 하나

### 문제

영역마다 확장 모듈을 따로 두면 이런 일이 생겨요.

- **스레드풀이 영역 수만큼 생겨요.** 각 모듈이 자기 풀을 정적으로 링크해요. 여러 영역을 한 프로그램에서 쓰면 상주 워커가 여러 무리 생기고, 서로의 존재를 모르니 코어를 두고 다퉈요. 스레드 수를 맞추려면 나눌 때마다 Python을 거쳐 다른 모듈의 `get_num_threads()`를 불러야 해요.
- **배열을 직접 넘길 수 없어요.** 다른 모듈의 배열은 버퍼 프로토콜(buffer protocol)로 읽고(`PyObject_GetBuffer` + format 문자열 해석), 결과는 자기 메모리 블록에 만든 뒤 배열 모듈의 `asarray`로 감싸서 돌려줘야 해요. 같은 기계, 같은 프로세스 안에서 Python을 한 바퀴 돌아 데이터를 주고받는 거예요.
- **같은 이름의 다른 타입이 생기기 쉬워요.** 영역마다 `sd::Buffer`, `sd::DType`을 따로 정의하면 이름은 같고 내용이 조금 다른 정의가 생겨요. C++에서는 이름이 같은 정의가 둘이면 ODR(One Definition Rule, 하나의 정의 규칙) 위반이라 한 모듈에 그냥 합칠 수 없어요.

### 접근

모든 영역을 확장 모듈 `_core` 하나에 넣고, nanobind의 `def_submodule`로 하위 모듈을 만들어요.

```cpp
// csrc/bind/linalg_bind.cpp (줄인 발췌)
void bind_linalg(nb::module_& core) {
    nb::module_ m = core.def_submodule("linalg", "stardust linalg native core");
    sd::linalg::register_error_translator();
    sd::linalg::bind_setup(m);
    sd::linalg::bind_lu(m);
    // ...
}
```

Python 쪽 하위 패키지는 그 하위 모듈을 가리켜요.

```python
>>> import stardust as sd
>>> sd.linalg._core is sd._core.linalg
True
>>> sd.special._core is sd._core.special
True
>>> type(sd.asarray([1.0])).__module__
'stardust._core'
```

### 얻는 것

- **풀이 하나, 스레드 수 API가 하나예요.** `sd.set_num_threads`, `sd.get_num_threads`만 있고 `sd.frame`에는 따로 없어요. 풀은 `parallel/pool.cpp`의 정적 객체 하나예요.
- **배열을 C++ 객체로 직접 받아요.** nanobind의 타입 등록이 모듈 하나 안에 있으니, linalg나 frame의 C++ 코드도 `is_ndarray(o)`, `as_ndarray(o)`(`bind/pyutil.hpp`)로 Python 객체 안의 `NDArray`를 바로 꺼내요. linalg는 `const NDArray&`를 받고, 결과도 `new_array_strided`로 `NDArray`를 직접 만들어요.
- **경계 비용이 없어요.** linalg를 별도 모듈로 두면 결과 배열 하나에 드는 경계 비용은 항목별로 더해 약 200ns예요(`asarray`로 감싸기 113ns, 블록 할당·해제 82ns, 입력의 `GetBuffer`/`Release` 5ns, `get_num_threads` 7ns). 경계가 있는 판과 없는 판을 같은 자리에서 재면 결과 배열 하나에 약 120ns 차이가 나요. 200ns가 다 줄지 않는 것은 `NDArray`와 그 Python 객체를 만드는 약 75ns가 어느 쪽이든 남기 때문이에요.

### 배열에 Python을 거의 두지 않는 이유

작은 배열에서는 계산이 아니라 호출 경로의 고정 비용이 시간을 정해요. numpy의 연산 하나는 1µs 이하예요. shape 계산, 브로드캐스팅, 인덱싱을 Python으로 짜고 C++은 커널만 맡게 하면 읽기는 쉽지만, Python 로직이 몇 줄만 끼어도 연산 한 번이 수 µs가 돼서 작은 배열에서 numpy보다 몇 배 느려져요.

그래서 배열은 타입부터 C++이에요. nanobind의 함수 호출 경로 자체는 약 10ns로 작고(macOS `sample` 프로파일러로 잰 값), 나머지 비용은 C++ 안에서 줄일 수 있어요. 작은 호출의 비용은 이래요.

| 연산 | sd | numpy |
|---|---:|---:|
| 작은 `a + b` | 179ns | 151ns |
| `x[1, 2]` | 25ns | 33ns |
| `x[1]` | 72ns | 43ns |
| `zeros(3)` | 91ns | 61ns |
| `x.shape` | 19ns | 18ns |
| `len(x)` | 7ns | 7ns |

`a + b`는 numpy보다 약 20% 느리고, `x[1, 2]`는 빨라요. 이 차이의 원인과 비용을 줄이는 방법(고정 크기 배열을 필요한 칸만 복사하기, Buffer 안에 작은 데이터 두기 등)은 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

### 출력 형식만은 Python에

`repr`은 문자열 배치가 대부분이고 자주 불리지 않아요. C++로 쓰면 길고 읽기 어려워서 `_format.py`(75줄)에 둬요. 다만 큰 배열을 Python 객체로 통째로 만들지 않도록, C++의 `ndarray._summary(edge)`가 원소가 1000개를 넘는 배열에서는 축마다 양 끝 3개만 Python 리스트로 넘기고 가운데는 `Ellipsis`로 채워요. 1억 원소짜리 1차원 배열의 `repr`도 Python 객체 몇 개만 만들어요.

### 데이터프레임이 반대인 이유

데이터프레임의 `Series`, `DataFrame`은 Python 클래스예요. 배열과 같은 이유를 들면 C++로 만들어야 할 것 같지만, 그럴 필요가 없어요. 비교 대상인 pandas의 고정비가 훨씬 크기 때문이에요.

- pandas 연산 하나의 고정비는 수 µs예요. Python 층이 수백 ns를 더해도 pandas보다 훨씬 빨라요.
- `merge`처럼 옵션이 많은 API를 C++로 파싱하면 코드가 길고 읽기 어려워요.
- C++ Column과 커널 위에 Python Series를 얹은 구조에서 원소 10개 `s + s`가 256ns, `s.sum()`이 66ns예요. 같은 연산이 pandas에서 9.16µs, 3.28µs, Polars에서 716ns, 80ns예요. Python 층이 더하는 비용은 연산 하나에 30~200ns이고, 원소 100만 개에서는 측정 오차 안이에요.

## 층과 영역 사이의 의존 규칙

### 규칙

- **아래로만 의존해요.** `base/`, `parallel/`은 다른 디렉터리를 include하지 않아요. 영역은 바닥을 쓰고, 바닥은 영역을 몰라요.
- **`array/`는 다른 영역을 몰라요.** `linalg/`, `frame/`, `stats/`, `random/`, `regression/`, `optimize/`를 include하지 않아요. `special/`에서 가져오는 것은 같은 x의 sin과 cos를 한 번에 구하는 작은 헤더 `special/sincos.hpp` 하나예요(표준 헤더 말고는 아무것도 include하지 않아요). complex `expm1`이 special의 함수들과 같은 sincos를 써요.
- **`linalg/`는 `array/`의 `NDArray`를 직접 받아요.** 버퍼 프로토콜을 거치지 않아요. 결과 레이아웃(행렬마다 열 우선, 배치 축은 바깥에 C 순서)은 linalg의 정책이라 linalg가 정하고, 배열은 `new_array_strided(dtype, shape, strides, nbytes)`로 메모리와 플래그만 맡아요.
- **`frame/`은 배열을 한 파일로만 만나요.** Column(1차원, validity 비트맵, 문자열 offsets)과 NDArray(N차원, 임의의 strides, 결측 없음)는 다른 물건이라, Column을 NDArray 위에 올리지 않아요. 둘을 잇는 코드(`to_array`, 배열에서 Series 만들기)는 `frame/interop.cpp` 한 곳에만 있어요. int64 평균처럼 두 영역이 같은 답을 내야 하는 계산은 서로를 부르지 않고 바닥(`base/`)의 같은 정의를 함께 써요. 그 밖에 `array/` 헤더를 include하는 frame 파일은 `frame/ops/elementwise.cpp` 하나예요. float64 거듭제곱에 배열의 커널(`array/kernels/elementwise.hpp`의 `pow_float_run`)을 그대로 써서, Series와 배열의 `**`가 같은 비트를 내게 해요. 이 커널은 포인터와 stride로 도는 루프라서 Column을 NDArray로 바꾸지 않고 그대로 불러요.
- **`special/`은 배열의 원소별 엔진 위에 올라가요.** 특수함수는 `logsumexp`, `softmax` 같은 몇 개를 빼면 모두 원소별 함수라서, 배열의 n항 디스패처(`array/ops/ufunc.hpp`의 `nary`)와 연속 fast path(`array/kernels/elementwise.hpp`), 스칼라 규칙(`array/kernels/scalar_ops.hpp`)을 그대로 써요. 특수함수 때문에 배열 쪽에 일반 n항 디스패처가 있고, 피연산자 상한(`kMaxOperands`)이 5예요.
- **`stats/`는 `special/` 위에 올라가요.** 분포의 메서드는 감마, 불완전 감마·베타, 오차함수 같은 특수함수로 계산하므로, `stats/`의 include는 대부분 `special/`이에요. 메서드 하나하나가 원소별 함수라서 special과 같은 방법(`bind/nary_bind.hpp`)으로 배열의 n항 디스패처에 얹혀요. 그 밖에는 배열의 연속 fast path(`array/kernels/elementwise.hpp`)와 조각 실행기(`array/ops/pieces.hpp`), 표본과 다변량 누적분포의 몬테카를로 점을 만드는 Philox(`random/philox.hpp`), vForce 래퍼를 써요.
- **`random/`은 배열만 써요.** 결과 배열을 만들고 채울 범위를 조각내 풀에 나누는 데에 배열 헤더 둘(`array/convert.hpp`, `array/ops/pieces.hpp`)을 써요. 원소 하나의 값이 키와 수열 위치만으로 정해지므로, 조각을 어떻게 나누든 결과가 같아요.
- **`regression/`은 `linalg/` 위에 올라가요.** 회귀 하나가 배치의 원소 하나라서 linalg의 배치 드라이버와 입력·결과 블록(`linalg/ops/common.hpp`), LAPACK 래퍼(`linalg/lapack.hpp`)를 그대로 써요. double-double 산술은 `special/dd.hpp`, GLM과 정규화 회귀의 링크 함수와 로그우도는 special의 `erf`, `gamma`, `logistic` 헤더에서 가져와요. `rlm`의 후보 부분집합과 기울기 추정의 피벗 표본은 고정 키의 Philox(`random/philox.hpp`)로 뽑아요. `array/`는 직접 include하지 않고 linalg를 거쳐 `NDArray`를 만나요.
- **`optimize/`는 `linalg/`와 배열 타입 위에 올라가요.** 사용자 함수가 Python이라 반복은 C++ 커널이 돌고 함수값은 Python 콜백으로 받아요. 콜백에 넘기는 x는 새 float64 `sd.ndarray`(`array/ndarray.hpp`)이고, 돌려받은 배열은 linalg의 입력 읽기(`linalg/input.hpp`)로 읽어요. QR, Cholesky, SVD, 삼각 풀이는 LAPACK 래퍼(`linalg/lapack.hpp`)를 쓰고, 내적과 행렬·벡터 곱(BLAS)과 선형 최소제곱의 몇 루틴(`gelsd`, `dlarfgp` 등)은 Accelerate를 직접 불러요(`linalg/types.hpp`가 Accelerate 헤더를 가져와요). special, stats, random, regression은 include하지 않아요. 방향은 반대예요. `sd.regression`의 `nls`가 Python 층에서 최적화의 커널(`_core.optimize.lsq_solve`)과 차분(`optimize/_diff.py`)을 불러요. optimize는 regression을 몰라요.
- **새 영역은 디렉터리 하나와 Python 하위 모듈 하나로 붙어요.** 아래 층만 쓰고 기존 영역을 고치지 않아요. 영역마다 `docs/design/`, `docs/api/`의 문서와 `tests/<영역>/`, `bench/<영역>/`이 함께 있어요.

### 영역 사이의 일관성

같은 개념은 어느 영역에서든 같은 이름, 같은 시그니처, 같은 동작이에요. 기준은 Python Array API 관례예요 [6]. 영역 사이에 차이가 남는 것은 두 경우뿐이에요.

- **데이터 모델이 달라요.** 예를 들어 `int // 0`은 배열에서 0이고 데이터프레임에서 NA인데, 배열에는 NA가 없기 때문이에요.
- **그 영역이 따르는 라이브러리의 관례가 달라요.** 바꾸면 그 라이브러리에서 옮겨 온 코드가 조용히 다른 값을 내는 곳이에요.
  - `correction`의 기본값: 배열의 `sd.var`·`sd.std`와 frame의 `var`·`std`는 numpy처럼 `correction=0`이고, `sd.stats`의 `describe`와 `sem`은 scipy.stats처럼 `correction=1`이에요. 뜻(자유도에서 빼는 수)은 같고 기본값만 달라요. 표본 분산은 어디서든 `correction=1`로 적으면 같아요.
  - `rtol`: `sd.linalg`(`matrix_rank`, `pinv`, `lstsq`)와 `sd.regression`에서는 랭크를 정하는 상대 기준이에요. linalg는 가장 큰 특이값에 대고, 회귀는 열마다 그 열의 노름에 대고 재요(`|R_jj| ≤ rtol·‖x_j‖`). 기본값의 식(행과 열 수 가운데 큰 것 × float64의 머신 엡실론)은 같아요. `sd.optimize.root_scalar`에서는 scipy처럼 근의 상대 허용오차이고, 다른 풀이 함수는 같은 뜻에 `xrtol`을 써요.

결과가 뜻하지 않게 바뀌지 않았는지는 골든 출력으로 지켜요. 공개 함수 전부의 결과를 고정된 입력에서 비트까지 기록해 두고(`tests/golden/data/`), 바뀐 코드의 결과를 스레드 수 1, 3, 10에서 그것과 비트까지 비교해요. 자세한 내용은 [테스트 체계](/internals/core/testing/)에 있어요.

### 무엇을 어디에 둘지 정한 사례

**NEON 커널과 vForce 표는 배열에 있어요.** 손으로 짠 NEON 커널(`array/kernels/neon.hpp`)과 "어느 연산이 vForce로 가는가"의 표(`array/kernels/vforce.hpp`)는 둘 다 배열의 연산 정의(`ops::Maximum`, `ops::Exp` …, `array/kernels/scalar_ops.hpp`)를 include해야 해요. 이 둘을 `base/`나 `accelerate/`에 두면 바닥이 위 층을 아는 역방향 의존이 생기므로 배열 쪽에 둬요. `accelerate/vforce.hpp`에는 연산과 무관한 부분만 있어요. 함수 포인터 타입, `vvatan2`를 이항 함수의 한 모양 `f(out, a, b, n)`으로 감싸는 래퍼, strided 입력을 연속 버퍼로 모아 실행하는 실행기가 그것이에요.

**병렬화 기준값은 영역마다 따로예요.** 풀은 하나지만 "얼마나 큰 일부터 나눌까"는 영역의 커널에 따라 잰 값이 달라요. 그래서 풀 헤더에는 기준값이 없고, 각 영역이 자기 이름공간에 둬요.

| 영역 | 기준 | 위치 |
|:---:|---|---|
| array | `sd::kParallelThreshold = 1 << 15`, 태스크 `1 << 12` | `array/parallel_limits.hpp` |
| frame | `sd::frame::kParallelThreshold = 1 << 17`, 청크 `1 << 14`행 | `frame/parallel.hpp` |
| linalg | 비용 모델(연산 수를 ns로 환산) | `linalg/cost.hpp` |
| special | 배열의 기준값에 함수별 비용 가중치(원소 하나가 덧셈 몇 번 분량인지)를 곱해요 | `special/cost.hpp` |
| stats | special의 가중치 방식을 그대로 쓰고, 분포와 메서드마다 이 기계에서 잰 원소당 비용(ns)을 써요 | `stats/engine.hpp`, `stats/cost_table.hpp` |
| random | 배열의 기준값과 태스크 크기를 쓰고, 원소 하나를 일 8로 쳐요(`kWordWork`) | `random/random.cpp` |
| regression | 회귀끼리는 linalg의 배치 드라이버가 비용 모델로 나눠요. 회귀 하나 안의 행 합은 모형마다 기준을 따로 둬요(선형과 정규화는 행×열 65,536 이상, GLM과 `rlm`은 2¹⁶행 이상, `quantreg`는 2¹⁵행 이상) | `regression/*.cpp` |
| optimize | 배치 스칼라는 아직 끝나지 않은 원소가 2¹⁵개 이상이면 원소 2¹³개씩 나눠요(`kBatchParallel`, `kBatchTask`). lmder의 열 피벗 QR은 한 단계의 일이 4×10⁵ 플롭 이상이면 열을 나눠요(`kQrfacParallel`). 그 밖의 반복은 사용자 함수를 부르는 사이의 계산이 작아 나누지 않아요 | `optimize/batch.cpp`, `optimize/lsq.cpp` |

### 실제 include 관계

아래 표는 실제 `#include` 줄을 센 값이에요. 칸의 숫자는 그 디렉터리의 파일이 다른 디렉터리의 헤더를 include하는 줄 수예요.

| 누가 → 무엇을 | base | parallel | accelerate | array | linalg | frame | special | stats | random | regression | optimize | bind |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| base | · | | | | | | | | | | | |
| parallel | | · | | | | | | | | | | |
| accelerate | | | · | | | | | | | | | |
| array | 7 | 14 | 3 | · | | | 1 | | | | | 30 |
| linalg | 3 | 2 | | 3 | · | | | | | | | 15 |
| frame | 6 | 1 | | 2 | | · | | | | | | 2 |
| special | | | 1 | 6 | | | · | | | | | 1 |
| stats | | 1 | 2 | 2 | | | 36 | · | 2 | | | |
| random | | | | 2 | | | | | · | | | 2 |
| regression | | 6 | | | 7 | | 9 | | 2 | · | | 6 |
| optimize | | 2 | | 5 | 15 | | | | | | · | 15 |
| bind | 1 | 2 | | 35 | 17 | 12 | 25 | 42 | 4 | 5 | 5 | · |

읽을 때 알아 둘 점이 일곱 있어요.

- `array`, `linalg`, `special`, `random`, `regression`, `optimize`가 `bind/`를 include하는 것은 연산의 입구(`ops/*.cpp`)가 인자 해석 도구(`bind/pyutil.hpp`)와 에러 이름(`bind/errors.hpp`)을 쓰기 때문이에요. `array/kernels/`에는 `bind/` include가 하나도 없어요.
- `accelerate/`는 위의 어느 디렉터리도 include하지 않아요. LAPACK 래퍼는 linalg의 타입(LAPACK 정수 타입 `lint`, 배치 구조 `linalg/batch.hpp`)에 묶여 있고 linalg와 그 위의 regression, optimize만 쓰므로 `linalg/lapack.hpp`에 둬요. 바닥에 두면 바닥이 영역의 헤더를 include하게 돼요. linalg는 Accelerate 프레임워크 헤더를 직접 include하므로 `accelerate/` 헤더가 필요 없어요.
- linalg의 `array/` 3줄은 `NDArray`를 받고 돌려주는 `linalg/input.hpp`, `linalg/outblock.hpp`와, 결과 namedtuple의 배열 필드를 쓰기 금지로 만드는 `linalg/pyrefs.cpp`예요. float64 → int64 변환 규칙은 `linalg/types.hpp`가 `base/saturate.hpp`에서 직접 가져와요. 배열의 변환 헤더를 거치지 않으므로 linalg의 타입 정의가 배열 내부에 기대지 않아요.
- frame의 `array/` 2줄 중 1줄과 `bind/pyutil.hpp` 1줄은 `interop.cpp`에 있고, 나머지 1줄은 float64 거듭제곱 커널을 쓰는 `ops/elementwise.cpp`예요. `base/` 6줄 가운데 2줄은 int64 평균의 정확한 정수 합(`base/int_sum.hpp`)을 쓰는 Series와 그룹별 평균이에요. 배열의 `mean`과 같은 정의라서, frame은 배열을 부르지 않고도 배열과 같은 비트의 int 평균을 내요. `frame/convert.cpp`는 에러 메시지의 타입 이름(`py_type_name`)만 필요해서 `bind/errors.hpp`를 include해요. 이 헤더는 nanobind 말고는 아무것도 끌어오지 않으므로, 배열 헤더가 frame에 들어오는 곳은 이 두 파일로 남아요.
- stats 행은 대부분 `special/`이에요. 배열의 n항 디스패처에 분포를 얹는 곳과 `NDArray`를 받고 돌려주는 곳은 `bind/stats_*.cpp`와 `bind/nary_bind.hpp`라서, `stats/`의 헤더는 nanobind를 include하지 않아요. `array/` 2줄은 연속 fast path(`array/kernels/elementwise.hpp`)와 조각 실행기(`array/ops/pieces.hpp`)이고, `random/` 2줄은 표본(`sample.hpp`)과 다변량 누적분포(`mvcdf.hpp`)가 쓰는 Philox예요.
- regression 행에는 `array/`가 없어요. 입력과 결과의 `NDArray`는 linalg의 블록(`linalg/ops/common.hpp`)을 거쳐 만나고, `bind/` 6줄은 모두 에러 이름(`bind/errors.hpp`)이에요.
- optimize 행의 `array/` 5줄은 사용자 함수에 넘길 `sd.ndarray`를 만드는 `array/ndarray.hpp`예요. `linalg/` 15줄은 입력 읽기(`input.hpp`) 3줄, LAPACK 래퍼(`lapack.hpp`) 4줄, 정수 타입과 Accelerate 헤더(`types.hpp`) 6줄, SVD가 수렴하지 않을 때 던지는 `LinAlgError`(`errors.hpp`) 2줄이고, `parallel/` 2줄은 배치 스칼라(`batch.cpp`)와 lmder의 QR(`lsq.cpp`)이에요. regression의 `nls`가 optimize를 쓰는 것은 Python 층이라 이 표에 나오지 않아요.

## 결과의 비트: 지키는 것과 따르는 것

numpy, scipy, pandas는 모든 영역의 정답지예요. 다만 정답지와 무엇까지 같아야 하는지는 네 규칙으로 나눠 정해요. 모든 영역이 같은 규칙을 써요.

| 규칙 | 무엇 | 이유 |
|---|---|---|
| 1. stardust가 지키는 비트 | 결과는 스레드 수와 상관없이 비트까지 같아요. 공개 함수의 결과는 저장해 둔 stardust 자신의 출력(골든)과 비트까지 견줘요. 정확도는 Arb(구간 산술)로 만든 참값에 대고 정한 계약으로 재요 | 같은 프로그램이 같은 답을 내는 것은 stardust가 스스로 정하고 지킬 수 있어요. 옳은지는 참값으로 재야 해요. 다른 라이브러리의 반올림과 같다고 옳은 것은 아니에요 |
| 2. 반올림이 아닌 동작은 정답지와 같아요 | dtype 규칙, 정수 연산, 정렬 순서, NaN과 ±0의 규칙, 상태 값의 뜻, 기본값, 멈춤 규칙 | 사용자 코드가 기대어 갈라지는 것들이에요. 결과의 dtype, 고르는 원소, 분기, 반복 수가 다르면 반올림 크기의 차이가 아니라 다른 프로그램이 돼요. 일부러 다르게 정한 곳은 API 문서에 이유와 함께 적어요 |
| 3. 반올림 크기의 결과는 정확도 계약 안이면 돼요 | 마지막 자리는 numpy·scipy와 다를 수 있어요. 최적화는 같은 알고리즘과 같은 멈춤 규칙을 쓰지만, 마지막 자리의 차이 때문에 반복의 경로와 횟수가 조금 달라질 수 있어요 | 마지막 자리까지 같으려면 정답지의 안쪽 계산 순서(합을 묶는 법, 버퍼 크기, 커널의 FMA)를 그대로 따라야 해요. 그 순서는 정답지가 약속한 것이 아니라 판과 기계마다 바뀌고, 따라 하는 동안은 병렬화, SIMD, 더 정확한 합을 쓸 수 없어요 |
| 4. 지금 비트까지 같은 것은 일부러 깨지 않아요 | 고침이나 최적화가 필요로 할 때만 깨요. 정답지와 비트까지 견주는 테스트는 통과하는 동안 그대로 두고, 의도한 고침이나 최적화 때문에만 깨지면 허용오차와 반복 수의 비교로 바꿔요 | 비트가 같으면 따로 비용이 들지 않는 가장 강한 검사예요. 이유 없이 버리지 않지만, 그 검사가 고침과 개선을 막지도 않아요 |

3번 규칙으로 쓰는 계산은 이런 것들이에요. 모두 계약 안이고, 결과는 여전히 데이터 크기로만 정해져서 스레드 수와 상관없어요.

- int64의 `mean`은 정수로 정확히 더한 뒤 한 번 반올림해요(`base/int_sum.hpp`). numpy는 원소마다 float64로 바꿔 더해요. 합이 $2^{53}$을 넘지 않으면 지금 numpy와 비트도 같아요.
- float 합은 numpy와 같은 pairwise 알고리즘에 누산기를 넓힌 잎을 써요(아래 "pairwise 합").
- 다항식 계산(Horner)과 complex 절댓값은 FMA로 반올림을 하나 줄여요. 같은 x의 sin·cos는 `sd::sincos`로 함께 구해요(아래 "컴파일 플래그와 그 이유").

그래서 어떤 결과가 numpy·scipy와 비트까지 같다면 그것은 지금 그렇다는 사실이고, 약속은 아니에요. 약속은 스레드 수와 상관없이 같은 비트, 골든 기록과 같은 비트, 그리고 정확도 계약이에요. Accelerate(BLAS·LAPACK)를 부르는 계산은 Accelerate의 스레드 모드가 같을 때 비트까지 같아요. 이 모드는 stardust가 정하지도 바꾸지도 않아요([스레드풀과 결정성](/internals/core/threads/)).

## 공통 부품

여기 있는 부품은 배열만의 것이 아니에요. 모든 영역이 이 정의를 함께 써요.

### dtype (`base/dtype.hpp`)

```cpp
// csrc/base/dtype.hpp (줄인 발췌)
enum class DType : std::uint8_t { Bool, Int64, Float64, Complex128, String };

inline constexpr int kNumArrayDTypes = 4;   // 배열은 앞의 넷
constexpr bool is_array_dtype(DType d) { return static_cast<int>(d) < kNumArrayDTypes; }

// 배열 dtype의 승격: 더 큰 쪽
constexpr DType promote(DType a, DType b) { return a > b ? a : b; }
```

- **값의 순서가 곧 승격 순서예요.** 배열의 승격은 일직선 `bool < int64 < float64 < complex128`이라서, 두 dtype의 공통 dtype은 enum 값의 최댓값 하나로 계산돼요. 표를 찾아볼 필요가 없어요.
- **`String`은 데이터프레임 전용이에요.** 크기가 고정되지 않아(offsets + UTF-8 바이트) 승격에 끼지 않아요. 배열은 앞의 넷(`is_array_dtype`), Column은 `Complex128`을 뺀 넷을 받아요. 영역이 받지 않는 dtype을 주면 TypeError예요(`sd.zeros(3, dtype=sd.string)`).
- **저장 타입**은 `bool`, `int64_t`, `double`, `std::complex<double>`이에요. `dtype_of<T>`는 C++ 타입에서 DType을 얻는 컴파일 시점 상수인데, `if constexpr` 사슬을 즉시 호출한 람다로 계산해요. 지원하지 않는 타입을 넣으면 `static_assert(!sizeof(T))`가 컴파일을 막아요.

런타임 dtype을 컴파일 시점 타입으로 바꾸는 것이 `visit_dtype`이에요. 템플릿 함수 본문 하나가 dtype마다 한 번씩 인스턴스화되고, 실행 중에는 `switch` 하나로 골라져요.

```cpp
// csrc/base/dtype.hpp (줄인 발췌)
template <typename F>
decltype(auto) visit_dtype(DType d, F&& f) {
    switch (d) {
        case DType::Bool:       return f(std::type_identity<bool>{});
        case DType::Int64:      return f(std::type_identity<std::int64_t>{});
        case DType::Float64:    return f(std::type_identity<double>{});
        case DType::Complex128: return f(std::type_identity<complex128>{});
        case DType::String:     break;  // 배열 dtype이 아님
    }
    __builtin_unreachable();
}

// 쓰는 쪽: C++20의 템플릿 람다로 타입을 받아요
visit_dtype(a.dtype, [&]<typename T>(std::type_identity<T>) {
    T* out = reinterpret_cast<T*>(a.data);
    // ... T로 쓰인 루프
});
```

`std::type_identity<T>`는 값이 없는 빈 태그예요. 람다가 `<typename T>`로 그 타입을 받아서, 본문 안에서는 `T`가 실제 타입처럼 쓰여요. `visit_dtype`이 배열 dtype만 받는 것은 의도예요. `String`까지 받으면 모든 커널이 문자열 타입으로도 인스턴스화되어야 해서 컴파일 시간과 바이너리가 커지고, 대부분 뜻이 없는 코드가 돼요. 데이터프레임은 방문자를 따로 두지 않고 dtype마다 `switch`로 골라요.

Python 쪽 dtype 객체는 C++이 모듈을 만들 때 만든 싱글턴 다섯 개예요(`bind/pyutil.cpp`의 `register_dtypes`). 그래서 dtype 비교는 포인터 비교 하나예요. dtype 인자는 이 객체나 그 이름 문자열(`"float64"`)을 받고, Python 타입(`float`), numpy dtype, 다른 이름(`"float32"`)은 TypeError예요. 이 규칙은 배열과 데이터프레임이 같아요.

### Buffer (`base/buffer.hpp`)

Buffer는 참조 카운트로 수명을 관리하는 메모리 블록이에요. 배열의 뷰 여러 개, 또는 데이터프레임의 Column 여러 개가 Buffer 하나를 `std::shared_ptr<Buffer>`로 공유해요.

```cpp
// csrc/base/buffer.hpp (줄인 발췌)
class Buffer {
public:
    static constexpr std::size_t kAlignment = 128;  // M4의 캐시 라인
    static constexpr std::size_t kInline = 256;     // 이하의 데이터는 객체 안에

    static std::shared_ptr<Buffer> allocate(std::int64_t nbytes, bool zeroed);
    static std::shared_ptr<Buffer> adopt(const Py_buffer& view);  // 다른 객체의 메모리

    std::byte* data() const { return data_; }
    std::int64_t size() const { return size_; }

private:
    void* raw_ = nullptr;       // malloc/calloc이 돌려준 포인터 (자기 메모리일 때만)
    std::byte* data_ = nullptr;
    std::int64_t size_ = 0;
    bool external_ = false;
    Py_buffer view_{};
    alignas(kAlignment) std::byte inline_[kInline];
};
```

- **128B 정렬.** 할당의 시작을 캐시 라인(128B)에 맞춰서 SIMD 루프의 첫 load가 두 줄에 걸치지 않게 해요. `aligned_alloc`에는 0으로 채우는 짝(calloc판)이 없어서, 128B를 더 할당한 뒤 시작 주소를 올림해요(`aligned = (addr + 127) & ~127`).
- **`calloc`으로 0 채우기.** `zeros`는 `calloc`을 써요. 큰 할당에서는 OS가 0 페이지를 첫 접근 때 채우므로 `zeros((10000, 10000))`(800MB)은 쓰기 전까지 거의 비용이 없어요. 위의 올림 방식은 이 fast path를 살리려고 고른 거예요.
- **작은 배열은 Buffer 안에.** 256B 이하의 데이터는 Buffer 객체 안의 `inline_` 배열에 둬요. Buffer는 `std::make_shared`로 만들어 참조 카운트(제어 블록)와 한 덩어리로 할당되니, 작은 배열 하나의 할당이 세 번(Buffer, 데이터, 제어 블록)에서 한 번이 돼요. 대가로 모든 Buffer 객체가 256B 커지는데, 큰 배열에서는 무시할 만해요.
- **외부 메모리(`adopt`).** 버퍼 프로토콜로 가져온 numpy 배열의 메모리처럼, 다른 Python 객체가 가진 메모리를 복사 없이 쓸 때예요. `Py_buffer`를 쥐고 있다가 소멸할 때 `PyBuffer_Release`로 돌려줘요. 마지막 소유자가 GIL이 없는 워커 스레드에서 사라질 수도 있어서, 소멸자가 `PyGILState_Ensure`로 GIL을 잡아요.
- **`size()`.** 데이터의 바이트 수예요. 데이터프레임의 Column이 슬라이스 범위를 검사할 때 써요.

`Key`라는 빈 구조체를 생성자 인자로 받는 것은 "패스키" 기법이에요. `make_shared`는 public 생성자가 필요한데, 생성자를 public으로 열면 아무나 Buffer를 만들 수 있어요. `Key`는 Buffer 안에서만 만들 수 있으므로, 생성자는 public이지만 사실상 `allocate`와 `adopt`만 부를 수 있어요.

배열과 데이터프레임은 같은 Buffer를 써요. 데이터프레임의 Copy-on-Write는 `shared_ptr`의 `use_count()`를 보고 "다른 누가 이 메모리를 보고 있나"를 판단하는데, 배열 뷰와 Column이 같은 Buffer를 가리킬 수 있어서(`Series.to_array()`의 읽기 전용 뷰) 이 판단이 영역을 넘어 그대로 동작해요. 배열 뷰가 Buffer 참조를 하나 쥐고 있으면 `use_count()`가 늘어 있으니 frame 쪽 쓰기가 먼저 복사해요.

### pairwise 합 (`base/pairwise.hpp`)

float 합의 비트는 덧셈 순서가 정해요. stardust의 float 합은 numpy의 `DOUBLE_pairwise_sum`(numpy 소스 `numpy/_core/src/umath/loops_utils.h.src`)과 같은 pairwise 알고리즘이고 [1], 잎만 더 넓어요.

- 512개 이하(`kBlock`)의 구간은 독립 누산기 16개(`kLanes`)로 더하고, 누산기는 이웃끼리, 그 쌍끼리 고정된 트리로 합쳐요. 더 긴 구간은 16의 배수 자리에서 반으로 나눠 재귀해요. numpy는 누산기 8개, 구간 128개예요.
- 잎을 넓힌 것은 속도 때문이에요. 덧셈 지연에 묶인 사슬이 16개가 되고 컴파일러가 이것을 NEON 레지스터 8개로 묶어서, 긴 합 하나가 1스레드에서 numpy의 잎보다 1.2–1.6배 빨라요. 대신 마지막 자리는 numpy와 다를 수 있어요. 오차의 크기는 같은 꼴이라 정확도 계약 안이에요.
- 반올림 오차는 $n$이 아니라 $\log n$에 비례해서 자라요. 단순 누적의 오차 한계가 $(n-1)\,u \sum |x_i|$ 수준이라면 pairwise는 대략 $\lceil \log_2 n \rceil\, u \sum |x_i|$ 수준이에요($u = 2^{-53}$) [2].
- 이 정의는 `base/pairwise.hpp` 한 곳에 있어요. 트리 모양, 잎 합, 긴 합을 풀의 태스크로 자르고 다시 모으는 방법까지 정의하고, 영역은 "항을 잎에 어떻게 가져오는가"만 정해요. 배열은 원소를 읽는 접근자로, linalg는 잎마다 채운 버퍼로, frame은 자기 Column 접근으로요.

자세한 내용은 [집계](/internals/array/reductions/)에 있어요.

### 포화 변환 (`base/saturate.hpp`)

float64 → int64의 명시적 변환 규칙은 라이브러리 전체에 하나예요. 0 쪽으로 자르고, 범위 밖은 int64의 최솟값·최댓값으로 포화시키고, NaN은 0이에요. ARM의 `FCVTZS` 명령 하나가 정확히 이 일을 해서, 그 명령을 직접 불러요.

```cpp
// csrc/base/saturate.hpp
inline std::int64_t saturate_to_int64(double x) { return vcvtd_s64_f64(x); }
```

C++의 평범한 `static_cast<int64_t>(x)`는 NaN, inf, 범위 밖 값에서 정의되지 않은 동작(undefined behavior)이에요. 규칙을 분기 세 개로 적으면 정의는 되지만 루프가 벡터화되지 않아요. 이 함수를 쓰면 컴파일러가 루프를 벡터 `FCVTZS`로 바꿔요. 같은 자리에서 재면 분기 세 개 판이 464µs, `FCVTZS` 판이 89µs로 약 5배 차이가 나요. 같은 `astype`이 numpy에서는 243µs예요. 배열의 `astype`, linalg의 int 결과, frame의 `astype`이 모두 이 함수를 써서 세 영역의 결과가 같아요.

### 스레드풀 (`parallel/pool.hpp`)

풀은 하나이고 모든 영역이 같이 써요. 상주 워커, atomic 카운터 하나로 태스크 나눠 갖기, 호출 스레드도 참여하기, 일이 끝난 뒤 100µs spin 후 잠들기, 중첩 금지가 이 풀의 특징이에요. `fork()`한 자식 프로세스는 첫 사용 때 같은 스레드 수로 새 풀을 만들어요. 병렬 호출 한 번의 고정 비용은 약 1.5µs예요. 결과는 스레드 수와 무관하게 비트까지 같아요. 나누는 방식은 데이터 크기로만 정하고, 부분 결과는 정해진 순서로 합치기 때문이에요. 자세한 내용은 [스레드풀과 결정성](/internals/core/threads/)에 있어요.

### 에러 메시지 (`bind/errors.hpp`)

공개 함수가 내는 에러는 그 함수의 이름과 `(): `로 시작해요(`zeros(): negative dimensions are not allowed`). 공통 헬퍼와 커널은 이름 없이 메시지를 쓰고, 공개 함수의 바인딩이 이름을 붙여요. 모든 영역이 같은 형식을 써요(데이터프레임은 Python 층도 포함해요). 호출 모양이 틀린 에러(없는 키워드, 빠진 인자)는 Python으로 쓴 모듈 함수와 생성자가 같은 `f(): ` 꼴로 바꿔 내고(`src/stardust/_calls.py`), 작은 메서드와 C++ 바인딩 함수는 Python과 nanobind의 기본 꼴을 남겨요. 구현은 [Python과 C++의 경계](/internals/core/python-boundary/)에 있어요.

### 결과 namedtuple (`src/stardust/_results.py`)

여러 값을 돌려주는 함수는 namedtuple을 돌려줘요. 이 클래스는 영역과 상관없이 모두 `_results.py` 한 모듈에 있고, 이름은 `<함수>Result`예요(`UniqueAllResult`, `QRResult`, `SVDResult`, `HistogramResult`, `AiryResult` …). 필드 이름은 Array API가 정한 함수면 그 이름을 따라요.

C++에서 namedtuple을 만드는 방법은 영역에 따라 두 가지예요.

| 방식 | 쓰는 곳 | 어떻게 |
|---|---|---|
| 이름으로 찾기 | 배열(`unique_*`, `finfo`, `histogram`), special(`airy`) | 부를 때 `nb::module_::import_("stardust._results").attr("UniqueAllResult")`. `airy`는 처음 한 번 찾아 정적 변수에 둬요 |
| 시작할 때 받기 | linalg | `stardust/linalg/__init__.py`가 import될 때 `_core._setup(LinAlgError, _results.LINALG)`로 클래스 11개를 넘기고, C++이 `PyRefs`에 참조를 쥐어 둬요. 결과는 `PyObject_Vectorcall`로 바로 만들어요 |

linalg는 매 호출에 쓰는 Python 객체를 처음 한 번만 받아 둬요(`linalg/pyrefs`). 쥐고 있는 것은 결과 namedtuple과 `LinAlgError`예요. 배열은 C++ 객체로 직접 주고받으므로 배열 쪽 Python 함수는 쥐고 있지 않아요. `PyRefs`의 참조는 일부러 놓지 않아요. 인터프리터가 끝나는 도중에 놓는 것이 안전하지 않고, 프로세스가 끝나면 OS가 회수하기 때문이에요.

### 결과의 배열은 쓰기 금지

결과 객체와 namedtuple의 배열 필드는 모든 영역에서 쓰기 금지 배열이에요. 회귀와 최적화의 결과 객체, 배열의 `unique_*`, 선형대수의 `QRResult`·`LstsqResult` 등, 통계의 `DescribeResult` 등이 그래요. 분포의 매개변수 속성과 요약값(`mean()`, `covariance()` 등)이 돌려주는 배열도 같아요. 쓰려고 하면 다른 쓰기 금지 배열과 같은 `ValueError`(`assignment destination is read-only`)이고, 고쳐 쓰려면 `.copy()`로 복사해요.

- **읽을 때 복사하지 않아요.** 결과가 가진 메모리를 쓰기 금지 플래그만 세워 보여 줘요. linalg는 결과 namedtuple을 만드는 곳(`linalg/pyrefs.cpp`의 `make_result`)에서, Python으로 쓴 결과 객체는 배열을 넣을 때 플래그를 세워요. 큰 필드(최적화의 `hess_inv`)도 읽는 비용이 없어요.
- **필드가 서로에게서 나와서예요.** 회귀의 `bse`는 `cov_params()`의 대각에서 나와요. 필드를 고칠 수 있으면 한 필드를 고친 뒤에 처음 읽는 다른 필드가 바뀌어서, 같은 결과의 값이 읽는 순서에 따라 달라져요.
- **분포는 배열 매개변수를 생성할 때 한 번 복사해요.** 생성 뒤에 넘긴 배열을 고쳐도 분포는 그대로이고, 매개변수 속성은 그 복사본을 쓰기 금지로 돌려줘요. 속성과 메서드가 서로 다른 값을 보지 않게 하려는 거예요.

### Accelerate 래퍼 (`accelerate/`, `linalg/lapack.hpp`)

Apple의 Accelerate 프레임워크는 BLAS, LAPACK, vForce(배열 단위 초월함수)를 제공해요 [3].

| 파일 | 감싸는 것 | 쓰는 곳 |
|---|---|---|
| `blas.hpp` | `dot`, `gemv`, `gemm`, `syrk`/`herk` (실수판 `d`, 복소수판 `z`) | 배열의 `matmul`, `cov` |
| `linalg/lapack.hpp` | `getrf`, `getrs` 등 LAPACK 루틴. 템플릿 하나가 d(실수)/z(복소수) 판을 골라요. linalg의 타입에 묶여 있어 linalg 안에 둬요 | linalg, regression, optimize |
| `vforce.hpp` | `vvexp`, `vvsin` 등 함수 포인터 타입, 인자 순서 래퍼, strided 실행기 | 배열의 초월함수, special, stats |

컴파일 정의 `ACCELERATE_NEW_LAPACK`, `ACCELERATE_LAPACK_ILP64`를 모듈 전체에 걸어서, 새 LAPACK 인터페이스와 64비트 정수 인자를 써요. 행렬의 차원이 2³¹을 넘어도 정수가 넘치지 않아요.

- nanobind의 CMake 설정 위치는 설치된 nanobind 패키지에 물어서(`python -m nanobind --cmake_dir`) 찾아요. 그래서 빌드 환경의 nanobind 버전과 CMake 쪽이 어긋나지 않아요.
- `NB_STATIC`은 nanobind의 런타임 라이브러리를 `_core`에 정적으로 링크해요(`libnanobind-static.a`). 확장 모듈이 하나뿐이니 nanobind를 공유 라이브러리로 따로 설치할 이유가 없어요.
- Boost.Math 헤더는 `SYSTEM` include로 넣어서 우리 경고 플래그(`-Wall -Wextra -Wpedantic`)가 그 헤더에 걸리지 않게 해요. `BOOST_MATH_STANDALONE`은 다른 Boost 라이브러리 없이 Boost.Math만 쓰는 모드예요.
- 빌드는 경고 없이 끝나요. 경고가 하나도 없어야 새로 생긴 경고가 바로 눈에 띄어요.

### 컴파일 플래그와 그 이유

실제로 우리 소스에 걸리는 플래그는 이래요(빌드 디렉터리의 `build.ninja` 기준).

```text
-O3 -DNDEBUG -std=c++20 -arch arm64 -fPIC -fvisibility=hidden -fno-stack-protector
-mcpu=native -ffp-contract=off -fno-builtin-sin -fno-builtin-cos -Wall -Wextra -Wpedantic
```

앞줄은 CMake(Release의 `-O3 -DNDEBUG`, 모듈의 `-fPIC`)와 nanobind(`-fvisibility=hidden`, `-fno-stack-protector`)가 붙이고, 뒷줄은 우리가 붙여요. 모두 결과의 비트나 속도에 영향을 주므로 함부로 바꾸지 않아요.

| 플래그 | 하는 일 | 이유 |
|---|---|---|
| `NOMINSIZE` | nanobind가 기본으로 붙이는 `-Os`를 빼요 | `-Os`가 명령줄에서 `-O3` 뒤에 와서 이겨요. `-Os`는 루프를 거의 펼치지도 벡터화하지도 않아서, 같은 연속 fast path 코드가 `-O3`보다 약 2배 느려요 |
| `-mcpu=native` | 빌드하는 CPU의 명령어를 모두 써요 | 대상이 이 Mac 하나예요. 이 기계에서 clang은 `apple-m4`로 해석해요(`-###`로 볼 수 있어요) |
| `-ffp-contract=off` | 컴파일러가 `a * b + c`를 FMA 하나로 스스로 합치지 못하게 해요 | 아래 설명 |
| `-fno-builtin-sin`, `-fno-builtin-cos` | 컴파일러가 같은 인자의 `sin`/`cos`를 스스로 합치지 못하게 해요 | 아래 설명 |
| `-ffast-math` 없음 | — | NaN과 inf가 없다고 가정하고, 덧셈 순서를 컴파일러가 바꿀 수 있게 돼요. NaN·inf는 뜻을 지켜야 하고, 순서 재배치는 코드에서 명시적으로 해요(pairwise 합, 블록 리덕션) |
| `ACCELERATE_NEW_LAPACK`, `ACCELERATE_LAPACK_ILP64` | 새 LAPACK 헤더, 64비트 정수 인자 | 위 Accelerate 절 |
| `-Wall -Wextra -Wpedantic` | 경고 | 경고 0을 유지해요 |

링크에는 nanobind 기본값대로 `-Wl,-dead_strip`(쓰지 않는 코드 제거)과 `-Wl,-x -Wl,-S`(지역 심볼과 디버그 정보 제거)가 붙어요. 프로파일러로 디스어셈블할 때는 심볼을 남기는 빌드(`NOSTRIP`)를 따로 만들어요. 링크 시점 최적화(LTO)는 켜지 않아요.

#### `-ffp-contract=off`: FMA는 코드가 정한 곳에서만

FMA(fused multiply-add)는 $a \cdot b + c$를 반올림 한 번으로 계산하는 명령이에요. 따로 계산하면 곱셈 뒤와 덧셈 뒤에 두 번 반올림해요.

$$
\text{따로:}\ \operatorname{fl}\bigl(\operatorname{fl}(a \cdot b) + c\bigr)
\qquad
\text{FMA:}\ \operatorname{fl}(a \cdot b + c)
$$

둘은 다른 값을 낼 수 있어요. $a = 1 + 2^{-30}$, $b = 1 - 2^{-30}$, $c = -1$이면 정확한 $ab$는 $1 - 2^{-60}$이에요. 따로 계산하면 $\operatorname{fl}(ab) = 1$이 되어 결과가 $0$이고, FMA는 $-2^{-60}$을 내요.

clang은 기본으로 소스의 `a * b + c`를 FMA로 바꿀 수 있어요(`-ffp-contract=on`) [5]. 어디서 바꿀지는 인라인 상황에 따라 컴파일러가 정해요. 그러면 같은 식이 부르는 길마다 다른 비트를 낼 수 있어요. 원소별 함수의 `f(x)[i]`와 스칼라 `f(x[i])`, NEON 커널과 그 커널이 따르는 스칼라 정의가 서로 어긋나는 거예요. 그래서 모듈 전체에서 자동 축약을 끄고, FMA는 코드가 정한 곳에만 `std::fma`나 NEON의 `vfmaq`로 적어요. 같은 소스는 어느 길로 불러도 같은 비트를 내요.

FMA를 적는 곳은 이래요.

- **반올림을 하나 줄여 더 정확하고 빠른 곳.** 다항식 계산(`special/common.hpp`의 `horner`는 계수마다 `std::fma(r, x, c[i])`), complex 절댓값(`sqrt(fma(re, re, im * im))`, 최대 1.16 ULP), `var`의 편차 제곱합(`fma(d, d, acc)`), linalg의 `vecdot`과 2-노름의 곱의 합(잎마다 `vfmaq`). 반올림 크기의 결과는 정확도 계약 안이면 되므로, 이런 곳은 numpy·scipy와 마지막 자리가 다를 수 있어요.
- **numpy·scipy의 빌드와 같은 자리.** 이 기계의 numpy 바이너리는 컴파일러의 기본 FMA 축약으로 빌드되어 있어서, complex 곱셈의 `ar*br - ai*bi`가 numpy 안에서는 `fma(ar, br, -(ai*bi))`로 계산돼요. stardust는 complex 곱셈, 나눗셈, 제곱, 역수의 같은 자리에 `std::fma`를 적어요. 같은 순서로 계산하므로 지금은 무작위 곱 4000개에서 결과가 numpy와 비트까지 같아요(약속은 아니에요). optimize도 scipy의 MINPACK과 L-BFGS-B C 코드의 식을 옮긴 곳에서 같은 일을 해요. `optimize/hybrd.cpp`와 `optimize/lbfgsb.cpp`는 파일 안의 `#pragma clang fp contract(on)`으로 scipy 빌드와 같은 축약을 켜고, lmder(`optimize/lsq.cpp`)는 축약 자리를 `std::fma`로 적어요. 지금은 scipy와 같은 점에서 함수를 불러요.

```cpp
// csrc/array/kernels/scalar_ops.hpp (발췌)
inline c128 cmul(c128 a, c128 b) {
    const double ar = a.real(), ai = a.imag(), br = b.real(), bi = b.imag();
    return {std::fma(ar, br, -(ai * bi)), std::fma(ar, bi, ai * br)};
}
```

#### `-fno-builtin-sin -fno-builtin-cos`: sin과 cos는 코드가 합쳐요

Apple 대상에서 clang은 같은 `x`에 대한 `sin(x)`와 `cos(x)`를 보면 `__sincos_stret` 호출 하나로 합칠 수 있어요. 한 번의 인자 축소로 둘을 구하니 약 1.5배 빠르지만, 결과는 `sin()`, `cos()`를 따로 부른 것과 1 ULP(마지막 자리 한 칸) 다를 수 있어요. 컴파일러가 이것을 인라인 상황에 따라 정하면 FMA와 같은 문제가 생겨요. 그래서 이 플래그로 컴파일러의 합치기를 막고, 합친 호출이 필요한 곳은 코드에 `sd::sincos`(`special/sincos.hpp`)로 적어요. complex `expm1`과 special의 여러 함수가 이것을 써요.

```cpp
// csrc/special/sincos.hpp (발췌)
inline SinCos sincos(double x) {
#if defined(__APPLE__)
    const struct __double2 r = __sincos_stret(x);
    return {r.__sinval, r.__cosval};
#else
    return {std::sin(x), std::cos(x)};
#endif
}
```

플래그는 모듈 전체에 걸리므로 배열 밖의 영역도 모두 같은 규칙으로 컴파일돼요.

### import 때의 자기 점검



`_pool_smoke_test(n)`는 태스크 `t`가 자기 칸에 `t * t`를 쓰게 해서, 두 번 돈 태스크나 빠진 태스크가 결과에 드러나게 해요. 결과가 스레드 수와 무관해야 하는 것도 함께 확인해요.

## 대상 하드웨어: Apple M4 Pro 한 대

### 기계의 사실

모두 `sysctl`로 읽은 값이에요. 버퍼 크기, 정렬 단위, 누산기 개수, 기본 스레드 수가 여기서 나와요.

| 항목 | 값 | 설계에 주는 영향 |
|---|:---:|---|
| 코어 | P코어 10 + E코어 4 | 기본 스레드 수 10 (`hw.perflevel0.physicalcpu`) |
| 캐시 라인 | 128B | Buffer 할당을 128B로 정렬해요 |
| 페이지 | 16KB | 새 메모리의 첫 쓰기마다 페이지 폴트가 나요. 결과를 새 배열에 쓰는 연산의 시간에 섞여 들어가요 |
| P코어 L1d / L1i | 128KB / 192KB | L1d가 버퍼 캐스팅의 버퍼 크기 기준이에요 |
| P코어 L2 | 16MB, 코어 5개가 공유, 클러스터 2개 | 원소 100만 개(8MB)는 상당 부분 캐시에 남아요 |
| E코어 L1d / L2 | 64KB / 4MB | — |
| 메모리 | 48GB | — |
| NEON 폭 | 128비트 | float64·int64는 한 번에 2개, complex128은 1개 |
| 64비트 정수 벡터 곱셈 | 없음 | int64 곱셈은 스칼라로 해요 |
| 64비트 정수 벡터 min/max | 없음 | 비교 + 선택 두 명령으로 해요 |
| FCMA (복소 곱셈-누산) | 있음 | complex 곱셈을 `vcmlaq_f64`로 해요 |
| SME (행렬 확장) | 있음 | 직접 쓰지 않아요. BLAS 안에서만 간접적으로 쓰여요 |
| SVE | 없음 | — |

**기본 스레드 수가 14가 아니라 10인 이유**는 메모리에 묶인 연산이에요. 14스레드에서 계산에 묶인 연산은 5~27% 빨라지지만(`sin`이 1스레드 대비 9.4배에서 10.9배로), 메모리에 묶인 연산은 3~12% 느려져요. 태스크를 동적으로 나눠 주므로 E코어가 전체를 기다리게 하지는 않지만(E코어는 태스크를 적게 가져갈 뿐), 메모리 대역폭을 나눠 쓰는 손해가 있어요. 그래서 기본은 10이고, 필요하면 `sd.set_num_threads(14)`를 써요. 스레드 수별 측정은 [스레드풀과 결정성](/internals/core/threads/)에 있어요.

**SME를 직접 쓰지 않는 이유**는 streaming 모드로 들어가고 나오는 전환 비용과 코드의 복잡도예요. Accelerate의 BLAS가 내부에서 쓰는 것으로 충분해요.

### 한 기계만 겨냥한 결과

대상 기계를 이 Mac 한 대로 정한 데서 구조의 여러 부분이 나와요.

- **런타임 CPU 디스패치가 없어요.** 여러 CPU를 지원하는 라이브러리는 실행 시점에 CPU 기능을 확인하고 커널 판을 골라야 해요. stardust는 `-mcpu=native` 한 판뿐이라 그런 층이 없어요.
- **상수를 한 기계에서 재요.** 병렬화 기준값(`1 << 15`), 태스크 크기(`1 << 12`), 안쪽 축의 최소 조각(1024원소), 버퍼 캐스팅의 버퍼 크기가 모두 이 기계의 측정값이에요. 다른 기계에서는 최적이 아닐 수 있어요.
- **numpy와 견주는 것도 이 기계의 numpy예요.** 이 Mac의 numpy float64 초월함수는 시스템 libm과 비트가 같아요(`tanh`만 최대 1 ULP 차이). 그래서 같은 libm 함수를 부르는 stardust의 원소별 함수는 지금 numpy와 비트까지 같아요. 다만 numpy와 비트까지 같은 것은 약속이 아니에요. stardust가 약속하는 것은 스레드 수와 상관없이 같은 비트, 자기 골든 기록과 같은 비트, 그리고 Arb 참값에 대한 정확도 계약이에요. 다른 플랫폼의 numpy는 자체 SIMD 초월함수를 쓸 수 있어서 이런 비교 자체가 성립하지 않을 수 있어요.
- **결과물이 이식되지 않아요.** `-mcpu=native`로 만든 `_core`는 M4의 명령을 쓰므로 더 오래된 Apple 칩에서 돌지 않을 수 있어요. 소스에서 다시 빌드하면 그 기계의 `native`로 빌드되지만, 위 상수와 비트 일치는 보장하지 않아요.

<Callout type="warn" title="수치는 이 기계의 값이에요">
  이 사이트의 성능 수치는 모두 Apple M4 Pro 한 대에서 잰 값이에요. 비교 대상은 같은 기계의 numpy 2.5.4이고, 따로 적지 않으면 원소 100만 개, float64예요. 메모리에 묶인 연산의 1스레드 값은 측정마다 20~30% 흔들려요.
</Callout>

## 일부러 넣지 않은 최적화

넣으면 빨라지는 곳이 있어도, 안전하지 않거나 얻는 속도에 비해 코드가 크게 복잡해지는 최적화는 넣지 않아요.

### 임시 배열 재사용 (temporary elision)

`a + b + c`를 계산하면 `a + b`의 결과가 임시 배열로 생겼다가 `+ c`의 입력으로 쓰이고 버려져요. numpy는 이 임시 배열이 다른 곳에서 참조되지 않는다고 판단되면 `+ c`의 결과를 그 메모리에 덮어써서 할당 하나를 아껴요(numpy 소스 `numpy/_core/src/multiarray/temp_elide.c`).

stardust에는 이 최적화가 없어요. 판정을 안전하게 할 수 없기 때문이에요.

- CPython의 `PyUnstable_Object_IsUniqueReferencedTemporary`는 Python 코드에서 만든 임시 객체를 정확히 판정해요. 단, 인자를 `nb::handle`로 받거나 raw `nb_add` 슬롯을 써야 해요. `nb::object`로 받으면 참조가 하나 늘어서 한 번도 임시 객체로 잡히지 않아요.
- 문제는 다른 C 확장이에요. C 확장이 **빌린 참조**(참조 카운트를 올리지 않은 포인터)로 받은 `x`로 `x + y`를 계산하고 나중에 `x`를 다시 읽으면, 이 API는 `x`를 임시 객체로 판정해서 버퍼를 재사용해 버려요. 다시 읽은 `x`는 덮어써져 있어요. Cython 코드에서 흔한 패턴이에요.
- numpy는 이 문제를 막으려고 C 콜스택을 검사해서, 호출이 인터프리터에서 곧바로 왔는지 확인해요. 같은 방법을 쓰려면 실행 중인 C 콜스택을 들여다봐야 하는데, 플랫폼과 인터프리터의 내부 구현에 기대는 방법이라 맞지 않아요.
- 현재 프레임의 바이트코드가 `BINARY_OP`인지 보는 방법도 인터프리터 내부에 기대고, 반사 연산(`__radd__`) 경로에 구멍이 남아요.

그래서 연산자는 항상 새 출력 배열을 할당해요.

### 그 밖에 넣지 않은 것

| 넣지 않은 것 | 설명 |
|---|---|
| 런타임 CPU 디스패치 | 대상이 한 기계라 커널 판이 하나예요 |
| 손으로 짠 어셈블리 | 손으로 짠 SIMD 코드는 C++의 NEON intrinsic으로만 써요 |
| ULP 단위로 튜닝한 자체 SIMD 초월함수 | 대신 vForce를 써요. 오차 계약은 최대 8 ULP이고, 잰 최대는 4 ULP(`atanh`)예요 |
| 데이터를 보고 알고리즘을 고르는 휴리스틱 | 알고리즘은 dtype과 길이로만 골라요. int64 기수 정렬처럼 dtype과 길이로 고르는 것은 여기에 들지 않아요 |
| 작은 메모리 할당 캐시 | 해제한 메모리를 모아 두는 대신 할당 횟수를 줄여요. 작은 배열은 데이터를 Buffer 안에 둬서 할당이 한 번이에요 |
| 특수 케이스용 fast path 남발 | fast path는 연속 메모리처럼 정해진 경우에만 둬요 |
| SME 직접 사용 | streaming 모드 전환 비용과 복잡도 |
| `-ffast-math` | NaN·inf의 뜻과 덧셈 순서를 지켜야 해요 |

작은 호출 경로에도 넣지 않은 것이 있어요. nanobind의 저수준 API(`inst_alloc`/`inst_mark_ready`)로 인스턴스를 직접 만드는 방법은 `x[1]`에서 약 3ns, 곧 잡음 수준만 줄여요. `__getitem__`을 C 슬롯(`mp_subscript`)으로 직접 등록하면 약 7ns를 아끼지만, nanobind가 해 주는 예외 변환을 직접 처리해야 해요. 자세한 내용은 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

## 성능

이 페이지의 구조가 성능에 주는 영향을 모으면 이래요.

| 구조 결정 | 영향 |
|---|---|
| 확장 모듈 하나, `NDArray` 직접 전달 | linalg 결과 배열 하나에 약 120ns 절약 (작은 행렬 호출의 약 30%) |
| 타입까지 C++ | `x[1, 2]` 25ns (numpy 33ns), 작은 `a + b` 179ns (numpy 151ns) |
| `NOMINSIZE`(`-O3`) | 연속 fast path가 `-Os` 빌드보다 약 2배 빨라요 |
| `FCVTZS` 직접 호출 | 분기 세 개 판보다 약 5배 빨라요(464µs 대 89µs). numpy의 같은 `astype`은 243µs |
| 풀 하나, 영역별 기준값 | 병렬 호출 고정 비용 약 1.5µs. 원소 100만 개 `sin` 10스레드 94µs (numpy 3.81ms) |

연산마다 numpy보다 빠르거나 느린 원인은 [성능 종합](/internals/array/performance/)에 있어요.
