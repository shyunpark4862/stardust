## 한눈에 보기

stardust의 계산은 모두 C++에 있고, 사용자는 Python에서 불러요. 그 사이의 경계는 생각보다 많은 일을 해요.

| 경계에서 하는 일 | 어디서 | 핵심 |
|---|---|---|
| 함수와 타입 노출 | nanobind, `csrc/bind/` | 확장 모듈 `stardust._core` 하나. 인자는 대부분 `nb::handle`(가공하지 않은 Python 객체)로 받아요 |
| 배열 타입 | `bind/array_bind.cpp` | `sd.ndarray`는 C++ 구조체 `NDArray`를 담은 Python 타입이에요. 생성자가 없어요 |
| 인자 해석 | `bind/pyutil.cpp` | 배열과 주 인자는 위치 전용, 옵션은 키워드 전용. int는 `operator.index` 규칙, bool 옵션은 `True`/`False`만 |
| 에러 메시지 | `bind/errors.{hpp,cpp}` | 공개 함수가 낸 에러는 `name(): `로 시작해요. 헬퍼는 이름을 모르고, 바인딩이 붙여요 |
| GIL | `parallel/pool.{hpp,cpp}` | 일이 영역의 기준값 이상이면 스레드 수가 몇이든 놓아요. 놓은 구간에서는 Python 객체를 만지지 않아요 |
| 버퍼 프로토콜 | `bind/array_bind.cpp`, `array/ops/asarray.cpp` | 내보낼 때는 복사 없이, 가져올 때는 타입이 정확히 같고 정렬되어 있으면 복사 없이 |
| DLPack | `array/ops/dlpack.cpp` | 버전 있는 capsule과 옛 capsule을 모두 읽고 써요 |
| 수명과 소유권 | `NDArray::buffer`, `NDArray::base` | 메모리는 `shared_ptr<Buffer>`가, Python 쪽 주인은 `base`가 붙잡아요 |

이 원칙은 배열만의 것이 아니에요. 선형대수(`sd.linalg`), 특수함수(`sd.special`)는 같은 인자 해석 도구와 같은 에러 이름 장치를 써요. 데이터프레임(`sd.frame`)은 Python 클래스라서 인자 검사를 Python 층(`frame/_errors.py`)이 하지만, 규칙과 메시지 형식은 C++ 쪽과 한 글자까지 같아요.

## nanobind

### nanobind를 쓰는 이유

nanobind는 C++ 함수와 클래스를 Python 확장 모듈로 노출하는 라이브러리예요. pybind11을 만든 Wenzel Jakob이 pybind11의 후속으로 만들었고, 문서는 더 작은 바이너리, 더 빠른 컴파일, 더 낮은 호출 오버헤드를 내세워요 [1].

macOS `sample` 프로파일러로 작은 호출을 보면 nanobind의 함수 호출 경로 자체는 약 10ns이고, 작은 배열 연산의 나머지 비용은 대부분 stardust 쪽(할당, `NDArray` 복사, 이터레이터 준비)에 있어요. 바인딩 도구가 병목이 아니니, 남은 비용은 C++ 안에서 줄일 수 있어요.

### 쓰는 방식: 거의 모든 인자를 `nb::handle`로

nanobind는 C++ 함수의 시그니처를 보고 Python 인자를 자동으로 변환해 줘요. `bool keepdims`라고 적으면 Python의 `True`가 C++ `true`로 바뀌어 들어와요. 편하지만 stardust의 공개 함수는 이 기능을 거의 쓰지 않고, 인자를 `nb::handle`(참조 카운트를 건드리지 않는 Python 객체 포인터)로 받아 직접 해석해요.

```cpp
// csrc/bind/array_bind.cpp (발췌): sum을 메서드로 등록하기
.def("sum", named("sum", &sum), nb::kw_only(),
     nb::arg("axis").none() = nb::none(),
     nb::arg("dtype").none() = nb::none(),
     nb::arg("keepdims").none() = false)
```

이유는 세 가지예요.

1. **에러 메시지를 우리가 정해요.** nanobind의 자동 변환이 실패하면 "incompatible function arguments. The following argument types are supported: …"라는 시그니처 목록이 나와요. 어느 인자의 무엇이 틀렸는지는 말해 주지 않아요. `nb::handle`로 받으면 변환을 우리 코드가 하므로 `sum(): 'keepdims' must be True or False, not int`처럼 정해진 형식의 메시지를 낼 수 있어요.
2. **규칙을 한곳에 둬요.** int 인자를 `operator.index` 규칙으로 읽는다든가, `numpy.bool_`을 bool로 치지 않는다든가 하는 규칙은 nanobind의 변환과 다르거나 nanobind에 아예 없는 규칙이에요. 해석 함수(`bind/pyutil.cpp`)가 한 벌이라 모든 공개 함수가 같은 규칙을 따라요.
3. **참조 카운트를 아껴요.** `nb::handle`은 참조 카운트를 올리지 않아요. `nb::object`로 받으면 인자마다 참조가 하나 늘었다 줄어요.

`.none()`은 그 인자 자리에 `None`이 들어와도 nanobind가 거절하지 않고 우리 코드까지 넘기라는 표시예요. nanobind는 기본으로 `None`을 거절하는데, 그러면 `keepdims=None` 같은 실수가 다시 시그니처 목록 메시지가 돼요. 모든 인자에 `.none()`을 붙여서 `None`도 같은 검사를 받게 해요.

### 이름 없는 인자와 `kw_only`: 위치 전용과 키워드 전용

nanobind에서 이름 없이 `nb::arg()`로 적은 인자는 **위치 전용**(positional-only)이에요. Python의 `/` 앞에 있는 인자처럼 키워드로 넘길 수 없어요. `nb::kw_only()` 뒤의 인자는 **키워드 전용**(keyword-only)이에요.

이 규칙은 Python Array API 관례예요 [2]. 배열 인자와 그 함수의 "본 인자"(`reshape`의 `shape`, `full`의 `fill_value`)는 위치 전용, 이름 붙은 옵션(`dtype`, `axis`, `keepdims`, `out`, `copy` …)은 키워드 전용이에요. 선형대수, 특수함수, 데이터프레임도 같은 규칙이에요. 데이터프레임은 Python 클래스라서 Python의 `/`와 `*`로 같은 모양을 만들어요(`Series(data=None, /, *, index=None, ...)`).

이름 없는 인자는 nanobind가 스스로 시그니처를 만들 때 `arg0`으로 보여요. 그래서 공개 함수는 등록할 때 `nb::sig`로 API 문서의 시그니처를 그대로 넘겨요.

```cpp
// csrc/array/ops/reduction.cpp (발췌)
m.def(
    "sum", named("sum", &sum), nb::sig("def sum(x, /, *, axis=None, dtype=None, keepdims=False)"), arg().none(),
    nb::kw_only(), axis, dtype, keepdims
);
```

```python
>>> print(sd.sum.__doc__)
sum(x, /, *, axis=None, dtype=None, keepdims=False)
```

`help()`와 호출 모양이 틀렸을 때 nanobind가 내는 메시지(아래 "호출 모양이 틀렸을 때")가 이 시그니처를 보여요. 위치 전용 인자도 이름이 보여서, 무엇을 넘겨야 하는지 바로 읽혀요.

배열의 메서드(`x.sum()`, `x.reshape()`, `x.astype()` …)도 같아요. 모듈 함수의 시그니처에서 배열 인자 `x`를 `self`로 바꾼 것을 `nb::sig`로 넘겨요(`csrc/bind/array_bind.cpp`). 넘기지 않으면 nanobind가 타입 표기가 붙은 `sum(self, *, axis: object | None = None, ...) -> object` 꼴을 만들어서 모듈 함수와 모양이 달라져요.

```cpp
// csrc/bind/array_bind.cpp (발췌)
.def(
    "sum", named("sum", &sum), nb::sig("def sum(self, /, *, axis=None, dtype=None, keepdims=False)"),
    nb::kw_only(), nb::arg("axis").none() = nb::none(), nb::arg("dtype").none() = nb::none(),
    nb::arg("keepdims").none() = false
)
```

```python
>>> print(sd.asarray([1.0]).sum.__doc__)
sum(self, /, *, axis=None, dtype=None, keepdims=False)
```

nanobind 함수에는 Python의 `inspect.signature`가 `(*args, **kwargs)`만 보여요. 그래서 공개 API와 문서가 같은지 확인하는 테스트(`tests/<영역>/test_api_surface.py`)는 nanobind가 붙여 주는 `__nb_signature__`를 읽어서 위치 전용·키워드 전용 구분과 기본값을 비교해요.

### 짧은 타입 이름

nanobind는 바인딩한 타입의 C 수준 이름(`tp_name`)을 `"stardust._core.ndarray"`로 정해요. Python이 직접 만드는 메시지는 이 이름을 써서, 그대로 두면 `unsupported operand type(s) for +: 'stardust._core.ndarray' and 'list'`가 나와요. Python으로 쓴 클래스라면 `'ndarray'`만 나왔을 거예요.

```cpp
// csrc/bind/pyutil.cpp
void use_short_type_name(nb::handle type) {
    auto* t = reinterpret_cast<PyTypeObject*>(type.ptr());
    // tp_name은 타입이 가진 전체 이름 문자열 안을 가리켜요(타입과 함께 해제됨).
    // 마지막 점 다음을 가리키게 해도 소유 관계는 그대로예요.
    if (const char* dot = std::strrchr(t->tp_name, '.')) t->tp_name = dot + 1;
}
```

문자열을 새로 만들지 않고 포인터만 옮기는 것이 요점이에요. `__module__`과 `repr(type)`은 바뀌지 않아요(`<class 'stardust._core.ndarray'>`). `ndarray`, dtype 타입 `DType`, 배열 반복자 `_ArrayIterator`에 이렇게 해요. 그래서 Python 자신의 메시지가 모두 짧은 이름을 써요.

```python
>>> x = sd.asarray([1.0, 2.0, 3.0])
>>> x + [1, 2, 3]
Traceback (most recent call last):
  ...
TypeError: unsupported operand type(s) for +: 'ndarray' and 'list'
>>> hash(x)
Traceback (most recent call last):
  ...
TypeError: unhashable type: 'ndarray'
```

우리가 직접 만드는 메시지(`..., not list`)에 넣는 타입 이름도 같은 규칙이에요. `bind/errors.hpp`의 `py_type_name(o)`가 모듈 경로 없는 타입 이름(`ndarray`, `list`, `DType`)을 돌려줘요. 예외는 numpy의 타입이에요. numpy의 bool 스칼라가 `not bool`로 보이면 Python의 `True`/`False`를 넣은 것과 구별되지 않고, numpy 배열이 `not ndarray`로 보이면 sd 배열을 넣은 것처럼 읽혀요. 그래서 타입의 `__module__`이 `numpy`나 `numpy.`으로 시작하면 공개 모듈 경로를 붙여요. 경로는 밑줄로 시작하는 첫 부분 앞에서 끊어서, `numpy.random._generator.Generator`가 `numpy.random.Generator`가 돼요.

```cpp
// csrc/bind/errors.cpp
std::string py_type_name(nb::handle o) {
    // 정적 타입의 tp_name은 "module.Name"(numpy.int64), 힙 타입은 "Name"이에요.
    PyTypeObject* t = Py_TYPE(o.ptr());
    const char* name = t->tp_name;
    const char* dot = std::strrchr(name, '.');
    std::string out = dot ? dot + 1 : name;
    PyObject* mod = PyObject_GetAttrString(reinterpret_cast<PyObject*>(t), "__module__");
    if (mod == nullptr) {
        PyErr_Clear();
        return out;
    }
    if (PyUnicode_Check(mod)) {
        const char* m = PyUnicode_AsUTF8(mod);
        if (m == nullptr) PyErr_Clear();
        else if (std::strncmp(m, "numpy", 5) == 0 && (m[5] == '\0' || m[5] == '.')) {
            std::string pub;  // 처음 나오는 비공개 부분 앞까지의 모듈 경로
            for (const char *p = m, *e; *p != '\0'; p = *e ? e + 1 : e) {
                e = std::strchr(p, '.');
                if (e == nullptr) e = p + std::strlen(p);
                if (*p == '_') break;
                pub += (pub.empty() ? "" : ".") + std::string(p, e);
            }
            out = pub + "." + out;
        }
    }
    Py_DECREF(mod);
    return out;
}
```

```python
>>> sd.sum(x, keepdims=np.True_)
Traceback (most recent call last):
  ...
TypeError: sum(): 'keepdims' must be True or False, not numpy.bool
>>> sd.concat(np.zeros(2))
Traceback (most recent call last):
  ...
TypeError: concat(): 'arrays' must be a list or tuple of sd.ndarray, not numpy.ndarray
>>> sd.random.default_rng(np.random.default_rng(0))

```

데이터프레임처럼 Python으로 쓴 코드도 이 함수를 `_core._type_name`으로 불러서 이름을 만들어요. 모든 영역의 메시지가 한 함수에서 이름을 얻으니 같은 값은 어디서나 같은 이름으로 보여요. 이 함수는 인자 해석 도구(`bind/pyutil.hpp`)가 아니라 에러 헤더에 있어요. `pyutil.hpp`는 `NDArray` 정의를 끌어오는데, 데이터프레임의 변환 코드처럼 배열을 모르는 곳도 이 함수가 필요하기 때문이에요.

### nanobind의 `ndarray`를 쓰지 않는 이유

nanobind에는 numpy, PyTorch 같은 배열을 C++에서 받는 `nb::ndarray`가 있어요. stardust는 이것을 쓰지 않아요. stardust의 배열은 다른 라이브러리의 배열을 받는 장치가 아니라 그 자체가 배열 타입이고, 메모리 소유(Buffer), 차원 수 상한(32), 연속성 플래그, `base` 규칙을 자기 방식으로 정해야 하기 때문이에요. 다른 배열과의 교환은 표준 프로토콜(버퍼 프로토콜, DLPack)을 직접 구현해서 해요.

## ndarray 타입

### Python 객체 안의 C++ 구조체

`sd.ndarray`는 `nb::class_<NDArray>`로 바인딩한 타입이에요. Python 객체 하나가 `NDArray` 하나를 값으로 담아요. 결과를 돌려줄 때는 `wrap(NDArray&& a)`가 새 Python 객체를 받아 `NDArray`를 그 안으로 move해요. `nb::inst_alloc`으로 인스턴스를 받고, 그 자리에 `NDArray`를 옮겨 만든 뒤 `nb::inst_mark_ready`로 마쳐요. 인스턴스는 nanobind의 인스턴스 풀(`nb::pooled(256)`)에서 나와요. 해제된 ndarray 객체 256개까지를 nanobind의 해시표에 등록된 채로 모아 두었다가 다시 쓰므로, 결과 배열마다 `malloc`·`free`와 해시표 넣고 빼기가 없어요([작은 배열의 비용](/internals/array/small-arrays/)). `shared_ptr` 대신 값으로 담는 이유는 데이터프레임 쪽 측정이 보여 줘요. nanobind에 `shared_ptr`을 돌려주면 Python 객체마다 `shared_ptr<void>` 복사본을 힙에 새로 만들고 전역 keep-alive 표에 등록해서, 원소 10개 Column `add`가 190ns예요. 값 타입으로 담으면 89ns예요.

`NDArray`의 모양은 이래요. 자세한 내용은 [데이터 모델](/internals/array/data-model/)에 있어요.

```cpp
// csrc/array/ndarray.hpp (줄인 발췌)
struct NDArray {
    std::shared_ptr<Buffer> buffer;   // 메모리 소유
    std::byte* data = nullptr;        // Buffer 안의 시작 위치
    DType dtype = DType::Float64;
    int ndim = 0;
    Dims shape;                       // std::array<int64_t, 32>, 앞의 ndim칸만 의미
    Dims strides;                     // 바이트 단위
    bool c_contiguous = true, f_contiguous = true, writeable = true;
    nb::object base;                  // Python의 .base
};
```

C++ 쪽에서 Python 객체 안의 `NDArray`를 꺼내는 것은 포인터 계산 하나예요.

```cpp
// csrc/bind/pyutil.hpp (발췌)
extern PyTypeObject* g_ndarray_type;

inline bool is_ndarray(nb::handle o) {
    PyTypeObject* t = Py_TYPE(o.ptr());
    return t == g_ndarray_type || (g_ndarray_type != nullptr && PyType_IsSubtype(t, g_ndarray_type));
}

inline NDArray& as_ndarray(nb::handle o) { return *nb::inst_ptr<NDArray>(o); }
```

`g_ndarray_type`은 `bind_ndarray`가 클래스를 만든 직후 한 번 정해요. 타입 검사는 `Py_TYPE(o)`를 저장한 포인터와 비교하는 것이고, 하위 타입일 때만 `PyType_IsSubtype`을 불러요. `nb::isinstance<NDArray>`는 호출마다 nanobind의 `type_info` 해시표를 찾아요.

확장 모듈이 하나라 이 타입 등록도 하나예요. 그래서 linalg와 frame의 C++ 코드도 이 두 함수로 배열을 바로 받아요. 함수가 도는 동안에는 Python 인자 자체가 배열 객체를 살려 두므로, C++은 `const NDArray&`를 복사 없이 빌려 써요.

### 생성자가 없어요

```cpp
// csrc/bind/array_bind.cpp (발췌)
.def("__init__", [](NDArray*, nb::args, nb::kwargs) {
    throw nb::type_error("ndarray(): there is no constructor; use asarray() or another creation function");
})
```

`sd.ndarray`는 `isinstance(x, sd.ndarray)` 검사를 위해 이름만 공개해요. 배열은 `asarray`, `zeros`, `arange` 같은 생성 함수로만 만들어요. 생성자까지 두면 같은 일을 하는 길이 둘이 되기 때문이에요. `__init__`을 아예 정의하지 않으면 nanobind가 "stardust._core.ndarray: no constructor defined!"라는 내부 이름이 섞인 메시지를 내서, 정해진 형식의 메시지를 내는 `__init__`을 일부러 넣어요.

### 속성

| 속성 | 돌려주는 것 | 비고 |
|:---:|---|---|
| `dtype` | dtype 객체 (`sd.float64` 등) | 싱글턴이라 `x.dtype is sd.float64`가 성립해요 |
| `shape` | int의 tuple | 고정 배열의 앞 ndim칸으로 만들어요 |
| `strides` | int의 tuple, 바이트 단위 | numpy와 같은 단위 |
| `ndim`, `size`, `itemsize`, `nbytes` | int | — |
| `base` | 메모리를 실제로 가진 Python 객체 또는 `None` | 아래 "수명과 소유권" |
| `T`, `mT` | 전치 뷰 | `.T`는 2차원만, `.mT`는 마지막 두 축 |

모두 읽기 전용이에요. 등록하는 방법은 두 가지예요.

**단순한 속성은 타입 슬롯으로 직접 등록해요.** `shape`, `strides`, `ndim`, `size`, `dtype`, `itemsize`, `nbytes`, `base`는 CPython의 `PyGetSetDef` 표(`tp_getset` 슬롯)에, `len()`은 `sq_length`/`mp_length` 슬롯에 C 함수로 넣어요. nanobind의 `def_prop_ro`로 등록하면 속성을 읽을 때마다 nanobind의 함수 호출 경로(인자 변환, 오버로드 확인, 결과 변환)를 지나요. 속성 하나는 일이 거의 없어서 이 경로가 시간의 대부분이에요. `def_prop_ro`로 등록하면 `x.shape`가 34ns, `len(x)`가 17ns이고, 슬롯으로 등록하면 19ns(numpy 18ns), 7ns(numpy 7ns)예요. 이 함수들은 메모리 부족 말고는 실패하지 않으므로 nanobind의 예외 변환이 없어도 돼요.

```cpp
// csrc/bind/array_bind.cpp (줄인 발췌)
PyObject* get_ndim(PyObject* self, void*) { return PyLong_FromLong(self_array(self).ndim); }
Py_ssize_t array_len(PyObject* self) { return self_array(self).shape[0]; }  // 0차원이 없어요
int read_only(PyObject*, PyObject* value, void* name) {   // 대입·삭제는 property와 같은 메시지로
    PyErr_Format(PyExc_AttributeError, value ? "property '%s' of 'ndarray' object has no setter"
                                             : "property '%s' of 'ndarray' object has no deleter",
                 static_cast<const char*>(name));
    return -1;
}
PyGetSetDef ndarray_getset[] = {
    {"shape", get_shape, read_only, nullptr, const_cast<char*>("shape")},
    {"ndim", get_ndim, read_only, nullptr, const_cast<char*>("ndim")},
    // size, dtype, strides, itemsize, nbytes, base ...
};
PyType_Slot ndarray_slots[] = {
    {Py_bf_getbuffer, (void*)getbuffer}, {Py_tp_getset, (void*)ndarray_getset},
    {Py_sq_length, (void*)array_len},    {Py_mp_length, (void*)array_len}, {0, nullptr},
};
```

`self_array`는 nanobind 인스턴스 안의 `NDArray`를 가리키는 포인터를 꺼내는 한 줄(`nb::inst_ptr`)이에요. 대입과 삭제는 setter 자리의 `read_only`가 막고, Python property가 내는 것과 같은 메시지를 내요.

**`.T`와 `.mT`는 nanobind property로 둬요.** 2차원이 아니면 에러를 내야 하고, 그 메시지에 공개 이름이 붙어야(`named`) 해서 nanobind의 예외 변환을 거치는 편이 맞아요. nanobind가 만든 `property`에는 이름이 없어서, 그대로 두면 `x.T = y`에 "property '' of 'ndarray' object has no setter"라는 빈 이름 메시지가 나와요. 바인딩 끝에서 `__set_name__`을 직접 불러 이름을 넣어요.

```cpp
for (const char* name : {"T", "mT"}) cls.attr(name).attr("__set_name__")(cls, name);
```

```python
>>> x.shape = (1, 3)
Traceback (most recent call last):
  ...
AttributeError: property 'shape' of 'ndarray' object has no setter
```

연속성 플래그는 공개 속성이 아니에요. 테스트용 비공개 메서드 `_flags()`가 dict로 돌려줘요.

```python
>>> m = sd.asarray([[1.0, 2.0], [3.0, 4.0]])
>>> m._flags()
{'c_contiguous': True, 'f_contiguous': False, 'writeable': True}
>>> m.T._flags()
{'c_contiguous': False, 'f_contiguous': True, 'writeable': True}
```

### 메서드는 모듈 함수를 그대로 불러요

`x.sum(axis=0)`과 `sd.sum(x, axis=0)`은 같은 C++ 함수예요. 메서드 등록이 모듈 함수의 포인터(`&sum`)를 그대로 쓰고, `x`가 첫 인자(self)가 돼요. 그래서 동작도 에러 메시지도 같아요. 메서드로도 제공하는 것은 정해진 목록(`reshape`, `astype`, `copy`, `tolist`, 리덕션 11개)뿐이에요.

### 연산자

연산자는 원소별 함수의 얇은 래퍼예요. `x + y`는 `sd.add(x, y)`와 같은 커널(`binary<ops::Add>`)을 불러요.

```cpp
// csrc/bind/array_bind.cpp (줄인 발췌)
template <typename Op>
void def_arith(nb::class_<NDArray>& cls, const char* fwd, const char* refl, const char* inplace,
               const char* symbol, const char* inplace_symbol) {
    cls.def(fwd, [symbol](nb::handle self, nb::handle other) {          // x + y
        return is_operand(other) ? binary<Op>(self, other, nb::none(), symbol) : not_implemented();
    }, nb::arg().none());
    cls.def(refl, [symbol](nb::handle self, nb::handle other) {         // y + x (반사)
        return is_operand(other) ? binary<Op>(other, self, nb::none(), symbol) : not_implemented();
    }, nb::arg().none());
    cls.def(inplace, [inplace_symbol](nb::handle self, nb::handle other) {  // x += y
        return is_operand(other) ? binary<Op>(self, other, self, inplace_symbol) : not_implemented();
    }, nb::arg().none());
}
```

- **받는 피연산자**는 `sd.ndarray`와 Python 스칼라(`bool`, `int`, `float`, `complex`)와 numpy 스칼라예요(`is_operand`). 리스트, numpy 배열, `None`이면 `NotImplemented`를 돌려줘요. 그러면 Python이 반대쪽의 반사 메서드를 시도하고, 그쪽도 거절하면 Python 자신의 TypeError를 내요. 리스트나 다른 라이브러리의 배열을 몰래 배열로 바꾸면 어떤 변환과 복사가 일어났는지 코드에 드러나지 않아서, 바꾸지 않아요. 필요하면 `sd.asarray`로 먼저 바꿔요.
- **제자리 연산자** `x op= y`는 `op(x, y, out=x)`예요. `out=`과 같은 규칙(승격 순서의 위로만 변환, 메모리 겹침 안전)이 적용되고 같은 객체를 돌려줘요.
- **`@`**는 배열끼리만 받아요(스칼라 없음). `x @= y`는 결과의 shape가 `x`와 같아야 해요.
- **연산자 기호를 커널에 넘겨요.** 마지막 인자 `symbol`(`"+"`, `"+="`)은 에러 메시지에 쓰여요. 아래 "에러 메시지 체계"에서 다뤄요.

**`==`와 `!=`는 따로 다뤄요.** 다른 비교와 같은 방식이면 `x == [1, 2]`에서 양쪽이 모두 `NotImplemented`를 돌려주고, Python은 이때 TypeError 대신 객체 동일성 비교로 물러나서 조용히 `False`를 줘요 [3]. 다른 연산자는 모두 TypeError인데 `==`만 조용히 `False`이면 버그를 숨겨요. 그래서 받지 않는 피연산자이면, 반대쪽 타입의 비교 함수(`tp_richcompare`)를 직접 불러 보고 그쪽도 거절하면 TypeError를 직접 내요.

```cpp
// csrc/bind/array_bind.cpp
template <typename Op>
nb::object op_equality(nb::handle self, nb::handle other) {
    constexpr bool eq = std::is_same_v<Op, ops::Equal>;
    if (is_operand(other)) return binary<Op>(self, other, nb::none(), eq ? "==" : "!=");
    const std::string refused = std::string("'") + (eq ? "==" : "!=") + "' not supported between instances of ";
    if (richcmpfunc cmp = Py_TYPE(other.ptr())->tp_richcompare) {
        nb::object r = nb::steal(cmp(other.ptr(), self.ptr(), eq ? Py_EQ : Py_NE));  // == and != reflect to themselves
        if (!r.is_valid()) {
            // The other side's refusal names the operands in its own order
            // ('Series' and 'ndarray'); ours below keeps the user's order.
            // Any other error is the other side's to tell.
            nb::python_error err;
            if (!err.matches(PyExc_TypeError) || std::string(nb::str(err.value()).c_str()).rfind(refused, 0) != 0)
                throw err;
        } else if (r.ptr() != Py_NotImplemented) {
            return r;
        }
    }
    throw nb::type_error((refused + "'" + py_type_name(self) + "' and '" + py_type_name(other) + "'").c_str());
}
```

반대쪽 타입이 `sd.ndarray`를 아는 타입이면 그 답을 돌려줘요. 반대쪽도 같은 꼴의 `TypeError`로 거절하면(`Series`의 `==`가 그래요) 그 메시지는 피연산자를 자기 순서(`'Series' and 'ndarray'`)로 적으므로, 버리고 사용자가 쓴 순서로 다시 내요. 그 밖의 에러는 반대쪽이 알릴 일이라 그대로 올려요.

`[1] == x`처럼 배열이 오른쪽에 있어도 리스트의 비교가 거절한 뒤 Python이 우리 `__eq__`를 부르므로 결과가 같아요. 데이터프레임의 `==`도 같은 규칙이에요.

```python
>>> x == [1, 2, 3]
Traceback (most recent call last):
  ...
TypeError: '==' not supported between instances of 'ndarray' and 'list'
```

### Python 프로토콜 훅

| 훅 | 동작 | 이유 |
|:---:|---|---|
| `__bool__`, `__int__`, `__float__`, `__complex__` | 모두 TypeError, 원소가 하나여도 | 배열은 크기와 상관없이 스칼라가 아니에요(0차원 배열이 없고, 스칼라 결과는 Python 숫자로 나와요). 넷 다 있어야 해요. `__int__`, `__float__`가 없으면 `int(x)`, `float(x)`가 버퍼 프로토콜로 넘어가 원시 바이트를 문자열로 해석하려 해요 |
| `__index__` | TypeError | 배열을 인덱스로 쓰는 것을 막아요. 이 훅이 있으면 다른 코드가 "`__index__`가 있으니 int"로 오해할 수 있어서, int 인자 해석(`index_value`)은 배열을 따로 제외해요 |
| `__hash__` | `None` | 가변 컨테이너라 해싱할 수 없어요(리스트와 같아요) |
| `__contains__` | TypeError | 없으면 `v in x`가 조용히 반복(`__iter__`)으로 떨어져 첫 축의 원소와 `==`를 해요. `x == v`와 `any()`를 쓰게 해요 |
| `__delitem__` | TypeError (`'ndarray' object doesn't support item deletion`) | 없으면 "AttributeError: __delitem__"이 나와요. tuple과 같은 메시지를 내요 |
| `__len__` | `shape[0]` | 0차원이 없으니 언제나 있어요. 위의 슬롯(`sq_length`, `mp_length`)으로 등록해요 |
| `__iter__` | 첫 축을 따라 `x[0]`, `x[1]`, … | 1차원이면 Python 스칼라, 그 밖에는 뷰를 내요. 반복자(`_ArrayIterator`)는 `tp_iter`/`tp_iternext` 슬롯이라 원소마다 메서드를 찾지 않고, 끝에서는 `StopIteration` 객체를 만들지 않고 NULL을 돌려줘요 |
| `__getitem__` | `None`을 받아요 | `x[None]`은 `newaxis`예요. nanobind의 기본은 `None` 거절이라 `.none()`을 붙여요. `x[key]`는 바인딩이 끝난 뒤 바꿔 단 타입 슬롯 `mp_subscript`가 먼저 받아요. int와 slice만인 키는 슬롯 안에서 끝나고, 그 밖의 키와 C++ 예외는 바인딩한 `__getitem__`을 vectorcall로 불러 nanobind의 예외 변환을 그대로 써요 |
| `__repr__`, `__str__` | `stardust._format`의 Python 함수를 불러요 | 문자열 배치는 Python이 읽기 쉬워요 |

### numpy 스칼라를 피연산자로

`x + np.float64(1)`, `x + np.int32(1)`도 받아요. numpy 스칼라 판정(`array/convert.cpp`의 `scalar_dtype`)은 numpy를 import하지 않고 해요.

1. `bool`, `int`, `float`, `complex`의 인스턴스면 바로 정해요. `numpy.float64`와 `numpy.complex128`은 Python `float`, `complex`의 하위 클래스라서 여기서 잡혀요.
2. 타입 이름(`tp_name`)이 `"numpy."`으로 시작할 때만 numpy의 추상 타입(`numpy.bool`, `numpy.integer`, `numpy.floating`, `numpy.complexfloating`)과 `isinstance`로 대조해요.
3. 추상 타입은 이미 import된 numpy 모듈에서(`PyImport_GetModule`) 처음 한 번 가져와 프로세스 끝까지 쥐어 둬요. numpy 스칼라가 존재한다면 numpy는 이미 import되어 있으므로, stardust가 numpy를 import할 필요가 없어요.
4. `numpy.timedelta64`는 `numpy.integer`의 하위 타입이지만 `__index__`가 없어서 받지 않아요.

값은 Python 스칼라와 같은 변환 함수(`__index__`, `__float__`, `__complex__`)로 읽어요. 데이터프레임도 같은 규칙으로 numpy 스칼라를 받아요.

### `__array_ufunc__ = None`

```cpp
cls.attr("__array_ufunc__") = nb::none();
```

numpy는 `np_array + sd_array`를 보면 오른쪽 피연산자를 numpy 배열로 바꿔 계산하려 해요. 우리 배열은 버퍼 프로토콜을 내보내므로 이 변환이 성공하고, 결과는 numpy 배열이 돼요. 사용자는 두 라이브러리를 섞었다는 것을 모른 채 numpy 결과를 받게 돼요.

NEP 13은 타입에 `__array_ufunc__ = None`이 있으면 numpy ufunc가 그 피연산자에 대해 물러나도록 정해요 [4]. 그러면 `np_array + sd_array`에서 numpy의 `__add__`가 `NotImplemented`를 돌려주고, 우리 `__radd__`도 numpy 배열을 받지 않으니 TypeError가 나요. `np.add(np_array, sd_array)`처럼 ufunc를 직접 불러도 TypeError예요.

```python
>>> import numpy as np
>>> np.add(np.ones(3), x)
Traceback (most recent call last):
  ...
TypeError: operand 'ndarray' does not support ufuncs (__array_ufunc__=None)
```

<Callout type="tip" title="numpy와 섞을 때">
  섞는 것은 막지만 주고받는 것은 쉬워요. `np.asarray(x)`는 stardust 배열을 복사 없이 numpy 배열로 보여 주고(버퍼 프로토콜), `sd.asarray(a)`는 float64 numpy 배열을 복사 없이 가져와요. 어느 라이브러리로 계산할지 한쪽을 골라 변환한 뒤 계산하면 돼요.
</Callout>

numpy 2.5.4에서 `np.ones(3) + x`(연산자 쪽)는 numpy의 다른 경로를 거쳐 "Concatenation operation is not implemented for NumPy arrays…"라는 numpy의 TypeError가 나와요. 예외 종류는 같지만 메시지는 numpy가 정해요.

## 인자 해석

모든 해석 함수는 `bind/pyutil.cpp`에 한 벌씩 있어요. 메시지에는 인자 이름(`'axis'`)만 넣고 함수 이름은 넣지 않아요. 함수 이름은 바인딩이 붙여요(다음 절).

### 인자 종류별 규칙

| 종류 | 함수 | 받는 것 | 틀리면 |
|:---:|---|---|---|

| `copy` | `parse_copy` | `True`, `False`, `None` | TypeError `'copy' must be True, False or None, not int` |
| 실수 | `real_value` | float(numpy의 실수 스칼라 `float64`, `float32`, `float16` 포함), int 규칙의 int | 타입: 호출하는 쪽이 TypeError (`'correction' must be an int or a float, not NoneType`). double 범위 밖 int: OverflowError `'correction' is out of range` |
| 문자열 옵션 | `parse_choice` | 정해진 문자열 중 하나 | 문자열이 아니면 TypeError, 목록에 없으면 ValueError. 두 경우 모두 `'side' must be 'left' or 'right', not ...` |
| dtype | `parse_dtype` | dtype 객체 넷이나 그 이름, `None` | TypeError `'dtype' must be sd.bool, sd.int64, sd.float64 or sd.complex128 (or their names), not float` |

### 데이터 자리에 받는 것

데이터를 받는 자리는 함수가 놓인 층에 따라 두 가지예요.

| 함수 | 받는 것 | 다른 것을 주면 |
|---|---|---|
| 배열, 선형대수, 특수함수의 함수와 분포의 매개변수·메서드, 희소 행렬의 함수 | `sd.ndarray`만(희소 함수는 희소 배열과 `LinearOperator`도). 원소별 함수와 분포는 Python 스칼라도 받아요 | TypeError (`sum(): 'x' must be an sd.ndarray, not list`, `erf(): 'x' must be an sd.ndarray or a bool, int, float or complex, not list`) |
| `sd.stats`의 기술통계, `sd.htest`의 검정, `sd.regression`의 모형 함수, `sd.optimize`의 시작점 `x0`, `sd.integrate`의 표본 규칙(`y`, `x`)과 `tanhsinh`·`nsum`의 끝, `sd.differentiate`의 `x` | `sd.ndarray`, 수의 리스트·튜플, numpy 배열, `sd.frame`의 열(`Series`, 기술통계·가설검정·회귀는 `DataFrame`도) | 받은 것을 그 함수가 계산하는 dtype의 배열로 바꿔 써요. frame의 결측값은 NaN이 돼요 |

`sd.differentiate`의 `x`와 `tanhsinh`·`nsum`의 끝은 `sd.optimize`의 배치 스칼라(`find_root` 등)와 같은 검사를 써서 frame의 열은 받지 않아요. 표본 규칙은 `Series`도 받아요.

첫째 줄의 함수는 다른 계산을 짜는 부품이라 작은 입력으로 자주 불려요. 리스트를 몰래 배열로 바꾸면 그때마다 복사와 dtype 추론이 숨어서 일어나고, sd의 dtype은 numpy보다 적어서 어떤 dtype이 나오는지가 코드에 보여야 해요. 그래서 `sd.asarray`로 먼저 바꾸게 해요. 둘째 줄의 함수는 밖에서 가져온 자료를 처음 넣는 자리예요. 바꾸는 비용이 계산에 비해 작아서 그 자리에서 바꿔 줘요.

```python
>>> sd.sum([1.0, 2.0])
Traceback (most recent call last):
  ...
TypeError: sum(): 'x' must be an sd.ndarray, not list
>>> sd.stats.describe([1.0, 2.0, 4.0]).mean
2.3333333333333335
```

### int는 `operator.index` 규칙으로

Python에서 "int처럼 쓸 수 있는 객체"의 표준은 `__index__` 메서드예요(PEP 357) [5]. 리스트 인덱싱이 `np.int64(3)`을 받는 것도 이 규칙 덕분이에요. stardust는 모든 영역의 int 인자(`shape`, `axis`, `k`, `n`, `num`, `head(n)`, `RangeIndex`, `set_num_threads` …)와 인덱싱에 이 규칙 하나를 써요.

```cpp
// csrc/bind/pyutil.cpp (줄인 발췌)
IndexResult index_value(nb::handle o, std::int64_t& out) {
    PyObject* p = o.ptr();
    if (PyBool_Check(p)) return IndexResult::NotInt;   // bool은 int의 하위 클래스지만 int 인자가 아님
    nb::object owned;
    if (!PyLong_Check(p)) {
        // sd.ndarray의 __index__는 거절용이라 미리 뺌
        if (!PyIndex_Check(p) || is_ndarray(o)) return IndexResult::NotInt;
        PyObject* r = PyNumber_Index(p);               // numpy.int64 → int, numpy.bool_은 거절
        if (r == nullptr) {
            if (!PyErr_ExceptionMatches(PyExc_TypeError)) throw nb::python_error();
            PyErr_Clear();
            return IndexResult::NotInt;
        }
        owned = nb::steal(r);
        p = r;
    }
    int overflow = 0;
    const long long v = PyLong_AsLongLongAndOverflow(p, &overflow);
    if (overflow != 0) return IndexResult::Overflow;
    if (v == -1 && PyErr_Occurred()) throw nb::python_error();
    out = v;
    return IndexResult::Ok;
}
```

- **bool은 int가 아니에요.** Python의 `True`는 `int`의 하위 클래스라 그대로 두면 `sd.zeros(True)`가 길이 1 배열이 돼요. 이런 코드는 거의 언제나 실수라서 bool은 int 인자로 받지 않고, 맨 먼저 `PyBool_Check`로 걸러요. `numpy.bool_`은 `__index__`가 TypeError를 내므로 저절로 걸러져요.
- **Python int는 빠른 길로 가요.** `PyLong_Check`가 참이면 `PyNumber_Index`를 부르지 않고 바로 읽어요. 대부분의 호출이 이 길이에요.
- **세 가지 결과를 돌려줘요.** `Ok`, `NotInt`, `Overflow`로 나눠 돌려주고, 메시지는 부른 쪽이 정해요. `axis`는 "an int or a tuple or list of ints", `shape`는 "an int or a tuple of ints"처럼 그 인자가 받는 것을 정확히 말해야 하기 때문이에요.
- **int64 밖이면 OverflowError예요.** `PyLong_AsLongLongAndOverflow`는 예외를 만들지 않고 넘침만 알려 줘서, 정해진 메시지로 바꾸기 쉬워요. 예외가 `set_num_threads` 하나 있어요. 1~1024 밖이면 크기와 상관없이 `ValueError: 'n' must be between 1 and 1024`예요. `2**70`도 "범위 밖의 스레드 수"라는 같은 실수라서예요.

```python
>>> sd.zeros(np.int64(2)).shape
(2,)
>>> sd.zeros(True)
Traceback (most recent call last):
  ...
TypeError: zeros(): 'shape' must be an int or a tuple of ints, not bool
>>> sd.zeros(2**63)
Traceback (most recent call last):
  ...
OverflowError: zeros(): 'shape' is out of range
```

shape는 tuple만, axis는 list도 받아요. `axis`가 list도 받는 것은 linalg의 `vector_norm(axis=[0, 1])`과 같은 모양을 받으려는 거예요. `shape`는 Array API대로 int나 tuple이에요.

### bool 옵션은 `True`와 `False`만

```cpp
bool parse_bool(nb::handle o, const char* what) {
    if (o.ptr() == Py_True) return true;
    if (o.ptr() == Py_False) return false;
    throw nb::type_error((std::string("'") + what + "' must be True or False, not " + py_type_name(o)).c_str());
}
```

`True`와 `False`는 싱글턴이라 포인터 비교 두 번이면 돼요. `0`, `1`, `None`, `numpy.bool_`은 모두 TypeError예요. `numpy.bool_`은 메시지에서 `not numpy.bool`로 보여서 Python의 bool과 구별돼요. "진릿값으로 읽기"(`bool(o)`)를 하면 `keepdims="no"`가 참이 되는 것 같은 실수가 조용히 통과해요.

### `None`

`None`이 뜻이 있는 인자에서만 `None`을 받아요.

| `None`의 뜻이 있는 인자 | 뜻 |
|---|---|
| `axis=None` | 모든 축 |
| `dtype=None` | 입력에서 정해요 |
| `copy=None` | 필요할 때만 복사해요 |
| `out=None` | 새 배열에 써요 |

그 밖의 인자에 `None`을 주면 다른 틀린 값과 똑같은 검사를 거쳐요(`sort(): 'axis' must be an int, not NoneType`, `searchsorted(): 'side' must be 'left' or 'right', not NoneType`). `None`이라고 특별 취급해 기본값으로 바꾸지 않아요.

### dtype 인자

dtype 객체는 C++이 모듈을 만들 때 만든 다섯 개(`sd.bool`, `sd.int64`, `sd.float64`, `sd.complex128`, `sd.string`)뿐이에요. 해석은 포인터 비교 다섯 번, 아니면 문자열 비교예요.

```cpp
// csrc/bind/pyutil.cpp (줄인 발췌)
std::optional<DType> parse_any_dtype(nb::handle o) {
    if (o.is_none()) return std::nullopt;
    for (int i = 0; i < kNumDTypes; ++i)
        if (o.ptr() == g_dtype_objects[i]) return static_cast<DType>(i);   // 객체
    if (PyUnicode_Check(o.ptr())) {
        Py_ssize_t len = 0;
        const char* s = PyUnicode_AsUTF8AndSize(o.ptr(), &len);
        if (auto d = dtype_from_name(std::string_view(s, len))) return d;  // 이름 문자열
    }
    return std::nullopt;  // 부른 쪽이 받는 것을 말하며 에러를 내요
}
```

`g_dtype_objects`는 빌린 포인터예요. 객체의 소유자는 모듈 속성(`sd.float64` 등)이고, `_core` 안의 어떤 코드도 모듈이 해제된 뒤에 돌지 않으니 안전해요. 거절한 값은 `describe_dtype_arg`가 무엇이었는지 보여 줘요. dtype 객체면 `sd.string`, 문자열이면 `'float32'`, 타입이면 모듈을 붙인 이름(`numpy.int64`, 내장 타입은 `float`처럼 이름만), 그 밖에는 타입 이름이에요. 타입에만 모듈을 붙이는 것은 numpy의 `int64` 타입을 `sd.int64`와 헷갈리지 않게 하려는 거예요.

### 데이터프레임의 같은 규칙

데이터프레임의 공개 메서드는 Python이라, 같은 규칙을 Python으로 한 벌 더 둬요(`frame/_errors.py`).

```python
# src/stardust/frame/_errors.py (줄인 발췌)
def as_index(value):
    if isinstance(value, bool):
        return None
    if isinstance(value, int):
        return int(value)
    try:
        return operator.index(value)  # numpy.bool_과 sd.ndarray는 거절해요
    except TypeError:
        return None

def check_int(value, what, func):
    v = as_index(value)
    if v is None:
        raise TypeError(named(func, f"'{what}' must be an int, not {type_name(value)}"))
    if not _INT64_MIN <= v <= _INT64_MAX:
        raise OverflowError(named(func, f"'{what}' is out of range"))
    return v
```

`check_bool`, `check_real`, `check_choice`도 C++의 `parse_bool`, `real_value`, `parse_choice`와 같은 메시지를 내요. 같은 실수는 어느 영역에서든 같은 예외, 같은 메시지예요(`head(): 'n' must be an int, not bool`).

## 에러 메시지 체계

### 형식

- **공개 함수와 메서드가 낸 에러는 그 이름과 `(): `로 시작해요.** `vector_norm(): 'ord' must be ...`
  - 메서드는 클래스 이름 없이 메서드 이름만 써요. `x.astype(...)`과 `sd.astype(x, ...)`은 둘 다 `astype(): `예요. 같은 이름은 어느 클래스, 어느 영역에서든 같은 일을 하기 때문이에요.
  - 생성자는 클래스 이름이에요(`Series(): `, `ndarray(): `). 프로퍼티는 점을 붙여요(`.T: `).
  - 사용자가 부른 함수의 이름이에요. 여러 함수가 함께 쓰는 검사는 이름을 넘겨받아요. `drop_duplicates(keep=...)`의 검사는 안에서 `duplicated`의 코드를 쓰더라도 `drop_duplicates(): `예요.
- **인자는 작은따옴표**로 써요(`'axis'`). 받은 값은 짧은 타입 이름으로 보여요(`not list`, `not ndarray`). numpy의 타입만 공개 모듈을 붙여요(`not numpy.bool`, `not numpy.float64`, `not numpy.ndarray`, `not numpy.random.Generator`).
- **메시지에 문서의 절 번호를 넣지 않아요.** 문서의 번호는 바뀌어도, 사용자 코드가 메시지를 붙잡고 있을 수 있어요.
- **Python 프로토콜은 Python의 형식**이고 이름을 붙이지 않아요. 연산자, 인덱싱과 그 대입, `len`, `in`, `bool`, `iter`, `repr`, 속성 대입이 여기에 들어요.

### 구현: 헬퍼는 이름을 모르고, 바인딩이 붙여요

`parse_axes` 같은 헬퍼와 커널은 수십 개의 공개 함수가 함께 써요. 헬퍼가 "지금 어느 공개 함수 안에서 불렸는지"를 알려면 모든 호출에 이름을 넘겨야 해요. 대신 stardust는 예외를 잡아 이름을 붙여 다시 던져요.

```cpp
// csrc/bind/errors.hpp (줄인 발췌)
template <class R, class... A>
auto named(const char* func, R (*f)(A...)) {
    return [func, f](A... args) -> R {
        try {
            return f(std::forward<A>(args)...);
        } catch (...) {
            rethrow_named(func);
        }
    };
}

template <class F>
decltype(auto) call_named(const char* func, F&& f) {
    try {
        return std::forward<F>(f)();
    } catch (...) {
        rethrow_named(func);
    }
}
```

- `named("zeros", &zeros)`는 함수 포인터를 받아 같은 시그니처의 람다를 돌려줘요. 템플릿 인자 `R`, `A...`가 함수 포인터의 타입에서 추론되므로, nanobind는 람다를 원래 함수처럼 바인딩해요(인자 이름과 기본값은 `.def`에서 따로 정해요). 등록은 `m.def("zeros", named("zeros", &zeros), ...)` 한 줄이에요.
- `call_named(func, [&] { ... })`는 이름이 실행 시점에 정해질 때 써요. 데이터프레임 커널은 Python 층이 넘긴 `func=` 인자로, `set_num_threads`는 람다 본문으로 써요.
- **정상 경로의 비용은 없어요.** C++ 예외는 ARM64에서 표 기반으로 구현돼서, `try` 블록에 들어가고 나오는 데 명령이 들지 않아요. 비용은 예외가 실제로 던져질 때만 들어요.

다시 던지는 쪽은 예외의 종류를 지키고 메시지만 바꿔요.

```cpp
// csrc/bind/errors.cpp (줄인 발췌)
void rethrow_named(const char* func) {
    try {
        throw;                                   // 지금 처리 중인 예외를 다시 던져 종류를 가려요
    } catch (const nb::builtin_exception& e) {
        switch (e.type()) {
            case nb::exception_type::type_error:
            case nb::exception_type::value_error:
            case nb::exception_type::index_error:
            case nb::exception_type::key_error:
            case nb::exception_type::buffer_error:
                throw nb::builtin_exception(e.type(), with_name(func, e.what()).c_str());
            default:
                throw;                           // stop_iteration 등: 메시지가 아니라 흐름 제어
        }
    } catch (const linalg::LinAlgError& e) {
        throw linalg::LinAlgError(with_name(func, e.what()));
    } catch (const std::overflow_error& e) {
        throw std::overflow_error(with_name(func, e.what()));
    } catch (const std::bad_alloc& e) {          // MemoryError. Buffer::allocate의 것은 이유를 담아요
        const bool plain = std::strcmp(e.what(), "std::bad_alloc") == 0;
        PyErr_SetString(PyExc_MemoryError, with_name(func, plain ? "out of memory" : e.what()).c_str());
        throw nb::python_error();
    }
    // 그 밖의 것(이미 설정된 Python 에러 …)은 catch에 걸리지 않고 그대로 나가요
}

std::string with_name(const char* func, const char* msg) {
    if (func == nullptr || *func == '\0') return msg;
    const std::string prefix = std::string(func) + (func[0] == '.' ? ": " : "(): ");
    if (std::strncmp(msg, prefix.c_str(), prefix.size()) == 0) return msg;  // 이미 붙어 있으면 그대로
    return prefix + msg;
}
```

- `throw;`를 `try` 안에서 다시 던지는 것은 "지금 처리 중인 예외의 실제 타입으로 `catch`를 고르는" 관용구예요. `catch (...)`는 타입을 모르지만, 다시 던지면 아래 `catch`들이 타입별로 받아요.
- `std::overflow_error`는 nanobind가 Python의 `OverflowError`로 바꿔요. 그래서 int64 범위 밖의 int와 double 범위 밖의 int는 C++ 표준 예외로 던지고, 이름을 붙일 때도 같은 종류로 다시 던져요. CPython의 `PyFloat_AsDouble`이 내는 이름 없는 `OverflowError`는 받아서 지우고 stardust의 메시지로 다시 던져요. 데이터 원소이면 `Python int too large to convert to float64`, 실수 인자이면 `'correction' is out of range`처럼 인자 이름을 써요.
- `std::bad_alloc`은 Python의 `MemoryError`로 바꾸면서 이름을 붙여요. 메모리 할당기가 그냥 실패한 경우(메시지가 `std::bad_alloc`)에는 `out of memory`를, `Buffer::allocate`가 물리 메모리보다 큰 요청을 거절한 경우에는 그 이유를 써요(`zeros(): cannot allocate 8796093022208 bytes: more than this machine's physical memory`).
- **이미 이름이 붙은 메시지는 그대로 둬요.** linalg는 에러 메시지용으로 함수 이름을 직접 넘겨받는 곳(`Input`)이 있어서, 메시지가 이미 `inv(): `로 시작할 수 있어요. 두 번 붙지 않게 접두사를 확인해요.
- **이미 설정된 Python 에러**(`nb::python_error`, 예를 들어 다른 객체의 `__index__`가 낸 에러)는 Python이 만든 예외라 건드리지 않아요.

### 연산자는 기호를 넘겨요

연산자는 `named` 없이 바인딩하고, 대신 커널에 기호를 넘겨요. 같은 커널이 함수로 불리면 기호 자리가 `nullptr`예요. 그래서 같은 실수가 부르는 길에 따라 Python의 형식과 함수의 형식으로 나뉘어요.

```cpp
// csrc/array/ops/ufunc.cpp (줄인 발췌): 루프가 없을 때의 메시지
if (symbol == nullptr) throw nb::type_error(("not supported for " + names).c_str());
throw nb::type_error(("unsupported operand dtypes for " + std::string(symbol) + ": " + names).c_str());
```

```python
>>> c = sd.asarray([1j])
>>> c < c
Traceback (most recent call last):
  ...
TypeError: unsupported operand dtypes for <: complex128 and complex128
>>> sd.less(c, c)
Traceback (most recent call last):
  ...
TypeError: less(): not supported for complex128 and complex128
```

연산자 쪽 메시지는 Python 자신의 `unsupported operand type(s) for <: …`를 본떠 "type" 대신 "dtype"을 써요. 받지 않는 **타입**은 Python이 직접 내는 메시지이고, 받는 타입이지만 받지 않는 **dtype**은 우리가 같은 모양으로 내는 메시지예요.

### 데이터프레임: Python이 이름을 알아요

데이터프레임의 공개 메서드는 Python이라 자기 이름을 알아요. 여러 메서드가 함께 쓰는 헬퍼는 `func`를 인자로 받아 `_errors.named(func, msg)`로 메시지를 만들고, 사용자가 닿는 C++ 커널(`Column.from_list`, `astype`, `reduce`, `join_indices` 등)은 `func=` 인자를 받아 바인딩에서 `call_named`로 이름을 붙여요. 연산자와 인덱싱은 `func=None`으로 불러 Python의 형식을 남겨요.

```cpp
// csrc/bind/frame_bind.cpp (줄인 발췌)
// func를 Python 객체 그대로 받아요. 호출마다 std::string으로 바꾸면 작은 리덕션(약 200ns)에서
// 약 15ns를 써요. str의 UTF-8 표현은 str 객체 안에 캐시돼요.
using Func = nb::handle;

const char* name_of(const Func& func) {
    if (!func.is_valid() || func.is_none() || !PyUnicode_Check(func.ptr())) return nullptr;
    return PyUnicode_AsUTF8(func.ptr());
}
```

### `LinAlgError`

선형대수의 수치적 실패(특이 행렬, 양정치가 아닌 행렬, 수렴 실패)는 C++에서 `struct LinAlgError : std::runtime_error`로 던지고, nanobind의 예외 변환기가 Python의 `sd.linalg.LinAlgError`로 바꿔요. 이 Python 클래스는 `stardust/linalg/_errors.py`에 `ValueError`의 하위 클래스로 정의되어 있어서, C++은 import될 때 `_core.linalg._setup(LinAlgError, ...)`로 클래스를 받아 쥐어 둬요. 받기 전이면 `ValueError`로 바꿔요. 클래스의 `__module__`은 `_errors.py`가 `"stardust.linalg"`로 바꿔 둬서, traceback에는 `stardust.linalg.LinAlgError`로 보여요. 이름 붙이기도 같은 장치를 거쳐요(`inv(): singular matrix`).

### 호출 모양이 틀렸을 때

인자의 **값**이 아니라 **호출 모양**이 틀릴 때도 있어요. 없는 키워드, 빠진 인자, 넘치는 위치 인자, 위치 전용 인자를 키워드로 준 호출이에요. 이 에러의 꼴은 함수가 어떻게 만들어졌는지에 따라 셋으로 나뉘어요.

| 함수 | 꼴 | 예 |
|---|---|---|
| Python으로 쓴 무거운 입구: 모듈 수준 함수(`sd.stats`의 기술통계, `sd.regression`, `sd.optimize`, `sd.htest`, `sd.sparse`, `sd.integrate`, `sd.differentiate`의 모든 함수, `sd.random.default_rng`, `sd.frame`의 `read_csv`·`merge`·`concat`), 생성자(frame의 `Series`·`DataFrame`·`Index`·`RangeIndex`, 분포, 희소 배열), 희소 배열·`LinearOperator`·`SparseLU`의 메서드, frame의 `groupby` | `f(): ` 다음에 Python의 문장 | `minimize(): unexpected keyword argument 'foo'`, `Normal(): takes 0 positional arguments but 1 was given` |
| 작은 메서드: frame의 메서드, `Generator`의 메서드, 분포의 메서드 | Python의 기본 꼴 그대로 | `Series.head() got some positional-only arguments passed as keyword arguments: 'n'`, `sample() missing 1 required keyword-only argument: 'rng'` |
| C++ 바인딩으로 바로 묶은 함수: 배열의 함수와 메서드, `sd.linalg`, `sd.special` | nanobind의 메시지와 받을 수 있는 시그니처 | `solve(): incompatible function arguments. The following argument types are supported: 1. solve(a, b, /) ...` |

무거운 입구는 Python이 낸 `TypeError`를 받아 앞부분 `f() got an`을 `f(): `로 바꿔 다시 던져요(`src/stardust/_calls.py`). 값이 틀린 에러와 호출이 틀린 에러의 꼴이 같아야 메시지만 보고 어느 함수인지 알 수 있어요.

```python
# src/stardust/_calls.py (발췌)
def _converted(e, head, name, self_counted):
    """The library's form of e when e is the binding error of the function named by `head` (no
    frame of the function beneath the wrapper's), else None."""
    msg = str(e)
    if not msg.startswith(head) or e.__traceback__.tb_next is not None:
        return None
    return TypeError(message(name, msg[len(head) :], self_counted))
```

- 바꾸는 것은 그 호출 자체의 바인딩 에러뿐이에요. traceback에 감싼 함수의 프레임이 하나도 없어야(`tb_next is None`) 호출 모양의 에러예요. 함수 안에서 난 `TypeError`는 메시지가 우연히 같은 머리로 시작해도 그대로 지나가요.
- 메서드와 생성자는 Python의 개수에 `self`가 들어 있어서, 하나를 빼고 적어요(`summary(): takes 0 positional arguments but 1 was given`).
- 분포의 생성자는 키워드 전용 매개변수만 받아요. 같은 `__init__`를 여러 분포가 함께 써도 메시지에는 부른 클래스의 이름이 나와요(`Gamma(): missing 1 required keyword-only argument: 'a'`).

작은 메서드를 감싸지 않는 것은 비용 때문이에요. 꼴을 바꾸는 감싸기는 호출마다 약 60ns를 더하는데, 이 메서드들은 한 번에 수백 ns로 끝나는 일이 많아요. C++ 바인딩의 메시지를 바꾸려면 모든 바인딩이 인자를 `*args, **kwargs`로 받아 직접 풀어야 하고, 그 비용도 호출마다 들어요. 호출 모양은 코드를 쓸 때 한 번 고치는 실수라서 이 둘은 기본 꼴을 남겨요. 그 대신 C++ 바인딩은 `nb::sig`로 문서의 시그니처를 붙여 두어서(위 "이름 없는 인자와 `kw_only`"), nanobind의 메시지에 인자 이름이 보여요. 인자의 **값**이 틀린 것은 어느 함수든 언제나 위의 형식이에요.

### 에러 종류

| 예외 | 언제 |
|:---:|---|
| `TypeError` | 인자의 타입이 맞지 않아요. 배열 자리에 다른 객체, 그 dtype을 받지 않는 함수, 암묵적 하향 변환(`int_arr += 1.5`), bool 옵션에 `True`/`False`가 아닌 값, int 인자에 int가 아닌 값 |
| `ValueError` | 타입은 맞지만 값이 맞지 않아요. shape 불일치, 범위 밖이거나 중복된 축, 음수 길이, 0차원 요청, `copy=False`인데 복사가 필요함, 쓰기 금지 배열에 쓰기, 빈 배열의 `min`/`argmax` |
| `IndexError` | 인덱스가 범위 밖이거나 허용하지 않는 형태예요 |
| `KeyError` | 데이터프레임의 `.loc`에서 없는 라벨 |
| `BufferError` | 버퍼나 DLPack으로 데이터를 주고받을 수 없어요(CPU가 아닌 장치, 읽기 전용 배열을 옛 DLPack 형식으로, 버퍼 내보내기 실패) |
| `OverflowError` | int64 밖의 Python int를 int64로 바꿔야 해요. float로 계산할 수 있으면 float로 바꿔요(`float_arr + 2**70`은 정상). float로 바꿔야 하는데 double 범위도 넘으면(`10**400`) 역시 `OverflowError`예요 |
| `MemoryError` | 배열 하나의 요청이 이 컴퓨터의 물리 메모리보다 커요. 할당하기 전에 내요 |
| `LinAlgError(ValueError)` | 선형대수의 수치적 실패. 희소 직접 풀이의 특이 행렬도 같은 예외예요(`spsolve(): singular matrix`) |

경고는 어느 영역도 내지 않아요. 문제가 있으면 에러를 내요. 배열의 원소별 연산은 원소의 값 때문에 실패하지 않아요(정수 오버플로는 wrap, `a // 0`은 0).

`tests/test_error_messages.py`가 세 영역의 메시지 형식을 함께 고정해요. 공개 함수가 자기 이름을 붙이는지, 연산자와 인덱싱이 Python 형식을 지키는지, 어떤 메시지도 문서 절을 인용하지 않는지를 봐요.

## GIL

### 규칙

GIL(Global Interpreter Lock)은 CPython에서 한 번에 한 스레드만 Python 객체를 다루게 하는 잠금이에요. C++ 계산이 GIL을 쥔 채 오래 돌면 다른 Python 스레드가 그동안 멈춰요. 반대로 GIL을 놓은 동안에는 Python 객체(참조 카운트 포함)를 만지면 안 돼요.

stardust의 규칙은 이래요.

1. **일이 영역의 기준값 이상이면 스레드 수가 몇이든 GIL을 놓아요.** 기준값보다 작은 일은 GIL을 쥔 채 그 자리에서 돌아요. 그래서 `sd.set_num_threads(1)`이어도 큰 계산이 도는 동안 다른 Python 스레드가 돌고, 작은 호출은 GIL을 놓았다 다시 잡는 비용을 내지 않아요. 기준값은 스레드풀로 나누기 시작하는 일의 양과 같아요.
2. **GIL을 놓은 구간에서는 Python 객체를 만지지 않아요.** 풀의 태스크도, 호출 스레드에서 GIL 없이 도는 구간도 같아요. `NDArray`를 복사하거나 없애는 것조차 `base`(`nb::object`)의 참조 카운트를 바꾸므로, 필요한 `NDArray` 복사는 구간 밖에서 미리 해요. 결과 배열과 namedtuple도 구간이 끝난 뒤 GIL을 다시 쥐고 만들어요.
3. **에러 위치도 GIL 밖에서 정하고, 메시지는 안에서 만들어요.** 여러 태스크가 검사하다 실패하면 `parallel::FirstRow`가 가장 앞의 위치를 atomic으로 골라요(데이터프레임의 검사가 써요). 메시지(Python 문자열)는 병렬 구간이 끝난 뒤 만들어요. 그래서 실행마다 같은 위치를 보고하고, 지금은 스레드 수가 달라도 같은 위치예요.

### 구현

```cpp
// csrc/parallel/pool.cpp (줄인 발췌)
void parallel_for(std::int64_t ntasks, const std::function<void(std::int64_t)>& fn, std::int64_t task_ns) {
    if (ntasks <= 0) return;
    if (ntasks == 1 || t_in_task) {
        for (std::int64_t t = 0; t < ntasks; ++t) fn(t);  // 하나뿐, 중첩: GIL은 그대로 두고 그냥 루프
        return;
    }
    GilRelease release;
    if (pool().threads() <= 1) {                          // 1스레드: GIL 없이 태스크를 차례로
        for (std::int64_t t = 0; t < ntasks; ++t) fn(t);
        return;
    }
    pool().run(ntasks, fn, task_ns);  // 풀로 나눠요. 다른 Python 스레드의 일로 풀이 바쁘면 run()이 직렬로 돌려요
}

GilRelease::GilRelease() {
    if (!t_in_task && PyGILState_Check()) state_ = PyEval_SaveThread();  // 이 스레드가 GIL을 쥐고 있을 때만
}
GilRelease::~GilRelease() {
    if (state_) PyEval_RestoreThread(static_cast<PyThreadState*>(state_));
}

// csrc/parallel/pool.hpp: 기준값 이상인데 호출 스레드에서 도는 구간
class Unlocked {
public:
    explicit Unlocked(bool release) { if (release) release_.emplace(); }
private:
    std::optional<GilRelease> release_;
};
```

`PyEval_SaveThread`는 GIL을 놓고 현재 스레드 상태를 돌려주고, `PyEval_RestoreThread`가 그 상태로 GIL을 다시 잡아요 [6]. RAII(객체의 수명에 자원을 묶는 C++ 관용구)라서 태스크가 예외를 던져도 소멸자가 GIL을 되찾아요. 생성자는 태스크 안이 아닌지, `PyGILState_Check`로 GIL을 지금 쥐고 있는지를 먼저 봐서, GIL이 없는 곳에서 만들어지면 아무 일도 하지 않아요. 그래서 놓는 구간이 겹쳐도 돼요.

**놓는 곳은 두 가지예요.** `parallel_for`는 태스크가 둘 이상이면 놓아요. 풀로 나눌 때도, 1스레드라 호출 스레드가 태스크를 차례로 돌 때도 같아요. 태스크 수는 일의 양만으로 정해지므로 놓는지도 스레드 수와 상관없어요. `task_ns`는 잠든 워커를 깨울지만 정해요([스레드풀과 결정성](/internals/core/threads/)). 태스크가 하나이면 호출하는 쪽의 크기 판단이라 GIL을 그대로 둬요. 일이 기준값 이상인데 `parallel_for` 없이 호출 스레드에서 도는 구간(1스레드나 바쁜 풀이라 직렬 경로를 고른 경우, 자를 축이 없는 경우, 나누는 경로가 없는 직렬 루프)은 `Unlocked(work >= 기준값)`으로 감싸요. 배열의 이터레이터와 조각 실행기(`for_pieces`), linalg의 배치 드라이버와 긴 합, frame의 직렬 구간이 이것을 써요. 줄마다 불리는 커널 안에는 두지 않고, 호출 한 번에 한 번 지나는 곳에만 둬요.

**큰 BLAS 호출도 놓아요.** `matmul`의 float64·complex128 경로는 곱셈-덧셈이 $2^{15}$개(`kBlasTaskWork`) 이상이면, `cov`와 `corrcoef`는 언제나 BLAS를 부르는 동안 GIL을 놓아요. 이 호출은 Accelerate가 안에서 스레드를 정하므로(`sd.set_num_threads`를 따르지 않아요) 1스레드 설정에서도 여러 코어를 쓸 수 있어요. BLAS와 행렬을 모으는 준비 코드는 Python 객체를 만지지 않아요.

**기준값 이상이어도 GIL을 쥐는 곳**도 있어요. Python 객체를 읽거나 만드는 변환(리스트를 받는 `asarray`, `tolist`), 인덱스 배열 하나로 하는 대입 `x[idx] = v`(같은 인덱스의 마지막 쓰기가 남도록 한 스레드에서 순서대로 써요), `unique_all`·`unique_counts`·`unique_inverse`의 묶음 세기, 메모리를 받기만 하는 `zeros`와 `eye`예요. 사용자의 Python 함수를 부르는 `sd.optimize`의 반복과 `sd.regression.nls`의 반복, `sd.integrate`와 `sd.differentiate`의 반복도 GIL을 쥔 채 돌아요. 반복마다 그 함수를 불러야 하기 때문이에요.

### 영역마다의 기준값

| 영역 | GIL을 놓는 일의 양 |
|:---:|---|
| array | float64 덧셈 2¹⁵개 분량(`kParallelThreshold`). 원소 하나가 무거운 함수는 그만큼 적은 원소부터, 배열 둘만 움직이는 원소별 연산(복사, `abs(x)`)은 1.5배 많은 원소부터, bool 배열은 바이트로 세어 262,144 원소부터 |
| linalg | 호출 하나의 추정 계산 시간 10µs(`kParallelMinNs`) 이상. 행렬 하나여도 같아요 |
| special, stats의 분포 함수 | 배열의 이터레이터를 거치므로 배열과 같아요 |
| random | 배열과 같은 기준을 `for_pieces`로 적용해요(원소 4096개부터). `permutation`과 비복원 추출은 언제나 |
| frame | 2¹⁷행(`frame/parallel.hpp`의 `Unlocked`) |
| htest | 배열과 같은 기준을 배치의 줄에 적용해요(줄 수 × 줄 하나의 비용, `htest/lanes.hpp`). 재표본에서 사용자의 `statistic`을 부르는 동안은 Python 층이라 쥐어요 |
| sparse | 저장된 원소와 출력 크기로 센 일 2¹⁵개 분량부터(`sparse/parallel.hpp`). Accelerate LU의 분해와 풀이는 언제나 놓아요. 반복법과 고유값 풀이는 연산자가 Python 함수(`LinearOperator`)이면 쥐고, 희소 행렬이면 한 걸음의 일이 기준값 이상일 때 풀이 전체에서 놓아요 |
| integrate | 표본 규칙은 배열과 같은 기준을 줄 수 × 길이에, `fixed_quad`의 마디 계산(n > 100)은 점화식 걸음 수에 적용해요. `quad` 계열, `quad_vec`, `cubature`의 반복은 사용자 함수를 부르므로 내내 쥐어요. `tanhsinh`과 `nsum`의 원소 패스는 남은 원소 수 × 원소마다의 점 수가 2¹⁵개부터 놓아요 |
| differentiate | 반복은 쥐어요. `derivative`의 원소 패스는 `tanhsinh`과 같은 기준, `jacobian`·`hessian`의 항목 갱신은 남은 항목 2¹⁵개부터 놓아요 |
| optimize | 반복은 쥐어요. 사용자 함수를 부르는 사이의 큰 선형대수(BFGS의 H 갱신, L-BFGS-B의 방향 계산, Nelder–Mead의 무게중심, 야코비안의 QR 등)는 linalg와 같은 10µs 규칙(추정 2×10⁵ 플롭), 배치 스칼라의 원소 패스는 2¹⁵개부터 놓아요. 사용자 함수가 없는 `lsq_linear`과 `nnls`는 2mn² > 2×10⁵이면 풀이 전체에서 놓아요 |

모든 영역이 같은 규칙을 쓰고, 다른 것은 기준값과, 사용자 함수를 부르는 동안 쥐는 곳(optimize, integrate, differentiate, Python 연산자를 받은 희소 풀이)뿐이에요. 비용은 기준값 이상인 호출마다 GIL을 한 번 놓았다 잡는 것으로, 호출당 0.1µs 안팎이에요([스레드풀과 결정성](/internals/core/threads/)).

### 다른 스레드에서 GIL을 다시 잡는 곳

마지막 참조가 어느 스레드에서 사라질지 모르는 객체는 소멸자에서 GIL을 직접 잡아요.

- **가져온 버퍼**(`Buffer::adopt`)의 소멸자는 `PyBuffer_Release`를 부르기 전에 `PyGILState_Ensure`로 GIL을 잡아요. `PyBuffer_Release`가 내보낸 객체의 참조 카운트를 내리기 때문이에요.
- **DLPack으로 내보낸 텐서**의 deleter는 소비자가 아무 스레드에서나 부를 수 있어서, 역시 GIL을 잡고 지워요.

## 버퍼 프로토콜

버퍼 프로토콜(PEP 3118)은 Python 객체가 자기 메모리를 다른 객체에게 복사 없이 보여 주는 C 수준의 표준이에요 [7]. 내보내는 쪽은 메모리 주소, 원소 형식(format 문자열), shape, strides를 담은 `Py_buffer` 구조체를 채워 주고, 받는 쪽은 다 쓰면 `PyBuffer_Release`로 돌려줘요. numpy, `memoryview`, `bytearray`가 이 프로토콜을 써요.

### 내보내기

`bf_getbuffer` 슬롯(버퍼를 요청받았을 때 불리는 C 함수)을 직접 구현하고, 속성 슬롯과 같은 표에 넣어 nanobind의 `nb::type_slots`로 타입에 붙여요.

```cpp
// csrc/bind/array_bind.cpp (줄인 발췌)
static_assert(sizeof(Py_ssize_t) == sizeof(std::int64_t), "shape/strides are handed out as Py_ssize_t*");
const char* const kFormats[kNumArrayDTypes] = {"?", "q", "d", "Zd"};

int getbuffer(PyObject* self, Py_buffer* view, int flags) {
    const NDArray& a = *nb::inst_ptr<NDArray>(self);
    if ((flags & PyBUF_WRITABLE) && !a.writeable) return fail("array is read-only");
    if ((flags & PyBUF_C_CONTIGUOUS) == PyBUF_C_CONTIGUOUS && !a.c_contiguous) return fail("array is not C-contiguous");
    // ... F_CONTIGUOUS, ANY_CONTIGUOUS도 같은 식
    const bool with_strides = (flags & PyBUF_STRIDES) == PyBUF_STRIDES;
    if (!with_strides && !a.c_contiguous) return fail("array is not C-contiguous; request strides");

    view->buf = a.data;
    view->obj = Py_NewRef(self);          // 내보낸 동안 배열(과 Buffer)을 살려 둬요
    view->len = a.nbytes();
    view->readonly = !a.writeable;
    view->itemsize = a.itemsize();
    view->format = (flags & PyBUF_FORMAT) ? const_cast<char*>(kFormats[int(a.dtype)]) : nullptr;
    view->ndim = a.ndim;
    view->shape = reinterpret_cast<Py_ssize_t*>(const_cast<std::int64_t*>(a.shape.data()));
    view->strides = with_strides ? reinterpret_cast<Py_ssize_t*>(const_cast<std::int64_t*>(a.strides.data())) : nullptr;
    return 0;
}

// getbuffer는 위 "속성"에서 본 ndarray_slots 표에 Py_bf_getbuffer로 들어가요.
auto cls = nb::class_<NDArray>(m, "ndarray", nb::type_slots(ndarray_slots));
```

- **format 문자열**: `?`(bool, 1바이트), `q`(int64, C의 `long long`), `d`(float64, `double`), `Zd`(complex128, `double` 두 개). PEP 3118의 `Z` 접두사가 복소수를 뜻해요.
- **shape와 strides는 복사하지 않아요.** `NDArray` 안의 고정 배열(`std::array<int64_t, 32>`)을 그대로 가리켜요. `Py_ssize_t`가 64비트라는 것을 `static_assert`로 컴파일 시점에 확인해요. `NDArray`의 shape와 strides는 만든 뒤 바뀌지 않고(속성에 setter가 없어요), `view->obj`가 배열 객체를 붙잡고 있으니 이 포인터는 내보낸 동안 유효해요.
- **요청 플래그를 지켜요.** 받는 쪽이 쓰기 가능을 요구했는데 읽기 전용이면, 연속을 요구했는데 아니면 `BufferError`로 거절해요. strides를 요청하지 않은 소비자는 C 연속 메모리를 가정하므로, 그때 C 연속이 아니면 거절해요.
- **strides가 0이어도 내보내요.** `broadcast_to`의 결과처럼 같은 메모리를 여러 원소가 공유하는 배열은 stride가 0인 채로, 읽기 전용으로 나가요.

```python
>>> m = sd.asarray([[1.0, 2.0], [3.0, 4.0]])
>>> v = memoryview(m)
>>> v.format, v.shape, v.strides, v.readonly
('d', (2, 2), (16, 8), False)
>>> memoryview(m.T).strides
(8, 16)
>>> b = memoryview(sd.broadcast_to(sd.asarray([1.0, 2.0]), (3, 2)))
>>> b.strides, b.readonly
((0, 8), True)
```

numpy가 우리 메모리를 읽는 것도 이 길이에요. `np.asarray(x)`는 복사 없이 같은 메모리를 보는 numpy 배열을 만들어요. 테스트도 결과를 이 길로 numpy에 가져와 비트를 비교해요.

### 가져오기

`sd.asarray(obj)`는 입력의 종류를 이 순서로 봐요(`array/ops/asarray.cpp`).

1. `sd.ndarray` → 그대로 돌려주거나, `dtype=`/`copy=True`면 변환·복사
2. 정확한 `numpy.ndarray`로 아래 조건에 맞는 것 → 버퍼 프로토콜을 거치지 않고 바로 공유(아래 "numpy 배열은 바로 공유해요")
3. Python 스칼라 → ValueError (0차원 배열은 없어요)
4. 중첩된 list/tuple → shape를 읽고 dtype을 추론해 복사
5. `range` → int 리스트로 바꿔 4번 길로. `range`는 버퍼가 아니에요
6. 버퍼 프로토콜을 지원하는 객체 → 아래

버퍼는 `PyObject_GetBuffer(obj, &view, PyBUF_RECORDS_RO)`로 받아요. strides와 format을 요청하고, 읽기 전용 버퍼도 받겠다는 뜻이에요. 그다음 format 문자열을 해석해요.

| format (`@`, `=`, `<` 접두사 무시) | 원소 | 자연스러운 dtype | 공유 가능 |
|:---:|:---:|:---:|:---:|
| `?` | bool | bool | ✓ |
| `b h i l q n` (크기 1·2·4·8) | int8~int64 | int64 | int64만 |
| `B H I L Q N` (크기 1·2·4) | uint8~uint32 | int64 | ✗ |
| `B H I L Q N` (크기 8) | uint64 | TypeError | — |
| `e f d` | float16, 32, 64 | float64 | float64만 |
| `Zf`, `Zd` | complex64, 128 | complex128 | complex128만 |
| `>` 또는 `!` 접두사 | big-endian | 위와 같음 | ✗ (바이트를 뒤집으며 복사) |

복사 없이 공유하는 조건은 넷이에요.

1. **format이 우리 저장 타입과 정확히 같아요.** int32 버퍼를 int64 배열로 "공유"할 수는 없어요.
2. **native 바이트 순서예요.** 이 기계는 little-endian이라 `<`, `=`, `@`가 native예요.
3. **원소가 자연 정렬되어 있어요.** 시작 주소와 모든 stride가 원소의 정렬 단위(bool 1, int64·float64 8, complex128 8)의 배수예요. 커널이 `alignof(T)` 정렬을 가정하므로, 정렬되지 않은 버퍼는 복사해요.
4. **bool 버퍼의 모든 바이트가 0이나 1이에요.** 아래에서 설명해요.

```cpp
// csrc/array/ops/asarray.cpp (줄인 발췌): 공유하는 길
if (shareable && aligned && valid && copy != true) {
    foreign.data = static_cast<std::byte*>(view.buf);
    foreign.writeable = !view.readonly;                 // 읽기 전용 버퍼 → 쓰기 금지 배열
    foreign.base = nb::borrow(view.obj ? view.obj : obj.ptr());
    foreign.update_flags();
    guard.armed = false;                                // Py_buffer의 소유권을 Buffer로 넘겨요
    foreign.buffer = Buffer::adopt(view);
    return wrap(std::move(foreign));
}
```

`ViewGuard`는 `Py_buffer`를 소멸자에서 놓아 주는 작은 RAII 객체예요. 중간에 예외가 나면 버퍼가 놓이고, 공유에 성공하면 `armed = false`로 소유권을 `Buffer::adopt`에 넘겨요. 그 뒤에는 Buffer가 마지막 참조와 함께 버퍼를 놓아요.

공유할 수 없으면 복사하면서 변환해요. 정보 손실이 없는 확장(int8/16/32, uint8/16/32 → int64, float16/32 → float64, complex64 → complex128)만 해요. `copy=False`이면 복사가 필요한 순간 ValueError예요. 복사 결과는 원본의 메모리 축 순서를 따라요(`new_array_like`: F 순서 원본이면 F 순서 결과). big-endian은 원소마다 바이트를 뒤집는데, complex는 실수부와 허수부를 따로 뒤집어요(16바이트 통째로 뒤집으면 두 부분의 자리가 바뀌어요).

```python
>>> a = np.arange(6.0).reshape(2, 3)
>>> y = sd.asarray(a)
>>> y.base is a
True
>>> a[0, 0] = 100.0
>>> y[0, 0]
100.0
>>> sd.asarray(np.arange(3, dtype=np.float32)).base is None
True
>>> sd.asarray(np.arange(3, dtype=np.float32), copy=False)
Traceback (most recent call last):
  ...
ValueError: asarray(): copy=False, but this buffer can only be converted by copying
```

**numpy 배열은 바로 공유해요.** numpy는 버퍼를 내보낼 때마다 format 문자열을 다시 만들고 캐시와 비교해서, 그것이 `sd.asarray(numpy 배열)` 시간의 절반이었고 `Py_buffer` 관리가 나머지였어요. 그래서 정확히 `numpy.ndarray`(하위 클래스는 아니에요)이면 numpy의 공개 C 구조체에서 바로 읽어요(`share_numpy`).

```cpp
// csrc/array/ops/asarray.cpp (share_numpy의 앞부분): numpy의 공개 C 구조체에서 읽는 필드
struct NumpyArrayFields {
    PyObject_HEAD char* data;
    int nd;
    Py_ssize_t* dimensions;
    Py_ssize_t* strides;
    PyObject* base;
    PyObject* descr;
    int flags;
};
struct NumpyDescrHead {
    PyObject_HEAD PyTypeObject* typeobj;
    char kind;
    char type;
    char byteorder;
    char former_flags;
    int type_num;
};
```

- 두 구조체는 `numpy/_core/include/numpy/ndarraytypes.h`의 `PyArrayObject_fields`와 `PyArray_Descr`의 앞부분이에요. numpy 1.x와 2.x에서 자리가 같아요. numpy 타입은 이름(`tp_name`이 `"numpy.ndarray"`)으로 한 번 알아보고 포인터를 저장해요. numpy를 import하지 않아요.
- 조건은 버퍼 경로의 공유 조건과 같아요. 원소 타입이 우리 넷 중 하나(`type_num`: bool 0, long 7·longlong 9, double 12, cdouble 15)이고, native 바이트 순서이고, 시작 주소와 stride가 정렬되어 있고, `dtype=`이 다르지 않고 `copy=True`가 아니어야 해요. bool은 0/1 검사를 똑같이 해요.
- 원소가 없는 배열은 버퍼 경로로 보내요. numpy의 빈 배열은 stride가 0일 수 있는데 버퍼 내보내기는 C 연속 stride를 주기 때문이에요.
- 결과의 `base`는 그 numpy 배열이고 Buffer는 없어요. 메모리는 numpy 배열에 대한 참조가 살려 둬요. 버퍼 내보내기도 같은 일을 해요(numpy는 다른 곳이 참조하는 배열의 크기를 바꾸지 않아요). 쓰기 가능 여부도 numpy의 내보내기와 같아요(`WRITEABLE`이고 `WARN_ON_WRITE`가 아닐 때).
- 조건에 맞지 않으면(big-endian, float32, 하위 클래스, 정렬 안 됨 등) 빈 객체를 돌려주고 버퍼 경로로 가요. 그래서 결과는 어느 길이든 같은 뷰, 같은 `.base`예요.

**uint64는 값을 보지 않고 거절해요.** uint64를 int64로 바꾸면 2⁶³ 이상의 값이 손실돼요. 값을 훑어서 범위 안이면 받는 방법도 있지만, 그러면 같은 코드가 데이터에 따라 성공하거나 실패해요. 암묵적 변환도 값이 아니라 dtype만 보고 판단하므로, 같은 이유로 `dtype=`을 주어도 TypeError예요. 데이터프레임도 같아요.

### bool 버퍼의 바이트 검사

bool 커널 중에는 바이트를 정수로 더하는 것이 있어요. `sum`은 바이트를 더해 `True`를 세고, 마스크 인덱싱의 분기 없는 압축은 모든 원소를 작은 버퍼의 `buf[cnt]`에 쓰고 `cnt += 마스크 바이트`로 다음 자리를 정해요. 바이트가 0과 1뿐이면 맞지만, 바깥에서 온 버퍼에 `2`가 들어 있으면 `sum`은 틀린 개수를 내고, 압축은 미리 센 결과 크기와 쓰는 자리가 어긋나요.

모든 bool 커널에 방어 코드를 넣는 대신 입구 한 곳에서 막아요. 공유하기 전에 모든 바이트의 OR을 계산해서 1 이하인지 봐요.

$$
\Bigl(\bigvee_{i} b_i\Bigr) \le 1 \iff \forall i,\ b_i \in \{0, 1\}
$$

분기 없는 OR 리덕션 하나라 컴파일러가 벡터화해요. 원소 100만 개에서 8.3µs예요. 원소마다 `b != 0 && b != 1`을 비교하는 방식은 235µs예요. 0/1이 아닌 바이트가 있으면 0/1로 정규화해서 복사해요(`copy=False`이면 에러).

<Callout type="warn" title="공유한 뒤 바깥에서 바꾸면">
  검사는 가져오는 순간에만 해요. 공유한 numpy bool 배열에 나중에 numpy 쪽에서 `2` 같은 바이트를 써 넣는 것은 막지 않아요. 이것까지 막으려면 모든 bool 커널이 매번 검사해야 해요.
</Callout>

## DLPack

DLPack은 배열 라이브러리 사이에서 텐서를 복사 없이 넘기는 C 구조체 규약이에요 [8]. 버퍼 프로토콜과 달리 장치(CPU, GPU …)와 정확한 dtype 코드를 담고, Python에서는 `PyCapsule`(C 포인터를 담는 Python 객체)에 넣어 주고받아요. Array API는 `x.__dlpack__()`, `x.__dlpack_device__()`, `from_dlpack(x)`를 표준으로 정해요 [2].

stardust는 CPU와 배열 dtype 넷만 지원해요. DLPack 1.0의 구조체는 헤더를 들여오지 않고 직접 적어요.

```cpp
// csrc/array/ops/dlpack.cpp (줄인 발췌): DLPack 1.0 ABI
struct DLTensor {
    void* data;
    DLDevice device;           // {device_type, device_id}, CPU = (1, 0)
    std::int32_t ndim;
    DLDataType dtype;          // {code, bits, lanes}
    std::int64_t* shape;
    std::int64_t* strides;     // 원소 단위, null이면 C 연속
    std::uint64_t byte_offset;
};
struct DLManagedTensorVersioned {          // capsule 이름 "dltensor_versioned"
    DLPackVersion version;
    void* manager_ctx;
    void (*deleter)(DLManagedTensorVersioned*);
    std::uint64_t flags;                   // 1: 읽기 전용, 2: 복사됨
    DLTensor dl_tensor;
};
// 옛 형식 DLManagedTensor (capsule 이름 "dltensor")에는 version과 flags가 없어요
```

| 배열 dtype | DLPack `code`, `bits` |
|:---:|:---:|
| bool | `kDLBool`(6), 8 |
| int64 | `kDLInt`(0), 64 |
| float64 | `kDLFloat`(2), 64 |
| complex128 | `kDLComplex`(5), 128 |

### 내보내기 (`x.__dlpack__`)

```cpp
// 줄인 발췌
struct Export {                      // capsule이 살려 두는 것
    NDArray keep;                    // 배열의 뷰: buffer와 base를 붙잡아요
    std::vector<std::int64_t> shape, strides;   // DLTensor가 가리키는 배열 (strides는 원소 단위)
};
```

1. `stream`은 `None`이어야 하고, `dl_device`는 `None`이거나 `(1, 0)`이어야 해요. 다른 장치면 `BufferError`, int 두 개의 tuple이 아니면 `TypeError`예요. `max_version`도 int 두 개의 tuple이어야 해요.
2. `max_version`의 major가 1 이상이면 버전 있는 형식, `None`이면 옛 형식으로 내보내요. 소비자가 받을 수 있는 가장 새 형식을 알려 주는 것이 `max_version`이에요.
3. `copy=True`면 복사본을 내보내고 "복사됨" 표시를 달아요. 아니면 `view_of`로 만든 뷰(같은 Buffer, 같은 base)를 `Export`에 담아요.
4. 쓰기 금지 배열은 버전 있는 형식의 읽기 전용 표시로 내보내요. 옛 형식에는 그 표시가 없어서 `BufferError`예요. numpy도 같아요.
5. deleter는 GIL을 잡고 `Export`와 텐서 구조체를 지워요. 아무도 소비하지 않은 capsule은 capsule 소멸자가 deleter를 불러요. capsule 이름이 소비된 뒤의 `used_...`로 바뀌어 있으면 소멸자는 아무것도 하지 않아요(소비자가 책임져요).

### 가져오기 (`sd.from_dlpack`)

```cpp
// csrc/array/ops/dlpack.cpp (from_dlpack의 줄인 발췌)
// numpy 배열은 생산자를 부르지 않고 asarray와 같은 길로 바로 공유해요
if (nb::object r = share_numpy_array(x, std::nullopt, copy); r.is_valid()) return r;
static PyObject* const s_dlpack = PyUnicode_InternFromString("__dlpack__");
static PyObject* const s_device = PyUnicode_InternFromString("__dlpack_device__");
static PyObject* const s_kwnames = Py_BuildValue("(ss)", "max_version", "copy");
static PyObject* const s_version = Py_BuildValue("(ii)", kMajor, kMinor);
PyObject* raw = nullptr;
if (PyObject_GetOptionalAttr(x.ptr(), s_dlpack, &raw) < 0) throw nb::python_error();
if (!raw)
    throw nb::type_error(("'x' must support the DLPack protocol (__dlpack__), not " + py_type_name(x)).c_str());
const nb::object method = nb::steal(raw);
// ... (__dlpack_device__도 같은 식으로 한 번 찾아 CPU인지 확인)
nb::object cap;
{
    PyObject* args[] = {s_version, copy ? (*copy ? Py_True : Py_False) : Py_None};
    PyObject* c = PyObject_Vectorcall(method.ptr(), args, 0, s_kwnames);
    if (c) {
        cap = nb::steal(c);
    } else {
        if (!PyErr_ExceptionMatches(PyExc_TypeError)) throw nb::python_error();
        PyErr_Clear();
        PyObject* c0 = PyObject_CallNoArgs(method.ptr());  // a producer from before DLPack 1.0 takes no keywords
        if (!c0) throw nb::python_error();
        cap = nb::steal(c0);
    }
}

// Take ownership first, so every error below still frees the tensor.
// ...
if (PyCapsule_IsValid(cap.ptr(), "dltensor_versioned")) {
    auto* m = static_cast<DLManagedTensorVersioned*>(PyCapsule_GetPointer(cap.ptr(), "dltensor_versioned"));
    PyCapsule_SetName(cap.ptr(), "used_dltensor_versioned");
    PyObject* own = PyCapsule_New(m, "sd_dlpack_owner", &owner_versioned);
    if (!own) {  // we own the tensor now: free it before failing
        m->deleter(m);
        throw nb::python_error();
    }
    owner = nb::steal(own);
    if (m->version.major > kMajor)
        throw nb::buffer_error(("DLPack version " + std::to_string(m->version.major) + "." +
                                std::to_string(m->version.minor) + " is newer than the supported 1.x")
                                   .c_str());
    t = &m->dl_tensor;
    // ...
}
```

- **numpy 배열은 바로 공유해요.** 장치 인자를 확인한 뒤, 정확한 `numpy.ndarray`이면 `asarray`와 같은 공유([버퍼 프로토콜](#버퍼-프로토콜)의 numpy 길)를 먼저 해 봐요. `__dlpack__`이 설명할 뷰와 같은 뷰이고, `base`가 capsule 대신 그 numpy 배열이에요. 두 번의 메서드 호출과 capsule 둘을 만들지 않아서 numpy 배열을 가져오는 일이 훨씬 싸요. `copy=True`이거나 그 조건에 맞지 않으면 아래의 일반 경로예요.
- **장치를 먼저 물어봐요.** `__dlpack_device__`가 있으면 CPU인지 확인하고, 아니면 `BufferError`예요. 그 답이 int 두 개의 tuple이 아니면 `TypeError`예요. 이름, 키워드 이름 tuple, 버전 tuple은 처음 한 번만 만들어요.
- **Python 수준의 일을 줄여요.** 속성은 `PyObject_GetOptionalAttr`로 한 번씩만 찾아요(있는지 확인하고 다시 꺼내는 두 번이 아니라). 속성 이름은 intern된 문자열이라 조회가 해시 비교로 끝나요. 키워드 인자는 vectorcall(인자를 C 배열과 키워드 이름 tuple로 넘기는 호출 규약)로 넘겨, 호출마다 dict나 tuple을 만들지 않아요.
- **옛 생산자에게 물러나요.** `__dlpack__(max_version=..., copy=...)`가 TypeError를 내면 키워드 없이 다시 불러요. DLPack 1.0 전의 생산자는 키워드를 몰라요.
- **소유권이 먼저예요.** capsule의 이름을 `used_...`로 바꾸는 순간 텐서의 해제 책임이 우리에게 와요. 그래서 바로 우리 소유자 capsule(`sd_dlpack_owner`)로 감싸고, 그 뒤에 장치, dtype, 0차원, 차원 수, 버전을 검사해요. 어느 검사에서 에러가 나도 소유자 capsule이 사라지면서 생산자의 deleter가 불려요. 소유자 capsule조차 만들지 못하면 deleter를 직접 부르고 에러를 내요.
- **strides는 원소 단위예요.** DLPack의 strides는 원소 단위라 itemsize를 곱해 바이트로 바꾸고, `byte_offset`을 시작 주소에 더해요.
- **정렬과 bool 규칙은 버퍼 프로토콜과 같아요.** 정렬되지 않았거나 bool 바이트가 0/1이 아니면 C 순서로 복사해요.
- **`copy=True`의 두 번 복사를 피해요.** 생산자가 "복사됨" 표시를 달았으면 다시 복사하지 않아요. 표시가 없으면(옛 형식이거나 생산자가 무시함) 우리가 복사해요.

```python
>>> n = np.arange(4.0)
>>> sd.from_dlpack(n).base is n
True
>>> k = sd.from_dlpack(sd.arange(4.0))
>>> k.base
<capsule object "sd_dlpack_owner" at 0x...>
>>> k.tolist()
[0.0, 1.0, 2.0, 3.0]
>>> ro = sd.broadcast_to(sd.asarray([1.0, 2.0]), (3, 2))
>>> ro.__dlpack__()
Traceback (most recent call last):
  ...
BufferError: __dlpack__(): cannot export a read-only array with the legacy DLPack format; pass max_version=(1, 0)
>>> ro.__dlpack__(max_version=(1, 0))
<capsule object "dltensor_versioned" at 0x...>
```

DLPack의 일반 경로로 가져온 배열의 `buffer`(`shared_ptr<Buffer>`)는 비어 있어요. 메모리를 붙잡는 것은 `base`인 소유자 capsule이에요. 그래서 이 배열의 뷰도 `base`로 같은 capsule을 쥐어서 메모리를 지켜요.

## 수명과 소유권

### 두 개의 고리: `buffer`와 `base`

배열이 가리키는 메모리가 살아 있게 하는 고리는 둘이에요.

- **`buffer`** (`std::shared_ptr<Buffer>`): C++ 쪽 소유. 마지막 `shared_ptr`가 사라지면 Buffer가 메모리를 해제하거나(자기 메모리), 가져온 `Py_buffer`를 놓아요(외부 메모리). 메모리를 붙잡는 데만 쓰고 아무 코드도 읽지 않아요. 그래서 `base`가 메모리를 붙잡는 배열은 `buffer`가 비어 있어요.
- **`base`** (`nb::object`): Python 쪽 주인. 사용자가 `.base`로 보는 객체예요. 배열이 메모리를 직접 가지면 비어 있고(`None`), 다른 Python 객체의 메모리를 보면 그 객체예요.

| 배열을 만든 방법 | `buffer` | `base` (`.base`) | 메모리를 붙잡는 것 |
|---|---|---|---|
| 생성 함수, 연산 결과 | 새 Buffer | `None` | Buffer |
| 메모리를 직접 가진 배열의 뷰 (슬라이스, 전치, `reshape`) | 비어 있음 | 원본 배열 | `base`(원본 배열)가 원본의 Buffer를 살려 둬요 |
| 뷰나 외부 메모리 배열의 뷰 | 원본과 같은 Buffer | 원본의 `base` | Buffer와 `base` |
| numpy 배열을 바로 공유 (`asarray`, `from_dlpack`) | 비어 있음 | 그 numpy 배열 | numpy 배열에 대한 참조 |
| 버퍼 프로토콜로 가져옴 | `Buffer::adopt(Py_buffer)` | 내보낸 객체 (`view.obj`) | `Py_buffer`가 쥔 내보낸 객체 |
| DLPack의 일반 경로로 가져옴 | 비어 있음 | 소유자 capsule | capsule의 소멸자가 생산자 deleter를 불러요 |
| linalg 결과 (`new_array_strided`) | 새 Buffer | `None` | Buffer |
| `Series.to_array()` (읽기 전용 뷰) | Column의 Buffer와 같은 것 | `None` | Buffer. `use_count()`가 늘어 frame의 쓰기가 먼저 복사해요 |

### 뷰의 `base`는 최종 주인으로 접어요

```cpp
// csrc/bind/pyutil.cpp (발췌)
NDArray view_of(nb::handle x) {
    const NDArray& a = as_ndarray(x);
    NDArray v = NDArray::meta_of(a);  // data, dtype, shape, strides, 플래그만 복사
    if (a.base.is_valid()) {
        // x가 뷰이거나 외부 메모리: 같은 주인, 같은 Buffer(외부 메모리를 붙잡는 Py_buffer일 수 있어요)
        v.base = a.base;
        v.buffer = a.buffer;
    } else {
        // x가 메모리를 직접 가져요: x에 대한 참조가 x의 Buffer를 살려 두니 뷰는 Buffer를 갖지 않아요
        v.base = nb::borrow(x);
    }
    return v;
}
```

뷰의 뷰를 만들어도 `base`는 중간 뷰가 아니라 메모리의 최종 주인을 가리켜요. 그러지 않으면 `x[1:][1:][1:]…`가 중간 뷰를 줄줄이 붙잡는 사슬이 되고, 중간 뷰가 쓸데없이 살아남아요. numpy 2.x도 같은 규칙이에요.

메모리를 직접 가진 배열의 뷰는 Buffer를 갖지 않아요. 원본 배열에 대한 참조(`base`)가 이미 원본의 Buffer를 살려 두기 때문이에요. 뷰를 만들고 버릴 때마다 `shared_ptr`의 원자적 증감이 두 번 줄어요. 원본이 이미 뷰이거나 외부 메모리이면 그 `base`와 Buffer를 그대로 물려받아요. 버퍼 프로토콜로 가져온 배열의 Buffer는 `Py_buffer` 내보내기 자체라서, 그것을 놓으면 내보낸 쪽(`bytearray` 등)이 메모리를 옮길 수 있기 때문이에요.

```python
>>> base = sd.asarray([[1.0, 2.0], [3.0, 4.0]])
>>> row = base[0]
>>> row[1:].base is base
True
>>> a = np.arange(4.0)
>>> sd.asarray(a)[::2].base is a
True
```

### 내보낸 쪽을 살려 두기

- **버퍼 프로토콜로 내보낼 때**: `view->obj = Py_NewRef(self)`가 배열 객체의 참조를 하나 올려요. `memoryview`나 numpy 배열이 살아 있는 동안 우리 배열과 그 Buffer가 살아 있어요.
- **버퍼 프로토콜로 가져올 때**: `Py_buffer` 안의 `obj`가 내보낸 객체의 참조를 쥐고, Buffer가 마지막 뷰와 함께 사라질 때 놓아요. 그동안 내보낸 쪽은 "내보낸 버퍼가 있다"는 상태라서, 예를 들어 `bytearray`는 크기를 바꾸지 못해요.

```python
>>> ba = bytearray(16)
>>> arr = sd.asarray(memoryview(ba).cast("d"))
>>> tail = arr[1:]
>>> del arr
>>> ba.extend(b"x" * 8)
Traceback (most recent call last):
  ...
BufferError: Existing exports of data: object cannot be re-sized
>>> del tail
>>> ba.extend(b"x" * 8)
>>> len(ba)
24
```

`arr`를 지워도 뷰 `tail`이 같은 Buffer를 쥐고 있어서 버퍼는 아직 내보낸 상태예요. 마지막 뷰가 사라져야 `PyBuffer_Release`가 불려요.

- **DLPack으로 내보낼 때**: `Export::keep`(배열의 뷰)이 Buffer와 `base`를 붙잡아요. 소비자가 deleter를 부를 때 놓여요.
- **데이터프레임이 numpy로 내보낼 때**(`to_numpy`): `shared_ptr<Buffer>`의 복사본을 담은 capsule이 numpy 배열의 주인이 돼요. Series가 먼저 사라져도 numpy 배열은 유효해요.

### 프로세스 끝까지 쥐는 참조

C++ 정적 변수가 쥔 Python 객체 가운데는 일부러 놓지 않는 것이 있어요.

| 무엇 | 어디 | 쥐는 방식 |
|---|---|---|
| dtype 객체 다섯 | `g_dtype_objects` | 빌린 포인터. 주인은 모듈 속성 |
| numpy의 추상 스칼라 타입 넷 | `numpy_scalar_types()` | 처음 찾을 때 참조를 얻고 놓지 않아요 |
| `LinAlgError`, linalg 결과 namedtuple 11개 | `linalg::refs()` | `_setup`에서 참조를 올리고 놓지 않아요 |
| `AiryResult` | `special_bind.cpp`의 정적 변수 | 처음 한 번 찾고 놓지 않아요 |
| `finfo`, `iinfo`의 결과 | `dtype_info.cpp`의 정적 변수 | 처음 부를 때 한 번 만들고 놓지 않아요 |
| DLPack 속성 이름, 키워드 이름과 버전 tuple | `dlpack.cpp`의 정적 변수 | 처음 가져올 때 한 번 만들고 놓지 않아요 |

인터프리터가 끝나는 도중에 이 참조를 놓는 것은 순서를 보장할 수 없어 안전하지 않아요. 프로세스가 끝나면 OS가 회수해요. nanobind는 모듈이 내려갈 때 살아 있는 객체를 "누수"로 보고하는데, 사용자의 전역 변수가 `sd.float64`를 쥐고 끝나는 평범한 경우에도 뜨기 때문에 이 경고를 꺼요(`nb::set_leak_warnings(false)`). 대신 테스트가 참조 카운트를 직접 재요.

## 성능

작은 입력의 호출은 계산이 거의 없어서, 시간 대부분이 경계를 넘는 고정 비용이에요. 그래서 경계의 각 단계를 줄여요.

| 항목 | 줄이는 방법 |
|---|---|
| 결과 객체의 할당과 해제 | ndarray 인스턴스 풀(`nb::pooled(256)`)에서 다시 써요. `NDArray`(560바이트)를 담은 객체는 512바이트를 넘어 Python의 소형 할당기를 쓰지 못하지만, 풀이 차 있으면 `malloc`까지 가지 않아요 |
| 타입 찾기 | `is_ndarray`와 `wrap`이 저장한 타입 포인터를 써요(위 "Python 객체 안의 C++ 구조체") |
| 속성 읽기 | `shape`, `len()` 같은 속성은 타입 슬롯의 C 함수예요(위 "속성") |
| `x[key]` | 흔한 키(int와 slice만인 키)는 타입 슬롯 `mp_subscript`가 바로 처리하고, 나머지만 바인딩한 `__getitem__`으로 넘겨요 |
| numpy 배열 가져오기 | 버퍼 프로토콜과 DLPack 생산자를 거치지 않고 numpy의 C 구조체에서 바로 읽어요(위 "가져오기") |
| Column을 `shared_ptr` 대신 값 타입으로 | nanobind의 keep-alive 등록을 피해요 |
| frame 커널의 `func`를 `std::string` 대신 `nb::handle`로 | 호출마다 문자열로 바꾸지 않아요. str의 UTF-8은 캐시돼요 |
| bool 버퍼 바이트 검사 | 원소별 비교 대신 모든 바이트의 OR 하나예요 |
| 에러 이름 붙이기 (`named`) | 예외가 날 때만 비용이 들고 정상 경로에서는 0이에요 |

- nanobind 함수 호출 경로 자체는 약 10ns로 작아요(`sample` 프로파일러).
- 큰 배열에서는 경계 비용이 측정 오차 안이에요. 버퍼 프로토콜, numpy 공유, DLPack으로 가져오기는 공유할 수 있으면 원소 수와 무관한 상수 시간이에요.
- 자세한 내용은 [작은 배열의 호출 비용](/internals/array/small-arrays/)에 있어요.

### numpy와 배열을 주고받는 고정 비용

복사 없이 주고받을 때도 고정 비용은 들어요. 크기와 상관없는 비용이에요.

**`np.asarray(sd 배열)`과 `np.asarray(numpy 배열)`은 같은 일이 아니에요.** `np.asarray(numpy 배열)`은 이미 numpy 배열이면 같은 객체를 그대로 돌려줘요. `np.asarray(sd 배열)`은 numpy가 남의 객체에서 새 numpy 배열을 만드는 일이에요. stardust 배열에는 `__array__`도 `__array_interface__`도 없어서 numpy는 버퍼 프로토콜로 가져가요. 결과의 `base`가 `memoryview`예요. 그러니 공정한 비교 대상은 numpy가 다른 외부 버퍼를 받는 비용이에요. 그 비용에는 우리 `getbuffer` 한 번과 numpy가 안에서 새로 만드는 `memoryview`가 들어 있어요. 우리 `getbuffer`는 shape와 strides를 복사하지 않고 `NDArray` 안의 배열을 그대로 가리키므로 `bytearray`의 내보내기와 같은 비용이에요.

**`sd.asarray(numpy 배열)`도 같은 일이 아니에요.** numpy의 `np.asarray`는 입력을 그대로 돌려주지만, stardust는 결과 객체를 하나 만들어야 해요. 그 객체 하나만큼의 시간이 남아요. `sd.from_dlpack(numpy 배열)`도 같은 공유를 해서, `__dlpack__`을 부르고 capsule 둘을 만드는 numpy의 `np.from_dlpack`보다 빨라요.

numpy가 아닌 생산자의 DLPack 가져오기는 위 "가져오기 (`sd.from_dlpack`)"의 일을 다 해요. 속성을 한 번씩만 찾고 vectorcall을 쓰는 것이 그 비용을 줄이는 방법이에요. 어느 쪽이든 한 번에 수백 ns 아래인 비용이라, 큰 배열을 주고받을 때는 문제가 되지 않아요.

`sd.asarray`의 다른 입력(리스트, 버퍼)의 비용은 [변환과 승격](/internals/array/conversion/)에서 다뤄요.
