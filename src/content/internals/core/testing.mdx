## 한눈에 보기

stardust가 맞게 계산하는지는 네 가지 장치로 따져요. 장치마다 묻는 질문이 달라요.

| 장치 | 묻는 질문 | 어디에 |
|---|---|---|
| 단위 테스트 | 이 결과가 참값, 다른 라이브러리, 문서의 약속과 맞나요? | `tests/<영역>/`, `tests/test_*.py`, `tools/test.py` |
| 골든 테스트 | 바뀌면 안 되는 변경 뒤에도 모든 결과가 형과 비트까지 그대로인가요? | `tools/golden.py`, `tests/golden/` |
| 커버리지 | 어떤 테스트도 지나가지 않는 코드와 분기가 어디인가요? | `tools/coverage.py` |
| 정확도 측정 | 함수마다 오차가 얼마이고, 기준선보다 나빠진 것이 있나요? | `bench/accuracy/` ([정확도 측정](/internals/core/accuracy/)) |

열두 영역과 공통 폴더의 단위 테스트는 181개 파일에 17,715개예요. 평소에 돌리는 `quick` 등급이 그중 16,992개를 고르고, 나머지 723개는 시간이 오래 걸려 `deep` 등급에서만 돌아요. 저장소 밖에서 받은 파일(희소 행렬, QUADPACK의 Fortran 원본)을 쓰는 테스트 40개는 `all` 등급에서만 돌아요. 골든 테스트는 열두 영역에 케이스 34,391개를 기록해 두었어요. 테스트를 여러 프로세스로 나눠 돌리는 `tools/test.py`가 있고, 기계를 혼자 써야 하는 테스트는 따로 모아 마지막에 혼자 돌려요.

모든 명령은 라이브러리 저장소 맨 위에서 `.venv`의 Python으로 돌려요. 명령과 옵션의 전체 목록은 라이브러리 저장소의 `tests/README.md`(테스트, 골든, 커버리지)와 `bench/README.md`(속도, 정확도)에 있어요.

## 도구의 공통 규칙

테스트 도구(`tools/test.py`, `tools/golden.py`, `tools/coverage.py`)와 측정 도구(`python -m bench.speed`, `python -m bench.accuracy`)는 명령행을 한 모듈(`bench/cli.py`)로 만들어요. 그래서 이름이 같은 옵션은 어느 도구에서나 뜻과 기본값이 같아요.

| 규칙 | 뜻 |
|---|---|
| `AREA …` | 위치 인자로 주는 영역 이름이에요. 영역 이름은 `array linalg frame special stats regression random optimize htest sparse integrate differentiate`의 열둘이고, `bench/areas.py`에 적힌 순서가 결과와 표의 순서예요. 주지 않으면 그 도구가 다루는 영역 전부예요 |
| `--match PATTERN` | id가 맞는 것만 남겨요. `*`나 `?`가 있으면 id 전체와 맞춰 보는 glob이고, 없으면 부분 문자열이에요. `[`와 `]`는 보통 글자라서 표에서 복사한 id가 그대로 맞아요. 여러 번 주면 하나만 맞아도 돼요 |
| `--jobs N` | 작업 프로세스 수예요. 기본 8, 최대 10이에요 |
| `--out FILE` | 결과를 쓸 파일이에요. 폴더가 아니라 파일을 받아요 |
| 종료 코드 | 0은 모두 됐다는 뜻이에요. 1은 실패, 차이, 계약을 넘은 값, 기준선보다 나빠진 측정, 또는 견줄 것이 없을 때예요. 2는 명령행 오류나 도구 자신의 오류예요 |
| 로그 | `build/logs/<도구>/<시각>.log`에 남고, 도구마다 최근 20개를 둬요. pytest, cmake, llvm-cov 같은 하위 도구의 출력과 traceback은 터미널이 아니라 여기에 남아요 |

터미널 출력도 한 틀이에요. 머리 블록, 단계마다 진행 막대와 결과 한 줄, 끝에 요약 블록과 표, 실패 목록, 번호 붙은 메모(Notes)가 나와요.

### 무엇에 대 보나요

테스트가 하는 일은 결국 stardust의 결과를 믿을 만한 다른 무엇과 비교하는 거예요. 비교 대상은 영역마다 달라요.

- **다른 라이브러리.** 배열 테스트는 numpy를 기준으로 삼아요. 반올림이 아닌 동작(dtype, 정수 연산, 정렬 순서, NaN과 ±0, 상태 값, 기본값, 멈춤 규칙)은 정확히 견줘요. 반올림 크기의 값은 정확도 계약으로 견주고, 비트까지 같아야 하는 기준은 stardust 자신의 골든 기록이에요. `tests/array/conftest.py`의 `assert_same`은 shape, dtype, 비트가 numpy의 결과와 모두 같아야 통과시켜요(NaN끼리는 같다고 보고, `-0.0`과 `+0.0`은 다르다고 봐요). 지금 numpy와 비트까지 같은 곳에 쓰는 검사이고, vForce 함수와 자체 초월함수 커널(`exp`, `expm1`, `log1p`, `cos`)처럼 numpy와 끝자리가 다를 수 있는 곳은 `assert_ulp`로 ULP 거리(두 값 사이에 있는 double의 수)를 봐요. 데이터프레임은 pandas, 특수함수와 통계는 scipy, 회귀는 statsmodels, 최적화, 적분, 미분은 scipy, 가설검정은 scipy와 statsmodels, 희소 행렬은 scipy와 비교해요. 희소 행렬은 같은 행렬을 CSR·CSC·COO로 넣은 결과가 비트까지 같은지, 결과가 밀집 배열의 같은 연산과 같은지도 봐요. 적분과 미분은 scipy와 같은 점에서 같은 순서로 사용자 함수를 부르는지도 봐요. 기록해 둔 scipy의 호출점(점의 hex, 배열로 부르는 함수는 호출마다의 모양과 바이트의 SHA-256)과 stardust가 부른 점을 비트까지 견줘요. 최적화, 적분, 미분에서 scipy를 함께 돌려 단계마다 견주는 테스트는 기록을 만든 scipy 판(1.18.1)이 아니면 건너뛰지 않고 실패해요.
- **규칙을 그대로 옮긴 느린 구현.** 문서의 규칙을 그대로 코드로 옮긴 느린 구현(오라클)과 비교하기도 해요. `merge`의 테스트는 문서에 적힌 행 순서 규칙대로 이중 루프를 돌아 어느 행과 어느 행이 짝지어지는지를 만들고, stardust의 결과가 그 짝과 순서까지 같은지 봐요(`tests/frame/test_merge.py`의 `oracle`).
- **Arb로 만든 참값.** 특수함수와 통계 분포는 Arb(구간 산술)로 만든 참값 파일을 읽어, 보장 영역에서 상대오차가 $10^{-14}$ 이하인지 봐요(`tests/special/test_reference.py`, `tests/stats/test_reference.py`). 다변량 정규분포와 t 분포의 누적분포도 참값 파일에 대 봐요(`tests/stats/test_mvcdf.py`). 배열의 원소별 함수(`exp`와 vForce를 쓰는 14개, `pow`, 복소수의 절댓값, `deg2rad`, `rad2deg`)는 함수마다 정한 ULP 한계 안인지(`tests/array/test_reference.py`), 선형대수는 참값 행렬에서 잔차가 계약 안인지(`tests/linalg/test_reference.py`) 봐요. 가설검정은 Arb와 정확한 유리수로 만든 통계량·p값·신뢰구간의 참값에, 희소 행렬은 시험 행렬의 곱·합·풀이·고유값·행렬 지수의 Arb 참값에 대 봐요(`tests/htest/test_reference_data.py`, `tests/sparse/test_reference_data.py`). 적분은 시험 적분과 급수의 Arb 참값, 표본 규칙의 식을 같은 double에서 정확한 유리수로 계산한 값, Gauss–Legendre 마디와 가중치의 Arb 값에, 미분은 해석적 도함수·야코비안·헤시안의 Arb 값에 대 봐요(`tests/integrate/test_reference_data.py`, `tests/differentiate/test_reference_data.py` 등). 영역마다 `tests/<영역>/refdata.py` 하나가 참값 파일을 읽고 계약 대비 오차를 내고, 테스트와 정확도 측정이 그 함수를 같이 써요. 참값을 만드는 법과 오차 척도는 [정확도 측정](/internals/core/accuracy/)에 있어요.
- **기록해 둔 R과 Fortran의 결과.** 회귀는 R의 `lm`, `glm`, `glmnet`, `quantreg`, `MASS::rlm`, `nls`의 결과를, 최적화는 MINPACK과 L-BFGS-B의 Fortran 원본을, 적분은 QUADPACK의 Fortran 원본을 돌린 결과를, 가설검정은 R의 base `stats` 검정과 `car`, `multcomp`, `nortest`, `goftest`, `coin`의 결과를, 희소 행렬은 R의 `Matrix`, `RSpectra`, `irlba`의 결과를 JSON으로 저장해 두고 읽어요. 가설검정, 희소 행렬, 적분, 미분은 scipy·statsmodels의 결과도 같은 방식으로 기록해 둬요. 테스트를 돌릴 때 R이나 Fortran 컴파일러는 필요 없어요.
- **문서.** 영역마다 있는 `test_api_surface.py`는 `docs/api/<영역>.md`의 시그니처 블록을 읽어, 문서에 있는 이름이 모두 공개되어 있고 문서에 없는 이름은 공개되지 않았는지 봐요.

값이 같은지는 `tests/_bits.py`의 세 함수로만 봐요. 뜻이 셋이라 섞이지 않게 이름을 나눴어요.

| 함수 | 같다고 보는 것 |
|---|---|
| `bits_equal` | 바이트까지 같은 것. NaN의 payload와 0의 부호도 봐요 |
| `bits_equal_any_nan` | NaN끼리는 어떤 NaN이든 같고, ±0은 달라요 |
| `value_equal` | 원소마다 `==`이고, NaN끼리는 같아요 |

선형대수처럼 답이 하나로 정해지지 않는 문제(고유벡터의 부호, 랭크가 모자란 최소제곱)는 먼저 잔차로 확인하고, 답이 하나로 정해지는 곳에서만 numpy와 직접 비교해요(`tests/linalg/conftest.py`).

### 불변식

참값 없이도 확인할 수 있는 성질도 많이 테스트해요. 같은 계산을 다른 길로 했을 때 비트까지 같아야 한다는 성질이에요.

- **스레드 수.** 약속은 같은 스레드 수에서 실행마다 같은 비트이지만, 지금은 스레드 수가 몇이든 결과가 비트까지 같아서 테스트도 그것을 봐요. `tests/array/test_threads.py`는 스레드 수 1, 2, 3, 7, 10에서 같은 계산을 하고 결과의 바이트를 비교해요. 왜 같을 수 있는지는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.
- **배치와 하나씩.** 행렬을 쌓은 배치를 한 번에 넣은 결과의 `i`번째는 `i`번째 행렬 하나만 넣은 결과와 비트까지 같아야 해요(`tests/linalg/test_optimizations.py`의 `test_batch_equals_one_by_one`). 이 테스트는 일부러 홀수 `n`을 써요. 배치 원소가 16바이트 경계에 맞지 않는 자리에 놓이면 Accelerate가 다르게 반올림하기 때문이에요.
- **스칼라와 배열.** 원소별 함수는 `f(x)[i]`와 `f(x[i])`가 같은 비트여야 해요. 참값 파일의 입력에서 200점을 골라 확인해요(`test_scalar_path_gives_the_same_bits`).
- **지금 numpy와 같은 비트.** numpy와 비트까지 같은 것은 약속이 아니지만, 지금 같은 곳은 그것을 견주는 테스트를 통과하는 동안 그대로 둬요. 비트가 같다는 것은 따로 비용이 들지 않는 가장 강한 검사이기 때문이에요. `tests/linalg/test_lstsq_numpy_bits.py`는 여러 shape에서 `lstsq`의 해가 `np.linalg.lstsq`와 비트까지 같은지 봐요. 의도한 고침이나 최적화 때문에만 이런 테스트가 깨지면 허용오차와 반복 수의 비교로 바꿔요.

### 영역을 가로지르는 테스트

`tests/` 바로 아래 일곱 파일과 `tests/interop/`는 한 영역에 속하지 않는 약속을 확인해요.

| 파일 | 확인하는 것 |
|---|---|
| `test_error_messages.py` | 공개 함수의 에러 메시지가 `func(): `로 시작하는지, 연산자와 인덱싱은 Python의 꼴을 지키는지, 같은 실수에는 영역이 달라도 같은 메시지가 나오는지, 메시지에 문서 절 번호가 섞이지 않는지 |
| `test_gil_release.py` | 긴 호출이 스레드 수가 몇이든 GIL을 놓는지, 같은 호출이 스레드 1개와 10개에서 같은 비트를 내는지 |
| `test_out_of_range.py` | double 범위를 넘는 정수(`10**400`)는 함수 이름이 붙은 `OverflowError`, 물리 메모리를 넘는 요청은 `MemoryError`가 되는지 |
| `test_build.py` | 확장 모듈이 C++20, NEON, FCMA로 빌드되었는지, Accelerate가 ILP64로 연결되었는지, 풀이 태스크를 모두 정확히 한 번씩 돌리는지 |
| `test_bits.py` | 값 비교 도우미(`tests/_bits.py`)의 세 뜻이 서로 섞이지 않는지 |
| `test_summary.py` | 모든 결과의 `summary()`가 함께 쓰는 상자(`stardust._summary`)의 폭, 머리, 표의 열과 정렬, 긴 표 자르기, 수의 형식 |
| `test_tools.py` | 테스트 도구 자신의 규칙. `tools/test.py`의 옵션과 종료 코드, 문서 참조와 경로 검사, 참값 폴더의 크기 검사 |
| `interop/test_frame_array.py` | Series·DataFrame과 `sd.ndarray` 사이에서 무엇을 공유하고 무엇을 복사하는지, 읽기 전용 뷰와 Copy-on-Write가 경계를 넘어서도 지켜지는지 |

에러 메시지 테스트는 (호출, 예외 형, 메시지) 세 개를 한 줄씩 늘어놓은 표예요(`tests/test_error_messages.py`).

```python
NAMED = [
    # array: functions, the same function as a method, a property
    (lambda: sd.zeros(-1), ValueError, "zeros(): negative dimensions are not allowed"),
```

GIL 테스트는 GIL을 직접 볼 수 없어서 간접적으로 재요. Python 스레드 하나(watcher)가 루프를 돌며 두 바퀴 사이의 가장 긴 멈춤을 기록해요. 호출이 GIL을 쥐고 있으면 watcher는 호출 내내 멈추고, 놓으면 짧게만 멈춰요. 기계가 다른 일로 바빠 한 번 길게 멈출 수 있으니 네 번까지 해 보고, 한 번이라도 멈춤이 호출 시간의 4분의 1보다 짧으면 통과예요(`tests/test_gil_release.py`).

```python
            for _ in range(4):
                pause, took = w.longest_pause_during(call)
                ratios.append((pause / took, took))
```

### hypothesis

29개 파일은 hypothesis를 써요. hypothesis는 입력을 직접 적는 대신 "어떤 입력이 나올 수 있는지"(정수 범위, dtype, shape, NaN을 섞을지)를 적어 두면 그 안에서 예제를 많이 만들어 테스트를 돌려 주는 도구예요. 실패하는 예제를 찾으면 그 예제를 가장 단순한 꼴로 줄여서 보여 줘요. 데이터프레임의 `merge`는 키 값을 `-2`부터 `2`까지의 정수, `0.0`·`-0.0`·`1.5`·NaN, `"a"`·`"b"`·빈 문자열, 참·거짓에서 뽑아요. 가짓수가 적어서 같은 키가 자주 겹치고 NaN 키도 자주 나와요.

### 케이스

### 값을 적는 법

결과는 정확한 JSON으로 옮기고, 키를 정렬해 정규화한 글자열끼리 비교해요. 그래서 형도 결과의 일부예요. `True`는 `1`과 다르고, numpy 스칼라는 같은 값의 Python 스칼라와 달라요. 함수가 `bool` 대신 `int`를 돌려주게 바뀌면 값이 같아도 잡혀요.

float 하나는 `float.hex`로 적어요. `0x1.5b08c21171646p-1`처럼 가수와 지수를 16진수로 쓴 꼴이라, 되읽으면 정확히 같은 비트가 나와요. NaN은 비트가 여러 가지일 수 있어서 기본 NaN(`0x7ff8000000000000`)이면 `nan`, 아니면 비트 전체를 붙여 적어요(`tools/golden.py`).

```python
def fhex(v):
    """A float as exact text: float.hex, with the bits of a NaN that is not the default one."""
    if v != v:
        bits = struct.unpack("<Q", struct.pack("<d", v))[0]
        return "nan" if bits == 0x7FF8000000000000 else f"nan:{bits:016x}"
    return float.hex(v)
```

나머지는 이래요.

- **bool, int, str, None**: 그대로 적어요. complex는 실수부와 허수부의 hex 두 개예요.
- **numpy 스칼라**: dtype과 값을 함께 적어요. 내장 형을 상속한 클래스(IntEnum, 이름 붙은 튜플 등)는 클래스 이름과 값을 적어요.
- **작은 배열**(원소 1024개 이하): dtype, shape, strides와 원소 하나하나의 hex를 적어요.
- **큰 배열**: 원소를 다 적으면 파일이 너무 커져서, dtype·shape·strides와 바이트 전체의 SHA-256(앞 32자리), 원소 조각마다의 해시, 정해진 표본 원소를 적어요. 조각은 원소 256개 이상이고, 배열 하나에 256조각을 넘지 않게 길이를 정해요. 조각마다 SHA-256의 앞 8자리를 이어 붙여 둬요. 전체 해시는 한 비트만 달라도 바뀌고, 조각 해시는 달라진 원소가 몇 조각에 걸쳐 어디에 있는지 짚어 주고, 표본은 값이 어떻게 달라졌는지 보여 줘요. 표본은 양 끝 네 개씩과 안쪽을 16등분한 자리 15개예요.
- **예외와 경고**: 클래스를 `모듈.이름`(`builtins.TypeError`, `stardust.linalg.LinAlgError`)으로, 메시지와 함께 적어요.
- **stardust 클래스의 객체**(결과 객체, 분포 등): 공개 속성 전부와 인자 없이 부를 수 있는 메서드 전부를 불러서 그 결과를 적어요.

큰 배열의 표본 위치는 이렇게 정해요(`tools/golden.py`).

```python
def sample_indices(n):
    """A fixed sample of a large array's elements: both ends and 15 evenly spaced inside."""
    return sorted({0, 1, 2, 3, n - 4, n - 3, n - 2, n - 1} | {n * k // 16 for k in range(1, 16)})
```

### NaN의 비트

NaN은 부호 비트와 가수 부분(payload)이 달라도 모두 NaN이에요. 기계어가 조금만 달라져도 NaN의 부호가 뒤집힐 수 있어요. 골든 테스트는 이런 차이도 기본으로 잡되, 차이가 NaN의 비트뿐이면 출력에 `only NaN bits differ`라고 따로 적어요. `--any-nan`을 주면 이런 차이를 같다고 봐요. 큰 배열은 해시만 적으므로, NaN을 모두 기본 NaN으로 바꾼 뒤의 해시(`shan`)를 원래 해시와 다를 때만 함께 적어 두고 `--any-nan`에서는 그것으로 비교해요. NaN의 비트를 보는 조각 해시는 이때 쓰지 않아요.

`--any-nan`은 커버리지를 잴 때 써요. 계측 플래그를 넣어 빌드한 코어는 기계어가 달라서 몇몇 케이스에서 NaN 결과의 부호가 달라요. 그 밖의 비트는 모두 같아야 해요.

### 멈춘 케이스

케이스 하나가 `GOLDEN_TIMEOUT`초(기본 120초)를 넘기면 그 작업 프로세스를 끝내고 어느 케이스에서 멈췄는지 알려요. 작업 프로세스는 지금 돌리는 케이스 이름을 늘 작은 파일(`.cur`)에 적어 두고, 시간 제한은 `faulthandler`로 걸어요. GIL을 쥔 채 멈춰도 끝낼 수 있어요. `GOLDEN_TRACE=1`이면 케이스를 시작할 때마다 이름을 찍어요.

### 다시 기록하기

결과를 일부러 바꾸는 변경(정확도 개선, 버그 수정)이면 `check`로 바뀐 케이스가 의도한 것뿐인지 본 다음 `record`로 다시 기록하고 코드와 함께 커밋해요. `--match`를 주면 `check`는 이름이 맞는 케이스만 견주고, `record`는 이름이 맞는 케이스만 다시 쓰고 더는 없는 맞는 이름을 지워요. 나머지 기록은 그대로 둬요. 새 공개 함수를 더하면 그 영역의 `cases_<영역>.py`에도 케이스를 더해요.

### 무엇을 재나요

테스트를 고르는 법은 `tools/test.py`와 같아요(영역 위치 인자, `--match`, `--` 뒤의 pytest 인자). `--jobs`는 계측 빌드의 컴파일 작업 수예요. 종료 코드는 모든 단계가 통과하면 0, 테스트나 골든 비교가 실패하면 1, 명령행 오류나 단계 자체의 실패면 2이고, 하위 도구의 출력은 `build/logs/coverage/`에 남아요.

`report`가 쓰는 파일은 모두 `build/coverage/` 아래에 생기고 커밋하지 않아요.

- `summary.md`: 영역별 C++ 줄·함수·분기, Python 줄·분기의 비율
- `<영역>.md`: 파일별 비율과, 실행되지 않은 분기 하나하나(`파일:줄:열`, 안 간 쪽, 그 줄의 소스)
- `html/cpp/`, `html/py/`: 줄마다 실행 횟수와 분기 횟수를 단 소스

C++ 분기는 소스 위치마다 한 번 세요. 템플릿은 dtype마다 인스턴스가 따로 생기는데, 그 횟수를 위치별로 합쳐요. 그래서 "float64에서는 갔지만 complex128에서는 안 간" 분기는 놓친 것으로 치지 않아요. 놓친 분기는 세 가지로 적어요. `true never`는 참으로 한 번도 안 간 것, `false never`는 거짓으로 한 번도 안 간 것, `never reached`는 조건 자체를 한 번도 평가하지 않은 것이에요.

`--golden`을 주면 테스트 뒤에 고른 영역의 골든 비교(`tools/golden.py check --any-nan`)도 계측한 코어로 돌려요. 골든 케이스가 지나가는 분기도 세고, 계측 빌드가 평소 빌드와 같은 결과를 내는지도 함께 봐요.

### 계측 코어에서만 죽는 테스트

계측한 코어에서만 죽는 테스트는 `tools/coverage.py`의 `CRASHES`에 적어 빼고 돌려요. 테스트 하나가 죽어 전체 실행이 끝나 버리지 않게 하려는 거예요. 이런 테스트는 정의되지 않은 동작(정수를 0으로 나누기 같은)이 평소 빌드에서 우연히 지나가는 자리를 가리켜요. arm64의 정수 나눗셈 명령은 0으로 나누면 0을 내지만, 계측한 빌드는 기계어가 달라서 같은 자리에서 죽을 수 있어요. 그래서 `CRASHES`에 오른 테스트는 고쳐야 할 라이브러리 버그의 목록이기도 하고, 버그를 고치면 목록에서 지워요. 지금 목록은 비어 있어요.

## 등급과 병렬 실행

### 세 등급

테스트는 비용에 따라 세 등급으로 나뉘어요. 등급은 `--tier`나 환경 변수 `SD_TIER` 하나로 고르고, 정의는 `tests/conftest.py`와 `tests/_tier.py`에 있어요.

| 등급 | 고르는 테스트 | hypothesis | `examples(n)` | 테스트 수 |
|---|---|---|---|---:|
| `quick` (기본) | `deep`·`external` 마커가 없는 것 | 매번 같은 예제(`derandomize=True`), 기본 100개 | n | 16,992 |
| `deep` | `quick`과 `deep` 마커 | 무작위, 기본 1000개 | 10n | 17,715 |
| `all` | `deep`과 `external` 마커 | 무작위, 기본 1000개 | 10n | 17,755 |

- `deep` 마커는 넓은 격자를 쓰거나 비싼 참값을 그 자리에서 계산하는 테스트에 달아요. 지금 723개예요. 대부분은 최적화의 문제 모음을 모두 도는 테스트(589개: Newton 계열이 scipy와 같은 점에서 함수를 부르는지 보는 460개와 `minimize`의 129개)예요. quick에서는 문제 목록의 여덟 개에 하나와 MGH 모음 밖의 문제만, scipy와 단계를 견주는 스윕은 첫 문제만 돌아요. 나머지는 통계 분포의 넓은 검사(81개: 분포 31개마다 잘못된 매개변수로 모든 메서드를 불러 끝나는지 보는 하위 프로세스, 비중심 F 분포가 `nc=0`에서 F 분포와 같은지 보는 격자 48개, 극단 매개변수 2개), 회귀의 Arb 참값 대조(GLM 44개)와 Theil-Sen 기울기의 큰 문제용 알고리즘을 작은 문제에 강제로 돌리는 테스트(5개), 희소 행렬과 적분의 참값 도구가 점 몇 개를 다시 만들어 파일과 같은지 보는 테스트 하나씩, 그리고 골든 비교(`tests/golden/test_golden.py`)와 정확도 비교(`tests/bench/test_accuracy_baseline.py`) 하나씩이에요.
- `external`은 R이나 Fortran 컴파일러를 실제로 부르거나 저장소 밖에서 받은 파일을 읽는 테스트의 마커예요. 지금은 SuiteSparse 모음의 실제 행렬 여덟을 읽는 `tests/sparse/test_suitesparse.py`의 39개와, QUADPACK의 Fortran 원본을 gfortran으로 빌드해 기록의 문제 12개를 다시 돌리고 고정 기록과 같은지 보는 `tests/integrate/test_reference_data.py`의 하나, 모두 40개가 달려 있어요. 행렬은 `tools/sparse_suitesparse.py`가 `build/sparse/suitesparse/`에, Fortran 원본은 `build/comparators/quadpack/`에 받아 두고(저장소에 넣지 않아요), 파일이나 컴파일러가 없으면 건너뛰어요. 행렬이 없을 때는 받는 명령도 알려 줘요.
- 고르지 않은 등급의 테스트는 건너뛰기(skip)가 아니라 선택 해제(deselect)해요. 요약에 `N deselected`처럼 보여요. 파일 하나의 `deep` 테스트를 돌리려면 `--tier deep`이나 `SD_TIER=deep`을 함께 줘요.
- `--match`는 테스트 id(`tests/<영역>/test_<주제>.py::test_<이름>[…]`)에 맞춰요. `tests/conftest.py`가 이 옵션을 처리하므로 `pytest`에 바로 줘도 돼요.
- `--strict-markers`가 켜져 있어서 등록하지 않은 마커(오타)는 에러예요. 마커는 `deep`, `external`, `serial` 세 개예요.

### 예제 수

hypothesis 테스트는 대부분 등급의 기본 예제 수(quick 100, deep 1000)를 따라요. 수를 따로 정하는 테스트는 `examples(n)`으로 적어요(`tests/_tier.py`).

```python
def examples(n):
    """A test's hypothesis example count: n in quick, DEEP_FACTOR * n in deep and all. Each
    test keeps its own n (the cost of one example differs); the tier is the one knob."""
    return n if tier == "quick" else DEEP_FACTOR * n
```

`DEEP_FACTOR`는 10이에요. 예제 하나의 비용이 테스트마다 달라서 n은 테스트마다 따로 정해요. 지금 쓰는 n은 150(9곳), 200(5곳), 300(7곳), 100(1곳), 60(1곳)이에요.

`quick`이 매번 같은 예제를 쓰는 것은 결과를 재현할 수 있게 하려는 거예요. 같은 커밋에서 테스트를 두 번 돌리면 같은 예제가 나오고, 여러 프로세스로 나눠 돌려도 결정적이에요. `deep`은 무작위라서 돌릴 때마다 새 예제를 찾아요. 실패한 예제는 hypothesis가 출력하는 `@reproduce_failure`로 다시 돌릴 수 있어요.

### 여러 프로세스로 나눠 돌리기

`pytest`만 치면 테스트가 한 프로세스에서 차례로 돌아요. `tools/test.py`는 두 단계로 돌려요.

1. `serial` 마커가 없는 테스트를 pytest-xdist 워커 `--jobs`개(기본 8, 최대 10)에 나눠 돌려요.
2. 그다음 `serial` 테스트만 한 프로세스에서 혼자 돌려요.

영역 위치 인자는 `tests/<영역>`을 고르고, 주지 않으면 영역 밖(`tests/interop`, `tests/bench`, `tests/test_*.py`)까지 모두 돌려요. `--` 뒤의 인자는 pytest에 그대로 넘기되, `-k`, `-m`, `-n`은 받지 않아요. 고르기는 `--match`가, 마커는 등급과 두 단계가, 워커 수는 `--jobs`가 정하기 때문이에요.

종료 코드는 두 단계 중 나쁜 쪽이에요. 고른 테스트가 모두 통과하면 0, 실패가 있거나 두 단계 모두 고른 테스트가 없으면 1, 명령행 오류나 pytest 자신의 오류(중단, 내부 오류)면 2예요. pytest의 출력과 실패한 테스트의 traceback은 `build/logs/test/`에 남아요. 워커 8개는 quick 전체를 다른 일이 없는 기계에서 6개, 8개, 10개로 재 보고 가장 빨랐던 수예요(76.6초, 69.6초, 75.7초). 워커마다 sd의 스레드 수는 기본값 그대로 둬요. 워커마다 2개로 줄인 측정이 더 느렸어요.

`serial`은 다른 테스트 프로세스와 기계를 나눠 쓰면 안 되는 테스트예요. 모듈 전체는 `tests/conftest.py`의 `SERIAL`에, 테스트 하나는 `@pytest.mark.serial`로 적어요.

```python
SERIAL = {
    "tests/test_gil_release.py",  # GIL release measured by wall time (failed at 8 workers)
    "tests/random/test_alloc_errors.py",  # allocations near the physical memory
}
```

GIL 테스트는 벽시계 시간으로 재므로 다른 프로세스가 CPU를 차지하면 틀린 결과가 나와요. 메모리 할당 테스트는 물리 메모리 가까이까지 할당해요. 이 밖에 시간 제한을 건 하위 프로세스를 띄우는 속도 측정 도구의 테스트 6개와, 시간을 재서 GIL 해제나 두 호출의 시간을 견주는 선형대수·특수함수·회귀의 테스트 4개에 마커가 하나씩 달려 있어요. 모두 합쳐 quick에서 25개이고, `deep`에서는 골든 비교와 정확도 비교 2개가 더해져요. 이 둘은 스스로 작업 프로세스를 여럿 띄워요. 모두 보려면 `.venv/bin/python -m pytest -m serial --co -q`예요.

스레드 수를 바꾸는 테스트(`tests/array/test_threads.py`, `tests/frame/test_threads.py`, `tests/linalg/test_parallel.py`의 대부분)는 `serial`이 아니에요. 자기 프로세스의 풀만 바꾸고 시간은 재지 않으니 다른 테스트 옆에서 돌아도 돼요.

| `tests/integrate/data/` | scipy의 결과와 호출점, QUADPACK Fortran 원본의 결과와 그것을 scipy와 견준 비교 | `tools/gen_integrate_scipy.py`, `tools/gen_integrate_fortran.py` |
| `tests/differentiate/ref/` | 초등 함수와 끝 근처의 104점에서 1·2계 도함수(`derivatives.json`), MGH 문제의 야코비안 47개와 헤시안 42개(`mgh.npz`)의 Arb 값 | `tools/differentiate_ref.py` |
| `tests/differentiate/data/` | scipy의 `derivative`, `jacobian`, `hessian`의 결과와 호출점 | `tools/gen_differentiate_scipy.py` |

`.npz` 참값 파일은 모두 한 형식이에요(`tests/reffile.py`). 파일 하나가 점과 그 입력, 그리고 그 점에서의 메서드 하나 이상의 참값을 담아요.

| 이름 | 내용 |
|---|---|
| `inputs`, `input/<이름>` | 점의 입력. 첫 축이 점이에요 |
| `group`, `group_input/<이름>` | 점이 속한 묶음과 묶음이 함께 쓰는 입력(분포의 매개변수처럼) |
| `methods`, `method/<m>/hi`, `lo` | 메서드마다 참값을 두 double의 합(double-double)으로 |
| `method/<m>/guaranteed`, `scale`, … | 메서드마다 점별 필드(보장 영역인지, 계약의 배율, 이산 분포 역함수의 허용 구간 등) |
| `method/<m>/dropped` | 생성기가 정해진 정밀도와 반복 상한 안에서 참값을 정하지 못해 버린 점 |
| `arb`, `target_bits`, `tool`, `n_requested` | 출처. 계산한 python-flint 판, 참값이 맞는 비트 수, 만든 도구, 요청한 점 수 |

JSON 참값도 `_provenance`에 같은 출처를 적어요. 참값은 Arb의 공(참값을 반드시 담는 구간)이 값의 $2^{-110}$보다 작아질 때까지 정밀도를 올려 계산해서, `hi`가 참값을 반올림한 double이고 `hi + lo`는 그보다 훨씬 정확해요. 그래서 테스트는 Arb 없이도 오차를 ULP의 몇 분의 1까지 잴 수 있어요. 생성기는 시드를 받아서 다시 돌리면 같은 파일이 나와요.

참값 폴더의 크기는 영역마다 60 MiB를 넘지 않아야 하고, `tools/check.py`가 영역의 `tests/<영역>/ref`(와 `ref_*`) 폴더를 합한 크기를 재요. 지금 가장 큰 것은 stats의 35.5 MiB이고, array 20.0, special 11.3, sparse 6.1, linalg 4.3, regression 1.0, integrate 0.53, htest 0.25, optimize 0.08, differentiate 0.06 MiB예요.

R과 Fortran의 생성기는 테스트의 의존성이 아니에요. Rscript(필요한 R 패키지 포함)나 Fortran 컴파일러가 있는 곳에서 한 번 돌려 JSON을 만들어 두고, 테스트는 그 기록만 읽어요. `tools/`에는 이 밖에도 `gen_`으로 시작하는 도구가 여럿 있는데(`gen_debye.py`, `gen_zeta_even.py` 등), 이것들은 테스트 기록이 아니라 C++ 코드에 들어가는 계수 표를 만들어요.

참값을 어떻게 고르고 오차를 어떻게 재는지, 결과 표가 어떻게 만들어지는지는 [정확도 측정](/internals/core/accuracy/)에서 다뤄요.

## 테스트를 짜는 원칙

위의 장치들이 공통으로 따르는 원칙을 모으면 이래요.

- **독립된 기준과 비교해요.** 같은 코드를 다시 불러 비교하지 않고, 다른 라이브러리, 규칙을 그대로 옮긴 느린 구현, Arb 참값, 다른 언어의 원본과 비교해요.
- **답이 하나면 비트로, 아니면 성질로 봐요.** 결과가 하나로 정해지는 곳은 비트까지 같아야 하고, 그렇지 않은 곳(고유벡터, 랭크가 모자란 해)은 잔차와 성질로 확인해요.
- **입력은 고정하거나 시드를 줘요.** 단위 테스트는 `np.random.default_rng(s)`처럼 시드를 준 생성기를, 골든 케이스는 `L.rng(seed)`를 써요. `quick`의 hypothesis도 매번 같은 예제예요.
- **특별한 값을 일부러 넣어요.** 무한대, NaN, 부호 있는 0, 비정규 수, 정의역의 끝, 빈 배열, 0차원 배열, 건너뛰는 stride, 브로드캐스팅을 따로 다뤄요.
- **에러도 결과예요.** 어떤 예외가 어떤 메시지로 나는지도 테스트하고 골든에 기록해요.
- **시간을 재는 테스트는 잡음을 견디게 짜요.** 몇 번 시도해 가장 좋은 결과를 보고, 기계를 혼자 쓰게 `serial`로 돌려요.

## 언제 무엇을 돌리나

```bash
# 파일 하나, 또는 id가 맞는 테스트만 (quick)
.venv/bin/python -m pytest -q -p no:cacheprovider tests/special/test_erf.py
.venv/bin/python tools/test.py frame --match merge

# 커밋 전: quick 전체를 병렬로
.venv/bin/python tools/test.py

# 큰 변경 뒤: deep 전체 (골든 비교와 정확도 비교 포함)
.venv/bin/python tools/test.py --tier deep

# 결과가 바뀌면 안 되는 변경(옮기기, 리팩터링, 포매터) 뒤
.venv/bin/python tools/golden.py check
.venv/bin/python tools/golden.py check special --match 'erf *'

# 결과를 일부러 바꾼 뒤, 바뀐 케이스가 의도한 것뿐임을 보고 나서
.venv/bin/python tools/golden.py record special

# 영역별 케이스 수
.venv/bin/python tools/golden.py list

# 어떤 분기가 실행되지 않는지
.venv/bin/python tools/coverage.py all
.venv/bin/python tools/coverage.py all --golden
.venv/bin/python tools/coverage.py run special --match bessel
.venv/bin/python tools/coverage.py report

# 포매터와 린트, 참값 폴더의 크기 (파일은 고치지 않음), 문서의 절 번호 참조가 끊기지 않았는지
.venv/bin/python tools/check.py
.venv/bin/python tools/check_refs.py
```

<Callout type="tip" title="골든 check를 먼저">
결과가 바뀌면 안 되는 변경이라면 단위 테스트보다 `tools/golden.py check`가 더 날카로워요. 단위 테스트는 허용 오차 안의 차이를 통과시키지만, 골든 비교는 공개 함수 전부에서 한 비트의 차이나 형의 차이도 케이스 이름과 위치까지 짚어 줘요.
</Callout>
