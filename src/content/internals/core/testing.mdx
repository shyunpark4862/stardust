## 한눈에 보기

stardust가 맞게 계산하는지는 네 가지 장치로 따져요. 장치마다 묻는 질문이 달라요.

| 장치 | 묻는 질문 | 어디에 |
|---|---|---|
| 단위 테스트 | 이 결과가 참값, 다른 라이브러리, 문서의 약속과 맞나요? | `tests/<영역>/`, `tests/test_*.py` |
| 골든 테스트 | 바뀌면 안 되는 변경 뒤에도 모든 결과가 비트까지 그대로인가요? | `tools/golden.py`, `tests/golden/` |
| 커버리지 | 어떤 테스트도 지나가지 않는 코드와 분기가 어디인가요? | `tools/coverage.py` |
| 정확도 측정 | 함수마다 오차가 얼마이고, 기준선보다 나빠진 것이 있나요? | `bench/accuracy/` ([정확도 측정](/internals/core/accuracy/)) |

단위 테스트는 123개 파일에 10,636개예요. 평소에 돌리는 `quick` 등급이 그중 10,494개를 고르고, 나머지 142개는 시간이 오래 걸려 `deep` 등급에서만 돌아요. 골든 테스트는 여덟 영역에 케이스 18,788개를 기록해 두었어요. 테스트를 여러 프로세스로 나눠 돌리는 `tools/test.py`가 있고, 기계를 혼자 써야 하는 테스트는 따로 모아 마지막에 혼자 돌려요.

모든 명령은 라이브러리 저장소 맨 위에서 `.venv`의 Python으로 돌려요.

### 무엇에 대 보나요

테스트가 하는 일은 결국 stardust의 결과를 믿을 만한 다른 무엇과 비교하는 거예요. 비교 대상은 영역마다 달라요.

- **다른 라이브러리.** 배열 테스트는 numpy를 기준으로 삼아요. 반올림이 아닌 동작(dtype, 정수 연산, 정렬 순서, NaN과 ±0, 상태 값, 기본값, 멈춤 규칙)은 정확히 견줘요. 반올림 크기의 값은 정확도 계약으로 견주고, 비트까지 같아야 하는 기준은 stardust 자신의 골든 기록이에요. `tests/array/conftest.py`의 `assert_same`은 shape, dtype, 비트가 numpy의 결과와 모두 같아야 통과시켜요(NaN끼리는 같다고 보고, `-0.0`과 `+0.0`은 다르다고 봐요). 지금 numpy와 비트까지 같은 곳에 쓰는 검사이고, vForce 함수처럼 계약이 ULP로 적힌 곳은 `assert_ulp`로 ULP 거리를 봐요. 데이터프레임은 pandas, 특수함수와 통계는 scipy, 회귀는 statsmodels, 최적화는 scipy와 비교해요.
- **규칙을 그대로 옮긴 느린 구현.** 문서의 규칙을 그대로 코드로 옮긴 느린 구현(오라클)과 비교하기도 해요. `merge`의 테스트는 문서에 적힌 행 순서 규칙대로 이중 루프를 돌아 어느 행과 어느 행이 짝지어지는지를 만들고, stardust의 결과가 그 짝과 순서까지 같은지 봐요(`tests/frame/test_merge.py`의 `oracle`).
- **Arb로 만든 참값.** 특수함수와 통계 분포는 Arb(구간 산술)로 만든 참값 파일을 읽어, 보장 영역에서 상대오차가 $10^{-14}$ 이하인지 봐요(`tests/special/test_reference.py`, `tests/stats/test_reference.py`). 다변량 정규분포와 t 분포의 누적분포도 참값 파일에 대 봐요(`tests/stats/test_mvcdf.py`). 참값을 만드는 법과 오차 척도는 [정확도 측정](/internals/core/accuracy/)에 있어요.
- **기록해 둔 R과 Fortran의 결과.** 회귀는 R의 `lm`, `glm`, `glmnet`, `quantreg`, `MASS::rlm`, `nls`의 결과를, 최적화는 MINPACK과 L-BFGS-B의 Fortran 원본을 돌린 결과를 JSON으로 저장해 두고 읽어요. 테스트를 돌릴 때 R이나 Fortran 컴파일러는 필요 없어요.
- **문서.** 영역마다 있는 `test_api_surface.py`는 `docs/api/<영역>.md`의 시그니처 블록을 읽어, 문서에 있는 이름이 모두 공개되어 있고 문서에 없는 이름은 공개되지 않았는지 봐요.

선형대수처럼 답이 하나로 정해지지 않는 문제(고유벡터의 부호, 랭크가 모자란 최소제곱)는 먼저 잔차로 확인하고, 답이 하나로 정해지는 곳에서만 numpy와 직접 비교해요(`tests/linalg/conftest.py`).

### 불변식

참값 없이도 확인할 수 있는 성질도 많이 테스트해요. 같은 계산을 다른 길로 했을 때 비트까지 같아야 한다는 성질이에요.

- **스레드 수.** 스레드 수가 몇이든 결과는 비트까지 같아야 해요. `tests/array/test_threads.py`는 스레드 수 1, 2, 3, 7, 10에서 같은 계산을 하고 결과의 바이트를 비교해요. 왜 같을 수 있는지는 [스레드풀과 결정성](/internals/core/threads/)에 있어요.
- **배치와 하나씩.** 행렬을 쌓은 배치를 한 번에 넣은 결과의 `i`번째는 `i`번째 행렬 하나만 넣은 결과와 비트까지 같아야 해요(`tests/linalg/test_optimizations.py`의 `test_batch_equals_one_by_one`). 이 테스트는 일부러 홀수 `n`을 써요. 배치 원소가 16바이트 경계에 맞지 않는 자리에 놓이면 Accelerate가 다르게 반올림하기 때문이에요.
- **스칼라와 배열.** 원소별 함수는 `f(x)[i]`와 `f(x[i])`가 같은 비트여야 해요. 참값 파일의 입력에서 200점을 골라 확인해요(`test_scalar_path_gives_the_same_bits`).
- **지금 numpy와 같은 비트.** numpy와 비트까지 같은 것은 약속이 아니지만, 지금 같은 곳은 그것을 견주는 테스트를 통과하는 동안 그대로 둬요. 비트가 같다는 것은 따로 비용이 들지 않는 가장 강한 검사이기 때문이에요. `tests/linalg/test_lstsq_numpy_bits.py`는 여러 shape에서 `lstsq`의 해가 `np.linalg.lstsq`와 비트까지 같은지 봐요. 의도한 고침이나 최적화 때문에만 이런 테스트가 깨지면 허용오차와 반복 수의 비교로 바꿔요.

### hypothesis

29개 파일은 hypothesis를 써요. hypothesis는 입력을 직접 적는 대신 "어떤 입력이 나올 수 있는지"(정수 범위, dtype, shape, NaN을 섞을지)를 적어 두면 그 안에서 예제를 많이 만들어 테스트를 돌려 주는 도구예요. 실패하는 예제를 찾으면 그 예제를 가장 단순한 꼴로 줄여서 보여 줘요. 데이터프레임의 `merge`는 키 값을 `-2`부터 `2`까지의 정수, `0.0`·`-0.0`·`1.5`·NaN, `"a"`·`"b"`·빈 문자열, 참·거짓에서 뽑아요. 가짓수가 적어서 같은 키가 자주 겹치고 NaN 키도 자주 나와요.

## 골든 테스트

### 생각

단위 테스트는 "참값에 충분히 가까운가"를 물어요. 그래서 결과가 1ULP 달라져도 대부분 통과해요. 그런데 어떤 변경은 결과를 한 비트도 바꾸면 안 돼요. 코드를 다른 파일로 옮기기, 리팩터링, 포매터 적용 같은 변경이에요. 이런 변경이 실수로 덧셈 순서 하나를 바꿨다면 단위 테스트로는 알 수 없어요.

골든 테스트는 이것을 잡아요. 공개 함수 전부를 정해진 입력에서 돌려 결과를 비트까지 파일에 적어 두고(record), 변경 뒤에 다시 돌려 한 비트라도 다른 곳을 모두 적어요(check). 참값이 무엇인지는 묻지 않고, 전과 같은지만 물어요.

### 케이스

케이스는 영역마다 `tests/golden/cases_<영역>.py`에 있어요. 파일마다 `cases(L)`라는 생성기가 하나 있고, 케이스 하나는 이름과 인자 없는 함수(thunk)의 쌍이에요. `L`에는 라이브러리(`L.sd`), 입력을 만들 때만 쓰는 numpy(`L.np`), 시드를 받는 numpy 생성기(`L.rng(seed)`)가 들어 있어요. 입력을 이것들로만 만들어서 언제 돌려도 같은 입력이 나와요.

특수함수의 원소별 함수 하나는 이런 케이스들을 내요(`tests/golden/cases_special.py`의 발췌).

```python
    yield f"{name} grid", lambda: f(*grid())
    yield f"{name} random", lambda: f(*rand(1000))
    yield f"{name} large", lambda: f(*rand(4101 if name in HEAVY else 2**15 + 5, 1))
    yield f"{name} scalar", lambda: f(*[SCALAR[kd] for kd in kinds])
    yield f"{name} scalar nan", lambda: f(*[NAN] * k)
```

`grid`는 인자 종류마다 정한 특별한 값(무한대, NaN, 부호 있는 0, 비정규 수, 정의역의 끝)의 모든 조합이에요. `large`는 원소 $2^{15}+5$개라서 여러 스레드가 여러 태스크로 나눠 도는 길을 지나요. 이 밖에 정수와 bool 입력, 리스트, 건너뛰는 stride, 브로드캐스팅, `out=`, 빈 배열, 복소수, 잘못된 호출을 함수마다 따로 케이스로 둬요. 에러도 결과라서, 잘못된 호출이 어떤 예외를 어떤 메시지로 내는지도 비트처럼 고정돼요.

### 값을 적는 법

float 하나는 `float.hex`로 적어요. `0x1.5b08c21171646p-1`처럼 가수와 지수를 16진수로 쓴 꼴이라, 되읽으면 정확히 같은 비트가 나와요. NaN은 비트가 여러 가지일 수 있어서 기본 NaN(`0x7ff8000000000000`)이면 `nan`, 아니면 비트 전체를 붙여 적어요(`tools/golden.py`).

```python
def fhex(v):
    """A float as exact text: float.hex, with the bits of a NaN that is not the default one."""
    if v != v:
        bits = struct.unpack("<Q", struct.pack("<d", v))[0]
        return "nan" if bits == 0x7FF8000000000000 else f"nan:{bits:016x}"
    return float.hex(v)
```

나머지는 이래요.

- **작은 배열**(원소 1024개 이하): dtype, shape, strides와 원소 하나하나의 hex를 적어요.
- **큰 배열**: 원소를 다 적으면 파일이 너무 커져서, 바이트 전체의 SHA-256(앞 32자리)과 정해진 표본 원소만 적어요. 표본은 양 끝 네 개씩과 안쪽을 16등분한 자리 15개예요. 해시는 한 비트만 달라도 바뀌고, 표본은 어디가 어떻게 달라졌는지 보여 줘요.
- **예외**: 예외 형의 이름과 메시지.
- **stardust 클래스의 객체**(결과 객체, 분포 등): 공개 속성 전부와 인자 없이 부를 수 있는 메서드 전부를 불러서 그 결과를 적어요.
- **경고**: 케이스가 낸 경고의 종류와 메시지.

큰 배열의 표본 위치는 이렇게 정해요(`tools/golden.py`).

```python
def sample_indices(n):
    """A fixed sample of a large array's elements: both ends and 15 evenly spaced inside."""
    return sorted({0, 1, 2, 3, n - 4, n - 3, n - 2, n - 1} | {n * k // 16 for k in range(1, 16)})
```

기록 파일(`tests/golden/data/special.json`)에서 케이스 몇 개를 한 줄씩으로 줄여 보면 이래요(`...`는 줄인 곳이에요).

```text

"erf err no args": {"r": {"error": "TypeError", "msg": "erf(): incompatible function arguments. ... 1. erf(x, /, *, out=None) ..."}}
"erf large": {"r": {"n": 32773, "nd": "float64", "sha": "4e5c686dd30cb7a4307be8326c3acb5e",
               "sample": [[0, "-0x1.0000000000000p+0"], [1, "0x1.577712cc888bdp-6"], ...],
               "shape": [32773], "strides": [8]}}
```

### 스레드 수

영역마다 스레드 수 1, 3, 10에서 프로세스를 따로 띄워 같은 케이스를 돌리고, 세 결과가 같아야 해요. 그래서 골든 테스트는 스레드 수와 상관없이 결과가 같다는 약속을 골든 케이스 전부에서 확인하는 일도 해요. 스레드 수에 따라 결과가 다른 케이스가 나오면 스레드 수별로 따로 기록하고 `THREADS`로 알려요. 지금 기록에는 그런 케이스가 하나도 없어요.

### check의 출력

기록 파일 하나를 다른 폴더에 복사해 `erf` 케이스 세 개의 값을 일부러 1ULP 바꾸거나 NaN에 부호를 붙인 뒤 `--out`으로 그 폴더를 가리켜 돌리면 이렇게 나와요.

```text
special          3 cases: 3 changed, 0 new, 0 gone  DIFFERS
CHANGED  special/erf random [threads 1,3,10]
           .r: 1 of 1000 elements differ; first at (5): got -0x1.99698e2ac50a7p-6 (-0.024988545260456487), want -0x1.99698e2ac50a8p-6 (-0.02498854526045649), 1 ulp
CHANGED  special/erf scalar [threads 1,3,10]
           .r: got 0x1.5b08c21171646p-1 (0.6778011938374184), want 0x1.5b08c21171645p-1 (0.6778011938374183), 1 ulp
CHANGED  special/erf scalar nan [threads 1,3,10]
           .r: only NaN bits differ: got nan, want nan:fff8000000000000

```

바뀐 케이스마다 달라진 스레드 수, 배열이면 달라진 원소 수와 첫 위치, 옛 값과 새 값을 hex와 10진수로, 둘 사이가 몇 ULP인지 적어요. 같은 차이가 세 스레드 수에서 똑같이 나면 한 번만 적어요.

### NaN의 비트

NaN은 부호 비트와 가수 부분(payload)이 달라도 모두 NaN이에요. 기계어가 조금만 달라져도 NaN의 부호가 뒤집힐 수 있어요. 골든 테스트는 이런 차이도 기본으로 잡되, 차이가 NaN의 비트뿐이면 출력에 `only NaN bits differ`라고 따로 적어요. `--any-nan`을 주면 이런 차이를 같다고 봐요. 큰 배열은 해시만 적으므로, NaN을 모두 기본 NaN으로 바꾼 뒤의 해시(`shan`)를 원래 해시와 다를 때만 함께 적어 두고 `--any-nan`에서는 그것으로 비교해요.

`--any-nan`은 커버리지를 잴 때 써요. 계측 플래그를 넣어 빌드한 코어는 기계어가 달라서 몇몇 케이스(복소수 NaN이 섞인 나눗셈, t 분포의 역함수)에서 NaN 결과의 부호가 달라요. 그 밖의 비트는 모두 같아야 해요.

### 멈춘 케이스

케이스 하나가 `GOLDEN_TIMEOUT`초(기본 120초)를 넘기면 그 작업 프로세스를 끝내고 어느 케이스에서 멈췄는지 알려요. 작업 프로세스는 지금 돌리는 케이스 이름을 늘 작은 파일(`.cur`)에 적어 두고, 시간 제한은 `faulthandler`로 걸어요. GIL을 쥔 채 멈춰도 끝낼 수 있어요. `GOLDEN_TRACE=1`이면 케이스를 시작할 때마다 이름을 찍어요.

### 다시 기록하기

결과를 일부러 바꾸는 변경(정확도 개선, 버그 수정)이면 `check`로 바뀐 케이스가 의도한 것뿐인지 본 다음 `record`로 다시 기록하고 코드와 함께 커밋해요. `--case 정규식`을 주면 이름이 맞는 케이스만 다시 기록하고 나머지는 그대로 둬요. 새 공개 함수를 더하면 그 영역의 `cases_<영역>.py`에도 케이스를 더해요.

## 커버리지

### 무엇을 재나요

커버리지는 테스트를 도는 동안 코드의 어느 줄과 어느 분기가 한 번이라도 실행되었는지를 세요. `if` 하나에는 참으로 가는 쪽과 거짓으로 가는 쪽이 있는데, 테스트가 한쪽만 지나갔다면 다른 쪽의 코드는 맞는지 틀린지 아무도 확인하지 않은 거예요. 커버리지가 결과의 옳고 그름을 말해 주지는 않아요. 어떤 테스트도 닿지 않는 곳을 찾아 새 테스트를 쓸 자리를 알려 줘요.

`report`가 쓰는 파일은 모두 `build/coverage/` 아래에 생기고 커밋하지 않아요.

- `summary.md`: 영역별 C++ 줄·함수·분기, Python 줄·분기의 비율
- `<영역>.md`: 파일별 비율과, 실행되지 않은 분기 하나하나(`파일:줄:열`, 안 간 쪽, 그 줄의 소스)
- `html/cpp/`, `html/py/`: 줄마다 실행 횟수와 분기 횟수를 단 소스

C++ 분기는 소스 위치마다 한 번 세요. 템플릿은 dtype마다 인스턴스가 따로 생기는데, 그 횟수를 위치별로 합쳐요. 그래서 "float64에서는 갔지만 complex128에서는 안 간" 분기는 놓친 것으로 치지 않아요. 놓친 분기는 세 가지로 적어요. `true never`는 참으로 한 번도 안 간 것, `false never`는 거짓으로 한 번도 안 간 것, `never reached`는 조건 자체를 한 번도 평가하지 않은 것이에요.

`--golden`을 주면 테스트 뒤에 골든 비교(`tools/golden.py check --any-nan`)도 계측한 코어로 돌려요. 골든 케이스가 지나가는 분기도 세고, 계측 빌드가 평소 빌드와 같은 결과를 내는지도 함께 봐요.

### 계측 코어에서만 죽는 테스트

계측한 코어에서만 죽는 테스트는 `tools/coverage.py`의 `CRASHES`에 적어 빼고 돌려요. 테스트 하나가 죽어 전체 실행이 끝나 버리지 않게 하려는 거예요. 이런 테스트는 정의되지 않은 동작(정수를 0으로 나누기 같은)이 평소 빌드에서 우연히 지나가는 자리를 가리켜요. arm64의 정수 나눗셈 명령은 0으로 나누면 0을 내지만, 계측한 빌드는 기계어가 달라서 같은 자리에서 죽어요. 그래서 `CRASHES`에 오른 테스트는 고쳐야 할 라이브러리 버그의 목록이기도 해요.

## 등급과 병렬 실행

### 세 등급

테스트는 비용에 따라 세 등급으로 나뉘어요. 등급은 환경 변수 `SD_TIER` 하나(또는 `--tier`)로 고르고, 정의는 `tests/conftest.py`에 있어요.

| 등급 | 고르는 테스트 | hypothesis | `examples(n)` | 테스트 수 |
|---|---|---|---|---:|
| `quick` (기본) | `deep`·`external` 마커가 없는 것 | 매번 같은 예제(`derandomize=True`), 기본 100개 | n | 10,494 |
| `deep` | `quick`과 `deep` 마커 | 무작위, 기본 1000개 | 10n | 10,636 |
| `all` | `deep`과 `external` 마커 | 무작위, 기본 1000개 | 10n | 10,636 |

- `deep` 마커는 넓은 격자를 쓰거나 비싼 참값을 그 자리에서 계산하는 테스트에 달아요. 지금 142개이고, 회귀의 Arb 참값 대조(GLM 44개), Theil-Sen 기울기의 큰 문제용 알고리즘을 작은 문제에 강제로 돌리는 테스트(5개), 통계 분포의 넓은 검사(81개: 분포 31개마다 잘못된 매개변수로 모든 메서드를 불러 끝나는지 보는 하위 프로세스, 비중심 F 분포가 `nc=0`에서 F 분포와 같은지 보는 격자 48개, 극단 매개변수 2개), 최적화의 Newton 계열이 scipy와 같은 점에서 함수를 부르는지 모든 문제로 보는 테스트(10개), 그리고 골든 비교와 정확도 비교(`tests/golden/test_golden.py`, 2개)예요.
- `external`은 R이나 Fortran 컴파일러를 실제로 부르는 테스트를 위한 마커예요. 등록만 되어 있고 달린 테스트는 없어요. 그래서 `all`과 `deep`이 고르는 테스트가 같아요.
- 고르지 않은 등급의 테스트는 건너뛰기(skip)가 아니라 선택 해제(deselect)해요. 요약에 `142 deselected`처럼 보여요. 파일 하나의 `deep` 테스트를 돌리려면 `SD_TIER=deep`을 함께 줘요.
- `--strict-markers`가 켜져 있어서 등록하지 않은 마커(오타)는 에러예요. 마커는 `deep`, `external`, `serial` 세 개예요.

### 예제 수

hypothesis 테스트의 예제 수는 테스트마다 `examples(n)`으로 적어요(`tests/_tier.py`).

```python
def examples(n):
    """A test's hypothesis example count: n in quick, DEEP_FACTOR * n in deep and all. Each
    test keeps its own n (the cost of one example differs); the tier is the one knob."""
    return n if tier == "quick" else DEEP_FACTOR * n
```

`DEEP_FACTOR`는 10이에요. 예제 하나의 비용이 테스트마다 달라서 n은 테스트마다 따로 정해요. 지금 쓰는 n은 150(10곳), 200(6곳), 300(7곳), 60(2곳)이에요. `examples`를 쓰지 않는 `@given`은 프로필의 기본값(quick 100, deep 1000)을 따라요.

`quick`이 매번 같은 예제를 쓰는 것은 결과를 재현할 수 있게 하려는 거예요. 같은 커밋에서 테스트를 두 번 돌리면 같은 예제가 나오고, 여러 프로세스로 나눠 돌려도 결정적이에요. `deep`은 무작위라서 돌릴 때마다 새 예제를 찾아요. 실패한 예제는 hypothesis가 출력하는 `@reproduce_failure`로 다시 돌릴 수 있어요.

### 여러 프로세스로 나눠 돌리기

`pytest`만 치면 테스트가 한 프로세스에서 차례로 돌아요. `tools/test.py`는 두 단계로 돌려요.

1. `serial` 마커가 없는 테스트를 pytest-xdist 워커 `-n`개에 나눠 돌려요(`-m "not serial"`). 워커는 기본 6개, 최대 8개예요.
2. 그다음 `serial` 테스트만 한 프로세스에서 혼자 돌려요(`-m serial`).

종료 코드는 두 단계 중 나쁜 쪽이에요. 어느 단계에서 고른 테스트가 하나도 없으면(pytest의 종료 코드 5) 성공으로 쳐요. 워커 8개는 6개보다 빠르지 않았고 GIL 테스트가 부하 때문에 실패해서 기본값이 6이에요. 워커마다 sd의 스레드 수는 기본값 그대로 둬요. 워커마다 2개로 줄인 측정이 더 느렸어요.

`serial`은 다른 테스트 프로세스와 기계를 나눠 쓰면 안 되는 테스트예요. 모듈 목록은 `tests/conftest.py`의 `SERIAL`이에요.

```python
SERIAL = {
    "tests/test_gil_release.py",  # GIL release measured by wall time (failed at 8 workers)
    "tests/bench/test_speed_harness.py",  # timing; subprocesses with time limits
    "tests/random/test_alloc_errors.py",  # allocations near the physical memory
}
```

GIL 테스트는 벽시계 시간으로 재므로 다른 프로세스가 CPU를 차지하면 틀린 결과가 나와요. 속도 측정 도구의 테스트는 시간 제한을 건 하위 프로세스를 띄우고, 메모리 할당 테스트는 물리 메모리 가까이까지 할당해요. 셋을 합쳐 39개이고, `deep`에서는 골든 비교와 정확도 비교 2개가 더해져요. 이 둘은 자기 프로세스를 여럿 띄우므로 `serial` 마커를 파일에 직접 달아요.

스레드 수를 바꾸는 테스트(`tests/array/test_threads.py`, `tests/frame/test_threads.py`, `tests/linalg/test_parallel.py`)는 `serial`이 아니에요. 자기 프로세스의 풀만 바꾸고 시간은 재지 않으니 다른 테스트 옆에서 돌아도 돼요.

| `tests/stats/ref_mv/` | 다변량·행렬 분포 7개의 log 밀도, 밀도, 엔트로피 참값(`.npz`). 정확도 측정이 읽어요 | `tools/mv_ref.py` |
| `tests/stats/ref_mvcdf/` | 다변량 정규분포와 t 분포의 누적분포 참값 | `tools/mvcdf_ref.py` |
| `tests/regression/ref/` | R의 회귀 결과와 Arb로 만든 회귀 참값(JSON 8개) | R: `tools/gen_regression_r.py`, `gen_quantreg_r.py`, `gen_robust_r.py`, `gen_nls_r.py`. Arb: `tools/regref.py`를 부르는 `tests/regression/refdata*.py` |
| `tests/regression/data/` | NIST StRD 문제와 인증값(`.dat`) | NIST가 공개한 파일 |
| `tests/optimize/data/` | MINPACK·L-BFGS-B Fortran 원본과 scipy의 결과, Arb로 찾은 근 | `tools/gen_optimize_fortran.py`, `gen_optimize_scipy.py`, `tools/optimize_ref.py` |

`.npz` 참값 파일에는 입력(`x0`, `x1`, …), 참값을 double-double로 나눈 `hi`와 `lo`(참값 ≈ `hi + lo`), 입력이 보장 영역에 드는지 표시한 `guaranteed`, 점마다 계약의 배율 `scale`, 만든 도구의 출처(`arb`, `target_bits`)가 들어 있어요. 참값은 Arb의 공(참값을 반드시 담는 구간)이 값의 $2^{-110}$보다 작아질 때까지 정밀도를 올려 계산해서, `hi + lo`가 참값을 반올림한 것과 같아요. 그래서 테스트는 Arb 없이도 오차를 ULP의 몇 분의 1까지 잴 수 있어요. 생성기는 시드를 받아서 다시 돌리면 같은 파일이 나와요.

R과 Fortran의 생성기는 테스트의 의존성이 아니에요. Rscript(필요한 R 패키지 포함)나 Fortran 컴파일러가 있는 곳에서 한 번 돌려 JSON을 만들어 두고, 테스트는 그 기록만 읽어요. `tools/`에는 이 밖에도 `gen_`으로 시작하는 도구가 여럿 있는데(`gen_debye.py`, `gen_zeta_even.py` 등), 이것들은 테스트 기록이 아니라 C++ 코드에 들어가는 계수 표를 만들어요.

참값을 어떻게 고르고 오차를 어떻게 재는지, 결과 표가 어떻게 만들어지는지는 [정확도 측정](/internals/core/accuracy/)에서 다뤄요.

## 테스트를 짜는 원칙

위의 장치들이 공통으로 따르는 원칙을 모으면 이래요.

- **독립된 기준과 비교해요.** 같은 코드를 다시 불러 비교하지 않고, 다른 라이브러리, 규칙을 그대로 옮긴 느린 구현, Arb 참값, 다른 언어의 원본과 비교해요.
- **답이 하나면 비트로, 아니면 성질로 봐요.** 결과가 하나로 정해지는 곳은 비트까지 같아야 하고, 그렇지 않은 곳(고유벡터, 랭크가 모자란 해)은 잔차와 성질로 확인해요.
- **입력은 고정하거나 시드를 줘요.** 단위 테스트는 `np.random.default_rng(s)`처럼 시드를 준 생성기를, 골든 케이스는 `L.rng(seed)`를 써요. `quick`의 hypothesis도 매번 같은 예제예요.
- **특별한 값을 일부러 넣어요.** 무한대, NaN, 부호 있는 0, 비정규 수, 정의역의 끝, 빈 배열, 0차원 배열, 건너뛰는 stride, 브로드캐스팅을 따로 다뤄요.
- **에러도 결과예요.** 어떤 예외가 어떤 메시지로 나는지도 테스트하고 골든에 기록해요.
- **시간을 재는 테스트는 잡음을 견디게 짜요.** 몇 번 시도해 가장 좋은 결과를 보고, 기계를 혼자 쓰게 `serial`로 돌려요.

## 언제 무엇을 돌리나

```bash
# 파일 하나, 또는 이름이 맞는 테스트만 (quick)
.venv/bin/python -m pytest -q -p no:cacheprovider tests/special/test_erf.py
.venv/bin/python tools/test.py tests/frame -k merge

# 커밋 전: quick 전체를 병렬로
.venv/bin/python tools/test.py

# 큰 변경 뒤: deep 전체 (골든 비교와 정확도 비교 포함)
SD_TIER=deep .venv/bin/python tools/test.py

# 결과가 바뀌면 안 되는 변경(옮기기, 리팩터링, 포매터) 뒤
.venv/bin/python tools/golden.py check
.venv/bin/python tools/golden.py check special --case '^erf '

# 결과를 일부러 바꾼 뒤, 바뀐 케이스가 의도한 것뿐임을 보고 나서
.venv/bin/python tools/golden.py record special

# 영역별 케이스 수
.venv/bin/python tools/golden.py list

# 어떤 분기가 실행되지 않는지
.venv/bin/python tools/coverage.py all
.venv/bin/python tools/coverage.py all --golden
.venv/bin/python tools/coverage.py run tests/special
.venv/bin/python tools/coverage.py report

# 포매터와 린트 (파일은 고치지 않음), 문서의 절 번호 참조가 끊기지 않았는지
.venv/bin/python tools/check.py
.venv/bin/python tools/check_refs.py
```

<Callout type="tip" title="골든 check를 먼저">
결과가 바뀌면 안 되는 변경이라면 단위 테스트보다 `tools/golden.py check`가 더 날카로워요. 단위 테스트는 허용 오차 안의 차이를 통과시키지만, 골든 비교는 공개 함수 전부에서 한 비트의 차이도 케이스 이름과 위치까지 짚어 줘요.
</Callout>
