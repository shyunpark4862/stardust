## 한눈에 보기

속도는 저장소의 `bench/speed/` 하나가 재요. 모든 영역이 같은 시간 재기 규칙, 같은 스레드 조절, 같은 결과 형식을 써요. 그래서 배열의 `sum`과 회귀의 `glm`을 같은 기준으로 읽을 수 있어요.

| 파일 | 하는 일 |
|---|---|

| `cases/<영역>.py` | 영역의 사례 목록(`cases()`) |
| `rsession.py` | 실행 하나에 R 프로세스 하나 |
| `boost.py`, `boost_speed.cpp` | Boost.Math 비교 대상의 빌드와 호출 |

## 작은 호출을 재기 어려운 이유

스칼라 하나를 넣는 호출은 마이크로초 단위이고, 원소 $10^6$개짜리 호출도 대개 밀리초 단위예요. 이런 시간을 한 번 재서 믿으면 틀리기 쉬워요. 무엇이 방해하는지와, 하네스가 각각에 무엇을 하는지 먼저 정리해요.

| 방해하는 것 | 무슨 일이 생기나 | 하네스가 하는 일 |
|---|---|---|
| 시계의 해상도와 루프의 비용 | 1µs짜리 호출을 한 번 재면 시계의 눈금과 재는 코드 자체의 비용이 결과에 섞여요 | 호출을 여러 번 묶은 **배치**를 재고 호출 수로 나눠요. 배치 하나가 20 ms 이상이 되게 해요 |
| 첫 호출 | 캐시가 비어 있고, 지연 import와 할당자의 첫 메모리 접근이 첫 호출에 몰려요 | 처음 한 번은 **예열**로 부르고 버려요. 배치 크기를 고르는 배치들도 예열이 돼요 |
| 다른 프로세스와 OS | 측정 도중 다른 일이 CPU를 잠깐 가져가면 그 배치만 느려져요 | 배치를 여러 번 재서 **최솟값**을 보고해요. 측정 전과 도중에 다른 프로세스의 CPU 사용을 재요 |
| 기계 상태의 변화 | 열, 클록, 배경 작업 때문에 몇 분 동안 기계 전체가 느려질 수 있어요 | 사례 안에서 sd와 비교 대상을 **잇달아** 재고, 라운드를 여러 번 돌아요. 느린 때가 비율의 양쪽에 같이 걸려요 |
| 같은 입력의 되풀이 | 분기 예측기와 캐시가 그 입력을 배워서 실제보다 빨라 보여요 | 가지가 많은 계산은 같은 모양의 **새 입력** 여럿을 돌려 가며 불러요 |
| 쓰레기 수집 | 배치 하나 안에서 Python GC가 돌면 그 배치만 느려져요 | 배치 동안 GC를 끄고, 측정마다 그 앞에서 한 번 모아요 |
| 스레드 설정 | BLAS가 몇 스레드로 도는지에 따라 같은 호출의 시간이 크게 달라요 | BLAS 스레드 설정마다 **측정 프로세스를 따로** 띄워요 |

아래 절들이 이 표의 각 줄을 자세히 설명해요.

## 측정 하나: `harness.measure`

### 상수

시간 재기의 기본값은 `harness.py` 맨 위에 있어요. 사례가 `timing`으로 바꿀 수 있어요.

```python
# bench/speed/harness.py
TARGET_S = 0.02  # one batch takes at least this long
BATCHES = 7  # batches per measurement when the calls are cheap
MIN_BATCHES = 3  # at least this many, unless one call is very slow
BUDGET_S = 2.0  # aim for at most this much time per measurement
SLOW_CALL_S = 5.0  # a single call slower than this is timed once per round
MAX_CALLS = 1 << 24
```

| 상수 | 값 | 뜻 |
|---|---|---|
| `TARGET_S` | 20 ms | 배치 하나가 적어도 이만큼 걸리게 배치 크기를 정해요 |
| `BATCHES` | 7 | 측정 하나의 배치 수 |
| `MIN_BATCHES` | 3 | 시간 예산 때문에 줄여도 이 아래로는 줄이지 않아요 |
| `BUDGET_S` | 2초 | 측정 하나에 쓰려는 시간의 상한 |
| `SLOW_CALL_S` | 5초 | 한 번에 이보다 오래 걸리는 호출은 라운드마다 한 번만 재요 |
| `MAX_CALLS` | $2^{24}$ | 배치 하나의 호출 수 상한 |

예를 들어 special의 비용표 단위인 `add(x, y)` 사례는 `timing={"batches": 25, "budget_s": 5.0}`으로 배치를 늘려 재요.

배치 크기와 배치 수를 정하는 부분이에요.

```python
    # bench/speed/harness.py (measure)
    n = 1
    per = first
    if first < target_s:
        while n < MAX_CALLS:
            dt = _batch(fn, n)
            per = dt / n
            if dt >= target_s:
                break
            n *= 2
    k = batches
    if per * n * k > budget_s:
        k = max(min_batches, int(budget_s / (per * n)))
```

시계는 `time.perf_counter_ns`예요. 배치 하나가 20 ms면, 시계의 눈금이나 루프 한 바퀴의 비용은 그 시간에 비해 무시할 만큼 작아요. 측정 하나는 배치 시간 목록(`Sample.times`)과 배치당 호출 수(`Sample.calls`)를 남겨요.

`--smoke`로 돌리면 시간을 재지 않고 sd와 비교 대상을 한 번씩만 불러요. 모든 사례가 오류 없이 도는지, 그리고 두 쪽이 같은 값을 내는지 보는 점검 실행이에요([결과 확인](#결과-확인---smoke)).

### 최솟값, 중앙값, 잡음 폭

보고하는 시간은 **모든 라운드의 모든 배치 중 최솟값**이에요. 방해는 시간을 늘리기만 하고 줄이지는 않아요. 그래서 가장 빠른 배치가 OS와 다른 프로세스가 가장 덜 방해한 경우에 가장 가까워요.

최솟값만 보면 그 측정이 얼마나 흔들렸는지 알 수 없어요. 그래서 배치들의 중앙값을 함께 남기고, 둘의 차이를 **잡음 폭**으로 써요.

```python
    # bench/speed/harness.py (Sample)
    @property
    def noise(self) -> float:
        """The noise band: how far the median batch lies above the best one."""
        return self.median / self.min - 1.0 if self.min > 0 else 0.0
```

잡음 폭이 3%라면 배치의 절반은 최솟값보다 3% 넘게 느렸다는 뜻이에요. 이 값은 두 측정을 비교할 때 기준이 돼요. 두 실행의 차이가 잡음 폭보다 작으면 코드가 아니라 흔들림일 수 있어요([느려진 것 찾기](#느려진-것-찾기-compare)).

### 라운드: 번갈아 재기

실행은 라운드를 여러 번 돌아요. 기본은 3라운드이고 `--quick`과 `--smoke`는 1라운드예요. 한 라운드는 고른 사례를 모두 한 번씩 돌고, 사례 하나 안에서는 sd와 비교 대상을 잇달아 재요. 같은 측정의 배치는 라운드를 넘어 합쳐지고(`Sample.merged`), 최솟값과 중앙값은 합친 배치 전체에서 구해요.

이렇게 하면 기계가 잠깐 느려진 때가 한 사례의 양쪽에 같이 걸려요. sd만 느린 때 재고 numpy는 빠른 때 재는 일이 줄어들어요. 라운드가 시간에 걸쳐 흩어져 있으니 배경 작업이 한때 몰려도 한 라운드만 손해를 봐요.

### 쓰레기 수집

배치 안에서는 `gc.disable()`로 Python의 쓰레기 수집을 꺼요. 수집이 배치 하나 안에서 돌면 잡음만 더해요. 대신 측정마다 그 앞에서 `gc.collect()`로 한 번 모아요. statsmodels의 결과 객체는 순환 참조를 만들고, 원소 $10^6$개에서는 이것이 GB 단위로 쌓이기 때문이에요.

### 같은 입력을 되풀이하지 않기

정렬처럼 가지가 많은 계산은 같은 입력으로 되풀이해 재면 실제보다 빠르게 나와요. CPU의 분기 예측기가 그 입력의 분기 순서를 배우고, 캐시에도 그 입력이 남기 때문이에요. numpy의 `argsort`(원소 $10^3$개)는 한 입력을 되풀이하면 7.6 µs, 매번 새 입력이면 29 µs였어요. 실제 사용에서 같은 배열을 수천 번 정렬하는 일은 드무니, 뒤쪽이 맞는 값이에요.

그래서 가지가 많은 계산은 같은 분포와 모양의 입력 여럿을 미리 만들어, 부를 때마다 다음 입력을 써요(`harness.rotate`). 입력 수는 원소 수에 따라 정해요.

```python
# bench/speed/harness.py
def fresh_count(n: int) -> int:
    """How many inputs to rotate for a branchy case of n elements: many small ones, a
    few big ones (about 4·10^6 elements in all, at least 4, at most 64)."""
    return min(64, max(4, 4_000_000 // max(n, 1)))
```

원소 $10^6$개면 4벌, $10^3$개면 64벌이에요. 입력을 돌리는 비용은 호출당 30–40 ns이고 양쪽에 똑같이 들어요.

| 새 입력을 돌려 쓰는 계산 | 한 입력을 쓰는 계산 |
|---|---|
| 정렬, `argsort`, `median`, `quantile`, `unique_*`, `searchsorted`, `nonzero`, 마스크로 고르기와 마스크 대입 (array) | 원소별 연산, 보통의 리덕션과 NaN을 건너뛰는 리덕션, 누적, gather·scatter (array) |
| 해시, 정렬, groupby, merge, 파싱 (frame) | 원소별 연산, 리덕션, 마스크 필터 (frame) |
| $10^2$–$10^4$개 배열의 특수함수와 분포 함수, 작은 입력의 기술통계 (special, stats) | 원소 $10^5$–$10^6$개의 원소별 함수 (special, stats) |

난수는 돌릴 필요가 없어요. 부를 때마다 새 수를 뽑기 때문이에요.

## 스레드

stardust와 비교 대상이 각각 몇 스레드로 도는지 정해 두지 않으면 배율이 아무 뜻이 없어요. 스레드풀 자체는 [스레드풀과 결정성](/internals/core/threads/)에서 다뤄요. 여기서는 측정이 스레드 수를 어떻게 고정하는지만 설명해요.

### stardust의 스레드

사례의 `threads`가 sd를 잴 스레드 수들이에요. 기본은 `(1, 10)`이고, 10은 이 기계의 성능 코어 수이자 sd의 기본 스레드 수예요. 측정 프로세스는 `harness.sd_threads(n)` 안에서 `sd.set_num_threads(n)`을 부르고, 측정이 끝나면 원래 값으로 되돌려요.

1,989개 중 1,550개는 1·10스레드를 모두 재고, 437개는 1스레드만, 2개는 10스레드만 재요. 1스레드만 재는 사례는 나눌 일이 없는 호출이에요. 3×3 행렬 하나, 원소 $10^3$개, 스칼라 하나, 뷰 만들기처럼 병렬 경로가 없거나 병렬 기준값 아래인 경우예요. 그중 몇 개는 일부러 10스레드로도 재요. 기준값 아래에서 풀을 쓰는 실수를 잡으려는 줄이에요.

### 비교 대상의 스레드: `fixed`와 `follow`

Python 비교 대상(`Ref`)은 두 방식 중 하나로 재요.

| 방식 | 언제 | 어떻게 재나 |
|---|---|---|
| `"fixed"` (기본) | 원소별 계산, 리덕션, 정렬, 데이터프레임, 특수함수와 분포 함수처럼 BLAS를 거의 쓰지 않는 비교 | 라운드마다 한 번, 그 라이브러리의 기본 스레드로 재요. numpy·scipy의 원소별 계산과 pandas는 1스레드예요 |
| `"follow"` | BLAS·LAPACK이 일의 대부분인 비교. array의 `matmul`·`cov`·`corrcoef`·`tensordot`, linalg 전체, regression, optimize | sd의 스레드 수마다, 비교 대상의 BLAS·OpenMP 스레드를 같은 수로 묶어 재요 |

`fixed`는 사용자가 그 라이브러리를 그대로 쓸 때의 시간이에요. numpy의 `sin`은 설정을 바꿔도 1스레드로 도니, sd의 1스레드와 10스레드를 모두 numpy 하나와 견줘요. `follow`는 같은 스레드 수에서 누가 빠른지를 봐요. BLAS가 일의 대부분이면, 비교 대상의 BLAS 스레드를 sd와 같게 두어야 스레드 수마다 견줄 수 있어요. 그래서 sd의 1스레드 줄은 1스레드 BLAS와, 10스레드 줄은 10스레드 BLAS와 만나요. linalg는 308개 모두, regression은 190개 중 120개, optimize는 113개 중 86개, array는 10개가 `follow` 비교 대상을 가져요. R은 어느 쪽이든 늘 1스레드로 돌아요([R과 비교하기](#r과-비교하기)).

### BLAS 스레드는 측정 프로세스마다 묶어요

numpy, scipy, sd의 BLAS·LAPACK은 모두 Accelerate예요. Accelerate는 스레드 수를 프로세스가 뜰 때 환경 변수 `VECLIB_MAXIMUM_THREADS`로 한 번만 읽어요. threadpoolctl로는 실행 중에 바꿀 수 없어요. 한 프로세스에서 "sd 1스레드"를 재더라도 그 안의 BLAS 호출은 여러 코어를 쓸 수 있다는 뜻이에요.

그래서 감독 프로세스는 BLAS 스레드 설정마다 측정 프로세스를 따로 띄워요.

```python
        # bench/speed/run.py (WorkerHandle.__init__)
        env = dict(os.environ)
        env.pop("VECLIB_MAXIMUM_THREADS", None)
        if blas_threads is not None:
            env["VECLIB_MAXIMUM_THREADS"] = str(blas_threads)
```

사례 하나(`threads=(1, 10)`)는 두 프로세스에 나뉘어 재요.

| 측정 프로세스 | `VECLIB_MAXIMUM_THREADS` | 여기서 재는 것 |
|---|---|---|
| 1스레드용 | `1` | sd 1스레드, `follow` 비교 대상의 1스레드 |
| 기본용 | 설정하지 않아요(Accelerate의 기본값) | sd 10스레드, `follow` 비교 대상의 10스레드, `fixed` 비교 대상, R |

그 밖의 스레드 수(`--threads 1,4,10`처럼)를 주면 그 수마다 프로세스를 하나씩 더 띄워요. scikit-learn의 OpenMP는 threadpoolctl로 같은 프로세스 안에서 묶을 수 있어서 따로 띄우지 않아요. 라운드가 여럿이면 라운드마다 측정 프로세스를 다시 띄워요. 짧은 병렬 호출은 프로세스마다 빠른 쪽이나 느린 쪽에 자리 잡을 수 있어서, 최솟값이 여러 프로세스에서 나오게 하려는 거예요. 사례의 데이터는 프로세스마다 `setup`으로 다시 만들어요.

<Callout type="note" title="sd 1스레드는 BLAS도 1스레드예요">
sd의 1스레드 줄은 `VECLIB_MAXIMUM_THREADS=1`인 프로세스에서 재요. 그래서 `matmul`, `cov`, linalg의 분해처럼 Accelerate를 부르는 사례는 1스레드와 10스레드의 차이가 sd 풀만이 아니라 BLAS의 차이까지 담아요. 사용자가 `sd.set_num_threads(1)`만 부르면 Accelerate는 여전히 여러 코어를 쓸 수 있으니, 표의 1스레드 줄은 그보다 엄격한 조건이에요.
</Callout>

## 사례

### 모델: `Case`, `Ref`, `RRef`, `Check`

사례 하나는 **한 크기에서의 호출 하나**예요. 데이터를 만드는 `setup`과, 그 데이터를 받아 잴 함수를 돌려주는 공장(factory)으로 이루어져요. numpy 배열을 sd 배열로 바꾸거나 상수 열을 붙이는 변환은 `setup`이나 공장에서 해서 시간에 들어가지 않게 해요. regression의 실제 사례 하나예요.

```python
    # bench/speed/cases/regression.py (_ols_case)
    return Case(
        area="regression",
        group="ols",
        name="ols(y, X)",
        size=_size(n, k),
        setup=setup,
        sd=lambda d: lambda R=_R(), y=d["ys"], X=d["Xs"]: R.ols(y, X),
        refs=(
            Ref("statsmodels", lambda d: lambda: _sm().OLS(d["y"], d["Xc"]).fit(), threads="follow"),
            Ref("scikit-learn", lambda d: lambda: _linreg().fit(d["X"], d["y"]), threads="follow", lib="sklearn"),
        ),
        quick=quick,
        note="10^4행: 2^15·2^16행 문턱 아래의 중간 크기" if size == (10_000, 10) else "",
    )
```

`sd=lambda d: lambda …: R.ols(y, X)`처럼 람다가 두 겹이에요. 바깥 람다가 데이터 `d`를 받아 안쪽의 인자 없는 함수를 만들고, 하네스는 안쪽 함수만 되풀이해 불러요. 데이터를 꺼내는 일(`d["ys"]`)도 기본 인자로 미리 묶어 두어 시간에 들어가지 않아요. statsmodels는 상수 열을 미리 붙인 `d["Xc"]`를 받아요.

| 필드 | 뜻 |
|---|---|
| `area`, `group`, `name`, `size` | 사례의 id를 이뤄요. `group`은 짧은 영어 키(`ols`, `binary-f64` 등)이고, 표의 절 제목은 사례 파일의 `TITLES`(키 → 한글 제목)에서 와요 |
| `n` | 호출 하나가 다루는 원소 수. 원소당 비용을 낼 때 써요 |
| `setup` | 사례마다, 라운드마다 한 번 데이터를 만들어요 |
| `sd`, `refs` | sd의 공장과 비교 대상들 |
| `threads` | sd를 잴 스레드 수들(기본 `(1, 10)`) |
| `quick` | 빠른 묶음에 드는지 |
| `cost` | 이 사례의 1스레드 시간이 들어갈 비용표와 키, 예: `("stats", "normal.cdf")` |
| `note` | 표의 비고 열(한글) |
| `timing` | `measure`의 기본값을 바꿔요 |
| `teardown` | `setup`이 바꾼 전역 설정을 되돌려요 |
| `check` | 점검 실행에서 결과를 견주는 방법(`Check`) |

비교 대상은 두 종류예요.

- **`Ref(label, make, threads=..., lib=..., n=..., differs=...)`**: Python 비교 대상이에요. `label`은 표의 열 이름("scipy", "scikit-learn lbfgs tol=1e-10")이고, `lib`은 결과에 적는 라이브러리 이름이에요(생략하면 `label`의 첫 단어). `n`은 비교 대상이 너무 느려 입력의 일부만 잴 때 그 원소 수예요. `differs`는 비교 대상이 이 입력에서 원래 다른 계산을 할 때 그 까닭이에요(R의 `choose`는 정수가 아닌 k를 반올림한다 등). 그런 비교 대상은 결과 확인에서 빼고, 까닭을 표의 비고에 붙여요.
- **`RRef(label, expr, data, setup, packages, sets)`**: R 비교 대상이에요. `expr`은 부를 때마다 평가할 R 식이고, `data`는 사례 데이터의 어느 배열을 R의 어느 이름으로 넘길지예요. `sets`는 새 입력을 돌려 쓰는 사례의 입력 묶음 목록이고, R도 다른 쪽처럼 호출마다 다음 묶음을 써요([R과 비교하기](#r과-비교하기)).
- **`Check(sd, ref, rtol, atol, agree, skip)`**: 점검 실행이 결과를 견주는 방법이에요. 결과의 꼴이 다르면 견줄 값을 고르는 함수(`sd`, `ref`)를 주고, 값을 견줄 수 없으면(두 난수 흐름, 대입문 등) 까닭을 `skip`에 적어요([결과 확인](#결과-확인---smoke)).

### id와 고르기

사례 id는 `영역/묶음/이름 [크기]`예요. 같은 id가 둘이면 등록부를 불러올 때 오류가 나요. id는 ASCII로만 쓰고, 크기는 정해진 표기 하나로 적어요(`registry.py`의 `SIZE_RE`, 테스트가 확인해요).

| 크기 표기 | 뜻 | 예 |
|---|---|---|
| `COUNT [UNIT]` | 원소 수. $10^3$ 이상의 10의 거듭제곱은 `10^k`로 쓰고, 단위는 `rows`, `points`, `matrices` 중 하나 | `10^6`, `200`, `10^5 rows` |
| `(m, n)` | 모양. 쉼표 뒤에 빈칸 하나, 자릿수 쉼표 없이 | `(100000, 10)` |
| `B x (m, n)` | 같은 모양의 문제 B개의 배치 | `1000 x (8, 8)` |
| `n=COUNT` | 최적화 문제의 차원 | `n=100` |

이름이 붙은 시험 문제는 크기가 아니라 이름에 넣어요. 비교 대상의 이름(`Ref.label`)도 ASCII이고, 비고(`note`)만 한글로 써요. `list`로 보면 이래요.

```text
  QC  special/array-1e6/erf(x) [10^6]                                   1, 10 threads · scipy, Boost
      special/array-small/erf(x) [10^3]                                 1, 10 threads · scipy, Boost
  Q   special/scalar/erf(x)                                                         1 thread · scipy
  Q   regression/ols/ols(y, X) [(100000, 10)]              1, 10 threads · statsmodels, scikit-learn
```

맨 앞의 `Q`는 빠른 묶음, `C`는 비용표 사례예요. 끝은 sd의 스레드 수와 비교 대상이에요.

`list`, `estimate`, `run`은 고르기를 같이 써요. 영역은 위치 인자로 주고(주지 않으면 모든 영역), `--match`는 id 전체에 맞춰요. `*`나 `?`가 있으면 id 전체와 맞춰 보는 glob이고, 없으면 부분 문자열이에요. `[`와 `]`는 보통 글자라서 표에서 복사한 id가 그대로 맞아요. 여러 번 주면 하나만 맞아도 돼요. `--quick`은 빠른 묶음만 골라요.

```bash
.venv/bin/python -m bench.speed list special --match erf
.venv/bin/python -m bench.speed list --match 'regression/ols/ols(y, X) [*'
.venv/bin/python -m bench.speed list --match 'stats/discrete/*'
.venv/bin/python -m bench.speed list stats --quick
```

**빠른 묶음**(`quick=True`)은 영역마다 대표 사례를 골라 둔 것이에요. 합쳐서 122개이고, 영역마다 1–3분 안에 돌아요. 짧은 시간에 여러 영역을 훑어볼 때 써요. **비용표 사례**(`cost`가 있는 사례)는 460개로, special 98개와 stats 362개예요([비용표](#비용표)).

### 공정하게 맞추기

배율이 뜻을 가지려면 두 쪽이 같은 입력으로 같은 일을 해야 해요. 사례는 이렇게 맞춰요.

- **같은 입력.** 한 사례의 모든 호출은 같은 `setup`이 만든 데이터를 써요. sd 배열은 같은 numpy 배열에서 `sd.asarray`로 만들어요. 새 입력을 돌려 쓰는 사례는 양쪽이 같은 입력을 같은 순서로 받아요.
- **같은 일.** 비교 대상은 sd와 같은 결과를 내도록 옵션을 맞춰요. sd의 정렬은 기본이 안정 정렬이라 numpy의 `sort`와 `argsort`는 `stable=True`로 불러요. pandas는 같은 옵션(안정 정렬, `ddof=0`)과 같은 결측값 표현으로 불러요. linalg에서는 numpy의 `full_matrices`와 `mode`를 sd에 맞추고, scipy의 `cho_solve`는 sd가 `cholesky`의 결과를 받듯 `cho_factor`의 결과를 받아요.
- **같은 정확도.** 반복해서 푸는 비교 대상은 sd의 정확도까지 풀게 해요. scikit-learn의 풀이기는 `tol=1e-10`(saga는 `1e-8`)을 받고, 그 사실이 열 이름에 들어가요("scikit-learn lbfgs tol=1e-10"). 기본 `tol`로 풀었을 때 계수의 오차가 얼마인지는 그 사례의 비고에 적어요. scipy의 다변량 정규 cdf는 sd의 `atol`을 `abseps`로 받아요(`releps=0`). 느슨한 정확도로 빨리 끝내는 쪽이 이겨 보이지 않게 하려는 거예요.
- **기본과 대안을 함께.** 라이브러리에 방식이 여럿이면 열을 더해요. stats의 "scipy new API"(`scipy.stats.Normal` 같은 새 클래스, 64개)와 "scipy.special"(스칼라 cdf, 14개), frame의 "pandas python str"(38개)과 "pandas pyarrow engine"(`read_csv`의 `engine="pyarrow"`, 14개), array의 "numpy default (unstable)", random의 "numpy PCG64"와 "numpy Philox"(sd가 쓰는 비트 생성기)가 그런 열이에요.
- **너무 느린 비교 대상.** 비교 대상이 입력 전체에 너무 오래 걸리는 경우에는 입력의 앞부분만 재고(`Ref.n`), 표에서 원소 수에 비례해 사례의 크기로 늘린 값에 `*`를 붙여요. stats에서는 scipy 비교 37개 사례가 그래요.

### 결과 확인: `--smoke`

같은 일을 시키도록 호출을 짰는지는 점검 실행으로 확인해요. `run --smoke`는 시간을 재지 않고 사례마다 sd와 비교 대상을 한 번씩 부른 뒤 결과를 견줘요(`check.py`). 견주는 상대는 첫 Python 비교 대상과 모든 R·Boost 비교 대상이고, `differs`가 있는 비교 대상은 빼요. R의 값은 같은 R 세션에서 받아 와요.

- 두 값은 둘 다 NaN이거나, 같거나, 큰 쪽 크기의 $10^{-6}$(사례의 `Check.rtol`) 안이면 맞아요. 0 근처에서 다르게 언더플로하는 값($10^{-300}$ 안)도 맞아요.
- 한쪽만 NaN인 값은 틀린 것으로 세지 않고 NaN 비율로 따로 적어요. 비교 대상이 sd보다 NaN을 1%p 넘게 더 내면 표의 비고에 그 비율이 붙어요.
- 둘 다 값을 낸 점 중 절반(`Check.agree`) 이상이 맞아야 통과해요. special과 stats의 입력은 함수의 어려운 구석에 몰려 있어 비교 대상의 정확도가 떨어지는 점이 섞이지만, 다른 함수를 계산하는 비교 대상(인자 순서가 틀리거나 인자를 반올림하는 것)은 거의 모든 점에서 틀리기 때문이에요.
- 결과 확인이 실패한 사례는 실패로 세고, 종료 코드가 1이에요.

점검 실행은 아무것도 재지 않으므로 사례를 여러 갈래로 나눠 동시에 돌려요. 프로세스는 R 세션까지 합쳐 `--jobs`개(기본 8, 최대 10) 이하이고, R을 쓰면 갈래 수를 절반으로 줄여요. 메모리 한도는 모든 갈래를 합쳐 보고, 넘으면 메모리를 가장 많이 쥔 갈래의 사례만 멈췄다가 마지막에 혼자 다시 돌려요. 측정 실행은 늘 사례를 하나씩 재요.

결과가 참값에 얼마나 가까운지는 [테스트 체계](/internals/core/testing/)와 [정확도 측정](/internals/core/accuracy/)이 맡아요. 점검 실행은 두 쪽이 같은 계산을 하는지만 봐요.

## R과 비교하기

R 비교 대상은 array 46개, linalg 60개, special 85개, stats 290개, regression 56개, optimize 29개예요. base R 함수가 대부분이고, 다변량 정규·t 누적분포의 `mvtnorm`, 분위 회귀의 `quantreg`, 강건 회귀의 `robustbase`, 모형 검정의 `lmtest`와 `car`, 띠 행렬의 `Matrix`, 비선형 최소제곱의 `minpack.lm` 꾸러미를 써요. optimize의 R은 목적 함수, 잔차, 기울기를 R로 다시 써서 불러요. R의 반복 상한과 허용오차는 sd·scipy 호출과 같은 멈춤 일이 되도록 Python 쪽 값에 맞추고, R의 알고리즘이 다른 곳은 사례의 비고에 적어요.

R을 사례마다 따로 띄우면 시작 비용과 꾸러미 불러오기가 매번 들어요. 그래서 실행 하나가 R 프로세스(`R --vanilla`) 하나를 띄워 끝까지 써요(`rsession.py`). R 프로세스는 표준 입력으로 요청을 받아요.

시간은 R 안에서 재므로, Python과 R 사이에 데이터를 넘기는 비용은 들어가지 않아요. R의 시계는 `Sys.time()`이에요. R은 배치 안에서 쓰레기 수집을 끌 수 없어서 배치 전에 `gc()`를 한 번 불러요. R은 1스레드로 돌아요. 이 기계의 R은 OpenMP판 OpenBLAS를 쓰므로 `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`로 띄워요. R의 표준 오류 출력은 파이프가 아니라 파일로 받아요. 파이프가 차면 R이 멈추기 때문이에요. R 세션은 기본용 측정 프로세스의 자식이고 같은 프로세스 그룹에 들어가요. 감독이 한계를 넘은 측정 프로세스의 그룹을 죽이면 R도 함께 죽어요.

R이 설치되어 있지 않으면 R 비교만 건너뛰고 나머지는 그대로 재요. `--no-r`로 일부러 뺄 수도 있어요.

### Boost.Math

special과 stats의 Boost.Math 비교 대상(`boost.py`, `boost_speed.cpp`)은 정확도 측정이 쓰는 Boost 소스(`build/comparators/boost-math`)를 정확도 측정과 같은 함수와 같은 옵션(sd의 최적화 옵션 `-O3 -mcpu=native -ffp-contract=off`와 `-std=c++17`)으로 빌드해요. 배열 하나에 ctypes 호출 한 번이고, 그 안에서 원소마다 Boost 함수를 직접 부르는 C++ 반복문이 돌아요. 빌드한 라이브러리의 이름에 소스, 옵션, Boost 체크아웃의 커밋이 들어가서 하나라도 바뀌면 다시 빌드해요. 소스가 없으면 Boost 열을 빼고 돌아요. 비교 대상의 Boost 판과 sd.special이 담은 Boost 판은 다를 수 있어서 결과 파일에 둘 다 적어요.

## 긴 실행

모든 사례를 3라운드로 다시 재면 몇 시간이 걸릴 수 있어요. 그동안 사례 하나가 멈추거나 메모리를 다 쓰거나 기계가 바빠질 수 있어요. 실행기는 이런 일에 대비해 측정을 별도 프로세스에서 해요.

감독은 측정 프로세스(`worker.py`)에 한 줄짜리 JSON 요청을 보내고 한 줄짜리 답을 받아요. 측정되는 코드가 `print`한 내용은 로그로 가요. 측정 프로세스는 표준 출력을 복사해 둔 뒤 원래 표준 출력을 표준 오류로 돌리고, 복사본으로만 답을 써요. 사례가 끝나면 numpy의 오류 설정을 되돌리고 사례의 `teardown`을 불러서, 한 사례의 전역 설정이 다음 사례로 새지 않게 해요.

### 한계

한계값은 `run.py`의 `Limits`에 있어요.

| 한계 | 값 | 넘으면 |
|---|---|---|
| 사례 하나(한 라운드의 모든 스레드와 비교 대상) | 15분 (`--timeout 분`) | 프로세스 그룹을 죽이고 "제한 시간 초과"로 적어요 |
| 상주 메모리(살아 있는 모든 측정 프로세스와 R의 합) | 16 GB (`--max-rss GB`) | 프로세스 그룹을 죽이고 "메모리 초과"로 적어요 |
| 감시 간격 | 2초 | |
| 측정 프로세스 하나가 맡는 사례 | 40개 | 새 프로세스로 바꿔 쌓인 메모리를 버려요 |
| 쉬는 측정 프로세스의 메모리 | 2 GB | 다른 프로세스가 재기 전에 닫아요 |
| 측정 프로세스가 뜨는 시간 | 30분 | `import stardust`가 C++를 다시 빌드할 수 있어서 넉넉히 둬요 |

한계를 넘거나 측정 프로세스가 죽으면, 그 사례를 실패로 적고 새 측정 프로세스로 다음 사례를 재요. 실행 전체는 멈추지 않아요.

메모리는 macOS의 libproc(`proc_pidinfo`, `proc_listchildpids`)으로 읽어요. `ps` 같은 프로세스를 2초마다 띄우면 그 자체가 측정을 방해하기 때문이에요. 쉬는 측정 프로세스도 메모리 합에 들어가요. macOS는 해제한 큰 블록을 상주 메모리에 남겨 두기도 해서, 원소 $10^6$개 사례를 마친 프로세스가 GB 단위를 쥔 채 쉬고 있을 수 있어요. 그래서 2 GB를 넘게 쥔 채 쉬는 프로세스는 닫았다가 필요할 때 다시 띄워요.

### 조용한 기계에서 재기

다른 프로그램이 CPU를 쓰고 있으면 결과가 흔들려요. 그래서 실행기는 CPU를 두 번 살펴요.

1. **시작하기 전.** 3초 동안 다른 프로세스가 쓰는 CPU를 재요. 커널의 CPU별 시간 계수기(`host_processor_info`)에서 기계 전체의 사용 시간을 읽고, 실행 자신(감독, 측정 프로세스, R)의 CPU 시간을 빼요. 평균 1코어(`--quiet-cores`)를 넘으면 가장 바쁜 프로세스들을 보여 주고, 10초 간격으로 다시 재며 조용해질 때까지 최대 10분 기다려요. 그래도 바쁘면 경고를 남기고 시작해요. `--no-wait`는 기다리지 않고, `--strict`는 바쁘면 멈춰요(종료 코드 1). `--smoke`는 재지 않으므로 검사하지 않아요.
2. **사례마다.** 사례 하나를 재는 동안 다른 프로세스가 평균 몇 코어를 썼는지(`other_cpu`) 적어요. 1코어를 넘으면 그 사례를 `busy`로 표시하고 진행 줄에 알려요.

`busy`인 사례는 표에서 이름 옆에 †가 붙고, `compare`는 느려짐으로 세지 않아요. 이런 사례만 골라 다시 잴 수 있어요.

```bash
.venv/bin/python -m bench.speed run --rerun-busy build/speed/<실행>.jsonl
```

다시 잴 때는 원래 실행의 라운드 수, 스레드 수, R 사용 여부를 따라요(명령행에 주면 그 값이에요). 그 실행을 `promote`하면 기준선의 그 사례들만 바뀌어요.

CPU 계수기를 읽을 수 없는 기계에서는 1분 부하가 3을 넘을 때 경고만 해요. 1분 부하는 사례마다 기록도 해요.

### 끊겨도 이어 달리기

실행 파일은 JSON Lines예요. 첫 줄은 실행의 머리이고, 사례 하나가 끝날 때마다 그 사례의 줄을 배치 시간까지 덧붙여요. Ctrl-C나 전원 문제로 끊겨도 많아야 사례 하나를 잃고, 끊긴 마지막 줄은 읽을 때 버려요. 같은 실행을 남은 곳부터 이어요.

```bash
.venv/bin/python -m bench.speed run --resume build/speed/<실행>.jsonl
```

진행 줄에는 경과 시간과 남은 예상 시간이 나와요. 예상은 기준선에 적힌 사례별 라운드당 시간으로 어림하고, 이번 실행이 지금까지 기준선보다 얼마나 빨랐는지의 비율로 고쳐요. 기준선에 없는 사례는 그런 사례 중 이번 실행에서 이미 잰 것들의 평균으로 어림해요. `estimate` 명령은 같은 방식으로 재기 전에 걸릴 시간을 보여 줘요.

```bash
.venv/bin/python -m bench.speed estimate stats
```

1분 넘게 걸린 실행이 끝나면 macOS 알림을 띄워요(`--no-notify`로 꺼요). 로그는 `build/logs/speed/<시각>.log`에 쌓여요. 터미널에 나온 줄(시각과 함께), 사례마다 한 줄의 진행, 측정 프로세스의 표준 오류가 들어가고, 로그의 경로는 실행 파일에도 적어 둬요.

## 결과와 표

### 실행 파일과 기준선

| | 실행 파일 | 기준선 |
|---|---|---|
| 위치 | `build/speed/<날짜-시각>[-이름].jsonl` (git이 무시해요) | `bench/speed/results/<영역>.json` (저장소에 둬요) |
| 범위 | 실행 하나가 잰 사례 | 영역 하나의 모든 사례 |
| 내용 | 커밋과 작업 중 변경 여부, 기계(칩, 코어, macOS, 메모리), 라이브러리 판(numpy, scipy, pandas, statsmodels, scikit-learn, R과 그 꾸러미, 비교 대상의 Boost와 sd.special이 담은 Boost), BLAS(numpy·scipy와 R이 쓰는 BLAS·LAPACK, 그 스레드 변수), sd의 기본 스레드 수, 시작할 때의 부하, 사례마다 측정 전부 | 측정마다 그 측정이 온 실행과 라운드 수, 그리고 그 실행들의 환경 |

사례의 측정 하나에는 대상, 스레드 수, 최솟값, 중앙값, 잡음 폭, 배치 수, 배치당 호출 수, 배치 시간 전부, 결과의 NaN 비율이 들어가요. 점검 실행이면 결과 확인도 들어가요. 사례에는 라운드당 시간, 1분 부하, 최대 메모리, `other_cpu`, `busy`도 붙어요. 배치 시간 전부는 실행 파일에만 있고 기준선에는 넣지 않아요.

`promote`가 실행 파일을 기준선에 넣어요.

```bash
.venv/bin/python -m bench.speed promote build/speed/<실행>.jsonl
```

- 측정 하나(대상, 스레드 수) 단위로 합쳐요. 실행이 잰 측정만 바꾸고, 실행에 없거나 실패한 측정(1스레드만 잰 실행의 10스레드, 시간 초과한 R 등)은 기준선 값을 둬요. 그래서 함수 하나, 스레드 수 하나만 다시 재서 넣을 수 있어요.
- 기준선보다 적은 라운드로 잰 측정은 `--force` 없이는 넣지 않아요.
- 등록부에서 사라진 사례는 기준선에서 빼고, 사례 순서는 등록부의 순서를 따라요.
- 끝나지 않은 실행은 넣지 않아요(`--force`로 넣을 수 있어요). `--smoke` 실행은 넣을 수 없어요. 넣을 수 없는 실행을 넣으려 하면 종료 코드가 2예요.
- 넣고 나면 그 영역의 표 `bench/<영역>/speed.md`를 다시 만들어요. 실행에 비용표 사례가 들어 있으면 `cost`를 돌리라고 알려요.

### 생성되는 표 읽기

`bench/<영역>/speed.md`는 기준선에서 만드는 파일이에요(`promote`가 만들고, `table` 명령으로 따로 만들 수도 있어요). 손으로 고치지 않아요. 묶음마다 절이 하나이고, 절 제목은 사례 파일의 `TITLES`에서 와요. 맨 위에 측정 환경(기계, 라이브러리 판)이 있어요.

- **시간**은 호출 한 번의 시간이에요. 모든 라운드의 배치 중 가장 빠른 값이에요.
- **배율(÷ sd)**은 비교 대상 시간 ÷ sd 시간이에요. 1보다 크면 sd가 빨라요. sd가 느린 줄은 배율을 굵게 써요.
- **잡음**은 그 줄의 측정마다 잡음 폭을 구한 것 중 가장 큰 값이에요.
- **†**는 잴 때 다른 프로세스가 CPU를 1코어 넘게 쓴 사례, **\***는 입력의 일부로 재서 늘린 값이에요.
- 비고에는 사례의 `note`, 비교 대상의 `differs` 까닭, 비교 대상이 sd보다 NaN을 1%p 넘게 더 낸 비율이 붙어요.
- 측정이 실패한 것은 표 끝의 "측정 실패" 절에 오류와 함께 모여요.

묶음은 비교 대상의 방식에 따라 두 모양 중 하나로 나와요.

| 묶음의 비교 대상 | 표의 모양 |
|---|---|
| 모두 `fixed` | 사례 하나에 한 줄. sd의 스레드 수마다 열이 있고, 비교 대상마다 시간 열과 스레드별 배율 열이 붙어요 |
| `follow`가 하나라도 있음 | 사례와 스레드 수마다 한 줄. "스레드" 열이 있고, `follow` 비교 대상은 그 줄의 스레드 수로 잰 값이에요 |

묶음 머리에는 비교 대상마다 배율의 요약이 한 줄씩 붙어요. 스레드 수마다 배율의 중앙값, 기하평균, sd가 느린 줄의 수예요.

10%를 넘게 느려졌어도 그 차이가 잡음 폭 안이면 코드가 아니라 기계 탓일 수 있어요. 예를 들어 잡음 폭이 15%인 측정이 12% 느려졌다면 "잡음 안"으로 적고, 종료 코드에도 세지 않아요.

비교 대상 라이브러리의 시간 변화도 함께 보여요. 비교 대상들의 새 ÷ 기준선의 중앙값이에요. numpy와 scipy도 같이 느려졌다면 코드가 아니라 기계 상태가 달라진 것이고, 이 값이 10%를 넘게 벗어나면 그렇게 알려요. 문턱은 `--threshold`(기본 0.10)로 바꾸고, `--base FILE`로 기준선 대신 다른 결과 파일과 비교할 수 있어요. `--faster`는 빨라진 것도 보이고, `--out FILE`은 보고서를 Markdown 표로 써요. 실행의 사례가 기준선에 하나도 없으면 비교할 것이 없다고 알리고 종료 코드 1로 끝나요.

## 비용표

### 무엇에 쓰나

배열의 원소별 연산은 일이 float64 원소 $2^{15}$개의 덧셈 분량 이상이면 스레드로 나누고, 태스크 하나는 $2^{12}$개 분량이에요([스레드풀과 결정성](/internals/core/threads/)). 특수함수와 분포 함수는 원소 하나의 비용이 덧셈 하나의 몇 배에서 수천 배예요. 덧셈과 같은 원소 수 기준을 쓰면 비싼 함수는 너무 늦게 나눠요.

그래서 함수마다 **원소 하나의 1스레드 비용(ns)**을 표로 두고, 병렬 분할이 그 비용으로 일의 양을 세요. 이 표가 비용표예요. special에서는 비용을 덧셈 한 번의 비용으로 나눈 가중치로 바꿔 배열의 이터레이터에 넘겨요.

```cpp
// csrc/special/cost.hpp
inline constexpr std::int64_t kMaxWeight = 256;
constexpr std::int64_t weight_of(double ns) {
    const double w = ns / kAddNs;
    return w < 1.0 ? 1 : std::min<std::int64_t>(static_cast<std::int64_t>(w + 0.5), kMaxWeight);
}
```

가중치가 $w$인 함수는 원소 $2^{15}/w$개부터 나누고, 태스크 하나는 원소 약 $2^{12}/w$개예요. 가중치는 256에서 잘라요. 그러면 가장 비싼 함수도 원소 128개부터 나눠요. 자르지 않으면 아주 비싼 함수는 태스크 하나가 원소 하나가 되고, 스레드들이 풀의 카운터를 두고 다퉈요. stats는 분포와 메서드마다 같은 방식으로 비용을 넘기고(`stats/engine.hpp`의 `cost_of`), 표에 줄이 없으면 분포가 스스로 주는 어림값이나 20 ns를 써요.

비용은 나눌 위치만 바꿔요. 결과의 비트는 바꾸지 않아요. 두 배쯤 틀려도 병렬이 시작되는 크기가 조금 옮겨질 뿐이에요. 반대로 비용을 여러 배 크게 잡으면 일을 수십 원소짜리 태스크로 잘게 쪼개서 10스레드가 1스레드보다 느려질 수 있어요.

### 어떻게 만드나

`cost` 태그가 있는 사례의 **sd 1스레드 최솟값 ÷ 원소 수**가 그 키의 비용이에요. `cost` 명령이 기준선에서 이 값을 모아 두 헤더를 다시 써요.

```bash
.venv/bin/python -m bench.speed cost            # 두 헤더 다시 쓰기
.venv/bin/python -m bench.speed cost --check    # 쓰지 않고 바뀔지만 알리기(바뀌면 종료 코드 1)
```

| 표 | 키 | 채우는 사례 |
|---|---|---|
| `csrc/special/cost_table.hpp` | 함수 이름(`erf`, `erf_complex`, `_add`) | special의 원소 $10^6$개 사례(비중심 분포 함수는 $10^5$개), 그리고 덧셈과 엔진 시험용 커널 |
| `csrc/stats/cost_table.hpp` | `분포.메서드`(`normal.cdf`) | stats의 연속·이산·극값 분포의 배열 사례 |

- 같은 키의 사례가 여럿이면(매개변수 묶음이 여럿) 기하평균을 써요.
- 이산 분포의 좁은 지지 사례는 키 `분포.메서드@memo`로 따로 재요. 스칼라 매개변수에서 정수점 기억 표가 답하는 호출은 원소당 1–2 ns인데, 넓은 지지의 계산(수백 ns에서 수십 µs)과 섞으면 좁은 호출이 무거운 가중치를 받아 10스레드가 1스레드보다 느려져요. 이 줄은 표에서 `memo = true`가 돼요. 잰 적이 없는 `@memo` 줄은 `cost.py`의 값으로 채워서, 첫 측정 전에도 좁은 지지의 가중치가 켜져요. 역함수 줄은 점검 실행에서 잰 1스레드 시간(`MEMO_PRESET_NS`), 나머지는 `MEMO_DEFAULT_NS`(1.5 ns)이고, 측정하면 잰 값으로 바뀌어요.
- 기준선에 없는 키는 지금 헤더의 값을 그대로 둬요. 영역 하나나 함수 하나만 다시 재고 `cost`를 돌리면 잰 줄만 바뀌어요. 헤더 맨 위의 주석은 몇 줄을 기준선에서 쟀는지와, 나머지 줄이 앞 파일에서 이어 온 값이라는 것을 적어요.
- 헤더의 주석이 아니라 줄이 달라질 때만 "바뀜"으로 세요. `cost --check`는 기준선이 없는 영역, 먹이는 사례가 없어 바뀌지 않을 줄, 줄이 없는 사례 키도 함께 알려요.
- 헤더가 바뀌면 다음 `import stardust`에서 C++가 다시 빌드돼요.

생성된 special 표의 일부예요.

```cpp
// csrc/special/cost_table.hpp
namespace sd::special::cost_table {

struct Row {
    std::string_view name;
    double ns;
};

inline constexpr Row kRows[78] = {
    {"_add", 0.19},
    {"_cf_tan", 16},
    {"_fma3", 0.24},
    {"_powers4", 0.45},
    {"_sum4", 0.3},
    {"airy_ai", 270},
    {"beta", 60},
    {"betainc", 401},
```

`_add`가 단위예요. 연속인 float64 두 배열의 덧셈 원소 하나의 비용이고, 다른 함수의 가중치는 이 값으로 나눠 구해요. `_add` 사례는 배치를 25개, 시간 예산을 5초로 늘려 재요. `csrc/special/cost.hpp`는 연산마다 이 표의 어느 이름을 쓰는지만 적어요(`cost_table::ns("erf")`). `ns`는 `consteval` 함수라, 표에 없는 이름을 쓰면 컴파일되지 않아요. 측정에서 빠진 함수가 조용히 아무 값이나 받는 일이 없어요.

stats 표는 줄마다 `memo` 열이 하나 더 있고, 같은 방식으로 찾아요.

```cpp
// csrc/stats/cost_table.hpp
constexpr double find(std::string_view dist, std::string_view method, bool memo = false) {
    for (const Row& r : kRows)
        if (r.dist == dist && r.method == method && r.memo == memo) return r.ns;
    return -1.0;
}
```

## 숫자를 읽을 때

- **한 기계의 숫자예요.** 모든 측정은 Apple M4 Pro(성능 코어 10, 효율 코어 4)에서 해요. sd의 기본 스레드 수 10은 성능 코어 수예요. 표 맨 위의 측정 환경에 칩, 코어 수, macOS, 라이브러리 판이 적혀 있어요. 다른 기계에서는 배율을 경향으로만 읽어요.
- **최솟값은 좋은 조건의 시간이에요.** 같은 호출을 연달아 부르는 상황이라 캐시가 따뜻하고 스레드풀의 워커도 깨어 있어요. 병렬 호출 사이에 오래 쉬는 실제 코드에서는 워커를 깨우는 비용이 더 들 수 있어요([스레드풀과 결정성](/internals/core/threads/)).
- **잡음 열을 같이 봐요.** 잡음이 큰 줄의 작은 배율 차이는 같음으로 읽어요.
- **1스레드 줄은 BLAS도 1스레드예요.** BLAS를 부르는 사례에서 sd의 1스레드 줄은 Accelerate까지 1스레드로 묶은 시간이에요.
- **†와 \*를 놓치지 않아요.** †는 기계가 바쁠 때 잰 줄이고, \*는 입력의 일부로 재서 늘린 값이에요.

재서 나온 시간은 영역마다 `bench/<영역>/speed.md` 표에 모여요. 영역마다 어디서 왜 빠르거나 느린지, 무엇과 견주는지는 [배열 성능](/internals/array/performance/), [데이터프레임 성능](/internals/frame/performance/), [난수 성능과 검증](/internals/random/performance/), [특수함수 정확도와 성능](/internals/special/accuracy-performance/), [통계 정확도와 성능](/internals/stats/accuracy-performance/), [회귀 정확도와 성능](/internals/regression/accuracy-performance/), [최적화 정확도와 성능](/internals/optimize/accuracy-performance/)에서 다뤄요.

## 명령 모음

명령은 모두 라이브러리 저장소 맨 위에서 돌려요.

```bash
.venv/bin/python -m bench.speed list stats --quick                 # 사례 보기 (Q: 빠른 묶음, C: 비용표)
.venv/bin/python -m bench.speed estimate                           # 걸릴 시간 어림
.venv/bin/python -m bench.speed run stats --smoke                  # 모든 사례가 돌고 값이 맞는지만 (한 번씩 불러요)
.venv/bin/python -m bench.speed run --quick                        # 모든 영역의 빠른 묶음, 1라운드
.venv/bin/python -m bench.speed run stats --label stats            # 영역 하나, 3라운드
.venv/bin/python -m bench.speed run --resume build/speed/<실행>.jsonl
.venv/bin/python -m bench.speed run --rerun-busy build/speed/<실행>.jsonl
.venv/bin/python -m bench.speed compare build/speed/<실행>.jsonl   # 기준선보다 느려진 것
.venv/bin/python -m bench.speed promote build/speed/<실행>.jsonl   # 기준선에 넣고 speed.md 다시 만들기
.venv/bin/python -m bench.speed table special                      # 표만 다시 만들기
.venv/bin/python -m bench.speed cost                               # C++ 비용표 다시 만들기
```

전체를 다시 잴 때는 먼저 `--smoke`로 모든 사례가 돌고 값이 맞는지 본 다음, 영역마다 재서 `compare`와 `promote`를 하고, stats나 special을 다시 쟀으면 `cost`로 비용표를 다시 만들어요. 비용표가 바뀌면 다음 `import stardust`에서 C++가 다시 빌드되므로 테스트도 다시 돌려요. 영역마다 따로 재서 넣어도 돼요.
