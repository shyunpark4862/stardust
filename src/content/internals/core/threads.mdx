## 한눈에 보기

stardust에는 스레드풀이 하나 있어요. `csrc/parallel/pool.hpp`와 `pool.cpp`, 합쳐서 약 400줄이에요. 배열(`sd`), 선형대수(`sd.linalg`), 데이터프레임(`sd.frame`), 특수함수(`sd.special`), 통계(`sd.stats`), 난수(`sd.random`), 회귀(`sd.regression`), 최적화(`sd.optimize`), 가설검정(`sd.htest`), 희소 행렬(`sd.sparse`), 적분(`sd.integrate`), 미분(`sd.differentiate`)이 모두 이 풀 위에서 돌아요. 특수함수와 통계의 원소별 함수는 배열의 이터레이터로, 난수와 통계의 표본·기술통계·다변량 커널은 배열의 조각 실행기(`for_pieces`)나 `parallel_for`로, 회귀는 linalg의 배치 드라이버(`run_batch`)와 회귀 하나 안의 행 합으로, 최적화는 배치 스칼라의 원소 패스와 lmder의 열 피벗 QR을, 가설검정은 배치의 줄을 배열의 조각 실행기로, 희소 행렬은 압축 배열의 줄 구간을 `parallel_for`로, 적분은 표본 규칙의 줄과 Gauss–Legendre 마디, 원소별 반복(`tanhsinh`, `nsum`)의 원소 패스를, 미분은 원소별 반복의 원소 패스를 풀에 보내요.

이 페이지의 내용은 세 층으로 나뉘어요.

| 층 | 하는 일 | 어디에 |
|---|---|---|
| 풀 | 태스크 번호 `0 … ntasks-1`을 여러 스레드에 나눠 돌리기만 해요 | `parallel/pool.*` |
| 영역의 정책 | **언제** 나눌지(기준값), **얼마나 잘게** 나눌지(태스크 크기)를 정해요 | `array/parallel_limits.hpp`, `array/iter.cpp`, `frame/parallel.hpp`, `linalg/cost.hpp`, `special/cost.hpp`, `stats/engine.hpp`, `regression/*.cpp`, `elementwise/loop.hpp`, `optimize/lsq.cpp`, `htest/lanes.hpp`, `sparse/parallel.hpp`, `integrate/samples.cpp`, `integrate/gauss.cpp` |
| 알고리즘 | **어디서** 자르고 부분 결과를 **어떤 순서로** 합칠지 정해요 | 각 연산의 코드 |

핵심 아이디어는 네 가지예요.

1. **상주 워커와 atomic 카운터 하나.** 워커 스레드는 처음 한 번 만들어 두고 계속 살려 둬요. 일이 오면 워커와 호출한 스레드 자신이 공유 카운터에서 "다음 태스크 번호"를 하나씩 집어 가요. 빠른 스레드가 더 많이 집어 갈 뿐, 누가 어떤 태스크를 할지는 미리 정하지 않아요.
2. **spin 후 잠들기, mutex 없는 시작.** 일이 끝난 워커는 바로 잠들지 않고 최대 100µs 동안 다음 일을 기다리며 돌아요(spin). 그동안 새 일이 오면 잠금(mutex) 없이 바로 시작해요. 그래서 연달아 오는 병렬 호출의 고정 비용이 약 1.5µs예요. 잠든 워커를 깨워야 하면 약 25µs가 들어서, 태스크가 16개 이하인 짧은 일에는 잠든 워커를 깨우지 않아요(spin 중인 워커는 그래도 들어와요).
3. **나눌지는 영역이 정해요.** 배열은 일이 float64 원소 2¹⁵개(256KB) 분량 이상이어야 나누고, 태스크 하나는 2¹²개(32KB) 분량이에요. 두 값 모두 이 기계에서 잰 값이에요.
4. **결과는 스레드 수와 무관하게 비트까지 같아요.** 자르는 위치는 데이터의 크기와 레이아웃만으로 정하고, 부분 결과는 늘 같은 순서로 합쳐요. 스레드 수가 1이든 10이든 14이든 같은 덧셈을 같은 순서로 해요.

`parallel_for` 한 번이 어떻게 흘러가는지 요약하면 이래요.

1. 호출하는 쪽(예: 원소별 연산의 이터레이터)이 일의 양을 보고 나눌 가치가 있는지 정해요. 가치가 없으면 `parallel_for`를 부르지 않고 GIL을 쥔 채 그 자리에서 돌아요.
2. `parallel_for(ntasks, fn)`은 태스크가 하나이거나 태스크 안에서 다시 불린 경우면 GIL을 그대로 두고 그 자리에서 평범한 루프로 돌아요. 그 밖이면 GIL을 놓아요. 스레드 수가 1이면 GIL을 놓은 채 호출 스레드가 태스크를 차례로 돌고 끝나요.
3. 풀이 비어 있으면 일의 내용(`fn`, `ntasks`)을 기록하고 세대 번호를 하나 올려요. spin 중이던 워커는 이것을 보고 곧바로 일에 들어오고, 잠든 워커는 태스크가 16개를 넘는 일일 때만 condition variable로 깨워요.
4. 호출 스레드도 같은 카운터에서 태스크를 집어 처리해요.
5. 태스크를 다 집으면 일을 닫고, 그 일에 들어온 워커가 모두 나가기를 기다려요. 그다음 GIL을 다시 잡고 돌아와요. 태스크에서 난 예외가 있으면 여기서 다시 던져요.

## 풀의 구조

### 상태 변수

풀은 `Pool` 클래스 하나이고, 프로그램 전체에 객체가 하나만 있어요. 멤버를 보면 구조가 거의 다 보여요.

| 멤버 | 타입 | 역할 |
|---|---|---|
| `workers_` | `std::vector<std::thread>` | 상주 워커. 스레드 수가 n이면 n − 1개예요(호출 스레드가 하나를 맡아요) |
| `job_` | `const std::function<void(int64_t)>*` | 지금 일의 태스크 함수. 호출자 스택에 있는 객체를 가리켜요 |
| `ntasks_` | `int64_t` | 지금 일의 태스크 수 |
| `next_` | `std::atomic<int64_t>` | 다음에 집어 갈 태스크 번호 |
| `state_` | `std::atomic<uint64_t>` | 일의 상태를 한 단어에 담아요. 위 32비트는 세대 번호(새 일마다 1씩 올라가요), 31번 비트는 "닫힘"(태스크를 다 집어 호출 스레드가 기다리는 중), 아래 31비트는 이 일에 들어와 아직 나가지 않은 워커 수예요 |
| `busy_` | `std::atomic<bool>` | 지금 어떤 호출이 풀을 쓰고 있는지 |
| `nthreads_` | `std::atomic<int>` | 스레드 수(워커 수 + 1)의 복사본 |
| `m_`, `cv_work_`, `cv_done_` | mutex 하나, condition variable 둘 | 잠들 때와 깨울 때만 써요 |
| `stop_`, `stop_flag_` | `bool`, `std::atomic<bool>` | 워커 종료 신호(mutex 아래에서 읽는 것과 spin 중에 읽는 것) |
| `error_` | `std::exception_ptr` | 태스크에서 처음 난 예외 |

`job_`과 `ntasks_`는 atomic이 아니에요. 그래도 안전한 이유는 아래 "동기화 도구" 절에서 설명해요.

### 작업 하나의 흐름: `run()`

호출 스레드 쪽 코드예요. 주석만 한국어로 줄여 바꾼 발췌예요.

```cpp
// csrc/parallel/pool.cpp (Pool::run)
void run(std::int64_t ntasks, const std::function<void(std::int64_t)>& fn) {
    if (busy_.exchange(true)) {  // 다른 Python 스레드의 일이 풀을 쓰는 중: 기다리지 않고 혼자 처리
        serial(ntasks, fn);
        return;
    }
    if (workers_.empty()) {  // 1스레드
        busy_ = false;
        serial(ntasks, fn);
        return;
    }
    {
        std::lock_guard lock(m_);
        job_ = &fn;
        ntasks_ = ntasks;
        next_ = 0;
        error_ = nullptr;
        // 새 세대, 열림, 아직 아무도 들어오지 않음 (release: 위의 내용이 이것을 본 워커에게 보여요)
        state_.store((generation(state_.load()) + 1) << kGenShift, std::memory_order_release);
    }
    if (ntasks > kWakeTasks) cv_work_.notify_all();  // 잠든 워커는 긴 일에만 깨워요
    work();  // 호출 스레드도 태스크를 집어요
    // 태스크를 다 집었어요: 일을 닫고, 이 일에 들어온 워커만 기다려요
    state_.fetch_or(kClosed, std::memory_order_acq_rel);
    auto done = [&] { return (state_.load(std::memory_order_acquire) & kCount) == 0; };
    spin_until(done);
    if (!done()) {
        std::unique_lock lock(m_);
        cv_done_.wait(lock, done);
    }
    job_ = nullptr;
    std::exception_ptr error = error_;
    busy_ = false;
    if (error) std::rethrow_exception(error);
}
```

태스크를 집는 `work()`는 호출 스레드와 워커가 똑같이 써요.

```cpp
// csrc/parallel/pool.cpp (Pool::work)
void work() {
    t_in_task = true;  // 이 스레드는 지금 태스크 안이에요 (중첩 금지용)
    for (std::int64_t t; (t = next_.fetch_add(1)) < ntasks_;) {
        try {
            (*job_)(t);
        } catch (...) {
            std::lock_guard lock(m_);
            if (!error_) error_ = std::current_exception();  // 첫 예외만 남겨요
        }
    }
    t_in_task = false;
}
```

`next_.fetch_add(1)`은 카운터를 1 올리고 올리기 전 값을 돌려주는 원자적 연산이에요. 여러 스레드가 동시에 불러도 같은 번호를 두 번 돌려주는 일이 없어요. 돌려받은 번호가 `ntasks_` 이상이면 남은 태스크가 없다는 뜻이고, 그 스레드는 루프를 빠져나와요. 카운터는 `ntasks_`를 넘어 계속 올라가도 상관없어요. 다음 일이 시작될 때 0으로 되돌려요.

### 워커의 일생: `worker_main()`

워커는 만들어질 때 시작해서 풀의 스레드 수가 바뀌거나 프로세스가 끝날 때까지 이 루프를 돌아요. 주석만 한국어로 바꾼 발췌예요.

```cpp
// csrc/parallel/pool.cpp (Pool::worker_main)
void worker_main(std::uint64_t seen) {  // seen: 만들어질 때의 세대 번호
    pthread_set_qos_class_self_np(QOS_CLASS_USER_INTERACTIVE, 0);  // P코어에 머물게
    for (;;) {
        // 1) 최대 100µs 동안 새 세대가 오는지 지켜봐요 (mutex 없음)
        auto fresh = [&] { return generation(state_.load(std::memory_order_acquire)) != seen; };
        spin_until([&] { return fresh() || stop_flag_; });
        if (!fresh() && !stop_flag_) {
            // 2) 안 왔으면 잠들어요. mutex는 여기서만 잡아요
            std::unique_lock lock(m_);
            cv_work_.wait(lock, [&] { return stop_ || fresh(); });
        }
        if (stop_flag_) return;
        // 3) 본 일에 들어가요. 일이 아직 열려 있을 때만, 세대·닫힘·인원을 compare-and-swap 한 번으로
        std::uint64_t s = state_.load(std::memory_order_acquire);
        seen = generation(s);
        bool joined = false;
        while (!joined && !(s & kClosed) && generation(s) == seen)
            joined = state_.compare_exchange_weak(s, s + 1, std::memory_order_acq_rel);
        if (!joined) continue;  // 늦었어요: 호출 스레드가 이미 혼자 끝냈어요
        work();
        // 4) 나가요. 일이 닫혔고 마지막으로 나가는 워커면 호출 스레드를 깨워요
        const std::uint64_t left = state_.fetch_sub(1, std::memory_order_acq_rel) - 1;
        if ((left & kClosed) && (left & kCount) == 0) {
            std::lock_guard lock(m_);
            cv_done_.notify_one();
        }
    }
}
```

워커는 "지난번에 본 세대 번호" `seen`만 기억해요. 세대 번호가 바뀌었다는 것이 곧 "새 일이 왔다"는 신호예요. 별도의 작업 큐가 없어요. 동시에 진행되는 일은 언제나 많아야 하나이기 때문이에요(다음 절의 `busy_` 규칙).

spin은 이렇게 생겼어요.

```cpp
constexpr auto kSpin = std::chrono::microseconds(100);

template <typename Done>
void spin_until(Done done) {
    const auto until = std::chrono::steady_clock::now() + kSpin;
    for (int i = 0; !done(); ++i) {
        __builtin_arm_yield();                               // ARM YIELD 힌트
        if ((i & 63) == 63 && std::chrono::steady_clock::now() > until) return;
    }
}
```

- **시계로 재요, 반복 횟수로 재지 않아요.** ARM의 `YIELD` 명령은 "다른 하드웨어 스레드에 양보해도 된다"는 힌트일 뿐이라 1~2사이클이면 끝나요. "10만 번 돌기"처럼 횟수로 정하면 겉보기에 큰 숫자도 몇 µs면 끝나 버려서, 의도한 시간만큼 기다리지 못해요.
- 시계를 읽는 것은 `YIELD`보다 훨씬 비싸서 64번에 한 번만 읽어요.

### 태스크 나눠 주기: 동적 분할과 카운터 하나

일을 스레드에 나누는 방법은 크게 둘이에요.

- **정적 분할:** 스레드가 p개면 일을 p조각으로 나눠 하나씩 맡겨요. 간단하지만 가장 늦게 끝나는 스레드를 모두가 기다려요.
- **동적 분할:** 일을 스레드 수보다 훨씬 많은 작은 태스크로 나누고, 끝난 스레드가 다음 태스크를 가져가요.

stardust는 동적 분할을 써요. 이 기계(Apple M4 Pro)는 성능 코어(P코어) 10개와 효율 코어(E코어) 4개가 섞여 있고, 같은 일이라도 코어마다 속도가 달라요. 다른 프로세스가 코어 하나를 잠깐 빼앗아 가기도 해요. 또 `sd.special`의 연분수나 Halley 반복처럼 원소마다 반복 횟수가 다른 함수는 같은 크기의 태스크라도 걸리는 시간이 달라요. 동적 분할에서는 느린 스레드가 태스크를 적게 가져갈 뿐이라서 이런 불균형이 저절로 흡수돼요.

태스크 하나는 float64 원소 4096개 분량이에요(아래 "기준값과 태스크 크기"). 원소 100만 개면 태스크가 245개라서 10스레드에 평균 24~25개씩 돌아가고, 마지막에 남는 불균형은 태스크 하나(수 µs) 정도예요.

<Callout title="work stealing을 쓰지 않는 이유">
TBB나 Rayon 같은 범용 풀은 스레드마다 큐를 두고 남의 큐에서 일을 훔쳐 오는 work stealing을 써요. 태스크가 또 태스크를 낳는 재귀적인 병렬성을 다루려면 work stealing이 필요해요. stardust의 풀은 중첩을 금지하고(아래 "중첩"), 한 번에 일 하나만 돌려요. 태스크 목록이 평평한 번호 `0 … ntasks-1`뿐이라 공유 카운터 하나로 충분해요.
</Callout>

### 동기화 도구와 그 이유

| 도구 | 쓰는 곳 | 고른 이유 |
|---|---|---|
| `state_`의 release 쓰기 / acquire 읽기 | 일의 발행과 수신 | mutex 없이 일의 내용(`job_`, `ntasks_`, `next_ = 0` …)을 워커에게 보이게 해요 |
| `state_`의 compare-and-swap | 일에 들어가기 | 세대, 닫힘, 인원을 한 번에 봐요. 이미 닫힌 일이나 다음 일에 자기를 세어 넣는 일이 없어요 |
| `next_.fetch_add` | 태스크 번호 나눠 주기 | 원자적 증가 하나로 중복 없는 번호를 줘요. 잠금이 필요 없어요 |
| `state_.fetch_sub` (acq_rel) | 일에서 나가기 | 워커가 태스크에서 쓴 결과가, 인원 0을 본 호출 스레드에게 보이게 해요 |
| `busy_.exchange(true)` | 풀 차지하기 | 읽고 쓰기를 한 번에 해서, 두 호출이 동시에 "비었다"고 판단하는 일이 없어요 |
| mutex + condition variable | 잠들기와 깨우기만 | OS의 대기 기능을 쓰려면 필요해요. 빠른 경로에서는 잡지 않아요 |
| `nthreads_` (atomic 복사본) | `get_num_threads()` | 다른 스레드가 `workers_`를 다시 만드는 중에도 안전하게 읽어요 |
| `thread_local bool t_in_task` | 중첩 판정 | 스레드마다 따로 있는 값이라 동기화가 필요 없어요 |

**release/acquire가 하는 일.** C++의 메모리 모델에서, 스레드 A가 atomic 변수에 release로 쓰고 스레드 B가 그 값을 acquire로 읽으면, A가 그 쓰기 전에 한 모든 메모리 쓰기가 B에게 그 읽기 뒤에 보이도록 보장돼요 [1]. 풀은 이 보장을 이렇게 써요.

1. 호출 스레드가 `job_ = &fn; ntasks_ = …; next_ = 0; error_ = nullptr`를 평범하게 써요.
2. 그다음 새 세대 번호를 `state_`에 release로 써요.
3. spin 중인 워커가 `state_.load(acquire)`로 바뀐 세대를 보면, 1에서 쓴 값이 모두 보여요.

그래서 `job_`과 `ntasks_`는 atomic이 아니어도 돼요. 코드에서 1~2를 `lock_guard` 안에서 하는 것은 잠든 워커 때문이에요. 잠든 워커는 mutex를 잡은 채 조건을 검사하므로, 발행도 mutex 아래에서 해야 "검사하고 잠드는 사이에 신호를 놓치는" 일이 없어요. spin 중인 워커는 mutex를 잡지 않으므로 이 잠금과 다투지 않아요(mutex를 잡은 쪽은 호출 스레드 하나뿐이에요).

**mutex 없는 시작이 필요한 이유.** 워커가 일을 기다릴 때 condition variable로만 잠들면 고정 비용이 커요. 세 방식을 재면 이래요(원인은 `sample` 프로파일러로 본 것이에요).

| 방식 | 병렬 호출 한 번의 고정 비용 |
|---|---:|
| 잠든 워커를 깨우기만 | 약 25µs |
| spin하지만 새 일을 볼 때 mutex를 잡음 | 약 18µs |
| spin 중에는 mutex 없이 시작 | **약 1.5µs** |

- macOS에서 잠든 스레드를 깨우는 비용은 작업당 수십 µs예요. 원소 100만 개 덧셈 전체보다도 크고, 원소 수만 개짜리 연산에서는 계산보다 훨씬 커요.
- spin을 넣어도 18µs가 남는 원인은 깨우기가 아니라 mutex 경합이에요. 새 일이 나타나는 순간 워커 9개가 한꺼번에 같은 mutex를 잡으려 해서, 프로파일에 `__psynch_mutexwait`(macOS의 mutex 대기)가 크게 보여요.
- 대가도 있어요. 일이 끝난 뒤 워커가 최대 100µs 동안 CPU를 써요. 워커 9개면 일 하나마다 최대 0.9ms의 CPU 시간이에요. 원소별 연산은 연달아 오는 경우가 많아서(`a * b + c`는 연산 둘) 이 절충이 이득이에요. OpenMP 런타임도 같은 종류의 절충을 해요. OpenMP 표준은 기다리는 스레드가 돌지 잠들지를 `OMP_WAIT_POLICY`로 고르게 하고 [2], LLVM의 OpenMP 런타임은 `KMP_BLOCKTIME`(기본 200ms) 동안 돌다가 잠들어요 [3]. stardust의 100µs는 그보다 훨씬 짧아요.

### 완료 기다리기

호출 스레드는 자기 몫의 태스크를 다 집은 뒤(카운터가 바닥나면) `state_`에 닫힘 비트를 세우고, 그 일에 들어온 워커 수가 0이 되기를 기다려요. 워커는 대개 몇 µs 안에 끝나므로 먼저 spin하고, 100µs가 지나도 안 끝나면 `cv_done_`에서 잠들어요. 일이 닫힌 뒤 마지막으로 나간 워커가 `cv_done_`을 깨워요.

기다리는 것은 모든 워커가 아니라 **그 일에 들어온 워커**뿐이에요. 이유는 `job_`이 가리키는 `fn`의 수명이에요. `fn`은 호출자의 스택에 있는 객체라서 `run()`이 돌아오면 사라져요. 일에 들어온 워커는 아직 `fn`을 부르는 중일 수 있으니 나갈 때까지 기다려야 해요. 들어오지 않은 워커는 `fn`을 만지지 않아요. 늦게 깨어난 워커는 일이 이미 닫힌 것을 보고 들어가지 않으므로, 사라진 `fn`이나 다음 일의 `ntasks_`를 읽을 일이 없어요. 들어가기(인원 +1)와 닫힘 확인을 compare-and-swap 한 번으로 하는 것이 이 보장의 중심이에요. 둘을 따로 하면 "열린 것을 보고, 닫힌 뒤에 인원을 올리는" 틈이 생겨요.

그래서 늦게 깨는 워커가 호출을 붙잡지 않아요. 잠든 워커를 깨우는 신호는 도착하는 데 약 25µs, 보내는 호출 스레드 쪽에서도 약 5µs가 들어요. 태스크 하나는 0.5–1.5µs라서, 태스크가 몇 개 안 되는 일은 깨운 워커가 시작하기 전에 호출 스레드 혼자 끝내요. 그래서 태스크가 16개(`kWakeTasks`) 이하인 일은 잠든 워커를 깨우지 않아요. spin 중인 워커는 신호 없이도 새 세대를 보고 들어와요. 2ms 쉰 뒤의 원소 4만 개 `x + x`는 깨우면 16µs, 깨우지 않으면 11µs였어요(1스레드 12µs). 어느 스레드가 어느 태스크를 하든 결과는 같아요. 반대로 태스크는 몇 개뿐인데 하나하나가 무거운 일(`tukey_hsd`의 p값 하나가 수 ms)은 이 규칙 때문에 호출 스레드와 마침 spin 중이던 워커만 돌게 돼요. 그래서 가설검정의 줄 병렬은 조각마다 2¹⁵개 분량 이상인 조각이 2–16개이면 빈 태스크를 덧붙여 17개로 부르고, 잠든 워커도 깨워요(`htest/lanes.hpp`의 `for_pieces_woken`). 조각의 경계는 그대로라서 결과도 같아요.

### 예외

태스크에서 C++ 예외가 나면 `work()`가 잡아서 `error_`에 첫 번째 것만 저장하고, 남은 태스크는 계속 돌려요. 일이 끝나면 호출 스레드가 `std::rethrow_exception`으로 다시 던지고, 그 위의 바인딩 층이 Python 예외로 바꿔요. 다른 스레드에서 난 예외를 그 스레드에서 그대로 던지면 프로세스가 끝나 버리므로(`std::terminate`) 반드시 호출 스레드로 옮겨야 해요.

"첫 번째"는 시간상 처음이라서 스레드 수에 따라 달라질 수 있어요. 그래서 실제로 값을 검사하는 커널은 예외 대신 `FirstRow`를 써서 "가장 앞의 실패 위치"를 고르게 해요(아래 "에러 위치도 결정적"). 풀의 예외 경로는 메모리 부족처럼 위치가 의미 없는 실패용이에요.

### 중첩: `t_in_task`

태스크 안에서 다시 `parallel_for`를 부르는 일도 생겨요. 예를 들어 블록 리덕션은 블록마다 태스크를 만들고, 각 블록은 이터레이터로 접는데, 이터레이터는 일이 크면 또 나누려고 해요. 중첩을 그대로 허용하면 스레드 10개가 각자 10개짜리 일을 만들어 100개가 다투거나, 한 번에 일 하나만 도는 풀 구조가 깨져요.

그래서 `work()`와 `serial()`은 스레드 지역 변수 `t_in_task`를 켜 두고, `available()`이 이것을 봐요.

```cpp
bool available() { return !t_in_task && pool().threads() > 1 && !pool().busy(); }

void parallel_for(int64_t ntasks, const std::function<void(int64_t)>& fn) {
    if (ntasks <= 0) return;
    if (ntasks == 1 || t_in_task) {                // 태스크 하나, 중첩
        for (int64_t t = 0; t < ntasks; ++t) fn(t);  // GIL은 그대로 두고 그 자리에서
        return;
    }
    GilRelease release;
    if (pool().threads() <= 1) {                   // 1스레드: GIL 없이 차례로
        for (int64_t t = 0; t < ntasks; ++t) fn(t);
        return;
    }
    pool().run(ntasks, fn);  // 풀로 나눠요 (다른 스레드의 일로 바쁘면 run()이 직렬로 돌려요)
}
```

`parallel_for`는 `t_in_task`를 직접 봐서, 태스크 안에서 불리면 그 스레드에서 차례로 도는 평범한 루프가 돼요. 결과는 바뀌지 않아요. 자르는 위치는 스레드 수와 무관하게 정해지므로(아래 "결정성"), 나눠서 차례로 돌아도 나눠서 병렬로 돈 것과 같은 계산이에요.

### 다른 Python 스레드가 풀을 쓰고 있을 때

풀로 나눠 도는 `parallel_for`는 GIL을 놓으므로, 한 Python 스레드가 큰 연산을 병렬로 돌리는 동안 다른 Python 스레드가 GIL을 잡고 또 stardust 함수를 부를 수 있어요. 이때 두 번째 호출은 기다리지도, 풀을 같이 쓰지도 않고 자기 스레드에서 혼자 돌아요.

| 시점 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | `sd.exp(x)` → `parallel_for` → GIL 해제, `busy_ = true` | (대기) |
| 2 | 워커 9개와 함께 태스크 처리 | GIL 획득, `sd.sum(y)` 호출 |
| 3 | | `available()`이 false(`busy_`) → 직렬 경로를 골라 혼자 계산 |
| 4 | 끝, `busy_ = false`, GIL을 다시 잡으려 함 | 계산 끝, GIL 해제 |

- **기다리지 않는 이유:** A의 일이 끝날 때까지 B를 세워 두면, B가 고른 일이 작아도 A의 큰 일만큼 기다려요.
- **같이 쓰지 않는 이유:** 두 일이 각자 10스레드를 쓰면 코어 10개에 스레드 20개가 붙어 서로 밀어내요(과다 구독). 풀 구조도 동시에 일 하나만 다루도록 되어 있어요.
- **경로 선택에도 반영해요.** `available()`은 풀이 바쁘면 false예요. pairwise 합이나 긴 정렬처럼 "병렬용 경로"와 "직렬용 경로"가 따로 있는 알고리즘은 이 값을 보고 직렬용 경로를 골라요. 병렬용 경로를 고른 뒤 그것을 혼자 차례로 돌리는 것보다 빠르고, 결과는 같아요(이런 경로 전환은 결과가 같다고 보장된 경우에만 해요, 아래 "결정성").
- 이 표의 3에서 B의 직렬 계산은 일이 기준값 이상이면 GIL을 놓고 돌아요(아래 "GIL"의 `Unlocked`). 그동안 A는 일을 끝내자마자 GIL을 다시 잡고 결과를 돌려줄 수 있어요. B의 일이 기준값보다 작으면 GIL을 쥔 채 돌지만, 그만큼 짧아서 A가 오래 기다리지 않아요.
- 아주 드문 경쟁도 있어요. `available()`이 true를 본 직후 다른 스레드가 먼저 `busy_`를 차지하면, `run()`의 첫 줄 `busy_.exchange(true)`가 이것을 잡아내서 그 호출을 `serial()`로 돌려요. 이 경우에는 GIL이 이미 풀린 상태로 혼자 돌아요.

`tests/array/test_threads.py`는 Python 스레드 6개가 동시에 40만 원소 배열을 20번씩 계산하면서 모든 결과가 맞는지 확인해요.

### 스레드 수 바꾸기

`sd.set_num_threads(n)`은 워커를 모두 멈추고 새로 만들어요(`Pool::resize`).

```cpp
void resize(int n) {
    while (busy_.exchange(true)) std::this_thread::yield();  // 돌던 일이 끝나기를 기다린다
    stop();          // stop_flag_ 세우고, 깨우고, join
    start(n);        // 워커 n-1개를 "현재 세대 번호"로 만든다
    busy_ = false;
}
```

여기에는 함정이 두 개 있어요.

- **새 워커의 세대 번호.** 새 워커가 `seen = 0`에서 시작하면, 세대 번호는 이미 수백, 수천까지 올라가 있으므로 "0 ≠ 지금 세대"를 보고 이미 끝난 일을 새 일로 착각해요. 그래서 `start()`가 현재 세대 번호를 읽어 새 워커에 넘겨요. "계산 중에 스레드 수 바꾸기" 스트레스 테스트가 이 경우를 지켜요.
- **스레드 수 읽기.** `get_num_threads()`가 `workers_.size() + 1`을 바로 읽으면, 다른 스레드가 `resize()`로 vector를 다시 만드는 중일 때 데이터 경쟁이에요. `run()`이 `busy_`를 잡기 전에 `workers_.empty()`를 보는 것도 같은 경쟁이에요. 그래서 스레드 수를 atomic 복사본 `nthreads_`에 두고, `run()`은 `busy_`를 차지한 뒤에만 `workers_`를 봐요. `resize()`도 `busy_`를 쥐고 `workers_`를 바꾸므로 둘이 겹치지 않아요.

인자는 1부터 1024까지의 int예요. 범위 밖이면 ValueError, int가 아니면 TypeError이고, 위치 인자로만 받아요([`set_num_threads`](/api/array/threads/)).

### 풀의 수명

```cpp
// csrc/parallel/pool.cpp (줄인 발췌)
std::atomic<Pool*> g_pool{nullptr};
std::atomic<int> g_threads{0};  // 나중에 만드는 풀의 스레드 수 (0: 기본값)

void after_fork_in_child() {
    if (Pool* old = g_pool.load(std::memory_order_relaxed)) {
        g_threads.store(old->threads(), std::memory_order_relaxed);
        g_pool.store(nullptr, std::memory_order_relaxed);  // leaked on purpose
    }
    t_in_task = false;
}

Pool& pool() {
    Pool* p = g_pool.load(std::memory_order_acquire);
    if (p) [[likely]]
        return *p;
    static const bool registered = [] { return pthread_atfork(nullptr, nullptr, &after_fork_in_child) == 0; }();
    (void)registered;
    const int n = g_threads.load(std::memory_order_relaxed);
    Pool* made = new Pool(n > 0 ? n : performance_cores());
    if (g_pool.compare_exchange_strong(p, made, std::memory_order_acq_rel)) return *made;
    delete made;  // another thread made one first
    return *p;
}
```

- **처음 쓸 때 만들어요.** `import stardust` 자체는 풀을 만들지 않고, 처음으로 풀에 무언가를 묻는 순간 만들어져요. 작은 원소별 연산도 이터레이터가 `available()`을 부르므로, 실제로는 첫 연산에서 워커가 생겨요. 여러 스레드가 동시에 처음 부르면 각자 만들어 보고 compare-and-swap에서 이긴 하나만 남아요.
- **없애지 않아요.** `new`로 만들고 `delete`하지 않아요. 정적 객체로 두면 인터프리터가 끝날 때 소멸자가 돌면서 워커를 `join`하는데, 인터프리터 종료 중에 스레드를 기다리는 것은 순서 문제로 불안정해요. 프로세스가 끝나면 OS가 스레드와 메모리를 회수해요.
- **`fork()` 뒤의 자식은 새 풀을 만들어요.** `fork()`한 자식 프로세스에는 fork를 부른 스레드 하나만 있어요. 워커는 없는데 옛 풀이 그대로 있으면 첫 병렬 호출이 오지 않을 워커를 영원히 기다려요. 그래서 `pthread_atfork`로 등록한 함수가 자식에서 옛 풀을 건드리지 않고 잊어요(`join`도 소멸자도 부르지 않아요. 그 스레드와 mutex 상태는 부모의 것이에요). 스레드 수만 기억해 두었다가 첫 사용 때 같은 스레드 수로 새 풀을 만들어요. OpenBLAS와 OpenMP 런타임도 같은 방법을 써요.

## GIL

CPython에는 GIL(Global Interpreter Lock)이 있어서, 한 순간에 한 스레드만 Python 객체를 만지는 코드를 실행할 수 있어요. 이 절의 규칙에는 목적이 두 가지 있어요. 계산 중에 다른 Python 스레드가 돌 수 있게 하는 것, 그리고 GIL 없이 도는 워커가 Python 객체를 건드려 인터프리터를 망가뜨리지 않게 하는 것이에요.

### 언제 놓나

`GilRelease`는 생성될 때 GIL을 놓고 소멸될 때 다시 잡는 RAII 객체예요.

```cpp
GilRelease::GilRelease() {
    // 태스크는 GIL을 쥐고 있지 않아요: 워커는 가진 적이 없고, 호출 스레드는 첫 태스크 전에 놓았어요
    if (!t_in_task && PyGILState_Check()) state_ = PyEval_SaveThread();
}
GilRelease::~GilRelease() { if (state_) PyEval_RestoreThread(static_cast<PyThreadState*>(state_)); }

class Unlocked {                       // parallel/pool.hpp
public:
    explicit Unlocked(bool release) { if (release) release_.emplace(); }
private:
    std::optional<GilRelease> release_;
};
```

`GilRelease`는 이 스레드가 GIL을 쥐고 있을 때만 놓아요. 태스크 안이나 이미 GIL을 놓은 구간에서는 아무것도 하지 않아요. 그래서 놓는 구간이 겹쳐도(태스크 안의 `parallel_for`, `Unlocked` 안의 `parallel_for`) 문제가 없어요. `Unlocked(bool)`은 인자가 참일 때만 `GilRelease`를 만드는 얇은 감싸개예요. 호출 스레드에서 도는 구간을 `Unlocked u(work >= 기준값);`처럼 감싸요.

규칙은 하나예요. **일이 영역의 기준값 이상이면 스레드 수와 상관없이 GIL을 놓고, 그보다 작으면 쥔 채 돌아요.** `sd.set_num_threads(1)`이어도 큰 계산이 도는 동안 다른 Python 스레드가 돌아요. 작은 호출은 GIL을 놓았다 다시 잡는 비용(스레드 상태 저장과 복원, 다시 잡을 때의 경쟁)을 내지 않아요. 기준값은 스레드풀로 나누기 시작하는 일의 양과 같아요.

| 영역 | 기준값 |
|---|---|
| 배열, special, stats의 분포 함수, random | float64 덧셈 2¹⁵ = 32,768개 분량(`kParallelThreshold`). 원소 하나가 무거운 함수는 그만큼 적은 원소부터, bool 배열은 바이트로 세어 262,144 원소부터 |
| linalg | 호출 하나의 추정 계산 시간이 10µs(`kParallelMinNs`) 이상. 행렬 하나여도 같아요 |
| frame | 2¹⁷ = 131,072행 |
| htest, sparse | 배열과 같은 2¹⁵개 분량. htest는 줄 수에 줄 하나의 비용을 곱해 세고, sparse는 저장된 원소와 출력 크기로 세요(`sparse/parallel.hpp`의 `kParallelThreshold`) |
| integrate, differentiate | 배열과 같은 2¹⁵개 분량. 표본 규칙은 줄 수 × 길이, Gauss–Legendre 마디는 점화식 걸음 수, 원소별 반복은 남은 원소 수 × 원소마다의 점 수로 세요(`elementwise/loop.hpp`의 `kParallel`) |

놓는 곳은 두 가지예요.

- **`parallel_for`**: 태스크가 둘 이상이면 놓아요. 풀로 나누든, 1스레드라 호출 스레드가 차례로 돌든, 풀이 바빠 `run()`이 직렬로 돌리든 같아요. 태스크가 하나이면 GIL을 그대로 두고 그 자리에서 불러요. 태스크 수는 일의 양만으로 정해지므로([결정성](#결정성)), GIL을 놓는지도 스레드 수와 무관해요. 중첩된 호출은 놓을 GIL이 애초에 없어요.
- **`Unlocked`**: 일이 기준값 이상인데 `parallel_for` 없이 호출 스레드에서 도는 구간이에요. 1스레드이거나 풀이 바빠 직렬 경로를 고른 경우, 자를 축이 없는 경우, 처음부터 나누는 경로가 없는 직렬 루프가 그래요. 배열의 이터레이터(`NdIter::run`), 조각 실행기(`for_pieces`), linalg의 배치 드라이버(`run_batch`)와 긴 합(`pairwise_sum_mt`, `vnorm`, 행렬 노름의 줄 합), frame의 `frame::Unlocked`(`parallel::Unlocked`를 frame의 기준값으로 감싼 것)가 이것을 써요.

**줄마다 불리는 커널 안에는 `Unlocked`를 두지 않아요.** 호출 한 번에 한 번 지나는 곳(이터레이터, `for_pieces`, 함수 본문)에만 둬요. 리덕션 루프 안에 두면 길이 4인 줄의 `sum(axis=1)`이 13–25% 느려져요. 소멸자 호출이 생기고 인라인이 달라지기 때문이에요.

기준값과 상관없이 GIL을 놓거나 쥐는 곳도 있어요.

- **언제나 놓아요**: `cov`, `corrcoef`의 행렬 곱(BLAS), stats의 여러 기술통계와 다변량 분포, 분포의 `sample`, random의 `permutation`과 비복원 추출(`fisher_yates`). `matmul`의 float64·complex128 BLAS 경로는 곱셈-덧셈이 $2^{15}$개(`kBlasTaskWork`) 이상이면 놓아요. BLAS 호출은 우리 풀이 아니라 Accelerate가 스레드를 정하므로 `sd.set_num_threads(1)`이어도 여러 코어를 쓸 수 있어요. 희소 행렬의 Accelerate LU 분해와 풀이도 언제나 GIL을 놓고 불러요(`sparse/direct.cpp`). 그래서 여러 Python 스레드가 동시에 분해할 수 있어요.
- **사용자 함수를 부르는 동안 쥐어요**: `sd.optimize`의 반복과 `sd.regression.nls`의 반복은 사용자의 Python 함수를 부르므로 GIL을 쥔 채 돌아요. 그 사이의 계산 가운데 linalg의 10µs 규칙(추정 2×10⁵ 플롭)을 넘는 것(BFGS의 H 갱신, L-BFGS-B의 방향 계산, Nelder–Mead의 무게중심, trust-exact의 Cholesky, 야코비안의 QR, `lsq_linear`과 `nnls`의 풀이)과 2¹⁵개 이상인 배치 스칼라의 원소 패스만 GIL을 놓아요. 희소 반복법과 고유값 풀이도 연산자가 Python 함수(`LinearOperator`)이면 풀이 내내 GIL을 쥐고, 희소 행렬이면 한 걸음의 일이 기준값 이상일 때 풀이 전체에서 놓아요. 가설검정의 재표본에서 사용자의 `statistic`은 Python 층이 부르므로 그동안 GIL을 쥐어요. 적분과 미분도 같아요. `quad` 계열, `quad_vec`, `cubature`는 사용자 함수를 부르는 반복이라 내내 쥐고, 원소별 반복(`derivative`, `tanhsinh`, `nsum`)과 `jacobian`·`hessian`은 사용자 함수를 부르는 동안 쥐고 그 사이의 원소 패스만 기준값 이상일 때 놓아요.
- **기준값 이상이어도 쥐어요**: Python 객체를 읽거나 만드는 변환(리스트를 받는 `asarray`, `tolist`), 인덱스 배열 하나로 하는 대입 `x[idx] = v`(같은 인덱스의 마지막 쓰기가 남아야 해서 한 스레드에서 순서대로 써요), `unique_all`·`unique_counts`·`unique_inverse`에서 정렬 뒤에 묶음을 세는 부분, 메모리를 받기만 하는 `zeros`와 `eye`.

비용은 기준값 이상인 호출마다 GIL을 한 번 놓았다 다시 잡는 것으로, 호출당 0.1µs 안팎이에요. 1스레드의 `sum`·`max`·`x + x`를 기준값 바로 위(32,768–65,536 원소, 2–7µs짜리 호출)에서 GIL을 쥐는 빌드와 번갈아 20번씩 잰 최솟값으로 비교하면 −1.4%~+3.2%였어요. 열세 연산, 여섯 크기(100~100만 원소), 1·10스레드의 156가지 경우를 12번씩 번갈아 쟀을 때 기하평균은 +0.5%(최솟값 기준)였어요. 다른 Python 스레드가 Python 코드를 돌리고 있으면, 계산을 마친 호출은 GIL을 돌려받을 때까지 기다려요(최대 `sys.getswitchinterval()`, 기본 5ms).

### 태스크 안에서 지키는 것

**태스크와 `Unlocked` 구간은 Python 객체를 만지지 않아요.** 둘 다 GIL 없이 돌기 때문이에요. 결과 배열을 만들고 Python 객체로 감싸는 일(`wrap`)은 구간 밖에서 하고, 구간 안의 실패는 C++ 예외로 던져 GIL을 다시 잡은 뒤에 Python 예외로 바꿔요. 생각보다 넓은 규칙이에요.

- `NDArray`를 복사하거나 없애는 것도 안 돼요. `NDArray`에는 Python의 `.base`를 가리키는 `nb::object`가 있어서, 복사하면 그 객체의 참조 횟수가 바뀌어요. 참조 횟수 변경은 GIL 아래에서만 안전해요. 그래서 블록 리덕션은 블록마다의 뷰(`NDArray`)를 태스크 밖에서 미리 만들어 vector에 담아 두고, 태스크는 그것을 읽기만 해요(`array/ops/reduction.cpp`의 `reduce_blocked`).
- 에러 메시지에 값의 `repr`이 들어가면 그것도 Python 호출이에요. 그래서 검사하는 태스크는 실패 위치만 기록하고, 메시지는 병렬 구간이 끝나 GIL을 다시 잡은 뒤에 만들어요.
- 외부 메모리를 빌려 쓰는 `Buffer`(버퍼 프로토콜로 가져온 메모리)는 마지막 소유자가 워커 스레드에서 사라질 수 있어요. 그래서 그 소멸자는 `PyGILState_Ensure`로 GIL을 직접 잡고 `PyBuffer_Release`를 불러요.

### numpy의 방식

numpy도 원소별 루프 같은 긴 C 루프를 도는 동안 GIL을 놓아요(`numpy/_core/include/numpy/ndarraytypes.h`의 `NPY_BEGIN_THREADS` 매크로 계열). 다만 numpy 자신은 그 루프를 한 스레드에서만 돌려요. 여러 코어를 쓰려면 사용자가 Python 스레드를 여러 개 띄워 배열을 나눠 맡겨야 해요. stardust는 한 호출 안에서 나눠 돌리고, 그동안 GIL도 놓아요.

## 스레드 수

### 기본값: P코어 수

```cpp
int performance_cores() {
    int n = 0;  size_t len = sizeof n;
    if (sysctlbyname("hw.perflevel0.physicalcpu", &n, &len, nullptr, 0) != 0 || n < 1)
        n = static_cast<int>(std::thread::hardware_concurrency());
    return n > 0 ? n : 1;
}
```

macOS는 코어를 성능 등급별로 알려 줘요. `hw.perflevel0`이 가장 빠른 등급(P코어), `hw.perflevel1`이 그다음(E코어)이에요. 이 기계에서 `hw.perflevel0.physicalcpu`는 10이에요. 이 값을 읽지 못하면 논리 코어 수 전체(`hardware_concurrency`, 이 기계에서 14)를 써요. 테스트(`test_default_is_the_performance_cores`)는 새 프로세스에서 `sd.get_num_threads()`가 `sysctl -n hw.perflevel0.physicalcpu`와 같은지 확인해요.

**10을 고른 이유.** E코어까지 써서 14스레드로 돌리면 연산의 성격에 따라 결과가 갈려요.

- 계산에 묶인 연산은 5~27% 빨라져요. 예: `sin`이 1스레드 대비 9.4배에서 10.9배로.
- 메모리에 묶인 연산은 3~12% 느려져요. 대역폭이 이미 다 찼는데 스레드만 늘어나 서로 방해해요.

동적 분할이라 E코어가 섞여도 "가장 느린 코어를 모두가 기다리는" 문제는 없어요. E코어는 태스크를 적게 가져갈 뿐이에요. 그래서 기준은 위의 두 성격뿐이고, 흔한 메모리 연산이 느려지지 않는 10이 기본이에요. 계산이 무거운 일에는 `sd.set_num_threads(14)`를 쓰면 돼요.

### P코어에 머물기

워커는 시작할 때 `pthread_set_qos_class_self_np(QOS_CLASS_USER_INTERACTIVE, 0)`을 불러요. macOS는 스레드마다 QoS(Quality of Service) 등급을 두고 이것을 보고 스케줄해요. 가장 높은 `USER_INTERACTIVE`면 P코어가 비어 있는 한 P코어에 놓여요 [4]. 호출 스레드(Python 스레드)의 등급은 건드리지 않아요.

### 다른 영역과 함께

스레드 수 API는 `sd.set_num_threads`, `sd.get_num_threads` 하나뿐이에요. `sd.frame`이나 `sd.linalg`에는 따로 없어요. 풀이 하나이니 한 번 바꾸면 모든 영역에 적용돼요. linalg도 Python을 거치지 않고 C++에서 `parallel::num_threads()`를 직접 읽어요.

### Accelerate는 따르지 않아요

`sd.set_num_threads`가 정하는 것은 우리 풀의 스레드 수예요. 큰 BLAS·LAPACK 호출(`matmul`, `cov`, linalg의 분해)은 Accelerate가 안에서 스레드를 정하고, 이 설정을 따르지 않아요. 그래서 `cov` 1000×1000은 1스레드 설정에서 1.89ms, 10스레드 설정에서 1.60ms로 거의 같아요. 일부러 이렇게 둬요.

- **결과는 Accelerate의 스레드 모드가 같을 때 비트까지 같아요.** `sd.set_num_threads`로 우리 풀의 스레드 수를 바꿔도 BLAS·LAPACK을 부르는 계산(행렬 곱, 분해, 회귀의 QR 등)의 비트는 그대로예요. Accelerate가 한 스레드로 돌지 여러 스레드로 돌지는 환경 변수 `VECLIB_MAXIMUM_THREADS`가 정하고, 두 모드 사이에서는 마지막 자리 몇 개가 다를 수 있어요(`ols`의 `bse`가 상대 $2 \times 10^{-16}$, `lstsq`가 $3 \times 10^{-14}$). Accelerate가 안에서 일을 나누는 방식은 stardust가 정하지 않아요. stardust가 모드를 고정하면 사용자의 설정을 덮고 큰 행렬 곱이 느려질 수 있어서, 모드는 바꾸지 않아요.
- **고칠 수단이 프로세스 전체에 걸려요.** Accelerate의 스레드를 제한하는 함수(`BLASSetThreading`)는 호출 하나가 아니라 프로세스 전체의 설정이에요. 호출마다 바꾸고 되돌리면 같은 프로세스에서 Accelerate를 쓰는 다른 코드(numpy, 다른 Python 스레드의 호출)까지 그 사이에 설정이 바뀌어요.
- **두 풀이 겹치지 않아요.** 큰 BLAS 호출은 우리 풀의 태스크 안에서 부르지 않고 호출한 스레드에서 차례로 불러요. 그동안 우리 풀은 쉬고 있으므로, Accelerate가 코어를 여러 개 써도 과다 구독이 생기지 않아요. Accelerate가 한 스레드로 도는 작은 행렬의 배치만 우리 풀로 나눠요([행렬곱](/internals/array/matmul/)).
- **희소 LU는 AMD 순서만 써요.** Accelerate의 희소 분해는 순서 매기기에 따라 결정성이 달라요. 기본 순서(다중 스레드 Metis)는 같은 스레드 모드에서도 실행마다 끝자리가 달랐고, 여러 스레드에서 동시에 부르면 프로세스가 죽기도 했어요. 희소 Cholesky와 LDLᵀ도 기본 모드에서 실행마다 달랐어요. 같은 입력을 20번씩 분해한 측정에서 LU와 AMD 순서의 조합만 모드와 동시 호출에 상관없이 늘 같은 비트였어요. 그래서 `sd.sparse`의 직접 풀이는 이 조합으로 고정해요([희소 LU](/internals/sparse/lu/)).
- **Accelerate는 필요할 때만 스레드를 써요.** 정사각 `dgemm`은 256까지 한 스레드이고, LAPACK 루틴은 n = 1024까지 대부분 한 스레드예요(LU 분해 `getrf`의 n ≥ 768만 여러 스레드). 그래서 이 설정이 실제로 차이를 내는 것은 큰 행렬 곱 정도예요.

## 언제 나누나: 기준값과 태스크 크기

### 풀은 정하지 않아요

풀 헤더에는 기준값이 없어요. 언제 나눌지는 커널마다 비용이 다르므로 각 영역이 자기 커널로 재서 정해요. 여러 영역이 쓰는 풀에 값을 하나만 두면 영역 중 적어도 하나에는 틀린 값이 돼요.

| 영역 | 기준 | 값 |
|---|---|---|
| 배열 | `sd::kParallelThreshold`, `sd::kParallelTask` | float64 원소 2¹⁵개, 2¹²개 (바이트로 셈) |
| frame | `sd::frame::kParallelThreshold`, `kChunkRows` | 2¹⁷행, 청크 2¹⁴행 |
| linalg | 비용 모델 `a + c·w` ns (`linalg/cost.hpp`) | 행렬 함수 계열마다 상수 두 개 |
| special | 원소당 비용 가중치 (`special/cost.hpp`) | 배열의 이터레이터에 가중치로 넘겨요 |
| stats | 원소당 비용 (`stats/engine.hpp`, `stats/cost_table.hpp`) | 분포와 메서드마다 잰 ns를 special과 같은 방식으로 넘겨요 |
| random | `kWordWork` (`random/random.cpp`) | 원소 하나를 일 8로 쳐서 배열의 기준값과 태스크 크기를 써요 |
| regression | 행 합의 기준 (`regression/*.cpp`) | 선형과 정규화는 행×열 65,536, GLM과 `rlm`은 2¹⁶행, `quantreg`는 2¹⁵행. 회귀끼리는 linalg의 비용 모델로 나눠요 |
| optimize | `kParallel`, `kTask` (`elementwise/loop.hpp`, 원소마다 따로 푸는 반복의 공용 고리), `kQrfacParallel` (`optimize/lsq.cpp`) | 배치 스칼라는 아직 끝나지 않은 원소 2¹⁵개부터 2¹³개씩, lmder의 QR은 한 단계 4×10⁵ 플롭부터 열 8개 이상씩 나눠요 |
| htest | 배열의 `kParallelThreshold`, `kParallelTask` (`htest/lanes.hpp`의 `each_lane`) | 줄 하나의 비용을 원소 수로 어림해 배열의 기준값과 태스크 크기를 써요. 조각이 2–16개뿐이고 조각마다 2¹⁵개 분량 이상이면 잠든 워커도 깨워요(`for_pieces_woken`). 긴 표본 하나의 합은 2¹⁶개부터 4096개씩의 고정 덩어리로 나눠요 |
| sparse | `kParallelThreshold`, `kChunk` (`sparse/parallel.hpp`) | 일 2¹⁵개 분량부터, 압축 배열의 줄을 `indptr`만으로 저장된 원소 약 2¹⁴개씩의 구간으로 잘라요(`line_bounds`) |
| integrate | 배열의 `kParallelThreshold`, `kParallelTask` (`integrate/samples.cpp`, `integrate/gauss.cpp`), 공용 고리의 `kParallel`, `kTask` (`elementwise/loop.hpp`의 `for_weighted`) | 표본 규칙은 줄 수 × 길이가 2¹⁵개부터 줄을 나누고, 긴 줄 하나는 pairwise 합의 같은 트리를 부분 트리로 나눠요. Gauss–Legendre 마디(n > 100)는 걸음 2¹⁵개부터 마디마다 나눠요. `tanhsinh`과 `nsum`은 남은 원소 수 × 원소마다의 점 수가 2¹⁵개부터 약 2¹³점씩, 조각 17개 이상으로 나눠 잠든 워커도 깨워요 |
| differentiate | 공용 고리의 `kParallel`, `kTask` (`elementwise/loop.hpp`) | `derivative`는 `tanhsinh`과 같은 `for_weighted`, `jacobian`과 `hessian`은 남은 항목 2¹⁵개부터 항목의 갱신을 2¹³개씩 나눠요 |

이름은 같고 값이 다른 상수가 배열은 `sd` 이름공간에, frame은 `sd::frame`에 있어서 각 영역의 코드가 자기 값을 찾아요. 아래는 배열의 정책이에요.

### `kParallelThreshold` = 2¹⁵

```cpp
// array/parallel_limits.hpp
inline constexpr std::int64_t kParallelThreshold = 1 << 15;  // 이보다 작은 일은 1스레드
inline constexpr std::int64_t kParallelTask      = 1 << 12;  // 태스크 하나의 일
```

기준값은 "10스레드가 1스레드를 이기기 시작하는 크기"예요. 기준값을 1로 낮춘 빌드에서 크기별로 재면 이래요.

| 연산 | 10스레드가 이기기 시작하는 원소 수 |
|---|---:|
| `exp(f)` | 약 8,000 |
| `f + g` | 약 16,000 |
| `sum(f)` | 약 32,000 |

- 계산이 무거운 `exp`는 일찍 이득이 나고, 원소당 일이 가장 가벼운 `sum`이 가장 늦어요.
- 연산마다 다른 기준값을 두지 않고 상수 하나를 써요. 가장 늦게 이득이 나는 `sum`에 맞추면 어떤 연산도 나눠서 손해 보지 않아요. 대가로 `exp`는 8천~3.2만 원소 구간에서 낼 수 있는 이득을 놓쳐요.
- 계산이 훨씬 무거운 함수는 같은 장치(가중치)로 기준값을 옮겨요. `sd.special`은 함수마다 원소당 비용을 재서 가중치 `w`로 넘기고, 그러면 원소 `2¹⁵/w`개부터 나눠요(상한 256).

### `kParallelTask` = 2¹²

태스크 하나는 float64 원소 4096개(피연산자 하나당 32KB) 분량이에요. 고정 비용이 약 1.5µs로 작아서 태스크를 잘게 해도 부담이 없고, 잘게 할수록 마지막 불균형이 작아져요. 기준값 2¹⁵에서는 태스크가 8개이고, 원소 100만 개면 245개예요.

### 일을 바이트로 세요

이터레이터는 일의 양을 원소 수가 아니라 바이트로 세요(`array/iter.cpp`의 `NdIter::plan`).

$$
\text{work} = w \times \min\!\Big(8,\ \max_k \big|\text{stride}_k^{\text{inner}}\big|\Big) \times \prod_d \text{extent}_d
$$

- $w$는 가중치(보통 1), 가운데 항은 피연산자의 가장 안쪽 stride 중 가장 큰 것(8바이트 상한, 전부 0이면 8)이에요.
- 기준값과 태스크 크기는 원소 수 × 8바이트와 비교해요. 그래서 8바이트 피연산자가 하나라도 있으면 원소 수로 센 것과 같아요.
- **이유:** bool처럼 1바이트 피연산자만 있는 루프는 원소 하나에 옮기는 메모리가 8분의 1이에요. 원소 수로 세면 4096개짜리 bool 태스크가 4KB밖에 안 돼서, atomic 카운터를 건드리고 캐시 라인을 주고받는 비용이 실제 일보다 커져요. 그렇게 세면 1000만 개 `b & b`가 10스레드에서 187µs로 1스레드(122µs)보다 느려요. 바이트로 세면 bool은 원소 2¹⁸개부터 나누고 태스크 하나가 3만 2768개가 되어 38µs예요.

### 어느 축을 자르나

이터레이터는 축 정리(크기 1인 축 제거, stride 순 재배열, 차원 합치기)를 마친 뒤 축 하나를 골라 잘라요([연산 엔진](/internals/array/engine/)).

```cpp
// 바깥쪽부터 보며, 길이 16 이상인 첫 축. 없으면 가장 긴 축.
// 리덕션이면 출력이 실제로 걸친 축(출력 stride ≠ 0)만 후보다.
int NdIter::split_axis(Split split) const {
    int best = -1;
    for (int d = 0; d < ndim_; ++d) {
        if (split == Split::Reduction && strides_[nop_ - 1][d] == 0) continue;
        if (shape_[d] >= 16) return d;
        if (shape_[d] >= 2 && (best < 0 || shape_[d] > shape_[best])) best = d;
    }
    return best;
}
```

- **바깥 축을 먼저 골라요.** 바깥 축을 자르면 조각마다 안쪽 구간이 그대로 길게 남아 커널이 끊김 없이 돌아요. 길이 16 이상이면 스레드마다 조각이 여럿 돌아가요.
- 조각 크기는 "태스크 하나가 약 `kParallelTask` × 8바이트"가 되게 정해요. `chunk = max(8·kParallelTask / (work / extent), 1)`이에요.
- **안쪽 축을 자를 때는 조각을 1024원소(`kMinInnerPiece`) 이상으로 해요.** 안쪽 축을 자르면 커널 호출 하나가 처리하는 구간이 짧아져서, 호출과 루프 시작 비용이 늘고 벡터화된 루프가 제 속도를 못 내요. 아래는 3000×3000 행렬의 `sum(axis=0)`을 10스레드에서 최소 길이별로 잰 값이에요.

| 안쪽 조각의 최소 길이 | 시간 (10스레드) |
|---|---:|
| 10 | 1스레드보다 2.7배 느림 |
| 256 | 1.50ms |
| **1024** | **0.91ms** |
| 4096 | 1.11ms |
| (1스레드) | 1.05ms |

자른 조각은 태스크 안에서 이터레이터를 복사해 그 축의 길이와 시작 포인터만 바꾼 뒤 직렬로 돌려요(`NdIter::run`).

```cpp
parallel::parallel_for(p.tasks, [&](int64_t t) {
    NdIter piece = *this;                                    // 이터레이터 복사
    const int64_t begin = t * p.chunk;
    piece.shape_[p.axis] = std::min(extent, begin + p.chunk) - begin;
    for (int k = 0; k < nop_; ++k) piece.data_[k] += begin * strides_[k][p.axis];
    piece.run_serial(kernel, ctx);
});
```

### 이터레이터 밖의 병렬 경로

이터레이터를 거치지 않고 손으로 나누는 경로도 있어요. 모두 길이나 크기로만 나눠요.

| 경로 | 나누는 기준 |
|---|---|
| pairwise 합, `prod`, 정수 스캔 | n ≥ `kParallelThreshold`, 잎·조각 4096원소 |
| float/complex 누적 스캔 | n ≥ 8192, 블록 4096 (1스레드에서도 같은 구조) |
| 바깥 축 블록 리덕션 | 줄이는 축을 최대 16블록, 블록당 인덱스 32개 이상 |
| bool 마스크 인덱싱 | 청크 2¹⁴원소, 청크가 둘 이상이면 |
| 긴 레인 하나의 정렬 | n ≥ 2¹⁷, 조각 2¹⁶, 병합 구간 2¹⁵ |
| int64 matmul | 곱셈-덧셈 약 2¹² 분량의 출력 행 |
| 작은 BLAS 행렬의 배치 | 행렬 m·n·k ≤ 256³, 태스크당 곱셈-덧셈 약 2¹⁵ |

`array/ops/pieces.hpp`의 `for_pieces(n, per, work, fn)`가 이런 경로의 공통 틀이에요. 조각 `[t·per, min(n, (t+1)·per))`는 `n`과 `per`로만 정해지고, `work`가 기준값 이상이고 조각이 둘 이상이고 풀이 비어 있을 때만 `parallel_for`로 돌려요.

## 결정성

### 규칙

**결과는 스레드 수와 무관하게 비트까지 같아요.** 이를 위해 두 가지를 지켜요. 나누는 방식은 데이터의 크기와 레이아웃(그리고 dtype)으로만 정하고, 부분 결과는 고정된 순서로 합쳐요. "스레드가 있을 때만 다른 경로"는 쓰지 않아요. 결과가 같다고 보장되는 경우만 예외예요.

모든 영역이 이렇게 동작해요. 그래서 1스레드로 디버깅한 결과와 10스레드로 돌린 결과를 그대로 비교할 수 있고, 테스트는 정답을 하나만 두면 돼요. BLAS·LAPACK을 부르는 계산은 Accelerate의 스레드 모드가 같다는 조건이 하나 더 붙어요(위 "Accelerate는 따르지 않아요").

이것이 stardust가 비트로 약속하는 것이에요. numpy와 비트까지 같은 것은 약속이 아니에요. 아래 pairwise 합처럼 numpy와 같은 알고리즘을 쓰더라도 더 빠른 잎을 쓰면 마지막 자리가 달라질 수 있고, 그 대신 스레드 수와 상관없이 같은 비트는 언제나 지켜요([전체 구조](/internals/core/overview/)의 "결과의 비트").

### 부동소수점 덧셈은 결합법칙이 성립하지 않아요

실수에서는 $(a + b) + c = a + (b + c)$이지만, 부동소수점에서는 덧셈마다 반올림이 일어나서 순서가 바뀌면 결과의 마지막 비트가 달라질 수 있어요.

$$
\mathrm{fl}(\mathrm{fl}(a + b) + c) \ne \mathrm{fl}(a + \mathrm{fl}(b + c)) \quad \text{(일반적으로)}
$$

예를 들어 $a = 10^{16}$, $b = -10^{16}$, $c = 1$이면 왼쪽은 $0 + 1 = 1$이지만, 오른쪽은 $b + c$가 $-10^{16}$으로 반올림돼 $0$이 돼요.

흔한 병렬 합은 "스레드가 p개면 배열을 p등분해서 각자 더하고, 부분합을 더한다"예요. 이러면 스레드 수가 덧셈 순서를 바꿔요. 표준정규분포 원소 100만 개(`numpy.random.default_rng(0).standard_normal(1_000_000)`)를 k등분해 조각마다 `np.sum`으로 더한 뒤 조각 합을 왼쪽부터 더하면 이래요(numpy 2.5.4).

| 방법 | 결과 | `np.sum(x)`와 같은가 |
|---|---|:---:|
| `np.sum(x)` (기준) | `998.5706494386213` | — |
| 2등분 | `998.5706494386213` | 같음 |
| 3등분 | `998.5706494386214` | 다름 |
| 7등분 | `998.570649438621` | 다름 |
| 10등분 | `998.5706494386216` | 다름 |
| `sd.sum(x)`, 1·3·10스레드 | `998.5706494386211` | 다름 (세 스레드 수에서 서로 같음) |

차이는 마지막 한두 자리뿐이지만, 스레드 수에 따라 결과가 바뀌면 디버깅이 어려워져요. 2등분이 같은 것은 우연이 아니에요. numpy의 합 트리가 100만 개를 정확히 50만/50만으로 나누기 때문이에요. `sd.sum`은 numpy와 잎의 크기가 달라서(아래) 마지막 자리가 numpy와 다르지만, 스레드 수를 바꿔도 같은 값이에요.

### 실제 예 1: 긴 합 하나 (pairwise 트리의 잎)

stardust의 float 합은 **pairwise 합**이에요([집계](/internals/array/reductions/)). numpy의 `DOUBLE_pairwise_sum`(`numpy/_core/src/umath/loops_utils.h.src`)과 같은 알고리즘이고 잎만 더 넓어요 [5].

- 원소가 512개(`kBlock`) 이하면 누산기 16개로 더하고, 누산기는 이웃끼리, 그 쌍끼리 고정된 트리로 합쳐요. numpy는 누산기 8개, 128개예요.
- 그보다 길면 반으로 나누되, 자르는 위치를 16의 배수로 내려요($\text{split}(n) = \lfloor n/2 \rfloor - (\lfloor n/2 \rfloor \bmod 16)$). 양쪽을 재귀로 더한 뒤 왼쪽 + 오른쪽.

이렇게 더하면 반올림 오차가 n이 아니라 $\log n$에 비례해 자라요 [6]. 이 재귀 트리의 모양은 n에만 의존해요. 그래서 병렬화는 이렇게 해요(`base/pairwise.hpp`의 `plan`, `combine`).

1. **계획:** 트리를 위에서부터 내려가다가 크기가 4096(`kLeaf = kParallelTask`) 이하인 부분 트리를 만나면 그것을 "잎"으로 목록에 넣어요. 왼쪽에서 오른쪽 순서예요.
2. **병렬 계산:** 잎마다 태스크 하나. 잎 안에서는 직렬 pairwise 합과 똑같이 더해요. 어느 스레드가 어느 잎을 언제 더하든 각 잎의 결과는 같아요.
3. **합치기:** 같은 트리를 다시 내려가면서, 잎 자리에 2의 결과를 차례로 끼워 넣고 왼쪽 + 오른쪽을 해요.

덧셈 하나하나가 직렬 트리와 같은 피연산자, 같은 순서예요. 그래서 결과는 1스레드와 비트까지 같아요. n = 40,000이면 이렇게 돼요.

### 실제 예 2: 바깥 축 리덕션 (고정 블록)

C 순서 1000×1000 행렬의 `sum(m, axis=0)`을 보면, 줄이는 축(행 방향)이 메모리상 바깥에 있어요. 이터레이터는 리덕션에서 "출력이 걸친 축"만 자를 수 있는데, 남는 축(열 1000개)은 가장 안쪽이라 1024원소 하한에 걸려 태스크가 하나뿐이에요. 그래서 줄이는 축을 고정 개수의 블록으로 나눠요(`plan_blocks`, `reduce_blocked`).

블록 수는 $\min(16,\ \lfloor \text{extent}/32 \rfloor,\ \lfloor \text{work}/(8 \cdot 4096) \rfloor)$이에요. 1000×1000이면 $\min(16, 31, 244) = 16$이고, 블록 크기는 $\lceil 1000/16 \rceil = 63$행이에요. 그래서 63행짜리 블록 15개와 55행짜리 블록 하나가 돼요.

1. 블록마다 출력의 복사본(시작값 0으로 채움)에 자기 행을 접어요. 블록끼리는 독립이라 병렬로 돌아요.
2. 복사본 16개를 블록 순서대로 출력에 접어요.

블록 구조는 shape, 레이아웃, dtype만으로 정해지고 스레드가 1개여도 같은 16블록으로 계산해요. 그래서 스레드 수와 무관하게 같은 비트예요. 대신 덧셈 순서가 numpy의 "행을 위에서부터 차례로 더하기"와 달라져서 float 합은 numpy와 마지막 비트가 다를 수 있어요(정규분포 1000×1000에서 최대 상대 차이 $10^{-13}$ ~ $10^{-12}$). 정수 합, max/min, any/all은 순서와 무관하므로 numpy와도 같아요. 수치는 1스레드 130µs, 10스레드 32µs, numpy 123µs예요.

### 연산별 나누는 방법

| 연산 종류 | 나누는 방법 | 결과가 같은 이유 |
|---|---|---|
| 원소별 (산술, 초월함수, 캐스트, 복사, gather) | 아무 축이나 | 원소마다 따로 계산해요. vForce도 원소 위치에 독립이에요 |
| 축 리덕션 (`Split::Reduction`) | 출력이 실제로 걸친 축만 | 출력 원소 하나에 입력이 접히는 순서가 직렬과 같아요 |
| 바깥 축 블록 리덕션 | 줄이는 축의 고정 블록 | 블록 구조가 스레드 수와 무관해요 |
| 출력이 하나인 긴 float 합 | pairwise 트리의 잎 | 같은 트리 순서로 합쳐요 |
| 정수 +/×, max/min, and/or | 고정 조각, 조각 순서대로 합침 | 결합법칙이 정확히 성립해요(정수는 wrap) |
| 긴 argmax/argmin | 고정 조각, 조각 순서대로 비교 | NaN이 있는 첫 조각 우선, 동점이면 앞 조각 |
| float/complex `prod`, 긴 누적 스캔 | 고정 조각·블록 | 구조가 n에만 의존해요 |
| 정렬, 누적, `argmax(axis=)` | 레인 단위 | 레인끼리 독립이에요 |
| 긴 레인 하나의 정렬 | 고정 조각 + 왼쪽 우선 병합, 기수 정렬은 자리마다 병렬 | 안정 정렬의 결과와 같아요. int64·float64는 `stable=False`도 안정 알고리즘을 쓰고, bool의 불안정 `argsort`는 항상 조각이에요 |
| bool 마스크 | 고정 청크 + 앞부분 합 | 원소마다 출력 자리가 정해져요 |
| 인덱스 하나짜리 scatter | 나누지 않아요 | 반복된 인덱스에서 마지막 쓰기가 이겨야 해요 |
| matmul | 출력 행, 배치 | 행렬 하나·행 하나는 한 스레드가 계산해요 |

`max`/`min`이 결합적이라는 것은 IEEE의 `FMAX`/`FMIN`도 마찬가지예요(NaN이 하나라도 있으면 NaN). 그래서 float `max`도 조각으로 나눠도 numpy와 같아요.

### 예외: 결과가 같다고 보장된 경로 전환

"스레드가 있을 때만 다른 경로"를 쓰지 않는다는 규칙에는 예외가 하나 있어요. 어떻게 나눠도 결과가 정확히 같다고 증명되는 경우예요.

- **안정 정렬의 조각:** 긴 레인 하나를 정렬할 때, 풀을 쓸 수 있으면 조각으로 정렬한 뒤 병합하고, 아니면 직렬 정렬을 해요. 병합은 직렬 정렬에 없는 추가 패스라, 1스레드에서도 항상 조각을 쓰면 `sort(i)`가 5.8ms가 아니라 13.6ms가 걸려요. 안정 정렬의 결과는 유일하므로(같은 값의 원래 순서가 유지됨) 경로가 바뀌어도 결과는 같아요.
- **불안정 정렬이면 이 전환을 할 수 없어요.** introsort 같은 불안정 정렬은 같은 값의 순서가 조각 경계에 따라 달라지므로 결과가 유일하지 않아요. 이런 정렬이 긴 레인을 만나면 1스레드도 같은 조각으로 정렬해야 결과가 스레드 수와 무관해요. int64와 float64는 `stable=False`여도 안정 알고리즘(기수 정렬, float 값의 NEON 정렬과 0의 부호 복원)을 쓰므로 이 경우가 생기지 않아요. 안정 정렬의 결과는 불안정 정렬로서도 올바른 결과이기 때문이에요. 남는 것은 bool의 `argsort(stable=False)`예요. introsort로 정렬하므로 긴 레인이면 스레드 수와 상관없이 항상 조각으로 나눠요. 자세한 것은 [정렬과 집합](/internals/array/sorting/)에 있어요.
- **pairwise 합의 직렬 경로:** `available()`이 false면 계획을 만들지 않고 직렬 트리로 바로 가요. 직렬 트리와 병렬 계획이 같은 트리이므로 결과는 같아요.
- frame도 같은 원칙의 예외를 둬요. factorize(처음 나타난 순서로 코드를 매김), 안정 counting sort, 기수 정렬, CSV 읽기는 결과가 나누는 방식과 무관하게 정확히 정해지므로, 나누는 방식이 스레드 수를 따라요. 나누면 패스가 늘어 1스레드가 1.5~2.5배 느려지기 때문이에요.

### 에러 위치도 결정적이에요: `FirstRow`

여러 태스크가 값을 검사하다가 여러 곳에서 실패하면, 어느 태스크가 먼저 실패할지는 스케줄에 달려 있어요. 그대로 두면 "1번째 행이 잘못됐다"와 "70만 번째 행이 잘못됐다"가 실행마다 바뀌어요. 그래서 `parallel::FirstRow`는 가장 작은 실패 위치를 골라요.

```cpp
class FirstRow {
public:
    void offer(int64_t row) {   // 이 태스크의 첫 실패 위치를 낸다
        int64_t cur = row_.load(std::memory_order_relaxed);
        while (row < cur && !row_.compare_exchange_weak(cur, row, std::memory_order_relaxed)) {}
    }
    bool failed_before(int64_t row) const { return row_.load(std::memory_order_relaxed) < row; }
    ...
private:
    std::atomic<int64_t> row_{INT64_MAX};
};
```

- `offer`는 compare-and-swap 루프로 "지금 값보다 작을 때만 바꾸기"를 원자적으로 해요. 여러 태스크가 동시에 내도 가장 작은 값이 남아요. 값 하나의 최솟값만 필요하고 다른 메모리와의 순서는 상관없어서 relaxed로 충분해요. 결과는 `parallel_for`가 돌아온 뒤에 읽는데, 그때는 워커가 일에서 나갈 때의 `state_` 갱신(acq_rel)과 호출 스레드의 acquire 읽기가 순서를 보장해요.
- `failed_before(row)`가 true면 앞쪽에서 이미 실패했으므로 뒤쪽 태스크는 일찍 멈춰도 돼요.
- frame(문자열 → 숫자 변환 등)이 쓰고, linalg는 같은 원리로 "배치에서 가장 작은 실패 인덱스"를 보고해요. 메시지는 병렬 구간이 끝나고 GIL을 다시 잡은 뒤에 만들어요.

- **메모리에 묶인 연산은 대역폭에서 멈춰요.** `f + g`(원소 400만 개, 읽기 64MB + 쓰기 32MB = 96MB)는 1스레드가 이미 초당 약 130GB를 옮기고, 스레드를 늘려도 1.7배가 한계예요. 결과는 항상 새 배열에 쓰므로 새 메모리의 첫 쓰기에서 나는 페이지 폴트(페이지 16KB마다 한 번)도 이 크기에서는 무시할 수 없어요.
- **계산에 묶인 연산은 거의 코어 수만큼 빨라져요.** `argmax`나 정렬은 원소당 일이 많아 메모리를 기다리는 시간이 상대적으로 작아요. 원소 100만 개, 10스레드에서 `exp`는 121µs, `sin`은 94µs예요(numpy는 1스레드로 1.49ms, 3.81ms).
- 10스레드를 넘으면 E코어가 붙어요. 메모리 연산은 조금 느려지고(`f + g` 1.7 → 1.5), 계산 연산은 조금 더 빨라져요(`argmax` 8.0 → 9.7). 기본값이 10인 이유예요.

### numpy와 BLAS의 스레드

- **numpy는 BLAS 말고는 한 스레드로 돌아요.** 위 표의 numpy 수치는 모두 1스레드예요. stardust 1스레드가 numpy보다 빠른 줄(`i + f`, `var`, `sort` 등)은 알고리즘이나 커널이 달라서이고, 여러 스레드 열의 차이는 여기에 병렬화가 더해진 것이에요.
- **BLAS는 자기 스레드를 따로 가져요.** 이 환경의 numpy 2.5.4는 BLAS와 LAPACK으로 Apple Accelerate를 써요(`numpy.show_config()`에 나와요). stardust의 float64·complex128 matmul도 Accelerate를 부르므로, 큰 행렬 하나의 곱은 양쪽 모두 Accelerate 안에서 나뉘어 돌아요. 두 쪽이 같은 BLAS 호출을 하는 셈이라 시간도 거의 같아요.
- **두 풀을 겹치지 않아요.** stardust는 큰 행렬의 배치를 우리 풀로 나누지 않고 차례로 돌려요. 우리 풀과 Accelerate의 스레드가 동시에 코어를 다투면 둘 다 느려지기 때문이에요. 반대로 Accelerate는 정사각 `dgemm`을 256까지는 한 스레드로 돌리므로(CPU 시간/경과 시간이 256에서 1.00, 288에서 1.62), 행렬 하나가 256³ 이하인 배치는 우리 풀로 나눠요(1000 × 8×8: 1스레드 65µs → 10스레드 14µs, numpy 66µs). 자세한 것은 [행렬곱](/internals/array/matmul/)에 있어요.
- Linux에서 흔한 OpenBLAS는 자기 스레드 수를 `OPENBLAS_NUM_THREADS` 같은 환경 변수로 따로 정해요. numpy 사용자가 Python 스레드로 직접 병렬화하면서 BLAS도 여러 스레드를 쓰면 과다 구독이 생기기 쉬워요. stardust 안에서는 `busy_` 규칙과 "큰 BLAS 배치는 차례로" 규칙이 이것을 막아요.

### 복잡도 요약

- `parallel_for` 한 번: 고정 비용 $O(1)$(약 1.5µs) + 태스크당 $O(1)$(atomic 증가와 간접 호출).
- pairwise 합의 병렬 계획: 잎 수 $L = O(n / 4096)$, 계획과 합치기 모두 $O(L)$ 시간, $O(L)$ 메모리(부분합 배열). 원소 100만 개면 $L = 256$이에요.
- 블록 리덕션: 블록 수 $B \le 16$, 추가 메모리 $B \times$ (출력 크기), 추가 일은 복사본 채우기와 마지막 접기로 $O(B \times \text{출력 크기})$예요. (64, 2000)을 8행 블록 8개로 나누면 이 추가 일 때문에 1스레드가 30% 느려져요. 블록 하나를 인덱스 32개 이상으로 하면 이 비용이 그 약 10분의 1로 줄어요.
