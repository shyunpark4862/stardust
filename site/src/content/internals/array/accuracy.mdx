## 한눈에 보기

stardust의 배열 영역이 결과에 대해 약속하는 것은 셋이에요.

1. 결과는 결정적이에요. 같은 기계, 같은 스레드 수에서 같은 데이터, 같은 레이아웃이면 실행마다 같은 비트가 나와요. 스레드 수가 달라도 같은 비트인 것은 약속이 아니지만, 지금 배열 영역의 분할은 모두 데이터 크기와 레이아웃으로만 정해져서 스레드 수와도 상관없어요.
2. 자기 기록과 같은 비트예요. 공개 함수의 결과를 저장해 둔 sd 자신의 출력(골든)과 견주어, 결과가 바뀌면 안 되는 변경(리팩터링, 옮기기)에서 비트까지 그대로인지 확인해요.
3. 정확도는 계약으로 정해요. 반올림이 끼는 결과는 Arb(구간 산술)로 만든 참값이나 numpy와 견준 한계(ULP, 상대오차) 안이면 돼요.

반올림이 아닌 동작(dtype 규칙, 정수 연산, 정렬 순서, NaN과 ±0의 규칙)은 numpy와 똑같아요. 반올림 크기의 결과는 numpy와 마지막 자리까지 같을 필요가 없어서, 더 빠르거나 더 정확한 계산 순서를 써요. 성능이 먼저이고 정확도가 그다음이에요. 지금 numpy와 비트까지 같은 코드는 그것만을 위해 바꾸지 않지만, 고침이나 최적화가 필요하면 바꿔요. 아래 표는 지금의 관계예요.

| 범주 | numpy와의 관계 |
|---|---|
| 원소별 연산 (vForce·자체 커널 함수, complex `abs`·`expm1` 제외) | 지금은 비트까지 같아요 |
| vForce를 쓰는 float64 함수 14개 | 끝자리가 다를 수 있어요. 계약은 Arb 참값에서 함수마다 3–5 ULP이고, 잰 numpy와의 거리는 최대 4 ULP(`atanh`)예요 |
| 자체 NEON 커널의 `exp` `expm1` `log1p` `cos` | 끝자리가 다를 수 있어요. Arb 참값에서 잰 최대는 1 ULP예요(`exp`의 계약은 3 ULP). 나머지 셋은 참값 파일이 없어 테스트가 numpy와의 거리 8 ULP를 봐요 |

| float64 `pow` | 같은 libm `pow`라 지금은 비트까지 같아요. 지수 2, 0, 1, −1, 0.5는 정확한 꼴로 계산해서 두 경우에 달라요(아래) |
| 긴 float 합 (`sum(f)`), `mean`, `var`/`std` | 같은 pairwise 알고리즘에 넓은 잎이라 끝자리가 다를 수 있어요. 오차 한계는 같은 수준이에요 |
| int64·bool `mean` (전체, 안쪽 축) | 정확한 정수 합이라 합이 $2^{53}$을 넘으면 다를 수 있어요(stardust가 더 정확해요) |
| 순서와 무관한 리덕션 (정수 합·곱, max/min, any/all, argmax) | 같아요 |
| 블록 리덕션, float/complex `prod`, 긴 float 누적 스캔, 형변환이 있는 리덕션 | 다를 수 있어요. 오차 한계는 numpy보다 작거나 같아요 |
| 가중치 `bincount`·`histogram` | 끝자리가 다를 수 있어요 |
| 분위수, `median` | 지금은 비트까지 같아요(`-0.0`과 `+0.0`이 같은 순위에 섞인 경우만 예외) |

| float `matmul` | Accelerate가 정해요. 시험한 경우는 같지만 보장하지 않아요 |
| `repr` | 같을 필요가 없어요 |

## ULP: 차이를 재는 단위

### 정의

부동소수점 수 사이의 차이는 **ULP**(unit in the last place, 마지막 자리의 한 칸)로 재요. float64에서 정규수 $x$가 $2^e \le |x| < 2^{e+1}$이면

$$
\operatorname{ulp}(x) = 2^{e-52}
$$

이에요. 가수(significand)가 52비트이므로, 그 지수 구간 안에서 이웃한 두 float64의 간격이에요. 서브노멀 구간에서는 $2^{-1074}$로 일정해요. 상대 크기로 보면

$$
2^{-53} < \frac{\operatorname{ulp}(x)}{|x|} \le 2^{-52} \approx 2.2 \times 10^{-16}
$$

이라서 "5 ULP 차이"는 상대오차로 많아야 $5 \times 2^{-52} \approx 1.1 \times 10^{-15}$이에요. 올바르게 반올림한(correctly rounded) 결과는 참값에서 0.5 ULP 이내예요[1][6].

### ULP 거리를 세는 방법

두 수 사이에 float64가 몇 개 있는지를 세면 ULP 거리가 돼요. 같은 값이면 0, 이웃한 두 float64이면 1이에요. 참값과 견줄 때는 참값을 float64로 반올림한 값과의 거리를 세요. 그래서 0이면 올바르게 반올림한 결과이고, 1이면 그 이웃이에요. 테스트, 정확도 측정, 골든 비교가 모두 같은 함수(`bench/accuracy/common.py`의 `ulp_distance`)로 세요. 이 함수는 float64의 비트 패턴을 "크기 순서가 보존되는 정수"로 바꿔서 이 개수를 뺄셈 하나로 계산해요. $x$의 64비트 패턴을 부호 있는 정수로 읽은 값을 $b(x)$라 하면

$$
\kappa(x) =
\begin{cases}
b(x) & b(x) \ge 0 \\
-2^{63} - b(x) & b(x) < 0
\end{cases}
\qquad
d(x, y) = |\kappa(x) - \kappa(y)|
$$

예요. 양수는 비트 패턴의 정수 순서가 크기 순서와 같아요(지수가 위 비트, 가수가 아래 비트). 음수는 부호 비트가 켜져 있어 $b(x) = \operatorname{bits}(|x|) - 2^{63}$이므로 $\kappa(x) = -\operatorname{bits}(|x|)$가 되어, 결국 $\kappa(x) = \operatorname{sign}(x) \cdot \operatorname{bits}(|x|)$예요. 이웃한 두 float64는 $\kappa$가 정확히 1 차이 나고, 0을 가로질러도(음의 최소 서브노멀, ±0, 양의 최소 서브노멀) 거리가 이어져요.

$\kappa(+0) = \kappa(-0) = 0$이라서 이 거리로는 0의 부호를 구별하지 못해요. 그래서 vForce 테스트는 특수값(±0, ±inf, NaN)을 따로 비트까지 비교해요. NaN끼리는 거리 0이고 NaN과 수 사이는 어떤 거리보다 큰 값이에요. numpy와 견주는 테스트는 두 결과의 NaN 위치가 같은지 먼저 확인해요.

## 원소별 연산: 식을 코드가 정하게 하기

같은 식을 같은 순서로 계산하면 IEEE 754의 각 연산(덧셈, 곱셈, 나눗셈, 제곱근, FMA)은 올바르게 반올림되므로 결과가 하나로 정해져요[2]. 문제는 식과 순서를 컴파일러와 라이브러리가 몰래 바꾸는 곳이에요. 그러면 같은 식이 경로(연속, strided)마다 다른 비트를 낼 수 있어요. stardust는 그런 곳을 하나씩 막아서 식을 소스 코드가 정하게 해요([원소별 커널](/internals/array/elementwise/)). numpy가 식을 적어 둔 연산은 같은 식을 쓰므로, vForce 함수 15개, float64 `pow`의 두 경우([아래](#pow-libm과-정확한-꼴)), complex `abs`와 `expm1`을 빼면 지금은 numpy와 비트까지 같아요.

| 바뀔 수 있는 곳 | 막는 방법 |
|---|---|
| 컴파일러가 `a + b*c`를 인라인 상황에 따라 FMA 하나로 합침(반올림이 한 번 줄어요) | `-ffp-contract=off`. FMA가 필요한 자리는 코드에 `std::fma`로 명시해요 |
| numpy 바이너리는 FMA로 축약되어 빌드됨 | complex 곱셈·나눗셈·제곱, `expm1`, complex `reciprocal`의 분모는 numpy가 FMA를 쓴 자리와 같은 곳에 `std::fma`를 적어요. 지금은 무작위 곱 4000개에서 numpy와 비트까지 같아요. complex `reciprocal`은 FMA 없이 계산하면 원소의 9%가 1 ULP 달라요 |
| 컴파일러가 같은 인자의 `sin`과 `cos`를 인라인 상황에 따라 `__sincos_stret` 하나로 합침 | `-fno-builtin-sin -fno-builtin-cos`. 합친 호출이 필요한 곳(complex `expm1`)은 코드에 `sd::sincos`로 적어요 |
| `-ffast-math`가 재배치하고 NaN·inf가 없다고 가정 | 쓰지 않아요. 재배치가 필요한 곳(리덕션)은 코드에서 명시적으로 해요 |
| `std::complex`의 연산자가 C99 Annex G의 inf/nan 복구를 더함 | 쓰지 않고 numpy의 식(Smith 나눗셈 등)을 직접 적어요 |
| libc++의 `std::exp(complex)`는 자체 구현 | C 라이브러리의 C99 함수(`cexp` 등)를 직접 선언해 불러요 |
| `abs(z)`: 공식마다 반올림이 달라요 | `sqrt(fma(re, re, im·im))`을 써요. 계약은 Arb 참값에서 3 ULP이고 잰 최대는 1 ULP예요. numpy의 공식 `큰 쪽 × sqrt(1 + (작은 쪽/큰 쪽)²)`는 같은 점에서 최대 2 ULP라, 이쪽이 더 정확하고 빨라요 |

손으로 짠 NEON 커널(`maximum`, `clip`, complex 곱셈 등)은 스칼라 정의와 비트가 같아야 해요. 원소별 테스트는 dtype 쌍마다 세 레이아웃(연속, 스칼라 브로드캐스트, strided)을 모두 돌려요. 레이아웃에 따라 실행되는 커널이 달라지기 때문이에요(연속 fast path, 스칼라 fast path, 일반 strided 루프).

float64 초월함수 가운데 `tan`과 `sqrt`는 numpy와 같은 libm 함수를 부르거나 같은 명령을 쓰므로 지금은 비트까지 같아요. 이 기계의 numpy float64 초월함수는 libm과 비트가 같고, `tanh`만 최대 1 ULP 달라요. float64 `pow`도 numpy와 같은 libm `pow`를 원소마다 불러요([아래](#pow-libm과-정확한-꼴)).

## 초월함수와 Arb 참값 계약

### 무엇이 다른가

`log` `log2` `log10` `sin` `asin` `acos` `atan` `sinh` `cosh` `tanh` `asinh` `acosh` `atanh`, 그리고 이항 함수 `atan2`는 Apple Accelerate의 vForce(배열 단위 초월함수)로 계산해요. `exp` `expm1` `log1p` `cos`는 배열 영역의 자체 NEON 커널이에요([원소별 커널](/internals/array/elementwise/#자체-neon-커널-exp-expm1-log1p-cos)). 둘 다 libm보다 빠르지만 결과가 libm과, 따라서 numpy와 마지막 몇 비트가 달라요.

### 계약

vForce 14개와 `exp`, float64 `pow`, complex `abs`의 계약은 Arb(구간 산술)[7]로 만든 참값을 float64로 반올림한 값에서 함수마다 정한 ULP 안이에요. 특수값(±0, ±inf, NaN)은 부호까지 비트가 정확해야 해요.

| 한계 | 함수 |
|:---:|---|
| 3 ULP | `exp` `acos` `atan` `atan2` `pow` complex `abs` |
| 4 ULP | `log` `log2` `log10` `asin` `sinh` `cosh` `tanh` `asinh` `acosh` |
| 5 ULP | `sin` `atanh` |

한계는 참값 점에서 잰 최대에 2를 더한 값이에요. numpy와의 거리는 기록만 하고 약속하지 않아요. `expm1` `log1p` `cos`는 `tests/array/ref`에 참값 파일이 없어요. 이 셋은 Arb 참값과 따로 견줘 잰 최대가 1 ULP이고(함수마다 10–20만 점), 테스트(`tests/array/test_ufunc.py`)는 numpy(libm)와의 거리 8 ULP를 봐요.

참값은 `tools/array_ref.py`가 만들어 `tests/array/ref/<함수>.npz`에 둬요. 점은 함수마다 무작위 2만 개(`test_vforce.py`와 같은 범위, 여러 자릿수에 걸친 범위는 로그 균등)에, 오차가 몰리는 곳(영점과 극 근처, 정의역의 끝, 서브노멀과 아주 큰 인자)을 더한 것이에요. 값마다 float64 입력에서의 정확한 함숫값을 상대 $2^{-110}$까지 좁혀 double-double로 저장해요. `tests/array/test_reference.py`가 모든 점에서 한계를 확인하고, `tests/array/test_vforce.py`는 numpy와 8 ULP 안인지(가벼운 확인), 특수값, 위치 독립성을 봐요.

참값 점에서 잰 값이에요(`bench/array/accuracy.md`, Apple M4 Pro, numpy 2.5.4). "numpy와의 거리"는 같은 점에서 stardust와 numpy의 결과 사이의 ULP 거리이고, "numpy의 최대"는 numpy를 같은 참값에 견준 값이에요.

| `sin` | 5 | 24,000 | 3 | 2 | 3 | 1 |
| `asin` | 4 | 23,000 | 2 | 2 | 2 | 1 |
| `acos` | 3 | 22,485 | 1 | 1 | 1 | 1 |
| `atan` | 3 | 22,000 | 1 | 1 | 1 | 1 |
| `sinh` | 4 | 22,500 | 2 | 1 | 2 | 1 |
| `cosh` | 4 | 22,500 | 2 | 1 | 2 | 1 |

| `asinh` | 4 | 22,000 | 2 | 1 | 3 | 1 |

모든 함수가 한계 안이고, 가장 큰 것은 `sin`과 `atanh`의 3 ULP예요. numpy는 libm을 부르므로 numpy의 최대는 대부분 1 ULP예요. vForce의 결과는 numpy보다 한 칸쯤 더 벗어나고, numpy와는 많아야 4 ULP 떨어져요. 자체 커널인 `exp`는 numpy와 같은 최대 1 ULP이고, 99.9% 분위수는 0이에요.

### vForce를 써도 된다고 판단한 근거

정확도만으로는 부족해요. 결정성과 특수값까지 지켜야 해요. 아래는 확장 모듈과 별개인 작은 프로그램으로 검사한 결과예요.

| 항목 | 결과 |
|---|---|
| 위치 독립성(인덱스, 배열 길이, 정렬) | 약 24만 회 검사에서 불일치 0. 그래서 `exp(x)[i] == exp(x[i])`이고, 스레드 청크가 결과를 바꾸지 않아요 |
| 스레드 안전성 | 14개 스레드 동시 호출에서 불일치 0 |
| 내부 스레드 | 쓰지 않아요(CPU 시간 / 경과 시간 = 1.00). stardust의 풀과 충돌하지 않아요 |
| 특수값 | 검사한 15개 함수(지금은 `exp`를 뺀 14개를 써요)는 ±0, ±inf, NaN에서 부호까지 정확해요 |

이 가운데 위치 독립성이 가장 중요해요. vForce는 SIMD로 여러 원소를 함께 계산하는데, 배열의 시작이나 끝, 남는 원소를 다른 코드로 처리해서 결과가 달라진다면 "같은 값이 배열 어디에 있느냐"에 따라 다른 비트가 나와요. 그러면 청크 경계를 정하는 방식에 결과가 달려요. 지금은 청크 경계가 스레드 수와 상관없지만, 위치에 독립인 함수는 어떤 분할에서도 같은 값을 내요. 테스트는 Python 스칼라(n = 1), 여러 오프셋, `[::3]`, 뒤집은 뷰, 전치(스택 버퍼로 모으는 경로)에서 비트가 같은지 확인해요. 스칼라 입력도 vForce를 n = 1로 부르는 것은 이 성질을 지키기 위해서예요.

### 특수값과 vForce를 쓰지 않는 함수

vForce의 `vvexpm1`, `vvlog1p`, `vvcos`, `vvtan`은 IEEE 754 / C99 Annex F의 특수값 의미론을 어겨요.

- vForce의 `cos(±0)`은 정확히 1이 아니에요.
- `expm1`, `log1p`, `tan`이 `-0`의 부호를 잃어요.
- `expm1`이 서브노멀 입력을 0으로 만들어요.

그래서 `expm1`, `log1p`, `cos`는 자체 NEON 커널로, `tan`은 libm으로 계산해요. 자체 커널은 레인이 맡지 않는 인자(넘침 구간, NaN, 정의역의 끝 등)를 libm에 넘겨 특수값을 C99 그대로 지켜요.

ULP 한계는 보통 값에 대한 것이고, 특수값에서 비트가 정확해야 한다는 것이 계약의 나머지 절반이에요. 그래서 이 넷은 vForce로 계산하면 계약을 지킬 수 없어요.

### `pow`: libm과 정확한 꼴

float64 `pow`(연산자 `**`)는 vForce의 `vvpow`가 아니라 libm의 `pow`를 원소마다 불러요. numpy도 같은 함수를 부르므로 보통의 지수에서는 numpy와 비트까지 같아요. libm을 쓰는 이유는 정확도예요. 무작위 400만 쌍에서 두 구현을 Arb[7]로 구한 올바르게 반올림한 값과 비교했어요. 밑 $x$는 $[10^{-300}, 10^{300}]$에서 로그 균등, 지수 $y$는 $[-50, 50]$에서 균등한 값·정수·정수 근처의 값이고, $\lvert y \log x \rvert$가 넘침과 서브노멀 경계 근처인 쌍도 넣었어요.

| 구현 | 올바르게 반올림되지 않은 원소 |
|---|:---:|
| libm `pow` | 0.014–1.2% |
| vForce `vvpow` | 2.6–26% |

(비율의 범위는 입력 분포마다 잰 값의 범위예요.) 위 계약 표의 참값 점에서 libm `pow`는 최대 1 ULP예요. 대가는 속도예요. 원소 $10^6$개의 `x ** 2.5`가 1스레드 5.0 ms(numpy 4.7 ms), 10스레드 0.55 ms예요. `vvpow`로 계산하면 4.0 ms, 0.45 ms예요.

지수가 2, 0, 1, −1, 0.5이면 libm을 부르지 않고 정확한 꼴로 계산해요. numpy가 스칼라 지수일 때 따로 처리하는 다섯 값과 같아요.

| 지수 | 계산 | 특수값 |
|:---:|---|---|
| 2 | `x * x` | |
| 0 ($-0$ 포함) | `1` | NaN에도 1 |
| 1 | `x` | |
| −1 | `1 / x` | ±0, ±inf, NaN에서 `pow`와 같아요 |
| 0.5 | `sqrt(x)` | `pow(-0, 0.5) = +0`, `pow(-inf, 0.5) = +inf` (`sqrt`는 $-0$과 NaN) |

모두 곱셈, 나눗셈, 제곱근 하나이거나 계산이 없어서 올바르게 반올림돼요. 특수값은 C99 `pow`의 규칙을 따라요[8]. libm `pow`는 이 지수에서도 올바르게 반올림되지 않는 원소가 있어서, 2, −1, 0.5에서 원소의 약 0.1%가 1 ULP 벗어나요. 지수가 스칼라든 배열이든 같은 규칙을 쓰므로 비트도 같아요. frame의 `**`도 같은 커널을 불러요([원소별 커널](/internals/array/elementwise/#float64-pow-libm과-정확한-꼴)).

그래서 numpy와 다른 곳이 둘 있어요.

1. 스칼라 지수 0.5에 $-0$과 $-\infty$가 들어올 때예요. numpy는 배열에 스칼라 0.5를 주면 `sqrt`를 그대로 써서 $-0$과 NaN을 내요. stardust는 C99 `pow`처럼 $+0$과 $+\infty$를 내요.
2. 지수가 배열일 때예요. numpy는 지수가 배열이면 이 다섯 값에서도 libm `pow`를 불러서, 2, −1, 0.5에서 원소의 약 0.1%가 1 ULP 달라요. stardust는 지수의 모양과 상관없이 정확한 꼴로 계산하므로, numpy에 스칼라 지수를 준 결과와 같아요.

```python
>>> import math
>>> import numpy as np
>>> import stardust as sd
>>> sd.asarray([-0.0, -math.inf, 4.0]) ** 0.5
array([0.0, inf, 2.0], dtype=float64)
>>> with np.errstate(invalid="ignore"):
...     print(repr(np.asarray([-0.0, -math.inf, 4.0]) ** 0.5))
array([-0., nan,  2.])
>>> v = 3.883186831326051e-98
>>> float(sd.pow(sd.asarray([v]), sd.asarray([2.0]))[0]) == v * v
True
>>> float(np.power(np.asarray([v]), np.asarray([2.0]))[0]) == v * v   # libm pow
False
```

## 집계: 순서를 바꾼 곳과 그 대가

### pairwise 합: numpy의 알고리즘, 넓은 잎

`sum`, `mean`, 그리고 형변환 없이 출력이 하나인 긴 합은 numpy의 `DOUBLE_pairwise_sum`/`CDOUBLE_pairwise_sum`(`numpy/_core/src/umath/loops_utils.h.src`)과 같은 알고리즘이고, 잎이 더 넓어요[3]. 정의는 `base/pairwise.hpp` 한 벌이고 linalg와 frame도 같은 정의를 써요([집계](/internals/array/reductions/)).

- $n < 16$이면 차례로 더해요.
- $n \le 512$이면 누산기 16개가 16칸 간격으로 원소를 맡아 독립적으로 더하고, 이웃끼리, 그 쌍끼리 고정된 트리로 합친 뒤 16의 배수를 넘는 나머지를 차례로 더해요. numpy는 누산기 8개, 잎 128개예요.
- 그보다 길면 반(16의 배수로 내림)으로 나눠 재귀해요.

원소가 $2^{16}$개 이상이면 4096원소 이하의 부분 트리를 잎으로 삼아 병렬로 계산하고, 같은 트리를 따라 합쳐요. 덧셈 하나하나가 직렬 계산과 같은 순서이므로 스레드 수가 몇이든 같은 비트예요. 테스트는 원소 300만 개에서 1스레드와 10스레드의 `sd.sum(x)`가 같은지 확인해요. 잎의 크기가 numpy와 달라서 numpy와는 마지막 비트가 다를 수 있어요.

이 순서의 오차 한계는 합 트리의 깊이로 정해져요. 어떤 덧셈 트리든 원소 $x_i$가 거치는 덧셈이 $h_i$번이면 계산한 합 $\hat{s}$는

$$
|\hat{s} - s| \;\le\; \sum_i \gamma_{h_i} |x_i| \;\le\; \gamma_h \sum_i |x_i|,
\qquad \gamma_h = \frac{h\,u}{1 - h\,u},\; u = 2^{-53}
$$

를 만족해요($h = \max_i h_i$)[1]. 차례로 더하면 $h = n - 1$이에요. stardust의 pairwise 트리에서 가장 긴 경로는 $n = 10^6$에서 $h \lesssim 60$이에요(재귀 11단계에, 512원소 잎 안에서 최대 49번). 그래서 한계가 $\gamma_{60} \approx 6.7 \times 10^{-15}$로, 차례로 더할 때의 $\gamma_{999999} \approx 1.1 \times 10^{-10}$보다 약 1.7만 배 작아요. 정규분포 원소 $10^7$개를 시드 4개로 재면 상대오차가 차례로 더할 때 $4.0 \times 10^{-16}$ ~ $2.9 \times 10^{-13}$, pairwise로 $1.3 \times 10^{-16}$ ~ $8.4 \times 10^{-16}$이에요.

### numpy와 순서가 다른 곳

결정성(같은 설정이면 실행마다 같은 비트)은 모든 경우에 지키고, 지금은 모든 경우가 스레드 수와도 상관없어요. 위의 넓은 잎 말고도 아래 경우는 numpy와 다른 순서로 더해요. numpy의 순서를 지키면 병렬로 나눌 수 없거나, 덧셈 하나가 앞 덧셈을 기다리는 사슬 하나에 묶여 느리기 때문이에요.

| 경우 | 더하는 순서 | 얻는 것 |
|---|---|---|
| 줄이는 축이 메모리상 바깥인 리덕션(C 순서의 `sum`/`mean`/`var`/`prod(axis=0)` 등) | 줄이는 축을 고정 개수(최대 16)의 블록으로 나눠 블록마다 접고, 블록 결과를 차례로 합침 | 1000×1000 `sum(axis=0)` 10스레드 32µs (numpy의 순서로는 나눌 수 없어 115µs) |
| float/complex `prod` | 4096원소 조각 안에 누산기 8개 | 1스레드 7.8배 |
| 8192원소 이상의 float/complex `cumulative_sum`/`cumulative_prod` | 4096원소 블록의 2단계 스캔 | 1스레드 1.4배, 10스레드 7배 |
| 형변환이 필요한 리덕션(`sum(x, dtype=float64)`, 바깥 축의 `mean(int64)` 등) | 4096원소 버퍼 단위로 접고, 전체 리덕션은 고정 블록으로 | 메모리 왕복 감소, 병렬화 |

블록 구조는 shape, 레이아웃, dtype만으로 정하고, 스레드가 하나여도 같은 블록 구조로 계산해요. 그래서 이 경우들은 1스레드에서도 numpy와 비트가 다를 수 있고, 대신 몇 스레드에서든 같은 비트가 나와요.

정수 결과(`sum(bool)`, 정수 합)는 순서와 무관하므로 이 경로에서도 numpy와 정확히 같아요. max/min, any/all도 같아요.

int64와 bool의 `mean`(전체와 안쪽 축)은 순서를 바꾸는 것이 아니라 계산이 달라요. 값을 정수 그대로 정확히 더한 뒤 한 번만 반올림해요. 합이 $2^{53}$을 넘지 않으면 numpy와 같고, 넘으면 stardust가 참값에 더 가까워요. `var`/`std`는 편차의 제곱을 `fma`로 더해 반올림이 하나 적어요([집계](/internals/array/reductions/)).

### 달라지는 크기: 오차 한계는 오히려 작아요

순서를 바꾸면 결과가 numpy와 달라지지만, 덧셈 사슬이 짧아지므로 오차 한계는 numpy보다 작거나 같아요.

- 블록 리덕션: 1000×1000 C 순서 행렬의 `sum(axis=0)`에서 numpy는 열마다 1000개를 차례로 더해요($h = 999$). stardust는 16개 블록(블록당 약 63행)으로 나눠 블록마다 차례로 더하고, 블록 결과 16개를 차례로 합쳐요($h \approx 62 + 16 = 78$). 정규분포 1000×1000에서 비교하면 결과 원소의 94%가 numpy와 비트가 다르고, 상대 차이의 최댓값은 입력에 따라 $10^{-13}$ ~ $10^{-12}$ 정도예요(시드 4개로 잰 값). 합이 0에 가까운 열일수록 상대 차이가 커져요.
- 누적 합: numpy의 $j$번째 출력은 $j$번 차례로 더한 값이라 $h = j$예요. stardust는 블록 안에서 차례로(최대 4095번), 블록 끝값으로 carry를 차례로(블록 수만큼), 마지막으로 carry를 한 번 더해요. $j = 10^6$이면 $h \approx 4095 + 244 + 1 = 4340$으로 numpy의 약 230분의 1이에요. 정규분포 10만 개에서 비교하면 원소의 95%가 numpy와 비트가 다르고, `math.fsum`으로 구한 정확한 누적 합과의 최대 차이는 stardust $6.8 \times 10^{-13}$, numpy $2.3 \times 10^{-12}$예요.

테스트는 이 경로를 조각·블록 경계 근처의 길이(0, 1, 7~9, 15~17, 4095~4097, 8191~8193, 16384~16385, 49169, 4만, 10만)에서 numpy와 상대오차 $10^{-12}$ 이내로 비교해요. 경계에서 한 칸씩 어긋나는 실수(off-by-one)가 가장 흔하기 때문이에요.

<Callout type="warn" title="prod는 마지막 비트에서 끝나지 않을 수 있어요">
곱하는 순서가 바뀌면 오버플로와 언더플로가 일어나는 시점도 바뀌어요. 그래서 numpy가 유한한 값을 낼 때 stardust가 `inf`나 `nan`을 낼 수 있고, 그 반대도 있어요. 예를 들어 `[1e200, 1e-200]`을 8번 반복한 16개의 `prod`는 numpy가 1.0, stardust가 `nan`이에요. numpy는 왼쪽부터 곱해 중간값이 1과 $10^{200}$ 사이를 오가요. stardust에서는 누산기 0이 짝수 번째 둘을 맡아 $10^{200} \cdot 10^{200} = \infty$, 누산기 1이 홀수 번째 둘을 맡아 $10^{-200} \cdot 10^{-200} = 0$이 되고, 합칠 때 $\infty \cdot 0 = \text{nan}$이에요. 넘쳤을 때 왼쪽부터 다시 계산하는 대안은 택하지 않아요. 넘침을 보고 경로를 바꾸면 데이터의 값에 따라 계산 순서가 달라지기 때문이에요. NaN 전파와 $\infty \cdot 0 = \text{nan}$ 규칙, 스레드 수와 무관한 결과는 그대로예요.
</Callout>

### 통계 함수

- 분위수와 `median`: 지금은 numpy와 비트까지 같아요. 값은 순서 통계량만 쓰는데, 순서 통계량은 고르는 방법과 상관없이 같아요. 위치와 보간 공식은 numpy 2.x 소스와 같아요(`_compute_virtual_index`, `_lerp`의 두 갈래, `np.around`의 짝수 반올림). 예외는 `-0.0`과 `+0.0`이 같은 순위에 섞인 경우예요. stardust는 전순서(`-0.0 < +0.0`)로 정하고, numpy의 introselect는 정해 두지 않아서 부호가 다를 수 있어요.
- NaN을 건너뛰는 리덕션: NaN이 없으면 이름 앞의 `nan`을 뗀 함수와 비트가 같아요. NaN이 있으면 "NaN을 중립값으로 바꾼 복사본의 리덕션"과 비트가 같아요(numpy의 정의 그대로예요).
- `cov`, `corrcoef`: 평균의 합 순서와 BLAS가 numpy와 달라서 비트는 같지 않아요. 테스트는 상대 $10^{-13}$으로 비교해요.
- `bincount`: 개수는 numpy와 같아요. 가중치 합은 원소가 $2^{15}$개 이상이고 결과 길이의 16배 이하이면 길이만으로 정한 16구간으로 나눠 병렬로 더하고, 구간 순서대로 합쳐요. 그래서 원소 순서대로 직렬로 더하는 numpy와 끝자리가 다를 수 있어요.
- `histogram`: 같은 너비 구간은 numpy처럼 65536개 블록마다 0.0부터 더해요. 경계 배열을 주고 가중치가 있으면, 블록마다 구간별 합을 원소 순서대로 더해요. numpy는 블록마다 정렬한 누적합의 차를 내서 블록 전체 크기만큼의 오차가 나고, stardust는 구간 자신의 합만큼의 오차라 더 정확해요. float 가중치는 numpy와 끝자리가 달라요.

자세한 내용은 [통계 함수](/internals/array/statistics/)에 있어요.

## 만들기: `arange`

`arange`의 float 원소는 `start + i*step`으로 계산해요(`csrc/array/ops/creation.cpp`). numpy는 처음 두 원소를 구한 뒤 `step`을 `(start + step) - start`로 다시 계산하고, 나머지 원소를 `start + i*delta`로 채워요(numpy의 `@NAME@_fill`, `numpy/_core/src/multiarray/arraytypes.c.src`)[4]. 다시 계산한 `delta`가 `step`과 다르면 그 차이가 $i$배로 쌓여요.

```python
>>> import numpy as np
>>> import stardust as sd
>>> (-3.3 + 0.37) - (-3.3)          # numpy가 다시 구한 step
0.3700000000000001
>>> float(sd.arange(-3.3, 7.1, 0.37)[9])
0.03000000000000025
>>> float(np.arange(-3.3, 7.1, 0.37)[9])
0.030000000000001137
```

참값은 $-3.3 + 9 \times 0.37 = 0.03$이에요. stardust의 오차는 $2.5 \times 10^{-16}$이에요. numpy는 다시 구한 step이 `0.37`의 float64보다 $1.1 \times 10^{-16}$ 크고, 이 차이가 9배로 쌓여 오차가 $1.1 \times 10^{-15}$예요. 결과가 0 근처라 ULP로 재면 256 ULP나 되지만, 절대 크기로는 step의 반올림 오차 몇 개 수준이에요. 다른 예로 `arange(0.1, 10, 0.3)`은 33개 중 30개가 최대 2 ULP 다르고, `arange(0, 1, 0.1)`은 10개 모두 같아요.

stardust는 원소마다 `start + i*step`의 곱셈 하나와 덧셈 하나로 반올림이 두 번뿐이라, step을 다시 구할 때 생기는 오차가 $i$배로 쌓이지 않아요. 원소 수는 양쪽 모두 $\lceil (\text{stop} - \text{start}) / \text{step} \rceil$이라 같아요. 정수 인자만 있으면 `__int128`로 정확히 계산하므로 numpy와 같아요. `linspace`는 numpy와 같은 식(`i*step + start`, 마지막 원소는 `stop`으로 고정)이라 지금은 비트까지 같아요. 다만 양 끝이 유한한데 `stop - start`가 float64를 넘으면 `step = stop / div - start / div`로 구해 모든 값이 유한해요(numpy는 여기서 `nan`과 `inf`를 내요).

## 행렬곱

- int64, bool: 정수 곱셈-덧셈은 wrap까지 포함해 결과가 하나로 정해지고, numpy도 wrap해요. 테스트는 비트까지 비교해요.
- float64, complex128: 합 순서는 Accelerate가 정해요. numpy 2.5.4도 같은 Accelerate를 쓰므로, 큰 행렬은 여러 크기, 전치, F 순서, 복사가 필요한 레이아웃, 행렬 × 벡터, 벡터 · 벡터에서 지금 비트까지 같아요. 예외는 곱셈-덧셈이 512개 이하인 2차원 float64 행렬 둘의 곱이에요. 이 곱은 BLAS를 부르지 않고 자체 커널이 원소마다 $p$ 순서로 FMA를 쌓아서, BLAS·numpy와 끝자리가 달라요(8×8 sweep의 최대 상대오차 $7.19 \times 10^{-15}$, $0.848\,u\cdot$조건수, 계약 안). numpy가 어떤 레이아웃에 어떤 BLAS 인자를 쓰는지는 stardust가 통제하지 못하므로 어느 쪽도 보장하지 않고, 테스트는 상대·절대 $10^{-12}$로 비교해요. 내적 하나의 오차 한계는 순서와 상관없이 $\gamma_k \sum_p |a_{ip}||b_{pj}|$예요[1].

자세한 내용은 [행렬곱](/internals/array/matmul/)에 있어요.

## 결정성

### 약속

같은 기계, 같은 스레드 수에서 같은 데이터, 같은 레이아웃이면 실행마다 같은 비트가 나와요. 이것이 약속이에요. 원자 연산이나 작업 가로채기(work stealing)의 순서에 기대는 합은 쓰지 않아요. 배열 영역은 지금 여기서 더 나아가 스레드 수와도 상관없는 비트를 내요. 그 이유인 규칙은 둘이에요.

1. 나누는 방법은 데이터 크기와 레이아웃으로만 정하고, 스레드 수를 보지 않아요. 블록 리덕션의 블록 수, pairwise 트리의 잎, 스캔 블록, 마스크 청크, 정렬 조각이 모두 길이와 shape에서 나와요.
2. 부분 결과는 고정된 순서로 합쳐요. 어느 스레드가 먼저 끝나든 합치는 순서는 같아요.

"스레드가 있을 때만 다른 경로"는 결과가 같다고 보장되는 경우에만 써요. 예를 들어 안정 정렬은 조각으로 나눠 정렬하고 병합해도 직렬 안정 정렬과 비트까지 같으므로, 풀을 쓸 수 있을 때만 조각 경로를 타요. 불안정 정렬은 조각 경계에 따라 결과(동점 인덱스의 순서)가 달라질 수 있어요. 그래서 int64와 float64는 `stable=False`여도 안정 알고리즘(기수 정렬, 짧은 float 값의 NEON 정렬과 0의 부호 복원)을 써서 결과가 안정 정렬과 같아요. 16개 이하의 짧은 레인은 모든 dtype이 정렬 네트워크로 정렬하고 같은 값이면 원래 인덱스 순이라, 이것도 안정 정렬의 결과예요. 불안정 정렬이 남는 긴 bool 레인의 `argsort(stable=False)`만은 스레드 수와 상관없이 언제나 조각으로 나눠 정렬해요. 연산 종류별 규칙은 [스레드풀과 결정성](/internals/core/threads/)에 있어요.

### "같은 레이아웃"이 붙는 이유

레이아웃은 결과를 바꿀 수 있어요. 같은 값을 담은 1000×1000 행렬이라도, C 순서이면 `sum(axis=0)`의 줄이는 축이 메모리상 바깥이라 블록 리덕션을 타고, F 순서이면 줄이는 축이 안쪽이라 열마다 pairwise 합을 타요. 두 결과를 비교하면 원소의 84%가 비트가 달라요.

레이아웃은 데이터의 일부로 봐요. 같은 레이아웃이면 몇 번을 다시 계산해도 같고, 지금은 몇 스레드로 계산해도 같아요. 레이아웃과 상관없는 비트는 약속하지 않아요.

### numpy를 정답지로

numpy를 **정답지**(oracle)로 써요. 무작위 shape, stride, dtype 조합을 만들어 numpy의 결과와 비교해요. numpy는 정답지 용도로만 설치해요. 비교 함수는 둘이에요(`tests/array/conftest.py`).

- `assert_same`: shape, dtype, 비트까지 같아야 해요. NaN은 어떤 NaN과도 같다고 보지만(NaN의 페이로드 비트는 보지 않아요) `-0.0`과 `+0.0`은 달라요. complex는 실수부와 허수부를 따로 비교해요. 결과는 버퍼 프로토콜로 복사 없이 numpy로 가져와요.
- `assert_ulp`: vForce 함수용이에요. 위의 $\kappa$로 numpy와의 ULP 거리를 재고, 주어진 허용치(`test_vforce.py`는 8 ULP)를 넘으면 실패해요. NaN 위치는 같아야 해요. 정확도 계약은 numpy가 아니라 Arb 참값으로 확인해요(`test_reference.py`).

numpy와 의미론을 일부러 다르게 한 곳은 기대값을 따로 정의해요. 정수 `% 0`(numpy는 경고와 함께 0, stardust는 경고 없이 `a % 0 == a`라서 `a == (a // b) * b + a % b`가 b = 0에서도 성립), bool 산술(int64로 계산), 정수의 음수 지수, 0차원 배열이 없는 것 등이에요. 이런 곳은 numpy가 아니라 Python 산술로 기대값을 만들어요.

버그를 막는 테스트는 고치기 전 빌드에서 실패해야 해요. 고친 뒤에 통과하는 것만으로는 그 테스트가 버그를 잡는다는 증거가 되지 않아요. 입력 패턴이 우연히 대칭이면(예: 길이 40000의 `[::3]`을 뒤집기) 고치기 전에도 통과할 수 있어서, 고치기 전 코드에서 한 번 돌려 실패하는 것을 확인해요.

### hypothesis 속성 테스트

hypothesis는 무작위 입력을 만들어 "어떤 입력에서도 성립해야 하는 성질"을 시험하고, 실패하면 입력을 가장 단순한 반례로 줄여 보여 주는 라이브러리예요[5]. 배열 영역에서는 아홉 파일에서 쓰고, 성질은 대부분 "numpy와 같은 결과"예요.

- 원소별: 무작위 dtype 둘, 무작위 shape(최대 3차원, 축 길이 4 이하), 무작위 뷰(뒤집기, 건너뛰기, 전치)와 브로드캐스팅을 섞어 `add`, `multiply`, `subtract`, `equal`, `maximum`, `divide`를 numpy와 비교해요. 레이아웃이 섞이면 이터레이터의 축 재정렬·합치기 경로가 모두 열려요.
- 리덕션: 무작위 shape(최대 4차원, 길이 0 포함), 무작위 axis(None, 정수, 튜플), `keepdims`에서 정수 `sum`, `prod`, `any`, `all`, `max`를 정확히 비교해요.
- NEON 접기: `0.0, -0.0, 1.0, 2.0, -3.0, inf, -inf, nan`에서 뽑은 길이 1~40의 리스트로 `argmax`, `argmin`, `max`, `min`을 비교해요. 동점, NaN, 부호 있는 0이 NEON 레인의 모든 자리에 떨어지게 하려는 거예요.
- 정렬: 작은 float64·int64 배열과 int64 전체 범위의 리스트로 정렬과 `unique`를 비교해요.
- 그 밖에 기본·고급 인덱싱, 뷰, `asarray`(중첩 리스트), 버퍼 프로토콜, `astype`도 같은 방식으로 시험해요.

### 골든 출력

**골든 출력**(`tests/golden/`, 도구 `tools/golden.py`)은 numpy가 아니라 stardust 자신이 기록해 둔 결과를 기준으로 해요. 고정된 입력에서 공개 함수의 결과를 기록해 두고, 바뀐 코드의 결과를 그것과 비트까지 비교해요. numpy 대조 테스트가 허용치로 넘어가는 경로까지 포함해서, 코드를 고칠 때 결과가 한 비트라도 바뀌면 드러나요.

- 사례: 배열은 10,557개(그중 2,321개는 에러가 나야 하는 사례)이고, `tests/golden/cases_array.py`에 `(이름, 인자 없는 함수)`로 적혀 있어요. 입력은 고정 리터럴과 시드를 준 난수로만 만들어요. 공개 이름은 모두 사례에 나오거나, 빼는 이유가 적혀 있어야 해요.
- 기록(`tests/golden/data/array.json`): 결과를 정확한 JSON으로 바꿔 저장해요. 형도 결과의 일부라 `True`와 `1`은 달라요. float는 16진 표기(`float.hex`)로, 원소가 1024개 이하인 배열은 원소마다, 그보다 큰 배열은 dtype, shape, strides, 바이트의 SHA-256, 조각마다의 해시, 정해진 표본 원소로 적어요. strides까지 적으므로 값이 같아도 결과 레이아웃이 바뀌면 불일치예요. 에러는 예외 종류와 메시지로 적어요.
- 스레드 수 검사: 모든 사례를 스레드 1, 3, 10에서 돌려 세 결과가 같아야 저장해요. 스레드 수에 따라 결과가 다른 사례는 기록을 거절해요. 배열 영역에는 그런 사례가 없어요.
- 비교: 같은 사례를 스레드 1, 3, 10에서 돌려 기록과 비교하고, 바뀐 사례마다 어느 원소가 몇 ULP 바뀌었는지 적어요. 결과를 일부러 바꾼 변경이면 바뀐 사례가 의도한 것뿐인지 본 뒤 다시 기록해요.

### 에러 메시지 테스트

`tests/test_error_messages.py`는 라이브러리 전체(배열, linalg, frame)의 에러 메시지 형식을 고정해요.

- 공개 함수와 메서드의 메시지는 `zeros(): negative dimensions are not allowed`처럼 자기 이름으로 시작해요. 같은 함수를 메서드로 불러도(`x.sum(axis=1.5)`) 같은 메시지예요.
- 연산자와 인덱싱은 `unsupported operand dtypes for <: complex128 and int64`처럼 Python의 형식을 지키고, `func(): `로 시작하면 안 돼요.
- 같은 실수에는 영역과 상관없이 같은 메시지가 나와요. bool 옵션에 다른 값을 주면 `sort()`든 `cholesky()`든 Series의 `sum()`이든 `'stable' must be True or False, not int` 형식이에요.
- 메시지에는 문서 절 번호(`§`)나 문서 이름이 들어가지 않아요.
- 퍼징도 해요. C++로 바인딩된 배열·linalg의 모든 공개 함수에, 인자 하나씩과 keyword 옵션 하나씩 틀린 값 10가지(`None`, 1, True, "a", 1.5, `[1]`, numpy 정수, numpy bool, `object()`, $2^{70}$)를 넣어 봐요. 어떤 메시지에도 nanobind의 시그니처 덤프("incompatible function arguments"), stardust 내부 모듈 경로(`stardust._core`), 줄바꿈이 나오면 안 돼요. 틀린 값마다 인자 이름을 말하는 검사에 닿아야 한다는 뜻이에요. numpy 타입은 공개 모듈을 붙인 이름(`not numpy.bool`, `not numpy.int64`)으로 보여요.

### API 표면 테스트

`tests/array/test_api_surface.py`는 API 문서를 계약으로 봐요. 문서의 시그니처 블록(언어 태그 없는 코드 블록)에서 이름을 읽어, 문서에 적힌 함수가 모두 있는지, 문서에 없는 이름을 `sd.__all__`로 내보내지 않는지 확인해요.

### 문서 참조 검사기

코드 주석은 설계 문서의 절을 번호로 가리켜요(예: "이 상수의 근거는 설계 문서의 어느 절"). 문서를 고치다 절 번호가 바뀌면 주석이 엉뚱한 절을 가리키게 돼요. `tools/check_refs.py`는 코드(`csrc`, `src`), 테스트, 도구, 설계·API 문서, 벤치 스크립트를 모두 훑어 `<문서> §N.M` 형식의 참조를 찾고, 그 문서에 그 번호의 제목이 실제로 있는지 확인해요. 짧은 이름(`array.md`)은 쓰인 위치에 따라 API 문서나 설계 문서로 해석해요. 코드에는 참조가 1,369개 있고, 깨진 것은 없어요.
