## 약속과 이 영역의 동작

라이브러리 전체의 약속은 같은 기계, 같은 스레드 수, 같은 입력이면 실행마다 같은 비트라는 것이에요. `sd.fft`는 그보다 세게 정해 둬요. **같은 입력이면 스레드 수, 배치의 모양, 메모리 레이아웃, Accelerate의 스레드 모드와 상관없이 같은 비트**예요.

이 약속의 단위는 줄이에요. 줄은 변환 축을 따라 놓인 원소들이고, 한 줄의 결과는 네 가지로만 정해져요.

1. 그 줄의 값
2. 변환의 종류(복소, 실수, DCT의 형 등)
3. 길이 $n$
4. 정규화 인자(`norm`)

줄이 어떤 배열의 몇 번째 행인지, 옆에 줄이 몇 개 있는지, 메모리에서 붙어 있는지 띄엄띄엄 있는지, 몇 번째 스레드가 계산했는지는 들어가지 않아요.

```python
>>> import stardust as sd
>>> F = sd.fft
>>> rng = sd.random.default_rng(3)
>>> X = rng.random((6, 1000)) + 1j * rng.random((6, 1000))
>>> Y = F.fft(X)
>>> Y[3].tolist() == F.fft(X[3]).tolist()
True
```

변환 축이 마지막이 아니어도, 줄이 한 칸씩 건너뛰어 놓여 있어도, 배열을 뒤집어 놓은 보기여도, 0을 채워 길이를 늘려도 같아요.

```python
>>> Y0 = F.fft(X, axis=0)
>>> all(Y0[:, j].tolist() == F.fft(X[:, j].copy()).tolist() for j in range(0, 1000, 97))
True
>>> X[:, ::2].strides, X.T.strides
((16000, 32), (16, 16000))
>>> F.fft(X[:, ::2])[2].tolist() == F.fft(X[2, ::2].copy()).tolist()
True
>>> F.fft(X.T, axis=0).T.tolist() == Y.tolist()
True
>>> F.fft(X.T, n=1024, axis=0)[:, 3].tolist() == F.fft(X[3], n=1024).tolist()
True
```

이 호출들은 구동기 안에서 서로 다른 실행 방식을 타요. `fft(X)`는 줄을 그 자리에서 읽고, `fft(X, axis=0)`과 띄엄띄엄한 보기는 두 줄을 한꺼번에 도는 두 줄 커널을, 0을 채우는 `n=1024`의 호출은 줄을 버퍼에 모았다 흩는 묶음을 써요. 그래도 결과가 같은 것은 세 방식이 줄에 하는 산술이 같기 때문이에요. 아래에서 그 근거를 하나씩 봐요.

## 길이마다 길이 하나

FFT는 알고리즘이 달라지면 끝자리가 달라져요. 혼합 기수, 4단계, Bluestein은 같은 변환을 다른 순서의 덧셈과 곱셈으로 계산하고, 반올림은 순서를 따라가요. 그러니 같은 길이가 어떤 때는 이 알고리즘, 어떤 때는 저 알고리즘으로 가면 한 줄의 비트가 상황에 따라 달라져요.

그래서 규칙이 이래요. **한 (종류, 길이)는 한 길로만 계산해요.** 길은 [구조](/internals/fft/overview/)의 표처럼 종류와 길이의 함수예요. 길을 고르는 데 쓰지 않는 것들이 중요해요.

- **값.** 허수부가 모두 0인 complex128 배열을 실수 길로 돌리지 않아요. 실수 길인지는 dtype이 정해요.
- **정렬과 간격.** 줄의 주소가 16바이트 경계에 있는지, 원소 사이가 몇 바이트인지는 산술에 들어가지 않아요. 띄엄띄엄한 줄은 같은 연산을 다른 순서로 메모리에서 읽을 뿐이에요.
- **배치의 크기.** 줄이 하나든 백만 개든 줄마다 같은 계획을 돌려요. 여러 줄을 한 번의 큰 변환으로 묶는 기법(예를 들어 실수 줄 둘을 복소 줄 하나의 실수부와 허수부로 실어 한 번에 변환하기)은 쓰지 않아요. 그러면 한 줄의 반올림이 짝이 된 줄의 값에 달려요.
- **스레드 수.** C++ 코드는 일을 나눌 때 스레드 수를 읽지 않아요.
- **실행 시간.** 계획을 만들 때 후보 알고리즘을 돌려 보고 빠른 것을 고르는 일이 없어요. 그런 선택은 그 순간의 기기 부하에 따라 달라져요.

dtype이 길을 정한다는 것은 눈으로 볼 수 있어요. 같은 값이라도 float64와 complex128은 다른 길을 타고 끝자리가 갈려요. 둘 다 정확도 계약 안이에요.

```python
>>> x = rng.random(1000)
>>> a, b = F.fft(x), F.fft(x + 0j)
>>> a.tolist() == b.tolist(), float(sd.max(sd.abs(a - b))) < 1e-12
(False, True)
```

레이아웃을 보고 고르는 것도 있어요. 구동기의 세 실행 방식(바로 읽기, 두 줄 커널, 묶음)이 그래요. 이것은 규칙의 예외가 아니에요. 세 방식은 같은 계획의 같은 나비를 같은 회전 인자로 돌리고, 다른 것은 값을 메모리에서 가져오고 내려놓는 순서뿐이에요. 복사는 값을 바꾸지 않아요.

한 길 안에서 반올림을 정하는 것도 모두 길이의 함수예요.

- 기수의 순서는 $n$의 소인수 분해에서 정해져요(4를 되는 대로, 남으면 2, 그다음 3, 5, 7, … 31).
- 회전 인자는 정수 $k$와 $n$에서 정확한 정수 연산으로 각을 접어 계산해요. 표의 값은 $k \bmod n$과 $n$만의 함수예요.
- 4단계의 분해 $n = n_1 n_2$는 $n_1$이 $\sqrt n$ 이하의 가장 큰 약수라는 규칙 하나로 정해져요.
- Bluestein의 안쪽 길이 $m$은 $2n - 1$ 이상인 가장 작은 $2^a 3^b 5^c$예요.
- 빌드는 컴파일러가 곱셈과 덧셈을 FMA로 합치지 못하게 꺼 두고, FMA를 쓸 자리는 코드에 직접 적어요. 그래서 같은 식이 인라인 여부에 따라 다른 반올림이 되는 일이 없어요.

## 홀수 길이의 꼬리

NEON 레지스터 하나에는 double이 둘 들어가요. 커널은 이웃한 두 자리를 한 레지스터에 실어 함께 계산하는데, 고리의 길이가 홀수면 마지막 자리 하나가 남아요. 여기서 흔한 방법은 남은 자리를 스칼라 코드로 따로 계산하는 것이에요. 그러면 같은 수식이 두 벌의 코드로 존재하게 되고, 컴파일러가 두 벌을 다르게 다루면 그 자리의 비트가 "짝이 있었느냐"에 따라 달라질 수 있어요.

이 영역의 커널은 남은 자리를 레지스터의 두 레인에 같은 값으로 넣어 같은 벡터 코드로 계산하고 첫 레인만 저장해요.

```cpp
// csrc/fft/cfft.hpp
template <bool Swap>
inline CV load_il1(const double* x) {  // one complex number in both lanes
    const V r = vld1q_dup_f64(x), i = vld1q_dup_f64(x + 1);
    return Swap ? CV{i, r} : CV{r, i};
}
```

NEON의 레인별 연산은 레인마다 독립이고 IEEE 754의 스칼라 연산과 같은 결과를 내요. 그러니 짝을 이뤄 계산된 자리와 혼자 계산된 자리가 같은 연산을 거치고, 한 자리의 결과는 옆 레인에 무엇이 있었는지와 무관해요. 두 줄 커널이 한 줄 커널과 같은 비트인 것도 같은 사실에서 나와요. 두 줄 커널은 레지스터의 두 레인에 두 줄의 같은 자리를 싣고, 한 줄 커널이 그 자리에 하는 연산을 그대로 해요.

## 스레드 수와 무관한 까닭

일을 나누는 곳이 넷이고, 넷 모두 나눈 조각이 서로의 반올림에 끼어들지 않아요.

| 나누는 곳 | 나누는 방법 | 결과가 같은 까닭 |
|---|---|---|
| 줄의 배치(1차원, 다차원의 각 패스) | 줄 수와 한 줄의 비용으로만 정한 줄 덩어리 | 한 줄은 한 태스크가 처음부터 끝까지 계산하고, 어디서든 같은 계획의 같은 연산이에요 |
| 긴 줄 하나($n \ge 2^{15}$) | 4단계의 열 묶음과 행 묶음(16개씩) | 분해가 $n$으로만 정해지고, 안쪽 변환들은 서로 독립이에요 |
| 긴 줄의 $O(n)$ 패스 | $2^{14}$칸씩 | 칸마다 따로 계산해요 |
| 한켈 변환의 계수 | 16개씩 | 계수는 색인마다 따로 계산해요 |

여기에 합치는 단계가 없다는 점이 중요해요. 스레드마다 부분합을 구해 마지막에 더하는 꼴의 계산은 나누는 수에 따라 덧셈 순서가 달라지는데, FFT의 병렬화에는 그런 합이 없어요. 태스크는 결과 배열의 서로 다른 칸을 쓸 뿐이에요.

4단계가 특히 그래요. 긴 줄을 나눠 푸는 방법은 스레드가 여럿일 때만 쓰고 싶어지지만, 그러면 1스레드의 결과와 10스레드의 결과가 다른 알고리즘에서 나와요. 그래서 $n \ge 2^{15}$인 줄은 스레드가 하나여도 같은 4단계를 같은 순서로 해요. 1스레드에서는 그 분해가 이득이 없거나 조금 손해인 길이가 있어요. 그만큼이 스레드 수와 무관한 비트를 얻는 값이에요.

```python
>>> def run():
...     out = []
...     r = sd.random.default_rng(5)
...     for shape, ax in (((1 << 16,), 0), ((65537,), 0), ((300, 1001), 1), ((257, 256), 0), ((40, 50, 60), 1)):
...         v = r.random(shape) + 1j * r.random(shape)
...         out.append(F.fft(v, axis=ax).tolist())
...     w = r.random((64, 4096))
...     out.extend([F.rfft(w).tolist(), F.dct(w).tolist(), F.fftn(w).tolist()])
...     return out
>>> n0 = sd.get_num_threads()
>>> res = []
>>> for t in (1, 3, 10):
...     sd.set_num_threads(t)
...     res.append(run())
>>> sd.set_num_threads(n0)
>>> res[0] == res[1] == res[2]
True
```

이 예에는 4단계($2^{16}$), 안쪽이 4단계인 Bluestein(65537), 기수 13이 든 혼합 기수의 배치, 마지막 축이 아닌 축의 패스, 실수 변환, DCT, 다차원 변환이 들어 있어요.

계획 캐시도 비트에 끼어들지 않아요. 계획은 (종류, 길이)의 함수라서 캐시에서 쫓겨난 뒤 다시 만들든, 두 스레드가 동시에 만들어 한쪽이 버려지든 같은 표가 나와요.

## vDSP를 쓰지 않는 까닭

macOS에는 Accelerate의 vDSP가 있고 그 안에 잘 다듬어진 DFT가 있어요. 선형대수 영역이 LAPACK을 Accelerate에 맡기는 것처럼 FFT도 맡길 수 있었지만, 이 영역은 모든 길이를 자체 C++로 계산하고 vDSP를 부르지 않아요. 까닭은 다섯이에요.

**받는 길이가 일부예요.** vDSP의 배정밀도 DFT는 복소 변환에서 $2^k$와 $f \cdot 2^k$($f = 3, 5, 15$) 꼴의 길이만 받고, 실수 변환도 같은 꼴만 받아요. 배정밀도 DCT는 없어요. 그러니 1000이나 1009 같은 길이를 위해 자체 변환은 어차피 있어야 하고, vDSP를 쓰면 길이에 따라 엔진이 둘로 갈려요. 그 자체는 규칙을 어기지 않지만(길이로만 고르니까요), 한쪽 엔진의 성질만으로 말할 수 있던 것들이 깨져요. 아래 넷이 그 성질이에요.

**오차 한계를 증명할 수 없어요.** 이 영역의 정확도 계약은 나비 하나하나의 반올림을 코드 그대로 따라가 얻은 한계예요([Stockham 혼합 기수](/internals/fft/stockham/)). vDSP는 소스가 닫혀 있어서 최악의 경우를 따질 방법이 없고, 그 길이들의 계약은 측정으로만 뒷받침하게 돼요. 모든 길이가 자체 길이면 모든 길이의 계약이 증명된 한계예요.

**메모리의 꼴이 달라요.** `sd.ndarray`의 complex128은 실수부와 허수부가 번갈아 놓인 꼴이에요. vDSP의 DFT는 실수부 배열과 허수부 배열을 따로 받는 꼴(split)에 간격 1을 요구해요. 그래서 부를 때마다 입력을 둘로 풀고 결과를 다시 엮는 패스가 앞뒤로 붙어요. 자체 커널은 그 풀기와 엮기를 첫 단의 읽기와 마지막 단의 쓰기에 합쳐서 따로 도는 패스가 없어요. 그래서 vDSP가 받는 여덟 가지 길이 꼴(복소와 실수 각각 $2^k$, $3 \cdot 2^k$, $5 \cdot 2^k$, $15 \cdot 2^k$)에서도 `sd.ndarray`를 받아 `sd.ndarray`를 내는 호출 전체로 보면 자체 길이 더 빨라요. 속도를 위해 vDSP를 부를 까닭이 없어요.

**역변환의 관계가 서지 않아요.** 자체 커널의 역변환은 정변환과 같은 산술을 실수부와 허수부만 바꿔서 돌려요. 그래서 `ifft`와 `fft` 사이의 관계가 비트로 성립해요(아래 절). vDSP에서는 이 관계가 길이에 따라 서기도 하고 안 서기도 해요. 2의 거듭제곱에서는 역변환이 정변환을 켤레로 감싼 것과 같은 비트지만 $3 \cdot 2^k$ 같은 길이에서는 아니에요.

**결과가 운영체제에 묶여요.** vDSP의 끝자리는 운영체제에 딸린 Accelerate가 정하고, 판이 바뀌어도 그대로라는 보장이 없어요. 자체 커널의 반올림은 이 저장소의 코드가 정해요. 덧붙여 2의 거듭제곱이 아닌 길이 꼴에서는 vDSP의 설정 객체가 자체 계획의 회전 인자 표보다 메모리를 더 써요.

vDSP가 비결정적이어서 쓰지 않는 것은 아니에요. vDSP의 DFT는 실행마다, 스레드마다, 입출력의 정렬을 바꿔도 같은 비트를 내고 안에서 스레드를 쓰지도 않아요. 쓰지 않는 까닭은 위의 다섯이에요. 저장소의 `csrc/fft/vdsp.hpp`는 vDSP를 감싼 헤더인데, 라이브러리에는 빌드되지 않고 두 길을 견주는 탐침 도구(`tools/fft_probe.py`)만 써요.

vDSP를 부르지 않고 BLAS도 부르지 않으니, `sd.fft`의 결과는 Accelerate의 스레드 모드(`VECLIB_MAXIMUM_THREADS`)와 무관해요.

## 비트로 지키는 관계

아래는 반올림 한계 안에서 "거의 같다"가 아니라 비트까지 같은 관계들이에요. 구현이 그 관계의 양쪽을 같은 연산으로 계산하기 때문에 성립해요.

### 정확한 것

- **길이 1의 변환**은 입력을 complex128로 옮긴 것 그대로예요. 정규화 인자도 1이에요.
- **2의 거듭제곱 배율**은 넘침과 언더플로가 없으면 정확히 옮겨져요. 덧셈, 곱셈, FMA가 모두 지수만 달라진 같은 연산이 되기 때문이에요.
- **정규화 인자가 2의 거듭제곱**이면(예를 들어 $n = 1024$의 `ifft`) 그 곱셈은 정확해요.

```python
>>> z = X[0]
>>> F.fft(2 * z).tolist() == (2 * F.fft(z)).tolist()
True
>>> F.fft(sd.asarray([3.5 - 2j])).tolist(), F.ifft(sd.asarray([3.5 - 2j]), norm="ortho").tolist()
([(3.5-2j)], [(3.5-2j)])
```

### 역변환은 실수부와 허수부를 바꾼 정변환

$\mathrm{swap}(a + bi) = b + ai$라고 하면 $\mathrm{swap}(z) = i\,\bar z$예요. 정변환을 $F$라고 할 때

$$
\mathrm{swap}(F(\mathrm{swap}(x)))_k = i\,\overline{\sum_j i\,\bar x_j\, e^{-2\pi i jk/n}} = i \cdot (-i) \sum_j x_j\, e^{+2\pi i jk/n} = \sum_j x_j\, e^{+2\pi i jk/n}
$$

이라서, 입력의 실수부와 허수부를 바꿔 정변환하고 결과를 다시 바꾸면 부호가 $+$인 변환이 돼요. 커널은 이것을 그대로 써요. 역변환은 첫 단이 읽을 때 두 부분을 바꾸고 마지막 단이 쓸 때 다시 바꿀 뿐, 가운데의 산술은 정변환과 한 글자도 다르지 않아요. 바꾸기는 복사라서 정확해요.

```python
>>> sw = lambda v: sd.imag(v) + 1j * sd.real(v)
>>> F.ifft(z, norm="forward").tolist() == sw(F.fft(sw(z))).tolist()
True
```

역변환용 회전 인자 표를 따로 두지 않아도 되고, 정변환에 대해 증명한 오차 한계가 역변환에도 그대로 서요.

### 실수 입력

실수 dtype의 `fft`는 실수 변환으로 앞쪽 $\lfloor n/2 \rfloor + 1$칸을 구하고 나머지를 $y_{n-k} = \overline{y_k}$로 채워요. 채우기는 부호 바꾸기라 정확해요. 그래서

- `rfft(x)`는 `fft(x)`의 앞쪽과 비트까지 같고,
- 스펙트럼의 에르미트 대칭이 정확하고,
- DC 칸의 허수부가 정확히 $+0$이에요.

```python
>>> F.rfft(x).tolist() == F.fft(x)[:501].tolist()
True
>>> f = F.fft(x)
>>> all(f[1000 - k] == f[k].conjugate() for k in range(1, 500))
True
```

복소 길로는 이 대칭이 반올림 크기로만 맞아요. 길이 4의 입력을 6으로 늘린 변환의 넷째 칸은 참값이 $-2$인데, 실수 길은 허수부가 정확히 0이고 복소 길은 반올림 찌꺼기가 남아요.

```python
>>> q = sd.asarray([1.0, 2.0, 3.0, 4.0])
>>> F.fft(q, n=6)[3], F.fft(q + 0j, n=6)[3]
((-2+0j), (-2+4.440892098500626e-16j))
```

그 밖의 실수·에르미트 쪽 관계는 이래요. $a'$는 방향을 바꾼 `norm`이에요(`'backward'`와 `'forward'`를 맞바꾸고 `'ortho'`는 그대로).

| 왼쪽 | 오른쪽 |
|---|---|
| 실수 `x`의 `ifft(x, norm=a')` | `conj(fft(x, norm=a))` |
| `ihfft(x, norm=a)` | `conj(rfft(x, norm=a'))` |
| `hfft(x, norm=a)` | `irfft(conj(x), norm=a')` |
| `irfft(x)` | 버리는 허수부(DC와 짝수 $n$의 나이퀴스트 칸)를 무엇으로 바꾸든 같은 결과 |

```python
>>> F.ifft(x, norm="forward").tolist() == sd.conj(F.fft(x)).tolist()
True
>>> h = F.rfft(x)
>>> F.ihfft(x).tolist() == sd.conj(F.rfft(x, norm="forward")).tolist()
True
>>> F.hfft(h, n=1000).tolist() == F.irfft(sd.conj(h), n=1000, norm="forward").tolist()
True
```

켤레는 정규화 인자를 곱한 뒤에 취해요. 부호 바꾸기가 정확해서 순서는 비트를 바꾸지 않아요.

### 다차원

- 축이 하나인 다차원 함수는 1차원 함수와 같아요.
- 정규화 인자가 1인 `fftn`(`'backward'`)과 `ifftn`(`'forward'`)은 1차원 변환을 `axes`의 뒤에서 앞으로 이은 것과 같아요([구조](/internals/fft/overview/)의 예).
- `rfftn(x)`는 실수 입력 `fftn(x)`의 마지막 축 앞쪽 $\lfloor n/2 \rfloor + 1$칸과 같아요.
- `hfftn`과 `ihfftn`은 켤레와 방향을 바꾼 `irfftn`, `rfftn`과 같아요.

```python
>>> W = rng.random((6, 10, 16))
>>> F.fftn(W, axes=(1,)).tolist() == F.fft(W, axis=1).tolist()
True
>>> F.rfftn(W).tolist() == F.fftn(W)[:, :, :9].tolist()
True
```

다차원의 정규화 인자는 마지막 패스가 한 번 곱해요. 그래서 인자가 1이 아닌 `ifftn`은 `ifft`를 이은 것(축마다 $1/n_i$를 곱해요)과 끝자리가 다를 수 있어요.

### 코사인·사인 변환과 도우미

- DST의 형 2, 3, 4는 부호를 바꾸고 뒤집은 입력의 같은 형 DCT와 같아요. 복소 입력의 `dct(x)`는 실수부와 허수부를 따로 변환한 것과 같아요([DCT와 DST](/internals/fft/dct-dst/)).
- `fftshift`와 `ifftshift`는 값을 옮기기만 해요. 배열의 `roll`과 같아요.
- 한켈 변환의 한 줄도 그 줄만 변환한 것과 같아요. 계획의 계수는 색인마다 따로 계산하니, 계획을 몇 스레드로 만들었는지도 상관없어요([FFTLog](/internals/fft/fftlog/)).

```python
>>> F.fftshift(W, axes=(1, 2)).tolist() == sd.roll(W, (5, 8), axis=(1, 2)).tolist()
True
```

## 약속하지 않는 것

- **다른 라이브러리와 같은 비트.** numpy나 scipy의 FFT와 값은 계약 안에서 같지만 끝자리는 달라요. 지금 비트까지 같은 것은 계산식이 같은 `fftfreq`, `rfftfreq`와 값을 옮기기만 하는 `fftshift`, `ifftshift`예요(약속은 아니에요).
- **NaN과 inf의 무늬.** 유한하지 않은 값이 든 입력은 IEEE 산술을 그대로 거친 결과를 내요. 어느 출력 칸이 NaN이 되고 어느 칸이 inf가 되는지는 계산 순서에 달려 있어 정해 두지 않았어요. 같은 기계, 같은 입력이면 그 무늬도 같은 비트예요.
- **다른 기계와 같은 비트.** 회전 인자는 시스템 수학 라이브러리의 사인·코사인에서 출발해요. 그 함수가 다른 값을 내는 환경에서는 표의 끝자리가 달라질 수 있어요. 약속의 범위는 라이브러리 전체와 같이 같은 기계까지예요.
- **길 사이의 같은 비트.** 같은 값을 float64로 주느냐 complex128로 주느냐, 길이를 1000으로 하느냐 0을 채워 1024로 하느냐에 따라 다른 길을 타요. 길이 다르면 끝자리가 다를 수 있어요.
