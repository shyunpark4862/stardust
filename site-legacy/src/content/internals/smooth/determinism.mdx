## 약속

라이브러리 전체의 약속은 같은 기계, 같은 스레드 수, 같은 입력이면 실행마다 같은 비트라는 것이에요. `sd.smooth`는 그보다 세게 정해 둬요. **같은 입력이면 스레드 수와 상관없이 같은 비트**예요. 테스트는 함수마다 1, 2, 3, 7, 10(또는 1, 3, 10)스레드에서 결과의 바이트를 견주고, 골든 기록도 1·3·10스레드에서 같아야 해요.

```python
>>> S = sd.smooth
>>> def run():
...     r = sd.random.default_rng(5)
...     x = 10 * r.random(5000)
...     y = sd.sin(x) + 0.3 * sd.stats.Normal().sample(5000, rng=r)
...     X = r.random((3000, 2))
...     yy = sd.sin(4 * X[:, 0]) + X[:, 1]
...     return [
...         S.lowess(x, y, frac=0.1).fittedvalues.tolist(),
...         S.loess(X, yy, span=0.1).fittedvalues.tolist(),
...         S.smoothing_spline(x, y).fittedvalues.tolist(),
...         S.kernel_regression(x[:1500], y[:1500], bw=0.2).fittedvalues.tolist(),
...         S.kde(X).pdf(X[:500]).tolist(),
...         S.kde(x).density().density.tolist(),
...         S.savgol_filter(r.random((2000, 300)), 31, 4, axis=0).tolist(),
...     ]
>>> n0 = sd.get_num_threads()
>>> res = []
>>> for t in (1, 3, 10):
...     sd.set_num_threads(t)
...     res.append(run())
>>> sd.set_num_threads(n0)
>>> [res[0][k] == res[1][k] == res[2][k] for k in range(7)]
[True, True, True, True, True, True, True]
```

이 호출들은 모두 병렬 경로를 타요. 그래도 결과가 같은 근거는 세 가지 규칙이에요.

## 규칙 1: 점 하나는 한 커널

평활의 일은 대부분 "평가점마다 독립인 계산"이에요. lowess·loess·핵 회귀의 국소 적합, KDE의 합, Savitzky–Golay의 내적이 그래요. 이 영역은 평가점 하나를 언제나 같은 함수 한 번으로 계산해요.

| 영역 | 점 하나의 계산 |
|---|---|
| `lowess` | `fit_line`(정렬된 창, tricube 모멘트, 닫힌 꼴 또는 다시 훑기) |
| `loess` | `fit_point`(창 모으기, 모멘트 Cholesky 또는 QR) |
| 핵 회귀 | `local_fit` 한두 번(한 점 뺀 적합과 갱신) |
| KDE | `value_at`(직접 합, 반사, 누적분포) |
| Savitzky–Golay | 출력 하나의 fma 사슬 |

그 함수 안의 연산은 자료와 평가점으로만 정해져요. 창의 왼쪽 끝은 평가점마다 이분 탐색으로 찾고(앞 점에서 이어 훑지 않아요), 합은 정렬된 자료의 순서로, 묶음은 더하는 점의 수로만 정해요. 그러니 이 점이 어느 태스크에 들었는지, 그 태스크에 점이 몇 개 있었는지가 값에 들어갈 자리가 없어요.

NEON 레인으로 둘씩 계산하는 곳도 같아요. 레인별 연산은 레인마다 독립이고 IEEE 754의 스칼라 연산과 같은 결과라서, 레인에 실린 값과 남은 한 점을 스칼라로 계산한 값이 같은 비트예요. 지수 함수도 배열 영역의 NEON 커널(`exp_lanes`)과 그 스칼라 짝(`exp1`)이 같은 비트를 내요. 빌드는 컴파일러가 곱셈과 덧셈을 FMA로 합치지 못하게 꺼 두고, FMA를 쓸 자리는 코드에 직접 적어요.

## 규칙 2: 합의 순서는 길이로만

점 여럿의 값을 하나로 모으는 합이 있는 곳(국소 모멘트, 가우스 합, 기준의 합, 대각합)은 순서를 길이로만 정해요.

- **가우스 합**(핵 회귀, KDE, 교차 검증): 64개 묶음 안은 누산기 넷($j \bmod 4$), 묶음끼리는 짝으로([핵 회귀](/internals/smooth/kernel-regression/)의 `tree_sum`). 여러 합을 함께 훑어도 각 합은 따로 훑은 것과 같은 비트예요.
- **lowess의 모멘트**: 네 점씩 두 레인 쌍, 남은 두 점, 마지막 한 점.
- **loess의 모멘트**: 두 레인으로 256점 묶음마다 모아 전체에 더해요.
- **기준과 대각합**(`df`, CV, AICc, $\delta_1$): 점마다의 항을 정렬 순서로 짝지어 더해요. 태스크는 항을 배열에 쓰기만 하고, 합은 모든 태스크가 끝난 뒤 한 번 해요.
- **$\delta_2$의 블록 Gram**: 블록 행마다 한 태스크가 더하고, 블록 행의 합은 차례로 더해요.

스레드마다 부분합을 구해 마지막에 더하는 꼴은 쓰지 않아요. 그 꼴은 나누는 수에 따라 덧셈 순서가 바뀌기 때문이에요.

## 규칙 3: 나눔은 크기로

태스크의 크기는 일의 양으로 정해요. 작업량이 float64 연산 $2^{15}$개 분량 이상이면 나누고 GIL을 놓아요(배열 영역의 기준). 태스크 하나는 약 $2^{17}$의 작업량이에요.

| 병렬 경로 | 나누는 방법 | 결과가 같은 까닭 |
|---|---|---|
| `lowess`·`loess`·핵 회귀의 적합과 `predict` | 평가점 조각 | 규칙 1 |
| 강건 반복의 잔차와 무게 | 차례 계산 | 원소별 계산, 중앙값은 정확한 순서통계량 |
| 띠 QR의 회전 | 나누지 않아요 | 한 호출이 한 사슬로 차례 계산 |
| 띠 QR의 오른쪽 변(배치의 열) | 같은 회전을 열마다 | 열마다 같은 연산 |
| $\lambda$·대역폭 찾기의 격자 | 격자점 묶음 | 격자점마다 독립인 풀이, 가장 작은 점은 값으로 골라요(동점 규칙 고정) |
| Brent·Nelder–Mead의 반복 | 차례(안쪽의 기준 계산이 나란해요) | 기준 값이 스레드와 무관 |
| CV·AICc의 기준 | 행 조각, 합은 짝 합 | 행마다 독립, 규칙 2 |
| KDE의 직접 합 | 평가점 조각 | 규칙 1 |
| 선형 구간화 | 점의 위치는 점 조각, 합은 격자 구간 | 격자점마다의 합이 정렬 순서 |
| KDE 자료의 기수 정렬 | 점 조각(단계마다 세기와 흩기) | 안정 정렬의 결과는 하나 |
| FFT 합성곱 | fft 영역의 구동기 | [fft의 결정성](/internals/fft/determinism/) |
| `savgol_filter` | 출력 행 묶음과 512열 묶음, 끝 맞춤은 줄 묶음 | 출력 하나가 그 창과 계수만의 함수 |
| KD 트리의 구성과 질의 | spatial | 거리와 색인의 전순서 |

나눔이 스레드 수를 읽는 곳도 있어요. 핵 회귀와 KDE는 태스크를 스레드마다 8개까지로 묶고(점 하나가 $2^{17}$을 넘는 큰 크기에서 태스크마다 작업 공간을 만드는 비용을 줄이려고), $\lambda$ 격자의 태스크는 스레드 수의 두 배까지예요. 이런 곳에서도 태스크 안의 계산은 규칙 1의 함수이고 합은 규칙 2라서, 나눔이 달라져도 값은 같아요. 바뀌는 것은 속도뿐이에요.

하나의 긴 띠 QR은 나누지 않아요. 영역을 나눠 푸는 병렬 띠 풀이는 반올림이 나눔에 따라 달라져요. 그래서 $n = 10^6$의 평활 스플라인 하나는 1스레드 시간이고, 대신 $\lambda$ 찾기의 격자 평가가 나란해요.

## 빠른 길과 느린 길

같은 양을 두 길로 계산할 수 있는 곳은 두 길이 **같은 정의의 같은 비트**를 내거나, 사용자가 이름으로 고르는 다른 함수예요. 길을 고르는 기준은 모양($n$, $m$, $p$)뿐이고 값이나 스레드 수가 아니에요.

| 두 길 | 고르는 기준 | 같은 비트인 까닭 |
|---|---|---|
| `loess` 여러 변수의 KD 트리 kNN과 모든 거리 훑기 | $32q \le n$ | 같은 거리 커널, $q$번째 거리는 값 하나, 창은 "거리 $\lt h$"를 색인 순서로 |
| 여러 변수 가우스 합의 KD 트리 후보와 모든 점 훑기 | KDE: $n \ge 4096$·평가점 16개 이상·자르기 반경이 좁을 때, 핵 회귀: $n \ge 2048$·국소 상수 | 후보가 남길 점을 모두 담고, 같은 규칙으로 걸러 같은 순서로 더해요 |
| 가우스 합의 조밀한 합과 성긴 합 | 남는 항이 $1/16$ 이상인지 | 잘린 항을 $+0$으로 두면 더해도 비트가 바뀌지 않아요 |
| lowess의 닫힌 꼴과 다시 훑기 | $\kappa_1 \gt 2^{20}$(자료로 정해짐) | 갈래가 자료의 함수라 스레드와 무관 |
| loess의 고친 Cholesky와 QR | 대각 비의 제곱 $\gt 2^{32}$(자료로 정해짐) | 같은 이유 |
| KDE의 직접 합과 구간화 FFT | 사용자(`density(binned=...)`) | 다른 함수예요. `pdf`는 언제나 직접 합 |

테스트는 내부 스위치로 두 길을 강제해 비트까지 견줘요(`loess`의 `path`, 가우스 합의 `kde_tree_mode`). 두 길의 비트가 같으니 문턱은 속도만 바꿔요.

## 입력 순서와 척도

스레드 수와 별도로, 이 영역의 몇 함수는 자료를 값으로 정렬해 쥐어서 **같은 점들을 다른 순서로 주면 같은 비트가 그 순서로** 나와요.

| 함수 | 정렬 열쇠 |
|---|---|
| `lowess` | $(x, y, \text{무게}, \text{색인})$ |
| `loess` | $(\text{나눈 좌표}\ldots, y, \text{무게}, \text{색인})$ |
| `kernel_regression` | 양수 무게 점의 $(\text{좌표}\ldots, y, \text{무게}, \text{색인})$ |
| `kde`와 대역폭 규칙 | 양수 무게 점의 $(\text{좌표}\ldots, \text{무게}, \text{색인})$(기수 정렬) |

$x$만으로 안정 정렬하면 같은 $x$의 점들이 입력 순서로 남아 합의 순서가 입력에 달려요. 열쇠에 값을 더 넣으면 마지막의 색인은 모든 값이 같은 점(서로 바꿔도 합이 같은 점)에서만 쓰여요. 스플라인 계열은 $x$만의 안정 정렬이에요. 서로 다른 $x$에서는 순서와 무관하지만, 같은 $x$의 묶음은 그 무게 평균을 입력 순서로 더하니 같은 $x$가 있는 자료를 섞어 주면 끝자리가 달라질 수 있어요. FITPACK 계열은 매듭 규칙이 자료의 순서에 기대서 정렬하지 않고 비감소 $x$를 요구해요.

```python
>>> rng = sd.random.default_rng(7)
>>> x = 10 * rng.random(300)
>>> y = sd.sin(x) + 0.3 * sd.stats.Normal().sample(300, rng=rng)
>>> p = rng.permutation(300)
>>> r = S.kernel_regression(x, y, bw=0.3)
>>> S.kernel_regression(x[p], y[p], bw=0.3).fittedvalues.tolist() == r.fittedvalues[p].tolist()
True
```

척도도 비슷해요. 대역폭 단위의 좌표를 $((x - x_0)\cdot sc)\cdot\mathit{inv}$로 구하고 찾기의 변수를 $\log(h/h_{\mathrm{ref}})$나 $\log(\lambda/\lambda_0)$처럼 척도 없는 꼴로 둔 까닭은, $x$에 2의 거듭제곱을 곱해도 모든 중간값이 같은 비트로 옮겨 가게 하려는 것이에요. 2의 거듭제곱을 곱하는 것은 정확하니까요.

```python
>>> a = S.kernel_regression(x, y)
>>> b = S.kernel_regression(x * 0.125, y)
>>> b.bw == a.bw * 0.125, b.fittedvalues.tolist() == a.fittedvalues.tolist()
(True, True)
```

## 다른 라이브러리와의 비트

scipy·statsmodels·R과 비트가 같다는 약속은 없어요. 합의 순서, 정렬, 지수의 계산이 다르니 끝자리가 다를 수 있고, 계약 안이라면 어느 쪽이 틀린 것이 아니에요. FITPACK 계열의 매듭은 시험한 모든 자료에서 지금은 scipy와 비트까지 같아요(약속은 아니에요). 매듭이 이산 결정이라 scipy와 같은 연산을 같은 순서로 하도록 옮긴 결과예요([FITPACK식 매듭 고르기](/internals/smooth/fitpack/)).
